# strength-in-numbers

Workout-logging + progress-tracking web app. Responsive web only for v1 (mobile-first, usable one-handed in a gym); native mobile is post-v1 but the API/domain layer is kept ready for it. Solo-developer project — keep process proportional, and cover frontend / JS-ecosystem concepts from first principles rather than assuming familiarity.

## Layout (pnpm workspaces, Node 22)

The root `.npmrc` pins `use-node-version=22.23.4`: every `pnpm` command in this repo runs on that
Node regardless of the shell's `node` (pnpm downloads it once). Use `pnpm run …` / `pnpm exec …`,
never `npx` — `npx prisma` fetches the latest Prisma instead of the repo's pinned one.

- `apps/api` — Fastify + Prisma + TypeScript backend (`@sin/api`)
- `packages/core` — framework-agnostic domain code (`@sin/core`); CI purity check forbids
  React / DOM / Node-only imports
- `apps/web` — Vite + React SPA (`@sin/web`): Auth0 PKCE, React-free API client, CSS-Modules
  design tokens (`src/ui/tokens.css` is the only place design values are written)
- `docs/` — see below

## How work is structured

- **Spec-driven.** Every component gets a `docs/specs/NN-slug.md` following the **12-section template** in `docs/specs/README.md`. Feature work splits into an API spec and a UI spec,
  API-first. Keep each spec to one work session.
- **`docs/DESIGN.md` is the source of truth.** If a spec or the code disagrees with it, update DESIGN.md so they stay consistent — don't let them drift.
- **TDD.** Every behavioral acceptance criterion has ≥1 test that names its number (`describe("AC7 — …")`). Infra/pipeline criteria are verified by CI, not unit tests. `apps/api/src/plugins/auth` and `apps/api/src/repositories/user` stay ≥90% line coverage.
- **Before a PR:** run `/security-review`, `/code-review`, and the `change-auditor` agent.

## Conventions & gotchas

- **Telemetry** (Spec 13.0): off unless `OTEL_*_EXPORTER` is set. Boot entry is `dist/main.js` (it starts telemetry before importing `server.js` — don't import Fastify from `telemetry/`). A new span attribute or metric attribute is exported only if added to `telemetry/allowlist.ts` / `telemetry/views.ts` with a test; never ids, paths, IPs, user agents or user input. Metric names in `METRIC_NAMES` are queried by `ops/grafana/` — rename both together. Business counters sit beside their log line (`workout_started`, `workout_finished`, `set_created`). Telemetry tests import the app dynamically *after* `startTestTelemetry()`.
- **Error contract** (RFC 9457 problem+json) must be registered on BOTH the root scope and the `/v1` child scope.
- **Finished-workout edits** (Spec 07.4 Phase A): set / workout-exercise writes and title/notes work on a finished workout. Every repository write runs inside `withWriteMode` (`apps/api/src/repositories/write-mode.ts`): the mode comes from the existing unlocked preflight; finished mode takes `lockUserRecords` FIRST, then the usual locks, then recomputes only the lineages the edit can affect (`@sin/core` `setChangeAffectsRecords`; a reorder only the moved card's root, and only if that lineage appears twice in the workout); a live write runs today's statements, and a finish landing mid-write restarts it once in finished mode (`assertStillLive`). `409 workout-finished` means only a re-finish; `409 workout-would-be-empty` guards the two deletes (any set type counts); a finished-mode working set must be complete (`422`); a finished-mode `completed_at` is `LEAST(GREATEST(now(), started_at), ended_at)` (NULL bounds in live mode). Write results carry `finishedEdit` for the `workout_edited` / `workout_edit_refused` log lines (Spec 09.4 adds the `edit` kinds `section_added`, `section_changed`, `section_removed`, `exercise_sectioned`). **Change Time (Phase B):** `PATCH /v1/workouts/{id}` takes `startedAt`, `tzOffsetMinutes` (only with `startedAt`) and `durationSeconds`; every time rule is `@sin/core` `resolveRetime` (the API wraps it as `retimeOrThrow`), and a `startedAt` equal to the stored one is no change. `local_date` / `tz_offset_minutes` are re-derived only when `startedAt` changes (`calendarFor`). A live workout's "took" is `planned_duration_s` (live-only CHECK; the finish clears it, and the client sends `endedAt = startedAt + plan`); a live Change Time never touches sets. A finished re-time shifts set times by Δ from the stored start (`shiftSetTimes`), any finished time change and every finish clamp them into `[started_at, ended_at]` (`clampSetTimes`), and only a start change recomputes records. Neither rewrites a set's `updated_at`. Migration `0012` is a manual release step before the code goes live.
- **Validation messages are static** (#57): every Zod issue message in `@sin/core` is fixed text or a module constant — never the parsed value, no `params`, no `reportInput` — because a `custom` message is returned verbatim in the 422 body. `packages/core/test/static-issue-messages.test.ts` probes every exported schema's message functions and scans every `message:` in `src/`. The API `err` serializer (`apps/api/src/logging.ts`) stubs Prisma, Zod and request-validation errors and masks path segments that aren't identifiers or indexes.
- **OpenAPI publication is opt-in** (#10): a public `/v1` route needs `config: { published: true, problems: [...] }` to appear in `/openapi.json`; anything else is hidden by default. `schema: { hide: true }` is now only the infra routes' opt-out from the response-schema check. Never set `config.swaggerTransform` (app assembly fails — it bypasses the gate).
- **CORS methods**: `CORS_METHODS` (`apps/api/src/plugins/cors-methods.ts`) is the only list of cross-origin methods; app assembly fails if a route uses one that isn't in it (`HEAD` excepted). A missing method makes the browser refuse the request, which the SPA can only report as "offline" — the 2026-10-11 routine-edit `PUT` bug. `app.inject` tests skip the preflight, so they never catch this on their own.
- **`/v1` caching** (#17/#18): `Cache-Control` is set only by the `/v1` cache policy (`apps/api/src/plugins/cache-policy.ts`) — `no-store` by default and on every error; a `GET` that serves an `ETag` declares `config: { httpCache: "revalidate" }` → `private, no-cache`. Never hand-set `Cache-Control` in a `/v1` handler, and no `Vary: Authorization` (`private` is the cross-user protection).
- **Catalog seed** (`apps/api/prisma/seed.ts` → `src/seed/`) is a manual release step after `migrate deploy`, NOT Prisma's `prisma.seed` hook. Append-only: never edit a live row's `name`/`modality` in `prisma/catalog/exercises.json` — retire the key and add a new one.
- **Prisma migrations** run as a release step, never on app boot. Additive / expand-only — never drop or rename a column in the same release as the code that stops using it.
- **`DATABASE_URL`**: `resolveDatabaseUrl` backfills `sslmode=require` + `sslaccept=strict` (server-cert + hostname verification) + `connection_limit=8` at runtime, and boot rejects libpq's `sslmode=verify-full` (Prisma silently downgrades it to `prefer`). The stored secret must carry `sslaccept=strict` itself because `prisma migrate deploy` reads the raw URL. For Neon, use the **direct** host (not `-pooler`) for `prisma migrate deploy`.
- **Docker**: the runtime stage generates the Prisma client explicitly (`@prisma/client` postinstall can't find the schema in a pnpm monorepo); base stage installs `openssl` + `ca-certificates` (`node:22-slim` omits them). Don't remove those lines.
- **Image + action pins** (#9): `Dockerfile`, `docker-compose.yml` and `apps/api/test/integration/postgres-image.ts` pin images as `name:patch-tag@sha256:…` (multi-arch *index* digest — never a per-platform one); `ci.yml` pins actions to commit SHAs. Bump via the Dependabot PR, or `docker buildx imagetools inspect <ref>` by hand; keep `postgres-image.ts` identical to compose (the `image-pins` unit test enforces it).
- **Fastify v5** wants `loggerInstance` (not `logger`) for a prebuilt pino; `buildApp` branches on the arg type.
- `describe.skipIf(cond)` still runs `beforeAll` when `cond` is wrong — guard setup too.
- Never use the word "dummy" (code, comments, config, docs) — use placeholder / test / fake / stub.
- **Web logout + user data** (Spec 06.0): `logoutAndClear()` (`apps/web/src/auth/logout.ts`) is the only place that calls Auth0 `logout` — a unit test fails if another source file builds `logoutParams`. Anything that persists per-user data in `localStorage` uses a `sin:<name>:` key prefix listed in `USER_DATA_KEY_PREFIXES` (`apps/web/src/storage/clearUserData.ts`) so logout clears it, and goes through the `StorageAdapter` in `apps/web/src/storage/storage.ts` — the Spec 04.0 AC7 source scan fails if any other non-test module names `localStorage` / `sessionStorage` (comments included). The delete confirmation's Sign out calls `logoutAndClear` via `useAuth0`, never `useSession` (that would restart a `useMe` fetch).
- **jsdom has no `<dialog>` `showModal()`/`close()`** — `apps/web/src/test/setup.ts` shims them (attribute toggle only). Real focus/Escape behavior needs a browser test.
- **Personal records** (Spec 07.0): `personal_record` is a rebuildable cache keyed on the exercise's lineage root (`COALESCE(forked_from_exercise_id, id)`). Every write goes through `recomputeRecordsForRoots` (finish, delete, `records:rebuild`), and every PR writer takes `lockUserRecords` (per-user advisory lock) as its FIRST statement, before any workout row lock — the recompute's INSERTs take FK `KEY SHARE` locks on other workouts' rows, so row-lock-first deadlocks (AC18). PR math lives only in `@sin/core` `records.ts` on integer milli-units; Spec 07.2's e1RM chart must reuse `estimate1rm`. Seven record types since Spec 05.3 (below).
- **Paginated lists** (Spec 07.1 §6.2): keyset, never offset; an opaque `v1.` cursor encoding the sort tuple with a unique tiebreaker; timestamps travel as Postgres-formatted UTC text with microseconds (`to_char(… AT TIME ZONE 'UTC', …US"Z"')`), never through a JS `Date`; a malformed cursor is a 422 on `cursor` before any query; `next: null` ends the list. Copy `apps/api/src/repositories/workout-cursor.ts`.
- **Rate limits** (Spec 05.2): every `/v1` write route declares `config: { writeGroup }` (app assembly fails without it); limits live only in `RATE_LIMITS` (`apps/api/src/plugins/rate-limit.ts`); a test that exceeds them passes `rateLimits: GENEROUS_LIMITS` / `limitsWith(...)` to `buildTestApp`. `config.skipRateLimit` is for the liveness/readiness probes only; `/openapi.json` is limited (L1 + its `ipBudget: "docs"` budget, AC17). The client address is `clientAddress()` — `CF-Connecting-IP` only when the socket is private/loopback (Render's own infrastructure), else the socket itself; Fastify has no `trustProxy` and `X-Forwarded-For` is never read. Never trust Cloudflare's IP ranges as proxies — WARP/Worker end users egress from them and could forge either header. Every request logs `client_ip`; re-run runbook D4.d after any hosting change. On Cloud Run, `CLIENT_IP_SOURCE=cloud-run` selects the Spec 15 rule (the right-most `X-Forwarded-For` entry, `CLOUD_RUN_XFF_HOPS` from the right, behind a non-public socket; `CF-Connecting-IP` never read); `render` (the default) is the Cloudflare rule — re-run D4.d (or Part F11 on Cloud Run) after any hosting change.
- **Routines** (Spec 09): routine writes are whole-document `PUT`s with unstable item ids; `supersetGroup` on a routine is normalised dense via `@sin/core` `normalizeSupersetGroups`, on a workout it is stored as sent (any 1–99, a group of one allowed). `targetRpe` converts to tenths in exactly one place (`rpeToTenths` / `tenthsToRpe`). Start-from-routine is `POST /v1/workouts { routineId }`: the copy runs inside the start transaction after the one-active insert, under `FOR SHARE` on the routine row, and snapshots the five targets, `supersetGroup` and the item's `notes` (D22); a replay never re-reads the routine. Migration `0009` is a manual release step before the code goes live (the new workout reads select `routine_name_snapshot`).
- **Routines UI** (Spec 10.0): routines live under the Workouts tab (`/app/workouts/routines/…`; the bare path redirects). The editor's draft is the pure, private `routineDraft` reducer — one `settle` pass keeps every superset a contiguous run of 2–8, and its `key`s never reach the server. Routine reads and writes are online-only with `networkMode: "always"` (no outbox, no stored draft); the start reuses `useBeginWorkout`, which keeps its key after success so a late tap replays it. Catalog sync drops retired exercises, so a routine item whose exercise is absent after a sync renders as "Removed exercise". `workout_started` carries `fromRoutine`. The item sheet has a quick line and a plan mode (Spec 10.2). Sections live in the draft (`DraftSection`, `sectionKey` on items); `settle` also keeps items in canonical section order and splits supersets at section boundaries (Spec 10.3).
- **Planned sets** (Spec 09.1): `routine_item_set` rows are the source of truth; `routine_item.target_sets/target_reps_*` are derived by the server on every write (`resolveItemPlan` → `@sin/core` `deriveTargets`) — never assign them by hand. A routine item takes `sets` OR the legacy quick fields, never both (key presence, `null`s included); legacy input expands into identical working rows (`expandQuickLine`), and a rep range with no set count stays rowless (O1). `workout_planned_set` is an immutable snapshot written only by the start copy (`INSERT … SELECT` joined on `position`, under the routine's `FOR SHARE`); a replay never re-reads the routine. Migration `0010` is a manual release step before the code goes live; if an old-code routine `PUT` ran in the window, re-run the guarded backfill (runbook). Routine write routes have a 128 KiB `bodyLimit`; SQL-side inserts use `gen_random_uuid()` (Postgres 16 has no `uuidv7()`).
- **Routines session side** (Spec 10.1): superset link / split / block-move rules live in `@sin/core` `supersets.ts` (the 10.0 editor delegates to them; `settle` stays on top). The session regroups with `planSessionChange` → a minimal ordered `PATCH /v1/workout-exercises/{id}` list (group patches first, position last; untouched groups keep their numbers; new runs take the smallest free 1–99), sent one at a time by `useRegroup` (online-only, no outbox, no Try again except a single-position move). Display: a bracket only on contiguous runs ≥ 2; "superset N" is the on-screen ordinal (`runOrdinals`), never the stored `supersetGroup`; both session screens go through `supersetRows`. `updateWorkoutExercise` has no `notes` parameter (Spec 09 D22). `workouts/` may import only `targetFormat`, `LinkToggle`, `SupersetBracket` (plus the existing `RoutinesSection`) from `routines/`. Response fields follow DESIGN §6's rollout convention (API one release first; no `.default(null)`).
- **Account lifecycle** (Spec 11): `DELETE /v1/account` only sets `deleted_at` (every `/v1` call then 403s via `resolveUser`); data is removed only by `account:purge --confirm` after ≥ `ACCOUNT_PURGE_GRACE_DAYS` (`@sin/core`), which takes `lockUserRecords` first and keeps the grace check inside the `DELETE`. A new user-owned table must cascade from `user` — the purge test discovers tables from `pg_constraint` and fails otherwise. The export composes the read DTOs through `routes/mappers.ts`; when a read DTO gains a field the export gains it for free, so never hand-map in the export. `GET /v1/account/export` has its own per-user budget (`config.userBudget: "export"`, `RATE_LIMITS.exportPerUser`).
- **Account lifecycle UI** (Spec 12): downloads go through `ApiClient.requestBlob` (token, 401 refresh, `ApiError`, `Retry-After`, filename from `Content-Disposition`) and `saveBlob` — never a bare `fetch` or an `<a href>` to the API; the export Blob is never parsed or stored. `useExportAccount` is called once in the Profile form and shared with the delete dialog. The delete result lives in the TanStack **mutation** cache (`["account","delete"]`, `gcTime: Infinity`) and `ProtectedLayout` renders `AccountDeletedConfirmation` instead of the app when it is set — so no provider can call `/v1` again; never `queryClient.clear()` there (it empties the mutation cache and reverts the gate). A `403 account-deleted` from any account call means 'done': invalidate `["me"]` and let the layout render `AccountDeleted` (the export awaits that refetch and stays quiet only if `meTookOver` — `me` itself 403s or 401s — else it shows its generic failure, BL-17); a `401` shows no notice (`onAuthLost` has started the logout). The grace days in copy come from `ACCOUNT_PURGE_GRACE_DAYS`; copy says 'at least', 'erase', never 'purge'. `ConfirmDialog` focuses Cancel explicitly; with `dismissible={false}` it ignores Escape and reopens itself on a native close (a second Escape), which the exercise Delete dialog sets while busy (Spec 12's delete keeps Escape working mid-request, AC18).
- **Planned sets UI** (Spec 10.2): the entry row is a draft, so the next planned set is *prefilled* into it, never stored — progress is positional (`exercise.sets.length` of the outbox-projected list picks `plannedSets[n]`; never `setNumber`, which is not dense), a planned field left null keeps today's copy-forward, and an edited draft is never overwritten by a re-seed (`seedDraft` in `setDraft.ts` is the one place a draft is built from the list; `EntryRow` re-seeds only an untouched draft when the count changes by any route but its own log). The routine editor's item is in quick mode (`plan: null`) or plan mode; the item sheet keeps its own state and commits once on Done (`setPlanned` + `setTargets`), the structural row operations are the pure functions in `planRows.ts`, and `toRoutineInput(draft, { modalityOf })` is the only place that picks the request form — exactly one of `sets` or the legacy quick-line keys, never `null`s beside `sets`, omitting fields the exercise's modality cannot carry. `targetLine(t, sets?)` shows the weight only when given the plan, and `supersetRows` passes each exercise's `plannedSets` on every screen (no per-screen option). The plan rows component is `PlanRowList.tsx` (a file named `PlanRows.tsx` would collide with `planRows.ts` on case-insensitive disks). Rolling 10.2 back and re-saving routines from the old editor flattens plans.
- **Routine sections UI** (Spec 10.3): `routineDraft` holds `sections` and a `sectionKey` per item; `settle` is the one place that keeps items loose-first / section-ordered and splits supersets at section boundaries, and `toRoutineInput` is the only place request keys (`s1…`) are minted — a section-free draft sends today's body. The session groups through `supersetRows` (runs break at section boundaries) then `sectionSegments`; a workout's section structure is seeded by the start copy, then the workout's own (Spec 09.4), and may hold a loose tail, so never compare `sectionId`s by hand. Session Move/link act on the card's segment (`planSessionChange` is fed the segment's slots; `useRegroup.run`'s `positionOffset` makes its position patches absolute). An exercise note is a `note` outbox op (`WorkoutClient.setExerciseNote`, coalescing, Finish waits for it); `WorkoutExercisePatch`/`useRegroup` still never carry `notes`.
- **Routine from text** (Spec 10.4): the reader is pure `@sin/core` (`readWorkoutText`, `buildImportPlan`; furniture lists are constants; notices are codes, messages static); the import session is in memory only (no storage key, no URL state) and `USER_DATA_KEY_PREFIXES` is unchanged; an imported item carries a placeholder exercise id that exists only in the draft and the session — `saveImport` creates the still-referenced pending exercises online-only and substitutes ids in the request body only; a retry reuses `created`; `ExerciseFields` is the one set of create-exercise inputs (`CreateExerciseForm` and the import's New card); `ExercisePicker allowCreate={false}` for any caller that must not create; the screens harness types the fixture `packages/core/test/fixtures/hiraya-2026-10-19.txt`. `RoutineEditor` takes an optional `initial` (`draft`, `notices`, `prepareBody`, awaited by Save before the routine write) and `PendingExercisesContext` lets `useExerciseLookup` answer for placeholders (`isNew`), so no other consumer changes. The import session also mirrors the import's own history entries in memory (`useImportHistory`, a cursor over location keys; never router state): Back to text goes Back when the paste screen is behind it, and Save leaves through `EditorStart.leaveTo`, which goes back to the first import entry and replaces it with the preview, so one Back returns to where the import began. Round 2 (AC42–AC54): a clock line may carry one icon (`11:08 →`), symbol-only icon lines are furniture anywhere but a short non-Latin word only beside the tab bar or a clock at a screenshot's top (a mid-text `4:00` opens no window, #168), the overlap compares `ocrKey`s (case kept except same-shape letters; headers compare without case via `headerKey`), and when a paste has header badges (`NO SCORE`, `REPS`…) the line above a badge (`CleanResult.tagged`) and the strict headers (`Workout: "X"`, the `HEADING_WORDS`) start sections, never a guessed generic title; the variant-label words are `VARIANT_WORDS` (never any line ending `:` — "For Time:" precedes real exercises; never `rx` — an `Rx` line is a note that keeps the run open). A name with no letter or digit keys as `written:<name>` (#169), never `""`. Round 3 (AC55–AC66): a clock may carry a glued digit, one letter or a leading icon (`3:524`, `3:52 A`, `€ 3:53`); the cellular status bar (`isStatusBarLine`: signal-bar tokens, a `NETWORK_NAMES` entry, a short tail), the trophy before and the score after `RESULTS (n)`, and slash-joined badges (`isBadgeLine`, `ROUNDS/REPS`) are furniture; `ocrKey` ignores apostrophes; a ` @ load` is the item's note (`splitLoad`); `L-H Sets` opens L sets; inside a non-Warmup section an un-bulleted counted line (reps, calories or a leading distance, never a time — `20 Minute Cap` stays a note) is a rowless exercise and consecutive ones are one `list` run, so one superset (owner ruling 2026-10-26). All three fixtures (`hiraya-2026-10-19.txt`, `-24.txt`, `-26.txt`) must keep reading as their example tests say.
- **Workout screen "now"** (Spec 17.1): one exercise is current (`chooseCurrent` / `advanceAfterLog` in `currentExercise.ts` are pure; `useCurrentExercise` holds only the lifter's choice, and `advanceFrom` never moves a lifter who already tapped elsewhere); collapsed rows come from `collapsedSummary`; the bottom `ActionBar` button (`LogBarButton`) is fed by the `logAction` store (published by the current `EntryRow`, which calls `onLogged` last and withdraws on unmount) and is the screen's one primary `Button`, one element across Log / Finish / Add modes, with the 600 ms double-tap window spanning a panel swap. Steppers (`stepper.ts`) step by the draft's weight unit (5 lb / 2.5 kg) in integer milli-units and dispatch the ordinary `edit` action, so they are edits like keystrokes. The component is `NumberStepper.tsx` (a `Stepper.tsx` would collide with `stepper.ts` on case-insensitive disks). End workout early and Finish share `confirmFinish`. Session tests reach controls through `src/test/sessionHelpers.ts` (`makeCurrent`, `logButton`, `optionsButton`, `finishButton`, `discardWorkout`). RPE is hidden, never stripped: the draft, `parseDraft`, DTOs and the export keep it, and a sheet that cannot show a value must not null it (`ItemSheet`, `SetEditSheet`). The rest timer (Phase C) is timestamp-based (`remainingSeconds(timer, now)` in `restTimer.ts`; `restAfterLog` decides start/clear and runs in `onLogged` before the advance guard), stored under `sin:workout:rest` by `restStore.ts` (zod-checked; 5 s future tolerance; the 900 s bound comes from `RoutineItemInputSchema`), ticked only by `useNow` in `SessionClock`, `RestReadout` and `RestLine`, cleared on finish, discard and gone beside the drafts, and has no sound, vibration or notification. The header's "Started …" label reads today from `useToday` (one re-render at local midnight and on becoming visible), which is not `useNow`; `useNow` keeps its three callers. The line's fill is a native `<progress>` (no inline style, CSP).
- **Edit past workouts** (Spec 18.0): the edit screen is a sibling of `ActiveSession`, never a mode of it. - **Keep screen on** (#108): `ActiveSession` calls `useKeepScreenAwake` (`features/workouts/useKeepScreenAwake.ts`), which holds a Screen Wake Lock while the workout screen is mounted and visible, asks again on every `visibilitychange` back to visible (the browser drops it when hidden), and stays quiet on a refusal or an unsupported browser. The preference is per device, on by default: `ui/keepAwake.ts` stores only `"off"` under `sin:pref:keep-awake` (not a user-data prefix, so logout keeps it), read once per workout-screen mount; Profile's `KeepAwakeSetting` is disabled with "Not available in this browser." where `navigator.wakeLock` is missing.
- **Front door** (Spec 17.3): `screens/FrontDoor.tsx` is the shared title card (the "Strength in Numbers" `h1` in two authored lines, the column, the hairline line style, the 48rem layout); its users are `Landing`, `ResumingSession` and `AuthError` (BL-20), which passes `decorativeName` so the name is an `aria-hidden` `<p>` and its own `h1` ("Couldn't sign you in.") sits in the line; Auth0's description shows verbatim as "Details: …", and Try again still goes to `/?signin`. `Landing` is one two-line sentence and one block primary `Button` calling `login()` with `returnTo`; it goes `busy` after the first tap and clears it on a `pageshow` with `persisted: true` (a back/forward-cache restore), makes no request and does not redirect, and `PublicEntry` alone decides which screen shows. `ResumingSession`'s `role="status"` is on its sentence, not the `main`. Copy and test ids (`landing`, `landing-login`, `resuming-session`, `auth-error`, `auth-error-detail`) are pinned by tests and the e2e helper finds the button by the name "Log in", so change them together. `FrontDoor.module.css` uses only `--color-text` / `--color-muted` / `--color-line` and the `--*-brand` / `--landing-column-*` tokens, plus `env(safe-area-inset-*)` on all four sides; the harness's `frontDoor` report fails the run on a layout violation. The name "Strength in Numbers" is also `<title>` and `AppShell`'s `APP_NAME`; export filenames keep the slug. A request-access or waitlist control is BL-19.
- **Production deploy** (Spec 15): `GET /healthz` returns `{ status, commit }` (`resolveCommit`: `SIN_COMMIT` baked in by the image's `GIT_COMMIT` build arg, else `RENDER_GIT_COMMIT`, else `"dev"`).
