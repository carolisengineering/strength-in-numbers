# Spec 05.2 — Rate Limiting & Per-User Write Limits (API)

**Status:** Implemented (2026-10-04). D14 recorded during implementation. The
§11 post-deploy proxy check is still pending (it needs a staging deploy).
**Last updated:** 2026-10-04
**Design refs:** DESIGN.md §8.2 ("Rate limiting at the API (Fastify plugin),
with Cloudflare in front once the custom domain lands; per-user quotas on write
endpoints"). Closes Spec 03.2's **D20** (advisory-lock connection-pool blast
radius) and **D21** (unbounded growth via create→delete cycling), carried
forward unresolved in Spec 05.0 §12 "Open", and answers the
`docs/specs/README.md` question "pull a minimal per-user create quota forward,
or record the gap?".

---

## 1. Purpose, scope & non-goals

Put three in-process limits in front of the API so that no single client — a
scripted abuser, or our own SPA with a retry bug — can monopolise the database
connection pool or grow the database without bound, while a real lifter
logging fast (including an outbox replay after a gym-basement dead zone) never
sees a `429`.

| # | Layer | Keyed by | Runs | Closes |
|---|---|---|---|---|
| L1 | Per-IP limit on all traffic | client IP | root `onRequest`, before auth | unauthenticated floods reaching JWT verification / JWKS fetch |
| L2 | Per-user write-rate limits, one budget per route group | `request.user.id` | `preParsing` on each write route | D21 (rate of growth) |
| L3 | Per-user in-flight write cap | `request.user.id` | `preHandler` acquire, `onSend` release (`onResponse` backstop) | D20 (pool monopolisation) |

### In scope

- `@fastify/rate-limit` (in-memory store) for L1 and L2; a small hand-written
  in-flight counter for L3.
- A `clientAddress()` helper (`CF-Connecting-IP` behind a known proxy, else
  the socket — §6.6, D12), so L1 keys on the real client
  and not on Render's proxy.
- A `RateLimitedError` (`429`, slug `rate-limited`) rendered through the
  existing problem+json contract, with a `Retry-After` header, documented on
  every `/v1` operation in OpenAPI.
- `Retry-After` exposed through CORS; the web API client parses it and the
  Spec 06.2 outbox waits at least that long before retrying.

### Non-goals

- **Long-window volume quotas** (N workouts / day). Owner decision during
  brainstorming (option B, 2026-10-04): short burst limits bound the growth
  *rate*; total volume per account is not capped. Residual risk accepted —
  D3.
- **A shared store** (Redis / Postgres). One Render instance; counters live in
  process memory and reset on restart. Spec 15 (AWS, multiple instances) owns
  the swap — D2.
- **Per-user limits on reads.** `GET`s get L1 only — D5.
- **Edge / CDN limiting** (Cloudflare). Arrives with the custom domain;
  out of scope here.
- **Metrics and alerting** on rejections. Spec 13 owns metrics; this spec
  emits a log event only (§9).
- **A runtime kill switch.** No env var disables limiting — D7.

## 2. Acceptance criteria

1. **AC1 — L1 per-IP limit.** More than `ip.max` requests from one client IP
   within one `ip.windowMs` window get `429 rate-limited` for the rest of that
   window, on any route except those listed in AC6.
2. **AC2 — L1 runs before auth.** A request rejected by L1 never reaches the
   token verifier (no JWT verification, no JWKS fetch) — including requests
   with no or an invalid `Authorization` header.
3. **AC3 — L2 per-user group limits.** For each group in §6.2, more than the
   group's `max` write requests from one user within one window get
   `429 rate-limited`. Requests on different routes in the same group share
   one counter.
4. **AC4 — L2 isolation.** Exhausting one group's budget does not affect the
   same user's other groups, and does not affect any other user.
5. **AC5 — reads are not per-user limited.** `GET` routes carry no L2 or L3
   limit; a user who has exhausted every write group can still `GET`.
6. **AC6 — exemptions.** `/healthz`, `/readyz` and `/openapi.json` are never
   counted or limited by any layer.
7. **AC7 — L3 in-flight cap.** When a user already has `inflight.max` write
   requests in progress, the next write request from that user gets
   `429 rate-limited` immediately (it is not queued) with `Retry-After: 1`.
8. **AC8 — L3 releases on every exit, and only when the work ends.** A slot is
   released exactly once when the request completes successfully or fails
   with any error status. A request the client aborts keeps its slot until
   its handler finishes, then releases it. After any mix of these, the
   user's in-flight count returns to 0 and the user's map entry is removed.
9. **AC9 — the `429` response.** Every rejection from L1, L2 or L3 is an RFC
   9457 problem+json body with `type` ending `rate-limited`, `status: 429`, a
   `detail` that names the retry delay but not the layer or group, the
   request's `instance`, and a `Retry-After` header holding a whole number of
   seconds ≥ 1. No `X-RateLimit-*` / `RateLimit-*` headers are sent on any
   response.
10. **AC10 — fail open.** If the limiter store throws, the request proceeds
    and an error is logged; the API does not return `5xx` because of the
    limiter.
11. **AC11 — proxy trust.** The L1 key resolves to the real client address
    behind Render and Cloudflare (`CF-Connecting-IP` when the socket is a known
    proxy), and nothing the client sends — a forged `X-Forwarded-For`, or a
    `CF-Connecting-IP` on a direct connection — can choose it, including from
    Cloudflare-owned client addresses (WARP, Workers).
12. **AC12 — CORS exposes `Retry-After`.** A cross-origin `429` from an
    allowlisted origin carries `Access-Control-Expose-Headers` including
    `Retry-After`.
13. **AC13 — OpenAPI documents `429`.** Every `/v1` operation in the emitted
    document lists a `429` problem response with type `rate-limited`, and the
    committed `openapi.json` matches (Spec 03.0 drift check).
14. **AC14 — web client honours `Retry-After`.** The web `ApiError` exposes
    the parsed `Retry-After` (in ms, or `null` when absent / unparsable), and
    the outbox schedules the retry of a `429`-rejected op no sooner than
    `max(backoffMs(attempt), retryAfterMs)`.
15. **AC15 — a real session never trips a limit.** Replaying 60 set creates
    back-to-back (the outbox's one-in-flight drain, §6.2) plus a workout start,
    6 add-exercise calls and a finish, all as one user, produces no `429`
    against a real Postgres.
16. **AC16 — rejection log.** Each rejection emits one `warn` log line
    `rate_limited` with `layer` (`ip` / `user-rate` / `user-inflight`),
    `group` (L2 only), and `userId` (L2/L3) or `ip` (L1); no request body, no
    token.

## 3. Dependencies & exposed interface

### Needs

- Spec 01: the auth plugin (`onRequest`, attaches `request.user`), the error
  contract (`AppError` → problem+json on root and `/v1` scopes), CORS config.
- Spec 03.0: the OpenAPI pipeline and `problem-responses.ts`'s
  `EVERY_V1_OPERATION` group; the `openapi.json` drift check.
- Spec 06.2: the outbox's `classify` / `backoffMs` and its one-op-in-flight
  drain (sets the burst shape L2's `sets` budget must absorb).
- New dependency: `@fastify/rate-limit` (the Fastify-5-compatible major,
  exact version pinned in the plan).

### Provides — stable surface

- The **`rate-limited` problem type** (`429`, `Retry-After`) on every `/v1`
  route. Clients treat it as retryable after `Retry-After`. Breaking to change
  the slug or drop the header.
- The **limits table** (§6.2) is *not* a stable surface: values may be tuned in
  any release without a spec amendment, as long as AC15 still passes.

## 4. Data model

None. No table, no migration. All counters are process memory.

## 5. API surface

No new endpoints. Every existing route gains the possible response below
(except the AC6 exemptions).

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 17

{
  "type": "https://strengthinnumbers.app/problems/rate-limited",
  "title": "Too many requests",
  "status": 429,
  "detail": "Too many requests — retry after 17 seconds.",
  "instance": "<request id>"
}
```

### New `AppError` subclass

`RateLimitedError` in `apps/api/src/errors/app-error.ts`: `slug =
"rate-limited"`, `status = 429`, `title = "Too many requests"`, constructed
as `new RateLimitedError(retryAfterSeconds = 1, source = { layer: "ip" })`
(defaults so the OpenAPI placeholder instance is constructible with no
arguments). `retryAfterSeconds` is clamped to an integer ≥ 1. `source`
(`{ layer: "ip" | "user-rate" | "user-inflight"; group?: string }`) is
internal — logged, never in the body. The error contract's error handler, on a
`RateLimitedError`, sets `Retry-After`, logs the AC16 `warn rate_limited` line
(instead of the generic `error` "request error" line), and renders the
problem. It joins `EVERY_V1_OPERATION` in `openapi/problem-responses.ts`, not
per-route `config.problems`.

## 6. Behavior & logic

### 6.1 Module layout

`apps/api/src/plugins/rate-limit.ts` owns all three layers and exports:

- `RATE_LIMITS` — the §6.2 table as one frozen constant.
- `registerRateLimits(app, config)` — registers `@fastify/rate-limit` with
  `global: false` (so it attaches **no hooks of its own** — D11), builds one
  `app.createRateLimit(...)` limiter for L1 and one per L2 group, adds the L1
  root `onRequest` hook, and returns `attachWriteLimits(v1)`, which the `/v1`
  scope calls before its routes register. That adds an `onRoute` hook: each
  route declares its group as `config: { writeGroup: "sets" }` next to
  `config.problems`, and the hook appends the L2 `preParsing` and L3
  `preHandler` hooks to it.
  It also adds the L3 release hooks.
- `buildApp` accepts an optional `rateLimits` override in `BuildAppDeps`
  (tests only; there is no env var — D7).
- Route opt-out for AC6 is `config: { skipRateLimit: true }`.

The `onRoute` hook **fails app assembly** if a `/v1` route whose method is
not `GET` / `HEAD` / `OPTIONS` declares no `writeGroup`, or if a `GET` route
declares one — the same structural style as Spec 03.0's
`assertRouteHasResponseSchema`, so a new write route can't ship unlimited.

### 6.2 Limits

Fixed one-minute windows. Groups share one counter across their routes.

| Layer | Group | Routes | Limit |
|---|---|---|---|
| L1 | `ip` | every route except AC6's | **600 / min** per IP |
| L2 | `sets` | `POST /v1/workout-exercises/{id}/sets`, `PATCH /v1/sets/{id}`, `DELETE /v1/sets/{id}` | **120 / min** per user |
| L2 | `workouts` | `POST /v1/workouts`, `PATCH`/`DELETE /v1/workouts/{id}`, `POST /v1/workouts/{id}/exercises`, `PATCH`/`DELETE /v1/workout-exercises/{id}` | **60 / min** per user |
| L2 | `exercises` | `POST /v1/exercises`, `PATCH /v1/exercises/{id}`, `POST /v1/exercises/{id}/fork`, `DELETE /v1/exercises/{id}` | **20 / min** per user |
| L2 | `me` | `PATCH /v1/me` | **10 / min** per user |
| L3 | `inflight` | every route in an L2 group | **4** concurrent per user |

Sizing:

- **`sets` 120/min.** The outbox drains one op at a time, oldest first, and
  sends the next as soon as the previous returns. A 60-set offline session
  replays in roughly 10–20 s at staging latency, so 120/min is about twice the
  worst realistic replay. Live logging is ~1 set / 30 s.
- **L1 600/min** is generous because a gym's shared Wi-Fi puts many users
  behind one NAT address, and every authenticated request also counts against
  L1.
- **L3 = 4** is half of the pool's `connection_limit=8`: room for the outbox
  drain plus a concurrent screen action plus headroom, while one account can
  never hold the whole pool.

### 6.3 L1 — per-IP

An app-level `onRequest` hook added on the **root** instance, before the
`/v1` scope registers. App-level hooks of a parent run before a child scope's
hooks, so it runs before the auth hook (AC2) — and it runs for unmatched
routes too, so a scanner probing random paths is counted. It skips when
`request.routeOptions.config.skipRateLimit === true` (AC6), calls the L1
limiter (`app.createRateLimit({ max, timeWindow, keyGenerator: (req) => req.ip
})`), and on `isExceeded` throws `RateLimitedError(ttlInSeconds)`, which the
error contract renders (§5).

`createRateLimit` returns the result and never throws on its own or sets a
header, so the plugin emits no `X-RateLimit-*` headers anywhere (AC9, D6). The
limiter call is wrapped in `try/catch`: on any error it logs
`rate_limiter_failed` at `error` and lets the request through (AC10, D8).

### 6.4 L2 — per-user groups

One `app.createRateLimit({ max, timeWindow, keyGenerator: (req) =>
req.user!.id })` limiter per group; `createRateLimit` gives each call its own
child store, so groups never share counters (AC4), and every route in a group
calls the same limiter, so they do share one (AC3). It runs in
`preParsing`: after the auth `onRequest` hook, so `request.user` is always set
(an unauthenticated write was already rejected `401` by auth), and **before**
the body is read, parsed or validated, so a write that fails any of those (bad
JSON, wrong media type, too large, schema-invalid) still counts — a later hook
would only see writes that got that far, leaving a malformed-body flood
unlimited per user (D14). Exceeded → throw
`RateLimitedError(ttlInSeconds)`; same `try/catch` fail-open as L1.

### 6.5 L3 — in-flight cap

```
Map<UserId, number>                  // only users with ≥1 write in flight
preHandler:   n = map.get(id) ?? 0
              if n >= max → throw RateLimitedError(1)       // AC7
              map.set(id, n + 1); request[ACQUIRED] = true
onSend (and onResponse, as a backstop):
              if !request[ACQUIRED] return                  // never acquired
              request[ACQUIRED] = false                     // release once
              n = map.get(id) - 1
              n <= 0 ? map.delete(id) : map.set(id, n)
              if n < 0 → log.warn("inflight_underflow")      // can't happen; tripwire
```

- L3's `preHandler` runs **after** L2's `preParsing` and after body parsing
  and validation, so a request rejected by L2 or by validation never takes a slot —
  only work that reaches a handler holds one.
- **Release on `onSend`, not `onResponse` / `onRequestAbort` (D13).** Probed
  on Fastify 5.12.1 (2026-10-04): when the client aborts while the handler is
  running, the raw response's `close` fires at once, `onSend` fires when the
  handler finishes, and **neither `onResponse` nor `onRequestAbort` fires**. So
  `onResponse` alone would leak the slot forever, and releasing on the raw
  `close` would free it while the handler still holds a pooled connection —
  letting an open-then-abort loop exceed the cap. `onSend` fires on every reply
  the handler or error handler sends, after the work is done.
  `onResponse` is also wired, made harmless by the per-request flag.
- Memory is bounded by the number of users with a write currently in
  flight.

### 6.6 Proxy trust

Fastify has **no `trustProxy`**: `req.ip` is the socket and no
`X-Forwarded-*` header is trusted anywhere. The L1 key and the L1 rejection
log use `clientAddress(request)` (`plugins/rate-limit.ts`):

- If the socket is a **known proxy** — private / loopback / RFC 6598 shared
  (Render's internal hops) or in **Cloudflare's published ranges** (an edge) —
  the request came through Cloudflare, which sets `CF-Connecting-IP` to the
  address that connected to it, **overwriting anything the client sent**. That
  value (if it parses as an IP) is the client.
- Otherwise the socket itself is the client (a direct peer), and any header it
  sent is ignored.

`X-Forwarded-For` is deliberately not walked (D12): Cloudflare's ranges also
carry end-user traffic (WARP, Workers), so trusting them as hops let such a
client prepend a forged entry and choose its key. AC11's unit tests cover the
staging chains, an IPv6 edge, a direct public peer, a garbage header and the
WARP/Worker spoof end to end. Every request's log bindings carry `client_ip`
(set in the L1 hook before the health-route skip), which is what the
post-deploy check (§11, runbook D4.d) reads.

Tripwire: in production, the first request that **carried
`X-Forwarded-For`** (i.e. came through some forwarding proxy) but breaks the
Cloudflare assumption — a known-proxy socket with no usable `CF-Connecting-IP`
(`reason: "no-cf-connecting-ip"`) or an unknown public socket
(`reason: "unknown-proxy"`, e.g. Spec 15's AWS load balancer) — logs one
`warn` `trust_proxy_suspect` (then stays silent), so the change shows up in the
logs instead of silently collapsing every user into one L1 bucket. Requests
without the header (internal probes, health checks, direct clients) never
count, so they can't spend the one warning.

### 6.7 Web client

- `apps/web/src/api/problem.ts`: `ApiError` gains `retryAfterMs: number |
  null`, parsed from `Retry-After` as delta-seconds only (an HTTP-date or
  garbage → `null`), capped at 5 minutes.
- `apps/web/src/features/workouts/outbox/outbox.ts`: on a `retry` verdict for
  an `ApiError` with `retryAfterMs`, `nextAttemptAt = now + max(backoffMs,
  retryAfterMs)`. No other client change; `classify` already maps `429` →
  `retry`.

## 7. Security & privacy

- **Authorization boundary.** L2/L3 key on `request.user.id`, the internal id
  resolved by auth, never on a client-supplied value. L1 keys on
  `clientAddress()` — Cloudflare's `CF-Connecting-IP` behind a known proxy,
  else the socket (AC11, §6.6).
- **Information leak.** The `429` body does not name the layer, group, limit
  or remaining budget, and no rate-limit headers are sent (D6), so a script
  cannot read the budgets off responses.
- **IP addresses in logs.** An IP is personal data under GDPR. It is logged
  **only** on an L1 rejection (AC16), for abuse investigation (legitimate
  interest), under the same Render log retention as every other log line. L2
  and L3 rejections log the user id instead.
- **Residual risks (accepted).**
  - Counters reset on restart / deploy, giving a script a fresh window. Low
    value to an attacker; restarts are infrequent.
  - Total volume per account is uncapped (D3).
  - A NAT'd gym shares one L1 bucket; 600/min is sized for it, and L1 is not
    the per-user control.
  - Distributed (many-IP) unauthenticated floods are not stopped by L1; that is
    the edge's job (Cloudflare, later).

## 8. Config & secrets

No new env vars or secrets. Limits are code constants (§6.2); the only
override is the test-only `rateLimits` dep on `buildApp`. Fastify has no
`trustProxy`; the client address comes from `clientAddress()` in
`plugins/rate-limit.ts` (§6.6). The Cloudflare range list there is a code
constant, re-checked when the D4.d post-deploy check fails.

## 9. Observability

- `warn` `rate_limited` per rejection — AC16.
- `warn` `trust_proxy_suspect`, once per process — §6.6.
- `warn` `inflight_underflow` — §6.5 tripwire.
- `error` `rate_limiter_failed` when a limiter call throws (AC10) — §6.3.
- No metrics. Spec 13 can turn `rate_limited` into a counter.

## 11. Deployment & rollback

- Ships with the normal merge to `main` (staging auto-deploy). No migration,
  no seed, no release step.
- **After the first staging deploy:** the §6.6 check —
  `curl -H 'X-Forwarded-For: 203.0.113.9' https://si-api-ft2f.onrender.com/healthz`,
  then the Render log's `incoming request` line must show the sender's real
  public IP as `remoteAddress`, not `203.0.113.9` and not a `10.x` / Cloudflare
  address. If it doesn't, revert and re-pin.
- **After deploy:** the post-deploy API smoke and (once its secrets exist)
  the Spec 06.3 browser smoke must stay green — they are a real session and
  must not trip a limit.
- **Rollback:** revert the merge commit. No data to back out.

## 12. Decisions & open questions

- ✅ **D1 — three layers (IP / per-user rate / per-user in-flight).** A rate
  limit alone does not close D20: D20 is about *concurrency*, and 60/min still
  allows 8 simultaneous requests. L3 caps concurrency directly.
- ✅ **D2 — in-memory store.** One Render instance. A Postgres-backed store
  would add a round trip per request on the same 8-connection pool D20 is
  about. Spec 15 (multiple instances) swaps in a shared store (Redis /
  ElastiCache) through the plugin's store option; L3's map moves with it or
  becomes per-instance with `max` divided by instance count.
- ✅ **D3 — no long-window volume quotas.** Owner decision, 2026-10-04. D21
  becomes "bounded growth rate" (≤ ~120 sets / min / account), not "bounded
  volume". Accepted; if it ever matters, the clean-up is the one-off purge job
  03.2 D21 already describes.
- ✅ **D4 — `@fastify/rate-limit` over a hand-rolled limiter.** Official,
  maintained, handles windows / keys / `Retry-After`; L3 is hand-written
  because the plugin counts requests per window, not requests in flight.
- ✅ **D5 — reads are L1-only.** Reads are cheap, the catalog sync is
  `ETag`-conditional, and no read path takes an advisory lock. Revisit if read
  abuse appears.
- ✅ **D6 — no rate-limit headers except `Retry-After`.** No client needs the
  remaining budget; publishing it helps a script pace itself to the limit.
- ✅ **D7 — no kill switch.** An env var that disables limiting is a
  production bypass flag. Rollback is a revert.
- ✅ **D8 — fail open.** The limiter is protection, not correctness; a limiter
  bug must not take the API down.
- ✅ **D9 — IPs logged plainly, only on L1 rejection.** No hashing precedent
  exists in the codebase; truncation would defeat abuse investigation, which
  is the only reason to log it.
- ✅ **D10 — the `Retry-After` client change ships here,** not in a UI spec:
  a few lines in `problem.ts` and `outbox.ts` that only matter because this
  spec starts sending the header.

- ✅ **D11** (implementation planning, 2026-10-04) — **use the plugin's
  store and `createRateLimit`, not its hooks.** Reading `@fastify/rate-limit`
  11.2.0's source: (a) its `global` / `config.rateLimit` hooks attach at the
  *route* level, and route-level `onRequest` hooks run *after* the `/v1`
  scope's app-level auth hook — that would break AC2; (b) every handler it
  creates shares one per-request "already ran" flag, so an L2 handler on a
  route already limited by L1 returns without counting — that would break AC3.
  `createRateLimit` returns `{ isExceeded, ttlInSeconds, … }` from a per-call
  child store and never throws or sets headers, so our own hooks keep full
  control of ordering, the `429` body and headers. D4's choice of the plugin
  stands (its fixed-window LRU store and the Spec 15 store swap).
- ✅ **D12** (implementation planning, 2026-10-04) — **`trustProxy: 2`,**
  from Render's documented Cloudflare → Render-proxy chain rather than a
  pre-merge staging probe (staging only deploys from `main`), confirmed by the
  §11 post-deploy check. `True-Client-IP` / `CF-Connecting-IP` were not used:
  they would make the key depend on a header whose trust rests on the same
  chain, with no gain over the hop count. **Amended in implementation
  (2026-10-04):** Fastify 5.12 ignores a numeric `trustProxy` (it fails closed,
  because a bare count can't check the immediate peer), so the two hops are
  expressed as the `trustRenderProxy` function — private socket, then one more
  hop — which also rejects forwarding headers from a public peer.
  **Amended after deploy (2026-10-04, runbook D4.d):** the post-deploy check
  logged `remoteAddress` = a Cloudflare edge (`104.22.64.33`), and the tripwire
  had fired on a `127.0.0.1` request with no header — Render's real chain is
  not "private socket + one hop" (either the socket is the Cloudflare edge, or a
  loopback sidecar sits in front of the Render proxy). A first fix trusted
  private and Cloudflare-published addresses at any hop; `/code-review` and a
  security pass showed that lets a client on a Cloudflare-owned address (WARP,
  Workers) prepend a forged `X-Forwarded-For` entry and choose its L1 key.
  **Final form (2026-10-04, superseding the earlier rejection of
  `CF-Connecting-IP` above):** Fastify has no `trustProxy`; `clientAddress()`
  uses `CF-Connecting-IP` — which Cloudflare overwrites on every proxied
  request — only when the socket is Render-internal or a Cloudflare edge, else
  the socket. `X-Forwarded-For` is never read. The Cloudflare range list in
  code now only decides "did this come through Cloudflare?", not which
  address is the client. The tripwire counts only forwarded requests
  (`no-cf-connecting-ip` / `unknown-proxy`), so header-less internal probes
  can't spend it. Every request logs `client_ip` for the D4.d check.

- ✅ **D13** (implementation planning, 2026-10-04) — **L3 releases on
  `onSend`** (with an idempotent `onResponse` backstop), not on `onResponse` /
  `onRequestAbort` as first drafted — see §6.5 for the probe that found
  neither fires after a mid-handler client abort.

- ✅ **D14** (implementation, 2026-10-04) — **L2 runs in `preParsing`, not
  `preHandler`.** Found by the AC3/AC4 tests: Fastify validates the body before
  `preHandler`, so a write with an invalid body returned `422` without ever
  counting. First moved to `preValidation`; `/code-review` then showed the body
  is *parsed* before `preValidation`, so unparsable JSON / 413 / 415 still
  escaped — moved to `preParsing`. Every authenticated write attempt now counts
  against its group; L3 stays in `preHandler` (§6.5). L3 releases are attached
  per write route, not scope-wide.
