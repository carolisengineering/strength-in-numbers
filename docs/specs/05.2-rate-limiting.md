# Spec 05.2 — Rate Limiting & Per-User Write Limits (API)

**Status:** Draft (2026-10-04)
**Last updated:** 2026-10-04
**Design refs:** DESIGN.md §8.2 ("Rate limiting at the API (Fastify plugin),
with Cloudflare in front once the custom domain lands; per-user quotas on write
endpoints"). Closes Spec 03.2's **D20** (advisory-lock connection-pool blast
radius) and **D21** (unbounded growth via create→delete cycling), carried
forward unresolved in Spec 05.0 §12 "Open", and answers the
`docs/specs/README.md` question "pull a minimal per-user create quota forward,
or record the gap?".

---

## 1. Purpose, scope & non-goals

Put three in-process limits in front of the API so that no single client — a
scripted abuser, or our own SPA with a retry bug — can monopolise the database
connection pool or grow the database without bound, while a real lifter
logging fast (including an outbox replay after a gym-basement dead zone) never
sees a `429`.

| # | Layer | Keyed by | Runs | Closes |
|---|---|---|---|---|
| L1 | Per-IP limit on all traffic | client IP | root `onRequest`, before auth | unauthenticated floods reaching JWT verification / JWKS fetch |
| L2 | Per-user write-rate limits, one budget per route group | `request.user.id` | `preHandler` on each write route | D21 (rate of growth) |
| L3 | Per-user in-flight write cap | `request.user.id` | `preHandler` acquire, `onResponse` / `onRequestAbort` release | D20 (pool monopolisation) |

### In scope

- `@fastify/rate-limit` (in-memory store) for L1 and L2; a small hand-written
  in-flight counter for L3.
- `trustProxy` configured to Render's verified proxy hop count, so L1 keys on
  the real client and not on Render's proxy.
- A `RateLimitedError` (`429`, slug `rate-limited`) rendered through the
  existing problem+json contract, with a `Retry-After` header, documented on
  every `/v1` operation in OpenAPI.
- `Retry-After` exposed through CORS; the web API client parses it and the
  Spec 06.2 outbox waits at least that long before retrying.

### Non-goals

- **Long-window volume quotas** (N workouts / day). Owner decision during
  brainstorming (option B, 2026-10-04): short burst limits bound the growth
  *rate*; total volume per account is not capped. Residual risk accepted —
  D3.
- **A shared store** (Redis / Postgres). One Render instance; counters live in
  process memory and reset on restart. Spec 15 (AWS, multiple instances) owns
  the swap — D2.
- **Per-user limits on reads.** `GET`s get L1 only — D5.
- **Edge / CDN limiting** (Cloudflare). Arrives with the custom domain;
  out of scope here.
- **Metrics and alerting** on rejections. Spec 13 owns metrics; this spec
  emits a log event only (§9).
- **A runtime kill switch.** No env var disables limiting — D7.

## 2. Acceptance criteria

1. **AC1 — L1 per-IP limit.** More than `ip.max` requests from one client IP
   within one `ip.windowMs` window get `429 rate-limited` for the rest of that
   window, on any route except those listed in AC6.
2. **AC2 — L1 runs before auth.** A request rejected by L1 never reaches the
   token verifier (no JWT verification, no JWKS fetch) — including requests
   with no or an invalid `Authorization` header.
3. **AC3 — L2 per-user group limits.** For each group in §6.2, more than the
   group's `max` write requests from one user within one window get
   `429 rate-limited`. Requests on different routes in the same group share
   one counter.
4. **AC4 — L2 isolation.** Exhausting one group's budget does not affect the
   same user's other groups, and does not affect any other user.
5. **AC5 — reads are not per-user limited.** `GET` routes carry no L2 or L3
   limit; a user who has exhausted every write group can still `GET`.
6. **AC6 — exemptions.** `/healthz`, `/readyz` and `/openapi.json` are never
   counted or limited by any layer.
7. **AC7 — L3 in-flight cap.** When a user already has `inflight.max` write
   requests in progress, the next write request from that user gets
   `429 rate-limited` immediately (it is not queued) with `Retry-After: 1`.
8. **AC8 — L3 releases on every exit.** A slot is released exactly once when
   the request completes successfully, fails with any error status, or is
   aborted by the client; after any mix of these, the user's in-flight count
   returns to 0 and the user's map entry is removed.
9. **AC9 — the `429` response.** Every rejection from L1, L2 or L3 is an RFC
   9457 problem+json body with `type` ending `rate-limited`, `status: 429`, a
   `detail` that names the retry delay but not the layer or group, the
   request's `instance`, and a `Retry-After` header holding a whole number of
   seconds ≥ 1. No `X-RateLimit-*` / `RateLimit-*` headers are sent on any
   response.
10. **AC10 — fail open.** If the limiter store throws, the request proceeds
    and an error is logged; the API does not return `5xx` because of the
    limiter.
11. **AC11 — proxy trust.** `request.ip` resolves to the real client address
    behind Render's proxy, and a client-supplied `X-Forwarded-For` cannot
    choose the L1 key (a request carrying a forged leftmost entry is keyed on
    the address Render's proxy observed).
12. **AC12 — CORS exposes `Retry-After`.** A cross-origin `429` from an
    allowlisted origin carries `Access-Control-Expose-Headers` including
    `Retry-After`.
13. **AC13 — OpenAPI documents `429`.** Every `/v1` operation in the emitted
    document lists a `429` problem response with type `rate-limited`, and the
    committed `openapi.json` matches (Spec 03.0 drift check).
14. **AC14 — web client honours `Retry-After`.** The web `ApiError` exposes
    the parsed `Retry-After` (in ms, or `null` when absent / unparsable), and
    the outbox schedules the retry of a `429`-rejected op no sooner than
    `max(backoffMs(attempt), retryAfterMs)`.
15. **AC15 — a real session never trips a limit.** Replaying 60 set creates
    back-to-back (the outbox's one-in-flight drain, §6.2) plus a workout start,
    6 add-exercise calls and a finish, all as one user, produces no `429`
    against a real Postgres.
16. **AC16 — rejection log.** Each rejection emits one `warn` log line
    `rate_limited` with `layer` (`ip` / `user-rate` / `user-inflight`),
    `group` (L2 only), and `userId` (L2/L3) or `ip` (L1); no request body, no
    token.

## 3. Dependencies & exposed interface

### Needs

- Spec 01: the auth plugin (`onRequest`, attaches `request.user`), the error
  contract (`AppError` → problem+json on root and `/v1` scopes), CORS config.
- Spec 03.0: the OpenAPI pipeline and `problem-responses.ts`'s
  `EVERY_V1_OPERATION` group; the `openapi.json` drift check.
- Spec 06.2: the outbox's `classify` / `backoffMs` and its one-op-in-flight
  drain (sets the burst shape L2's `sets` budget must absorb).
- New dependency: `@fastify/rate-limit` (the Fastify-5-compatible major,
  exact version pinned in the plan).

### Provides — stable surface

- The **`rate-limited` problem type** (`429`, `Retry-After`) on every `/v1`
  route. Clients treat it as retryable after `Retry-After`. Breaking to change
  the slug or drop the header.
- The **limits table** (§6.2) is *not* a stable surface: values may be tuned in
  any release without a spec amendment, as long as AC15 still passes.

## 4. Data model

None. No table, no migration. All counters are process memory.

## 5. API surface

No new endpoints. Every existing route gains the possible response below
(except the AC6 exemptions).

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 17

{
  "type": "https://strengthinnumbers.app/problems/rate-limited",
  "title": "Too many requests",
  "status": 429,
  "detail": "Too many requests — retry after 17 seconds.",
  "instance": "<request id>"
}
```

### New `AppError` subclass

`RateLimitedError` in `apps/api/src/errors/app-error.ts`: `slug =
"rate-limited"`, `status = 429`, `title = "Too many requests"`, constructed
with `retryAfterSeconds: number` (default `1`, so the OpenAPI placeholder
instance is constructible with no arguments). The error contract sets the
`Retry-After` header from it. It joins `EVERY_V1_OPERATION` in
`openapi/problem-responses.ts`, not per-route `config.problems`.

## 6. Behavior & logic

### 6.1 Module layout

`apps/api/src/plugins/rate-limit.ts` owns all three layers and exports:

- `RATE_LIMITS` — the §6.2 table as one frozen constant.
- `rateLimitPlugin` — registers L1 at the root scope and decorates the
  instance with the L2/L3 `preHandler`s that write routes attach by group name
  (e.g. `writeLimits("sets")`), so a route declares its group in one place.
- `buildApp` accepts an optional `rateLimits` override in `BuildAppDeps`
  (tests only; there is no env var — D7).

A unit test asserts every non-`GET` `/v1` route has exactly one L2 group
attached (a new write route can't ship unlimited).

### 6.2 Limits

Fixed one-minute windows. Groups share one counter across their routes.

| Layer | Group | Routes | Limit |
|---|---|---|---|
| L1 | `ip` | every route except AC6's | **600 / min** per IP |
| L2 | `sets` | `POST /v1/workout-exercises/{id}/sets`, `PATCH /v1/sets/{id}`, `DELETE /v1/sets/{id}` | **120 / min** per user |
| L2 | `workouts` | `POST /v1/workouts`, `PATCH`/`DELETE /v1/workouts/{id}`, `POST /v1/workouts/{id}/exercises`, `PATCH`/`DELETE /v1/workout-exercises/{id}` | **60 / min** per user |
| L2 | `exercises` | `POST /v1/exercises`, `PATCH /v1/exercises/{id}`, `POST /v1/exercises/{id}/fork`, `DELETE /v1/exercises/{id}` | **20 / min** per user |
| L2 | `me` | `PATCH /v1/me` | **10 / min** per user |
| L3 | `inflight` | every route in an L2 group | **4** concurrent per user |

Sizing:

- **`sets` 120/min.** The outbox drains one op at a time, oldest first, and
  sends the next as soon as the previous returns. A 60-set offline session
  replays in roughly 10–20 s at staging latency, so 120/min is about twice the
  worst realistic replay. Live logging is ~1 set / 30 s.
- **L1 600/min** is generous because a gym's shared Wi-Fi puts many users
  behind one NAT address, and every authenticated request also counts against
  L1.
- **L3 = 4** is half of the pool's `connection_limit=8`: room for the outbox
  drain plus a concurrent screen action plus headroom, while one account can
  never hold the whole pool.

### 6.3 L1 — per-IP

`@fastify/rate-limit` registered with `global: true` at the root scope,
`keyGenerator: (req) => req.ip`, `hook: "onRequest"`. Root-scope `onRequest`
hooks run before the `/v1` child scope's auth hook, which gives AC2. The AC6
routes opt out with `config: { rateLimit: false }`. The plugin's
`errorResponseBuilder` returns a `RateLimitedError(retryAfterSeconds)` so the
rejection goes through the error contract, not the plugin's own body.

Headers: `addHeadersOnExceeding` all off; `addHeaders` only `retry-after` —
AC9 (D6).

`skipOnError: true` — AC10.

### 6.4 L2 — per-user groups

One `fastify.rateLimit({ max, timeWindow, keyGenerator, hook: "preHandler" })`
handler is created **per group** and the same instance is attached to every
route in that group, which is what makes the group share one counter (AC3).
`keyGenerator: (req) => req.user.id` — `preHandler` runs after the auth
`onRequest` hook, so `request.user` is always set on these routes (an
unauthenticated write was already rejected `401` by auth).

The plan verifies, against the pinned plugin version, that (a) a per-group
handler instance keeps its own store separate from L1's global store, and (b)
attaching it to a route alongside `global: true` adds to L1 rather than
replacing it. If either fails, the fallback is the plugin's route-level
`groupId` option; the externally visible behaviour (AC3, AC4) is the same.

### 6.5 L3 — in-flight cap

```
Map<UserId, number>                  // only users with ≥1 write in flight
preHandler:   n = map.get(id) ?? 0
              if n >= max → throw RateLimitedError(1)       // AC7
              map.set(id, n + 1); request[ACQUIRED] = true
onResponse / onRequestAbort:
              if !request[ACQUIRED] return                  // never acquired
              request[ACQUIRED] = false                     // release once
              n = map.get(id) - 1
              n <= 0 ? map.delete(id) : map.set(id, n)
              if n < 0 → log.warn("inflight_underflow")      // can't happen; tripwire
```

- L3's `preHandler` runs **after** L2's, so a request rejected by L2 never
  takes a slot.
- Fastify does not guarantee `onResponse` for a request the client aborts
  before the reply is sent, so release is wired to both hooks and made
  idempotent with the per-request flag (AC8).
- Memory is bounded by the number of users with a write currently in
  flight.

### 6.6 Proxy trust

Fastify's `trustProxy` is set to the **hop count** of Render's proxy chain
(a number, never `true` — `true` makes the leftmost, client-supplied
`X-Forwarded-For` entry the key). The hop count is not assumed: the plan's
first task logs `X-Forwarded-For` and the socket address from a staging
request (through a temporary hidden route or a one-off log line, removed
before merge) and pins the number in `app.ts` with a comment citing the
observation date. AC11's unit test injects a forged `X-Forwarded-For` and
asserts the key is the proxy-observed address.

Tripwire: in production, the first request whose `req.ip` is a private /
loopback address logs one `warn` `trust_proxy_suspect` (then stays silent),
so a hop-count change — e.g. Spec 15's move to an AWS load balancer — shows up
in the logs instead of silently collapsing every user into one L1 bucket.

### 6.7 Web client

- `apps/web/src/api/problem.ts`: `ApiError` gains `retryAfterMs: number |
  null`, parsed from `Retry-After` as delta-seconds only (an HTTP-date or
  garbage → `null`), capped at 5 minutes.
- `apps/web/src/features/workouts/outbox/outbox.ts`: on a `retry` verdict for
  an `ApiError` with `retryAfterMs`, `nextAttemptAt = now + max(backoffMs,
  retryAfterMs)`. No other client change; `classify` already maps `429` →
  `retry`.

## 7. Security & privacy

- **Authorization boundary.** L2/L3 key on `request.user.id`, the internal id
  resolved by auth, never on a client-supplied value. L1 keys on `req.ip`
  under the pinned `trustProxy` (AC11).
- **Information leak.** The `429` body does not name the layer, group, limit
  or remaining budget, and no rate-limit headers are sent (D6), so a script
  cannot read the budgets off responses.
- **IP addresses in logs.** An IP is personal data under GDPR. It is logged
  **only** on an L1 rejection (AC16), for abuse investigation (legitimate
  interest), under the same Render log retention as every other log line. L2
  and L3 rejections log the user id instead.
- **Residual risks (accepted).**
  - Counters reset on restart / deploy, giving a script a fresh window. Low
    value to an attacker; restarts are infrequent.
  - Total volume per account is uncapped (D3).
  - A NAT'd gym shares one L1 bucket; 600/min is sized for it, and L1 is not
    the per-user control.
  - Distributed (many-IP) unauthenticated floods are not stopped by L1; that is
    the edge's job (Cloudflare, later).

## 8. Config & secrets

No new env vars or secrets. Limits are code constants (§6.2); the only
override is the test-only `rateLimits` dep on `buildApp`. `trustProxy` is a
code constant in `app.ts` (§6.6).

## 9. Observability

- `warn` `rate_limited` per rejection — AC16.
- `warn` `trust_proxy_suspect`, once per process — §6.6.
- `warn` `inflight_underflow` — §6.5 tripwire.
- `error` when the limiter store throws (AC10), via the plugin's
  `onExceeding`/error path.
- No metrics. Spec 13 can turn `rate_limited` into a counter.

## 12. Decisions & open questions

- ✅ **D1 — three layers (IP / per-user rate / per-user in-flight).** A rate
  limit alone does not close D20: D20 is about *concurrency*, and 60/min still
  allows 8 simultaneous requests. L3 caps concurrency directly.
- ✅ **D2 — in-memory store.** One Render instance. A Postgres-backed store
  would add a round trip per request on the same 8-connection pool D20 is
  about. Spec 15 (multiple instances) swaps in a shared store (Redis /
  ElastiCache) through the plugin's store option; L3's map moves with it or
  becomes per-instance with `max` divided by instance count.
- ✅ **D3 — no long-window volume quotas.** Owner decision, 2026-10-04. D21
  becomes "bounded growth rate" (≤ ~120 sets / min / account), not "bounded
  volume". Accepted; if it ever matters, the clean-up is the one-off purge job
  03.2 D21 already describes.
- ✅ **D4 — `@fastify/rate-limit` over a hand-rolled limiter.** Official,
  maintained, handles windows / keys / `Retry-After`; L3 is hand-written
  because the plugin counts requests per window, not requests in flight.
- ✅ **D5 — reads are L1-only.** Reads are cheap, the catalog sync is
  `ETag`-conditional, and no read path takes an advisory lock. Revisit if read
  abuse appears.
- ✅ **D6 — no rate-limit headers except `Retry-After`.** No client needs the
  remaining budget; publishing it helps a script pace itself to the limit.
- ✅ **D7 — no kill switch.** An env var that disables limiting is a
  production bypass flag. Rollback is a revert.
- ✅ **D8 — fail open.** The limiter is protection, not correctness; a limiter
  bug must not take the API down.
- ✅ **D9 — IPs logged plainly, only on L1 rejection.** No hashing precedent
  exists in the codebase; truncation would defeat abuse investigation, which
  is the only reason to log it.
- ✅ **D10 — the `Retry-After` client change ships here,** not in a UI spec:
  a few lines in `problem.ts` and `outbox.ts` that only matter because this
  spec starts sending the header.

**Open:** none.
