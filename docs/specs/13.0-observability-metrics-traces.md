## 1. Purpose, scope & non-goals

Instrument the API with **OpenTelemetry** so that (a) the owner can see how
staging is behaving — per-route rate / errors / latency, Node runtime health,
slow DB queries — on Grafana dashboards and is **emailed when it degrades**,
and (b) the same signals can be explored hands-on with **Prometheus, PromQL,
Tempo and Grafana** in a local stack. One instrumentation layer, two
destinations, chosen by standard `OTEL_*` env vars:

| | Metrics | Traces |
|---|---|---|
| **Local** | Prometheus **pulls** `/metrics` on `:9464` | pushed (OTLP/HTTP) to local **Tempo** |
| **Staging** | pushed (OTLP) to **Grafana Cloud** | pushed (OTLP) to **Grafana Cloud** |
| **Tests / CI / default** | off | off |

### In scope

- `apps/api/src/telemetry/` — SDK bootstrap loaded with `node --import`,
  telemetry config parsing, the span-attribute allowlist processor, metric
  Views, and the three business counters.
- Instrumentation: HTTP server (route-templated), Fastify, Prisma queries, Node
  runtime, pino log ↔ trace correlation.
- Business counters: `sin_workouts_started_total`,
  `sin_workouts_finished_total`, `sin_sets_logged_total{modality}`.
- Graceful-shutdown flush of the SDK.
- `docker-compose.observability.yml`: Prometheus + Tempo + Grafana, digest-
  pinned, with provisioned data sources, dashboards and alert rules.
- `ops/grafana/` — checked-in dashboard JSON (API overview, Usage) and alert
  rules (3), shared by local and Grafana Cloud.
- Staging wiring: `render.yaml` non-secret `OTEL_*` values, a Grafana Cloud
  write-only token in the Render dashboard, a runbook
  (`docs/runbooks/observability.md`).
- Doc edits: DESIGN.md §3.2 / §8.1, specs README roadmap (13 → 13.0 / 13.1 /
  13.2), backlog entries, CLAUDE.md commands.

### Non-goals

- **Error tracking (Sentry)** — Spec 13.1. **Product analytics (PostHog) and
  browser performance / Web Vitals** — Spec 13.2. This spec is backend-only;
  the SPA is untouched.
- **Log shipping to Loki.** pino keeps writing to Render's log stream; this
  spec only adds `trace_id` / `span_id` to log lines so they can be joined to
  traces by hand. Shipping is backlogged (§12, D9).
- **Uptime / synthetic checks.** On Render free a frequent check keeps the
  instance awake ~730 h/month of the workspace's 750 free hours. Deferred to
  Spec 01.1 (paid, non-sleeping prod). Until then the CI post-deploy smoke is
  the liveness signal (§12, D7).
- **Alerts / dashboards as code against Grafana Cloud** (Terraform, API
  scripts). Imported by hand per the runbook; automated in Spec 15 (§12, D8).
- **Prod.** Prod does not exist yet; §8 lists the values Spec 01.1 sets.
- **`@opentelemetry/auto-instrumentations-node`.** Instrumentations are listed
  explicitly (§12, D3).
- Any change to `packages/core` (purity check stays green).

## 2. Acceptance criteria

Behavioural criteria get ≥1 test naming their number (`describe("AC3 — …")`):
unit tests under `apps/api/test/unit/telemetry/`, integration tests under
`apps/api/test/integration/`. *(manual)* criteria are verified by hand and
recorded in the PR description; *(CI)* criteria are enforced by existing jobs.

1. **Off by default.** With no `OTEL_*` variables set, the API boots and serves
   exactly as before: no exporter is constructed, nothing listens on `:9464`,
   and no outbound telemetry request is made. Existing unit and integration
   suites pass unchanged.
2. **Fail-fast config.** Boot exits 1 with a `ConfigError` naming the offending
   variable, before any port is bound, when: an `OTEL_*_EXPORTER` value is not
   one of its allowed values (§8); a signal uses `otlp` with no resolvable
   endpoint; `OTEL_EXPORTER_OTLP_HEADERS` (or a per-signal variant) is not a
   comma-separated `key=value` list; `OTEL_TRACES_SAMPLER_ARG` is not a number
   in `[0, 1]`; or `OTEL_METRICS_EXPORTER=prometheus` with
   `NODE_ENV=production`.
3. **Route-templated HTTP metrics.** A request to `GET /v1/workouts/<uuid>`
   records one observation in the `http.server.request.duration` histogram
   (Prometheus: `http_server_request_duration_seconds`) whose attributes are
   exactly `http.request.method`, `http.route = "/v1/workouts/:id"`,
   `http.response.status_code`, and — on a 5xx only — `error.type`. The raw id
   appears in no metric attribute.
4. **Health and metrics paths are not measured.** Requests to `/healthz`,
   `/readyz` and the Prometheus endpoint produce no HTTP metric observation and
   no span.
5. **Runtime metrics.** With metrics enabled, the export includes Node
   event-loop delay (`nodejs.eventloop.delay.p99` among others), V8 heap
   usage (`v8js.memory.heap.*`), GC duration (`v8js.gc.duration`), and the
   app's own `sin.process.start_time` gauge (Unix seconds, constant per
   process) used for restart annotations.
6. **Request traces.** An authenticated request that queries the DB produces a
   server span named `<METHOD> <route template>` with Prisma query spans as
   descendants in the same trace.
7. **Span attribute allowlist.** Every exported span carries only attributes on
   the §7 allowlist. In particular `client.address`, `network.peer.address`,
   `user_agent.original`, `url.full`, `url.path`, `url.query`, `enduser.id`,
   any `http.request.header.*` / `http.response.header.*`, and SQL parameter
   values never appear. A recorded exception keeps `exception.type` and drops
   `exception.message` and `exception.stacktrace`.
8. **Metric attribute allowlist.** Every exported metric carries only the
   attributes its View allows (§6.3); an attribute added upstream by an
   instrumentation upgrade is dropped, not exported.
9. **Log ↔ trace correlation.** A log line written through `request.log`
   during a traced request carries `trace_id` and `span_id` matching the
   request's server span. With tracing off, log lines are unchanged.
10. **Business counters count real events once.**
    - `POST /v1/workouts` returning 201 adds 1 to `sin_workouts_started_total`;
      an idempotent replay returning 200 adds 0.
    - A `PATCH /v1/workouts/:id` that finishes a workout adds 1 to
      `sin_workouts_finished_total`; a rejected finish (`409`) adds 0.
    - `POST /v1/workout-exercises/:id/sets` returning 201 adds 1 to
      `sin_sets_logged_total{modality=<modality_snapshot>}`; any 4xx adds 0.
      (If set create gains idempotent replay — Spec 05.1 follow-ups D15 — a
      replay adds 0.)
    - Counters carry no attribute other than `modality` on the sets counter.
11. **Export failures never reach a request.** With the OTLP endpoint
    unreachable or an exporter that throws, every response is identical
    (status, body, latency within normal variance) to the telemetry-off case,
    and the failure is logged at `warn` at most once per 5 minutes per signal.
12. **Shutdown flush.** On SIGTERM the existing graceful shutdown drains the
    app and disconnects Prisma, then calls the SDK's `shutdown()` (which
    flushes pending metrics and spans) bounded by a 5 s timeout; a hung flush
    does not prevent exit. With telemetry off, shutdown is unchanged.
13. **Prometheus endpoint is local-only and off the API port.** With
    `OTEL_METRICS_EXPORTER=prometheus`, `GET http://localhost:9464/metrics`
    returns Prometheus text format including the AC3 histogram;
    `GET /metrics` on the API port returns the normal problem+json 404.
14. **Local stack** *(CI + manual)*. `docker-compose.observability.yml` pins
    Prometheus, Tempo and Grafana as `name:patch-tag@sha256:<index digest>`
    (extended `image-pins` unit test). A unit test parses every file under
    `ops/grafana/` (dashboards JSON, alert-rule YAML, provisioning YAML).
    *(manual)* `docker compose -f docker-compose.observability.yml up` + `pnpm
    --filter @sin/api run dev` with `.env.example` values shows **every panel**
    of both dashboards populated, a trace in Tempo for a scenario run, and a
    trace → metrics jump in Explore.
15. **Staging** *(manual)*. After deploy, the CI smoke run's requests appear in
    Grafana Cloud as AC3 metrics and as at least one trace; **the same
    dashboard JSON as AC14 shows every panel populated** (proves the
    metric-name mapping, §6.11); the three alert rules are imported and a
    contact-point test email is received. Recorded in the PR / runbook.
16. **Purity** *(CI)*. `pnpm run core:purity` passes; no OTel package is
    imported from `packages/core` or `apps/web`.

## 4. Data model

None. No tables, no migration.

## 5. API surface

No `/v1` endpoints. Two process-level surfaces:

- **`:9464/metrics`** (Prometheus text format) — only when
  `OTEL_METRICS_EXPORTER=prometheus`, which AC2 forbids under
  `NODE_ENV=production`. Separate listener from the API port; Render exposes
  only `PORT`, so it is unreachable from outside even if misconfigured. Not in
  `openapi.json`.
- **Outbound OTLP/HTTP (protobuf)** to `OTEL_EXPORTER_OTLP_ENDPOINT` — when a
  signal's exporter is `otlp`.

## 6. Behavior & logic

### 6.1 Boot order

OTel instruments `http`, Fastify, Prisma and pino by patching them **as they
are loaded**, so the SDK must start before `server.ts` imports anything. The
API is ESM, so patching also needs OTel's module-loader hook.

```
node --import ./dist/telemetry/register.js dist/server.js
        │
        ├─ register.ts
        │    1. loadTelemetryConfig(process.env)     ← pure, unit-tested; ConfigError → stderr, exit 1
        │    2. all exporters "none"?  → return (AC1: no SDK, no hook)
        │       NB: sdk-node defaults an UNSET exporter variable to "otlp". Our
        │       config treats unset as "none", and register.ts passes readers /
        │       span processors to NodeSDK explicitly from the parsed config, so
        │       the SDK's own env defaults never decide what is exported.
        │    3. module.register("@opentelemetry/instrumentation/hook.mjs", import.meta.url)
        │       (the ESM loader hook, wraps import-in-the-middle)
        │    4. new NodeSDK({ resource, spanProcessors, metricReader(s), views, instrumentations })
        │    5. sdk.start(); expose the sdk handle for shutdown (module singleton)
        │
        └─ server.ts → loadConfig(...) → buildApp(...) → listen
```

`loadTelemetryConfig` lives in `src/telemetry/config.ts` and throws the
existing `ConfigError` type. `config.ts` (`loadConfig`) calls it too and merges
its issues into its own error list, so a single boot reports every bad
variable, and `Config` carries `telemetry` for `shutdown.ts`. Boot scripts:

| Where | Command |
|---|---|
| `Dockerfile` `CMD` | `node --import ./apps/api/dist/telemetry/register.js apps/api/dist/server.js` |
| `apps/api` `start` | `node --import ./dist/telemetry/register.js dist/server.js` |
| `apps/api` `dev` | `tsx watch --env-file-if-exists=.env --import ./src/telemetry/register.ts src/server.ts` |
| `docker-compose.yml` `api` | migrate, then the `CMD` form above |

`dev` loads `.env` before `--import`, so `register.ts` sees `OTEL_*` values
from `apps/api/.env`.

### 6.2 Instrumentations

| Instrumentation | Gives | Config |
|---|---|---|
| `instrumentation-http` | the server span; `http.server.request.duration` | `ignoreIncomingRequestHook` drops `/healthz`, `/readyz` (AC4); outgoing-request spans **off** (JWKS fetches are noise; revisit if Auth0 latency matters); no header capture |
| `@fastify/otel` (`FastifyOtelInstrumentation`) | writes the route template into the HTTP instrumentation's RPC metadata, which sets `http.route` on the server span **and** the duration metric; adds an INTERNAL handler span | `registerOnInitialization: true` (hooks Fastify's init diagnostics channel — **no change to `buildApp`**); `ignorePaths` for `/healthz`, `/readyz`. Needs `instrumentation-http` alongside it — it does not create the server span |
| `@prisma/instrumentation` | `prisma:client:operation` → `prisma:engine:query` → `prisma:engine:db_query` (parameterized SQL in `db.statement`, no bound values) | `ignoreSpanTypes` drops the `*:serialize` and `response_json_serialization` spans (noise); no schema `previewFeatures` change on Prisma 6.19 |
| `instrumentation-runtime-node` | `nodejs.eventloop.delay.*` (seconds), `nodejs.eventloop.utilization`, `v8js.gc.duration`, `v8js.memory.heap.*` | defaults |
| `instrumentation-pino` | `trace_id` / `span_id` on log lines (AC9) | log-sending **off** (no OTLP logs) |

No instrumentation touches app code: with the SDK off nothing is registered,
so tests that build the app without the SDK are unaffected. `metrics.ts` also
registers one observable gauge, `sin.process.start_time`, for restart
annotations (the runtime instrumentation does not emit one).

### 6.3 Metric Views (attribute allowlist + cardinality)

Every metric gets a View with an explicit `attributeKeys` allowlist (AC8):

| Metric | Kept attributes |
|---|---|
| `http.server.request.duration` | `http.request.method`, `http.route`, `http.response.status_code`, `error.type` |
| `sin.workouts.started`, `sin.workouts.finished` | none |
| `sin.sets.logged` | `modality` |
| `sin.process.start_time` | none |
| runtime metrics | the instrumentation's own bounded attributes (e.g. GC type) |

A catch-all View drops any other instrument the SDK might register. Histogram
buckets for the HTTP duration use the OTel semconv advice
(`0.005 … 10` s), which covers both warm requests and Render cold starts.

**Cardinality rule:** an attribute is allowed only if its value set is fixed
and small (route templates, HTTP methods, status codes, modalities). Never ids,
raw URLs, user input or user identifiers. Grafana Cloud free caps active
series; this design stays in the low hundreds.

### 6.4 Business counters

Counters are incremented **beside the existing log events**, inside the branch
that already decides "this was a real event", so the counter and the log line
cannot disagree:

| Counter (OTel → Prometheus) | Call site |
|---|---|
| `sin.workouts.started` → `sin_workouts_started_total` | `routes/workouts.ts` POST, the `if (created)` branch (`workout_started`) |
| `sin.workouts.finished` → `sin_workouts_finished_total` | `routes/workouts.ts` PATCH, `isFinishAttempt && updated.endedAt !== null` (`workout_finished`) |
| `sin.sets.logged{modality}` → `sin_sets_logged_total` | `routes/sets.ts` POST, after `createSet` resolves (`set_created`) |

`metrics.ts` creates instruments from `@opentelemetry/api`'s global meter. With
the SDK off that meter is a no-op, so call sites need no guards and unit tests
need no setup.

### 6.5 Sampling

`OTEL_TRACES_SAMPLER=parentbased_traceidratio`. Staging and local set
`OTEL_TRACES_SAMPLER_ARG=1` (keep everything — volume is tiny). Prod picks its
ratio in Spec 01.1. Parent-based means an inbound `traceparent` header is
honoured; the SPA does not send one in v1.

### 6.6 Failure isolation (AC11)

- Exporters run on the SDK's batch processor / periodic reader — off the
  request path by construction.
- Export errors go to a diagnostic logger (`diag.setLogger`) adapter that
  forwards to pino at `warn`, throttled to one line per signal per 5 minutes.
  `register.ts` runs before `server.ts` builds the app logger, so it builds its
  own pino instance with the same `logging.ts` options (level, redaction) for
  this adapter.
- An export timeout (`OTEL_EXPORTER_OTLP_TIMEOUT`, default 10 s) bounds each
  attempt; the batch span processor's queue is bounded (default 2048) and drops
  on overflow rather than growing memory.

### 6.7 Shutdown (AC12)

`createGracefulShutdown` gains an optional `telemetry: { shutdown(): Promise<void> }`
dependency. Order: `app.close()` (drain) → `prisma.$disconnect()` →
`telemetry.shutdown()` raced against 5 s → exit. Telemetry goes last so spans
for drained requests are flushed. A flush timeout logs `warn` and still exits 0.

### 6.8 The Render sleep gap

Render free stops the instance after ~15 min without traffic. While asleep the
API pushes nothing, so **missing data means idle, not down**:

- every alert rule sets *no data → OK* (and *error → alerting*, so a broken
  query is noticed);
- latency / error alerts evaluate over 10 min and require ≥ 20 requests in the
  window, so one cold start (30 s+ first request) cannot fire them;
- the API overview dashboard annotates restarts from `sin.process.start_time`
  changes.

Consequence (accepted, D7): staging has no "API is down" alert.

### 6.9 Dashboards and alerts (`ops/grafana/`)

```
ops/grafana/
  dashboards/api-overview.json   RED per route (rate, 5xx ratio, p50/p95/p99), event-loop p99, heap, restarts
  dashboards/usage.json          workouts started / finished, sets logged by modality
  alerts/api.yaml                Grafana alert-rule provisioning format
  provisioning/                  local-only: datasources (Prometheus, Tempo), dashboard + alert providers, contact point
```

Dashboards use a `datasource` template variable (no hard-coded UID), so the
same JSON imports into Grafana Cloud. Alert rules (all *no data → OK*):

| Rule | Condition | For |
|---|---|---|
| `api-high-error-rate` | 5xx / all > 5 % over 10 m, and ≥ 20 requests | 5 m |
| `api-slow` | p95 `http_server_request_duration_seconds` > 1 s over 10 m, and ≥ 20 requests | 5 m |
| `api-event-loop-blocked` | event-loop delay p99 > 200 ms | 5 m |

Contact point: email to the owner. Locally Grafana provisions the same rules
from file with a log-only contact point, so a rule can be tripped with a load
test without sending mail.

### 6.10 Local stack

`docker-compose.observability.yml` (separate from `docker-compose.yml`, so the
default dev loop is unchanged):

| Service | Port | Notes |
|---|---|---|
| `prometheus` | 9090 | scrapes `host.docker.internal:9464` (API via `pnpm dev`) and `api:9464` (API in compose), 15 s interval; `extra_hosts: host.docker.internal:host-gateway` for Linux |
| `tempo` | 4318 (OTLP/HTTP), 3200 (query) | monolithic mode, local block storage in a named volume, 24 h retention; the OTLP HTTP receiver must bind `0.0.0.0:4318` explicitly (default is localhost since 2.7, grafana/tempo#4465) |
| `grafana` | 3001 | anonymous admin, local only; provisions `ops/grafana/provisioning/` + dashboards + alerts; Tempo data source configured with a trace → metrics link |

Grafana is on 3001 because the compose `api` service owns 3000. Image lines at
drafting: `prom/prometheus:v3.15.0`, `grafana/tempo:3.1.0` (Tempo 3 dropped
ingesters and the 2.x config blocks — write the config against the 3.x docs),
`grafana/grafana:13.2.3`, each with its multi-arch index digest.

Trace → logs is **not** a Grafana link locally or on staging (logs are not in
Loki, D9): you copy the `trace_id` and search the terminal / Render logs.

### 6.11 Metric-name mapping (local vs Grafana Cloud)

OTel names are dotted and carry a unit; Prometheus names are underscored. The
two backends translate differently: the JS Prometheus exporter appends `_total`
to counters but **no unit suffix** (`http_server_request_duration_bucket`,
`nodejs_eventloop_delay_p99`), while Grafana Cloud's OTLP ingestion may append
the unit (`…_seconds_bucket`). The shared dashboards must therefore resolve to
the same series on both. Implementation picks the first that works and records
it in D13:

1. Views give the affected instruments explicit names whose translation is
   identical on both backends;
2. failing that, a dashboard-level `metric_suffix` constant variable, set to
   `""` locally (provisioned) and `_seconds` in Cloud (set once at import).

AC14 + AC15 ("every panel populated on both") are the test.

## 7. Security & privacy

**Threat:** telemetry leaves our infrastructure for a third party (Grafana
Cloud). DESIGN §8.2 forbids sharing training or body-weight data, and IPs,
user-agents and user ids are personal data under GDPR. Instrumentation
defaults record several of these, so the control is an **allowlist**, not a
denylist (D5).

**Span attribute allowlist** — a `SpanProcessor` (`telemetry/allowlist.ts`)
wraps the exporting processor and, on `onEnd`, rebuilds each span's attributes
keeping only:

- `http.request.method`, `http.route`, `http.response.status_code`,
  `error.type`, `url.scheme`, `server.address`, `server.port`
- `db.system`, `db.statement` (Prisma emits parameterized SQL with no bound
  values; prisma/orm#26731 tracks an *opt-in* for values, which we never
  enable), and any Prisma model / operation attributes found on real spans
  during implementation — each added to the list by name, with a test
- `sin.request_id` (the random per-request id already in logs), set by an
  `onRequest` hook in `buildApp`
- span events: `exception` with `exception.type` only

Resource attributes are fixed by the SDK config: `service.name`,
`service.version` (git SHA), `deployment.environment`, plus the SDK's
`telemetry.sdk.*`. No host / process / container detectors that would leak
hostnames or command lines (`process.command_args` includes nothing secret
today, but the allowlist keeps it that way).

**Never captured:** the Auth0 `sub` or `user.id`, request / response bodies,
any header (incl. `Authorization`), query strings, path parameters, set
measures, body weight, notes / titles.

**Grafana Cloud token:** an access-policy token scoped to **`metrics:write`
and `traces:write` only** — a leak lets someone write junk, not read data.
Stored as a Render secret (`sync: false`). It sits in
`OTEL_EXPORTER_OTLP_HEADERS`, so `logging.ts` redaction must cover that key if
config is ever logged (it is not today; AC2's `ConfigError` names the variable,
never its value).

**`/metrics`:** separate port, refused under `NODE_ENV=production` (AC2),
never exposed by Render.

**Local stack:** Grafana anonymous admin and unauthenticated Prometheus /
Tempo bind to localhost only (`127.0.0.1:` port mappings).

## 12. Decisions & open questions

### Resolved

- **D1 ✅ Grafana Cloud free tier for staging, local Prometheus + Tempo +
  Grafana for development.** Alerts need an always-on evaluator, which rules
  out local-only; a self-hosted VM (~$5–7/mo) teaches Prometheus operations
  but adds a server to patch, secure and back up, and moves again at Spec 15.
  The local compose stack covers pull-based Prometheus hands-on.
- **D2 ✅ OpenTelemetry SDK with per-signal exporters, not `prom-client`.**
  Render free sleeps, so a pull model would need Grafana Cloud to scrape a
  public, token-protected `/metrics` every minute, which keeps the instance
  awake 24/7 and needs its own auth. OTel push fits a sleeping instance,
  DESIGN §8.1 already names OTel, traces come from the same SDK, and Spec 15
  re-points the exporter (AMP / ADOT) without touching instrumentation.
  Cost: OTel → Prometheus name translation and a `--import` boot step.
- **D3 ✅ Explicit instrumentations, not `auto-instrumentations-node`.** The
  meta-package patches `fs`, `dns`, `net` and dozens of libraries we do not
  use — span noise, image weight, and more attributes to allowlist.
- **D4 ✅ Local traces included** (owner, 2026-10-01). One Tempo container;
  the payoff is debugging slow requests locally without a cloud round-trip.
- **D5 ✅ Allowlist, not denylist, for span and metric attributes.**
  Instrumentation upgrades add attributes silently; a denylist would export
  them until someone noticed. Allowlist fails closed.
- **D6 ✅ Off by default; `prometheus` refused in production.** Tests and CI
  need zero telemetry setup; production `/metrics` is a needless surface.
- **D7 ✅ No synthetic uptime check on staging** (owner, 2026-10-01). It
  would keep the free instance awake (~730 of 750 workspace hours), leaving no
  headroom for Spec 11's cron. The post-deploy smoke covers "deployed and up";
  Spec 01.1 adds the check on non-sleeping prod.
- **D8 ✅ Dashboards / alerts checked in, imported by hand to Grafana Cloud.**
  Grafana Cloud has no file provisioning; Terraform for three rules and two
  dashboards is disproportionate before Spec 15.
- **D9 ✅ Logs stay on Render; only trace ids are added.** Loki shipping needs
  an OTLP log pipeline or Render log streams; deferred to keep this to one
  session (BL-11).
- **D10 ✅ Business counters sit beside the existing log events**, so "event
  happened" has a single decision point and counter / log cannot disagree.

- **D11 ✅ No DB connection-pool gauge in 13.0.** Prisma's `metrics` preview
  (`$metrics`, `prisma_pool_connections_busy`) was deprecated in 6.14 and
  removed in 7.0; adopting it now builds on a dead end. The supported route is
  observable gauges over `pg.Pool` (`totalCount − idleCount` busy,
  `waitingCount` saturation), which needs a Prisma driver adapter we do not
  use. Interim proxy: `prisma:engine:connection` span durations in traces.
  BL-14 tracks the gauge.
- **D12 ✅ No exemplars.** `@opentelemetry/exporter-prometheus` (0.222.0) has
  no exemplar support, so a latency-panel point cannot link to a trace
  locally. The jump is trace → metrics in Explore, or Tempo search by route +
  duration.
- **D13** *(deliberately left for implementation — the only one)* — which
  §6.11 option made the dashboards backend-agnostic. It needs a real Grafana
  Cloud ingest to observe; AC14 + AC15 gate it.
