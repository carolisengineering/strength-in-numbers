## 1. Purpose, scope & non-goals

Ship the **exercise catalog** as a read API: the three catalog tables, the
curated global seed, `ExerciseId` in `@sin/core`, and three cache-friendly read
endpoints. It consumes the contract pipeline from **Spec 03.0** — DTOs are
authored as Zod schemas in `@sin/core`, routes use the type provider, and the new
endpoints appear in the emitted OpenAPI document automatically.

Per the scoping decision (§12 D1) this spec is **read only**: custom-exercise
writes and the copy-on-write fork of a global row move to **Spec 03.2**.

> **First-principles note (for a backend dev newer to the browser side):**
> The catalog is a few hundred rows that every client needs in full to render a
> picker and to show exercise names in workout history — so the client pulls it
> once and caches it locally, then only asks "what changed?" on later launches.
> Two HTTP mechanisms do that. An **`ETag`** is a short fingerprint the server
> puts on a response; the client sends it back as `If-None-Match`, and if nothing
> changed the server answers `304 Not Modified` with no body. A **`updated_since`
> query param** is an app-level delta: "give me only the rows changed after this
> time", including rows that were *retired* (so the client drops them). Together:
> first launch → full pull; quiet re-open → `304`; after a catalog revision →
> a small delta. `serverTime` in every response is the timestamp the client
> stores and passes as the next `updated_since` — the server derives it from the
> catalog's own last-change time (§6.1), not from its wall clock, so client-clock
> skew never enters the cursor.

### In scope

- **`exercise` / `muscle_group` / `equipment` tables** + migration
  `0002_create_exercise_catalog`, additive / expand-only (CLAUDE.md).
- **`exercise.catalog_key`** — a `kebab-case`, human-readable **stable
  identifier for the seed** (and a future URL segment). `UNIQUE` where
  `owner_user_id IS NULL`; `NULL` for custom rows. *Not* the client's cache key
  — the client caches and reconciles by `id` (§6.1). Adds one column to
  DESIGN §4.2.
- **Global catalog seed** — an idempotent script run as a release step (§12 D2):
  curated rows authored as checked-in JSON, validated on load against a Zod
  **input schema** (stricter than the wire DTO — §6.3), then `INSERT` new rows /
  `is_active = false` retired ones / non-identifying-field `UPDATE`s /
  **abort** on an identifying change to a live row.
- **Seed ships against a ~10-row fixture catalog; full curation is an immediate
  data-only follow-up PR** (§12 D8). This spec is the mechanism + the endpoints;
  authoring ~50 exercises + the natural-code vocabularies is real work that would
  push it past one session, and the follow-up needs no code review — just a data
  file and a re-run of the idempotent seed.
- **`GET /v1/exercises`** — full caller-visible catalog, no pagination, strong
  content `ETag`, `updated_since` delta. **`GET /v1/muscle-groups`** and
  **`GET /v1/equipment`** — the reference tables, each independently `ETag`d.
  All auth-required.
- **`ExerciseId`** brand exported from `@sin/core` (via `brandId()`), plus the
  catalog Zod DTO schemas (`ExerciseSchema`, `MuscleGroupSchema`,
  `EquipmentSchema`) and their inferred types.

### Non-goals

- **The contract pipeline itself** — Spec 03.0 (deps wiring, error-mapper
  extension, `/v1/me` migration, OpenAPI emit + drift check). Spec 03.1 assumes it
  is in place.
- **Custom-exercise writes** (`POST /v1/exercises`) and the **copy-on-write
  fork** (`PATCH`/`DELETE`) — **Spec 03.2** (§12 D1). This spec creates the
  `owner_user_id` column + FK + index and seeds only `NULL`-owner rows.
- **`GET /v1/exercises/{id}`** — no consumer until 03.2 / deep links (§12 D5).
- **Modality → required-measure validation** — Spec 05 (DESIGN §4.4).
- **Exercise-picker UI** — Spec 06. **Images** — `image_key` stays a reserved
  post-v1 column. **Muscle/equipment admin** — the reference tables are
  seed-only in v1.

## 2. Acceptance criteria

AC1–AC10 each get ≥1 test naming their number (`describe("AC6 — …")`) — mostly
integration (Testcontainers) plus a few `@sin/core` unit tests. AC11 is verified
by review of the doc diff (§10).

1. **Migration creates the catalog schema.** `0002_create_exercise_catalog`
   applies cleanly on a fresh DB and on top of `0001_create_user`; creates
   `exercise`, `muscle_group`, `equipment` with the columns, FKs, `CHECK`s and
   partial indexes in §4. Verified by the integration suite running real
   migrations. Its down migration (drops all three) is exercised by the same
   suite's teardown / `migrate reset`; production undo is `git revert` + a
   forward migration if ever needed, never `migrate down` (Spec 01 §11, §11).
2. **`modality` is constrained, and the constraint can't silently drift.** A
   `CHECK` (§12 D6) rejects any `modality` not in `@sin/core` `MODALITY_VALUES`.
   The **primary** check is behavioral: a raw insert of a bogus value → DB error,
   each valid member → accepted. The **drift-guard** is a string-containment
   assertion that the migration `.sql` file contains a `CHECK (modality IN (…))`
   clause whose literal list is rendered from `MODALITY_VALUES` — *not* a parse of
   `pg_get_constraintdef()`, which PG normalizes to `= ANY (ARRAY[...])` and would
   make the assertion brittle. A future vocabulary change that misses the
   migration is still caught.
3. **`catalog_key` is unique among global rows only.** Two global rows can't
   share a `catalog_key`; a custom row may have `NULL`, and many custom rows
   with `NULL` coexist. Partial-unique-index integration test.
4. **Seed is idempotent, validated, append-only.** Running the seed twice
   against a fresh DB yields the same row set (no duplicates). Every data-file
   row is checked against the seed Zod input schema on load — an unknown
   `primaryMuscleId` / bad `modality` / missing `catalogKey` / a `name` outside
   `1..120` chars or containing control characters fails the run before any
   write. A data file that changes a live entry's `name` or `modality` **fails
   the seed**, naming the `catalog_key`. A new entry is inserted. An entry marked
   `retired` gets `is_active = false` and its `updated_at` bumped — **all other
   columns unchanged**. (§6.3)
5. **`GET /v1/exercises` returns the caller-visible catalog, and only that.**
   Auth required (`401` without a valid token). The full pull and the
   `updated_since` delta each contain every visible global row and the calling
   user's own custom rows, and **no** other user's custom rows — the visibility
   filter is `AND`ed onto both query paths (§6.1). `camelCase` fields;
   `exercises` ordered by `name COLLATE "C", id` (locale-independent — §6.1);
   response carries only the `Exercise` DTO fields (serializer strips extras —
   Spec 03.0 §6.5).
6. **`updated_since` returns a delta including deactivations.** With
   `?updated_since=<rfc3339>` the response is exactly the caller-visible rows
   with `updated_at > since` — **including** rows now `is_active = false`, each
   carrying that flag. No param → the full `is_active` set. Malformed
   `updated_since` → `422 validation-error` + `errors: [{ path: "updated_since",
   … }]`. Future timestamp → `{ exercises: [], serverTime }`, where `serverTime`
   is clamped to server-now (`LEAST(transaction_timestamp(), …)`), never echoed
   forward as the future input (§6.1).
7. **`ETag` / `304` + cache headers.** The `ETag` is a strong validator computed
   over the **exact serialized bytes of the `exercises` array sent on the wire**
   plus the `updated_since` cursor value (a distinct sentinel for its absence /
   the full pull), excluding `serverTime` (§6.1). An identical catalog payload at
   the same cursor with a later `serverTime` yields the **same** `ETag`; a delta
   that serializes to the same bytes as an earlier full pull yields a
   **different** `ETag` (so the client can't `304` past a revision). Row order is
   locale-independent (`ORDER BY name COLLATE "C", id`). `If-None-Match` with no
   catalog change → `304`, empty body; after any change the `ETag` differs and
   `200` is returned. Every `200` and `304` on all three endpoints carries
   `Cache-Control: private, no-cache` and `Vary: Authorization`.
8. **Reference endpoints.** `GET /v1/muscle-groups` and `GET /v1/equipment`
   (auth required) each return the full table as `camelCase` DTOs ordered by
   `displayOrder` then `id COLLATE "C"` (the `id` is `TEXT` — §6.1), with their
   own strong `ETag` / `304` and the same cache headers.
9. **`ExerciseId` brand.** `@sin/core` exports `ExerciseId`, `ExerciseIdSchema`,
   `parseExerciseId`, `isExerciseId` via `brandId("ExerciseId")`; a raw `string`
   is not assignable to `ExerciseId` and a `UserId` is not an `ExerciseId`
   (`--typecheck` negative assertions); `parseExerciseId` accepts a UUID, throws
   on malformed input.
10. **Catalog routes are in the published contract.** After this spec, the three
    read endpoints appear in `GET /openapi.json` (Spec 03.0) with `camelCase`
    schemas derived from the catalog Zod DTOs, and the CI drift check stays
    green.
11. **Docs consistent.** `specs/README.md` gains a 03.2 row and marks 03.1's
    scope; DESIGN §4.2 carries `catalog_key` (and a note that `owner_user_id IS
    NULL` rows are never deleted, `owner_user_id` is `ON DELETE CASCADE`) **and
    the reference-code immutability rule** (D3); DESIGN §6 gains the one-sentence
    `GET /v1/exercises` pagination carve-out; DESIGN §5.2 wording matches §6.1
    (`serverTime` derived from `MAX(updated_at)`, `ETag` namespaced by the
    cursor). *(The §6 Zod/OpenAPI reframe and the §7 CI row are Spec 03.0's edits,
    not this one's.)*

**Consumers must note:**
- `exercise.owner_user_id` is `ON DELETE CASCADE`. Spec 05's
  `workout_exercise.exercise_id → exercise(id)` FK must be defined so an account
  purge deletes `workout_exercise` rows **before / together with** the user's
  custom `exercise` rows — purge ordering is deliberate, not incidental.
- The `Exercise` DTO caps `name` at `1..120` chars, no control characters; Spec 06
  is responsible for output-encoding it at render time (the API stores it raw).
- `GET /v1/exercises` has no pagination and assumes a bounded caller-visible set
  (§6.1). **Spec 03.2 must not ship `POST /v1/exercises` without a hard per-user
  custom-exercise cap** (≈500) — the un-paginated read has no fallback.
- **Cursor update is server-authoritative, not monotonic.** A consumer that
  caches incrementally MUST overwrite its stored cursor with the `serverTime`
  from each good response — **never** `max(stored, received)`. A one-off future
  or skewed cursor (e.g. AC6's future-timestamp case) otherwise wedges the client
  permanently: no row ever has `updated_at >` a far-future cursor. (§6.1)
- **Incremental-sync contract (Spec 06).** A consumer that caches incrementally
  does **exactly one** full pull, persists `serverTime`, then uses `updated_since`
  exclusively; a later fresh full pull resets the baseline (persist the new
  `serverTime`, discard the old cursor).

## 4. Data model

Owned by this spec: **`exercise`**, **`muscle_group`**, **`equipment`**.
Migration **`0002_create_exercise_catalog`** — additive, expand-only. The
migration SQL is **hand-authored** (`prisma migrate diff` as a starting point,
then edited): the partial unique index `WHERE owner_user_id IS NULL`, the
`CHECK (modality IN (…))` literal list, and the partial `is_active` index are not
expressible in the Prisma schema DSL, so the `.sql` file is the source of truth
and the Prisma models exist for the client only (same raw-SQL carve-out Spec 01
used for its `ON CONFLICT` provisioning). The down migration drops all three
tables — for local `migrate reset` / test teardown, not production (§11). Seed
data loads via a separate release step, not the migration (§12 D2, §11).

`muscle_group` / `equipment` use a **`TEXT` natural-code PK** (§12 D3) —
self-describing in the DB and in API payloads (`primaryMuscleId: "chest"`), no
lookup needed to render a response.

```
Table: muscle_group
  id            text         PK          -- natural code, e.g. 'chest', 'lats'
  name          text         NOT NULL    -- display label, e.g. 'Chest'
  display_order smallint     NOT NULL DEFAULT 0
  created_at    timestamptz  NOT NULL DEFAULT now()
  updated_at    timestamptz  NOT NULL DEFAULT now()

Table: equipment
  id            text         PK          -- natural code, e.g. 'barbell', 'dumbbell'
  name          text         NOT NULL
  display_order smallint     NOT NULL DEFAULT 0
  created_at    timestamptz  NOT NULL DEFAULT now()
  updated_at    timestamptz  NOT NULL DEFAULT now()

Table: exercise
  id                   uuid        PK, app-generated UUIDv7
  catalog_key          text        NULL   -- kebab-case; set for curated rows, NULL for custom
  owner_user_id        uuid        NULL   FK → user(id) ON DELETE CASCADE   -- NULL = global/curated
  name                 text        NOT NULL
  modality             text        NOT NULL  CHECK (modality IN (<@sin/core MODALITY_VALUES>))
  primary_muscle_id    text        NULL   FK → muscle_group(id)
  secondary_muscle_ids text[]      NOT NULL DEFAULT '{}'            -- text[] of muscle_group.id
  equipment_id         text        NULL   FK → equipment(id)
  is_active            boolean     NOT NULL DEFAULT true
  created_at           timestamptz NOT NULL DEFAULT now()
  updated_at           timestamptz NOT NULL DEFAULT now()

Indexes:
  exercise_catalog_key_key  UNIQUE (catalog_key) WHERE owner_user_id IS NULL
  exercise_owner_idx        (owner_user_id)
  exercise_updated_at_idx   (updated_at)          -- drives ?updated_since
```

(No `is_active` index — negligible at a few hundred rows; add one only if a query
plan later needs it.)

- **`updated_at`** is set by the application on every write (no DB trigger —
  matches Spec 01's `user`). The seed sets it explicitly (§6.3).
- **Append-only for global rows** (DESIGN §4.2): a curated row's `name` /
  `modality` / `catalog_key` are never updated in place; retiring is
  `is_active = false` plus a new row. Enforced by the seed (§6.3); no endpoint
  in this spec can write a global row.
- **`owner_user_id` is `ON DELETE CASCADE`** — a user's custom exercises are
  their data and go on account purge. `owner_user_id IS NULL` (curated) rows are
  never deleted. DESIGN §4.2 gains this note; the §4.9 matrix already carries a
  "custom exercise" row and is not restructured here (that is 03.2's concern).
- `primary_muscle_id` / `equipment_id` are nullable for 03.2 custom-create;
  curated rows always set `primary_muscle_id`.
- **The `User` model gains a back-reference.** Prisma requires both sides of a
  relation, so `exercise.owner_user_id → user(id)` obliges a
  `customExercises Exercise[]` field on the `User` model (owned by Spec 01) or
  `prisma validate` fails in CI (Spec 01's CI history shows `prisma validate`
  biting). It is a **Prisma-client-only change** — no column, no migration — and
  does not otherwise disturb Spec 01's ownership of `user`.
- **`secondary_muscle_ids` has no DB-level referential integrity** — Postgres
  cannot FK array elements. Every element being a real `muscle_group.id` is
  enforced by the seed's Zod pass (§6.3) for curated rows and by the 03.2 create
  endpoint for custom rows. A join table or a `CHECK`-function is deferred unless
  the array proves error-prone.

## 5. API surface

Three read endpoints under `/v1`, all auth-required, all reusing the Spec 01
problem+json contract and the Spec 03.0 Zod-schema convention. Reference data is
served separately from the catalog (§12 D3). No single-resource
`GET /v1/exercises/{id}` (§12 D5). Behaviour — sync rules, `ETag`/`304`,
`updated_since` — is §6.1–6.2.

```
GET /v1/exercises[?updated_since=<rfc3339>]      auth required   (HEAD auto-added)
  200  { exercises: Exercise[], serverTime: string }   ETag: "<strong: cursor + content>"
  304  If-None-Match matched (full pull OR repeated delta), no body
  422  updated_since not a valid RFC 3339 instant      (validation-error)
  401  unauthenticated / invalid-token                 (Spec 01 contract)

GET /v1/muscle-groups                            auth required
  200  { muscleGroups: MuscleGroup[] }   ETag: "<strong>"   |   304

GET /v1/equipment                                auth required
  200  { equipment: Equipment[] }        ETag: "<strong>"   |   304
```

**Every response** (`200` and `304`) on all three endpoints carries
`Cache-Control: private, no-cache` and `Vary: Authorization` — the catalog `ETag`
is per-caller (custom rows join it in 03.2), so no shared or intermediary cache
may store or reuse it across users (§7). `no-cache` means "revalidate every
time", which is exactly the `If-None-Match` round-trip the design wants. It is
`no-cache`, **not `no-store`**: the browser HTTP cache may keep the body so a
later `304` rehydrates it without re-transferring the catalog. The SPA also
caches at the app layer (TanStack Query); both layers then revalidate cheaply.

**Response-schema declaration.** Each route declares only
`{ 200: <Zod schema> }`, matching `/v1/me`. `304` / `401` / `422` are produced by
Fastify conditional-request handling and the Spec 01 error handler and are **not**
separately declared — `assertRouteHasResponseSchema` is satisfied by the `200`,
and AC10 only checks the paths appear in the emitted doc. Declare the error codes
explicitly only if a consumer need for OpenAPI completeness emerges.

**`HEAD /v1/exercises`.** Fastify auto-adds it (`exposeHeadRoutes`); it runs the
same handler and MUST carry the same `ETag` and cache headers as the `GET`, so a
client that probes with `HEAD` before a conditional `GET` sees a consistent
validator (§6.1).

**DTOs** — authored as Zod in `@sin/core` (`dto/exercise.ts`), `camelCase`
(DESIGN §6), the same pattern as Spec 02's `MeSchema`. These are what the OpenAPI
document shows and what the client (05/06) parses.

```ts
// @sin/core — shared refine, reused by the seed input schema (§6.3) and 03.2
export const noControlChars = (s: string) => !/[\u0000-\u001F\u007F]/.test(s);
export const CatalogName = z.string().min(1).max(120).refine(noControlChars, "control characters not allowed");

export const ExerciseSchema = z.object({
  id: ExerciseIdSchema,                         // brandId("ExerciseId")
  catalogKey: z.string().min(1).nullable(),     // set for curated, null for custom
  ownerUserId: UserIdSchema.nullable(),         // null = global/curated
  name: CatalogName,
  modality: z.enum(MODALITY_VALUES),
  primaryMuscleId: z.string().nullable(),
  secondaryMuscleIds: z.array(z.string()),      // muscle_group ids; order per §6.1
  equipmentId: z.string().nullable(),
  isActive: z.boolean(),                        // false rows appear only in an updated_since delta
  createdAt: z.string().datetime({ offset: true }),
  updatedAt: z.string().datetime({ offset: true }),
});                                             // plain z.object → serializer allowlist (03.0 §6.5)
export type Exercise = z.infer<typeof ExerciseSchema>;

export const MuscleGroupSchema = z.object({ id: z.string(), name: z.string(), displayOrder: z.number().int() });
export const EquipmentSchema   = z.object({ id: z.string(), name: z.string(), displayOrder: z.number().int() });

export const ExercisesResponse = z.object({ exercises: z.array(ExerciseSchema), serverTime: z.string().datetime({ offset: true }) });
export const UpdatedSinceQuery  = z.object({ updated_since: z.string().datetime({ offset: true }).optional() });
```

The response serializer strips unknown keys (Spec 03.0 §6.5), so the `Exercise`
DTO is a field allowlist — a repo row object that also carries internal columns
cannot leak them onto the wire.

## 6. Behavior & logic

### 6.1 Catalog read + incremental refresh

**Caller visibility** for every read here is `owner_user_id IS NULL OR
owner_user_id = :actingUserId`, applied in the repository layer (Spec 01's
`actingUserId`-first convention). No custom rows exist in Spec 03.1, but the filter
is written now so 03.2 is purely additive, and a test (§10 AC5) inserts a
row owned by another user and asserts it never leaks.

**Security invariant:** the visibility filter is `AND`ed onto **every** query
path — the full pull, the `updated_since` delta, `findVisibleById`, and any count
used for an `ETag`. The delta query is `WHERE updated_at > :since AND
(owner_user_id IS NULL OR owner_user_id = :actingUserId)` — never the filter as
an `OR` sibling of the timestamp clause. §10 asserts a delta request as user A
never returns user B's changed rows.

**Repo lookup for later specs.** `exerciseRepository.findVisibleById(actingUserId,
id)` applies the same filter and returns the row or throws Spec 01's
`NotFoundError` (`404`, not `403`, on a miss — a probe can't tell "not yours"
from "absent"). Spec 05 uses it to validate `exercise_id` on a workout write; no
HTTP `GET /v1/exercises/{id}` endpoint is added here (§12 D5).

**Full pull** — `GET /v1/exercises`, no `updated_since`:

1. Select visible rows with `is_active = true`, ordered by `name COLLATE "C", id`
   — a **locale-independent** collation. A DB's `LC_COLLATE` otherwise differs
   between Testcontainers Postgres and Neon, so the two would order rows
   differently, produce different `ETag`s, and cause confusing test failures.
2. Serialise to the `Exercise` DTO — `camelCase`, keys in a fixed order,
   `secondaryMuscleIds` in a fixed order (see below).
3. `ETag` = `"` + first 32 hex of `sha256(cursor-sentinel ‖ wire-bytes)` + `"`,
   where `wire-bytes` is the exact serialized `exercises` array as sent on the
   wire. Two rules make it deterministic and correct:
   - **Hash the wire bytes, not repo rows.** The hash input is the array *after*
     the DTO serializer runs (Spec 03.0 §6.5) — so key order and the
     `timestamptz`→string form (µs-vs-ms truncation) can never disagree with what
     the client receives and re-hashes.
   - **Namespace by the delta cursor.** `<cursor-sentinel>` is the literal
     `updated_since` value on a delta, and a distinct fixed sentinel (e.g.
     `"full"`) on a full pull. Without it a delta can serialize to the exact same
     bytes as an earlier full pull (very likely with the ~10-row fixture),
     `If-None-Match` returns `304`, and the client skips a revision it should
     have applied.
   **`serverTime` is not in the hashed input** — two responses with the same
   payload at the same cursor but different `serverTime`s share an `ETag`, so
   `If-None-Match` works. The `ETag` is per-caller (custom rows join the payload
   in 03.2). *Empty-array case:* with the cursor folded in, an empty full pull and
   an empty delta produce different `ETag`s; even if they collided it would be
   harmless (client applies an empty change set).
4. If `If-None-Match` matches the `ETag` (RFC 9110 weak comparison — a `W/`
   prefix is ignored, `*` matches) → `304`, empty body (still send the
   `ETag`, `Cache-Control: private, no-cache`, `Vary: Authorization`). Else
   `200` with `{ exercises, serverTime }` and the same headers. The
   Fastify-generated `HEAD /v1/exercises` runs this same path and returns the
   identical `ETag` + headers with no body.
5. `serverTime` is **derived from the catalog data, not the wall clock.** The
   seed is the only writer in Spec 03.1, so `MAX(updated_at)` over the caller's
   visible rows *is* the timestamp of the last revision that touched anything.
   The full pull already scans every visible row, so the `MAX` is free — no
   separate table-wide aggregate:
   - rows visible →
     `serverTime = LEAST(transaction_timestamp(), MAX(updated_at))`;
   - no visible rows → `serverTime = transaction_timestamp()`.
   Then **truncate down to whole milliseconds** before it leaves the server
   (`date_trunc('milliseconds', …)` server-side, or `Math.floor` on epoch ms).
   That is the *only* rule — **there is no precision margin.** Truncating down can
   only leave the cursor equal-to or behind the true `updated_at`, never ahead, so
   there is no gap to protect against. Worst case the client re-fetches rows from
   the same millisecond and dedups by `id`. The `LEAST(transaction_timestamp(),
   …)` clamp means the server can never *emit* a future cursor.

   *Why this replaces `transaction_timestamp() − SYNC_LOOKBACK` (10 s):* during a
   deploy the serving read runs on the **old image**, which has no knowledge of
   the seed transaction. `transaction_timestamp()` alone can land past the new
   revision's `updated_at` but before the seed commits, handing the client a
   cursor it will never see that revision behind (for any row not touched again).
   "10 s > a seed transaction" is an assumption that decays as the catalog grows
   and under load. `MAX(updated_at)` **cannot outrun the data it is read from** —
   a read that can't see the seed's rows also can't see their `updated_at`, so the
   cursor stays at the previous revision until the seed is visible, atomically
   (§6.3's single `revisionTimestamp`). **Spec 03.2 revisits cursor derivation**
   once concurrent user writes mean `MAX(updated_at)` is no longer one writer's
   revision marker.

**Delta** — `GET /v1/exercises?updated_since=<rfc3339>`:

1. Parse `updated_since`; not a valid RFC 3339 instant → `422 validation-error`
   (via the Spec 03.0 Zod error mapping) with `errors: [{ path: "updated_since",
   … }]`. Bind the parsed value into the raw SQL **as `timestamptz`** — cast the
   RFC 3339 string in-query (`:updated_since::timestamptz`), **not** round-tripped
   through a millisecond-precision JS `Date`: the seed stamps `updated_at` at µs
   precision via `transaction_timestamp()`, and a ms round-trip can move the
   boundary across a revision.
2. Select visible rows with `updated_at > :updated_since::timestamptz` — **no
   `is_active` filter**: a row retired since the client's last sync must arrive as
   `{ …, isActive: false }` so the client drops it. (Symmetric for a future
   reactivation once 03.2 can un-retire — the client re-adds it.) Ordered by
   `name COLLATE "C", id`, same as the full pull.
3. `ETag` computed over the delta's wire bytes with `<cursor-sentinel>` = the
   `updated_since` value (same rule as the full pull, step 3); `If-None-Match` on
   a repeated identical delta → `304`, and a delta can no longer collide with a
   full pull.
4. `serverTime` is computed from **what this query already has** — no separate
   table-wide `MAX`:
   `serverTime = LEAST( transaction_timestamp(),
   GREATEST( :updated_since::timestamptz, MAX(updated_at) over the rows just
   returned ) )`, then truncated down to whole milliseconds (full pull step 5).
   - Non-empty delta → the newest returned row's `updated_at` is the correct new
     high-water mark.
   - Empty delta → `:updated_since` is echoed back: nothing has `updated_at >`
     the cursor, so it is still a valid "seen everything up to here" marker.
   - The `LEAST(transaction_timestamp(), …)` clamp means a client that *sends* a
     future or crafted cursor gets it clamped to server-now, not echoed forward —
     it heals on the next real revision instead of sticking forever.
5. Body `{ exercises, serverTime }`; `exercises` is `[]` when nothing changed.

**The `serverTime` cursor.** The client persists `serverTime` from its last good
response and sends it back verbatim as the next `updated_since`. It **always
overwrites** its stored cursor with the value just received — never
`max(stored, received)` (§3, "Consumers must note") — so a one-off future or
skewed cursor cannot wedge it. Two gaps and how they close:

- **Split revision.** The seed writes every row of one catalog revision with a
  **single, transaction-stable `updated_at`** (§6.3), so `updated_at > :since`
  includes a whole revision or none of it.
- **Read-vs-commit skew during a deploy.** A deploy runs the seed **while the
  previous image is still serving reads**, and that old image has no knowledge of
  the in-flight seed transaction. Deriving `serverTime` from `MAX(updated_at)`
  over visible rows (step 5) closes this by construction: a read that cannot yet
  see the seed's rows also cannot see their `updated_at`, so it returns the
  *previous* revision's timestamp and the client picks up the whole new revision
  on the next sync once it commits. There is **no time-based race margin and no
  precision constant** — the cursor is just `MAX(updated_at)` (clamped by
  `transaction_timestamp()`) truncated down to whole milliseconds, which can only
  land at or behind the true value. On staging the seed is a **manual** step with
  no old image serving concurrent reads (§8, §11, D12), so the deploy-time skew
  does not even arise there today; the derivation is what keeps it correct once
  automatic wiring lands. Deltas are still applied idempotently by `id`, and the
  `ETag` keeps the steady state a `304`. **Spec 03.2 revisits cursor derivation**
  when concurrent user writes exist.

**`secondaryMuscleIds` ordering.** Preserved as **authoring order** — the array
exactly as written in the seed JSON (or, later, as submitted to the 03.2 create
endpoint) — stored, returned, and fed to the `ETag` in that order. The curator
puts the more-relevant secondary muscle first; sorting would throw that away for
no gain, and a stable stored order keeps the `ETag` deterministic without a
sort step. (§12 D11.)

**Bounded-set assumption.** The un-paginated full pull, and the per-request
`sha256` over the payload, are only safe because the caller-visible set is
bounded: curated globals are a few hundred rows and a user's custom rows are
capped (§7, enforced in 03.2). If that assumption is ever violated — an
unbounded custom count, or a global catalog that grows past ~1–2k rows —
`GET /v1/exercises` must be retrofitted with cursor pagination before the cap is
lifted. Recorded so the constraint is explicit, not implicit.

### 6.2 Reference endpoints

`GET /v1/muscle-groups` → `{ muscleGroups: [{ id, name, displayOrder }] }`
ordered by `displayOrder` then `id COLLATE "C"` (the `id` is `TEXT`, so the
tiebreak needs the locale-independent collation for the same reason as the
exercise list — §6.1); `GET /v1/equipment` symmetric. Each carries
its own strong content `ETag`, honours `If-None-Match` → `304`, and sends
`Cache-Control: private, no-cache` + `Vary: Authorization` (the data is the same
for every user, but the response is auth-gated, so shared caching stays off for
consistency). No `updated_since` — the tables are tiny and change only on a
deploy, so a client re-fetches whenever its `304` check misses. Auth required
(consistent with `/v1`; nothing here is public — the OpenAPI doc is the one
public thing, Spec 03.0 §7).

### 6.3 Seed algorithm (release step, idempotent)

Input: JSON files under a **catalog directory that is a parameter** — an optional
CLI arg / env var defaulting to `apps/api/prisma/catalog/` (§12 D8), the same
pattern 03.0's purity check adopted for its optional dir arg. Files:
`muscle-groups.json`, `equipment.json`, `exercises.json`; the exercise file holds
global rows only and every entry has a `catalog_key`. The directory **must** be a
parameter so AC4 can point the seed at fixture directories containing
deliberately-broken data — hardcoding the path would make those tests impossible.

The seed is a **plain script** (`apps/api/prisma/seed.ts`, run explicitly by
`pnpm --filter @sin/api run seed:catalog`) — **not** wired to Prisma's
`prisma.seed` hook, so a dev `prisma migrate reset` does not silently run it. For
M1/staging it is a **manual release step** run by the operator right after
`prisma migrate deploy` (§8, §11, D12); automatic wiring waits for Spec 01.1 / the
paid plan. It first parses **every row against a Zod input schema** and aborts
before touching the DB on any failure. **The input schema is stricter than the
`exercise` table:** `catalogKey`, `primaryMuscleId`, and `modality` are
*required* (the table makes the first two nullable only for 03.2 custom rows);
`name` reuses the shared `CatalogName` refine from `@sin/core` (§5 — `1..120`
chars, no C0/DEL control characters), the same constraint 03.2 applies to user
input; and every `primaryMuscleId` / `equipmentId` / `secondaryMuscleIds[]` is
checked against the reference rows just loaded from the other two files.

It then runs in **one transaction**, stamping every write in the run with a
single `revisionTimestamp` = the transaction-stable clock (`now()` /
`transaction_timestamp()` — **not** `clock_timestamp()`), so all rows of the
revision share one exact `updated_at` (the split-revision guarantee in §6.1
depends on this):

**Reference rows** (`muscle_group`, `equipment`): `INSERT … ON CONFLICT (id) DO
UPDATE` the display fields (`name`, `display_order`) — pure labels, no history
semantics, safe to update in place. (`updated_at` bumps every run; harmless —
not in any DTO, so reference `ETag`s stay stable; AC4's "same row set" compares
DTO-projected columns.)

**Reference codes are immutable once shipped.** A `muscle_group` / `equipment`
`id` is never removed from the JSON files and never renamed in place — these
tables have **no `is_active` column** and `exercise` rows reference the codes by
value. Retiring or renaming a code is a deliberate data migration (add the new
code, migrate referencing `exercise` rows, then drop the old — D3), not a seed
edit. If the seed finds a DB reference row with no matching file entry it **logs a
warning and leaves the row** (mirroring the exercise-row "absent from file" rule
below), never deletes it.

**`exercise` rows**, keyed by `catalog_key`:

| Data file vs DB | Action |
|---|---|
| in file, not in DB | `INSERT` new row, `is_active = true`, fresh UUIDv7 `id`, `updated_at = revisionTimestamp` |
| in file & DB, `name` + `modality` unchanged, other fields differ | `UPDATE` the non-identifying fields, `updated_at = revisionTimestamp` |
| in file & DB, `name` **or** `modality` changed | **abort the whole seed** with a message naming the `catalog_key` — an identifying change to a live global row must be modelled in the data file as *retire the old key + add a new key* (DESIGN §4.2) |
| in DB, entry marked `retired: true` in the file | `UPDATE is_active = false, updated_at = revisionTimestamp`; every other column untouched |
| in DB, absent from the file | leave as-is, log a warning (a row should be explicitly `retired`, never dropped from the file) |
| not in DB, entry marked `retired: true` | skip with a warning — a row that never shipped gets no tombstone (implementation decision 2026-09-09) |

The "identifying change ⇒ hard abort" rule makes the append-only invariant
impossible to breach by editing a data file — the most likely mistake.

**The seed does *not* use `INSERT … ON CONFLICT (catalog_key)` for `exercise`
rows** — it does the explicit read-then-branch above (SELECT by `catalog_key`,
then INSERT / UPDATE / abort). Two reasons: the branch logic (abort on an
identifying change) can't be expressed as an upsert anyway; and `catalog_key`'s
uniqueness is a **partial** index (`WHERE owner_user_id IS NULL`), so an
`ON CONFLICT (catalog_key)` target would need the predicate repeated
(`ON CONFLICT (catalog_key) WHERE owner_user_id IS NULL`) or PG raises *"no unique
or exclusion constraint matching the ON CONFLICT specification"*. Stated here so
nobody "optimizes" the read-then-branch into a broken upsert.

**Un-retiring** a global row (a curated row wrongly retired, now to be brought
back) is deliberately *not* a seed branch here — it is mistake-correction, needs
a review, and belongs with the write path in Spec 03.2. The v1 seed only ever
adds or retires.

## 7. Security & privacy

- **Authorization boundary.** Every read filters `owner_user_id IS NULL OR
  owner_user_id = :actingUserId` in the repository layer, `AND`ed onto every
  query path including the `updated_since` delta (§6.1 security invariant).
  Exercised now by a test that inserts a row owned by another user and asserts it
  never appears in the caller's full pull **or** delta — the regression guard for
  when 03.2 makes custom rows real.
- **Cross-tenant cache safety.** The catalog `ETag` is per-caller (custom rows in
  03.2), so all three endpoints send `Cache-Control: private, no-cache` +
  `Vary: Authorization` (§5, §6.1–6.2). No shared/intermediary cache — a future
  CDN, a corporate proxy — may store one user's catalog and serve it to another.
  A test asserts the headers are present on `200` and `304`.
- **Response is a field allowlist.** The Spec 03.0 serializer strips unknown
  keys, so the `Exercise` / `MuscleGroup` / `Equipment` DTOs are the wire
  contract — a repo row that also carries internal columns cannot leak them.
- **No single-object endpoint** (§12 D5) → no `{id}` enumeration surface here.
  When 03.2 adds one, a miss returns `404` (not `403`) so a probe can't tell
  "not yours" from "absent" (DESIGN R8).
- **`name` is stored verbatim, but bounded.** The API does **not** HTML-sanitise
  `name` (rendering-time output encoding is Spec 06's job — a stored value must
  round-trip unchanged). The shared `@sin/core` `CatalogName` refine (§5) caps it
  at `1..120` chars and rejects C0/DEL control characters; it gates the seed
  (§6.3) and 03.2 custom input, limiting abuse and payload bloat at the point of
  entry.
- **No PII.** The catalog and reference tables are curated, non-personal data.
- **Abuse / resource bounds.** All three endpoints are read-only, auth-gated, and
  cheap in steady state (`updated_since` deltas, `304`). The full pull is
  un-paginated, so its cost — and the per-request `sha256` — scale with the
  caller-visible row count. Curated globals are bounded by curation; a user's
  **custom** rows must be capped: **03.2 ships a hard per-user custom-exercise
  limit (e.g. 500), independent of the Spec 05 rate limiter**, precisely because
  there is no pagination to fall back on. Until 03.2, no user can create custom
  rows, so the read is bounded by the curated set. The general write limiter
  stays Spec 05's cross-cutting deliverable. (§6.1 "bounded-set assumption".)
- **Seed integrity.** The append-only invariant is enforced in code (§6.3): an
  identifying change to a live global row aborts the release, so a bad data-file
  edit cannot rewrite history users have workouts against. The seed runs with
  `DATABASE_URL` write credentials as an isolated release step; its inputs are
  repo-reviewed JSON.

## 8. Config & secrets

**No new environment config, and no correctness constant.** The old
`SYNC_LOOKBACK` (10 s) is gone; there is no `CURSOR_PRECISION_MARGIN` either.
`serverTime` is derived from `MAX(updated_at)` over the data and **truncated down
to whole milliseconds** before it leaves the server (§6.1, D4) — truncating down
can only put the cursor at or behind the true value, so there is nothing to tune
and no "how long does a seed take" guess to encode.

The seed is a dedicated command (`pnpm --filter @sin/api run seed:catalog`) that
reuses `DATABASE_URL`, takes an **optional catalog-directory arg** (§6.3,
defaulting to `apps/api/prisma/catalog/`), and needs no config of its own. **For
M1 it is a manual release step**, documented in `docs/runbooks/first-deploy.md`
alongside the manual `prisma migrate deploy` — Render's free plan has no
pre-deploy hook (CLAUDE.md), which is also why the migration is manual today. It
is idempotent by construction (§6.3), so it is simply re-run on every deploy; a
"only when files changed" optimisation is unnecessary. Automatic wiring (a
`preDeployCommand` or a release job) lands with Spec 01.1 / the paid plan (D12).
Under a manual seed there is **no old-image-serving-reads window** on staging —
the operator runs migrate + seed, then the new image starts — so the deploy-time
read-vs-commit skew (§6.1) does not even arise today; the data-derived cursor is
what keeps it correct once the step is automated.

## 9. Observability

The Spec 01 request log (`request_id`, `user_id`, status, duration) covers these
routes. This spec adds:

- **Catalog cache-hit signal.** Log/count `GET /v1/exercises` outcomes as `full`
  (200, no param) / `delta` (200, `updated_since`) / `not-modified` (304), plus
  the delta row count. Healthy steady state is mostly `304` + small deltas; a
  high `full` rate means clients aren't persisting `serverTime` and the
  DESIGN §5.2 delivery design isn't paying off.
- **Seed run summary.** One structured line —
  `{ inserted, updated, retired, unchanged, skipped, revisionTimestamp }` —
  and a non-zero exit naming the offending `catalog_key` on an append-only
  violation or Zod failure.
- No traces/metrics backend yet (Spec 13); these are log fields.

## 11. Deployment & rollback

No feature flag — the endpoints are new, so "off" is the absence of callers
(Spec 04/05).

**Release ordering** (extends Spec 01 §11):

1. `prisma migrate deploy` applies `0002_create_exercise_catalog` — additive /
   expand-only, so the still-running pre-deploy code tolerates the new tables.
   For Neon, run against the **direct** (non-pooler) host (CLAUDE.md).
2. `pnpm --filter @sin/api run seed:catalog` runs **after the migration**. For
   M1/staging this is a **manual step in `docs/runbooks/first-deploy.md`** — same
   status as the manual `prisma migrate deploy` (Render's free plan has no
   pre-deploy hook, CLAUDE.md). The operator runs migrate, then seed, then lets
   the new image start, so there is **no window where the old image serves reads
   against a half-committed seed**. When this is later automated
   (`preDeployCommand` or a one-off job, with Spec 01.1 / the paid plan — D12) the
   old image *does* serve concurrent reads during the seed; the data-derived
   `serverTime` (`MAX(updated_at)`, §6.1 / D4) is what makes that safe, not a time
   margin. The seed is idempotent, so every deploy re-runs it. A seed failure
   (append-only violation, Zod error) aborts the deploy.
3. New code goes live; the three read endpoints start serving and appear in
   `/openapi.json`.

**OpenAPI emit + drift check** are build/CI-time only (Spec 03.0) — no runtime
component.

**Rollback.** Revert the code commit. The three tables and seeded rows are inert
with no consumer until Spec 05, so a straight `git revert` is safe; the down
migration need not be run (if it is, it drops the tables — no data worth
keeping). The catalog routes vanish from the next `/openapi.json` emit.

## 12. Decisions & open questions

### Resolved

- ✅ **D1 — Spec 03.1 is read-only; writes are Spec 03.2.** 03.1 ships the three
  tables, the global seed, `ExerciseId`, and the read endpoints. 03.2 adds
  `POST /v1/exercises` (custom create) and the copy-on-write `PATCH` / `DELETE`
  fork of a global row. The contract pipeline that was also bundled here is now
  **Spec 03.0** (extracted on the `architect` review — it has no catalog
  dependency and is the riskier infrastructure). Read-only catalog is
  independently shippable and is all Spec 04's shell and Spec 05's logging need;
  the write path is only consumed by the Spec 06 picker. *(Applied
  2026-09-03:* `specs/README.md` row `03.1` = "Exercise catalog — read" (depends
  `01, 02, 03.0`), row `03.2` added, milestone mapping `M1 = 02, 03.0, 03.1,
  03.2, 05, 06`.*)*

- ✅ **D2 — the global catalog loads via an idempotent seed script, run as a
  release step**, keyed on `catalog_key`, `INSERT`/retire only, never mutating a
  live global row's `name`/`modality` (aborts instead — §6.3). Reference tables
  seeded by the same script. Chosen over data-only SQL migrations (every future
  catalog edit becomes a migration) and a migration/script hybrid. Stable key
  column named **`catalog_key`**.

- ✅ **D3 — `muscle_group` / `equipment` use a `TEXT` natural-code PK**
  (`chest`, `barbell`), served by their **own endpoints** (`GET /v1/muscle-groups`,
  `GET /v1/equipment`), each independently `ETag`d, rather than bundled into
  `GET /v1/exercises`. TEXT codes are self-describing and stable for the seed;
  separate endpoints keep each cache independent. Cost: three requests on a cold
  first launch; codes chosen up front (renaming one is a data migration).
  **Reference codes are immutable once shipped** (added 2026-09-08, finding 5): a
  code is never removed from the JSON files or renamed in place — these tables
  have no `is_active` and `exercise` rows reference codes by value. Retiring or
  renaming one is a deliberate three-step data migration (add new, migrate
  referencing rows, drop old). The seed **logs, never errors,** on a DB reference
  row absent from the file — mirroring the exercise-row rule (§6.3).

- ✅ **D4 — `GET /v1/exercises` is a single un-paginated response with a strong
  content `ETag` and a `serverTime` delta cursor.**
  - **No pagination** — a documented exception to DESIGN §6, justified by §5.2
    (bounded catalog, pulled whole into a local cache). DESIGN §6 gains one
    sentence (§11).
  - **`ETag`** = truncated `sha256` over `cursor-sentinel ‖ wire-bytes` (the
    exact serialized `exercises` array), *excluding* `serverTime`.
    Refined 2026-09-08 (findings 2–3): hash the post-serializer wire bytes (not
    repo rows, so key order / timestamp string form can't disagree with the
    payload); fold the `updated_since` value in (a distinct sentinel for the full
    pull) so a delta can't collide with an earlier full pull and cause a spurious
    `304`; row order is `ORDER BY name COLLATE "C", id` — locale-independent,
    since `LC_COLLATE` differs between Testcontainers PG and Neon. Same
    `COLLATE "C"` on the reference-table `id` tiebreak. Per-caller (custom rows in
    03.2).
  - **`updated_since`** selects `updated_at > :since::timestamptz` (cast
    in-query, not via a millisecond-precision JS `Date`) over the visibility
    filter, **including** `is_active = false` rows. Malformed → `422`; future →
    empty delta whose `serverTime` is clamped to server-now, never the future
    input (see the `serverTime` bullet).
  - **`serverTime`** is **derived from the catalog data, not the wall clock**
    (revised 2026-09-08, findings 1 + review pass 2). Computed from what each path
    already scans — **no separate table-wide `MAX`**:
    - full pull → `LEAST( transaction_timestamp(), MAX(updated_at) over all
      visible rows )` (or `transaction_timestamp()` when none are visible);
    - delta → `LEAST( transaction_timestamp(), GREATEST( :updated_since,
      MAX(updated_at) over the rows just returned ) )` — a non-empty delta lifts
      the cursor to the newest returned row, an empty delta echoes `:updated_since`
      back (still a valid "seen up to here" marker).
    Then **truncate down to whole milliseconds** before it leaves the server.
    That is the only rule: **no `CURSOR_PRECISION_MARGIN`, no `SYNC_LOOKBACK`.**
    Truncating down can only leave the cursor at or behind the true `updated_at`,
    never ahead. The `LEAST(transaction_timestamp(), …)` clamp means the server
    can never *emit* a future cursor even if a client *sends* one — a skewed or
    crafted `updated_since` is clamped to server-now and heals on the next real
    revision instead of sticking forever. The incoming cursor string is bound
    directly as `:updated_since::timestamptz`, never parsed into a ms-only JS
    `Date` first (which can round up). Revision atomicity (one `updated_at` per
    seed run — §6.3) still closes the split-revision gap; `MAX(updated_at)` cannot
    outrun the data it is read from, so the old-image-serving-reads skew is closed
    by construction. The client **always overwrites** its cursor with the received
    `serverTime`, never `max(stored, received)` (§3). **Spec 03.2 revisits cursor
    derivation** once concurrent user writes exist.

- ✅ **D5 — no single-resource `GET /v1/exercises/{id}` HTTP endpoint in Spec
  03.1.** The client works from its cached full catalog; Spec 05 validates
  `exercise_id` on a write via the `exerciseRepository.findVisibleById` repo
  lookup (§3, §6.1), not an HTTP round-trip. The `{id}` *endpoint* is added in
  03.2 (or later, for deep links / cold-cache history).

- ✅ **D6 — `modality` is `TEXT` + a `CHECK` constraint**, list from `@sin/core`
  `MODALITY_VALUES`, matching Spec 01's `unit_preference`. Not a Postgres `enum`
  type: the vocabulary is append-only and expected to grow (DESIGN §4.2),
  `ALTER TYPE` is transaction-hostile under Prisma Migrate and value removal is
  unsupported; a `CHECK` swap in a migration is routine. AC2 adds a drift-guard
  test since the `CHECK` literal is a second copy of the list; a vocabulary
  change is a new migration.

- ✅ **D7 — the contract pipeline (Zod source of truth → OpenAPI) is Spec 03.0.**
  Extracted from this spec on the `architect` review. All pipeline mechanics,
  the `/v1/me` migration, and the DESIGN §6/§7 reframe live there. Spec 03.1 just
  authors its DTOs as Zod in `@sin/core` and its routes appear in the emitted
  document (AC10).

- ✅ **D8 — seed data is JSON files under `apps/api/prisma/catalog/`**
  (`muscle-groups.json`, `equipment.json`, `exercises.json`), validated against
  a Zod input schema on load (§6.3). Plain data — diffable, hand-editable,
  generatable by a future admin tool — with load-time type safety, chosen over a
  typed TS module (code in a data role) and CSV (weak typing, awkward arrays).
  **Spec 03.1 ships against a ~10-exercise fixture catalog** (a handful of
  muscle groups + equipment codes) so the one session is mechanism + endpoints +
  tests. The **full v1 catalog** — `~50` exercises, `~12` muscle groups, `~10`
  equipment types, and the natural-code vocabularies — is an **immediate
  data-only follow-up PR**: a new/expanded JSON file plus a re-run of the
  idempotent append-only seed, no code review. This keeps the risky curation
  work off the critical path without leaving a stub — the fixture catalog is real
  data, just small.

- ✅ **D10 — security hardening baked into the read design** (from the
  design-level security review, 2026-09-03):
  - All three endpoints send `Cache-Control: private, no-cache` +
    `Vary: Authorization` — the catalog `ETag` is per-caller, so no shared cache
    may cross users (§5, §7).
  - The visibility filter is `AND`ed onto **every** query path, delta included —
    a stated invariant with a delta-isolation test (§6.1, AC5).
  - Response bodies are field allowlists via the Spec 03.0 serializer (§6.5).
  - `name` is stored verbatim but the shared Zod DTO bounds it (`1..120`, no
    control chars); output encoding is Spec 06's job (§7).
  - The un-paginated full pull is only sound for a **bounded** caller-visible
    set: **Spec 03.2 must ship a hard per-user custom-exercise cap** (≈500),
    independent of the Spec 05 rate limiter, or add pagination before lifting it
    (§6.1 "bounded-set assumption", §7).
  - `GET /openapi.json` (Spec 03.0) excludes probe/health routes and internal
    host names; it is the only anonymous endpoint.

- ✅ **D11 — `secondaryMuscleIds` is stored and returned in authoring order**,
  not sorted (§6.1). The curator orders by relevance; sorting discards that. A
  stable stored order also keeps the content `ETag` deterministic with no sort
  step. The 03.2 create endpoint likewise preserves submitted order.

- ✅ **D12 — for M1 the catalog seed is a manual release step; automatic wiring
  waits for Spec 01.1 / the paid plan** (resolved 2026-09-08, finding 4). §8
  originally said the seed "runs on every deploy" while §11 deferred the wiring —
  and Render's free plan has no pre-deploy hook (CLAUDE.md), which is why
  `prisma migrate deploy` is already manual on staging. Resolution: the operator
  runs `pnpm --filter @sin/api run seed:catalog` (against the direct Neon host)
  right after `prisma migrate deploy`, as a documented step in
  `docs/runbooks/first-deploy.md`. Consequence: on staging there is **no window
  where the old image serves reads against a half-committed seed**, so the
  deploy-time read-vs-commit skew (§6.1) does not arise today — the data-derived
  `serverTime` (D4) is what keeps it correct once a `preDeployCommand` or one-off
  job automates the step. Rationale for not automating now: it matches the
  existing manual-migration posture, needs no new infra, and the seed is
  idempotent so a missed run self-corrects on the next deploy.

- ✅ **D13 — the delta cursor is an `updated_since` query parameter, not the
  `If-Modified-Since` request header** (resolved 2026-09-08, finding 15).
  `If-Modified-Since` is second-granularity (the seed stamps `updated_at` at µs
  precision) and, more fundamentally, cannot express "include rows retired since
  this time" — the delta must return `is_active = false` rows so the client drops
  them, which a conditional-GET header has no way to signal. A first-class query
  parameter also keeps the delta visible in logs and network tools. The `ETag` /
  `If-None-Match` pair is still used, for the orthogonal "nothing changed at all"
  `304` fast path.
