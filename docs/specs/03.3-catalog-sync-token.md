## 1. Purpose, scope & non-goals

Spec 03.1's `?updated_since=<rfc3339>` / `serverTime` cursor is a
timestamp taken before a write's commit becomes visible. Under concurrent
writers — any mix of `POST`/`PATCH`/`DELETE /v1/exercises*` (Spec 03.2) and the
catalog seed (Spec 03.1 §6.3) — a delta's cursor can advance past a
still-uncommitted row via a *different*, already-visible row, and that row is
then permanently skipped by every later delta. BL-1 documents the concrete
same-caller sequence; the seed variant is worse (an entire catalog revision can
be skipped for any user who wrote during the seed's 60 s transaction).

This spec replaces the timestamp cursor with a **commit-ordered sync token**
derived from the Postgres snapshot horizon (`pg_snapshot_xmin`), stamped by a
trigger so no write path can forget it. It is a data-model + behavior fix to an
existing, not-yet-consumed contract — not a new feature.

### In scope

- Migration `0004_exercise_change_xid` (additive/expand-only): a
  `change_xid xid8 NOT NULL` column on `exercise` (added in one statement, so
  existing rows are stamped by the column default), a BEFORE INSERT OR UPDATE
  trigger that re-stamps it on every later write, plus a supporting index.
- Replacing the delta cursor and its wire representation: `?updated_since=`
  → `?since=`; `serverTime` → `syncToken`; an opaque `"1.<xid>"` token.
- A new `410 sync-token-expired` error for a token ahead of the server's
  current snapshot; `422 validation-error` for a malformed token (unchanged
  status, new predicate).
- The `@sin/core` DTO/query renames this implies
  (`UpdatedSinceQuery` → `CatalogSinceQuery`, `isPostgresTimestamptz` →
  `isSyncToken`) and their knock-on OpenAPI drift-check delta (including the
  regenerated root `openapi.json`).
- The repository/route changes in §5 ("Repository and route changes"): the
  single-statement catalog read, the `410`, and the `serverTime` → `syncToken`
  plumbing. Every existing write path (create, fork, patch, soft-delete, seed
  insert/update/retire) stamps `change_xid` mechanically via the trigger, not
  per-call-site code.
- The consumer rules a client needs to make `410` actually self-heal (§3), and
  a Prisma-model/migration drift check (§4, AC1).

### Non-goals

- **The restore-epoch hardening** discussed in the design comment (§12,
  Open) — deferred, with a hard trigger (D27: before the Spec 15 cutover);
  the versioned `"1."` token prefix is chosen so it can be added later
  without a breaking change.
- **`idle_in_transaction_session_timeout` on the app role** — recommended as a
  small, independent follow-up (§8), not shipped in this PR.
- **Any change to `updated_at`, its index, or its role in the `Exercise` DTO**
  — it stays exactly as-is: application-stamped, shown for display/"last
  edited", included in the ETag hash. It simply stops being a sync input.
- **No new consumer.** As of this spec, nothing calls `GET /v1/exercises`
  outside its own test suite — verified by grep: `apps/api/scripts/smoke.ts`
  has no reference to `exercises`/`updated_since`/`serverTime`, and the only
  hit under `apps/web/src/api/` is a unit test of the cache-key `routeTemplate`
  helper that uses `/v1/exercises?updated_since=...` as a generic example URL,
  not a real call site. This is why the breaking rename is nearly free right
  now and gets more expensive every release the picker (Spec 06) waits.

## 2. Acceptance criteria

1. **Migration `0004_exercise_change_xid` applies cleanly, is additive, and
   matches the Prisma model.** On a fresh DB and on top of `0003`: adds
   `change_xid xid8 NOT NULL DEFAULT pg_current_xact_id()` (one statement — no
   nullable window, no separate backfill), the `exercise_stamp_change_xid()`
   trigger function, the `exercise_change_xid` `BEFORE INSERT OR UPDATE`
   trigger, and `exercise_change_xid_idx`. Rows that exist before the
   migration all carry a non-null `change_xid` afterward. The still-running
   pre-deploy (old) image tolerates the new column/trigger/index — its
   `INSERT`s omit `change_xid`, the trigger stamps it before the `NOT NULL`
   check runs, and its `UPDATE`s re-stamp it, so every row is stamped before
   the new image goes live. After all migrations are applied, a
   `prisma migrate diff` from the migrated database to `schema.prisma`
   (`--exit-code`) reports no drift (D30). Testcontainers migration test.
2. **Every write path stamps `change_xid` via the trigger, not per-call-site
   code.** `createExercise`, `forkExercise`, `updateExercise`,
   `deleteExercise` (soft-delete `UPDATE`), and every seed write (insert,
   non-identifying update, retire) leave a non-null `change_xid` that is
   `>=` the horizon (`pg_snapshot_xmin(pg_current_snapshot())`) sampled just
   before the write, with no change to those statements' column lists. All
   writes of one seed revision share one `change_xid` (one transaction, one
   xid). No row has `change_xid IS NULL` (integration + migration test).
3. **The token comes from the same statement as the rows it describes.** Both
   the full pull and the delta compute
   `pg_snapshot_xmin(pg_current_snapshot())` in the identical query that scans
   `exercise`, including when the result set is empty — replacing the current
   `findCatalogDelta` empty-delta fallback, which runs a **second**, later
   query and would reintroduce a skip if reused here. Verified two ways: a
   repository unit test spies the Prisma client and asserts exactly one
   `$queryRaw` per catalog read (full, delta, and empty delta), and an
   integration test pins the Postgres semantic the design relies on (§10).
4. **`?since=<token>` returns a correct delta.** Visible rows with
   `change_xid >= :since` — no `is_active` filter, so a retired row still
   arrives as a tombstone, unchanged from today. No `since` param behaves as
   today's full pull (`is_active = true` only), with the same token derivation
   rule as the delta. The retired `?updated_since=` name is ignored like any
   unknown query key and yields a full pull (pinned by a test). `HEAD
   /v1/exercises` mirrors `GET` exactly, same as today.
5. **The #23 regression is fixed.** Connection L holds
   `pg_advisory_xact_lock(hashtext(userId))`; a `createExercise` call blocks
   inside its transaction behind it; a concurrent `updateExercise` on a
   different owned row commits with no lock; a delta pull runs and returns a
   token; L is released and the blocked create then commits. The **next**
   delta must contain the created row. The same interleaving, written against
   the current timestamp-cursor implementation, is run once as a recorded TDD
   red step (its failure output goes in the PR description); the permanent
   test targets the new API.
6. **The seed-transaction variant is fixed.** A seed-style transaction updates
   a global row and stays open past its statement; a concurrent user `PATCH`
   commits; a delta pull runs; the seed transaction then commits. The next
   delta must contain the global row's revision.
7. **An empty delta uses the same snapshot as its (absent) rows.** A delta
   that returns zero rows while another transaction commits during the same
   statement must not skip that commit on the *next* delta — pins the
   single-statement token rule (AC3) specifically for the zero-row case,
   which is the code path most likely to regress back to a second query.
8. **Future and malformed tokens are rejected, on `GET` and `HEAD`.** A
   `since` value whose xid exceeds the current snapshot's `xmax` →
   `410 sync-token-expired` (problem+json, `SyncTokenExpiredError`), with
   `Cache-Control: no-store` (a `410` is heuristically cacheable; a cached one
   would keep a healed client failing). A `since` value that fails the wire
   format (`^1\.(0|[1-9]\d{0,18})$` — at most 19 digits, so it always fits an
   `xid8`, and canonical, so two spellings of one token can't yield two
   `ETag` sentinels) → `422 validation-error` with
   `errors: [{ path: "since", … }]`. No submitted value can reach Postgres and
   fail the `::xid8` cast as a `500`. Both checked on
   `GET /v1/exercises?since=...` and the Fastify-generated `HEAD`.
9. **`ETag`/`304` behavior is preserved under the rename.** The cursor
   namespace-sentinel folded into the hash (Spec 03.1 §6.1 and its D4) is now
   the `since` token value (or the fixed `"full"` sentinel for a full pull) —
   same rule, renamed input. The assertions of Spec 03.1 AC7 hold under the
   new names: `syncToken` is excluded from the hash, so a response that
   differs only in its `syncToken` keeps the same `ETag`; `304` on a repeated
   identical request; `ETag` differs after a real change; cache headers on
   `200` and `304`.
10. **`@sin/core` ships the renamed/added exports.** `CatalogSinceQuery`
    (`{ since: <string matching ^1\.(0|[1-9]\d{0,18})$>.optional() }`, built
    with `.regex()` so the OpenAPI emit carries the `pattern`) replaces
    `UpdatedSinceQuery`; `ExercisesResponse.syncToken` replaces `.serverTime`;
    `isSyncToken` is added; `isPostgresTimestamptz` is removed (no remaining
    caller). Unit tests: `isSyncToken` accepts `"1.0"`, `"1.736"` and the
    19-digit maximum; rejects `"736"`, `"1.-1"`, `"1.abc"`, `"1.01"` (leading
    zero), `"1.99999999999999999999"` (20 digits), `"2.736"` and `""`. OpenAPI
    emit + CI drift check reflect the renamed query param, its `pattern`, and
    the renamed response field.
11. **`updated_at` is unaffected.** It keeps being application-stamped on
    every write, stays in the `Exercise` DTO, stays in the ETag hash, and
    `exercise_updated_at_idx` is not touched by `0004` (kept this release —
    the old image still filters on it; dropping it is a separate later
    release once no code path reads by it).
12. **Docs stay consistent with the shipped behavior** — verified by review of
    the PR's doc diff against §11's list below (DESIGN.md, Specs 03.0 / 03.1 /
    03.2, `docs/backlog.md`, the README rows, the seed header comment, and the
    regenerated `openapi.json`); `docs/specs/README.md`'s 03.3 row updated to
    "Implemented".

## 3. Dependencies & exposed interface

### Needs

- **Spec 03.1** — the `exercise` table, `GET /v1/exercises` route, the
  visibility filter, the `ETag`/`304` helpers (`strongEtag`, `ifNoneMatchHits`,
  `addVary`), the Testcontainers integration harness.
- **Spec 03.2** — the write paths (`createExercise`, `forkExercise`,
  `updateExercise`, `deleteExercise`) whose `INSERT`/`UPDATE` statements the
  new trigger attaches to; the shared `AppError` hierarchy and problem+json
  mapper this spec adds `SyncTokenExpiredError` to.
- **Postgres ≥ 13** for `xid8`/`pg_current_xact_id()`/`pg_current_snapshot()`.
  Both CI (Testcontainers) and Neon run 16 — no version change needed.
- **Sync reads must run on the primary** (D32). A read replica's snapshot lags
  the primary's, so a token issued by the primary would look "ahead of the
  server" to a lagging replica and draw a false `410`. Today there is a single
  Neon endpoint and no replica; if one is ever added, `GET /v1/exercises` stays
  on the primary.

### Provides — stable surface (changes here are breaking)

This spec **changes**, not extends, the surface Spec 03.1 §3 listed as
"Provides": `GET /v1/exercises`'s query param and response cursor field are
renamed and the cursor's wire type changes from an RFC 3339 timestamp to an
opaque token string. Per §1's non-goals, this is safe to do as a breaking
rename **only because there is currently no consumer** (verified above); this
is the last point at which that is true, since Spec 06 is the next spec to
actually call this endpoint.

| Export | Shape | Consumed by |
|---|---|---|
| `GET /v1/exercises` (`?since=`, `syncToken` response field) | catalog DTO (renamed fields) | 06 (the exercise picker is the first real consumer; Spec 05 resolves ids via `findVisibleById` and does not sync) |
| `CatalogSinceQuery`, `ExercisesResponse` (updated), `isSyncToken` (`@sin/core`) | Zod DTO + type | 06 |
| `SyncTokenExpiredError` (`apps/api/src/errors/app-error.ts`) | `AppError` subclass, 410 | route error mapping only — no other spec consumes it directly |

**Consumers must note:**
- **The client rule is unchanged**: always overwrite the stored cursor with
  the `syncToken` from the latest good `200` response; never `max(stored,
  received)`. A **`304` carries no body, so the client keeps its stored
  token** (safe: the next delta re-sends rows, never skips them). A `410`
  means "your stored token is unusable — discard it and do a full pull," not
  "clamp and continue" (there is no clamp for a future token in this design,
  unlike the old `serverTime`'s clamp-a-future-input behavior, which no longer
  applies).
- **The post-`410` full pull must bypass the HTTP cache** (e.g. `fetch(url,
  { cache: "reload" })`). The `ETag` deliberately excludes `syncToken` (so an
  unchanged catalog still gets a `304`), and the route is `no-cache` +
  `ETag`, so a browser revalidates and, on a `304`, hands the app its cached
  `200` body — whose `syncToken` is the stale, future token that caused the
  `410`. After a database restore the catalog bytes are often identical, so
  without `reload` the client would loop `410` → full pull → `304` → same
  stale token → `410`.
- **The token is opaque.** A consumer must not parse, compare, or derive
  anything from its contents beyond storing and replaying it verbatim. The
  `"1."` prefix exists so the *server* can change the encoding later; a client
  that assumes a numeric suffix format ties itself to today's implementation.
- `exerciseRepository.findVisibleById` (Spec 03.1 §3) is untouched — it does
  not participate in sync at all.

## 4. Data model

Extends the `exercise` table (owned by Spec 03.1, extended by 03.2 and now by
this spec). Migration **`0004_exercise_change_xid`** — additive, hand-authored
SQL (matching `0002`/`0003`'s convention: a trigger and its function are
not expressible as declarative Prisma DSL).

```sql
-- Spec 03.3 §4 — 0004_exercise_change_xid. Additive, expand-only.
-- Down (test teardown / local `migrate reset` only, never production —
-- Spec 01 §11): DROP TRIGGER exercise_change_xid ON "exercise";
--               DROP FUNCTION exercise_stamp_change_xid();
--               DROP INDEX "exercise_change_xid_idx";
--               ALTER TABLE "exercise" DROP COLUMN "change_xid";

-- One statement: existing rows are stamped with this migration's xid by the
-- column default (a volatile default rewrites the table; fine at this size —
-- see the lock note below). The column is never nullable, so there is no
-- backfill UPDATE and no separate SET NOT NULL scan. The trigger is created
-- after, so the default — not the trigger — stamps the pre-existing rows.
ALTER TABLE "exercise"
  ADD COLUMN "change_xid" xid8 NOT NULL DEFAULT pg_current_xact_id();

CREATE FUNCTION exercise_stamp_change_xid() RETURNS trigger
  LANGUAGE plpgsql AS $$
BEGIN
  NEW.change_xid := pg_current_xact_id();
  RETURN NEW;
END $$;

CREATE TRIGGER exercise_change_xid BEFORE INSERT OR UPDATE ON "exercise"
  FOR EACH ROW EXECUTE FUNCTION exercise_stamp_change_xid();

CREATE INDEX "exercise_change_xid_idx" ON "exercise" ("change_xid");
```

- **Prisma model** (D30): `changeXid Unsupported("xid8")
  @default(dbgenerated("pg_current_xact_id()")) @map("change_xid")` plus
  `@@index([changeXid], map: "exercise_change_xid_idx")` on the `Exercise`
  model, so `schema.prisma` and the migration describe the same column,
  default and index. This is the first `Unsupported(...)` field in
  `schema.prisma` (the existing model has none), so the first implementation
  step is a spike: `prisma validate` + `prisma generate` with the field and
  the index declared (Prisma has had `generate` failures with indexes on
  `Unsupported` fields, prisma/prisma#20993). If the index declaration cannot
  be made to work, drop `exercise_change_xid_idx` from `0004` (it is only an
  optimisation at this table size and can be added later under the
  expand-only rule) rather than carry model/migration drift. Prisma omits
  `Unsupported` fields from its typed client, and every write in this codebase
  is already `$queryRaw`/`$executeRaw` (Spec 03.1/03.2 convention), relying on
  the trigger. **`$queryRaw` cannot deserialize `xid8`**, so any test or code
  that reads the column must select `change_xid::text`.
- **Drift check** (AC1): CI only runs `prisma validate`, which never compares
  the model to the migrations; so the migration integration test also runs a
  `prisma migrate diff` from the migrated Testcontainers database to
  `schema.prisma` with `--exit-code`, failing on drift. (Prisma does not model
  triggers or functions, so those stay migration-only and are covered by the
  AC1 catalog assertions.)
- **Lock and cost.** `ADD COLUMN` with a volatile default, `CREATE INDEX` and
  `CREATE TRIGGER` each take a strong lock on `exercise` (the table rewrite
  and the index build hold `ACCESS EXCLUSIVE`/`SHARE` for their duration).
  With the catalog at hundreds of rows this is milliseconds; the spec assumes
  it. **Do not run `migrate deploy` while `seed:catalog` is running** — the
  migration would queue behind the seed's 60 s transaction, and the seed's
  writes behind the migration. If the table ever grows large, revisit before
  adding another rewriting migration.
- **No semantic change to existing rows**: no row's `updated_at` or any other
  column changes.
- **`exercise_updated_at_idx` (Spec 03.1 §4) is kept, unmodified.** The old
  image queries `updated_at > :updated_since` until it is fully rolled off;
  dropping the index is a separate, later, decoupled release once no code
  path filters on it (Spec 01 CLAUDE.md's additive-only migration
  discipline — never drop a column/index in the same release as the code
  that stops needing it).
- **The trigger fires for every `INSERT` and `UPDATE`**, which is exactly the
  property this fix needs: API writes, the seed's `$executeRaw`
  `INSERT`/`UPDATE` statements (`apps/api/src/seed/catalog.ts`), and any
  future write path or ad hoc fixture insert are all covered without a
  per-call-site change. It does **not** cover `DELETE`, `TRUNCATE`, or a
  session running with `session_replication_role = replica` (or a
  `pg_restore --disable-triggers` load). That is safe because of an invariant
  this spec records (and the implementation PR adds to DESIGN §4.2):
  **application code never hard-deletes an `exercise` row** — global rows are retired (`is_active =
  false`), custom rows are soft-deleted, and the only hard delete is the
  `ON DELETE CASCADE` on an account purge, which removes rows visible only to
  the purged user. A hard delete is invisible to a delta (no tombstone is
  ever sent), so any future code that hard-deletes a row other users can see
  must first give it a tombstone. This is a deliberate departure from this codebase's
  general "app stamps its own timestamps, no DB triggers" convention (Spec
  01, reaffirmed at Spec 03.2 D15) — the trigger is not a stand-in for
  `updated_at` (which stays app-stamped), it exists specifically because the
  sync token's correctness argument (§6.5) depends on **every** write being
  stamped, with no path that could forget to.

## 5. API surface

Only `GET /v1/exercises` (+ its Fastify-generated `HEAD`) changes; the four
Spec 03.2 write endpoints are unaffected by this spec (their `INSERT`/`UPDATE`
statements pick up `change_xid` for free, via the trigger, with no route or
DTO change).

```
GET /v1/exercises[?since=<syncToken>]              auth required   (HEAD auto-added)
  200  { exercises: Exercise[], syncToken: string }     ETag: "<strong: cursor + content>"
  304  If-None-Match matched (full pull OR repeated delta), no body
  422  since is not a valid sync token                  (validation-error)
  410  since is ahead of the server's current snapshot   (sync-token-expired),
       Cache-Control: no-store
  401  unauthenticated / invalid-token                   (Spec 01 contract)
```

A `since` that is not the current name (`updated_since`) is an unknown query
key: it is ignored, and the request is a full pull.

**Removed**: `?updated_since=<rfc3339>` / `serverTime`. There is no
backward-compatible dual-accept window — §1's non-goals section is why: no
client exists to break.

**New `AppError` subclass** (`apps/api/src/errors/app-error.ts`), following
the existing style:

```ts
export class SyncTokenExpiredError extends AppError {
  readonly status = 410;
  readonly slug = "sync-token-expired";
  readonly title = "Sync token expired";
  readonly publicDetail =
    "This sync token is no longer valid. Discard your cached catalog and pull it fresh.";

  constructor(internal = "since token is ahead of the server's current snapshot") {
    super(internal);
  }
}
```

Registered through the existing shared problem+json mapper
(`normalizeError`/`toProblem`, Spec 01 §5) — already mounted on both the root
scope and the `/v1` child scope (CLAUDE.md), so no new registration is needed
for this slug specifically.

**DTOs** (`packages/core/src/dto/exercise.ts`), replacing the corresponding
03.1 declarations:

```ts
// Replaces UpdatedSinceQuery. Version "1", then a canonical decimal xid: no
// leading zeros, at most 19 digits (9_999_999_999_999_999_999 < 2^64 - 1, so
// every accepted value is a valid xid8 and can never fail the ::xid8 cast).
const SYNC_TOKEN = /^1\.(0|[1-9]\d{0,18})$/;
export const isSyncToken = (s: string): boolean => SYNC_TOKEN.test(s);

// .regex() (not .refine()) so the OpenAPI emit carries the pattern.
export const CatalogSinceQuery = z.object({
  since: z.string().regex(SYNC_TOKEN, "not a valid sync token").optional(),
});
export type CatalogSinceQueryInput = z.infer<typeof CatalogSinceQuery>;

// ExercisesResponse.serverTime -> .syncToken; shape (a string) is unchanged,
// only the field name and its semantic (opaque token, not a timestamp).
export const ExercisesResponse = z.object({
  exercises: z.array(ExerciseSchema),
  syncToken: z.string(),
});
```

`isPostgresTimestamptz` is deleted — its only caller (`UpdatedSinceQuery`) is
gone, and its problem (an RFC 3339 string that Postgres's `timestamptz`
input rejects) cannot recur once the wire type is an opaque digit-string
matched against a fixed regex before it ever reaches SQL.

The 19-digit cap is deliberately **below** `2^64 - 1` (20 digits): a 20-digit
pattern would admit values above `2^64 - 1`, which pass validation, then fail
the `::xid8` cast in Postgres and surface as a `500`. 19 digits reach
`9.99e18`, far beyond any xid this database will issue, and everything the
regex accepts is a valid `xid8`. Rejecting leading zeros keeps the token
canonical, so `"1.01"` and `"1.1"` can't become two distinct `ETag`
sentinels for the same cursor. A value that passes the regex but exceeds the
snapshot's `xmax` is the `410` case, not a validation error.

### Repository and route changes

Only `@sin/core` gets the DTO/regex above. The token's encoding and decoding
stay **server-side** in `apps/api` (D33), because `@sin/core` is imported by
the web client and the token is opaque to clients (§3).

- `apps/api/src/repositories/exercise.ts` / `exercise.prisma.ts`:
  `CatalogPage.serverTime: Date` becomes `syncToken: string`.
  `findVisibleCatalog` and `findCatalogDelta` merge into
  `findCatalog(actingUserId, since?)` — one method, one SQL statement per
  call (§6.3), so the single-statement rule (AC3) has one place to break, not
  two. The delta's `sinceIso` parameter becomes the token's xid decimal; the
  empty-delta `serverNow()` / clamp second query is deleted. The **repository**
  throws `SyncTokenExpiredError` when `since_is_future` is true, so the check
  cannot be skipped by a caller.
- `apps/api/src/repositories/sync-token.ts` (new, server-only):
  `formatSyncToken(xid: string): string` (`"1." + xid`) and
  `parseSyncToken(token: string): string` (strips the `1.` prefix from a token
  already validated by `CatalogSinceQuery`).
- `apps/api/src/routes/exercises.ts`: reads `request.query.since`, passes the
  parsed xid to `findCatalog`, hashes `since ?? "full"` into the `ETag`, and
  returns `{ exercises, syncToken: page.syncToken }`. The `410` is emitted
  with `Cache-Control: no-store` (route-level catch, or the error mapper
  keyed on `SyncTokenExpiredError`).
- Test doubles: `apps/api/test/helpers/fakes.ts` (the fake exercise repository
  exposing `serverTime` / `lastDeltaSince`) and `routes-exercises.test.ts` move
  to `syncToken` / `since`. Route tests use the fake; anything that needs a
  real snapshot (the xmax-based `410`) is an integration `inject` against the
  real repository (§10).

## 6. Behavior & logic

### 6.1 Why a timestamp cursor can't be closed by narrowing

BL-1 already showed the concrete failure sequence. Restated at the general
level (from the design comment, §1): **any** write's `updated_at` is fixed
before its commit becomes visible to a reader. A cursor built from
`MAX(updated_at)` over currently-visible rows can therefore advance past a
still-uncommitted row's eventual timestamp, because the cursor moves via a
*different*, already-visible row — not via the uncommitted one. The width of
the resulting gap is bounded by how long the writer waits between stamping and
committing:

| Writer | Stamp point | What widens the stamp→commit gap |
|---|---|---|
| `POST /v1/exercises`, `/fork` (`insertWithCap`) | transaction start | Waiting on `pg_advisory_xact_lock` behind the same user's other creates/forks (the #23 sequence, AC5) |
| `PATCH`, `DELETE` | statement start | Row-lock wait behind a concurrent `PATCH`/`DELETE` of the same row; commit round trip |
| Catalog seed (`src/seed/catalog.ts`) | one `transaction_timestamp()` for the whole revision | **The whole seed transaction** (60 s timeout) — AC6 |

Narrowing the gap (`clock_timestamp()` instead of `now()`, a look-back margin)
was considered and rejected — see the design comment §2 for the full
alternatives table. Every alternative either doesn't close the gap or trades
it for a different failure mode (serializing all writers; relying on
`pg_stat_activity` permissions the seed's role may not have). None of them is
correct by construction the way a commit-ordered token is.

### 6.2 The token: definition and single-statement rule

The token is `pg_snapshot_xmin(pg_current_snapshot())` — the oldest
transaction id still in-flight as of the *statement's* active snapshot; every
transaction below it has already finished (committed or aborted). Postgres
hands out xids in strictly increasing order, at the moment a transaction first
writes — never in advance and never out of order — so:

- a transaction that has already been assigned an xid `< token` has finished
  and is fully visible;
- a transaction whose xid is `≥ token`, or that hasn't been assigned one yet
  (blocked on a lock before its first write, or not yet begun), can never
  "sneak behind" the token — its xid, once assigned, will be `≥` it.

`pg_current_xact_id()` returns the **top-level** transaction's xid even inside
a subtransaction (savepoint), so a row stamped in a subtransaction is covered
by the same argument as any other. The snapshot functions and `xid8` carry
the epoch, so there is no 32-bit wraparound cast anywhere in this design; and
because the token comes from a single statement, it is unaffected by whether
the connection is a Neon pooled or direct one.

**Critically, the token must come from the same statement that scans the
rows.** `pg_current_snapshot()` is evaluated against the calling statement's
own active snapshot, so the token and the rows describe the exact same
instant — including when the row set is empty. This is a deliberate departure
from the current `findCatalogDelta`'s empty-delta path, which runs a
**second**, later query to compute its echoed cursor; reusing that structure
here would silently reopen the exact gap this spec closes, because the second
query's snapshot is later than the first's (AC3, AC7 pin this specifically).

Wire format: an opaque string `"1.<xid decimal>"`, e.g. `"1.736"`. The `1.`
prefix is a format version — reserved for the eventual restore-epoch addition
(§12, Open) — and clients must treat the whole string as opaque (§3).

### 6.3 Queries

Full pull (token folded into a `WITH` so it shares the row scan's snapshot):

```sql
WITH snap AS (SELECT pg_snapshot_xmin(pg_current_snapshot())::text AS token)
SELECT snap.token, e.id, e.catalog_key, e.owner_user_id, e.name, e.modality,
       e.primary_muscle_id, e.secondary_muscle_ids, e.equipment_id,
       e.is_active, e.forked_from_exercise_id, e.created_at, e.updated_at
FROM snap
LEFT JOIN "exercise" e
  ON e.is_active = true
 AND (e.owner_user_id IS NULL OR e.owner_user_id = ${actingUserId}::uuid)
ORDER BY e.name COLLATE "C", e.id;
-- An empty visible set still yields one row (snap joined against no `exercise`
-- match, e.* NULL): keep snap.token, drop that placeholder row before mapping.
```

Delta:

```sql
WITH snap AS (
  SELECT pg_snapshot_xmin(pg_current_snapshot())::text AS token,
         pg_snapshot_xmax(pg_current_snapshot())      AS xmax
)
SELECT snap.token, (${sinceXid}::xid8 > snap.xmax) AS since_is_future,
       e.id, e.catalog_key, e.owner_user_id, e.name, e.modality,
       e.primary_muscle_id, e.secondary_muscle_ids, e.equipment_id,
       e.is_active, e.forked_from_exercise_id, e.created_at, e.updated_at
FROM snap
LEFT JOIN "exercise" e
  ON e.change_xid >= ${sinceXid}::xid8   -- ">=": the horizon xid may itself
                                          -- commit after this read
 AND (e.owner_user_id IS NULL OR e.owner_user_id = ${actingUserId}::uuid)
ORDER BY e.name COLLATE "C", e.id;
```

`sinceXid` is the numeric suffix `parseSyncToken` (§5) strips from the
already-validated `"1.<xid>"` token (the `1.` prefix never reaches SQL). It is
bound as a query parameter through Prisma's tagged `$queryRaw`, exactly like
the existing repository queries — never string-built.
`since_is_future` is read once from the (possibly placeholder) row; a `true`
value throws `SyncTokenExpiredError` before any row is mapped or returned —
this must be checked even when the visible row set is otherwise empty, since
"no rows changed" and "your token is bogus" are different conditions.

**No `is_active` filter on the delta** — tombstones still arrive, unchanged
from today. **The visibility filter is still `AND`ed in** on every path,
identically to Spec 03.1 §6.1's invariant — this spec does not touch
authorization, only the sync mechanism (§7).

### 6.4 API-visible behavior changes vs. today

| | Today (Spec 03.1) | This spec |
|---|---|---|
| Delta param | `?updated_since=<rfc3339>` | `?since=<syncToken>` |
| Response field | `serverTime` (RFC 3339) | `syncToken` (opaque string) |
| Malformed cursor | `422 validation-error` | `422 validation-error` (regex, not date parsing) |
| Future cursor | Clamped to server-now, `{ exercises: [], serverTime }` | **`410 sync-token-expired`** |
| `ETag` sentinel | The `updated_since` value, or `"full"` | The `since` token, or `"full"` (same rule) |
| Client rule | Always overwrite the stored cursor | Unchanged |

**Future tokens now get `410`, not a clamp.** A legitimate token can never
exceed the current snapshot's `xmax` (§6.3's `since_is_future` check), so one
that does is either crafted, or — more realistically — a client that held a
token from *before* a database restore or cluster move, where xids reset
backwards while the client's stored token does not (and, while a read replica
lags, a token issued by the primary; see D32).
Clamping (as the old `serverTime` design did for a future timestamp) would
silently skip every write made after such a restore; `410` forces a clean
resync instead, matching the pattern used by sync APIs like Google Calendar's
`syncToken` → `410 Gone`.

### 6.5 Correctness argument

Take any row version `R`, committed by transaction `X`, and a delta pull at
snapshot `S` returning token `t = xmin(S)`.

- **`X < t`**: `X` finished before `S` was taken, so `R` is visible in `S`.
  If the client's previous token was `≤ X`, this delta returns `R` (its
  `change_xid ≥` that previous token, since `X` was assigned strictly after
  it — `X` can't be a *retroactive* commit). If the previous token was
  `> X`, an earlier delta already returned `R`, by the same argument applied
  one step back, bottoming out at the initial full pull.
- **`X ≥ t`**: the next delta filters `change_xid ≥ t`, so it includes `R`
  once `R` is visible (i.e., once `X` has committed), or a later delta does
  if `X` hadn't committed yet at that delta's own snapshot.
- **`X` had no xid assigned when `S` was taken** — the #23 case (blocked on
  the advisory lock before its `INSERT`) and the seed case (long-running
  transaction): `X`'s xid is assigned only once it actually writes, which is
  necessarily after `S`, so it is `≥ xmax(S) ≥ t`. The previous bullet then
  applies once `X` commits.

A row may be re-sent more than once (a row with `change_xid` between the
previous and current token that's already visible is re-sent until the
horizon passes it); clients already de-duplicate by `id` (Spec 03.1 §3
consumer note, unchanged). **No row can be permanently skipped** — this is
the property BL-1's timestamp cursor lacked.

### 6.6 Long transactions widen re-send, never skip

Only a transaction that **holds an xid** — one that has performed a write —
pins `pg_snapshot_xmin`, and only until it ends: the catalog seed's 60 s
transaction, a slow multi-statement write, a Prisma interactive transaction
that wrote and is now awaiting I/O, or an orphaned prepared transaction. (A
slow *read-only* query or a session idle after only reads has no xid, so it
does not hold the token back — it holds back the vacuum horizon, which is a
different mechanism.) While an xid holder is open anywhere on the instance,
deltas re-send rows that are already visible but whose `change_xid` is `≥`
the held-back horizon. The current worst case is bounded by the seed's 60 s
transaction timeout. **This is extra payload, never a correctness gap** — a
materially better failure mode than the timestamp design's silent, permanent
skip.

`ALTER ROLE <app role> SET idle_in_transaction_session_timeout = '30s'` would
bound the *leaked-session* variant of this (a connection that wrote, then sat
idle mid-transaction, rather than one doing legitimate long work) —
recommended as a small, independent follow-up; not shipped here (§8).

## 7. Security & privacy

- **The authorization boundary is unchanged.** The visibility filter
  (`owner_user_id IS NULL OR owner_user_id = :actingUserId`) is still `AND`ed
  onto both the full pull and the delta (§6.3), exactly as Spec 03.1 §6.1's
  security invariant requires. This spec touches only the sync-cursor
  mechanism, not what rows a caller can see. The existing delta-isolation
  test (Spec 03.1 §10 AC5 — a custom row owned by another user never leaks)
  exercises the delta through `updated_since`, so it is **ported** to
  `since` in the implementation PR and must stay green; it is not merely
  unaffected.
- **The token is not per-user**, so replaying one user's token as another
  user's `since` is harmless: the visibility predicate is applied to the
  second user's own rows regardless of the cursor.
- **What the token reveals.** `pg_snapshot_xmin` is a transaction-id counter
  shared by the *entire* database instance, not scoped to the `exercise`
  table or to the caller's own writes. An authenticated caller polling
  `GET /v1/exercises` can observe how fast that counter advances between
  calls, which is a coarse proxy for **overall transaction volume across the
  whole database** (every table, every user, including unrelated write
  traffic like workout logging once Spec 05 ships) — not specifically
  catalog activity, and not attributable to any other individual user or
  row. Assessed as **not independently exploitable**: it requires an already-
  authenticated session (this endpoint has no anonymous access), it leaks no
  row content, no other user's identity, and no timing finer than "an
  arbitrary number of transactions happened somewhere, at some point, between
  my two polls" — a much coarser signal than the request/response timing any
  authenticated endpoint already exposes. No mitigation is proposed beyond
  what already exists (auth-required, no anonymous endpoint other than
  `/openapi.json` per Spec 03.0 §7); recorded here as a considered-and-
  accepted low-severity information exposure, not a residual risk requiring a
  decision.
- **No new PII.** The token is a number; nothing in it is derived from user
  content.
- **Abuse/resource bounds are unaffected.** The delta query is a comparison
  against an indexed column (`exercise_change_xid_idx`) instead of
  `exercise_updated_at_idx`, same cost shape; the full pull's un-paginated
  scan and per-request `sha256` are as bounded as Spec 03.1 §7 already
  describes (the 500-row cap, Spec 03.2 D15).

## 11. Deployment & rollback

No feature flag — this changes an existing, unconsumed contract; "off" is the
continued absence of callers until Spec 06.

**Release ordering** (extends Spec 01 §11 / Spec 03.1 §11):

1. `prisma migrate deploy` applies `0004_exercise_change_xid` — additive, so
   the still-running old image tolerates it. The old image's writes fire the
   trigger and get stamped correctly; it just never reads `change_xid` (it
   doesn't know the column exists). For Neon, run against the **direct**
   (non-pooler) host (CLAUDE.md). Do not run it while `seed:catalog` is
   running (§4, lock note). **Run it before merging**: a merge to `main`
   auto-deploys the code (Render `autoDeploy`) while `migrate deploy` is a
   manual step, and the new catalog read selects `change_xid`, so code that
   goes live first would fail `GET /v1/exercises` with a `500` until the
   migration lands. Nothing consumes the endpoint yet, so that would be
   harmless — but ordering it correctly costs nothing (same as the 03.2
   release steps).
2. New code goes live. `GET /v1/exercises` starts accepting `?since=`. The old
   `?updated_since=` name is not rejected: under the new Zod querystring
   schema (`z.object`, not `.strict()`) an unknown key is ignored, so an
   old-format request is treated as "no `since`," i.e. a full pull, rather
   than erroring — matching how an unrecognized query key already behaves
   elsewhere in this codebase. AC4 pins this so it can't change silently.
3. `/openapi.json` reflects the renamed field/param on the next emit; the CI
   drift check catches any mismatch before merge.

No seed step is touched — the seed's SQL is unmodified; the trigger stamps its
writes automatically (§4).

**Rollback:** revert the code commit. The column, trigger, and index are
inert to the old code (same posture as every additive migration in this repo)
— no data cleanup is needed, and the migration's down step is dev/test-only
per the established convention (Spec 01 §11, Spec 03.1/03.2 §11). Because
there is no current consumer, a rollback carries zero client-visible risk
either direction.

## 12. Decisions & open questions

### Resolved

D24–D29 were decided by the user in the design comment on issue #23
(`issue-23-fix-design.md`, root of the repo at review time) prior to this
spec; they are recorded here, not re-derived. Decision numbers are global
across the 03.x specs (03.1 has D1–D13, 03.2 has D14–D23), so these continue
at D24. D30–D33 came out of the architect and security reviews of this draft
and refine implementation details without changing the accepted mechanism.

- ✅ **D24 — replace the timestamp cursor with a commit-ordered sync token.**
  A trigger-stamped `change_xid xid8` column plus a token taken as
  `pg_snapshot_xmin(pg_current_snapshot())` in the same statement as the row
  scan; delta predicate `change_xid >= since`. Chosen over narrowing the
  stamp-to-commit window (`clock_timestamp()`, a look-back margin — neither
  closes the gap, per §6.1's table), a deferred-constraint double-stamp
  (still stamps before commit-visibility, doubles writes), clamping to
  `pg_stat_activity.xact_start` (NULL for other roles without
  `pg_read_all_stats`; the seed's Neon-owner role would be invisible to it),
  and serializing all catalog writers (correct but a real throughput cost —
  every user's writes would queue behind the seed and each other).
- ✅ **D25 — rename the wire contract**: `?updated_since=` → `?since=`,
  `serverTime` → `syncToken`; the token is opaque, wire format `"1.<xid
  decimal>"`. Chosen because an opaque value continuing to appear under a
  timestamp-shaped name (`serverTime`, `updated_since`) would mislead a
  future client author into parsing or comparing it as a date. The version
  prefix is free optionality for the deferred restore-epoch (D27 below).
- ✅ **D26 — future token → `410 sync-token-expired`, not a clamp.** A
  legitimate token can never exceed the current snapshot's `xmax`; one that
  does is either crafted or predates a database restore (where xids run
  backwards while a client's stored token does not). Clamping — the old
  design's behavior for a future `updated_since` — would silently skip every
  write made after such a restore. `410` forces a clean resync, matching the
  `syncToken` → `410 Gone` pattern used by comparable external sync APIs
  (e.g. Google Calendar).
- ✅ **D27 — defer the restore-epoch hardening.** The `410` future-token check
  catches a post-restore client *unless* the xid counter has already caught
  back up to the client's stale token by the time it reconnects — a real but
  narrow residual gap. Closing it fully needs a `sync_epoch` table and a
  `1.<epoch>.<xid>` token plus a runbook step to bump the epoch after any
  point-in-time or branch restore. Deferred because restores are rare and
  the *current* (pre-this-spec) timestamp design has an equivalent blind
  spot of its own (it never tombstones rows a restore removed) — this is not
  a regression relative to today, just an incompletely-closed edge relative
  to the ideal. The versioned `"1."` prefix is kept specifically so this can
  be added later without another breaking rename. **Hard trigger (review
  amendment):** "restores are rare" does not cover the planned Neon → AWS
  move (Spec 15), which is a cluster change that resets the xid space under
  every stored client token. Before the Spec 15 data cutover, either land the
  epoch or make the server answer `410` to every `1.` token (bumping the
  version prefix does this with no schema change), so clients resync once.
  Spec 15 must list this as a cutover step.
- ✅ **D28 — `updated_at` and `exercise_updated_at_idx` are untouched.**
  `updated_at` keeps its existing role (display, "last edited," `ETag` hash
  input); the index stays because the old image still filters on it during
  rollout, and dropping an index the current release's code no longer needs
  is a separate, later, decoupled change under this codebase's additive-only
  migration discipline (CLAUDE.md).
- ✅ **D29 — migration `0004` is additive/expand-only**, applied ahead of the
  code that uses it; the old image continues serving `?updated_since=` reads
  correctly throughout the rollout window (its writes are stamped by the
  trigger regardless of whether its own code knows the column exists).
- ✅ **D30 — the Prisma model declares the column, default and index, and a
  drift check enforces it** (review). The first draft's model had a
  `@default` the migration didn't create and omitted the index, and CI's
  `prisma validate` cannot see model/migration drift, which would have shown
  up later as a phantom `migrate dev` migration. The migration now sets the
  same `DEFAULT pg_current_xact_id()` the model declares; AC1 runs
  `prisma migrate diff --exit-code`; a spike confirms Prisma accepts an index
  on an `Unsupported` field, with dropping the index (not tolerating drift) as
  the fallback.
- ✅ **D31 — the migration adds the column in one statement**
  (`ADD COLUMN … NOT NULL DEFAULT pg_current_xact_id()`) instead of add
  nullable → backfill `UPDATE` → `SET NOT NULL` (review). It removes the
  nullable window, an extra table scan and a pointless trigger-fired update,
  and it lines up with D30's default. Accepted cost: a table rewrite under an
  exclusive lock, which is milliseconds at this table size (§4 lock note).
- ✅ **D32 — sync reads run on the primary** (review). A lagging read
  replica's snapshot would call a valid primary-issued token "in the future"
  and return a false `410`. No replica exists today; this is a standing
  constraint on adding one.
- ✅ **D33 — token parsing and formatting live in `apps/api`, not
  `@sin/core`** (review, adapted). Only the wire regex, `isSyncToken` and the
  DTOs belong in `@sin/core`, which the web client imports; putting
  `parseSyncToken` there would invite clients to parse an opaque token.

### Open

- **Restore epoch** (see D27) — tracked as a genuinely deferred hardening
  item, not resolved here. It has a hard deadline: land it (or force `410` on
  all `1.` tokens) before the Spec 15 cutover, and earlier if a database or
  branch restore is ever performed against an environment with real clients
  holding tokens (currently none).
- **`idle_in_transaction_session_timeout`** — recommended (§6.6, §8) as a
  small, independent infrastructure change bounding how long a *leaked*
  session that has written can pin the sync horizon. Not a blocking dependency of this spec
  (a legitimate long transaction, like the seed, would still widen the
  re-send window regardless of this setting) and not implemented here;
  worth a `docs/backlog.md` entry at implementation time if not picked up
  directly.
