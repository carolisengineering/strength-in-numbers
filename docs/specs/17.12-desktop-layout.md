# Spec 17.12 — Desktop layout: a side rail and two-pane History, Exercises and Routines (web)

**Status:** v0.1 draft (2026-11-08). Not implemented. **A mockup comes before any code (Phase 0, §5).**

**Source:** the whole-app Impeccable critique of 2026-11-08 (23/40). The direction is the owner's call: D1 recommends one and §12 leaves it open.

**Design refs:** `PRODUCT.md` (lifters plan routines and review history on a desktop; reviewers count equally); Spec 04.1 Q24 (bottom nav at every width, "a side rail is additive later, a media-query block in `AppShell.module.css`") — **this spec revisits Q24**; Spec 18.2 (the Exercises routes); Specs 08.0, 08.1 (History, the chart); Spec 10.0 (the routine routes, the leave guard); `apps/web/CLAUDE.md` "iPhone keyboard frame" and "Front door"; Spec 17.13 (`Screen`'s `hideTitle`); Spec 17.10 (sheets).

---

## 1. Purpose, scope & non-goals

**Purpose.** At 1280 px the app is a 608 px column in the middle of the screen with a nav bar along the bottom (desktop screenshots 08, 12, 14). PRODUCT.md says this is where lifters plan and review, and a portfolio reviewer probably opens the app on a desktop first. The phone layout is right for the phone; the desktop needs its own.

**What was checked.**
- **A 608 px column: right.** `Screen` caps at `--measure-max` (40rem = 640 px less 2 × 16 px padding), and `AppShell`'s only wide rule (`@media (min-width: 48rem)`) caps `<main>` the same. The header's title and the user name sit at the page edges, 640 px apart from the content.
- **Nav at the bottom: right,** by Q24's own design.
- **The chart scales its text with its box: an extra finding.** `LineChart` draws a fixed 360 × 220 viewBox that scales to the container, so the axis labels are 14 px on a phone and about 24 px at 608 px (visible in desktop 15). A wider chart makes it worse, so Phase C fixes it.
- **`fixed; inset: 0`.** `AppShell`'s frame is `position: fixed; inset: 0` (#204, #207) with a three-row grid; `data-keyboard="open"` swaps its top and height for the visible rectangle and hides the nav (#206). A side rail has to keep both.
- **The router** has History, Exercises and the routine routes as siblings (`history`, `history/:id`, `exercises` with its children, `exercises/:id` outside the layout on purpose, `workouts/routines/:id[/edit]`). Master-detail needs those under layout routes without changing any URL.

**In scope.**
1. The breakpoints, as tokens and one constant, and what happens at tablet widths.
2. A side rail instead of the bottom nav at desktop widths.
3. Two panes (list and detail) for History, Exercises and Routines.
4. A wider, honest chart.

**Non-goals.**
- The phone and tablet layouts (they stay as they are).
- The live workout screen, which stays a single column (D3).
- A desktop presentation for sheets (they stay a 40rem column; a side drawer is a follow-up, §12).
- New features, shortcuts, hover-only behavior or a different information architecture. Every control keeps its 44 px target: some desktops are touch screens, and tablets in landscape are in range.
- Any API, schema or `@sin/core` change. **No API change is needed.**

## 2. Acceptance criteria

### Phase A — breakpoints and the shell

1. **Breakpoints are tokens, once.** `tokens.css` gains `--bp-desktop: 64rem`, `--sidebar-width: 15rem`, `--pane-list-width: 20rem` and `--content-max-wide: 80rem`, and records the existing 48rem as `--bp-tablet`. Because a custom property cannot be read inside an `@media` condition (the condition is evaluated before any element has computed values), each `@media (min-width: …)` repeats the value, and `ui/breakpoints.ts` exports `DESKTOP_QUERY` for `matchMedia`. A test scans every media condition in `src` (CSS and TS) and fails if one uses a width other than `--bp-tablet` or `--bp-desktop`.
2. **`useIsDesktop()`.** Reads `matchMedia(DESKTOP_QUERY)` through `useSyncExternalStore`, so the first render is right (no flash) and a resize re-renders. It returns false where `matchMedia` doesn't exist (jsdom), so every existing test runs the phone layout.
3. **Phone and tablet are unchanged.** Below 64rem the shell is today's: header, bottom nav, and from 48rem `<main>` capped at `--measure-max`. The `AppShell` tests pass unchanged.
4. **The rail.** At 64rem and wider the shell is a rail of `--sidebar-width` and a main area. The rail holds the app name as text (no mark, owner decision 2026-10-15), the four nav items stacked (each icon beside its label, a row at least `--tap-target-min` tall, the current one teal and bold with `aria-current="page"`), and at its bottom the signed-in user's name as a link to Profile (accessible name "Profile: …" as now, `data-testid="app-shell-user"`). There is no top header and no bottom nav.
5. **DOM order matches the picture.** At wide widths the rail comes before `<main>` in the DOM, so Tab order and the screen-reader order match what is drawn. Below 64rem the order is today's. The rail is `<nav aria-label="Primary">`.
6. **Skip link.** At wide widths the first focusable element is a visually hidden "Skip to content" link that appears on focus and moves focus to `<main>`.
7. **Width.** `<main>` fills the rest of the width. Single-column screens (Profile, the live workout, the summary reached from Finish, routine New and Import, the Hevy screens, Not found) stay at `--measure-max`, centered in `<main>`. Panes (below) cap at `--content-max-wide`, centered.
8. **The frame is still fixed.** `.shell` remains `position: fixed; inset: 0`; `trackKeyboardFrame` still sets `--app-top` / `--app-height` and `data-keyboard`; the rule that hides the nav under `data-keyboard="open"` applies below 64rem only, so a tablet in landscape keeps its rail. `<main>` is still the scroller outside panes, and the `data-action-bar` scroll-padding rule is unchanged.
9. **Headings.** With no header, the title a screen hides on a phone (Spec 17.13's `hideTitle`) is visible at wide widths. Each page has one visible `h1`.
10. **Sheets and dialogs** are unchanged at every width.
11. **Harness.** `screens` captures the shell at 1440 × 900, 1280 × 800 and 1024 × 768 (desktop) and 820 × 1180 (tablet), light and dark, and fails the run on horizontal overflow, a rail target under `--tap-target-min`, or overlapping controls. The pinned-layer checks treat the rail as part of the shell.
12. **Tablet is checked, not assumed.** At 820 × 1180 the shell shows the phone layout in a centered 40rem column with the bottom nav; at 1024 × 768 it shows the rail with a 784 px main.

### Phase B — History as two panes

13. **`Panes`.** A new `ui/Panes.tsx` takes a list, a detail and `showDetail`. At wide widths it draws a list pane of `--pane-list-width` and a detail pane, each its own scroller (`min-height: 0; overflow-y: auto`), under one cap of `--content-max-wide`. Below 64rem it renders only the detail when `showDetail`, else only the list, so the phone is exactly today's. The scroll-padding rule for `data-action-bar` applies inside a pane's scroller too.
14. **Routes don't change.** `/app/history` and `/app/history/:id` (and `/edit`) keep their URLs. They become children of one layout route whose element is `Panes`. The detail is the `<Outlet/>` in a fixed position of the tree, so a resize across 64rem keeps the detail's state.
15. **The newest workout shows without a redirect.** At wide widths `/app/history` shows the newest workout in the detail pane (a derived id, no `navigate`), and that row is the selected one. With no workouts the pane shows today's empty text.
16. **Selection.** The current row has `aria-current="page"`, a `--color-signal-soft` ground and a bold name, so it isn't color alone. Opening another row swaps the detail and scrolls the detail pane to its top, and leaves the list's scroll where it was.
17. **Headings and links.** The detail screen's `h1` is the page's one `h1`; the list pane's title is an `h2`. The Back link on the summary, edit screen and exercise page is not drawn inside a pane. The summary's Workout menu stays, with Edit workout and Delete workout in it (Spec 17.6 AC22).
18. **Edit and delete work in the pane.** `/app/history/:id/edit` renders in the detail pane with its Done bar sticky at the pane's bottom; deleting a workout returns to `/app/history`, which shows the next newest.
19. **Roles.** The selected-row style's file is added to `SIGNAL_ALLOWED` in `ui/roles.test.ts`, with its reason (a selection, as chips are).

### Phase C — Exercises as two panes, and the chart

20. **Layout.** `ExercisesLayout` becomes the panes layout: the list pane holds the All exercises / Records switch and its list; the detail pane is `exercises/:id`, which moves under the layout (today it is a sibling on purpose, so a phone page has no tabs; the phone keeps that: below 64rem a child route shows only the detail). URLs are unchanged and Spec 18.2's path scan passes.
21. **Index.** At wide widths `/app/exercises` shows the most recently logged exercise's page (derived, no redirect); with none logged, a one-line prompt "Choose an exercise".
22. **Selection and headings** follow AC16–AC17. The page's `h1` is the exercise name; the list pane's title is "Exercises" as an `h2`.
23. **The chart measures itself.** `LineChart` takes its drawing width from its container (a `ResizeObserver`, with 360 as the fallback where there is none, so jsdom and today's tests are unchanged) and uses a viewBox equal to that width in pixels, with a height of half the width clamped between 220 and 320. Axis and tick text are `--font-size-sm` on every width (14 px at 390 and at 1280, checked by the harness), and the line, dots and selection stay as today.
24. **Details at wide widths** stay in the "Exercise details" disclosure of Spec 17.11, closed.

### Phase D — Routines as two panes

25. **Layout.** With no live workout, `/app/workouts` at wide widths is the list pane (Start, then the routine list, as the screen shows today) and a detail pane that shows `/app/workouts/routines/:id` (the preview) or `…/:id/edit` (the editor), or "Choose a routine" when none is open. A pathless layout route groups exactly those three routes, so `workouts/:id` (the finished summary) and `routines/new` and `routines/import/*` stay full-width single columns.
26. **A live workout wins.** With a live workout, `/app/workouts` is the single-column session as today, at every width.
27. **The leave guard covers the pane.** Choosing another routine, or any nav item, while the editor has unsaved changes asks first (the existing `useLeaveGuard`); choosing the same routine does not. A resize across 64rem keeps the editor's draft.
28. **The editor's bar** is sticky at the detail pane's bottom, and the item sheet still opens as a sheet.
29. **Selection and headings** follow AC16–AC17. "Back to Workouts" is not drawn in the pane.

### Must keep

30. **Regression guards.** Every existing test passes (they run with `useIsDesktop()` false). No route, path, query key, request or event changes. The Spec 10.0 leave guards, the 17.1 keyboard frame and the offline outbox behave as before.
31. **Accessibility.** Landmarks are one `nav` (the rail), one `main`, and the panes as labelled regions; focus order is rail, list, detail; every target is at least `--tap-target-min`; text contrast is unchanged (no new color); the pages hold at 200% text size.

### Docs and verification

32. **Docs consistent.** The cross-doc updates in §12 are made, including Spec 04.1's Q24 note.
33. **Every behavioral AC has a tagged test.** AC1–AC10, AC13–AC30 have ≥1 test named `17.12 ACn — …`, enforced by a scan; harness ACs are marked in §10.
34. **Visual review and the owner's eye.** The mockup (Phase 0) is approved first; the harness then captures each phase's screens at the widths of AC11.
35. **Phone and tablet checks (owner).** On the iPhone: nothing has changed. On a desktop browser: resize slowly from 1440 to 400 px and confirm the layout switches at 1024 and 768, an open editor keeps its text, and the browser's Back works through the panes.

## 6. Behavior & logic

### 6.1 Why a JS hook as well as CSS

CSS alone could show or hide a pane, but both panes would then be in the DOM at every width. That gives a phone page two `h1`s in the tree for tests and for anything that reads the DOM without styles, and mounts a second set of queries. `useIsDesktop` lets the layout render the structure for the width it is at. The cost is that a window dragged across 64rem changes the tree: the detail stays at one position (`Outlet` in a fixed slot) so its state survives, and the rail and bottom nav are the only things that remount.

### 6.2 `AppShell`

Narrow: unchanged. Wide: the grid is `var(--sidebar-width) minmax(0, 1fr)` in one row; the rail is rendered before `<main>`; there is no `<header>`. The frame stays `position: fixed; inset: 0` for the reasons in `AppShell.module.css`'s comment (#204, #207). `trackKeyboardFrame` is untouched; the `[data-keyboard="open"]` rules that set the frame's top and height apply at every width, and only the rule that hides the nav is scoped to under 64rem.

### 6.3 `Panes`

```
<Panes list={…} detail={<Outlet />} showDetail={Boolean(useMatch(detailPattern))} />
```

Wide: `display: grid; grid-template-columns: var(--pane-list-width) minmax(0, 1fr); gap: var(--space-6); max-width: var(--content-max-wide); margin-inline: auto; height: 100%`. Each pane is `min-height: 0; overflow-y: auto`, with `padding: var(--screen-pad)`. Narrow: one element. A `PaneContext` tells the embedded screens (`embedded: true`) to skip their Back link; the list screens read it to render their title as an `h2`.

### 6.4 Derived selection

`useSelectedId(routeId, ids)` returns the route's id, or at wide widths the first id of the list when there is no route id. The same value marks the row and picks the detail, so they never disagree. It is a pure function with a table test.

### 6.5 The chart

`LineChart` keeps `scale.ts` and `VIEW`'s margins; only `width` and `height` become parameters (`useMeasuredWidth` returns 360 where `ResizeObserver` is missing). Ticks and labels use the measured width.

### 6.6 Risks

- Route restructuring is where this can break. Each phase keeps the old routes' tests as they are and adds route tests at wide widths with a mocked `matchMedia`.
- Two pane scrollers plus the sticky bar: the `data-action-bar` scroll-padding rule must cover the pane scroller (AC13).
- Both pane lists mount only at wide widths; at narrow widths the phone mounts exactly what it does today.

## 11. Deployment & rollback

Web only; five steps: the mockup (no PR), then **Phase A** (shell), **B** (History), **C** (Exercises and the chart), **D** (Routines), each its own PR. Each merge auto-deploys staging; A is useful alone, B to D each need A. No migration, no release step. Rollback is a revert of the latest PR. D is the largest and may split into D1 (the preview pane) and D2 (the editor pane) if the PR grows.

## 12. Decisions & open questions

- ⚠️ **D1 — A side rail at 64rem and over, and two panes for History, Exercises and Routines (proposed; needs the owner's OK, after the mockup).** **Rationale:** planning and review are list-and-detail tasks; a list that stays in view while you read one workout is what a desktop is for, and a rail uses the width a bottom bar wastes. It matches what PRODUCT.md says desktop is for. **Revisits Spec 04.1 Q24** ("bottom nav at every width"), which anticipated this: "a media-query block in `AppShell.module.css`". **Cost:** about four PRs, and the route restructuring (§6.6). **Rejected:** (a) bottom nav kept, column widened to about 72rem: cheap, but the page would be a wider version of a phone list and the History list and its detail still can't be seen together; (b) the rail alone, no panes: the cheapest change that looks designed, but it leaves the 608 px column in a field of empty stone. (b) is Phase A on its own and is a fair place to stop.
- ✅ **D2 — 64rem for the desktop layout; 48rem to 64rem stays the phone layout in a centered column (owner, 2026-11-08, accepted recommendation).** An iPad in portrait (820 px) is a touch device held like a tablet; a rail and two panes at 784 px would give each pane less than a phone. iPad in landscape (1024 px and up) gets the desktop. **Rejected:** a third, tablet layout (a rail without panes): more to build and test for a case with no owner use.
- ✅ **D3 — The live workout stays a single column (owner, 2026-11-08, accepted recommendation).** Logging happens on the phone; PRODUCT.md puts only planning and review on the desktop. Spec 17.9's docked panel changes this screen's structure, and a desktop layout built now would be built twice. **Cost:** a reviewer who opens a live workout on a desktop sees a 640 px column in a wide field; the rail frames it.
- ✅ **D4 — A pane with nothing selected shows the newest item, with no redirect (owner, 2026-11-08, accepted recommendation).** A bare right pane makes the first impression an empty screen. The selection is derived, so the URL stays honest and Back works. **Rejected:** `replace`-navigating to the newest id (a surprise in history and a flash); an empty state with a prompt (kept only where there is nothing to show).
- ✅ **D5 — Panes render by JS, not by hiding with CSS.** See §6.1.
- ✅ **D6 — Sheets stay as they are at wide widths.** A 40rem sheet over a rail is acceptable; a drawer is a follow-up.

**Settled (owner, 2026-11-08, accepted recommendation): each recommendation below was taken.**
1. D1: decided in part (owner, 2026-11-08): mock up the rail and panes first, then choose on the mockup. The side rail alone (Phase A) is a fair place to stop.
2. D3 and D4 as proposed? Recommendation: yes to both.
3. Should Profile, which is one column, get a two-column form at wide widths? Recommendation: not now; nothing there is faster for being wider.

**Deferred follow-ups.** A side drawer for sheets at wide widths. Item editing inline in the routine editor's pane instead of in a sheet. Keyboard shortcuts for list navigation. A `layout` property on analytics events. No API items.
