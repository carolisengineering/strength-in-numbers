## 1. Purpose, scope & non-goals

### 1.1 Purpose

Carol wants to see every exercise in the app, open its page, and fix the two mistakes that started #104: an exercise created without muscle groups, and an exercise created with the wrong type. Today the Progress tab lists only exercises that hold a record, nothing in the web can edit, copy or delete an exercise (`PATCH`, `POST …/fork` and `DELETE` have no caller), and a never-logged or duration-only exercise has no page at all.

This spec renames the Progress tab to **Exercises**, makes **All exercises** its default view (today's Progress list becomes the **Records** view, unchanged), puts the per-exercise Progress screen under an **exercise page** with details, Edit and Delete at the top, and adds **make your own copy** for built-ins.

**Success:** Carol opens Exercises, searches "echo", sees "Echo Bike · Last logged Sat 24 Oct", opens it, taps Edit, adds a primary muscle and saves; opens a built-in, taps **Make your own copy**, lands on her copy; deletes an exercise a routine uses after reading which routine it breaks; every old `/app/progress` link still works; and nothing about the chart, the Records list or the picker looks or behaves differently.

### 1.2 In scope

**Phase A (PR 1): tab, list, page (read-only)**
- Nav rename, routes, redirects from `/app/progress…`, the view switch (§5.1, §6.1).
- **All exercises**: usage query, pure row model and sort, search, **+ New exercise** (reusing `CreateExerciseForm`), loading / offline / empty states (§5.2, §6.2).
- **Records** view: today's `ProgressScreen` moved under the tab (§6.1).
- **Exercise page**: details block, never-logged / deleted variants, today's Progress body unchanged below (§5.3, §6.3).
- Screens harness, e2e smoke step, tag test, docs.

**Phase B (PR 2): Edit, copy, Delete**
- Catalog store writes (`updateCustom`, `forkExercise`, `deleteCustom`) and their mutation hooks (§6.4).
- **Edit** sheet: `ExerciseFields` in edit mode, only-changed-fields `PATCH`, type options by `canChangeModality`, `409 exercise-type-locked` path, the rename note (§6.5).
- **Make your own copy** (§6.6) and **Delete** with the routine warning (§6.7).
- The D22 pin (§6.8), telemetry (§9), harness, phone check.

### 1.3 Non-goals (and where they live)

| Not here | Lives in / why |
|---|---|
| Any API, `@sin/core` or migration change | 03.4 / 05.3. The UI consumes `canChangeModality`, `compatibleModalities`, `lineageRootId`, `ExerciseUsageResponseSchema`, `ExerciseRoutinesResponseSchema`. |
| Improving the per-exercise Progress view | Design non-goal: it moves under the page as it is. |
| Editing or deleting a built-in in place; editing the catalog | Design non-goal. A built-in gets **Make your own copy**. |
| Undo for Delete, restoring a deleted exercise | No restore route exists; D14. |
| Offline edit, copy or delete (an outbox op) | D11: online-only, like routines. |
| Muscle / equipment filters on All exercises | Owner ruling O2 (search only). |
| Merging two exercises, moving sets, "my minutes were really calories" | Design non-goals. |
| Calorie targets in routines | FI-11. |
| A change to what the Records list, Progress chart, picker or History show | Anti-goal: Records must not differ from today's Progress list. |

### Fit for one work session

Phase A is wide and shallow: one nav entry, five routes, one pure row model, one query, one screen with a search, a details block, and the existing Progress body re-parented. Phase B is one sheet, one dialog, three store methods and their hooks. Two PRs at the phase boundary; if the session runs out, the cut is that boundary.

## 2. Acceptance criteria

Every behavioral criterion has at least one test whose `describe` is tagged **`"18.2 ACn — …"`**; `acTags.18-2.test.ts` (AC30, AC56) checks the tags. §10 maps each to a method. "Row" means a `visibleRows` catalog entry; "root" means `lineageRootId(row)`; "logged" means its root has an entry in `GET /v1/exercises/usage`.

### Phase A: tab, list, page (read-only)

**Tab, routes, redirects**

1. **The tab.** `NAV_ITEMS` entry 3 is `{ to: "/app/exercises", label: "Exercises", icon: ChartIcon }` (slot and icon unchanged; the path and label are the only changes). `navItemFor` marks it current on `/app/exercises` and every path under it; no nav label, heading or `aria-current` assertion anywhere says "Progress" for this tab.
2. **Routes.** The route table gains exactly `exercises` (layout; children: index = All exercises, `records` = Records), and `exercises/:id` (the exercise page, not inside the layout). The static `records` segment outranks `:id` (a test navigates to `/app/exercises/records` and gets the Records view); an unknown deeper path (`/app/exercises/x/y`) is `NotFound`. The comment block in `router.tsx` is updated.
3. **Redirects.** `/app/progress` replace-navigates to `/app/exercises/records`; `/app/progress/:exerciseId` replace-navigates to `/app/exercises/:exerciseId` (the id re-encoded as one path segment). Both are `<Navigate replace>`, so Back never returns to a redirecting URL. Both stay indefinitely (bookmarks, an Auth0 `returnTo` captured before this release). They sit inside the protected layout, so a signed-out visit signs in first and then redirects.
4. **No stale links.** A source scan fails if any non-test module under `apps/web/src` contains the string `/app/progress` other than the two redirect routes in `router.tsx`. Every former link (the Records rows, the page's back link) points at the new paths. History and the finish summary never linked to Progress (verified); they gain no link here.
5. **Layout and view switch.** `/app/exercises` and `/app/exercises/records` render one `Screen` titled "Exercises" (one `h1`) with a `nav` labeled "Exercise views" holding two links, **All exercises** (`/app/exercises`) and **Records** (`/app/exercises/records`), each ≥ 44 px, the current one `aria-current="page"`. The links `replace` (switching views does not pile up history). The default view is All exercises; a deep link to Records opens Records.
6. **Records view unchanged.** The body is today's `ProgressScreen` content moved verbatim: same query (`useAllRecords`), grouping (`groupByExercise`), order (newest record first), headline text (`headlineText`), empty state ("No records yet — finish a workout to see your progress" with the Go to Workouts link), load and refresh notices and list label. The only differences: it no longer draws its own `Screen` or `h1`, and each row links to `/app/exercises/{encoded exerciseId}` with router state `{ from: "records" }`. The 08.1 tests for these behaviors move with it and pass with only heading / route edits.

**All exercises**

7. **The usage query.** `useExerciseUsage()` (`features/exercises/usage.ts`) calls `GET /v1/exercises/usage` through `useApi()` with `ExerciseUsageResponseSchema`; key `["exercises","usage"]`; `staleTime: 0`, `retry: false`, `networkMode: "always"` (an offline open fails as a `network` error instead of pausing); the browser's `private, no-cache` + `ETag` revalidation makes a repeat a `304`. Nothing is written to `localStorage` (no new key, `USER_DATA_KEY_PREFIXES` unchanged).
8. **Row model and sort (pure).** `buildExerciseRows(visible, usage, today)` returns the rows in this order: logged rows first by `lastLoggedOn` descending, ties by name (the pinned `"en"` collator, `sensitivity: "base"`), then `id`; then never-logged rows by name, then `id`. Each result carries `{ row, lastLoggedOn: string | null, source: "builtin" | "yours" }`. Table-driven unit test, including equal dates, equal names, a blank usage, and a usage entry for a root no visible row maps to (ignored).
9. **Lineage mapping.** A usage entry is found for a row by `usage.get(lineageRootId(row))`. A fork whose built-in has logged sets shows the built-in's date; a fork of a never-logged built-in is never-logged; the hidden built-in (an origin of an active fork) is never listed (`visibleRows`); a deleted fork's built-in is listed again with the same date (03.4 D21).
10. **Row text.** Line 1 is the name. Line 2 is `{lastLogged} · {type label}` where `lastLogged` is "Last logged {formatLocalDate(date)}" (e.g. "Last logged Tue 6 Oct"), with the year appended (`formatLocalDateWithYear`) only when the date's year is not the current local year, and, for a never-logged row, "Built in" (`ownerUserId === null`) or "Yours" (otherwise, forks included). The type label is `MODALITY_LABELS[row.modality]`. "Today" is read from `ProgressClockContext` (the 08.1 test seam).
11. **Row accessibility.** Each row is one `<a>` to `/app/exercises/{encoded id}` inside a `<ul aria-label="All exercises">`, min-height 44 px, whose accessible name begins with the exercise name (so `getByRole("link", { name: /^Barbell bench press/ })` is stable). The meta line is plain text in the same link, not a second control.
12. **Search.** An `<input type="search">` with the accessible name "Search exercises" filters with the picker's `searchByName` (folded, case- and diacritic-insensitive, substring on the name); the sort is unchanged; the filter is a `useMemo` over (rows, query), not an effect. A polite `role="status"` line reads "N exercises" / "1 exercise" while a query is active and is empty while there is no query (the region stays mounted, visually hidden, so the first count is announced; deferred minor 122). No muscle or equipment filter (owner ruling O2).
13. **Catalog states.** Catalog rows come from `useCatalog().visible` (raw `state.rows` is never rendered). Empty store and `lastRefreshAt === null` or `status: "loading"`: a `Spinner` "Loading exercises…". Empty store and `status: "error"`: the picker's notice, "Couldn't load exercises" with a Retry that calls `refresh(true)`. Rows present: the list renders at once whatever the sync status.
14. **Usage states.** (a) Usage pending and no cached data: the list is held behind the same Spinner until usage settles, so the order never jumps under a finger. (b) Usage data present (fresh or cached from an earlier visit in the session): the list renders at once; a background refetch that changes the data re-sorts silently. (c) Usage failed with no data: the list renders A–Z with the type label as line 2 only (no "Built in" / "Yours" claim, since the app does not know), and an `InlineNotice` "Couldn't load when you last logged these" with **Try again** (refetch). (d) A refetch failure with data on screen keeps the data and shows the same notice.
15. **Offline.** With the catalog in the store and the network down: the list, search and every row work; the usage query fails as `network`, so state 14(c) applies. No Retry loop, no exception reported (`reportUnexpected` only for non-network, non-4xx failures, as 08.1).
16. **Empty states.** A catalog that loaded with zero visible rows: "No exercises yet." plus the **+ New exercise** button. A query with no match: `No exercises match "{query}".` with a button **New exercise "{query}"** that opens the New exercise sheet prefilled with the query.
17. **+ New exercise.** A button (visible text "+ New exercise", the plus `aria-hidden`) sits on the same row as the search input, ≥ 44 px, and stays in the layout while the list is narrowed. It opens a `Sheet` "New exercise" containing `CreateExerciseForm` with `initialName` = the search text, the muscle and equipment reference data from `useMuscleGroups` / `useEquipment`, and no new inputs (`ExerciseFields` stays the one set). Cancel closes it. On `onCreated` the sheet closes and the router **pushes** `/app/exercises/{new id}` (Back returns to the list); the create form's cap and field-error messages are unchanged.
18. **Scale.** The list is not virtualized (D8). A unit test renders 600 rows, filters to 3 and back, and asserts the rendered `li` count each time; the rows are a `React.memo` component keyed by id, so a keystroke re-renders only changed rows.

**Exercise page**

19. **Resolution.** `useExercisePage(id)` returns one of: `loading` (store empty or `lastRefreshAt === null` with no error), `error` (store empty and `status: "error"`: notice + Retry), `found` (the id is a `visibleRows` row), `redirect` (the id is a fork origin with an active fork: `<Navigate replace>` to the newest active fork by `createdAt`, ties by `id`), or `deleted` (the store has synced, `lastRefreshAt !== null`, and no active row has the id). A row that is in the store but `isActive: false` cannot occur (sync drops it); if it did it is `deleted`. A cold deep link to an exercise created on another device waits for the first sync before it can say `deleted`.
20. **Page chrome.** `Screen title` is the exercise name (`h1`); `lead` is a `BackLink`: `/app/exercises/records` "Back to Records" when `location.state?.from === "records"`, else `/app/exercises` "Back to Exercises". It is a link, not `history.back()`, as 08.1's "Back to Progress" was. The page remounts per id (keyed route), so moving between exercises starts from default range and metric (08.1 §6.4).
21. **Details block.** A `<dl aria-label="Exercise details">` with: **Source** ("Built-in exercise" / "Your exercise" / "Your copy of {origin name}", or "Your copy of a built-in exercise" if the origin row is not in the store), **Type** (`MODALITY_LABELS`), **Primary muscle**, **Secondary muscles** (comma-joined, authoring order), **Equipment**; an unset value reads "Not set". Muscle and equipment names come from `useMuscleGroups` / `useEquipment`; while those load the value is omitted (not "Not set"), and if they fail the row reads "Unavailable". Values are text, never links.
22. **Never logged.** When the usage data has loaded and the page's root has no entry, the Progress body is replaced by one line: "Not logged yet. Log a set in a workout and its chart and records show up here." and no series or records request is made. While usage is pending or failed, the body renders as today (it handles empty data itself). A live-workout-only set counts as logged (03.4 O1), so its page shows the body's own empty state until the workout finishes.
23. **Logged: today's content, unchanged.** Below the details block the page renders what `ExerciseProgressScreen` rendered inside its `Screen` (metric and range controls, chart, readout, sessions list, Open workout link, `RecordsSection`), extracted as `ExerciseProgressBody({ exerciseId })` in `features/progress/`. All 08.1 behavior tests for it pass unmodified except the ones that asserted the old `Screen` title, the records-derived title and the "Back to Progress" link. The body no longer renders a title or a back link.
24. **Deleted exercise (reached by a Records link or an old link).** A `deleted` id renders the page with the title from the exercise's records (`groupByExercise(records)[0].name`) else "Removed exercise", the line "This exercise was deleted. Past workouts keep its sets, and the history below stays.", no details block, no actions, and the Progress body (a retired root's series and records still serve, 03.4 AC36). A deleted exercise appears in no list.
25. **Gone is still gone.** The 08.1 rule survives the move: if the page's default series (`useSeries(id, "3m")`, deduplicated with the body's identical query) fails on first load with `404` or `422` and no data, the whole screen is `NotFound` (a made-up or foreign id), whatever the catalog said.
26. **Import boundaries.** A scan test fails if `features/progress/` imports from `features/exercises/` (the arrow points only the other way), if any module outside `features/catalog/catalogStore.ts` calls `PATCH`/`DELETE`/`POST …/fork` on `/v1/exercises`, or if `features/progress/ProgressScreen.tsx` still exists.

**Harness, e2e, hygiene**

27. **Harness (A).** `apps/web/scripts/screens/data.mjs` serves `GET /v1/exercises/usage` (derived from `allWorkouts`, keyed by root) and the capture fake answers it; `pnpm --filter @sin/web run screens` captures, light and dark, 390 and 1280 px, with no layout violation: All exercises (mixed logged, never-logged, a fork), a search with a match and with none, Records, the page of a logged built-in, the page of a never-logged own exercise, the deleted variant, and the usage-failed notice. A 600-row fixture is captured once at 390 px.
28. **e2e (A).** `apps/web/e2e/helpers.ts` `NAMES.progress` becomes `exercises: "Exercises"`; the 08.1 step clicks that tab, finds the row by `/^Barbell bench press/`, opens it and still sees the chart summary and Metric group; a new line in the step visits `/app/progress` and expects the URL to end `/app/exercises/records`. No e2e step writes an exercise (the test account's catalog is not mutated).
29. **No new design values.** `assert:css-tokens` passes; every new CSS rule uses existing tokens; `roles.test.ts` allow-lists are unchanged (brass is still records only; nothing here uses it).
30. **Legacy tests and tags (A).** Existing web tests pass unmodified except those that pin what this phase moves on purpose (the nav label and heading, `/app/progress` paths, `ProgressScreen` / `ExerciseProgressScreen` as screens, `AppShell.test`, `HistoryScreen.test` line 106, `routes.test` nav names, `a11y.test`); `acTags.18-2.test.ts` fails if any unit-tested Phase A criterion in §10 lacks a `describe` tagged "18.2 ACn".
31. **Phone check (A, manual, after Phase A is on staging).** On Carol's iPhone, one-handed: open the Exercises tab; scroll the full list; type in search; open a logged exercise, a never-logged one and a built-in; switch to Records and back; tap Back at each; open an old `/app/progress` bookmark. Recorded in `gym-checklist-2026-10.md`.

### Phase B: Edit, make your own copy, Delete

**Catalog store and mutations**

32. **Store writes.** `CatalogStore` gains `updateCustom(id, patch)`, `forkExercise(id)` and `deleteCustom(id)` (React-free, through `api.patch` / `api.post` / `api.delete`; `CatalogStoreDeps.api` widens to include them). Each merges its result into `rows` (a delete marks the row inactive so `mergeCatalogRows` drops it), persists, and calls `refresh(true)` un-awaited so the sync token catches up, exactly as `createCustom` does. `updateCustom` and `forkExercise` parse the response with `ExerciseSchema`; none touches `recents` except `forkExercise`, which `recordPick`s the copy. A rejection is the API client's `ApiError`, unmodified.
33. **Mutation hooks.** `useUpdateExercise`, `useForkExercise`, `useDeleteExercise` (`features/exercises/useExerciseMutations.ts`) are TanStack mutations with `networkMode: "always"` and `retry: false`, no outbox, no stored draft. Success runs `applyExerciseCaches`: `invalidateQueries` on `["records"]` and `["progress"]`, and `removeQueries` on `["exercises","routines",id]` after a delete. The mutations outlive the sheet or dialog that started them (the result is applied even if the user left), and navigation stays at the call site.

**Actions on the page**

34. **Which actions show.** `ownerUserId !== null` (an own exercise or a copy): **Edit** and **Delete exercise**. `ownerUserId === null` (built-in): the note "Built-in exercises can't be edited. Make your own copy to change the name, type, muscles or equipment. Your history and records come with it." and one **Make your own copy** button. A `deleted` page shows none. The buttons sit under the details block, each ≥ 44 px; Delete uses the `danger` `Button` variant only inside its dialog, the page button is `secondary`.

**Edit**

35. **The sheet.** Edit opens a `Sheet` "Edit exercise" with `ExerciseFields` prefilled from the row (`valuesFromExercise`), "More details" open, Save and Cancel. Save is disabled while nothing changed or the name is blank. `dismissible={!saving}` (DM-12): Close and Escape do nothing while a save is in flight. Closing without saving discards the edits; there is no unsaved-changes guard (five fields, D10).
36. **Only changed fields are sent.** `toUpdateExerciseInput(initial, current)` returns `{}` for no change and otherwise only the keys that changed: `name` (trimmed, compared trimmed), `modality`, `primaryMuscleId`, `secondaryMuscleIds` (compared as a set; sent in the form's order), `equipmentId`; a cleared select sends `null`. Unit-tested over every field, including clearing and no-op.
37. **Type options (the rule).** With the usage data loaded, `hasLoggedSets = usage.has(lineageRootId(row))`. The type radios list all eight; each value `v` is `disabled` iff `!canChangeModality({ from: row.modality, to: v, hasLoggedSets })`; the current type is always enabled. When `hasLoggedSets` and the type is locked, a note under the choices reads "This exercise has logged sets, so its type can only change to {A} or {B}. To use another type, create a new exercise." (partners from `compatibleModalities(row.modality)` minus itself, labels from `MODALITY_LABELS`) or, with no partner, "This exercise has logged sets, so its type can't change. To use another type, create a new exercise." With no logged sets, all eight are enabled and there is no note. Disabled choices are visibly muted (`--color-muted` text, no opacity-only cue), stay in the DOM and keep their label, so a screen reader hears them as unavailable.
38. **Usage unknown.** While the usage query is pending, the type radios are all disabled except the current one, with the note "Checking whether this exercise has logged sets…"; if it failed, the same plus "Couldn't check whether this exercise has logged sets, so its type can't be changed right now. Everything else can." and Save still sends the other fields. Opening the sheet forces a usage refetch (a `304` when unchanged), so the options reflect sets logged since the tab was last viewed.
39. **The weight-meaning note (03.4 D8).** When `hasLoggedSets` and the selected type differs from the current one and both are in `{weight_reps, weighted_bodyweight}`, a second note shows: "Weight × reps counts the full weight and Weighted bodyweight counts only the added weight. Your history keeps its numbers, so this exercise's charts and records will compare the two." It disappears if the selection returns to the current type.
40. **Rename note and success.** Under the Name field (the existing `nameNotice` slot): "Renaming doesn't change past workouts. History keeps the name each workout was logged with." (03.4 D20). On success: the store holds the returned row, the sheet closes, focus returns to the Edit button (the native dialog restores it), the page shows the new details and a polite status "Saved." (cleared when the sheet next opens), and `applyExerciseCaches` has run.
41. **`409 exercise-type-locked`.** The slug (`ApiError.type`), never the text, selects this path. The sheet stays open, keeps every other edit, resets the type to the current one, shows the form-level error "This exercise already has logged sets, so its type can only change to one that logs the same measures. Create a new exercise instead.", and invalidates the usage query so the options re-disable from fresh data; a second Save with the type reset succeeds.
42. **Other errors** (`classifyExerciseError`, keyed on status and slug, never on text). `422` field errors map onto the form with the create form's shared mapping (`features/catalog/fieldErrors.ts`, extracted from `CreateExerciseForm`, whose tests pass unchanged; a message under collapsed "More details" opens it) and unplaced ones become the form message; `409 exercise-retired` or `404`: "This exercise was already deleted." and the sheet closes after a forced catalog refresh so the page becomes the `deleted` variant; `409 exercise-immutable-use-fork` or `403 exercise-immutable` (a stale row): the form message "This is a built-in exercise, so it can't be edited. Make your own copy instead." after a forced refresh; network: "You're offline. Editing an exercise needs a connection."; `429`: "You're doing that too fast. Try again in a moment."; `401` shows nothing (`onAuthLost` has started the logout); anything else "Couldn't save. Try again." (and `reportUnexpected` only for an unclassified failure). Static copy; no problem `detail` is echoed.

**Make your own copy**

43. **The flow.** The button calls `forkExercise(builtin.id)` with **no body** (D6: no overlay; the copy is edited afterwards). On success the router **replace**-navigates to `/app/exercises/{copy id}` with state `{ notice: "copied" }`; the copy's page shows the polite status "Your copy is ready. Edit it to change the name, type, muscles or equipment." (cleared from router state by a replace navigation so a reload does not repeat it) and focus moves to the page `h1`. The built-in leaves every list at once (the store now holds an active fork of it) and its URL redirects to the copy (AC19), so Back never lands on a redirect loop.
44. **Disabled on tap (03.4 D11).** The button is `busy` (disabled) from the tap until the request settles, and a ref guard ignores a second activation that arrives before React re-renders. It re-enables on failure and stays disabled through the navigation on success. A test taps twice in one tick and asserts exactly one `POST …/fork`.
45. **Copy errors.** `409 exercise-limit-reached` (03.4 AC18): "You've reached the maximum number of custom exercises." (the create form's text, one constant); `409 exercise-retired`, `404`: "This exercise is no longer available." after a forced refresh; network, `429`, `401`, other: as AC42. The error shows in an `InlineNotice` above the button, which keeps its place, except the "no longer available" text, which goes to the page's status line because the forced refresh may turn the page into the deleted variant without the button (deferred minor 126).

**Delete**

46. **The dialog opens and asks.** **Delete exercise** opens a `ConfirmDialog` titled "Delete {name}?" (`variant="danger"`, confirm label "Delete", Cancel focused first). Opening it starts `GET /v1/exercises/{id}/routines` (`useExerciseRoutines(id, { enabled: open })`, key `["exercises","routines",id]`, `staleTime: 0`, `gcTime: 0`, `retry: false`, `networkMode: "always"`, schema `ExerciseRoutinesResponseSchema`). Delete is disabled (`confirmDisabled`) until the answer is in. Loading: a `Spinner` "Checking your routines…" in the body.
47. **The warning names the routines.** With no routine: "Past workouts keep their sets and still show this exercise. You won't be able to add it to new workouts." ## 6. Behavior & logic

### 6.1 Routes, nav, redirects (D1, D2)

```
/app/exercises            ExercisesLayout (Screen "Exercises" + view switch) > <Outlet/>
   index                    AllExercises
   records                  RecordsView
/app/exercises/:id        ExerciseRoute (keyed by id) > ExerciseScreen
/app/progress             <Navigate replace to="/app/exercises/records">
/app/progress/:exerciseId RedirectProgressExercise (<Navigate replace to={exercisePath(id)}>)
```

`exercises/:id` is a sibling of the layout route, not a child, because the page draws its own `Screen` (title = the exercise). React Router ranks the static `exercises/records` above `exercises/:id`. `navItemFor` already matches by prefix, so no change there beyond the entry. `features/exercises/` is the new directory; `features/progress/` keeps the chart, series, range and metrics code and loses `ProgressScreen.tsx` (its body becomes `exercises/RecordsView.tsx`) and the `Screen` wrapper of `ExerciseProgressScreen.tsx`.

The view switch is two `Link`s (`replace`), not `aria-pressed` buttons: they navigate and deep-link, so they are links and carry `aria-current`. The 44 px / selected styling reuses `ChoiceGroup`'s look through its own small CSS module (existing tokens).

### 6.2 The list model

```
buildExerciseRows(visible: Exercise[], usage: Map<rootId, lastLoggedOn>, today): ExerciseRow[]
  for each row: last = usage.get(lineageRootId(row)) ?? null
  logged   = rows with last !== null, sorted (last desc, name asc [collator "en"], id)
  unlogged = the rest, sorted (name asc, id)
  result   = logged ++ unlogged
```

`lastLoggedLine(last, today)` formats the date (D5). `useExerciseUsage` returns the `Map` built from the response array (the server order is already date-desc; the client re-sorts anyway so the name tiebreak is the client's). `visible` is `useCatalog().visible` (already name-sorted; the model re-sorts). The search is `searchByName(rows, query)` applied to the model's output, so narrowing never reorders.

Gate order in `AllExercises`: catalog gate (AC13) → usage gate (AC14) → list. The New exercise sheet and button render in every state that has rows or has finished loading.

### 6.3 The page

`useExercisePage(id)` (pure part `resolveExercise(rows, id, synced)`, unit-tested) implements AC19. `ExerciseScreen`:

1. Resolve. `loading` → `Spinner`; `error` → the notice; `redirect` → `<Navigate replace>`.
2. `found` → `Screen` with the details `<dl>`, the actions (Phase B), and either the never-logged line or `ExerciseProgressBody` (AC22).
3. `deleted` → AC24.
4. The gone rule (AC25) is evaluated from `useSeries(id, "3m")` before any of the above renders content, as 08.1 did.

The details rows come from a pure `detailRows(row, { muscles, equipment, origin })` so the "Not set" / omitted / "Unavailable" rules are tested without React.

### 6.4 Store writes and mutations (Phase B)

```
updateCustom(id, patch): api.patch(`/v1/exercises/${id}`, patch, ExerciseSchema) -> merge, persist, refresh(true); track
forkExercise(id):       api.post(`/v1/exercises/${id}/fork`, undefined, ExerciseSchema) -> merge, persist, recordPick, refresh(true); track
deleteCustom(id):       api.delete(`/v1/exercises/${id}`) -> merge {…row, isActive:false} (dropped), persist, refresh(true); track
```

Ids are one `encodeURIComponent` segment. The merged row is the server's, so `updatedAt` and every field follow it. The follow-up `refresh(true)` is the same "let the token catch up" step `createCustom` takes. A delete of a row the store does not hold (another device already removed it) still resolves.

`applyExerciseCaches(queryClient, { id?, deleted? })` is the one place that touches the query cache for these writes: `invalidateQueries(["records"])`, `invalidateQueries(["progress"])`, and on a delete `removeQueries(["exercises","routines",id])`. A rename changes the name the Records list and series screens show, which is why `["records"]` is invalidated (D9). Usage is invalidated only on the type-locked path (AC41); a rename, copy or delete does not change when anything was last logged.

### 6.5 Edit

`EditExerciseSheet({ open, row, onClose })`:

- `valuesFromExercise(row)` builds `ExerciseFieldValues` (null ids become `""`); `ExerciseFields` gets `disabledModalities`, `modalityNotice` (the AC37/AC38/AC39 notes), `nameNotice` (the rename note), `detailsOpen` initially true.
- `disabledModalities = new Set(MODALITY_VALUES.filter(v => !canChangeModality({ from: row.modality, to: v, hasLoggedSets })))`; while usage is unknown it is every value but the current one.
- Save sends `toUpdateExerciseInput(initial, current)`; an empty result keeps Save disabled, so `PATCH {}` (which bumps `change_xid` for no change, 03.4 §6.6) is never sent.
- The type-locked path (AC41) is the only place the sheet resets a field programmatically.
- `ExerciseFields` renders a disabled radio by adding the `choiceDisabled` class (muted text and border from existing tokens) next to `disabled`; nothing else in the component changes, and with no `disabledModalities` it renders exactly as today.

### 6.6 Make your own copy

A bodiless `POST …/fork` (D6). The new row is immediately in the store, so `visibleRows` hides the built-in (it is an origin of an active fork) in the same render the navigation happens in. The built-in's page, if reached again by a Records link or a bookmark, resolves to `redirect` (AC19). Copies count against the shared 500-exercise cap with create (03.4 AC18). A second copy is possible from another device (03.4 D11); both then list, and the redirect picks the newest.

### 6.7 Delete

`DeleteExerciseDialog({ open, row, onClose, onDeleted })` owns the routines query, the copy of AC47 / AC49 and the busy state. The routines read is exact-id (03.4 D13), so for a copy it names only routines that use the copy; routines that use the built-in keep working after the copy is deleted and are not mentioned. After the write, the page navigates away from an id that no longer resolves, with `replace` (AC50).

Why the warning is read, not assumed: the catalog row carries nothing about routines (03.4 D12), and a stale list in the cache is the failure that matters on a destructive action, so the read is `gcTime: 0` / `staleTime: 0` and Delete waits for it.

### 6.8 The D22 audit (what was checked)

`seedDraft` (`setDraft.ts`) overlays `row.repsLow` and `row.weight` + `row.weightUnit` from the next planned set onto the copied-forward draft with no modality check. Every consumer then goes through `visibleMeasures(modality)`: `parseDraft` parses only visible measures, `SetFields` renders only visible measures, `nextText` in `summaryLine.ts` switches on the modality and falls to `set N` in its `default` arm (18.1 AC18 adds the weighted arm), and `logLabel` reads the parsed body. So a stale reps target on a Duration card sits in the draft state, never renders and never reaches a request body. The only residue is that a persisted edited draft (06.5) can carry the hidden string, which is inert. AC52 pins this; if a future change adds a consumer of the raw draft fields, that test is the tripwire.

## 7. Security & privacy

- **Authorization is the server's.** Every write is a `PATCH`/`POST`/`DELETE` the API already authorizes (own rows only; built-ins `409`/`403`). The UI hides Edit and Delete on built-ins as a courtesy, never as the check; a stale row that slips through gets the server refusal (AC42).
- **Static copy, no echoed server text.** Problem handling keys on `status` and slug; no `detail`/`title` is shown (the "Validation messages are static" rule, #57). User-typed strings (exercise and routine names, search text) are rendered as React text only.
- **No new data stored or sent.** No request beyond the three documented reads and three writes; usage and routine lists are not persisted. Logout clears `sin:catalog:` as today; the TanStack cache is cleared by the existing sign-out path.
- **Telemetry carries counts and booleans only** (AC53); never a name, id, search text or muscle.
- **Open redirects:** router state is read only for display strings and a `from` enum; no state value is used as a navigation target.
- **CSP:** no inline style, font or data URL (all styling by class).

## 8. Config & secrets

None. No env var, secret, flag, build or hosting change.

## 9. Observability

- `custom_exercise_updated { typeChanged }`, `custom_exercise_forked`, `custom_exercise_deleted { routineCount }` via `track`, beside the existing `custom_exercise_created`; success only.
- Failures: expected ones (network, 4xx in the AC42 table) are not reported; an unclassified failure goes to `reportUnexpected` with a new static op name per write (`update-exercise`, `fork-exercise`, `delete-exercise`, plus `load-exercise-usage`, `load-exercise-routines`), never an id or name. These op names are added to `ReportOp`.
- No new metric or span attribute (13.0 rules); the server already logs `custom_exercise_updated`, the type-change refusal, and the fork (03.4 §9).

## 12. Decisions & open questions

All decisions are the designer's calls unless marked owner. Owner-fixed inputs (design doc, 03.4): the two views and their names; All exercises' content, order and row labels; the page layout; Edit's fields; the built-in "make your own copy"; Delete's scope, warning and "Removed exercise" consequence; the type-change rule; routes are the builder's call.

- **D1 ✅ Routes: `/app/exercises` (All), `/app/exercises/records`, `/app/exercises/:id`; the old `/app/progress` paths move and redirect permanently (mine).** Rationale: a tab called Exercises whose URLs say `progress` is a trap for the next reader and for deep links; the move costs one `Navigate` per old path, and the only in-app links to the old paths are the Records rows and the page's back link (grep: History and the summary never linked to Progress). Redirects are `replace` so Back never bounces, and they stay (bookmarks, a captured Auth0 `returnTo`). Records is a path, not component state, so it deep-links and Back works; the view links `replace` so toggling does not stack history. Rejected: keep `/app/progress` as the real route (permanent mismatch); view as a `?view=` query (a second router mechanism the app does not use).
- **D2 ✅ The exercise page is a sibling route, not a child of the layout (mine).** Rationale: it has its own title (the exercise name), back link and actions; nesting it under a layout whose `h1` is "Exercises" would give two headings or force the layout to know the exercise.
- **D3 ✅ Edit is a `Sheet`, not a route (mine).** Rationale: five fields, one decision, no deep link needed, the page stays visible behind, and Close/Escape/back-gesture already work on `Sheet` (06.1 AC32) with the `dismissible` lock for an in-flight save. A route would add a path, a not-found state, and a draft to lose on refresh. Same reasoning puts **+ New exercise** in a `Sheet` (the picker already does).
- **D4 ✅ "+ New exercise" lands on the new exercise's page (mine).** Rationale: the reason Carol creates from here is often to fill in details or fix a type; the page has Edit one tap away and shows the result. Push (not replace) so Back returns to the list she was searching.
- **D5 ✅ "Last logged" uses `formatLocalDate` ("Tue 6 Oct"), with the year added only outside the current year, and no relative words (mine).** Rationale: it matches History rows and the Progress list headline (08.0 AC11); the year is needed because a bare day-month is ambiguous after a year (the 08.1 sessions list added it for the same reason); "Today" / "Yesterday" would need midnight handling the date string does not (the live-workout case already reads "today" via 03.4 O1, and the date line says so honestly).
- **D6 ✅ Make your own copy forks immediately with no body, then the lifter edits the copy (owner ruling O1, 2026-10-25: "copy first").** Rationale: one code path for editing (the Edit sheet only ever edits an own row), no overlay to validate or `409` on at fork time, and the fork is cheap and reversible (deleting the copy re-surfaces the built-in, 03.4 D21). Cost: two steps to a renamed copy. The page note says what the button does before the tap.
- **D7 ✅ Edit, copy and Delete are online-only mutations with `networkMode: "always"`, no outbox (mine).** Rationale: the outbox (06.2) exists so a set logged in a signal-poor gym is never lost; these are deliberate, rare edits whose outcome depends on server rules a queued op could not answer (type-locked `409`, the cap, "was it already deleted"), and a queued delete would skip the very routine warning Carol asked for. This is the routines precedent (10.0) and `createCustom` today. The failure copy says plainly that editing needs a connection.
- **D8 ✅ The list is not virtualized (mine).** Rationale: the catalog is at most the seeded built-ins (10 today) plus 500 custom exercises (the cap), i.e. roughly 510 plain rows with two lines of text and no images; that is a few milliseconds to render and fine to scroll on a phone, while virtualization would break find-in-page, the browser's scroll restoration, and accessibility-tree completeness for a problem that does not exist. Rows are memoized so a keystroke re-renders only what changed; AC18 and the phone check are the tripwires. If the cap rises tenfold, revisit.
- **D9 ✅ Cache updates: the store holds the row; `["records"]` and `["progress"]` are invalidated on every edit, copy and delete; usage only on type-locked (mine).** Rationale: the Records list and the series screens show server-resolved exercise names, so a rename must refresh them; last-logged dates do not change on an edit. The catalog follows `createCustom`'s pattern (merge, persist, forced refresh so the sync token catches up), so the picker, routine editor and lookup see the change with no extra plumbing. A routine list is not invalidated: it renders names through the catalog, not from its own cache.
- **D10 ✅ No unsaved-changes guard on the Edit sheet (mine).** Rationale: five fields; the routine editor's guard (10.0) protects a long document. Close discards, as the create sheet does.
- **D11 ✅ Type options: all eight shown, incompatible ones disabled with one explanatory note (not hidden, not a per-option reason) (mine).** Rationale: hiding would make a type look missing from the app, which is exactly the confusion behind the Echo Bike mistake; the actual reason is one sentence about the exercise, not about each option, so one note under the group says it and names the allowed alternatives. Disabled radios stay readable (muted, labeled). When usage is unknown the safe state is locked-with-a-note, and the server `409` remains the authority (a stale client gets the AC41 path).
- **D12 ✅ Delete waits for the routines answer (mine).** Rationale: the owner's rule is "warns and names the routines, then proceeds"; allowing Delete before the warning loaded would delete without the warning. Failing closed (Delete disabled, Try again) costs only a retry; the alternative, deleting blind on a failed check, is the "delete that breaks a routine without saying so" anti-goal.
- **D13 ✅ The D22 prefill needs no code change, only a pin (mine).** Rationale: §6.8. `seedDraft` copies planned measures regardless of type, but every parse and display path filters through `visibleMeasures`, so nothing stale is visible or sent. A test over modality × forbidden measure is cheaper and safer than threading the modality into `seedDraft`, and fails if a new consumer reads the raw draft.
- **D14 ✅ No Undo for Delete (mine).** Rationale: there is no restore route (03.4 is read-only plus the existing soft delete), the dialog already states the consequence and names every routine it breaks, and an Undo that only the client remembers would have to re-create the exercise as a new row, orphaning its lineage and records. A mistaken delete of a copy is recoverable (the built-in returns; copy again); of an own exercise it is not, which is why the dialog is the gate.
- **D15 ✅ A copy's page resolves a hidden fork origin to its newest active fork, by `replace` (mine).** Rationale: Records rows are keyed on the lineage root (the built-in's id once the lifter forked it), so without this a Records link would open a hidden, uneditable built-in whose history is the copy's. `replace` keeps Back from bouncing.
- **D16 ✅ A deleted exercise reached by link still gets a page: title from its records, the history below, no actions (mine).** Rationale: catalog sync drops retired rows (06.0), so the page cannot describe the exercise, but the series and records still serve for a retired root (03.4 AC36) and Records still lists it; a `NotFound` there would strand real history. The 404/422 `NotFound` rule still covers ids the server does not know.
- **D17 ✅ Telemetry is three success events with counts and a boolean (mine).** Rationale: enough to see whether editing and copying are used and whether delete warnings matter; nothing that identifies an exercise (DESIGN §8.1).
- **D18 ✅ Page back link is a link chosen by router state (`from: "records"`), not `history.back()` (mine).** Rationale: 08.1 and #98 use links; a link is stable when the page was opened from a bookmark or after a reload, and the one state value is display-only.
- **D19 ✅ Copy lives in `features/exercises/messages.ts` (mine).** Rationale: the routines (`messages.ts`) and workouts (`messages.ts`) precedent; every string in this spec is a constant there, so tests pin text in one place. The type-change error text is client-owned and keyed on the slug, not on the server's `detail`.
- **D20 ✅ File names avoid case-insensitive collisions (mine).** `ExerciseScreen.tsx` (component) beside `resolveExercise.ts` (pure), `ExerciseDetails.tsx` beside `detailRows.ts`, `AllExercises.tsx` beside `exerciseRows.ts`, `EditExerciseSheet.tsx` beside `exerciseInput.ts`: no pair differs only by case (CLAUDE.md rule).
