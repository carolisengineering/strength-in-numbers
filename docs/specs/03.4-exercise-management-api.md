## 1. Purpose, scope & non-goals

### Purpose

The Exercises tab and exercise page need three things the API lacks:

1. **A type-change rule.** `PATCH /v1/exercises/{id}` changes `modality` without looking at logged sets, so an exercise with a year of weighted sets can be turned into a timed one. The design closes that gap: the type changes freely while the lineage has no logged sets, and afterwards only between types that need the same numbers.
2. **Which routines use an exercise,** so the delete warning can name them before the existing soft delete runs.
3. **When each exercise was last logged,** so "All exercises" can sort logged exercises first, most recent at the top.

Edit (name, type, muscles, equipment), delete and "make your own copy" already exist as `PATCH`, soft `DELETE` and `POST …/fork` with no UI caller. This spec pins what they do (§6.5, §6.6), closes the one hole in them (the fork overlay can set a type, §6.2), and adds two reads.

**Success:** the UI can (a) offer exactly the types an exercise may become, and trust the server to refuse the rest with a stable, static problem; (b) show "Used in A, B, C" before a delete; (c) sort and label All exercises from one small request; and none of the existing exercise, routine, History or export behavior changes.

### In scope

- `@sin/core` pure functions: `modalitiesCompatible`, `compatibleModalities`, `canChangeModality`, `lineageRootId` (§6.1).
- `409 exercise-type-locked` from `PATCH /v1/exercises/{id}` and from `POST /v1/exercises/{id}/fork` (when the overlay sets an incompatible `modality`), enforced inside the guarded `UPDATE` (§6.2, §6.3).
- `GET /v1/exercises/{id}/routines` (§5.1, §6.4) and `GET /v1/exercises/usage` (§5.2, §6.7).
- Characterization tests that pin the delete, edit and fork behavior the UI will rely on (§6.5, §6.6), including that a delete never touches a routine, a set, a snapshot, a record or the export.
- One log field and one log line (§9). README row, DESIGN.md Q33.

### Non-goals

- **Any routine edit by a delete or a type change** (design). Routines are not checked on a type change; a stale plan complains at the next routine save through `plannedSetViolations`, and a retired exercise blocks a routine save and a start through `assertItemExercisesUsable` (09 D12).
- **A type change that touches a snapshot.** `PATCH` writes only the `exercise` row (design): past workouts, a workout in progress and a card with no sets keep the `modality_snapshot` they were added under.
- **Editing or deleting a built-in.** `PATCH` on a built-in stays `409 exercise-immutable-use-fork`; `DELETE` stays `403 exercise-immutable`.
- **A UI, copy, routes or nav.** Spec 18.2.
- **Merging exercises, moving sets between exercises, a "my minutes were really calories" conversion** (design non-goals).
- **A built-in-copy guard** (a second "make your own copy" of a built-in you already copied). Settled behavior (DESIGN §4.5: a user may fork a global row more than once); owner ruling O2 (D11).
- **New records, charts, migrations, indexes, rate-limit groups, lock keys, env vars, metrics or span attributes.**

### Fit for one work session

Small: four pure functions, one error class, one guarded predicate on an existing `UPDATE`, two read statements with two routes, and characterization tests. Two PRs at the natural boundary, independent of each other:

- **Phase A: the rule.** `@sin/core` functions, the problem type, `PATCH` and fork enforcement, the log line. AC1-AC20.
- **Phase B: the reads and the delete pins.** Routines-using, usage, the delete / edit characterization, the benchmark, docs. AC21-AC38.

If the session runs out, the cut is that boundary, not a spec split. Phase B can ship first; the UI needs both.

## 2. Acceptance criteria

Tag every test `describe("03.4 ACn — …")`. A criterion with several clauses has a test per clause.

### Phase A: the type-change rule

1. **Compatibility is derived, symmetric and pinned.** `modalitiesCompatible(a, b)` is true iff `requiredMeasuresFor` and `forbiddenMeasuresFor` return equal sets for `a` and `b` (order ignored). It is reflexive and symmetric. Over all 64 ordered pairs of the eight modalities, the true pairs are the eight self-pairs plus exactly `weight_reps` ↔ `weighted_bodyweight`; a unit test pins that list, so a ninth modality or a changed rule forces a review.
2. **The UI-facing helpers.** `compatibleModalities(m)` returns `m` plus its partners in `MODALITY_VALUES` order (`weight_reps` → `[weight_reps, weighted_bodyweight]`; `calories` → `[calories]`). `canChangeModality({ from, to, hasLoggedSets })` is true iff `from === to`, or `!hasLoggedSets`, or `modalitiesCompatible(from, to)`. Both are pure, take no I/O, and `core:purity` passes.
3. **`lineageRootId`.** `lineageRootId({ id, forkedFromExerciseId })` returns `forkedFromExerciseId ?? id`; it is the one TypeScript statement of `COALESCE(forked_from_exercise_id, id)`.
4. **The problem type.** `ExerciseTypeLockedError` is `409`, slug `exercise-type-locked`, title "Exercise type locked", with one fixed `publicDetail` and a fixed internal message; neither contains a modality value, name or id (#57). It is listed in `config.problems` for `PATCH /v1/exercises/{id}` and `POST /v1/exercises/{id}/fork`, so both appear in `/openapi.json` with it.
5. **No logged sets: every type is allowed.** `PATCH { modality }` on an owned, active exercise whose lineage has no `set_entry` row returns `200` for each of the eight target values, and the row's `modality` is the new value.
6. **Logged sets: an incompatible change is refused and nothing changes.** With one set logged under the exercise, `PATCH { modality }` to a type that is not compatible returns `409 exercise-type-locked`. The row's `modality`, `updated_at` and `change_xid` are unchanged, and a later `GET /v1/exercises?since=` delta does not contain the row.
7. **Logged sets: the one compatible pair is allowed, both ways.** `weight_reps` → `weighted_bodyweight` and back return `200` and apply. A combined body (`name` plus a compatible `modality`) applies both.
8. **An unchanged type is no change.** With logged sets, `PATCH { modality: <the stored value> }` returns `200` and never reads sets; combined with other fields it applies them.
9. **"Logged" means any `set_entry` row.** Each of these locks the type: a warm-up set; a drop set; a failure set; a set with `is_complete = false`; a set in a live workout (`ended_at IS NULL`); a set in a finished workout. A `workout_exercise` with no sets does not.
10. **The check is on the lineage, through the built-in.** A fork of a built-in whose parent has the caller's sets, and none of its own, refuses an incompatible `PATCH` and allows a compatible one.
11. **The check is on the lineage, through a retired sibling.** The caller forked a built-in twice, logged sets under the first, then deleted it; the second fork refuses an incompatible `PATCH`.
12. **The check is scoped to the caller.** Another user's sets on the same built-in never lock the caller's fork. The caller's sets on an unrelated exercise never lock this one.
13. **Other fields never consult sets.** With logged sets, a `PATCH` of `name`, `primaryMuscleId`, `secondaryMuscleIds` and `equipmentId` (including clearing them with `null`) returns `200`, runs no set query, and equals today's behavior.
14. **Check order.** Not visible or malformed id: `404`. Retired (whoever owns it): `409 exercise-retired`. A global row: `409 exercise-immutable-use-fork`. A merged-field or reference failure: `422`. Only then the type rule. So an incompatible `modality` sent to a retired exercise is `exercise-retired`, to a built-in is `exercise-immutable-use-fork`, and with a bad `primaryMuscleId` is the `422`.
15. **The refusal is atomic with the write.** The type rule is a `NOT EXISTS` predicate on the same `UPDATE` statement that writes the row (§6.3), not a read followed by a write. With a client stubbed so the pre-read shows no sets and the `UPDATE` matches no row, the recheck reports `exercise-type-locked` when sets now exist, `exercise-retired` when the row was retired, and re-runs the statement once when neither holds (a set vanished in the gap). No advisory lock is taken.
16. **A type change touches only the `exercise` row.** After a compatible change on a lineage with finished workouts, a live workout and records: every `workout_exercise.modality_snapshot` (finished and live), every `set_entry` row, and every `personal_record` row are byte-identical; `records:rebuild --user` produces the same rows; `lockUserRecords` is not called and no recompute runs.
17. **The fork overlay obeys the rule.** `POST /v1/exercises/{builtIn}/fork { modality }` with logged sets in the origin's lineage and an incompatible value returns `409 exercise-type-locked`, inserts nothing and leaves the caller's active count unchanged; a compatible or equal value returns `201`; with no sets in the lineage every type returns `201`. The comparison is against the origin's `modality`.
18. **Fork characterization.** `POST …/fork` bodiless returns `201` with `Location`; copies `name`, `modality`, both muscle fields and `equipmentId`; sets `forkedFromExerciseId` to the origin and `ownerUserId` to the caller; applies a `name` overlay; counts against the shared cap (the 500th active exercise succeeds, the 501st is `exercise-limit-reached`); and a second fork of the same origin while the first is active also returns `201` (settled behavior, D11), both sharing the root.
19. **Built-ins stay immutable.** `PATCH` on a built-in is `409 exercise-immutable-use-fork`; `DELETE` is `403 exercise-immutable`; neither changes the row.
20. **Logging.** `custom_exercise_updated` gains a boolean `modality_changed` (true only when the stored value changed). A refused type change logs `custom_exercise_type_change_refused` once with `exercise_id`, `owner_user_id`, `from_modality`, `to_modality` (enum values only); a fork refusal logs the same line with the origin's id. No line carries a name, muscle or equipment id.

### Phase B: the reads and the delete pins

21. **Routines using an exercise: shape and order.** `GET /v1/exercises/{id}/routines` returns `200 { routines: [{ id, name, oneOffUntil }] }`: every routine of the caller with at least one item whose `exercise_id` is `{id}`, each once even if the exercise appears twice in it, ordered by `lower(name)` then `id`. A caller with no such routine gets `{ routines: [] }`.
22. **Ownership and visibility.** The id of another user's custom exercise, an absent id and a malformed id are all `404`. A built-in id returns `200` with the caller's routines that use it (never another user's). An owned retired exercise returns `200`, so the list is still available after a delete.
23. **Exact id, not lineage.** A routine using the built-in parent is not listed for the caller's fork of it, and a routine using the fork is not listed for the parent.
24. **One-off routines count.** A one-off routine that uses the exercise is listed with its `oneOffUntil`; an ordinary routine has `null`. The read performs no sweep and no write: an expired, unswept one-off is listed and the `routine` row count is unchanged after the call.
25. **Routines read: cache, publication, limits.** The response has `Cache-Control: no-store` and no `ETag`; the route is in `/openapi.json` with `problems: [NotFoundError]`; it declares no `writeGroup` (assembly fails if it did); with the 50-routine cap reached and every routine using the exercise, all 50 are returned in one response (no pagination).
26. **Usage: shape and order.** `GET /v1/exercises/usage` returns `200 { exercises: [{ rootId, lastLoggedOn }] }` with `lastLoggedOn` a `YYYY-MM-DD` string, ordered by `lastLoggedOn` descending then `rootId`; a user with no sets gets `{ exercises: [] }`.
27. **Usage is keyed by lineage root.** Sets logged under a fork and under its built-in parent fold into one entry whose `rootId` is the built-in's id and whose date is the latest of the two; a fork's own id never appears as a `rootId`; a custom non-fork exercise is its own root. `lineageRootId` maps a catalog row to its entry.
28. **The date is the workout's `local_date`.** A workout started 23:30 local with a negative offset (so its UTC date differs) reports its `local_date`; after a Change Time that moves `local_date`, the next read reports the new date; the latest of several workouts wins.
29. **What counts as logged.** An exercise appears iff some `set_entry` row exists under it in the caller's workouts: a warm-up-only exercise, an `is_complete = false` set and a set in a live workout all count; a card with no sets does not; deleting the last set (or the workout) removes the entry. This is the same definition as AC9, so `rootId` present ⇔ the type is locked to compatible changes.
30. **Usage is scoped and complete.** Another user's workouts never contribute. Retired exercises (a deleted custom exercise, a deleted fork) still produce an entry under their root; the client ignores roots it does not show.
31. **Usage cache.** `Cache-Control: private, no-cache` with a strong `ETag`; a repeat with `If-None-Match` is `304` with no body; the `ETag` changes after a set is logged and after a Change Time that changes a date; `/openapi.json` lists it with `problems: []`.
32. **Usage latency.** `bench:exercise-usage` (a dev tool in the style of `bench:progress`, Docker, not CI) seeds 2,000 finished workouts × 10 exercises × 5 sets for one user plus 4 other users with similar volume, and reports `GET /v1/exercises/usage` p95 under 100 ms against local Postgres; the result is recorded in the PR.
33. **Delete: semantics unchanged.** `DELETE /v1/exercises/{id}` on an owned active exercise returns `204`, sets `is_active = false` and bumps `change_xid`; a repeat is `204` and a no-op; a built-in is `403 exercise-immutable`; another user's or an absent id is `404`. The route, its handler and its `problems` list are unchanged by this spec.
34. **Delete touches nothing else.** After deleting an exercise that has sets, records and routine items: every `set_entry`, `workout_exercise` (name and modality snapshots), `personal_record` and `routine_item` row is unchanged; `GET /v1/workouts/{id}` and the History list still show the exercise by its snapshot name.
35. **Routines after a delete (09 D12, pinned).** The routine still reads (`GET /v1/routines/{id}` returns the item with the retired exercise's id); `PUT` of that routine unchanged is `409 exercise-retired` naming `items.<i>.exerciseId`; `POST /v1/workouts { routineId }` is `409 exercise-retired`; `PUT` after removing the item succeeds. `GET /v1/exercises/{id}/routines` still lists it (AC22).
36. **Progress and records after a delete.** `GET /v1/progress/exercises/{id}` and `GET /v1/personal-records?exerciseId={id}` still return `200` with the lineage's data for the deleted id. Deleting a fork makes the built-in the visible row again: the delta carries a tombstone for the fork and no row for the built-in; the built-in's own `change_xid` is unchanged.
37. **A stale plan starts as planned (characterization).** Starting a workout from a routine whose item plan carries measures the exercise's current type forbids (after an unlogged type change) returns `201`, copies the plan verbatim into `workout_planned_set`, and snapshots the new `modality_snapshot`. The 18.2 prefill must show only measures the type carries (§12 D22); this AC pins that the server does not rewrite or refuse.
38. **No collateral change.** The account export contains the same exercise and routine documents as before (inactive owned exercises included, as today); the Spec 11 purge test still passes with no new table; `/openapi.json` is regenerated and the CI drift check passes; `lint`, `typecheck`, `core:purity` and the app-assembly gates (CORS methods, `writeGroup`, publication) pass.

## 4. Data model

**No migration.** `0015` (Spec 05.3) stays the newest, so the whole-schema `prisma migrate diff` no-drift check stays where 05.3 puts it; nothing moves. Every statement in §6 runs on existing indexes:

| Statement | Access path |
|---|---|
| lineage ids (§6.2) | `exercise` primary key for the root; `exercise_owner_idx` for the caller's forks (≤ 500 rows) |
| has-sets probe | `workout_exercise_exercise_idx` (`exercise_id`) → `workout` primary key filtered by `user_id` → `set_entry_workout_exercise_number_key` (leading `workout_exercise_id`) |
| usage | `workout_user_started_idx` (`user_id`, …) → `workout_exercise` by `workout_id` (the `workout_exercise_position_key` constraint's leading column) → `exercise` primary key; `set_entry` probed by the unique key |
| routines using | `routine_item_exercise_idx` (`exercise_id`) → `routine` primary key filtered by `user_id` |

`exercise.forked_from_exercise_id` has no index (0003 added only the FK); the lineage statement avoids it by reading the root by primary key and the caller's forks through `owner_user_id`, so the table's growth with other users' rows never enters the plan (D18).

## 5. API surface

### 5.1 `GET /v1/exercises/{id}/routines`

Auth: bearer. Path param: the exercise id (any visible exercise, retired included). Response `200`:

```json
{ "routines": [ { "id": "…", "name": "Push A", "oneOffUntil": null } ] }
```

`oneOffUntil` is the routine's `one_off_until` as an ISO-8601 UTC string, or `null` (Spec 09.3). No other routine field. Config: `published: true`, `problems: [NotFoundError]`, no `httpCache` (so `Cache-Control: no-store`), no `writeGroup` (a read). Rate limit: the existing `/v1` read limits (05.2 L1); no new group or budget.

### 5.2 `GET /v1/exercises/usage`

Auth: bearer. No parameters. Response `200`:

```json
{ "exercises": [ { "rootId": "…", "lastLoggedOn": "2026-10-24" } ] }
```

`rootId` is a **lineage root** exercise id (the built-in's id for a fork), `lastLoggedOn` the latest `workout.local_date` of the caller's workouts that hold at least one set under that root. Sorted by `lastLoggedOn` descending, `rootId` ascending. Un-paginated: bounded by the number of distinct exercises the caller ever logged (at most the catalog plus 500 custom exercises, about 60 KB), the same documented exception as 07.2 D6. Config: `published: true`, `problems: []`, `httpCache: "revalidate"` with `strongEtag("exercise-usage", JSON.stringify(exercises))` and `If-None-Match` → `304`, as `GET /v1/routines` does. The route is `GET`-only and registered beside `/exercises`; the only other `/exercises/…` GET is the `{id}/routines` read above, so there is no path collision (find-my-way matches the static segment first in any case).

### 5.3 Changed behavior on existing routes

| Route | Change |
|---|---|
| `PATCH /v1/exercises/{id}` | adds `409 exercise-type-locked` (AC6); request and response shapes unchanged |
| `POST /v1/exercises/{id}/fork` | adds `409 exercise-type-locked` when the overlay's `modality` is incompatible and the lineage has sets (AC17); shapes unchanged |
| `DELETE /v1/exercises/{id}` | none (AC33) |

Problem body (RFC 9457, both scopes as today):

```json
{ "type": "…/exercise-type-locked", "title": "Exercise type locked", "status": 409,
  "detail": "This exercise already has logged sets, so its type can only change to one that logs the same measures. Create a new exercise instead." }
```

## 6. Behavior & logic

### 6.1 The rule, as pure `@sin/core` functions

New file `packages/core/src/modality-change.ts`, exported from the package index:

```ts
modalitiesCompatible(a: Modality, b: Modality): boolean   // same required set AND same forbidden set
compatibleModalities(m: Modality): readonly Modality[]    // m and its partners, MODALITY_VALUES order
canChangeModality(i: { from: Modality; to: Modality; hasLoggedSets: boolean }): boolean
lineageRootId(e: { id: string; forkedFromExerciseId: string | null }): string
```

**Checked against Spec 05.3 §6.1 (all eight rows).** Each row's required and forbidden lists partition the five measures `reps, weight, distance, durationS, calories`, so "equal required set" implies "equal forbidden set"; the function compares both so a future *optional* measure cannot slip through.

| Modality | Required | Partners |
|---|---|---|
| `weight_reps` | weight, reps | `weighted_bodyweight` |
| `weighted_bodyweight` | reps, weight | `weight_reps` |
| `bodyweight_reps` | reps | none |
| `duration` | durationS | none |
| `distance_duration` | distance, durationS | none |
| `calories` | calories | none |
| `weight_distance` | weight, distance | none |
| `weight_duration` | weight, durationS | none |

So the design's statement holds after 05.3: `weight_reps` ↔ `weighted_bodyweight` is the only pair; none of the three new types pairs with anything (`weight_distance` shares `weight` with `weight_reps` but needs `distance`, not `reps`; `weight_duration` needs `durationS`; the nearest legacy neighbor of each differs in a required measure). Compatibility is an equivalence relation (equal required sets), so any lineage that obeys the rule stays internally compatible however many hops it took.

### 6.2 "Has logged sets": the lineage of the caller's sets

For the target row `x`, `root = lineageRootId(x)` (computed in SQL as `COALESCE(forked_from_exercise_id, id)`). The lineage ids are the root itself plus the **caller's** forks of it, retired included:

```sql
WITH lineage AS (
  SELECT id FROM "exercise" WHERE id = $root
  UNION ALL
  SELECT id FROM "exercise" WHERE owner_user_id = $user AND forked_from_exercise_id = $root
)
SELECT EXISTS (
  SELECT 1
  FROM "workout_exercise" we
  JOIN "workout" w     ON w.id = we.workout_id AND w.user_id = $user
  JOIN "set_entry" se  ON se.workout_exercise_id = we.id
  WHERE we.exercise_id IN (SELECT id FROM lineage)
)
```

Any `set_entry` row counts: any `set_type`, complete or not, in a live or a finished workout (D3). The `w.user_id` filter is what keeps a built-in's other users' sets out. The same statement text, as a `Prisma.sql` fragment, is the `NOT EXISTS` in §6.3 and the fork pre-check; there is one copy (`lineageHasSetsSql`, in `exercise.prisma.ts`).

**Fork overlay.** `forkExercise` runs the probe with `root = origin.id` only when `overlay.modality` is present, differs from `origin.modality`, and is not `modalitiesCompatible` with it. It is a plain read before the capped insert, not part of the insert statement: the insert already holds the per-user cap lock, and a set logged in that millisecond window is the same accepted residual as in D7.

### 6.3 `updateExercise`, in order

1. Existing: `loadVisibleRow` (`404`), retired (`409 exercise-retired`), global (`409 exercise-immutable-use-fork`), `mergeWritableFields`, `assertMergedFieldsValid` (`422`), `validateReferences` (`422`).
2. `typeChange = merged.modality !== before.modality`. Needs the lineage guard iff `typeChange && !modalitiesCompatible(before.modality, merged.modality)`. When it does not, the statement is today's, byte for byte (AC8, AC13).
3. The guarded `UPDATE` gains one conjunct, only when the guard is needed:

   ```sql
   UPDATE "exercise" SET … WHERE id = $id AND owner_user_id = $user AND is_active = true
     AND NOT EXISTS (<§6.2 probe>)
   RETURNING …
   ```

   Postgres evaluates the predicate in the statement's own snapshot, so there is no gap between check and write other than the statement's own duration.
4. Zero rows: re-read the row. Retired → `exercise-retired`. Otherwise run the probe: sets exist → `ExerciseTypeLockedError`. Otherwise (the retired/locked cause vanished: a set deleted in the gap) re-run the `UPDATE` once; a second zero-row result is the existing `InternalError` branch.
5. The route logs `custom_exercise_updated` with `modality_changed = typeChange`, or, on `ExerciseTypeLockedError`, `custom_exercise_type_change_refused` and rethrows (§9).

### 6.4 Routines that use an exercise

```sql
SELECT r.id, r.name, r.one_off_until
FROM "routine" r
WHERE r.user_id = $user
  AND EXISTS (SELECT 1 FROM "routine_item" ri WHERE ri.routine_id = r.id AND ri.exercise_id = $id)
ORDER BY lower(r.name), r.id
```

Visibility first: the route resolves `$id` with `loadVisibleRow`'s predicate (`owner_user_id IS NULL OR owner_user_id = $user`; malformed ids are `404`, the exercise family's convention) with **no** `is_active` gate. One statement, no transaction, no sweep, no lock; a routine written concurrently is either in or out of the snapshot. The match is on the exact exercise id (D13). The response is `no-store` so the warning is as current as the request (D15).

### 6.5 Delete (unchanged, pinned)

`DELETE /v1/exercises/{id}` stays the 03.2 soft delete: `UPDATE exercise SET is_active = false, updated_at = now()` on the caller's own active row; `204`, idempotent; a built-in `403`; an invisible id `404`. The warning is client-side, from §6.4. What the delete leaves alone, all pinned by AC34-AC36:

- **Sets, workout cards, snapshots.** `workout_exercise.exercise_name_snapshot` and `modality_snapshot` are copied at add time, so History, the workout detail and the export show the exercise by that name; a later *rename* of a live exercise does not rewrite them either (D20).
- **Records.** `personal_record` is keyed on the lineage root and rebuilt from sets, not from `is_active`; nothing recomputes, nothing is deleted, and `resolveVisibleRoot` includes retired rows, so the Records list and the chart for a deleted id keep working. Deleting a fork changes the root's visible row back to the built-in (the client's `visibleRows` rule); the lineage's records are unchanged.
- **Routines.** The items stay; reads return them; `assertItemExercisesUsable` rejects a save or start with `exercise-retired` until the item is removed (09 D12). The delete never edits a routine (design).
- **Catalog sync.** The row's `change_xid` bump delivers a tombstone and the client drops it (03.3).
- **Hard deletes.** `workout_exercise.exercise_id` and `routine_item.exercise_id` are `ON DELETE CASCADE`, but no path hard-deletes an exercise except the account purge (DESIGN §4.2); the soft delete cannot trigger them.

### 6.6 Edit and fork (confirmed against the code)

- **`PATCH` accepts** `name` (1-120 chars, no control characters), `modality` (the eight values), `primaryMuscleId` (`string | null`), `secondaryMuscleIds` (≤ 4, no duplicates, none equal to the primary), `equipmentId` (`string | null`); `strict()`, so an unknown key is `422`; every key optional; `null` clears a nullable field. Muscle and equipment ids are verified to exist (`422`). Names are **not unique** (DESIGN §4.2): the exercise edit form does not need a duplicate check. `{}` is accepted and bumps `updated_at` and `change_xid` for no change; harmless, left alone (a client sends only changed fields).
- **`POST …/fork`** meets "make your own copy": it requires a visible, active, global origin (`404`, `409 exercise-retired`, `409 exercise-already-owned` for the caller's own row), copies `name`, `modality`, `primaryMuscleId`, `secondaryMuscleIds`, `equipmentId`, sets `forked_from_exercise_id`, inserts under the shared 500-exercise cap and the per-user advisory lock (`exercise-limit-reached` at the cap), and answers `201` with the new `Exercise` and `Location`. The overlay is optional (bodiless is `201`) and uses the `PATCH` field set. The copy carries no sets: history and records stay with the origin and are shared through the lineage root (DESIGN §4.5), which is why the type rule looks at the whole lineage (D3). Existing routines and past workouts keep pointing at the built-in; new workouts add the copy, and the client hides the built-in once the copy exists.
- **Gaps recorded:** (1) the fork overlay could set any `modality` regardless of the origin's history; closed by AC17. (2) A second fork of the same built-in is allowed (settled, D11; O2). (3) `PATCH` and `DELETE` take a non-UUID id as `404`, while the progress read takes it as `422`; the new routines read follows the exercise family (`404`).

### 6.7 Usage

```sql
SELECT COALESCE(x.forked_from_exercise_id, x.id)::text AS root_id,
       max(w.local_date)::text AS last_logged_on
FROM "workout" w
JOIN "workout_exercise" we ON we.workout_id = w.id
JOIN "exercise" x          ON x.id = we.exercise_id
WHERE w.user_id = $user
  AND EXISTS (SELECT 1 FROM "set_entry" se WHERE se.workout_exercise_id = we.id)
GROUP BY 1
ORDER BY 2 DESC, 1
```

One statement; a plain `date::text` is `YYYY-MM-DD` (never through a JS `Date`, the 07.1 convention). The route computes the `ETag` over the serialized array. **Cost:** one pass over the caller's `workout_exercise` rows (about 6-10 per workout; 20,000 at 2,000 workouts) with an index probe per row for the `EXISTS`; expected single-digit to low tens of milliseconds on Neon; AC32 measures it. If it ever matters, the next step is a per-user cache table, not an index.

**What the UI does with it** (for 18.2, not built here): sort the visible catalog rows by `usage.get(lineageRootId(row))` descending, then A-Z by the existing collator; a row with no entry shows "Built in" or "Yours".

## 7. Security & privacy

- **Authorization boundary.** Both reads filter by the acting user in SQL (`routine.user_id`, `workout.user_id`), never by trusting an id from the client. Exercise visibility uses the established predicate; a cross-user custom exercise id is `404`, indistinguishable from an absent one (no existence oracle).
- **Cross-user sets.** The has-sets probe joins `workout.user_id = $user`; a built-in is shared by every account, so omitting that join would let one user's logging lock another's fork. AC12 pins it.
- **Static messages (#57).** The new problem's detail and internal message are fixed text; the log line carries enum values and ids only. Request validation is unchanged (`UpdateExerciseSchema`).
- **No new data collected or stored;** the reads project existing columns. Routine names appear in a response to their owner only.
- **Rate limits.** The two reads use the existing `/v1` read limits; `PATCH`/`fork` stay in the `exercises` write group (a refusal costs a request like any other `409`).
- **Account lifecycle.** A soft-deleted account's `/v1` calls already `403` at `resolveUser`; nothing here bypasses it.

## 11. Deployment & rollback

- **No migration, no release step.** Deploy is the ordinary merge-to-`main`; staging auto-deploys, production by `deploy-prod` (Spec 15).
- **Order.** Either phase first. Both are additive for clients that do not call them. The one behavior change an existing client can see is `409 exercise-type-locked` on `PATCH`/fork; today's web never sends `modality` on an update.
- **Rollback.** `git revert`. No data was written differently, so nothing needs undoing.
- **Smoke.** After Phase B on staging: `GET /v1/exercises/usage` returns the owner's list; `GET /v1/exercises/{id}/routines` for a known routine item; `PATCH` an incompatible type on an exercise with sets returns `409`.

## 12. Decisions & open questions

- **D1 ✅ Delete is the existing soft delete, unchanged; the warning is client-side (owner, design).** Rationale: the design fixes it; the server already does the right thing (§6.5), and a server-side "force" flag would add a state the UI does not need. The warning needs only the §6.4 read.
- **D2 ✅ The type rule's shape (owner, design):** free while no sets; afterwards only between types that need the same numbers; routines unchecked; `PATCH` writes only the `exercise` row; built-ins are copied, not edited. Everything below is the builder's reading of "has logged sets" and "the same numbers".
- **D3 ✅ "Has logged sets" = any `set_entry` row of the caller's, any set type, complete or not, live or finished, anywhere in the exercise's lineage (the root plus the caller's forks, retired included) (mine).** Rationale: the harm to prevent is sets whose numbers a type forbids sharing a lineage with a type that forbids them; every `set_entry` row carries numbers, so any row counts, and an incomplete or warm-up row is as stranded as a working one. The **lineage, not the row,** because everything that reads history already works on the lineage: records are keyed on the root (07.0), the Progress chart and its sessions list fold a fork and its parent together (07.2), and a fork's page shows the built-in's history. If the check were per row, a user could fork a built-in with years of sets, change the copy to Duration, and the one chart would mix reps and seconds. Retired siblings count for the same reason: their sets are still in the lineage's chart. Rejected: row-only (the mixing above); finished-workouts-only or working-sets-only (a live set or a warm-up would be stranded by the change).
- **D4 ✅ Compatibility = equal required and equal forbidden measure sets, derived from `MEASURE_RULES` (mine).** Rationale: it is exactly "types that need the same numbers" with no second table to keep in sync; checked against all eight rows (§6.1): the only pair is `weight_reps` ↔ `weighted_bodyweight`, and none of the new types pairs. A test pins the pair list so a rule change is reviewed, not silently widened.
- **D5 ✅ The rule is pure `@sin/core`, shared with the UI (mine).** Rationale: the UI offers only allowed types and explains the refusal; the server enforces the same function, so they cannot disagree. `lineageRootId` is added so the web's mapping from a catalog row to a usage entry is not a second hand-written copy of the SQL expression.
- **D6 ✅ `409 exercise-type-locked`, a new problem type with a fixed message (mine).** Rationale: the request is well formed and valid for the exercise in the abstract; it conflicts with the exercise's state, which is what `409` means here (`exercise-retired` and `exercise-immutable-use-fork` are the precedent), so a client can tell it from a field error (`422`) and show "create a new exercise instead" without parsing. The detail names no modality (#57). Rejected: `422` (reads as a bad value); reusing `exercise-retired` (wrong meaning).
- **D7 ✅ The check is a `NOT EXISTS` predicate on the same `UPDATE`; no advisory lock, no new lock key (mine).** Rationale: it removes the read-then-write gap, leaving only the statement's own duration. A lock would have to be taken by set logging too, or it guards nothing: the 03.2 cap lock (`hashtext(user_id)`) serializes exercise inserts, which set writes never take, and CLAUDE.md says a lock key is never reused across caps. Taking a new lock in the set-write hot path for a rare edit is the wrong cost. **Accepted residual:** a set committed in the statement's own window can still land under the old type's snapshot. The design already accepts the larger case (a card added before the change keeps its snapshot, and sets logged on it afterwards stay valid under that snapshot), so the data is never invalid, only mixed in the same way; no stranded numbers, because set validation reads the snapshot, not the exercise.
- **D8 ✅ A type change never recomputes records and takes no `lockUserRecords` (mine).** Rationale: records are computed per set from `modality_snapshot`, never from `exercise.modality`, and the change writes no snapshot or set. With no sets there are no records; with sets the only allowed change is within `{weight_reps, weighted_bodyweight}`, which have identical eligibility for all of `heaviest_weight`, `best_est_1rm`, `best_set_volume` (the same `LOAD_MODALITIES` gate, 05.3 §6.2) and no other record type. AC16 proves it. **Known consequence, accepted by the design:** the weight means the bar load on `weight_reps` and the added load on `weighted_bodyweight`, so a lineage that crosses the pair compares the two in one chart. The UI may say so when offering the pair.
- **D9 ✅ A `modality` equal to the stored one is no change (mine).** Rationale: a form that always sends all fields must not be refused for an exercise it did not retype; it also costs no probe.
- **D10 ✅ The fork overlay obeys the same rule against the origin's type (mine).** Rationale: without it `POST …/fork { modality }` is a bypass of the very gap this spec closes, and the new copy shares the origin's lineage. Gap found in 03.2, closed here.
- **D11 ✅ Repeated forks of one built-in stay allowed (settled, DESIGN §4.5). Owner ruling O2 (2026-10-25): no.** Rationale: DESIGN says a user may fork a global row more than once and the lineage handles it; a guard would revisit a settled decision for a UI double-tap that the UI can prevent (disable the button on tap while the request is in flight; the built-in disappears from the list once the copy exists). DESIGN §4.5 is unchanged.
- **D12 ✅ Routines-using is its own read, `GET /v1/exercises/{id}/routines`, not a field on `Exercise` (mine).** Rationale: the catalog is a cached, `ETag`'d, delta-synced list whose rows change only on exercise writes; a field derived from routines would go stale on every routine write with no `change_xid` bump (or force one and re-send rows), and bloat a 500-row payload for a number needed on one screen. A read on demand is always current.
- **D13 ✅ Match on the exact exercise id, not the lineage (mine).** Rationale: the delete retires one row, and only routines that point at that row break (`assertItemExercisesUsable` checks the row's `is_active`); a routine using the built-in parent keeps working after the fork is deleted, so naming it would be a false warning.
- **D14 ✅ One-off routines are listed, with `oneOffUntil`; expired-but-unswept ones too; the read never sweeps (mine).** Rationale: a routine row that exists will fail to start or save, so it belongs in the warning, and the UI can label it; a `GET` that deletes would break the rule in CLAUDE.md that only the routine list and create sweep.
- **D15 ✅ Ordered `lower(name), id`, unpaginated, `no-store` (mine).** Rationale: at most 50 routines (the cap) and each once; alphabetical reads best in a sentence (the list's one-offs-first order serves browsing, not a warning). `no-store` because this is the last look before a destructive action; a stale cached answer is the one failure that matters.
- **D16 ✅ Last-logged is a new read, `GET /v1/exercises/usage` (mine).** Rationale: nothing existing serves it. The Records list (`GET /v1/personal-records`) omits any exercise with no record (all duration and distance + duration exercises, and bodyweight sets of 0 reps); History is paginated, so the client would walk every page and every workout's exercises; Progress is one request per exercise. One small request that returns exactly the data the tab needs is the smallest coherent change, and the unconditional `ETag` keeps repeat opens cheap.
- **D17 ✅ Usage is keyed by lineage root, dated by `workout.local_date`, and counts the same sets as the type lock (mine; the live-workout and warm-up part is owner ruling O1, 2026-10-25: yes).** Rationale: **root** because a fork shows the built-in's history on its page and its records and chart are lineage-wide; an unhidden fork must not read "never logged" for an exercise the lifter has done for years. The server returns roots and the client maps with `lineageRootId` (the client already holds `forkedFromExerciseId`), so the server need not know which rows the client hides. **`local_date`** because it is the calendar day the lifter sees in History and survives a Change Time; a `completed_at` is per set, can be null, and shifts in finished edits. **The lock's definition** so one rule holds: an exercise appears iff its type is locked to compatible changes, which lets the UI decide what to offer from the same request.
- **D18 ✅ No new index or migration (mine).** Rationale: the access paths in §4 are indexed; the one missing index (`forked_from_exercise_id`) is avoided by the lineage statement; the data per user is thousands of rows. AC32 is the tripwire; a cache table is the answer if it ever fails, not an index.
- **D19 ✅ Observability is one field and one `info` line; export and telemetry are unchanged (mine).** Rationale: a refusal is a lifter's mistake worth seeing in the log (is the UI offering a type the server refuses?), not worth a metric or a new allowlisted attribute (13.0 rules).
- **D20 ✅ Renaming an exercise does not rewrite history (mine, noted for the UI).** Rationale: snapshots are the point (05.0); History and the workout detail keep the name the set was logged under, and the exercise page and routines show the new name. The UI spec should say so near Edit.
- **D21 ✅ Deleting a fork re-surfaces the built-in; its records and history stay with the lineage (mine, pinned by AC36).** Rationale: it follows from the client rule that a built-in is hidden only while an active fork exists, and the records never moved.
- **D22 ✅ A started routine copies a stale plan verbatim (mine, pinned by AC37).** Rationale: "routines are not checked" (design). The start copy does not validate planned measures against the exercise's current type, and an immutable snapshot should not be rewritten. The UI spec must make the entry prefill show only measures the card's type carries (`visibleMeasures`), so a stale reps target on a Duration card is invisible rather than wrong. If the owner wants the start to refuse, that is a later spec.

### Owner rulings (2026-10-25)

- **O1: yes, "last logged" counts a live workout's sets and warm-ups** (D17, D3, AC9, AC29). One definition, shared with the type lock, so the UI decides what to offer from the usage request alone. Accepted cost: an exercise being logged right now reads "today" while its Progress page has no session until the workout finishes.
- **O2: no server guard against a second copy of the same built-in** (D11, AC18). The UI disables the button on tap; the built-in leaves the list once the copy exists. DESIGN §4.5 stays as it is.

No question remains open.
