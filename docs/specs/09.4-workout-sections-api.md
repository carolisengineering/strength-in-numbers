## 1. Purpose, scope & non-goals

The owner follows plans someone else wrote and types them in while training. A workout started empty is a flat list; a workout started from a routine has sections the owner cannot touch. Spec 09.2 made a workout's sections an immutable snapshot of the start copy (D9). This spec reverses that for the **workout's own** sections: the owner can **add** a section (name, optional note) to a live or finished workout, **rename / re-note** it, **remove** it (its exercises stay, loose), **move an exercise into or out of a section**, and the next exercises they add **land in the section they just made**. Nothing goes back to the routine. Spec 10.6 is the UI.

> **First-principles note — "placement is the server's job".** A workout's exercises are one list ordered by `position`; a section is only a label (`section_id`) on some of them, and the screen draws a heading wherever a run of the same label begins. So "put this exercise into Warm-up" is really two writes: set the label, **and** move the exercise to where Warm-up's run is, or the heading would be drawn twice. If the browser did both as two requests, a failure between them (or two tabs) would leave the list in a state the rules forbid. So the server does both in one transaction, with the same position-shifting code that Move up/down already uses.

> **First-principles note — "why the database cannot fix gaps for us".** `workout_section.position` is unique per workout through a plain unique **index**. Unlike the exercise positions (a deferrable constraint the code defers per transaction), an index is checked row by row, so `UPDATE … SET position = position - 1` over several rows can collide with a neighbor mid-statement and fail depending on row order. Closing the gap after a delete therefore renumbers one row at a time in ascending order (§6.4).

### In scope

- Migration `0014_workout_section_origin`: `workout_section.added_in_workout boolean NOT NULL DEFAULT false`.
- `@sin/core`: `WorkoutSection.addedInWorkout`; `CreateWorkoutSectionSchema`, `UpdateWorkoutSectionSchema`; `UpdateWorkoutExerciseSchema.sectionId`; pure `sectionForNewExercise`, `insertIndexForSection` (`sections.ts`).
- Routes: `POST /v1/workouts/{id}/sections`, `PATCH /v1/workout-sections/{id}`, `DELETE /v1/workout-sections/{id}` (new); `sectionId` on `PATCH /v1/workout-exercises/{id}`; the C4 rule on `POST /v1/workouts/{id}/exercises` (no new key).
- All of them on a live **and** a finished workout through `withWriteMode` (Spec 07.4); a section move reuses the reorder path including its record recompute.
- Logging, `finishedEdit` kinds, export, the `assertSectionsConsistent` extension.

### Non-goals

- **UI** (Spec 10.6). **No client reads or writes the new surface until 10.6** (DESIGN §6 rollout convention).
- Reordering sections, inserting a section in the middle (a new one is always last), nesting, templates, offline section writes (outbox), saving a workout as a routine, any routine change (brief C2, non-goals).
- Any change to records, progress, finish stats, the History list row, the one-off routine flow, or the start copy (it still writes `added_in_workout = false` by default).
- A new advisory-lock key (§6.6), a new rate-limit group, a body-limit change, a scheduler.
- Idempotency for `POST …/sections` (D10): like `POST …/exercises` it has none; duplicates by name are legal.

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("09.4 AC7 — …")`). Infra / pipeline criteria are verified by CI or review (§10). "Finished" means the preflight read `ended_at IS NOT NULL`.

**Shapes**

1. **Contract.** `WorkoutSection` gains `addedInWorkout: boolean` as its **last** key, **required** in `@sin/core` (no `.default`, `.optional()`, `.catch`; Spec 10.1 D4). `UpdateWorkoutExerciseSchema` gains `sectionId` (`WorkoutSectionId | null`, optional) and stays strict; `AddWorkoutExerciseSchema` is unchanged and strict (a `sectionId` key there is `422`). New `CreateWorkoutSectionSchema` `{ name, notes? }` and `UpdateWorkoutSectionSchema` `{ name?, notes? }` (both strict). `WorkoutSchema` (hence `POST /v1/workouts`, the finish response, `WorkoutSummary`, every History row) and `WorkoutExercise` are unchanged: a test pins their key sets. `/openapi.json` is regenerated (CI drift step green) and publishes the three new routes with their problems.
2. **Reads carry the flag.** `GET /v1/workouts/{id}`, `GET /v1/workouts/active` and the account export return `addedInWorkout` on every section: `false` for a section copied from a routine and for every section that existed before `0014`, `true` for one created by `POST …/sections`. It comes from the same single statement as the section list (`workoutSectionsJson`, Spec 09.2 §6.3), so a read can never show sections of one moment and exercises of another.

**Section writes**

3. **Create.** `POST /v1/workouts/{id}/sections` with `{ name, notes? }` answers `201` with a `WorkoutSection`: `position` = the current section count (it goes after the last one), `name` trimmed, `notes` as sent or `null`, `addedInWorkout: true`. It works on a live and a finished workout. The workout's exercises, sets and other columns are untouched.
4. **Field matrix.** Strict; paths `name` / `notes`. `name` is required, trimmed, 1–40 characters, no control characters, duplicates allowed (also against copied sections); `notes` is `null` / absent or 1–2 000 characters, multi-line allowed, no control characters other than TAB / LF / CR (the `noControlCharsExceptWhitespace` rule); `""` notes, `name: ""`, a 41-character name, `notes: 2001` characters, an unknown key (`position`, `addedInWorkout`, `id`) and an empty body are each `422` on the offending path, all issues of a body collected into one `422`. Messages are static (§7).
5. **Cap.** The ninth section is `409 workout-section-limit` (new slug); copied sections count; removing one frees a slot. Two concurrent creates at seven sections end with exactly one `201` and one `409`, never nine rows, a duplicate position or a `500`. The DB (`position` 0–7 + unique index) is the floor under the handler.
6. **Update.** `PATCH /v1/workout-sections/{id}` changes exactly the keys sent: `name` (rules of AC4), `notes` (a string, or `null` to clear). `id`, `position`, `addedInWorkout` never change; `{}` and a body equal to the stored values answer `200` with the section and write nothing (`updated_at` unchanged, no `workout_edited` line). `position`, `addedInWorkout`, `id` or any unknown key is `422`.
7. **Remove.** `DELETE /v1/workout-sections/{id}` answers `204`. Every exercise that was in it keeps its row, its position, its sets and its notes and gets `section_id = NULL` (the FK's `SET NULL`; no exercise is deleted or moved). The remaining sections keep their relative order and are renumbered densely from 0 (§6.4). A repeat answers `404`. Removing the last section makes later `POST …/exercises` loose (AC16).
8. **Authorization.** For all three routes, a missing, malformed, foreign (another user's) workout or section is `404 not-found`, never `403`; a section addressed through the wrong workout cannot exist (the section route is addressed by section id and ownership is resolved through its workout, as `workout_exercise` is).
9. **Finished workouts.** The three routes (and AC11–AC16's writes) work on a finished workout: no `409 workout-finished`, no `409 workout-would-be-empty`. A section create / update / remove recomputes **no** records: the finished-mode statement log shows the per-user PR lock first (`lockUserRecords`, 07.0 AC18) and no `personal_record` statement; `workout_edited` carries `records_recomputed: false`. The workout's `ended_at`, `started_at`, `local_date`, sets, History row and `GET /v1/personal-records` are byte-identical before and after.
10. **Live workouts.** On a live workout the same routes run exactly their own statements (no PR lock). A finish that commits between the preflight and the row lock restarts the write once in finished mode (`assertStillLive`, 07.4 §6.1); a test races each write against a finish and asserts a legal outcome and no `40P01`.

**Exercise moves**

11. **`sectionId` on the exercise `PATCH`.** `PATCH /v1/workout-exercises/{id}` accepts `sectionId`: a section id of **the exercise's own workout** moves the exercise into it; `null` makes it loose. A `sectionId` that does not exist, belongs to another workout, or to another user's workout is `404 not-found` (one error for all three; the client treats it as "that section no longer exists"). A malformed id is `422` on `sectionId`. `sectionId` together with `position` is `422` on `sectionId` (static message `can't be combined with position`): the server decides the position (AC12). `sectionId` may be combined with `notes` and `supersetGroup`. A `sectionId` equal to the stored one is a `200` no-op for the section part (nothing moves, even in a non-contiguous list).
12. **Placement.** On a change of section the server moves the exercise to `insertIndexForSection(ranks of the workout's OTHER exercises in position order, rank of the target)` (§6.2): after the last exercise whose section is the target or an earlier section; if none, at the start of the first sectioned run; if there are no sectioned exercises at all, at the end. "No section" uses rank `-1`, i.e. the end of the leading loose run. Loose exercises in the middle or tail never count as anchors. The shift uses the existing reorder statements, so positions stay dense and unique, and the response is the moved `WorkoutExercise` with its new `position` and `sectionId`. A table test pins at least: first exercise into an empty section; into a section with exercises; into an earlier and a later section; out to "No section" with and without a loose tail; into an empty section whose predecessors are empty; a non-contiguous list.
13. **A superset does not cross a section boundary.** When the section changes and the body has no `supersetGroup` key, the server sets the exercise's `superset_group` to `NULL`; a body that carries `supersetGroup` stores it as sent (workout side, 09.2 §6.5). The other members of the old group are not touched (a group of one is legal and draws no bracket). A same-section request never changes the group.
14. **Finished mode follows Spec 07.4.** The move runs inside the same `withWriteMode` transaction; it reuses `repeatedRootOfWorkoutExercise`, so records are recomputed **exactly** as 07.4 AC7 does today: the moved card's lineage root is recomputed iff the position changed **and** that lineage appears more than once in the workout; no other root; a section change that leaves the position unchanged recomputes nothing. After any such edit `personal_record` equals what `records:rebuild` produces. Sets are never touched.
15. **Concurrency.** Racing (a) two moves of one exercise, (b) a move against the removal of its target section, (c) a move against `POST …/exercises`, (d) a section create against `POST …/exercises`, (e) a section remove against a set write on one of its exercises, (f) any of them against a finish or a discard, never raises `40P01`, never leaves a duplicate `(workout_id, position)`, an exercise pointing at a deleted or foreign section, or a gap in section positions (`assertSectionsConsistent` after each run).

**Add exercise (C4)**

16. **Where an added exercise goes.** `POST /v1/workouts/{id}/exercises` **without `position`**: if the workout's last section (highest `position`) has `added_in_workout = true`, the exercise gets that `section_id` and lands at `insertIndexForSection(…, that section's rank)`; otherwise (no sections, or the last section was copied from the routine) it is loose at the end, byte-for-byte today's behavior. **With `position`** the exercise is loose at that position, as today (the caller chose the place). The `201` carries the resulting `sectionId`. In a finished workout it recomputes nothing (adding a card changes no existing order, 07.4 AC7). Tests: manual workout + section → joins; routine workout with copied sections → loose; routine workout + added section → joins that section only; the added section removed → loose again; the added section is not last (cannot happen through the API, but a hand-built fixture) → loose.

**Migration, cross-cutting**

17. **Migration `0014`.** Additive: one `NOT NULL DEFAULT false` column; applies cleanly over `0001–0013` with existing rows untouched (all read `false`); the start copy leaves new rows `false` without naming the column (test: a routine-started workout's sections read `addedInWorkout: false`). No backfill, no new table, foreign key or index.
18. **No-drift check moves.** `prisma migrate diff` (migrated database → `schema.prisma`) reports no difference beyond the two generated `set_entry` columns, asserted in `0014`'s integration test (`workout-sections-migration`); `routine-one-off-migration.integration.test.ts` keeps its `0013` checks but no longer carries the whole-schema diff (CLAUDE.md).
19. **Export and purge.** The export carries `addedInWorkout` through the shared `workoutSectionsJson` + `toWorkoutSectionRecord` + `toWorkoutSectionDto`, with no export-specific statement; Spec 11's parity AC (export deep-equals the read routes) passes with a user-added section in the fixture; the export still issues **≤ 8** statements; the purge discovery test needs no change (no table or foreign key added).
20. **Route wiring.** The three new routes and the changed ones declare `config: { published: true, problems: […], writeGroup: "workouts" }` (app assembly fails without `writeGroup`); `RATE_LIMITS` is unchanged. `CORS_METHODS` already lists `POST`, `PATCH`, `DELETE` and is unchanged; real preflight tests are added for `POST /v1/workouts/{id}/sections`, `PATCH /v1/workout-sections/{id}` and `DELETE /v1/workout-sections/{id}` (an `inject` test never exercises the preflight, CLAUDE.md). The new `409` slug `workout-section-limit` renders as RFC 9457 on the root and the `/v1` scope and is added to the problem-matrix test.
21. **Logging hygiene.** New lines `workout_section_added`, `workout_section_updated`, `workout_section_removed`, `workout_exercise_sectioned` and the field additions of §9 carry ids, counts and booleans only: no section name, section note, exercise name or note in any captured line (distinctive strings sent, none found). `telemetry/allowlist.ts`, `views.ts` and `METRIC_NAMES` are unchanged (a test pins the allowlist).
22. **Unchanged behavior stays unchanged.** For a workout with no section call, everything in Spec 05.0 / 07.4 / 09.2 behaves byte-for-byte as before apart from `addedInWorkout` on sections (the existing suites pass unmodified apart from that field and 09.2 AC17's two assertions, §11). Routines, the start copy's snapshot and a later routine edit never reach a workout section, and a workout section write never reaches a routine (C2).
23. **Consistency helper.** `assertSectionsConsistent(db)` (Spec 09.2 AC29) gains: every workout's section positions are dense from 0, and every `workout_exercise.section_id` belongs to the exercise's own workout; it runs after each integration test of this spec.
24. **Pure helpers.** `sectionForNewExercise(sections)` and `insertIndexForSection(ranks, rank)` live in `@sin/core` `sections.ts` (no I/O; `core:purity` green), are exhaustively unit-tested against the table of AC12, and are the **only** implementations — the API uses them for AC12 / AC16 and Spec 10.6 uses `sectionForNewExercise` for the "New exercises go into …" line, so server and screen cannot disagree.
25. **Docs and release order.** DESIGN.md, `docs/specs/README.md`, CLAUDE.md, the amended specs and the runbook carry the edits of §11; the release order (migration `0014` before the code; API before Spec 10.6) is stated in the PR description and a runbook "0014" note.

## 4. Data model

Migration `apps/api/prisma/migrations/0014_workout_section_origin/migration.sql`, hand-authored like `0009`–`0013`; `schema.prisma` gains `WorkoutSection.addedInWorkout Boolean @default(false) @map("added_in_workout")`. Additive / expand-only.

```sql
-- Spec 09.4 §4 — 0014_workout_section_origin. Additive, expand-only.
-- Down (dev/test teardown only; production undo is `git revert` + a forward migration):
--   ALTER TABLE "workout_section" DROP COLUMN "added_in_workout";

ALTER TABLE "workout_section"
    ADD COLUMN "added_in_workout" BOOLEAN NOT NULL DEFAULT false;
```

Notes:

- **Why a column.** "Added during this workout" (brief C4) cannot be derived: a copied section and an added one have the same shape, and `created_at` is no help (a routine-started workout's sections are created at start, inside the same second a quick lifter adds their own). A stored fact is one boolean on the row it describes (D3).
- **Lock profile.** A constant `DEFAULT` on `NOT NULL` is metadata-only in PostgreSQL 11+ (no rewrite); the `ACCESS EXCLUSIVE` lock lasts milliseconds on a small table.
- **No backfill.** Before `0014` nothing could add a section, so `false` is correct for every existing row. The start copy (`INSERT … SELECT` of 09.2 §6.4) names no such column and gets the default.
- **No cross-workout guard in the schema.** `workout_exercise.section_id` stays a single-column FK; the handler checks the section belongs to the exercise's workout (AC11) and `assertSectionsConsistent` is the test-side guard — the same trade 09.2 §4 made (a composite FK would need `SET NULL (column)`, which Prisma cannot express; the no-drift check would flag it). No `0014` constraint is added for it (D11).
- **Positions.** `workout_section_workout_position_key` stays a plain unique index (non-deferrable), `position` CHECK 0–7 stays: the cap's floor. Deleting a middle section leaves a gap until the same transaction renumbers (§6.4); after commit positions are dense.

## 6. Behavior & logic

### 6.1 Shared envelope

Every write below resolves ownership with a cheap unlocked preflight (`… JOIN workout w ON … WHERE w.user_id = $acting`, returning `w.ended_at`), then runs in `withWriteMode(prisma, userId, preflightEndedAt, run)`: finished mode takes `lockUserRecords` first; inside, `SET CONSTRAINTS workout_exercise_position_key DEFERRED`, `pg_advisory_xact_lock(hashtext(workoutId))`, `SELECT ended_at FROM workout … FOR SHARE`, `assertStillLive`. This is the existing per-workout structure lock of Spec 05.0 §6.8, now also serializing section writes (D6). A vanished row under the lock is `404`.

### 6.2 Placement (`insertIndexForSection`)

Under the lock the handler reads the workout's OTHER exercises as `(position, section position or -1)` in position order, calls the pure helper, and uses the result as the exercise's final index in the existing shift statements of `addWorkoutExercise` (insert at `i`, shift `>= i` up) or `updateWorkoutExercise` (move to `i`, shift the rows in between). Worked examples (sections W, S; `·` = loose):

| List (before) | Action | After |
|---|---|---|
| `[·A]` + empty W | move A into W | `[A(W)]` (no sectioned exercise: end) |
| `[a1(W), a2(W), b1(S)]` | move `·X` (last) into W | `[a1, a2, X(W), b1]` |
| `[a1(W), b1(S), ·Y]` + empty section C added last | add X (C4) | `[a1, b1, X(C), ·Y]` — before the loose tail |
| `[a1(W), b1(S)]` | move `a1` to "No section" | `[a1, b1]` (first sectioned index = 0 → stays first) |
| `[·L, a1(W), b1(S), ·Y]` | move `b1` to "No section" | `[·L, b1, a1, ·Y]` |
| `[a1(S), ·M, b2(S)]` (a gap) | move `X` into S | after `b2` |

Moving to the exercise's current index is a position no-op: no shift, no `moved`.

### 6.3 `PATCH /v1/workout-exercises/{id}` with `sectionId`

After the existing locks and the target `FOR UPDATE`: if `sectionId` is a string, `SELECT position FROM workout_section WHERE id = $s AND workout_id = $w FOR SHARE` (no row → `404`); `null` → rank `-1`. If it equals the stored `section_id`, the section part is a no-op. Otherwise compute the final index (6.2), run the existing reorder shift, write `section_id`, set `superset_group = NULL` unless the body has `supersetGroup` (AC13), and `updated_at = now()` — one `UPDATE … RETURNING`. Finished mode: `moved` (position changed) → `repeatedRootOfWorkoutExercise` → `recomputeTimed`, as today; the `FinishedEdit` and `moved` flags feed `workout_edited`. `exerciseEditKind` gains `exercise_sectioned` (checked first: a request that changed the section is classified by it; `records_recomputed` still tells whether the move mattered).

### 6.4 Section writes

- **Create:** under the lock, `SELECT count(*)`; `>= 8` → `WorkoutSectionLimitError`; insert at `position = count` with `added_in_workout = true`, `id = uuidv7()`.
- **Update:** `SELECT … FROM workout_section WHERE id = $s FOR UPDATE`; compare; `UPDATE` only if a value differs (sets `updated_at`); return the row.
- **Remove:** `SELECT position FROM workout_section WHERE id FOR UPDATE` (gone → `404`); count its exercises (for the log); `DELETE` (the FK nulls `section_id` on those exercises; their positions are untouched); then, for each remaining section with `position > removed`, ascending, `UPDATE … SET position = position - 1 WHERE id = $` — at most seven single-row statements, each into a slot the previous one freed, so the non-deferrable index is never violated (D5). No exercise statement.
- None of the three recomputes records (AC9). Exercises removed from a section keep their places; a loose exercise in the middle of the list is legal and drawn honestly by `sectionSegments` (Spec 10.3 AC11, 09.2 §6.5).

### 6.5 C4 on add

In `addWorkoutExercise`, after the count read and only when `fields.position === undefined`: read the workout's sections; `const target = sectionForNewExercise(sections)`; if `target`, compute the index (6.2) with `rank = target.position`, shift as for an explicit position, and insert with `section_id = target.id`; else `computeAppendPosition(n)` and `section_id` null — exactly today. The add stays `noRecompute` in finished mode: inserting a card changes no existing card's relative order.

### 6.6 Locks and order

No new key. Section writes use the per-workout structure lock (`hashtext(workoutId)`), the same one exercise adds / moves / removes already use, so C4 (a read of the sections followed by an insert) and moves (a read of the target section followed by a shift) are atomic against section creates and removes. Lock order, all modes: **[finished: PR lock] → structure advisory lock → workout row `FOR SHARE` → section row → exercise rows**. A finish takes PR lock → (routine row) → workout `FOR UPDATE`, which waits on our `FOR SHARE`; a discard takes PR lock → workout row. Neither can form a cycle with a section write (it holds the PR lock first in finished mode and requests nothing the finish holds in live mode). Set writes lock the exercise row and the workout `FOR SHARE`, which is compatible; AC15 (e) races them.

### 6.7 Edge cases

- **A section with no exercises** is legal everywhere (it already is, 09.2); it never blocks a finish.
- **The last section removed** while earlier sections exist: the previous section is now last; if it was added during the workout, the next plain add joins it (the screen's line follows, 10.6).
- **A copied section can be renamed, re-noted and removed** (brief C1, owner-confirmed); renaming it does not make it "added" (the flag is origin, not edit history).
- **Re-adding after a lost response:** the create is not idempotent; a retry may produce two sections with one name (legal). The client refetches before offering a retry (10.6, as for add-exercise).
- **Clock:** `updated_at` uses the database `now()`.
- **A workout deleted while the request waits:** `404`.

## 7. Security & privacy

- **Authorization is inherited.** Every statement resolves the section / exercise through its workout's `user_id = $acting`; a foreign id is `404`. The `sectionId` in a body is checked against the exercise's own workout inside the transaction, so a client cannot attach an exercise to another workout's (or user's) section even by guessing a uuid (AC11; an integration test uses two users).
- **Mass assignment.** The client chooses a name, a note, and which section an exercise is in. `position`, `addedInWorkout` and `id` of a section are never accepted (strict schemas, AC4 / AC6).
- **Input as text.** Names and notes are user text; the server stores them verbatim (after trim) and never interprets them. Validation messages are static (#57): the new schemas' `message:` strings are constants (`static-issue-messages.test.ts` probes them), so a 422 body never echoes a value.
- **Logging.** Never a section name, section note, exercise name or exercise note (AC21). The `err` serializer already masks request-validation errors.
- **Abuse bounds.** The cap (8) and the `workouts` write group (60/min) and in-flight cap bound a loop; a section note is ≤ 2 000 characters, so a workout's sections total ≤ 16 KB.
- **No new PII.** The export already contains sections.

## 11. Deployment & rollback

`0014` is additive and expand-only: one column with a constant default, a millisecond lock.

**Release order (hard dependency):**

1. **Migrate first.** `DATABASE_URL='<neon direct url>' pnpm run db:migrate:deploy` applies `0014` **before** the code goes live (manual step, never on boot); verify with `db:migrate:status` on Neon. Old code never reads or writes the column.
2. **Then merge 09.4** → Render auto-deploys the API and the static site; the new bundle's `@sin/core` requires `addedInWorkout` in every workout read, so for the minutes the new bundle is live against the not-yet-deployed API the session and History screens would fail to parse — accepted on staging as 09.1 / 09.2 / 09.3 did; the web gains no *use* of the surface in this release.
3. **Verify** on staging: `GET /v1/workouts/{id}` shows `addedInWorkout: false` on every section; `POST /v1/workouts/{id}/sections` on a scratch workout answers `201`, a `PATCH` of an exercise's `sectionId` moves it, `DELETE` answers `204`. Consistency queries, expected `0`: `SELECT count(*) FROM workout_section WHERE added_in_workout;` immediately after deploy (before any test write), and `SELECT count(*) FROM (SELECT workout_id FROM workout_section GROUP BY workout_id HAVING max(position) + 1 <> count(*)) t;`. Record as a "0014" note in `docs/runbooks/first-deploy.md`. No backfill, no `records:rebuild`.
4. **Spec 10.6 may merge only after step 3** (API one release ahead).

**Rollback:** revert the code commit; the column stays, inert. Old code ignores it: sections added in workouts remain (they are ordinary rows; the old UI draws them as sections, and cannot edit them). If 10.6 is merged, **revert it first** (DESIGN §6: rolling the API back past a response field rolls the client back). Nothing to convert: no data is hidden by a rollback.

**No feature flag** — "off" is the absence of a client that calls the routes.

## 12. Decisions & open questions

Owner decisions are labeled **(owner)**; calls that are the designer's or builder's and may be refined are labeled **(mine)**.

### Resolved (owner-approved 2026-10-22, from the brief)

- ✅ **D1 — A workout's sections are the workout's own (owner).** Sections can be added to a live **and** a finished workout, including a workout started from a routine (C1, "Yes"); editing a copied section is allowed; nothing goes back to the routine (C2). **Rationale:** the owner types other people's plans in as they train; a flat list loses the parts of the plan and the details ("EMOM 10 min") that have no other home. **Rejected:** a frozen snapshot with a "save as routine" round trip (a different feature, out of scope).
- ✅ **D2 — "Add exercise" keeps today's behavior in a routine workout until the owner adds a section (owner, C4).** *Rationale:* a copied plan's added exercise stays "Other exercises" at the end; once the owner makes a section themselves, the next exercises go into it. The stored fact that makes this knowable is D3.
- ✅ **Remove asks first, exercises survive (owner, C6).** The server side is: delete the section row, loosen its exercises, delete nothing else. The confirm dialog is Spec 10.6.
- ✅ **Limits (C3), online-only (C8), new section last (C7), picking a section places the exercise at the end of that section (C5), a superset splits at a section boundary (C9).** Server forms of C5 and C9 are D4 and D7.

### Resolved — builder calls the brief left open or qualified (mine)

- ✅ **D3 (mine) — `workout_section.added_in_workout`, migration `0014`, and the field on the DTO.** The brief said a migration "may" be needed; it is. **Rationale:** origin cannot be derived (§4), and the screen needs it too (the "New exercises go into …" line shows only when C4 applies), so it must travel on `WorkoutSection`. **Rejected:** a `kind`/`origin` enum (two values today, a boolean says it; a third origin would be its own migration), `created_at > started_at + ε` (a heuristic that mis-labels a quick lifter's copied sections), the client remembering which sections it made (lost on reload, wrong on a second device).
- ✅ **D4 (mine) — The server owns placement; the client sends only the target section (§6.2, §6.5).** **Rationale:** a client-computed `position` plus a `sectionId` is two facts that must agree; a stale list (second tab, a racing add) would produce a split section run the server then has to accept (workout writes are "stored as sent"). One transaction under the structure lock cannot. It also gives Spec 10.6 a one-request move (no `planSessionChange` choreography, no partial failure), and `sectionId` + `position` together is a `422` so the two facts cannot disagree. **Rejected:** the client planning position patches (the 10.1 regroup model: sequential `PATCH`es, partial failure, no Try again) and an optional `sectionId` on `POST …/exercises` (a second way to say what C4 already says; the client can move afterwards if it ever needs to).
- ✅ **D5 (mine) — Section removal renumbers one row at a time.** **Rationale:** the workout-side position index is a plain unique index, not a deferrable constraint (§1), so a set-based `position - 1` can fail on row order. Eight rows at most; ascending single-row updates always move into a freed slot. **Rejected:** leaving gaps (the next create at `count` could collide, and `position` 0–7 plus gaps breaks the cap's floor), making the index deferrable (a `0014` constraint change Prisma's schema language cannot express without drift).
- ✅ **D6 (mine) — Reuse the per-workout structure lock; no new advisory key.** C4 and moves each read the sections and then write exercise positions; they must be atomic against a section create or remove. The lock that already serializes exercise structure writes does exactly that. CLAUDE.md's "never reuse a key across caps" is about caps counted over different sets; this is one lock over one workout's structure.
- ✅ **D7 (mine) — The server drops a moved exercise from its superset.** The brief (C9) says "same rule as the routine editor"; the editor enforces it in `settle` (client-side). On a workout, the server stores supersets as sent (09.2 §6.5), so a second client or an old tab would otherwise create a superset spanning sections that `supersetRows` already splits for display but the data still holds. Clearing the label on the moved exercise is the minimal server rule; the rest of the group is left alone (a group of one draws nothing).
- ✅ **D8 (mine) — Routes under `/workout-sections/{id}` and `/workouts/{id}/sections`.** Mirrors `/workout-exercises/{id}` and `/workouts/{id}/exercises`: a child is created under its parent and addressed by its own id after.
- ✅ **D9 (mine) — A missing / foreign `sectionId` is `404`, not `422`.** The same call as `exerciseId` on add and `routineId` on start: an id that is not yours or not there is "not found", never a validation message that could tell a guessed uuid apart.
- ✅ **D10 (mine) — No idempotency key on section create.** Like `POST …/exercises` (Spec 05.0), a duplicate costs one extra, removable, legal section; a key would need a column. The UI refetches before offering a retry.
- ✅ **D11 (mine) — No composite FK or trigger for cross-workout `section_id`.** As 09.2 D11: the single write path checks it, `assertSectionsConsistent` is the guard, and the schema language cannot express the alternative without drift.
- ✅ **D12 (mine) — `exercise_sectioned` is checked first in `exerciseEditKind`.** A request that changed the section would otherwise log as `exercise_moved`; the section is the intent, `records_recomputed` carries the consequence.
- ✅ **D13 (mine) — Removing a section does not tidy its exercises' places.** They keep their positions (brief C6), so a loose exercise can sit between sectioned runs. Moving them would be a position change with record consequences in a finished workout; `sectionSegments` already draws this ("Other exercises") and the next move into "No section" tidies it.

### Resolved by reading the code (corrections and qualifications to the brief)

- **The brief's "A new migration may not be needed" — it is.** D3.
- **The workout-side position index is not deferrable** (`workout_section_workout_position_key` is a `CREATE UNIQUE INDEX`; the exercise one is a constraint the code defers). D5.
- **Today's "Add exercise" leaves a loose tail** after a routine workout's sections (09.2 §6.5), so "right after the section's own exercises, before any loose tail" (C4) needs the anchor rule of §6.2, not "append".
- **`PATCH /v1/workout-exercises/{id}` already has the machinery** for a move (position shift, deferred constraint, finished-mode recompute via `repeatedRootOfWorkoutExercise`); the new key reuses it rather than adding a route.

- **`409 workout-finished` cannot be returned by these routes** (07.4 D17 narrowed it to a re-finish; the live-to-finished race restarts the write).
