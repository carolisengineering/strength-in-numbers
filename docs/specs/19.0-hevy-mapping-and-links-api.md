## 1. Purpose, scope & non-goals

### Purpose

Carol has more than 1,000 workouts, routines and custom exercises in Hevy and wants (a) all of it in Strength in Numbers (SIN) once, and (b) Hevy to hold an accurate copy of the workouts she logs in SIN. Both directions need the same four things, and this spec builds them before any screen or bulk write exists:

1. **A gate.** The whole feature is for Carol's account only for now *(Carol)*. Every Hevy route answers `404` to anyone else and is absent from the public API document.
2. **The mapping:** which Hevy exercise is which SIN exercise, how their measures line up (the "(calories)" rule), which SIN exercise is the one a workout is sent as, and how SIN sections become Hevy placeholder exercises. It lives in the database, per account *(Carol)*.
3. **The translation,** as pure `@sin/core` code, in both directions: set types, units, RPE steps, types, sections, the mapping file's CSV format, and a fingerprint that says whether a workout changed since it was sent.
4. **Links to Hevy copies:** which SIN workout has which Hevy workout, set by a send, an import or a duplicate match, with a claim step that makes a double tap or a retry unable to create a second Hevy copy.

**Success:** with Carol's id in the allow-list, the web (Specs 20.x) can load, replace, patch and download the mapping, ask "has this workout been sent, and has it changed since", and build the exact body to send to Hevy, all from tested pure code; for every other user the routes do not exist; and no existing route, row or response changes except one enum value and one export block.

### In scope

- **Phase A (pure `@sin/core`, no migration, no route):** Hevy API schemas; the vocabulary; the type-pairing table and `hevyPairingProblem`; set translation both ways (units, rounding, RPE, set types, the measure rules); section rules; the workout export builder `buildHevyWorkout`; the fingerprint source `hevyFingerprintSource`; the mapping CSV (`parseMappingCsv`, `formatMappingCsv`); the export-as normalizer; muscle and equipment name tables; `WORKOUT_SOURCE_VALUES` gains `"hevy"` (so every web bundle knows the value a release before anything writes it, DESIGN §6).
- **Phase B (API):** the allow-list config and gate; migration `0016` (three mapping and link tables, a records-stale flag, the widened `workout.source` CHECK); `GET /v1/hevy/status`; `GET` / `PUT` / `PATCH /v1/hevy/mapping`; `GET` / `POST` / `PUT` / `DELETE /v1/workouts/{id}/hevy-link`; the `hevy` write group; the account export block; logs.

### Non-goals

- **Writing any workout, routine or exercise as an import.** Spec 19.1 (bulk workouts) and 20.1 (routines and custom exercises, through the routes that exist). Nothing in this spec writes `source = 'hevy'`.
- **Any call to Hevy from the server.** The Hevy key never reaches SIN's server *(Carol, option 2)*: no route takes it, CORS does not allow an `api-key` header to this API, and `req.headers` is already redacted from logs. A server-held key is a noted future option.
- **A UI,** copy, routes, CSP (20.0).
- **Fetching new Hevy workouts later,** Hevy's CSV export, copying every routine, exporting routines, deleting anything in Hevy (non-goals of the design).
- **Opening the feature to every user** (a separate decision; §12 D1 makes it a config change).
- **New metrics, span attributes, lock keys.** Logs only (D17).

### Fit for one work session

Phase A is wide and shallow: a dozen pure functions with table-driven tests. Phase B is one migration, four small repositories and eight routes on existing patterns. Two PRs: **Phase A** AC1-AC15, **Phase B** AC16-AC39. If the session runs out, the cut is that boundary. Phase A ships alone with no behavior change anywhere except the enum value.

## 2. Acceptance criteria

Tag every test `describe("19.0 ACn — …")`. A criterion with several clauses has a test per clause. "Pair" means one `hevy_exercise_pair` row; "mapping" means a user's pairs plus section rules.

### Phase A: pure `@sin/core`

1. **Vocabulary.** `@sin/core` exports frozen `HEVY_TYPE_VALUES` (`weight_reps, reps_only, bodyweight_reps, bodyweight_assisted_reps, duration, weight_duration, distance_duration, short_distance_weight`), `HEVY_SET_TYPE_VALUES` (`warmup, normal, failure, dropset`), `HEVY_RPE_STEPS` (`6, 7, 7.5, 8, 8.5, 9, 9.5, 10`), `MEASURE_RULE_VALUES` (`calories_as_reps, assist_weight_ignored`), `PAIR_ROLE_VALUES` (`exercise, skip, warmup_placeholder, workout_placeholder`), `SECTION_TREATMENT_VALUES` (`warmup_placeholder, workout_placeholder, notes_on_first`), and the limits `HEVY_PAIRS_MAX = 2000`, `HEVY_SECTION_RULES_MAX = 20`, `HEVY_LINK_CLAIM_TTL_S = 120`. Each is in `check-exports.mjs` and the barrel type test; `core:purity` passes.
2. **`WORKOUT_SOURCE_VALUES`** is exactly `["manual", "hevy"]`; `WorkoutSchema.source`, the OpenAPI enum and the web `Workout` type accept both; the existing `enums-workout` test is updated to the new list and nothing in `apps/api` or `apps/web` writes `"hevy"` yet.
3. **Hevy API schemas** (`dto/hevy-api.ts`). `HevyUserInfoSchema`, `HevyTemplatePageSchema`, `HevyWorkoutPageSchema`, `HevyRoutinePageSchema`, `HevyFolderPageSchema`, `HevyWorkoutSchema`, `HevyRoutineSchema`, `HevyTemplateSchema` parse fixtures copied from the OpenAPI examples (field names exactly those of Hevy's document: `exercise_templates`, `routines`, `routine_folders`, `workouts`, `page`, `page_count`; the user-info reply is wrapped, `{ data: { id, name, url, … } }`, and `HevyUserInfoSchema` parses that wrapper; the create-workout reply is `{ workout: [Workout] }`, the `PUT` reply a bare `Workout`; the create-template reply `id` is accepted as a string or a number and returned as a string). They require only the fields this app reads, tolerate absent or `null` optionals, strip unknown keys, and reject a missing required field, a wrong type and an enum outside the lists in AC1, with one exception: a **set's `type` is read as a plain string**, so one odd set type (for example `superset`) does not fail a whole page (Spec 20.1 D9 marks that workout unreadable on the client). Read-side required fields: template `id`, `title`, `type`, `is_custom`; workout `id`, `title`, `start_time`, `end_time`, `exercises[]`; workout exercise `index`, `title`, `exercise_template_id`, `sets[]` (`notes`, `superset_id` optional); set `type` (`index` optional; `weight_kg`, `reps`, `distance_meters`, `duration_seconds`, `custom_metric`, `rpe` optional and nullable); routine `id`, `title`, `folder_id` (nullable), `exercises[]`, each routine exercise `index`, `title`, `exercise_template_id`, `sets[]` (`notes`, `superset_id` optional and nullable); folder `id`, `index`, `title`. Also exported: `HevyWorkoutCountSchema` (`{ workout_count }`, a non-negative integer, for `GET /v1/workouts/count`), `HevyCreateTemplateBodySchema` (`{ exercise: { title, exercise_type, equipment_category, muscle_group, other_muscles } }`, with Hevy's enums) and `HevyCreateTemplateReplySchema`. `HevyPostWorkoutSchema` (the body we send: `{ workout: { title, description, start_time, end_time, is_private, exercises[] } }`) is strict.
4. **The type table and `hevyPairingProblem`.** `canonicalModalityForHevyType` is `weight_reps→weight_reps, reps_only→bodyweight_reps, bodyweight_reps→weighted_bodyweight, duration→duration, weight_duration→weight_duration, distance_duration→distance_duration, short_distance_weight→weight_distance`, and `null` for `bodyweight_assisted_reps`. `hevyPairingProblem(hevyType, modality, rule)` returns `null` (allowed) or a code (`type_mismatch`, `rule_not_allowed`, `rule_required`). Over all 8 × 8 × 3 (no rule, each rule) combinations the allowed set is pinned by a unit test: exactly the pairs where `modalitiesCompatible(canonical, modality)` holds (so `weight_reps` ↔ `weighted_bodyweight` both pair with Hevy `weight_reps` and `bodyweight_reps`), plus Hevy `reps_only` + SIN `calories` + `calories_as_reps` (the only calories pairing), plus Hevy `bodyweight_assisted_reps` + SIN `bodyweight_reps` + `assist_weight_ignored` (the only assisted pairing); every other combination is a problem; a rule on a combination it does not apply to is `rule_not_allowed`.
5. **`defaultMeasureRule(title, hevyType)`** returns `calories_as_reps` iff the title contains `(calories)` (case-insensitive) and the type is `reps_only`, else `null`. Pure; the UI uses it only to propose, never to apply silently.
6. **Import set translation** `hevySetToSin(set, ctx)`. Set types map `warmup→warmup, normal→working, dropset→drop, failure→failure`. Weight: Hevy kg becomes the user's unit, **rounded to the nearest 0.1 of that unit**, half away from zero (61.235 kg is `135` for a `lb` user and `61.2` for a `kg` user; 0.04 kg for a `kg` user is `0`). Distance stays meters, `distanceUnit: "m"`. Duration is seconds. Reps are integers. `rpe` is kept as sent. `custom_metric` is ignored and counted. The result is `{ ok: true, set, ignored }` or `{ ok: false, reason }` with a code from a fixed list (`missing_measure`, `forbidden_measure`, `out_of_range`). Pinned per Hevy type and per target modality: a null or zero value of a measure the modality forbids is ignored (not a drop); a non-zero one is `forbidden_measure`; a required measure that is `null` is `missing_measure` (for every set type: an incomplete set is dropped, not stored half-filled, D9); a value above `SET_*_MAX` after conversion is `out_of_range`. `isComplete` is always `true` on a kept set.
7. **Measure rules in translation.** With `calories_as_reps`, Hevy `reps` becomes SIN `calories` (a whole number, `0 … SET_CALORIES_MAX`) and a non-zero Hevy weight is `forbidden_measure`; with `assist_weight_ignored`, the Hevy weight of a `bodyweight_assisted_reps` set is ignored and counted, the reps kept. Without a rule an assisted exercise cannot be paired (AC4), so the translator never sees one.
8. **Export set translation** `sinSetToHevy(set, pair)`. For each Hevy type, only the fields the type holds are written (`weight_reps`: `weight_kg` + `reps`; `reps_only`: `reps`; `bodyweight_reps`: `weight_kg` + `reps`; `bodyweight_assisted_reps`: `reps`; `duration`: `duration_seconds`; `weight_duration`: `weight_kg` + `duration_seconds`; `distance_duration`: `distance_meters` + `duration_seconds`; `short_distance_weight`: `weight_kg` + `distance_meters`). `weight_kg` is the canonical `weightKg`; `distance_meters` is the canonical meters rounded to the nearest integer (a `km`, `mi` or `ft` distance too); `calories_as_reps` writes `calories` as `reps`. Set types map back one to one. A set that lacks a measure its modality requires is **not sent** and counted (`sets_not_sent`), never sent half-filled. `custom_metric` is never written.
9. **RPE.** `roundRpeForHevy(rpe)` returns `null` for `rpe < 6`, otherwise the nearest of `HEVY_RPE_STEPS`, a tie going to the higher step (7.25 → 7.5, 8.75 → 9, 6.5 → 7); a table-driven test pins 5.9 → `null`, 6 → 6, 6.4 → 6, 6.5 → 7, 7.2 → 7, 7.3 → 7.5, 9.7 → 9.5, 9.75 → 10, 10 → 10. Import keeps the value as sent.
10. **Section rules.** `SECTION_DEFAULT_RULES` is `Warm-up → warmup_placeholder`, `Accessory → notes_on_first`; any name matching no rule uses `workout_placeholder`. `sectionTreatment(name, rules)` matches **case-insensitively on trimmed names** and returns the user's rule over the default. On import, `sectionFromPlaceholder(role, notes)`: a `warmup_placeholder` exercise starts a section named `Warm-up` with the exercise's notes as the section note; a `workout_placeholder` starts a section named by the **first line** of its notes (trimmed; `Workout` if the notes are empty), the remaining lines (trimmed) as the section note (`null` if none); names are cut to the section-name limit (`SECTION_NAME_MAX`, 40) and notes to the section-note limit with a notice code (`section_name_cut`, `section_note_cut`). A section rule's `name` is likewise 1 to `SECTION_NAME_MAX` characters after trimming (a longer rule could never match a section name; the table has no length CHECK, so `name_key` is not capped at 80 in the database). Placeholders are never exercises.
11. **`buildHevyWorkout`.** For a finished `WorkoutDetail` and a mapping, it returns `{ ok: true, body, notices }` or `{ ok: false, unmapped }` (every workout exercise with no usable export pair, each once, with its name and modality; nothing else computed). The body (`HevyPostWorkoutSchema`): `title` is the workout title, else the routine name, else `Workout`; `description` the workout notes or `null`; `start_time` / `end_time` the exact instants as ISO UTC strings; **`is_private: true`**; exercises in position order, sets in `setNumber` order; `superset_id` maps each distinct SIN `supersetGroup` to `0, 1, 2…` in order of first appearance, and a group with one member becomes `null`; exercise notes copy. Sections follow the rules of AC10 exactly: `Warm-up` → a placeholder exercise (the pair with role `warmup_placeholder`, `sets: []`, `notes` = the section note or `null`) just before the section's exercises; `Accessory` → no placeholder, the section's note prepended to the first exercise's notes (`note`, blank line, `exercise notes`); any other name → a `workout_placeholder` whose notes are the section name, then a newline and the section note when there is one; **a missing placeholder pair makes the section's name and note go on the first exercise's notes instead** and adds the notice `section_no_placeholder`. Loose exercises (no section) get no placeholder. An empty section (no exercises) emits nothing. The pair for an exercise is the `exportAs` pair whose `exerciseId` equals the workout exercise's, else (through the injected `rootOf`) the `exportAs` pair of any exercise in the same lineage root. Notices are data, never prose: `{ code, count }` over a fixed code list (`rpe_dropped`, `rpe_rounded`, `distance_rounded`, `sets_not_sent`, `section_no_placeholder`, `title_fallback`), where `count` is the number of sets (or sections) affected, plus `names: string[]` on `section_no_placeholder` only (the affected sections' names, in order), so Spec 20.2 can phrase "2 sets weren't sent" and "Section 'Warm-up' had no marker" without 19.0 carrying any sentence. A name is data for the UI to render as text; it is never put in a log (AC37).
12. **`buildHevyWorkout` is pure and total:** the input is not mutated; the same input gives equal output; a workout with every set unsendable returns `ok: true` with exercises that have `sets: []` and the notice (it is the caller's decision to refuse), and a workout of zero exercises returns an empty `exercises` array.
13. **Fingerprint.** `hevyFingerprintSource(detail)` returns a canonical string (keys in a fixed order, no whitespace) over exactly the fields the export reads: workout `title`, `notes`, `startedAt`, `endedAt`, `routineName` (used only for the title fallback); each section's `name`, `notes` and position; each exercise's position, `exerciseId`, `notes`, `supersetGroup`, section index; each set's `setType`, `reps`, `weightKg`, `distanceM`, `durationS`, `calories`, `rpe`, in order. It is unchanged by `updatedAt` / `createdAt` / `localDate` / `tzOffsetMinutes`, set and exercise ids, planned sets, `isComplete`, `completedAt`, `routineIsOneOff`, `routineNotes`, and `addedInWorkout`; it changes when any one included field changes (a test mutates each field in turn). It starts with the version tag `v1`.
14. **Mapping CSV.** `formatMappingCsv(lines)` writes (from `MappingCsvLine[]`; `mappingToCsvLines(mapping, sinNameOf)` adapts a mapping and writes the **effective** section rules, `SECTION_DEFAULT_RULES` merged under the user's by name key; the SIN name needs a catalog lookup the mapping does not carry) a header row `kind,hevy_id,hevy_title,sin_id,sin_name,rule,export_as` and one line per pair (`kind` `exercise`, `skip` or `placeholder`, `placeholder` carrying `warmup` / `workout` in `rule`) and per section rule (`kind` `section`, `sin_name` the section name, `rule` the treatment), lines grouped by `kind` in the order `exercise`, `skip`, `placeholder`, `section`, within a group by `hevy_title` (code-unit order of the lowercased title) then `hevy_id`, section lines by name key, `export_as` `yes`/`no`, RFC 4180 quoting (comma, quote, CR, LF), `\r\n` line ends, UTF-8 without a byte-order mark. `parseMappingCsv(text)` accepts a leading BOM, `\n` or `\r\n`, and returns `{ lines, errors }`; for every canonically ordered line list `m`, `parse(format(m)).lines` equals `m` (a hand-written line may carry a title and no id, so `parse` returns the written cells; `MappingCsvLine` is `{ kind, hevyId, hevyTitle, sinId, sinName, rule, exportAs }`), and `format(parse(format(m)))` equals `format(m)`. Errors carry a 1-based line number and a code from a fixed list (`bad_header`, `unknown_kind`, `missing_column`, `bad_rule`, `bad_export_as`, `no_hevy_ref`, `no_sin_ref`, `too_many_lines`, `file_too_large`), never the cell's text. A file over 1 MiB or 5,000 lines is refused before parsing.
15. **Normalizers and tables.** `normalizeExportAs(pairs)` gives every exercise with at least one pair exactly one `exportAs: true` (the first in the given order if none or several are marked; a pair that is not `role: "exercise"` is never `exportAs`); it is idempotent. `HEVY_MUSCLE_TO_SIN` / `SIN_MUSCLE_TO_HEVY` and `HEVY_EQUIPMENT_TO_SIN` / `SIN_EQUIPMENT_TO_HEVY` are pinned (§6.8): an unmatched Hevy value maps to `null` ("Not set"); a SIN muscle without a counterpart exports as `other`. `hevyTypeForModality(modality)` (used to prefill creating a Hevy exercise) is `weight_reps→weight_reps, bodyweight_reps→reps_only, weighted_bodyweight→bodyweight_reps, duration→duration, distance_duration→distance_duration, weight_duration→weight_duration, weight_distance→short_distance_weight, calories→reps_only`.

### Phase B: gate, migration, mapping, links

16. **The allow-list.** `HEVY_ENABLED_USER_IDS` is optional, a comma-separated list of user ids; unset or empty means nobody; whitespace is trimmed; an entry that is not a UUID fails boot with a `ConfigError` naming the variable. The loaded config exposes a frozen `Set`. A test builds the app with the list containing user A only.
17. **The gate.** Every route in §5 answers `404` (the standard problem body of an unknown route, no hint the feature exists) to an authenticated user not on the list, and the same `404` before reading the body, for every method. A not-allowed user's oversized body, malformed JSON or 61st request in a minute is still that `404`, never `413`, `400`, `422` or `429`. A deleted account still gets `403 account-deleted` first (the existing `resolveUser` order). No Hevy route appears in `/openapi.json` (none is `published`), and the OpenAPI drift check is unchanged.
18. **Status.** `GET /v1/hevy/status` returns `200 { enabled: true, pairCount, linkCount, recordsStale }` for an allowed user (`recordsStale` is `false` until Spec 19.1 writes), `Cache-Control: no-store`; `404` for anyone else.
19. **Migration `0016`.** On a database populated by `0001`-`0015` with data, applying `0016` creates `hevy_exercise_pair`, `hevy_section_rule`, `hevy_link`, `hevy_account` exactly as §4, widens `workout_source_check` to `('manual','hevy')`, changes no existing row and no existing column, and contains no data statement. The constraints reject: an unknown role, rule, type, treatment or origin; a `role = 'exercise'` pair with no `exercise_id` and any other role with one; `export_as` on a non-exercise pair; a second `export_as` pair for one `(user, exercise)`; a duplicate `(user, hevy_template_id)`; a `hevy_link` that is neither linked nor claimed; a second link for one Hevy workout id; a second link for one SIN workout. All four tables cascade from `user`.
20. **Drift guards.** A unit test renders `WORKOUT_SOURCE_VALUES`, `HEVY_TYPE_VALUES`, `MEASURE_RULE_VALUES`, `PAIR_ROLE_VALUES`, `SECTION_TREATMENT_VALUES` and the link origins verbatim from `0016`'s SQL; `0005`'s guard keeps a frozen `('manual')` list (frozen in Phase A, in the same PR that widens `WORKOUT_SOURCE_VALUES`, so Phase A's unit tests stay green). The whole-schema `prisma migrate diff` no-drift check moves from `0015`'s test into `0016`'s and reports only the two generated `set_entry` columns.
21. **Mapping read.** `GET /v1/hevy/mapping` returns `{ pairs, sectionRules }`: pairs ordered by `lower(hevyTitle)` then `hevyTemplateId`, each `{ hevyTemplateId, hevyTitle, hevyType, role, exerciseId, exerciseActive, measureRule, exportAs }` (`exerciseId` and `exerciseActive` are `null` for a non-exercise role; `exerciseActive` is `false` for a soft-deleted exercise), rules ordered by lowercase name. Never another user's rows. `Cache-Control: private, no-cache` with a strong `ETag`, `If-None-Match` → `304`; an empty mapping is `{ pairs: [], sectionRules: [] }`.
22. **Mapping replace** (`PUT`). The body is the whole mapping; it replaces the caller's pairs and rules in one transaction and returns the new mapping (`200`, same shape). A second identical `PUT` is a no-op with the same response. `export_as` is normalized (AC15) before storing. A failure leaves the previous mapping untouched.
23. **Replace validation.** All of these are `422 validation-error` with static `errors[]` messages and a `path` like `pairs.3.exerciseId`, nothing written: a `role: "exercise"` pair whose exercise is not visible to the caller (another user's, absent, malformed) or is retired; a non-exercise role with an `exerciseId`; a pair failing `hevyPairingProblem` (path `pairs.i.measureRule`); a duplicate `hevyTemplateId`; two `exportAs: true` for one exercise (the request is refused here, unlike the file loader which normalizes); `exportAs: true` on a non-exercise role; more than one `warmup_placeholder` or one `workout_placeholder` pair; more than `HEVY_PAIRS_MAX` pairs or `HEVY_SECTION_RULES_MAX` rules; a duplicate section-rule name (case-insensitive); an unknown key (`strict`); a `hevyTitle` over 200 characters or with control characters. Request-body limit 512 KiB.
24. **Mapping patch** (`PATCH`). Body `{ upsert?: Pair[], remove?: string[] }` (template ids), both optional, at least one present. Upserts are keyed by `hevyTemplateId` and idempotent; the same validation as AC23 applies to the upserted pairs; a pair that gains the first pairing of an exercise becomes its `exportAs`; an upsert with `exportAs: true` clears the flag on the exercise's other pairs in the same statement; removing the `exportAs` pair of an exercise promotes that exercise's oldest remaining pair (by `created_at`, then template id); an unknown id in `remove` is ignored. The response is the new mapping. The result always satisfies "every exercise with pairs has exactly one `exportAs`".
25. **Pairs survive exercise changes.** Soft-deleting a paired exercise leaves its pairs (`exerciseActive: false` on read); renaming or retyping it changes nothing stored; a type change that makes a stored pair fail `hevyPairingProblem` leaves the row and surfaces `exerciseActive`/type on the next read for the client to flag (the server re-validates only on write). Hard deletion by the account purge cascades.
26. **Link read.** `GET /v1/workouts/{id}/hevy-link` returns `{ state, hevyWorkoutId, origin, syncedAt }`: `none` (no row, a live workout, or only a stale claim), `sending` (a claim younger than `HEVY_LINK_CLAIM_TTL_S` on a row with no Hevy id), `sent` (linked and `synced_fingerprint` equals the current fingerprint, or carries a different version tag), `changed` (linked and the fingerprints differ). `404` for another user's, an absent, a malformed or a deleted workout. `no-store`.
27. **Begin** (`POST`). On a finished workout with no link row it inserts a claim row (`origin: "sent"`, `claimed_at = now()`) and returns `200 { mode: "create", hevyWorkoutId: null, staleClaim: false, fingerprint }`. A second begin while the claim is younger than the TTL is `409 hevy-send-in-progress`, changing nothing; an older claim is taken over and answered with `staleClaim: true`. On a linked workout it sets `claimed_at` and returns `mode: "update"` with the stored `hevyWorkoutId`; a fresh claim there is also `409 hevy-send-in-progress`. An optional body `{ relink: true }` on a linked workout (the Hevy copy was deleted in Hevy, Spec 20.2 AC12) clears the stored Hevy id, takes the claim and answers `mode: "create"`; `relink` on an unlinked workout is a no-op. A live workout is `409 hevy-workout-not-finished`. `fingerprint` is the current version-tagged SHA-256 hex over `hevyFingerprintSource` of the workout read in the same statement snapshot.
28. **Complete** (`PUT`). Body `{ hevyWorkoutId, fingerprint }` (`hevyWorkoutId` 1-64 characters, no control characters; `fingerprint` the begin value, `v1:` plus 64 hex). Requires a claim (`409 hevy-no-claim` otherwise); records the id, `synced_fingerprint` = the body's fingerprint, `synced_at = now()`, clears the claim, and returns the link read. Replaying the same body is `200` with the same result. A different `hevyWorkoutId` for an already-linked workout is `409 hevy-link-conflict`; an id already linked to another SIN workout (or tombstone) is `409 hevy-id-in-use`. A fingerprint that is not well formed is `422`.
29. **Changed since sent.** After a completed send, editing a set's weight, reps, type or measures, adding or removing a set or an exercise, changing the title, notes, a section name or note, a superset, or Change Time (start or end) makes `GET` report `changed`; a planned-set edit, a routine edit, `updatedAt`-only churn and a no-op `PATCH` leave it `sent`. A completed update (`mode: "update"` then `PUT` with the new fingerprint) returns it to `sent`. A fingerprint recorded for a state older than a concurrent edit (the edit landed between begin and the Hevy request) reads `changed` afterwards: the safe direction.
30. **Release** (`DELETE`). Idempotent `204`. Deletes a row that is only a claim; clears the claim on a linked row; never unlinks a linked workout.
31. **Deleted workouts keep a tombstone.** Deleting a linked SIN workout leaves its `hevy_link` row with `workout_id = NULL`, so the Hevy id stays unique and Spec 19.1 reports "deleted in SIN" instead of importing it again; a claim-only row is removed with the workout (an explicit `DELETE` in `deleteWorkout`, because the FK is `SET NULL`). Deleting the account removes every row (purge test, AC35).
32. **Rate limits and assembly.** Every write route declares `config: { writeGroup: "hevy" }` (`RATE_LIMITS.groups.hevy = 60` per minute, D15); app assembly fails without it; a test that exceeds it gets `429 rate-limited` with `Retry-After`. Reads use the existing `/v1` read limits. `CORS_METHODS` already carries `GET, POST, PUT, PATCH, DELETE`; a test asserts every Hevy route's method is in it.
33. **Caching.** `no-store` on every Hevy response except the mapping `GET` (`private, no-cache` + `ETag`); the cache policy plugin is unchanged.
34. **The key never reaches the server.** No Hevy route's body or query schema has a key field (a body with `apiKey` / `api_key` is `422` by `strict`); the CORS `allowedHeaders` still omit `api-key` (a preflight asking for it is not allowed); a request carrying an `api-key` header logs no header value (`req.headers` redaction, asserted by a log-capture test).
35. **Account export and purge.** `GET /v1/account/export` carries `hevy: { pairs, sectionRules, links }` for every user (empty arrays for users with none), composed through shared mappers in `routes/mappers.ts` with the same shapes as the reads (`links` = `{ workoutId, hevyWorkoutId, origin, syncedAt }`, tombstones included with `workoutId: null`); `ACCOUNT_EXPORT_FORMAT_VERSION` stays `1` (an added field); the Spec 11 purge integration test, which discovers tables from `pg_constraint`, passes with the four new tables and leaves no row.
36. **Static messages and validation hygiene.** `static-issue-messages.test.ts` passes with the new schemas probed (every message fixed text, none echoing a title, id or value); a `422` for a bad pair names the path, never the Hevy title.
37. **Logs.** `hevy_mapping_replaced`, `hevy_mapping_patched` (counts of pairs, upserts, removals, section rules), `hevy_link_begun` (`mode`, `stale_claim`), `hevy_link_completed`, `hevy_link_released` at `info`, each with `user_id` and counts only; no Hevy title, no Hevy id, no exercise name. `telemetry/allowlist.ts` and `views.ts` are untouched.
38. **No collateral change.** Every existing test passes; `/openapi.json` differs from `main` only by the `Workout.source` enum (Phase A) and the account export's new `hevy` block (Phase B; `GET /v1/account/export` is published), with no Hevy route listed; `lint`, `typecheck`, `core:purity` and the app-assembly gates pass; a user not on the list sees no difference anywhere.
39. **Rollout order.** Phase A (with the widened enum) is deployed and reaches the web bundle before any release that can write `source = 'hevy'` (Spec 19.1 Phase B); asserted by §11, not by a test.

## 6. Behavior & logic

### 6.1 The gate

`requireHevyAccess` is an `onRequest` hook (not `preHandler`: that runs after body parsing and validation, and this repo's write-group limit runs in `preParsing`, so a `preHandler` gate would show a probe `413`/`400`/`422`/`429`) registered once on a child scope that holds every Hevy route (and a thin wrapper for the `workouts/{id}/hevy-link` routes, registered in the same scope with their full paths). After `resolveUser` it checks `config.hevyEnabledUserIds.has(request.user.id)` and otherwise throws the same `NotFoundError` an unknown route produces, before anything else runs (so a probe cannot tell a gated route from a missing one by its error). The allow-list is read from the frozen config, never from the database or the client (D1). `GET /v1/me` is untouched: the capability is `GET /v1/hevy/status`, whose `404` is the "off" signal (D2).

### 6.2 The type table and pairing (pure)

`hevyPairingProblem(hevyType, modality, rule)`:

1. `rule = calories_as_reps` → allowed iff `hevyType = reps_only` and `modality = calories`.
2. `rule = assist_weight_ignored` → allowed iff `hevyType = bodyweight_assisted_reps` and `modality = bodyweight_reps`.
3. no rule → `canon = canonicalModalityForHevyType(hevyType)`; `null` (assisted) → `type_mismatch` (it needs the rule); else allowed iff `modalitiesCompatible(canon, modality)`.
4. Anything else: `type_mismatch` (no rule) or `rule_not_allowed` (a rule on the wrong pair).

Hevy `reps_only` + SIN `calories` with no rule is `rule_required` (the calories exercise would read reps as reps and be rejected as a forbidden measure on every set), so the UI must propose `calories_as_reps` (AC5). This is the "calories read as reps" anti-goal: it can only be paired with the rule, and with the rule the numbers cross over by name.

### 6.3 Set translation

**Import (Hevy → SIN)**, in order, per set: map the set type; apply the rule (`calories_as_reps`: `reps` → `calories`; `assist_weight_ignored`: drop the weight, count it); for each measure the SIN modality forbids, null or `0` is ignored and anything else is `forbidden_measure`; convert weight (kg → user unit, nearest 0.1, half away from zero, computed on `Math.round(x * 10) / 10` of the converted value with a guard for floating error: values are compared after `toFixed(6)`); check bounds against `SET_*_MAX`; check every required measure is non-null (`missing_measure`). `rpe` passes as sent (Hevy sends only its steps, all valid SIN RPE values). The weight conversion uses the user's `unitPreference` (`kg` or `lb`) passed in `ctx`.

**Export (SIN → Hevy)** uses the stored canonical values (`weightKg`, `distanceM`), so a lb or ft set exports exactly what the records engine sees. Distance is `Math.round(distanceM)`; a distance of 0.4 m rounds to `0` (kept, notice `distance_rounded`). Calories export as Hevy `reps` only through the rule. A SIN exercise exported as a Hevy type that cannot hold one of its set's measures cannot occur: pairing already required compatible types.

### 6.4 Sections

Export is AC11 verbatim. Import placeholders (AC10) are consumed by Spec 19.1's workout translator, which walks the Hevy exercises in order: a placeholder starts a section; exercises up to the next placeholder belong to it; exercises before the first placeholder are loose; **an Accessory section has no marker in Hevy, so its exercises stay in the preceding section** *(Carol, via the design)*. The 8-section cap (`ROUTINE_SECTIONS_MAX`) is 19.1's.

### 6.5 The fingerprint

`hevyFingerprintSource(detail)` is built from the same `WorkoutDetail` the read route returns (`toWorkoutDetailDto`), in a fixed key order, with numbers printed by `JSON.stringify` (the DTO's numbers are already normalized: `weightKg`, `distanceM` come from `numeric` columns). The API hashes it: `"v1:" + sha256(source)` in hex (`node:crypto`, API only; `@sin/core` stays pure). Why server-side: it is the authority on "what is stored" and the client cannot make a stale copy look current (D6). Why it excludes `isComplete`: the export sends a set iff its required measures are present, and the fingerprint includes the measures themselves, so completeness is already in it.

### 6.6 Link lifecycle

```
none ──begin──▶ claim(create) ──Hevy POST ok──▶ complete ──▶ sent ──edit──▶ changed
  ▲                │ Hevy 4xx / user stop                         │ begin(update) ──Hevy PUT ok──▶ complete ──▶ sent
  └──release───────┘ (network lost: claim stays; next begin sees staleClaim after the TTL, the client verifies in Hevy)
```

- **Begin** is one transaction: `SELECT … FOR UPDATE` of the workout row (finished or `409`), read the link row, insert or take over the claim, read the workout detail for the fingerprint in the same transaction, through a client-parameterized `readWorkoutDetail(tx, …)` extracted from `workout.prisma.ts`. No `lockUserRecords`: a link is not a record write, and no lock order with the PR lock is introduced (D16).
- **Complete** is one `UPDATE … WHERE claimed_at IS NOT NULL` (an in-transaction pre-check for another row holding `(user_id, hevy_workout_id)` gives `hevy-id-in-use`; a racing `23505` is mapped by its **column list**, `user_id, hevy_workout_id`, because `pg-errors.ts` exposes no constraint name for `$queryRaw` errors).
- **The double-copy guards,** in order of strength: the web disables the button while its own request runs; begin refuses a second claim for `HEVY_LINK_CLAIM_TTL_S`; a taken-over stale claim tells the client to look in Hevy first (Spec 20.2 §6.3); `hevy_link_hevy_id_key` makes it impossible to record one Hevy workout for two SIN workouts. Nothing here can make Hevy itself idempotent (it has no idempotency key); what is left is a Hevy copy created while the response was lost and never found, which 20.2 surfaces instead of hiding.
- **Imported and matched links** (Spec 19.1) are inserted with `synced_fingerprint` = the fingerprint at that moment, so they read `sent`/"in Hevy" until the first edit (D8).

### 6.7 Mapping writes

`PUT`: `DELETE` the caller's pairs and rules, `INSERT` the new rows, all in one transaction under `SELECT … FROM "user" WHERE id = $1 FOR UPDATE` (serializes two writers; no new advisory key, D16). The visibility check is the exercise predicate of 03.2 (`owner_user_id IS NULL OR owner_user_id = $user`, `is_active`). `PATCH` upserts with `INSERT … ON CONFLICT (user_id, hevy_template_id) DO UPDATE`, in the same lock. The `export_as` normalization runs in SQL-free TypeScript over the rows after the write inside the transaction (`normalizeExportAs`), then updates the flags that changed.

## 7. Security & privacy

- **Authorization boundary.** The allow-list (D1) gates every route; all data access filters by `request.user.id` in SQL. An exercise id in a pair is checked with the 03.2 visibility predicate, so one user cannot pair, and so read the name of, another user's custom exercise; a workout id in a link route is resolved by `workout.user_id`. A cross-user id is `404`, indistinguishable from absent.
- **The Hevy key** is never an input here (AC34). It also must not appear in a Hevy title or note stored by this spec: the stored text is Hevy exercise titles and ids only.
- **Hevy titles and ids are user data,** stored per account, exported with the account (AC35), erased by the purge. They are not secrets and are not logged (AC37).
- **The mapping CSV** is parsed on the client (20.0); the server sees structured JSON only, so there is no CSV parser on the server to attack. The `PUT` body is bounded (512 KiB, 2,000 pairs).
- **Abuse.** Owner-only plus the `hevy` write group and the global in-flight cap bound a script; `PUT` replace is `O(pairs)` under a per-user row lock.
- **No new third-party calls from SIN's server.** Hevy is called by the browser only.
- **Static messages (#57).** Validation texts are fixed; the repository's `23505` handling maps column lists, never values.

## 11. Deployment & rollback

- **Order.** (1) **Phase A** merges and deploys with the web: the widened `source` enum reaches the bundle first. (2) **Phase B:** apply migration `0016` to Neon **before** the code goes live (`DATABASE_URL='<direct url>' pnpm run db:migrate:deploy`, runbook B4 style; `prisma migrate status` first), then the code. Set `HEVY_ENABLED_USER_IDS` per environment (Render dashboard on staging; `terraform apply` by hand on production, Part F). Until set, the feature is invisible. (3) Spec 19.1 Phase B is the first thing that writes `source = 'hevy'`, and must not merge before (1) is on staging and production.

## 12. Decisions & open questions

- **D1 ✅ The gate is an env allow-list of user ids, checked per request (mine).** Rationale: the feature is for one account, on two environments with different user ids; an env variable needs no schema change, no operator CLI, and is the smallest thing that can later become "everyone" (`*` or removing the check is a one-line change in one hook). Rejected: a `user.hevy_enabled` column (a migration to `user`, a manual SQL or CLI step per environment, and a flag that is easy to leave on for the wrong row); an email allow-list (email is not unique and can change); an Auth0 role claim (puts product gating in the identity provider). Cost: a change is a redeploy on Cloud Run (a Terraform `apply` by hand); acceptable for a value that changes once.
- **D2 ✅ The capability probe is `GET /v1/hevy/status` (404 = hidden); `/v1/me` is untouched (mine).** Rationale: adding `hevyEnabled` to `Me` would be a response-field change to a settled, exported DTO for one account, with the DESIGN §6 rollout cost and a field every user's export carries; a gated route that 404s for everyone else costs nothing outside the feature.
- **D3 ✅ Unpublished routes (Carol, design: "no public OpenAPI publication").** Rationale: publication is opt-in already; the routes list `problems` so the assembly gate still checks them.
- **D4 ✅ The mapping is a structured JSON resource, the CSV is parsed and written on the client (mine).** Rationale: resolving a CSV line needs two things only the browser has (Hevy's template list, fetched with the key that never leaves the device, and the synced SIN catalog); the server then sees only ids, which it can validate against rows. A server-side parser would force the Hevy title → id step to happen without Hevy. The pure parser and formatter live in `@sin/core`, so both are unit-tested and shared. Rejected: uploading the file to the API (needs the key or a stale template copy; adds a parser to attack and a multipart route).
- **D5 ✅ `PUT` replaces the whole mapping, `PATCH` upserts pairs (mine).** Rationale: loading the file means "the file is the mapping" (the download is the backup, so file and database never drift, per the design); on-screen pairing during an import adds a few pairs at a time and must not erase the rest. Two verbs, no ordering hazard, each idempotent.
- **D6 ✅ The fingerprint is computed by the server from stored data; the client echoes it (mine).** Rationale: "changed since sent" must not be fakeable by a stale tab, and only the server reads the stored workout atomically with the claim. The echo costs nothing: a lying client can only mislabel its own button. Rejected: a client-computed hash (needs the full detail plus the exact algorithm in two places); `updated_at` (set edits do not reliably bump the workout row, and retimes rewrite no set's `updated_at`, 07.4).
- **D7 ✅ The fingerprint covers what the export reads and nothing else (mine).** Rationale: "changed" should mean "Hevy would now receive different data"; a routine edit, planned sets or an `updated_at` touch must not nag. Cost: a change to the exported field set (a later spec) changes every fingerprint; the `v1` tag means an older-version fingerprint reads `sent`, not `changed`, so no false alarm after such a change.
- **D8 ✅ Imported and matched links start in sync (mine).** Rationale: the Hevy copy of an imported workout *is* the original; flagging every imported workout "changed" would be noise. The first SIN edit flips it, and the design accepts overwriting the Hevy original on Update.
- **D9 ✅ An incomplete set is not translated or sent, whatever its type (mine).** Rationale: SIN stores a finished working set only complete; Hevy has no half-filled set and the design's "a bad set is dropped" rule covers it. Half-filled warm-ups from Hevy would be rows the lifter cannot interpret. The drop is counted and listed (19.1), never silent.
- **D10 ✅ Pairing validity is derived from `modalitiesCompatible` plus two named rules (mine).** Rationale: one source of truth (the measure table), consistent with Spec 03.4 D4; the two rules are exactly the design's two exceptions (Carol's calories convention; assisted weight has no SIN counterpart). New rules are new enum values plus a row in the table, not a free-form field.
- **D11 ✅ Placeholders are pairs with a `role`, section rules are a separate table (mine).** Rationale: a placeholder is a Hevy exercise (a template id the client can resolve and the import must recognize), so it belongs with the exercise pairs and the unique-per-role index; a section rule is a SIN-side name → treatment table. Defaults are code, not rows, so a new user needs no setup and Carol's convention is the default *(Carol)*.
- **D12 ✅ A missing placeholder degrades to notes on the first exercise (mine).** Rationale: an export must not fail or silently drop a section's text because the placeholder pair is not configured yet; the text lands where Hevy can hold it and a notice says so.
- **D13 ✅ `hevy_link` is one table for sent, imported and matched copies, with claim columns, and keeps a tombstone (mine).** Rationale: the design asks for one "does this workout have a Hevy copy" answer across the three origins; the claim is the only server-side serialization available for a call to a service with no idempotency key; a tombstone stops a resumed import from resurrecting a workout Carol deleted in SIN. Rejected: a column on `workout` (cannot hold a tombstone or a claim without widening a hot table); a separate claims table (two reads for one answer).
- **D14 ✅ One migration for the whole family, including `hevy_account` (mine).** Rationale: `0016` is expand-only and has no consumer until 19.1; one release step instead of two, and the status route is final here.
- **D15 ✅ A sixth write group, `hevy`, 60 per minute (mine).** Rationale: the bulk import (19.1) sends up to ~80 requests over minutes, and mapping and link writes are interactive; `workouts` (60) is the right order of magnitude and must not be shared with real logging, whose budget an import would starve. Per-IP and the in-flight cap still apply.
- **D16 ✅ No new advisory lock; the user row lock serializes mapping writes, the workout row lock serializes begin (mine).** Rationale: CLAUDE.md forbids reusing a key and the PR lock order is delicate; these writes touch no record, so they sit outside it. `SELECT … FOR UPDATE` on `user` and on the workout row are ordinary row locks, taken in one fixed order (user then workout) and never together with `lockUserRecords`.
- **D17 ✅ Logs only, no metric (mine).** Rationale: the feature has one user; a metric would need an allow-listed attribute (13.0) for no reader.
- **D18 ✅ The widened `source` enum ships a release before its first writer (mine).** Rationale: DESIGN §6's response-field rollout convention: an old bundle that has `z.enum(["manual"])` would reject a History response containing a `'hevy'` workout. Phase A carries it; 19.1 Phase B writes it.
- **D19 ✅ Hevy exercise types: the table is the design's, the assisted case needs a rule (Carol/mine).** The design says to check the table against real Hevy data before relying on it. The builder's first step is a read-only pass over Carol's templates (`GET /v1/exercise_templates`, her key, run locally, nothing stored) comparing each template's `type` with the table; any surprise is recorded here and in the PR before Phase A merges.
- **D20 ✅ A deleted Hevy copy is re-pointed with `relink`, never by editing the link directly (mine).** Rationale: Hevy's API has no delete, but Carol can delete a copy in the Hevy app; an update would then `404`. `relink` is the one explicit way to forget the old id (making it available again, which is harmless: it no longer exists in Hevy), and it keeps `complete` strict (a different id on a linked workout stays a `409`).

- **D21 ✅ The gate is an `onRequest` hook, not a `preHandler` (mine, from the build plan).** Rationale: Fastify runs `preHandler` after parsing and validation, and the write-group limit runs in `preParsing`; only `onRequest` makes AC17 true for oversized, malformed and rate-limited requests.
- **D22 ✅ A unique violation is identified by column list, with an in-transaction pre-check (mine).** Rationale: `$queryRaw` errors carry only the DETAIL line, as the workout and routine repositories already assume.
- **D23 ✅ `deleteWorkout` deletes claim-only `hevy_link` rows explicitly (mine).** Rationale: the FK is `SET NULL`, which would leave an orphan "sending" row; a linked row still becomes a tombstone. Lock order is unchanged (PR lock, workout row, link rows).
- **D24 ✅ CSV order is grouped by kind, and formatting takes lines (mine).** Rationale: reconciles AC14 ("by title") with Spec 20.0 §6.5 (pairs, skips, placeholders, sections); the SIN name needs the catalog, so `mappingToCsvLines` adapts a mapping and the formatter stays pure over lines.
- **D25 ✅ Section-rule names are at most 40 characters (mine).** Rationale: `SECTION_NAME_MAX` is 40; a longer rule never matches.
- **D26 ✅ Read schemas are tolerant where the client decides (mine).** Rationale: a set `type` read as a plain string and the routine, folder and optional-index fields keep Carol's real data parsing; Spec 20.1 marks an odd workout unreadable rather than failing a page. The user-info wrapper, the count schema and the create-template schemas live here so the web defines no substitute.
- **D28 ✅ Export notices carry counts, and section names as data (mine, from Spec 20.2's plan).** Rationale: 20.2's sentences need a count and a section name; "codes only" could not supply them, and the alternative (count-free sentences) throws away information the lifter wants.
- **D27 ✅ AC38's OpenAPI claim is the export block (mine).** Rationale: the export is published and §5.6 adds a required field, so the document changes there; no Hevy route appears.

### Owner questions (resolved 2026-10-26)

- **O1. Hevy workouts created through the API and `is_private`.** The design sets `is_private: true` *(mine)*. The Hevy read schema has no `is_private` field, so we cannot verify the flag took effect after the send.
