# Spec 01.1 — Production deploy pipeline (staging → prod promotion)

**Status:** Draft v0.1
**Last updated:** 2026-09-01
**Kind:** platform / CI-CD
**Depends on:** Spec 01 (Foundation & Auth — the deployable API, `render.yaml`, `scripts/smoke.ts`, the staging `smoke` CI job)
**Design refs:** DESIGN.md §7 (CD v1 row), Spec 01 §11

> Sub-spec of Spec 01. Spec 01 stood up the API and an **auto-deploy to staging on
> merge to `main`**. This spec adds the other half of the DESIGN §7 sentence —
> *"git tag → promote the same API image to `production`"* — as an automated,
> **manually-gated** GitHub Actions pipeline, so a prod release is one reviewed
> click rather than dashboard clicking through the Part E runbook.

---

## 1. Purpose, scope & non-goals

### Purpose

Make production deploys of `apps/api`:

- **automated** — no manual Render dashboard steps in the happy path;
- **gated** — a human explicitly approves each prod release before it happens;
- **identical to what passed staging** — the byte-for-byte image that the staging
  smoke went green against is what production runs, not a fresh rebuild;
- **verified** — the same `scripts/smoke.ts` runs against production after the
  rollout and fails the run (and pages the operator) if prod is not healthy.

### In scope

- A container image published to a registry on every merge to `main`, tagged with
  the commit SHA (immutable), so a specific build can be promoted later.
- Staging deploy consumes that published image (replaces Render's build-from-
  Dockerfile for the `si-api` staging service).
- A `deploy-prod` GitHub Actions workflow: trigger, approval gate (GitHub
  Environment protection rule), promote-image step (Render API), prod pre-deploy
  `prisma migrate deploy`, prod smoke.
- `render.yaml` changes: a `si-api-prod` service (image-sourced, `autoDeploy:
  false`) + `si-postgres-prod`, and the staging service switched to image source.
- The prod half of the CI secret/var set (`PROD_*`, `AUTH0_PROD_*`,
  `RENDER_*`).
- Rollback procedure: redeploy a previous SHA through the same gated workflow.
- Concurrency control so two prod deploys cannot overlap.

### Non-goals

- **Auth0 config as code** (Deploy CLI / Terraform for tenants, Actions, M2M
  apps) — still hand-synced; Spec 15.
- **Blue/green, canary, or progressive rollout** — Render does a rolling replace
  gated on `/healthz`; that is the v1 strategy.
- **Automated DB rollback / down-migrations** — forward-fix only, per Spec 01 §11.
- **Multi-region, autoscaling, IaC for the platform itself** — Spec 15 (AWS).
- **Web / SPA deploy** — Spec 04 owns the static-site pipeline; this spec is
  API-only. (04 may copy this shape.)
- **Preview environments per PR** — out of scope for v1.
- Changing the staging behaviour from Spec 01 other than its image source.

## 2. Acceptance criteria

1. A merge to `main` builds one container image and pushes it to the registry
   tagged `sha-<short>` (immutable) and `main` (moving); the digest is recorded
   in the run summary.
2. The staging Render service deploys **that pushed image** (by digest), not a
   Render-side rebuild; the existing staging `smoke` job still passes against it.
3. `deploy-prod` cannot run without a successful staging `smoke` for the same SHA
   (either chained from the `main` run or validated at dispatch).
4. `deploy-prod` pauses on the GitHub Environment `production` and does not
   proceed until a designated reviewer approves it in the GitHub UI.
5. On approval, the prod Render service is deployed to the **same image digest**
   that ran on staging for that SHA — verified by comparing the digest reported
   by the Render API against the one from criterion 1.
6. `prisma migrate deploy` runs as the prod service's pre-deploy step; migrations
   already applied on staging apply cleanly to the prod DB.
7. After the prod rollout reports live, `scripts/smoke.ts` runs against
   `PROD_BASE_URL` with `AUTH0_PROD_*` and passes all five checks; a failure
   fails the workflow run.
8. A failed prod smoke (or a failed rollout) leaves the previous prod deploy
   serving traffic (Render gates the swap on `/healthz`) and surfaces as a red
   GitHub run + a notification to the operator.
9. Re-running `deploy-prod` with an earlier `sha-<short>` input redeploys that
   prior image to prod through the same gate — this is the documented rollback.
10. Two `deploy-prod` runs cannot execute concurrently; the second queues or is
    cancelled, never interleaved.
11. `render.yaml` remains the source of truth: staging and prod services, both
    DBs, and both env groups are declared there; no service config exists only in
    the dashboard except secret **values**.
12. No secret (`RENDER_API_KEY`, M2M client secrets, DB URLs) appears in the repo,
    in `render.yaml`, or in workflow logs.

## 4. Data model

No tables. Migration behaviour only:

- The prod service runs `prisma migrate deploy` as its Render **pre-deploy**
  command, identical to staging (Spec 01 §6.4, §11). Because every prod release is
  a promotion of an image that already deployed to staging, the migration set is
  always one that has already applied to the staging DB.
- **Ordering rule (inherited, restated):** a column drop/rename never ships in
  the same release as the code change that stops using it — expand on release N,
  contract on release N+1, so any image on either side of a prod swap is
  schema-compatible and Render's rolling replace is safe.
- No backfill machinery here; a spec that needs a data backfill defines it as an
  idempotent step in its own spec.

## 5. API surface

No application endpoints. External control-plane calls the pipeline makes:

### Render API (from `deploy-prod`, `RENDER_API_KEY` bearer)

| Call | Purpose | Assert |
|---|---|---|
| `POST /v1/services/{prodServiceId}/deploys` with `{ imageUrl: "ghcr.io/<owner>/si-api@<digest>" }` | Promote the exact staging digest to prod | `201`, capture `deploy.id` |
| `GET /v1/services/{prodServiceId}/deploys/{deployId}` (poll) | Wait for rollout | terminal state `live`; any of `build_failed` / `update_failed` / `canceled` fails the run |
| `GET /v1/services/{prodServiceId}` | Confirm promoted digest | `imageUrl` digest == the one built for this SHA (criterion 5) |

Poll: every 15 s, cap ~20 min, then fail (Render's own `/healthz` gate means a
stuck rollout will not swap traffic).

### Auth0 (prod smoke, unchanged script)

`scripts/smoke.ts` already parameterised on env — `POST {AUTH0_TOKEN_URL}` client-
credentials grant, then `GET {SMOKE_BASE_URL}/{healthz,readyz,v1/_authcheck,v1/me}`.
Prod run supplies `PROD_*` values; no code change.

## 6. Behavior & logic

### 6.1 Build-and-publish (extends `ci.yml`, on push to `main`)

New job `publish` — `needs: [check, integration, docker]`, `if: github.ref ==
'refs/heads/main'`:

1. `docker/login-action` to `ghcr.io` with `GITHUB_TOKEN` (`packages: write`).
2. `docker/build-push-action` — build the existing `Dockerfile`, push tags
   `ghcr.io/<owner>/si-api:sha-${{ github.sha (short) }}` and `:main`.
3. Emit `digest=${{ steps.build.outputs.digest }}` as a job output and into the
   run summary.

The `docker` job (criterion 14 build check on every PR) stays — `publish` is the
`main`-only superset that also pushes.

### 6.2 Staging deploy (Render, unchanged trigger, new source)

`si-api` staging becomes `runtime: image` with `image.url:
ghcr.io/<owner>/si-api:main` and `autoDeploy: true`. Render redeploys staging
when the `:main` tag moves. Pre-deploy `prisma migrate deploy` and the
`/healthz` gate are unchanged. The existing `smoke` job in `ci.yml` runs after,
exactly as today (Spec 01 criterion 12).

> Trade-off: Render polls the registry for `:main` rather than getting a push
> webhook, so staging deploy can lag a merge by Render's poll interval. Chaining
> is tightened in §6.3 for prod; for staging the poll is acceptable (solo repo).
> Alternative considered: call the Render deploy API from `publish` with the
> digest, same as prod. Kept simple for now — see §12 Q3.

### 6.3 Prod promotion (`.github/workflows/deploy-prod.yml`)

```
name: deploy-prod
on:
  workflow_dispatch:
    inputs:
      sha:
        description: "Short SHA to promote (defaults to latest main build)"
        required: false
concurrency:
  group: deploy-prod
  cancel-in-progress: false
permissions:
  contents: read
  packages: read
jobs:
  gate:
    # resolve target SHA -> digest; verify a green staging smoke exists for it
  deploy:
    needs: gate
    environment: production        # <-- pauses here for a required reviewer
    steps:
      - promote digest to si-api-prod via Render API
      - poll deploy to `live`
      - verify promoted digest == target digest
      - run scripts/smoke.ts with PROD_* env
```

- **Gate job.** Resolve the target: dispatch input `sha`, else the head of
  `main`. Map to an image digest via `docker buildx imagetools inspect
  ghcr.io/<owner>/si-api:sha-<sha>` (fails if that image was never built).
  Confirm the staging `smoke` for that SHA succeeded — query the GitHub API for
  the `CI` run on that SHA and check the `smoke` job conclusion (criterion 3).
- **Approval.** `environment: production` with a required reviewer makes the
  `deploy` job wait in the GitHub UI until the maintainer approves or rejects.
  Rejection ends the run; nothing prod-side has happened yet.
- **Promote.** `POST …/deploys { imageUrl: …@<digest> }`; poll to `live`; then
  `GET …/services/{id}` and assert the live `imageUrl` digest matches
  (criterion 5). The prod service's own pre-deploy `prisma migrate deploy` runs
  as part of Render's rollout.
- **Verify.** `scripts/smoke.ts` with `SMOKE_BASE_URL=$PROD_BASE_URL`,
  `AUTH0_TOKEN_URL=$AUTH0_PROD_TOKEN_URL`, `AUTH0_M2M_CLIENT_ID/SECRET=$AUTH0_PROD_M2M_*`,
  `AUTH0_M2M_AUDIENCE=https://api.strengthinnumbers.app`. Non-zero exit → red run
  → §6.4.

### 6.4 Failure handling

| Failure | State | Operator action |
|---|---|---|
| `publish` build/push fails | Nothing deployed | Fix build; re-merge or re-run. |
| Staging deploy or `smoke` red | Prod gate (criterion 3) refuses this SHA | Fix forward; new SHA. |
| Reviewer rejects | No prod change | — |
| Render prod rollout non-`live` | Old prod deploy still serving (`/healthz` gate never swapped) | Read Render deploy log; fix forward; re-dispatch. |
| Prod smoke red after `live` | New image **is** live and failing | **Rollback:** re-dispatch `deploy-prod` with the last known-good `sha-<short>` (criterion 9). If migration-caused, forward-fix migration first. |

Render "roll back to previous deploy" in the dashboard remains the
break-glass path if Actions is unavailable.

### 6.5 Sequence (happy path)

```
merge PR → main
  └─ CI: check, integration, docker
        └─ publish: build image, push ghcr sha-<x> + :main, output digest
challenge
  Render (staging): pull :main → pre-deploy migrate deploy → /healthz gate → live
  └─ CI smoke (staging, SHA x): healthz/readyz/authcheck/me  ✔

[later, when ready to release]
maintainer: Actions → deploy-prod → Run (sha defaults to x)
  └─ gate: resolve x→digest, confirm staging smoke x was green
  └─ deploy: ⏸ waits for approval
        maintainer approves
        └─ Render API: deploy si-api-prod @digest
              pre-deploy migrate deploy → /healthz gate → live
        └─ assert live digest == digest
        └─ smoke (prod): healthz/readyz/authcheck/me  ✔
  run green → prod is on x
```

## 7. Security & privacy

- **`RENDER_API_KEY`** is account-scoped and powerful (can deploy/modify any
  service). Store only in the GitHub `production` Environment secret set, so it is
  not readable by workflows triggered from forks or by the `pull_request` events
  in `ci.yml`. Rotate on staff change; it is the highest-value secret here.
- **`GITHUB_TOKEN`** for GHCR push is the ephemeral per-run token with
  `packages: write` added only on the `publish` job. No PAT.
- **M2M client secrets** (`AUTH0_PROD_M2M_CLIENT_SECRET`) — Environment secrets,
  same handling as the staging ones today (Spec 01 §8). The prod M2M app gets no
  API scopes (smoke needs none).
- **Approval gate is the authorization boundary for prod.** Only users on the
  `production` Environment reviewer list can release. Enforce branch protection on
  `main` so the image being promoted always came from reviewed code.
- **Log hygiene** — never `echo` the digest-inspect with credentials; pass the
  Render key via `env:` not as a CLI arg; `set -x` off in the deploy script.
- **Registry visibility** — the GHCR package can stay private (default). The
  image contains only built `dist/` + prod deps, no secrets (Spec 01 §11 Build),
  but private is the safe default.
- No PII flows through this pipeline; the prod smoke uses an M2M token with no
  user identity.

## 9. Observability

- **Pipeline visibility** — each `deploy-prod` run's summary records: target SHA,
  image digest, Render deploy id, approval actor + timestamp, prod smoke result.
  This is the release log for v1 (no separate deploy tracker until Spec 13).
- **Notification** — on `deploy-prod` failure (any job), notify the operator.
  v1: GitHub's own "workflow run failed" email / mobile push. A Slack/webhook
  step is a §12 open question, not required for done.
- **Render** emits build + deploy logs and its own deploy notifications per
  service — leave those on for `si-api-prod`.
- **App-level** prod observability (traces, Sentry, dashboards, alerts on the
  §1.3 metrics) is **Spec 13**, explicitly not here. This spec only asserts the
  smoke's four HTTP checks post-release.
- The API's structured request logs (Spec 01 §9) are unchanged; prod logs go
  wherever Render ships them until Spec 13 wires an exporter.

## 10. Testing

Infra spec — criteria are verified by pipeline execution, not unit tests.

| Criterion | How verified |
|---|---|
| 1 build+push, digest recorded | Inspect the `publish` job on the first post-merge run; `ghcr` shows `sha-<x>` + `main`; digest in summary. |
| 2 staging runs the pushed image | `GET` Render staging service `imageUrl` digest == `publish` output; existing `smoke` job green. |
| 3 gate needs green staging smoke | Dispatch `deploy-prod` for a SHA whose staging smoke failed → `gate` job fails before any approval prompt. |
| 4 approval pause | Dispatch → `deploy` job shows "Waiting for review" in the Actions UI; no Render call in logs until approve. |
| 5 same digest to prod | `deploy` job's post-deploy assertion step; compare logged digests. |
| 6 prod migrate deploy | First prod release: Render pre-deploy log shows `0001_create_user` (and any later) `applied` / `already applied`. |
| 7 prod smoke passes | `deploy-prod` run green; smoke stdout shows all five `ok` lines against `PROD_BASE_URL`. |
| 8 failed smoke ⇒ old deploy stays | Force a prod smoke failure (e.g. wrong `AUTH0_PROD_AUDIENCE` once) → run red, `GET /healthz` on prod still 200 from the prior image, notification received. |
| 9 rollback = re-dispatch old SHA | Dispatch `deploy-prod` with the previous `sha-<short>`; prod `imageUrl` reverts; smoke green. |
| 10 no concurrent prod deploys | Dispatch twice quickly → second run blocked by `concurrency: deploy-prod`. |
| 11 render.yaml is source of truth | `render.yaml` diff shows both services, both DBs, both env groups; a `render blueprint` re-sync reports no drift. |
| 12 no secret leakage | `gitleaks` / manual scan of `render.yaml` + workflows; inspect a run log for masked values. |

One-time **first prod release** doubles as the end-to-end test of criteria
4–8 and is captured as a checklist in §11.

## 11. Deployment & rollback

### Shipping this spec

1. **GHCR + staging cutover** (no prod yet):
   - Add the `publish` job to `ci.yml`; add `packages: write` to its job
     permissions.
   - Switch `render.yaml` staging `si-api` to `image.url:
     ghcr.io/<owner>/si-api:main`; `render` blueprint re-sync.
   - Merge. Confirm: image in GHCR, staging redeploys from it, staging `smoke`
     still green. (Criteria 1–2.)
2. **Prod infra** (runbook `docs/runbooks/first-deploy.md` Part E, amended):
   - `si-prod` Auth0 tenant per Spec 01 §11 (API, M2M, Action on Login flow).
   - `render.yaml`: add `si-api-prod` (image, `autoDeploy: false`),
     `si-postgres-prod`, `api-shared-prod`; re-sync; set secret values +
     `WEB_ORIGIN` on the prod service.
   - Render Account → API key.
3. **GitHub wiring:**
   - Create Environment `production`; add the maintainer as a required reviewer.
   - Add the §8 secrets/vars to that Environment.
   - Add `.github/workflows/deploy-prod.yml`.
4. **First prod release (the e2e test):**
   - Merge something trivial to `main`; let staging go green.
   - Actions → `deploy-prod` → Run (default SHA).
   - Watch `gate` pass → approve at the prompt → watch promote + prod smoke.
   - Prod `curl /healthz`, `/readyz` → 200; `/v1/me` unauth → 401.
5. Update `docs/runbooks/first-deploy.md` Part E to point at this workflow
   instead of manual Render promotion, and the DESIGN §7 CD row / Spec 01 §11 to
   reference this spec.

### Rollback

- **Of a bad prod release:** re-dispatch `deploy-prod` with the previous
  `sha-<short>` (criterion 9). Same gate, ~2–3 min. Break-glass: Render dashboard
  "roll back to previous deploy".
- **Of this pipeline itself:** revert the `render.yaml` staging block to
  `dockerfilePath` and drop the `publish` / `deploy-prod` workflows; Spec 01's
  staging auto-deploy is unaffected. Prod, if already created, can still be
  deployed by hand via the old Part E steps.
- **DB:** unchanged from Spec 01 — forward-fix migration, never `migrate down` in
  prod.

## 12. Decisions & open questions

- **Q1 — Promote a prebuilt image vs. rebuild for prod.** ✅ **Build once on
  `main`, promote the digest.** "Same artifact that passed staging" is the whole
  point of a staging gate; a prod rebuild can diverge (base-image drift, cache).
  Cost: `render.yaml` services move from `dockerfilePath` to `image.url` and we
  depend on GHCR. Worth it, and it is the shape Spec 15's ECS rollout needs
  anyway.
- **Q2 — Where the approval gate lives.** ✅ **GitHub Environment protection rule
  on a `deploy-prod` job.** Native, auditable (who approved, when), no extra
  service. Alternative — a manual Render "promote" click — has no link to the
  passing SHA and no record. Alternative — a `production` branch with its own
  protection — adds a second long-lived branch for no gain.
- **Q3 — Staging deploy trigger: Render registry poll vs. API call from CI.**
  ✅ **Registry poll on `:main` for staging; explicit digest API call for prod.**
  Staging can tolerate a poll-interval lag; prod must deploy an exact digest and
  wait for `live` before smoking. Revisit if staging lag becomes annoying — the
  `publish` job already has the digest to make the call.
- **Q4 — Trigger for `deploy-prod`: git tag push vs. `workflow_dispatch`.**
  ✅ **`workflow_dispatch` with an optional `sha` input.** A solo maintainer
  releasing from the Actions tab is simpler than tag hygiene, and the SHA input
  covers rollback cleanly. A `v*` tag trigger can be added later as an
  alternative entry point (it would still hit the same gated `deploy` job).
- **Q5 — One Render account/project for both envs?** ✅ **Yes for v1** — separate
  services + separate databases in one Render account, distinguished by name and
  the `api-shared` / `api-shared-prod` groups. Separate accounts is a Spec 15
  concern.
- **Q6 — GHCR vs. Render's own registry / Docker Hub.** ✅ **GHCR** — no new
  account, `GITHUB_TOKEN` pushes it, private by default, and it is where a
  future GitHub-Actions-driven ECS push (DESIGN §7 phase 2) would read from too.
- **Open — failure notifications.** GitHub's built-in failed-run notification is
  the v1 mechanism. A dedicated Slack/Discord/webhook step on `deploy-prod`
  failure (and success) is desirable but deferred; fold into Spec 13 with the
  rest of alerting, or add a 10-line step here if it proves needed sooner.
- **Open — prod smoke as a recurring synthetic check.** This spec runs the smoke
  once, at release. A scheduled (cron) prod smoke for ongoing liveness belongs in
  Spec 13 (observability) — noted so it is not assumed to be here.
- **Open — DB migration safety review in the gate.** Currently the reviewer
  eyeballs the diff before approving. A `prisma migrate diff` summary posted into
  the run for the approver to read would make the gate more informed; small
  addition, not required for done.
