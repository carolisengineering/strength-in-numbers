## 1. Purpose, scope & non-goals

Put notes where they apply, read them while training, and see them again afterwards. **In the routine editor** a lifter can group exercises into named **sections** ("Warm-up", "Main", …), each with a note, and move exercises between them. **In the session** the exercises sit under their section headings with the section's note beneath each, the routine's own note is at the top, and every exercise card has a **Note** action that edits *this workout's* copy of the exercise note — queued through the offline outbox like a logged set. **In History** (and the post-finish summary) the finished workout shows the same structure, read-only. **This spec changes no API, no migration and no server behavior.**

> **First-principles note — "pure reducer" and "settle".** The editor's draft lives in a plain function `reduce(state, action) → state` (Spec 10.0 D7); components only dispatch and render. Because every action can leave the item list in a shape the rest of the app cannot handle (a superset split across two places, an item in the wrong place), the reducer ends every changing action with one function, `settle`, that repairs the list into the canonical form. Adding sections adds two more rules to that one function — it does not scatter them across the actions, which is what keeps "no single action can forget a rule" (10.0 D8) true.

> **First-principles note — "outbox", and why a note is a different kind of write.** The *outbox* (Spec 06.2) is a list of unsent writes kept in `localStorage`, replayed one at a time when the network allows, so a lifter in a basement gym loses nothing. Today it only knows **sets**: each queued write names a set by a client-made key, and the server's answer teaches it the real id. A note is simpler — it is a replacement of one string on an exercise that already exists — so a note write needs no id mapping, and two edits of the same note collapse into one (the newer text wins). But it is not a set, and a few places count "unsaved sets" (the Finish button, the status line): those must learn about notes too, because a note that has not arrived when the workout is finished would be refused (`409 workout-finished`) and lost.

### In scope

- **Editor:** section list in `routineDraft` (add, rename, note, move, delete), "Move to section" in the row menu, `settle`'s two new rules, request building and validation for sections, server-error mapping, preview grouping.
- **Session:** `supersetRows` made section-aware, `sectionSegments`, section headings and notes, the routine-note panel, section-bounded Move up / Move down and link toggles, the exercise **Note** action and sheet.
- **Outbox:** a fourth op kind `note`, its coalescing, projection, counting and Finish gating.
- **Finished workout (both routes):** sections, routine note and the unchanged exercise notes, read-only.
- Draft / validation / fakes changes in `routineDraft.ts`, `validateDraft.ts`, `routineErrors.ts`, `supersetRows.ts`, `outbox/*`, `workoutClient.ts`, and the web test fakes. A manual phone check.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.3 ACn — …"`** (the 08.x / 10.x convention). Levels are in §10. **Phase A** (AC1–AC13): pure editor, grouping and outbox code. **Phase B** (AC14–AC23): editor screens. **Phase C** (AC24–AC33): session and History. **Phase D** (AC34–AC40): cross-cutting, verification, docs.

### Phase A — pure code: draft, request, grouping, outbox

1. **Draft model and load.** `Draft` gains `sections: readonly DraftSection[]` (`{ key, name, notes }`; `key`s are client-only, minted at load / add, never sent) and `DraftItem` gains `sectionKey: string | null`. `load` from a server `Routine` sorts sections by `position`, maps each item's `sectionId` to its section's key, and keeps item order; a routine without sections loads exactly as today (`sections: []`, every `sectionKey` null). Loading never marks the draft dirty, except when `settle` had to change something on load (the existing `adjusted` case, now also covering a section-order repair — AC6).
2. **Section text actions.** `addSection(name)` appends a section after the last one with a fresh key, trimming the name; it is a no-op (state identical by reference, `dirty` unchanged) when the name is blank after trimming or when 8 sections (`ROUTINE_SECTIONS_MAX`) exist. `renameSection(key, name)` and `setSectionNotes(key, notes)` replace the text; an unchanged value is a no-op by reference (Done on an untouched sheet must not arm the leave guard, 10.0 AC1). Every changing action sets `dirty`.
3. **Section move and delete.** `moveSectionUp` / `moveSectionDown` swap the section with its neighbor and carry its items with it; at either edge they are no-ops. `deleteSection(key)` removes the section; **its exercises are kept and become loose**, placed after the routine's existing loose exercises in their current order (D4); the section's name and note are discarded with it. A superset inside a deleted section stays a superset (the run stays contiguous among the loose items and is renumbered by `settle`).
4. **Item placement.** `moveItemToSection(itemKey, sectionKey | null)` takes the item out of its place and appends it to the **end of the target section's run** (`null` = the end of the loose run, i.e. immediately before the first section); it sets the item's `supersetGroup` to `null` first, and a superset left with one member dissolves (via `settle`). Moving to the item's current section is a no-op by reference. When the item had been linked, the draft carries a dismissible notice (`SECTION_UNLINK_NOTICE`, D2). `add` (a new exercise) appends to the end of the **last** section's run when sections exist, else loose (D3). `remove` is unchanged.
5. **Item moves and links stay inside a section.** `moveUp` / `moveDown` act on the item's own section run (the loose run counts as one): they apply `moveRule` (Spec 10.1 AC3, block moves and group-edge exits included) to that run only, and are no-ops at the run's edges. `toggleLink(index)` between two items in different sections is a no-op by reference. `canLink` reports the existing 8-member cap per section run. A superset's 8-member cap is unchanged.
6. **`settle` enforces three invariants in one pass.** After every changing action (and `load`): (a) items are in canonical order — loose items first, then each section's items in the sections' order, relative order preserved within each; (b) every non-null `supersetGroup` is one contiguous run of 2–8 **within a single section run** (a run that crosses a section boundary is split there; a run of one becomes ungrouped); (c) groups are numbered 1, 2, 3 … by first appearance. A property test over random sequences of every action (existing and new) asserts, on every intermediate state, that `sectionOrderViolations` and `sectionSpanViolations` (`@sin/core`, Spec 09.2 AC25) report nothing for the refs derived from the draft and that the 10.0 superset invariant holds; the existing 10.0 / 10.1 draft tests pass unmodified.
7. **The request body.** `toRoutineInput(draft, { modalityOf })` emits, for a draft with ≥ 1 section, `sections: [{ key, name, notes? }]` with request-local keys `s1 … sN` minted from section order (the draft's own keys are never sent; a blank note omits the `notes` key, as for items) and `sectionKey` on each sectioned item (loose items omit the key); for a draft **with no section** the body is **byte-identical to today's** (no `sections` key, no `sectionKey`) — the Spec 10.2 recorded bodies still replay. Positions are never sent.
8. **Validation.** `validateDraft` runs `RoutineWriteSchema.safeParse(toRoutineInput(...))` (which now covers section name / note / count / order / span, Spec 09.2 AC5–AC8) and maps issues to places: `sections.<j>.name` / `notes` → that section's header sheet; `items.<i>.sectionKey` / `supersetGroup` (span) → a form-level message (a draft built by this reducer can never produce them — they indicate a bug and are reported via `reportRoutineUnexpected`, like `groupBug`). Client messages come from a static table in the app's wording, never Zod's text, and never echo input: a blank name → "Give the section a name", over 40 → "Keep section names to 40 characters", note over 500 → "Keep section notes to 500 characters". `ITEM_FIELDS` / `issueForPath` learn the new paths; the 10.0 / 10.2 `validateDraft` tests pass unmodified.
9. **Server errors map to the same places.** `routineErrors.ts` maps a `422` whose `errors[].path` is `sections.<j>.<field>` to the section header (by the saved draft's section order), and `items.<i>.sectionKey` / `.supersetGroup` to the form-level fallback (`FORM_INVALID`); a `422` that names nothing on screen falls back to the existing form-level message. `409 exercise-retired` and `routine-name-taken` are unchanged.
10. **Session grouping is section-aware.** `supersetRows(exercises)` (the one place session superset display is derived) computes runs **within** a section segment: two adjacent exercises with the same `supersetGroup` but different `sectionId` are two separate ungrouped-or-run slots, never one bracket; `SupersetRow` gains `sectionId: string | null`; `runOrdinals` ("superset N") count the runs after that split. For a workout whose exercises all have `sectionId: null` the output is **identical to today's** (the 10.1 / 10.2 tests pass unmodified).
11. **`sectionSegments`.** `sectionSegments(rows, sections)` (`features/workouts/sectionSegments.ts`, pure) turns the position-ordered rows plus the workout's sections into the render list: each **maximal run** of rows with the same `sectionId` is one segment; a segment of a section carries that section's `name`, `notes`; a **loose segment** that is first in the list has no heading, and a loose segment after any sectioned segment has the heading "Other exercises" (D8); a section **with no rows** becomes a heading-only segment placed before the first segment that belongs to a later section or is a trailing loose segment (else last); a section split into two runs shows its note only under the first. With no sections it yields one headingless segment of all rows.
12. **The `note` outbox op.** The outbox (Spec 06.2) gains a fourth op kind `note` — `{ kind: "note", workoutExerciseId, body: { notes: string | null } }` — in `ops.ts` and `OutboxFileSchema` (the file's `v` stays `1`), with these rules in `combine`: an incoming note op **replaces the body** of the last op for the same exercise when that op is a `note` that is queued and never attempted (the newer text wins); otherwise it is appended (a sent op may already have been applied, so nothing is merged into it — the 06.2 rule); a `note` op that failed with `422` is reset and replaced by the next edit (parity with set ops); note ops of different exercises never merge. `classify`: network / `5xx` / `408` / `429` → retry; `404` → **done** (the exercise or workout is gone, so there is nothing to save); any other status → fail. A `409 workout-finished` fails the op and, as for sets, every later op of that workout. Note ops never emit `set_sync_failed` / `set_sync_delayed` (D13).
13. **Projection and counts.** `project(workout, outbox)` overlays a queued or failed `note` op onto the matching exercise's `notes` (in queue order; set ops never touch notes) and marks it in the `sync` map under the **exercise id** (pending / failed — the same map and `RowSync` type as set rows; ids cannot collide). A new pure `unsavedNotes(ops, workoutId)` returns `{ pending, failed }` counted in **exercises** (an exercise with several queued edits counts once); `unsavedSets` is unchanged and ignores note ops. A discarded failed note op reverts the exercise to the server's copy (the cache is refetched, as for a discarded set edit).

### Phase B — routine editor screens

14. **Layout.** The editor lists, in order: loose exercises (no heading); then each section as a labeled region — a header with the section's name, its note (shown in full, wrapped, when present) and an **Options** button — followed by that section's exercises; a section with no exercises shows the line "No exercises yet — use Move to section on an exercise" (a hint, not an error). Below the list: **Add section** and **Add exercise**. A routine with no sections looks exactly as in 10.2 (a markup comparison). The routine's own note field is unchanged.
15. **Add section.** **Add section** opens a sheet with the five starters — **Warm-up, Main, Accessory, Finisher, Cooldown** — as buttons, and a free-text field with an **Add** button (D5). Tapping a starter adds that section immediately and closes the sheet; **Add** adds the typed name (trimmed, 1–40 characters). All starters stay available whether or not a same-named section exists (duplicates are legal). At 8 sections the **Add section** button is disabled and a line beside it says "A routine can have up to 8 sections" (`aria-describedby`); the sheet cannot be opened then.
16. **Section sheet.** Activating a section's header (its name) opens the full-height `Sheet` with **Name** and **Note** fields, **Done** and **Close**, with the 10.0 sheet semantics: local state, **Done** parses and commits, **Close** discards, an invalid field keeps the sheet open with a message beside it (AC8's text), and **Done** on an untouched sheet does not arm the leave guard (AC2).
17. **Section Options.** The header's **Options** shows **Move up**, **Move down** (disabled, not hidden, at the edges, with the reason in text) and **Delete section**. Delete acts at once, with no confirmation (D4): the draft is unsaved until Save and the leave guard covers a mistaken tap; the section's exercises are kept (AC3). Focus returns to the next control sensibly (the 10.0 pending-focus pattern).
18. **Move to section.** An exercise row's **Options** gains **Move to section…**, which opens a small sheet listing **No section** and every section by name (the item's current place is shown selected and disabled); choosing one dispatches `moveItemToSection` (AC4), closes the sheet, and returns focus to the moved row's main control. When the move unlinked a superset, the `SECTION_UNLINK_NOTICE` ("Supersets stay inside one section, so this exercise was unlinked") appears in the existing dismissible notice slot. The list of choices is hidden when the routine has no sections (the button is then absent).
19. **Links and Add exercise follow sections.** The "Superset with next" toggle is rendered only between two exercises of the same section run (no toggle across a heading); the bracket never spans a heading. **Add exercise** appends per AC4 (to the last section, or loose when there are none) and the new row takes focus as today. The item cap (30) message is unchanged.
20. **Preview.** The routine preview (`RoutineItems`) shows the same grouping read-only: section headings with their notes between the exercise rows, loose exercises first without a heading, empty sections as a heading and note only, brackets within sections. A section-free routine renders exactly as in 10.2. The routine's own note is shown as before.
21. **Leave guard and save.** Every section action marks the draft dirty and so arms the Discard-changes guard (10.0 AC34); **Save** sends the whole document (AC7); a loaded sectioned routine saved after an edit elsewhere sends a body that the (fake) server stores as the same sections and memberships (no-op sheet **Done** on any section or item changes nothing — a regression test over one routine containing every shape).
22. **Server errors in the UI.** A `422` on `sections.<j>.name` shows beside that section's header (its sheet reopens with the message); a `422` that cannot be placed shows the existing form-level message. Messages come from the app's table (AC8).
23. **Routine start is unchanged.** Starting a workout from the preview or Start screen sends exactly the request it sends today (`useBeginWorkout` test unmodified); the editor never writes a workout.

### Phase C — workout session and History screens

24. **Session layout.** `ActiveSession` renders `sectionSegments` (AC11): each section segment is a labeled region whose heading is the section name with its note directly beneath (full text, wrapped), then its exercise cards with their brackets; "Other exercises" labels a loose tail; empty sections show their heading and note. A workout whose `sections` is `[]` renders exactly as in 10.2 (AC32). Sticky bar, banners, `SyncStatus` and the structure lock are unchanged.
25. **Routine note.** When `routineNotes` is non-null, a panel at the top of the session shows it (full text, wrapped, headed by the routine name — "Routine note · Push day"). It is **expanded when the session screen mounts**; a **Hide** button collapses it to a single "Routine note · Show" line and **Show** re-expands it. The state is component-local: nothing is stored in the browser (D9), so a reload expands it again. A workout with `routineNotes: null` shows no panel.
26. **Moves and links stay inside a section.** Move up / Move down act on the card's own segment: disabled (not hidden) at the segment's edges with the reason in text, never moving a card across a heading. The planner is called with the **segment's** slot list and the resulting `position` patches are offset by the segment's start, so a move is still one absolute `PATCH` (the 10.1 D7 retry rule) and `sectionId` is never written; the "Superset with next" toggle appears only between cards of the same segment, with its 8-member refusal computed on the segment. `planSessionChange` and `useRegroup` are unchanged.
27. **The Note action.** Every card on the **active** screen has a **Note** button (labeled **Add note** when the exercise has none, **Edit note** otherwise), a full-size tap target, under the exercise's note text. It opens the full-height `Sheet` with a labeled textarea prefilled with the current note, a live "n / 500" count, **Save** and **Cancel**. **Save** trims; empty text means *clear* (`notes: null`); text over 500 characters (D6) keeps the sheet open with "Keep notes to 500 characters"; control characters other than TAB / LF / CR are refused with the same static message as routine notes. **Save** on an unchanged value just closes. Both outcomes close the sheet immediately — the edit is optimistic (AC28).
28. **Note delivery.** Saving enqueues a `note` op (AC12) through a new `WorkoutClient.setExerciseNote(id, notes)` — REST: `PATCH /v1/workout-exercises/{id}` with **exactly** `{ "notes": … }` (never `position` or `supersetGroup`); queued client: enqueue and resolve at once. The card shows the new note at once and a "Not saved yet" tag while the op is queued, "Couldn't save" with a **Discard** button when it failed (a failed op is never retried silently once `fail`ed; **Try again** is the status line's existing Retry now), and the tag clears when the server acknowledges (the cache then holds the server's copy). `WorkoutExercisePatch` and `useRegroup` still have **no** `notes` key (Spec 10.1 AC11 stays true: a regroup cannot overwrite a note) — a type-level test and a body-capture test pin it.
29. **Finish waits for notes.** The Finish button is disabled while any note op of the workout is queued or failed (AC13), exactly as for unsaved sets; the bar's hint reads "{n} note(s) not saved yet" on its own line when only notes are pending; a queue holding only set ops renders the **exact** copy and states of 06.2 (a regression test). The status line (`SyncStatus`) is unchanged for sets; its Retry now / Discard failed also drive note ops.
30. **Offline, reload, other user.** A note saved offline survives a reload and drains when the network returns (the outbox file in `sin:workout:outbox`, already covered by `USER_DATA_KEY_PREFIXES`); ops of another user's session are ignored and logout clears them (06.2 AC8 / 06.0 logout rule); an outbox file written by a tab that was open before this spec (set ops only) loads unchanged; a `409 workout-finished` on a note op takes the 06.2 "finished elsewhere" path.
31. **Finished workout and History.** `FinishedWorkoutScreen` at both routes (`/app/workouts/:id` and `/app/history/:id`) renders `sectionSegments` read-only — section headings with notes, "Other exercises", empty sections, section-bounded brackets — and shows `routineNotes` as a plain paragraph under the existing "From routine:" line (no collapse, no Note action); exercise notes appear as today. The History **list** row, the Progress screens and the personal-records block are unchanged.
32. **No sections, no change.** A manually started workout, a workout started before Spec 09.2 and a routine started without sections render **exactly today's** active and finished screens (markup comparison), apart from the new Note button on active cards.
33. **Strict schemas stay strict; fakes keep up.** The web adds no `.default(…)` / `.catch` for the new fields; `workoutFake` and `routineFake` (the msw handlers) **always** emit `sections`, `sectionId`, `routineNotes`; the routine fake validates writes with the same `@sin/core` section helpers and the workout fake copies sections, section ids and the routine note on start by position — so the editor and session tests exercise the same rules as production.

### Phase D — cross-cutting and verification

34. **Boundaries and purity.** `workouts/ → routines/` imports stay exactly the leaf modules of Spec 10.1 AC28 (`targetFormat.ts`, `LinkToggle.tsx`, `SupersetBracket.tsx`, plus the existing `RoutinesSection`): the session's heading component lives under `workouts/`, the editor's under `routines/`, and `sectionSegments` under `workouts/` (the 10.1 source scan passes unmodified). New pure code imports only `@sin/core` and sibling leaf modules; `core:purity` is untouched (this spec adds nothing to core).
35. **Observability and hygiene.** No new `track()` event or property and no change to `set_logged` / `workout_started { fromRoutine }`; `reportError` is unchanged; no section name, section note, routine note or exercise note appears in any `track` / `reportError` / console argument (a spy test over the new paths); note ops emit no `set_*` events (AC12).
36. **User text is text.** Section names, section notes, the routine note and exercise notes are rendered as React text children (line breaks via CSS `white-space: pre-wrap`), never as markup, links or attributes; a source scan of the files this spec adds finds no `dangerouslySetInnerHTML`, `innerHTML`, `style=` or `<style`; a component test renders a note containing `<img src=x onerror=…>` and finds it as text.
37. **Accessibility and tokens (component level).** In `a11y.test.tsx` (`describe("10.3 AC37 — …")`): each section is a region named by its heading; the heading, the note and the cards read in that order; every control has a visible label and a name that includes its target ("Move Main up", "Edit note for Bench press", "Delete section Warm-up"); disabled controls are `disabled` with the reason in text, not tooltip-only; the starter buttons are a labeled group; the routine-note toggle has `aria-expanded`; the sheet textarea is labeled and its count is not the only error cue. Every touched `*.module.css` uses `var(--…)` only and `assert:css-tokens` passes. Pixel sizes, focus and the 320 px layout need a browser (AC39).
38. **No other behavior change; no backend change.** The existing `@sin/web` suites pass with edits limited to fixtures that gain the new fields and to the signature changes named in this spec; the Playwright smoke is unchanged; `git diff main --stat` shows **no** path under `apps/api/`, `packages/core/` (Spec 09.2 already added the helpers), `render.yaml`, `Dockerfile` or `.github/workflows/`.
39. **Manual phone check (owner, recorded in the PR description).** On a phone against staging (Spec 09.2 deployed): build a routine with a loose exercise, a "Warm-up" section with a note and no exercises, and a "Main" section with a superset; move an exercise between sections and see the superset unlink with its notice; delete a section and see its exercises kept; save and reopen; start it; confirm the routine note is open at the top and Hide / Show works, headings and notes read well, and the superset bracket stops at the section edge; add a note to an exercise **in airplane mode**, reload, reconnect and see it sync; try to Finish with the note unsynced and see Finish wait; finish and confirm the summary and History show the structure and notes; check **320 px and 390 px** — nothing overflows sideways, every control is reachable one-handed and ≥ 44 px; VoiceOver reads a section ("Main, region") then its cards.
40. **Docs stay consistent.** DESIGN.md, `docs/specs/README.md` carry the edits listed in §11; each of AC1–AC38 has ≥1 committed test tagged with its number; AC39 is verified by the PR description, AC40 by review.

## 6. Behavior & logic

### 6.1 The editor draft (AC1–AC6)

The item list is one flat array in canonical order (AC6a); a section's items are the contiguous slice whose `sectionKey` equals the section's key. Flat indexes keep every existing action (`toggleLink(index)`, the 10.0 focus bookkeeping) working; section-aware actions work on slices.

| Action | Effect on the flat list | Then |
|---|---|---|
| `add` | append after the last section's slice (loose when there are no sections) | `settle` |
| `moveItemToSection(k, s)` | remove `k`, `supersetGroup := null`, insert at the end of `s`'s slice (`null`: after the last loose item) | `settle` (dissolves a one-member run) |
| `moveUp` / `moveDown` | `moveRule` on the item's slice only | `settle` |
| `moveSectionUp/Down` | swap the two sections; their slices swap | `settle` |
| `deleteSection(s)` | `sectionKey := null` on its items | `settle` stable-sorts them behind the existing loose items |
| `addSection` / `renameSection` / `setSectionNotes` | section list only | — |

`settle` (AC6) is: (1) stable-sort by section order, loose first; (2) compute superset labels with a new run starting wherever the group **or the section** changes (extending the 10.0 label loop), dissolve runs of one; (3) `normalizeSupersetGroups`. It also repairs a bad `load` (and flags `adjusted`), so a server document that violates the invariants (impossible after 09.2, possible from data written by another client) still opens cleanly.

### 6.2 Request building and validation (AC7–AC9)

`toRoutineInput` is the only place that decides the body: it numbers sections `s1 …` from their order, so request keys never depend on draft keys and are deterministic in tests; with no sections it emits today's body (AC7). The parity guarantee is structural — the same `RoutineWriteSchema` the API runs, so the editor cannot accept a value the API would reject; the server stays the authority (a `422` is mapped back, AC9).

### 6.3 Session segments (AC10, AC11)

```
rows      = supersetRows(workout.exercises)            // position order; runs split at section boundaries
segments  = sectionSegments(rows, workout.sections)    // maximal runs + heading-only segments for empty sections
```

Heading rule: a headed segment is a section's; the first segment, when loose, has none; a later loose segment is "Other exercises". Empty-section placement is by section `position`: before the first segment belonging to a later section or the trailing loose segment, else last — a table-driven unit test, including the defensive cases of a section split into two runs and a group spanning two sections (which `supersetRows` renders as two separate slots).

### 6.4 Section-bounded moves in the session (AC26)

`ActiveSession` builds the slot list of the card's **segment** (`SessionSlot[]` with `id` and `group`) and calls `regroup.run(segmentSlots, op)`. `planSessionChange` returns patches whose `position` is the target index inside that list; the screen adds the segment's start index before sending, so the wire body is an absolute position as in 10.1. Group numbers are chosen by the planner among the numbers used **inside the segment**; a number that also appears in another section is harmless because runs end at section boundaries (AC10) and "superset N" is the on-screen ordinal. A segment that is not contiguous (defensive) is treated as two segments.

### 6.5 The note write (AC12, AC13, AC27–AC30)

```
Save in the sheet ─▶ trim; "" → null ─▶ client.setExerciseNote(id, notes)
   queued client: outbox.enqueueNote({ workoutId, workoutExerciseId, body: { notes } })  → resolves at once
   outbox: combine (newest text replaces an unsent op) ─▶ drain, one op at a time, oldest first
   call(op): rest.setExerciseNote(id, notes) → PATCH /v1/workout-exercises/{id} { notes }
   succeed: remove op; applySynced patches the cached exercise's notes/updatedAt from the response, then re-projects the rest
   fail: status line + card tag; Discard drops the op and refetches
```

The overlay is by queue order, so a later edit always wins. The sheet closes at once; there is no spinner because nothing waits on the network. Finish is disabled while a note op is queued or failed (AC29): a PATCH after Finish returns `409 workout-finished` and would be lost.

### 6.6 Edge cases

- **Exercise removed with a note op queued** — the `404` is "done"; nothing to show.
- **Two edits in a row while offline** — one queued op carrying the latest text.
- **Note cleared** — `notes: null`; the "Add note" label returns.
- **Long note on a routine-started exercise** — the routine's copy is ≤ 500; the editor caps at 500 too (D6); a longer value (written through the API) displays in full and is edited down to 500 on save.
- **A section with a very long note** — wrapped in full; the phone check (AC39) decides whether a clamp is warranted (O3 of Spec 10.1 is the precedent).
- **Defensive data** — a loose tail, a split section, or a group spanning sections (09.2 §6.5) never throws: runs are maximal, brackets break at headings.
- **The routine was deleted after the start** — nothing changes; the workout is self-contained (09.2 AC15).

## 7. Security & privacy

- **Authorization is the server's** (Spec 09.2 §7): the client adds no authority; every id goes to the API in the path as before, and the client never sends a section id.
- **User text** — section names and notes, the routine note, exercise notes — is free text that may hold health information. It is rendered as React text and never reaches `track` / `reportError` / the console (AC35, AC36). It lives in the DOM, in the routine `PUT` and note `PATCH` bodies, and in the outbox file for as long as a note is unsent; it is never in URLs.
- **Nothing new is stored in the browser beyond the existing outbox file** (§4); logout clears it (the `sin:workout:` prefix), and an outbox file of another user is ignored.
- **Abuse:** bounded by the server (8 sections, 500-character section notes, the `routines` and `workouts` write groups). A note edit is one coalesced op per exercise, so the 60 / min `workouts` budget is not at risk from repeated saves.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-13, from the brief)

- ✅ **D1 — Sections are authored only in the routine editor and are optional everywhere (brief decisions 1–3).** The draft gains an ordered section list and a `sectionKey` per item; `settle` enforces the three invariants in one pass (AC6); keys never reach the server (the request uses `s1…` minted by `toRoutineInput`). **Rationale:** the 10.0 reducer design already puts every superset rule in one function; sections are two more rules there, tested by the same property test. **Rejected:** heading pseudo-items in the draft (every action and `settle` would branch on item kind).
- ✅ **D2 — "Move to section" appends to the end of the target section; a linked item is unlinked, with a notice (brief decision 3; the brief's "same wording as other unlink cases" resolved by reading the code).** No unlink wording exists in the app today — Spec 10.0's only superset message is `ADJUSTED_NOTICE` ("Supersets were adjusted so grouped exercises sit together"), shown for a bad load — so this spec adds one string, `SECTION_UNLINK_NOTICE` ("Supersets stay inside one section, so this exercise was unlinked"), in the same dismissible notice slot. **Rationale for "append":** it is predictable and testable; the lifter then uses Move up / Move down inside the section. **Rejected:** keeping the superset by moving the whole run (the brief says moving an exercise unlinks it); a position picker in the move sheet (extra UI for a rare need).
- ✅ **D3 — A new exercise goes to the end of the last section, or loose when there are none (found by reading the code; the brief does not say).** The editor's single **Add exercise** button appends to the end of the flat list, which with sections *is* the last section's run. **Rationale:** the smallest rule that keeps the invariant with one button. **Cost:** an exercise meant for an earlier section needs one **Move to section**; **O3** asks whether a per-section "Add exercise" is worth building.
- ✅ **D4 — Deleting a section keeps its exercises (brief), without a confirmation.** They become loose and sit behind the existing loose exercises. **Rationale:** the draft is unsaved until Save, the leave guard covers a mistaken tap, and nothing but a name and a note is lost; a confirmation dialog on a reversible, in-memory action is friction in a gym. **Rejected:** deleting the exercises with the section (the brief says kept).
- ✅ **D5 — One-tap starters; free text beside them (brief decision 2).** Tapping a starter adds the section immediately; all five stay available even when a same-named section exists. **Rationale:** "one-tap" means one tap; hiding used starters would imply names are unique, which 09.2 D3 deliberately does not require.
- ✅ **D6 — The session note editor caps at 500 characters although the API accepts 4 000 (found by reading the code).** `UpdateWorkoutExerciseSchema.notes` allows up to `WORKOUT_NOTES_MAX` (4 000); the routine item note, which seeds the exercise note, is ≤ 500. **Rationale:** the brief says "lightweight, not a note-taking feature"; a 4 000-character note under a card pushes the Log row off a phone screen (Spec 10.1 O3). The cap is a UI choice (one constant, no API change); a longer legacy value displays in full and shrinks on save. **Rejected:** mirroring the API limit.
- ✅ **D7 — An exercise note is a new `note` op in the offline outbox (brief: "go through the offline outbox"; qualified by reading the code).** The brief called this a reuse; the outbox is in fact built for *set* writes — ops are keyed by a set's client id, `OutboxFileSchema` is a discriminated union of set operations, the drain loop resolves set ids, `unsavedSets` gates Finish, `queuedWorkoutClient` intercepts only the three set methods. A note therefore needs a new op kind, coalescing, projection, counting and Finish gating (AC12, AC13, AC29), and a rollback caveat (§11). **Why still the outbox:** the lifter writes notes mid-session, where signal is worst, and a note typed and lost is exactly the failure Spec 06.2 exists to prevent; the write is the simplest possible one (one string, no id mapping). **Alternative (O1):** online-only like a regroup (Spec 10.1 D6): about a third of the work and no rollback caveat, at the price of "You're offline — try again" on a note. **Rejected:** a separate mini-queue (a second persisted store with its own drain and conflict rules).
- ✅ **D8 — The session renders maximal runs of equal section; a loose tail is "Other exercises"; empty sections are shown (brief + found by reading the code).** A running workout can hold a loose tail (exercises added after the start are appended at the end, 09.2 D9) and, from other clients, split sections; showing the tail under the previous section's heading would be wrong, and a plain break with no label would read as part of it. **Rationale:** an honest, deterministic rule over `position` order with no data repair; the copy "Other exercises" is a proposal for the phone check (AC39). Empty sections show because their note may be the whole instruction ("5 min rower").
- ✅ **D9 — The routine-note panel is expanded on mount, collapsible, and its state is local (brief open item 2, resolved).** The brief suggested not persisting it. Persisting would need a `sin:workout:`-prefixed key through the `StorageAdapter`, a per-workout id, and clearing rules for something that is only a convenience; component state costs none of that, and "expanded again after a reload" is arguably right (the note may matter again). **Rejected:** persistence; auto-collapse on first scroll (surprising).
- ✅ **D10 — Section headings are `h2` inside a labeled region; exercise names stay `h2`.** Changing the exercise heading level would touch every existing card test and screen-reader expectation for a case (sections) most workouts do not have; the region landmark (named by its heading) carries the grouping for assistive technology, and the DOM order heading → note → cards is the reading order. **Revisit** if the phone check with VoiceOver finds the flat heading outline confusing.
- ✅ **D11 — The finished workout and History show the structure read-only; the routine note is plain text there (brief decision 5).** The same `sectionSegments` path as the active screen, no collapse (nothing to dismiss), no Note action (a finished workout is read-only, Spec 06.1 D18). **Rationale:** one rendering path means the two screens cannot disagree (the 10.2 D8 reasoning).
- ✅ **D12 — Session moves are planned on the card's segment and offset (resolved with 09.2 D9).** The existing planner is fed a shorter slot list and the screen adds the offset; nothing in `@sin/core` changes. **Rationale:** the smallest change that keeps Move up / Move down inside a heading; a cross-heading move would need a way to write `sectionId`, which does not exist by design.
- ✅ **D13 — No analytics change, and note ops emit no `set_*` events.** `set_sync_failed` / `set_sync_delayed` describe set writes; reusing them would corrupt that signal, and a new event has no consumer before Spec 13. **Rationale:** same as 10.2 D10.
- ✅ **D14 — `workouts/` and `routines/` each get their own section heading component.** Spec 10.1 D10 limits `workouts/ → routines/` imports to three leaf modules enforced by a source scan; two small components (one per feature, sharing only tokens) cost less than widening the boundary.

### Resolved by reading the code (corrections and qualifications to the brief)

- **`PATCH /v1/workout-exercises/{id}` already accepts `notes`** (09.2 D10): the brief's "gains `notes`" is client-side only — `WorkoutExercisePatch` has no `notes` by design (10.1 AC11), so this spec adds `WorkoutClient.setExerciseNote` rather than a patch key, keeping the 10.1 guarantee literally true.
- **The outbox is set-specific** (D7), which is the largest unplanned cost in this spec.
- **The export is not "free" on the workout side** (09.2 D13) — an API-side matter, noted here because History reads the same fields.
- **There is no existing unlink wording to reuse** (D2).
- **The advisory-lock key the brief asked for is unnecessary** (09.2 D8) — nothing on the client side changes.

### Open

- **O1 — Session notes: offline outbox or online-only?** Recommended default drafted: **outbox** (the owner's decision in the brief; D7, AC12–AC13, AC28–AC30). The code shows it costs a fourth op kind across `ops.ts`, `outbox.ts`, `classify.ts`, `project.ts`, `queuedWorkoutClient.ts` and `WorkoutClientProvider.tsx`, Finish gating, and a rollback caveat (§11). **Alternative:** online-only like a regroup — the Note sheet saves with a plain `PATCH` (a mutation hook like `useRegroup`), shows "You're offline — try again" when it cannot, and Finish needs no change; AC12, AC13, AC29, AC30 shrink to one failure-handling criterion. Pick the outbox if notes will often be written in the gym with poor signal (the phone feedback suggests they will); pick online-only if you want M3 finished sooner. Needs a one-line ruling before implementation.
- **O2 — One spec or two?** This spec carries four things: the editor (A/B), the session and History (C), and the note write through the outbox. It is the largest UI spec so far. **Recommendation:** keep one spec but implement in the AC order (editor → session read → note write); if the outbox work overruns a session, **split the Note action (AC12, AC13, AC27–AC30) into a Spec 10.4** — it depends only on 09.2's existing `PATCH` and on nothing else in this spec, so nothing here blocks the split.
- **O3 — A per-section "Add exercise"?** Today's single button appends to the last section (D3). If the phone check shows lifters mostly build a routine section by section, a button at the end of each section header block (adding into that section) would save a **Move to section** per exercise. It is additive (one more action and button; no data change). Recommended default: not in v1.
