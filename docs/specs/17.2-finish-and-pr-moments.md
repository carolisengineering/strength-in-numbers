## 1. Purpose, scope & non-goals

### 1.1 Purpose

Finishing a workout is the one moment the app can say "here is what you did". Today it says little:

- The Finish dialog says "3 exercises · 14 sets. A finished workout can't be edited." and "End workout early" (17.1) lists unlogged sets after a bare title.
- The summary opens with `{date} · {minutes} min` and then a bulleted text list ("Bench Press — Heaviest weight 102.5 kg (was 100 kg)") that repeats the exercise name once per record type and prints raw e1RM such as "137.08 kg".
- History marks a record with a trophy and no number.

After this spec:

- **Finish and End-early dialogs lead with what you did** (duration, exercises, working sets; **a change from today**, when the Finish dialog counts every logged set including warm-ups, see AC4 and D14). End-early then says "N planned sets not logged" before the "can't be edited" note.
- **The summary header** reads duration · exercises · sets · volume.
- **One record card per exercise**: the lead record is big, with a brass "+N" gain and "was …" underneath; the exercise's other records are name-only chips. Set-volume records are not shown there.
- **e1RM is rounded for display** to 1 lb (0.5 kg for kg users); deltas are computed after rounding.
- **History**: a brass trophy plus a count, only on workouts that hold records.
- **The celebration is quiet**: no animation. Brass and layout carry it.

### 1.2 In scope

**Phase A, the dialogs and the header (AC1–AC14)**
- `FinishStats` (duration, exercises, sets) in both dialogs; the End-early order; the unlogged flag; the header with volume.
- Pure helpers for the duration text, working-set count and volume.

**Phase B, records and History (AC15–AC34)**
- `RecordCards` replacing `RecordsSection` on the summary only; the display rounding and delta rules; the History badge with a count.
- The History count dependency on Spec 07.3 (§3.2), which makes the badge number equal the summary's "N new" (AC32).

**Both**: tokens/roles/contrast (AC35–AC37), docs, screenshots, phone check (AC38–AC41).

### 1.3 Size and split

One spec, two PRs, in order A then B (same pattern as 17.1's D1). Phase A is the dialogs and the header and is independent of records. Phase B is the larger one (new component, rounding, History). If the owner prefers separate files, cut at the phase headings: **17.2a = Phase A**, **17.2 = Phase B** (D1). Phase B is gated on Spec 07.3 being deployed (D11); there is no web-only fallback.

### 1.5 First-principles notes

> **Derived values are computed, never stored.** Duration, the working-set count and the total volume are functions of the workout the screen already has, so the dialog and the summary compute them through the same pure functions. If each screen kept its own arithmetic they would drift ("41 min" in the dialog, "42 min" on the summary). The one input that differs is the end time: the dialog uses the moment it opened, the summary uses the server's `endedAt`, and both go through `finishTimestamp` so a skewed device clock clamps the same way.

> **Rounding for display is not rounding the data.** The server keeps e1RM exact (integer milli-kg). The screen shows a rounded value because the formula is an estimate: "137.08 kg" claims a precision the Epley formula does not have. The catch is the delta. If we showed the exact gain (+0.31 kg) beside rounded numbers (137 → 137.5) the arithmetic on screen would not add up. So we round the new and previous values first and subtract the rounded numbers. A real gain can then show as "+0"; AC22 says what we do then.

> **Hidden is not deleted.** Set-volume records still exist, still count toward the engine's rebuilds, and still show in Progress. The summary filters them at render time, and so must every number derived from the list (the "N new" count). Anywhere a count and a list can be computed from different inputs, they will eventually disagree; that is exactly the History problem in §3.2.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"17.2 ACn — …"`**, enforced by a scan test in the style of 17.1's (AC38). Levels are in §10.

### Phase A — the dialogs and the header

1. **Finish dialog leads with stats.** The "Finish workout?" dialog shows, in order, a `FinishStats` list (duration, exercises, sets) and then the sentence "A finished workout can't be edited." The title ("Finish workout?"), confirm ("Finish") and cancel ("Keep logging") labels are unchanged. The old one-line "N exercises · N sets." text is gone.
2. **End-early dialog order.** The "End workout early?" dialog shows, in order: `FinishStats`; the flag "N planned sets not logged" ("1 planned set not logged" for one); the per-exercise list ("Bench Press · 1 set"); then the note "Unlogged sets aren't saved. You can't edit a workout after finishing it." Title, "End workout" confirm and "Keep logging" cancel are unchanged. **(Copy from the mockup; D12.)**
3. **The flag lives in the shared component.** `FinishStats`'s dialog wrapper renders the flag, list and then the note whenever it is given `unlogged.total > 0`, so the plain Finish dialog also shows "N planned sets not logged" before its "can't be edited" sentence if it is ever opened with unlogged sets. (Today it cannot be, because the bar and menu route unlogged workouts to End-early; this keeps the rule true by construction rather than by call site.)
4. **Stats definitions.** In both dialogs and the summary header: **exercises** = the workout's exercise count (same as History's `exerciseCount`); **sets** = logged *working* sets (warm-ups, drop and failure sets: see AC5); **duration** per AC6. **Owner decided 2026-10-17 (D14): working sets, matching History's `workingSetCount`.**
5. **Working-set count.** `workingSetCount(exercises)` counts `setType === "working"` sets only, including outbox-queued and failed ones in the active session (the same projected list `unloggedPlanned` reads). Warm-up, drop and failure sets are logged but not counted in the stat. A workout with 6 warm-ups and 3 working sets reads "3 sets". **This changes today's Finish dialog**, which counts every logged set ("14 sets" including warm-ups); it now counts working sets only, so the dialog, the summary and the History row agree. The enabling rule for Finish (`totalSets === 0` disables it) and the `workout_finished` event's `setCount` are **unchanged** (they keep counting every set), and a test pins both so only the displayed number moves. The label stays "sets" with no "working" qualifier (D14).
6. **Duration.** `workoutMinutes(startedAt, endedAt)` = `Math.round((end − start) / 60 000)`, never negative. `formatMinutes(n)`: under 1 → "Under 1 min"; 1–59 → "52 min"; 60 and over → "1 h 5 min" (a whole hour reads "2 h"). The dialogs use `endedAt = finishTimestamp(startedAt, openedAt)` where `openedAt` is captured once when the dialog opens (so the number does not tick while the lifter reads it); the summary uses the server's `endedAt`. The same inputs give the same text in the dialog and the summary.
7. **Frozen contract.** Both dialogs still confirm through `confirmFinish(false | true)` with the existing `finishLock`, waits and failure banners (17.1 §6.7). A test asserts the same spy is called with the same arguments as before, and that nothing in 17.2 touches `confirmFinish`, `finishLock` or `useFinishWorkout`.
8. **Summary header.** `FinishedWorkoutScreen` renders, under the unchanged "Workout summary" `h1`: the date line (`formatLocalDate`, without the old " · N min"), the unchanged "From routine: X" and routine-notes lines, then a `FinishStats` row of duration · exercises · sets · volume. No "Workout finished" extra heading (the Screen title stays; e2e asserts it). **(Mine; the mockup's "Workout finished" eyebrow would read oddly on a workout opened from History.)**
9. **Volume stat.** The header's volume is `sumVolumeMilli` from `@sin/core` over the working sets of load modalities (the same function behind History's `totalVolume`, so the two agree), converted to kg (`milli / 1000`) and formatted by `formatVolumeKg(…, unitPreference)` → "14,250 lb" / "6,463.6 kg". When no set qualifies (`null`) the volume stat is omitted entirely, never "0". The dialogs do not show volume (the mockup's dialog has three stats).
10. **Parity with History.** For one fixture workout, the header's sets and volume equal the History row's `workingSetCount` and `totalVolume` formatted the same way.
11. **Modalities and warm-ups.** A workout of duration / distance exercises only: three stats, no volume, no records section (AC24). Warm-up sets never enter sets or volume. A bodyweight-only workout (reps without weight) has no volume.
12. **Layout.** `FinishStats` is a `ul` of `li`s, each "value unit" then a label ("52 min" / "duration", "4" / "exercises", "18" / "sets", "14,250 lb" / "volume"); the values use the 17.0 figure tokens (tabular). At 390 px the four stats fit one row or wrap 2 × 2 with no horizontal overflow; at 320 px they wrap. A long figure ("12,345.6 kg") does not clip.
13. **Quiet.** The new CSS files contain no `animation`, `@keyframes` or `transition`, no `aria-live` or `role="status"` is added for the celebration, and nothing is announced on arrival. (A scan test; the screen is static.)
14. **Offline.** The header and cards read only cached data. Opening a just-finished summary with the network off shows the header and, when the finish response seeded the records (the normal path), the cards. If the seed was lost and the records query cannot load, the header still renders and the records section shows the existing "Couldn't load records" notice with "Try again" (08.0 AC19). The dialogs work offline as far as 17.1 lets Finish work offline (unchanged).

### Phase B — record cards, rounding, History

15. **One card per exercise.** The summary groups the workout's visible records (AC16) by `exerciseId` (the lineage root) and renders one card per group, inside a `ul`, under the existing `h2` "Personal records" (`RecordCards` replaces `RecordsSection` on the summary only; Progress keeps `RecordsSection`).
16. **Set-volume hidden.** Records with `recordType === "best_set_volume"` are filtered out of the cards, the chips and every count on the summary. They remain in the cache and in Progress. A workout whose only records are set-volume records shows no records section at all.
17. **The lead record.** Per exercise the lead is the first of `heaviest_weight`, `best_est_1rm`, `max_reps` that is present (the `RECORD_TYPE_VALUES` order minus volume), except per AC22. **(D17, accepted.)** It sets the card's label (`recordLabel`: "Heaviest weight", "Best est. 1RM", "Most reps").
18. **Card content.** In order: the exercise name (`h3`, `exerciseName`); the lead set's text beside or under it ("190 × 5", from the workout's own set with id `sourceSetId`, through `formatSet` core; omitted if that set is not found); the lead label; the new value, large, with its unit smaller; the gain "+5 lb" in brass; "was 185 lb" muted. Nothing else per card.
19. **First records.** A lead with `previousValue === null` shows "First record" in brass in place of the gain and no "was" line. It still counts and still gets a card. **Owner decided 2026-10-17 (D13).**
20. **Chips.** The exercise's other visible records render as name-only chips after the lead: "Heaviest", "Est. 1RM", "Most reps" (short names; **mine**). They are not interactive, carry no values, and sit in a `ul` named "Also set records for {exercise}". Zero other records means no list and no empty space.
21. **e1RM display rounding.** `roundedE1rm(valueKg, pref)` in `features/units/format.ts` converts to the display unit and rounds to the nearest 1 lb (lb users) or 0.5 kg (kg users) using integer arithmetic on the step (`Math.round(v / step)`, then multiply), so "137.08 kg" shows as "137 kg" and 225.4 lb as "225 lb". It is a display function only: nothing in `@sin/core` changes. **(Mine: it lives with the other formatters, whose header says they may move to core later.)** Values for other record types keep today's `formatRecordValue` output.
22. **Deltas after rounding.** For `best_est_1rm` the new and previous values are rounded first and the gain is the difference of the rounded numbers, computed in integer steps (no float subtraction noise). If the rounded gain is 0 (or negative from a boundary case), the e1RM is not eligible to lead while another record exists, and when it is the only record it leads with its value but **no gain and no "was" line** (the card says only the new number). **(D16, accepted.)** For every other type the gain is the exact difference formatted by the existing formatter (`+2.5 kg`, `+5 lb`, `+1 rep`, `+2 reps`).
23. **Units.** Values and gains follow the profile unit (`unitPreference`), exactly like 08.0. A kg account sees "+2.5 kg"; an lb account sees "+5 lb" for a 2.268 kg gain (lb to 1 decimal, as today, so 225 lb stored as 102.058 kg reads 225 lb).
24. **Empty and modality states.** No records (or only set-volume ones): the section is absent and no brass appears on the screen. Duration and distance exercises produce no records and therefore no cards; a mixed workout shows cards only for the exercises that set records. Max-reps cards use "reps" as the unit and "+1 rep" / "+2 reps".
25. **Order.** Cards follow the workout's exercise order (matched by `sourceExerciseId` to the workout's exercises); a card whose exercise cannot be matched goes after those, in `sortRecords` name order. **(D17, accepted.)**
26. **Section header.** The `h2` reads "Personal records" (unchanged) and is followed by "N new" ("1 new"), where N is the number of visible records (cards plus chips), the figure History shows (AC32).
27. **Many records.** A workout with 12 record-holding exercises renders 12 cards with no cap or "show more", names wrap (`overflow-wrap: anywhere`), and chips wrap onto further lines; no horizontal scroll at 320 px.
28. **States unchanged from 08.0.** While the query is pending nothing renders; a failed refresh keeps the cards already shown and adds the existing notice beside them (08.0 AC19); the finish response's `newRecords` still seeds the cache (no spinner).
29. **Rounding applies everywhere e1RM is shown.** The Progress records list (`recordLine`) and the e1RM chart's point readout (`metrics.ts`) show the rounded value too, so "137.08 kg" appears nowhere in the app. The chart's plotted data is not rounded. **(D15, accepted.)**
30. **Accessible.** The cards are in landmark order (`h1` > `h2` > `h3`), every figure is text, the card needs no color to be understood ("First record" or "+5 lb" is text), and the chips are plain list items. Axe-clean in light and dark on the card and dialog (the 17.1 `a11y.test.tsx` pattern).
31. **History badge.** `HistoryRow` shows, for `recordCount > 0` only, the brass trophy (decorative, `aria-hidden`) and the text "N PR" / "N PRs" in brass; the screen-reader name stays "N personal record(s)" (a visually hidden span carries the long form and the short text is `aria-hidden`). With `recordCount === 0` there is no badge and the row is unchanged. The long-routine-name truncation (10.1 AC25) still keeps the badge's box; no overflow at 320 px. *(As built: the badge keeps `role="img"` with an `aria-label` of the long form, and the trophy and the short text are `aria-hidden` children of it; same accessible name as a separate visually hidden span, and the 08.0 tests keep their contract.)*
32. **The count matches the summary (Spec 07.3).** For one fixture, the History badge number equals the summary's "N new". Spec 07.3 makes the served `recordCount` exclude `best_set_volume`, so the web shows `recordCount` as served with no client arithmetic (the web never subtracts or re-derives it). A workout whose only records are set volume has `recordCount: 0`: no badge on the row and no records section on the summary. Phase B is implemented against, and merged after, a deployed 07.3 (verified in the PR with one staging `GET /v1/workouts`); the web fake (`workoutFake`, `data.mjs`) serves `recordCount` computed the 07.3 way so the parity test is honest. *(Owner decided 2026-10-17, D11.)*
33. **Why the trophy appeared on every row (finding).** The logic is already conditional (`HistoryRow` renders the badge only when `recordCount > 0`, and the server counts `personal_record` rows the workout holds *now*). The screenshots harness fake data gives 8 of its 9 workouts at least one record (counts 6, 9, 3, 10, 3, 3, 3, 0, 3 as served before 07.3) because each fake workout introduces exercises and every first-ever value is a record. So the critique's trophy-everywhere came from the fake data, not from the logic, but real accounts show the same effect for first-time exercises, which are kept on purpose (AC19, D13). The harness data is changed in this spec to include several workouts with zero records so the screenshots show the real range, with each fake `recordCount` computed the 07.3 way (set-volume records not counted), and a RTL test asserts no badge at `recordCount: 0`.
34. **Held now.** The badge and the summary show records the workout holds now (07.0 D18): beating a record in a later workout removes it from the earlier summary and History row. A one-line "records are removed when you beat them later" note is not added (existing behavior, no copy).

### 3.2 The API dependency: Spec 07.3 (History's `recordCount` excludes set volume)

`WorkoutSummary.recordCount` was `count(*)` of every `personal_record` row the workout holds (07.0 D18; `workout-history.prisma.ts`), including `best_set_volume`. This spec hides set-volume records on the summary (owner decision), so a History row could say "3 PRs" over a summary that lists 2, or a trophy over a summary with no records section. The number must mean the same thing in both places or the trophy stops being trustworthy.

**Owner decided 2026-10-17 (D11): option A.** A tiny API-first [Spec 07.3](07.3-history-record-count.md) changes the History count query to `AND pr.record_type <> 'best_set_volume'`. No schema or shape change and no migration, so old web builds just show a lower number; it ships one release before Phase B (DESIGN §6's rollout convention). The field name now slightly understates ("records shown"); 07.3's doc comment records it. Options B (a second field) and C (accept the mismatch) were rejected. Phase A does not depend on 07.3 and can start immediately.

## 6. Behavior & logic

### 6.0 Decisions carried over (owner, 2026-10-15)

One card per exercise with the lead big, brass "+N", "was …", others as name-only chips; set-volume hidden here; e1RM rounded to 1 lb (0.5 kg), deltas after rounding; header = duration · exercises · sets · volume; quiet celebration; dialogs and History follow the mockup; trophy only on workouts that hold records.

### 6.1 Stats

`finishStatsFor(workout, endedAt)` returns `{ minutes, exercises, sets, volumeKg | null }`. `sets` and `volumeKg` come from `exercises` filtered to working sets; milli ints for volume come from `Math.round(weightKg * 1000)` (the API serves `weightKg` as a number of ≤ 3 decimals). The active session passes the outbox-projected exercise list (so a queued set counts), the summary passes the server detail.

### 6.2 The dialogs

`FinishDialog` is the body only; both usages stay `ConfirmDialog`s (17.1 §6.7: children and titles may change, the call, lock and waits may not). Duration: `ActiveSession` stores `openedAt` in a ref when `finishOpen` / `endEarlyOpen` flips to true. The flag is the existing `unlogged.total` text. List markup is unchanged from `EndEarlyDialog` (`name · N sets`).

### 6.3 Records on the summary

Pipeline (pure): `records` → drop `best_set_volume` → group by `exerciseId` → per group order by type, pick the lead (AC17, AC22) → map to `{ name, setText, lead: { label, valueText, gainText | null, wasText | null, first }, chips }` → order groups (AC25). Rendering is dumb. The lead's value text is `roundedE1rm` for e1RM and `formatRecordValue` otherwise (`kg_reps` never reaches here).

### 6.4 e1RM rounding, exactly

`step = pref === "lb" ? 1 : 0.5` in the display unit. `display = pref === "lb" ? kgToLb(valueKg) : valueKg`; `steps = Math.round(display / step)`; shown value = `steps * step` (a whole number in lb, a multiple of 0.5 in kg). Gain = `(newSteps − prevSteps) * step`, formatted like the value ("+5 lb", "+0.5 kg"). `Math.round` rounds half up for positive values, matching the engine's half-up rule for Epley (07.0). A kg value formats with up to 1 decimal ("137", "137.5").

### 6.5 History

`HistoryRow` keeps its layout; the badge becomes trophy + count. The count text uses `plural`-style copy ("1 PR", "6 PRs"). History never fetches records.

### 6.6 What is deliberately not done

No lead-record animation or count-up; no auto-scroll to the cards; no "share"; the chips are not links to Progress (a possible later step, since they are names only by the owner's decision).

### Decisions

- ✅ **D1 (mine) — One spec, two PRs: A (dialogs + header), then B (records + History).** *Rationale:* the two are different shapes of work (A is arithmetic and layout over data already on screen; B adds a component, a rounding rule and a dependency on Spec 07.3) and A has no dependency on 07.3. *Rejected:* one PR (the diff would mix the finish contract with the records work); separate files (more README rows for no gain; the 17.1a/b cut is described in §1.3 if wanted).

- ✅ **D3 (owner) — One card per exercise; the lead is big, others are name-only chips.**
- ✅ **D4 (owner) — Set-volume records hidden on the summary, shown in Progress.**
- ✅ **D5 (owner) — e1RM rounds to 1 lb (0.5 kg); deltas are computed after rounding.**
- ✅ **D6 (owner) — Header includes volume; the dialog leads with duration, exercises, sets; End-early spells out unlogged sets before the "can't be edited" note; the trophy plus count appears only on workouts with records.**
- ✅ **D7 (mine) — Volume is computed on the client with `sumVolumeMilli` from `@sin/core`, not added to the workout DTO.** *Rationale:* the function already defines a set's volume for both History and the engine (07.1 D4), so there is one definition and no API change; adding a field to the detail would be an API spec for a number the client can derive exactly. *Revisit* if the detail ever paginates sets.
- ✅ **D8 (mine) — The summary screen keeps its "Workout summary" heading and a neutral date line (no "Workout finished" eyebrow).** *Rationale:* the screen also opens from History; e2e and 08.0 tests key on the heading.
- ✅ **D9 (mine) — Rounding is display-only and lives in `units/format.ts`; `@sin/core` is untouched.** *Rationale:* PR math (what is a record) must stay in core; how a value is shown is presentation, like the existing kg/lb formatters.
- ✅ **D10 (mine) — Cards use `--color-pr-soft` grounds and chips a neutral surface tint; the new file joins the brass allow-list.** *Rationale:* continuity with the old records block; Earned Brass and Tint Not Outline hold. To be confirmed in the screenshots against the mockup.

### Owner decisions (2026-10-17) and accepted recommendations

The draft's seven open questions are resolved here.

- ✅ **D11 — Spec 07.3 excludes `best_set_volume` from History's `recordCount` (was O1). Owner decided 2026-10-17.** A small API-first spec (a query predicate and a doc comment; no migration, no shape change, no release step) so the History row and the summary agree (AC32). It deploys one release before Phase B. *Rationale:* one number with one meaning; a second field would live forever, and shipping with a known mismatch puts a trophy over an empty summary. *Rejected:* a new `highlightRecordCount` field; no API change plus a backlog entry. *Consequence:* 07.1's AC14 test numbers change (3 becomes 2) inside 07.3.
- ✅ **D12 — End-early and Finish keep their separate "can't be edited" sentences (was O3). Accepted as drafted 2026-10-17.** End-early uses the mockup text "Unlogged sets aren't saved. You can't edit a workout after finishing it."; Finish keeps "A finished workout can't be edited." *Rationale:* End-early has the extra fact (unlogged sets are dropped), the plain Finish dialog does not. *Rejected:* one shared sentence (loses the "not saved" warning or adds a false one to the plain Finish).
- ✅ **D13 — First-ever records still count (was O2). Owner decided 2026-10-17.** A record with `previousValue: null` counts toward the trophy count and "N new", gets a card, and is labeled "First record" in brass with no "+N" and no "was" line (AC19). *Rationale:* it is a record under 07.0 D16 and the first lift of a new exercise is worth marking; the label keeps the brass honest. *Rejected:* excluding first records from the count (would need a 07.x count change and redefine 07.0's records). *Consequence:* new lifters and new exercises will see trophies often; that is the intended behavior.
- ✅ **D14 — Stats count working sets only, in the dialogs, the header and History (was O4). Owner decided 2026-10-17.** This **changes today's Finish dialog**, which counts all logged sets including warm-ups, drop and failure sets. Copy, ACs and tests say "sets" and mean working sets (AC4, AC5), so the Finish dialog, the summary header and the History row (`workingSetCount`) show the same number. *Rationale:* the three places must agree, and History already counts working sets. *Unchanged:* the Finish button's enabling rule and `workout_finished.setCount` still count every set. *Rejected:* counting warm-ups in the dialog (disagrees with History for the same workout).
- ✅ **D15 — e1RM display rounding also applies to the Progress records list and the e1RM chart's point readout (was O5). Accepted as drafted.** So "137.08 kg" appears nowhere in the app (AC29). *Rationale:* one display rule beats two for one number. *Rejected:* summary only (the same value would read differently in two screens).
- ✅ **D16 — When rounding makes the gain 0, demote e1RM from lead; if it is alone, show the new number with no gain (was O6). Accepted as drafted.** (AC22.) *Rationale:* a "+0" or a gain that does not add up with rounded numbers is worse than silence. *Rejected:* showing "+0"; showing the exact gain beside rounded values.
- ✅ **D17 — Cards follow workout order; the lead is heaviest weight, then est. 1RM, then max reps (was O7). Accepted as drafted.** (AC17, AC25.) *Rationale:* matches the mockup and the order the lifter did the work. *Rejected:* leading with the largest relative gain.
