## 1. Purpose, scope & non-goals

Spec 10.4 turns a pasted gym class into a routine. Most imports are used once, so Spec 09.3 makes a routine saved from text a **one-off**: it sits at the top of the list, tagged, until a workout started from it is finished, and then it removes itself on the server (History keeps the workout). This spec is the UI for that: the **tag and the dates** on the list, the **note and Keep as a routine** on the preview, the **line and the Keep it in my routines checkbox** in both Finish dialogs, the **cache refresh** after a finish or a Keep, and the **one-line amendment to 10.4's Save** (send `oneOff: true`). The owner always learns before it happens: the tag on the list, the note on the preview, the line in the Finish dialog.

> **First-principles note — "cache invalidation".** The app keeps a copy of the routines list in the browser (TanStack Query) so screens open instantly. When the server removes a routine as a side effect of finishing a workout, the browser's copy is wrong until something tells it to ask again. "Invalidating" a cached query marks it stale and, if a screen is showing it, re-fetches. So the Finish success path must invalidate the routines list, or the removed one-off would still be listed until the next reload.

> **First-principles note — why the client re-sorts.** The list arrives in the server's order, but after the owner's own create, edit or Keep the app updates its copy by hand (`writeSaved`) and must put the row where the server will next put it. `sortRoutines` is that mirror. Because the server's order gains "one-offs first", the mirror must change in the same release or a freshly saved one-off would sit in the wrong place until the next refetch.

### In scope

- `routines/oneOff.ts` (pure): `isOneOff`, the expiry-day formatter, the list meta line, the preview note.
- `RoutinesSection`: tag + meta on one-off rows; `sortRoutines` and `writeSaved` follow the new order.
- `RoutinePreview`: tag, note, **Keep as a routine** (`useKeepRoutine`, `RoutineClient.keep`).
- `FinishDialogBody` + `ActiveSession` + `EndEarlyDialog`: the line and checkbox when `workout.routineIsOneOff`; `keepRoutine` on the finish request.
- Invalidation of the routines list after every finish (success and the lost-response recovery) and local cache update after Keep.
- The amendment to 10.4's Save (`oneOff: true` on every import create).
- Screenshot-harness captures, a manual phone check, docs.

### Non-goals

| Not here | Lives in |
|---|---|
| Any API, migration or expiry/removal logic | Spec 09.3 |
| A "make one-off" control, or one-off for hand-built routines | Not planned (brief non-goal) |
| Raising the 50-routine cap | Not planned |
| Changing History, the workout or the summary | Not planned (brief non-goal) |
| An undo for the removal | Not planned; the workout is in History and the text can be pasted again |
| Any editor change: the routine editor shows nothing about one-off (an edit keeps it one) | — |
| A client-side expiry timer or sweep | The server decides; the list refetches on mount |
| A request-access / product analytics event for Keep | Spec 13 reads the server's `routine_kept` / `one_off_kept` log lines |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.5 ACn — …"`**. Levels are in §10.

**List**

1. **Order and its client mirror.** The list renders in the order it is served. `sortRoutines` mirrors Spec 09.3 AC3: one-offs first (`oneOffUntil !== null`), newest `createdAt` first, then by lowercase name and id; ordinary routines after them in today's order. A table test over a mixed fixture proves the function equals the order the fixture was served in; `writeSaved` (create, replace) and the Keep cache update call it, so a fresh import appears first and a kept routine moves into the ordinary order without a refetch.
2. **Tag and meta.** Each one-off row shows the text tag **One-off** and the meta line `{routineSummary} · from text · until {Day D Mon}` — for example `6 exercises · 2 supersets · from text · until Fri 30 Oct` and, with no supersets, `6 exercises · from text · until Fri 30 Oct` (the existing `routineSummary` omits the superset part when there are none, so the template's "{M} supersets" is present only when M ≥ 1). Ordinary rows are byte-identical to today (snapshot).
3. **The date.** `{Day D Mon}` is the expiry instant `oneOffUntil` formatted in the **device's time zone**, weekday-short, day numeric, month-short, locale pinned to `en-GB` (`Fri 30 Oct`) — the same style as `formatLocalDate`, without its UTC pin (an instant, not a stored calendar date). A test pins the zone and a boundary near local midnight.
4. **Past expiry.** A one-off whose `oneOffUntil` is already past by the device clock (it can exist only while a live workout holds it, Spec 09.3 AC20) drops the date: meta `… · from text`, with no "until". "Now" is read once per list data change, not on a timer.
5. **Limit and loading unchanged.** At 50 routines (one-offs included) the limit state of 10.0 AC17 applies as today; loading, error and empty states are untouched.

**Preview**

6. **Tag and note.** A one-off's preview shows the **One-off** tag and, above the actions, the note `Leaves your routines when you finish a workout from it, or after 14 days, on {Day D Mon}. Your workout stays in History.` (the 14 comes from `ROUTINE_ONE_OFF_DAYS`; the date is AC3's). With a past expiry (AC4) the note is the reduced form (O1). An ordinary routine's preview is byte-identical to today (snapshot).
7. **Keep as a routine.** A one-off's preview shows a secondary button **Keep as a routine** beside Edit; an ordinary routine's preview shows none. Tapping it calls `POST /v1/routines/{id}/keep` (no body), is busy while pending, and a second tap sends no second request (a ref guard, as Start). On success the tag, the note and the button disappear in the same render (the caches are patched, AC8), a polite status confirms, and focus moves to the Edit link (the button it came from has unmounted). *(Amended 2026-10-23, deferred minor 47: the confirmation is announced through a polite live region (`aria-live="polite"`, no status role) that holds only the confirmation, is present and empty from first paint, and stays mounted across the Keep. The note is outside it, so a change in its wording is not announced.)*
8. **Keep's caches.** On success `onSuccess` (hook level, so it runs even if the screen unmounted) sets `oneOffUntil: null` on the list entry and the detail entry, re-sorts the list with `sortRoutines`, then invalidates `ROUTINE_KEYS.all` so the server's `updatedAt` and `ETag` replace the local patch. A `404` is not success: the preview becomes the existing "That routine no longer exists" state and the list is invalidated.
9. **Keep failures.** Offline → "You're offline — try again when connected"; `429` → the shared rate-limit text; any other failure → a form-level `InlineNotice` with the request id and a Retry, reported through `reportRoutineUnexpected("keep-routine", …)`. The one-off stays a one-off in every failure case, with its tag and note. Copy: O1. *(Amended 2026-10-23, deferred minors 51 and 53: the `429` notice shows the request id too. The Retry notice stays up while its retry is in flight, so focus stays on Retry, and success moves focus to Edit. A notice without Retry is cleared when Keep is tapped again.)*
10. **Keep and the other actions.** While a delete is in flight Keep is disabled; deleting a one-off works as for any routine (10.0 AC24, copy unchanged); Edit opens the editor as today and the saved result keeps the one-off (the `PUT` response carries `oneOffUntil`, which `writeSaved` stores; the editor itself shows nothing about one-off and `toRoutineInput` never emits `oneOff`, AC18).

**Finish dialogs**

11. **The line and checkbox.** When the active workout's `routineIsOneOff` is true, `FinishDialogBody` shows, after the stats and the unlogged-planned list and before the note, the line `'{name}' is a one-off: it leaves your routines when you finish.` ({name} is the workout's `routineName`, rendered as a text child; straight single quotes) and a native checkbox labeled **Keep it in my routines**, **unchecked**. When the flag is false (a manual workout, an ordinary routine, a routine already gone) the body is byte-identical to today (snapshot) and nothing changes in the request.
12. **Both dialogs.** The Finish dialog and End workout early both render it, through the one `FinishDialogBody`, from one piece of state in `ActiveSession`. The state is reset to unchecked **each time either dialog opens** and is not persisted anywhere.
13. **The request.** `confirmFinish` (the one finish path, which both dialogs call) sends `keepRoutine: true` iff the flag is true **and** the box is checked; otherwise the request body is exactly `{ endedAt }` as today (a deep-equality test on both dialogs and on a manual workout). The banner's Retry after a failed finish uses the state as it stands (the lifter's choice survives a failure). `useFinishWorkout`'s variables gain `keepRoutine?: boolean`; `WorkoutClient.finish` forwards it only when true.
14. **Discard and cancel change nothing.** Discard (10.1/06.1 `confirmDiscard`) issues no routine request and no routines invalidation, and the one-off is still listed afterwards with its original date. Cancel on either dialog changes nothing.
15. **Invalidation after finish.** After a successful finish **and** after the `409 workout-finished` recovery (`confirmAlreadyFinished`, the lost-response path) the routines list is invalidated (`ROUTINE_KEYS.all`), always, whatever the flag says (the recovery's refetched detail already reads `routineIsOneOff: false`, so the flag cannot gate it). It lives in `applyFinishedCaches` (`features/records/cache.ts`), which already fans a finish out to History, Progress and records, so `workouts/` imports nothing new from `routines/` (AC25). Opening Workouts afterwards shows the one-off gone, or kept and no longer tagged.
16. **A stale flag is harmless.** If the dialog was opened with the flag true but the routine was kept or deleted on another device, the finish still succeeds (Spec 09.3 AC14), and the list invalidation of AC15 shows the truth. No client code re-checks the flag at confirm time.

**Import Save (the 10.4 amendment)**

17. **Every import create is a one-off.** The Save of the import editor (10.4's `saveImport`, path `/app/workouts/routines/import/edit`) sends `POST /v1/routines` with `oneOff: true` — with pending exercises, **without** pending exercises (a text whose names all matched), and for "Open in the editor anyway" once an exercise is added. A retry after a failed create keeps it. A request-order test pins: N × `POST /v1/exercises` (N ≥ 0) then one `POST /v1/routines` whose body is `toRoutineInput(draft)` plus `oneOff: true`.
18. **Nothing else sends it.** The ordinary New routine editor's `POST`, every editor `PUT` and every other request carry no `oneOff` key (a request-capture test on each). `toRoutineInput` is unchanged and never emits the key; `oneOff` appears only in `routineClient.ts` and the import's Save (a source scan).
19. **The result is shown as a one-off.** After the import's Save the app navigates to the saved routine's preview as 10.4 does; the response is written to the caches, so the preview shows the tag, the note (AC6) and Keep, and the list (reopened) shows the routine first with the tag and meta (AC1, AC2).

**Cross-cutting**

20. **Copy is pinned.** Every string of AC2, AC6, AC7, AC11 comes from one constant/template each (`routines/messages.ts` for the list/preview, `workouts/messages.ts` for the Finish dialog) and is asserted by exact text. The strings are exactly: `One-off`; `{N} exercises · {M} supersets · from text · until {Day D Mon}`; `Leaves your routines when you finish a workout from it, or after 14 days, on {Day D Mon}. Your workout stays in History.`; `Keep as a routine`; `'{name}' is a one-off: it leaves your routines when you finish.`; `Keep it in my routines`.
21. **Strict schemas, rollout.** The web parses `oneOffUntil` and `routineIsOneOff` as required (no `.default(null)`, `.catch`; the 10.1 AC26 scan stays green); test and harness fixtures gain the fields; this spec merges only after Spec 09.3 is deployed and verified on staging (PR description + checklist).
22. **Storage, privacy, text as text.** No new `localStorage` / `sessionStorage` key (`USER_DATA_KEY_PREFIXES` unchanged); nothing user-derived reaches `track`, `reportError` or the console (spies, including the Keep failure path); the routine name in the Finish line renders as a React text child (a name containing `<img src=x onerror=…>` is text); a source scan of the files this spec adds finds no `dangerouslySetInnerHTML`, `innerHTML`, `style=` or `<style`.
23. **Observability.** No new `track` event or property (`workout_finished` keeps its props). `reportError` is called only for an unexpected non-`ApiError` failure or an unclassified Keep failure, with no user text.
24. **Accessibility and tokens.** In `a11y.test.tsx` (`describe("10.5 AC24 — …")`): the tag is text inside the row link and the preview heading region (not color alone); the checkbox is a native `input type="checkbox"` with an associated `label`, reachable and togglable by keyboard inside the dialog (ConfirmDialog still focuses Cancel first); the Keep confirmation is a `role="status"`; *(amended 2026-10-23, deferred minor 47: a polite live region, see AC7)* Keep's busy and disabled states are exposed. The one-off tag uses `--color-muted` and `--color-line` only (teal stays interactive and brass records-only: `roles.test.ts` allow-lists unchanged); every added CSS rule uses `var(--…)` and `assert:css-tokens` passes. Pixel sizes (≥ 44 px targets, 320 px layout, the dialog's scrolling with the extra block) need a browser (AC27).

|---|---|

## 6. Behavior & logic

### 6.1 `routines/oneOff.ts` (pure)

```ts
export const isOneOff = (r: Pick<Routine, "oneOffUntil">): boolean => r.oneOffUntil !== null;

const DAY = new Intl.DateTimeFormat("en-GB", { weekday: "short", day: "numeric", month: "short" }); // device zone, no timeZone pin
export const oneOffDay = (iso: string): string => DAY.format(new Date(iso));            // "Fri 30 Oct"

/** "6 exercises · 2 supersets · from text · until Fri 30 Oct"; the "until" part is dropped when expiry <= now. */
export function oneOffMeta(routine: Routine, now: number): string;
/** The preview note (AC6), or the reduced form when expiry <= now; null for an ordinary routine (amended 2026-10-23, DM-50). */
export function oneOffNote(routine: Routine, now: number): string | null;
```

`oneOffMeta` composes `routineSummary(routine)` so the singular/plural and superset rules stay in one place. The text "from text" is correct for every one-off because Spec 10.4's Save is the only creator (Spec 09.3 D13); if another creator is ever added this needs a source field.

### 6.2 The mirror of the server's order

```ts
export function sortRoutines(list: readonly Routine[]): Routine[] {
  // one-offs first, createdAt descending; then lowercase name, then id — Spec 09.3 §5
}
```

`createdAt` is the ISO string (ms precision) while the server orders on microseconds; a sub-millisecond tie falls through to name/id, and the next refetch settles any difference (the same caveat 10.0 O7 records for non-ASCII names).

### 6.3 Keep

`RoutineClient.keep(id)` is `api.request(`/v1/routines/${seg(id)}/keep`, { method: "POST" })` with **no body**, so the API client sends no `Content-Type` (Spec 09.3 AC10). `useKeepRoutine` follows the shape of `useDeleteRoutine`: `networkMode: "always"`, hook-level `onSuccess` (AC8), `404` surfaced (unlike delete, a missing routine is not success here: the routine was removed by a finish, and "Kept" would be a lie).

### 6.4 The Finish dialogs

`ActiveSession` holds `const [keepOneOff, setKeepOneOff] = useState(false)` and clears it in the two handlers that open the dialogs. It passes to both dialogs, only when `workout.routineIsOneOff`:

```ts
oneOff={workout.routineIsOneOff && workout.routineName !== null
  ? { name: workout.routineName, keep: keepOneOff, onKeepChange: setKeepOneOff }
  : undefined}
```

`confirmFinish` adds `keepRoutine: workout.routineIsOneOff && keepOneOff` to the `mutateAsync` variables; `useFinishWorkout` passes it to `client.finish(id, { endedAt, ...(keepRoutine ? { keepRoutine: true } : {}) })`. `routineName` is the snapshot taken at start, so a routine renamed during the workout shows its old name in the line (accepted: the owner knows it by the name they started).

### 6.5 Invalidation

`applyFinishedCaches(queryClient, workoutId, newRecords)` gains `void queryClient.invalidateQueries({ queryKey: ROUTINE_KEYS.all })`. Both the success path (`useFinishWorkout.onSuccess`) and the recovery path (`confirmAlreadyFinished`) already call it. An inactive routine detail query is marked stale and refetched only if a screen mounts it (a refetch of a removed routine's detail is a `404`, which the preview already handles as "gone"). `applyDeletedCaches` (deleting a finished workout) is not changed: a deletion cannot change which routines exist.

The rest of this section holds.)* `saveImport` (10.4) calls the create with `{ body: toRoutineInput(draft), oneOff: true }`; `useCreateRoutine` merges `oneOff: true` into the request body at the client (`routineClient.create(body, { oneOff })`), so `toRoutineInput` stays the one place that mints request keys and the editor `PUT` cannot send it. ## 7. Security & privacy

- **No new authority.** The calls are existing or Spec 09.3's, authenticated and scoped server-side; the client cannot choose an expiry (it sends only `oneOff: true`) or reach another user's routine.
- **Text as text.** The routine name in the Finish line and on the preview is rendered as a React text child; no HTML path (AC22).
- **No leakage.** Nothing is logged, tracked or stored beyond what exists; the Finish checkbox state lives in memory only and is cleared on each open.
- **Honest warnings.** The three warnings (tag, note, line) are the user-facing counterpart of the server's "only marked rows are ever removed": a routine the owner did not see tagged is never removed by this feature.

## 12. Decisions & open questions

Owner decisions are labeled **(owner)**; calls that are the designer's and may be refined are labeled **(mine)**.

### Resolved (owner-approved 2026-10-19, from the brief)

- ✅ **D1 — Tell the owner three times before it happens (owner).** The tag and expiry on the list, the note on the preview, the line in the Finish dialog. **Rationale:** the anti-goal is silent surprise; each is where the owner is when the question "what happens to this routine?" arises.
- ✅ **D2 — Keep in two places, never required (owner).** **Keep as a routine** on the preview; **Keep it in my routines** (unchecked) in the Finish dialog. **Rationale:** the default is the common case (a class done once); keeping is a deliberate act at the moment the owner knows they liked it.
- ✅ **D3 — Discard and start remove nothing; End workout early is a finish (owner).** Both Finish dialogs carry the line and checkbox because both end in `confirmFinish`.
- ✅ **D4 — Copy (owner).** The six strings of AC20 are the owner's wording from the mockups and the 2026-10-19 revisions (the list meta carries the expiry date, the preview note names the 14 days and the date).

### Resolved — designer's calls (mine; refine freely)

- ✅ **D5 (mine) — The client mirrors the server's order in `sortRoutines`.** The list is rendered in the served order, but `writeSaved` and Keep update the cache by hand, so the pure comparator must match. **Rejected:** invalidating and refetching after every save (an extra round trip and a flash of stale order); a shared comparator in `@sin/core` (the SQL is the authority and a comparator in core would give a false sense of a single source; Spec 09.3's integration test and AC1's table are the guard).
- ✅ **D6 (mine) — The invalidation lives in `applyFinishedCaches` and is unconditional.** `workouts/` may not import `routines/` beyond three leaf files (10.1 AC28), and `records/cache.ts` is already the finish fan-out (History, Progress, records). Gating on the flag would be wrong on the `409` recovery path (the refetched detail reads `false` once the routine is gone). The cost is one conditional `GET /v1/routines` after each finish, `304` when nothing changed. **Rejected:** a literal `["routines"]` key in `workouts/` (duplicates a key owned elsewhere); relaxing the boundary scan.
- ✅ **D7 (mine) — One state, reset on open, shared by both dialogs.** The choice is one decision about one routine; a value left over from a canceled dialog would be an invisible default, so each open starts unchecked as the brief says, and a failed finish keeps the lifter's choice for the banner's Retry.
- ✅ **D8 (mine) — The import editor always creates a one-off, with or without pending exercises.** 10.4 routes only pending-exercise saves through `saveImport`; the one-off decision belongs to "this editor was opened by an import", not to "it has new exercises", or a text whose names all matched would silently save an ordinary routine.
- ✅ **D9 (mine) — `oneOff: true` is added in `routineClient.create`, not in `toRoutineInput`.** `toRoutineInput` is shared with the editor `PUT`, and Spec 09.3 makes `PUT` reject the key; keeping it out of the shared function makes the mistake impossible rather than tested.
- ✅ **D10 (mine) — "from text" is literal for every one-off.** Correct while 10.4's Save is the only creator (Spec 09.3 D13).
- ✅ **D11 (mine) — Layout.** The tag on the name line, muted (teal is interactive, brass is records, Spec 17.0); the preview note above the actions, because it must be read before Start and is only two lines (#98); the Finish line and checkbox after the stats/unlogged list and before the dialog's own note, so the dialog's closing sentence stays last.
- ✅ **D12 (mine) — A past expiry drops the date.** Only reachable while a live workout holds the routine; "until Mon 5 Oct" on a row in the future tense would mislead. Copy: O1.

### Resolved by reading the code (corrections and qualifications to the brief)

- **`sortRoutines` mirrors the server's order** (Spec 10.0): the brief says "one-offs first" without noting that the client re-sorts after its own writes; without D5 a fresh import would land in the alphabetical position until the next refetch.
- **`workouts/` cannot import `routines/` for the key** (the 10.1 boundary scan) — D6.
- **`confirmFinish` / `useFinishWorkout` were declared "not touched" by 17.2 Phase A**; this spec touches them by one variable (AC13) and §11 amends the CLAUDE.md sentence.
- **10.4's Save has two paths** (pending exercises or none, AC31); the brief says only "10.4's Save sends `oneOff: true`" — D8 and §11 amendment 2.
- **The brief's Goal 2 text "from text, Fri 16 Oct"** is superseded by its decisions block ("from text · until {Day D Mon}").
- **A body-less `POST`** (Keep) must not send `Content-Type: application/json`: the API client only sets it with a body, so `request` is used without one (Spec 09.3 AC10).
