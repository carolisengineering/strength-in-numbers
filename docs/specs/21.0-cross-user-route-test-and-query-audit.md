## 1. Purpose, scope & non-goals

About 100 people at the owner's gym will trust the app with their training data, and the owner wants to answer "can anyone else see my workouts?" with "no" and believe it. The app is **private-only for the foreseeable future** (owner, 2026-11-05): the rule everywhere is "you see your own rows"; the only exception is shared reference data (built-in catalog exercises, muscle groups, equipment). The brief defines three independent layers; this spec is layers 1 and 2, the two that need no database change:

1. **Every route is tested against someone else's data, automatically, including routes added later.** A table-driven suite reads the route list from the app itself and fails when a `/v1` route has neither a cross-user case nor a reasoned exemption.
2. **Every SQL statement has been read and the result is written down,** in `docs/security/query-audit.md`, kept current by a check that fails when a statement is added, removed or edited without the audit changing. The statements that rely on one earlier ownership check get a direct user predicate.

Layer 3 (Postgres row-level security) is Spec 21.1.

> **First-principles note — "what a cross-user test proves".** Today every handler passes the verified user's id into a repository and every query is meant to filter on it. A bug in that chain (a forgotten `WHERE user_id = …`, an id taken from the body without an owner check) is invisible to a test that only ever uses one user: the code works, and works for everybody. A cross-user test creates two users, A and B, gives B data, then makes A's requests aim at B's data. Passing means B's data neither appears in any response nor changes. The subtle part is *how* the app says no. If a foreign id answers `403 Forbidden` and a nonexistent id answers `404 Not Found`, an attacker can learn which ids exist by trying them. The project's rule (DESIGN §5.1, the `404`-not-`403` contract) is that **another user's id is indistinguishable from an id that does not exist**; this suite tests that sentence literally, by comparing the two responses field for field.

> **First-principles note — "the `onRoute` hook".** Fastify (the HTTP framework) calls every function registered with `addHook("onRoute", fn)` once for each route as it is registered, passing the route's options (method, URL, schema, config). The app already uses this for assembly-time checks: a route without a response schema, an unpublished route, a method CORS would block, a write route without a rate-limit group all fail the *build of the app*, not a request. The same mechanism can simply *record* the routes. That gives the suite a list that is the truth about what the running app serves, rather than a hand-kept list that drifts.

### In scope

- **Phase A (layer 1):** an optional `onRoute` observer on `buildApp`; the route registry; the world fixture (users A, B and a clean actor C, each with a full data set); the case table for every `/v1` route; the exemption list; the coverage, staleness and id-slot gates; the indistinguishability, B-unchanged, A-unchanged and positive-control assertions; the leak scan.
- **Phase B (layer 2):** `docs/security/query-audit.md`; `apps/api/scripts/query-audit.ts` (`pnpm --filter @sin/api run audit:queries`) that extracts statements and writes the fingerprints; the unit test that fails on a stale audit; `repositories/ownership.ts` (shared SQL predicates); the direct user predicates for the weak spots in §6.7.

### Non-goals

- Any database change (roles, policies, columns): Spec 21.1.
- Changing any route's status code, body or headers. Where a route answers a nonexistent id with `422` or `200 []` today, it keeps doing so (§5).
- Sharing between users, visibility rules beyond "your own rows" (the social phase is not planned).
- Converting the ~34 existing cross-user tests: they stay as they are and do **not** count toward coverage (§12 D3).
- Rewriting repositories away from raw SQL.
- Proving the absence of SQL injection (the audit asserts statements are tagged-template parameterized; §7).
- Protecting against someone who holds the database owner login.

### Anti-goals (a failure even if the suite is green)

- **A suite that passes because everything answers `404`.** Every case has a positive control: the same call on A's own data succeeds (§6.4).
- **A coverage gate that can be silenced by editing a list nobody reads.** Exemptions live in the test file, one line per route with its reason; a new one is a reviewed diff (§12 D5).
- **An audit that is accurate once and then rots.** The staleness check fails the build on any textual change to a statement (§6.6, §12 D13).
- **A fix that changes behavior.** The hardening in §6.7 adds predicates; no response a client relies on changes, and the Phase A suite plus every existing test proves it.

### Fit for one work session

Two PRs at one boundary. **Phase A** (AC1–AC17) is the suite alone — tests, one small `buildApp` seam, no production behavior change — and merges first, so Phase B's SQL edits are protected by it. **Phase B** (AC18–AC31) is the audit, its check, the shared predicates and about two dozen one-line SQL edits. If the session runs out, the cut is that boundary; Phase A ships alone and is already worth having.

## 2. Acceptance criteria

Behavioral criteria are named in tests as `AC<n> — …`. Verification method in brackets; §10 maps each.

### Phase A — the cross-user route suite

1. **The registry lists exactly the app's `/v1` routes.** `buildApp` accepts an optional `onRoute` observer, registered on the root instance with the existing assembly hooks (before any route), and called with every route. The registry keeps `{method, url}` with the URL as Fastify's template (`/v1/workouts/:id`), drops the derived `HEAD` routes Fastify adds for every `GET` and the `OPTIONS` preflights, and for this commit holds exactly the 51 routes of §5. [unit]
2. **The seam is inert.** `buildApp` without the observer registers the same routes, in the same order, as with it; no handler, hook order or response changes. [unit]
3. **Coverage gate.** A registered `/v1` route that has neither a case nor an exemption fails the suite and the message names it (`METHOD url`). A case or exemption naming a route that is not registered fails ("stale entry"). A route that is both covered and exempt fails. [unit, with a fake registry; plus the live registry in integration]
4. **Non-`/v1` routes are listed too.** Routes outside `/v1` must appear on a short allow-list in the test (`/healthz`, `/readyz`, `/openapi.json`, each with a reason); an unlisted one fails. [unit]
5. **Exemptions carry reasons.** Each exemption has a non-empty reason string. For this commit the exemptions are exactly `GET /v1/_authcheck`, `GET /v1/me`, `PATCH /v1/me`, `GET /v1/muscle-groups` and `GET /v1/equipment` (reasons in §5). [unit]
6. **Id-slot coverage.** For every non-exempt route the test derives its *id slots* — every path parameter, and every key in the body and query schemas (walking objects, arrays, optional and nullable wrappers) whose name is `id` / `ids` or ends in `Id` / `Ids` (a list of ids is a slot too), plus every path parameter. Each case declares the slots it `covers`. A slot that is neither covered by a case nor on `NOT_A_SIN_ID` (idempotency keys, Hevy's own ids, with a reason each) fails the suite. [unit]
7. **The world.** Before the cases run, a fixture builds three users on real Postgres (Testcontainers): **B** (the victim) and **A** (the actor) each with a custom exercise (one active, one retired), a routine with a section, items and planned sets, a finished workout with exercises, a section with round times and a result, sets and personal records, a live workout, and Hevy pairs, section rules and a link; and **C**, an actor with no live workout and one routine, used by cases whose precondition is "no live workout". Every string B owns carries a unique marker, and B's ids are recorded. [integration]
8. **Indistinguishability.** For every case that addresses a foreign id, the suite makes the call twice as A: once with B's id in the slot, once with a freshly generated well-formed id that exists nowhere. After substituting each id string with a placeholder, the two responses are deeply equal in status, headers (excluding `x-request-id` and `date`) and body. The documented answer of §5 is also pinned (`expect` per case), so a route changing what it says for a nonexistent id fails the suite and forces §5 to be updated. [integration]
9. **B is unchanged.** Before and after every case, a snapshot of every row B owns (every table, child rows included, ordered, all columns including `updated_at`) and of the shared catalog rows is identical. [integration]
10. **A is unchanged by a rejected case.** For every case whose documented answer is a rejection (`404`, `422`), A's snapshot is identical before and after: no partial effect (for example `POST /v1/workouts` with B's `routineId` leaves A with no new workout). [integration]
11. **Positive control.** Every case has an own-data control: the same call on A's own resource returns the documented success status and, for reads, a body containing A's resource id. Controls that destroy their target (`DELETE …`, `POST …/keep`, `PUT` replace) run on a disposable resource created for the purpose. [integration]
12. **Leak scan.** No response body produced anywhere in the suite — rejections, controls and collection reads — contains any of B's ids or marker strings. [integration]
13. **Collections show A only.** With B's data present, each collection route returns A-only data: `GET /v1/exercises` (full list and a `since` delta, including B's retired custom exercise), `GET /v1/exercises/usage` (a global exercise only B logged is absent), `GET /v1/workouts` (including a `cursor` built from B's workout key), `GET /v1/routines`, `GET /v1/personal-records` (unfiltered and with each filter), `GET /v1/hevy/status` and `GET /v1/hevy/mapping` (counts and pairs are A's), and `GET /v1/account/export`. [integration]
14. **Key collisions never replay or conflict across users.** A creating a workout with B's `clientGeneratedId`, a set with a key B used on another workout exercise, a routine with B's name, an exercise with B's name, and a Hevy pair with a template id B also holds, each succeeds as a new row of A's (never a replay of B's row, never a `409` that reveals B's). [integration]
15. **`HEAD` agrees with `GET`.** For every `GET` case with a path id, a `HEAD` with B's id and a `HEAD` with a nonexistent id return the same status. [integration]
16. **The Hevy routes are tested as an allow-listed user.** The world adds A to `HEVY_ENABLED_USER_IDS`; the gate itself stays Spec 19.0's. [integration]
17. **The suite is reusable on another database login.** The case runner takes its database handle (`makeCrossUserApp(db)`) as a parameter and builds every repository from it; it reads nothing from a module-level `db`. (21.1 passes the restricted login.) [unit/review]

### Phase B — the query audit and the weak-spot fixes

18. **The audit exists and is complete.** `docs/security/query-audit.md` has one row for every SQL statement in `apps/api/src`: a stable key, file and function, a one-line description, a category (§6.5), the check or anchor it relies on (for the *anchored* category), and a fingerprint. [unit]
19. **Extraction is syntactic and total.** Statements are extracted from the TypeScript AST: tagged templates whose tag is `$queryRaw`, `$executeRaw` or `Prisma.sql`, and `$queryRaw(…)` / `$executeRaw(…)` calls whose argument is a `Prisma.sql` value. `$queryRawUnsafe`, `$executeRawUnsafe` and `Prisma.raw` in `apps/api/src` fail the test unless the call site is on a justified allow-list (empty at this commit). [unit]
20. **Staleness.** The fingerprint is a hash of the statement's normalized text (whitespace collapsed, every `${…}` replaced by `?`). The test fails when a statement exists in code with no matching row, when a row has no statement in code, or when a statement's text changed; the message names the file, the function and the instruction `pnpm --filter @sin/api run audit:queries --write`, which rewrites fingerprints, keeps classifications and marks changed rows `needs review` — the test also fails while any row says `needs review`. [unit]
21. **Category sanity.** A row marked *user-filtered* must contain a user predicate (the token `user_id` or `owner_user_id`, or a call of an `ownership.ts` helper); *shared on purpose* may touch only `muscle_group`, `equipment`, the catalog (`owner_user_id IS NULL`) reads and no table at all (§6.6); *cross-user maintenance* must be in `account/purge.ts`, `records/rebuild.ts`, `seed/catalog.ts`; *anchored* must name an anchor row that exists in the audit; no row is uncategorized. [unit]
22. **Shared predicates.** `repositories/ownership.ts` exports one SQL fragment per owned table that has no `user_id` today (`workout_exercise`, `set_entry`, `workout_planned_set`, `workout_section`, `workout_section_round`, `routine_item`, `routine_item_set`, `routine_section`); each takes the acting user id and the row reference and expands to an `EXISTS` through the parent chain to the root table's `user_id`. [unit, SQL against Postgres]
23. **The replay lookup is user-filtered.** `findSetByClientGeneratedId` (`set-entry.prisma.ts:117`) matches only sets whose workout belongs to the acting user: called with B's workout exercise id and B's key as user A, it returns nothing. [integration]
24. **Every fixed statement is exercised directly with another owner's id.** For each statement changed under §6.7 a repository-level test calls the exported function with a mismatched (user, id) pair and shows it matches or changes nothing. [integration]
25. **The anchor statements are user-filtered.** `lockedWorkoutSpan`, `lockWorkoutStructure` and the section envelope's workout lock take the acting user id and filter on it; a call with another user's workout id finds no row. [integration]
26. **No behavior change.** The Phase A suite, every existing unit and integration test and the OpenAPI drift check pass unchanged; no response status or body differs. [integration, CI]
27. **No latency regression.** `bench:finish`, `bench:history`, `bench:progress`, `bench:exercise-usage` and `bench:hevy-import` rerun after Phase B; none regresses its figure recorded in its spec by more than 10%. Figures are recorded in §12. [manual]
28. **The audit script is wired.** `audit:queries` (check) and `audit:queries --write` exist in `apps/api/package.json`; the check runs in the existing unit job. [CI-pipeline]
29. **The convention is written down.** `CLAUDE.md` (root) gains the one-line rule "a new SQL statement needs an audit row — run `audit:queries --write`, classify it, and `needs review` fails CI", and the `docs/` map lists `docs/security/query-audit.md`. [review]
30. **Maintenance scope is explicit.** `apps/api/scripts/*.ts` (benches, smoke, dev tools) are not in the audit; a test fails if any file under `apps/api/src` imports from `apps/api/scripts`. [unit]
31. **The audit answers the owner's question.** The audit's header states, in plain words, how many statements are in each category and lists every *anchored* statement with its anchor, so a reader can see exactly which statements rely on an earlier check. [review]

## 4. Data model

No database change. This spec reads the schema only. For orientation, the ownership paths the helpers and the audit use (a row "belongs to" the user at the end of the arrow):

| Table | Reaches `user_id` through |
|---|---|
| `workout`, `routine`, `personal_record`, `hevy_exercise_pair`, `hevy_section_rule`, `hevy_link`, `hevy_account` | own `user_id` column |
| `exercise` | `owner_user_id` (NULL = shared catalog row) |
| `workout_exercise`, `workout_section` | `workout` |
| `set_entry`, `workout_planned_set` | `workout_exercise` → `workout` |
| `workout_section_round` | `workout_section` → `workout` |
| `routine_item`, `routine_section` | `routine` |
| `routine_item_set` | `routine_item` → `routine` |
| `muscle_group`, `equipment` | none (shared reference data) |

Cross-links that point at another table (`workout_exercise.exercise_id`, `routine_item.exercise_id`, `personal_record.exercise_id`, `hevy_exercise_pair.exercise_id`, `workout.routine_id`, `hevy_link.workout_id`) are *not* ownership paths: the database does not stop them pointing at another owner's row; only app checks do, and §5's body-id cases test those checks.

## 6. Behavior & logic

### 6.1 The registry (AC1–AC5)

`buildApp` gains an optional dependency `onRoute?: (route: RouteOptions) => void`, registered with `app.addHook("onRoute", …)` next to the existing assembly checks (`app.ts` ~169) so it sees every route, including those in encapsulated child scopes (the hook is inherited by plugins registered after it). The test passes a function that pushes `{ method, url }` for each route. The URL is Fastify's *prefixed template* (`/v1/workouts/:id`). The registry drops `HEAD` (Fastify's automatic twin of each `GET`) and `OPTIONS` (CORS preflights); `HEAD` is still exercised by AC15.

The route key is `` `${METHOD} ${url}` ``. The coverage gate is three set comparisons: registered − (cases ∪ exemptions) must be empty; (cases ∪ exemptions) − registered must be empty; cases ∩ exemptions must be empty.

### 6.2 The world (AC7)

A, B and C are real users created through the app's provisioning path (a request with a fake token) so the rows are the ones production creates, then given data through the routes too (D11): records by finishing a workout, Hevy rows by the mapping, link and import routes. Only the two built-in exercises are SQL fixtures (`insertExercise`), since no route creates catalog rows. B's strings carry markers (`B-SECRET-<kind>-<n>`); B's ids are collected into `world.b.ids` so the leak scan (AC12) can search for them. A has the same shape as B so every positive control has something to hit.

Order does not matter: a correct app changes nothing on a rejected call, so cases run sequentially on one world (AC9 and AC10 fail the first case that breaks this). Destructive controls use disposable resources (AC11).

### 6.3 Indistinguishability (AC8)

```
slot S in route R, actor A, victim id Vb, fresh id Vn (a well-formed UUIDv7 nowhere in the DB)
resp_b = call(R, S := Vb); resp_n = call(R, S := Vn)
normalize(resp): replace every occurrence of Vb / Vn / any other id in the response with "<ID>"
assert  resp_b.status == resp_n.status
        headers(resp_b) \ {x-request-id, date} == headers(resp_n) \ {x-request-id, date}
        normalize(resp_b.body) == normalize(resp_n.body)      # field for field
        resp_b.status == case.expect                            # pinned to §5
```

Where the id appears in the response (`instance`, a detail string), the normalization makes the comparison about *shape*; it is not allowed to hide a difference in the words of `title` / `detail` / field-error paths and messages. For routes whose slot is a body id, the rest of the request is identical and valid, so the only difference between the two calls is the id.

### 6.4 Controls, snapshots and the leak scan (AC9–AC12)

`snapshot(db, userId)` returns canonical JSON of every row the user owns (the ownership table in §4, children included) plus the global catalog rows; it is taken before and after each case and compared with `deepStrictEqual`. The own-data control for a case is the same request with A's equivalent id (for example `GET /v1/workouts/:id` with A's finished workout) expecting the success status in the case; if the app wrongly answered `404` to everything, controls fail. The leak scan walks every response body ever produced by the run and asserts it contains none of `world.b.ids` or `world.b.markers`.

### 6.5 Id slots (AC6)

The test derives slots from the Zod schemas on the route. A path parameter is always a slot (every path param in this API is a row id or an integer; `:round` is on a declared `NOT_A_SIN_ID` list because it is an integer). In body and query schemas, a key named `id` / `ids` or ending in `Id` / `Ids` is a slot, found by walking objects, arrays, optionals and nullables (Zod 4 exposes `def.shape`, `def.element`, `def.innerType`). `NOT_A_SIN_ID` lists the keys that look like ids but are not another row of ours, with a reason each: `clientGeneratedId` (the caller's idempotency key; scope is the caller or the parent they own — cases in AC14 cover collisions), `hevyTemplateId` and `hevyWorkoutId` (Hevy's namespace; scoped by `user_id` in every Hevy table), `sourceExerciseId` (response-only), the shared reference ids `primaryMuscleId`, `secondaryMuscleIds` and `equipmentId` (row 9), and Hevy's `exerciseTemplateId` and `supersetId` inside an import (row 50). Adding a route with a new `fooId` body field that nobody covered fails the suite, which is what makes "every id a route accepts" mechanical.

### 6.6 The audit and its staleness check (AC18–AC21)

**Categories** (every statement gets exactly one):

| Category | Meaning | Machine check |
|---|---|---|
| **user-filtered** | The statement itself carries a user predicate: `user_id = $acting`, `owner_user_id IS NULL OR owner_user_id = $acting`, `id = $acting` on `"user"`, an `ownership.ts` helper, or an `INSERT` that writes the acting user's id. | contains `user_id` / `owner_user_id` or a helper call |
| **anchored** (by id after an owner check) | Keyed by an id, with no user predicate, but safe because of a named *anchor*: a user-filtered **locking** statement (`FOR UPDATE` / `FOR SHARE`) on the root row, earlier in the **same transaction**, and the statement's key is that row's id or a column tied to it (`workout_id = $anchor`, `routine_id = $anchor`, `workout_section_id` of a locked section). The row names the anchor. | anchor key exists in the audit and is user-filtered; same function |
| **shared on purpose** | Reads of `muscle_group` and `equipment`, the catalog branch of `exercise` (`owner_user_id IS NULL`), and statements that read no table at all (`SELECT 1`, `pg_advisory_xact_lock`, `SET TRANSACTION …`, `SET CONSTRAINTS …`, `transaction_timestamp()`). | table names only (none, for the no-table kind) |
| **cross-user maintenance** | Scripts that act on many users: `account/purge.ts`, `records/rebuild.ts`, `seed/catalog.ts`. They run on the owner login (21.1). | file allow-list |
| **fragment** | A `Prisma.sql` piece composed into other statements (`SET_ENTRY_COLUMNS`, `ROUTINE_WITH_ITEMS`); classified through its callers, which are listed. | callers listed |

The rule that separates *anchored* from "weak spot": **a statement may rely on an earlier owner check only if the check and the statement run in the same transaction and the check locked the row it established ownership of.** An unlocked, separate, earlier statement (a bare preflight) does not qualify: its answer can be stale by the time the statement runs, and the dependence is invisible when the statement is read on its own. Everything else gets a direct predicate (§6.7).

**Staleness mechanism (decided).** An AST-based fingerprint per statement. Rejected alternatives: a **per-file statement count** (the brief's example) — it notices a statement added or removed but not one *edited*, and deleting `AND user_id = …` from a `WHERE` is exactly the edit that matters; a **line-number index** — rots on every unrelated edit; a **hand-kept list** — what the audit is meant to replace. The fingerprint costs one failing test and one command (`audit:queries --write`) whenever SQL changes, and that small friction *is* the review: a changed statement is flagged `needs review` and cannot merge until a human sets its category. `needs review` is a third state the script writes and the test refuses.

## 7. Security & privacy

- **The suite and the audit are the security artifact;** nothing here widens access. The suite uses fake users and fake tokens; no real account, secret or health value is involved.
- **`docs/security/query-audit.md` contains SQL text with placeholders, never values,** and no secret. It is safe to commit.
- **A test-only seam.** The `onRoute` observer exposes route metadata, not data; it is unset in `main.ts`. A reviewer can confirm by the AC2 test and by grep.
- **Static messages.** Nothing here adds a validation message; the pinned answers in §5 are existing static texts (CLAUDE.md "Validation messages are static").
- **What layer 2 does not claim.** The audit asserts every statement is a parameterized tagged template and classifies its ownership predicate; it does not prove the absence of logic bugs in how a predicate is written, which is why layers 1 and 3 exist. A user-filtered statement with a wrong predicate is caught by layer 1 only if a case reaches it.
- **Ids in responses.** The leak scan treats B's ids appearing in any A response as a failure, including ids inside lists, links and `instance` fields.

## 11. Deployment & rollback

- **No migration, no config, no release step.** Phase A is test code plus one inert optional parameter; Phase B edits SQL predicates (additive `AND …`) and adds a document and a script. Both ship with the normal merge-to-`main` staging deploy; the staging post-deploy smoke is unchanged.
- **Rollback:** revert the PR. Because the SQL edits only narrow statements to rows the preceding check already established, a revert returns the previous behavior exactly.
- **Order:** Phase A first (so Phase B's edits are protected by it), then Phase B. Spec 21.1 starts after both.
- **After deploy (Phase B):** nothing to run by hand. The bench figures (AC27) are recorded from a local Docker run, not from staging.
