## 1. Purpose, scope & non-goals

A lifter wants a routine to say exactly what to lift, set by set — including ramps and warm-ups ("60 × 10, 80 × 8, 100 × 6") — and the session to fill that in so logging is one tap. Spec 09 can only say "4 sets of 6–8" per exercise, with no weight. This spec adds the **data and the API**: a routine item owns an ordered list of **planned sets** (type, rep range, weight with its unit); starting a workout from the routine **snapshots** those rows onto the workout's exercises; both are returned on the existing read routes. Spec 10.2 is the UI (the editor's weight field and "Plan each set", the session's prefill and "Set 3 of 4").

> **First-principles note — "derived columns".** A *derived column* is a value the database stores that is always computable from other stored data. Here `routine_item.target_sets` (a count) and `target_reps_low` / `target_reps_high` (min / max) can be computed from the item's planned-set rows. We keep them because other readers (Spec 10.1's target line, every started workout's snapshot) already use them and expand-only migrations forbid dropping a column in the release that stops writing it. The rule that keeps two copies of a fact honest is: **one is the source, the other is written only by the code that writes the source, in the same transaction.** The rows are the source; the server recomputes the columns on every write, so a client can never send them out of step with the rows.

> **First-principles note — "legacy-input expansion".** Today's web client (Spec 10.0) sends an item as `{ targetSets: 4, targetRepsLow: 6, targetRepsHigh: 8 }`. After this spec the server stores *rows*, so it **expands** those three fields into four identical `working` rows before writing. The client does not change in this release, which is what makes the rollout safe: the API can ship, and be verified, before any client knows rows exist.

### In scope

- Migration `0010_create_planned_sets`: tables `routine_item_set` and `workout_planned_set`; a **backfill** of existing routine items.
- `@sin/core`: `dto/planned-set.ts` (`PlannedSetSchema`, `PlannedSetInputSchema`, caps), pure `plannedSets.ts` (`expandQuickLine`, `deriveTargets`, `plannedSetViolations`, `isUniformWorking`).
- Routine routes: `RoutineItem` gains `sets`; `RoutineItemInput` accepts `sets` **or** the legacy quick fields; the server derives the item's `target*` columns from the rows (§6.2).
- `POST /v1/workouts { routineId }` copies the rows to `workout_planned_set` (§6.4).
- Workout reads: `WorkoutExercise` gains `plannedSets` (detail, active, add, patch).
- A route-level body limit for routine writes (§6.6).

### Non-goals

- **UI** (Spec 10.2). **No client reads `sets` / `plannedSets` until 10.2** (DESIGN §6 rollout convention).
- **Planned duration / distance** for timed and distance exercises (rows carry only a set type for them in v1; FI-11).
- **Per-set RPE** (the item-level `targetRpe` stays, in both input forms), automatic progression ("+2.5 kg next time"), planned rest per set.
- **Editing the plan inside a session.** `workout_planned_set` is a snapshot written only by the start copy; there is no write route (§5).
- **Matching logged sets to planned rows** by type or value (Spec 10.2's index rule is the whole mapping).
- **A weight-in-kg generated column** on the plan tables: nothing compares or aggregates planned weights (PRs and volume read `set_entry` only), so the §4.8 canonical column would be dead weight.
- **Backfilling planned rows for existing workouts.** Their targets still display; they simply have no rows (`plannedSets: []`).
- **Dropping `target_sets` / `target_reps_*`** (a later contract step, if ever).

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("AC7 — …")`, the Spec 09 convention). Infra / pipeline criteria are verified by CI or review (§10).

**Shapes and reads**

1. **Contract.** `RoutineItem` (response) gains `sets: PlannedSet[]` and `WorkoutExercise` (response) gains `plannedSets: PlannedSet[]`; both are **required, never null, always an array** in `@sin/core` (no `.default`, no `.optional()` — Spec 10.1 D4). `PlannedSet` is exactly `{ setType, repsLow, repsHigh, weight, weightUnit }` — `setType` one of `warmup | working | drop | failure`, the rest nullable numbers / `kg | lb`; it carries **no id and no position** (array order is the order). The five routine routes remain published in `/openapi.json` with the new schemas; `401` behavior is unchanged.
2. **Ordered, atomic reads.** Every routine read (list, get-one, and the `POST` / `PUT` responses) returns each item's `sets` ordered by position, from the **same single statement** that reads the routine header and items (§6.5) — extending Spec 09 AC14: a concurrent `PUT` can never produce a read with the old items and new rows, or the reverse. The strong `ETag` hashes the new bytes: a change to one row's weight changes the validator; an unchanged routine keeps it; the first conditional `GET` after the deploy answers `200` (the bytes gained `sets`), not `304`.

**Routine writes**

3. **Row form.** `POST` / `PUT` accept per item `sets: PlannedSetInput[]` (0–20 rows). The rows are stored in array order (`position` = index, never sent); an omitted `setType` is `working`; `repsLow` / `repsHigh` / `weight` / `weightUnit` may each be omitted or `null`. `sets: []` is a valid **no plan** item (zero rows). The response echoes exactly what was stored (the round trip is byte-stable except item ids, Spec 09 AC13).
4. **Row validation matrix.** Per row, strict (unknown key → `422`), paths `items.<i>.sets.<j>.<field>`: `setType` in the four values; `repsLow` / `repsHigh` ints 1–100, **both or neither**, `low ≤ high` (equal allowed); `weight` a number `0 … SET_WEIGHT_MAX` (9 999.999); `weightUnit` present **iff** `weight` is present (a weight without a unit → `422` on `weightUnit`; a unit without a weight → `422` on `weight`); more than **20** rows → `422` on `items.<i>.sets`; `sets: null` → `422`. All issues are collected in one `422`, like Spec 09 §6.2 step 2.
5. **Modality rules.** After the exercise lookup (§6.1): for `weight_reps` and `weighted_bodyweight` a row may plan reps and weight; for `bodyweight_reps` a row may plan reps but a `weight` / `weightUnit` is `422` on `items.<i>.sets.<j>.weight`; for `duration` and `distance_duration` a row carries only `setType` — a `repsLow` / `repsHigh` / `weight` / `weightUnit` is `422` on that row's field. A row that is only a set type is valid on every modality. These rules apply to the **row form only** (D5): legacy input is exempt. Order: absent / invisible exercise `422` → retired `409` → modality `422` (first the visibility and retired checks of Spec 09 AC8, then this).
6. **Legacy expansion.** An item that sends none of `sets` but any of `targetSets` / `targetRepsLow` / `targetRepsHigh` (Spec 09's fields, validated exactly as Spec 09 AC9) is expanded: `targetSets = N` → **N identical `working` rows** carrying the rep range (and no weight); `targetSets` null / absent with a rep range and `N` absent → **zero rows, the rep range stored as sent** (O1 default; §6.2); all three null / absent → zero rows. `targetRpe`, `restSeconds`, `supersetGroup`, `notes` are item-level and identical in both forms (RPE still converts to tenths in exactly one place, `rpeToTenths`).
7. **One form per item.** An item that has the key `sets` **and** any of the keys `targetSets`, `targetRepsLow`, `targetRepsHigh` — even with `null` values — is `422` on `items.<i>.sets` ("send either sets or the quick-line fields"). Presence of the key, not its value, decides (today's client always sends all three keys as `null` and never sends `sets`).
8. **Derived columns.** After every write path (row form, legacy form, `POST`, `PUT`, and the backfill), for each item with ≥1 row: `target_sets` = the row count; `target_reps_low` = the minimum `reps_low` and `target_reps_high` = the maximum `reps_high` over the rows that have reps, or both `NULL` when no row has reps. For an item with no rows: `target_sets IS NULL` and the rep columns hold only what a legacy-form write sent (AC6), `NULL` for the row form. A ramp `10 / 8 / 6` stores `target_sets 3`, `6 … 10`. An integration helper `assertDerivedColumnsConsistent(db)` checks this over every routine item and every `workout_exercise` that has planned rows, and is called at the end of each write-path test.
9. **Whole replace still replaces.** A `PUT` replaces the item list **and its rows** in one transaction (rows are deleted by the item cascade and re-inserted under the new item ids); no row from the previous document survives; a `PUT` that fails (`422`, `409`) leaves the routine, its items and its rows exactly as they were (Spec 09 AC13 extended to rows).
10. **Spec 09's rules are unchanged.** Name rules, limits (50 / 30 / 8), RPE half steps, superset density, `exercise-retired`, last-write-wins, delete and the authorization boundary (Spec 09 AC5–AC15, AC28) pass **unmodified** apart from additive `sets` assertions in the shape checks.
11. **Body size.** `POST` / `PUT /v1/routines` carry a route-level `bodyLimit` of 128 KiB (§6.6); a legal maximum document (30 items × 20 rows, 500-character item notes, 2 000-character routine notes — about 74 KB) is accepted, and a body over the route limit answers the existing `413` problem+json. The global 64 KiB limit is unchanged for every other route.

**Start from a routine and workout reads**

12. **Start copies the rows.** `POST /v1/workouts { routineId }` copies each item's rows to `workout_planned_set` in the same transaction, after the `workout_exercise` insert and under the same `FOR SHARE` on the routine: every field verbatim (`setType`, reps, weight, **unit**), `position` preserved, attached to the `workout_exercise` created from that item (matched on position — correct for a routine that lists one exercise twice, where each copy gets its own item's rows). An item with no rows copies none. No `set_entry` is created.
13. **The workout stays self-contained.** After a start, editing, replacing or deleting the routine changes nothing in the workout's `plannedSets` (Spec 09 AC21 extended). There is no route that writes `workout_planned_set`; removing a workout exercise or the workout deletes its rows (cascade).
14. **Replay and atomicity.** An idempotent replay of the start returns the stored workout and **never re-reads the routine or copies rows again** (Spec 09 AC18 / AC33 hold, tested after the routine was replaced and deleted); a failed start (`404`, `409 exercise-retired`, `409 workout-in-progress-exists`) leaves no `workout` and no `workout_planned_set` rows. The `workout_exercise` target snapshot columns are copied verbatim from the (already derived) item columns; for a started workout with rows, `assertDerivedColumnsConsistent` holds.
15. **Workout read shapes.** `GET /v1/workouts/{id}`, `GET /v1/workouts/active`, `POST /v1/workouts/{id}/exercises` (`201`) and `PATCH /v1/workout-exercises/{id}` (`200`) return `plannedSets` ordered by position: the copied rows for a routine-started exercise, `[]` for a manually added exercise and for every workout started before `0010`. Reordering exercises (`PATCH position`) or changing `supersetGroup` never changes or detaches a row.
16. **Logging and records are indifferent.** A routine-started workout creates no `set_entry`; the finish integrity rule (Spec 05.1) and the PR engine (Spec 07.0, including `records:rebuild`) read `set_entry` only and produce identical results with and without planned rows; a workout whose planned sets were never logged finishes normally.

**Migration**

17. **Migration `0010`.** Additive only; applies cleanly over `0001–0009` with existing data untouched. The database itself rejects (raw SQL insert) on each plan table: an unknown `set_type`, a `position` outside 0–19, a duplicate `(parent, position)`, reps with one bound, `low > high`, reps outside 1–100, a negative weight, a weight without a unit and a unit without a weight, a unit other than `kg` / `lb`; deleting a `routine_item` / `workout_exercise` cascades its rows.
18. **Backfill.** On a database holding routines written before `0010`: every `routine_item` with `target_sets = N` gains **N `working` rows** carrying the item's rep range (or none) and no weight; an item with `target_sets IS NULL` gains none and **keeps its rep columns untouched**; no `workout_planned_set` row is created for any existing workout; no existing column value changes. `assertDerivedColumnsConsistent` holds immediately after the migration.
19. **Backfill is re-runnable.** The backfill statement is guarded (`WHERE NOT EXISTS` a row for the item); running it a second time inserts nothing, and running it after a pre-`0010` code `PUT` has re-created items without rows (the rollout window, §11) restores exactly those items' rows.
20. **No-drift check moves.** `prisma migrate diff` (migrated database → `schema.prisma`) reports no difference beyond the two generated `set_entry` columns, asserted in `0010`'s integration test; `routine-migration.integration.test.ts` keeps its `0009` constraint checks but no longer carries the whole-schema diff (CLAUDE.md: it lives in the newest migration's test).
21. **Account purge.** `DELETE FROM "user"` cascades both new tables in one statement (via `routine_item` and `workout_exercise`); the purge fixtures contain at least one row in each (so Spec 11 AC23's "every discovered table had victim rows" guard stays green — §3).

**Cross-cutting**

22. **Today's client keeps working.** A recorded set of request bodies produced by the Spec 10.0 editor (`toRoutineInput`: all five target keys sent as numbers or `null`, never `sets`) replays against the new API with the same status codes as before, and a `GET` read-back of the targets equals what the pre-change API returned for the same body (reps-only and sets-only items included). The existing 10.0 / 10.1 web suites pass with edits limited to fixtures that gain `sets` / `plannedSets`.
23. **Pure helpers.** `@sin/core` `plannedSets.ts` (no I/O, no imports beyond core siblings; `core:purity` green) exports `expandQuickLine`, `deriveTargets`, `plannedSetViolations(modality, rows)` and `isUniformWorking(rows)` with the behavior of §5 / §6; the API uses them for AC5, AC6 and AC8 and Spec 10.2 reuses them, so server and editor cannot disagree.
24. **Strict schemas stay strict.** Core tests pin that a `RoutineItem` without `sets` and a `WorkoutExercise` without `plannedSets` fail `safeParse`; no `.default([])` / `.catch` anywhere in `@sin/core` or `apps/web` for these fields (a source scan).
25. **Error contract, OpenAPI, rate limits.** No new error slug and no new route; the new `422` paths use the existing `validation-error`; `/openapi.json` is regenerated (CI drift check green) and the `contract-pipeline` / problem-matrix tests need no row change; routine writes stay in the `routines` write group; `RATE_LIMITS` is unchanged.
26. **Logging hygiene.** `routine_created` / `routine_updated` gain `planned_set_count`, `workout_started_from_routine` gains `planned_set_count` — counts only; no weight, rep value, name or note appears in any captured line (Spec 09 AC30 extends).
27. **Worst-case read is bounded.** A fixture at the product maximum (50 routines × 30 items × 20 rows = 30 000 rows) is returned by `GET /v1/routines` in **one** database statement and under a loose time bound (a CI tripwire, not a benchmark; the bound is set at implementation from a local run, ×5).
28. **Spec 11 interaction.** The new fields flow through the shared Record → DTO mappers, so Spec 11's export carries them with no export-specific code; whichever of 09.1 and Spec 11 merges second updates the export fixtures and the purge fixtures (AC21), and Spec 11's parity AC (export deep-equals the read routes) is the proof.
29. **Docs and release order.** DESIGN.md §4.3 / §4.4 / §4.8 / §4.9 / §6 / §9 / Q20 and the README rows match this spec (§11 list); the release order of §11 (migration `0010` before the code; API before Spec 10.2) is stated in the PR description and the runbook note.

## 4. Data model

Migration `apps/api/prisma/migrations/0010_create_planned_sets/migration.sql`, hand-authored like `0009` (CHECKs and unique indexes carry the contract; `schema.prisma` gains `RoutineItemSet` and `WorkoutPlannedSet` models with back-relations on `RoutineItem` and `WorkoutExercise`, and the CI `prisma migrate diff` check is the guard — AC20). Additive / expand-only: no existing column is dropped, renamed or retyped, and the backfill only inserts into the new table.

```sql
-- Spec 09.1 §4 — 0010_create_planned_sets. Additive, expand-only.
-- Down (dev/test teardown only; production undo is `git revert` + a forward migration):
--   DROP TABLE "workout_planned_set", "routine_item_set";

CREATE TABLE "routine_item_set" (
    "id"              UUID           NOT NULL,
    "routine_item_id" UUID           NOT NULL,
    "position"        SMALLINT       NOT NULL,
    "set_type"        TEXT           NOT NULL DEFAULT 'working',
    "reps_low"        SMALLINT,
    "reps_high"       SMALLINT,
    "weight"          NUMERIC(7,3),
    "weight_unit"     TEXT,
    "created_at"      TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    "updated_at"      TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    CONSTRAINT "routine_item_set_pkey" PRIMARY KEY ("id"),
    CONSTRAINT "routine_item_set_item_fkey" FOREIGN KEY ("routine_item_id") REFERENCES "routine_item"("id") ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT "routine_item_set_position_check" CHECK ("position" BETWEEN 0 AND 19),
    CONSTRAINT "routine_item_set_type_check" CHECK ("set_type" IN ('warmup', 'working', 'drop', 'failure')),
    CONSTRAINT "routine_item_set_reps_check" CHECK (
        (("reps_low" IS NULL) = ("reps_high" IS NULL))
        AND ("reps_low" IS NULL OR ("reps_low" BETWEEN 1 AND 100
                                    AND "reps_high" BETWEEN 1 AND 100
                                    AND "reps_low" <= "reps_high"))),
    CONSTRAINT "routine_item_set_weight_check" CHECK (
        (("weight" IS NULL) = ("weight_unit" IS NULL))
        AND ("weight" IS NULL OR "weight" >= 0)
        AND ("weight_unit" IS NULL OR "weight_unit" IN ('kg', 'lb')))
);
-- Not deferrable: PUT deletes an item (cascading its rows) before re-inserting (Spec 09 §6.3).
-- Also the FK lookup index, and with the position CHECK it caps a parent at 20 rows.
CREATE UNIQUE INDEX "routine_item_set_item_position_key" ON "routine_item_set" ("routine_item_id", "position");

CREATE TABLE "workout_planned_set" (
    "id"                  UUID           NOT NULL,
    "workout_exercise_id" UUID           NOT NULL,
    "position"            SMALLINT       NOT NULL,
    "set_type"            TEXT           NOT NULL DEFAULT 'working',
    "reps_low"            SMALLINT,
    "reps_high"           SMALLINT,
    "weight"              NUMERIC(7,3),
    "weight_unit"         TEXT,
    "created_at"          TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    "updated_at"          TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    CONSTRAINT "workout_planned_set_pkey" PRIMARY KEY ("id"),
    CONSTRAINT "workout_planned_set_exercise_fkey" FOREIGN KEY ("workout_exercise_id") REFERENCES "workout_exercise"("id") ON DELETE CASCADE ON UPDATE CASCADE,
    -- the same four CHECKs, named workout_planned_set_{position,type,reps,weight}_check
);
CREATE UNIQUE INDEX "workout_planned_set_exercise_position_key" ON "workout_planned_set" ("workout_exercise_id", "position");

-- Backfill (AC18, AC19): N identical working rows per item that has a set count.
-- Items with target_sets NULL get none and keep their rep columns (O1). Guarded so it can be re-run.
INSERT INTO "routine_item_set" ("id", "routine_item_id", "position", "set_type", "reps_low", "reps_high")
SELECT gen_random_uuid(), ri."id", g.n, 'working', ri."target_reps_low", ri."target_reps_high"
FROM "routine_item" ri
CROSS JOIN LATERAL generate_series(0, ri."target_sets" - 1) AS g(n)
WHERE ri."target_sets" IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM "routine_item_set" s WHERE s."routine_item_id" = ri."id");
```

Notes:

- **Columns are the brief's, plus `created_at` / `updated_at`** because DESIGN §4.0 says every table carries them. They are informational on these tables (rows are never updated in place: a routine's rows are replaced with the item, a workout's are a snapshot) — D7.
- **`set_type` is `TEXT` + `CHECK`**, like `set_entry.set_type` (0006), not a Postgres enum: widening a `CHECK` list is additive; altering an enum is not.
- **`weight NUMERIC(7,3)`** matches `set_entry.weight` (so the same `SET_WEIGHT_MAX` bound is a 422 here rather than a numeric-overflow 500). The unit is stored exactly as typed (DESIGN §4.8); a later change of the profile's `unit_preference` never rewrites a plan.
- **The position `CHECK` (0–19) plus the unique index is the DB-level 20-row cap** — the same defense-in-depth as Spec 09's target `CHECK`s.
- **ids:** the application inserts rows with `uuidv7()` ids (as everywhere); the two SQL-side writers — the backfill and the start copy (§6.4) — use `gen_random_uuid()` because the production Postgres (16) has no `uuidv7()`. v4 ids on a child table that is always read through its parent's index cost nothing; D6.
- **No new index beyond the unique ones.** Every read is "all rows of this parent", served by `(parent, position)`.
- **The `0010` lock profile** is two `CREATE TABLE`s and one `INSERT … SELECT` into the new table; `routine_item` is only read, so routine writes are not blocked.
- **Hard purge:** both tables cascade from their parents (`routine_item` ← `routine` ← `user`; `workout_exercise` ← `workout` ← `user`) — no purge-ordering step (AC21).
- **Derived columns** stay on `routine_item` and `workout_exercise` unchanged (no new CHECK relates them to the rows; a CHECK cannot span tables, so the invariant is enforced by the single write path and AC8's helper).

No new routes; every change is an additive field or an accepted input form on existing routes. Publication, `problems`, `writeGroup`, caching: all as in Spec 09 §5.

## 6. Behavior & logic

### 6.1 Validation order (POST / PUT; extends Spec 09 §6.2)

1. Zod: shape, ranges, strict keys, `1 ≤ items.length ≤ 30`, `sets.length ≤ 20` (`422`).
2. Zod `superRefine`, per item: the two-forms rule (AC7); each row's reps pair / order and weight-unit pairing; the Spec 09 per-item reps rule (legacy form); then across items the superset group sizes. All issues collected.
3. Repository transaction: **one** query resolves every item's exercise — `assertItemExercisesUsable` now selects `id, is_active, modality` and returns the map (it returned `void`); absent → `422`, retired → `409` (Spec 09 AC8), unchanged order.
4. Modality: for each item in the row form, `plannedSetViolations(modality, sets)`; every violation across all items becomes one `422` with `errors[]` at `items.<i>.sets.<j>.<field>`.
5. Resolve each item's rows (§6.2), normalize groups, convert RPE, write (§6.3).

Shape errors still never take a lock or run a query. The modality check needs the database (it needs the modality), so — like visibility — it runs inside the write transaction.

### 6.2 Rows, legacy expansion and the derived columns

| Item as sent | Rows stored | `target_sets` | `target_reps_low` / `high` |
|---|---|---|---|
| `sets: [r0 … rk]` (k+1 ≥ 1) | those rows | `k+1` | min `repsLow` / max `repsHigh` over rows with reps; both `NULL` if none |
| `sets: []` | none | `NULL` | `NULL` |
| legacy `targetSets: N` (+ optional reps range) | N identical `working` rows `{repsLow, repsHigh}` | `N` | the range (or `NULL`) |
| legacy `targetSets` null/absent **with** a reps range | none | `NULL` | the range **as sent** (O1 default) |
| legacy, all three null/absent | none | `NULL` | `NULL` |

One function (`deriveTargets`, plus `expandQuickLine` for the legacy rows) computes the columns; the repository never hand-assigns them. The exception row — a rep range with no set count — exists because Spec 10.0's sheet allows it ("8–10 reps"), `targetLine` renders it, and rows cannot represent "reps but no number of sets"; collapsing it to one row would silently turn "8–10 reps" into "1 × 8–10", and dropping it would lose data on any unrelated `PUT`. It is the only case in which the rep columns are not a function of the rows, and it is reachable only through the legacy form (the row form cannot express it). Open question O1 asks the owner to confirm the default.

A started workout copies the item's columns verbatim (§6.4), so `workout_exercise.target_*` obey the same table: they are derived at routine-write time and snapshotted, never recomputed on the workout side.

### 6.3 Create and replace

As Spec 09 §6.3, with the item insert extended: items are inserted with `uuidv7()` ids generated in the application, their derived columns from §6.2; then, if any item has rows, **one** bulk `INSERT INTO "routine_item_set" … VALUES (…)` for all rows of the document (≤ 30 × 20 = 600 rows × 8 bound parameters = 4 800, well under Postgres' 32 767-parameter limit). `PUT` still deletes the routine's items first; the `ON DELETE CASCADE` removes their rows, so no row-level delete statement exists. `created_at` of the routine and the lock order (advisory lock on create; `FOR UPDATE` row lock on replace) are unchanged.

### 6.4 Start from a routine (extends Spec 09 §6.5 step 4)

Steps 1–3 and the `workout_exercise` insert are unchanged. Immediately after that insert, still inside the transaction and under the step-2 `FOR SHARE`:

```sql
INSERT INTO "workout_planned_set"
  (id, workout_exercise_id, position, set_type, reps_low, reps_high, weight, weight_unit)
SELECT gen_random_uuid(), we.id, s.position, s.set_type, s.reps_low, s.reps_high, s.weight, s.weight_unit
FROM "routine_item" ri
JOIN "routine_item_set" s  ON s.routine_item_id = ri.id
JOIN "workout_exercise" we ON we.workout_id = $workout AND we.position = ri.position
WHERE ri.routine_id = $routine
```

The join on `position` is exact: the preceding copy gave each `workout_exercise` its item's `position` verbatim (dense, unique within the workout), so each item's rows land on precisely the exercise created from it — including when a routine lists one exercise twice. The statement returns the inserted row count, which feeds the log line (§9). The replay path (Spec 09 step 1, no row inserted) returns before any of this — it never reads the routine or copies twice (AC14). A failure anywhere rolls the whole transaction back.

### 6.5 Reads

- **Routine:** `ROUTINE_WITH_ITEMS` gains a nested aggregate inside each item's `json_build_object`: `'sets', COALESCE((SELECT json_agg(json_build_object('set_type', s.set_type, 'reps_low', s.reps_low, 'reps_high', s.reps_high, 'weight', s.weight::float8, 'weight_unit', s.weight_unit) ORDER BY s.position) FROM "routine_item_set" s WHERE s.routine_item_id = ri.id), '[]'::json)`. It stays **one statement**, so the Spec 09 AC14 / `ETag` guarantee (no torn document) extends to rows. `weight::float8` mirrors `set_entry`'s read, so `62.5` is `62.5` on the wire.
- **Workout:** `loadExercises` gains the same kind of scalar subquery (`planned_sets` from `workout_planned_set` ordered by position) — no extra round trip. `PATCH /v1/workout-exercises/{id}` returns a `RETURNING` row today, so after its update it issues one `SELECT` for the row's `planned_sets`; `POST …/exercises` returns `[]` without a query (a new exercise has no plan). `toExerciseRecord` / `WorkoutExerciseDbRow` gain the field, which is how Spec 11's shared mapper carries it.
- The `ETag` of a routine read changes for every routine at deploy (the bytes gained `sets`); clients revalidate once with a `200`. Harmless, and AC2 says so.

### 6.6 Body size

Spec 09 AC25 assumed a routine body is "a few KB". With rows it is not: the legal maximum — 600 rows at ≈ 87 bytes (`{"setType":"warmup","repsLow":100,"repsHigh":100,"weight":9999.999,"weightUnit":"kg"},`), 30 items with 500-character notes (≈ 19.5 KB) and routine notes (2 KB) — is ≈ 74 KB, over the global `BODY_LIMIT_BYTES` of 64 KiB, so a legal document would be refused with `413`. The two routine write routes therefore set Fastify's route-level `bodyLimit: 128 * 1024` (a named constant beside `BODY_LIMIT_BYTES`; D9). The global limit and every other route are untouched. *Verify at implementation* that the existing `413` → problem+json mapping applies at the route-level limit.

### 6.7 Edge cases

- A row may be only a set type (`{ "setType": "warmup" }`) on any modality; on `duration` / `distance_duration` it is the only form allowed.
- `weight: 0` is a valid plan (a deliberate bodyweight row on `weighted_bodyweight`), distinct from `null` ("no planned weight"); `weight` more than three decimals is rounded by the column, as for `set_entry` (the response shows the stored value).
- An item whose exercise is retired later keeps its rows; the start still fails `409 exercise-retired` (Spec 09 AC17), so rows are never copied for a retired exercise.
- A `PUT` of an unchanged document still re-creates items and rows (new item ids, new row ids; the `ETag` changes by the item ids only, Spec 09 §6.8).
- Mixed units within one item are legal at this layer (a client may store `60 lb` and `100 kg` rows); Spec 10.2's editor does not create them (its D3) but must display them faithfully.
- A legacy-form `PUT` on an item that currently holds a ramp or warm-up **flattens it**: the body is a whole replacement and the legacy form can only say "N identical rows". That is the contract (D11), not a bug; it matters for a Spec 10.2 rollback (10.2 §11).
- Rowless items (`sets: []`) coming out of the rollout window (§11) read as `sets: []` with their old `targetSets`; the start copies no rows for them, so the session degrades to "no plan" — never to a wrong plan.

## 7. Security & privacy

- **Authorization is inherited, with no new surface.** There is no route addressed by a row id; rows are reached only through a routine or workout the caller owns (every Spec 09 query is `user_id = $acting`; the start copy joins from the user-scoped routine under `FOR SHARE`). User B cannot read, write or copy A's rows (Spec 09 AC28 extends: the fixture includes rows).
- **Mass-assignment.** `PlannedSetInputSchema` is strict; ids, positions and timestamps are never accepted; the derived columns cannot be sent (`targetSets` together with `sets` is `422`, AC7).
- **Abuse bounds.** ≤ 20 rows per item (schema and DB), ≤ 30 items, ≤ 50 routines, so ≤ 30 000 plan rows per user (≈ 2.7 MB in the unpaged list at the absolute maximum; AC27 is the tripwire, D10 records why there is no extra total cap and the upgrade path). Bodies are bounded at 128 KiB on two routes; the `routines` write group (30 / min) and the in-flight cap bound the write rate.
- **PII / sensitivity.** Planned weights and reps are training data, as sensitive as `set_entry`; they are never logged (§9) and are included in the account export (Spec 11) and removed by the purge (AC21).
- **Cache.** Routine reads stay `private, no-cache` + `ETag`; workout reads stay `no-store`; error bodies carry no row values.
- **No new secret, no new egress, no new dependency.**

## 11. Deployment & rollback

`0010` is additive and expand-only: two new tables and an insert into one of them; no lock on a hot table beyond reads of `routine_item`.

**Release order (hard dependency; extends Spec 09 §11):**

1. **Migrate first.** `DATABASE_URL='<neon direct url>' pnpm run db:migrate:deploy` applies `0010` **before** the code goes live (manual step, never on boot). Old code ignores the new tables, so the migration safely precedes it. Verify with `db:migrate:status` on Neon (the 2026-10-04 incident: do not assume).
2. **Then merge 09.1** → Render auto-deploys the API. The same commit also redeploys the static web site, whose `@sin/core` schemas now require `sets` / `plannedSets`; for the minutes in which the new bundle is live against the not-yet-deployed API the routine and workout screens would fail to parse. This is accepted on staging (single tester, no data effect, self-healing); the prod pipeline (Spec 01.1) promotes both artifacts together. This is the "API one release ahead" convention applied to a monorepo with a shared schema package, and it is why the web gains no *use* of the fields in this release.
3. **Verify** on staging: `GET /v1/routines` shows `sets` on every item; run the **consistency query** (routine items with `target_sets IS NOT NULL` and no rows — expected 0). A non-zero count means a pre-`0010` code `PUT` ran between steps 1 and 2 (the old writer deletes and re-creates items without rows); re-run the guarded backfill `INSERT` of §4 by hand (AC19). The consistency query and the backfill text go into `docs/runbooks/first-deploy.md` as a short "0010" note.
4. **Spec 10.2 may merge only after step 3** (API one release ahead).

**Rollback:** revert the code commit. The tables and rows stay, inert. Because the item `target_*` columns are kept correct by every new-code write, **old code reads new-code routines correctly**; its only loss is that an old-code `PUT` deletes the items and, through the cascade, their rows (the plan is lost; the targets survive). Workout snapshots keep their `workout_planned_set` rows; old code ignores them. Production undo is a forward migration, never a down script. After a revert, 10.2 (if merged) must be reverted too (DESIGN §6).

**No feature flag** — "off" is the absence of a UI consumer until Spec 10.2.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-11, from the brief)

- ✅ **D1 — Child tables with rows as the single source of truth (brief decision 6).** `routine_item_set` and `workout_planned_set`; `routine_item.target_*` and `workout_exercise.target_*` become derived. **Rationale:** per-set plans need an ordered list with database-enforced rules; the derived columns keep Spec 10.1's target line and every started workout's snapshot working with no reader changes, and an expand-only release cannot drop them anyway. **Rejected:** a `jsonb` column on `routine_item` (no CHECKs, and it contradicts Spec 09 D1's rejection of a JSON snapshot); a quick-line-only `target_weight` (no ramps — fails decision 2 of the brief).
- ✅ **D2 — Rows carry a set type; the plan is per-set, with an optional quick line (brief decisions 2, 3, 5).** A planned row has `setType` (default `working`), a rep range, a weight and its unit; "of N" counts every row. **Rationale:** a planned warm-up must log as a warm-up so PRs and volume (working sets only) stay correct. The editor's quick line is the UI's default; the API simply accepts either form.
- ✅ **D3 — No per-set RPE; no `weight_kg` column; units as typed.** The item-level `targetRpe` stays in both input forms; the plan stores weight and unit exactly as entered (DESIGN §4.8), never converted when the profile unit changes. **Rationale:** RPE is per set and never copied forward today; nothing aggregates planned weights.
- ✅ **D4 — ≤ 20 rows per item, enforced three times** (schema `max(20)`, the `position` CHECK 0–19 with the unique index, and `targetSets` max 20). **Rationale:** matches the existing `targetSets` ceiling, so the legacy form can never expand past the cap.
- ✅ **D5 — Modality rules apply to the row form only (resolved by reading the code; a qualification of the brief).** `bodyweight_reps` rejects weight; `duration` / `distance_duration` carry only a set type; but the **legacy form is exempt** and expands verbatim. **Rationale:** Spec 10.0's sheet accepts reps on any exercise and Spec 09 never checked modality on targets, so existing routines may legitimately hold reps on a timed exercise; rejecting that on a legacy `PUT` would turn an unrelated edit into a `422` for today's client, which AC22 forbids. Spec 10.2's editor strips fields a modality cannot use when it builds the row form (its D6), so the exemption closes itself as routines are re-saved. **Rejected:** applying the rules to both forms (breaks today's client); silently dropping the reps on expansion (changes what the client sent without telling it).
- ✅ **D6 — SQL-side inserts use `gen_random_uuid()`; the application keeps `uuidv7()`.** **Rationale:** the production Postgres (16) has no `uuidv7()`; the backfill and the start's `INSERT … SELECT` (chosen over a JS round trip, per the brief) need ids generated in SQL. v4 ids on a child table read only through its parent cost nothing. The `INSERT … SELECT` runs under the routine's `FOR SHARE`, so it sees one consistent set of rows.
- ✅ **D7 — The new tables carry `created_at` / `updated_at` although the brief's column list omitted them.** **Rationale:** DESIGN §4.0 says every table carries them; two defaulted columns are cheaper than an exception to a stated convention. They are informational (rows are replaced, not updated).
- ✅ **D8 — Duration and distance exercises plan only a set type in v1 (brief); planned duration / distance is FI-11.** The plan tables have no `duration_s` / `distance` columns; adding them later is an additive migration plus an additive field on `PlannedSet`.
- ✅ **D9 — Routine writes get a 128 KiB route-level body limit (found by reading the code).** **Rationale:** the legal maximum document is ≈ 74 KB, above the global 64 KiB; refusing a legal document would be a bug, while raising the global limit would widen every route's abuse surface. **Rejected:** raising `BODY_LIMIT_BYTES` globally; capping total rows per routine below the product maximum (see D10).
- ✅ **D10 — No total-rows cap per routine or per user beyond 20 × 30 × 50; the worst-case list is a tripwire, not a limit.** At the absolute maximum `GET /v1/routines` carries 30 000 rows (≈ 2.7 MB) in one statement, against Spec 09 D7's ≈ 1 500 item rows. Reaching it needs a deliberate script through the `routines` write group (30 writes / min), and real routines hold dozens of rows. **Upgrade path if AC27 or real data says otherwise:** a per-routine total (e.g. 200 rows, a `422` on `items`) or a summary-only list with `sets` on the detail read — both additive on the request side. Recorded rather than pre-empted so no legal document is refused without evidence.
- ✅ **D11 — The legacy form is expanded, never rejected, so the API can ship alone.** **Rationale:** DESIGN §6's rollout convention (API a release ahead) is only meaningful if today's client keeps working unchanged against the new API; a rejected legacy form would force the client first. Both forms are accepted indefinitely; whether the legacy form is ever retired is a later, separate decision.
- ✅ **D12 — "Sending both forms" is decided by key presence.** **Rationale:** today's client always sends `targetSets`, `targetRepsLow`, `targetRepsHigh` as numbers or explicit `null`; value-based detection (`!= null`) would let `sets` + three `null`s through and make the rule depend on the sender's habits. Presence is simple, symmetric and testable; Spec 10.2's client sends exactly one form.
- ✅ **D13 — `RoutineItemInputSchema` stays a single `z.strictObject`; the two-forms rule lives in `RoutineWriteSchema`'s `superRefine`.** **Rationale:** the web's `targetFormat.ts` reads `RoutineItemInputSchema.shape.targetSets` etc. (Spec 10.0 AC9); a union or transformed schema has no `.shape`. All cross-field rules already live in that `superRefine` (Spec 09 D16), so editors still get every problem in one `422`.
- ✅ **D14 — `PlannedSet` has no id and no position on the wire.** **Rationale:** nothing addresses a row (no route), array order is the order, and Spec 09 already treats item ids as unstable across `PUT`; omitting ids avoids promising stability that whole-replace cannot keep. Adding ids later is additive.

### Resolved by reading the code (corrections and qualifications to the brief)

- **The brief's "duration, distance" is two modality values**: `duration` and `distance_duration` (`packages/core/src/enums.ts`); `weighted_bodyweight` requires weight + reps like `weight_reps` (`MEASURE_RULES`). AC5 uses the real names.
- **Derived reps cannot represent "reps without a set count".** The brief derives `target_sets` as the row count and reps as min / max of the rows; but Spec 10.0's sheet lets a lifter save "8–10 reps" with no sets, which rows cannot express. The brief's backfill ("items without a set count get none") would leave such items consistent, but the next legacy `PUT` would erase their reps. §6.2 therefore keeps the reps columns as sent when an item has no rows — **O1**.
- **Legacy clients send explicit `null`s** for all three quick-line keys, so "sending both → 422" had to be defined on key presence (D12).
- **Spec 09 AC25's "bodies are small" no longer holds** (D9).
- **`assertItemExercisesUsable` returns `void` and selects `id, is_active`** — the brief is right that it can read the type in the same query, but the signature changes to return a map (§6.1).
- **`PATCH /v1/workout-exercises/{id}` and the add route return `RETURNING` rows**, not the detail read, so `plannedSets` needs one extra `SELECT` on the patch path and a literal `[]` on the add path (§6.5).
- **Rollout window.** Between `migrate deploy` and the API deploy, a pre-`0010` code `PUT` recreates items without rows (the cascade removed the backfilled ones). Not corruption — the item keeps `target_sets` and starts as "no plan" — but it needs the re-runnable backfill (AC19) and a verification query (§11).
- **Spec 11's purge test fails on empty tables** (its AC23 vacuous-pass guard), so the fixtures of both specs must contain plan rows (§3, AC21, AC28).
- **The same-commit web redeploy** reads the new required fields as soon as it is live (§11 step 2); the convention's "one release ahead" is honored at the level of verified deploys, not of separate commits.

### Open questions for the owner

- ✅ **O1 — A rep range with no set count (e.g. "8–10 reps", no sets).** *Resolved 2026-10-11 (owner): option A, the drafted default.* Spec 10.0's sheet allows it and `targetLine` renders it, but planned-set rows cannot represent it. **Default drafted (recommended):** such an item has **no rows** and keeps its rep range on the item as sent — the one exception to "rows are the source" (§6.2); it displays and round-trips exactly as today, and Spec 10.2's editor keeps it editable in the quick line (sets blank, reps filled, no weight). **Alternative:** treat it as one row (`1 × 8–10`), which removes the exception but changes what the lifter sees and what the session shows ("Set 1 of 1", then "Extra set"). **Alternative:** reject it in the row form and let the editor require a set count whenever reps or weight are entered, leaving the legacy form tolerant for old clients. The first costs one documented exception; the other two change behavior the owner has already used. Needs a one-line ruling before implementation.
