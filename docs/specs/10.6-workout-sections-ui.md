## 1. Purpose, scope & non-goals

The owner types a coach's plan in as they train. This spec is the screens for Spec 09.4: a **section heading with an Edit button**, **Add section** beside **Add exercise**, the line **"New exercises go into {name}."**, the **New section** and **Edit section** sheets, **Remove section** behind a confirm, and a **Section** select in an exercise's Options — on the live workout and, in Phase B, on the edit screen for a finished one. The History summary already draws section headings and notes (Spec 10.3); it gains nothing and loses nothing.

> **First-principles note — "a card remounts when its section changes".** React keeps a component's state (an open Options panel, focus) only while the component stays in the same place in the tree. The session draws each section as its own `<section>` element; moving an exercise to another section moves its card to a different parent, so React destroys it and builds a new one. The Options panel the lifter just used closes and the focused button vanishes. So after a section move the screen deliberately reveals the moved card and puts focus on its heading (§6.4), using the same "reveal" mechanism that already scrolls a newly added exercise into view.

> **First-principles note — "pessimistic, online-only writes".** Sets log offline because a queue (the outbox) replays them later. Structure changes (add an exercise, link a superset, and now sections) do not: they change what the list *is*, and a queued "move X into Warm-up" replayed after another tab removed Warm-up would be wrong. So these writes wait for the server, say "offline" if there is no signal, and the screen changes only from the server's answer (a refetch, or the response itself on the edit screen). This is the existing rule (Spec 10.1 D6, Spec 18.0 D5), applied unchanged.

### In scope

- `features/workouts/sections/`: copy, failure mapping, `SectionSheet`, `SectionPicker`, the C4 line, `useSectionActions`, live and edit mutation hooks, `SectionDialogs`.
- `SessionSection` (an Edit button, the empty line), `sectionSegments` (two new fields on a segment), `ExerciseCard` (the Section select in Options), `ActiveSession` and `EditWorkoutScreen` (wiring).
- `WorkoutClient`: `addSection`, `updateSection`, `removeSection`, `setExerciseSection`.
- Screenshot-harness captures 52–58, the fake API's section handling, a manual phone check, docs.

### Non-goals

| Not here | Lives in |
|---|---|
| Any API, migration, placement, cap or superset rule | Spec 09.4 (the client never computes a position) |
| Reordering sections; a section in the middle; drag and drop | Not planned (brief) |
| Offline section writes, an outbox op, a stored draft of the sheet | Not planned (brief C8) |
| Writing anything back to the routine; "save as routine" | Not planned (brief C2) |
| A section on the History **list** row, the Progress list, the summary stats | Unchanged |
| Collapsing a section; section timers | Not planned (10.3) |
| Editing a section from the History summary | The edit screen is the way (Phase B) |
| Reading section text from **New from text** during a live workout | Not planned (brief) |
| Any change to the Log button, the current exercise, the rest timer, Finish | Anti-goal: they stay exactly as they are |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.6 ACn — …"`**, enforced by a scan test in the style of `acTags.10-5.test.ts` (AC30). "Live" means `ActiveSession`; "edit" means `EditWorkoutScreen`. Levels are in §10.

### Phase A — shared pieces and the live screen

**Heading and empty section**

1. **Edit on the heading.** On the live screen, the heading of every real section shows a secondary **Edit** button (visible text `Edit`, accessible name `Edit section {name}`, ≥ `--tap-target-min`) beside the name, under which the note shows as today. Only the **first** segment of a section carries it (a split section's later segment has none, as it has no note, 10.3 AC11); the synthetic **Other exercises** heading and a screen with no sections never do; the History summary and any other read-only use of `SessionSection` never do (the button exists only when the caller passes `onEdit`).
2. **Empty section.** A section with no exercises shows its heading, its note and, in place of cards, the muted line `No exercises yet.` — live and edit only; the summary shows the heading and note alone (O1).

**Add section and the line**

3. **Add section.** The list-end row shows a secondary **Add section** next to **Add exercise**. In a workout with no exercises yet the row shows **Add section** alone (the bottom bar's primary already says Add exercise; the row still exists so a section can be made first). It is disabled while `structureBusy`; at 8 sections it is disabled with the visible reason `A workout can have up to 8 sections.` (`aria-describedby`; the client count is a convenience, the server's `409` is authoritative, AC13). It never appears in the `ActionBar`, and the bar's `LogBarButton` stays the screen's one primary `Button` (Spec 17.1) in every bar mode, with the 600 ms double-tap window unchanged.
4. **The line.** Directly above the list-end buttons the screen shows `New exercises go into {name}.` with the name in `<strong>` — **iff** `sectionForNewExercise(workout.sections)` (Spec 09.4 AC24) returns a section, and never otherwise (no sections; the last section was copied from the routine). It reads the same cached `workout.sections` the headings do, so it appears the moment an added section is cached and follows a remove. The name is a React text child (§7).

**New section**

5. **The sheet.** **Add section** opens the full-height `Sheet`: title `New section`; the line `Exercises you add next go into this section.`; a labeled single-line **Name** (required, `autoComplete="off"`) and a labeled multi-line **Note** with the hint `Anything beyond sets and reps.` (`aria-describedby`); **Cancel** and **Add section**. Name is trimmed; empty after trimming shows `Enter a name.` and sends nothing; over 40 characters trimmed shows `Keep the name to 40 characters.`; a note over 2000 characters shows `Keep the note to 2000 characters.`; control characters other than TAB / LF / CR show `Remove characters that can't be saved.`; all client checks are advisory, the server's `422` field errors map to the same texts (AC13). The sheet does not autofocus a field (the `Sheet` rule: no phone keyboard on open).
6. **Adding.** **Add section** sends exactly `POST /v1/workouts/{id}/sections` with `{ name }` or `{ name, notes }` (`notes` omitted when the trimmed note is empty), once per tap (a ref guard; a second tap sends no second request). On success the sheet closes, the detail is refetched, the new heading appears under the last section, the line of AC4 appears, the status line says `Section added: {name}`, and focus is on the **Add section** button (the sheet's opener; the browser restores it).

**Edit and remove**

7. **Edit section.** **Edit** opens the sheet titled `Edit section` with Name and Note prefilled and **Cancel** / **Save**. **Save** sends only the groups that changed (`name`, `notes`; an emptied note is `notes: null`); with nothing changed it closes and sends nothing. On success the sheet closes, the heading updates from the refetch, the status line says `Section saved`, and focus is on that section's **Edit** button.
8. **Remove.** Under a divider the sheet shows a danger **Remove section** with the line `Its exercises and sets stay in the workout, without a section.` Tapping it opens a `ConfirmDialog` — title `Remove {name}?`, body `Its exercises and sets stay in the workout, without a section.`, **Cancel** / **Remove** (danger), **Cancel focused** (`ConfirmDialog`'s explicit rule) — and sends nothing until **Remove**. **Cancel** returns focus to **Remove section** and changes nothing. **Remove** sends `DELETE /v1/workout-sections/{id}`; a `404` counts as done. On success both dialogs close, the detail is refetched (the exercises now show loose, under **Other exercises** where they sit between sections), the line of AC4 follows the new last section, the status line says `Section removed`, and focus moves to the **Add section** button (the opener of the sheet, the Edit button, no longer exists).

**Moving an exercise**

9. **The Section select.** An exercise's **Options** panel shows a native `<select>` labeled **Section** when the workout has ≥ 1 section: `No section` first, then each section by `position`, the exercise's current one selected (a controlled value, so a failed change visibly reverts). Choosing a different value sends exactly `PATCH /v1/workout-exercises/{id}` with `{ sectionId }` (`null` for No section) through the new `WorkoutClient.setExerciseSection` — never `position`, never through `useRegroup` or `planSessionChange`, and `WorkoutExercisePatch` still has no `sectionId` (the 10.1 AC11 / 10.3 AC28 pattern: a regroup can never write it). Choosing the current value sends nothing. The select is disabled while `structureBusy`. The placement is the server's: the client sends no position and reorders nothing itself.
10. **After a move.** On success the detail is refetched and the status line says `Moved {exercise} to {section}` or `Moved {exercise} out of its section`; the moved card is revealed and focus is on its heading (the card remounts, §6.4), Options closed. The lifter's current exercise does not change (`useCurrentExercise` holds the choice by id; `advanceFrom` is not invoked).
11. **Supersets.** When the exercise is in a linked run, the panel shows beneath the select the muted line `Changing the section takes it out of its superset.` (`aria-describedby` on the select); otherwise nothing. After the move the card shows no bracket and its former partners show no bracket either if only one remains (the server clears the label, Spec 09.4 AC13; `supersetRows` draws it).

**Writes, failures, caches**

12. **Online-only, one at a time.** The four writes are TanStack mutations with `networkMode: "always"`, `retry: false`, on the live client (`useWorkoutClient()`); none enqueues an outbox op, reads or writes `sin:workout:outbox`, `sin:workout:drafts` or `sin:workout:rest`, or touches `["workouts","edit"]`. They take the screen's `structureLock` (a write begun while another structure write is in flight is ignored) and count in `structureBusy`, so Finish and the other structure controls wait. Offline they fail at once with the offline text. A queued set still logs and syncs while a section sheet is open.
13. **Failure table (live).** Resolved by one pure function `resolveSectionFailure(op, error, { offlineText })` from status and problem slug only, never from message text:

    | Case | Where | Text | Then |
    |---|---|---|---|
    | Offline (any op) | sheet / banner | the screen's offline text | stays open; the button is the retry |
    | `429` | same | the shared rate-limit text (`Retry-After` used) | same |
    | `422` on `name` / `notes` | sheet field | AC5's texts; unmatched → `Check the name and note and try again.` | stays open |
    | `409 workout-section-limit` (add) | sheet | `A workout can have up to 8 sections.` | stays open; the row's count refreshes |
    | `404` on the section (update, move target) | banner | `That section no longer exists` | refetch; sheet closes |
    | `404` on the workout | — | the existing "gone" path (`gone()`) | as every structure write |
    | `404` on remove | — | done (AC8) | refetch |
    | Add, any other failure | banner, no Try again | `Couldn't confirm that section was added — check your workout before adding it again` | refetch first (AC14) |
    | Update / remove / move, any other failure | sheet or banner | `Couldn't save the section — try again` / `Couldn't remove the section — try again` / `Couldn't move that exercise — try again` | **Try again** on move and remove; update's Save is its retry |

    Every banner shows the request id when the server sent one; `reportUnexpected` is called once for an unexpected failure, with a static operation name (`add-section`, `update-section`, `remove-section`, `set-section`) and no user text.
14. **No blind retry of a create.** Section create has no idempotency key (Spec 09.4 D10). On any non-offline, non-`4xx` failure the screen refetches the detail **before** it shows the "Couldn't confirm…" banner and offers no **Try again**, so the lifter sees whether the section exists.
15. **Live caches.** Each success invalidates `["workouts","active"]` and nothing else (no history / progress / records keys: a live workout has none, 08.0 AC8). The outbox projection (`project`) leaves `sections` untouched, so a refetch with queued ops pending keeps the headings. A failed write leaves the cache as it was.

**The summary**

16. **History / summary unchanged in structure.** `FinishedWorkoutScreen` draws a user-added section exactly as a copied one — heading, note, then its cards via `sectionSegments` — with no Edit button, no empty-section line and no `addedInWorkout`-dependent markup; existing summary snapshots pass unmodified. (Screen 5 of the brief is this, and a harness capture, AC28.)

### Phase B — the edit screen

17. **Same controls, same components.** The edit screen renders the heading **Edit** button, the empty line, the C4 line, **Add section** (beside **Add exercise**), the Section select, the sheets and the confirm through the same components as AC1–AC11, with identical texts and rules. The edit screen's own pieces (`EditWorkoutScreen`, its `structureLock`, its `report` / banner, its status line) call them; the screen is still a sibling of `ActiveSession`, never a mode of it (Spec 18.0 D3).
18. **Edit writes.** On the edit screen the four writes use the plain REST client (`useEditWorkoutClient()`), `mutationKey: EDIT_MUTATION_KEY`, `networkMode: "always"`, `retry: false`, hook-level `onSuccess`. A create or update writes the returned section into `["workouts","detail",id]` (`sections`, ordered by `position`); a remove or a move refetches that detail (positions and `sectionId`s of other rows change). **Every** success calls `editSucceeded` (→ `applyEditedCaches`: reset `["history","list"]`, invalidate `["progress"]` and `["records"]`), because a move can change records and the History row's first names. A failed write changes no cache. The live `["workouts","active"]`, the outbox, the drafts and the rest store are never touched (Spec 18.0 AC21's test and AC46's source scan are extended to the new files).
19. **Events.** Live success emits one scalar event each: `section_added`, `section_edited`, `section_removed { exerciseCount }`, `exercise_sectioned`. Edit success emits `workout_edit { edit }` with `edit ∈ section_added | section_changed | section_removed | exercise_sectioned` (the server's enum, Spec 09.4 §9, appended to 18.0 AC27's list); edit mode emits none of the live events. No event carries a name, note or id.
20. **Edit failures.** The AC13 table applies with the edit screen's offline text (`EDIT_COPY.offline`), its banner and its "workout vanished" view for a workout-level `404`; a section-level `404` shows `That section no longer exists`, refetches and closes the sheet; `409 workout-would-be-empty` and `409 workout-finished` cannot occur for these routes and are not handled (they fall into the generic row).
21. **A finished-workout move refreshes derived data.** In a test with records fixtures, moving a card between sections (the server's fake recomputes) leaves `["history","list"]` reset and `["progress"]` / `["records"]` invalidated; adding, renaming and removing a section do the same (the screen cannot know which writes mattered).

## 6. Behavior & logic

### 6.1 Client methods and cache keys

`WorkoutClient` gains `addSection(workoutId, body): Promise<WorkoutSection>`, `updateSection(id, body)`, `removeSection(id): Promise<void>`, `setExerciseSection(id, sectionId | null): Promise<WorkoutExercise>` (exactly `{ sectionId }` on the wire). `queuedWorkoutClient` passes all four through to the REST client (no queueing; the queued client's offline behavior is the network error). Ids go through the existing `seg()` encoder. Live hooks live in `sections/useSectionMutations.ts` (`useWorkoutClient`, invalidate `WORKOUT_KEYS.active`); edit hooks in `edit/useEditSectionMutations.ts` (`useEditWorkoutClient`, `EDIT_MUTATION_KEY`, write-through for create / update, refetch `detail(id)` for remove / move, then `editSucceeded`).

### 6.2 `sectionSegments` and `SessionSection`

`SectionSegment` gains `sectionId: string | null` (null for loose segments) and `editable: boolean` (true only on a real section's first segment, i.e. where `notes` can be non-null). `SessionSection` gains optional `onEdit?: () => void` (renders the **Edit** button in `SessionSectionHeading`) and optional `emptyText?: string` (rendered when `children` is empty). Callers that pass neither (the summary) render byte-identically. Keys are unchanged (content-derived), so adding an Edit button never remounts cards.

### 6.3 `useSectionActions` (shared by both screens)

```ts
useSectionActions({
  workout, mutations,            // live or edit hook set (same shape)
  structureLock, setBanner, announce, onGone, refetch, offlineText, reportOp,
}): {
  sheet, openAdd, openEdit, closeSheet, submitSheet,
  removing, requestRemove, cancelRemove, confirmRemove,
  setExerciseSection,            // for ExerciseCard
  addSectionRef,                 // the Add section button
}
```

It owns the sheet/confirm state, the busy ref guards, `resolveSectionFailure`, the announcements and the focus rule of AC6–AC8; the screens own their locks, banners and status lines and inject them. `SectionDialogs` renders the `SectionSheet` and the remove `ConfirmDialog` from that state. The sheet's text state is local to the sheet and keyed by an open counter (the `ChangeTimeSheet` pattern), so it resets on each open and is never stored.

### 6.4 After a move

`setExerciseSection` runs under the lock, awaits the mutation (which awaits the refetch), then sets the screen's existing reveal target to `{ id, focus: true }` (the mechanism `addExercise` uses with `focus: false` and the "advance" path with `focus: true`); the reveal effect scrolls the moved card into view and focuses its heading via `headingRefFor`. On a failed move nothing is revealed and the select, controlled by `exercise.sectionId`, shows the old value. Both screens share the rule through `useRevealMoved`: the reveal is armed only if the cached workout already shows the exercise under its new section when the write resolves (its re-read may have failed), and fires only once the card shows there, so a later refetch never pulls focus to it (#157). An Edit section sheet whose section disappears (another device removed it) closes with `SECTION_COPY.sectionGone` — not while this screen's own write is in flight (#159).

### 6.5 The line

`NewExercisesLine` takes `sections` and renders `null` or the sentence from `sectionForNewExercise(sections)`; it is the only reader of `addedInWorkout` in the web (a source scan pins that, so the rule has one implementation, AC4).

### Resolved by reading the code (corrections and qualifications to the brief)

- **An empty workout has no list-end row** (`exercises.length > 0` gates it), so "Add section beside Add exercise" needs D8.
- **A section move remounts the card** (`SessionSection` is a per-section parent), so Options state and focus are lost; hence the reveal rule (§6.4).
- **`ActiveSession`'s Move up / down are segment-bounded** (10.3) and unchanged; the Section select is the only way across a boundary.
- **The live client is the queued client;** its structure methods pass through to REST, so the new methods need no queue support — only the pass-through.
- **`classifyWorkoutError` returns `unknown` for an unlisted 409 slug**, so `workout-section-limit` must be added to it or the cap message would never show.
- **The summary is read-only and shared** (`SessionSection` is used by it); Edit and the empty line are therefore opt-in props, not defaults.
