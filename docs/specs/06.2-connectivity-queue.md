## 1. Purpose, scope & non-goals

Make a logged set survive a dropped connection and a killed tab, so M1's exit criterion ("log real gym sessions for a week, no data loss") can be met. Today (06.1 §6.9) every write is pessimistic: the screen waits for the server, a failed write is the lifter's to retry by hand, and a reload loses anything the server has not confirmed.

This spec puts a persisted **outbox** behind the existing `WorkoutClient` seam (06.1 D4). Set writes (create, edit, delete) are enqueued, shown at once, persisted to `localStorage`, and sent in order with retry and backoff. A reloaded tab keeps its queue: once the lifter is signed back in, the pending sets reappear and are sent. Finish is blocked while sets are unsaved.

> **First-principles note (outbox, projection).** An *outbox* is a list of writes the client has promised to deliver, stored locally until the server confirms each one. A *projection* is what the screen shows: the last copy the server sent, with the outbox's pending writes applied on top. Keeping the projection a pure function, `project(serverCopy, pendingOps)`, means the hard cases (an edit of a set the server has not seen yet, a replay whose response was lost) are table-tested without a DOM, a network or a clock.

### In scope

- The outbox store, the op model and its combining rules, ordered sending, the failure table and backoff (§6.1–§6.4).
- `QueuedWorkoutClient`, which wraps the REST client and is supplied by `WorkoutClientProvider` (§6.5).
- The `sin:workout:` storage prefix and the persisted outbox (§4); a reloaded tab restores and drains it (§6.6).
- Per-row sync state, the session status line, and the Finish gate (§5).
- The auth fix: a token refresh that fails for network reasons is a network error, not a lost session (§6.7).
- A guard against two tabs writing the same outbox (§6.8).

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|
| Persisting unlogged entry-row values (drafts) across a reload | Spec 06.5 |
| A confirm dialog when logging out with unsaved sets | Spec 06.5. Until then, logout discards them silently, as today (§11) |
| Two tabs co-operating on one outbox (Web Locks, `storage`-event sync) | Spec 06.5. This spec only detects the second tab and stops it (§6.8) |
| Playwright run with `context.setOffline()` | Spec 06.5 (on top of 06.3's harness) |
| Queuing exercise-structure writes (add / move / remove exercise), start, finish, delete workout, create custom exercise | Not planned for v1. Workout-exercise create has no idempotency key, so a replay could duplicate (§12 D1). These stay pessimistic, with an offline message |
| Service worker, background sync, installable PWA | Post-v1 (DESIGN §2 non-goals) |
| Keeping the outbox through a genuine lost session | Rejected (§12 D6) |
| Opening the app with no signal (a reloaded or evicted tab offline) | Not possible while tokens are memory-only (DESIGN Q12): a reload needs Auth0 over the network before any screen renders. The outbox waits in storage and drains after the next sign-in (§12 D11) |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"06.2 ACn — …"`** (06.4 D6's prefix convention). Levels are in §10. **Phase A** (AC1–AC9): the React-free outbox. **Phase B** (AC10–AC18): the screen. **Docs and gates** (AC19–AC21).

### Phase A — outbox core

1. **`project()` overlays pending ops on a server copy.** Pure, in `outbox/project.ts`. A queued create appears in its workout-exercise with `id = clientGeneratedId`, the create body's values, and `setNumber = max(setNumber in that card, including pending rows) + 1` (Spec 05.1 §6's rule). A queued update overwrites only the fields in its body. A queued delete removes the row. If the server copy already contains a row with the op's `clientGeneratedId`, that server row is shown once and the create is not overlaid again (no duplicate). An op whose workout-exercise is not in the server copy is ignored by the projection (the card is gone; AC17 handles the op). Every row carries a sync state, `synced | pending | failed`, through a side map, never on `SetEntry` itself.
2. **Ops never attempted are combined.** Editing a set whose create is still queued merges the edit into the create's body (one `POST`, no `PATCH`). Deleting a set whose create is still queued removes the create, and nothing is sent. Repeated edits of one synced set merge into one `PATCH`, later fields winning. A delete replaces any queued edits of the same set.
3. **An attempted op is frozen.** Once an op has been sent at least once, nothing is merged into it. A later edit or delete of that set becomes a new op that targets it. Scenario (fixes 06.1 D6): a create is sent, the server stores it, the response is lost; the lifter edits weight 60 → 62.5; on reconnect the queue replays the `POST` (the server answers `200` with the stored row, weight 60), then sends `PATCH { weight: 62.5 }`. The server and the screen both end at 62.5.
4. **One op in flight, first in, first out.** The drainer sends the oldest sendable op, waits for its outcome, then the next. An op that targets a set by its `clientGeneratedId` is sent with the server id learned when its create synced. An op that depends on a create which failed permanently fails too, with the same reason.
5. **Failures are classified and retried by one table.** `outbox/classify.ts`:

   | Outcome | Treatment |
   |---|---|
   | 2xx; `404` on a delete | Done. |
   | `ApiError` with `isNetworkError`, `status` 0 from a network-caused token failure (AC9), 5xx, 408, 429 | Retryable. Backoff 1, 2, 4, 8, 16, then 30 s for every later attempt, each ±20 % jitter. No attempt counter limit while the page is open. |
   | `404` on a create or update (set or workout-exercise gone), `409 workout-finished`, `422` | Permanent: the op becomes `failed`, is never retried, and keeps the `ApiError`'s `status`, `type` and `requestId`. |
   | Any other 4xx | Permanent, as above. |
   | A genuine lost session | Not reached: `onAuthLost` clears everything (AC9). |

   `Retry-After` is not read (`ApiError` carries no headers); the 30 s cap bounds the load. A `status: 0` error that is not a network error (an unserializable body) is permanent. Failures that `reportUnexpected` treats as unexpected are reported with the set operation's tag, as in 06.1.
6. **The drainer runs on these triggers only:** an enqueue; the `online` event; `visibilitychange` to visible; store start (after loading persisted ops); and **Retry now**. While `navigator.onLine === false`, no trigger sends anything (an enqueue just stores the op; no wasted attempts), except **Retry now**, which always makes one attempt. A retry timer never runs while an op is in flight.
7. **The outbox survives a reload.** Ops are written through `StorageAdapter` under `sin:workout:outbox` after every change. A new store over the same storage restores every op with its status, attempted flag and target, then drains. If `storage.set` throws, the store keeps working in memory, reports `{ source: "workout-storage" }` once (06.0 AC11's pattern), and never throws to a caller. After logout's write block trips (06.1 AC13), the store writes nothing.
8. **Ops belong to one user.** Each op records the `userId` (`Me.id`, the same id 06.0 scopes the catalog by) that queued it. On load, ops with a different `userId` are discarded unsent. The drainer never sends an op whose `userId` is not the signed-in user's.
9. **Losing the network is not losing the session.** When `getToken` rejects because of the network (a `TypeError` from fetch, an Auth0 SDK error whose `error` is not one of `login_required`, `invalid_grant`, `missing_refresh_token`, `consent_required`, `interaction_required`, or any rejection while `navigator.onLine === false`), the API client throws `ApiError.network(…)` and does **not** call `onAuthLost`. A rejection with one of the listed codes keeps today's behavior: `onAuthLost` → `clearUserData` (which now includes `sin:workout:`) → Auth0 logout. A double `401` also keeps today's behavior.

### Phase B — the session screen

10. **`QueuedWorkoutClient` is the screen's client.** `WorkoutClientProvider` supplies it. `createSet`, `updateSet` and `deleteSet` enqueue and resolve at once: `createSet` with the projected row (AC1), `updateSet` with the projected row after the edit, `deleteSet` with `undefined`. They never reject for network reasons. Every other `WorkoutClient` method passes straight to the REST client. `getActive()` fetches and returns `project(server, pendingOps)`. The mutation hooks in `useWorkoutMutations.ts` keep their shape; their `onSuccess` cache writes now write projected rows.
11. **Logging works with the browser offline.** The three set mutations use `networkMode: "always"`, so TanStack Query runs them while `navigator.onLine` is false (§12 D5). With the fake API offline, logging three sets shows three rows at once, with set numbers 1, 2, 3.
12. **A synced op updates the cache without a flicker or a duplicate.** When a create syncs, the row whose `id` is its `clientGeneratedId` is replaced in `["workouts","active"]` by the server row, in place. When an update syncs, the server row replaces the projected one. A background refetch of `/active` while ops are pending (focus, AC11 of 06.1) does not remove a pending row or show it twice.
13. **A reloaded tab keeps its queue.** With pending ops in storage, opening `/app/workouts` (after the usual sign-in) shows the server's workout with the pending sets overlaid and marked pending, then drains them. A pending set the server already holds (its create landed before the reload) appears once.
14. **Every set row shows its sync state.** Pending: a visible "Not saved yet" tag (text, not colour alone, as 06.1's "Needs data"; the design tokens have no visually-hidden utility and `assert:css-tokens` forbids adding px values outside `tokens.css`); the row can still be edited and deleted (AC2 applies). Failed: "Couldn't save" in the error tone with **Discard**; a `422` also offers **Edit**, which opens the edit sheet and replaces the failed op with a new one. Discarding a failed create removes the row. Synced rows look exactly as in 06.1. Markers meet 06.1 AC33's tap-target and contrast rules.
15. **A status line says what is outstanding.** Above the sticky bar, only while the outbox holds ops for this workout: offline (`navigator.onLine` false) "Offline — N sets will save when you're back online"; otherwise "Saving N sets…" with **Retry now**; if any op failed, "N sets couldn't be saved" with **Show** (scrolls to the first failed row on screen, 06.4's ref-based scroll, AC3; hidden when none is on screen) and **Discard** (discards every failed op for this workout). It is a polite live region that announces a change of state, not each retry. Exercise-structure, start and finish failures caused by the network say "You're offline — try again when you have signal" instead of the generic error.
16. **Finish waits for the outbox.** While the outbox holds any op for this workout, Finish is disabled with the hint "N sets not saved yet". When it empties, Finish works as in 06.1 and 06.4 (the detail seed in the hook, the active-entry removal in `FinishedWorkoutScreen`, 06.4 D1). 06.1's in-flight guard stays for exercise-structure writes.
17. **Ending the workout cleans up.** On a successful finish, a delete of the workout, or the gone path (06.1 AC29), every op for that workout is removed. If draining meets `409 workout-finished`, that op and every later op for the same workout become `failed` (AC5), so the lifter sees which sets were not saved before discarding them. A `404` on one op fails that op only (its set or workout-exercise is gone); the drainer then refetches `/active` once so the screen shows the server's copy. A failed op whose set is no longer on screen still counts in the status line (AC15), whose **Discard** clears it. When `getActive()` returns no active workout or a different one, ops for any other workout are dropped (the gone path). Queued set writes no longer raise 06.1's "out of date" / "already finished" notices; the row and status line say it instead.
18. **Telemetry.** `set_logged` still fires when the set is logged (at enqueue; `msToLog` unchanged). New: `set_sync_failed { status }` when an op becomes `failed`; `set_sync_delayed { ms }` when an op syncs more than 2 000 ms after it was enqueued. Neither carries an id, a name or a measure value (06.1 AC35's spy covers them).

### Docs and gates

19. **Two tabs cannot corrupt the outbox.** If a `storage` event shows another tab writing `sin:workout:outbox`, this tab stops draining and writing, and shows "This workout is open in another tab. Reload to continue here." with **Reload**. (Co-operation is Spec 06.5.)
20. **Coverage and docs.** `src/features/workouts/outbox/**` gets its own ≥ 90 % line gate in `vitest.config.ts`; the `src/auth`, `src/api`, `src/storage` and `src/features/workouts/**` gates still pass. DESIGN §5.3, the README roadmap and 06.1 §6.9 are updated as listed in "Cross-doc updates".
21. **Each of AC1–AC19 has ≥1 committed test tagged with its number** (`"06.2 ACn — …"`).

## 4. Data model

No server-side tables or migrations. New browser-storage keys, all under the new prefix `sin:workout:` (added to `USER_DATA_KEY_PREFIXES`):

| Key | Value | Written | Removed |
|---|---|---|---|
| `sin:workout:outbox` | `{ v: 1, ops: OutboxOp[] }` | after every op change | when empty; logout; lost session; AC17 |
Both are parsed with a zod schema on load; a value that fails to parse is dropped and reported once (`{ source: "workout-storage" }`), never thrown. `v` lets a later spec migrate the shape.

Size: one workout with a long session is a few tens of KB, far under the ~5 MB `localStorage` quota.

## 5. Screens & flows

*(UI spec — replaces "API surface". **No API change**: every request is Spec 05.0 / 05.1's.)*

### 5.1 Logging with no signal

1. The lifter taps **Log set**. The row appears at once with a "Saving…" marker; the entry row resets as today.
2. The status line reads "Offline — 1 set will save when you're back online". Finish is disabled: "1 set not saved yet".
3. They log two more sets, edit one, delete another: rows update at once (AC2 combines the ops).
4. Signal returns. The queue drains; markers disappear row by row; the status line goes; Finish is available.

### 5.2 A set that cannot be saved

The workout was finished on another device. On drain, `409 workout-finished` fails this workout's ops (AC17). Each affected row shows "Couldn't save" + **Discard**; the status line says "2 sets couldn't be saved". Discarding them all empties the outbox; the next refetch takes the gone path (06.1 AC29).

### 5.3 Reopening the tab

The phone evicted the tab during rest. On reopen with signal: the usual automatic sign-in, then the normal load, with pending rows overlaid until they sync. On reopen without signal: today's sign-in failure; the queue waits in storage until the next successful sign-in.

### 5.4 Other writes while offline

Add / move / remove exercise, start, finish, delete workout: unchanged pessimistic flows (06.1 §6.3); a network failure says "You're offline — try again when you have signal" with **Try again**.

## 6. Behavior & logic

### 6.1 Op lifecycle

```
enqueue ─▶ queued ──send──▶ sending ──2xx──▶ (removed; onSynced)
             ▲                  │
             └──retry (backoff)─┤
                                └──permanent──▶ failed ──Discard──▶ (removed)
```

`attempted` becomes true on the first transition to `sending` and never goes back (AC3). `sending` is persisted; on load, a `sending` op becomes `queued` with `attempted: true`, because its outcome is unknown. That is safe: a create replays by `clientGeneratedId`, a `PATCH` is idempotent, a delete's `404` counts as done.

### 6.2 Combining rules (AC2, AC3)

Applied at `enqueue`, against the last op for the same set:

| Existing op (never attempted) | New | Result |
|---|---|---|
| create | update | create, body merged |
| create | delete | both removed; `onSynced` not called; the row disappears |
| update | update | one update, later fields win |
| update | delete | delete only |
| any attempted op | any | appended as a new op |

### 6.3 Ids

A pending set's `id` is its `clientGeneratedId` (already a GUID, so `SetEntrySchema`'s id type holds; §12 D4). The outbox keeps a map `clientGeneratedId → server id`, filled when a create syncs, and persisted with the ops while any op still targets that key. Server ids and client keys never collide in practice (both v4 GUIDs).

### 6.4 Draining

`drain()` is a single loop guarded by an in-flight flag: pick the first op whose `nextAttemptAt ≤ now`, mark `sending`, call the REST client, apply §2 AC5. On success: drop the op, update the id map, call `onSynced(op, serverRow)`. The provider's `onSynced` writes the cache (AC12) with `setQueryData(active, …)`, matching by `clientGeneratedId` for a create and by id otherwise. Retry timers use an injected `clock` so tests run on fake time.

### 6.5 Where the projection is applied

Only in `QueuedWorkoutClient`: in `getActive()`, and in the values `createSet` / `updateSet` resolve with. TanStack Query's cache therefore always holds a projected workout, and no component calls `project()` itself. `onSynced` keeps the cache in step between reads.

### 6.6 After a reload (AC13)

A reload empties the in-memory token cache (DESIGN Q12), so the app signs in again through Auth0 before `ProtectedLayout` mounts the providers. Signing in is not logging out: nothing under `sin:workout:` is cleared. `WorkoutClientProvider` builds the outbox with `Me.id`, the outbox loads its ops (dropping other users', AC8), and the first `getActive()` overlays them. A create whose `POST` reached the server before the reload is found by its `clientGeneratedId` in the server copy (AC1), so it shows once; its op replays harmlessly (`200`, the stored row).

### 6.7 Network vs lost session (AC9)

`api/client.ts`'s `fetchOnce` today calls `onAuthLost` on any `getToken` rejection. It gains `isLostSession(cause)`: true only for an Auth0 error whose `error` is one of the five listed codes, and false whenever `navigator.onLine === false`. Otherwise it throws `ApiError.network(requestId, cause)`. The `src/auth` / `src/api` coverage gates apply.

### 6.8 A second tab (AC19)

A `storage` event fires only in *other* tabs. If one arrives for `sin:workout:outbox`, a second tab has written ops. This tab sets `conflict: true`, stops its drainer and its storage writes, and shows the reload notice. Reloading re-reads storage and starts cleanly. Spec 06.5 replaces this with co-operation.

## 7. Security & privacy

- **New data at rest.** `localStorage` now holds unsent set writes (measure values, set type; ids, no names). This is the same class as 06.0's catalog cache and recents. It is cleared on logout and on a lost session through `USER_DATA_KEY_PREFIXES`, and every write respects 06.1's logout write block.
- **No cross-user replay.** Ops carry the `userId` (AC8); a different user signing in on the same browser never sends or sees them, even if a clear was missed.
- **Lost session still clears** (§12 D6): a forced logout leaves no user data on the device, as 06.0 AC20 requires.
- **No new ingress.** Stored values are zod-parsed on load (§4), so a tampered key cannot inject an unexpected shape into the cache; the server re-validates every body anyway.
- **Observability hygiene.** New events carry a status code and a duration only (AC18).

## 11. Deployment & rollback

- **Web only. No API change, no migration, no env var.** Merge to `main` → Render static-site auto-deploy.
- **Order:** after 06.4 is merged. Independent of 06.3; re-run its smoke afterwards. 06.5 follows.
- **Known gaps until 06.5:** logout discards unsaved sets without warning; typed-but-unlogged values are lost when a tab is evicted; a second tab must reload.
- **Rollback:** revert the PR. A user who has ops in `sin:workout:outbox` at that moment loses them (the old code ignores the key, and logout clears it). Acceptable for staging; before any production rollback, check that no session is mid-workout.

## 12. Decisions & open questions

### Resolved (owner, 2026-10-03 brainstorming)

- ✅ **D1 — Only set writes are queued.** **Rationale:** sets carry a `clientGeneratedId` and replay safely; workout-exercise create has no key, so a replay after a lost response would duplicate the exercise, and queued sets under a queued exercise would need temporary parent ids and dependency ordering. The gym loop is "add once, log many". **Consequence:** structure, start, finish and delete stay pessimistic with an offline message; making them queueable needs an API follow-up first.
- ✅ **D2 — Outbox store + pure projection behind `WorkoutClient` (approach 1).** **Alternatives rejected:** TanStack Query's paused / persisted mutations (changes the hooks against 06.1 D4, needs a persister routed through `StorageAdapter`, spreads retry rules between the library and us, and makes combining ops awkward); a retry list with no projection (an offline-logged set would not appear until it synced).
- ✅ **D3 — Combine only never-attempted ops; freeze the rest.** **Rationale:** an attempted op may already be applied, so merging into it could send values the server will ignore (05.1 replays return the stored row). Freezing closes 06.1 D6.
- ✅ **D4 — A pending set's id is its `clientGeneratedId`.** **Rationale:** `SetEntry.id` is a GUID type; a `local:` string would break the type and the zod schema. The outbox's id map says which ids are still local.
- ✅ **D5 — `networkMode: "always"` for every workout mutation; the active query keeps the default.** **Rationale:** TanStack's default (`"online"`) pauses a mutation while `navigator.onLine` is false: an offline set tap would never reach the outbox, and an offline structure write, finish or discard would hang instead of showing AC15's "You're offline" message (found at implementation; the draft named the set mutations only). The active query keeps the default: while offline its refetches pause and the cached (projected) workout stays on screen.
- ✅ **D13 — A same-values re-tap within 600 ms is the same tap (found at implementation).** A queued log resolves at once, so 06.1 AC23's busy button no longer spans a double tap, and a double tap logged two sets. `EntryRow` ignores a second Log tap within 600 ms when nothing was typed in between. **Rationale:** nobody logs two identical sets that fast on purpose; a tap after any edit is never blocked. **Consequence:** 06.1 AC23's "one set per double tap" still holds.
- ✅ **D6 — A genuine lost session still clears the outbox and logs out.** **Alternative rejected:** keep the outbox bound to the user id and drain it when the same user signs back in. **Rationale:** rare (refresh-token revocation or expiry), cannot be confirmed with the user, and keeping 06.0 AC20's "a forced logout leaves no user data" is worth more. A token refresh that fails only because the network is down is **not** a lost session (AC9).
- ✅ **D7 — Split: 06.2 queue core, 06.5 resilience extras.** **Rationale:** the full design is two to three times 06.1's set-logging work, beyond the one-session rule. 06.2 alone meets "no logged set is lost".
- ✅ **D8 — Drafts will be persisted** (owner choice) — in 06.5, not here.
- ✅ **D9 — Logout with unsaved sets: try to sync, then warn, then allow** (owner choice) — in 06.5. Until then logout discards, as today.
- ✅ **D11 — No offline reopen; no workout snapshot (owner, 2026-10-03, at planning).** The first draft mirrored the active workout so a tab reopened without signal could render it. Tokens are memory-only (DESIGN Q12), so a reload must reach Auth0 before any protected screen renders; offline it never gets there. **Alternatives rejected:** persisting the refresh token (reopens Q12's XSS trade-off); storing a snapshot nothing reads yet (YAGNI). **Consequence:** the outbox alone survives a reload and drains after the next sign-in; an offline reopen shows today's sign-in failure.
- ✅ **D12 — Ops are bound to `Me.id`, not the Auth0 `sub`.** **Rationale:** 06.0 already scopes per-user storage by `Me.id`, and the workout providers mount only after `/v1/me` answers, so the id is always known there.
- ✅ **D10 — Retries are unlimited while the page is open**, backing off to 30 s. **Rationale:** the alternative (give up after N) turns a long dead zone into lost sets; a retryable failure is by definition not the data's fault.
