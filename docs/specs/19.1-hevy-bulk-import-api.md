## 1. Purpose, scope & non-goals

### Purpose

Carol's Hevy history (1,000+ workouts) must appear in SIN once, correctly, with records and charts complete, and with **no duplicate** of a session she also logged by hand or sent from SIN. Today's API can only start a live workout and edit finished ones (05.0, 07.4); there is no way to write a finished workout in one request. This spec adds that way, only for the Hevy importer and only for the gated account:

1. **Pure translation** of a Hevy workout into SIN's rows (sections from placeholders, sets, supersets, drops and skips, each reported), and of a Hevy routine into a routine write body, and of a Hevy template into a create-exercise prefill.
2. **One endpoint that imports a batch of up to 25 Hevy workouts,** idempotent per Hevy workout id, which also does the duplicate matching and records the link.
3. **One finish step** that rebuilds `personal_record` once, after the batches, resumable if the tab closed.

**Success:** a batch can be sent twice, or by two tabs, and creates each workout once; a workout SIN already has (sent from SIN, matched by day, time and name, or deleted in SIN earlier) is never created; every drop and skip is returned with a reason; records and History agree after the finish step; and a dry run of the same batch reports exactly what the real run will do without writing a byte.

### In scope

- **Phase A (pure `@sin/core`):** `HevyImportBatchSchema` and the result DTOs; `translateHevyWorkout`; `isDuplicateWorkout`; `translateHevyRoutine`; `exerciseFromHevyTemplate`.
- **Phase B (API):** `POST /v1/hevy/import/workouts` (`dryRun`), `POST /v1/hevy/import/finish`; the repository (`hevy-import.prisma.ts`); the `rebuildUserRecords` extraction; logs; a benchmark.

### Non-goals

- **Routine and custom-exercise import endpoints.** Routines go through the existing `POST /v1/routines` (its 50-routine cap, name rule and body limit apply as they are) and custom exercises through the existing `POST /v1/exercises` (its 500 cap), both called by the web (Spec 20.1) with bodies built by this spec's pure functions (D2).
- **Fetching from Hevy.** The server never calls Hevy (19.0); the browser sends the workouts it fetched.
- **Fetching new Hevy workouts after the one-time import,** Hevy's CSV, deleting in Hevy (design non-goals).
- **Relaxing any rule.** The import applies the finished-workout rules; it drops or skips, it never loosens them (§6.4).
- **Importing as a live workout,** per-set times (Hevy has none; D9), body measurements, social data.
- **A change to History, Progress, records or the export** other than the rows they now contain.

### Fit for one work session

Phase A is a pure translator with table-driven tests. Phase B is one repository with one transaction per workout, two routes, and a refactor of an existing function. Two PRs: **Phase A** AC1-AC14, **Phase B** AC15-AC36.

## 2. Acceptance criteria

Tag every test `describe("19.1 ACn — …")`. A criterion with several clauses has a test per clause. "The mapping" is Spec 19.0's; "a workout" in a criterion is a Hevy workout unless it says SIN.

### Phase A: pure `@sin/core`

1. **Request and result schemas.** `HevyImportBatchSchema` is strict: `{ dryRun: boolean, workouts: ImportWorkout[1..25] }`, `ImportWorkout = { hevyWorkoutId (1-64), title (≤ 200) | null, description (≤ 20000) | null, startTime, endTime (ISO with offset), tzOffsetMinutes (−720 … 840), exercises[0..200] }`, each exercise `{ exerciseTemplateId (1-64), notes | null, supersetId (integer ≥ 0) | null, sets[0..200] }`, each set `{ type (HEVY_SET_TYPE_VALUES), weightKg, reps, distanceMeters, durationSeconds, rpe, customMetric }` (all numbers nullable, finite). Exercises arrive in workout order. An unknown key, a 26th workout and a 201st set are rejected. `HevyImportResultSchema` is `{ hevyWorkoutId, outcome, workoutId, matchedWorkoutId, unpaired[], drops[], notices[], exerciseCount, setCount }` with `outcome` in `create, already_imported, sent_from_sin, already_matched, deleted_in_sin, duplicate, unpaired, no_usable_sets, time_invalid, rejected`, and `drops` / `notices` arrays of `{ code, count }` over fixed code lists: drops `exercise_skipped, exercise_no_sets, set_missing_measure, set_forbidden_measure, set_out_of_range`; notices `custom_metric_ignored, assist_weight_ignored, placeholder_sets_ignored, section_empty, sections_over_limit, section_name_trimmed, section_notes_trimmed, superset_over_limit, title_trimmed, notes_trimmed`; routine notices `name_trimmed, items_cut, rest_clamped, superset_cut, time_targets_not_kept, distance_targets_not_kept, sets_cut, notes_trimmed, section_empty, sections_over_limit, section_name_trimmed, section_notes_trimmed`. A placeholder's own sets are counted as `placeholder_sets_ignored`. An unpaired template id appears once in `unpaired[]`, in first-seen order.
2. **Times.** `translateHevyWorkout` returns `time_invalid` when `endTime` is before `startTime`, when either does not parse, when the start is before `2000-01-01T00:00:00Z`, or when the end is more than 5 minutes after the caller's `now` (`WORKOUT_START_EDIT_FLOOR`, `WORKOUT_FUTURE_SKEW_MAX_MS`). An end equal to the start is valid. `localDate` is `localDateFor(startTime, tzOffsetMinutes)`; `startedAt` / `endedAt` are the instants unchanged.
3. **Sections.** Walking the exercises in order: a `warmup_placeholder` pair starts a section `Warm-up`; a `workout_placeholder` starts a section named by the first line of its notes (`Workout` if empty) with the remaining lines as the note (19.0 AC10); exercises before the first placeholder are loose; exercises after a placeholder belong to its section until the next; a placeholder's own sets are ignored; **an Accessory section is never created** (its exercises stay in the preceding section); a section left with no exercises is not created (notice `section_empty`); at most `ROUTINE_SECTIONS_MAX` (8) sections are created, a ninth and later placeholder is ignored and the exercises after it stay in the eighth (notice `sections_over_limit`, counted).
4. **Exercises.** For each exercise the pair is looked up by template id. Missing pair, or `role: "exercise"` whose exercise the caller's `ctx` marks inactive or absent: the template id goes to `unpaired[]` (each once) and the outcome is `unpaired` with **nothing else computed** (precedence: `time_invalid` first, then `unpaired`, then the rest). `role: "skip"`: its sets are dropped with code `exercise_skipped` (count = sets) and the exercise is not stored. An exercise in which no set survives is not stored (drop `exercise_no_sets`, count 1). Stored exercises carry the paired SIN exercise's id, current name (snapshot) and modality (snapshot), the Hevy notes (control characters removed, cut to the exercise-notes limit with notice `notes_trimmed`).
5. **Sets.** Every set is translated by 19.0's `hevySetToSin` with the pair's modality, rule and the user's unit; a drop is counted under its code (`set_missing_measure`, `set_forbidden_measure`, `set_out_of_range`); `custom_metric_ignored` and `assist_weight_ignored` notices are counted. Surviving sets are numbered from 1 in order, `isComplete: true`, with no completion time.
6. **No usable sets.** A workout whose stored exercises are all empty or whose every exercise was a placeholder or skipped yields `no_usable_sets` (with its drops, so the summary can say why). Placeholder-only and empty Hevy workouts are covered.
7. **Supersets.** Each distinct Hevy `supersetId` among stored exercises becomes a SIN `supersetGroup` `1, 2, 3…` in order of first appearance; a group left with one stored member becomes `null`; placeholders never carry a group; the value never exceeds 99 (a 100th group is `null` with notice `superset_over_limit`).
8. **Text.** `title`: control characters removed, trimmed, cut to `WORKOUT_TITLE_MAX` (notice `title_trimmed`), an empty result is `null` (never `"Workout"`: the History row already shows a fallback). `description` becomes `notes`: control characters other than TAB, LF, CR removed, cut to `WORKOUT_NOTES_MAX` (notice `notes_trimmed`), empty is `null`. Cuts never split a surrogate pair: they go through a code-point helper (`cutCodePoints`), not `Intl.Segmenter` (AC14); trimming alone is not a cut and sets no notice (a title of only spaces or control characters is `null` with no `title_trimmed`).
9. **Units.** For a `kg` user the stored weight is the Hevy kg rounded to 0.1; for a `lb` user the converted lb rounded to 0.1 (`61.235` kg → `135`); `weightUnit` is the user's unit; distances are `m`; the same inputs give the same rows on every run (no clock, no randomness; ids are the repository's).
10. **`isDuplicateWorkout(h, s)`** is true iff all hold: `h.localDate === s.localDate`; `|h.startedAt − s.startedAt| ≤ 1 hour` (inclusive); and **names match**: when both have a non-empty title, the titles are equal after trimming, collapsing inner whitespace runs and lowercasing; when either has no title, the two sets of lineage roots `A` (Hevy's mapped exercises) and `B` (the SIN workout's) satisfy `2 × |A ∩ B| > max(|A|, |B|)` (and neither is empty). Two different non-empty titles are never a match, whatever the exercises. A truth table pins each clause, the boundary at exactly 1 h, 3,600.001 s, one shared of two (not a match), two shared of three (match), and the empty cases.
11. **`translateHevyRoutine(routine, ctx)`** returns `{ ok: true, input, notices }` or `{ ok: false, reason: "unpaired", unpaired }` or, when no item is left after skips, placeholders and the item cap, `{ ok: false, reason: "no_items", unpaired: [] }` (the body would fail `RoutineWriteSchema`'s `items.min(1)`; the UI says "nothing to import"). `input` is a `RoutineWrite` (the existing write type) in the `sets` form (never the quick-line keys): `name` the title trimmed and cut to 80 (notice `name_trimmed`); items in order; placeholders become sections (`sections[].key` `s1`, `s2`…, as the editor mints them; same naming as AC3; at most 8; loose-first order kept); `skip` pairs omitted; items cut to `ROUTINE_ITEMS_MAX` (30, notice `items_cut`); `rest_seconds` clamped to 0-900 (notice `rest_clamped`); supersets as in AC7 but a group is kept only with 2-8 members (a single member → none; extra members beyond 8 → none, notice `superset_cut`); planned rows: type mapped, Hevy `rep_range` → `repsLow`/`repsHigh` (clamped to 1-100, ordered), else `reps` ≥ 1 → both, weight converted (0.1 of the user's unit) **only if the SIN modality takes weight**; reps are omitted for every modality whose measure table forbids reps (`calories`, `weight_distance`, `weight_duration`, `duration`, `distance_duration`); duration and distance targets are not kept (notices `time_targets_not_kept`, `distance_targets_not_kept`); rows cut to `PLANNED_SETS_PER_ITEM_MAX` (20, notice `sets_cut`); item notes cut to 500. No routine-level notes are written (Hevy's read shape has none). The output parses with `RoutineWriteSchema` and passes the editor's `plannedSetViolations` for every item (a test runs both over every fixture).
12. **`exerciseFromHevyTemplate(template)`** returns a `CreateExercise` prefill: `name` the title (cut to 120), `modality` from the type table (`reps_only` → `calories` when the title contains `(calories)`, else `bodyweight_reps`; `bodyweight_assisted_reps` → `bodyweight_reps`), `primaryMuscleId` / `secondaryMuscleIds` / `equipmentId` through the 19.0 tables (unmatched → `null` / dropped; secondary deduplicated, without the primary, at most 4), and a `suggestedRule` (`calories_as_reps` for the calories case, `assist_weight_ignored` for assisted, else `null`) the UI shows and the user confirms. It parses with `CreateExerciseSchema`.
13. **Static messages.** `packages/core/test/static-issue-messages.test.ts` passes with the new schemas probed.
14. **Purity and exports.** Every new export is in `check-exports.mjs` and the barrel type test; `core:purity` passes; none of the functions reads a clock, `Intl`, `Math.random` or the DOM (the caller passes `now`).

### Phase B: endpoints

15. **Gate, group, publication.** Both routes sit behind 19.0's gate (`404` for anyone not allowed), are unpublished, declare `writeGroup: "hevy"`, and the assembly gates pass. `bodyLimit` is 512 KiB; a larger body is the existing `413`. A batch of 0 or more than 25 workouts, an unknown key or a bad value is `422` with static messages and writes nothing.
16. **Dry run writes nothing.** `dryRun: true` runs every read and the whole translation and returns the results the real run would, with `workoutId: null`. Before and after, the row counts of `workout`, `workout_section`, `workout_exercise`, `set_entry`, `hevy_link`, `hevy_account` and `personal_record` are equal; `records_stale` is unchanged. A dry run and then a real run of the same batch give the same outcomes, counts, drops and notices (a test compares them, with `workoutId` ignored).
17. **A created workout.** A real run of a `create` result inserts, in one transaction: a `workout` with `source = 'hevy'`, the translated times, `local_date` and `tz_offset_minutes` from the request offset, `title`, `notes`, a random `client_generated_id`, no routine columns, no `planned_duration_s`; its sections (`added_in_workout = false`, positions from 0); its exercises (positions from 0 in order, snapshots, `superset_group`, `section_id`); its sets (`set_number` from 1, `is_complete = true`, `completed_at` NULL, `weight_unit` the user's unit, `distance_unit` `m`, `calories` only on calories exercises); and a `hevy_link` (`origin: "imported"`, `synced_fingerprint` the fingerprint of the stored workout, `synced_at` now). `GET /v1/workouts/{id}` returns it with every field valid under the response schema; History lists it in start-time order beside manual workouts (the 07.1 cursor, no change).
18. **The finished-workout rules apply.** Every stored set passes `assertSetMeasuresValid(modality, { …, isComplete: true })`, every exercise has at least one set, the workout has at least one set, `ended_at ≥ started_at`, the section count is ≤ 8. A test that feeds the repository a translated body corrupted after translation (a forbidden measure, an incomplete set, an inverted time) gets outcome `rejected`, no row written, no `500`, and the other workouts in the batch unaffected. A Postgres `23503` (an exercise deleted or retired between the context load and the write) or `23514` is likewise `rejected`.
19. **Idempotent per Hevy workout id.** Sending the same batch again returns `already_imported` (or `sent_from_sin` / `already_matched` by the link's origin) for every workout and writes nothing; two concurrent identical batches (`Promise.all`) create each workout once, the loser answering `already_imported`; the unique index `hevy_link_hevy_id_key` is the guard and no half-written workout remains from the loser.
20. **Links decide skips.** A Hevy workout whose id is linked to a SIN workout with `origin: "sent"` is `sent_from_sin`; with `imported` / `matched`, `already_imported` / `already_matched`; a link with `workout_id IS NULL` (the SIN workout was deleted) is `deleted_in_sin`. None writes anything, none is translated beyond the lookup (an unpaired exercise in such a workout does not matter).
21. **Duplicate matching.** For a Hevy workout with no link, the candidate SIN workouts are the caller's **finished** workouts with the same `local_date` and a start within one hour either side that have no Hevy link; of those, `isDuplicateWorkout` decides, using lineage roots on both sides (a fork and its built-in are the same root); with several matches the nearest start wins, then the lowest id. A match yields `duplicate` with `matchedWorkoutId` and, on a real run, a `hevy_link` (`origin: "matched"`, `synced_fingerprint` the matched workout's current fingerprint) and no new workout. A live workout, a workout already linked to another Hevy id or holding a claim (a Send that never completed, D22), another user's workout, and a workout 61 minutes away are never candidates. Two Hevy workouts matching one SIN workout within one request: the first links it, the second sees it claimed and is created (D6), in the dry run and the real run alike (an in-request set of claimed SIN workout ids). If a Send in another tab links the candidate between the candidate read and the link insert (`23505` on `hevy_link_workout_key`), that candidate is dropped and the candidate step re-run once, then the workout is created; never a `500`. A `23505` on `hevy_link_hevy_id_key` answers `already_imported`. A batch that carries one Hevy id twice creates the first and answers `already_imported` for the second.
22. **Unpaired.** A workout with any unmapped exercise (or a mapped one whose SIN exercise is retired) returns `unpaired` with the template ids and writes nothing for it; the rest of the batch proceeds; after the mapping gains the pairs, the same workout imports.
23. **Everything dropped is reported.** For each result, `drops` and `notices` carry the codes and counts of AC4-AC8 (a test builds one workout with every kind of drop and asserts each count); a workout that creates with drops is still `create`; the sum of kept and dropped sets equals the sets received (placeholder sets excluded and counted separately as ignored).
24. **Per-workout atomicity and resume.** Each created workout is one transaction; an error inside it (an injected failure after the set-insert statement, through a repository seam that fires after each write statement: workout, sections, exercises, sets, link) rolls back that workout, its sections, exercises, sets and link, leaves the batch's earlier workouts committed, and returns `500` only for the unexpected error class (the client retries the batch); sending the whole batch again completes the rest with no duplicate.
25. **The stale-records flag.** A real run that creates at least one workout sets `hevy_account.records_stale = true` in the same transaction as that workout (insert-or-update); a dry run, a batch of only skips and a batch of only matches do not set it. `GET /v1/hevy/status` reports it. No batch recomputes records or takes `lockUserRecords`.
26. **Finish.** `POST /v1/hevy/import/finish` (no body, `writeGroup: "hevy"`) in one transaction takes `lockUserRecords` **first**, then locks the `hevy_account` row; if `records_stale` is false, or there is no `hevy_account` row yet (none is inserted), it returns `200 { recomputed: false, rootCount: 0 }`; otherwise it rebuilds the caller's `personal_record` rows exactly as `records:rebuild --user` does (the same extracted function), clears the flag and returns `{ recomputed: true, rootCount }`. Calling it twice is safe; after a successful finish `personal_record` equals a full recompute (a test compares to `rebuildRecords` output on the same data); `recordCount` on History and `GET /v1/personal-records` reflect the imported workouts; `records:rebuild --user` output and tests are unchanged by the refactor.
27. **Lock order and concurrency.** One real-concurrency test: a finish (of an imported batch) and a live workout's finish for the same user at the same time end in a serial outcome with no `500` and no `40P01`, and `personal_record` equals a full recompute. Concurrent batches and a finish do not deadlock (batches take no PR lock).
28. **A live workout is untouched.** With a live workout in progress, import batches succeed; the live workout, its sets and the one-active index are unchanged; finishing it afterwards computes records over the lineage including the imported history (and the final import finish corrects any earlier state).
29. **Units.** For a `kg` user and for a `lb` user, an imported 61.235 kg set stores `61.2` kg and `135` lb with `weight_unit` set accordingly and `weight_kg` generated (`61.235` for the lb case: `135 × 0.45359237 = 61.23497`, rounded by `NUMERIC(7,3)`); the stored `weightKg` of a lb set is what the records engine sees.
30. **Records agree end to end.** Importing a fixture history (a PR progression across 12 workouts on a `weight_reps` exercise, a calories exercise through `calories_as_reps`, a farmer carry through `short_distance_weight`), then finish, gives the same `personal_record` rows and the same progress series as logging the same sets through the ordinary API on a second user (compared field by field, modulo ids and `completed_at`).
31. **Export and purge.** `GET /v1/account/export` contains the imported workouts (`source: "hevy"`) and the links; the purge test removes them; a workout deleted by `DELETE /v1/workouts/{id}` leaves its tombstone link (19.0 AC31) and a re-import answers `deleted_in_sin`.
32. **Logs.** `hevy_import_batch` (`dry_run`, `workouts`, and counts per outcome, `sets_created`, `sets_dropped`, `ms`) and `hevy_import_finished` (`recomputed`, `root_count`, `ms`) at `info`, with `user_id`; no title, id or name. `telemetry/allowlist.ts` and `views.ts` are untouched.
33. **Latency.** `bench:hevy-import` (a dev tool in the style of `bench:finish`: Docker, not CI) seeds one user with 1,500 finished workouts of 10 exercises × 5 sets, then imports 1,500 more in batches of 25 (real runs) and runs the finish: p95 per batch under 2 s, the finish under 10 s on local Postgres; results recorded in the PR. If the finish exceeds it, the PR records the number and the runbook's `records:rebuild --user` (B5a) is the documented fallback.
34. **Existing behavior unchanged.** `POST /v1/workouts` still stores `source = 'manual'`; every existing workout, History, edit and records test passes; the `workout_source_check` is not touched (19.0 widened it).
35. **Static messages and redaction.** Validation texts are fixed; no log or error body contains a Hevy title, note or id.
36. **CI.** `lint`, `typecheck`, `core:purity`, the OpenAPI drift check (no change), `test:unit`, integration and the app-assembly gates pass.

## 4. Data model

**No migration.** Every table and the widened `workout_source_check` come from Spec 19.0's `0016`. This spec adds no column, index or constraint. It writes `workout`, `workout_section`, `workout_exercise`, `set_entry`, `hevy_link` and `hevy_account` rows with the same column lists the existing repositories use (`SET_ENTRY_COLUMNS`, `workout-section.prisma.ts`, `workout.prisma.ts`).

Access paths: the link lookup is `hevy_link_hevy_id_key`; the candidate query is `workout_user_started_idx` (`user_id`, `started_at DESC`) bounded to a two-hour range; the roots come from `workout_exercise` by `workout_id` and the `exercise` primary key.

## 5. API surface

Both routes: `/v1`, bearer, behind the 19.0 gate, unpublished, `writeGroup: "hevy"`.

### 5.1 `POST /v1/hevy/import/workouts`

Request: `HevyImportBatchSchema` (AC1). Response `200`:

```json
{ "dryRun": false,
  "results": [
    { "hevyWorkoutId": "b459cba5-…", "outcome": "create", "workoutId": "0192…", "matchedWorkoutId": null,
      "unpaired": [], "drops": [ { "code": "set_missing_measure", "count": 2 } ],
      "notices": [ { "code": "custom_metric_ignored", "count": 1 } ], "exerciseCount": 6, "setCount": 21 },
    { "hevyWorkoutId": "…", "outcome": "unpaired", "workoutId": null, "matchedWorkoutId": null,
      "unpaired": ["D04AC939"], "drops": [], "notices": [], "exerciseCount": 0, "setCount": 0 } ] }
```

`results` has one entry per request workout, in request order. `workoutId` is null on a dry run and for every outcome except `create`. Problems: `ValidationError` (422), the existing `413`/`429`. A failure inside one workout's write is reported as `rejected` (an invariant check, AC18) or aborts the request with `500` (an unexpected error, AC24); earlier workouts stay committed.

### 5.2 `POST /v1/hevy/import/finish`

No body. `200 { "recomputed": true, "rootCount": 41 }`. Problems: none beyond the common ones.

## 6. Behavior & logic

### 6.1 Per workout, in order

1. **Link lookup** by `(user_id, hevy_workout_id)` → outcomes of AC20; stop.
2. **Translate** (`translateHevyWorkout`, pure) → `time_invalid`, `unpaired`, `no_usable_sets`, or an `ImportedWorkout`.
3. **Duplicate candidates** (AC21) → `duplicate`; stop.
4. **Dry run:** stop with `create`.
5. **Write:** one transaction (§6.2).

The mapping, the user's unit and the exercise table (id → modality, name, active, root) are loaded **once per request**, not per workout; a batch is therefore translated against one consistent mapping.

### 6.2 The write transaction

```
BEGIN
  INSERT workout (source 'hevy', ended_at set) …
  INSERT workout_section …, INSERT workout_exercise … (one multi-row statement), INSERT set_entry … (one multi-row statement)
  INSERT INTO hevy_link (…) ON CONFLICT (user_id, hevy_workout_id) WHERE hevy_workout_id IS NOT NULL DO NOTHING RETURNING id
    -- no row returned: another request linked this id first -> ROLLBACK, outcome already_imported
  INSERT INTO hevy_account (user_id, records_stale) VALUES (…, true) ON CONFLICT (user_id) DO UPDATE SET records_stale = true, updated_at = now()
COMMIT
```

Workout, section, exercise and set ids are generated in the application (UUIDv7), so the multi-row inserts need no `RETURNING`. The `workout_exercise_position_key` is deferrable and positions are inserted dense and ascending, so no deferral is needed. No `lockUserRecords`, no recompute (D3). The fingerprint stored in the link is computed by loading the just-written workout inside the transaction, through the client-parameterized detail reader (`readWorkoutDetail(tx, …)`, added by 19.0 Phase B) (`hevyFingerprintSource` + SHA-256, the 19.0 §6.5 function).

### 6.3 Duplicate matching (server)

```sql
SELECT w.id, w.title, w.started_at, w.local_date,
       array_agg(DISTINCT COALESCE(e.forked_from_exercise_id, e.id)) AS roots
FROM "workout" w
JOIN "workout_exercise" we ON we.workout_id = w.id
JOIN "exercise" e ON e.id = we.exercise_id
WHERE w.user_id = $user AND w.ended_at IS NOT NULL AND w.local_date = $localDate::date
  AND w.started_at BETWEEN $start - interval '1 hour' AND $start + interval '1 hour'
  AND NOT EXISTS (SELECT 1 FROM "hevy_link" l WHERE l.workout_id = w.id)   -- a claim-only row too (D22)
GROUP BY w.id
```

The decision is `isDuplicateWorkout` over the rows (the SQL narrows, the pure function decides). The Hevy side's roots are the lineage roots of its mapped SIN exercises (resolved with the exercise table loaded per request).

### 6.4 "Same validation as a finished-workout edit"

The importer never writes a state a finished edit would refuse (07.4): required measures present on every stored set, forbidden measures null, distance within `SET_DISTANCE_MAX` after conversion, a workout with at least one set, a section count ≤ 8, times consistent. The translator enforces them by dropping; the repository re-checks with the same pure functions as a last line (AC18) and reports `rejected` rather than writing. It does **not** take the edit path's `withWriteMode` or its per-edit record recompute, because there is no live phase and the recompute is deliberately deferred to the finish step (D3). It does bypass two **creation** bounds that do not apply to history: the 7-day `startedAt` window and the one-active-workout rule (the row is finished at insert).

### 6.5 Finish

```
BEGIN
  lockUserRecords(user)                       -- FIRST (07.0 D9)
  SELECT records_stale FROM hevy_account WHERE user_id = $user FOR UPDATE
  if not stale: COMMIT, return { recomputed: false }
  rebuildUserRecords(tx, user)                -- extracted from rebuildRecords; same roots, same writes
  UPDATE hevy_account SET records_stale = false
COMMIT
```

`rebuildRecords(prisma, log, opts)` keeps its signature and per-user transaction and calls `rebuildUserRecords(tx, userId)`; its tests are unchanged. Re-running after a failure is safe (the flag stays set until the commit).

### 6.6 Why this order of work

Workouts first, finish second, routines last (Spec 20.1): history is the value and the only part with a correctness invariant (no duplicates, records right); routines can fail on caps and names without harming it.

## 7. Security & privacy

- **Authorization boundary.** The 19.0 gate plus `user_id = request.user.id` in every statement. A Hevy id cannot reach another user's rows: links are unique per `(user_id, hevy_workout_id)`.
- **Untrusted input.** The batch is the browser's rendering of a third party's JSON. It is schema-validated, bounded (25 × 200 × 200), and every string is sanitized (control characters, length) before storage; numbers are checked against the same bounds as ordinary sets, and the repository re-validates. No Hevy string is ever used as SQL text, a log field or an identifier.
- **Volume abuse.** Owner-only; `hevy` write group; body limit 512 KiB; the in-flight cap; one transaction per workout, no long locks (the only user-wide lock is in `finish`).
- **No PII in logs** (AC32, AC35); the Hevy key is not in any request (19.0 AC34).
- **Data minimization.** Only the fields SIN stores are accepted: `custom_metric` is accepted in the schema (so the client can forward Hevy's shape unfiltered) and discarded, counted.

(2) This spec's Phase A (pure) can merge any time after 19.0 A. (3) Phase B: no migration, no release step; ordinary merge-to-`main`. Production by `deploy-prod`. The gate means nothing reaches any other user.
- **Runbook entry** (`docs/runbooks/hevy-import.md`, new, with Phase B): the order of the one-time import; where a stuck `records_stale` shows (`GET /v1/hevy/status`) and the fix (`POST /v1/hevy/import/finish` from the UI, or `DATABASE_URL='<url>' pnpm --filter @sin/api run records:rebuild --user <id>` then `UPDATE hevy_account SET records_stale = false WHERE user_id = '<id>'`); how to undo an import (below).
- **Rollback and undo.** Code: `git revert`. Data: imported rows are findable by `source = 'hevy'`; a full undo is, for the user, `DELETE FROM workout WHERE user_id = '<id>' AND source = 'hevy'` (cascades to sections, exercises, sets, and sets the links' `workout_id` to NULL), then `DELETE FROM hevy_link WHERE user_id = '<id>' AND origin = 'imported'` (and, if wanted, the same for `matched`), then `records:rebuild --user`. That statement is in the runbook and is not a release step. An old web bundle would reject a response containing `source: "hevy"` only if 19.0 Phase A had not reached it, which §11 order (1) prevents.
- **Smoke (staging, after Phase B):** a dry run of one fixture workout (`dryRun: true`) returns `create`; a real run, a repeat (`already_imported`), `GET /v1/workouts/{id}`, then `DELETE` it; finish returns `recomputed: true` and a second call `false`.

## 12. Decisions & open questions

- **D1 ✅ The server translates, from a thin request that mirrors Hevy's shape (mine).** Rationale: the rules that make an import safe (pairing, drops, the finished-workout checks, the duplicate decision) belong where the data and the mapping are; the browser only fetches and forwards. A single pure function serves the dry run and the write, so the summary cannot disagree with the result (AC16). The web's mapping from Hevy's snake_case to the request is mechanical and tested in 20.1.
- **D2 ✅ Routines and custom exercises use the endpoints that exist (mine).** Rationale: they already enforce the 50- and 500-item caps, name rules, limits and the export; a second path would duplicate each. The pure functions here give the web correct bodies; idempotency for routines is the unique routine name (a second run gets `routine-name-taken`, reported as "already there"), and for exercises the check-the-list-first rule the bulk create already follows (10.4 AC27).
- **D3 ✅ Records are recomputed once, at the end, by a flag-and-finish step (Carol/mine: once at the end).** Rationale: per-workout recompute would run `lockUserRecords` and a lineage reload 1,000 times. The flag makes "the tab closed" recoverable and visible (`GET /v1/hevy/status`), and the finish is the existing rebuild under the existing lock order, so no new locking story. Rejected: recompute per batch (cost, and a half-imported lineage produces `previousValue`s that are then rewritten anyway); a background job (no queue infrastructure; GA item).
- **D4 ✅ Duplicate detection runs on the server (mine).** Rationale: it needs the caller's SIN workouts with lineage roots; the client would have to page all of History to know them. The pure `isDuplicateWorkout` keeps the rule testable and shared.
- **D5 ✅ "Names match" is read as the design agreed: equal titles, or, when either is untitled, more than half the larger set of lineage roots in common (mine, Carol agreed with the reading).** Rationale: two titled workouts with different titles are different sessions even on one day; an untitled SIN workout (the common case for a free-form session) needs the exercises to decide; "most" is strictly more than half so a one-of-two overlap is not a match. Roots, not ids, so a fork and its built-in count as the same exercise.
- **D6 ✅ A SIN workout is matched by at most one Hevy workout (mine).** Rationale: two Hevy workouts in one day an hour apart sharing exercises are two sessions (a morning and evening lift); letting the first claim the SIN workout and creating the second is the safe error. The in-request claimed set applies in the dry run too, so a dry run and the real run of one batch agree even in that case.
- **D7 ✅ Skips are outcomes, not errors; the summary is the server's own dry run (mine).** Rationale: every skip reason (`sent_from_sin`, `already_imported`, `deleted_in_sin`, `duplicate`, `unpaired`, `no_usable_sets`, `time_invalid`) is a normal state the lifter wants listed by date and title; one response shape serves the summary and the progress.
- **D8 ✅ A workout with an unmapped exercise is not imported partially (mine).** Rationale: dropping a whole exercise's sets because the lifter has not paired it yet would silently change her history and records; the pairing screen exists to remove that state. An exercise she wants gone is paired as `skip`, which is reported.
- **D9 ✅ Imported sets have no completion time and are `is_complete`; the workout keeps Hevy's duration (mine).** Rationale: Hevy has no per-set times; inventing them would be false data. `completed_at` is nullable everywhere it is read (07.4), `personal_record` orders by workout start and position, and the design says an imported workout keeps the duration Hevy shows (`started_at`/`ended_at` copied).
- **D10 ✅ Logs only (mine).** Same rationale as 19.0 D17.
- **D11 ✅ One transaction per workout, not per batch (mine).** Rationale: one bad workout must not roll back 24 good ones, and a failure leaves a state the next identical request completes; the cost is 25 small commits per batch, which the benchmark bounds.
- **D12 ✅ Imported workouts do not copy a routine or a routine name (mine).** Rationale: Hevy's `routine_id` refers to Hevy's routine, which may not be imported; History shows no routine line for them, which is true to the data.

- **D13 ✅ The test seam fires after each write statement (mine, from the build plan).** Rationale: §6.2 inserts all sets in one multi-row statement, so "the third set insert" cannot be injected; the seam names the step (`workout`, `sections`, `exercises`, `sets`, `link`, plus `match` for the match path).
- **D14 ✅ Planned rows carry no reps wherever the measure table forbids reps (mine).** Rationale: `plannedSetViolations` would otherwise reject `duration` and `distance_duration` rows, failing AC11's own check.
- **D15 ✅ A routine with no kept items is `no_items`, not a body (mine).** Rationale: `RoutineWriteSchema` requires at least one item; the UI shows it as nothing to import.
- **D16 ✅ A concurrent Send mid-import retries the match once, then creates (mine).** Rationale: the candidate was valid when read; dropping it and re-reading is correct and cheap, and creating is the safe fallthrough.
- **D17 ✅ Finish with no `hevy_account` row answers "not recomputed" and inserts nothing (mine).** Rationale: no batch has created anything, so there is nothing stale.
- **D18 ✅ AC29's lb weight is 61.235 kg (mine).** Rationale: the arithmetic and the column's rounding give 61.235; the earlier 61.234 was a draft slip.
- **D19 ✅ A routine superset never spans a section (mine, from the Phase A build).** Rationale: `RoutineWriteSchema` refuses a span (09.2), and AC11 requires every output to parse, so AC11's groups are per (section, Hevy superset id). "Extra members beyond 8 → none" is read literally: the first 8 keep the group, the rest lose it (`superset_cut`, once per group). The workout side keeps AC7 as written, because a workout's sections are stored as sent (09.4).
- **D20 ✅ Blank names and unsupported types (mine, from the Phase A build).** A routine title that is blank after cleaning is named "Hevy routine", a template title "Hevy exercise" (both schemas need a name). `exerciseFromHevyTemplate` returns `null` for a template whose type SIN does not support (`readHevyType` gives `null`): such a template can only be paired as a skip. Control characters are removed from a placeholder's notes before 19.0's `sectionFromPlaceholder` reads them, because SIN's section schemas refuse them.
- **D21 ✅ Routine rows and notice counts (mine, from the Phase A build).** An unknown Hevy set type in a routine plans as `working`; a weight of 0 is no weight; fractional reps and rest round to the nearest whole. Per-item notices count only for items kept after the 30-item cap; `items_cut` counts the items removed; `time_targets_not_kept` / `distance_targets_not_kept` count per row. A section the cap empties is removed with no further notice. A 0 in a forbidden measure (19.0's `zero_forbidden`) loses nothing and has no notice code.
- **D22 ✅ A claim is not a candidate (mine, from the Phase B review; owner may revisit).** A SIN workout holding any `hevy_link` row, a claim-only one included, is not a duplicate candidate. §6.3 first excluded only linked rows, so a claim left by a Send whose `complete` never arrived made the dry run answer `duplicate` while the real run's insert hit `hevy_link_workout_key` and created (AC16 broken without any race). Both runs now answer `create`. The cost: that workout's Hevy copy is imported as a second SIN workout. The alternative, matching it (turning the claim into a `matched` link), is the owner's call. The matched-link transaction also reads the SIN workout `FOR SHARE` first, as 19.0's complete does, so a delete during the match answers `taken` (then `create`), never a `500`.

### Owner questions (resolved 2026-10-26)

- **O1. Which end of the history first?** Carol's SIN-logged workouts overlap only her recent Hevy history (the duplicates).
