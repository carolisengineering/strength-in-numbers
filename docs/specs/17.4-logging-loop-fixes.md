# Spec 17.4 — Logging loop fixes: the next set, the Log button, the status line, the panel's place (web)

**Status:** v0.3 (2026-11-08), implemented on branch `feat/spec-17-4-logging-fixes`; D2 and the 44 px status line settled by the owner. The AC22 phone check is owed.

**Source:** the whole-app Impeccable critique of 2026-11-08 (23/40), step 1 of its agreed fix order. The owner reported that recording sets is clunky and kept the large numbers and buttons. The owner's decision on the next set is D1 below.

**Design refs:** DESIGN.md §4.3 and Q20 (planned sets, prefill); Spec 10.2 AC22, AC24, AC25, D1, D4 (seeding); Spec 17.1 AC9, AC14–AC15, AC21, AC24, AC25, AC29, AC35, AC39 (the "now" screen); Spec 06.2 (outbox); Spec 06.5 (drafts); `apps/web/DESIGN.md`.

---

## 1. Purpose, scope & non-goals

**Purpose.** Make logging hold up when the prefilled number is wrong. Today the next set forgets what the lifter just did, the panel drifts behind the bar as sets are logged, the Log button is the smallest control in the panel, and a status line can move that button by three quarters of its height under the thumb.

**In scope.**
1. The rule for the next set's prefill (`seedDraft`).
2. A taller button in the workout screen's bottom bar.
3. One fixed status line in that bar.
4. Keeping the current-set panel in view after each log.

**Non-goals (later steps of the fix order, each its own spec).**
- Undo after a log, and protecting Delete set (step 2).
- The records panel on the summary (step 3).
- Replacing dropdowns, a Warm-up toggle, moving Superset and Add note (step 4).
- The docked panel (step 5, mockup first).
- Any API, schema or `packages/core` change.
- Other screens' action bars, which keep their 44 px buttons and hints.

## 2. Acceptance criteria

### The next set (`seedDraft`, D1–D3)

Here, `last` is the last logged set, `prevRow` is the planned row it was logged against (`plannedSets[sets.length - 1]`), and `row` is the next planned row (`plannedSets[sets.length]`).

1. **A weight change carries on a level plan.** Plan 185, 185, 185 lb; the lifter logs 190. The next draft shows 190. Holds when `last.weight` is not null, `prevRow` and `row` have the same planned `weight` and `weightUnit`, and AC5's type rule passes.
2. **Reps inside the range carry.** Plan 6–8; the lifter logs 8. The next draft shows 8, and one tap repeats it. Holds when `last.reps` is not null, `row.repsLow ≤ last.reps ≤ (row.repsHigh ?? row.repsLow)`, and AC5's type rule passes.
3. **Reps outside the range go to the low end.** Plan 6–8; a set of 5 or a set of 10 is followed by a draft of 6. Plan exactly 5; a set of 6 is followed by a draft of 5.
4. **A planned change of weight is followed.** Plan 135, 155, 175 lb; the lifter logs 140. The next draft shows 155, because the plan means to go up.
5. **A change of set type follows the plan.** A value carries only when `last.setType`, `prevRow.setType` and `row.setType` are all equal. A warm-up never hands its weight or reps to a working set, and a set logged as Drop against a Working row doesn't lower the next Working set. `setType` itself always comes from `row`, as today.
6. **The unit travels with the weight.** When a weight carries, so does its unit: 100 lb logged against a kg plan gives a draft of 100 lb. When the plan's weight is used, the plan's unit is used, as today.
7. **Everything else is unchanged.**
   - A field the row leaves null keeps today's copy-forward (10.2 D4).
   - The first set, an extra set and a workout with no plan seed as they do today.
   - An edited draft is never overwritten (10.2 AC25, 06.5).
   - A log with typing since the tap keeps the typed values (06.1 §6.5).
   - RPE stays blank.
   - `seedDraft` stays the one builder, so mount, post-log and re-seed cannot differ. That includes returning to an exercise in a superset, re-seeding after a set is deleted, and re-seeding an untouched draft after the last set is corrected, so one tap can't record a value the lifter just fixed.
8. **The bar tells the truth.** After AC1 and AC2, the bar reads "Log 190 × 8", and one tap sends exactly those values with `isComplete: true`. A carried value is not an edit: the draft stays untouched and `set_logged.edited` is false, as for any prefill.

### The Log button

9. **56 px in the workout screen's bar.** The bar's one button has a minimum height of a new token, `--bar-action-height` (3.5rem), in all three modes (Log, Finish, Add). `ActionBar` on every other screen keeps `--tap-target-min`.

### The status line

10. **The button doesn't move.** The workout screen's bar always reserves one status line, above the button, 44 px tall through a new token, `--session-status-height` (= `--tap-target-min`), so Spec 17.5's Undo fits without moving Log again. With the same content, the button's top is at the same y with no message, with "Log at least one set to finish", and with "1 set not saved yet" (a harness measurement, AC17).
11. **One line, not a stack.** The four messages keep their current wording and conditions, and are joined with " · " in one `<p>`: "1 set not saved yet · 1 note not saved yet". Text that needs more than one line at a narrow width wraps rather than truncates (D6).
12. **Keyboard up.** While `data-keyboard="open"` is set on `<html>`, an empty status line takes no space, because room is scarcest then. A non-empty one still shows.
13. **Clearance matches.** A focused or revealed control stops above the taller bar (WCAG 2.4.11): the workout screen's `scroll-padding-bottom` uses a new `--session-bar-clearance` token, computed from the button and status-line heights. With the keyboard up and an empty status line it uses `--session-bar-clearance-compact`, so the padding gives that space back too. After the panel's reveal, whatever has focus in the list is brought back into view, so a panel taller than the room left never hides it. Other screens keep `--action-bar-clearance`.

### The panel's place

14. **After a log on the same exercise.** Once the new row is on screen (it is what pushes the panel down, and it renders after `onLogged` runs), the panel is scrolled into view with `block: "nearest"`, no smooth behavior, so it is a no-op when already visible.
15. **After an advance.** The new exercise's panel is revealed the same way, after its heading. When focus moved to the heading (17.1 AC29), the heading is revealed again last, per AC13. A tap that leaves focus in a field, which is expected on iPhone Safari, gets the same treatment rather than losing the reveal.
16. **It doesn't fight the lifter.** Nothing scrolls when the lifter typed since the tap, or has already made another exercise current.
17. **Verified in a real browser.** The screenshot harness logs four sets in a row at 390 × 844 (three on one exercise, then an advance, which is what its fake routine allows), measures the session bar, and fails its run if any control in the panel is covered after a log, or if the button's top moves (AC10). Four sets on one exercise is left to the phone check (AC22).

### Must keep

18. **Regression guards.** The 600 ms double-tap window across a panel swap, focus staying on the bar's button (17.1 AC29), one primary `Button` on the screen (17.1 AC39), offline queueing and "Not saved yet" on rows (17.1 AC34), and the Set options reveal are unchanged. All existing tests pass, with changes only where this spec amends a criterion (§12, Cross-doc updates).

### Docs and verification

19. **Docs consistent.** The cross-doc updates in §12 are made.
20. **Every behavioral AC has a tagged test.** AC1–AC16 and AC18 have ≥1 test named `17.4 ACn — …`, enforced by an `acTags.17-4.test.ts` scan.
21. **Visual review.** `pnpm --filter @sin/web run screens` captures the new bar with no message and with a message, light and dark, 390 and 1280 px, and at 320 × 568.
22. **Phone check (owner).** On the iPhone, with a real routine that has a level exercise, a ramp and a warm-up: change a weight and confirm it carries; hit the top of a rep range and confirm one tap repeats it; confirm the ramp and the warm-up follow the plan; log four sets of one exercise and confirm the steppers stay reachable without scrolling; confirm the button stays put on poor wifi.

## 6. Behavior & logic

### 6.1 `seedDraft`

```ts
const base = copy-forward of last set;             // today
const next = nextPlanned(plannedSets, sets.length);
if (next.kind !== "planned") return base;          // today
const row = next.row;
const prevRow = plannedSets[sets.length - 1];      // undefined for the first set
const last = sets.at(-1);
const sameType = last && prevRow
  && last.setType === row.setType && prevRow.setType === row.setType;

reps:   row.repsLow null → base.reps               // today (10.2 D4)
        sameType and last.reps in range → last.reps
        otherwise → row.repsLow

weight: row.weight or row.weightUnit null → base   // today (10.2 D4)
        sameType, last.weight not null, prevRow's weight and unit equal row's
          → last.weight, last.weightUnit
        otherwise → row.weight, row.weightUnit
```

Progress stays positional, never `setNumber` (10.2).

### 6.2 The scroll after a log

`ActiveSession.onLogged` already knows the outcome. When the log should reveal a panel (`advance` is true and the logged exercise is still current), it records in state the set count the log left in the cache. An effect declared after the existing heading reveal waits until the screen holds that many sets, finds the current card's panel the same way AC9's effect does, and calls `scrollIntoView({ block: "nearest" })`. The wait matters: the query cache tells its observers a moment after the write, so a reveal that runs at once lands one row short. The browser check caught this; jsdom has no layout, so a unit test records the row count at the moment of the reveal instead.

### 6.3 The bar

`ActionBar` takes a class and a data attribute from `ActiveSession`. Its `.bar > button` rule keeps the width behavior. The button's height and the status line are the session bar's own CSS, so no other screen changes. `AppShell.module.css` gets `.main:has([data-session-bar])` beside the existing `:has([data-action-bar])` rule.

## 12. Decisions & open questions

- ✅ **D1 — The next set keeps what the lifter just did (owner, 2026-11-08).** Keep the weight, and keep the reps when they're inside the planned range; otherwise the plan's low end. Amends Spec 10.2 D1 and AC22 and DESIGN Q20. **Rationale:** "repeat what I just did" stopped being one tap on the owner's own routines, and a careless tap could record a number not lifted. **Rejected by the owner:** carrying weight only; keeping today's behavior.
- ✅ **D2 — The carry applies only where the plan holds still (owner, 2026-11-08).** A ramp (135, 155, 175) and a warm-up to working change are followed as planned. **Rationale:** carrying 140 into a planned 155 would undo the plan's own progression. **Rejected:** applying the difference (+5 to every later row), which is too clever to predict at a glance; carrying always.
- ✅ **D3 — A carried value is not an edit.** It's a prefill, so an untouched draft stays untouched and is not stored (06.5).
- ✅ **D4 — 56 px only in the workout screen's bar.** It's the most-tapped control in the app, and the owner likes large buttons. Other bars aren't tapped per set.
- ✅ **D5 — The status line is reserved, above the button, 44 px tall (owner, 2026-11-08).** Reserving it costs about 48 px of list height on every workout screen, in exchange for a button that never moves and a 44 px Undo (Spec 17.5). It ships at 44 px here so the button doesn't move a second time when 17.5 lands. The docked panel (Spec 17.9, drafted, not yet committed) may revisit this. **Rejected:** a 21 px line, with Undo's hit area reaching up into the list.
- ✅ **D6 — Wrap, don't truncate.** A sync state must never be cut off. Two lines of status text fit in the 44 px line, so the button moves only in the rare case of three lines or more at a narrow width.
- ✅ **D8 — On a tall card, the panel wins over the exercise name.** After an advance, a card with several logged rows can be taller than the room left, and revealing the panel scrolls the name off the top, while the bar's visible text doesn't name the exercise. Reaching the steppers comes first (PRODUCT principle 1); Spec 17.8 puts the name in the panel's label, which closes this.
- ✅ **D7 — Set options is left alone.** Its reveal under the bar is a known problem, fixed by replacing it in step 4.
