## 1. Purpose, scope & non-goals

A load test (Spec 16) is only useful if, when the p95 climbs past 2 seconds, the dashboard says **why**. Spec 13.0 already shows request latency, error ratio, event-loop delay, heap and GC. Two answers to "why" are missing:

- **Is the server out of CPU?** Render's free plan gives the API 0.1 CPU; Cloud Run gives 1 vCPU. Slow requests with a busy event loop and a CPU pegged at its limit mean "too small a box". Slow requests with an idle CPU mean something else (the database, a lock, the network).
- **Is the database connection pool exhausted?** Prisma opens at most `connection_limit` connections to Postgres (8 here, backfilled by `resolveDatabaseUrl`). When all 8 are busy, the next query **waits for a free connection**. That wait is invisible in the HTTP histogram until it is already a slow request.

> **First-principles note — "connection pool".** Opening a TCP + TLS connection to Postgres costs tens of milliseconds (more to Neon, which is remote), so the API keeps a small set of connections open and lends one to each query. If eight queries are running and a ninth arrives, it queues. Under load, the queue is where latency hides. "In use vs the limit" and "how many are waiting" are the two numbers that show it.

> **First-principles note — "gauge vs counter, and why the CPU is a counter".** A *gauge* is a value you read at one instant ("8 connections busy right now"); a *counter* only goes up ("12.4 CPU-seconds used since the process started"). Metrics here are exported once a minute on staging (`OTEL_METRIC_EXPORT_INTERVAL=60000`). A gauge sampled once a minute can miss a spike entirely, while a counter never misses anything: the rate of change between two exports (`rate()` in PromQL) is the exact average over that minute. So CPU, and the accumulated pool wait time, are exported as counters; the instantaneous pool numbers are gauges and are read with that limit in mind (D5).

### In scope

- `apps/api/src/telemetry/`: the new instruments, their Views and `METRIC_NAMES` entries, and their tests.
- `apps/api/prisma/schema.prisma`: the generator's `previewFeatures = ["metrics"]` (D1).
- `apps/api/src/db.ts`: a tiny helper that reads the effective `connection_limit` from the resolved URL.
- `apps/api/src/server.ts`: one registration call after `createPrisma`.
- `ops/grafana/dashboards/api-overview.json`: new panels (CPU, CPU throttling when present, pool in use vs limit, pool waiting, mean pool wait).
- Doc edits (§11).

### Non-goals

- The load test, its dashboard and its alerts (Spec 16). No new alert rule here: thresholds for CPU and pool use are only worth choosing once a load run has shown where they sit.
- Production telemetry. Prod has no `OTEL_*` (Spec 15), so these metrics reach prod only when that is switched on; nothing here changes that.
- Per-query or per-route CPU attribution; anything in traces. Prisma's `prisma:engine:connection` span (the interim proxy from D11) stays as it is.
- A Prisma driver adapter / Prisma 7 migration, or the `pg.Pool` gauges BL-25 describes (D2).
- Host-level metrics (`@opentelemetry/host-metrics`) and any container-agent.
- Changing `connection_limit`, pool timeouts or any request behavior.

## 2. Acceptance criteria

Behavioral criteria get at least one test naming their number (`describe("AC3 — …")`), under `apps/api/test/unit/telemetry/` or, where a real database is needed, `apps/api/test/integration/`. *(manual)* criteria are checked by hand and recorded in the PR description; *(CI)* criteria are enforced by existing jobs. Names below are the Prometheus names; the OTel instrument names are the dotted forms in §6.

1. **Off by default.** With no `OTEL_*` exporter set, nothing is registered: no timer, no observable callback, no call to `$metrics`, no file read of a cgroup path. Existing unit and integration suites pass unchanged.
2. **Process CPU counter.** `sin_process_cpu_seconds_total` exists with exactly one attribute, `cpu_mode`, taking exactly the values `user` and `system`. With an injected CPU-usage source returning `{ user: 1_500_000, system: 500_000 }` microseconds, the export reads `user = 1.5` and `system = 0.5` seconds. With the real source (`process.cpuUsage()`), two consecutive collections never decrease, and after the test burns at least 50 ms of CPU in a loop the `user` value has grown.
3. **Throttling counter, only where the platform has it.** Where the cgroup v2 file `/sys/fs/cgroup/cpu.stat` is readable and contains a `throttled_usec` line, `sin_container_cpu_throttled_seconds_total` exports that value in seconds (no attributes). Where the file is missing, unreadable or has no such line, the instrument is **not registered** and boot is unaffected; at most one `debug` log line says so. Tested with an injected file reader (present, absent, malformed, a read error on a later collection).
4. **Pool gauges from the Prisma metrics source.** Given a recorded `getMetrics()` fixture from the pinned Prisma (6.19.x), the export contains `sin_db_pool_connections{state="busy"}` and `{state="idle"}` (from `prisma_pool_connections_busy` / `_idle`), `sin_db_pool_waiting` (from `prisma_client_queries_wait`: queries currently waiting for a free connection), and no other attribute values for `state`.
5. **Cumulative wait counters.** From the same fixture, `sin_db_pool_wait_seconds_total` equals the wait histogram's `sum` (`prisma_client_queries_wait_histogram_ms`) converted from milliseconds to seconds, and `sin_db_pool_waits_total` equals that histogram's `count`. Both are monotonic across collections within a process.
6. **The limit is exported.** `sin_db_pool_limit` equals the `connection_limit` of the URL the client was built with: `8` when `resolveDatabaseUrl` backfilled it, the explicit value when the stored URL carries one. A URL with a non-numeric or missing limit after resolution exports nothing for this gauge (never `NaN`).
7. **Reading costs no SQL and opens no connection.** Collecting these metrics issues no statement to Postgres (a Prisma `query` log listener sees nothing), and on a client that has not yet run any query it does not open a database connection (Postgres reports no session from that client). If reading the metrics would start the engine, the registration waits for the first real query before observing (§6.3).
8. **Failure isolation.** If `$metrics.getMetrics()` rejects, throws, or returns an unexpected shape, the callback observes nothing for that cycle, logs one `warn` per 5 minutes through the existing throttled reporter (signal `metrics`), and no request, export or shutdown is affected. Same for a throwing CPU or cgroup reader.
9. **Views and the allowlist.** Every new instrument has a View in `buildViews()` that keeps only its allowed attribute (`cpu.mode` or `state`, none for the rest) and renames it to the §6 Prometheus name; the names are in `METRIC_NAMES`; the catch-all DROP View still removes any other instrument; an unexpected attribute added to an observation is dropped, not exported (extends `views.test.ts`).
10. **Bounded cardinality.** All new instruments together export at most 9 series (2 CPU + 1 throttling + 2 pool states + waiting + limit + 2 wait counters). Collected in a test and asserted.
11. **Local scrape.** With `OTEL_METRICS_EXPORTER=prometheus`, `GET :9464/metrics` text includes every name in AC2–AC6 (the throttling counter only where AC3 registers it). The OTLP and Prometheus names are the same series (D13 convention, §6.4).
12. **Dashboards.** `ops/grafana/dashboards/api-overview.json` gains the panels in §6.5; the existing `ops-grafana` unit test (every dashboard and alert query uses only exported metric names) passes with the new `METRIC_NAMES`; the file is valid dashboard JSON.
13. **Prisma preview flag is present and guarded.** `schema.prisma` declares `previewFeatures = ["metrics"]`; `pnpm run build` (which runs `prisma generate`) and `prisma validate` succeed; a unit test asserts the generated client exposes `$metrics.getMetrics`, and fails with a message that points at BL-25 and this spec if a Prisma upgrade removes it.
14. **Cost is measured and small** *(manual)*. One full collection cycle (all new callbacks) is timed on the dev machine with the real client: the median is recorded in the PR and is under 10 ms (a larger number stops the PR for a rethink, §6.3). `pnpm --filter @sin/api run bench:finish` is run before and after; the finish-latency result stays within the benchmark's usual run-to-run variation (the preview flag makes the engine record metrics all the time).
15. **Local stack** *(manual)*. With the observability compose stack and `pnpm --filter @sin/api run dev`, a short `curl` traffic burst plus a 20-request parallel burst shows every new panel populated, the CPU panel rising and the pool-in-use panel moving off zero.
16. **Staging** *(manual)*. After the PR is deployed and the post-deploy smoke has run, the re-imported `api-overview` dashboard in Grafana Cloud shows every new panel populated with the same metric names as local (the D13 check again), the CPU panel reading plausibly against Render's 0.1 CPU. Whether `sin_container_cpu_throttled_seconds_total` exists on Render is **recorded** (present / absent) in the PR and in §12 D4. Done before Spec 16's first load run.
17. **Purity** *(CI)*. `pnpm run core:purity` passes; nothing under `apps/web` or `packages/core` imports an OTel or Prisma package; `telemetry/` still imports neither Fastify nor `@prisma/client` (the pool source is passed in structurally, §6.3).

## 6. Behavior & logic

### 6.1 Where the code goes

```
apps/api/src/telemetry/
  views.ts            + METRIC_NAMES entries and `keep(...)` Views for the seven instruments
  runtime-pressure.ts + registerRuntimePressureMetrics(meter, deps?)   // CPU + throttling
  db-pool.ts          + registerDbPoolMetrics(meter, source, limit, deps?) // pool gauges/counters
apps/api/src/db.ts    + connectionLimitOf(resolvedUrl): number | undefined
apps/api/src/server.ts + after createPrisma(config): registerDbPoolMetrics(...) via the global meter
apps/api/src/telemetry/sdk.ts + registerRuntimePressureMetrics(meterProvider.getMeter("sin-api")) beside registerProcessStartTime
```

CPU needs nothing from the app, so it is registered inside the SDK start, next to `sin.process.start_time`. The pool metrics need the Prisma client, which only exists after the server module loads (telemetry starts first, Spec 13.0 D15), so `server.ts` calls `registerDbPoolMetrics` right after `createPrisma(config)` using the **global** meter provider. With telemetry off that provider is a no-op and the call registers nothing (AC1). Following `metrics.ts`'s pattern, registration is repeated if the global provider changes (tests swap it).

`registerDbPoolMetrics` takes a **structural** source, `{ $metrics: { getMetrics(): Promise<PoolMetricsJson> } }`, so `telemetry/` imports nothing from `@prisma/client` (AC17); `PoolMetricsJson` is a small local type for the three fields read.

### 6.2 The instruments

| OTel instrument | Kind | Attribute | Prometheus name | Source |
|---|---|---|---|---|
| `sin.process.cpu.time` | observable counter | `cpu.mode` = `user` \| `system` | `sin_process_cpu_seconds_total` | `process.cpuUsage()` µs ÷ 1e6, cumulative since process start |
| `sin.container.cpu.throttled` | observable counter | none | `sin_container_cpu_throttled_seconds_total` | cgroup v2 `cpu.stat` `throttled_usec` ÷ 1e6; registered only if readable (AC3) |
| `sin.db.pool.connections` | observable gauge | `state` = `busy` \| `idle` | `sin_db_pool_connections` | `prisma_pool_connections_busy`, `_idle` |
| `sin.db.pool.waiting` | observable gauge | none | `sin_db_pool_waiting` | `prisma_client_queries_wait` |
| `sin.db.pool.limit` | observable gauge | none | `sin_db_pool_limit` | the resolved URL's `connection_limit` (constant) |
| `sin.db.pool.wait` | observable counter | none | `sin_db_pool_wait_seconds_total` | `prisma_client_queries_wait_histogram_ms` `sum` ÷ 1000 |
| `sin.db.pool.waits` | observable counter | none | `sin_db_pool_waits_total` | the same histogram's `count` |

Names follow D13: gauges with no natural unit keep a plain name; a counter's name ends in its unit so the JS Prometheus exporter and Grafana Cloud's OTLP translation agree (the suffix `_total` is added by both). The builder confirms the exact Prisma metric keys against real 6.19.3 `getMetrics()` output when recording the AC4 fixture; the keys above are from Prisma's documented list and must not be guessed past that check.

The "CPU utilization" the design asks about is **derived**, not stored: `rate(sin_process_cpu_seconds_total[1m])` is CPU cores in use; divided by the container's CPU allowance it is utilization. The allowance differs by host (0.1 on Render free, 1 on the prod Cloud Run), so it is a dashboard variable (§6.5), not a metric.

The process figure includes the Prisma query engine, which is a native library loaded into the API process (Prisma's default engine type), so engine work for slow queries is counted. It does not include a separate process, and the API has none.

### 6.3 Reading Prisma's pool numbers

Each export, one observable callback calls `getMetrics()` once and feeds the four pool instruments from that single result (a batch callback), so the cost is one call per export interval, not four. The call is in-process: Prisma's query engine keeps these numbers in memory and returns them as JSON. **It sends nothing to Postgres.** That is the property that makes this source safe on Neon's free plan, where any query keeps the compute awake and spends the monthly compute-hour allowance, and safe for a load test, where the measurement must not become part of the load.

Cost per interval, for the record: one in-process call returning on the order of a few dozen numbers (microseconds to low milliseconds); the CPU callback is one `getrusage` system call; the throttling callback is one read of a small file. Together far below the 10 ms bound of AC14, with no network traffic. Export cost on the wire is nine more series every 60 s against Grafana Cloud free's 10,000-series cap, which Spec 13.0 §6.3 keeps in the low hundreds.

**One thing the builder must check, not assume (AC7).** In some Prisma versions, asking the engine for metrics starts the engine if it is not running yet, which would open a database connection earlier than the first query. On a Cloud Run instance that is only a few hundred milliseconds early, but the principle (telemetry must not cause database activity) is firm. The builder verifies the 6.19.3 behavior. If metrics reads do start the engine, the callback is gated on a "first query has run" flag (the builder picks how it is set, for example by the first successful `/readyz` database check) and observes nothing until then; the gate is covered by AC7's test. Either outcome is acceptable; an unverified guess is not.

The limit is read once at registration from the same resolved URL the client was built with (`connectionLimitOf(resolveDatabaseUrl(config.databaseUrl))`), so it can never drift from the real pool size.

### 6.4 Local vs Grafana Cloud names

Same D13 rule as Spec 13.0 §6.11: every new name is set by a View and already ends in the form both backends produce. AC11 (local scrape) plus AC16 (Cloud, same dashboard JSON) are the proof; if a Cloud panel is empty, the fallback is the `metric_suffix` variable from §6.11 option 2, and this spec's D-entry is amended.

### 6.5 Panels added to `api-overview`

All use the existing `${datasource}` variable. Layout continues below the current row (y = 24):

| Panel | Query shape | Notes |
|---|---|---|
| CPU cores in use | `sum(rate(sin_process_cpu_seconds_total[1m]))` (also by `cpu_mode`) | A threshold line at the dashboard variable `cpu_limit` (a textbox, default `0.1` with a note that prod Cloud Run is `1`). Stacked user/system. |
| CPU throttled | `rate(sin_container_cpu_throttled_seconds_total[1m])` | Seconds throttled per second; the panel states "no data = this host does not report throttling". |
| DB connections in use vs limit | `sum(sin_db_pool_connections{state="busy"})` and `max(sin_db_pool_limit)` | Instantaneous, one point per export; the limit is a flat line. |
| DB queries waiting for a connection | `max(sin_db_pool_waiting)` | Same caveat (D5). |
| Mean pool wait per query | `rate(sin_db_pool_wait_seconds_total[2m]) / rate(sin_db_pool_waits_total[2m])` | Counter-based, so it does not miss spikes; guard the divide for zero (`clamp_min` on the denominator). |

Exact layout and panel types are the builder's. Spec 16's "Load test" dashboard reuses these queries.

### 6.6 Failure isolation

All callbacks run on the metric reader's collection path, never a request path (Spec 13.0 §6.6). Every callback wraps its body in try/catch and reports through the existing throttled `warn` reporter under signal `metrics` (AC8); an exception can never escape into the SDK's collection loop.

## 7. Security & privacy

Aggregate numbers about the process and its pool only. No user ids, no request data, no SQL text, no hostnames: the new attributes are the fixed sets `cpu.mode` (2 values) and `state` (2 values), enforced by Views (AC9, AC10). The cgroup read is of one kernel counter file, path hard-coded (no path from input). Nothing here is personal data under DESIGN §8.2. The "never add a telemetry attribute without extending the allowlist" gotcha is honored: the Views are the extension.

## 8. Config & secrets

No new environment variable and no secret. Everything keys off Spec 13.0's `OTEL_*` variables; with none set, nothing runs (AC1). The pool limit comes from the existing `DATABASE_URL` handling. The panel variable `cpu_limit` is dashboard state, not config.

## 9. Observability

This spec is observability. Emitted signals are the §6.2 table. Telemetry's own health is unchanged: a failing callback produces a throttled `warn` (AC8). The Spec 13.0 §9 table gains these rows when the PR lands (§11).

## 12. Decisions & open questions

### Resolved

- **D1 ✅ DB connection source: Prisma's `metrics` preview feature (`$metrics.getMetrics()`).** *Finding (verified 2026-11-05 against the repo's pinned Prisma 6.19.3):* the preview is **not** removed. `prisma validate` on the real schema with `previewFeatures = ["metrics"]` succeeds and prints `Preview feature "metrics" is deprecated. It will be removed in a future version of Prisma.`; the generated client's type definitions still declare `$metrics` and `metrics(...)`. This matches Spec 13.0 D11 (deprecated in 6.14, removed in 7.0) and corrects the 2026-11-05 design brief's "reportedly removed in 6.14". It gives exactly what is needed: busy and idle connections, **queries currently waiting for a connection**, and a wait-time histogram (sum and count), all in memory. **Cost per scrape / export interval:** one in-process call, no SQL, no network, no connection (§6.3, AC7, AC14). *Rejected:* **`pg_stat_activity`** — it needs a SQL query every interval, which takes a pool connection itself (so it perturbs the 8-connection pool being measured), spends Neon compute hours and keeps the Neon compute awake while the API is up, sees every client of the database rather than this process, and cannot see "waiting for a connection" at all because that wait happens before Postgres is involved. *Rejected:* **timing connection waits** (a query-timing extension or the `prisma:engine:connection` span) — query time and wait time are mixed together unless the engine reports the wait, a span-derived metric only exists for sampled requests (prod will sample), and it yields no "in use" gauge. *Cost accepted:* the feature is deprecated and ends at Prisma 7, so this is a bridge (D2); the engine records metrics continuously once the flag is on, measured by AC14.
- **D2 ✅ This spec supplies BL-25's gauges early, through a bridge, and keeps the names stable.** D11 deferred pool gauges to a driver adapter; the owner asked for them before the load test (2026-11-05), and the preview works on the pinned version. BL-25 stays open for the real route (`pg.Pool` observable gauges, `totalCount − idleCount` busy and `waitingCount` waiting, when the API gains a driver adapter or moves to Prisma 7); the metric names here are chosen so that swap changes only the source. A guard test (AC13) turns a silent loss into a loud failure on any Prisma upgrade.
- **D3 ✅ CPU: an observable counter from `process.cpuUsage()` (user and system seconds), with utilization derived by `rate()`.** The repo's only runtime instrumentation, `@opentelemetry/instrumentation-runtime-node`, emits event-loop, heap and GC metrics and no CPU, so something must be added. *Rejected:* `@opentelemetry/host-metrics` (a new dependency, host-wide numbers that on a shared container are the wrong scope, and its `process.cpu.utilization` is a gauge sampled per interval, which at 60 s misses spikes); a `process.cpu.utilization` gauge of our own (same sampling problem); reading cgroup usage as the *primary* measure (not available or not verified on every host, D4). The counter works identically on a laptop, Render and Cloud Run, loses nothing between exports, and the 0.1-vs-1 CPU difference is a dashboard variable rather than a metric.
- **D4 ✅ Container CPU throttling is best-effort, registered only where the cgroup file exists.** Whether Render's free containers expose `/sys/fs/cgroup/cpu.stat` with a `throttled_usec` line could not be verified from here (a Render community thread shows `/sys/fs/cgroup/cpu.max` readable on Render, which suggests cgroup v2 is mounted; throttling counters unconfirmed), and Cloud Run's sandbox may not expose it. A 0.1 CPU limit already shows up as `rate(sin_process_cpu_seconds_total)` flat-lining near 0.1, so throttling is corroboration, not the only signal. Hence: register if readable, skip silently if not (AC3), and record on staging whether it is present (AC16). The builder may drop this instrument and AC3 if the Render check shows it never appears, as a one-line amendment to this entry.
- **D5 ✅ Pool gauges are instantaneous; the signal that cannot miss a spike is the wait counters.** On staging, exports are 60 s apart, so `busy` and `waiting` are one sample a minute. Rather than add an in-process sampling timer (more moving parts, more code on the hot path of every load test), the cumulative wait counters carry the "did anything queue" truth (`rate(wait_seconds)/rate(waits)`, AC5), and the gauges are read alongside them. Consequence for Spec 16: each load step should hold long enough for several export intervals; that is Spec 16's builder choice (its §10).
- **D6 ✅ The pool source is injected structurally; telemetry never imports `@prisma/client`.** Keeps `telemetry/` import-light (the Spec 13.0 rule that it must not import Fastify extends in spirit to the database client) and makes AC4–AC8 unit-testable with a fake source.
- **D7 ✅ The limit is read from the resolved URL, not hard-coded.** `connection_limit=8` is a backfilled default (`resolveDatabaseUrl`) that a stored URL can override; a copied constant would silently disagree.
- **D8 ✅ No new alert rules.** Where CPU and pool use stop being fine is exactly what the first load runs will show; alerts on guessed thresholds would be noise. Revisit after Spec 16's first results.
