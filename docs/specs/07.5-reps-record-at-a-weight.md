## 1. Purpose, scope & non-goals

**Purpose.** Doing more reps than ever at a weight often shows nothing. Verified in code: `estimate1rm` returns `null` above 12 reps (`records.ts:72-75`), and `max_reps` is read only from `bodyweight_reps` sets (`records.ts:138-140`). So a set of 13 or more reps on a `weight_reps` or `weighted_bodyweight` lift can never become a record unless its weight is also the heaviest ever, such as lateral raises at 12–15 reps. Below 13 reps, the same gain stays hidden whenever a heavier set holds the best estimate (§6.7). This spec adds one record: **most reps at a given weight**, for sets of 6 or more reps.

> **First-principles note — why a reps record needs a weight in its identity.** "Most reps ever" is meaningless on a weighted lift, because a lighter weight always allows more reps. A fair comparison holds the weight still: 15 reps at 12.5 kg against 13 reps at 12.5 kg. So the record is not one number per exercise. It is one number per exercise *and weight*. That is why the other seven record types, which are one row per lineage root and type, do not fit without a change (§4).

> **First-principles note — "held now" with many rows.** A stored record is the current best, not an event (Spec 07.0 D18). With a record per weight, the table holds the best at each weight, and every edit or delete of a past set recomputes them all from the full history. A record whose source set is deleted or lowered does not stay: either the next-best set at that weight takes it, or, when nothing at that weight reaches the floor any more, the row is gone.

**In scope (three phases, three PRs).**
- **Phase A — compatible parsing (web, no API change).** The two places the web parses a record list drop a record type they do not know, so an old tab survives the new value (§6.8).
- **Phase B — the record (API + core).** Migration `0022`, the pure math in `@sin/core`, the recompute, the reads, the web's minimum to compile and label it, the rebuild, the benchmarks.
- **Phase C — the ledger row (web).** The row in Spec 17.6's ledger, the exercise page and Progress lists.

**Non-goals.**
- Changing `heaviest_weight`, `best_est_1rm`, `best_set_volume` or `max_reps`, or any record for sets of 1–5 reps (D1).
- A chart metric for it. The Progress series is unchanged (AC30).
- A weight tolerance, or converting between kg and lb to match weights (D4).
- A record for `weighted_bodyweight` sets with no added weight (O5), or for `bodyweight_reps` (it has `max_reps`).
- Changing History's `recordCount` rule. That is Spec 07.6. Either order is safe; 07.6 first is better (§11).
- The account export (Spec 11 excludes `personal_record`).
- Any Hevy code. The import's finish step recomputes through the same function (AC24).

## 2. Acceptance criteria

Terms. A **lineage** is the set of exercises sharing one root (`COALESCE(forked_from_exercise_id, id)`, Spec 07.0 §6.2). The **floor** is `REPS_AT_WEIGHT_MIN_REPS = 6`, a constant in `@sin/core`. An **eligible set** is a `working` set in a finished workout whose own `modality_snapshot` is `weight_reps` or `weighted_bodyweight`, with `weight_kg > 0` and an integer `reps ≥ 1`. `is_complete` is ignored (Spec 07.0 D5). Weights are compared as integer milli-kg, exactly.

### Phase A — compatible parsing (web only)

1. **Unknown types are dropped from record lists.** The web's parse of `GET /v1/personal-records` and of the finish `PATCH` response drops any `records` / `newRecords` item whose `recordType` is not in `RECORD_TYPE_VALUES`. The rest of the list, and the rest of the finish response, parse as before.
2. **Everything else stays strict.** A record of a known type with a missing or wrong-typed field still fails the parse, as today. The API, `@sin/core`'s `PersonalRecordSchema` and every other response schema are unchanged.
3. **It covers every web parse of a record list.** The records client and the workout client's `PATCH` parse; a test searches `apps/web/src` for any other use of `PersonalRecordSchema`, `PersonalRecordsResponseSchema` or `UpdatedWorkoutSchema` and fails on one not routed through the tolerant schemas.
4. **No visible change today.** With the current seven types, every existing web test passes unchanged.
5. **Phase B's gate.** Phase A is live on staging, and the owner has reloaded the phone's tab onto it (the page's `sin-commit` meta equals Phase A's merge commit). The Phase B PR states both.

### Phase B — the record

*The math (`@sin/core`)*

6. **A record per weight at the floor.** For a lineage, `computeRecords` returns one `max_reps_at_weight` record for each exact weight at which the current best reps is ≥ 6. Its `valueMilli` is reps × 1000, its `unit` is `reps`, its `atWeightKgMilli` is the weight, its `setId` / `workoutId` are the earliest set that reached that best.
7. **Eligibility.** Only eligible sets count. Warm-up, drop and failure sets, a `bodyweight_reps`, `weight_distance` or `weight_duration` set, a set with no weight or a weight of 0, and a live workout's sets produce nothing.
8. **The baseline is every earlier set at that weight, whatever its reps.** 5 reps then 7 gives `value` 7, `previousValue` 5. A first workout of 5 reps at a new weight makes no row; a later 7 makes a row with `previousValue` 5.
9. **Strictly more, earliest wins (Spec 07.0 D6, D16).** Equal reps in a later workout does not take the record. Within one workout the earliest set with the best reps is the holder. `previousValue` is the best at that weight over strictly earlier workouts, never the same workout's other sets. A first time at a weight has `previousValue: null`.
10. **A higher earlier best is kept.** 15 reps (week 1), 12 (week 2), 13 (week 3) at one weight leaves week 1 as the holder, with `previousValue: null`.
11. **Exact weight, in canonical kg.** 12.5 kg and 12.500 kg are one key; 25 lb (11.340 kg) and 11.5 kg are two. The same lb value always lands on the same key, because `weight_kg` is generated from the stored value.
12. **Order.** The new type is last in `RECORD_TYPE_VALUES`. Within `computeRecords`' output, its records follow the other types, by weight descending.
13. **A reference test.** A seeded-PRNG property test (Spec 07.0 AC9's pattern) compares `computeRecords` against a brute-force reference for the new type over random histories, with weights from a small set so that collisions are common.

*Data*

14. **Migration `0022` is additive.** It adds `personal_record.at_weight_kg NUMERIC(7,3) NULL`, widens the type and type-and-unit CHECKs for `max_reps_at_weight` (unit `reps`), adds `CHECK ((record_type = 'max_reps_at_weight') = (at_weight_kg IS NOT NULL))` and `CHECK (at_weight_kg IS NULL OR at_weight_kg > 0)`, creates a unique index on `(user_id, exercise_id, record_type, at_weight_kg) NULLS NOT DISTINCT`, then drops `personal_record_user_exercise_type_key`. No column is dropped or renamed.
15. **The previous release still runs on the migrated schema.** The whole existing integration suite passes unchanged against the migrated schema before any `src/` change (the `0019` approach, 21.1 AC5): finish, delete, edit and rebuild with the old statements write only the seven old types.
16. **Uniqueness.** Two rows of the seven old types for one `(user, root, type)` are still refused; two `max_reps_at_weight` rows at different weights are accepted; the same weight twice is refused.
17. **Drift guards.** The record-type list in the CHECK equals `RECORD_TYPE_VALUES` (the live list is guarded against `0022`; the `0015` guard is frozen to its list, as 05.3 did for earlier lists). `schema.prisma` gains `atWeightKg`; the unique index is hand-authored (Prisma ignores it, like `workout_routine_idx`) and the `@@unique` line is removed with a comment saying where the index lives. The whole-schema `migrate diff` no-drift check moves into `0022`'s integration test.
18. **Row-level security needs nothing new.** No table, grant or policy is added. As `sin_app` with RLS on, user B cannot read, update or delete user A's `max_reps_at_weight` rows; Spec 21.1's inventory test passes unchanged. `pnpm --filter @sin/api run audit:queries --write` is run, and every changed row is classified `user-filtered`.

*The write path*

19. **One recompute, unchanged shape.** `recomputeRecordsForRoots` writes the new rows with the other records, in the same transaction, under the same lock (`lockUserRecords` first). It issues one multi-row `INSERT` per root (not one per row), so the statement count does not grow with the number of weights.
20. **Finished edits and deletes follow (Spec 07.4).** After a finished-mode set create, patch (`reps`, `weight`, `weightUnit`, `setType`) or delete, an exercise delete, or a re-time, the table equals what `records:rebuild` gives from scratch. Deleting or lowering the holder promotes the next-best set at that weight and restates `previousValue`; when nothing at that weight reaches the floor, the row is gone.
21. **The edit predicate is unchanged and still right.** `setChangeAffectsRecords` already compares `reps` and `weight` for both load modalities, so a reps-only or weight-only edit recomputes and an `rpe`-only edit still issues no `DELETE FROM personal_record` and no loader query (07.4 AC8).
22. **Forks share rows.** Sets logged on a fork and on its origin at the same weight compete for one record. `exerciseId` is the root, `sourceExerciseId` and `exerciseName` come from the holder's own set.
23. **Rebuild and backfill.** `records:rebuild` writes the rows for every existing user, is idempotent, and equals the live path (the reconciliation helper, Spec 07.4 AC6). It is a manual release step after `migrate deploy` (§11).
24. **Hevy import.** Importing a fixture history with a set of 14 reps (Spec 19.1 AC30's fixture, extended) and running the finish step gives the same rows as `records:rebuild`. No Hevy file changes.

*The reads*

25. **The DTO.** `PersonalRecord` gains `atWeightKg: number | null` (required-nullable, canonical kg, `null` for the seven old types; Spec 07.0 D14's JSON-number rule), and `recordType` gains `max_reps_at_weight`. `value` and `previousValue` are reps as JSON numbers.
26. **Every record read returns it.** The finish response's `newRecords` (rows the finishing workout holds, including first-time rows), `GET /v1/personal-records`, `?workoutId=` and `?exerciseId=` (a fork id, the origin id and a second fork's id give the same list) include the new rows. Order: `achieved_at DESC, workout_id, exercise_id, record_type, at_weight_kg DESC NULLS LAST`. The finish response and the `GET` agree row for row.
27. **Not in the export.** `GET /v1/account/export` is unchanged (Spec 11 AC4 still holds).
28. **History.** While Spec 07.3's rule is in force a `max_reps_at_weight` row counts once like any other non-volume row; under Spec 07.6's rule it counts its lift once, and only when `previousValue` is not null. Both are tested here for whichever rule is live.

*Latency, rollback, web minimum*

29. **PR-engine latency.** `bench:finish` is re-run (a) on its unchanged fixture and (b) on a variant where every exercise holds `max_reps_at_weight` rows at 30 weights. Pass: (a) p50 within 25% of the figure 21.1 §12 records for the same bench through `sin_app`; (b) p99 under DESIGN §1.3's 400 ms. `bench:hevy-import` (batch and finish) is re-run on the unchanged fixture and stays within 25% of 21.1's figures. `GET /v1/personal-records` unfiltered on a fixture of 100 lineages with 30 weights each is measured and recorded (time and body size). Results go in §12.
30. **Charts and series are untouched.** `progressPoints` and `GET /v1/progress/exercises/{id}` return the same bytes as before for the same history; the "Reps" metric is still `bodyweight_reps` only. A test pins this.
31. **The web compiles and labels it.** `recordLabel(type)` handles the new value without throwing; a new `recordRowLabel(record, pref)` reads "Most reps at 32.5 kg" (profile unit); `recordLine`, `sortRecords` (type order, then weight descending) and the list key (`exerciseId:recordType:atWeightKg`) use it. `RecordsSection` no longer risks duplicate keys. Progress's headline order (`HEADLINE`) is unchanged and does not include the new type.
32. **Rollback is documented and tested.** After reverting the code, `records:rebuild` run by the old code removes every `max_reps_at_weight` row (it deletes by root and writes only the old types), proved by a test that applies the old statements to the migrated schema. The column and constraints stay.
33. **Docs consistent.** The cross-doc updates in §12 are made.
34. **Every behavioral AC has a tagged test.** AC1–AC4, AC6–AC13, AC15–AC16, AC18–AC22, AC24–AC26, AC28, AC30–AC32 have ≥1 test named `07.5 ACn — …`; Phase A and C tests are in the web package, tagged the same way and enforced by an `acTags.07-5.test.ts` scan.

### Phase C — the ledger row (web; needs Spec 17.6 Phase A merged)

35. **The row.** Under 17.6's ledger a beaten record reads: label "Most reps at 32.5 kg" (profile unit; 70 lb for a lb account that logged 70 lb), `12 → 14 reps` (the old value drops the unit, 17.6 AC5), and the gain `+2 reps` in brass. The gain is the exact integer difference; no rounding applies.
36. **Order.** A lift's rows are in `RECORD_TYPE_VALUES` order, then weight descending. A lift may show several rows of this type, one per weight, and a set of 6–12 reps may show both this row and an est. 1-rep max row; each states a different fact.
37. **A first time at a weight shows nothing on the summary.** A first-time `max_reps_at_weight` row adds no row and no line to the ledger, and isn't counted in its heading. A lift whose only records in the workout are such rows doesn't appear in the panel. The row is still stored and listed on the exercise page (AC39). A first-ever lift keeps 17.6's "First time logged" line from its other first-time records.
38. **Accessible.** The row's text is one sentence: "Most reps at 32.5 kg: was 12 reps, now 14 reps, up 2 reps". Brass appears only where 17.6 AC18 allows. The label may wrap above the figure (17.6 AC4); nothing clips at 320 px.
39. **Other lists.** The exercise page and Progress's records list show one line per weight, heaviest first, e.g. "Lateral Raise — Most reps at 12.5 kg 15 reps (was 13 reps)". At a floor of 6 a lift can collect many weights over the years, so a list shows the 5 most recently achieved and a "Show all" control (owner, 2026-11-08). Progress's list headline and the chart metrics are unchanged.
40. **Fixtures.** The screenshot harness adds: a beaten rep record (12 → 14), two weights in one lift, a first time at a weight (nothing shown), a lb account, and the 7-lift collapse with the new rows; light and dark, 390 and 1280 px, and 320 × 568.
41. **Phone check (owner).** On the iPhone, after beating your reps at a weight used before, with a set of 6 or more: the summary shows the row; the exercise page lists it; a new weight adds nothing to the summary.

## 4. Data model

### 4.1 Storage designs compared

| | **A. A nullable `at_weight_kg` column on `personal_record` (recommended)** | **B. A new table `personal_record_at_weight`** |
|---|---|---|
| Rows | Existing rows unchanged; new rows for the new type, many per root | Existing table unchanged; a second table, many rows per root |
| Constraint change | Type and unit CHECKs widened; the unique index widened to include the weight (`NULLS NOT DISTINCT`) | None on the old table; its own key `(user_id, exercise_id, weight)` |
| Spec 21.1 | **Nothing new**: the table already has grants and `personal_record_own` | A new table needs `0020`-style grants, a policy, an inventory entry, a cascade from `user` (the purge test discovers it) and audit rows |
| Reads | One query, as today; `GET` and the finish response stay one list | Two queries or a `UNION`; the DTO is a second shape or a merge |
| Recompute | The same function writes it; `DELETE` by root already clears it | A second `DELETE` and `INSERT`, kept in step by hand |
| History count (Spec 07.3 / 07.6) | The same subquery sees the rows | The subquery needs a second table or a `UNION` |
| Rollback | Old code deletes by root and rewrites; no stray rows survive a rebuild (AC32) | The table is ignored by old code and goes stale; nothing removes it |
| Downside | A mostly-NULL column; a type CHECK that grows | More code and more 21.1 surface for the same behavior |

Two more were considered and rejected: **derive on read** from `set_entry` (puts PR math outside `@sin/core`, forbidden by `CLAUDE.md`, and makes every read a history scan), and **encode the weight in `record_type`** (`'max_reps@12.5'`: breaks the enum, both CHECKs and the DTO).

**Recommendation: A.** It is the smallest change that keeps one recompute, one list and one set of policies. Its one real cost, the widened unique index, is a single hand-authored statement.

### 4.2 Migration `0022_reps_at_weight` (illustrative; hand-authored, additive, a manual release step before the code)

```sql
ALTER TABLE "personal_record" ADD COLUMN "at_weight_kg" NUMERIC(7,3);

ALTER TABLE "personal_record" DROP CONSTRAINT "personal_record_record_type_check";
ALTER TABLE "personal_record" DROP CONSTRAINT "personal_record_type_unit_check";
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_record_type_check" CHECK ("record_type" IN (
  'heaviest_weight', 'best_est_1rm', 'best_set_volume', 'max_reps', 'max_calories', 'max_distance', 'max_duration', 'max_reps_at_weight'));
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_type_unit_check" CHECK (
  /* the seven existing arms, then */ ("record_type" = 'max_reps_at_weight' AND "unit" = 'reps'));
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_at_weight_check" CHECK (
  ("record_type" = 'max_reps_at_weight') = ("at_weight_kg" IS NOT NULL) AND ("at_weight_kg" IS NULL OR "at_weight_kg" > 0));

-- widen the key first, then drop the old one (the table is never without a uniqueness rule)
CREATE UNIQUE INDEX "personal_record_user_exercise_type_weight_key"
  ON "personal_record" ("user_id", "exercise_id", "record_type", "at_weight_kg") NULLS NOT DISTINCT;
DROP INDEX "personal_record_user_exercise_type_key";
```

- `NULLS NOT DISTINCT` (Postgres 15+; the repo runs 16 locally and on Neon) makes two NULL weights equal, so the seven old types stay unique per root. If a target database were older, the fallback is two partial unique indexes (`WHERE at_weight_kg IS NULL` and `IS NOT NULL`).
- The `DROP INDEX` removes an index, not a column. The old statements never name it (`DELETE` then `INSERT`, no `ON CONFLICT`), so a release running before the code is unaffected. The `CHECK` replacement is the `0015` pattern.
- No backfill in the migration. Rows come from `records:rebuild`.
- `at_weight_kg` is `NUMERIC(7,3)`, the width of `set_entry.weight_kg`, so a value never needs rounding.
- Row count: at most one row per distinct weight per lineage whose best there is ≥ 6 reps. Over years of logging that can reach dozens per exercise, so AC29's fixtures use 30 weights. It is bounded by the number of distinct weights in the lineage's working sets.

### 4.3 Where the other rules live

`personal_record.value` and `previous_value` hold reps × 1000 (milli, like `max_reps`); the DTO shows reps. The floor is a `@sin/core` constant, not a column or a config value, so changing it is a core edit plus `records:rebuild` (no migration).

## 6. Behavior & logic

### 6.1 The rule (pure, `@sin/core`)

```ts
const REPS_AT_WEIGHT_MIN_REPS = 6;

// workouts: the lineage's working sets grouped per workout, chronological (as computeRecords has them)
running = Map<weightMilli, number>      // best reps over strictly earlier workouts
holder  = Map<weightMilli, {reps, set, previous: number | null}>
for group of workouts:
  best = Map<weightMilli, {reps, set}>  // within this workout; strict ">" so the earliest set wins
  for s of group where eligible(s):     // load modality, weight > 0, reps >= 1, working
    if reps > (best.get(w)?.reps ?? 0): best.set(w, {reps, set: s})
  for [w, b] of best:
    prev = running.get(w) ?? null
    if prev === null or b.reps > prev:  // strictly more than every earlier workout
      holder.set(w, {...b, previous: prev}); running.set(w, b.reps)
emit holder entries with reps >= REPS_AT_WEIGHT_MIN_REPS, by weight descending
```

The floor is applied to the *holder*, never to the baseline. That is how 5 then 7 reads "5 → 7", and why a 15 then 12 then 13 leaves week 1 in place. It is one extra pass of O(sets) with a `Map`, inside the function that already walks the same groups; it shares `groupByWorkout` and the chronology of `computeRecords` (Spec 07.0 D6, D13), so ties and ordering cannot differ from the other types.

### 6.2 The weight, and kg against lb

Identity is `set_entry.weight_kg` read as text and parsed to integer milli-kg (`parseWeightKgMilli`), the same path every other record uses. `weight_kg` is a generated column: the entered `weight` as is for kg, and `weight × 0.45359237` rounded to 3 places for lb. Consequences, all decided in D4:

- **Exact match on the canonical value is right.** The same entered weight always gives the same key, so 25 lb is always 11.340 kg, and a lb lifter's records at "25 lb" never split.
- **25 lb and 11.5 kg never match.** They are different weights (11.340 and 11.500 kg).
- **A lb plate entered as kg.** If the lifter's unit setting was kg when a 25 lb dumbbell was logged as "25", it is 25 kg, a different key from the same dumbbell logged as 25 lb. Nothing can detect that, and a tolerance (for example ±1%) would merge genuinely different weights and break transitivity (A≈B, B≈C, A≉C). The record is per weight as stored; correcting the set (Spec 07.4) fixes the record.
- **Display.** The label converts to the profile unit with the existing formatter: `LB` rounds to one decimal, so 11.340 kg shows "25 lb". The key never depends on the profile unit.

### 6.3 Held now, edits, deletes, re-times

Everything follows from the full recompute (Spec 07.0 D8): there is no incremental path to get wrong.

- A heavier-reps set at a weight replaces the row (new holder, `previousValue` = the old best).
- **Deleting or lowering the holder:** the recompute finds the next-best set at that weight. If its reps are ≥ 6 it holds the row (with a restated `previousValue`, possibly `null` again); if the best is now 5 or fewer, there is no row. A record can therefore be *lost*, exactly as an e1RM record is when its set is deleted. The summary of the workout that held it no longer lists it (17.6 AC15 states this for every type).
- **Changing a set's weight** moves it from one key to another; both keys are recomputed.
- **Re-time (07.4 Phase B)** recomputes all roots, so chronology and `previousValue` follow the new start.
- **Backdated finish:** a backdated workout with more reps at a weight takes the record and the later holder loses it, as for any type (07.0 §6.4).
- **Edit predicate:** `RECORD_MEASURES_BY_MODALITY` already lists `reps` and `weight` for both load modalities, so no change is needed (AC21).

### 6.4 Lineage and modality

Rows are keyed on the lineage root, so a fork and its origin share them (AC22). A lineage whose modality changed (`weight_reps` ↔ `weighted_bodyweight`) compares across modalities, the same accepted corner as Spec 07.0 D20: "12.5" means a barbell load in one and an added load in the other.

### 6.5 Rebuild and backfill

`records:rebuild` already recomputes every root of every user through `recomputeRecordsForRoots`, so it writes the new rows with no change of its own. After `0022` and the Phase B code are live, existing history has no rows of the new type until it runs (or until a finish touches that lineage). It is the same manual release step as Spec 07.0 §6.5 and `CLAUDE.md`'s `records:rebuild`; on staging it runs with `OWNER_DATABASE_URL` (Spec 21.1 AC28). It takes `lockUserRecords` per user, so it is safe beside live traffic.

### 6.6 Latency

The loader already reads every working set of the lineage; the new pass is O(sets). The write grows by up to one row per qualifying weight, so the `INSERT` becomes one multi-row statement per root (AC19). With 21.1's handle, a finish is one scoped transaction, so no added `set_config`. Levers if AC29 fails, in order: confirm the single `INSERT`, then skip the new pass when the root has no eligible set at the floor (a cheap pre-check in core), then reconsider the floor (O1).

### 6.7 Why the floor is 6, not 13

The design review recommended against records for 1–12 reps because "the estimate already rises with each rep". That holds for one set read alone. But a record compares against the best estimate across *all* weights.

Worked example, Epley half-up as in `estimate1rm`: 90 × 8 gives 114.0 kg; 90 × 9 gives 117.0 kg. If the lifter's best estimate came from 100 × 8 (126.7 kg), then 90 × 9 is not an e1RM record, and it is not a heaviest-weight record either. The lifter did more reps than ever at 90 kg and nothing shows.

This is the usual case for double progression (3 × 8–12 at a fixed weight, adding a rep a week) and for back-off sets, on any lift where an older or heavier set holds the best estimate. At a weight the lifter has not exceeded in years, rep gains at that weight are invisible. So a bound at 13 would hide real gains in the 1–12 range, for lifters whose best estimate is old, and the owner set the floor at 6 (D1). Below 6 reps the weight usually matters more than the reps, so those sets don't earn this record, though they still count as its baseline.

**What the lower floor costs.** Records appear more often, because a lifter working through a rep range can beat a rep best most sessions. Each lift holds more rows over time, which AC29's larger fixtures and AC39's list cap answer. A new weight with 6 or more reps is a first time, which is much more common than at 13, so the summary shows nothing for it (D9).

### 6.8 Rollout: the client must tolerate the new value first (follows DESIGN §6)

DESIGN §6 says a new response field ships in the API one release before a client reads it, and that response schemas stay strict. That rule covers the new `atWeightKg` field (old clients ignore the unknown key, because `z.object` strips it). It does **not** cover a new enum member, which an old client cannot ignore: its `z.enum` rejects the whole response (non-production), or the raw body reaches `recordLabel` and throws (production). The finish `PATCH` response carries `newRecords`, so an old tab finishing a workout that sets the new record would fail after the server has finished it.

So the order is reversed for the enum: **the client that tolerates it ships first.**

1. **Phase A** (web): a record list drops items with an unknown `recordType`. This is a narrow, explicit exception to "no shim": a record list is a set of independent facts, and dropping one the client cannot label hides one row; a missing field on a workout breaks the screen. Shape errors stay errors (AC2). It needs a one-line amendment to DESIGN §6 (D3).
2. Wait for the owner's phone to reload onto Phase A (AC5). The only user today is the owner, so this is a check, not a timer.
3. **Phase B** (migration by hand, then merge, then `records:rebuild`).
4. **Phase C** (the ledger row).

*Rejected alternative:* leave `recordType` alone and serve the new record in a sibling array (`newRepsRecords`, `repsRecords`). It follows §6 to the letter and needs no Phase A, but it duplicates the cache seeding, the client, the sorting, the Progress list and the ledger input for a value that is one more kind of record, and every future record type would repeat the choice. Not chosen (D3), but sound if the owner prefers no exception to §6.

## 7. Security & privacy

- **Authorization boundary unchanged.** Every statement keeps its user predicate; the new column rides the table's existing policy, so B cannot read A's rows even if a filter is forgotten (AC18).
- **No new data class.** The row holds a weight and a rep count the user logged. Logs gain nothing: `workout_finished.record_count` already counts rows and carries no value; no weight, reps or set id is logged (Spec 07.0 §6.6).
- **No new input.** No route, parameter or body changes, so no validation message is added (`CLAUDE.md` "Validation messages are static") and the cross-user route suite needs no new case.
- **Query audit.** The `recomputeRecordsForRoots` `INSERT` and `list` rows change fingerprint; both stay `user-filtered`. `Prisma.join` of `Prisma.sql` tuples builds the multi-row `INSERT`; no `Prisma.raw`.

## 11. Deployment & rollback

**Phase A:** web only. Ordinary merge; auto-deploys staging. No migration, no release step. Rollback is a revert.

**Phase B** (after Spec 21.1 has finished, and after Phase A is live and the phone has reloaded):

1. By hand, from the Phase B branch, with the owner login: `OWNER_DATABASE_URL=… pnpm run db:migrate:deploy` (applies `0022`). The runbook step is the `0015`/`0019` pattern: expand-only, brief `ACCESS EXCLUSIVE` while the CHECKs and index change; pick a quiet minute. Check `db:migrate:status`.
2. Merge. Render deploys; the smoke is green. The code is the first thing that writes the new type, but no rows exist yet.
3. `OWNER_DATABASE_URL=… pnpm --filter @sin/api run records:rebuild` (all users). Spot check: a staging account with sets of 6 or more reps lists the rows via `GET /v1/personal-records`.
4. Production is empty: it runs `0001`–`0022` in one pass (runbook Part F) and `records:rebuild` after the seed.

**Phase C:** web only; ordinary merge, after Phase B is verified (DESIGN §6) and after 17.6 Phase A.

**Order with Spec 07.6:** 07.6 first. Until it ships, Spec 07.3's row count counts each new row, so History's number would rise by the number of weights, which is the opposite of what 07.6 fixes.

**Rollback.** Phase C and A: revert. Phase B: revert the code; the column, CHECKs and index stay (expand-only; never roll a migration back). Then run `records:rebuild` with the reverted code, which deletes by root and writes only the old types. Until it runs, the reverted API would serve rows of a type it cannot validate, so run it straight after the revert. Never roll back past Phase A's web while Phase B's rows exist.

**Docs and runbook:** `docs/runbooks/first-deploy.md` B5a (`records:rebuild` after Phase B) and the `0022` step.

## 12. Decisions & open questions

- ✅ **D1 — Sets of 6 or more reps get a real reps record (owner, 2026-11-08).** The owner first approved a floor of 13, then lowered it to 6 after seeing §6.7's example. **Rationale:** an extra rep at a weight is the progress a rep-range lifter works for, and it often shows nothing today. **Rejected by the owner:** 13 (covers only sets with no estimate at all); no floor (records for low-rep sets, where the weight usually matters more).
- ✅ **D2 — A first-time number is not brass and not counted (owner, 2026-11-08, Spec 17.6 D1, applied here).** A weight with no earlier set is a first time (`previousValue: null`), and shows nothing on the summary (D9).
- ✅ **D3 — Add the value to the existing enum, and make the web tolerate unknown values first (owner, 2026-11-08, accepted recommendation).** Phase A's exception to DESIGN §6's "no shim" is narrow (record lists only). **Rationale:** one list, one cache, one sort and compiler-enforced handling in every `switch`. **Rejected:** a sibling array (§6.8), which follows §6 exactly but duplicates every consumer.
- ✅ **D4 — Identity is the exact canonical kg value; no tolerance (owner, 2026-11-08, accepted recommendation).** §6.2. **Rejected:** a ±% tolerance (merges different weights, not transitive); matching in the entered unit (a lb lifter's sets would key on a unit that can change).
- ✅ **D5 — Storage design A, a nullable column (owner, 2026-11-08, accepted recommendation).** §4.1. **Rejected:** a second table, derive on read, the weight inside `record_type`.
- ✅ **D6 — The floor applies to the holder, the baseline is every set at the weight (owner, 2026-11-08, accepted recommendation).** Gives "5 → 7 reps". **Rejected:** a baseline of only sets at the floor (7 after a 5 would read "first time").
- ✅ **D7 — First-time rows are stored, not skipped (owner, 2026-11-08, accepted recommendation).** The exercise page then lists the best at each weight at or above 6 reps, and 07.0 stores first rows for every other type. **Rejected:** storing only beaten rows (a current best would be invisible until beaten).
- ✅ **D8 — One multi-row `INSERT` per root (owner, 2026-11-08, accepted recommendation).** The number of rows per root is no longer fixed at seven.
- ✅ **D9 — A first time at a weight shows nothing on the summary (owner, 2026-11-08).** At a floor of 6 it would appear on most sessions that try a new weight, without beating anything. The row is still stored and shows on the exercise page. **Rejected by the owner:** a quiet "First time at 12.5 kg" line.

**Settled (owner, 2026-11-08, accepted recommendation): each recommendation below was taken.**
- **O1 — The floor.** Decided: 6 (D1). It is one constant plus `records:rebuild`, so it stays easy to change after some weeks of logging.
- **O2 — Approve D3's exception to DESIGN §6.** **Recommendation: yes.**
- **O4 — Does a beaten reps record count in History?** **Recommendation: yes,** its lift counts once (Spec 07.6).
- **O5 — `weighted_bodyweight` with no added weight (pull-ups, dips).** Not covered: `weight_kg > 0` is required, like every weight-based record. **Recommendation: leave it;** a "reps at bodyweight" record needs body weight (`body_metric`, not built).
