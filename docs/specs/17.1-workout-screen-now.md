## 1. Purpose, scope & non-goals

### 1.1 Purpose

Make the workout screen a tool for the **next set**. Today every exercise is a full card with its own entry row and its own "Log set" button, so a six-exercise workout is six forms, and logging a set means finding the right card, fixing the weight with the keyboard and tapping a button that looks like nine others. After this spec:

- **One exercise is "current" and expanded.** The others collapse to one summary line ("Bench Press · 3 sets", "Overhead Press · next 105 × 6"). Logging a set advances "current" for you.
- **Weight and reps are set with big ± buttons**, so the keyboard is the exception.
- **The bottom bar is the per-set action** ("Log 185 × 5"), and becomes "Finish workout" when every planned set is logged. It is the screen's one teal primary fill.
- **A rest timer** starts from the routine's stored rest after each logged set: a countdown in the current-set panel plus a thin teal line across the top of the screen.
- **RPE is no longer shown anywhere** the lifter looks. The data stays.

### 1.2 In scope

**Phase A, RPE hidden (AC1–AC8)**
- Remove the RPE input from the entry row and the set edit sheet, the RPE picker from the routine item sheet, and the RPE text from set rows and target lines (active session, finished summary, History detail, routine editor and preview).
- Keep the data path whole: drafts, request bodies, DTOs, the export, the database. Editing a set never clears a stored RPE.

**Phase B, the "now" screen (AC9–AC40)**
- The current-exercise model: collapsed summaries, tap-to-select, default current, auto-advance after a log, superset alternation (§6.1–§6.3).
- ± steppers for weight and reps (§6.4); the Stone entry panel with the current set's figures (§6.5).
- The bottom `ActionBar` as the per-set action, then Finish (§6.6); "Add exercise" moved to the end of the list.
- A **Workout menu** at the top holding **End workout early** (with the unlogged-sets list) and Discard; the **elapsed-time clock** (§6.7).
- The 17.0 reviewer notes: one teal primary fill, the "(Warm-up)" suffix hidden visually, signature figures (§6.9).
- Accessible names for the bare "Options", "Log set" and failed-row buttons (§6.8). New tests, extended AC6 allow-lists, docs.

**Phase C, rest timer (AC41–AC54)**
- A timestamp-based rest timer started by a logged set, its readout in the current-set panel, a sticky progress line at the top, restore after a reload (§6.10).

### 1.3 Size and split

This is three work sessions of different shapes: A is mechanical and independent; B is the restructure; C needs B's panel but has its own storage and tick logic. §12 D1 recommends **shipping them as three PRs in the order A, B, C**, and says how to cut them into separate spec files (17.1a, 17.1b) if you want that. ### 1.5 First-principles notes

> **Derived state versus stored state.** "Which exercise is current" can mostly be *computed* from the workout (the first exercise with sets left to do, or the one you last logged). State you can compute should be computed, because stored copies drift (another device logs a set, a reload happens, an exercise is removed). We store only what the lifter *chose* (they tapped a row) and fall back to the computed answer when that choice no longer applies. That is why §6.2 has a pure `chooseCurrent` function and a thin hook around it.

> **A stepper is just another way to type.** The entry-row draft is a record of *strings* (`"185"`, `"12."`), because a half-typed number is legitimate while typing. A ± button is a pure function from one string to another (`"185"` → `"190"`) dispatched through the same `edit` action the keyboard uses. So validation, the "edited" flag, draft persistence (06.5) and the re-seed rule (10.2) need **no new path**: a stepper tap is an edit, like a keystroke.

> **A countdown must be derived from a clock, never counted.** Browsers throttle `setInterval` in background tabs, and a phone with the screen off may not run JavaScript at all. A timer that subtracts 1 each tick would be minutes behind when you come back. Instead we store the moment the rest *started* and its length, and every render computes `remaining = start + length - now`. Ticks only trigger re-renders; they carry no state. The same trick makes the timer survive a reload: the start time can be written to storage and read back.

> **`useSyncExternalStore` and small external stores.** React re-renders a component when its state changes, and everything below it unless memoized. The bottom bar's button needs the current entry row's label ("Log 185 × 5") and validity, which change on every ± tap. Lifting that into `ActiveSession` state would re-render the whole card list per tap. A tiny external store (a value, a `subscribe` function) read with `useSyncExternalStore` re-renders only the subscribers. The entry row *publishes* to it, and the bar button *subscribes* (§6.6). The same pattern isolates the per-second tick (§6.10).

> **Label in name (WCAG 2.5.3).** A button's accessible name must contain its visible text, so voice control ("tap Log 185 times 5") works. That is why "Options" becomes `aria-label="Options for Bench Press"` (visible text first, exercise after) rather than a replacement name.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"17.1 ACn — …"`** (the 06.5 / 10.x convention; a scan test enforces it, AC56). Levels are in §10. Phases A, B and C ship as separate PRs; a phase's criteria must pass in its own PR.

### Phase A — RPE hidden (data and API unchanged)

1. **No RPE input in the logging forms.** The entry row has no "More" disclosure and no field labeled RPE; the set edit sheet has none. (`SetFields` no longer renders the field in either variant.)
2. **An edit never clears a stored RPE.** Editing the reps of a logged set that has `rpe: 8` through the sheet sends a `PATCH` body containing `reps` only, with **no `rpe` key** (`draftFromSet` still copies `set.rpe` into the draft's `rpe` string and `parseDraft` still reads it, so `diffForPatch` sees no change). A new log from the entry row sends no `rpe` key.
3. **Set rows never show RPE.** `formatSet` no longer appends " @8": the active card's rows, the finished-workout summary and the History detail show the same text without it, in both visible text and accessible names. A set with `rpe: 8` renders identically to one with `rpe: null`.
4. **Target lines never show RPE.** `targetLine` omits the "RPE n" part everywhere it renders (active card, finished summary, routine editor rows, routine preview), and so do the accessible names built from it (`itemAccessibleName`). The weight and rest parts, their order and separators are otherwise unchanged ("4 × 6–8 @ 100 kg · 2:00").
5. **The routine item sheet has no RPE control, and RPE round-trips.** The sheet shows no RPE field. Opening an item with `targetRpe: 8.5` and pressing Done, then saving, sends `targetRpe: 8.5` unchanged (the draft keeps the value; the sheet never nulls what it cannot show). A new item sends today's body.
6. **Nothing below the UI moved.** `git diff main --stat` shows no path under `apps/api/`, `packages/core/`, `render.yaml`, `Dockerfile` or `.github/workflows/`. The DTO schemas still carry `rpe` and `targetRpe`; the msw fakes still emit and accept them; the draft store still stores its nine fields including `rpe` (06.5 AC1 passes unmodified); and the account export still includes both (its existing integration test passes unmodified, because the export composes the read DTOs).
7. **Dead code is gone, not hidden.** `RPE_CHOICES` and the sheet's RPE `<select>` are deleted if nothing else uses them; `validateDraft`'s `targetRpe` message may stay if the schema path still exists (it cannot fire from the UI). A source scan finds no user-visible string "RPE" in a non-test `.tsx` / `.ts` file under `src/` (the schema field names and the stored-data comments are the only allowed mentions).
8. **Docs.** DESIGN.md records **Q23** (§ Cross-doc updates) and PRODUCT.md's existing line stays true; Spec 06.1 / 09 / 10.0 / 10.2 carry a one-line amendment note.

### Phase B — the "now" screen

**The current exercise**

9. **One expanded, the rest collapsed.** In a workout with ≥1 exercise, exactly one exercise renders the full card (header, note action, Options, logged sets, entry panel). Every other exercise renders a collapsed row: an `<article>` whose heading contains one button with `aria-expanded="false"`. A collapsed row mounts no `EntryRow`, `SetEditSheet`, `NoteSheet` or Options.
10. **Collapsed summaries.** The visible text is exactly the §6.2 table: done ("Bench Press · 3 sets" plus a drawn check icon), partly done ("Bench Press · 2 of 4 · next 185 × 5"), upcoming ("Overhead Press · next 105 × 6"), open exercise with sets ("Curl · 2 sets", no check), and open with none ("Triceps Pushdown · 3 × 12" from the target line, else "Curl · no sets yet"). The check is an SVG (`aria-hidden`), never a "✓" glyph; the accessible name carries the same information in words, includes the unit, and names the superset ("Bench Press, superset 1, 3 sets logged"). A collapsed row also shows "Not saved yet" / "Couldn't save" text when any of its sets or its note is queued or failed (06.2).
11. **Tap to make current.** Activating a collapsed row makes it current: it expands, the previous current collapses, and focus moves to the new card's heading button. The collapsed exercise's edited draft survives (it is persisted on unmount and restored on remount, 06.5 AC6–AC8); an untouched draft is simply re-seeded (10.2 AC25).
12. **Default current is computed, not stored.** `chooseCurrent(rows, lastLoggedId)` is pure: with no sets logged it is the first exercise in display order that has an unlogged planned set or is open; otherwise it is `advanceAfterLog` applied to the exercise holding the most recently created set (§6.2); with nothing left anywhere it is the last-logged exercise. The hook initializes its chosen id from it once, keeps the lifter's choice, and re-derives only if the chosen exercise disappears.
13. **Adding and removing.** A newly added exercise becomes current once it appears. Removing the current exercise re-derives current. Neither moves current when the lifter is not the one who acted (a refetch after another device's change never changes the chosen id).
14. **Auto-advance after a log.** When a log succeeds (accepted into the outbox, 06.2) and the lifter has **not typed since the tap**: (a) current stays on an exercise with more planned sets; (b) after its last planned set it moves to the next exercise in display order with unlogged planned sets, wrapping to earlier ones, and stays put when there is none; (c) an extra set (past the plan) or any set on an open exercise leaves current alone; (d) inside a superset run see AC15. If the lifter *has* typed since the tap (06.1 §6.5's `editedSinceTap` branch) current does not move.
15. **Superset alternation.** For an exercise in a run (a maximal chain of `linkedBelow` rows inside one segment): after a log, current becomes the next member in cyclic order (A → B → A …) that still has an unlogged planned set; a member with none is skipped; when only the logged member has sets left, it stays; when none do, AC14(b) applies from the run's last member. A member that is open (no plan) takes part only as the logged one. Alternation never reads the stored `supersetGroup` number, only `supersetRows`' links.
16. **Brackets and sections unchanged.** Collapsed rows sit inside the same bracket and the same section segments, with the same ordinals ("superset 1") and headings; `supersetRows` and `sectionSegments` stay the only places that derive them (the 10.1 / 10.3 source scans pass unmodified). The `LinkToggle` between two rows shows when either neighbor is current; for other pairs only the bracket's continuity renders. Move up/down and link/unlink on the **current** card behave exactly as in 10.1 / 10.3 (their tests are re-pointed to the expanded card, not rewritten).
17. **Reveal before scrolling.** Everything that scrolls to a row in a card that may now be collapsed first makes that card's exercise current: the sync line's "Show" for a failed set or note (06.2 AC14), and the Finish-blocked "Needs data" scroll (06.1 AC33). Both then scroll to the row after commit.

**Steppers and the entry panel**

18. **Weight stepper.** For `weight_reps` and `weighted_bodyweight` (label "Added weight") the entry panel shows a weight stepper: a − button, a big number, a + button. A tap changes the weight by **5 when the draft's unit is lb, 2.5 when kg**, computed in integer milli-units (`187.5 + 2.5 = 190`; no floating-point residue), floored at 0, capped at `SET_WEIGHT_MAX` (the + button is disabled at the cap and the − at 0). A blank or unparsable value steps from 0. The result is written back through the formatter `formatWeight` (no trailing zeros).
19. **Reps stepper.** For `weight_reps`, `bodyweight_reps` and `weighted_bodyweight`: ±1, floored at 0, capped at `SET_REPS_MAX`, blank steps from 0.
20. **The number is still an input.** The big number is a text input (`inputMode` decimal for weight, numeric for reps, `autoComplete="off"`), selects its text on focus so typing replaces it, and shows the same static validation messages as today (`parseDraft` is unchanged). Pressing Enter in it logs when the draft is valid and shows every message when it is not (the 06.4 D2 behavior).
21. **A stepper tap is an edit.** It goes through the `edit` action: the row becomes touched (not re-seeded by a count change, 10.2 AC25), the draft is persisted (06.5 AC6), `editedSinceTap` is set, and `set_logged.edited` is true. Seeding is untouched: `seedDraft` stays the only function that builds a `SetDraft` from a list (a source scan).
22. **Other modalities.** `bodyweight_reps`: the reps stepper only. `weighted_bodyweight`: both. `duration` and `distance_duration` keep their Minutes / Seconds and Distance fields (no stepper), restyled at the same size as the figures. The logged-set text, the label and the bar follow the modality (§6.6 table).
23. **Set type and unit stay reachable.** A collapsed "Set options" disclosure in the panel holds the Set type select and the weight / distance unit selects (their values are the draft's, so a lb/kg change re-steps by the new unit). A non-working planned set shows its type in the panel label ("Set 1 of 5 · Warm-up"); `data-set-type` is on the panel. The edit sheet keeps today's visible Set type and unit-beside-weight layout.
24. **44 px targets.** The ± buttons, the number inputs, the collapsed row, the Workout menu button and its items, "Set options", and the bar button are each ≥ `--tap-target-min` in both axes (a CSS scan plus a layout assertion in the screenshot harness); the ± buttons are sized for a thumb (≥ 3rem, §6.4).

**The bottom bar and finishing**

25. **The bar is the per-set action.** With a current exercise that has an unlogged planned set or is open, the `ActionBar` holds one full-width primary button reading "Log {values}" per the §6.6 table ("Log 185 × 5", "Log 12 reps", "Log +25 × 8", "Log 1:30", "Log 5 km · 25:00"). It reads "Log set" and is unavailable (`aria-disabled`, click ignored; §6.8 amendment) while the draft does not parse. Its accessible name starts with its visible text: "Log 185 × 5 for Bench Press".
26. **One tap logs a planned set.** On a routine-started exercise whose next planned row has the measures its modality requires, the draft arrives valid and one tap on the bar sends `POST …/sets` with the row's values and `setType`, `isComplete: true` and the draft's `attemptKey` as `clientGeneratedId` (10.2 AC23 restated). The double-tap window (600 ms with nothing typed; across a panel swap it covers only the advance the tap itself caused, so any other input in between, such as a row tapped or an exercise added, ends it; *amended 2026-10-16 after the post-merge smoke*), the in-flight guard and the retry-with-same-key rule (06.1 §6.5) behave as today. No button inside an exercise card is named "Log set".
27. **Finish mode.** The bar reads **"Finish workout"** exactly when the workout has ≥ 1 planned set, **no** unlogged planned set (positional, all exercises, queued sets counted as logged), and the current exercise has a plan. Otherwise it is a Log button; a workout with no exercises shows "Add exercise" instead. In Finish mode the entry panel stays (an extra set is still possible) and gains a **secondary** "Log extra set" button. A workout with no planned sets anywhere never shows Finish in the bar.
28. **Finish keeps every rule.** The Finish button opens today's Finish dialog and is unavailable in the same cases (the bar's button by `aria-disabled`, §6.8 amendment) (no sets, a set or note write pending or failed, structure busy, 06.2 AC16, 10.3 AC29) with today's hint lines; the incomplete-sets diagnosis (06.1 AC33) and the clock / conflict handling are unchanged.
29. **Focus survives advance.** The bar's button is one persistent element: after a log and an auto-advance, focus is still on it (the entry row publishes to an external store and unmounts; the button does not). `aria-busy` is set while a log is in flight, without `disabled` (06.1: a disabled button drops focus).
30. **Add exercise moved into the list.** "Add exercise" is a secondary button after the last section / row, disabled while a structure write is busy, and it is gone from the bar. In a workout with no planned sets anywhere, a secondary "Finish workout" sits beside it. Opening the picker and adding an exercise behaves as today (AC13 selects the new card).

**Top row: clock and Workout menu**

31. **Elapsed clock.** The top row shows the workout's elapsed time since `startedAt` as `m:ss`, switching to `h:mm:ss` at one hour, beside the existing "Started 10:15" text. It is clamped at 0:00 if the device clock is behind `startedAt`, updates once a second from the clock (§6.10 `useNow`), has no live-region announcements, and is unaffected by rest or by which exercise is current.
32. **Workout menu.** One secondary button "Workout menu" (`aria-expanded`) in the top row reveals two buttons inline (the ExerciseCard Options pattern, no popover): **End workout early** and **Discard workout**. Discard's dialog and rules are unchanged.
33. **End workout early.** The item opens a `ConfirmDialog` titled "End workout early?" whose body lists the unlogged planned sets by exercise ("Overhead Press · 3 sets", total "5 planned sets not logged"), then the note that a finished workout can't be edited. Confirming ("End workout") runs the same `confirmFinish` path as Finish, so every wait, block and failure message is identical. It is disabled with the reason "Log a set first" when nothing is logged, and with Finish's reasons otherwise. When nothing planned is unlogged (all done, or a workout with no plan), the item is labeled **"Finish workout"** and opens today's Finish dialog instead.

### Phase C — rest timer

41. **A rest starts after a log.** After a set is accepted for the current exercise, a timer `{ startedAt, durationS }` is set from that exercise's `restSeconds` when **all** hold: `restSeconds` is non-null and > 0; the logged set's type is not `warmup`; the workout still has an unlogged planned set (no rest after the last one); and, for an exercise in a superset run, the log completed a round (§6.10 table). The duration is the logged exercise's own `restSeconds` (≤ 900 by schema). Rest also starts when the advance rule was suppressed because the lifter typed (AC14).
42. **Every log replaces the timer.** A log that starts no rest (no stored rest, a warm-up, the final planned set, a mid-round superset member) **clears** a running timer; one that does replaces it with a fresh `startedAt`.
43. **The clock decides.** `remainingSeconds(timer, now)` is pure (`ceil((startedAt + durationS * 1000 - now) / 1000)`, clamped to 0); a test that advances a fake clock by 90 s in one jump shows 30 s left with no intermediate ticks. Nothing decrements per tick. The tick interval runs at most once a second, only while a timer is active and the page is visible, and a `visibilitychange` to visible recomputes at once.
44. **Where it shows (owner: placement A + line B).** While resting, the entry panel's label row shows "Rest 1:42" (`role="timer"`, not a live region), in the same slot where it otherwise shows nothing; at zero it shows "Ready" until the next log. A sticky 3-px line across the top of the scrolling area fills from empty to full over the rest (`aria-hidden`, width from the same `remainingSeconds`), and disappears at zero. With `prefers-reduced-motion: reduce` the fill is set per tick with no transition.
45. **The bar and the clock do not change.** During rest the bottom button still reads "Log …" and one tap logs (and restarts or clears the timer, AC42); the elapsed-time clock (AC31) keeps showing total workout time.
46. **Restored after a reload or a long background.** The timer is stored under `sin:workout:rest` through the `StorageAdapter` as `{ v: 1, userId, workoutId, startedAt, durationS }`, zod-checked on load: a failed parse, another user, another workout, a non-finite number, `durationS` outside 1–900, or a `startedAt` more than 5 s in the future (the clock was changed) is dropped; an already-expired timer restores as "no timer" (no "Ready"). Writes are not debounced (one tiny write per log). A storage failure is reported once through `reportUnexpected` with a static message and the timer keeps working in memory.
47. **It ends with the workout and the user.** Finish success, Discard success and the gone path remove the key (alongside `draftStore.clearWorkout`); `sin:workout:` is already in `USER_DATA_KEY_PREFIXES`, so `logoutAndClear` clears it and the logout write-block applies (06.5 AC5's rule); a different user signing in finds it dropped.
48. **Screen reader behavior.** The countdown text is not announced per second. One polite status ("Rest over") is announced when a visible timer reaches zero. A source scan finds no `navigator.vibrate`, `Notification`, `Audio`, `AudioContext` or `serviceWorker` use in the new files.
49. **The tick is isolated.** A shared `useNow(intervalMs, active)` hook feeds three small components (the clock, the readout, the line). A test renders a five-exercise session, advances the fake clock 5 s, and asserts no `ExerciseCard` or `EntryRow` re-rendered.
50. **A rest never blocks anything.** Finish, Discard, End early, Add exercise, regroup, note editing, a tab switch and navigating away all work during rest; leaving the screen unmounts the tick but the stored timer is still there when the screen returns.
51. **Hygiene.** No timer value, duration or exercise name goes to `track`, `reportError` or `console` (a spy test over the new paths); the stored key is under a `USER_DATA_KEY_PREFIXES` prefix; no new key prefix is added.
52. **Fake clock in tests.** The rest and clock code reads time through an injectable `now()` (default `Date.now`), so every Phase C test controls it.

## 6. Behavior & logic

### 6.1 Rows and progress

Everything derives from `supersetRows(workout.exercises)` (display order, run links, section ids) and the **outbox-projected** list already on `workout` (06.2). For each exercise: `planned = plannedSets.length`, `logged = sets.length` (all types, queued and failed included, as in 10.2 D2), `remaining = max(planned − logged, 0)`, `open = planned === 0`. Progress is **positional**, never `setNumber`.

### 6.2 The current exercise

**Choosing (`chooseCurrent`, pure).** `lastLoggedId` = the exercise holding the set with the greatest `createdAt` (ties: later position). If no set exists: the first exercise in display order with `remaining > 0` or `open`; if none, the first. Otherwise: `advanceAfterLog` applied to `lastLoggedId` with `wasExtra = false`.

**Advancing (`advanceAfterLog`, pure).** Given the rows (after the log), the logged exercise `X`:

1. If `X` is in a run: the next member after `X` in cyclic order (X last) with `remaining > 0`; found → it. None → step 3.
2. If `X` is not in a run: `wasExtra` or `open` → `X`; `remaining > 0` → `X`; else step 3.
3. The first exercise after `X` in display order with `remaining > 0`, wrapping to earlier ones; none → `X` (this is the "all done" state; the bar becomes Finish).

An exercise entered via step 3 that sits in a run is entered at its first member with `remaining > 0`. Runs never cross a section segment (`supersetRows`), so alternation never leaves a section.

**The hook.** `useCurrentExercise(rows)` holds `chosenId`, initialized from `chooseCurrent`. `select(id)` sets it (a tap, a reveal, a new exercise). `EntryRow`'s `onLogged` calls `advance`. If `chosenId` is no longer in the rows, it is re-derived. Another device's change never moves it.

**Collapsed summaries** (`collapsedSummary`). `next` is the next planned row: `{weight} × {reps}` for `weight_reps` (reps as `low–high` when they differ), `+{weight} × {reps}` for `weighted_bodyweight`, `{reps} reps` for `bodyweight_reps`, otherwise `set {logged + 1}`; the weight's unit is appended only when it differs from the profile's unit; a non-working row appends " · Warm-up" (or the type label).

| State | Condition | Visible text | Example |
|---|---|---|---|
| Done | `planned > 0`, `logged ≥ planned` | `{name} · {logged} sets` + check icon | Bench Press · 3 sets ✓ |
| Partly done | `planned > 0`, `0 < logged < planned` | `{name} · {logged} of {planned} · next {next}` | Bench Press · 2 of 4 · next 185 × 5 |
| Upcoming | `planned > 0`, `logged = 0` | `{name} · next {next}` | Overhead Press · next 105 × 6 |
| Open with sets | `planned = 0`, `logged > 0` | `{name} · {logged} sets` (never a check) | Curl · 2 sets |
| Open, none | `planned = 0`, `logged = 0` | `{name} · {target line}` else `{name} · no sets yet` | Triceps Pushdown · 3 × 12 |

A superset member's accessible name begins "Name, superset N" (the ordinal from `runOrdinals`, never the stored group).

### 6.3 Why one expanded card instead of an accordion of many

Several expanded cards would keep the page long, which is the problem. One current exercise also makes the bar's meaning unambiguous: "Log" always logs the current set of the current exercise. The cost: moving an exercise or editing its logged sets from a collapsed row takes one extra tap (make it current first). Link toggles follow the same rule (AC16) so a column of collapsed rows is not interleaved with 44-px toggles.

### 6.4 Steppers

- **Math:** parse the draft text with the same grammar as `parseDecimal` (commas allowed), convert to integer milli-units, add the step, clamp to `[0, SET_WEIGHT_MAX × 1000]`, convert back with `formatWeight`. Unparsable or blank text steps from 0. Reps: integer ±1, `[0, SET_REPS_MAX]`.
- **Step size follows the draft's `weightUnit`** (D5): 5 for lb, 2.5 for kg. The step is relative (187 + 5 = 192), never snapped to a plate multiple.
- **Layout:** a three-part control per measure: − button, the number input with its unit/label under it, + button; the weight and reps controls share a row where both numbers stay readable and stack otherwise (*amended in implementation, 2026-10-16:* with ≥ 3rem buttons two steppers side by side left each number 29 px wide at 390 px, so the entry panel wraps them below `--stepper-min-width`; on a phone they stack, on a desktop they share a row). Buttons are ≥ 3rem square so the thumb lands without aiming; the group has `role="group"` and a visible label ("Weight · lb", "Reps").
- **At a limit,** the button is `disabled` (not hidden), with the limit evident from the number.
- **Edits:** a tap calls the existing `onChange(field, value)` (AC21).
- **Duration and distance** keep their text fields, sized like the figures (D6).

### 6.5 The entry panel

`EntryRow` keeps its logic (draft reducer, in-flight guard, double-tap window, key re-minting, announcements, server field errors) and keeps `<form aria-label="Log a set of {exercise}">`. It drops its own submit button, renders the label row (`setLabel` text, and in Phase C the rest readout), the steppers (`SetFields variant="entry"`), the "Set options" disclosure and the messages, on a `--color-signal-soft` ground with no outline. It publishes its action to the `logAction` store whenever the label, validity or busy flag changes (one `useEffect`), and unpublishes on unmount. After a successful log it calls `onLogged({ exerciseId, set, advance, wasExtra })`, **last**, so its own bookkeeping (draft reset, `drafts.clear()`, `setSeededFor`) happens while it is still mounted. `advance` is false in the "typed since the tap" branch.

### 6.6 The bar

**Mode** (`barMode`, pure, from `unloggedPlanned` and the current progress): `add` (no exercises), `finish` (AC27), else `log`.

**Label** (`logLabel`, from the draft; mirrors `formatSet`'s core; the unit is appended only when it differs from the profile's):

| Modality | Label | Example |
|---|---|---|
| `weight_reps` | `Log {w} × {r}` | Log 185 × 5 |
| `weighted_bodyweight` | `Log +{w} × {r}` | Log +25 × 8 |
| `bodyweight_reps` | `Log {r} reps` | Log 12 reps |
| `duration` | `Log {m:ss}` | Log 1:30 |
| `distance_duration` | `Log {d} {unit} · {m:ss}` | Log 5 km · 25:00 |
| any, draft invalid | `Log set` (`aria-disabled`) | |

`LogBarButton` reads the store with `useSyncExternalStore` and renders a primary `Button` with `aria-label` = `{label} for {exercise}`, `aria-disabled={!valid}` with the click ignored (amended: never `disabled`, §6.8), `aria-busy` while in flight, and `onClick={run}`. In Finish mode `ActiveSession` renders its own Finish button in the same bar slot with today's `finishDisabled` and hints. `ActionBarHint` lines keep today's wording.

### 6.7 End early, the clock and the Finish contract with 17.2

`unloggedPlanned(rows)` returns `{ total, byExercise: [{ name, count }] }` (positional). End-early's dialog is `ConfirmDialog` with the list and the existing "A finished workout can't be edited." sentence; its confirm calls `confirmFinish()`. **Contract for 17.2:** `ActiveSession` exposes the finish dialog and the end-early dialog as two `ConfirmDialog` usages over the same `confirmFinish`; 17.2 may replace their children and titles but not the call, the lock (`finishLock`) or the waits. The clock is `SessionClock` over `useNow` (Phase B uses a plain 1 s interval; Phase C's `useNow` replaces it without changing the component).

### 6.8 Names and focus

Options, failed-row buttons, steppers and the bar get names per AC38. When current changes by a tap or a reveal, focus moves to the new card's heading button (a collapsed row's button no longer exists after it expands) and the card is scrolled into view with `block: "nearest"` (no smooth scrolling). When it changes by auto-advance, focus stays on the bar button (AC29) and the new card is scrolled into view.

*Amended in implementation (2026-10-16, final review):* the bar's button is never `disabled`, since a disabled button drops focus. An unparsed draft, Finish waiting on an unsaved set, or a busy Add use `aria-disabled` and ignore the click. A log made with Enter that advances moves focus to the new card's heading, because the focused input unmounts. When the screen opens, the current-set panel is scrolled into view once (`block: "nearest"`, clear of the bar).

### 6.9 The reviewer notes

- **One teal fill:** the session screen's only primary `Button` is the bar's. "Add exercise", "Log extra set", the Workout menu, the steppers and Set options are secondary. Dialogs are modal, so their confirm buttons do not compete.
- **Warm-up suffix:** `formatSet` returns `{ core, typeSuffix }` (or a second function does); the row renders the suffix in a visually hidden span for `warmup` (and the other non-working types keep their visible text, since only warm-up has the W mark). The W mark stays.
- **Figures:** the stepper numbers use the three figure tokens. No new token.

### 6.10 Rest timer (Phase C)

**When it starts** (`restAfterLog`, pure): given the logged exercise, the set, and the rows after the log, returns `{ durationS }` or `null`:

- `null` if `restSeconds` is null or 0, the set is a warm-up, or no exercise has an unlogged planned set (D8, D9).
- For an exercise **not** in a run: `{ durationS: restSeconds }`.
- For an exercise in a run: only when the log **completed a round**, meaning the next member in cyclic order is not later in display order than the logged one (the wrap, or the exercise itself). Mid-round it returns `null` (no rest between A and B). The duration is the logged member's own `restSeconds`; a null there means no timer. (DESIGN §2 item 8: one rest timer per group, after its last exercise.)

**State.** `useRestTimer(workoutId)` holds `timer | null`, started by `onLogged` (`start(durationS)` or `clear()`), reading and writing `restStore`. `remainingSeconds(timer, now)` is the only arithmetic.

**Ticking.** `useNow(250, active)` re-renders only `RestReadout`, `RestLine` and `SessionClock`. 250 ms keeps the displayed second accurate without drift; the interval is cleared when no timer is active (the clock keeps its own 1 s), and while `document.visibilityState === "hidden"`.

**Display.** Readout "Rest m:ss" (tabular figures, in the label row), "Ready" at zero. Line: a 3-px sticky bar at the top of the scrolling area, `--color-line` track, `--color-signal` fill.

**Why in the panel plus a line.** Owner chose placement A (calm, where you look for the next set) and added B's line (visible from any scroll position, whatever you are looking at); the mockup's third option (the button becoming the timer) was rejected because logging early would need a Skip tap (D7).

### 6.11 RPE (Phase A)

Hide by *not rendering*, never by stripping data: the draft type keeps its `rpe` field (06.5's nine-field store is unchanged), and the DTOs and fakes keep `rpe` and `targetRpe`. As built (2026-10-16, after the pre-PR reviews):

- **No new set carries RPE.** Every entry-row draft starts with a blank `rpe`: `seedDraft` blanks it on both branches and a restored draft has it blanked. Otherwise the copy-forward draft, or a draft saved before Phase A, would send a value the lifter can neither see nor clear.
- **No edit sends RPE.** The set edit sheet still builds its draft with `draftFromSet` (so the stored value is in the draft), but `diffForPatch` never includes `rpe`. A stored value can't be cleared, even one that fails to round-trip through the draft's text. `rpe` maps to no input in `draftFieldForPath`, so a server error on it is a form-level message.
- **`parseDraft` still reads `rpe`,** but an unparsable value is dropped rather than raised, because no input remains on screen to fix it.
- **Routines:** the item sheet passes `targetRpe` through unchanged. `validateDraft` sends a stored target the schema would refuse as `null` instead of blocking a save, and has no RPE message.

The only other change is what the forms render and what the formatters print.

## 7. Security & privacy

- **No new data leaves the device.** The rest key holds timestamps and a duration, scoped by `userId` + `workoutId`, under the `sin:workout:` prefix, so logout removes it (06.0 AC20) and a different user cannot read it (AC46).
- **RPE hiding is presentation only.** Data stays; the export and erase paths already cover it (Spec 11). No authorization change; no new route.
- **Static messages, no echoes.** New copy is static; no typed value, exercise name or timer value goes to `track`, `reportError` or `console` (AC51, AC53).
- **Clock tampering** can only change the lifter's own rest display; a future-dated stored timer is dropped (AC46).
- **The logout guard and `logoutAndClear` are untouched** (AC36).

None. No env var, secret, Auth0 or CSP change. Constants (`WEIGHT_STEP = { lb: 5, kg: 2.5 }`, the future-dated tolerance of 5 s, the tick interval) live in the modules that use them. The rest bound (900 s) comes from the schema (`routine.ts`), not a literal.

## 11. Deployment & rollback

**Ships** as three PRs merged in order A, B, C, each auto-deployed to staging by Render. **No release step, no migration, no API deploy, no env var, no ordering constraint with the backend.** The SPA is a static bundle with hashed assets, so a user mid-workout who reloads onto a new build simply gets the new screen; their outbox, drafts and workout are unchanged by shape (AC34, AC35), and a stored `sin:workout:rest` from Phase C is ignored harmlessly by an older build.

**Rollback:** revert the PR. Order matters: **revert C before B**, because the rest readout lives in B's panel and the timer reads B's `onLogged`; A is independent of B and C. Nothing is written to the server that old code cannot read; stored drafts keep the nine-field shape in every version, so a revert mid-workout restores the old per-card forms with the same draft values. A leftover `sin:workout:rest` key needs no cleanup (logout removes it). Re-saving routines after Phase A changes nothing about RPE (the draft preserves it).

After each deploy: the Spec 06.3 smoke (its selectors are updated, AC58), then the owner's phone check after B and again after C.

## 12. Decisions & open questions

### Decisions (✅ — to be recorded as Q23 and Q24 in DESIGN.md)

- ✅ **D1 — Three phases, three PRs, one spec (owner accepted 2026-10-16).** *Rationale:* the whole of 17.1 is more than one session (59 criteria). Ship A (RPE hidden: small, mechanical, independent, can go any time) first, then B (the restructure, the bulk of the risk), then C (the rest timer, with its own storage and tick logic) on B's panel. Keeping one spec document keeps the cross-cutting rules (§6.5's publish-then-`onLogged` order, the bar mode, the shared `useNow`) in one place; if you would rather have separate files, cut cleanly at the phase headings: **17.1a = Phase A** (AC1–AC8 plus its docs) and **17.1b = Phase C** (AC41–AC54 plus the 17.1b rows of AC55–AC59), leaving 17.1 as Phase B, with README rows "17.1a" and "17.1b" and the dependencies 17.1a → none, 17.1 → 17.0, 17.1b → 17.1. *Rejected:* one PR for everything (one revert unit, but an unreviewable diff touching every session test).
- ✅ **D2 — One current exercise; the rest collapse to one line** (owner, 2026-10-15). *Rationale:* the next set comes first (PRODUCT principle 1); one expanded card makes the bar's "Log" unambiguous. *Cost:* one extra tap to move or edit a collapsed exercise (§6.3). *Rejected:* an accordion with several open cards (keeps the page long, and "which set does Log mean?" returns).
- ✅ **D3 — Current is computed, with the lifter's choice on top** (§1.5, §6.2). In a superset it alternates automatically (owner, 2026-10-15); in a workout without a routine it is the exercise last logged or added, and the screen does not feel empty because the panel always shows "Set N" with copy-forward values and steppers, and the bar always logs. *Rejected:* storing current in `localStorage` (drift, a new key, logout handling for no benefit; the computed default is right after a reload).
- ✅ **D4 — Auto-advance moves only on a planned set that finished its exercise, or within a superset round;** extra sets and open exercises stay (a lifter who taps a finished exercise to add a set must not be bounced away), and typing since the tap suppresses it (06.1's `editedSinceTap` rule: they are mid-entry).
- ✅ **D5 — The stepper's step follows the unit of the set being logged (the draft's `weightUnit`), not the profile unit** (owner: ±5 lb, ±2.5 kg for kg users, 2026-10-15). *Rationale:* weights are stored as typed with their unit (DESIGN §4.8) and a planned row can carry lb for a kg-profile user (or the reverse); stepping 2.5 on a number the lifter reads as pounds would be wrong, and a step that changed when the profile changed would be surprising. The unit shown next to the number is the unit stepped. The change-unit select does not convert the number (as today), so the step changes with it. *Rejected:* profile unit (wrong step on a mismatched plan); one step for both units; snapping to plate multiples (surprising).
- ✅ **D6 — Steppers only for weight and reps; duration and distance keep their fields.** *Rationale:* the right step for a plank (5 s) differs from cardio (1 min) and a run (0.1 km): it depends on the exercise, and we hold no data to choose it. The fields restyle at figure size, so the screen is consistent. *Revisit:* with a per-exercise step, or after phone use shows which duration steps are right.
- ✅ **D7 — Rest: placement A plus B's line, bottom button stays "Log …"** (owner, 2026-10-15). The corner clock keeps total workout time. *Rejected:* C (the button becoming the timer; logging early would need a Skip tap).
- ✅ **D8 — A warm-up never starts a rest, and a log always replaces the previous timer.** *Rationale:* the routine's `restSeconds` is one number per exercise, meant for working sets; a two-minute rest after an empty-bar warm-up would be wrong more often than right. The last planned set of the workout starts none (nothing follows it). Superset members rest only at round end (DESIGN §2 item 8, one timer per group).
- ✅ **D9 — No stored rest means no timer** (decided here, as the owner asked). *Rationale:* a made-up default (90 s?) would be a number nobody chose, would fire in free-form workouts the lifter never asked it for, and would sit beside "2:00" timers that mean something. *Reversal cost:* one constant; the proper form is a Profile "default rest" later, which needs a per-user preference (an API field or a `sin:pref:` device key) and is out of scope.
- ✅ **D10 — Timestamp-based, persisted, restored** (§1.5). On a reload within the rest it resumes with the right time left; past zero it restores as nothing. *No vibration, sound or notification* (owner; iOS Safari cannot vibrate and notifications need a permission flow); the only non-visual cue is one polite "Rest over" for screen readers.
- ✅ **D11 — The bar's log button is a persistent element fed by a tiny external store,** not a submit button inside the form, not a portal, not lifted state. *Rationale:* a portal or a per-exercise button would unmount on advance and drop focus (the next set must be loggable by keyboard or switch control without re-finding it); lifting into `ActiveSession` state re-renders the card list per ± tap. `useSyncExternalStore` re-renders one button. *Rejected:* `<button form="…">` associated across the DOM (works, but still remounts per exercise).
- ✅ **D12 — Teal allow-list additions (17.0 D4 rules).** `EntryRow.module.css` (the current-set panel: the "do this next" surface, a `signal-soft` ground and its label) and, in Phase C, `RestLine.module.css` (the line fill). Both are "next/log" uses, consistent with teal as the interactive color. The collapsed rows, steppers, menu and dialogs use no teal beyond the shared `Button` primary. The entry panel is tinted, not outlined (17.0 AC12 list). No brass, no warm-up token, no new token.
- ✅ **D13 — "End workout early" and Discard share one "Workout menu" disclosure** at the top, inline (the Options pattern), not a popover. *Rationale:* both are rare and away from the thumb on purpose; one button replaces today's standalone Discard; an inline reveal needs no positioning, focus trap or outside-click logic. End early reuses `confirmFinish`, so its waits and failures cannot diverge from Finish. When nothing planned is unlogged the item says "Finish workout" so free-form workouts have a visible path.
- ✅ **D14 — "Add exercise" moves into the list, and free-form workouts get a secondary "Finish workout" beside it** (owner: Add exercise at the end of the list). An empty workout makes "Add exercise" the bar's primary button (there is nothing to log).
- ✅ **D15 — RPE is hidden everywhere the lifter sees it** (owner, 2026-10-15): logging, the routine editor and item sheet, target lines, finished workouts and History. The data stays in the database, the API keeps accepting and returning it, there is no migration, the export is unaffected (it composes the read DTOs). Edits never clear a stored value (AC2, AC5). *Rationale:* a product decision (PRODUCT.md): RPE was optional friction on the logging path; the schema cost of keeping it is zero and reversal is a UI change. *Rejected:* dropping the columns (a migration and an API break for no gain); hiding only in the entry row (target lines and finished views would still show RPE the lifter can no longer enter).
  *Implementation notes (2026-10-16, pre-PR reviews):* every entry-row draft starts with a blank RPE (a seeded or restored draft would otherwise send a value nobody can see); `diffForPatch` never sends `rpe` and `rpe` maps to no input, so a server error on it is a form-level message; a stored `targetRpe` the schema would refuse is sent as `null` instead of blocking the save, and validateDraft has no RPE message. *Known consequence:* a stored target RPE cannot be cleared from the UI (remove and re-add the item).
- ✅ **D16 — The `EntryRow` name, file and `<form aria-label>` stay** (06.5 and 10.2 tests and docs refer to them). Only its internals and look change.
- ✅ **D17 — "Last time" is out of scope** (owner, 2026-10-15): it needs an API, kept under Future enhancements in the plan.
- ✅ **D18 — Phase B owner answers (2026-10-16), from the implementation plan's spec questions.** (a) Control outlines inside the tinted current-set panel measured 2.99:1 (light) / 2.97:1 (dark) on `--color-signal-soft`, under WCAG 1.4.11's 3:1; `--color-border` is darkened to `#878075` / `#837d72` (both dark blocks), and the border-on-signal-soft pair joins 17.0's contrast test. (b) Superset alternation (AC15) is in scope here; DESIGN.md §2's "guided interleaved superset logging (Tier C), deferred" line is amended. (c) A log on an exercise with no plan inside a superset run alternates to the next member, like a planned one.
