# Spec 05.0 — Workout Session Lifecycle (API)

**Status:** Draft v0.1 — first draft, no review passes yet.
**Last updated:** 2026-09-20
**Design refs:** DESIGN.md §4.0 (cross-cutting conventions — calendar fields,
numeric precision), §4.4 (`workout` / `workout_exercise` — the hot path),
§4.5 (PRs are written at finish — deferred to Spec 07 here, see §6), §4.9
(deletion matrix), §6 (idempotency via `client_generated_id`, `/v1` REST
conventions)

---

## 1. Purpose, scope & non-goals

Ship the **session lifecycle** of workout logging: the `workout` and
`workout_exercise` tables, the endpoints that start, resume, edit, finish and
delete a workout session and that add, reorder and remove exercises within it,
and the `@sin/core` types those endpoints need. This is the first of three
specs that split the roadmap's Spec 05 (05.0 session lifecycle, 05.1 set
logging, 05.2 rate limiting and write quotas), because the original scope
bundled several work sessions' worth of change. It also fixes the two rules
every later logging feature leans on: workout creation is idempotent under
retry (DESIGN §6), and `local_date` is derived once, at write time, from the
client's own offset (DESIGN §4.0).

### In scope

- The `workout` and `workout_exercise` tables, in migration
  `0005_create_workout_session`.
- The session lifecycle endpoints: create, read the active session, read by
  id, update (including finish), delete; add, update (reorder) and delete a
  workout exercise.
- Workout-creation idempotency via `client_generated_id`, and the
  one-in-progress-session-per-user rule.
- The calendar-field rules (`local_date` / `tz_offset_minutes`): how they are
  supplied, derived and stored.
- The `@sin/core` additions those need: `WorkoutId` / `WorkoutExerciseId`,
  `WORKOUT_SOURCE_VALUES`, the workout DTOs, and a new `time.ts` module of pure
  calendar helpers.

### Non-goals

- **`set_entry` and everything measure-shaped** — the table, per-modality
  validation, and the finish integrity rule ("a working set needs at least one
  measure") — are **Spec 05.1**. 05.0's finish transition only sets
  `ended_at`.
- **Rate limiting and per-user write quotas** are **Spec 05.2**, which also
  closes 03.2's open D20 (connection-pool blast radius) and D21 (unbounded
  storage growth via create/delete cycling). 05.0 ships no write throttle.
- **The paginated history list and all PR/progress work** are **Spec 07**.
  There is deliberately no `GET /v1/workouts` list here, and finishing a
  workout does not write PRs; 07 adds the PR recompute to the finish
  transition and backfills workouts finished before it ships.
- **`routine_id` and `superset_group`** semantics are **Spec 09**. Neither
  column is created here (see §4 and §12).
- **The logging UI** — active-session screen, exercise picker integration,
  resume flow — is **Spec 06**.

## 2. Acceptance criteria

Every behavioral criterion below gets ≥1 test naming its number
(`describe("AC7 — …")`) — mostly integration (Testcontainers) plus `@sin/core`
and route-level unit tests. AC18 is part test, part CI-pipeline check, and AC19
is verified by review of the doc diff. §10 maps each criterion to its method.

1. **Migration creates the session schema.**
   `0005_create_workout_session` applies cleanly on a fresh database and on top
   of the existing migration chain, and creates `workout` and
   `workout_exercise` with exactly the columns, types and nullability of §4;
   the three FKs (`workout.user_id → user(id)`,
   `workout_exercise.workout_id → workout(id)`,
   `workout_exercise.exercise_id → exercise(id)`) all `ON DELETE CASCADE`; the
   two `CHECK`s; and the five named indexes — `workout_user_client_id_key`
   (unique), `workout_user_started_idx`, `workout_user_active_key` (unique,
   partial on `ended_at IS NULL`), `workout_exercise_position_key` (a unique
   **constraint**, `DEFERRABLE INITIALLY IMMEDIATE`) and
   `workout_exercise_exercise_idx`. `prisma validate` passes with the `Workout`
   / `WorkoutExercise` models and the `User.workouts` /
   `Exercise.workoutExercises` back-references, and no second migration is
   generated by the model additions.
2. **Both `CHECK` literal lists are drift-guarded against `@sin/core`.**
   A raw insert of a value outside the list is rejected by the database on both
   `workout.source` and `workout_exercise.modality_snapshot`, and each member of
   `WORKOUT_SOURCE_VALUES` / `MODALITY_VALUES` is accepted. The drift guard is
   03.1 AC2's technique applied to **both** lists: an assertion that the
   migration `.sql` file **contains** the clause rendered from the frozen
   constant — string containment, not a parse of `pg_get_constraintdef()`, which
   Postgres normalizes to `= ANY (ARRAY[...])`.
3. **Workout creation is idempotent under retry.** A first
   `POST /v1/workouts` returns `201` with `Location: /v1/workouts/{id}`. A
   replay with the same `(user, clientGeneratedId)` returns `200` with the
   **stored** row and **no `Location` header**, even when the replayed body
   differs from the stored row (the body is ignored, never compared, never
   `409`). Exactly one row exists afterwards, and this holds when the replays
   are concurrent rather than sequential.
4. **At most one in-progress session per user.** A second
   `POST /v1/workouts` under a *different* `clientGeneratedId` while the caller
   has a row with `ended_at IS NULL` is `409 workout-in-progress-exists`, and
   the problem+json body carries **no workout id** (no extension member) — the
   client recovers via `GET /v1/workouts/active`, which returns that one row, or
   `404` when there is none. A concurrent burst of creates for a user with no
   active session admits exactly one row.
5. **The replay outcome wins over the in-progress conflict, and `409` has one
   source.** A retried create of the *same* `clientGeneratedId` returns `200`
   and never `409`, including when the first attempt is what created the
   in-progress workout. `409 workout-in-progress-exists` is raised **only** by
   mapping SQLSTATE `23505` on constraint `workout_user_active_key` after the
   failed statement's rollback; a `23505` on any other constraint surfaces as
   `500`, not as the `409`. A re-read that finds nothing (the stored row was
   concurrently deleted) retries the insert once and never answers `409`.
6. **Calendar fields are derived once, at write time, and never re-derived.**
   `local_date` is `localDateFor(startedAt, tzOffsetMinutes)` and both
   `local_date` and `tz_offset_minutes` are stored on the row. When
   `tzOffsetMinutes` is absent the server uses
   `offsetMinutesForZone(startedAt, user.timezone)` — the offset **at that
   instant**, so a workout started on a DST-transition day gets the offset in
   force then. `local_date` is unchanged by finishing, by editing `title` /
   `notes`, and by every read path. Neither `localDate` nor `tzOffsetMinutes`
   is client-settable on `POST` (unknown key ⇒ `422`).
7. **`startedAt` is bounded against clock skew.** A `startedAt` more than §6.4's
   +5 minutes in the future, or more than §6.4's 7 days in the past, measured
   against the server clock at write time, is `422 validation-error`; values
   inside both bounds are accepted. `endedAt` on the finish transition is bound
   by the same future window.
8. **Finish is a `PATCH`, and a finished workout is immutable.** `PATCH
   /v1/workouts/{id}` with `endedAt` set on an in-progress workout returns `200`
   with `endedAt` stored. `endedAt < startedAt` is `422`; `endedAt ===
   startedAt` is accepted. Against a **finished** workout every `PATCH` is
   `409 workout-finished` — including `PATCH {}` and `PATCH { endedAt: null }`
   — because the target's state is checked before the body is inspected.
   Against an **in-progress** workout, `PATCH {}` and `PATCH { endedAt: null }`
   are `200` no-ops returning the row unchanged. There is no
   `POST /v1/workouts/{id}/finish`.
9. **`workout-finished` is the single immutability signal, and `DELETE` is its
   one exemption.** `POST /v1/workouts/{id}/exercises`,
   `PATCH /v1/workout-exercises/{id}` and `DELETE /v1/workout-exercises/{id}`
   each return `409 workout-finished` when the (parent) workout has `ended_at`
   set. `DELETE /v1/workouts/{id}` succeeds with `204` on an in-progress **and**
   on a finished workout, hard-deletes, cascades to `workout_exercise`, and a
   repeat `DELETE` of the same id is `404`, not a second `204`.
10. **Add-exercise resolves through `findVisibleById` and snapshots in the same
    transaction.** `POST /v1/workouts/{id}/exercises` returns `201` with
    `Location: /v1/workout-exercises/{id}` and a row whose
    `exercise_name_snapshot` / `modality_snapshot` equal the resolved
    exercise's `name` / `modality`; a later rename or soft-delete of that
    exercise leaves the snapshot unchanged. An `exerciseId` that
    `exerciseRepository.findVisibleById(actingUserId, …)` misses (absent, or
    another user's custom row) is `404 not-found`; an `isActive === false` row
    is `409 exercise-retired`. Adding the same `exerciseId` twice to one workout
    is allowed and creates a second row.
11. **Positions stay the dense sequence `0 … n-1`, and the range check is
    enforced below the schema.** Add without `position` appends at `n`; add with
    `0 ≤ position ≤ n` inserts and shifts the rows at and above it up by one;
    reorder with `0 ≤ position ≤ n-1` moves the row and renumbers the span
    between its old and new position; delete closes the gap. After each
    mutation the workout's positions are `0 … n-1` with no gap or duplicate, and
    `WorkoutDetail.exercises` is ordered by `position` ascending. A `position`
    above the allowed bound — including one above the `smallint` ceiling of
    32767, which must never reach the column as a Postgres `22003` `500` — is
    `422 validation-error`. A reorder to the row's current position is a `200`
    no-op.
12. **Concurrent position mutations neither collide at `COMMIT` nor serialize
    on the create path.** A reorder that passes through an intermediate state
    where two rows share a position commits successfully (it would fail without
    `SET CONSTRAINTS workout_exercise_position_key DEFERRED`), and concurrent
    adds to the same workout all succeed with a dense final sequence rather than
    failing the deferred check at `COMMIT` — the per-workout
    `pg_advisory_xact_lock(hashtext(workoutId))` is taken as its **own**
    statement at the top of the transaction, before the `n` read. `POST
    /v1/workouts` takes no advisory lock at all.
13. **404, never 403, and a malformed id is also 404.** On every id-taking
    route — `GET`, `PATCH`, `DELETE /v1/workouts/{id}`,
    `POST /v1/workouts/{id}/exercises`, `PATCH` and
    `DELETE /v1/workout-exercises/{id}` — another user's row answers `404
    not-found`, indistinguishable from an absent id, and never `403`. A
    malformed `{id}` is `404` on all six, not `422`, because the branded guard
    runs in the repository before any query. A `workout_exercise` row's
    ownership is resolved through its parent workout. The add-exercise body's
    `exerciseId` follows the same rule: another user's custom exercise is `404`.
14. **Request bodies are closed and free text is bounded at ingress.** Every
    write body is `z.strictObject`, so `userId`, `id`, `localDate`, `source`,
    `tzOffsetMinutes` on `PATCH`, or either snapshot field is `422
    validation-error`, never silently dropped. `title` over
    `WORKOUT_TITLE_MAX` (120) or `notes` over `WORKOUT_NOTES_MAX` (4000) is
    `422` naming the field and **never `413 payload-too-large`**; an empty
    string is `422` while `null` and an omitted key are accepted; `title`
    rejects every C0 control character and DEL, `notes` rejects the same set
    except TAB, LF and CR; accepted text round-trips byte-for-byte, with no
    escaping or normalisation (`<script>` is a legal title).
15. **An account purge reaches these rows down both FK paths.** Deleting a
    `user` row removes that user's `workout` rows, the `workout_exercise` rows
    under them (`user → workout → workout_exercise`), **and** the
    `workout_exercise` rows that reference the user's custom `exercise` rows
    (`user → exercise → workout_exercise`) — in one `DELETE`, with no ordering
    step and no FK violation. No other user's `workout_exercise` row is touched.
16. **The four business log lines are emitted with ids only.**
    `workout_started` is emitted on the fresh `201` create and **not** on the
    `200` idempotent replay; `workout_finished` is emitted on the finish
    transition only, not on a `PATCH` that edits `title` / `notes` and not on a
    `PATCH {}` no-op; `workout_deleted` and `workout_exercise_added` are emitted
    on their successes. No line, and no `422` problem+json `detail`, contains a
    `title` or `notes` value.
17. **The `@sin/core` additions land cleanly.** `WorkoutId` and
    `WorkoutExerciseId` ship the full `brandId()` quartet and a raw `string` is
    not assignable to either; `WORKOUT_SOURCE_VALUES` is frozen;
    `dto/workout.ts`'s seven schemas parse a valid payload and reject a missing
    required field and an unknown key; `time.ts`'s `localDateFor` and
    `offsetMinutesForZone` are pure and correct across a DST transition and a
    negative offset. Both new modules are re-exported from
    `packages/core/src/index.ts` **and** listed in the `EXPECTED` array of
    `packages/core/scripts/check-exports.mjs`; `pnpm run core:purity` stays
    green and `dependencies` remains exactly `["zod"]`.
18. **All eight routes are authenticated and in the published contract.** Each
    returns `401` with no token and with an invalid token, each appears in
    `GET /openapi.json` with camelCase schemas derived from the Zod DTOs
    (including a declared response schema for both `204` deletes), and the CI
    OpenAPI drift check stays green.
19. **Docs stay consistent.** The DESIGN.md edits this spec's §11 lists — the
    §4.4 `workout` / `workout_exercise` column list reconciled with what
    actually ships (`routine_id` and `superset_group` deferred to Spec 09), the
    §4.5 finish/immutability wording reconciled with the PR-recompute split, and
    the §4.9 deletion matrix confirmed against §6.5's `DELETE` semantics — are
    applied, and `docs/specs/README.md` carries the 05.0 / 05.1 / 05.2 roadmap
    rows with dependencies repointed.

## 4. Data model

Owned by this spec: **`workout`** and **`workout_exercise`**. Migration
**`0005_create_workout_session`** — additive, expand-only. The migration SQL is
**hand-authored**: the partial unique index `WHERE ended_at IS NULL`, the two
`CHECK (… IN (…))` literal lists, and the `DEFERRABLE` unique constraint are not
expressible in the Prisma schema DSL, so the `.sql` file is the source of truth
and the Prisma models exist for the client only (the same raw-SQL carve-out
Spec 03.1 §4 used for `0002`). The file follows the `0002` conventions: a
`NNNN_snake_case` directory, a header comment naming this section, explicit
`TIMESTAMPTZ(6)` column types, and a "Down = test teardown / local reset only,
never production" comment. Production undo is `git revert` plus a forward
migration, never a down script (Spec 01 §11).

```
Table: workout
  id                  uuid        PK, app-generated UUIDv7
  user_id             uuid        NOT NULL FK → user(id) ON DELETE CASCADE
  title               text        NULL
  notes               text        NULL
  started_at          timestamptz NOT NULL
  ended_at            timestamptz NULL            -- NULL = in progress
  local_date          date        NOT NULL
  tz_offset_minutes   smallint    NOT NULL
  client_generated_id uuid        NOT NULL        -- idempotency key
  source              text        NOT NULL DEFAULT 'manual'
                                  CHECK (source IN (<@sin/core WORKOUT_SOURCE_VALUES>))
  created_at/updated_at timestamptz NOT NULL      -- app-stamped, no trigger

Indexes:
  workout_user_client_id_key  UNIQUE (user_id, client_generated_id)
  workout_user_started_idx    (user_id, started_at DESC)   -- the 07 history list
  workout_user_active_key     UNIQUE (user_id) WHERE ended_at IS NULL

Table: workout_exercise
  id                     uuid        PK, UUIDv7
  workout_id             uuid        NOT NULL FK → workout(id) ON DELETE CASCADE
  position               smallint    NOT NULL
  exercise_id            uuid        NOT NULL FK → exercise(id) ON DELETE CASCADE
  exercise_name_snapshot text        NOT NULL
  modality_snapshot      text        NOT NULL
                                     CHECK (modality_snapshot IN (<MODALITY_VALUES>))
  notes                  text        NULL
  created_at/updated_at  timestamptz NOT NULL

Indexes:
  workout_exercise_position_key UNIQUE (workout_id, position) DEFERRABLE INITIALLY IMMEDIATE
  workout_exercise_exercise_idx (exercise_id)
```

- **`exercise_id` is `ON DELETE CASCADE`, which discharges the purge-ordering
  obligation.** Spec 03.1 §3 and Spec 03.2 §3 both hand Spec 05 the question of
  how an account purge orders `workout_exercise` against the user's custom
  `exercise` rows. `exercise.owner_user_id` is itself `ON DELETE CASCADE`
  (03.1 §4), so purging a user deletes their custom exercises; a `RESTRICT` or
  `NO ACTION` on `workout_exercise.exercise_id` would make that delete depend on
  the order Postgres happens to process the two cascades, and a purge that
  reaches an exercise row while `workout_exercise` rows still reference it is
  refused. With `CASCADE` on both paths (`user → workout → workout_exercise`
  and `user → exercise → workout_exercise`) no ordering is needed. The cascade
  can only ever fire for the purged user's own rows: global rows are never
  hard-deleted (DESIGN §4.2, append-only, retire by `is_active = false`), so no
  other user's history is reachable through it. `workout_exercise_exercise_idx`
  exists for exactly this delete path — without it, each exercise delete would
  sequentially scan `workout_exercise` to find referencing rows — and doubles as
  the lookup for "which workouts used this exercise" (Spec 07).
- **The snapshots are `NOT NULL` and written at add time.**
  `exercise_name_snapshot` and `modality_snapshot` are copied from
  `exerciseRepository.findVisibleById` inside the add-exercise write (§6), so a
  later rename, soft-delete or fork of the exercise never rewrites a logged
  session (DESIGN §4.4). They are `NOT NULL` because a snapshot that can be
  absent is a second code path every history reader must handle; the add path
  is the only writer and always has the row in hand. The `modality_snapshot`
  `CHECK` renders `MODALITY_VALUES` into the migration exactly as 03.1 AC2 does
  for `exercise.modality`, and inherits its drift guard: a unit test asserts
  the migration `.sql` **contains** the rendered clause (string containment, not
  a parse of `pg_get_constraintdef()`, which Postgres normalizes to
  `= ANY (ARRAY[...])`). The same applies to `source` against
  `WORKOUT_SOURCE_VALUES`.
- **`superset_group` and `routine_id` are deliberately omitted.** DESIGN §4.4
  lists both on `workout` / `workout_exercise`, but nothing in v1 M1 writes or
  reads them. Spec 09 adds `superset_group` additively, alongside
  `routine_item.superset_group`. `routine_id` waits because the `routine` table
  does not exist until 09, and a nullable `uuid` with no FK now and an FK later
  is worse than one additive `ALTER TABLE … ADD COLUMN … REFERENCES` in 09.
  Both omissions are recorded as decisions in §12 so a reader does not conclude
  DESIGN was missed.
- **No `change_xid`-style trigger.** `created_at` / `updated_at` stay
  app-stamped, as for `user` (Spec 01) and `exercise` (03.1 §4). The Spec 03.3
  trigger is a narrow exception whose only purpose is sync-correctness for a
  catalog that clients delta-pull; workouts have no delta-sync contract in v1,
  so a trigger would add write-path cost and a second stamping mechanism for no
  reader.
- **The three `workout` indexes each serve one rule.**
  `workout_user_client_id_key` is the idempotency key (DESIGN §6): a retried
  `POST /v1/workouts` collides on it and the handler replays the stored row
  (§6). It is scoped by `user_id` so one user's key can never leak or collide
  with another's. `workout_user_active_key` is a **partial** unique index on
  `user_id WHERE ended_at IS NULL`, which makes "at most one in-progress
  session per user" a database invariant rather than a check-then-insert race;
  it also serves the `GET /v1/workouts/active` lookup.
  `workout_user_started_idx` `(user_id, started_at DESC)` is the history-list
  access path that Spec 07 will read; it is created here, with the table, so
  07 needs no index build on a populated table.
- **`workout_exercise_position_key` is `DEFERRABLE INITIALLY IMMEDIATE`.** A
  reorder moves several rows' `position` values inside one transaction, and
  intermediate states (two rows briefly sharing a position) are unavoidable when
  swapping. A plain unique constraint checks each row as it is written and
  would reject the swap; a deferrable one lets the reorder transaction run
  `SET CONSTRAINTS workout_exercise_position_key DEFERRED` and have the check
  happen at commit. `INITIALLY IMMEDIATE` keeps ordinary inserts and deletes
  strict, so only the reorder path opts in. Note this must be a
  **constraint**, not a bare `CREATE UNIQUE INDEX`, because Postgres cannot
  defer a unique index.
- **The `User` and `Exercise` models gain back-references.** Prisma requires
  both sides of a relation, so `workout.user_id → user(id)` obliges a
  `workouts Workout[]` field on `User` (owned by Spec 01) and
  `workout_exercise.exercise_id → exercise(id)` obliges a
  `workoutExercises WorkoutExercise[]` field on `Exercise` (owned by 03.1), or
  `prisma validate` fails in CI — the same trap 03.1 §4 recorded for
  `User.customExercises`. The `Workout` and `WorkoutExercise` models also need
  `@@map("workout")` / `@@map("workout_exercise")` and per-field `@map`
  snake_case mappings so the client's camelCase fields line up with the
  hand-authored columns. All of this is a **Prisma-client-only change** — no
  column, no extra migration — and does not otherwise disturb Spec 01's or
  03.1's ownership of `user` and `exercise`.

## 5. API surface

All eight routes are under `/v1`, require authentication, and go through the
Spec 03.0 route-schema convention. Every route also has the two ambient
failures, `401 unauthenticated` / `401 invalid-token` (Spec 01 §5), listed once
per route below so the block is self-contained; `413 payload-too-large` and
`415 unsupported-media-type` come from the app-wide body parser and are not
repeated.

```
POST /v1/workouts                                 auth required
  201  Workout                                     Location: /v1/workouts/{id}
  200  Workout  — idempotent replay: (userId, clientGeneratedId) already
                  stored; the stored row is returned, the body is ignored (§6)
  409  workout-in-progress-exists    — caller already has an unfinished workout
                                       under a *different* clientGeneratedId
  422  validation-error              — malformed body, or startedAt outside
                                       the clock-skew window (§6)
  401  unauthenticated / invalid-token

GET /v1/workouts/active                           auth required
  200  WorkoutDetail                 — the caller's one in-progress workout
  404  not-found                     — the caller has no in-progress workout
  401  unauthenticated / invalid-token

GET /v1/workouts/{id}                             auth required
  200  WorkoutDetail                 — in progress or finished
  404  not-found                     — absent, or owned by a different user
  401  unauthenticated / invalid-token

PATCH /v1/workouts/{id}                           auth required
  200  Workout                       — { title?, notes?, endedAt? }; setting
                                       endedAt is the finish transition (§6)
  404  not-found                     — absent, or owned by a different user
  409  workout-finished              — the workout already has endedAt set;
                                       no field is editable, and endedAt
                                       cannot be cleared (§6)
  422  validation-error              — malformed body, or endedAt < startedAt
  401  unauthenticated / invalid-token

DELETE /v1/workouts/{id}                          auth required
  204  (no body) — hard delete; cascades to workout_exercise; allowed on an
                   in-progress or a finished workout
  404  not-found                     — absent, or owned by a different user
  401  unauthenticated / invalid-token

POST /v1/workouts/{id}/exercises                  auth required
  201  WorkoutExercise                             Location:
                                       /v1/workout-exercises/{id}
  404  not-found                     — the workout is absent or owned by a
                                       different user; or exerciseId is not
                                       visible to the caller (absent, or another
                                       user's custom exercise)
  409  workout-finished              — the workout already has endedAt set
  409  exercise-retired              — the exercise has isActive=false
  422  validation-error
  401  unauthenticated / invalid-token

PATCH /v1/workout-exercises/{id}                  auth required
  200  WorkoutExercise               — { position?, notes? }
  404  not-found                     — absent, or its workout is owned by a
                                       different user
  409  workout-finished              — the parent workout has endedAt set
  422  validation-error
  401  unauthenticated / invalid-token

DELETE /v1/workout-exercises/{id}                 auth required
  204  (no body)
  404  not-found                     — absent, or its workout is owned by a
                                       different user
  409  workout-finished              — the parent workout has endedAt set
  401  unauthenticated / invalid-token
```

**Path ids.** Every `{id}` path parameter is declared as
`z.object({ id: z.string() })`, exactly as `routes/exercises.ts` declares
`exerciseIdParams`, and the repository turns a malformed id into
`NotFoundError` with the branded `isWorkoutId` / `isWorkoutExerciseId` guard
before any query (as `exercise.prisma.ts` does with `isExerciseId`). A
malformed `{id}` is therefore `404 not-found`, not `422`, on every route above;
this follows 03.1 / 03.2, whose blocks list no `422` for a bad id. A malformed
`exerciseId` in the `POST .../exercises` **body** is different: it is body
validation, so `422 validation-error`.

Three things about this surface are pinned down here so a later spec does not
have to guess them.

- **There is no paginated `GET /v1/workouts`.** The history list is Spec 07's;
  05.0 ships only the reads the logging screen needs. `GET /v1/workouts/active`
  exists because Spec 06 must be able to **resume** an in-progress session: the
  cold-load redirect that Q12 and Spec 04.0 §12 make routine can drop a user
  onto a fresh page with no client state, and the client then needs "the
  workout I was in the middle of" without knowing its id. The partial unique
  index `workout_user_active_key` (§4) makes that well defined: at most one row
  can match, so the endpoint returns `200` with that row or `404`, never a
  list and never an ambiguity. The `409 workout-in-progress-exists` body
  carries no workout id (standard problem+json, no extension member), so the
  client's recovery from that `409` is the same call — `GET /v1/workouts/active`
  — and then "resume or discard". This spares Spec 01's problem+json contract
  an extension-member mechanism that one error would be the only user of.
- **404, never 403, for another user's row.** A workout that exists but belongs
  to someone else is indistinguishable, on the wire, from one that does not
  exist — the 03.1 / 03.2 convention, so a caller cannot probe for other users'
  ids. The repository enforces it: `workout` rows are `{ userId }`-shaped, so
  the ownership check is `assertOwned` (`apps/api/src/repositories/user.ts`),
  called with the acting user's id. A `workout_exercise` row carries no
  `user_id`; its ownership is its parent workout's, so the repository resolves
  it through the join and applies the same 404 (§6, Wiring points).
- **Schemas.** Response schemas are `z.object` (not `.strict()`), so the
  serializer treats each as a field **allowlist** (Spec 03.0 §6.5): a column
  added later is not exposed until a DTO opts it in. Request bodies are
  `z.strictObject`, so an unknown key is `422` rather than silently dropped —
  which is also what stops a client from smuggling `userId`, `localDate` or
  `source` into a write. Only the **success** response is declared per route
  (Spec 03.1 §5): `201` and `200` for `POST /v1/workouts` (both `Workout`),
  `200` for the rest, and `204` for the two deletes. Error bodies come from the
  shared problem+json contract, registered on both the root and `/v1` scopes.

### `@sin/core` DTOs

Wire fields are camelCase, the camelCase of the §4 column names, with the API
mapping to and from the snake_case columns. Neither row DTO carries a
**`userId`**: every row a caller can read is the caller's own, so the field
would carry no information (unlike `Exercise.ownerUserId`, where `null` means
"global"), and `workout_exercise` has no such column. Timestamps are
`z.iso.datetime({ offset: true })`; `localDate` is `z.iso.date()`; ids are the
branded schemas, never bare `z.string()`.

**Naming convention for 05.0's additions: `XxxSchema` for the Zod value, bare
`Xxx` for the `z.infer` type, and no `Body` / `Response` suffix.** The core
package carries two styles today: 03.1 and 03.2 use `ExerciseSchema` /
`Exercise` and `CreateExerciseSchema` / `CreateExercise`; Spec 02 uses
`MeSchema` / `Me` but names its update type `UpdateMeInput`; 03.3 introduced
suffix-less values (`ExercisesResponse`, `MuscleGroupsResponse`) with
`Body`-suffixed types (`ExercisesResponseBody`). The evidence for `Schema` is a
majority, not unanimity. It wins for three reasons. It is the existing majority
and what the branded ids already use (`UserIdSchema`, `ExerciseIdSchema`). It
makes the runtime value and the compile-time type distinct at a glance:
TypeScript would allow a const and a type to share one name (03.3's values could
have done so), but `WorkoutSchema.parse(x)` versus `Workout` is clearer than a
same-named pair whose meaning depends on the position it is used in. And it
needs no per-type suffix decision: the type is the bare noun. 03.3's shipped
exports are **not** renamed here, since that is churn on a merged wire contract
for no behavioral gain; if it is ever wanted it is its own change. The choice
is recorded as a decision in §12.

Points on the listing that are choices, not accidents:

- **`clientGeneratedId` is `z.guid()`, not a branded id.** It is a client-minted
  idempotency key, not the identity of a resource the server hands out, so
  branding it would add a type nobody passes between functions. It uses
  `z.guid()` for the same reason `brandId()` does (`ids.ts`): the lenient
  8-4-4-4-12 shape, so a client's v4 or v7 both pass and Postgres's `uuid`
  column accepts either.
- **`startedAt` and `endedAt` keep the offset the client sent**
  (`offset: true`). The instant is what is stored; `local_date` is derived
  from `tzOffsetMinutes`, not from the offset embedded in the string (§6), so
  the two cannot disagree in a way that matters.
- **The clock-skew window on `startedAt`, the `endedAt >= startedAt` rule, and
  every rule that needs the stored row** cannot be Zod refinements: a schema
  sees only the body, not the server clock or the database. They are handler
  rules that raise `ValidationError` (`422`); §6 states them.
- **`UpdateWorkoutSchema` and `UpdateWorkoutExerciseSchema` are not
  `.refine`d to "at least one field".** `PATCH {}` is a valid no-op that returns
  the row unchanged, which is also how a client fetches a fresh `updatedAt`.
- **`position` is a zero-based integer.** Range checks against the actual
  number of exercises, and the renumbering, are §6's; the schema only rejects
  negatives and non-integers.

### New `AppError` subclasses

`apps/api/src/errors/app-error.ts` gains two classes, in the existing style —
`status` / `slug` / `title` / `publicDetail` as `readonly` fields, and a
constructor whose defaulted argument is the **internal** reason (server logs
only, never the response body):

```ts
export class WorkoutFinishedError extends AppError {
  readonly status = 409;
  readonly slug = "workout-finished";
  readonly title = "Workout finished";
  readonly publicDetail =
    "This workout has already been finished and can no longer be modified.";

  constructor(internal = "target workout has ended_at set") {
    super(internal);
  }
}

export class WorkoutInProgressExistsError extends AppError {
  readonly status = 409;
  readonly slug = "workout-in-progress-exists";
  readonly title = "Workout already in progress";
  readonly publicDetail =
    "You already have a workout in progress. Resume or discard it first.";

  constructor(internal = "workout_user_active_key: caller already has ended_at IS NULL") {
    super(internal);
  }
}
```

`NotFoundError` and `ValidationError` are **reused**, not subclassed. So is
`ExerciseRetiredError` (`409 exercise-retired`, from 03.2) for adding an
`isActive = false` exercise; its `publicDetail` reads "can no longer be
modified", which is loose for an add but accurate enough that a third exercise
error is not worth it. The house style is **one class per business rule**: the
slug is the contract a client switches on, so `workout-finished` and
`workout-in-progress-exists` are distinct classes even though both are `409`.
There is no generic `ConflictError` carrying a slug string.

`workout-finished` is deliberately the single "the parent is immutable" signal:
it is returned by `PATCH /v1/workouts/{id}` and by all three
exercise-within-workout writes against a finished workout, so a client has one
rule to handle. `DELETE /v1/workouts/{id}` is the exception and is always
allowed (DESIGN §4.5, §4.9).

### `time.ts` — the one place `local_date` is derived

`packages/core/src/time.ts` (new) holds two pure functions.
`localDateFor(instantIso, offsetMinutes)` shifts the instant by the offset and
returns the calendar date as `"YYYY-MM-DD"` — plain arithmetic, no `Intl`.
`offsetMinutesForZone(instantIso, ianaTimeZone)` returns the zone's UTC offset
in minutes **at that instant** (so daylight saving is honored), using
`Intl.DateTimeFormat` with `timeZoneName: "longOffset"` and parsing the
resulting `GMT±HH:MM` (bare `GMT` means `0`). `Intl` is ECMA-402, a language
built-in rather than a Node API, and `dto/me.ts`'s `isValidTimeZone` already
depends on it, so it passes the `core:purity` check. These two are the only
code that derives `local_date`; the route handler calls them and nothing else
does (DESIGN §4.0, and §6 below). Both new modules must be re-exported from
`packages/core/src/index.ts` **and** added to the hand-maintained `EXPECTED`
array in `packages/core/scripts/check-exports.mjs`, or the export check fails.
There is no new runtime dependency: `test/deps.test.ts` pins `dependencies` to
exactly `["zod"]`, and nothing here needs a date library.

## 6. Behavior & logic

Eight rules carry the weight of this spec. Each is stated so it can be
asserted on its own; §2's acceptance criteria are drawn from them.

Two structural conventions apply throughout and are not repeated per rule.
First, **every repository method takes `actingUserId` as its first parameter**
and no handler ever queries by id alone (DESIGN R8). Second, **a malformed
`{id}` path parameter is `404 not-found`, never `422`**: the repository runs
the branded guard (`isWorkoutId` / `isWorkoutExerciseId`, spec'd in §5) before
it issues any query and throws `NotFoundError` on a miss, exactly as
`loadVisibleRow` in `apps/api/src/repositories/exercise.prisma.ts` does with
`isExerciseId`.

### 6.1 Idempotent create

`POST /v1/workouts` writes with `ON CONFLICT … DO NOTHING` on the idempotency
key and re-reads on a miss:

```sql
INSERT INTO workout (...)
VALUES (...)
ON CONFLICT (user_id, client_generated_id) DO NOTHING
RETURNING *;
```

A returned row is a fresh create ⇒ `201` plus a `Location` header. **Zero rows
⇒ re-read by `(user_id, client_generated_id)` and return the stored row with
`200`** and no `Location` header. Spec 03.1 §6.3 recorded the caveat that
`ON CONFLICT` needs a real unique index to infer against;
`workout_user_client_id_key` (§4) is that index, and it is scoped by `user_id`
so one user's key can never arbitrate against another's row.

**A replay whose body differs from the stored row returns the stored row
unchanged.** The body is ignored, not compared: DESIGN §6 says "replaying the
same id returns the existing resource, never a duplicate", and the only client
that sends a differing body is a buggy one or a retry after a local edit. A
`409` on a body mismatch would turn the one case idempotency exists to
survive — a retry over a flaky gym connection whose first attempt actually
succeeded — into a hard error the client cannot distinguish from a real
conflict. The `200`-versus-`201` split is the entire signal: a client that
cares whether it created the row reads the status code.

The `POST` body is `z.strictObject`, so `source`, `localDate`, `userId` and
`id` are rejected as unknown keys rather than silently dropped (§5).
`source` is server-set to `'manual'` in v1.

### 6.2 One in-progress session per user, and its interaction with replay

A user may have at most one workout with `ended_at IS NULL`. This is enforced
by the partial unique index `workout_user_active_key` (§4), not by a
check-then-insert in the handler, so two concurrent creates cannot both pass a
"do you already have one?" read and both insert. A second create while one is
in progress is `409 workout-in-progress-exists`
(`WorkoutInProgressExistsError`, §5).

**The `409` body carries no workout id.** The Spec 01 problem+json contract
has no extension-member mechanism and this error would be its only user, so
the client recovers the active workout by calling `GET /v1/workouts/active`
and then offers "resume or discard" (§5). That is one extra round trip on a
path the user is already stalled on, against permanently widening the
error contract.

**The replay outcome wins over the in-progress conflict, and Postgres gives
that for free.** `ON CONFLICT (user_id, client_generated_id) DO NOTHING`
swallows a violation of the **arbiter** index only. A violation of the
non-arbiter partial unique index `workout_user_active_key` is *not* swallowed:
it raises SQLSTATE `23505` and aborts the statement. So "zero rows" and "409"
are two disjoint outcomes of the same `INSERT`, not two branches of one
re-read:

1. Run the `ON CONFLICT (user_id, client_generated_id) DO NOTHING` insert.
2. **A row returned** ⇒ fresh create ⇒ `201` plus `Location`.
3. **Zero rows** ⇒ a row with this `(user_id, client_generated_id)` already
   existed ⇒ re-read by that key and return it with `200`. A re-read that
   finds nothing means the stored row was concurrently deleted between the
   insert and the re-read; **retry the insert once**, and never `409` on that
   path.
4. **SQLSTATE `23505`** ⇒ the only route to `409
   workout-in-progress-exists`, and only when the reported constraint / index
   name is `workout_user_active_key`. The statement has aborted the
   transaction, so the mapping happens after the rollback, outside the failed
   statement — not as a branch inside it. A `23505` on any other constraint is
   a bug, not a business rule, and must surface as `500` rather than be folded
   into the `409`.

**A retried create of the *same* `clientGeneratedId` therefore returns `200`,
never `409`**, even when the first attempt is what created the in-progress
workout the partial index would object to. The reason is the order Postgres
itself uses: speculative insertion checks the arbiter index first, and on a
conflict there the `DO NOTHING` action abandons the tuple before any other
index is touched. The partial index never gets the chance to raise. This is a
property of the statement, not of handler ordering, so it cannot be broken by
rearranging code — but it *would* break if the arbiter were ever changed or
the `ON CONFLICT` clause dropped, which is why the clause and the index are
described together here and in §4.

### 6.3 Calendar fields

The client sends `startedAt` (its own device clock, with offset) and
`tzOffsetMinutes` (its current UTC offset). The server derives `local_date`
once, at write time, by calling `localDateFor(startedAt, tzOffsetMinutes)`
(`packages/core/src/time.ts`, §5) and stores both `local_date` and
`tz_offset_minutes` on the row.

When `tzOffsetMinutes` is absent, the server falls back to the user's stored
`user.timezone` via `offsetMinutesForZone(startedAt, user.timezone)` — the
offset **at that instant**, so a workout started the morning a DST transition
lands gets the offset in force then, not the one in force at read time
(DESIGN §6).

`local_date` is **never re-derived from UTC afterwards** (DESIGN §4.0). It is
not recomputed when `startedAt` changes, because `startedAt` is not editable
(§5: `UpdateWorkoutSchema` has no `startedAt`); it is not recomputed on
finish; and no read path derives it. This is the whole point of storing it: a
calendar query ("this week", a streak, the month view in Spec 07) reads the
column, and re-deriving would silently move a late-evening session to the next
day for anyone east of UTC.

`local_date` and `tz_offset_minutes` are **not client-settable** — neither
appears in `CreateWorkoutSchema` or `UpdateWorkoutSchema`, and both bodies are
`z.strictObject`, so an attempt to send them is `422`.

### 6.4 Clock-skew bound on `startedAt`

`startedAt` is rejected with `422 validation-error` when it is more than
**5 minutes in the future** or more than **7 days in the past**, measured
against the server clock at the moment of the write. `endedAt`, on the finish
transition, is bound by the same 5-minute future window.

These cannot be Zod refinements — a schema sees the body, not the server
clock — so they are handler rules raising `ValidationError`, with the two
bounds as code constants in `packages/core/src/dto/workout.ts` alongside
`WORKOUT_TITLE_MAX` (§8: no env config, the `MAX_CUSTOM_EXERCISES_PER_USER`
precedent).

The numbers: 5 minutes future covers ordinary phone clock drift without NTP,
and nothing legitimate needs more, because the only v1 writer is "start a
session now" (Spec 06). 7 days past is generous for the same reason — there is
no backfill UI in v1 — and is deliberately not tighter, so a user who opens
the app after a week offline with a mis-set clock is not blocked outright.
Both bounds are guards against a device clock poisoning Spec 07's
`(user_id, started_at DESC)` history ordering, not product rules. Widening
either later is a pure relaxation and backward-compatible; narrowing is not,
which is the argument for erring generous now.

### 6.5 Finish

**`PATCH /v1/workouts/{id}` with `endedAt` set to a timestamp is the finish
transition.** There is no `POST /v1/workouts/{id}/finish`: finishing is
setting one column, the same `PATCH` that edits `title` and `notes` can do it
atomically with a last note, and an extra verb-shaped endpoint would need its
own schema and its own route for no additional behavior.

Rules, each independently assertable:

- `endedAt` must be **≥ `startedAt`**, else `422 validation-error`. Equality
  is allowed (a zero-length session is a user cancelling out, not an error).
- `endedAt` must be within the 5-minute future window of §6.4, else `422`.
- **A finished workout is immutable.** Any `PATCH` against a row that already
  has `ended_at` set is `409 workout-finished` (`WorkoutFinishedError`) — and
  the check runs on the **target's state, before the patch body is
  inspected**. That means `PATCH {}` against a finished workout is `409`, not
  a `200` no-op, even though `PATCH {}` against an in-progress workout is a
  `200` no-op (§5). The alternative — `{}` uniquely succeeding — makes the
  client model two rules instead of one ("a finished workout rejects writes"
  plus "except the empty one") to buy a way of re-fetching a row that
  `GET /v1/workouts/{id}` already provides.
- **`endedAt: null` never produces a `422`.** The schema accepts `null` (§5)
  precisely so that un-finishing reaches the handler and gets the answer it is
  owed: on a **finished** workout it is `409 workout-finished` (there is no
  un-finish in v1 — DESIGN §4.5 makes finished workouts immutable so Spec
  07's PR cache needs no invalidation path); on an **in-progress** workout,
  whose `ended_at` is already `NULL`, it is a **no-op** returning `200` with
  the row unchanged.
- **`workout-finished` is the single "the parent is immutable" signal.** It
  also guards `POST /v1/workouts/{id}/exercises`, `PATCH
  /v1/workout-exercises/{id}` and `DELETE /v1/workout-exercises/{id}` when the
  workout (respectively the parent workout) has `ended_at` set. A client has
  one slug to handle across all four writes.
- **`DELETE /v1/workouts/{id}` is the one exemption** and is allowed on a
  finished workout (DESIGN §4.5, §4.9: whole-workout hard delete is the
  sanctioned escape hatch from immutability). It hard-deletes and cascades to
  `workout_exercise`; a second `DELETE` of the same id is `404`, not a silent
  `204`, since after the first delete the row is indistinguishable from one
  that never existed.

**Extension seam 1 — Spec 05.1.** 05.1 adds the precondition that every
`working` set in the workout has at least one measure populated to *this*
transition, rejecting the finish when it does not hold; DESIGN §4.4 states
that rule as "enforced at finish", and `set_entry` does not exist until 05.1,
so there is nothing for 05.0 to check.

**Extension seam 2 — Spec 07.** 07 adds the personal-record recompute inside
this same transaction, and the matching recompute on `DELETE
/v1/workouts/{id}` (deleting a finished workout can retract a PR). DESIGN §4.5
says "PRs are written transactionally when a workout is finished", so reading
DESIGN literally, 05.0's finish is incomplete. **That is a deliberate split,
not an oversight:** `personal_record` is Spec 07's table in the M2 milestone,
and 05.0 cannot write rows to a table that does not exist. 07 both adds the
recompute here and backfills workouts finished before it ships. What 05.0 owes
07 is that the finish be a single transaction with one entry point in
`workoutRepository`, so 07 adds a call inside it rather than restructuring it.

### 6.6 Add exercise

`POST /v1/workouts/{id}/exercises`, in one transaction:

1. Load the workout via the repository with `actingUserId`; absent or another
   user's ⇒ `404 not-found` (§5). `ended_at` set ⇒ `409 workout-finished`.
2. Resolve `exerciseId` through
   `exerciseRepository.findVisibleById(actingUserId, exerciseId)`
   (`apps/api/src/repositories/exercise.ts`) — the method Spec 03.1 §3
   published for exactly this. A miss (absent, or another user's custom
   exercise) throws `NotFoundError` ⇒ `404`. `isActive === false` ⇒ `409
   exercise-retired` (`ExerciseRetiredError`, reused from 03.2): a retired
   exercise stays readable in history but is not something new sessions may
   add.
3. Copy `name` → `exercise_name_snapshot` and `modality` →
   `modality_snapshot` from that same record, in the same transaction, so a
   rename or soft-delete between the read and the write cannot produce a row
   whose snapshot disagrees with the exercise it was taken from (§4,
   DESIGN §4.4).
4. Insert at the resolved position (§6.7) and return `201` with a `Location`
   of `/v1/workout-exercises/{id}`.

Adding the **same** `exerciseId` twice to one workout is allowed and creates a
second row. Repeating an exercise later in a session is normal training, and
the two rows are distinguished by `position` and will carry different sets in
05.1. There is no idempotency key on this endpoint; a client that double-taps
gets two rows and deletes one.

### 6.7 Positions: append, reorder, and the deferred constraint

**A workout's exercise positions are always the dense sequence `0 … n-1`**,
zero-based (§5), with no gaps and no duplicates. Every mutation restores that
invariant before it commits, which is what makes the range checks below
statable and what lets `WorkoutDetail` order by `position` ascending and get
a stable list.

- **Add with `position` absent** appends at `n` (the current count).
- **Add with `position` present** requires `0 ≤ position ≤ n`; rows at
  `position` and above shift up by one. Out of range ⇒ `422
  validation-error`.
- **Reorder** (`PATCH /v1/workout-exercises/{id}` with `position`) requires
  `0 ≤ position ≤ n-1`; the row moves and the span between its old and new
  position is renumbered by one in the opposite direction. `position` equal to
  the row's current value is a `200` no-op. Out of range ⇒ `422`.
- **Delete** closes the gap: rows above the deleted one shift down by one.

**The range check is a repository/service-layer rule, not a schema rule**, for
two reasons. The schema cannot know `n` — it sees the body, not the workout.
And it is also what keeps `position` inside `smallint`: §5's DTOs bound
`position` below (`.min(0)`) but not above, so without this check a client
could send `2147483647` and get a Postgres `22003` numeric-overflow as a
`500`. Because `n` for a real workout is a few dozen at most, the `≤ n` /
`≤ n-1` check rejects everything above the `smallint` ceiling of 32767 long
before the column sees it. An implementer must therefore treat this check as
load-bearing, not cosmetic.

All four mutations renumber inside **one transaction** with the unique
constraint deferred:

```sql
BEGIN;
SET CONSTRAINTS workout_exercise_position_key DEFERRED;
-- renumber the affected span; intermediate states may collide, the commit cannot
COMMIT;
```

Deferral is needed even for the shifts that look safe. A set-based
`UPDATE workout_exercise SET position = position + 1 WHERE workout_id = $1 AND
position >= $2` updates rows in whatever order the plan produces; under the
constraint's `INITIALLY IMMEDIATE` default each row is checked as it is
written, so moving row `3` to `4` while row `4` is still at `4` fails, even
though the final state is unique. Deferring moves the check to `COMMIT`, where
only the final state is examined.

The alternatives were rejected:

- **No unique constraint at all.** Nothing then stops two rows sharing a
  position; the bug is silent, shows up as a list that reorders itself between
  reads, and is unrecoverable from the data. A constraint that costs one
  `SET CONSTRAINTS` on the reorder path is cheap insurance.
- **Fractional positions** (insert between `2.0` and `3.0` at `2.5`, never
  renumber). This is the right answer for collaborative documents with
  thousands of items and no write coordination. Here it buys nothing: a
  workout has a few dozen exercises, one writer, and a renumber is a
  single-digit-row `UPDATE`. In exchange it brings unbounded precision drift —
  repeated midpoint inserts run out of `float8` mantissa — plus a `numeric`
  column and a compaction job nobody would remember to write.

**The deferrable constraint must never be used as an `ON CONFLICT`
arbiter.** Postgres refuses to infer a conflict target from a deferrable
unique constraint, so `ON CONFLICT (workout_id, position)` fails outright —
which is fine, because nothing here wants upsert-on-position semantics. The
only `ON CONFLICT` in this spec is §6.1's, and it arbitrates on the
non-deferrable `workout_user_client_id_key`.

### 6.8 Concurrency

Two tabs on the same in-progress workout are **last-write-wins per row**, and
`updatedAt` is returned on every response so a client can detect that it lost
a race. This is DESIGN §4.4's existing posture restated, not re-litigated: v1
has one client, and real conflict resolution is a cost with no v1 payer.

**The create path takes no lock.** Its two concurrency guarantees come from
the two unique indexes alone (§4), and adding an advisory lock on top would
buy nothing. `ON CONFLICT … DO NOTHING` **waits** on an in-flight conflicting
inserter and re-checks once that transaction completes, so "zero rows" already
implies the winner committed; the re-read is a fresh `READ COMMITTED`
statement whose snapshot is taken after that, so it sees the committed row.
And `workout_user_active_key` makes "at most one in-progress session" a
constraint the database enforces, not a read the handler has to protect. A
per-user lock would add a serialization point on the app's most-called write
and hold a pooled connection while blocking — exactly the
connection-pool blast radius 03.2's D20 left open, which Spec 05.2 owns. The
correctness argument for the create path is §6.2's, and it needs no lock to
hold.

**Position mutations do need a lock**
(`pg_advisory_xact_lock(hashtext(workoutId))`, transaction-scoped), because
add, reorder and delete each read `n` — the current exercise count — and
then write rows whose positions depend on it. Two concurrent adds could
otherwise both compute the same `n` and collide on
`workout_exercise_position_key` at `COMMIT`, where the deferred check runs
and it is too late to renumber. The
lock is taken as its **own statement** at the top of the transaction,
following `insertWithCap` in
`apps/api/src/repositories/exercise.prisma.ts` (Spec 03.2 §6, D23). It is the
only advisory lock in this spec.

**That lock must be a separate statement from the read it protects.** Under
`READ COMMITTED` a statement's MVCC snapshot is fixed at that statement's
start, before the executor runs, so blocking mid-statement on
`pg_advisory_xact_lock` does not refresh the snapshot the rest of that
statement sees. A single statement that folds the lock into a CTE alongside
the `max(position)` read would take its snapshot before the lock was even
requested and read a stale `n` anyway — the exact trap Spec 03.2 §6 documents
at length and D23 forbids reintroducing. Both statements stay inside one
`prisma.$transaction`, so the lock is held across the read and the write and
released atomically with the commit.

`hashtext` returns 32 bits, so two distinct workouts can collide on a lock
key. The consequence is that two unrelated callers occasionally serialize
against each other for the duration of one short transaction — a latency blip,
never a correctness problem — and the key is not attacker-chosen: a caller
cannot address a workout that is not theirs (§5's 404 rule).

### Wiring points

The concrete seams an implementer works against, so they are not rediscovered:

- **`apps/api/src/repositories/workout.ts`** (interface plus `WorkoutRecord`
  and `WorkoutExerciseRecord` types) and **`workout.prisma.ts`**
  (`createWorkoutRepository(prisma)` factory) — the same split as
  `exercise.ts` / `exercise.prisma.ts`. `actingUserId` is every method's first
  parameter. Ownership is checked with `assertOwned`
  (`apps/api/src/repositories/user.ts`), which takes a `{ userId }`-shaped row
  and throws `NotFoundError` — `workout` rows are that shape. A
  `workout_exercise` row has no `user_id`, so the repository loads it joined to
  its parent workout and applies `assertOwned` to the parent. Pure, DB-free
  helpers (position arithmetic, the skew bound) get their own file, as
  `exercise-writes.ts` did, so they are unit-testable without a database.
- **`apps/api/src/routes/workouts.ts`** exporting
  `registerWorkoutRoutes(app, deps)`, registered at **four** points:
  `V1RouteDeps` and `registerV1Routes` in `apps/api/src/routes/v1.ts`,
  `BuildAppDeps` in `apps/api/src/app.ts`, and the composition root in
  `apps/api/src/server.ts`. Missing the last one yields an app that passes
  every unit test and serves 404s in staging.
- **Every route needs a declared response schema.**
  `assertRouteHasResponseSchema` (`apps/api/src/app.ts`, wired into the
  `onRoute` hook) throws at assembly time for any route without one —
  **including the two `204` deletes**. Copy whatever the existing `DELETE` in
  `apps/api/src/routes/exercises.ts` declares rather than inventing a second
  convention.
- **`apps/api/src/errors/app-error.ts`** gains `WorkoutFinishedError` and
  `WorkoutInProgressExistsError` exactly as listed in §5. `NotFoundError`,
  `ValidationError` and `ExerciseRetiredError` are reused.
- **Prisma models `Workout` and `WorkoutExercise`** with `@@map` / `@map`
  snake_case mappings, plus the back-reference fields both relations oblige
  (`User.workouts`, `Exercise.workoutExercises`), or `prisma validate` fails
  in CI — the trap 03.1 §4 recorded for `User.customExercises` (§4).
- **Tests.** `apps/api/test/helpers/fakes.ts` gains `makeWorkoutRecord` and
  `FakeWorkoutRepository`; `buildTestApp` gains a `workoutRepository` option
  defaulting to the fake. Unit tests authenticate with a plain
  `Bearer test-token` against `fakeVerifier` — **there is no JWT minting in
  unit tests**; the dev-idp on `:9999` is for manual and integration use.
- **Free-text bounds stay well inside `BODY_LIMIT_BYTES`**
  (`apps/api/src/app.ts`, 64 KiB). `WORKOUT_TITLE_MAX` (120) plus
  `WORKOUT_NOTES_MAX` (4000) is at most ~16 KB even at 4 bytes per character,
  so an over-long field is always `422 validation-error` from the schema and
  never `413 payload-too-large` from the body parser — which matters because
  `413` carries no field path and a user would have no idea which field to
  shorten.

## 7. Security & privacy

- **First table whose rows are entirely user-authored free text.**
  `workout.title`, `workout.notes` and `workout_exercise.notes` are arbitrary
  text from the caller, with no curated row behind any of them. Spec 03.2
  raised the same stakes for `exercise.name`; here nothing in the row is
  trusted. The storage contract is the 03.1 §7 `CatalogName` argument restated
  for free text: **bound length and control characters at ingress, store
  verbatim, output-encode at render time** (Spec 06). All three fields go
  through a shared `@sin/core` refine (§5) rather than per-route checks, so
  the create, update and add-exercise paths cannot drift apart.
- **Why those bounds.** `title` is `1..120` characters, the same ceiling as
  `CatalogName`: it is a single line shown in a list row, and 120 is longer
  than any real session name. `notes` is `1..4000`: several paragraphs of
  training prose, an order of magnitude more than anyone types on a phone in
  a gym, and small enough that a hostile client cannot use a notes field as
  free storage. The minimum of 1 means an empty string is `422`; a client that
  wants "no title" sends `null` or omits the key, so the column has one absent
  representation (`NULL`), not two. Zod counts length in UTF-16 code units, so
  an emoji costs two; that is stricter than the `text` column needs and is the
  safe direction for a bound.
- **Why reject control characters, and which.** `title` rejects every C0
  control character and DEL (`noControlChars`, reused from `dto/exercise.ts`).
  `notes` uses a second predicate that permits TAB, LF and CR, because notes
  are multi-line, and rejects the rest (§5). Control characters have no
  legitimate use in either field and do real damage downstream: NUL is
  refused by Postgres `text` outright (a `500` if it got that far), and the
  rest corrupt terminal log viewers, CSV export (Spec 11) and any
  line-oriented tool. Rejecting at ingress with `422` is cheaper and safer
  than sanitising on every read. Note this is a **format** check, not an
  HTML filter: `<script>` is a legal title.
- **Stored verbatim; encoding is the renderer's job.** The API does not
  HTML-escape, strip or normalise either field, so a stored value round-trips
  byte-for-byte. Escaping at write time would be wrong for every non-HTML
  consumer (the JSON API, native clients, export) and would double-encode in
  Spec 06's React render. React's default text rendering already encodes, and
  Spec 06 owns the rule that these fields are only ever rendered as text,
  never as HTML.
- **The bounds sit well inside `BODY_LIMIT_BYTES`.** The app-wide limit is 64
  KiB (`apps/api/src/app.ts`). A request that combines the largest title and
  notes is ~16 KB at 4 bytes per UTF-8 character; the adversarial encoding is
  worse, because a client may send every character as a JSON `\uXXXX` escape
  (6 bytes per code unit), so 4000 notes characters inflate to roughly 24 KB
  on the wire. That is still under half the limit. An over-long field is
  therefore always `422 validation-error` naming the field, never `413
  payload-too-large`, which carries no field path (§6, Wiring points). A body
  that is genuinely over 64 KiB is `413`, before the schema runs, and needs no
  handling here.
- **Every query goes through the repository, `actingUserId` first.** DESIGN R8
  is the seam the social phase's authorization layer will attach to, so it is
  enforced structurally rather than by reviewer vigilance: every method on
  `workoutRepository` takes `actingUserId` as its first parameter, and no
  handler queries `workout` or `workout_exercise` by id alone (§6). Ownership
  of a `workout` row is `assertOwned`; a `workout_exercise` row has no
  `user_id`, so the repository resolves it through its parent workout and
  applies the same check (§5, §6 Wiring points). There is deliberately no
  "get workout by id, trust the caller" method for a handler to reach for. The
  cross-user integration tests (§10) assert this on every route that takes an
  id.
- **404, never 403, for another user's row.** A workout or workout exercise
  belonging to someone else is indistinguishable on the wire from one that
  does not exist (§5), so a caller cannot probe for other users' ids. The same
  holds for `exerciseId` in the add-exercise body: another user's custom
  exercise is `404`, resolved by `exerciseRepository.findVisibleById`, so this
  endpoint cannot be used to test whether someone else's exercise exists. A
  malformed `{id}` is also `404`, so "wrong shape" and "not yours" cannot be
  told apart either. The `409 workout-in-progress-exists` body carries no
  workout id (§6.2), so even that error hands the caller nothing beyond what
  `GET /v1/workouts/active` (their own row only) already returns.
- **No client-settable ownership or provenance.** Request bodies are
  `z.strictObject` (§5), so `userId`, `localDate`, `source`, `id` and the
  snapshot fields are `422`, not silently dropped: a client cannot write a row
  into another user's account, forge a `local_date`, or supply its own
  `exercise_name_snapshot`.
- **Structured logs carry ids and durations only, never free text.** The
  lines in §9 record `workout_id`, `workout_exercise_id`, `exercise_id`,
  `user_id` and durations. `title` and `notes` are arbitrary user text with no
  business being duplicated into logs, the same rule as 03.2 §7 for `name`.
  The RFC 9457 `detail` for `422` names the failing field and rule, never
  echoes the submitted value.
- **No write throttle and no per-user quota in this spec.** 05.0 ships
  neither, and this is a stated gap, not an oversight. The repository has no
  rate-limit plugin or dependency today (`@fastify/rate-limit` and its
  equivalents are absent from `apps/api/package.json`), so **Spec 05.2 is
  greenfield**: it introduces the mechanism and the quotas, it does not extend
  something that exists. Until it lands, an authenticated user can create,
  delete and re-create workouts, and add exercises to one, as fast as the
  connection allows. Two of 03.2's open decisions therefore **stay open**:
  **D20** (advisory-lock connection-pool blast radius) and **D21** (unbounded
  storage growth via create/delete cycling). The per-workout position lock
  (§6.8) is a correctness lock scoped to one workout, held for one short
  transaction; it does **not** close D20, and this spec makes no claim that
  it does. The one-in-progress rule bounds *concurrent* open sessions per
  user to one, which limits nothing about *sequential* volume, so it does not
  address D21 either. The only volume bound in this spec is per-request:
  bounded free text and the 64 KiB body limit.
- **No new PII.** A workout's calendar fields, free text and exercise choices
  are the user's own data and are scoped to them by the rules above; the row
  carries no name, email or location. `tz_offset_minutes` is coarser than the
  `user.timezone` Spec 02 already stores. Whole-account export and purge are
  Spec 11's, and the `ON DELETE CASCADE` chain in §4 is what lets that purge
  reach these rows.

## 8. Config & secrets

**No new environment variables and no new secrets.** Everything this spec
tunes is a code constant in `@sin/core`, deliberately not env-configurable:

- The two `startedAt` clock-skew bounds of §6.4 (5 minutes into the future,
  7 days into the past, the former also applied to `endedAt` on finish),
  defined in `packages/core/src/dto/workout.ts` alongside `WORKOUT_TITLE_MAX`
  and `WORKOUT_NOTES_MAX`. §6.4 fixes the values and where they live; it does
  not assign identifiers, so the names are chosen at implementation and
  recorded in §12.
- `WORKOUT_TITLE_MAX` (120) and `WORKOUT_NOTES_MAX` (4000), which §7 argues.
- `WORKOUT_SOURCE_VALUES`, which renders the `source` `CHECK` (§4).

This follows the `MAX_CUSTOM_EXERCISES_PER_USER` precedent (03.2 §8): changing
any of these is a **code-reviewed decision, not an ops knob**. The skew bounds
guard the `(user_id, started_at DESC)` history ordering that Spec 07 reads;
the text bounds are tied to the body-limit argument in §7; the `source` list
is tied to a database `CHECK` that only a migration can change. Making any of
them an env var would let a staging value silently differ from production and
would make the behavior a spec cannot state as a number. The bounds are
shared with the client through `@sin/core`, so Spec 06 validates against the
same values the server enforces.

`DATABASE_URL`, the Auth0 settings and `BODY_LIMIT_BYTES` are unchanged and
owned by Specs 01 and 03.0. Nothing here needs a Render or CI setting.

## 9. Observability

The Spec 01 request log (`request_id`, `user_id`, status, duration) already
covers all eight routes. This spec adds four structured log lines, one per
business event, emitted by the handler after the write commits:

| Line | Emitted when | Fields |
|---|---|---|
| `workout_started` | `POST /v1/workouts` creates a row (`201`) | `workout_id`, `user_id` |
| `workout_finished` | `PATCH /v1/workouts/{id}` sets `endedAt` on an in-progress workout | `workout_id`, `user_id`, `duration_seconds` (`endedAt` minus `startedAt`), `exercise_count` |
| `workout_deleted` | `DELETE /v1/workouts/{id}` succeeds | `workout_id`, `user_id`, `was_finished`, `exercise_count` |
| `workout_exercise_added` | `POST /v1/workouts/{id}/exercises` succeeds | `workout_id`, `workout_exercise_id`, `exercise_id`, `user_id`, `position` |

- **Ids, counts and durations only, never `title` or `notes`** (§7). Field
  names are snake_case, matching the 03.2 §9 lines.
- **`workout_started` is emitted on the fresh-create path only.** The `200`
  idempotent replay (§6.1) does not log it, so a flaky-connection retry does
  not inflate the started count. A client's retry storm is visible in the
  request log, where the `200` / `201` split already distinguishes the two.
- **`workout_finished` fires on the transition, not on every `PATCH`.** A
  `PATCH` that only edits `title` or `notes`, or a `PATCH {}` no-op, logs
  nothing beyond the request line.
- **These lines are the business counters.** DESIGN §8.1 lists "business
  counters (workouts started/finished, sets logged)" among its metrics; the
  first two lines are their source for workouts, and 05.1 adds the sets-logged
  counterpart. DESIGN §1.3 has no metric literally named "workouts
  started/finished", but its "workouts with all sets logged during the
  session" target is a ratio over finished workouts, so `workout_finished`
  supplies its denominator (the numerator needs 05.1's set data). There
  is no metrics backend yet (Spec 13), so today these are log fields that can
  be counted from Render's log stream; Spec 13 lifts them into real counters
  without changing the lines.
- **BL-5 applies here and is not fixed here.** Routine `404` / `409` / `422`
  outcomes on these endpoints (`workout-finished`,
  `workout-in-progress-exists`, `exercise-retired`, a clock-skew `422`) have no
  dedicated log line, so they fall to the generic `error`-level handler until
  BL-5 is resolved. On these routes that is expected traffic: a resumed
  session that hits `workout-in-progress-exists` is the designed recovery path
  (§5), not an incident. Anyone alerting on `error` rate should read it with
  that in mind. This spec does not change the handler.
- No traces or metrics backend yet (Spec 13); DESIGN §8.1 asks for the finish
  transaction to be traced specifically, which is Spec 13's to wire.

Prisma migrations** (`startIntegrationDb` / `applyMigrationFile` in
`apps/api/test/integration/helpers.ts`). Order of attack: migration →
`@sin/core` ids / DTOs / `time.ts` → `workoutRepository` → routes → the OpenAPI
assertion. Route-level unit tests run against `FakeWorkoutRepository` through

(`shouldRunIntegration()`), and their container-startup `beforeAll` is

`describe.skipIf` still runs `beforeAll` (CLAUDE.md). A plain

Four of those rows are deliberately more demanding than a happy-path check,
and are called out here rather than left to a test author's taste: **AC3**
(≈10 parallel identical `clientGeneratedId`s, per 03.2 D23), **AC4** (a
concurrent burst of creates against the partial unique index), **AC12** (a

the advisory lock) and **AC15** (a purge that proves the FK direction down both
cascade paths). Each of the four is the cheapest test that would actually fail
against the plausible broken implementation; a weaker version of any of them
passes against code that is wrong.
