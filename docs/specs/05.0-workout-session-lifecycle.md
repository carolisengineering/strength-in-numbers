## 1. Purpose, scope & non-goals

Ship the **session lifecycle** of workout logging: the `workout` and
`workout_exercise` tables, the endpoints that start, resume, edit, finish and
delete a workout session and that add, reorder and remove exercises within it,
and the `@sin/core` types those endpoints need. This is the first of three
specs that split the roadmap's Spec 05 (05.0 session lifecycle, 05.1 set
logging, 05.2 rate limiting and write quotas), because the original scope
bundled several work sessions' worth of change. It also fixes the two rules
every later logging feature leans on: workout creation is idempotent under
retry (DESIGN §6), and `local_date` is derived once, at write time, from the
client's own offset (DESIGN §4.0).

### In scope

- The `workout` and `workout_exercise` tables, in migration
  `0005_create_workout_session`.
- The session lifecycle endpoints: create, read the active session, read by
  id, update (including finish), delete; add, update (reorder) and delete a
  workout exercise.
- Workout-creation idempotency via `client_generated_id`, and the
  one-in-progress-session-per-user rule.
- The calendar-field rules (`local_date` / `tz_offset_minutes`): how they are
  supplied, derived and stored.
- The `@sin/core` additions those need: `WorkoutId` / `WorkoutExerciseId`,
  `WORKOUT_SOURCE_VALUES`, the workout DTOs, and a new `time.ts` module of pure
  calendar helpers.

### Non-goals

- **`set_entry` and everything measure-shaped** — the table, per-modality
  validation, and the finish integrity rule ("a working set needs at least one
  measure") — are **Spec 05.1**. 05.0's finish transition only sets
  `ended_at`.
- **Rate limiting and per-user write quotas** are **Spec 05.2**, which also
  closes 03.2's open D20 (connection-pool blast radius) and D21 (unbounded
  storage growth via create/delete cycling). 05.0 ships no write throttle.
- **The paginated history list and all PR/progress work** are **Spec 07**.
  There is deliberately no `GET /v1/workouts` list here, and finishing a
  workout does not write PRs; 07 adds the PR recompute to the finish
  transition and backfills workouts finished before it ships.
- **`routine_id` and `superset_group`** semantics are **Spec 09**. Neither
  column is created here (see §4 and §12).
- **The logging UI** — active-session screen, exercise picker integration,
  resume flow — is **Spec 06**.

## 4. Data model

Owned by this spec: **`workout`** and **`workout_exercise`**. Migration
**`0005_create_workout_session`** — additive, expand-only. The migration SQL is
**hand-authored**: the partial unique index `WHERE ended_at IS NULL`, the two
`CHECK (… IN (…))` literal lists, and the `DEFERRABLE` unique constraint are not
expressible in the Prisma schema DSL, so the `.sql` file is the source of truth
and the Prisma models exist for the client only (the same raw-SQL carve-out
Spec 03.1 §4 used for `0002`). The file follows the `0002` conventions: a
`NNNN_snake_case` directory, a header comment naming this section, explicit
`TIMESTAMPTZ(6)` column types, and a "Down = test teardown / local reset only,
never production" comment. Production undo is `git revert` plus a forward
migration, never a down script (Spec 01 §11).

```
Table: workout
  id                  uuid        PK, app-generated UUIDv7
  user_id             uuid        NOT NULL FK → user(id) ON DELETE CASCADE
  title               text        NULL
  notes               text        NULL
  started_at          timestamptz NOT NULL
  ended_at            timestamptz NULL            -- NULL = in progress
  local_date          date        NOT NULL
  tz_offset_minutes   smallint    NOT NULL
  client_generated_id uuid        NOT NULL        -- idempotency key
  source              text        NOT NULL DEFAULT 'manual'
                                  CHECK (source IN (<@sin/core WORKOUT_SOURCE_VALUES>))
  created_at/updated_at timestamptz NOT NULL      -- app-stamped, no trigger

Indexes:
  workout_user_client_id_key  UNIQUE (user_id, client_generated_id)
  workout_user_started_idx    (user_id, started_at DESC)   -- the 07 history list
  workout_user_active_key     UNIQUE (user_id) WHERE ended_at IS NULL

Table: workout_exercise
  id                     uuid        PK, UUIDv7
  workout_id             uuid        NOT NULL FK → workout(id) ON DELETE CASCADE
  position               smallint    NOT NULL
  exercise_id            uuid        NOT NULL FK → exercise(id) ON DELETE CASCADE
  exercise_name_snapshot text        NOT NULL
  modality_snapshot      text        NOT NULL
                                     CHECK (modality_snapshot IN (<MODALITY_VALUES>))
  notes                  text        NULL
  created_at/updated_at  timestamptz NOT NULL

Indexes:
  workout_exercise_position_key UNIQUE (workout_id, position) DEFERRABLE INITIALLY IMMEDIATE
  workout_exercise_exercise_idx (exercise_id)
```

- **`exercise_id` is `ON DELETE CASCADE`, which discharges the purge-ordering
  obligation.** Spec 03.1 §3 and Spec 03.2 §3 both hand Spec 05 the question of
  how an account purge orders `workout_exercise` against the user's custom
  `exercise` rows. `exercise.owner_user_id` is itself `ON DELETE CASCADE`
  (03.1 §4), so purging a user deletes their custom exercises; a `RESTRICT` or
  `NO ACTION` on `workout_exercise.exercise_id` would make that delete depend on
  the order Postgres happens to process the two cascades, and a purge that
  reaches an exercise row while `workout_exercise` rows still reference it is
  refused. With `CASCADE` on both paths (`user → workout → workout_exercise`
  and `user → exercise → workout_exercise`) no ordering is needed. The cascade
  can only ever fire for the purged user's own rows: global rows are never
  hard-deleted (DESIGN §4.2, append-only, retire by `is_active = false`), so no
  other user's history is reachable through it. `workout_exercise_exercise_idx`
  exists for exactly this delete path — without it, each exercise delete would
  sequentially scan `workout_exercise` to find referencing rows — and doubles as
  the lookup for "which workouts used this exercise" (Spec 07).
- **The snapshots are `NOT NULL` and written at add time.**
  `exercise_name_snapshot` and `modality_snapshot` are copied from
  `exerciseRepository.findVisibleById` inside the add-exercise write (§6), so a
  later rename, soft-delete or fork of the exercise never rewrites a logged
  session (DESIGN §4.4). They are `NOT NULL` because a snapshot that can be
  absent is a second code path every history reader must handle; the add path
  is the only writer and always has the row in hand. The `modality_snapshot`
  `CHECK` renders `MODALITY_VALUES` into the migration exactly as 03.1 AC2 does
  for `exercise.modality`, and inherits its drift guard: a unit test asserts
  the migration `.sql` **contains** the rendered clause (string containment, not
  a parse of `pg_get_constraintdef()`, which Postgres normalizes to
  `= ANY (ARRAY[...])`). The same applies to `source` against
  `WORKOUT_SOURCE_VALUES`.
- **`superset_group` and `routine_id` are deliberately omitted.** DESIGN §4.4
  lists both on `workout` / `workout_exercise`, but nothing in v1 M1 writes or
  reads them. Spec 09 adds `superset_group` additively, alongside
  `routine_item.superset_group`. `routine_id` waits because the `routine` table
  does not exist until 09, and a nullable `uuid` with no FK now and an FK later
  is worse than one additive `ALTER TABLE … ADD COLUMN … REFERENCES` in 09.
  Both omissions are recorded as decisions in §12 so a reader does not conclude
  DESIGN was missed.
- **No `change_xid`-style trigger.** `created_at` / `updated_at` stay
  app-stamped, as for `user` (Spec 01) and `exercise` (03.1 §4). The Spec 03.3
  trigger is a narrow exception whose only purpose is sync-correctness for a
  catalog that clients delta-pull; workouts have no delta-sync contract in v1,
  so a trigger would add write-path cost and a second stamping mechanism for no
  reader.
- **The three `workout` indexes each serve one rule.**
  `workout_user_client_id_key` is the idempotency key (DESIGN §6): a retried
  `POST /v1/workouts` collides on it and the handler replays the stored row
  (§6). It is scoped by `user_id` so one user's key can never leak or collide
  with another's. `workout_user_active_key` is a **partial** unique index on
  `user_id WHERE ended_at IS NULL`, which makes "at most one in-progress
  session per user" a database invariant rather than a check-then-insert race;
  it also serves the `GET /v1/workouts/active` lookup.
  `workout_user_started_idx` `(user_id, started_at DESC)` is the history-list
  access path that Spec 07 will read; it is created here, with the table, so
  07 needs no index build on a populated table.
- **`workout_exercise_position_key` is `DEFERRABLE INITIALLY IMMEDIATE`.** A
  reorder moves several rows' `position` values inside one transaction, and
  intermediate states (two rows briefly sharing a position) are unavoidable when
  swapping. A plain unique constraint checks each row as it is written and
  would reject the swap; a deferrable one lets the reorder transaction run
  `SET CONSTRAINTS workout_exercise_position_key DEFERRED` and have the check
  happen at commit. `INITIALLY IMMEDIATE` keeps ordinary inserts and deletes
  strict, so only the reorder path opts in. Note this must be a
  **constraint**, not a bare `CREATE UNIQUE INDEX`, because Postgres cannot
  defer a unique index.
- **The `User` and `Exercise` models gain back-references.** Prisma requires
  both sides of a relation, so `workout.user_id → user(id)` obliges a
  `workouts Workout[]` field on `User` (owned by Spec 01) and
  `workout_exercise.exercise_id → exercise(id)` obliges a
  `workoutExercises WorkoutExercise[]` field on `Exercise` (owned by 03.1), or
  `prisma validate` fails in CI — the same trap 03.1 §4 recorded for
  `User.customExercises`. The `Workout` and `WorkoutExercise` models also need
  `@@map("workout")` / `@@map("workout_exercise")` and per-field `@map`
  snake_case mappings so the client's camelCase fields line up with the
  hand-authored columns. All of this is a **Prisma-client-only change** — no
  column, no extra migration — and does not otherwise disturb Spec 01's or
  03.1's ownership of `user` and `exercise`.
