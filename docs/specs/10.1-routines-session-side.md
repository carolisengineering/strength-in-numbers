## 1. Purpose, scope & non-goals

Show the routine on the session screens, and let the lifter group exercises while they train. On the **active workout** each card shows the exercise's target line and notes under its name, grouped cards sit inside the 10.0 bracket, and a "Superset with next" toggle between adjacent cards links and unlinks them live; Move up / Move down follow the editor's block-move rules. On the **finished workout** (`/app/workouts/:id` and `/app/history/:id`) the same target line, notes and bracket are shown read-only, plus a "From routine: <name>" line; the **History list** row appends the routine name after the date. **No API change, no migration, no release step, no env var, no new browser-storage key, no new dependency.**

> **First-principles note — why a "planner" and not a PATCH per tap.** The server stores a superset as a *number on each exercise* (`supersetGroup`); "A and B are a superset" means they carry the same number. One tap on "Superset with next" can therefore need several writes (merging a run of 4 into another run of 4 means renumbering 4 exercises), and the API has no "set these groups atomically" call. We do **not** add one: a half-applied change is a state the server already accepts (groups need not be dense, contiguous or ≥ 2 — Spec 09 D10), and the screen simply draws a run of one or a stray member as *ungrouped*. So the work is: (1) decide **what the groups should become** with one pure function shared with the routine editor, so editor and session cannot disagree; (2) **diff** that against what is on screen to get the *minimal ordered list* of PATCHes; (3) send them one at a time and, on the first failure, stop and re-read the server's truth. Step 1–2 are `packages/core` code (no React, no DOM — it is a table of `before → op → PATCH list` unit tests); step 3 is a small hook.
>
> **First-principles note — "pure" and `@sin/core`.** `@sin/core` is imported by both the web app and the API. A CI check (`pnpm run core:purity`) forbids React, DOM and Node-only imports there, so everything in it is plain functions over plain data. That is why the shared rules live there and not in `apps/web`: the planner, the editor's reducer and (later) a mobile client can all call the same code.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.1 ACn — …"`** (the 08.x / 10.0 convention). Levels are in §10. **Phase A** (AC1–AC10): `@sin/core` rules, the planner, the editor re-base. **Phase B** (AC11–AC15): client, hook, failure handling. **Phase C** (AC16–AC27): screens. **Phase D** (AC28–AC31): cross-cutting and verification. **Docs** (AC32–AC33).

### Phase A — `@sin/core`: shared rules, display helpers, planner

A *slot list* is `readonly { id: string; group: number | null }[]` in display order. A **run** is a maximal stretch of ≥ 2 consecutive slots with the same non-null `group`; a slot whose group is `null`, **or whose group is shared with no neighbour** (a group of one, or a member detached from its group), is *ungrouped* for every rule below.

1. **Link.** `linkRule(slots, i)` (core `supersets.ts`, pure) joins the runs / ungrouped slots on either side of the boundary between `i` and `i+1`: an ungrouped neighbour joins the other's run; two runs become one; two ungrouped slots form a run of two. If the merged run would exceed **8** (`SUPERSET_GROUP_MEMBERS_MAX`) it returns `{ ok: false, reason: LINK_CAP_MESSAGE }` ("A superset can have up to 8 exercises") and changes nothing; `i` on the last slot or out of range → `{ ok: false, reason: "No exercise to link with" }`. Output group *labels* are meaningful only as equality classes (a fresh label may be `max + 1`, even above 99); numbering is the caller's job (AC8 for the session, `settle` for the editor). `canLinkRule(slots, i)` reports the same refusal without computing the result.
2. **Unlink.** `unlinkRule(slots, i)` on a linked boundary splits the run in two at that boundary; a side left with one member becomes ungrouped. On an unlinked boundary it is a no-op. (The toggle is `isLinked ? unlink : link`; `isLinked(slots, i)` is true when slots `i` and `i+1` share a non-null group.)
3. **Block moves.** `moveRule(slots, i, dir)` (`dir` ±1): within a run → plain swap, group unchanged; a run's edge member moving *outward* leaves the group first (the run dissolves when one member remains) and then moves as an ungrouped slot; an ungrouped slot moving into a run **jumps the whole run** and never lands inside one; two adjacent runs: an edge member of one leaves its group and jumps the neighbouring run; moving the first slot up or the last down is a no-op (`null`). Table-driven, including runs at the start and end of the list and two adjacent runs.
4. **Tolerant inputs.** The rules accept slot lists that violate the editor's invariant — a group of one, a group split into two non-adjacent stretches, unordered or sparse numbers (e.g. `[3, null, 3, 3, 40]`) — treating each maximal stretch as its own run and each singleton as ungrouped; they never throw and never mutate their input.
5. **The editor is re-based, behaviour unchanged.** `routineDraft.ts` delegates `toggleLink`, `canLink`, `isLinked`, `move` (Move up / down), and `runPosition` to the core rules (mapping `DraftItem.key` ↔ slot `id`) and keeps its own `settle` (dense 1, 2, 3 … renumbering, `normalizeSupersetGroups`) on top. `runPosition` is re-exported from `routineDraft.ts`. **Every 10.0 test passes unchanged** — `routineDraft.test.ts`, `EditorRow.test.tsx`, `RoutineEditor*.test.tsx`, `ItemSheet.test.tsx`, `validateDraft.test.ts`, `routes.test.tsx`, `a11y.test.tsx` — with no edit to any assertion or import (a diff of those files shows nothing). `pnpm run core:purity` stays green.
6. **Display helpers.** `runPosition(groups, i)` (moved to core; `"none" | "first" | "middle" | "last"`, a run of one → `"none"`) and `runOrdinals(groups)` → `(number | null)[]`: each slot inside a run gets that run's **ordinal on screen** — 1, 2, … top to bottom over *runs only* — and every other slot gets `null`. So `[7, 7, null, 3, 3, 3, 40]` → `[1, 1, null, 2, 2, 2, null]` (the `40` is a group of one). Two adjacent runs with different stored numbers are two runs; two runs carrying the *same* stored number but separated by an ungrouped slot are two runs with two ordinals.
7. **`planSessionChange` contract.** `planSessionChange(current: readonly SessionSlot[], op): SessionPlan` (pure) where `SessionSlot = { id, group }` is in **position order** (index = `position`, dense per Spec 05.0 D41) and `op` is `{ type: "toggleLink"; index: number }` or `{ type: "move"; id: string; direction: "up" | "down" }`. It applies the matching shared rule (AC1–AC3), then diffs the result against `current`. Output: `{ ok: true; patches: SessionPatch[]; next: SessionSlot[] }` or `{ ok: false; reason: "cap"; message: string } | { ok: false; reason: "no-free-group" }`, where `SessionPatch` is `{ id; supersetGroup: number | null }` (group change) or `{ id; position: number }` (move). `next` is the state the patches produce. A rule no-op (edge move, last-slot toggle, unlink on an unlinked boundary…) is `{ ok: true, patches: [], next: current }`. The input is never mutated.
8. **Numbering.** Live groups are any integer 1–99, stored as sent (Spec 09 AC23, D10). **Groups the operation does not touch keep their numbers** (no patch is emitted for their members). A *touched* run keeps its stored number — the **larger** side keeps it on a merge or split (tie: the upper side) — provided no slot *outside* that run carries the same number; otherwise, and for every newly formed run, it takes the **smallest number in 1–99 not carried by any slot in `current`** (stray singletons and detached members count as carried). If no free number exists the plan is `{ ok: false, reason: "no-free-group" }` with nothing changed (unreachable for a 99-slot-or-fewer workout in practice; defined so the function is total). Tests: gaps (`[1, 1, null, 3, 3]` → a new run gets `2`), the 1–99 ceiling, a stray colliding with a touched run's number, untouched groups with sparse / high numbers.
9. **Minimality and order.** The plan contains **no patch that does not change a value** and the **fewest group patches** for the chosen numbering (the smaller side of a merge or split is the one renumbered: link of a 4-run and a 4-run → 4 patches; unlink 4|4 → 4; join of an ungrouped slot to a run → 1; unlink leaving a side of one → 1 patch for that member, or 2 patches when both sides are singletons). A link / unlink emits at most **4** group patches (the 8-member cap makes the smaller side ≤ 4 in the invariant case) and no position patch; a move emits at most **2 group patches + 1 position patch** (the worst case is a 2-run dissolving: both members become ungrouped, then the position patch). **Order:** all group patches first, in an order that leaves every group contiguous after every prefix when the input satisfies the invariant (renumbering into an *adjacent existing* run proceeds from the member nearest that run outward; splitting off a *fresh* number proceeds from the far end toward the boundary), then the single `{ id, position }` patch last, where `position` is the moved slot's index in `next`. A move-out that fails after its group patch therefore leaves "ungrouped but not yet moved" (harmless).
10. **Property-style test.** A seeded pseudo-random generator builds 500+ slot lists that satisfy the editor's invariant (runs of 2–8, dense or sparse numbers, mixed with ungrouped slots, 1–20 slots) and random ops (`toggleLink` at any boundary, `move` of any id up / down). For each: applying `patches` in order to `current` (group patches set `group`; a position patch removes the slot and re-inserts it at that index) yields exactly `next`; `next` equals the rule's result **up to relabelling**; every run in `next` is contiguous with a number unique to it and size 2–8; untouched runs keep their numbers; no patch is a no-op; every prefix of the patch list leaves each group contiguous. A second generator feeds *tolerant* inputs (AC4) and asserts: no throw, `next` equals `patches` applied, and every run in `next` that the operation touched is contiguous with a unique number.

### Phase B — client, hook, failures

11. **The client call.** `WorkoutClient` gains `updateWorkoutExercise(id, { position?, supersetGroup? }): Promise<WorkoutExercise>` → `PATCH /v1/workout-exercises/{id}` with exactly the keys passed (an absent key is absent from the body; `supersetGroup: null` is sent as `null`), response parsed with `WorkoutExerciseSchema`, id path-encoded (`encodeURIComponent`). `moveExercise(id, position)` becomes `updateWorkoutExercise(id, { position })` and issues the **byte-identical** request it does today (`{"position": n}`); the method has **no `notes` parameter**, so no regroup or move can overwrite a note copied from the routine at start (Spec 09 D22's cost); `client.moveExercise` stays on the interface. `useMoveExercise` is folded into the new hook (AC12) and its call sites updated.
12. **Sequential sending (`useRegroup`).** `useRegroup()` (`features/workouts/useRegroup.ts`) exposes `run(op)` and `busy`. It reads the current slots from the sorted exercises, calls `planSessionChange`, and sends the patches **strictly sequentially** through a `networkMode: "always"` mutation that calls `client.updateWorkoutExercise` (the next request starts only after the previous one resolves). A synchronous ref guard makes a second `run` while one is in flight a no-op. After the **last** patch — or after the first failure — `WORKOUT_KEYS.active` is invalidated **once** (no refetch between patches). A `move` op fires `track("exercise_moved", { direction })` once on success (the existing event; no new event, no id). An empty plan sends nothing and refetches nothing. A refused plan (`cap` / `no-free-group`) sends nothing and surfaces its message (AC19 / AC15).
13. **Failure handling.** On the **first** failed PATCH the hook stops (later patches are not sent), invalidates and awaits the active-workout refetch, and hands the error to `ActiveSession.handleFailure("regroup", error)`. `sessionErrors.ts` gains `Operation = … | "regroup"`, resolved exactly as `move-exercise`: `404` / `422` → `refetch` (the lifter's screen is stale; the refetch *is* the notice — the stale-position conflict, `track("workout_conflict", { kind: "stale-position" })`); `409 workout-finished` → `gone`; network → the banner **"You're offline — try again when you have signal"** (`OFFLINE_MESSAGE`); anything else, `429` and `5xx` included → the banner **"Couldn't change the superset — try again"** (+ request id). No "Try again" action is offered on the banner (D7): after a partial plan a retry would be re-planned from a half-applied state; the refetched cards show the truth and the lifter re-taps. `reportUnexpected("regroup", error)` runs as for the other operations (`ReportOp` gains `regroup`); static tags only. **Exception (implementation ruling R1):** a failed `move` whose plan was a single `{ position }` patch resolves as 06.1's `move-exercise` (its copy, and a Try again that re-sends that same absolute `{ position }` PATCH, so a lost response cannot move the card twice) — this keeps AC21's "06.1's move tests pass unmodified" true, and D7's rationale already names the single-position case.
14. **Online-only.** Regroup operations are never routed through the 06.2 outbox: offline, the first PATCH fails at once (mutations use `networkMode: "always"`, they never pause), the offline banner of AC13 shows, nothing is queued, and the cards are unchanged. No code in the regroup path imports `outbox/`; no `localStorage` / `sessionStorage` reference is added (Spec 04.0 AC7's scan stays green; `USER_DATA_KEY_PREFIXES` unchanged).
15. **Refusals are surfaced, not sent.** A `cap` refusal never reaches the hook: the toggle is disabled with the reason (AC19). If the plan nevertheless reports `cap` (a stale render) or `no-free-group`, the banner shows the refusal text (`LINK_CAP_MESSAGE`, or "This workout has too many supersets") as a warning and no request is made.

### Phase C — screens

16. **Active card content.** Under the exercise name, `ExerciseCard` renders `targetLine(exercise)` (the 10.0 `targetFormat.ts` function, imported as-is — `WorkoutExerciseDetail` carries the same five target fields) and then the exercise's `notes` as plain text. Each is omitted when empty (`""` / `null`), and an exercise with all targets and notes `null` renders **exactly the markup it renders today** (a snapshot-style test against the pre-change structure). No set is prefilled and no progress count is shown (D3). For a workout started from a routine whose items have notes, those notes appear on the matching cards (they are `workout_exercise.notes` from the Spec 09 D22 start copy); the web fake's start-from-routine copies item notes the same way.
17. **Bracket and names on the active screen.** `ActiveSession` computes `runPosition` and `runOrdinals` once over the sorted exercises' `supersetGroup`s and passes each card its `bracket` position and `superset` ordinal. A card in a **contiguous run of ≥ 2** gets the decorative left-edge bracket (the 10.0 `SupersetBracket`, `aria-hidden`, continuous across the run) and an accessible name from `itemAccessibleName(name, ordinal, targetLine, false)` ("Bench press, superset 1, 4 × 6–8") set as the article's `aria-label`; **N is the run's ordinal on screen**, not the stored number (`[7, 7, null, 3, 3]` reads "superset 1" and "superset 2"). Ungrouped cards keep today's name (`aria-labelledby` the heading) and show no bracket.
18. **Tolerant display.** A server state with a group of one, a member detached from its group, or two stretches sharing a stored number renders without a bracket for the singletons / strays, one bracket per genuine run, and **does not crash or warn** (tests render each shape through the real `ActiveSession` and through `FinishedWorkoutScreen`).
19. **Link toggles.** Between every pair of adjacent **active** cards `ActiveSession` renders the 10.0 `LinkToggle` ("Superset with next" / "Superset ✓", `aria-pressed`, accessible name "Superset {above} with {below}", ≥ 44 px) with the same 8-member refusal: when `canLinkRule` refuses, the toggle is disabled and the reason "A superset can have up to 8 exercises" is shown beside it and referenced by `aria-describedby`. There is no toggle after the last card, none on a finished screen, and none while the workout has fewer than two exercises.
20. **Toggle sends the planned PATCHes.** Pressing a toggle calls `useRegroup().run({ type: "toggleLink", index })`. Against the workout fake, tests assert the **exact request sequence** (method, path, body, order) for: ungrouped + ungrouped (one PATCH `{supersetGroup: smallest free}` per member that changes — both), ungrouped joins a run (1), run merges run (renumbers the smaller run), unlink leaving a side of one, unlink 4|4, and a numbering with gaps; and that after the sequence the refetched cards show the bracket / names of the new state.
21. **Block-aware Move up / Move down.** The Options-disclosure buttons call `run({ type: "move", id, direction })`. For a workout with no grouped exercise the wire is **identical to today**: one `PATCH {position: index ± 1}`, and 06.1's move tests pass unmodified. With groups: an ungrouped card moving next to a run sends **one** `PATCH {position}` to the far side of the run (non-adjacent target, accepted by the API: §6.1a); a grouped edge card moving outward sends its `supersetGroup` patch(es) first and the `position` patch last; a swap inside a run sends one `position` PATCH. Move up is disabled on the first card and Move down on the last, as today. A failed plain move keeps 06.1's Try again (AC13, R1).
22. **One regroup at a time.** While a regroup is in flight **every** link toggle and **every** Move up / Move down button is disabled (`disabled` + the section `aria-busy`), alongside the existing add / remove structure lock (`structureBusy` becomes `add || move/regroup || remove || pending`); a second tap during flight issues no request (AC12's ref guard, tested with `deferred()` promises). Controls re-enable after the final refetch settles, on success **and** on failure. Finish stays disabled while a regroup is in flight (as for other structure writes).
23. **Mid-plan failure.** With a 4-patch plan whose 2nd PATCH fails (`500`, `404`, network, `429` in turn): exactly 2 requests were sent, the active workout is refetched once, the cards show the server state, controls are re-enabled, and the banner / refetch of AC13 appears (offline → the offline message verbatim; `429` and `500` → "Couldn't change the superset — try again" with the request id; `404` / `422` → silent refetch + `workout_conflict` tracked). The banner has no "Try again" action.
24. **Finished workout and History detail.** `FinishedWorkoutScreen` → `SummaryExercise` (both `/app/workouts/:id` and `/app/history/:id`) renders, under each exercise name, the same target line and notes, and the bracket / `aria-label` ("…, superset N, …") by the same `runPosition` / `runOrdinals` / `itemAccessibleName` calls as AC17, over the sorted exercises. Under the date line it renders **"From routine: {routineName}"** when `routineName` is non-null (a deleted routine still shows — it is the snapshot) and nothing when null. No link toggles or move controls appear. The two screens keep their own layouts; the **shared pieces** are the `SupersetBracket` component and a `supersetRows(exercises)` helper (display-order exercises → `{ exercise, bracket, ordinal, line }`) that both import — a source test fails if either screen computes runs itself.
25. **History row.** `HistoryRow`'s first line becomes `"{date} · {routineName}"` (the existing `formatLocalDate` text, then ` · ` and the name as plain text) when `routineName` is non-null; unchanged when null. The name is truncated with CSS ellipsis on one line (no wrap pushing the record badge). The row stays one link; its other lines and the record badge are untouched; `HistoryScreen` tests pass unmodified apart from fixtures that gain a `routineName`.
26. **Strict schemas stay strict.** `WorkoutSchema.routineName` and the six `WorkoutExercise` fields (`targetSets`, `targetRepsLow`, `targetRepsHigh`, `targetRpe`, `restSeconds`, `supersetGroup`) remain **required, nullable** in `@sin/core`, and the web client adds no `.default(null)` / `.catch` / optional wrapper. Core tests pin it: a `Workout` without `routineName`, or a `WorkoutExercise` without any of the six, fails `safeParse`; the web `workoutFake` and fixtures always emit them.
27. **Accessibility and tokens (component level).** Following 10.0 AC36 / AC37: in `a11y.test.tsx` the grouped card's name contains "superset N", the toggle is a real button with `aria-pressed` and a name naming both exercises, disabled-with-reason has `aria-describedby`, the bracket is `aria-hidden` and carries no colour-only meaning, every new button carries the tap-target class; every touched `*.module.css` uses `var(--…)` only and `assert:css-tokens` passes; a source scan over the files this spec adds finds no `style=`, `<style`, `dangerouslySetInnerHTML`. Pixel sizes, focus and the 320 px layout need a browser (AC31).

### Phase D — cross-cutting and verification

28. **Module boundaries and purity.** `@sin/core` `supersets.ts` imports nothing but sibling core modules and types (`core:purity` passes). `workouts/` may import from `routines/` only the leaf modules `targetFormat.ts`, `LinkToggle.tsx` and `SupersetBracket.tsx` (none of which imports from `workouts/`); a source-scan unit test lists every `workouts/ → routines/` import and fails on any other, and on any `routines/ → workouts/` import of the new files.
29. **Observability and hygiene.** No new `track()` event and no new property (`exercise_moved { direction }` is the only regroup event, as today); `reportError` only through `reportUnexpected` with static `{ source: "workouts", op: "regroup" }`; no exercise name, note, routine name or id in any `track` / `reportError` argument — a spy test over every failure path of AC23 (06.1 AC35's pattern). `observability.test.tsx` passes unmodified.
30. **No other behaviour changes; no backend change.** The existing `@sin/web` suites pass with edits limited to fixtures that add `routineName` / target fields where a test constructs them by hand, and imports of the renamed mutation hook; the 06.3 Playwright smoke is unchanged (a grep of `apps/web/e2e` finds no assertion on a card's accessible name or the History first line — re-check at implementation). `git diff main --stat` shows **no** path under `apps/api/`, `apps/api/prisma/`, `render.yaml`, `Dockerfile` or `.github/workflows/`; no release-step command is added to the runbook.
31. **Manual phone check (owner, recorded in the PR description).** On a phone against staging, with a routine "Push A" containing one superset: start it and confirm in the session that targets and **the routine's item notes (write at least one in the editor first)** show under the names and the pair sits in one bracket; **link and unlink mid-session at 320 px and 390 px** (no sideways scroll, toggles reachable one-handed, ≥ 44 px); link two runs and confirm all renumbered cards re-bracket after one refetch; Move up / Move down across a run; VoiceOver reads a grouped card ("…, superset 1, …") and the toggle ("Superset X with Y", pressed state); **airplane mode on a link tap** shows the offline banner and leaves the cards unchanged; finish the workout and open it in Workouts and in History (bracket, target line, notes, "From routine: Push A"); delete the routine and confirm the History row and detail still show its name.

## 6. Behavior & logic

### 6.1 Verified API facts (the brief's two confirmations)

**(a) A non-adjacent `position` is accepted.** `PATCH /v1/workout-exercises/{id}` validates its body with `UpdateWorkoutExerciseSchema` (`packages/core/src/dto/workout.ts:131-136`: `position` int ≥ 0, `notes`, `supersetGroup` 1–99 or `null`, all optional, strict). The repository (`apps/api/src/repositories/workout.prisma.ts:619-736`, range check at `:698`) locks the workout, reads the row count `n`, and for any `requestedPosition ≠ current` requires only `0 ≤ position ≤ n−1` (`assertReorderPositionInRange`); it then shifts every row strictly between the old and new position by ±1 and writes the new position — a **jump of any distance in one statement**, with `SET CONSTRAINTS workout_exercise_position_key DEFERRED` so the unique `(workout_id, position)` constraint is checked at commit. `supersetGroup` and `position` may be combined in one body (`:726-729`; an absent key leaves the group, `null` clears it), and a same-position request is a 200 no-op. So a block move (an ungrouped card jumping a run of *k* members) is **one** PATCH with the destination index; **no fallback is needed**. (Had it been adjacent-only, the fallback would have been *k* sequential ±1 PATCHes with the same ordering rule.) Spec 05.0 §6.7 / Spec 05.1 move semantics are unchanged by 10.1.

**(b) Rate limit.** The route is declared `config: { writeGroup: "workouts" }` (`apps/api/src/routes/workouts.ts:303`). `RATE_LIMITS` (`apps/api/src/plugins/rate-limit.ts:39-46`): window 60 s, per-IP 600, group **`workouts: 60`** per user per minute (shared with start / finish / discard / add / remove exercise), plus the per-user **in-flight write cap of 4** (L3). Sequential sending keeps this spec's contribution at **1 in flight**. Cost per operation (AC9): link / unlink ≤ **4** PATCHes (merging two 4-runs, or unlinking a 4|4 run — the worst case), move ≤ **3** (a 2-run dissolving = 2 group patches + 1 position). Even the worst case at one operation every few seconds (15 worst-case operations a minute = 60 PATCHes) is far beyond real use — a lifter regroups a handful of times per session — and typical regroup traffic is 1–2 PATCHes per tap, ≪ 60 / min. A `429` lands in AC13's generic banner; no automatic retry (D7).

### 6.2 `supersets.ts` (core)

Pure functions over `SessionSlot[]` (`{ id, group }`), no imports beyond core siblings. Internals: `runs(slots)` computes maximal same-group stretches with length ≥ 2 (everything else is a singleton, AC4); `linkRule` / `unlinkRule` / `moveRule` are the 10.0 `routineDraft.ts` logic (`toggleLink`, `move`, `canLink`, `runBounds`) lifted verbatim over `{ id, group }` — the lift is mechanical, which is what makes AC5's "tests unchanged" credible — returning a new slot list whose labels are equality classes. `planSessionChange`: (1) rule → `result`; (2) identify touched runs (members whose class membership changed, plus a moved slot); (3) assign numbers (AC8) — preferring the larger side's stored number, collision-checked against all of `current`, else the smallest free in 1–99; (4) group patches for slots whose number changed, ordered per AC9; (5) a position patch if the moved slot's index changed; (6) `next` is `result` with the assigned numbers.

### 6.3 `useRegroup` and `ActiveSession`

`ActiveSession` replaces `useMoveExercise` + `moveExercise()` with `useRegroup`, keeping the shared `structureLock` ref so add / remove / regroup remain one-at-a-time (06.1 §6.3). `run(op)`: lock → `planSessionChange` → for each patch `await mutateAsync` → `invalidateQueries(active)` → unlock; a throw in the loop breaks it, awaits the refetch, calls `handleFailure("regroup", error)` with no `retry`, unlocks. While locked, `structureBusy` is true, which already disables Move up / Move down / Remove / Add; the link toggles read the same flag. The cards render from the cache, so they do not change mid-plan; they redraw once, from the refetch (a deliberate choice: intermediate half-states would flicker brackets for a 4-PATCH plan). The block-move *direction* semantics in the card's Options are unchanged for the lifter except that an ungrouped card now steps over a whole bracket rather than into it — the editor's behaviour (10.0 D8).

### 6.4 Display

`supersetRows(exercises)` sorts by `position`, computes `runPosition` and `runOrdinals` over `supersetGroup`, and `targetLine`; the active and finished renderers map over it. `SupersetBracket` is `ItemLine`'s bracket element extracted (same CSS module rules moved into `SupersetBracket.module.css`; `ItemLine` renders `<SupersetBracket position=… />`, so the 10.0 markup is byte-identical — covered by AC5's unchanged tests). Cards become `position: relative` with token-based left padding where bracketed; no inline styles.

## 7. Security & privacy

- **Authorization is the server's** (Spec 05.0 §6.7): a tampered id can only name a workout exercise the caller owns, otherwise `404`; the client adds no authority. A `WorkoutFinishedError` is the server's guard against writing to a finished workout.
- **User text** — exercise names, notes, routine names — is rendered as React text (escaped), never as markup, never in `track` / `reportError` (AC29), never in a URL. `routineName` in History persists as the snapshot (Spec 09 §7 PII note); nothing new is stored in the browser.
- **Path injection.** Every id goes into the path through `encodeURIComponent` (AC11).
- **Abuse.** The `workouts` write group and the in-flight cap are the server's (§6.1b); the client sends sequentially, latches the controls, and never auto-retries a write.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-11)

- ✅ **D1 — A pure regroup planner in `@sin/core` plus sequential per-exercise `PATCH /v1/workout-exercises/{id}`; no new API route.** **Rationale:** the failure an atomic endpoint would prevent (a half-applied regroup) is already harmless — a live group accepts any state, including a group of one (Spec 09 D10), and the screen draws strays as ungrouped — so a new write route (rate-limit group, OpenAPI, integration tests, a release step) would buy nothing the product needs. **Rejected:** an atomic `PUT …/superset-groups` (API work + a new write route for a harmless failure); end-only linking (diverges from the editor, and moves can split a bracket).
- ✅ **D2 — Live grouping is the 10.0 link toggle between adjacent cards; groups stay contiguous; moves follow the editor's block-move rules.** **Rationale:** one mental model across editor and session, and a non-adjacent or one-member group is unreachable from the UI. **Rejected:** a "Superset with…" picker (exposes the numbering, invites non-adjacent groups).
- ✅ **D3 — "Grid logging" = the bracket plus each card's own Log set row; targets are display-only.** No combined superset card in M3, no set prefill from targets, no "2 of 4 sets" count. **Rationale:** the bracket already is "no forced interleave" (DESIGN §2 item 8); prefill and progress counts are separate product decisions with their own edge cases (what does a prefilled set mean for the incomplete-set rule?). DESIGN §2 item 8 / Q5 now say so explicitly. *(Reversed by Spec 10.2 D1 for the prefill and count; the "no combined superset card" half stands.)*
- ✅ **D4 — Response schemas stay strict; DESIGN records a rollout convention instead.** `routineName` and the six `WorkoutExercise` fields remain required-nullable in core and in the client; no `.default(null)`. **Convention:** *a new response field ships in the API one release before any client that reads it; rolling the API back past such a field also rolls the client back.* **Rationale:** a tolerant default hides the failure it guards against — an older API would make every workout look target-less and ungrouped — and the real protection is deploy order, which a solo-developer pipeline controls (the API deploys first; the web is a static site that can be rolled back in lock-step). Strictness keeps one schema for server and client and makes a contract break loud in tests and at the first request. **Rejected:** `.default(null)` on the client parse (silent degradation, two schemas to keep in step); a core-level `.default(null)` (it would also loosen the server's allowlist).
- ✅ **D5 — Bracket and ordinal rules are shared pieces; N in "superset N" is the run's on-screen ordinal.** `runPosition` and `runOrdinals` live in core; `SupersetBracket`, `supersetRows`, `targetLine` and `LinkToggle` are shared by the screens. **Rationale:** the stored number is an arbitrary label (it may be 41 after a few regroups, or shared by two separated stretches), so it would be meaningless or wrong to read aloud; the ordinal is stable top-to-bottom and matches what is drawn. Shared pieces keep the active and finished renderers from drifting. A group of one or a detached member shows no bracket: it reads as ungrouped, because it is.
- ✅ **D6 — Regroup is online-only, not routed through the 06.2 outbox.** **Rationale:** the outbox replays *set* writes whose order does not depend on the screen's list; a regroup is computed from the on-screen list and its result depends on the server's current positions, so replaying it later could apply a stale plan (the same reason add / move / remove are online-only today, 06.1 §6.3). The cost is an immediate offline banner on a link tap — acceptable for a rare mid-session action.
- ✅ **D7 — No "Try again" on a regroup failure.** **Rationale:** a retry would re-plan from the refetched, possibly half-applied state; a *toggle* applied to a half-linked state could do the opposite of what the lifter meant (unlink instead of finish linking). Showing the true state and letting the lifter re-tap is safer and costs one tap. (Move up / Move down in 06.1 offer Try again because a single position patch is idempotent in effect; a multi-patch plan is not.)
- ✅ **D8 — The planner emits separate group and position patches, group changes first.** **Rationale:** a move-out that fails midway should leave "ungrouped but not yet moved" (harmless) rather than "moved but still grouped" (a bracket around a stranger, which the display would then render as a run). Also lets each patch be a minimal body that the server already supports.
- ✅ **D9 — The larger side keeps its stored number; a new run takes the smallest free number in 1–99.** **Rationale:** fewest PATCHes (cost is per member renumbered, and the rate limit is per request); deterministic, so tests and the manual check can predict numbers; "free" counts every stored number, so a stray singleton can never silently rejoin a new run.
- ✅ **D11 — Routine item notes reach the session through a Spec 09 amendment that merges and deploys first (owner decision, 2026-10-11; was O1, option A).** Spec 09 D22 / AC32–AC33: the start copy also writes `routine_item.notes` into `workout_exercise.notes` — one more column in the existing start copy (items `SELECT` + `INSERT … VALUES`), no migration, no new route, no response-shape change, no backfill. **Rationale:** a note written in the editor must be visible where the lifter trains, and the snapshot principle (D15 of Spec 09) covers it. It is its own small API PR, deployed **before** this spec's web code is implemented or merged — the response-field rollout convention (DESIGN §6) in spirit: API first. **Rejected:** leaving the notes line empty for routine-started workouts; a client-side join against the live routine (breaks the snapshot, and the routine may be deleted).
- ✅ **D10 — Shared module boundary: `workouts/` may import three leaf modules from `routines/`** (`targetFormat.ts`, `LinkToggle.tsx`, `SupersetBracket.tsx`), enforced by a source scan (AC28). **Rationale:** moving `targetLine` / `LinkToggle` would change 10.0's import paths and break its "tests unchanged" guarantee (AC5) for no benefit; a leaf import creates no cycle, since those files import nothing from `workouts/`. **Rejected:** copying `targetLine` (drift); a new `features/supersets/` folder (churn in 10.0 files and tests).

### Implementation rulings (2026-10-11)

- **R1** — single-position-patch move failures keep 06.1's copy and Try again, which re-sends the same absolute `{ position }` PATCH (`useRegroup().resend`) — idempotent, as 06.1's retry was (AC13, AC21).
- **R2** — core tests live in `packages/core/test/` (`supersets.test.ts`, `supersets-property.test.ts`, helper `test/helpers/supersets.ts`), the package convention, not beside the source as §6.5 shows.
- **R3** — `SupersetBracket` carries `data-bracket={position}` (test observability); the 10.0 markup gains that one attribute and its tests pass unedited (AC5).
- **R4** — `LinkToggle` gains an optional `disabled` prop for the in-flight latch (AC22).
- **R5** — the bracket is continuous across a run: on a linked boundary the spacer between two cards (the toggle row on the active screen, an empty spacer on the finished screen) carries a `middle` segment, and both card lists use `gap: 0` (§6.4).
- **R6** — `ActiveSession.handleFailure` takes `{ refetched: true }` from the regroup path, so the stale-position refetch is not repeated (one refetch, AC23).
- **R7** — `useRegroup().run(slots, op)` takes the slots from the caller; `ActiveSession` keeps them in a ref updated after commit (`useLayoutEffect`), so a tap plans from the list on screen.
- **AC15** is tested at hook level with real data (a 99-number workout) and at screen level with a stubbed planner; rendering 99 real cards in jsdom takes ~29 s.

### Open

- **O2 — Optimistic redraw during a multi-PATCH plan.** The cards redraw once, after the refetch (§6.3). If the phone check finds the 3–4 request delay on a bad connection feels slow, seeding the cache with `next` after the first patch is an additive change.
- **O3 — Notes display length.** Item notes can be up to 500 characters (routine) / 4000 (workout notes). A long note could push the Log set row off the first screen; the phone check decides whether to clamp with a "Show more" (CSS `line-clamp`, no behaviour change).
- **O4 — Per-run controls in M4.** The rest timer will need "which run is this card in"; `runOrdinals` is the intended seam. Revisit when M4 is specced.
