## 1. Purpose, scope & non-goals

Layers 1 and 2 (Spec 21.0) test and audit the application's own filtering. Layer 3 makes the **database refuse on its own**: with row-level security (RLS) on, the login the API connects with can read and write only the current user's rows (plus shared reference rows), whatever the SQL says. A forgotten `WHERE user_id = …` then returns nothing instead of everyone's data. The app is private-only for the foreseeable future (owner, 2026-11-05), so there is exactly one visibility rule: *your own rows*. All three layers land **before production's first real user**, so production starts with RLS on and there is no live-traffic switch-over.

> **First-principles note — "row-level security".** Normally a database user's rights are per table: you may `SELECT` from `workout` or you may not. RLS adds a per-*row* rule. You switch it on for a table (`ALTER TABLE workout ENABLE ROW LEVEL SECURITY`) and attach **policies**: SQL conditions Postgres adds, invisibly, to every statement that touches that table for the roles the policy names. A policy with `USING (user_id = X)` means "this role sees only rows where `user_id = X`" for `SELECT`, `UPDATE` and `DELETE`; `WITH CHECK (user_id = X)` means "this role may only write rows where `user_id = X`" for `INSERT` and `UPDATE`. A statement that breaks the rule does not error on read (the rows are simply absent, like a filter) and errors on write (`new row violates row-level security policy`). With RLS enabled and **no** matching policy, the role sees nothing: the default is closed.

> **First-principles note — "who is the database user, and how does it know the app user?"** The database has *roles* (logins). The API connects as one role for every request; to Postgres, user A and user B are indistinguishable, because they are both the same connection. A policy needs to know which app user is asking, so each statement must carry that fact in. Postgres has a mechanism for that: a **custom setting** such as `app.user_id`, set with `set_config('app.user_id', '<uuid>', true)`. The third argument, `true`, makes it **transaction-local**: it lasts until the current transaction ends and then vanishes, so a pooled connection cannot carry A's id into B's next request. Policies read it with `current_setting('app.user_id', true)`. If nobody set it, the policy sees an empty value, matches no row, and the statement returns nothing: **fail closed**.

> **First-principles note — "ownership and `BYPASSRLS`: why the API cannot use the login that owns the tables".** In Postgres a table's *owner* (the role that created it, here the migration login) is exempt from the table's RLS policies unless the table is also set to `FORCE ROW LEVEL SECURITY`. A *superuser*, and any role with the `BYPASSRLS` attribute, are exempt always. So RLS protects the API only if the API connects as a role that is none of those: not the owner, not a superuser, no `BYPASSRLS`, and not able to `SET ROLE` into one that is. That is why this spec creates a second, restricted login (`sin_app`), keeps the original for migrations and maintenance, and makes the API refuse to start if its login could bypass the policies (§6.8).

> **First-principles note — "composite foreign keys and denormalized ownership".** `set_entry` has no `user_id`: it belongs to a user through `workout_exercise` → `workout`. A policy on it would have to ask "does the parent workout belong to the current user?" for every row, a join per row. The alternative is to store `user_id` on every child row too (**denormalize**) and make the database prove the copy is right with a **composite foreign key**: `FOREIGN KEY (workout_id, user_id) REFERENCES workout (id, user_id)`. The parent must expose a unique key on `(id, user_id)`; then no child can exist whose `user_id` disagrees with its parent's. The policy becomes the same cheap `user_id = …` test on every table, and the database also guarantees the whole parent→child tree has one owner.

### In scope (four phases, four PRs)

- **Phase A — ownership in the child tables.** Migration `0019`: `user_id` on eight child tables, filled by a trigger and backfilled, composite foreign keys, unique `(id, user_id)` keys on the parents. No behavior change; the previous release still works. `ownership.ts` (21.0) simplified to direct predicates.
- **Phase B — "who is asking" on every call.** A scoped database handle (`createScopedDb`) and its adoption in all 13 repository files; the account export's read-only transaction moved into the handle; user provisioning keyed on `auth_sub`. The setting is set but nothing reads it yet, so it runs on today's owner login unchanged.
- **Phase C — the restricted login, grants, inert policies, the boot refusal.** Migration `0020` (role `sin_app` without login, grants, policy functions, policies; RLS not yet enabled), the `OWNER_DATABASE_URL` split for every maintenance command, the boot-time login check, `db:app-role`, the local-compose and Testcontainers setup, the HTTP-level tests moved onto `sin_app`.
- **Phase D — enable RLS and prove it.** Migration `0021` (`ENABLE ROW LEVEL SECURITY` on all 19 tables), the policy suite, the table-inventory test, the kill switch, the staging rollout, the performance gate, and the production runbook changes.

### Non-goals

- Sharing between users or any visibility rule beyond "your own rows" (the social phase is not planned).
- Per-user encryption at rest or field-level encryption.
- Changing Auth0, token verification, or the `404`-not-`403` contract.
- Protecting against someone who holds the database **owner** login (they can do anything; the login is kept for migrations and maintenance only).
- Protecting against SQL injection that lets an attacker run arbitrary statements as `sin_app`: such a statement can set `app.user_id` itself. RLS here guards against *the application forgetting a filter*, not against the application being made to run attacker-chosen SQL (§7).
- Rewriting the repositories away from raw SQL.
- Database-level ownership of cross-links to shared or foreign rows (`exercise_id` and friends), beyond what the composite keys give the parent→child tree (§6.6, D8).

### Anti-goals (a failure even if it "works")

- **A bypass the API can use:** a restricted login that is a superuser, has `BYPASSRLS`, owns a table, or can `SET ROLE` to one that does makes layer 3 decorative. The boot check refuses these (AC24–AC27).
- **A layer that only works in tests, or only in production.** Staging, production, local development and the integration tests run under the same rules and the same restricted login (AC30, AC31).
- **Failing open.** A missing "who is asking" returns no rows; it never means "no filter" (AC21–AC22).
- **Silent data loss.** A policy that wrongly hides a user's own data looks like data loss. Spec 21.0's positive controls and this spec's policy suite catch "can't see your own data" as well as "can see someone else's".
- **A slow gym.** Spec 16's threshold (set-save p95 under 2 s at 150 lifters) still holds with RLS on and is measured on staging, not assumed (AC38).

### Fit for one work session

It is not; it is four. **Phase A** AC1–AC8 (one migration, one trigger family, helpers). **Phase B** AC9–AC20 (the largest by lines, mechanical: 13 repository files and their helper modules, behavior-identical and protected by 21.0's suite). **Phase C** AC21–AC31 (role, grants, boot check, plumbing, tests). **Phase D** AC32–AC41 (the switch-on, tests, runbook, measurement). Each phase is deployable and rollback-able alone; B and C can proceed in either order after A but are listed in the order that keeps staging's manual steps simplest (§11).

## 2. Acceptance criteria

Behavioral criteria are named in tests as `AC<n> — …`. Verification method in brackets; §10 maps each.

### Phase A — ownership in the child tables (migration `0019`)

1. **Every child row has the right owner.** After `0019`, `user_id` is `NOT NULL` on `workout_exercise`, `workout_section`, `set_entry`, `workout_planned_set`, `workout_section_round`, `routine_item`, `routine_section` and `routine_item_set`, and for every row it equals the root table's `user_id` reached through the parent chain. The consistency query returns 0 rows on a seeded database and on staging after the manual apply. [integration; manual on staging]
2. **Inserts that do not mention `user_id` still work.** A `BEFORE INSERT` trigger on each child table sets `user_id` from its parent when the statement leaves it NULL; every existing fixture and repository INSERT is unchanged and passes. [integration]
3. **A wrong `user_id` is refused by the database.** Inserting a child with a `user_id` that differs from its parent's fails with a foreign-key violation (`23503`); so does updating a child's parent reference to a row of another user. [integration]
4. **Composite foreign keys replace the single-column ones** for the eight parent→child links and keep `ON DELETE CASCADE`: deleting a workout, a routine, or a user removes its whole tree; the existing purge, delete and replace tests pass unchanged. [integration]
5. **Expand-only and backward-compatible.** `0019` adds columns, keys, triggers and constraints and drops only the eight superseded single-column foreign keys (replaced in the same migration after validation); the **previous release's code and the whole existing integration suite run unchanged** against the migrated schema. [integration; CI]
6. **`schema.prisma` matches.** The eight models gain `userId` (`@map("user_id") @db.Uuid`) without a relation; `prisma generate` and the OpenAPI drift check pass; the hand-authored SQL carries the composite keys (the schema comment says so). [CI-pipeline]
7. **Spec 21.0's ownership helpers are direct.** `ownership.ts` helpers now expand to `<table>.user_id = $acting`; every caller is unchanged; the 21.0 suite, the weak-spot tests and the audit (its fingerprints regenerate with `--write`) pass. [integration; unit]
8. **No latency regression.** The five benches (`bench:finish`, `:history`, `:progress`, `:exercise-usage`, `:hevy-import`) rerun after Phase A; none regresses its recorded figure by more than 10% (the trigger and the second index cost something small on insert). Recorded in §12. [manual]

### Phase B — "who is asking" on every call

9. **One handle, two entry points.** `createScopedDb(prisma)` returns `{ as(userId), forAuthSub(authSub), shared() }`. `as` and `forAuthSub` return a `ScopedClient` with `$queryRaw`, `$executeRaw` and `$transaction`; `shared()` returns an unscoped client for statements on shared reference tables and statements that read no table. A malformed user id (not a `UserId`) throws before any database call. [unit]
10. **A bare scoped call is one short transaction.** A scoped `$queryRaw` / `$executeRaw` issues, in order on one connection, `BEGIN`, `SELECT set_config('app.user_id', $1, true)`, the statement, `COMMIT`; observed through Prisma query events. The statement's result and its error shape (including the raw unique-violation detection of `pg-errors.ts`) are identical to a bare call on the root client. [integration]
11. **A scoped `$transaction` sets the user once, first.** The callback receives the ordinary transaction client; the first statement after `BEGIN` (and after the isolation and read-only statements, when requested) is `set_config`; helper modules that take a `RawClient` are unchanged. Options `isolationLevel`, `readOnly`, `maxWait` and `timeout` are honored. [integration]
12. **The setting never outlives its transaction.** On a pool of one connection, after any scoped call returns, `current_setting('app.user_id', true)` on that connection is empty; the same after a rollback and after an error thrown inside the callback. [integration]
13. **No cross-talk under concurrency.** 200 interleaved scoped calls for 10 users on a pool of 2 connections each read `current_setting('app.user_id', true)` inside their own statement and always see their own id. [integration]
14. **All repositories use the handle.** `UserRepository`, `ExerciseRepository`, `WorkoutRepository` (with its set, section, history and retime modules), `RoutineRepository`, `PersonalRecordRepository`, `AccountExportRepository`, `HevyRepository`, `HevyImportRepository` and the helpers they share (`withWriteMode`, `lockUserRecords`, `rebuildUserRecords`, `sweepExpiredOneOffs`) take a `UserScopedDb` (or a `ScopedClient` / `RawClient` derived from it) and call `.as(actingUserId)` as the first line of each method; no file under `src/repositories`, `src/auth`, `src/records` (the library functions) or `src/account` (the library functions) calls `$queryRaw`, `$executeRaw` or `$transaction` on a `PrismaClient`. Factories also accept a bare `PrismaClient` (treated as unscoped) so tests and maintenance scripts that pass the owner client keep working. [unit (static scan + types); integration]
15. **Provisioning is keyed on the token's `auth_sub`.** `findByAuthSub`, `provision` and the re-read run on `forAuthSub(authSub)`; `syncEmail`, `updateProfile` and `markDeleted` run on `as(userId)`; the five Prisma model calls in `user.prisma.ts` become scoped raw statements with identical results. [integration]
16. **Shared reads use `shared()`.** `listMuscleGroups`, `listEquipment` and the reference validation in `exercise.prisma.ts` (the `Promise.all` pair) use `shared()` and run one statement each; the audit (21.0) classifies exactly the statements invoked on `shared()` as *shared on purpose* and none other. *(As built: `shared()` also carries the operator scripts' two cross-user listings, and the guard pins the call sites instead; see §12, "Phase B, as built".)* [unit]
17. **The export keeps its guarantees.** `AccountExportRepository.snapshot` runs on `as(userId).$transaction(fn, { isolationLevel: "RepeatableRead", readOnly: true })`; its AC7 probe from Spec 11 (a write inside fails `25006`, one snapshot) passes unchanged. [integration]
18. **Behavior parity.** With the handle in place and the database login still the owner, every existing unit and integration test and Spec 21.0's suite pass unchanged; no response differs. [integration; CI]
19. **Statement counts are recorded.** For the set-save, workout-detail, history-page and `resolveUser` paths, the number of database statements per request before and after Phase B is measured and recorded in §12 (expected: +3 per bare call, +1 per transaction). [manual]
20. **Server wiring.** `server.ts` constructs every repository from `createScopedDb(prisma)`; a unit test asserts it (an import-level check that the composition root passes no bare client to a repository factory). [unit]

### Phase C — the restricted login, grants, inert policies, the boot refusal

21. **Fail closed.** Connected as `sin_app` with RLS enabled on a table and `app.user_id` unset, set to `''`, or set to another user, `SELECT` returns no row of any other user, and `INSERT` / `UPDATE` / `DELETE` of another user's data affect or create nothing; a non-UUID value raises an error rather than returning rows. (Phase C proves this by enabling RLS per table inside the test; Phase D proves it on the migrated schema.) [integration]
22. **Grants are exactly the allow-list of §6.7.** `sin_app` cannot create objects in `public`, cannot read `_prisma_migrations`, cannot `DELETE` from `"user"` or `"exercise"`, cannot `UPDATE` `muscle_group` / `equipment`, cannot update `exercise.owner_user_id`, `exercise.id` or `exercise.catalog_key`, cannot update `"user".id` or `"user".auth_sub`; it is a member of no other role, and `SET ROLE` to the owner login or any `BYPASSRLS` role fails. [integration]
23. **The role migration is safe to repeat.** `0020` creates `sin_app` only if absent (`NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`), `REVOKE ALL` then re-`GRANT`s, and applies cleanly on a database where the role already exists (Prisma shadow databases, test containers, a second run in a fresh database of the same cluster). [integration]
24. **The boot check refuses a bypass-capable login.** `assertLoginCannotBypassRls(prisma)` throws a `ConfigError` subclass naming the problem (not the URL, not a password) when the current login: is a superuser; has `BYPASSRLS`; owns any ordinary table in `public`; or is a member (directly or through other roles) of a role that does any of these. Each of the four cases, and a clean `sin_app`, is exercised against real roles. [integration]
25. **The check runs before the server listens.** `server.ts` calls it after `createPrisma` and before `app.listen`; started with an owner or superuser URL, the process exits with code 1 within 25 s, prints the one-line reason, and never binds its port. [integration: spawn the real entry point]
26. **Connectivity is not a verdict.** If the database cannot be reached, the check retries with backoff for up to 20 s and then fails; a definite "unsafe login" verdict fails immediately without retry. [unit with a fake client]
27. **No opt-out, no owner URL on the API.** There is no environment variable that skips the check. If `OWNER_DATABASE_URL` is set in the API's environment, `loadConfig` fails with a `ConfigError` (the API must never hold the owner credential). [unit]
28. **Maintenance commands use only `OWNER_DATABASE_URL`.** `db:migrate:deploy`, `db:migrate:status`, `seed:catalog`, `records:rebuild`, `account:purge` and `scripts/check-migrate-status.ts` read `OWNER_DATABASE_URL` and never `DATABASE_URL`; if only `DATABASE_URL` is set they exit 1 with a message that says which variable to set and why. The `deploy-prod` workflow maps its existing `DATABASE_URL_PROD` secret to `OWNER_DATABASE_URL`, and `scrubDatabaseUrl` scrubs both variable names. [unit; CI-pipeline]
29. **`db:app-role` sets the login.** `pnpm --filter @sin/api run db:app-role` (owner URL; password from `APP_ROLE_PASSWORD` or a prompt) gives `sin_app` `LOGIN` and the password, prints the role's flags and `pg_auth_members` (both must be clean), never prints the password, and is idempotent. [integration]
30. **Tests run as `sin_app`.** `startIntegrationDb()` creates the login with a fixed test password and exposes `db.app` (a `PrismaClient` on `sin_app`) beside the superuser `db.prisma`. All 19 integration files that call `buildApp(` and Spec 21.0's `makeCrossUserApp` use `db.app`; a unit test lists the files that call `buildApp(` and fails on any that does not (with a reasoned allow-list, empty at this commit). Fixtures, truncation and the remaining repository-level integration files keep the superuser. [unit; integration]
31. **Local development uses the same login.** `apps/api/.env.example` lists `DATABASE_URL` (`sin_app`) only, and a new `apps/api/.env.owner.example` lists `OWNER_DATABASE_URL` (loaded by the maintenance scripts, never by `dev`, so the API's own environment never holds it); `docker-compose.yml`'s `api` service passes the owner URL inline to its migrate and `db:app-role` commands only (not in the service's `environment`), runs `db:app-role` with a fixed local password, then starts the API on `sin_app`; `pnpm --filter @sin/api run dev` on a database with no `sin_app` login stops at the boot check with the message that points to `db:app-role`. ## 4. Data model

### 4.1 Tables and what protects each

19 application tables (plus `_prisma_migrations`, which `sin_app` cannot touch):

| Table | Class | Policy shape (for `sin_app`) |
|---|---|---|
| `user` | identity | select own id **or** the token's `auth_sub`; insert only for the token's `auth_sub`; update own row; no delete |
| `exercise` | shared + owned | select NULL-owner or own; insert own; update (`USING` visible, `WITH CHECK` own) on an allow-listed column set; no delete |
| `muscle_group`, `equipment` | shared | select all; no write |
| `workout`, `routine`, `personal_record`, `hevy_exercise_pair`, `hevy_section_rule`, `hevy_link`, `hevy_account` | owned (have `user_id`) | all commands: `user_id = current user` |
| `workout_exercise`, `workout_section`, `set_entry`, `workout_planned_set`, `workout_section_round`, `routine_item`, `routine_section`, `routine_item_set` | owned child (get `user_id` in Phase A) | all commands: `user_id = current user` |

### 4.2 Migration `0019_child_table_owner` (Phase A, expand-only)

Order matters (parents first; triggers before backfill, so rows inserted by the running API during the migration are filled too). Illustrative SQL; the builder generates the eight repetitions in a loop at migration-writing time (the stored functions are static and plain, so their plans stay cached):

```sql
-- 1. the column (nullable: metadata-only, instant)
ALTER TABLE "workout_exercise" ADD COLUMN "user_id" uuid;      -- ... and the other seven

-- 2. the fill trigger (one small function per child; parent chosen at write time, no dynamic SQL)
CREATE FUNCTION workout_exercise_fill_user() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.user_id IS NULL THEN
    SELECT w.user_id INTO NEW.user_id FROM "workout" w WHERE w.id = NEW.workout_id;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER workout_exercise_fill_user BEFORE INSERT ON "workout_exercise"
  FOR EACH ROW EXECUTE FUNCTION workout_exercise_fill_user();

-- 3. backfill, parents before children (workout_exercise, workout_section; then set_entry,
--    workout_planned_set, workout_section_round; routine_item, routine_section; then routine_item_set)
UPDATE "workout_exercise" we SET user_id = w.user_id FROM "workout" w
 WHERE w.id = we.workout_id AND we.user_id IS NULL;

-- 4. the parents expose (id, user_id) so a child can point at the pair
ALTER TABLE "workout" ADD CONSTRAINT "workout_id_user_key" UNIQUE ("id", "user_id");
--    also routine, workout_exercise, workout_section, routine_item

-- 5. composite FK: add NOT VALID, validate (no long lock), then drop the superseded single-column FK
```

The eight links: `workout_exercise.workout_id`, `workout_section.workout_id`, `set_entry.workout_exercise_id`, `workout_planned_set.workout_exercise_id`, `workout_section_round.workout_section_id`, `routine_item.routine_id`, `routine_section.routine_id`, `routine_item_set.routine_item_id`. Five parents gain a `(id, user_id)` unique key: `workout`, `routine`, `workout_exercise`, `workout_section`, `routine_item`. Left alone: the `ON DELETE SET NULL` section links (`workout_exercise.section_id`, `routine_item.section_id`), `workout.routine_id`, `hevy_link.workout_id`, and every `exercise_id` (D8).

**Consistency query** (AC1; run in tests and by hand on staging) — each returns zero rows:

```sql
SELECT 'workout_exercise' AS t, count(*) FROM "workout_exercise" we JOIN "workout" w ON w.id = we.workout_id WHERE we.user_id IS DISTINCT FROM w.user_id
UNION ALL SELECT 'set_entry', count(*) FROM "set_entry" se JOIN "workout_exercise" we ON we.id = se.workout_exercise_id WHERE se.user_id IS DISTINCT FROM we.user_id
-- ... one line per child
```

**Cost on staging Neon.** `ADD COLUMN` takes `ACCESS EXCLUSIVE` for an instant; the backfill `UPDATE` rewrites every child row once (MVCC bloat is reclaimed by autovacuum); with the owner's current data (thousands of sets) it is seconds. Count `set_entry` first; if it exceeds ~500,000 rows, split the backfill by id range (not expected). Production is empty when this runs. Row cost afterwards: 16 more bytes per child row and one extra small index on each of five parents.

### 4.3 Migration `0020_app_role_and_policies` (Phase C, inert)

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'sin_app') THEN
    CREATE ROLE sin_app NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
  END IF;
END $$;

REVOKE ALL ON ALL TABLES IN SCHEMA public FROM sin_app;
GRANT USAGE ON SCHEMA public TO sin_app;                     -- not CREATE

-- policy helpers: one definition of the setting names and of "empty means no user"
CREATE FUNCTION app_user_id() RETURNS uuid LANGUAGE sql STABLE PARALLEL SAFE
  AS $$ SELECT nullif(current_setting('app.user_id', true), '')::uuid $$;
CREATE FUNCTION app_auth_sub() RETURNS text LANGUAGE sql STABLE PARALLEL SAFE
  AS $$ SELECT nullif(current_setting('app.auth_sub', true), '') $$;
GRANT EXECUTE ON FUNCTION app_user_id(), app_auth_sub() TO sin_app;

-- owned tables (the pattern, repeated for the 15 with a user_id column):
GRANT SELECT, INSERT, UPDATE, DELETE ON "workout" TO sin_app;
CREATE POLICY workout_own ON "workout" TO sin_app
  USING      (user_id = (SELECT app_user_id()))
  WITH CHECK (user_id = (SELECT app_user_id()));

-- user: identity, no delete, no id / auth_sub change
GRANT SELECT, INSERT ON "user" TO sin_app;
GRANT UPDATE (email, email_verified, display_name, unit_preference, timezone, updated_at, deleted_at) ON "user" TO sin_app;
CREATE POLICY user_select ON "user" FOR SELECT TO sin_app
  USING (id = (SELECT app_user_id()) OR auth_sub = (SELECT app_auth_sub()));
CREATE POLICY user_insert ON "user" FOR INSERT TO sin_app
  WITH CHECK (auth_sub = (SELECT app_auth_sub()));
CREATE POLICY user_update ON "user" FOR UPDATE TO sin_app
  USING (id = (SELECT app_user_id())) WITH CHECK (id = (SELECT app_user_id()));

-- exercise: shared NULL-owner rows readable and lockable by all; changes only to own rows
GRANT SELECT, INSERT ON "exercise" TO sin_app;
GRANT UPDATE (name, modality, primary_muscle_id, secondary_muscle_ids, equipment_id, is_active, updated_at /* + exactly the columns the API's UPDATE statements SET */) ON "exercise" TO sin_app;
CREATE POLICY exercise_select ON "exercise" FOR SELECT TO sin_app
  USING (owner_user_id IS NULL OR owner_user_id = (SELECT app_user_id()));
CREATE POLICY exercise_insert ON "exercise" FOR INSERT TO sin_app
  WITH CHECK (owner_user_id = (SELECT app_user_id()));
CREATE POLICY exercise_update ON "exercise" FOR UPDATE TO sin_app
  USING      (owner_user_id IS NULL OR owner_user_id = (SELECT app_user_id()))   -- lets FOR SHARE lock a global row
  WITH CHECK (owner_user_id = (SELECT app_user_id()));                           -- but a write must stay own

-- shared reference data
GRANT SELECT ON "muscle_group", "equipment" TO sin_app;
CREATE POLICY muscle_group_read ON "muscle_group" FOR SELECT TO sin_app USING (true);
CREATE POLICY equipment_read    ON "equipment"    FOR SELECT TO sin_app USING (true);
```

Notes that are load-bearing:

- **`(SELECT app_user_id())` and `nullif(…,'')`.** Wrapping the call in `(SELECT …)` makes Postgres evaluate it once per statement instead of once per row. `nullif(…,'')` handles a quirk: after a transaction-local `set_config` ends, the setting reads back as the empty string (not NULL) on that connection; casting `''` to uuid would raise, so it is mapped to NULL and the policy matches nothing.
- **Why the `exercise` update policy has two conditions.** In Postgres a row lock (`SELECT … FOR SHARE` / `FOR NO KEY UPDATE`) must pass the table's `UPDATE` policy `USING` as well as its `SELECT` policy. The Hevy import locks catalog rows `FOR SHARE`, so the `UPDATE` policy's `USING` must let a global row through. A real `UPDATE` of that row is then stopped twice over: `WITH CHECK` fails because the new row's owner is still NULL, and `owner_user_id` is not in the column grant, so it cannot be set to the caller either.
- **Why `user` has an `auth_sub` branch.** User provisioning runs before an id exists (the request carries only the verified token's `sub`); the handle's `forAuthSub` sets `app.auth_sub` and nothing else, and these two branches are the only way a row is visible or insertable without `app.user_id`.
- **Column grants.** `UPDATE (cols)` is checked against the columns named in the statement's `SET`; trigger-assigned columns (`exercise.change_xid`) are unaffected. A row lock needs `UPDATE` on at least one column, which `user` and `exercise` have. The builder fixes the `exercise` column list to exactly what the API's `UPDATE "exercise" SET …` statements write (3 statements), and AC22 pins it.
- **No default privileges.** `ALTER DEFAULT PRIVILEGES` is not used, so a future table is invisible to `sin_app` until its migration grants and polices it; AC33 fails CI otherwise.
- **Sequences.** None (all primary keys are application-generated UUIDs).

## 6. Behavior & logic

### 6.1 How "who is asking" reaches every statement (decided: D1)

The facts the design must fit: the one shared `PrismaClient` (`db.ts`, `server.ts`); Prisma 6.19 forbids nested interactive transactions; ~186 raw statements, most of them bare (no transaction); about 20 interactive transactions with deliberate lock order (`withWriteMode`, the PR lock, `FOR SHARE` then `FOR UPDATE`); one `Promise.all` of two parallel reads (the exercise reference validation); the export's `REPEATABLE READ` + `READ ONLY` transaction; an 8-connection pool; and `resolveUser` running a lookup by `auth_sub` on every request. One fact helps enormously: **every repository method already receives `actingUserId`** as an explicit argument.

**Chosen: an explicit scoped handle, obtained per repository call from that argument.** Each method starts with `const db = scoped.as(actingUserId)` and uses `db.$queryRaw` / `db.$executeRaw` / `db.$transaction`, exactly as it used the client before. Inside, the handle does:

- **Bare statement:** `prisma.$transaction([ set_config('app.user_id', id, true), statement ])`, Prisma's sequential batch form (one connection, `BEGIN` … `COMMIT`). Cost: 4 database statements instead of 1.
- **Interactive transaction:** `prisma.$transaction(async (tx) => { [SET TRANSACTION READ ONLY]; set_config(...); return fn(tx) }, opts)`. The callback gets the ordinary `tx`, so every helper that takes a `RawClient` (the large majority of SQL lives in such helpers) is untouched, and lock order is exactly today's with one cheap statement added in front. Cost: +1 statement.
- **Shared statement:** `shared()` returns the root client for the two shared reference tables and for statements that read no table (`SELECT 1`, advisory locks); no transaction, no setting. The audit (21.0) restricts what may be called on it.

Why per call and not per request: a request often needs several transactions with different isolation and lock needs, and Prisma cannot nest them; one request-wide transaction would change lock durations (advisory and row locks held until the request ends) and the carefully ordered locking. Per-call keeps each unit of work as it is.

**Rejected alternatives**

1. **One transaction per request** (open at the auth hook, close at the response). Prisma 6 has no nested interactive transactions; emulating with `SAVEPOINT` changes when `pg_advisory_xact_lock`, `FOR UPDATE` and `FOR SHARE` locks are released and breaks the documented lock order. High risk, large blast radius.
2. **A Prisma client extension (`$extends`, `query.$allOperations`).** It is built for model operations; the statements here are raw, and inside an interactive transaction the extension would run per operation without a place to put a single `set_config`. It also needs a per-request extended client (or ambient state) to know the user. More magic than the explicit handle for no gain.
3. **`AsyncLocalStorage` ambient user.** Hidden global state at a security boundary; if the context is lost across an `await` boundary the symptom is "no rows" (fail closed but baffling), and it creates two sources of truth next to the explicit `actingUserId` the SQL already uses.
4. **Session-level `set_config(…, false)` when a connection is checked out.** Pooled connections are reused across users; one missed reset serves A's connection to B. Exactly the failure layer 3 exists to prevent.
5. **A database role per user with `SET LOCAL ROLE`.** Unbounded role count, a grant per user, a migration burden. No.
6. **`SECURITY DEFINER` functions as the data access path.** The classic RLS-bypass footgun (`search_path`, owner privileges), invisible to the boot check, and a rewrite of 186 statements.
7. **Driver adapter with a connection hook (`@prisma/adapter-pg`).** Would cut the per-statement overhead to one setup per checkout, but replaces the query engine and the error shapes `pg-errors.ts` parses, for the whole app. Kept as the escape hatch if the performance gate fails (§6.11), not the first move.

**The compile-time guard.** Repository factories take a `UserScopedDb`; its `as()` is the only way to a client with `$queryRaw`. A repository method that reaches for a client without scoping does not type-check. A factory also accepts a bare `PrismaClient` (`toScoped` wraps it as unscoped) so the ~71 repository-level integration files and the maintenance scripts, which run on the owner login where RLS does not apply, are untouched; `server.ts` passes only the scoped handle (AC20).

### 6.2 What changes in the repositories

Mechanical, per file, protected by 21.0's suite and the existing tests:

- Replace the factory's `prisma: PrismaClient` with `db: UserScopedDb | PrismaClient`, and inner helpers that closed over `prisma` with a `client` parameter (many already have one).
- Each public method: `const c = db.as(actingUserId)` first; all `prisma.` in the body become `c.`.
- Helpers shared across modules (`withWriteMode`, `lockUserRecords`, `rebuildUserRecords`, `workoutPreflight`, `sweepExpiredOneOffs`, `readWorkoutDetail`) take `ScopedClient | RawClient`; the maintenance scripts pass the owner `PrismaClient`.
- `user.prisma.ts`: the five Prisma model calls (`findUnique`, `update`) become scoped raw statements with the same columns and mapping; nothing else in it needs a model.
- `exercise.prisma.ts`: `validateReferences`'s `Promise.all` runs on `shared()` (two single-statement reads on shared tables, no transaction, no extra connection pressure); `listMuscleGroups` / `listEquipment` on `shared()`.
- `account-export.prisma.ts`: `as(userId).$transaction(fn, { isolationLevel: "RepeatableRead", readOnly: true })`; the in-body `SET TRANSACTION READ ONLY` moves into the handle. Order inside the handle is: Prisma's `BEGIN` + isolation, `SET TRANSACTION READ ONLY`, then `set_config` (the first data-reading statement, so the snapshot is taken after both), then the repository's statements. `READ ONLY` stays ahead of the first query, as Spec 11 D7 requires, so the snapshot semantics it describes do not change; the AC17 probe verifies it.

### 6.3 Provisioning and `resolveUser`

`resolveUser` (`auth/provisioning.ts`) calls `repo.findByAuthSub(sub)` on every request, then maybe `provision`, then maybe `syncEmail`. With the handle: `findByAuthSub` and `provision`'s insert and re-read run on `forAuthSub(sub)` (sets `app.auth_sub` only); `syncEmail`, and everything after authentication, run on `as(user.id)`. The `user` policies of §4.3 make exactly this possible: a row is visible by its `auth_sub` to the token's holder, insertable only for that `sub`, and updatable only by its own id.

**Cost to flag.** `findByAuthSub` is the one bare read every request makes, so it goes from 1 to 4 statements per request. It is the first lever if the gate fails (§6.11).

### 6.4 The boot refusal (decided: D5)

`assertLoginCannotBypassRls(prisma)` in `db/login-check.ts`, called by `server.ts` between `createPrisma(config)` and `buildApp`/`listen`, with the pool's own connection (so it checks the login the API will actually use). It runs two catalog queries:

```sql
-- the login itself
SELECT r.rolname, r.rolsuper, r.rolbypassrls,
       EXISTS (SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
               WHERE n.nspname = 'public' AND c.relkind IN ('r','p') AND c.relowner = r.oid) AS owns_table
FROM pg_roles r WHERE r.rolname = current_user;

-- any role it could SET ROLE into (member directly or through other roles; INHERIT does not matter for SET ROLE)
SELECT r.rolname, r.rolsuper, r.rolbypassrls,
       EXISTS (SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
               WHERE n.nspname = 'public' AND c.relkind IN ('r','p') AND c.relowner = r.oid) AS owns_table
FROM pg_roles r
WHERE r.rolname <> current_user AND pg_has_role(current_user, r.oid, 'MEMBER')
  AND (r.rolsuper OR r.rolbypassrls OR EXISTS (… owns a table …));
```

It also asserts `current_setting('row_security') = 'on'` (a login configured with `row_security = off` would make RLS raise errors instead of filtering). Any hit throws `UnsafeDatabaseLoginError` (a `ConfigError`, so `startupFailureMessage` prints the message alone, no stack): *"Refusing to start: the database login "<role>" can bypass row-level security (<reason>). The API must connect as the restricted application login (see docs/runbooks/first-deploy.md, RLS rollout). Maintenance commands use OWNER_DATABASE_URL."* The message names the role and the reason, never the URL or password.

- **Connectivity vs verdict.** A connection error is retried with backoff for up to 20 s (below Cloud Run's 30 s startup budget in Spec 15, so a Neon wake-up does not turn into a crash loop), then the process fails; a definite verdict fails at once.
- **Tension with Spec 15, flagged.** Spec 15 chose a startup probe on `/healthz` precisely so a database wake-up could not fail startup. Checking before `listen` (the owner's decision) reintroduces a database dependency at boot; the bounded retry is the compromise.
- **No opt-out.** No flag, no environment variable. Local development and tests use the restricted login too (AC31). Accepted cost, the owner's: a mis-set secret means downtime until fixed; the deploy fails visibly, and the staging post-deploy smoke goes red instead of layer 3 being silently off.
- **What it deliberately does not check:** whether RLS is *enabled* on the tables. The rollout and the kill switch need windows where it is off while the API runs; that state is verified by the table-inventory test (AC33), by `db:rls status`, and in production by `deploy-prod`'s migration-status gate (it refuses a release while a migration, including `0021`, is unapplied).

### 6.5 Provisioning the login, and Neon's trap

The role is created by migration `0020` as `NOLOGIN` (a migration cannot hold a password). `db:app-role` then runs `ALTER ROLE sin_app WITH LOGIN PASSWORD …` over the owner login, passing the password as a bound value through `set_config` and `format('%L', …)` (never string-built), and prints the role's flags and `pg_auth_members`.

> **Neon-specific trap.** Roles created in the Neon Console, API or CLI are automatically made members of `neon_superuser`, which carries `BYPASSRLS` (and `CREATEROLE`, `CREATEDB`). A `sin_app` created there would silently be a bypass-capable login. It must be created **with SQL** (this migration), and the runbook verifies `pg_auth_members` is empty for it. The boot check catches a mistake: the "can `SET ROLE` into a bypass role" branch fires. (Neon documents the Console/CLI/API membership rule at <https://neon.tech/docs/manage/roles>; roles created by plain SQL are not covered by the docs, so the runbook checks rather than assumes.) The Neon *owner* login is a member of `neon_superuser` and so bypasses RLS: correct for migrations and maintenance, wrong for the API.

### 6.6 Child-table policies: denormalize `user_id` (decided: D7)

The question: policies on the eight child tables either (a) ask the parent per row, `EXISTS (SELECT 1 FROM workout_exercise we JOIN workout w … WHERE we.id = set_entry.workout_exercise_id AND w.user_id = current)`, or (b) test a `user_id` column stored on the child, made trustworthy by composite foreign keys.

| | (a) `EXISTS` via parent | (b) denormalized `user_id` + composite FK (**chosen**) |
|---|---|---|
| Policy cost on `set_entry` / `workout_planned_set` / `workout_section_round` / `routine_item_set` | 2 primary-key probes per candidate row (parent, grandparent), evaluated as a per-row sub-plan | one cheap comparison on the row itself |
| Cost on history, progress and PR-recompute reads | The 07.2 loader reads every working set of a lineage (thousands for a long-time lifter) through a join that already touches `workout` and `workout_exercise`; the policy adds its own probes on top, roughly tripling index work per set | none beyond the comparison |
| Migration | none (policies only) | `0019`: column, trigger, backfill, composite FKs, five parent keys |
| Backfill on staging Neon | none | seconds (thousands of rows); production empty |
| Expand-only | trivially | yes: add-only plus replacing eight FKs after validation; previous release unaffected (AC5) |
| Writer SQL changes | none | none (the trigger fills `user_id`; existing INSERTs and fixtures unchanged) |
| Database-level ownership of the parent→child tree | no | **yes**: a child with another owner than its parent is impossible (AC3) |
| Reversibility | policies are replaceable | the columns stay; policies can be rewritten to (a) at any time |
| Risk | per-row sub-plan cost is hard to predict on Neon's free compute | one more migration; triggers are hidden logic (the repo already has one, `exercise_change_xid`) |

**Decision: (b).** The deciding factor is timing, not elegance: production is empty *now*, so the backfill is free, while after launch it is a live migration on the largest tables; (a) can be adopted later as a fallback only by dropping a working design, whereas (b) can always fall back to (a)'s policies without undoing the columns. (b) also answers the brief's question "does it give database-level ownership of cross-links?" for the part of the graph it can: the whole parent→child tree. The trigger-fill keeps all writer SQL and all ~71 fixture-heavy test files unchanged: they insert rows without `user_id`, as the superuser, and the trigger completes them.

**Cross-links not covered (decided: D8).** `workout_exercise.exercise_id`, `routine_item.exercise_id`, `personal_record.exercise_id` and `hevy_exercise_pair.exercise_id` point at `exercise`, which is *either shared or owned*; a single foreign key cannot say "NULL owner or the same owner". Same-owner links (`workout.routine_id`, `hevy_link.workout_id`, `personal_record.workout_id`) could take a composite key with `ON DELETE SET NULL (col)`. Neither is needed for G3: with RLS on, a forged pointer to another user's row reveals nothing (the target is invisible, joins drop out) and the app checks plus 21.0's cases prevent creating one. They are deferred, listed as O2, to keep this spec from sprawling.

### 6.7 Grants and policies, exactly

Principle: `sin_app` gets the minimum the API's statements need, per table, found by reading every statement (21.0's audit lists them).

| Table | Privileges for `sin_app` |
|---|---|
| 15 owned tables with `user_id` (incl. the 8 children) | `SELECT, INSERT, UPDATE, DELETE` |
| `"user"` | `SELECT, INSERT`; `UPDATE (email, email_verified, display_name, unit_preference, timezone, updated_at, deleted_at)`; **no `DELETE`** (account deletion is soft: `deleted_at`; the hard purge is the owner's `account:purge`) |
| `"exercise"` | `SELECT, INSERT`; `UPDATE` on the columns the API writes; **no `DELETE`** (retire sets `is_active = false`); `owner_user_id`, `id`, `catalog_key` not updatable |
| `muscle_group`, `equipment` | `SELECT` |
| `_prisma_migrations` | none |
| schema `public` | `USAGE` only |

The 19 tables: `user`, `exercise`, `muscle_group`, `equipment`, and the 15 owned ones (7 with a `user_id` from the start: `workout`, `routine`, `personal_record`, `hevy_exercise_pair`, `hevy_section_rule`, `hevy_link`, `hevy_account`; 8 children). Policy names are `<table>_own` (owned), `user_select/insert/update`, `exercise_select/insert/update`, `<ref>_read`. All policies are `TO sin_app`, so they do not touch the owner or any other role.

**Referential-integrity checks are not subject to RLS.** The internal queries Postgres runs for foreign keys (the `KEY SHARE` lock a child insert takes on its parent or on an `exercise`) execute as the referenced table's owner and ignore RLS; no grant on the parent is needed beyond ordinary DML, and a child can reference an `exercise` row the caller could not otherwise see. That is why cross-links are a separate matter (D8).

**Unique-index probes.** Under RLS an `INSERT` that collides with an invisible row still raises a unique violation, which could reveal the row's existence. Every unique key in the schema either includes `user_id` (`workout (user_id, client_generated_id)`, `routine (user_id, lower(name))`, `hevy_link (user_id, hevy_workout_id)`) or is scoped to a parent the caller owns (`set_entry (workout_exercise_id, client_generated_id)`); the only global one is `user.auth_sub`, whose subject is the token's own `sub`. AC14 of Spec 21.0 tests the collisions end to end.

### 6.8 Maintenance commands and the owner login (decided: D4)

Every command that migrates or acts across users reads **`OWNER_DATABASE_URL`**, never `DATABASE_URL`:

- `db:migrate:deploy`, `db:migrate:status` go through `scripts/owner-env.mjs`, which runs the repo-pinned Prisma with `DATABASE_URL` set from `OWNER_DATABASE_URL` for the child process only, and exits 1 with *"set OWNER_DATABASE_URL to the owner login; DATABASE_URL is the application login and cannot migrate"* if it is unset.
- `seed:catalog`, `records:rebuild`, `account:purge`, `scripts/check-migrate-status.ts` read `OWNER_DATABASE_URL` (their existing `DATABASE_URL` reading and error text become the new variable's), and refuse a lone `DATABASE_URL`.
- The `bench:*` scripts start their own container, so they hold both logins in-process: fixtures as the owner, measurement through `sin_app`.
- `deploy-prod.yml` passes `OWNER_DATABASE_URL: ${{ secrets.DATABASE_URL_PROD }}` (the secret keeps its name and stays the owner's URL, read-only `migrate status`).
- **Why a new variable, not a convention.** After the switch, Render's and Cloud Run's `DATABASE_URL` is the `sin_app` URL. The CLAUDE.md commands today say "for Neon use the exact `DATABASE_URL` from Render", which would silently become the wrong login for a migration. A separate variable that the API refuses to hold (AC27) and the tools refuse to substitute (AC28) makes "which login" a property of the command, not of a runbook sentence. A useful side effect: **Cloud Run and Render never hold the owner credential**; a compromised runtime cannot migrate, drop, or bypass RLS.

Why no `FORCE ROW LEVEL SECURITY` (decided: D6): `FORCE` would subject the owner to the policies too, so every maintenance command and every data-backfilling migration would have to set a user id (the purge deletes across all users; `records:rebuild` reads all users; a migration backfill touches every row) or the owner would need an everything-allowed policy, which defeats the point. The case `FORCE` would guard — the API connecting as the owner again — is already stopped harder by the boot check (it refuses to start). The policies are `TO sin_app` so they cannot affect the owner either way.

### 6.9 Staging rollout order (expand-only; manual release steps)

The hazard in the brief: enabling RLS before the API's login has policies locks the running API out. The extra constraint found here: **Render auto-deploys on merge to `main`**, and the new code's boot check refuses the owner login. So the manual steps must precede the merges that need them. Order (each step ends with the staging smoke green; the memory rule "never `migrate dev` on Neon" applies throughout):

| Step | Action | Safe because |

### 6.11 The performance gate, and the levers if it fails

Spec 16 means the load-testing rework (`16-load-testing.md`; Phase A merged in #287, the staging and production runs are Phase B). The gate (AC38): a staging gym run before (S0) and after (S8); **set-save p95 under 2,000 ms at 150 lifters; N drops by no more than one step.** It blocks production's first real user, not the merges or the staging switch. If Spec 16 is not ready when Phase D is, the gate waits.

Expected cost: a bare read goes from 1 to 4 statements, a transaction gains 1. At Render-Oregon to Neon-Oregon (~1–2 ms round trip) that is single-digit milliseconds per request; the set-save path (a bare preflight, a bare replay lookup, the transaction) gains about 7 statements. **The staging measurement understates production**: Cloud Run is in `us-central1` and Spec 15 does not pin the production Neon project's region (O1). Each added statement costs a full round trip there, so choose the region deliberately.

**Levers, in the order to try if the gate fails** (each a separate, reviewed change): (1) pick the production Neon region nearest `us-central1`; (2) fold `resolveUser`'s lookup, or a handler's consecutive preflight reads, into one scoped call; (3) merge a bare preflight into the transaction that follows it where lock order allows (touches Spec 05.0's lock-order rules: needs its own review); (4) a short per-process cache of the `auth_sub` → user lookup (changes the deleted-account and email-sync windows: owner call); (5) the driver-adapter route of §6.1 rejected-alternative 7. The brief's wording stands: if set-save p95 nears 2 s, this spec revisits how the setting is attached.

## 7. Security & privacy

- **What layer 3 buys, and its edge.** With a non-owner, non-bypass login, a statement that forgets its `user_id` filter returns only the caller's rows, and a write that targets another user's row changes nothing or errors. It does **not** defend against an attacker who can run arbitrary SQL as `sin_app`: that statement can call `set_config('app.user_id', '<victim>', true)` itself. Every statement in the code base is a parameterized tagged template (21.0 AC19 bans `$queryRawUnsafe`, `$executeRawUnsafe` and `Prisma.raw` in `src`), which is the control for that class.
- **The login split is the point.** The API (and so a compromised runtime) holds only `sin_app`. The owner credential lives in the owner's password manager, the GitHub Environment secret `DATABASE_URL_PROD` and nowhere else; the API refuses to start if it is present (AC27).
- **The Neon Console trap** (§6.5): roles created there are `BYPASSRLS` members. The runbook says SQL only and verifies; the boot check is the backstop.
- **Fail closed everywhere:** unset, empty and garbage settings yield no rows or an error, never an unfiltered read (AC21). Policies name `TO sin_app`, so a role with no policy sees nothing once RLS is on.
- **No new data.** The new `user_id` copies are the same identifiers already in the parent rows; no health value, email or token moves. Logs gain no user data beyond the ids the request log already carries.
- **Secrets handling.** `APP_ROLE_PASSWORD` is read from the environment or a prompt, passed as a bound value, never logged, never in an error message, never in shell history in the documented flow (`read -s`). The boot-check message names the role, never the URL.
- **Error text.** `42501` messages from Postgres name the table and policy; the API's error serializer already stubs Prisma errors, and the request-logging masking of identifiers applies unchanged.
- **Static messages.** No Zod message is added (CLAUDE.md "Validation messages are static").

**Phase A, as built (2026-11-07):**

- **Migration `0019`** follows §4.2, with two additions.
  - It first takes every lock it needs in one statement (`SET lock_timeout = '5s'`, then `LOCK TABLE` in the API's write order: `routine`, `workout`, then each parent before its children). `prisma migrate deploy` runs the file as one transaction, so the locks are held to the commit either way; taking them first keeps the window for a lock conflict to that one statement. It can't close it: a read that names a child before its parent takes its locks in that order. The runbook's `0019` step says to pick a quiet minute and gives the `migrate resolve --rolled-back` recovery for any failed attempt.
  - A fill trigger that finds no parent raises `foreign_key_violation` (23503) itself, so an insert under a missing parent fails with the code it had before `0019`, not a `NOT NULL` 23502.
  - The `NOT VALID` → `VALIDATE` forms of §4.2 are kept although, inside one transaction, they save no lock time: they are the shape a split, by-hand apply needs (§4.2's 500,000-row fallback).
- **AC7's helpers** keep their `(actingUserId, ref)` signature and expand to `EXISTS (SELECT 1 FROM <child> own_x WHERE own_x.id = ${ref} AND own_x.user_id = $acting)`: one primary-key probe on the child's own column, no join, callers unchanged. `ownedSectionRound` is `ownedWorkoutSection` (a round's `ref` is its section id).
- **Three loaders outside `ownership.ts`** (21.0 deferred minor 396) also read the new column. `loadExercises` filters `workout_exercise.user_id`; `loadSetsForWorkout` and the History volume read (`loadWorkingSetRows`) filter the **workout exercise's** `user_id`, never `set_entry.user_id`, which has no index: a first version that filtered the set row doubled the Hevy import's slow batches (p95 770 ms), and filtering through the exercise is faster than `main`.
- **AC6 departure: `schema.prisma` declares the composite keys as relations.** AC6 said `userId` would carry no relation because Prisma couldn't express the key; it can. Each parent link is `@relation(fields: [<parent>Id, userId], references: [id, userId], …)` against the parent's `@@unique([id, userId])`, with `0019`'s key names. Left as single-column relations, the schema would describe the old keys, and the next migration generated by `migrate dev` or `migrate diff --script` would quietly drop the owner keys (code review). **Phase C, as built (2026-11-08):**

- **`db:app-role`** lives in `src/db/app-role-cli.ts` (library `app-role.ts`), with `scripts/db-app-role.ts` as its entry, the `records:rebuild` pattern, because compose runs it in the runtime image, which has no `tsx`. The password floor is 12 characters. `memberOf` reads only rows where `member = 'sin_app'::regrole`: Postgres 16 records a `CREATEROLE` creator as a member of the role it created, which is harmless and must not be reported or revoked.
- **The boot check's rejected login.** Prisma 6.19 raises `PrismaClientInitializationError` with no error code for all three cases: a wrong password or a role with no password ("Authentication failed against database server"), and a `NOLOGIN` role that has a password ("User was denied access on the database"). `DatabaseLoginRejectedError` therefore matches that text as well as `P1000` / SQLSTATE `28000` / `28P01`, and points at `db:app-role`; each is pinned against real Postgres. If an upgrade rewords it, or Neon's proxy words it differently, the check falls into the 20 s retry and then fails: slower, never unsafe. **Giving up** ends in one fixed line with the Prisma code or class (`DatabaseUnreachableError`), since Prisma's message names the host; the client's own `log` option still prints a `prisma:error` line per failed attempt, as for any database error. Beyond §6.4's connection errors, `P1008`, `P2024` (pool timeout) and SQLSTATEs `57P01`–`57P03` (a server restarting) are retried, and each attempt is bounded by the budget left, so a stalled connection cannot hang the boot past 20 s.
- **`db_login_checked`'s fields** are the `LoginFacts` names (`ownsTables`, and `memberOfBypass` as the list of roles), not §9's `owns_tables` and `member_of_bypass: false`: a list says which role, which is what a refusal needs.
- **`0020` takes its locks up front,** like `0019`, with a 5 s `lock_timeout`: `CREATE POLICY` holds `ACCESS EXCLUSIVE` on all 19 tables to the commit. A failed attempt changes nothing and clears with `migrate resolve --rolled-back` (runbook).
- **`owner-env.mjs` requires `sslmode=require&sslaccept=strict`, or `sslmode=disable` on a local host** (#8): the Prisma CLI reads the raw URL and treats any other `sslmode` as TLS optional, and B4 now takes the string from Neon rather than from Render. `check-migrate-status` runs through it too, so `deploy-prod` refuses a production secret without them. `.env.owner.example` carries no `APP_ROLE_PASSWORD`, so a run with a real owner URL exported can never set the repo's local password on it.

- **AC36 held with no code change.** The moment `0021` existed, the whole integration suite ran with RLS on: 109 files, 1,134 tests, including Spec 21.0's cross-user suite and its positive controls. No missed scope, grant or policy turned up, and no policy changed.
