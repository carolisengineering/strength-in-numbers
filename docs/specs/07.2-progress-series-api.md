## 1. Purpose, scope & non-goals

Ship the **progress series**: `GET /v1/progress/exercises/{id}?from=&to=` — for one
exercise (resolved through its fork lineage), one point per finished workout that
trained it, each point carrying the four numbers a chart needs (top-set weight, best
estimated 1RM, total volume, max reps). It is M2's last API piece; Spec 08 draws the
charts from it.

**Roadmap split (07.0 D1).** 07.0 PR engine (merged), 07.1 history list (merged),
**07.2 this**, 08 UI. **This spec replaces DESIGN §6's sketch** `?metric=est_1rm&from=&to=`
(owner decision, brainstorm 2026-10-07): one call returns every metric per point, so the
UI switches charts without a refetch and the API has no `metric` enum to grow.

**Dependencies, corrected.** README and 07.0 §12 D1 say 07.2 "needs only 05.1 and reuses
`estimate1rm`". It now needs **07.0** (the lineage loader, `records.ts`) and **07.1**
(`sumVolumeMilli`, merged), and does not call `estimate1rm` directly — it goes through
`setRecordValueMilli` (D2). README row and notes are updated (§11).

### In scope

- `GET /v1/progress/exercises/{id}?from=&to=` → `{ exerciseId, points }`.
- `@sin/core`: export `setRecordValueMilli` (the former private `candidate()`), add
  `progressPoints`; DTOs `ProgressPointSchema`, `ProgressSeriesSchema`,
  `ProgressQuerySchema` (`dto/progress.ts`).
- API: two extractions in `personal-record.prisma.ts` — `resolveVisibleRoot`,
  `loadLineageSets` — and `PersonalRecordRepository.getProgressSeries`; the route
  `routes/progress.ts`; the fake.
- Both public-surface inventory tests gain the route (§5).
- A one-off latency measurement (AC19).

### Non-goals

- **Bucketing** (weekly / monthly) — a client display choice; the API returns raw
  per-workout points.
- **Multi-exercise per call** — a chart is one exercise; the client issues N calls.
- **Bodyweight-relative metrics**, **duration / distance progress** — same deferrals as
  07.0 D2 (no `body_metric` table; no duration PR type). Such lineages return points
  whose metrics are all `null` (D7).
- **UI** (Spec 08). **Rollup table** (`exercise_daily_stat`, DESIGN §4.6 — deferred).
- **A migration or index** (§4). **Rate-limit changes** — the `GET` gets L1 only
  (05.2 D5). **Caching** — default `no-store`, no `ETag`.
- **Pagination** — documented exception (D6).

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("AC7 — …")`).

1. **Contract.** `GET /v1/progress/exercises/{id}` answers `200 { exerciseId: string,
   points: ProgressPoint[] }`; `401` with no/invalid token; `from` and `to` are the only
   query parameters, both optional.
2. **`404 not-found` for an exercise that does not exist or is not visible.** An absent
   id, another user's custom exercise and another user's fork all answer `404`
   `not-found` with **byte-identical** bodies. Visible = a global exercise or one owned
   by the caller, **including retired (`is_active = false`) rows** — a retired own
   custom exercise still charts. (Contrast 07.0's `?exerciseId=` filter, which returns
   `[]` — a path resource gets `404`, D3.)
3. **`422 validation-error` for malformed input.** A path `id` that is not a well-formed
   `ExerciseId`; `from` or `to` not a real `YYYY-MM-DD` calendar date (`2026-02-30`,
   `2026-1-5`, `2026-01-05T00:00:00Z`, empty `from=`); `from > to`. Raised before any
   database query.
4. **The id resolves through fork lineage, like 07.0.** `{id}` is resolved with
   `COALESCE(forked_from_exercise_id, id)`; the response `exerciseId` is the **root**. A
   global exercise's id, the caller's fork of it and a **second** fork all return
   identical bodies (`exerciseId` = the global's id). A from-scratch custom exercise is
   its own root.
5. **Scope.** Only `set_type = 'working'` sets of workouts with `ended_at IS NOT NULL`
   owned by the acting user are read; in-progress workouts, other users' workouts, and
   `warmup` / `drop` / `failure` sets never contribute. `is_complete` is ignored (07.0 D5).
6. **One point per finished workout with ≥ 1 working set of the lineage.** A workout
   that logged the lineage twice (a fork and its origin, or one exercise added twice)
   yields **one** point combining both. A workout whose only sets of the lineage are
   warm-up / drop / failure yields **no** point. A workout with working sets of the
   lineage that all fail every metric's eligibility yields a point with all four metrics
   `null` (D7).
7. **Metric values, each judged by the set's own `modality_snapshot`.**
   `topSetWeight` = the max working-set `weight_kg` over sets eligible for
   `heaviest_weight`; `bestE1rm` = the max Epley e1RM (07.0 AC3) over sets eligible for
   `best_est_1rm` (1–12 reps); `totalVolume` = `sumVolumeMilli` over the workout's
   working sets of the lineage; `maxReps` = the max reps over sets eligible for
   `max_reps` (`bodyweight_reps` only). Each is `null` when no set of that workout
   qualifies (`totalVolume` `null`, never `0`). An lb-entered set contributes via its
   canonical `weight_kg`. A mixed-modality lineage compares across modalities per set
   (07.0 D20's trade-off carries over).
8. **Serialization is exact.** `topSetWeight`, `bestE1rm`, `totalVolume` are JSON numbers
   equal to `Number(milliToDecimalString(milli))` (no division); `maxReps` is a JSON
   **integer**. `startedAt` is an ISO-8601 instant, `localDate` is `YYYY-MM-DD`.
9. **Order is `(started_at, workout id)` ascending** — 07.0's chronology — including two
   workouts with the same `started_at` and a **backdated** workout finished last, which
   sits at its true place in the series.
10. **`from` / `to` filter on `workout.local_date`, inclusive both ends.** `from` alone,
    `to` alone, both, and neither (the whole history) behave as stated; a workout whose
    `local_date` equals `from` or `to` is included. A point's values do not depend on the
    range (points are independent per workout, §6.3).
11. **A known exercise with no matching sessions is `200 { exerciseId, points: [] }`**
    — an exercise never trained, or a range with no sessions — not `404`.
12. **`setRecordValueMilli` is a refactor, not a change.** `records.ts` exports
    `setRecordValueMilli(recordType, set)`; `computeRecords` calls it; its output for
    every input is unchanged: 07.0's `records` unit suite, AC9 property test, and the
    reconciliation fixture pass unmodified, and a source scan finds exactly one
    definition of per-type eligibility (no second `candidate`-like switch).
13. **`progressPoints` is pure and exact.** `progressPoints(sets)` takes one lineage's
    working sets, sorted as `computeRecords` requires, and returns one entry per
    workout, in input order, with integer-milli `topSetWeightMilli`, `bestE1rmMilli`,
    `totalVolumeMilli`, `maxRepsMilli` (each `number | null`); it throws on a
    non-contiguous workout (a caller bug, like `computeRecords`).
14. **The guarantee: series max equals the PR, for three metrics.** For every history
    in the seeded generator: `max(topSetWeightMilli)` = `computeRecords`' `heaviest_weight`
    `valueMilli`; `max(bestE1rmMilli)` = `best_est_1rm`; `max(maxRepsMilli)` = `max_reps`;
    and a metric that is `null` at every point ⇔ that record type is absent.
    **`totalVolume` is deliberately not covered**: a point's `totalVolume` is a
    *session sum* and `best_set_volume` is a *single-set* best, so their maxima differ
    in general (a test pins a case where they do).
15. **Lineage extraction is behavior-preserving.** `resolveVisibleRoot(client, userId,
    exerciseId)` replaces `list()`'s inline resolution (null ⇒ `[]`, unchanged);
    `loadLineageSets(client, userId, roots, range?)` replaces the loader inside
    `recomputeRecordsForRoots` (called with no range ⇒ the same statement). 07.0's
    finish, delete, concurrency (AC18), reconciliation and rebuild integration suites
    pass **unmodified**.
16. **Contract & caching.** The route is in `GET /openapi.json` (`config.published: true`,
    `problems: [NotFoundError]`) with the `ProgressSeries` 200 schema and the `from` /
    `to` parameters; the response carries `Cache-Control: no-store` and no `ETag`; no
    `writeGroup`; the CI OpenAPI drift check is green.
    `apps/api/test/unit/contract-pipeline.test.ts` (the AC4 path set) and
    `apps/api/test/unit/openapi-problem-matrix.test.ts` list the route (matrix row:
    `"GET /v1/progress/exercises/{id}": withCentral("input", { 404: ["not-found"] })`)
    and pass. The 05.0-style exact inventory `openapi-workouts.test.ts` is **not**
    affected (it enumerates workout paths with `arrayContaining`); `openapi-personal-records`
    and `openapi-workouts-history` are untouched.
17. **`@sin/core` additions land cleanly.** `setRecordValueMilli`, `progressPoints`,
    `ProgressPointMilli` (type), `ProgressPointSchema`, `ProgressSeriesSchema`,
    `ProgressQuerySchema` (+ inferred types) are exported **by name** and added to
    `check-exports.mjs`'s `EXPECTED`; `pnpm run core:purity` stays green; the schemas
    parse a valid payload and reject a missing field, a negative metric, a non-integer
    `maxReps`, and (query) `from > to`.
18. **Hand reconciliation extends to the series.** Over 07.0's 10-session fixture
    (`apps/api/test/fixtures/pr-reconciliation`) a new hand-computed `expected-progress.ts`
    (arithmetic in comments, never generated from code) matches, per session, the
    series of each fixture lineage as served by the real route/repository; and the
    series max of `topSetWeight`, `bestE1rm`, `maxReps` equals the fixture's PR values
    (`expected.ts`) for the lineages that have those types.
19. **Latency is measured and recorded.** A benchmark script runs one series request
    over ~2 years of one user's history of one exercise and the measured p50/p99 are
    written into §12 O1 at implementation time against DESIGN §1.3's 400 ms. A
    measurement, not a CI gate.
20. **Logging.** A progress request emits only the generic request line (the exercise id
    and `from`/`to` appear only in its `req.url`, as for every route); no new business
    event; no weight, e1RM, volume or exercise name in any captured line.
21. **Docs stay consistent.** Every edit in §11's "DESIGN.md / doc edits" is applied.

**Consumers must note:**

- **One point per finished workout** — the x-axis is *sessions*, not calendar time. Any
  weekly/monthly bucketing (and gap handling) is the client's.
- **Any metric can be `null` at any point** ("no eligible set that session", e.g. a
  warm-up-heavy day, a 13+-rep set for e1RM). `null` ≠ `0`; draw a gap, not zero.
- **`bestE1rm` is session-best, not "since the last PR"**; its running maximum is the
  PR list's `best_est_1rm` (AC14). `totalVolume` is a **session sum** — its maximum is
  *not* `best_set_volume`.
- **Units are canonical**: kg, kg×reps, reps. Format to the user's preference (§4.8).
- **`exerciseId` in the response is the lineage root**, possibly different from the
  `{id}` requested; the series merges the global with the user's forks.
- **`404` means "no such visible exercise"; `points: []` means "no sessions".**
- **Un-paginated** (D6): the whole range comes back in one response.

## 4. Data model

**No tables, no migration, no new index.** The loader joins `workout` through
`workout_user_started_idx (user_id, started_at DESC)` and `workout_exercise` through
`workout_exercise_exercise_idx` (07.0 §4 / D17), exactly as 07.0's recompute does; the
optional `local_date` range is a plain filter on rows already selected by `user_id`,
not worth an index at one user's history (low thousands of sets). AC19's benchmark is
the check; the additive lever, if it ever fails, is an index (O1), as in 07.0 D17.

Rejected: **a stored per-workout stat table / `exercise_daily_stat`** (DESIGN §4.6) —
another derived copy for finish / delete / future set-edit to maintain, for a read that
measures in tens of milliseconds (D1).

## 5. API surface

Under `/v1`, authenticated, through the 03.0 route-schema convention, published
(OpenAPI opt-in, issue #10).

```
GET /v1/progress/exercises/{id}?from=&to=          auth required
  200  { exerciseId: string, points: ProgressPoint[] }
  404  not-found          — the exercise does not exist or is not visible to the caller
  422  validation-error   — malformed id; from/to not YYYY-MM-DD; from > to
  401  unauthenticated / invalid-token
  config: { published: true, problems: [NotFoundError] }   — no writeGroup (a GET)
```

- **`{id}`** — an `ExerciseId` (global, or owned by the caller; retired included).
  Resolved to its lineage root (§6.1); the response `exerciseId` is the root.
- **`from`, `to`** — optional, inclusive, `YYYY-MM-DD`, compared with
  `workout.local_date` (the user's calendar day, 05.0 — the same field a "this month"
  chart groups by, not the UTC date of `started_at`).
- **Order:** `started_at ASC, workout id ASC`. Oldest → newest, the natural chart order.
- **Un-paginated**, a documented exception to DESIGN §6's cursor rule (D6).
- **Caching:** default `/v1` policy — `no-store`, no `ETag`, no `config.httpCache`.
  **No rate-limit change** (§1).

### `@sin/core` additions

```ts

export const ProgressPointSchema = z.object({
  workoutId: WorkoutIdSchema,
  localDate: z.iso.date(),
  startedAt: z.iso.datetime({ offset: true }),
  topSetWeight: z.number().positive().nullable(),   // kg
  bestE1rm: z.number().positive().nullable(),       // kg
  totalVolume: z.number().positive().nullable(),    // kg × reps; a session sum
  maxReps: z.number().int().positive().nullable(),  // reps
});
export type ProgressPoint = z.infer<typeof ProgressPointSchema>;

export const ProgressSeriesSchema = z.object({
  exerciseId: ExerciseIdSchema,                     // the lineage root
  points: z.array(ProgressPointSchema),
});
export type ProgressSeries = z.infer<typeof ProgressSeriesSchema>;

/** `GET /v1/progress/exercises/{id}` querystring. */
export const ProgressQuerySchema = z
  .object({ from: z.iso.date().optional(), to: z.iso.date().optional() })
  .refine((q) => q.from === undefined || q.to === undefined || q.from <= q.to,
          { path: ["from"], message: "from must not be after to" });
export type ProgressQuery = z.infer<typeof ProgressQuerySchema>;

// packages/core/src/records.ts — additions (pure; the purity check applies)
/** The set's candidate value (milli) for one record type, or null when ineligible
 * (07.0 §6.1 table, D5). Was the private `candidate()`. */

export interface ProgressPointMilli {
  workoutId: string;
  topSetWeightMilli: number | null;    // max setRecordValueMilli("heaviest_weight", …)
  bestE1rmMilli: number | null;        // max setRecordValueMilli("best_est_1rm", …)
  totalVolumeMilli: number | null;     // sumVolumeMilli(the workout's sets)
```

## 6. Behavior & logic

### 6.1 The repository (`personal-record.prisma.ts`)

Two extractions, so lineage rules live in one place (this also closes part of 07.0's
code-review note that the lineage SQL was repeated in four queries — the remaining
copies are `rootsForWorkout` and the loader's own `LATERAL`; folding them is O3):

**`resolveVisibleRoot(client, userId, exerciseId): Promise<string | null>`** — lifted
verbatim from `list()`'s `?exerciseId=` resolution:

```sql
SELECT COALESCE(forked_from_exercise_id, id)::text AS root_id FROM "exercise"
WHERE id = ${exerciseId}::uuid AND (owner_user_id IS NULL OR owner_user_id = ${userId}::uuid)
```

`is_active` is deliberately not filtered (history of a retired exercise stays
chartable). `list()` now calls it (no row ⇒ `[]`, as before).

**`loadLineageSets(client, userId, roots, range?): Promise<Map<string, LineageSetRow[]>>`**
— 07.0 §6.3's loader statement, unchanged in shape, moved out of
`recomputeRecordsForRoots`, plus an optional `range: { from?: string; to?: string }`
that adds `AND w.local_date >= ${from}::date` / `AND w.local_date <= ${to}::date` as
`Prisma.sql` / `Prisma.empty` fragments (never string concatenation; 07.1 §6.1's
pattern). Rows are grouped by `root_id` in loader order (`ORDER BY root.id, w.started_at,
w.id, we.position, se.set_number`); a root with no rows is absent from the map.
`recomputeRecordsForRoots` calls it with **no** range, so its SQL is the same statement
it ran before — the guard is 07.0's own suites (AC15). `LineageSetRow` is the existing
`LoaderRow`.

**`getProgressSeries(userId, exerciseId, { from?, to? }): Promise<ProgressSeriesRecord>`**
(new method on the `PersonalRecordRepository` interface, `personal-record.ts`):

1. `root = resolveVisibleRoot(prisma, userId, exerciseId)`; `null` ⇒
   `throw new NotFoundError("exercise not found or not visible to the acting user")`
   — the same single path for absent and foreign (AC2), message never user-visible.
2. `rows = loadLineageSets(prisma, userId, [root], { from, to }).get(root) ?? []`.
3. Map rows → `RecordSet[]` (as the recompute does: `weightKgMilli` via
   `parseWeightKgMilli(weight_kg)` from **text**, never a float) and call
   `progressPoints`.
4. Attach `localDate` (`local_date.toISOString().slice(0, 10)`, the codebase's
   convention) and `startedAt` from the first loaded row of each workout (a
   `Map<workoutId, row>`); return `{ exerciseId: root, points }`.

```ts
export interface ProgressPointRecord {
  workoutId: string;
  localDate: string;        // YYYY-MM-DD
  startedAt: Date;
  topSetWeightMilli: number | null;
  bestE1rmMilli: number | null;
  totalVolumeMilli: number | null;
  maxRepsMilli: number | null;
}
export interface ProgressSeriesRecord { exerciseId: string; points: ProgressPointRecord[]; }
```

The route's `toProgressPointDto` converts milli → DTO next to `toPersonalRecordDto`
(07.1 §6.4's pattern; D5): weights and volume via `Number(milliToDecimalString(m))`,
`maxReps` via the same then asserted an integer.

**Hosted on `PersonalRecordRepository`** (D8): `buildApp` and `V1RouteDeps` already carry
`personalRecordRepository`, so no new wiring (07.0 needed six `buildApp` call-site edits for
a new repository). **Two statements, no wrapping transaction** (D9).

### 6.2 `@sin/core` (`records.ts`)

**`setRecordValueMilli(recordType, set)`** is `candidate()` exported under a name that
says what it is — **no behavior change**. `computeRecords` calls it exactly as it called
`candidate` (still guarding `v !== null && v > 0`). Guard: 07.0's `records` suite, the
AC9 property test and the fixture (AC12).

**`progressPoints(sets)`**:

1. Group `sets` into contiguous per-workout runs, throwing on a reappearing `workoutId`.
   The grouping loop is extracted from `computeRecords` into one shared helper (no
   behavior change) so the contiguity rule has one implementation.
2. Per workout, in input order: for each of `heaviest_weight`, `best_est_1rm`, `max_reps`
   take the maximum of `setRecordValueMilli(type, s)` over the workout's sets
   (applying `computeRecords`' own `v !== null && v > 0` guard; `null` if none);
   `totalVolumeMilli = sumVolumeMilli(sets)` (07.1; `null` if none qualifies).
3. Return one `ProgressPointMilli` per workout. A workout with no working sets does not
   exist in the input (the loader selects working sets only), so it has no point;
   a workout whose sets all fail every metric yields an all-`null` point (D7).

Because each point depends only on its own workout's sets — unlike `computeRecords`,
which carries a running best across workouts — **filtering by range in SQL cannot change
any point's value**, only which points appear (AC10). That is why the range lives in the
loader (D10) and not in a post-filter.

**The guarantee (AC14), stated precisely.** `computeRecords` takes, per type, the best
eligible value across all workouts; `progressPoints` takes the best per workout from the
**same function** over the **same input**. So `max over points` of `topSetWeightMilli` /
`bestE1rmMilli` / `maxRepsMilli` equals `computeRecords`' `valueMilli` for
`heaviest_weight` / `best_est_1rm` / `max_reps`, and a metric that is `null` everywhere
exactly when that record type is absent. **`totalVolumeMilli` is outside the guarantee:**
it sums a workout's sets while `best_set_volume` is the best *single* set, so a workout of
3 × 100 kg × 5 reps has `totalVolume` 1 500 and contributes only 500 to `best_set_volume`.
The two are separate definitions that share `setVolumeMilli`, which is what R4 asks for.
The guarantee holds for the series of **all** history; a `from`/`to` slice's max is the
best *within the slice*, which is not the all-time PR.

### 6.3 Edge behavior

- **Known exercise, no sessions** (never trained, or nothing in range): `200
  { exerciseId, points: [] }` (AC11).
- **A fork and its origin used in one workout** → one combined point (AC6): the loader
  groups by workout, `position` is only a tiebreak inside it.
- **Exercise renamed / forked later:** points are keyed by workout and carry no name, so
  a rename rewrites nothing. The client labels the chart from its catalog.
- **Mixed-modality lineage** (e.g. `weight_reps` → `weighted_bodyweight`): each set is
  judged by its own snapshot; maxima compare across modalities (07.0 D20, noted not
  solved). A `bodyweight_reps` period and a `weight_reps` period of one lineage yield
  points with `maxReps` and points with the weight metrics.
- **Backdated finish:** the workout appears at its true `started_at` position on the next
  request; there is no server cache to invalidate (default `no-store`).
- **Precision:** `started_at` is `timestamptz(6)`; the response `startedAt` is a
  millisecond ISO string like everywhere else, so two points may show an equal
  `startedAt`; their order is still the stored `(started_at, id)`.

## 7. Security & privacy

- **Authorization boundary.** Two gates, both in SQL: `resolveVisibleRoot` admits only a
  global or caller-owned exercise, and the loader is always `w.user_id = <authenticated
  user>`. The only caller-supplied identifier is the path `id`; it is never used to select
  workouts directly, only to find a root, and the workout filter is the acting user's.
  A caller can therefore never read another user's sets even by guessing a foreign
  exercise id.
- **No existence oracle.** An absent id and another user's custom exercise or fork take the
  same code path and return byte-identical `404`s (AC2); a *malformed* id is a `422`
  format error that reveals nothing. (07.0's `?exerciseId=` answers `[]` for the same
  reason; here the path resource form calls for `404` — D3.)
- **PII.** Per-workout strength numbers are the user's own training data (DESIGN §8.2 —
  sensitive), returned to them only, and never logged (AC20). `workoutId`s are the
  caller's own ids.
- **Abuse.** A read; L1 per-IP limiting applies (05.2). Cost is bounded by one user's own
  history of one lineage, un-paginated by design (D6): at the stated extreme (daily
  training, years) a few thousand points of ~120 bytes each, well under a megabyte. There
  is no `limit` parameter to widen the scan; `from`/`to` only narrow it.
- **Hostile-but-valid data** (reps 32 767 × weight 9 999.999 ≈ 3.3 × 10¹¹) is exact in a
  double and in `Number(milliToDecimalString(...))` (07.0 §6.1 magnitudes); a session sum
  would need > 27 000 maximal sets to approach 2⁵³ (07.1 §6.1), and set creation is
  rate-limited.

## 12. Decisions & open questions

- ✅ **D1 — approach A: compute the series in `@sin/core` from the same loaded lineage
  rows 07.0 uses (owner decision, 2026-10-07).** Rejected: **B — SQL `GROUP BY workout`**
  with the eligibility predicates and Epley rounding in the query: one statement, but a
  second implementation of what 07.0 / 07.1 made one, in `numeric` rather than exact
  integer milli — the drift DESIGN §3.2 / R4 warn about, and the chart and the PR list
  could disagree by a thousandth. **C — a daily rollup table** (`exercise_daily_stat`):
  DESIGN §4.6 defers it; another derived copy for finish / delete to keep in step, for a
  read measured in tens of ms. **Rationale:** one definition of every number; the chart's
  maximum *is* the PR (AC14); the cost is loading one lineage's working sets per request
  — already proven cheap by 07.0 AC27 / 07.1 O1.
- ✅ **D2 — export `candidate()` as `setRecordValueMilli`; `progressPoints` takes
  `RecordSet[]`.** The series calls the *same* per-type value function `computeRecords`
  does, so eligibility has one definition (07.1 D4's move, repeated for the other three
  types), and the loader rows feed both functions with no new input type. `estimate1rm`
  is reached through it, not called directly — README's "reuses `estimate1rm`" is
  satisfied. **Behavior-preserving:** 07.0's suite and AC9 property test are the guard.
- ✅ **D3 — `404` for an unknown or invisible exercise, `200 []` for a known exercise
  with no sessions (owner decision).** The resource *is* the exercise: a path resource
  with no visible match is `404`, identical for absent and foreign (no oracle), as
  `GET /v1/workouts/{id}`. **Contrast 07.0's `?exerciseId=` filter, which returns `[]`:**
  there the id is a filter over a collection and an empty collection is the answer.
  `points: []` for a visible exercise is a valid empty chart, not an error.
- ✅ **D4 — a malformed path id is `422`, via `ExerciseIdSchema` (departure from the
  neighbouring routes).** `GET /v1/workouts/{id}` and `GET /v1/exercises/{id}` declare
  `params: { id: z.string() }`, so a malformed id there reaches the repository and
  answers `404`. This route validates the id at the schema layer (the brief), so a
  malformed id is `422 validation-error` and **never queries the database**; the format
  error leaks nothing. The `404`/`422` split is therefore: well-formed-but-unseen ⇒ `404`;
  malformed ⇒ `422`. Not retrofitted onto the older routes (out of scope; O4).
- ✅ **D5 — number conversion: no division.** `topSetWeight`, `bestE1rm`, `totalVolume` =
  `Number(milliToDecimalString(milli))` (07.0 D14 / 07.1 D5). `maxReps` is a reps count:
  `max_reps`' milli value is `reps × 1000` (07.0 §5), so it is converted the same way
  (`"12.000"` → `12`) and the DTO is `.int()`; this keeps one conversion function and
  makes a non-multiple-of-1000 (a bug) fail the response schema loudly rather than render
  a fractional rep. (`milli / 1000` would also be exact; the string path is kept for
  uniformity, not necessity.)
- ✅ **D6 — un-paginated; a documented exception to DESIGN §6's cursor rule.** One point
  per workout per exercise, bounded by training frequency (~100 points/year/exercise, a
  few thousand at the extreme), ~120 bytes each. A cursor over a chart series is awkward
  (a chart needs the whole range) and `from`/`to` already bound it. The third exception
  after `GET /v1/exercises` and `GET /v1/personal-records`. Revisit only if a payload
  measured on real data is a problem (O1).
- ✅ **D7 — an all-`null` point is kept.** A workout with ≥ 1 working set of the lineage
  but no eligible set for any metric (e.g. a `duration` exercise, or only `reps: 0`
  sets) yields a point with four `null`s rather than being dropped. **Rationale:** the
  rule is the brief's literal one ("≥ 1 working set"); it keeps "this session trained
  it" separate from "this session had a countable load", and a client can choose to hide
  empty points. **Consequence:** for a `duration` / `distance_duration` exercise the whole
  series is all-`null` points (no duration progress in v1). Owner to confirm — O2.
- ✅ **D8 — `getProgressSeries` lives on `PersonalRecordRepository`.** No new repository,
  no `buildApp` / `V1RouteDeps` edits (07.0 D22 paid six call-site edits for a new
  repository); the method shares the file's loader and root helper. A dedicated
  `ProgressRepository` would be a cleaner noun but buys nothing the interface split
  doesn't already give. Rejected: a new repository (wiring cost for no isolation gain).
- ✅ **D9 — two statements, no wrapping transaction.** Resolve then load. Exercises are
  only hard-deleted by an account purge; workouts finished mid-request or deleted between
  the statements produce a series that is the state of one instant or the other, never
  inconsistent per point (each point is computed from one loader result). `REPEATABLE
  READ` would add a snapshot per read for nothing.
- ✅ **D10 — the range filters in the loader SQL, on `workout.local_date`.** Points are
  independent per workout (§6.2), so filtering in SQL changes only which points appear,
  not their values — unlike `computeRecords`, whose running best forbids it. SQL filtering
  keeps the loaded row count proportional to the requested range. `local_date`, not
  `started_at`, because a chart's x-axis is the user's calendar day (05.0 derives it once
  at write time) and a UTC-based filter would put a late-evening session on the wrong
  day. Rejected: filtering in JS after loading everything.
- ✅ **D11 — two extractions so lineage rules live in one place.** `resolveVisibleRoot`
  and `loadLineageSets` are lifted out of `list()` and `recomputeRecordsForRoots` rather
  than copied a third and fourth time; the recompute calls the loader with no range, so
  its statement is unchanged. Partially closes 07.0's code-review follow-up about the
  lineage SQL repeated in four queries (the other two copies — `rootsForWorkout` and the
  loader's inline `LATERAL` — remain; O3). **Guard:** 07.0's integration suites run
  unmodified (AC15).
- ✅ **D12 — the guarantee covers three metrics, not four (precise statement, §6.2).**
  `totalVolume` is a session sum; `best_set_volume` a single-set best; they are not
  expected to match, and a pinned test case documents it so nobody "fixes" the mismatch.
- ✅ **D13 — default `no-store`, no `ETag`, L1 only.** As 07.1 D14: the result changes with
  every finish, delete and backdated finish, and the body is cheap to recompute; a
  validator would buy little. A client caches in its own state (TanStack Query, Spec 08).
- ✅ **D14 — module and name choices.** `dto/progress.ts` in core (imports only ids —
  acyclic); `routes/progress.ts` registered in `routes/v1.ts` with the existing
  `personalRecordRepository`; DTO names `ProgressPointSchema`, `ProgressSeriesSchema`,
  `ProgressQuerySchema`; repository-level records `ProgressPointRecord` /
  `ProgressSeriesRecord` carry milli and the route converts (07.1 §6.4's split, so the
  fake and the Prisma repository agree on integers).

- **O1 — latency (AC19), to be measured at implementation.** `pnpm --filter @sin/api run
  bench:progress` against DESIGN §1.3's 400 ms; re-measure on Neon. If it fails, levers in
  order: an additive `set_entry` / `workout_exercise` index (07.0 D17), then a narrower
  loader select, then D1's rejected rollup. Also records the largest realistic payload
  (D6).
- **O2 — all-`null` points (D7).** Keep, or drop workouts where every metric is `null`?
  Owner to confirm; dropping would make "number of points" mean "sessions with a
  countable load" and is a one-line change in `progressPoints`.
- **O3 — fold the remaining lineage SQL copies?** `rootsForWorkout` and the loader's
  `LATERAL (SELECT COALESCE(...))` still spell the lineage rule inline. A follow-up could
  reduce all lineage SQL to one exported fragment; not needed for this spec's behavior.
- **O4 — malformed-path-id status across routes (D4).** This route answers `422`;
  `GET /v1/workouts/{id}` / `GET /v1/exercises/{id}` answer `404` for a malformed id.
  Owner to say whether to align the older routes (a small, separate change) or keep both.
- **O5 — a lineage that spans a catalog retire-and-replace** is two lineages and two
  series (07.0 O2), so a chart can have a seam where the catalog replaced a row. Same
  owner decision as 07.0 O2.
