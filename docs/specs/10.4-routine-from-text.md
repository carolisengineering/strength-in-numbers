## 1. Purpose, scope & non-goals

The owner's gym publishes each day's class as text inside its own app, which blocks copy and paste. Retyping every note, exercise and set line into Strength in Numbers is the cost this spec removes. The owner screenshots the class, copies the text out of the screenshots with the phone's own Live Text, and pastes it into a new **New from text** screen. The app reads the text, asks the owner to confirm each exercise name against their list, and lands in the ordinary routine editor with **sections, section notes, exercises, planned sets (reps), supersets and notes already filled in; only weights are left to type.** Nothing is saved until the owner taps Save in the editor. No paid or external service is involved; the text never leaves the phone before Save.

> **First-principles note — "Live Text" and why the reader takes plain text.** iOS can recognize the words in a photo (Live Text) and copy them like ordinary text. That copied text is just a string: no layout, no images. So the reader is a pure function from one string to a structure (`readWorkoutText(raw)`); everything the gym app drew around the workout (the status-bar clock, score badges, the bottom tab bar) arrives as extra lines in that string and has to be recognized and removed. Because it is a pure function of a string it lives in `@sin/core`, where it is unit-testable with the real example text and reusable by a future native app.

> **First-principles note — "pending" exercises.** The routine editor's items name exercises by id, and a routine can only be written with ids the server knows. A brand-new exercise has no id until it is created. Creating it when the owner finishes the name check would leave undeletable custom exercises behind if they back out (custom exercises cannot be deleted yet, #104). So an imported item carries a **placeholder id** (a random UUID that only this browser tab knows) plus a record of the exercise to create; **Save** creates the real exercises first, swaps the placeholder ids for the real ones in the request body only, and then writes the routine.

### In scope

- `@sin/core`: `cleanWorkoutText`, `readWorkoutText`, `normalizeExerciseName` / `matchExerciseName`, `guessModality`, `buildImportPlan` (all pure), the example text as a committed fixture.
- Web: the **New from text** entry on the Routines list; the paste screen; the **Check exercise names** screen; an in-memory import session; `draftFromImport`; the editor receiving an imported draft (pending exercises, notices); the Save sequence (create new exercises online-only, then the routine; a retry reuses what was created); overflow and nothing-found handling; accessibility; screenshot-harness captures; a manual phone check.
- Small changes to existing code: `CreateExerciseForm`'s fields extracted to a shared `ExerciseFields` (behavior unchanged); `ExercisePicker` gains `allowCreate`; `useExerciseLookup` learns pending exercises; `EditorRow` shows a "New" tag.

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|
| Reading the images themselves (OCR) | Not planned; may come later on top of `readWorkoutText` (brief §2) |
| Exercises inside a Warmup (its text becomes the section note) | Owner decision (brief §4.3) |
| Percentages, time caps, "for time", intervals ("1 set every 2:00"), weight levels (LV1–LV3), "or" choices as data — they stay note text | Time caps / AMRAP: issue #112 |
| Other gyms' formats as a goal (the reader is general where that is cheap; anything it cannot place becomes a note) | Not planned |
| Importing into an existing routine; starting a workout from the text | Not planned |
| Saving a routine without the editor review | Anti-goal: the editor is mandatory |
| Deleting a leftover custom exercise | Issue #104 |
| An all-or-nothing "create exercises + routine" server endpoint | Not needed (owner accepted leftovers, D5) |
| A new server-side exercise-name uniqueness rule | O1 |
| Same-line schemes with three or more numbers before a name ("21-15-9 Thruster") | Go to the section note (the editor shows them); a later increment if the owner meets them |
| Any API / migration / release step / env var | None |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.4 ACn — …"`**. Levels are in §10. **Phase A** (AC1–AC18): the pure reader and plan in `@sin/core`. **Phase B** (AC19–AC28): entry, paste and name-check screens. **Phase C** (AC29–AC41): editor, Save, limits, cross-cutting, verification, docs.

### Phase A — `@sin/core`

1. **Pure, total, linear.** The new modules (`workoutText.ts`, `exerciseMatch.ts`, `importPlan.ts`) import nothing but `@sin/core` siblings; `pnpm run core:purity` passes. Every exported function is **total**: any string (empty, one 40,000-character line, 5,000 lines, unpaired surrogates, only furniture) returns a value and never throws. Patterns are anchored and have no nested quantifiers; a 40,000-character single line and a 5,000-line input each finish in under one second in the unit test. No message text in these modules is derived from the input (#57): notices are **codes** (a closed string union) that the web maps to static copy, and `static-issue-messages.test.ts` still passes unmodified.
2. **Cleaning drops exact furniture lines.** A line is dropped when, after trimming and collapsing inner whitespace, it equals one of the following **whole-line** forms (case-insensitive): a clock `H:MM` or `HH:MM`, optionally followed by `AM`/`PM`; the badges `NO SCORE`, `WEIGHT`, `TIME`, `REPS`, `ROUNDS`, `DISTANCE`, `CALORIES`, `LOAD`; `RESULTS (n)` for any whole number n; `Log result`; the gym name lines `HIRAYA TRAINING HOUSE`, `HIRAYA`, `TRAINING HOUSE`; the navigation labels `Home`, `Schedule`, `Workouts`, `Social`. The lists are three exported constants (`CLOCK_LINE`, `BADGE_LINES`, `GYM_LINES`, `NAV_LINES`) so a new gym or badge is a one-line change. Lines that merely *contain* or *start with* one of these survive: "For Time:", "Push Press", "Weight training", "Time under tension 3:00", "Home stretch", "Results are mixed".
3. **Screenshot boundaries.** Before cleaning, the input is split into chunks at each clock line (the status-bar clock Live Text copies marks the start of a screenshot); text before the first clock line is its own chunk. With no clock line the paste is one chunk and no overlap removal runs. `cleanWorkoutText` reports `chunks` (the count after dropping chunks that clean to nothing) so the web can show "N screenshots".
4. **Overlap removal at boundaries only.** For each pair of consecutive cleaned chunks A, B, the longest k ≥ 1 is found such that A's last k lines repeat B's first k lines, and B's copy is removed. Equality is on normalized text (trimmed, whitespace collapsed). The first overlapping pair may be a **fragment**: B's first line equals, or is a word-boundary **suffix** of, A's line at that position (the owner's "our legs." after a paragraph ending "…use our legs."), or A's last line is a word-boundary **prefix** of B's first line (A was cut off at the screen edge; A's partial line is then dropped in favor of B's full one). A fragment needs ≥ 2 words. A line that repeats **inside** a chunk, or **away from** a boundary, is kept ("21-15-9" appears twice in the example and both stay). The example's boundaries are covered: "Strict Press" (end of screenshot 1 / start of 2, k = 1), the two repeated paragraphs (2 → 3, k = 2), "our legs." (4 → 5, fragment).
5. **Headings make sections.** A heading line starts a new section, and the lines up to the next heading belong to it. A heading is: (a) `Workout: "X"` (quotes straight or curly, optional spaces inside, case-insensitive prefix) whose section name is X trimmed; (b) a known heading word (`Warmup` family, `Strength`, `Accessory`/`Accessories`, `Conditioning`, `Metcon`, `Finisher`, `Cooldown`/`Cool down`, `Core`, `Skill`, `Mobility`, `Gymnastics`); or (c) a **generic title**: ≤ 5 words, ≤ 40 characters, no digit, no colon, no `. ! ? , ;`, every word of ≥ 4 letters starting uppercase (or the whole line uppercase), and **not the last line**. (c) is not applied while a movement list is open (AC8–AC10), so "Power Clean" under "21-15-9" is a movement, not a heading. Text before the first heading is the **preamble**. The section name is capped at `SECTION_NAME_MAX` (notice on a cut, AC17).
6. **Warmup is note-only.** A section whose heading is `Warmup`, `Warm-up` or `Warm up` (any case) has **no exercises**; every line under it up to the next heading (list lines, numbers, "then 2 Rounds") is kept verbatim, in order, joined by newlines, as the section note.
7. **Strength block from set lines.** Lines `Set n: R Reps [@ tail]` (case-insensitive, `n` and `R` whole numbers) in a non-Warmup section make **one** exercise named by the section's title, with one planned row per set line in order (reps R for low and high). Each set line that has a tail contributes `Set n @ tail` (one per line) to the **item note**; the tail text is copied as written ("45–50%", "Build If Able"). Every other line of the section — the title lines ("Heavy 10", "STRICT PRESS — BUILD TO A 10RM"), "6 Sets, 1 Set Every 2:00", "Score: …", the coaching paragraphs — goes to the **section note** in order. "1 Set Every 2:00" is not rest: `restSeconds` stays empty. The set lines are consumed (not repeated in the section note).
8. **Scheme blocks and runs.** A whole-line rep scheme `a-b-c` (two or more whole numbers joined by hyphens or en dashes) starts a **run** and sets the scheme for the movement lines that follow it. A movement line is: ≤ 6 words, ≤ 60 characters, no colon, no `. ! ? ;`, at least one letter, not a lead-in, not a scheme. Each movement becomes an item with one planned row per scheme number (reps = that number); the run's items are a superset when the run has ≥ 2 items. The run ends at the first non-movement line, at a lead-in, at a scheme line (which starts the next run) or at a separator line `Directly into:` / `Into:` / `Then:`, which is consumed. A separator or a second scheme line therefore starts a **second** superset in the same section. Movements are matched to lines only while the list is open: "LV1: 45/35, Hang Power Cleans" (a colon) closes it and goes to the section note with everything else unplaced.
9. **Lead-in lists and rep forms.** The lead-ins `N Sets` / `N Sets:` and `N Round(s)` / `then, N Rounds:` set a pending **set count** N and start a run; the movement lines that follow (with or without a leading `- `) are items with N planned rows. A leading rep form on a movement line is: `R name` (R reps, every set), `L-H name` (a rep range: low L, high H, L ≤ H), `a/b name` (**a + b reps**; the text `a/b` is kept in the item note), each with R/L/H/a+b in 1–100. A leading number that is > 100, or is followed by a distance/time unit word (`m`, `meter(s)`, `km`, `mi`, `min`, `sec`, `s`, `cal`), is **not** reps: it stays in the name (AC11). A run of ≥ 2 items is a superset; a run of one is not. A run of more than 8 items is split into groups of 8 (a remainder of one is ungrouped) with a notice (AC17).
10. **Bare lists and numbered sentences.** Outside a Warmup, a bulleted line (`-`, `•`, `*`) with a leading rep form and a name is an exercise even with no lead-in; with no set count it has **no rows** and carries its reps as the quick-line range (the "rowless" form of Spec 09.1 O1). An **un-bulleted** line that starts with a number and has no open lead-in is **not** an exercise: "5 Minutes to build to first strict press weight (build by 3-5 reps)" goes to the section note. A movement line with no leading reps under a lead-in is an item with N rows and no reps.
11. **Distances and times in a name.** A movement whose text starts with a distance or time ("400 Meter Run", "1 Mile Run") keeps the text **as written** as the exercise name (the New card's default; AC24) and puts the leading phrase ("400 Meter") in the **item note**, so the distance survives even if the name check maps it to a different exercise.
12. **Nothing is dropped silently.** Every non-empty input line ends up in exactly one place: dropped as furniture (AC2), removed as boundary overlap (AC4), consumed by a named construct (heading, set line, scheme, lead-in, separator, movement line), or in a note (routine, section, or item). A test over the example and over seeded random shuffles of its lines asserts the conservation count, and that every unconsumed, non-furniture line appears verbatim (after whitespace collapse) in a note. Notes join lines with `\n`.
13. **Routine name and preamble.** The routine name is X from the first `Workout: "X"` heading; otherwise the first non-Warmup heading's text; otherwise `null`. Preamble lines that no construct consumes become the **routine note**. Items that appear in the preamble (bulleted lines) are loose (no section).
14. **Name normalization and exact match.** `normalizeExerciseName` lowercases, folds diacritics, turns punctuation and hyphens into spaces, drops a leading `-`/bullet, strips simple plurals per word (a trailing `s` after ≥ 3 letters but not `ss`, the letters counted across the whole name so "Pull-Ups" ≡ "pull up" while "Abs" stays, and a lone possessive `s` dropped; `es` after `ch`, `sh`, `x`, `z`, `ss`) *(amended at implementation, 2026-10-21)*, and joins the words with no separator, so "Hand release pushups" and "Hand-release push-up" give the same key. `matchExerciseName(written, rows)` returns the exact match (first by key; if several rows share a key, the custom row, then the lowest name) from the rows it is given; the web passes only `useCatalog().visible` rows (active, not a fork origin).
15. **Similar suggestion.** With no exact match, `matchExerciseName` may return **at most one** `similar` row. Tokens are the normalized words with `db` → dumbbell, `kb` → kettlebell, `bb` → barbell expanded and numbers and unit words (`m`, `meter`, `min`, …) dropped; score = token Jaccard overlap, plus 0.25 when the last tokens (the head noun) are equal; suggest the best row scoring ≥ 0.3 (ties: shorter name, then alphabetical). Against the ten built-in names, "Strict Press" → "Overhead press", "DB Lateral Lunge" → "Dumbbell lunge" and "400 Meter Run" → "Treadmill run"; "Power Clean", "Hand Release Pushups", "Front Raise" and "Reverse Fly" → none. The threshold and bonus are constants in one place and tuned only against that table.
16. **Modality guess.** `guessModality(name)`: a leading distance, or a word `run`, `jog`, `sprint`, `bike`, `erg`, `swim` → `distance_duration`; `plank`, `hold`, `hang`, `wall sit` → `duration`; push-up/pull-up/chin-up/sit-up/burpee/hand release (any hyphen or plural form) → `bodyweight_reps`; otherwise `weight_reps`. Table-driven including the example's eight names.
17. **`buildImportPlan` makes the routine plan.** `buildImportPlan(read, modalityOf)` (where `modalityOf(nameKey)` is the chosen exercise's modality) returns `{ name, notes, sections, items, notices }` with weights, RPE and rest empty. (a) **Reps follow the type:** when the chosen modality refuses reps (`duration`, `distance_duration`, via the same `forbiddenMeasuresFor` rule as `plannedSetViolations`) the item keeps its **row count with no reps** and its rep scheme moves into the item note as `"<scheme> reps as written"` (a `a/b` item: `"10/10 reps as written"`); likewise any rep value outside 1–100. (b) **Quick vs plan:** rows that are all working, identical, no weight → quick form (`targetSets`, `targetRepsLow/High`); anything else → plan rows. (c) **Item order** is the canonical order (loose items first, then section by section); superset groups are numbered 1, 2, 3 … by first appearance and never span a section. (d) **Limits** (§6.6): a note over its cap, a name over its cap, more than 8 sections, 30 items, 20 sets per item, or a superset over 8 is cut **and reported** as a notice code with the counts; nothing is cut without a notice, and `buildImportPlan(...).items`/`sections`/notes always satisfy `RoutineWriteSchema`'s bounds.
18. **The example, end to end.** `readWorkoutText` + `buildImportPlan` on the committed fixture `packages/core/test/fixtures/hiraya-2026-10-19.txt` (the five screenshots of brief §9, with the clock lines, badges, gym lines, results and nav lines as transcribed), with the default guessed modalities, produce exactly the plan pinned in §6.9: routine name "Second Shift", four sections (Warmup note-only; Strict Press; Second Shift; Accessory), eight items (Strict Press 6 rows of 6, 6, 4, 4, 10, 10; Power Clean, Hand Release Pushups and Push Press 3 rows of 21, 15, 9; 400 Meter Run 3 rows with no reps; Front Raise 3 × 10; Reverse Fly 3 × 10–15; DB Lateral Lunge 3 × 20 with "10/10" in its note), three supersets, no notices. A second run of the same text with Treadmill run and Overhead press chosen as the matches produces the same structure (their types allow/forbid reps the same way), and a third with "Hand Release Pushups" forced to `duration` shows 3 rows with no reps and the scheme in its note.

### Phase B — entry, paste and name-check screens

19. **Entry and the 50-routine limit** (the link itself lands in Phase C, §11; the paste-screen limit state in Phase B). The Routines list shows **New from text** (a link) beside **New routine**. At `ROUTINES_PER_USER_MAX` routines both are disabled buttons described by the one `LIMIT_MESSAGE` text (`aria-describedby`); while the list is loading neither appears (today's rule). The paste screen, opened directly at the limit, shows `LIMIT_MESSAGE` and keeps **Read workout** disabled. The link opens the paste screen with `state: EDITOR_FROM_BACK` so Back returns to the Workouts tab.
20. **Routes and the in-memory session.** Three routes under one layout element that provides the import session: `/app/workouts/routines/import` (paste), `…/import/names`, `…/import/edit`. All three rank above `workouts/routines/:id` (a route-ranking test like 10.0 §6.1, including that `import/edit` is not read as routine "import"'s edit). The session holds the pasted text, the read result, the owner's choices and the pending exercises **in memory only**: nothing is written to `localStorage`/`sessionStorage` (a storage spy), nothing is put in a URL or router state, and a reload of the names or edit URL (empty session) redirects to the paste screen. Leaving the import routes for any other screen discards the session.
21. **Paste screen.** Title "New routine from text"; "‹ Back to Workouts"; one large `textarea` labeled "Workout text"; the Live Text how-to (§5.2) as an ordered list; the privacy line (§5.2); a primary **Read workout** button, disabled while the text is blank (whitespace only). Text longer than `IMPORT_TEXT_MAX` (40,000 characters) is **not truncated**: **Read workout** shows the static message "That is a lot of text (over 40,000 characters). Paste fewer screenshots at a time." and does nothing else. The text box keeps its content when the owner comes back from a later screen.
22. **Read outcomes.** Reading runs synchronously and never throws. When the reader finds ≥ 1 exercise, the owner goes to Check exercise names (the screen is always shown, even when every card is pre-decided). When it finds **no exercises**: if it found sections, a routine note or other text, the paste screen shows an info panel "No exercises found in this text" naming what *was* found (e.g. "Found 1 section: Warmup") and offers **Open in the editor anyway** (to the editor with the sections and notes filled in; Save stays disabled until an exercise is added, the editor's existing rule) beside the textarea; if it found nothing at all (empty after cleaning), the panel says "Nothing to read in this text" and offers no continue. Neither case saves anything.
23. **The catalog gate.** Names are classified only against a synced catalog: when the catalog store has never synced and has no rows, the Check screen shows "Loading your exercises…" and calls `refresh()`; a failed first sync shows "Couldn't load your exercises" with **Retry** and **no cards and no Continue** (so a name is never offered as New just because the list was missing). A synced catalog, or cached rows with a stale sync, proceeds (the picker's rule).
24. **Cards.** One card per distinct **normalized** name, in order of first appearance, each showing the name as written (first occurrence), a one-line "Used in <section name(s)>" context, and these states: **exact** — pre-picked "<exercise name>" with the tag "In your list"; **similar** — pre-picked suggestion with the visible text tag "Similar", plus **New: <name>** beside it; **nothing similar** — **New: <name>** pre-picked with the line "Nothing similar in your list."; **picked** (AC25). A summary line above the cards reads "Found N sections and M exercises" (and "from K screenshots" when K ≥ 2). A choice is a radio inside a radiogroup labeled with the written name; the tag is text, not color alone.
25. **Choose another.** Every card has **Choose another exercise**, opening the existing `ExercisePicker` with a new optional prop `allowCreate` set to `false` for this use (default `true` keeps every other caller as today): the picker's "Create a custom exercise" row is absent, so no exercise is created at this step. Picking returns to the card as a third option "<picked name>" (selected, with **Change**); the picker's own recents/search/filters are unchanged. `onPick` does not close the picker (06.0); the card closes it.
26. **The New card form reuses the create fields.** Selecting **New** shows, inside the card, the same fields as `CreateExerciseForm` — **Name**, **Type**, and a collapsed **More details** (primary muscle, secondary muscles up to 4, equipment, all optional and empty) — from a controlled `ExerciseFields` component extracted from `CreateExerciseForm` (props: values, `onChange`, `errors`, `idPrefix`, `modalityLabel`, `muscleGroups`, `equipment`). Name starts as the text as written (trimmed); Type starts as `guessModality(name)` and is editable; More details is closed. `CreateExerciseForm` keeps its Save/Cancel, its API error mapping and its ids/labels (default `idPrefix`, label "Modality"), and its **existing test file passes unmodified**. Each card's controls have distinct ids/names (`idPrefix` from the card's key), so two open forms never share a radio group. Reference data (muscles, equipment) that has not loaded omits More details, as today.
27. **Names that already exist.** While a New card is selected, its (normalized) name is compared with every row in `useCatalog().visible` and with the other cards' New names. A match with an existing exercise shows under the Name field: "<exercise name> is already in your list." with a **Use it instead** button, which selects that exercise on this card (state "exact"); the card stays blocked from Continue until then or until the name is changed. A match with **another New card** shows "Another new exercise has this name" (no button) and blocks Continue. The check is client-side, immediate, and ignores case, punctuation, hyphens and simple plurals (AC14). A name that is blank, over 120 characters or contains a control character is refused with the field's static message (`CreateExerciseSchema.shape.name`'s rule, shown in the app's wording).
28. **Continue.** **Continue** is enabled when every card has a choice and every New card's value passes `CreateExerciseSchema` (name, modality, ≤ 4 secondary muscles, no restated primary) and AC27. While disabled, a line of text beside it says why ("2 cards need attention", `aria-describedby`), and the first invalid card is reachable by that line's link. Continue builds the plan and draft (AC29) and navigates to the editor.

### Phase C — editor, Save, limits, verification

29. **The draft.** On Continue, `buildImportPlan(read, modalityOf)` is called with each chosen exercise's modality (matched, picked, or the New card's Type — so a change of Type on the check screen is reflected), and `draftFromImport(plan, idOf)` (a pure function in `routines/import/importDraft.ts`) returns a `Draft`: name, notes, sections (fresh keys), items (fresh keys; `sectionKey`; quick or plan form; notes; supersets), `dirty: true` (an unsaved import arms the leave guard), `adjusted: false`. A New choice is assigned a placeholder id once per card (`crypto.randomUUID()`, valid under `ExerciseIdSchema`) shared by every item with that name; an existing choice uses its real id. The draft passes `settle` unchanged (a property test: `reduce` of a no-op action returns identical items).
30. **The editor receives it.** `/app/workouts/routines/import/edit` renders the ordinary `RoutineEditor` in **"New routine"** mode with the imported draft as its initial state (a new optional `initial` prop; `routine={null}` semantics and every other path unchanged). Above the form it shows the dismissible info notice "Read from your text. Check the sections and notes, then add weights." and one warning notice per overflow (AC34). A row whose exercise is pending shows the name (as chosen on its card) with a visible **New** tag (text). All item controls work as usual — the item sheet gets the pending exercise's modality, so rep fields follow its type — and Remove/Move/Link/Move to section behave as for any item. Cancel and in-app Back go through the existing Discard changes guard; confirming Back from the editor returns to the Check screen with the owner's choices intact.
31. **Save sequence.** With pending items, **Save** (a) validates the draft as today (`validateDraft`, with the pending exercises' modalities); (b) creates each still-referenced pending exercise **one at a time, in order of first appearance**, with `useCatalog().createCustom` (a direct `POST /v1/exercises`, online-only, not through any queue) using the card's name, type, primary/secondary muscles and equipment; (c) builds the body with `toRoutineInput`, replacing every placeholder id by the created id **in the body only** (the draft is not rewritten); (d) sends `POST /v1/routines`; (e) on success navigates to the saved routine's preview as today. A test pins the order of requests (all `POST /v1/exercises` before the routine write) and that no request carries a placeholder id. A draft with no pending items saves exactly as today.
32. **Failure and retry.** If an exercise create fails (network, 429, 5xx, `exercise-limit-reached`, 422), the sequence stops, Save reopens, and a static form-level message names the cause and the exercise ("Couldn't create “<name>”. Nothing else was saved." / "You've reached the maximum number of custom exercises."); exercises already created in this attempt stay recorded (`name → created id`) in the import session. If the routine write fails after the creates (every case Spec 10.0 §5.6 already handles: name taken, limit, retired, 422, offline), the same recorded ids are used on the next Save — **no exercise is created twice**. Before creating anything on a retry (`attempts > 0`), Save awaits `refresh(true)` and reuses any visible exercise whose normalized name equals the pending name (the response of an earlier create may have been lost). Leftover created exercises when the owner gives up are accepted (D5); they appear in the picker and exact-match a later import.
33. **Backing out leaves nothing; removing an item leaves nothing.** Until Save, no request is made that creates an exercise, a routine or any data: leaving from the paste, names or editor screen (Back, Cancel, nav tab, reload) issues no `POST` (a request-capture test per screen). A pending exercise whose items were all removed in the editor is **not** created at Save.
34. **Limits and overflow are visible.** For each of the following, the editor shows a warning notice (static copy with the counts) and the draft holds the cut version, never silently: a section note over 2000 or an item note over 500 characters (cut at the limit), a routine name over 80 or a section name over 40 (cut), more than 8 sections (the 9th onward are left out with their exercises, their headings named), more than 30 items (the 31st onward left out), more than 20 planned sets on an item (cut to 20), a superset over 8 (split at 8). The cut text is the *end* of the note, never the start; a note cut at the limit ends with "…" inside the limit. The editor's own validation and caps (Spec 10.0/10.3) apply unchanged afterwards. A table test covers each row of §6.6.

## 6. Behavior & logic

### 6.1 Pipeline

```
raw string
  → split at clock lines → chunks
  → per chunk: drop furniture lines (whole-line table)
  → boundary overlap removal between consecutive cleaned chunks
  → lines
  → readWorkoutText: headings → sections; per section: constructs (set lines, schemes, lead-ins, lists) + notes
  → ReadResult (names, items with reps schemes, notes, notices-so-far)
  [name check: cards from ReadResult.names + the catalog]
  → buildImportPlan(read, modalityOf)  (after the check, so Type changes are reflected)
  → draftFromImport → Draft (+ pending exercises) → RoutineEditor
```

### 6.2 The import session

A React context provider mounted by the layout route above the three import routes. State: `text`, `read` (the `ReadResult`), `choices` (by normalized name key: `{ kind: "exact" | "similar" | "picked", exerciseId } | { kind: "new", value: ExerciseDraft }`), `pending` (placeholder id → `ExerciseDraft`), `created` (placeholder id → real id, filled during Save), `attempts`, `notices`. It is plain React state, never persisted. `useExerciseLookup()` reads the `pending` map from a second context (default empty) and answers `{ name, state: "active", modality, isNew: true }` for a placeholder, so no other consumer changes.

### 6.3 What the reader recognizes

| Input shape | Becomes |
|---|---|
| Clock line (`11:41`) | Screenshot boundary, then dropped |
| `NO SCORE`, `WEIGHT`, `TIME`, `RESULTS (5)`, `Log result`, gym lines, `Home`/`Schedule`/`Workouts`/`Social` | Dropped (whole-line, exact) |
| `Warmup` heading | Section; everything under it is its note |
| `Workout: " Second Shift"` | Section named `Second Shift`; the routine name |
| `Strict Press`, `Accessory` | Section heading |
| `Set n: R Reps @ tail` lines | One exercise (the section's title), a row per set, tails in the item note |
| `21-15-9` + movement lines | A superset run; each movement has a row per number |
| `Directly into:` | Separator; the next scheme starts a second superset |
| `3 Sets:` + `10 X`, `10-15 Y`, `10/10 Z` | A superset; N rows each; 10, 10–15, 20 reps (note `10/10`) |
| `- 10 Name` (bullet) | An exercise; with an open lead-in N rows, else rowless with reps |
| `400 Meter Run` | Name as written; "400 Meter" in the note |
| Everything else | The section note (or the routine note before the first heading) |

### 6.4 The name check (AC24–AC28)

Cards come from `read.names` (distinct by `normalizeExerciseName`, first-appearance order). Initial choice: exact → that exercise; similar → the suggestion; else New with `value = { name: written, modality: guessModality(written), muscles/equipment empty }`. The owner can switch among the offered options, pick another via the picker, or edit a New card. `Continue` validates once more with `CreateExerciseSchema.safeParse` per New card. A choice of an existing exercise is never modified; the New card never writes to the catalog.

### 6.5 Building the draft (AC29)

`buildImportPlan` is pure and takes `modalityOf`. `draftFromImport` mints keys, assigns placeholder ids (one per New card), and returns the `Draft` with `dirty: true`. It builds plan rows as `DraftSet` and quick items as `Targets` with `plan: null`; it never sets weights or units. The pending map is returned beside the draft; both go into the session and then into `RoutineEditor`.

## 7. Security & privacy

- **The text is the owner's and stays on the device until Save.** It is never sent to any service, never put in a URL, router state, storage key or log (AC35). The only requests are the existing exercise and routine writes, whose bodies carry the names and notes the owner has just reviewed in the editor.
- **No new authority.** Every write is an existing authenticated route under the existing write-rate groups; the client creates at most as many exercises as the routine has distinct pending names (≤ 30) and the 500-per-user cap is the server's (`exercise-limit-reached` is handled, AC32). A pending exercise is created only if an item still references it.
- **Hostile or accidental input.** The reader is a total, linear-time function with anchored patterns, a size cap and per-line handling (AC1, AC21); nothing from the text becomes markup, a link, an attribute or an id (AC35); static issue messages are preserved (#57). A 40,000-character cap bounds work and payload size.
- **Placeholder ids** are random UUIDs that exist only in this tab's draft and session; the request bodies carry only real ids (AC31).
- **Health information** can appear in section notes the owner pastes (class notes about injuries etc.); it is treated like any user note (rendered as text, not logged).

## 12. Decisions & open questions

Owner decisions are labeled **(owner)**; calls that are the designer's and may be refined are labeled **(mine)**.

### Resolved (owner-approved 2026-10-19, from the brief)

- ✅ **D1 — Paste the text; read it on the device; no paid or external service (owner).** Live Text does the image-to-text step; the reader is a pure function of the pasted string. **Rationale:** zero cost per import, no data leaves the phone, and the reader is testable with the real example. **Rejected (owner):** the Anthropic API (cost). **Later:** an on-device OCR front end on top of the same reader (about 10 MB and a CSP change for WebAssembly — not now).
- ✅ **D2 — Clean the screen furniture by exact whole-line match (owner list; exactness is mine).** The owner's list (clock, badges, `RESULTS (n)`, `Log result`, gym name, nav labels) is implemented as exact, case-insensitive whole-line matches, so "For Time:" and "Push Press" survive. **(mine)** The additional badge words `REPS`, `ROUNDS`, `DISTANCE`, `CALORIES`, `LOAD` are guesses at the gym app's other badges; a wrong guess only drops a one-word line that is exactly that word, and the phone check (AC40) confirms the real set.
- ✅ **D3 — Block classification (owner-approved mapping).** Headings become sections; Warmup is note-only; a strength block (set lines) is one exercise with per-set rows; a rep scheme + movements is a superset with a row per number; "Directly into:" starts a second superset; `3 Sets:` lists are supersets of N rows; `10/10` is 20 reps with `10/10` kept in the note (owner, 2026-10-19); percentages, caps, intervals and weight levels are note text; "1 Set Every 2:00" is not rest. **Rationale:** matches how the gym writes classes and what the routine model can carry (Spec 09.1/09.2).
- ✅ **D4 — The name check gives the owner the final say (owner).** One card per distinct name; exact matches pre-picked; a similar suggestion pre-picked with a "Similar" tag and New beside it; New pre-picked when nothing is similar; Choose another via the existing picker; New shows the create-exercise fields (Name, Type, More details) before the exercise exists; a name that already exists offers **Use it instead**. **Rationale:** a wrong silent match is worse than one extra tap.
- ✅ **D5 — Nothing is created before Save; leftovers after a failed routine write are accepted (owner).** New exercises are created at Save, immediately before the routine; backing out leaves nothing. If the routine write fails after the exercises were created and the owner gives up, those exercises stay: a retry reuses them, a later import exact-matches them, and #104 will make them deletable. **Rationale:** an all-or-nothing endpoint would be an API spec for a rare case; the cost of a leftover is a name in the picker.
- ✅ **D6 — The editor review is mandatory; the routine opens unsaved (owner).** The import lands in the ordinary editor in "New routine" mode; Save is the owner's act.
- ✅ **D7 — A Warmup gets no exercises (owner).** "Skip adding exercises for now, just add the notes."

### Resolved — designer's calls (mine; refine freely)

- ✅ **D8 (mine) — The reader lives in `@sin/core` as pure functions.** Unit-testable with the committed fixture, reusable by a native app, enforced pure by `core:purity`. The plan builder is also in core so its limits and the modality rule are tested without React.
- ✅ **D9 (mine) — A clock line marks the start of a screenshot; overlap removal is boundary-only.** From the owner's observation that Live Text copies the status-bar clock. A repeated *run* at a boundary (and a one- or two-line fragment) is removed; a line that repeats elsewhere is kept ("21-15-9"). With no clock line the paste is one chunk and nothing is removed. **Risk:** a stand-alone `H:MM` line inside the workout text (for example a wrapped "2:00") would be treated as a clock and dropped; the phone check looks for it.
- ✅ **D10 (mine) — The draft is built after the name check.** `duration` and `distance_duration` exercises refuse planned reps (`plannedSetViolations`), so the item keeps its row count with no reps and the rep scheme moves into the item note ("21-15-9 reps as written"). Building after the check means a Type change on a New card is reflected. The editor has no exercise swap, so a later Type change does not arise (Remove and re-Add is the path).
- ✅ **D11 (mine) — Quick form when the rows are uniform, plan rows otherwise.** Same wire result (Spec 09.1 `expandQuickLine`), and a plain "3 × 10–15" in the editor for the common accessory case.
- ✅ **D12 (mine) — `N Rounds` lead-ins behave like `N Sets:`.** A run of ≥ 2 list items under a rounds lead-in is a superset with N rows. (A circuit repeated N times is the superset case; the brief only says the rounds become the set count.)
- ✅ **D13 (mine) — Extract `ExerciseFields` from `CreateExerciseForm` rather than build a second form.** The brief says the New card "reuses the form's fields"; the existing form owns its own Save/Cancel and API call, so the fields must be separable. A controlled component with `idPrefix` and a label prop keeps both uses identical and keeps `CreateExerciseForm`'s tests unmodified. The card says "Type" (the approved mockups), the existing form keeps "Modality".
- ✅ **D14 (mine) — `ExercisePicker` gets `allowCreate`.** Its built-in "Create a custom exercise" row calls `createCustom` immediately, which would create an exercise before Save. The Choose-another picker hides the row.
- ✅ **D15 (mine) — Pending exercises are placeholder UUIDs in the draft plus a context, not a reducer concept.** The reducer and `settle` are unchanged; ids are swapped in the request body only; `useExerciseLookup` answers for placeholders. **Rejected:** a new `DraftItem` field (every action would carry it), router state (lost on reload, and would put user text in history state).
- ✅ **D16 (mine) — The import session is in memory only, with a layout route.** No stored draft, consistent with Spec 10.0 D5 (routine edits are online-only and not persisted). A reload on a later screen returns to the paste screen.
- ✅ **D17 (mine) — Creating exercises uses `createCustom` directly, one at a time, in order.** It is a direct `POST` today (Spec 06.0 left room for Spec 06.2 to queue it; 06.2 did not). A test pins the request order so a future queue cannot silently reorder the sequence. A retry awaits `refresh(true)` and reuses a visible exercise with the same normalized name before creating (lost-response safety; duplicates cannot be deleted yet).
- ✅ **D18 (mine) — Overflow is cut and reported, never silent.** Notes keep their beginning and end with "…"; sections/items beyond the caps are left out with their headings named in the notice. **Rejected:** folding left-out sections' text into the last section's note (hides structure); refusing the import (blocks a mostly-fine routine).
- ✅ **D19 (mine) — Zero-exercise text.** If the reader found sections or notes, offer **Open in the editor anyway** (the editor keeps Save disabled until an exercise exists); if it found nothing, say so. The names step is skipped only in that path.
- ✅ **D20 (mine) — Paste cap of 40,000 characters, refused with a message, never truncated.** A browser `maxLength` would silently cut a paste, which the owner's "never silent" rule forbids. Five example screenshots are about 6,000 characters.
- ✅ **D21 (mine) — Similarity is Jaccard over expanded tokens plus a head-noun bonus, threshold 0.3, at most one suggestion.** Tuned only against the brief's three examples and the four negatives; tolerates a wrong suggestion because the owner can switch (D4). Constants are in one place.
- ✅ **D22 (mine) — Phases.** Three PRs (A core, B screens, C editor + link); the entry link ships last so unfinished phases are unreachable.

### Resolved by reading the code (corrections and qualifications to the brief)

- **The API does not refuse a duplicate custom-exercise name.** The brief (§3, §4.4) says "A duplicate name is refused". There is no uniqueness rule: `exercise` has a partial unique index only on `catalog_key` for global rows (Spec 03.1), and `POST /v1/exercises` returns `201` for a repeated name. So "name already exists → Use it instead" is a **client-side** check (AC27) against the synced catalog; another device creating the same name between check and Save, or a lost response, can still produce a duplicate. D17's retry rule covers the second; the first is harmless (two same-named exercises) and tracked as O1.
- **`CreateExerciseForm` saves itself** (it calls `createCustom` on submit and owns Save/Cancel), so "reuse its fields" needs the extraction of D13.
- **`ExercisePicker` has a create row that creates at once** (D14).
- **`createCustom` is a direct `POST` today** — the brief's "doesn't go through the queueable path" is already true; AC31 pins it (D17).
- **The built-in list has ten exercises**; with it, nearly every name is New and the similar suggestion is for just a few (Overhead press, Dumbbell lunge, Treadmill run, …). The 500-custom-exercise cap is the realistic limit for heavy use (AC32).
- **The editor's draft holds quick vs plan items and cannot name a not-yet-created exercise**, hence D15; `Targets` has no weight, which is right for an import.
- **Spec 10.3 §12 O2 names a hypothetical "Spec 10.4"** (splitting the Note action) that was never created; this spec takes the number (§11 proposes a clarifying note).

### Open

- **O1 — Should the API refuse duplicate custom-exercise names?** *Recommendation: no, not in this spec.* The import's duplicate check is client-side (AC27) and covers the realistic case (the owner already has the exercise). A server rule would be a separate API spec: a case-insensitive unique index per user (or a pre-insert check), a `409`, a one-time scan of existing data for conflicts, an expand-only migration, and a decision about what happens to existing duplicates. It would also change Spec 03.2's contract and the picker's create flow. Cost of not doing it: an occasional duplicate name when two devices import at once, which #104 will let the owner delete. ✅ **Resolved (owner, 2026-10-19): client-side only.** No server uniqueness rule; this spec stays web-only.
