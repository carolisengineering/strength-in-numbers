# Spec 17.5 — Undo after a log, and a confirm on Delete set (web)

**Status:** v0.2 (2026-11-09), implemented on branch `feat/spec-17-5-undo-delete-set`; the AC26 phone check is owed. Built after Spec 17.4 (it uses 17.4's 44 px status line). The owner settled D2, D3 and D5 on 2026-11-08. §12 lists where the build departs from this text.

**Source:** the whole-app Impeccable critique of 2026-11-08 (23/40), step 2 of its agreed fix order. A decision marked "accepted recommendation" came from the drafting, and the owner accepted it on 2026-11-08.

**Design refs:** Spec 17.4 (status line, D5, AC10, AC12, AC13); Spec 17.1 AC14–AC15, AC29, AC39, AC41–AC42 (current exercise, bar, rest); Spec 06.1 §5.5 and D8 (set sheet, Delete); Spec 06.2 (outbox); Spec 06.5 (drafts); Spec 18.0 AC18 (`409 workout-would-be-empty`); `apps/web/PRODUCT.md` principle 2, "Never lose a set. Writes queue offline, drafts persist, and destructive actions confirm."

---

## 1. Purpose, scope & non-goals

**Purpose.** Make a mistaken log cheap to take back, and stop one tap from deleting a set for good. Today a wrong log costs two taps (open the set, Delete set), or three after the card has auto-advanced (select the exercise first). And Delete set removes the set at once, with no confirm and no undo, which contradicts "destructive actions confirm".

**In scope.**
1. An Undo button in 17.4's status line after each log, with the rules for what it does to the outbox, the rest timer, the current exercise, the draft and the bar.
2. An inline confirm on **Delete set**, in the live set sheet and in the edit screen's set sheet.

**Non-goals.**
- Undo for anything but the most recent log. No multi-step history, no redo.
- Undo on the edit screen (Spec 18.0): it has no Log button, and its writes are pessimistic.
- An Undo after Delete set (rejected, D5).
- Replacing dropdowns, a Warm-up toggle, the docked panel (later steps of the fix order).
- Any API, schema or `packages/core` change.

### Findings checked

| Finding | Verdict |
|---|---|
| `SetEditSheet.tsx:144,167`: Delete set deletes on one tap. | **Right.** `remove()` runs on the button's click; `EditSetForm.tsx` does the same. |

Only the **edit screen's** `useEditDeleteSet` is online-only (REST, Spec 18.0 D6). So Undo works offline on the live screen. |

## 2. Acceptance criteria

### Undo

1. **The offer.** After every successful log (queued or saved, any modality, including "Log extra set"), 17.4's status line shows "Set N logged · V" and an **Undo** button. N is the new set's `setNumber`. V is the Log button's label as it was, without "Log" ("47.5 × 6", "1:30", "20 cal", "32 kg · 40 m").
2. **It is the status line.** The line is a row: text on the left, Undo on the right. The text is 17.4's joined messages when any apply ("1 set not saved yet"), else the confirmation of AC1. When a sync message replaces the confirmation, Undo keeps its full name (AC12).
3. **A 44 px target.** Undo is at least `--tap-target-min` square and fits inside 17.4's status line (`--session-status-height`, 44 px). The bar's height and `--session-bar-clearance` don't change from 17.4.
4. **The button still doesn't move.** With 17.4's guarantee (AC10), the Log button's top is at the same y with no message, with a sync message, and with the Undo offer (a harness measurement, AC21).
5. **What Undo does.** One tap calls `useDeleteSet` on the offered set's id (the live, queued path: the same one Delete set uses). A set whose create was never sent is canceled with no request. A set the outbox has sent or may have sent gets a queued delete. The row leaves the card at once, as for Delete set today.
6. **Honest wording.** The line says "Set N undone" only when no op for that set remains in the outbox queue (an unsent create that was canceled, or a delete that has synced). While a delete is queued or sending it says "Undoing set N…". "1 set not saved yet" and the disabled Finish button follow the existing rules for any queued write. If the delete fails, the set comes back into view with the existing "Couldn't save" marks and SyncStatus actions, and the line says nothing of its own. No text says "deleted" or "removed" before the server has.
7. **Works offline.** With the device offline, Undo behaves as in AC5 and AC6 and needs no network.
8. **How long it stays.** The offer has no timer. It ends when: another set is logged (the new offer replaces it); the lifter taps another exercise; a sheet, menu, picker or Finish dialog opens; the set no longer exists (deleted or changed elsewhere); or the screen unmounts. It survives typing in the panel and auto-advance. It does not survive a reload (it is held in memory only, D2).
9. **The rest timer.** If the log started a rest and that rest is still the running one, Undo clears it. If the lifter has since started another, or the log cleared an earlier rest, the timer is left alone.
10. **The current exercise.** After Undo the logged exercise is current again, even if the log auto-advanced (including inside a superset). Its panel is revealed with `block: "nearest"`, no smooth behavior, and nothing steals focus (AC13).
11. **The draft.** The logged exercise's panel gets the undone set's own values (weight, unit, reps, set type; RPE stays blank) as its draft, so a mistaken Undo costs one Log tap. If the panel already holds an edited draft, that draft is kept and the undone values are dropped. The restored draft is a prefill, not an edit: `set_logged.edited` is false for a log of it, as in 17.4 D3. `seedDraft` itself is unchanged, and the re-seed that follows a smaller set count does not overwrite the restore. The next log's draft follows 17.4's rules from the new last set.
12. **Finish mode.** If the log was the last planned set and the bar read "Finish workout", Undo returns it to "Log …" with focus unchanged, and the one-primary-`Button` rule holds (17.1 AC39: Undo is a `secondary` or quieter variant).
13. **Focus and announcement.** Focus stays on the bar's Log button when Undo is tapped by pointer. When it is activated by keyboard, Undo unmounts, so focus moves to the Log button. The result is announced once, politely, through the screen's existing live region ("Set N undone", or "Undoing set N" then "Set N undone"). The status line's own text is not a live region, so the log is not announced twice. Undo's accessible name is "Undo set N, V, {exercise}".
14. **Double taps.** Undo targets the set it was offered for, never "the last set". A second tap on Undo, or a double tap, deletes nothing more: the offer ends on the first tap. A double tap on Log (17.1's 600 ms window) never makes a second offer. A tap on Undo ends the window, so a Log tap right after it logs.
15. **Mis-tap guard.** Undo sits on the right of the line, apart from the full-width Log button, with at least `--space-2` between their boxes (a harness measurement). Because of AC11, an accidental Undo is repaired by one Log tap.
16. **Keyboard up.** While `data-keyboard="open"` is set, the line takes space only while Undo is offered or a message shows (17.4 AC12).
17. **Telemetry.** An Undo emits `set_deleted` with a new boolean `viaUndo: true`. The Delete set button's event carries `viaUndo: false`. No other field is added.

### Delete set

18. **Inline confirm.** In the set sheet (live and edit screen), the first tap on **Delete set** replaces the Delete / Save row with a confirm: the text "Delete set 3? 47.5 kg × 6 will be removed.", a secondary **Keep set** (it takes focus) and a danger **Delete set**. No nested dialog. Keep set returns to the form with the typed values untouched. Close and Escape close the sheet as today.
19. **One tap commits.** The second Delete set runs today's `remove()`, unchanged: live it is queued and the sheet closes at once; on the edit screen it waits for the server and shows its failures in the sheet.
20. **The last set.** The edit screen's `409 workout-would-be-empty` still opens "Delete this whole workout instead?" after the confirm (no client pre-check, 18.0 D6). The confirm's text does not mention it.
21. **No undo after Delete.** Nothing offers to bring a deleted set back (D5).

### Must keep, docs and verification

22. **Regression guards.** The 600 ms window across a panel swap, focus on the bar's button, one primary `Button`, offline queueing and "Not saved yet" on rows, 17.4's reserved line, and Set options are unchanged. Existing tests pass, with changes only where this spec amends a criterion (§12, Cross-doc updates).
23. **Docs consistent.** The cross-doc updates in §12 are made.
24. **Every behavioral AC has a tagged test.** AC1–AC22 have ≥1 test named `17.5 ACn — …`, enforced by an `acTags.17-5.test.ts` scan.
25. **Visual review.** `pnpm --filter @sin/web run screens` captures the bar with the Undo offer, with a sync message plus Undo, and in Finish mode, light and dark, at 390 and 1280 px and at 320 × 568; and the inline confirm in the live and edit sheets. The harness fails the run if the Log button moves (AC4) or Undo overlaps it (AC15).
26. **Phone check (owner).** On the iPhone: log a set, tap Undo, confirm the values come back and one tap re-logs them; log with wifi off and Undo; log the last set of an exercise in a superset and Undo; try Delete set and Keep set.

## 6. Behavior & logic

### 6.1 The offer

`EntryRow` already calls `onLogged` last. `LoggedEvent` gains the logged `set` (it has it) and what `onLogged` needs to store an offer in `ActiveSession` state: `{ setId, exerciseId, set, label, advancedTo, restStartedAt }`. `restStartedAt` is read from `rest.get()` right after `rest.start(...)`, or `null` when the log cleared or did not start a rest. `setId` is the id the log returned (the client key for a queued set), which `queuedWorkoutClient.deleteSet` already resolves through `exerciseOfSet`.

### 6.2 Undo

1. End the offer first (synchronously), so a double tap does nothing more.
2. `deleteSet.mutateAsync({ id: setId, modality })`.
3. If `rest.get()?.startedAt === restStartedAt` and it was set, `rest.clear()`.
4. If the lifter has not chosen elsewhere (they cannot have: choosing ends the offer), make `exerciseId` current again.
5. Hand the exercise's panel the undone set as a restore. The panel applies it as a `reset` from that set (the reducer already has `reset: from: SetEntry`) unless its draft is touched.
6. Focus the Log button if focus was on Undo; announce.

### 6.3 Why Undo is a delete, not a delay

Holding a log back for a few seconds before sending it would make "Undo" free, but a set would be unsaved on purpose, the outbox's "never sent" state would be a timer, and a reload or a dead battery inside the window would lose the set. That breaks "Never lose a set". A real delete through the existing queue is already honest: the outbox cancels an unsent create, and queues a delete otherwise.

### 6.4 The inline confirm

`EditForm` (live) and `EditSetForm` (edit) hold one `confirming` state. `remove()` is unchanged and runs from the confirm's Delete set. While confirming, Save is hidden and the fields stay (so Keep set loses nothing).

## 7. Security & privacy

No new data, storage, request or log. `viaUndo` is a boolean. The offer holds the set's values in memory only, like any draft, and is never written to storage (so logout needs no new key).

## 12. Decisions & open questions

- ✅ **D1 — Undo is a real delete in the status line (owner, 2026-11-08, accepted recommendation).** **Rationale:** it reuses the outbox's cancel-or-delete rules, works offline, and keeps the set safe the moment it is logged (6.3). **Rejected:** delaying the send (loses sets on a crash); a toast outside the line (a second moving layer over the bar).
- ✅ **D2 — No timer; the offer ends on a deliberate action (owner, 2026-11-08).** A transient message is hard to reach for a slow reader or a screen-reader user (WCAG 2.2.1), and a rest is when a lifter notices a mistake. Held in memory, so a reload ends it; the set sheet is still there. **Rejected:** a 5–10 s window.
- ✅ **D3 — The status line is 44 px, always (owner, 2026-11-08; Spec 17.4 D5).** It costs about 23 px more of list height than a 21 px line on every workout screen, in exchange for a 44 px Undo and a Log button that never moves (17.4 D5). **Alternative:** a 21 px line whose Undo has a 44 px hit area reaching up into the list. It saves the 23 px, but the target is invisible and overlaps the content above the bar.
- ✅ **D4 — Undo puts the values back in the panel (owner, 2026-11-08, accepted recommendation).** It turns an accidental Undo into one tap, which is the mis-tap guard for a button sitting above Log. **Rejected:** a plain delete (one slip loses a set's numbers).
- ✅ **D5 — Delete set gets an inline confirm, not an Undo (owner, 2026-11-08).** PRODUCT.md says destructive actions confirm. An undo after Delete would have to re-create the set: on the live screen it would get a new id and move to the end, and on the edit screen it cannot work offline and would redo records. **Rejected:** a `ConfirmDialog` stacked on the sheet's own `<dialog>` (two modals, and focus returns to the sheet's opener). The same control on both screens keeps the habit consistent.
- ✅ **D6 — Undo covers the latest log only.** More would need a history list the screen does not have.

**Settled (owner, 2026-11-08, accepted recommendation): each recommendation below was taken.**
- **O2.** Should Undo also clear a rest that the log started when the lifter has already started typing? I clear it (AC9), because the set did not happen.

**Where the build departs from this text (2026-11-09).**
- §6.2 step 5: not `reset`, which always makes a working set (against AC11). A new `restore` draft action, built on `draftForEdit`, keeps the set type and mints a new attempt key.
- AC15 against AC3: a 44 px Undo that fills the 44 px line would sit 4 px from Log (the bar's `row-gap`), and growing the gap would move the bar. Undo sits 4 px up into the bar's top padding (`margin-block: calc(-1 * var(--space-1)) var(--space-1)`); its margin box is still 44 px.
- AC6, "the set comes back into view": a rejected delete now re-reads `/active` (`onFailed`), because the optimistic removal had taken the row out of the cache. A rejected create does too, because it fails any delete queued behind it without naming that delete.
- AC13, focus: if focus sits in the card Undo collapses, it moves to Log, as it does from Undo itself. AC13, announcing: a live region says nothing when its words don't change, so Undo clears the screen's region at the tap and a restore clears the panel's. An undo, re-log and undo is then announced each time.
- AC14: `EntryRow`'s own `lastLoggedAt` guard is reset by a restore; `LogBarButton`'s window already reset on any input outside it.
- §3 and §6.1: no `retreatTo` and no `advancedTo`: `select` and 17.4's `setsAwaited` reveal do it. The offer is held in `useUndoLastLog`, not `ActiveSession`, and shows once its row is listed (the row renders after `onLogged` runs).
- AC1's carry example: on a kg profile the Log label, and so V, reads "32 · 40 m"; the unit shows only when it differs from the profile.
- AC6: the line reads "Undoing set N…" until the delete has reached the queue, and a failed delete forgets the Undo, so discarding it later can't read as "undone".
- Choices the text left open: "[undo line] · [17.4's messages]" share the line while Undo's result shows; text is left-aligned only while Undo shows; a card's Options doesn't end the offer, the Workout menu does; a log that lands after the lifter moved on still offers; Keep set returns focus to Delete set, and so does a failed delete.
