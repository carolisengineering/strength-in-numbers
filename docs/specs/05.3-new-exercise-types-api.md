## 1. Purpose, scope & non-goals

### Purpose

The app can log reps, bodyweight reps, added-weight reps, a time, and a distance with a time. It cannot log a **calorie** count (an Echo Bike was logged as "duration" with calories typed as minutes), a **weight carried for a distance** (farmer carries) or a **weight held for a time** (a weighted sandbag hold). This spec makes the server and `@sin/core` able to hold, validate, record and chart those three kinds, everywhere the existing five are usable on the API side. The UI follows in a later spec.

| Type (`modality`) | Logs | PRs | Example |
|---|---|---|---|
| Calories (`calories`) | calories only, whole numbers, no time | most calories | Echo Bike |
| Weight + distance (`weight_distance`) | weight (the **total** carried) + distance | heaviest load, longest distance | farmer carries |
| Weight + duration (`weight_duration`) | weight + time | heaviest load, longest hold | weighted sandbag hold |

**Success:** every route that accepts or returns a set, an exercise, a routine item, a record, a progress point, a History row or the export handles the three values with no special casing outside the rule tables in `@sin/core`; and an existing user's data, records and responses are unchanged byte for byte except for the new fields.

### In scope

- `MODALITY_VALUES` gains `calories`, `weight_distance`, `weight_duration`; `MEASURE_RULES` gains three rows and a fourth-to-fifth measure, `calories` (§6.1).
- `set_entry.calories` (migration `0015`), the set DTOs, the set write / read / finish-check statements, finished-workout edit integrity, export.
- Routine targets and planned sets for the new types (derived from the rules; no calorie targets: FI-11).
- Records: three new record types (`max_calories`, `max_distance`, `max_duration`), `heaviest_weight` widened to the two weighted types, new units, the widened type-to-unit CHECK, the `records.ts` math, the loader, the finished-edit predicate (§6.2–§6.4).
- The progress series gains three nullable metrics (§5.2).
- **Feet (O4):** `ft` joins `DISTANCE_UNIT_VALUES`; `0015` widens the unit CHECK and rebuilds the generated `distance_m` with an explicit `ft` arm (§4, §6.10); the unit is shared by every modality that carries a distance.
- Routine-from-text: a `Max Cal …` line or a leading calorie line (`20 Cal Row`) makes the exercise a Calories guess (§6.7).
- DESIGN.md vocabulary, README row, runbook entry.
- **Web compile-compatibility only** (§3.3): the minimal `apps/web` edits that keep `typecheck` / `lint` / unit tests green when `@sin/core`'s unions widen, with no visible behavior change.

### Non-goals

- **Any new UI behavior**: the create form still offers five types, no calories input, no new labels shown to users (the UI spec, §3.2 lists its consumers).
- **Records for the existing `duration` and `distance_duration` types** (design non-goal). They still have none.
- **Calorie targets in routines** (FI-11). A Calories routine item carries a set count and set types only.
- **The type-change rule, the exercise page / list / edit / delete, "routines that use an exercise"** (the next API spec). `PATCH /v1/exercises/{id}` keeps its current behavior, now with eight values.
- **The Echo Bike data fix** (a one-off, after this is live on staging).
- **Built-in catalog rows** for the new types (D13, owner ruling). A built-in exercise pass is happening under another issue (likely #117); nothing is added here.
- **Any distance unit other than feet** (yards, furlongs): feet are the only addition (O4). **A unit for calories, per-hand carry weight, bodyweight-inclusive loads.** Weight on the two weighted types is the total carried, exactly like `weight_reps`'s weight is the bar load (D4).
- **New routes, methods, rate-limit groups or lock keys.** None (D12).

### Fit for one work session

The work is wide rather than deep: one migration, one rule table, three small branches in `records.ts`, mechanical plumbing of one column through about eight statements, and a one-line reader hint. It fits one long session as **two PRs at the phase boundary**, the way 07.4 did:

- **Phase A: vocabulary, storage, set logging.** Enums (modality *and* record vocabulary, because the migration's CHECKs render from them), `MEASURE_RULES`, the `calories` column, the `ft` unit and the `distance_m` rebuild, DTOs, set writes, finish and edit integrity, routines, export, the web compile-compat edits, the migration and its tests. Useful alone: the three types can be created and logged through the API. No record is produced for them yet.
- **Phase B: records, progress, reader.** `records.ts`, loader, predicate, series, `guessModality` hint. Needs no migration.

If the session runs out, the cut is that boundary, not a spec split.

## 2. Acceptance criteria

Every behavioral criterion has at least one test whose `describe` is tagged **`"05.3 ACn — …"`**; infra criteria are verified by CI. §10 maps each to a method. "New types" means `calories`, `weight_distance`, `weight_duration`; "legacy types" means the five that exist today.

### Phase A: vocabulary, storage, set logging

1. **Modality vocabulary.** `MODALITY_VALUES` is exactly `weight_reps, bodyweight_reps, weighted_bodyweight, duration, distance_duration, calories, weight_distance, weight_duration` (legacy order kept, new values appended). `Modality`, `CreateExerciseSchema`, `UpdateExerciseSchema`, `WorkoutExerciseSchema.modalitySnapshot` and the catalog seed schema accept all eight and reject anything else.
2. **Record vocabulary.** `RECORD_TYPE_VALUES` is the four legacy values, then `max_calories`, `max_distance`, `max_duration`; `RECORD_UNIT_VALUES` is `kg, kg_reps, reps, cal, m, s`; `RECORD_UNIT_BY_TYPE` maps `max_calories`→`cal`, `max_distance`→`m`, `max_duration`→`s` and leaves the legacy four as they were. `PersonalRecordSchema` accepts all of them.
3. **Measure rules.** `MEASURE_NAMES` is `reps, weight, distance, durationS, calories`. `requiredMeasuresFor` / `forbiddenMeasuresFor` return the §6.1 table for all eight modalities; every legacy modality now also forbids `calories` and otherwise keeps today's rows exactly.
4. **Calories on the wire.** `SetEntrySchema.calories` is a required-nullable integer `0 … 32767`; `CreateSetSchema` / `UpdateSetSchema` accept `calories` as an optional nullable integer in the same range. A non-integer, a negative, a value above `SET_CALORIES_MAX` or a string is `422` with a static message; an unknown key is still `422`.
5. **Exercise writes accept the new values.** `POST /v1/exercises`, the `POST /v1/exercises/{id}/fork` overlay and `PATCH /v1/exercises/{id}` accept each new modality and return it; `GET /v1/exercises` serves it unchanged in shape; a ninth value is `422`; a user cannot read or write another user's exercise of a new type (`404`).
6. **Calories sets.** On a `calories` workout exercise, `POST …/sets` with `{ calories: 20, isComplete: true }` is `201` and echoes `calories: 20` with `reps`, `weight`, `weightKg`, `distance`, `distanceM`, `durationS` all `null`; `PATCH /v1/sets/{id}` changes and clears it; `DELETE` removes it; a replayed `clientGeneratedId` answers `200` with the stored set. A set on another user's workout exercise is `404`.
7. **Weight + distance sets.** `{ weight: 24, weightUnit: "kg", distance: 40, distanceUnit: "m", isComplete: true }` is `201`; `weightKg` and `distanceM` are the generated canonical values (`lb` and `km` / `mi` / `ft` convert as for the legacy types); a complete set without `weight` or without `distance` is `422` naming the missing field(s); `reps`, `durationS` and `calories` are `422` not-allowed.
8. **Weight + duration sets.** `{ weight: 20, weightUnit: "kg", durationS: 90, isComplete: true }` is `201`; a complete set without `weight` or without `durationS` is `422` naming them; `reps`, `distance` and `calories` are `422` not-allowed.
9. **The forbidden and half-filled matrix.** For every modality and every measure in its forbidden list a write is `422` with `path` = the field and a message naming the modality (today's wording pattern); `calories` is `422` on each of the five legacy modalities; unit pairing errors still come first and alone; a live, incomplete (`isComplete: false`) set on a new type may be half-filled (even empty); `rpe` is accepted on every modality.
10. **Finish integrity.** Finishing a workout whose `working` set lacks a measure its modality requires is `409 incomplete-working-sets`, for each new type (calories missing; weight or distance missing; weight or duration missing); the same workout with the measures present finishes `200`; a `warmup` / `drop` / `failure` set with nothing in it never blocks.
11. **Finished-workout edit integrity** (07.4 AC9 for the new types). In finished mode a create or patch that leaves a `working` set of a new type without a required measure is `422` naming the missing fields, nothing written; the other three set types stay exempt; `completed_at` clamping and `409 workout-would-be-empty` are unchanged.
12. **Routine targets and planned sets.** A routine item of `weight_distance` or `weight_duration` accepts `sets` rows with `weight` + `weightUnit` and no reps; a row carrying `repsLow` / `repsHigh` is `422` (`plannedSetViolations`, `not allowed for this exercise type`). A `calories` item accepts `sets` rows holding only a set type and refuses `weight`, `weightUnit` and reps the same way. The legacy quick-line `targetRepsLow` / `targetRepsHigh` is `422` for all three; `targetSets`, `targetRpe`, `restSeconds` and `notes` work on all three. The start copy snapshots such an item, its `workout_planned_set` rows and a `modality_snapshot` of the new value.
13. **Snapshots.** Starting a workout from a routine and `POST /v1/workouts/{id}/exercises` store the exercise's modality in `workout_exercise.modality_snapshot` for the new values; a later `PATCH /v1/exercises/{id}` changing the modality does not change an existing snapshot (regression).
14. **Export.** `GET /v1/account/export` includes `calories` on every set and the new modality values on exercises and workout exercises, produced by the shared mappers (no hand-mapped field in the export); a calories set round-trips equal to `GET /v1/workouts/{id}`.
15. **History volume.** `setVolumeMilli` is `null` for the three new types whatever the measures; a finished workout containing only new-type sets appears in `GET /v1/workouts` with its exercise names and working-set count and `totalVolume: null`; a workout mixing a legacy `weight_reps` set and a new-type set has the legacy sets' volume only. The History row shape is unchanged.
16. **Migration `0015`.** Applied to a database with data: `set_entry.calories` exists, nullable, no default, `SMALLINT`, with a non-negative CHECK; `set_entry_distance_unit_check` accepts `ft` and still rejects any other unit (AC40); `exercise` and `workout_exercise` accept the three new modalities and still reject a ninth value; `personal_record` accepts the three new types with their units, rejects a mismatched pair (`max_calories` with `kg`) and a unit outside the list; `personal_record.value` / `previous_value` are `NUMERIC(14,3)`; existing rows are untouched; the migration is re-runnable only via the migrate tooling (no data statements).
17. **Drift guards.** Unit tests render `MODALITY_VALUES`, `RECORD_TYPE_VALUES`, `RECORD_UNIT_VALUES` and one type-to-unit clause per `RECORD_UNIT_BY_TYPE` entry verbatim from `0015`'s SQL; `0002`, `0005` and `0008` keep a frozen legacy list in their guards (they describe history, not the live constraint). The `0006` guard (`set-entry-migration-drift-guard.test.ts`) likewise freezes `m, km, mi` for its CHECK, and a new guard renders `DISTANCE_UNIT_VALUES` into `0015`'s `set_entry_distance_unit_check` and the four conversion constants (`1000`, `1609.344`, `0.3048` from `KM_TO_M`, `MI_TO_M`, `FT_TO_M`; `m` is the identity arm) into the rebuilt `distance_m` expression (AC40).
18. **No schema drift.** `schema.prisma` carries `SetEntry.calories`, `PersonalRecord.value` / `previousValue` as `Decimal(14,3)`; the whole-schema `prisma migrate diff` after all migrations reports only the two generated `set_entry` columns. This check moves from `workout-sections-migration` (0014) into `0015`'s integration test.
19. **OpenAPI and the static-message gate.** `/openapi.json` shows the eight-value `modality` enum, `calories` on `SetEntry` / create / update, and the widened record enums; no route is added or republished; `packages/core/test/static-issue-messages.test.ts` passes with `calories` in the probed schemas (every message fixed text).
20. **Telemetry.** `sin.sets.logged` carries the new modality values as its `modality` attribute (a bounded enum); `telemetry/allowlist.ts` and `views.ts` need no change, and a test asserts the attribute for a calories set.
21. **Web compile-compatibility.** With the widened unions, `pnpm run typecheck`, `pnpm run lint` and the web unit tests pass with only the §3.3 edits; the web create-exercise form still lists exactly the five legacy modalities; no other web behavior changes, with one deliberate exception: the two distance-unit selects in `SetFields.tsx` list `DISTANCE_UNIT_VALUES` (so they gain `ft`, D20) and a set typed in feet displays through the existing `withUnit` ("40 ft"); a web unit test pins the create-form list and the select options.

*Feet (O4). Numbered 39-41 and appended so the approved plans' AC citations stay valid; AC39-AC40 belong to Phase A, AC41 to Phase B.*

39. **Feet vocabulary and conversion.** `DISTANCE_UNIT_VALUES` is exactly `m, km, mi, ft` (legacy order kept, `ft` appended); `@sin/core` exports `FT_TO_M = 0.3048` (exact), `ftToM` and `mToFt`; `toCanonicalMeters(v, "ft")` is `v * FT_TO_M` and still throws on any other unit (`yd`). `SetEntrySchema`, `CreateSetSchema` and `UpdateSetSchema` accept `distanceUnit: "ft"` and reject `"yd"` with a static `422`; the unit-with-value pairing rule and `SET_DISTANCE_MAX` apply unchanged. The unit is accepted for every modality that carries a distance (`distance_duration` and `weight_distance`; D18); on a modality that forbids `distance` it is refused like any distance.
40. **Feet in the database.** On a database populated by `0001`-`0014`, applying `0015` leaves every existing row's `distance_m` identical (a before / after comparison over `m`, `km`, `mi` and null rows). After it: an `ft` set stores `distance_m` = `distance * 0.3048` rounded to `numeric(9,3)` (40 ft gives 12.192; 100 ft gives 30.48; 0.001 ft gives 0.000; 999999.999 ft fits); a `distance_unit` of `yd` is rejected by the CHECK; a row with a `distance` and a NULL `distance_unit` has a NULL `distance_m` (there is no catch-all arm); `distance_m` is still `numeric(9,3)`, `GENERATED ALWAYS ... STORED`, the table's indexes are unchanged, and through the HTTP API an `ft` set on a `weight_distance` and on a `distance_duration` exercise returns `distanceUnit: "ft"` and the generated `distanceM`.

### Phase B: records, progress, reader

22. **Eligibility matrix.** `setRecordValueMilli(type, set)` over all seven types by all eight modalities, with boundary values (null, 0, 1, a large value), returns exactly the §6.2 table: `best_est_1rm`, `best_set_volume` and `max_reps` are unchanged and never produced for a new type; `heaviest_weight` is produced for the two weighted types only with its second measure `> 0` and weight `> 0`.
23. **Calories records.** `computeRecords` over `calories` sets yields one `max_calories` record (unit `cal`, value = calories × 1000 milli), the earliest set wins a tie, `previousValueMilli` is the best of strictly earlier workouts, and no other type.
24. **Weight + distance records.** Yields `heaviest_weight` (kg) and `max_distance` (unit `m`, canonical meters from `distance_m`, whatever unit was typed: `m`, `km`, `mi` or `ft`), holders independent (the heaviest set and the longest set may differ); never e1RM, set volume or max reps.
25. **Weight + duration records.** Yields `heaviest_weight` (kg) and `max_duration` (unit `s`, seconds × 1000 milli), holders independent; never e1RM, set volume or max reps.
26. **Legacy records unchanged.** Every existing `records.test.ts` and `records-property.test.ts` expectation passes unmodified apart from the predicate's added `modality` field (AC29); `duration` and `distance_duration` still produce no records; a mixed lineage (sets under different `modality_snapshot`s) evaluates each set under its own snapshot.
27. **Persistence is exact and fits.** `recomputeRecordsForRoots` writes `max_calories` = `20.000`, `max_distance` = `40.000`, `max_duration` = `90.000` for the matching sets and reads them back as the JSON numbers 20, 40, 90; a `weight_duration` set of `2147483647` seconds (the DTO maximum) finishes without a numeric overflow and records `2147483647`; the DB rejects a hand-inserted mismatched type/unit pair.
28. **Recompute paths.** Finishing and deleting a workout, and `records:rebuild` (all users and `--user`), produce the new records; rebuild is idempotent and equals the live path's rows; the finish response's `newRecords` and `GET /v1/personal-records` (with `exerciseId` / `workoutId` filters) return them with correct `previousValue`.
29. **Finished edits follow.** `setChangeAffectsRecords` takes the set's modality and compares only the measures that modality's records read (§6.4): a change to `calories` of a calories set, to `weight` / `distance` of a `weight_distance` set, to `weight` / `durationS` of a `weight_duration` set, or a type change to or from `working`, recomputes the lineage in the edit's transaction; an `rpe`, `isComplete` or other inert change recomputes nothing; a `distance` / `durationS` change on a **legacy** `distance_duration` / `duration` set still recomputes nothing (07.4 AC8 holds). The truth table is unit-tested exhaustively.
30. **Lock order.** New-type finishes and finished-mode edits take `lockUserRecords` first via the existing paths; one real-concurrency test (a calories finish against a finished-mode edit of another calories workout, `Promise.all`) ends in a serial outcome with no `500` / `40P01` and a `personal_record` table equal to a full recompute.
31. **Progress series shape.** `ProgressPointSchema` gains required-nullable `maxCalories` (number, integer), `maxDistance` (meters), `maxDuration` (seconds, integer). For a `calories` lineage only `maxCalories` is non-null; for `weight_distance`, `topSetWeight` and `maxDistance`; for `weight_duration`, `topSetWeight` and `maxDuration`; every other metric is `null`. For a legacy lineage the three new fields are `null` and the four existing values are identical to before.
32. **Series max equals the PR.** Over a lineage's full history the maximum of `topSetWeight`, `maxCalories`, `maxDistance` and `maxDuration` equals the `heaviest_weight`, `max_calories`, `max_distance`, `max_duration` record value (07.2 AC14 extended); a `from` / `to` range changes which points appear, never a point's values (07.2 D10).
33. **History badge.** `recordCount` on `GET /v1/workouts` counts a workout's `max_calories` / `max_distance` / `max_duration` / `heaviest_weight` records on new-type exercises (the 07.3 predicate, which excludes only `best_set_volume`, is unchanged) and equals the finish summary's count.
34. **Reader hint.** For the text `Max Cal Echo Bike with remaining time` (and `Max Calories …`), `readWorkoutText` returns the item named `Echo Bike` and a `ReadName` with `calories: true`; a name with no calorie form has `calories: false`; `Max Reps …` and a bare `Max …` set no hint. The leading calorie form is AC36-AC38. `guessModality("Echo Bike", { calories: true })` is `calories`, also for names that contain a distance word (`Row`, `Bike`, `Run`), and `guessModality(name)` with no hint is exactly today's result for every existing test case. In `buildImportPlan` a `calories`, `weight_distance` or `weight_duration` item refuses reps into a note ("… reps as written") and never emits a weight.
35. **Core surface.** New exports are in `packages/core/scripts/check-exports.mjs` and the barrel type test; `pnpm run core:purity` passes (no DOM / Node imports); `parseWeightKgMilli` keeps its name and behavior and gains the alias `parseDecimalMilli` used for meters.
36. **Leading calorie lines.** Under an open run and as a bare bullet, a line that starts with a whole number of 1-4 digits, optional space, `Cal` / `Cals` / `Calorie` / `Calories` (any case) and then a movement is read as that movement with the calories hint, the measure kept as the item's note, and no reps or target. Exact examples (each in a run such as `3 Sets:` or after a `- ` bullet):
    - `20 Cal Row` gives name `Row`, `noteLines: ["20 Cal"]`, rows with `repsLow: null, repsHigh: null`, `ReadName.calories: true` (never 20 reps of `Cal Row`).
    - `15 Cals Ski Erg` gives name `Ski Erg`, note `15 Cals`.
    - `12 Calories Echo Bike` gives name `Echo Bike`, note `12 Calories`.
    - `20cal Row` gives name `Row`, note `20cal`.
    - `- 20 Cal Row` (bullet, no run) is a rowless item named `Row` with note `20 Cal`, `quickReps: null`.
    The number is never a planned target (no calorie targets, FI-11); it survives only in the note. `guessModality("Row", { calories: true })` is `calories`.
37. **Leading-calorie non-matches are unchanged.** Each of these reads exactly as it does today: `20 Row` (reps), `20 Cal` (no movement), `Cal Ripken Drill` and `Row 20 Cal` (bare or trailing "Cal"), `10-15 Cal Row` (a range), `20 Cal Row + 15 Burpees` (a `+` pair is left to the existing pair rule), `200 Meter Run` and `2 Min Plank` (other leading measures keep their measure in the name and note), and `20 Calf Raises` ("Calf" is not "Cal" / "Cals"). They set no hint.
38. **Both fixtures still read as their example tests say.** `hiraya-2026-10-19.txt` and `hiraya-2026-10-24.txt` read with every existing example-test expectation unchanged. The only difference is the new `calories` field: `true` for the `Echo Bike` name read from `Max Cal Echo Bike with remaining time`, `false` elsewhere. (Grepped: the only `Cal` lines in the 10-24 fixture are `Max Cal …` forms and prose; the 10-19 fixture has none; no fixture line starts with a number followed by Cal.)
41. **Feet in the reader.** `ft` (the abbreviation only) is a distance unit word like `m`: `100 ft Farmer Carry` reads as a named line `100 ft Farmer Carry` with the note `100 ft`, never as 100 reps of `ft Farmer Carry`, in the same places `400 Meter Run` is handled; `guessModality("100 ft Farmer Carry")` and `guessModality("100ft Sled Push")` are `distance_duration` (the leading-distance rule, as for `m`); and the match key drops a bare `ft` word like `m`. `feet` and `foot` are **not** unit words (real exercise-name words: "Rear Foot Elevated Split Squat", "Feet Elevated Push-up"). Every existing `guessModality`, `UNIT_WORD` and match-key test passes unmodified, and both fixtures (which contain no `ft`, `feet` or `foot`) still read as their example tests say.

## 4. Data model

One migration, hand-authored (CHECK lists are not expressible in the Prisma DSL, so the `.sql` is the source of truth and the model carries the client shape; 05.0 §4 / 03.1 `0002` carve-out). Migration directory `0015_new_exercise_modalities`. Expand-only in effect: one nullable column, widened CHECKs, one metadata-only numeric widening, and one **same-name, same-type rebuild of the generated column `set_entry.distance_m`** (the one step that is not strictly additive; D18). No data statements, no backfill.

```sql
-- Spec 05.3 §4 — 0015_new_exercise_modalities. Additive, expand-only.
-- Down (dev/test teardown only; production undo is `git revert` + a forward migration):
--   ALTER TABLE "set_entry" DROP CONSTRAINT "set_entry_calories_check";
--   ALTER TABLE "set_entry" DROP COLUMN "calories";
--   (the widened CHECKs, NUMERIC(14,3) and the rebuilt distance_m may stay; see §11 for the rows that block a code rollback)

ALTER TABLE "set_entry" ADD COLUMN "calories" SMALLINT;
ALTER TABLE "set_entry" ADD CONSTRAINT "set_entry_calories_check"
    CHECK ("calories" IS NULL OR "calories" >= 0);

-- Feet (O4, D18). The CHECK alone is NOT enough: 0006's expression ends in `ELSE distance * 1609.344`,
-- so an 'ft' row would be computed as miles. Postgres 16 has no ALTER COLUMN ... SET EXPRESSION
-- (that is PG17), so the generated column is dropped and re-added, in this transaction, with every
-- unit named and no catch-all. No CASCADE: if anything depended on distance_m the DROP would fail.
ALTER TABLE "set_entry" DROP CONSTRAINT "set_entry_distance_unit_check";
ALTER TABLE "set_entry" ADD CONSTRAINT "set_entry_distance_unit_check"
    CHECK ("distance_unit" IN ('m', 'km', 'mi', 'ft') OR "distance_unit" IS NULL);
ALTER TABLE "set_entry" DROP COLUMN "distance_m";
ALTER TABLE "set_entry" ADD COLUMN "distance_m" NUMERIC(9,3) GENERATED ALWAYS AS (
    CASE WHEN "distance" IS NULL THEN NULL
         WHEN "distance_unit" = 'm'  THEN "distance"
         WHEN "distance_unit" = 'km' THEN "distance" * 1000
         WHEN "distance_unit" = 'mi' THEN "distance" * 1609.344
         WHEN "distance_unit" = 'ft' THEN "distance" * 0.3048
    END) STORED;

ALTER TABLE "exercise" DROP CONSTRAINT "exercise_modality_check";
ALTER TABLE "exercise" ADD CONSTRAINT "exercise_modality_check" CHECK ("modality" IN
    ('weight_reps', 'bodyweight_reps', 'weighted_bodyweight', 'duration', 'distance_duration',
     'calories', 'weight_distance', 'weight_duration'));

ALTER TABLE "workout_exercise" DROP CONSTRAINT "workout_exercise_modality_snapshot_check";
ALTER TABLE "workout_exercise" ADD CONSTRAINT "workout_exercise_modality_snapshot_check" CHECK ("modality_snapshot" IN
    ('weight_reps', 'bodyweight_reps', 'weighted_bodyweight', 'duration', 'distance_duration',
     'calories', 'weight_distance', 'weight_duration'));

ALTER TABLE "personal_record" DROP CONSTRAINT "personal_record_record_type_check";
ALTER TABLE "personal_record" DROP CONSTRAINT "personal_record_unit_check";
ALTER TABLE "personal_record" DROP CONSTRAINT "personal_record_type_unit_check";
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_record_type_check" CHECK ("record_type" IN
    ('heaviest_weight', 'best_est_1rm', 'best_set_volume', 'max_reps',
     'max_calories', 'max_distance', 'max_duration'));
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_unit_check" CHECK ("unit" IN
    ('kg', 'kg_reps', 'reps', 'cal', 'm', 's'));
ALTER TABLE "personal_record" ADD CONSTRAINT "personal_record_type_unit_check" CHECK (
       ("record_type" = 'heaviest_weight' AND "unit" = 'kg')
    OR ("record_type" = 'best_est_1rm' AND "unit" = 'kg')
    OR ("record_type" = 'best_set_volume' AND "unit" = 'kg_reps')
    OR ("record_type" = 'max_reps' AND "unit" = 'reps')
    OR ("record_type" = 'max_calories' AND "unit" = 'cal')
    OR ("record_type" = 'max_distance' AND "unit" = 'm')
    OR ("record_type" = 'max_duration' AND "unit" = 's'));
ALTER TABLE "personal_record"
    ALTER COLUMN "value" TYPE NUMERIC(14,3),
    ALTER COLUMN "previous_value" TYPE NUMERIC(14,3);
```

- **Every place a modality list is rendered in SQL** (survey of all migrations): `exercise_modality_check` (`0002`) and `workout_exercise_modality_snapshot_check` (`0005`); nowhere else (`routine*`, `workout_planned_set`, `set_entry` carry none). The type-to-unit CHECK for records already exists (`0008`, `personal_record_type_unit_check`); this migration extends it rather than adding a second.
- **The `distance_m` rebuild (D18, AC40).** Nothing else depends on the column: every migration was grepped and only `0006` names it; no index, view, constraint or trigger uses it (`set_entry` has the primary key, the `(workout_exercise_id, set_number)` and `(workout_exercise_id, client_generated_id)` unique indexes, and the FKs); the Prisma model maps it as a plain `Decimal?` (`@map("distance_m") @db.Decimal(9, 3)`, no `Unsupported`), so `schema.prisma` and the no-drift report are unchanged. Cost: `ADD COLUMN ... GENERATED ... STORED` rewrites `set_entry` (and rebuilds its indexes) under `ACCESS EXCLUSIVE`, so reads and writes of sets wait for the few milliseconds the rewrite takes at this app's size; the DDL is transactional, so no other session ever sees the column missing. Two side effects the builder must check: the column moves to the end of the physical column order (every statement names its columns through `SET_ENTRY_COLUMNS`, no `SELECT *` was found; if `set-entry-migration.integration.test.ts` asserts an ordered column list it relaxes to a set), and a row with a `distance` but a NULL `distance_unit` (the API's pairing rule forbids it, so none should exist) changes from "miles" to NULL; the release step runs the zero-row check in §11 first.
- **Rounding.** `distance` is `numeric(9,3)` and `0.3048` has four decimals, so the product can have seven; Postgres rounds it half away from zero to the nearest millimeter when storing `distance_m`, exactly as it already does for `mi` (1.609344 m is stored as 1.609). Records and the series read the stored `distance_m` as decimal text (`parseDecimalMilli`, §6.3), so a record is the stored value and never a client recomputation; a distance too small to survive rounding (0.001 ft is 0.000 m) is not a `max_distance` record, which is the same `distance_m > 0` rule the other units get (D19).
- **Why drop-and-add in one migration file:** Prisma runs a migration file as one transaction, so there is no window without a constraint or a generated column. The tables are small; `NOT VALID` + `VALIDATE` is unnecessary.
- **Why `NUMERIC(14,3)`:** D8. `personal_record.value` is `NUMERIC(12,3)` (max 999,999,999.999) and a `max_duration` value is seconds, up to the DTO bound `SET_DURATION_S_MAX = 2,147,483,647`, which would overflow at finish. Widening the precision with the scale unchanged is metadata-only in Postgres (no table rewrite), and `previous_value` follows it.
- **`schema.prisma`:** `SetEntry.calories Int? @db.SmallInt` (the `distanceUnit` comment lists `m, km, mi, ft`; `distanceM` is unchanged); `PersonalRecord.value` / `previousValue` `@db.Decimal(14, 3)`; the `modality` comment (line 51) lists all eight.
- **Indexes:** none. `calories` is read with the row and never filtered.
- **Migration-test ownership:** the whole-schema no-drift `prisma migrate diff` check lives in the newest migration's test: it moves from `workout-sections-migration.integration.test.ts` (`0014`) into a new `new-modalities-migration.integration.test.ts` (`0015`). When `0016` lands it moves again. The drift-guard unit tests for `0002` / `0005` / `0008` are re-pointed (D14).

## 6. Behavior & logic

### 6.1 Measure rules (`MEASURE_RULES`, `packages/core/src/dto/set-entry.ts`)

`MEASURE_NAMES` becomes `reps, weight, distance, durationS, calories`. The table, as data (the only place rules live; `plannedSetViolations`, `assertSetMeasuresValid`, `isWorkingSetComplete`, `assertWorkingSetsComplete`, `importPlan.shape` and the web `carries()` / `visibleMeasures()` all derive from it):

| Modality | Required | Forbidden |
|---|---|---|
| `weight_reps` | weight, reps | durationS, distance, **calories** |
| `bodyweight_reps` | reps | weight, durationS, distance, **calories** |
| `weighted_bodyweight` | reps, weight | durationS, distance, **calories** |
| `duration` | durationS | weight, reps, distance, **calories** |
| `distance_duration` | distance, durationS | weight, reps, **calories** |
| `calories` | calories | weight, reps, distance, durationS |
| `weight_distance` | weight, distance | reps, durationS, calories |
| `weight_duration` | weight, durationS | reps, distance, calories |

Consequences that fall out with no extra code (each pinned by an AC): a routine plan for `weight_distance` / `weight_duration` may carry weight but never reps (AC12); a Calories plan carries neither (FI-11); the reader refuses reps into a note for all three (AC34); `rpe` is optional on every modality; a failed attempt on a weighted type is the weight plus a `0` of the second measure, the same convention as `reps: 0` (05.1 D14).

### 6.2 Record eligibility (`setRecordValueMilli`, `packages/core/src/records.ts`)

All values are integer milli-units of the record's unit (07.0 D3): kg × 1000, reps × 1000, calories × 1000, meters × 1000, seconds × 1000. Input sets are `working` sets of finished workouts, evaluated under their own `modality_snapshot`, `is_complete` ignored (07.0 D5; finish integrity guarantees the required measures).

| `record_type` (`unit`) | Value | Modalities and conditions |
|---|---|---|
| `heaviest_weight` (`kg`) | `weight_kg` | `weight_reps`, `weighted_bodyweight`: `reps ≥ 1` and `weight_kg > 0` (unchanged). `weight_distance`: `distance_m > 0` and `weight_kg > 0`. `weight_duration`: `duration_s ≥ 1` and `weight_kg > 0` |
| `best_est_1rm` (`kg`) | Epley, unchanged | `weight_reps`, `weighted_bodyweight` only |
| `best_set_volume` (`kg_reps`) | `reps × weight_kg`, unchanged | same two only |
| `max_reps` (`reps`) | `reps`, unchanged | `bodyweight_reps` only |
| `max_calories` (`cal`) | `calories` | `calories`, `calories ≥ 1` |
| `max_distance` (`m`) | `distance_m` | `weight_distance`, `distance_m > 0` (regardless of the load) |
| `max_duration` (`s`) | `duration_s` | `weight_duration`, `duration_s ≥ 1` (regardless of the load) |

**Heaviest load reuses `heaviest_weight` (D5), without e1RM or set volume.** Today the code gates all three of heaviest / e1RM / volume on one set, `LOAD_MODALITIES` (the rep-load types), and requires `reps ≥ 1` first. That set is renamed in a comment only (its name stays) and keeps gating e1RM and volume, which need reps. A second, separate set, `HEAVIEST_LOAD`, maps each load modality to the "second measure that must be positive" (`reps` / `distance` / `duration`) and gates only `heaviest_weight`. So `setVolumeMilli` (History's `totalVolume`, `best_set_volume`, the Finish stats) stays `null` for the new types, and `estimate1rm` is never reached for them. Both sets are constants in `records.ts`, covered by the AC22 matrix; a new modality that is in neither set has no records by construction.

`computeRecords` still loops `RECORD_TYPE_VALUES` in order; the three new types append, so existing output order is unchanged. Ties, chronology, lineage roots and `previousValueMilli` are exactly 07.0 §6.1.

### 6.3 Loader and persistence

- `RecordSet` gains optional `distanceMMilli`, `durationS`, `calories` (absent = null) so existing fixtures compile. `loadLineageSets` selects `se.calories`, `se.duration_s` and `se.distance_m::text`, and the two callers (`recomputeRecordsForRoots`, `getProgressSeries`) pass them through `parseDecimalMilli` / as integers. `LineageSetRow` gains the three fields.
- `value` is written with `milliToDecimalString`; `unit` from `RECORD_UNIT_BY_TYPE`; both checked by the widened DB CHECKs. `value` and `previous_value` are `NUMERIC(14,3)` (§4).
- The header comment in `records.ts` ("below 3.3e11 … one `numeric(12,3)`") is corrected to the new bound: the largest value is `SET_DURATION_S_MAX × 1000 ≈ 2.1e12`, inside `Number.MAX_SAFE_INTEGER` and `NUMERIC(14,3)`.
- Lock order is untouched: every writer already goes through `recomputeRecordsForRoots` with `lockUserRecords` first (07.0 D9, 07.4 AC4). This spec adds no writer and no lock key.

### 6.4 The finished-edit predicate (`setChangeAffectsRecords`)

07.4 AC8 skips the lineage recompute when an edit cannot change any record. The predicate today compares `setType`, `reps` and `weightKgMilli`; the new types make `calories`, `distance` and `durationS` record-relevant for *some* modalities only. Comparing all five for every modality would recompute on every distance or duration edit of a legacy `distance_duration` set, which 07.4 AC8 says must not happen, and would make that test lie. So:

`RecordRelevantSet` gains `modality` and the three optional measures (`distanceMMilli`, `durationS`, `calories`); a constant `RECORD_MEASURES_BY_MODALITY` (`weight_reps`: reps, weight; `bodyweight_reps`: reps; `weighted_bodyweight`: reps, weight; `duration` and `distance_duration`: none; `calories`: calories; `weight_distance`: weight, distance; `weight_duration`: weight, duration) says which measures that modality's records read, and the predicate compares only those, plus working-ness, exactly as before. (Today's comparison of `weightKgMilli` for `bodyweight_reps` is an over-approximation that this table makes exact; it can only remove no-op recomputes.) `recordRelevant()` in `set-entry.prisma.ts` fills the new fields from the returned row (`distance_m` and the integers), and the modality comes from the parent's `modality_snapshot`, already loaded in both write paths.

### 6.5 Progress series (`progressPoints`)

`ProgressPointMilli` gains `maxCaloriesMilli`, `maxDistanceMilli`, `maxDurationMilli`, each `bestOf(type, group)` through the same `setRecordValueMilli`, so series max = PR by construction (AC32). The repository maps milli to JSON numbers through the existing decimal-string path and the DTO gains the three fields. `topSetWeight` needs no change: `bestOf("heaviest_weight")` now simply returns a value for the weighted types. ### 6.7 Routine from text (`packages/core`, Spec 10.4)

The reader already turns `Max Cal Echo Bike with remaining time` into the item `Echo Bike` with the note `Max Cal, with remaining time` (AC50; "Max" is a rep count, never part of a name). The name alone ("Echo Bike") would be guessed `distance_duration` (`bike` is a distance word), so the signal must travel beside the name.

- `ReadName` gains `calories: boolean`: true iff any item with that name key was read from a calorie form (below). `ReadItem` carries the flag so the names pass can fold it.
- `guessModality(name, hint?: { calories?: boolean })`: `hint.calories` wins first, over the distance words, and returns `calories`; with no hint the function is byte-for-byte today's.
- **Two forms set the hint (D10).** (1) `Max Cal` / `Max Calories` (the existing `MAX_LINE` match). (2) The **leading calorie form**: `^(\d{1,4})\s?(cals?|calories?)\s+(\S.*)$`, case-insensitive, with a movement after it (`isMovementText`) and no ` + ` in the rest. `Max Reps`, bare `Max`, a bare or trailing "Cal" and a `Calf` word set nothing.
- **How the leading form interacts with the existing leading-number parsing.** Today `repFormOf` reads `20 Cal Row` as no rep form only because `UNIT_WORD` contains `cal` / `calorie`, so the line falls to a plain named line `20 Cal Row` with the note `20 Cal` (the `LEADING_MEASURE` path used for `400 Meter Run`). That guard is fragile and incomplete: `UNIT_WORD` lacks `cals`, so `20 Cals Row` would be read as 20 reps of `Cals Row`. The new form is therefore tested **before** `repFormOf`, right after the `MAX_LINE` check, in both places `MAX_LINE` is handled (under an open run in step 7, and as a bare bullet in step 8). On a match it calls `pushMovement(s, run, movement, null, [measure])` (run) or `pushItem(... noteLines: [measure])` (bullet): the name is the movement alone, like the Max form and unlike `400 Meter Run` (a distance is part of a real exercise name; a calorie goal is a target on the movement). `measure` is the leading text exactly as written (`20 Cal`). Nothing else changes: `REPS_FORM`, `RANGE_FORM`, `SPLIT_FORM`, `LEADING_MEASURE` and the pair rule are untouched, and `UNIT_WORD` gains `cals` so a stray `20 Cals` is never a rep form either.
- **The 20 is not a target.** There are no calorie targets (FI-11), so the number is never a planned row, a rep or a target; it stays only in the item note (`noteLines: ["20 Cal"]`), which is where the reader keeps leftover text. The user can read it in the routine's note on the exercise card.
- An existing exercise that matches by name keeps its own modality (the guess only seeds a New card), so until the Echo Bike fix an import of `Max Cal Echo Bike` matches Carol's existing duration-typed Echo Bike.
- `buildImportPlan` needs no change: `shape()` derives `refusesReps` from `forbiddenMeasuresFor`, so all three new types refuse reps into a note and no weight is ever emitted. The web passes `name.calories` into `guessModality` in the UI spec (§3.2).

## 11. Deployment & rollback

**Order (DESIGN §6; migration policy):**

1. Before merging Phase A, run the read-only pre-check `SELECT count(*) FROM set_entry WHERE distance IS NOT NULL AND distance_unit IS NULL;` (expect 0; D18 changes such a row's `distance_m` from miles to NULL), and a before snapshot `SELECT md5(string_agg(id::text || coalesce(distance_m::text,''), ',' ORDER BY id)) FROM set_entry;`. Then run `0015` on staging as a **manual release step before the code goes live**: `DATABASE_URL='<Neon direct URL>' pnpm run db:migrate:deploy` (runbook B4; never `migrate dev` on Neon). It is expand-only, so the running API (which names its columns) is unaffected. The migration briefly takes `ACCESS EXCLUSIVE` on `set_entry` for the `distance_m` rebuild (D18); the old API's statements wait and then succeed, because the column keeps its name and type. Verify with `db:migrate:status`, `\d set_entry`, and that the snapshot hash above is unchanged.
2. Merge Phase A (Render auto-deploys staging). Accepted few-minute parse window (§3.3). Run the staging API smoke. Nothing in the UI offers a new type yet.
3. Merge Phase B. Then run `records:rebuild` (runbook B5a, same direct-host URL, idempotent, safe under traffic): required only if a new-type workout was finished between A and B (none expected), and cheap otherwise. Verify `GET /v1/personal-records` for the test user is unchanged.
4. Production (Spec 15): `deploy-prod` never migrates. Apply `0015` by hand per the runbook before approving the release; the production database starts empty (Q31 D9), so no rebuild is needed there until data exists.
5. The UI spec merges only after A and B are deployed and verified (DESIGN §6).

**Rollback.** Revert the code; `0015` stays (expand-only; the column, widened CHECKs and `NUMERIC(14,3)` are harmless to old code). One caveat: the old code's `z.enum` rejects a new modality or record type in a response, so once any new-type exercise, snapshot or record exists a code rollback past this spec breaks the reads that include it. Before rolling back with such rows, convert or remove them: `DELETE FROM personal_record WHERE record_type IN ('max_calories','max_distance','max_duration')`, and move the exercises (and their snapshots) back to a legacy type by hand. Until the UI ships no UI path creates one; only a deliberate API call does. Likewise any set stored with `distance_unit = 'ft'` makes the old `z.enum(["m","km","mi"])` reject the set in responses: before such a rollback convert them by hand (`UPDATE set_entry SET distance = round(distance_m, 3), distance_unit = 'm' WHERE distance_unit = 'ft'`; this loses the typed unit, so it is a last resort). Rolling the API back past the new response fields also rolls the client back (DESIGN §6).

## 12. Decisions & open questions

All decisions are the designer's calls unless marked owner. The owner-fixed inputs (design doc): the three types and their PRs; whole-number calories; target weight for both weighted types, no calorie targets; reader reads `Max Cal` as Calories; widening CHECKs is additive; the Echo Bike fix is separate.

- **D1 ✅ Names: `calories`, `weight_distance`, `weight_duration`.** Rationale: they follow the existing `distance_duration` pattern (measures joined by an underscore, in logging order) and read well in logs and the metric attribute. Rejected: `calorie`, `loaded_carry` / `loaded_hold` (name an example, not the measures; `weight_reps` and `distance_duration` are named by what they log).
- **D2 ✅ Calories live in a new `set_entry.calories SMALLINT` column, whole numbers, no unit.** Rationale: every existing column has a fixed meaning (the design says so); reusing `durationS` is the Echo Bike bug itself and `reps` would drag calories into volume, e1RM and max reps; a generic `measure_value` column would break the explicit required / forbidden rule model. `SMALLINT` mirrors `reps`, and 32,767 calories in one set is beyond any real session (cap `SET_CALORIES_MAX`). A DB CHECK (`>= 0`) is added because the column is new and the cost is one line (the older columns rely on Zod alone; not retrofitted).
- **D3 ✅ Every legacy modality forbids `calories`; each new type forbids every measure it does not log.** Rationale: the rule model is symmetric (a value a type cannot use is refused, never silently kept), and it makes the Echo Bike fix's "a duration value on a Calories card is forbidden" true in both directions.
- **D4 ✅ Weight on the weighted types is the total carried; no new unit or column.** Rationale: the design says "the total carried"; it reuses `weight` / `weight_unit` / `weight_kg` and every kg / lb path. A per-hand entry is the lifter's arithmetic.
- **D5 ✅ Heaviest load reuses `heaviest_weight` through a separate `HEAVIEST_LOAD` gate; e1RM and set volume stay on the rep-load set.** Rationale: one "heaviest" record type means one label, one chart metric (`topSetWeight`) and one set of PR cards for every load exercise; the e1RM and volume gates stay untouched because both need reps, so a new type can never reach `estimate1rm` or `setVolumeMilli`. Rejected: a new `heaviest_load` type (duplicates `heaviest_weight`'s meaning, doubles the UI's label and chart work for no gain).
- **D6 ✅ Heaviest load requires the type's second measure to be positive** (distance for `weight_distance`, duration for `weight_duration`), as `heaviest_weight` requires `reps ≥ 1` today. Rationale: the same rule keeps a weight with no work done (a failed attempt, `0` distance) from being a record. `max_distance` and `max_duration` do not require a weight (the design says "longest distance", "longest hold": independent of load); a `0` weight is allowed to log but never records a load.
- **D7 ✅ New record types `max_calories` (`cal`), `max_distance` (`m`), `max_duration` (`s`); distance records are canonical meters.** Rationale: named like `max_reps` (`max_` + the measure), generic enough that the deferred records for `duration` / `distance_duration` can reuse them; meters come straight from the generated `distance_m` column, so the unit typed (m, km, mi) never changes the record, and the client converts for display (as kg to lb today). `s` and `cal` are canonical already.
- **D8 ✅ `personal_record.value` / `previous_value` widen to `NUMERIC(14,3)` in `0015`.** Rationale: record values are stored as integer milli of the unit; seconds × 1000 for the DTO maximum duration (about 2.1e12) exceeds the current 12-digit column (max about 1e9), so a legitimate (if absurd) long hold would fail the finish transaction with a numeric overflow. The alternative, capping duration on `weight_duration` only, would make one modality's DTO differ from the rest and change a settled bound. Widening precision at fixed scale is metadata-only. (Not a settled-decision reversal: 07.0 D4 chose `numeric(12,3)` for four types that all fit.)
- **D9 ✅ The progress series gains three new nullable fields rather than a generic metrics array.** Rationale: the smallest change coherent with the existing point shape and the 07.2 "series max = PR" rule; the UI's `METRICS` table already maps one field per metric. Required-nullable, API one release before any reader (DESIGN §6).
- **D10 ✅ Two forms set the reader's Calories hint: `Max Cal` / `Max Calories` and the leading calorie form (`20 Cal Row`).** The first was in the brief; the second is an **owner ruling** (the owner writes leading calorie-goal lines). Rationale for the narrow match: a bare or trailing "Cal" is ambiguous ("Cal Ripken Drill", "Calf Raises"), a leading number plus Cal / Cals / Calorie(s) plus a movement is not. The number stays in the note, never a target (FI-11).
- **D11 ✅ The records predicate becomes modality-aware (§6.4).** Rationale: it keeps 07.4 AC8's guarantee exactly true for legacy types and avoids an unconditional five-field comparison that would recompute on every legacy distance edit.
- **D12 ✅ No new routes, lock keys, rate groups, env vars or telemetry attributes.** Rationale: the types ride on existing writes; every writer already holds `lockUserRecords` first.
- **D13 ✅ No built-in catalog rows are added.** Rationale: the seed is append-only and the design says a built-in Echo Bike or farmer carry, "if added", is a new key; nothing requires one, and the owner's Echo Bike is a custom exercise. **Owner ruling (2026-10-25): no built-in rows in this spec;** a built-in exercise pass is happening under another issue (likely #117). Adding one is permanent once live (it can only be retired).
- **D14 ✅ Guards for `0002` / `0005` / `0008` are pinned to frozen legacy lists; the live lists are guarded against `0015`.** Rationale: those migrations describe history; if their guards still rendered `MODALITY_VALUES`, every future widening would fail them for a correct reason.
- **D15 ✅ The web compile-compatibility edits ship in the Phase A PR (§3.3), and the web create form is pinned to the legacy five. Owner ruling (2026-10-25): yes to both.** Rationale: `@sin/core` types are shared, so a widened union cannot ship without the web compiling; keeping the new types out of the create form keeps the "API one release before the UI" order true in practice. The alternative, shipping API and UI in one PR, breaks the API-first rule and the one-session limit.
- **D16 ✅ Two PRs, one spec (§1).** Rationale: the phase boundary (storage and logging vs records and series) is clean, the migration lands in the first, and the first is useful alone. A third spec would be bookkeeping.
- **D17 ✅ `records:rebuild` after Phase B on staging; not required in production until data exists.** Rationale: new-type sets finished before Phase B (possible only by direct API use) would have no rows; the rebuild is idempotent, so running it anyway costs nothing.

- **D18 ✅ `ft` is a fourth distance unit shared by every distance-carrying modality, and `0015` rebuilds `distance_m` to compute it.** Rationale: the owner measures a carry in meters or feet (O4); a unit list shared by `distance_duration` and `weight_distance` is the smallest change (no per-modality unit rule) and a run in feet is merely unusual, not wrong. Widening only the CHECK would be a silent corruption: 0006's `ELSE distance * 1609.344` would store an `ft` set as miles. Postgres 16 cannot change a generated expression in place (`SET EXPRESSION` is PG17), so the options were: (a) drop and re-add `distance_m` in the migration transaction, with every unit named and no `ELSE`; (b) add a second generated column and later retire the first (two releases, the same rewrite, and every reader to move); (c) convert feet to meters in the API before storing (breaks "stored as typed", DESIGN §4.0, and the database would no longer own the canonical value). Chosen: (a). **Expand-only ruling:** the rule exists so a running old build never meets a missing or renamed column; (a) keeps the name and type, runs in one transactional migration (no session sees the gap), recomputes identical values for every existing `m` / `km` / `mi` row, and old code reads `distance_m` unchanged afterwards. It is therefore an accepted, documented exception (a deliberate drop-and-re-add of a derived column), not a precedent for dropping stored data; the cost is a brief `ACCESS EXCLUSIVE` rewrite of a small table. No `CASCADE`, so an unseen dependency fails the migration instead of vanishing. Removing the `ELSE` arm is intended: an unnamed unit becomes NULL instead of silently becoming miles, and the 0015 drift guard fails when `DISTANCE_UNIT_VALUES` and the expression disagree.
- **D19 ✅ Feet round to the nearest millimeter in `distance_m`; records and charts stay in meters.** Rationale: `numeric(9,3)` is the existing canonical precision and `mi` already rounds the same way; keeping one canonical unit (DESIGN §4.0) is what makes records comparable across units. The UI shows meters for records (18.1 D6) and the unit typed on the set row.
- **D20 ✅ The reader learns `ft` (the abbreviation) only, in Phase B (AC41); the web unit selects take `DISTANCE_UNIT_VALUES` in Phase A.** Rationale: without it `100 ft Farmer Carry` would read as 100 reps of `ft Farmer Carry`, the failure the existing `m` / `km` / `mi` words prevent; `feet` and `foot` are real exercise-name words and are left alone (a lifter who writes "100 feet" gets today's behavior, a one-line follow-up if wanted). In the web, replacing the local list with the core constant is the smallest compile-time guarantee that a fifth unit never needs a web edit; its one visible effect (feet appear in Set options for `distance_duration` and `weight_distance`) is the deliberate exception in AC21, and it matters now because a set created through the API in feet would otherwise display and edit as the wrong unit.
