## 1. Purpose, scope & non-goals

Ship the screen a lifter uses in the gym: start a workout (or resume the one in progress), add exercises with Spec 06.0's picker, log sets with inputs that fit each exercise's modality, reorder and remove exercises, finish (including the `409 incomplete-working-sets` recovery), and delete a workout. The M1 browser smoke that drives all of it in a real browser is **Spec 06.3**.

This is the first spec that **mounts** anything from 06.0: `<CatalogProvider>` goes under the protected layout, the `Workouts` nav item stops being `comingSoon`, and `<ExercisePicker>` opens from "Add exercise".

> **First-principles note (what "the screen" is made of).** Three kinds of state meet on this screen, and mixing them up is the commonest source of React bugs. *Server state* is data the API owns and we hold a copy of (the workout, its exercises and sets); the copy goes stale, so it lives in a cache that knows how to refetch (TanStack Query, already in the app for `useMe`). *Draft state* is what the lifter has typed but not yet logged (the text in the weight box); only the browser knows it, it is lost on reload, and it lives in component state. *UI state* is which sheet is open. Every design choice below is about which of the three a given piece of data belongs to and how it moves between them.

### In scope

- **Routes & mounting** — `/app/workouts` (active session or Start screen), `/app/workouts/:id` (read-only finished workout), `/app` redirecting into Workouts, the nav item un-stubbed, `<CatalogProvider>` mounted in `ProtectedLayout`.
- **Start / resume** — `POST /v1/workouts` with a client-minted `clientGeneratedId`; resume is `GET /v1/workouts/active` on every visit to `/app/workouts` (this is also what a cold-load redirect lands on).
- **Exercises** — add via `<ExercisePicker>`, move up/down, remove (with confirm when it holds sets).
- **Set rows per modality** — an entry row that creates a set only when the lifter taps "Log set"; tap a logged set to edit or delete it. Inputs per modality are fixed in §5.4, derived from `requiredMeasuresFor` / `forbiddenMeasuresFor` in `@sin/core`.
- **Finish** — confirm, `PATCH { endedAt }`, the `409 incomplete-working-sets` diagnosis and recovery, the ambiguous-failure case.
- **Delete workout** — discard an in-progress workout; delete a finished one from its summary.
- **Finished-workout summary** — a minimal read-only view at `/app/workouts/:id` (the only place a finished workout can be reached until Spec 08 ships history).
- **Primitives** — `<ConfirmDialog>`, `<InlineNotice>` in `src/ui/`.
- **Carried from 06.0** — the logout "stop persisting" switch and `<Sheet>`'s native `close` handling (§1.2).

### Non-goals

- **Everything in Spec 06.2** (the boundary, drawn explicitly): the write queue, the unsynced-state UI, retry/backoff, the `localStorage` mirror of the in-progress workout (and of unlogged drafts), and blocking Finish on pending writes. This spec's writes are **pessimistic** (§6.3): the screen waits for the server's answer, shows a busy state, and on failure shows an error with a manual retry. There is **no automatic retry, no persisted draft, no "unsynced" badge, and no optimistic cache write** here. Consequence, stated plainly: a dropped connection or an evicted tab loses unlogged drafts, and a failed write is the lifter's to retry. Until 06.2 ships, gym use should keep a fallback note (§11).
- Workout `title` / `notes` and per-exercise `notes` editing (the API supports them; deferred — §12 D19).
- Rest timer (M4), a ticking elapsed-time clock, PR display (Spec 07/08), history list (Spec 08), routines / "start from routine" (Spec 10), supersets (Spec 10), drag-and-drop reordering (§12 D16), previous-session placeholders (needs Spec 07's read path), an "in progress" indicator on the nav tab.
- **The M1 Playwright smoke** (owner decision D24 — split out to Spec 06.3): Playwright, the Auth0 test user, the post-deploy CI job, and the browser-only obligations Specs 04.0 §10 / 04.1 §10 hand to a real browser. This spec's tests are Vitest/RTL + MSW only; behaviors jsdom cannot verify (real focus trapping, layout, CSP) are verified by 06.3.
- Any API change. Anything the screen wants that the API lacks is listed in §12 "API gaps observed", not worked around with new endpoints.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test naming their number (`describe("AC7 — …")`). Levels are in §10. **Phase A** (AC1–AC13): pure logic, the REST seam, cache rules, storage switch — no DOM beyond a hook harness. **Phase B** (AC14–AC36): components and routing. A session can stop cleanly at the A/B boundary. Real-browser criteria are in Spec 06.3.

### Phase A — logic, REST seam, cache

1. **`createWorkoutClient(api)` maps each operation to its exact request.** For each operation — `getActive`, `getById`, `start`, `finish`, `deleteWorkout`, `addExercise`, `moveExercise`, `removeExercise`, `createSet`, `updateSet`, `deleteSet` — a fake `api` receives the method, path, body and response schema in §6.1's table, and the result is parsed with the `@sin/core` schema named there. `getActive` turns a `404` `ApiError` into `null` and rethrows every other error. `addExercise` sends **no** `position` (append). `moveExercise` sends only `{ position }`.
2. **`classifyWorkoutError(error, context)` maps every error the screen can meet to one kind.** Table-driven over §5.8: `404`, `409 workout-in-progress-exists`, `409 workout-finished`, `409 incomplete-working-sets`, `409 exercise-retired`, `422` (with and without `errors[]`), `5xx`, a network `ApiError`, `401`, and a non-`ApiError` value. It never throws. The slug (`ApiError.type`) decides the `409` kind — never the title or detail text.
3. **Start and finish timestamps are built correctly.** `startWorkoutFields(now, tzOffsetFn)` returns an ISO `startedAt` and `tzOffsetMinutes` that is the **negation** of `Date.prototype.getTimezoneOffset()` (minutes **east** of UTC: UTC+02:00 → `+120`; UTC−05:00 → `−300`; UTC → `0`, never `-0`). `finishTimestamp(startedAt, now)` returns `now`, clamped up to `startedAt` when the device clock moved backwards mid-session (05.0 §6.5 rejects `endedAt < startedAt`).
4. **Cache transformers are pure and surgical.** `withSetUpserted(detail, set)` replaces a set with the same `id` or inserts it, keeping each exercise's `sets` ordered by `setNumber`; `withSetRemoved(detail, setId)` removes it. Neither mutates its input; exercises not touched keep reference equality.
5. **Visible measures are exactly the required measures.** `visibleMeasures(modality)` equals `requiredMeasuresFor(modality)` re-ordered into the fixed display order (`distance`, `weight`, `reps`, `durationS`), for all five modalities, and never contains a member of `forbiddenMeasuresFor(modality)` — so the UI cannot construct a body the server's forbidden-measure rule (05.1 AC7) would reject.
6. **`parseDraft(modality, draft)` produces a valid body or field errors.** Per modality, a valid draft yields a body containing exactly the visible measures plus their units (and `setType`, and `rpe` when non-empty) and no forbidden measure. Accepted: a comma decimal (`"52,5"` → `52.5`); `"0"` reps (a failed attempt, 05.1 D14); weight `0`. Rejected with a static, value-free message on the matching field: empty required field; non-numeric; negative; reps with a decimal point; weight/distance beyond three decimals; values above `SET_REPS_MAX` / `SET_WEIGHT_MAX` / `SET_DISTANCE_MAX` / `SET_DURATION_S_MAX`; a distance whose `toCanonicalMeters` exceeds `SET_DISTANCE_MAX` (05.1 D11's `distance_m` bound); seconds above 59; RPE outside 1–10 or with more than one decimal.
7. **`diffForPatch(set, parsed)` sends only what changed.** A weight-only edit yields `{ weight }`; a unit-only edit yields `{ weightUnit }`; clearing RPE yields `{ rpe: null }`; no change yields `null` (the caller sends no request). It never includes `isComplete`, `clientGeneratedId`, or a forbidden measure.
8. **`formatSet(set, modality)` renders every modality.** `weight_reps` → `60 kg × 8`; `bodyweight_reps` → `12 reps`; `weighted_bodyweight` → `+10 kg × 8`; `duration` → `1:30`; `distance_duration` → `5 km · 25:00`; an RPE appends `@8`; a non-`working` type adds its label; a null measure on a not-complete set renders `–`. Numbers use the pinned `"en"` formatter (no trailing `.000`). `formatDuration(seconds)` handles `0`, `59`, `60`, `3 600`.
9. **`findIncompleteWorkingSets(detail)` mirrors the server's finish rule.** Returns the ids of `working` sets for which any measure in `requiredMeasuresFor(modalitySnapshot)` is `null`; checks `=== null`, not truthiness, so `reps: 0` is **not** flagged; never flags `warmup` / `drop` / `failure`; handles exercises of different modalities in one workout.
10. **The draft's attempt key has a defined lifecycle.** The draft reducer mints `attemptKey` (a lower-case GUID, via an injected `newKey`) when the draft is created; it is **retained** across a failed attempt, across edits to the draft, and across retries; it is **re-minted** only after a successful create (the next set is a new attempt). The create body carries it as `clientGeneratedId`.
11. **A write-through cache update survives an in-flight refetch.** With a `["workouts","active"]` refetch already in flight (started before a set `POST` committed), a set-create success followed by that refetch resolving still leaves the new set in the cache — the mutation cancels in-flight queries on that key before writing (§6.2).
12. **Cache writes survive navigating away mid-request.** The cache update for a set create lives in the `useMutation` hook-level `onSuccess`: unmounting the component that called `mutate()` before the response arrives still updates the cache.
13. **After logout begins, nothing user-scoped is written to storage.** Once `logoutAndClear` has run, `set()` on **any** `localStorageAdapter()` instance is a silent no-op for user-data keys (it must not throw — a throw would trip 06.0 AC11's one-time `reportError`); `clearUserData` and `get` / `keys` / `remove` still work; a test helper resets the block. A catalog refresh resolving after `logoutAndClear` leaves no `sin:catalog:*` key behind.

### Phase B — UI

14. **Routing and mounting.** `/app` redirects (replace) to `/app/workouts`; the `Workouts` nav item has no `comingSoon`; `/app/workouts` and `/app/workouts/:id` are protected children of the existing layout; `<CatalogProvider userId={me.id}>` wraps the shell and mounts only after `GET /v1/me` is `200` (inside the 04.0 gate). A `404` on `/app/workouts/:id` renders `NotFound`.
15. **`/app/workouts` states.** Active query pending → `<Spinner>`; `GET /v1/workouts/active` `404` → the Start screen (not an error); `200` → the session; any other failure → an in-shell error notice with "Try again" and the `requestId`. The active query refetches on window focus (a phone returning from another app) and on remount.
16. **Start.** Tapping "Start workout" sends one `POST /v1/workouts` with `{ clientGeneratedId, startedAt, tzOffsetMinutes }` (AC3) — no `title`, no `notes`; the button is busy meanwhile (two quick taps → one request). A network/`5xx` failure shows an error and a retry that **reuses the same `clientGeneratedId`**. `409 workout-in-progress-exists` refetches `/active` and shows that workout with a one-line "You already had a workout in progress — resumed it." `422` → "Your device clock looks wrong — check the date and time, then try again." Success refetches `/active` (the `201` body is a `Workout`, not a `WorkoutDetail`; a `200` replay may already have exercises).
17. **Session layout and Add exercise.** Exercises render in `position` order as cards showing `exerciseNameSnapshot` and the modality label; with none, a "Add your first exercise" hint. A sticky bottom bar holds "Add exercise" and "Finish". "Add exercise" opens `<ExercisePicker>`; a pick sends exactly one `POST …/exercises` with `{ exerciseId }`, closes the picker, and shows a pending placeholder card until the refetch lands. A second pick while one is in flight is ignored. The same exercise may be added twice. A custom exercise created inside the picker is added through the same path.
18. **Add-exercise failures.** `409 exercise-retired` → "That exercise has been retired and can't be added" and `catalog.refresh(true)`; `404` → refetch `/active`: if the workout is gone or finished, handle per AC29's "gone" path, otherwise "That exercise isn't available" and `catalog.refresh(true)` (the API returns the same `404` for "workout gone" and "exercise not visible"); `409 workout-finished` → the gone/finished path; a network/`5xx` failure → refetch `/active`, then "Couldn't confirm that exercise was added — check your workout before adding it again" (no automatic retry: add-exercise has no idempotency key).
19. **Reorder.** Each card's options offer "Move up" / "Move down" (disabled at the ends and while any exercise-structure write or its refetch is pending). They send `PATCH /v1/workout-exercises/{id}` `{ position: p − 1 }` / `{ position: p + 1 }`; the new order comes from the refetched detail (the `200` carries only the moved row). A `422` (stale position) or `404` refetches; `409 workout-finished` → gone/finished path; a network/`5xx` failure shows a retryable error.
20. **Remove.** A card with no sets removes immediately; one with sets opens `<ConfirmDialog>` naming the exercise and the number of sets that will be deleted. `DELETE /v1/workout-exercises/{id}` `204` → refetch. A `404` is treated as success. `409 workout-finished` → gone/finished path.
21. **Entry row fields per modality (§5.4).** Table-driven over all five modalities: the visible measure inputs are exactly AC5's set — `weight_reps`: Weight + unit, Reps; `bodyweight_reps`: Reps; `weighted_bodyweight`: Added weight + unit, Reps; `duration`: Minutes, Seconds; `distance_duration`: Distance + unit, Minutes, Seconds — and none is a forbidden measure. Every modality also shows a Set-type select (default Working) and an optional RPE under "More". The weight unit defaults to `me.unitPreference`; the distance unit defaults per §5.4. Numeric inputs use `inputMode="decimal"` / `"numeric"` (never `type="number"`).
22. **Prefill.** With no sets logged for that exercise the inputs are empty (no invented values); with sets, the draft is initialised from the **last logged set** (measures and units), with `setType` reset to Working. After a successful log, the draft keeps the logged values (copy-forward) and gets a fresh attempt key.
23. **Log set.** "Log set" is disabled until `parseDraft` succeeds. Tapping sends one `POST …/sets` with the parsed body, `isComplete: true`, and `clientGeneratedId` (AC10); the button is busy meanwhile. On success the set appears in the list at the end, a polite live region announces "Set N logged", focus stays on the Log button, and no refetch is issued. A `weight_reps` set with `reps: 0` and a weight logs successfully.
24. **Log-set failures.** `422` → per-field messages from `errors[].path` (the 04.1 AC7 pattern) plus a form-level message for an unmatched path; network/`5xx` → "Couldn't log set — try again" with the draft intact and the **same** attempt key on retry; `404` / `409 workout-finished` → the gone/finished path. In every failure the entry row keeps its values and stays enabled.
25. **Edit and delete a logged set.** Tapping a logged row opens a `<Sheet>` titled with the set number and exercise name, with the same fields prefilled. Save sends `PATCH /v1/sets/{id}` with `diffForPatch`'s output only; no change closes the sheet without a request; clearing a required measure blocks Save with a field message. "Delete set" sends `DELETE /v1/sets/{id}`; `204` and `404` both remove it from the cache. `422` / `404` / `409` / network failures follow AC24's mapping. On success the cache is updated by `withSetUpserted` / `withSetRemoved` (no refetch).
26. **Finish — confirm and success.** "Finish" is disabled with the hint "Log at least one set to finish" while the workout has zero sets (§12 D17); otherwise it opens `<ConfirmDialog>` stating the exercise and set counts and that a finished workout can't be edited. Confirming sends `PATCH /v1/workouts/{id}` `{ endedAt: finishTimestamp(...) }` with the button busy (one request on a double tap). `200` removes the active query, seeds `["workouts","detail",id]`, and navigates to `/app/workouts/:id`; revisiting `/app/workouts` then shows the Start screen.
27. **`409 incomplete-working-sets`.** The screen refetches `/active`, runs `findIncompleteWorkingSets`, marks each offending row (visible "Needs data" text, not colour alone) and shows a banner "N working set(s) are missing data. Fix or delete them, then finish again." Tapping a flagged row opens the edit sheet pre-filled with its partial values; after fixing or deleting, Finish succeeds on the retry. If the scan finds nothing, the banner is "Some sets are incomplete — reload and check your sets." A set with `reps: 0` is never flagged. The 409 body is not parsed for ids (it carries none).
28. **Other finish outcomes.** `409 workout-finished` → `GET /v1/workouts/{id}`: `endedAt` set → treat as success and go to the summary (covers a lost first response and another tab finishing). `422` → the device-clock message. `404` → gone path. Network/`5xx` → "Couldn't finish — try again" with `requestId`; the retry is safe (a successful first attempt answers `409 workout-finished`, handled above).
29. **Discard and the "gone" path.** "Discard workout" opens a danger `<ConfirmDialog>`; confirming sends `DELETE /v1/workouts/{id}`; `204` and `404` both land on the Start screen; a network/`5xx` failure shows a retryable error. The shared "gone" path (any write answering `404` for the workout, or `409 workout-finished` on a non-finish write) refetches `/active` and shows the Start screen with "That workout was already finished or removed."
30. **Finished summary.** `/app/workouts/:id` for a finished workout renders read-only: date (`localDate`), duration, each exercise with its sets via `formatSet`, "Delete workout" (danger confirm → `204`/`404` → `/app/workouts`) and "Back to Workouts". No input, no edit affordance. An in-progress id redirects (replace) to `/app/workouts`. A fetch failure shows the in-shell error notice with retry.
31. **`<ConfirmDialog>`.** A native `<dialog>` opened with `showModal()` while `open`, labelled by its title; Confirm and Cancel buttons (Confirm is the thumb-zone-side action, with a `danger` variant); the dialog's `cancel` event (Escape / Android back) calls `onCancel` and does not close it itself; `busy` disables both buttons and sets `aria-busy`.
32. **`<Sheet>` forwards a native `close`.** While `open` is `true`, a `close` event on the dialog calls `onClose` once; when `open` flips to `false` programmatically (the parent closing it), no `onClose` call results. 06.0 AC24's existing behavior is unchanged.
33. **Accessibility and one-handed layout (component level).** Every interactive element carries a `--tap-target-min`-driven class; every input has a programmatic label; error text is `role="alert"`; the log/finish announcements are in a `role="status"` live region; a flagged set is announced ("needs data"), not conveyed by colour only. The sticky action bar sits above the shell nav (DOM and CSS order), and the entry row's "Log set" is its last element.
34. **No inline styles; tokens stay central.** A source scan fails if any module under `src/features/workouts/` or the two new `src/ui/` primitives uses a JSX `style=` prop (the production CSP is `style-src 'self'`, which blocks inline style attributes — Spec 04.0 §7); `assert:css-tokens` stays green for every new `*.module.css`.
35. **Observability hygiene.** The events in §9 fire with the listed properties; a spy over `track` / `reportError` across every flow in AC16–AC30 asserts that no payload contains an exercise name, workout/set/exercise id, or a measure value, and that `reportError` tags are static strings.
36. **Coverage gate.** `vitest.config.ts` adds `≥90%` line thresholds for `src/features/workouts/**`, alongside the existing gates.

**Consumers must note:**

- **Writes go through `WorkoutClient`; cache writes go through the hook-level `onSuccess` in `useWorkoutMutations.ts`** (so they survive unmounts, AC12). 06.2 should replace the client, not the hooks.
- **Drafts are component state** keyed by `workoutExerciseId`; leaving `/app/workouts` discards unlogged drafts (§6.9). 06.2 decides whether its mirror persists them.
- **Anything new that persists per-user data to browser storage uses a `sin:<name>:` prefix in `USER_DATA_KEY_PREFIXES` and the `StorageAdapter`** (CLAUDE.md). **This spec adds no new key** (§4).

## 4. Data model

No server-side tables or migrations. No new browser-storage keys: **06.1 persists nothing** (drafts, the attempt key and UI state are in memory; 06.2 owns persistence). `USER_DATA_KEY_PREFIXES` is unchanged.

### Client state

| State | Home | Lifetime |
|---|---|---|
| The in-progress workout (`WorkoutDetail`) | TanStack Query, key `["workouts","active"]` | session; refetched on mount and window focus |
| A finished workout (`WorkoutDetail`) | key `["workouts","detail",id]` | session; seeded on finish |
| Catalog + recents | 06.0's store (`localStorage` mirror via the adapter) | persisted, per user |

|---|---|---|---|---|

| **Remove exercise** | treat as success → refetch | `workout-finished` → *gone path* | — | retryable error (a repeat is a `404` = success) |
| **Create set** | workout-exercise gone → refetch `/active` | `workout-finished` → *gone path* | per-field messages from `errors[].path`; unmatched → form-level | draft + attempt key kept; retry reuses the key (§6.5) |

### 6.2 Server state, the cache, and why writes `cancelQueries` first

> **First-principles note (queries, mutations, cache).** A TanStack *query* is a read whose result is cached under a **key** (an array, here `["workouts","active"]`); components that use the same key share one request and one cached copy. A *mutation* is a write. A write changes the server, so the cached copy is now wrong, and there are two ways to fix it: **`setQueryData`** — we already know the new value (a `POST` set returns the new set), so write it into the cache directly, instantly, no round trip; or **`invalidateQueries`** — mark the copy stale so it is refetched, which is simpler and always right but costs a request and a flash of old data. This spec uses `setQueryData` for set writes (the response is the whole truth for that row, and the set loop must feel instant) and `invalidateQueries` for exercise structure changes (add/move/remove: the response is one row but sibling `position`s shifted, so the server's whole detail is the only trustworthy answer).

**The race this avoids.** A background refetch (window focus, remount) starts, then a set `POST` commits, then the refetch's older response arrives and overwrites the cache — the set you just logged vanishes until the next refetch. The fix (AC11): every set mutation calls `queryClient.cancelQueries({ queryKey: WORKOUT_KEYS.active })` in `onMutate` before it writes, so an in-flight read can no longer land on top of the write.

**Query options.** `useActiveWorkout`: `staleTime: 0`, `refetchOnMount: "always"`, `refetchOnWindowFocus: true` (overriding 04.0's global `false`: coming back to the tab from another app should show the truth; the cheapest multi-tab/multi-device sync available), `retry: false` (04.0's rule — the error notice's button is the retry). Its `queryFn` turns `404` into `null` so "no active workout" is data, not an error state.

### 6.3 Write policy: pessimistic, serialized, hook-level cache writes

> **First-principles note (optimistic vs pessimistic).** An *optimistic* update shows the result of a write before the server confirms it, and rolls back if it fails. It makes a UI feel instant on a slow link, but it needs a second, visible state ("this row isn't saved yet") and a rollback or retry story. A *pessimistic* update waits for the server's answer, then updates the screen. 06.1 is pessimistic because the "not saved yet" state, the queue, and the retry are exactly Spec 06.2's scope; building half of them here would be built twice. The one place the screen shows something before the server answers is the add-exercise placeholder card — a spinner, not a claim that the row exists.

- **Exercise-structure writes are serialized.** Add / move / remove each change sibling `position`s, and the next move's arithmetic (`p ± 1`) is computed from the list on screen, so only one such write (plus its refetch) may be in flight; the controls are disabled until the refetch settles. Set writes on different cards are independent and not serialized; two writes on the **same** card are prevented by the busy Log button / sheet.
- **Cache writes live in the hook-level `onSuccess`**, not in the `mutate(vars, { onSuccess })` call-level callback: TanStack skips call-level callbacks if the component unmounted before the response, but runs hook-level ones. A lifter who switches to the Profile tab mid-request still gets a correct cache (AC12). Navigation (`navigate('/app/workouts/:id')` after finish) stays at the call level, so a response arriving after unmount does not yank the user across screens.
- **Finish writes**: `removeQueries(active)`, `setQueryData(detail(id), { ...cachedDetail, ...workoutFromResponse })`, then navigate.

### 6.4 Drafts, controlled inputs, and parsing

> **First-principles note (controlled inputs).** A *controlled* input is one where React owns the value: the `<input>` always displays `draft.weight`, and each keystroke calls `onChange`, which stores the new text in state, which re-renders the input with it. The alternative (letting the browser own the text and reading it at submit) cannot do live validation, prefill, or reset-after-log. The draft holds **strings**, not numbers: while typing, `"12."` or `""` are legitimate intermediate values a number type cannot represent. Strings are parsed to numbers once, at submit (`parseDraft`), and only the fields the modality shows are read.

- **Why `inputMode`, not `type="number"`.** `type="number"` has a different decimal separator per locale, lets a scroll wheel change the value, accepts `e`, and on iOS Safari reports `""` for unparseable text so "empty" and "invalid" are indistinguishable. `<input type="text" inputMode="decimal">` summons the numeric keypad and leaves parsing to us: trim, replace `,` with `.`, match `^\d+(\.\d{1,3})?$` for weight/distance, `^\d+$` for reps/minutes/seconds, then range-check against the `@sin/core` constants (`SET_*_MAX`) and `toCanonicalMeters` for distance. Error messages are static strings ("Enter a whole number"), never echoing the typed value.
- **`reps: 0` is valid** (a failed attempt, 05.1 D14); so is weight `0`. Emptiness is `=== ""`, never truthiness.
- **RPE** accepts `1`–`10` with at most one decimal (`multipleOf(0.1)` server-side).
- **The draft reducer** (`draftReducer`) handles `edit(field, value)`, `reset(fromSet | null)`, and `logged(set)` (copy-forward + new attempt key). `draftFromSet` is the single place copy-forward and edit-sheet prefill happen.
- **Display numbers use a pinned `Intl.NumberFormat("en", { maximumFractionDigits: 3 })`** so tests and CI are locale-independent (06.0 AC6's reasoning); input parsing is lenient about the comma.

### 6.5 The create idempotency key (owner decision D15 — mint it now)

> **First-principles note (idempotency key).** A network write can fail in two different ways: the request never arrived, or it arrived and the *response* was lost. From the browser they look identical, and retrying the second case double-logs a set. An idempotency key is a client-chosen id sent with the write; the server remembers it and answers a repeat with the original result instead of acting twice (05.1 D15: a replay returns `200` with the stored row). The key must identify one *logical* attempt, so it is minted once per attempt and reused for every retry of it.

Decision, with its mechanics:

- Every set `POST` carries `clientGeneratedId = draft.attemptKey` (lower-case GUID, `crypto.randomUUID()`). The key is minted when a draft is created and **re-minted only after a success** (AC10). It is retained across failures and across edits to the draft.
- **Why send it in 06.1 rather than leave it to 06.2.** It costs one field; 06.2 then only has to persist and replay, without touching 06.1's call sites; and it makes this spec's one retry (the manual retry after a failed log) safe against the lost-response case.
- **The known edge, accepted and recorded (§12 D6).** The server answers a replay with the **stored** row and ignores the replayed body. If the first attempt actually succeeded, the response was lost, *and* the lifter then changed a value before retrying, the retry returns the old stored row: the screen shows what was stored (visible, one tap to edit), not a silent corruption. 06.2's retry layer can reconcile by refetching and matching the echoed `clientGeneratedId` before replaying; 06.1 does not.
- **Add-exercise and finish are not keyed.** Add has no key in the API (05.0 §6.6), so after an ambiguous failure the screen refetches and tells the lifter to check (AC18) instead of re-posting. Finish is made safe by handling its own replay answer (`409 workout-finished` ⇒ fetch and treat as done, AC28).
- The start-workout key (05.0 §6.1) is held in a ref for the lifetime of the Start screen and survives retries (AC16); it is not persisted (a reload mints a new one — the `409 workout-in-progress-exists` → resume path covers a started-but-unseen workout).

### 6.6 Finish: diagnosing `409 incomplete-working-sets`

The server's `409` carries no set or exercise id (05.1 AC13, the "no id leak" convention). The client therefore reproduces the server's rule locally with the same pure function the server uses (`requiredMeasuresFor`), after refetching so the screen is current:

1. On the `409`, `invalidate` and refetch `/active`.
2. `findIncompleteWorkingSets(detail)` (AC9) → ids of `working` sets with a `null` required measure. **`=== null`, not falsy** — `reps: 0` must not be flagged (it is a legitimate failed attempt, and the server's check is measures-presence, ignoring `isComplete`).
3. Flag those rows, show the banner, scroll the first into view. If the list is empty (server and client disagree, e.g. a rule changed), show the generic "Some sets are incomplete — reload and check your sets."
4. The client's diagnosis is **advisory**: the server stays the authority; the retry of Finish is what decides.

### 6.7 Logout write block and `<Sheet>` `close`

- **Write block (AC13).** `storage.ts` gains a module-level flag set by a new exported `blockUserDataWrites()`, called by `logoutAndClear` as its first line. While set, `localStorageAdapter().set()` is a silent no-op (not a throw — a throw would make 06.0's catalog store call `reportError` once and flip to in-memory mode, AC11). Module-level rather than per-adapter because the three logout sites each construct their own adapter and none holds the store's. The flag is never cleared in production (the page is about to unload through the Auth0 redirect); `resetUserDataWritesForTests()` clears it between tests. A page that survives the redirect failing (Auth0 unreachable) keeps working in memory with persistence off until reload — acceptable for a logged-out page.
- **`<Sheet>` `close` (AC32).** Add `onClose` handling for the native `close` event, guarded by a ref holding the latest `open` prop: if the dialog closed itself (a `<form method="dialog">`, a browser close request) while the parent still thinks it is open, tell the parent; if the parent closed it (the effect called `dialog.close()` after `open` went `false`), say nothing. Without it, a natively-closed sheet leaves `open === true` and the next "open" does nothing.

### 6.8 Layout, one-handed use, and the CSP

- **No `style=` props.** The production CSP is `style-src 'self'` (render.yaml): an inline style attribute is blocked as a violation. All styling is CSS Modules + tokens; dynamic variation uses class names or data attributes (AC34's scan; Spec 06.3's real-browser console check).
- **Thumb zone.** Primary repeated actions (Log set, Add exercise, Finish, confirm buttons) are in the lower third; destructive ones (Discard, Remove) are a deliberate extra tap away. The sticky action bar uses `position: sticky; bottom: 0` inside `AppShell`'s scrolling `<main>`, above the nav (which owns `env(safe-area-inset-bottom)`).
- **No auto-focus** of numeric inputs on mount or after a log (a phone keyboard popping up is the wrong default; same reasoning as 06.0's picker). After "Log set" focus stays on the button; the live region announces the result.
- **New tokens, if any, go in `tokens.css`** and nowhere else (CLAUDE.md); candidate additions are a `--color-warning` for the "Needs data" marker (text + border, never colour alone).
- **Real-keyboard behavior** (soft keyboard covering the sticky bar on iOS Safari, `100dvh` with a keyboard up) cannot be verified in jsdom or in Playwright's emulation (Spec 06.3); it is a **manual device check** recorded in the PR description (§10), and the M1 gym week is its real test.

### 6.9 Known limitations handed to 06.2

- Unlogged drafts are component state: leaving the Workouts tab, a reload, or an OS-evicted tab (R1) loses them. Logged sets are safe (they are on the server).
- A failed write must be retried by hand; there is no queue, no backoff, no "unsynced" indicator, and Finish is not blocked by anything pending.
- Closing the tab mid-request leaves the outcome unknown (the same ambiguity as a lost response; the key in memory is gone too).
- The active workout is only as fresh as the last focus/mount refetch; two devices editing one workout are last-write-wins per row (DESIGN §4.4).

## 7. Security & privacy

- **Authorization is the server's.** Every id this screen sends belongs to the caller; a cross-user probe is `404` (05.0 AC15, 05.1 AC4) and the UI treats `404` as "gone", never as a hint. The client's incomplete-set scan is advisory (§6.6).
- **No credentials or workout data in browser storage.** 06.1 writes nothing to storage (§4); tokens stay in memory (Q12). The logout write block (§6.7) closes the one window where catalog data could be re-persisted after clearing.
- **Output encoding.** Exercise names (`exerciseNameSnapshot`, server-stored verbatim) render through React's escaping; no `dangerouslySetInnerHTML`. Free text is not entered in this spec at all (titles/notes are deferred), so there is no new ingress to bound.
- **Inputs are numeric and validated twice**: client-side against the same `@sin/core` bounds the server enforces (so an out-of-range value is a field message, not a `422` round trip), and again by the server. A client check is a UX aid, never a control.
- **Observability hygiene.** No event or error tag carries an exercise name, an id, or a measure value (§9, AC35).
- **CSP.** The screen must work under the strict production CSP; no inline styles, no inline scripts, no `eval`-like APIs. Verified by AC34's scan here and in a real browser by Spec 06.3.

## 9. Observability

Via the existing `track()` / `reportError()` seams (no-ops until Spec 13). Events are fixed snake_case names with scalar, non-identifying properties:

| Event | Properties | Fires |
|---|---|---|
| `workout_started` | `resumed: boolean` (true when `409` → resumed) | start success |
| `exercise_added` | `modality` | add success |
| `exercise_moved` | `direction: "up" \| "down"` | move success |
| `exercise_removed` | `setCount: number` | remove success |
| `set_logged` | `modality`, `setType`, `edited: boolean`, `msToLog: number` | create success. `msToLog` is first interaction with the entry row → tap (0 when logged straight from prefill): the client-side proxy for DESIGN §1.3's < 5 s metric (it excludes rest time on purpose). |

| `finish_blocked` | `incompleteCount: number` | `409 incomplete-working-sets` |

| `workout_conflict` | `kind: "gone" \| "finished" \| "retired" \| "unavailable" \| "stale-position" \| "clock"` | each mapped conflict in §5.8 |

`reportError` is called only for a failure the user cannot act on and we did not predict (an unrecognised problem type on a mapped route; a state the matrix does not cover), with static tags `{ source: "workouts", op: "<operation name>" }` — never the error's detail, never an id (AC35). ## 11. Deployment & rollback

- **Web only. No API change, no migration.** Merge to `main` → the existing Render static-site auto-deploy. No feature flag: the "off" state is the previous deploy.
- **Order dependency:** 06.1 is meaningful only after Spec 05.1's D14/D15 follow-up (`feat/spec-05.1-followups`) is merged and deployed to staging — otherwise `clientGeneratedId` is rejected as an unknown key (`422`) by the strict create schema and every Log set fails. - **CI:** rides the existing `@sin/web` job (lint, typecheck, Vitest with the new coverage threshold, build, `assert:css-tokens`). No new job, step, or dependency.
- **Rollback:** Render "roll back to previous deploy", or revert the PR — `Workouts` returns to `ComingSoon`. Server data written by the screen (workouts, sets) stays valid and untouched; an in-progress workout simply becomes invisible until the screen returns. Nothing to unwind server-side, no stored-data migration (the screen persists nothing).
- **Dogfooding caveat.** M1's exit criterion ("log real gym sessions for a week, no data loss") needs Spec 06.2. Until it ships, this screen can be used on staging, but in the gym keep a fallback note: a dropped connection loses unlogged drafts and requires manual retries (§6.9). Spec 06.3's smoke is separate and does not gate this spec's merge.

## 12. Decisions & open questions

### Resolved (drafting-time; reversible at review)

- ✅ **D1 — The Workouts section is the resume surface.** `/app/workouts` asks `GET /v1/workouts/active` on every mount and focus; there is no client-side "current workout id". **Rationale:** the cold-load redirect (Q12) can drop the user on a page with no client state, and 05.0 added `GET /active` for exactly this; `staleTime: 0` + refetch-on-focus is the cheapest honest freshness. **Consequence:** one extra GET per visit; the resume path is also the recovery path for `409 workout-in-progress-exists`.
- ✅ **D2 — Set writes `setQueryData`; structure writes invalidate.** §6.2. **Rationale:** a created/patched set response is the whole truth for that row and the loop must feel instant; an exercise add/move/remove returns one row while sibling positions change, so only the server's detail is trustworthy. **Consequence:** one refetch per structure change; the `cancelQueries` rule (AC11) is load-bearing.
- ✅ **D3 — Writes are pessimistic in 06.1.** §6.3. **Rationale:** optimistic updates need the unsynced state, rollback and retry that Spec 06.2 owns; building a partial version twice is waste. **Consequence:** on a slow link each log shows a busy button until the response — this is the cost 06.2 removes.
- ✅ **D4 — All writes go through `WorkoutClient`; cache writes in hook-level `onSuccess`.** The seam 06.0 asked for ("one small seam so 06.2 can insert a queue without reworking 06.1"). **Rationale:** 06.2 swaps one object, not N call sites; hook-level callbacks survive unmounts (AC12).
- ✅ **D5 — `409 incomplete-working-sets` is diagnosed client-side with the shared rule.** §6.6. **Rationale:** the body carries no ids by design (05.1 AC13); `requiredMeasuresFor` is exported from `@sin/core` precisely so the client can field-gate and diagnose with the server's own rule. **Consequence:** advisory only; `=== null` (not falsy) is the one place a subtle bug would flag legitimate `reps: 0` sets (AC9).
- ✅ **D6 — The retained attempt key's lost-response-then-edited edge is accepted.** §6.5. **Rationale:** it needs a lost response *and* an edit before retry, produces a visible stored row (not corruption), and 06.2's reconcile-by-echoed-key fixes it properly.
- ✅ **D7 — Dispositions of 06.0's deferred items** — see §1's table: write block and `<Sheet>` `close` are in; store interleaving tests go to 06.2; `reportError` sanitization goes to Spec 13 (06.1 constrains its own call sites).
- ✅ **D8 — Shared `SetFields` for the entry row and the edit sheet; the edit surface is a `<Sheet>`.** One modality-driven field component, one overlay primitive; the edit sheet reuses 06.0's `<Sheet>` rather than adding an inline-expand variant. **Consequence:** editing a set is a full-height overlay (an acceptable cost for a rare action).
- ✅ **D9 — `<ConfirmDialog>` is a new small primitive on a native `<dialog>`, not `window.confirm`.** **Rationale:** `confirm()` is a blocking, unstyled, hard-to-test browser dialog with poor mobile behavior; the app already depends on the `<dialog>` and its jsdom shim. Remove-with-sets, Finish and Discard are all irreversible, so all three confirm; removing an empty exercise and deleting a single set do not (cheap to redo).
- ✅ **D10 — Duration is two numeric fields; weights/distances are `inputMode` text inputs, never `type="number"`.** §5.4, §6.4.
- ✅ **D11 — The pure modules live in `apps/web`, React-free, not yet in `@sin/core`.** Keeps 06.1 a UI-only spec (no `check-exports.mjs` churn). **Consequence:** `findIncompleteWorkingSets`, `formatSet`, `parseDraft` and `visibleMeasures` are promotion candidates (alongside 06.0's `visibility.ts`, Spec 16); `findIncompleteWorkingSets` in particular restates a server rule next to its source and should move to `core` with `requiredMeasuresFor` the first time anything else needs it.
- ✅ **D12 — `InlineNotice`, not `RetryScreen`, for in-shell errors.** `RetryScreen` renders its own `<main>` (it is a full-page gate screen); inside `AppShell`'s `<main>` that would nest landmarks.

### Resolved — owner decisions (2026-10-01)

The owner reviewed v0.1 and accepted every recommendation. Numbered D13–D26 (v0.1's O1–O14, in order).

- ✅ **D13 — Set-logging model: an entry row plus "Log set" (was O1; owner decision, 2026-10-01).** The entry row is a draft; the `POST` happens on tap with `isComplete: true`; logged sets are separate rows you tap to edit. **Rationale:** it matches the owner constraint (a server row exists only when logged; no local row pretends to be a set), makes every `POST` a complete set so D14's strict gate and the finish rule hold by construction, and makes the common "same again" set one tap. **Consequence:** no "3 × 8" laid out up front — that is routine-target territory (Spec 10), delivered as placeholders on this same entry row. Pre-listed tick-off rows can be built on top later; the reverse is harder.
- ✅ **D14 — Prefill the next set from the previous one, with real values (was O2; owner decision, 2026-10-01).** **Rationale:** it is what makes DESIGN §1.3's < 5 s metric reachable. **Consequence:** a lifter who forgets to change the weight logs the previous weight (one tap to edit; `set_logged.edited` shows how often).
- ✅ **D15 — Mint and send `clientGeneratedId` on every set create in 06.1 (was O3; owner decision, 2026-10-01).** §6.5. **Rationale:** free now; 06.2 then only adds persistence and replay; it makes this spec's manual retry safe. **Consequence:** the key-lifecycle rules (AC10) and the accepted edge (D6) are 06.1's.
- ✅ **D16 — Reorder with Move up / Move down buttons (was O4; owner decision, 2026-10-01).** `PATCH { position: p ± 1 }`. **Rationale:** no dependency, accessible, deterministic, testable in jsdom; reordering is rare. Drag-and-drop is revisited only if reordering proves frequent.
- ✅ **D17 — Finish always confirms and is disabled at zero sets (was O5; owner decision, 2026-10-01).** A UI policy, not an API rule (the API allows an empty finish). **Rationale:** an empty finished workout is clutter the lifter cannot remove until Spec 08; Discard is the right action for an empty session.
- ✅ **D18 — After Finish, show the read-only summary with Delete (was O6; owner decision, 2026-10-01).** **Rationale:** finished workouts are immutable, so a mistaken Finish is recoverable only by delete-and-relog, and nothing else reaches a finished workout until Spec 08; the route is reused by 08.
- ✅ **D19 — Title / notes editing deferred (was O7; owner decision, 2026-10-01).** Additive later (`UpdateWorkoutSchema` supports it); not in the README scope; avoids free-text ingress rules for little M1 value.
- ✅ **D20 — `/app` redirects to `/app/workouts` (was O8; owner decision, 2026-10-01).** Replaces 04.1's welcome placeholder, which was documented as temporary. **Consequence:** `AppIndex` and its test are removed or repointed.
- ✅ **D21 — The browser smoke runs post-deploy against staging with a real Auth0 test user (was O9; owner decision, 2026-10-01).** Detailed in Spec 06.3.
- ✅ **D22 — Silent refresh-token rotation stays a documented manual check (was O10; owner decision, 2026-10-01).** Detailed in Spec 06.3.
- ✅ **D23 — The smoke uses Chromium with Pixel 7 emulation only (was O11; owner decision, 2026-10-01).** Detailed in Spec 06.3.
- ✅ **D24 — The smoke is split out of 06.1 into Spec 06.3 (was O12; owner decision, 2026-10-01).** §1 "Scope split". **Rationale:** Phases A+B are one session; the smoke has external prerequisites that can stall independently of the screen.
- ✅ **D25 — Starting always creates a workout (was O13; owner decision, 2026-10-01).** The API allows an empty workout and the one-in-progress rule prevents accumulation; deliberate, no UI guard.
- ✅ **D26 — Unit and duration defaults (was O14; owner decision, 2026-10-01).** Weight unit = `unitPreference`; distance unit derived from it (`kg` → `km`, `lb` → `mi`) with `m` selectable; duration as minutes + seconds fields. **Rationale:** the preference is the only unit signal the app has; each set stores its own unit, so a wrong default costs one tap and corrupts nothing. A separate distance-unit preference would need a `PATCH /v1/me` change (out of scope).
