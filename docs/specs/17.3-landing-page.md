## 1. Purpose, scope & non-goals

### 1.1 Purpose

`screens/Landing.tsx` is the one screen a new or signed-out visitor sees. It is still the unstyled Spec 04.0 placeholder:
- a browser-default `h1`, no page padding;
- a "Log in" button that `reset.css` strips to plain text.

Its neighbor `screens/ResumingSession.tsx`, the screen a returning lifter sees on nearly every open as the app bounces to Auth0, is unstyled in the same way. The rest of the app now has an identity (Spec 17.0), so the front door is the one place that looks like a different product.

After this spec:

- **The landing page is a calm title card.** In order down the page:
  - the name **Strength in Numbers**, large and condensed in Instrument Sans, centered, on two lines ("Strength" / "in Numbers"), in the middle of the space above the sentence;
  - a hairline;
  - "Log your lifts." / "Count your progress." on two centered lines;
  - a big teal **Log in** button at the bottom of the screen, where a thumb rests.
  It sits on the Stone background, with nothing else on the page.
- **`ResumingSession` uses the same title card.** It shows the same name and hairline, "Resuming your session…" as the status line, and its existing "Go to sign in" link in the thumb zone (D14). A shared `screens/FrontDoor.tsx` renders the parts both screens have (D18).
- **The name is "Strength in Numbers" everywhere a person reads it** (PRODUCT.md's Brand Commitments): the landing, `<title>`, the in-app header's fallback title and the `Misconfigured` screen. Export filenames and the boot console message keep the slug (D10, D16).
- **Log in starts one login per tap.** After the first tap the button is busy, so a fast second tap cannot start a second login that breaks the first. A browser Back to the page re-enables it (D9).
- **Nothing else it does changes.**
  - The button runs the same `login()` helper with the same `returnTo`.
  - The page makes no request and no redirect on its own.
  - `PublicEntry` still decides which screen shows.

### 1.5 First-principles notes

> **"Thumb zone" is a layout rule, not a decoration.** On a phone held in one hand, the thumb comfortably reaches the lower part of the screen and poorly reaches the top corners. A primary action at the top of a tall screen costs a grip change.
>
> So on a phone the button sits at the bottom edge of the viewport, full column width, with the sentence just above it; the name takes the space above that. On a desktop (a pointer, not a thumb) the same column is capped in height and centered, so the button stays close to the sentence instead of 260 px below it.
>
> On a phone with a notch or a home indicator, the OS partly covers the very bottom and sides. CSS exposes those sizes as `env(safe-area-inset-bottom)` (and top, left, right). They are non-zero only when the page opts in with `viewport-fit=cover`, which it already does in `index.html`. Padding by those values keeps the button clear of the home indicator. A desktop browser reports 0, so nothing changes there.

> **The landing page is not a gate; it is one of four things `/` can show.** `PublicEntry` renders, in priority order:
> 1. a redirect to `/app` (live session);
> 2. `ResumingSession` (the Auth0 hint cookie exists, so it bounces straight to Universal Login);
> 3. the Auth0 spinner (`BootstrapGate`, while the SDK initializes);
> 4. `Landing`.
>
> A returning lifter with the hint cookie therefore usually sees `ResumingSession`, not this page. That is why it joins the restyle (D14). New visitors, and anyone who cancels out of Universal Login (via `AuthError` "Try again" to `/?signin`), see `Landing`.

> **What a "busy" button does, and why the browser's Back needs care.** `Button` already supports `busy`. It sets `aria-busy` and `disabled`, so the button keeps its look but ignores further clicks, Enter and Space.
>
> **The double tap.** Two very fast taps would call `loginWithRedirect` twice. Each call stores a fresh PKCE state, and the second overwrites the first. When Auth0 sends the visitor back with the first state, the callback's check fails and shows "Couldn't sign you in".
>
> **The Back button.** A browser can keep a page in its back/forward cache: pressing Back from Universal Login then restores the page exactly as it left it, busy button included, without remounting React. The browser fires a `pageshow` event with `persisted: true` when it does that. `PublicEntry` already listens for it (#14). `Landing` listens too and clears its busy flag, so the restored button works.

> **Why a design-only spec still needs acceptance criteria.** The risk is not the CSS. It is a restyle quietly changing behavior, for example a wrapper that swallows `returnTo`, or a heading change that breaks the e2e login helper, which finds the button by its name. The criteria pin the frozen behavior with tests that exist today and add the missing ones. Purely visual properties are checked by the screenshot harness and review, not by tests that scan the stylesheet (D17).

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"17.3 ACn — …"`**. Titles contain no quote or apostrophe characters, so the scan regex in AC34 matches. A scan test in the style of 17.2's enforces this. Levels are in §10.

### Copy and structure

1. **Exact landing copy.** The landing renders exactly:
   - an `h1` whose accessible name and whitespace-normalized text is `Strength in Numbers`. It is two `span` lines, "Strength" and "in Numbers", separated by a space text node.
   - a `p` whose normalized text is `Log your lifts. Count your progress.`, as two `span` lines, "Log your lifts." and "Count your progress.", separated by a space.
   - one `button` with the text `Log in`.

   In addition:
   - `index.html`'s `<title>` is `Strength in Numbers`.
   - None of these lines appears in `src/` outside test fixtures that assert their absence: "Log your lifts. See the numbers move." (today's), "Log your lifts, follow your plan, see your progress." (v0.1's) and "See your progress." (v0.2's).
2. **Nothing else.** The landing `main` contains exactly one heading, one paragraph and one button. The only other elements are the layout `div`s and the line `span`s inside the heading and the paragraph. There is:
   - no `a`, `img`, `svg`, `canvas`, `video` or `br`;
   - no icon, second `button`, form, nav or footer;
   - no `aria-live` region;
   - no text node outside those three elements.

   No "mark" is added; the name is plain text.
3. **Landmarks, heading, names.** One `main` landmark holds one `h1`, the app name, which is the only heading. The button's accessible name is `Log in`: it matches `/^log in$/i` via `getByRole("button", { name })`, which is what the e2e helper `NAMES.logIn` and the router tests use. The DOM order is `h1`, `p`, `button`. No redundant `aria-label`, `role` or `aria-labelledby` is added.
4. **One primary Button.** The login control is the shared `ui/Button` with `variant="primary"` and `block`, and `Landing.tsx` contains no raw `<button`. It is the page's only control, so it is the screen's one primary Button (DESIGN's "ideally one per screen").
5. **One front door.** `Landing` and `ResumingSession` both render through `FrontDoor`: the same `main` column, the same name `h1` and the same hairline line style. Neither screen writes the name, the column or the line styles itself; `FrontDoor.tsx` is the only source file that renders the two-line name (`<span>in Numbers</span>`). (`AppShell` and `Misconfigured` print the name as plain text, D16.)

### Behavior preserved

6. **Log in runs the same login.** The first activation of the button calls `loginWithRedirect` exactly once, through the shared `login()` helper, with today's arguments:
   - `appState: { returnTo }`;
   - `authorizationParams` with the configured `audience`, the `/callback` `redirect_uri` and `scope: "openid profile email offline_access"`.

   `returnTo` is `/app` by default, and the captured deep path when `PublicEntry` passes one (04.0 AC5, AC13). The existing router tests for both stay green without edits to their assertions.
7. **The page is inert on arrival.** Mounting `Landing` makes no `/v1/*` request (04.0 AC3), no other `fetch`/XHR, no `loginWithRedirect` call and no navigation. 04.0 AC3's existing test is updated only for the new copy.
8. **`PublicEntry` still decides when each screen shows, unchanged.** This spec does not modify `PublicEntry.tsx`, `BootstrapGate.tsx`, `login.ts`, `Callback.tsx` or `router.tsx` (a diff check in the PR). The existing 04.0 tests for the four outcomes pass unchanged:
   - a live session goes to `/app`;
   - the hint cookie goes to `ResumingSession` with the redirect;
   - no cookie goes to `Landing`;
   - `?signin`, and a history entry that already attempted a resume, go to `Landing`.
9. **Loading and error paths preserved.**
   - (a) While the Auth0 SDK is `isLoading`, the route shows the full-screen "Starting…" spinner, not `Landing` (the existing 04.0 "Bootstrap gate" test).
   - (b) After a failed login, `AuthError`'s "Try again" goes to `/?signin`, which renders `Landing`, and its Log in button works there. One new end-to-end router test covers this, from `/callback?error=access_denied` through "Try again" to a `loginWithRedirect` call.

   The landing screen itself has no loading or error state of its own (it never had one).
10. **Already signed in.** With `isAuthenticated`, `/` redirects to `/app` and `Landing` is not rendered (the existing 04.0 test), including with `?signin` present.
11. **Stable test hooks.**
    - `data-testid="landing"` stays on the landing `main`, `data-testid="landing-login"` on its button, and `data-testid="resuming-session"` on the resuming `main`. `FrontDoor` takes the test id as a prop.
    - `router.test`, `AppShell.test` and `workoutRouting.test` find the screens by these ids.
    - Nothing in `e2e/` or `scripts/smoke.mjs` names landing text or test ids, and neither is edited, so the Spec 06.3 smoke's `NAMES.logIn` lookup keeps working.

### One tap, one login (D9)

12. **A second tap does nothing.** After the first click (or Enter, or Space), the button is busy: `aria-busy="true"` and `disabled`. It keeps the primary look (Button's busy rule) and its label stays `Log in`. A second click, Enter or Space in the same page life does not call `loginWithRedirect` again: the spy is called exactly once after two rapid clicks.
13. **Back restores a usable button.**
    - When the page is restored from the back/forward cache, a `pageshow` event with `persisted: true` clears the busy state: the button is enabled, and a further click calls `loginWithRedirect` once more.
    - A `pageshow` with `persisted: false` changes nothing.
    - A fresh mount starts not busy.
    - The listener is removed on unmount.

**Landing's busy state:**

```tsx
const [busy, setBusy] = useState(false);
useEffect(() => {
  const onPageShow = (event: PageTransitionEvent) => { if (event.persisted) setBusy(false); };
  window.addEventListener("pageshow", onPageShow);
  return () => window.removeEventListener("pageshow", onPageShow);
}, []);
const start = () => {
  if (busy) return;
  setBusy(true);
  login(loginWithRedirect, returnTo);
};
```

*As built:* the guard is a ref (`inFlight`), not the `busy` state. Two events in the same task share one render, so `if (busy) return` read `false` in both and let a second login through (found in code review; the AC12 test now clicks twice inside one `act`). `busy` only drives the button's look and `disabled`.
