### 1.5 First-principles notes

> **"Thumb zone" is a layout rule, not a decoration.** On a phone held in one hand the thumb comfortably reaches the lower part of the screen and poorly reaches the top corners. A primary action placed at the top of a tall screen costs a grip change. So the button sits at the bottom edge of the viewport, full column width, and the name and sentence take the space above it. On a phone with a notch or a home indicator, the very bottom and sides are partly covered by the OS: CSS exposes those sizes as `env(safe-area-inset-bottom)` (and top, left, right), which are non-zero only when the page opts in with `viewport-fit=cover` (it already does, in `index.html`). Padding by those values keeps the button clear of the home indicator. A desktop browser reports 0 and nothing changes.

> **The landing page is not a gate; it is one of four things `/` can show.** `PublicEntry` renders, in priority order: a redirect to `/app` (live session), `ResumingSession` (the Auth0 hint cookie exists, so it bounces straight to Universal Login), the Auth0 spinner (`BootstrapGate`, while the SDK initializes), or `Landing`. A returning lifter with the hint cookie therefore usually never sees this page. Restyling Landing changes the first impression of new visitors and of anyone who cancels out of Universal Login (via `AuthError` "Try again" to `/?signin`), not of the daily open. That is why this spec stays small.

> **Why a design-only spec still needs acceptance criteria.** The risk is not the CSS; it is a restyle quietly changing behavior (a wrapper that swallows `returnTo`, a heading change that breaks the e2e login helper that finds the button by its name). The criteria pin the frozen behavior with tests that exist today and add the missing ones.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"17.3 ACn — …"`** (titles contain no quote or apostrophe characters, so the scan regex in AC27 matches), enforced by a scan test in the style of 17.2's. Levels are in §10.

### Copy and structure

1. **Exact copy.** The page renders exactly: an `h1` with the text `strength-in-numbers`; a `p` with `Log your lifts, follow your plan, see your progress.` (with the commas and the final period); and one `button` with the text `Log in`. The old line "Log your lifts. See the numbers move." appears nowhere in `src/` (outside test fixtures that assert its absence).
2. **Nothing else.** The landing `main` contains exactly one heading, one paragraph and one button: no `a`, `img`, `svg`, `canvas`, `video`, icon, second `button`, form, nav, footer or `aria-live` region, and no text node outside those three elements (a "mark" is explicitly not added; the name is plain text).
3. **Landmarks, heading, names.** One `main` landmark holds one `h1`, and the `h1` is the app name (the only heading); the button's accessible name is `Log in` (matches `/^log in$/i` via `getByRole("button", { name })`, which is what the e2e helper `NAMES.logIn` and the router tests use). The DOM order is `h1`, `p`, `button`. No redundant `aria-label`, `role` or `aria-labelledby` is added.
4. **One primary Button.** The login control is the shared `ui/Button` with `variant="primary"` and `block`; `Landing.tsx` contains no raw `<button`. It is the page's only control, so it is the screen's one primary Button (DESIGN's "ideally one per screen").

### Behavior preserved

5. **Log in runs the same login.** Activating the button calls `loginWithRedirect` exactly once, through the shared `login()` helper, with today's arguments: `appState: { returnTo }`, `authorizationParams` with the configured `audience`, the `/callback` `redirect_uri` and `scope: "openid profile email offline_access"`. `returnTo` is `/app` by default and the captured deep path when `PublicEntry` passes one (04.0 AC5, AC13). The existing router tests for both stay green without edits to their assertions.
6. **The page is inert on arrival.** Mounting `Landing` makes no `/v1/*` request (04.0 AC3), no other `fetch`/XHR, no `loginWithRedirect` call and no navigation. (04.0 AC3's existing test is updated only for the new one-liner.)
7. **`PublicEntry` still decides when it shows, unchanged.** `PublicEntry.tsx`, `BootstrapGate.tsx`, `login.ts`, `Callback.tsx` and `router.tsx` are not modified by this spec (a diff check in the PR), and the existing 04.0 tests for the four outcomes (live session to `/app`; hint cookie to `ResumingSession` with the redirect; no cookie to `Landing`; `?signin` and an already-attempted history entry to `Landing`) pass unchanged.
8. **Loading and error paths preserved.** (a) While the Auth0 SDK is `isLoading`, the route shows the full-screen "Starting…" spinner and not `Landing` (the existing 04.0 "Bootstrap gate" test). (b) After a failed login, `AuthError`'s "Try again" goes to `/?signin`, which renders `Landing`, and its Log in button works there: one new end-to-end router test, from `/callback?error=access_denied` through "Try again" to a `loginWithRedirect` call. The landing screen itself has no loading or error state of its own (it never had one).
9. **Already signed in.** With `isAuthenticated`, `/` redirects to `/app` and `Landing` is not rendered (the existing 04.0 test), including with `?signin` present.
10. **Stable test hooks.** `data-testid="landing"` stays on the `main` and `data-testid="landing-login"` on the button (`router.test`, `AppShell.test` and `workoutRouting.test` find the screen by the first; nothing in `e2e/` or `scripts/smoke.mjs` names landing text or test ids, and they are not edited, so the Spec 06.3 smoke's `NAMES.logIn` lookup keeps working).

### Layout (320 / 390 / 1280 px)

11. **Thumb-zone composition.** At 390 x 844 and 320 x 568 (light and dark), the button's box lies entirely in the lower 30% of the viewport and its bottom edge is at least the safe-area inset plus `--space-6` above the viewport's bottom edge; the name and the sentence sit above it, grouped, in the free space (vertically centered in it). The same single layout is used at every width (D6). Checked by the screenshot harness's `_report.json` (§6.6) and visually.
12. **A big button.** The button fills the column's width and is at least `--tap-target-min` + `--space-3` (56 px) tall with `--font-size-lg` text; it stays a native `button` with the shared primary look (teal fill, on-signal text, `--radius-md`).
13. **Safe areas.** The page's padding on all four sides adds `env(safe-area-inset-*)` to its base padding (top, right, bottom, left), so the button clears a home indicator in portrait and a notch in landscape. A CSS scan test asserts all four `env()` uses in `Landing.module.css`; the notched-phone behavior is the owner's phone check (a desktop browser cannot emulate insets).
14. **No horizontal scroll; wrapping is safe.** At 320, 390 and 1280 px, `document.documentElement.scrollWidth <= clientWidth`. The name (one unbroken, hyphenated word of 19 characters at the display size) wraps after a hyphen at 320 px ("strength-in-" / "numbers") and never clips or overflows (`overflow-wrap: anywhere` is the backstop, `text-wrap: balance` for the break). With the browser's text size at 200% the content may scroll vertically, but the button stays reachable by scrolling and never overlaps the text. *(Checked by the harness at the three widths; the 200% case is manual.)*
15. **Desktop.** At 1280 x 800 the content is a single left-aligned column of at most `--landing-column-max`, centered in the viewport; the button is the column's width (not 40 rem wide), still at the bottom. No two-column hero, no max-width image.

### Visual

16. **Stone ground and nothing decorative.** The page paints on the page's `--color-bg` (inherited from `body`; `Landing.module.css` sets no background), with no panel, card, border, outline, shadow, gradient, image or pattern of its own.
17. **Type.** The name is the app's one typeface (the stylesheet declares no `font-family`; it inherits Instrument Sans from `body`), weight 700, at the new `--font-size-brand` token, `--color-text`, line-height at most 1.15. The sentence is `--font-size-lg` in `--color-muted`. Numbers do not appear on the page, so the figure tokens are not used. No second typeface or font request is added.
18. **Color roles and contrast.** `Landing.module.css` uses only `--color-text` and `--color-muted` (on `--color-bg`) for color; the button's teal comes from `Button.module.css`. No brass, no teal in Landing's own stylesheet, so `roles.test.ts` needs no new allow-list entry. The three contrast pairs the page uses (text on bg, muted on bg, on-signal on signal) are already in the 17.0 table and pass in both themes at 4.5:1; no pair is added.
19. **Tokens only.** Every length, size and color in `Landing.module.css` is a token or an arithmetic of tokens; the two new tokens (`--font-size-brand`, `--landing-column-max`) are written once in `tokens.css`'s base block (non-color tokens are not duplicated into the dark blocks). No inline `style`. `assert:css-tokens` passes.
20. **No animation.** `Landing.module.css` contains no `animation`, `@keyframes`, `transition` or `transform`, and the component uses no timer or effect. *(The shared `Button` keeps its existing 120 ms color ease on hover and focus; this spec does not touch it.)*
21. **Dark and the theme override.** In dark (OS preference) and with `sin:pref:theme` set to `dark` on a light OS, the page shows the dark Stone values with the same layout; with `light` stored on a dark OS it shows light. (Unit: the theme helper's existing tests; screenshots: both themes at both widths, plus an override capture on the landing.)

### Interaction and accessibility

22. **Focus order and keyboard.** There is exactly one tab stop, the Log in button; nothing is auto-focused on load; pressing Tab from the document start lands on it; Enter and Space activate it (native button) and call `login()` once. The global `:focus-visible` ring (2 px `--color-focus`, 2 px offset) is visible on it in both themes and not clipped (the column's padding is larger than the ring plus offset). A harness capture shows the focused state.
23. **Axe-clean.** `jest-axe` finds no violations on the rendered page in light and dark (the 17.1 `a11y.test.tsx` pattern), covering the heading structure (one `h1`, no skipped level), the landmark (one `main`) and names.

### Constraints

24. **No new dependency, request or asset.** `package.json` and `pnpm-lock.yaml` are unchanged; no new file under `public/` or `src/ui/fonts/`; the page issues no network request of its own (AC6) and `assert:build-output` and `assert-render-yaml` pass unchanged (CSP unchanged).
25. **Smoke and e2e unchanged and green.** `apps/web/e2e/**` and `apps/web/scripts/smoke.mjs` are not edited; the post-deploy smoke and the Spec 06.3 e2e (which find the button by the name "Log in" on `/app/workouts`'s redirect to the landing) pass on staging after the deploy.

### Harness, gates, docs

### 5.2 Flows (all unchanged; stated so the restyle cannot change them)

- `/` with no session and no hint cookie: this page. Tap Log in: `login(loginWithRedirect, returnTo)`: full-page redirect to Auth0 Universal Login, back to `/callback`, then to `returnTo` (default `/app`).
- A deep link while signed out (`/app/history/123`): `ProtectedRoute` sends the visitor to `/` with `state.returnTo`; this page forwards it; after login the lifter lands on the deep link.

- Signed in: `/` redirects to `/app`. Hint cookie present: `ResumingSession` and an immediate redirect (this page is skipped).
- Auth0 initializing: the "Starting…" spinner (`BootstrapGate`), then one of the above.

## 6. Behavior & logic

### 6.0 Decisions carried over (owner, 2026-10-15, accepted defaults)

A calm front door for the owner and invited friends, not a product page. The page has the app name set in Instrument Sans, one plain line on what it does and a big Log in button in the thumb zone, on the Stone background. Nothing else. One-liner: "Log your lifts, follow your plan, see your progress." No mark: the name is set in Instrument Sans. The button says "Log in". Whether strangers can sign up is an Auth0 setting to check separately, not a design decision. A product page waits for the production launch. **Scope (owner, 2026-10-17):** design only, same functionality; a request-access button or waitlist is a separate, later spec.

### 6.1 Markup

```tsx
<main className={styles.landing} data-testid="landing">
  <div className={styles.column}>
    <div className={styles.intro}>
      <h1 className={styles.name}>strength-in-numbers</h1>
      <p className={styles.line}>Log your lifts, follow your plan, see your progress.</p>
    </div>
    <Button block className={styles.login} data-testid="landing-login"
            onClick={() => login(loginWithRedirect, returnTo)}>Log in</Button>
  </div>
</main>
```

`Button`'s default `type="button"` and `variant="primary"` apply. The screen does not use `ui/Screen` (a `section` with its own padding and a 40 rem measure, built for in-app pages inside `AppShell`); the landing renders outside `AppShell` and needs its own full-viewport column. (D8.)

### 6.2 Stylesheet shape (the design values are tokens; this is the structure, not final numbers)

- `.landing`: `min-height: 100dvh`, flex column, `align-items: center`, padding = `--screen-pad` (sides) / `--space-8` (top) / `--space-6` (bottom), each plus the matching `env(safe-area-inset-*)`.
- `.column`: `width: 100%`, `max-width: var(--landing-column-max)`, `flex: 1`, flex column.
- `.intro`: `flex: 1`, flex column, `justify-content: center`, `gap: var(--space-3)`. Left-aligned text.
- `.name`: `font-size: var(--font-size-brand)`, `font-weight: 700`, `line-height: 1.1`, `text-wrap: balance`, `overflow-wrap: anywhere`.
- `.line`: `font-size: var(--font-size-lg)`, `color: var(--color-muted)`.
- `.login`: `min-height: calc(var(--tap-target-min) + var(--space-3))`, `font-size: var(--font-size-lg)`.

New tokens (base block of `tokens.css` only): `--font-size-brand: 2.5rem;` and `--landing-column-max: 22rem;`. (Layout tokens of this kind already exist: `--stepper-min-width`, `--field-min-width`.) Dark values are untouched.

### 6.3 Focus and keyboard

No `autoFocus`, no `tabIndex`, no focus management effect. The button is the first and only tab stop; the global focus ring applies. A screen reader reads the landmark, the heading (the app name), the sentence, then the button.

### 6.4 Reduced motion

Nothing moves, so there is nothing to reduce (AC20).

### 6.5 What is deliberately not done

No busy/disabled state after a tap (D9); no `Cache-Control`/preload additions (the font is already preloaded in `index.html`); no `<meta name="description">` or Open Graph tags (they are product-page and sharing concerns, deferred with the GA site); no autofocus; no login-hint prefill; no "remember me" copy.

### 6.6 Harness checks (AC26)

In `capture.mjs`, after the landing loads, evaluate in the page: the button's `getBoundingClientRect()` against `window.innerHeight` (the box's top must be at least 70% of the viewport height, and `innerHeight - bottom >= space-6` in CSS pixels, read from the computed `padding-bottom` of `main`), and `scrollWidth <= clientWidth`. Violations go to `_report.json` under `landing`. A new 320 x 568 mobile context (landing only; the rest of the harness keeps 390 and 1280), a `page.keyboard.press("Tab")` capture for the focus state, and an override-theme capture reuse the existing anonymous-context code.

## 12. Decisions & open questions

### Decisions

- ✅ **D1 (owner, 2026-10-17) — Design only, the same functionality.** The page keeps one control, a Log in button that starts the existing Auth0 flow. *Rejected for now:* a request-access button or waitlist (BL-19), and any sign-up-policy change.
- ✅ **D2 (owner, 2026-10-15) — A calm front door, not a product page.** Name in Instrument Sans (no mark), one line, a big Log in button in the thumb zone, on the Stone background, nothing else. A product page waits for the production launch (Spec 14).
- ✅ **D3 (owner, 2026-10-15) — The one-liner is "Log your lifts, follow your plan, see your progress."** Replaces "Log your lifts. See the numbers move."
- ✅ **D4 (owner, 2026-10-15) — The button says "Log in".** Unchanged; it is also the accessible name the e2e login helper finds.
- ✅ **D5 (owner, 2026-10-15) — Whether strangers can sign up is an Auth0 setting to check separately, not a design decision.** See "Owner-side checks".
- ✅ **D6 (mine) — One layout at every width: the button is bottom-anchored in a capped column.** *Rationale:* the thumb-zone rule matters on phones, and one layout is the smallest coherent thing (the repo has no width breakpoints today, and a media query cannot read the tokens). On a 1280 px desktop the column is narrow and centered, so the bottom button is a little far from the sentence; that costs a mouse user a longer glide, not a failed tap. *Rejected:* a `(pointer: coarse)` query to float the button under the sentence on desktops (a second layout to test for a screen the owner mostly sees on a phone); a full-width 40 rem button (a 640 px bar reads as a banner, not a front door). *Revisit* if the 1280 px capture reads as stranded.
- ✅ **D7 (mine) — Two new layout tokens: `--font-size-brand` (2.5rem) and `--landing-column-max` (22rem), base block only.** *Rationale:* `tokens.css` is the only place design values are written, the name needs a size above `--font-size-xl` (1.75rem, a screen title), and nothing else should reuse either, so they get role-named tokens instead of a general scale. Non-color tokens are not duplicated into the dark blocks (17.0). 2.5rem is the proposed size: at 320 px the 288 px content width should fit "strength-in-" (12 characters) on one line and wrap before "numbers"; confirm in the 320 capture and adjust the token if not.
- ✅ **D8 (mine) — Keep a plain `main` with its test ids; do not use `ui/Screen`.** *Rationale:* `Screen` is the in-app scaffold (a `section` with the standard gutter and 40 rem measure, inside the `AppShell` scroller); the landing is outside the shell and needs a full-viewport column. The `landing` and `landing-login` test ids are used by several router and shell tests, so removing them would churn tests for no gain.
- ✅ **D9 (mine) — No busy/disabled state after the tap.** *Rationale:* the owner asked for the same functionality, and `loginWithRedirect` leaves the page within moments. `Button` does support `busy`, which would also stop a double tap (a second `loginWithRedirect` overwrites the first PKCE state in storage, so a very fast double tap could, in theory, fail the callback's state check and show `AuthError`; this was never reported). *Revisit* only if that is ever seen; it would be a one-line change plus a test. Not an open question because behavior is out of scope.
- ✅ **D10 (mine) — The name is the lowercase, hyphenated `strength-in-numbers`, exactly as in `<title>` and today's `h1`; the sentence keeps sentence case with the final period.** *Rationale:* the owner said "the app name" and every existing surface (title, current heading, `Landing` test) spells it that way; changing capitalization or inserting spaces would be a branding decision.
- ✅ **D11 (mine) — Left-aligned text, not centered.** *Rationale:* the rest of the app is left-aligned in one column, and a centered block of one hyphenated word and a wrapping sentence leaves ragged edges on both sides. Confirm in the screenshots.
- ✅ **D12 (mine) — Muted, not ink, for the sentence.** *Rationale:* it makes the name the single strongest element and keeps the page to two weights of gray plus one teal action; `--color-muted` on `--color-bg` passes 4.5:1 in both themes (17.0 table).
