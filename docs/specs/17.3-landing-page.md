### 1.5 First-principles notes

> **"Thumb zone" is a layout rule, not a decoration.** On a phone held in one hand the thumb comfortably reaches the lower part of the screen and poorly reaches the top corners. A primary action placed at the top of a tall screen costs a grip change. So on a phone the button sits at the bottom edge of the viewport, full column width, with the sentence just above it, and the name takes the space above that. On a desktop (a pointer, not a thumb) the same column is capped in height and centered, so the button stays close to the sentence instead of 260 px below it. On a phone with a notch or a home indicator, the very bottom and sides are partly covered by the OS: CSS exposes those sizes as `env(safe-area-inset-bottom)` (and top, left, right), which are non-zero only when the page opts in with `viewport-fit=cover` (it already does, in `index.html`). Padding by those values keeps the button clear of the home indicator. A desktop browser reports 0 and nothing changes.

> **The landing page is not a gate; it is one of four things `/` can show.** `PublicEntry` renders, in priority order: a redirect to `/app` (live session), `ResumingSession` (the Auth0 hint cookie exists, so it bounces straight to Universal Login), the Auth0 spinner (`BootstrapGate`, while the SDK initializes), or `Landing`. A returning lifter with the hint cookie therefore usually never sees this page. Restyling Landing changes the first impression of new visitors and of anyone who cancels out of Universal Login (via `AuthError` "Try again" to `/?signin`), not of the daily open. That is why this spec stays small.

> **Why a design-only spec still needs acceptance criteria.** The risk is not the CSS; it is a restyle quietly changing behavior (a wrapper that swallows `returnTo`, a heading change that breaks the e2e login helper that finds the button by its name). The criteria pin the frozen behavior with tests that exist today and add the missing ones.

### Behavior preserved

5. **Log in runs the same login.** Activating the button calls `loginWithRedirect` exactly once, through the shared `login()` helper, with today's arguments: `appState: { returnTo }`, `authorizationParams` with the configured `audience`, the `/callback` `redirect_uri` and `scope: "openid profile email offline_access"`. `returnTo` is `/app` by default and the captured deep path when `PublicEntry` passes one (04.0 AC5, AC13). The existing router tests for both stay green without edits to their assertions.
6. **The page is inert on arrival.** Mounting `Landing` makes no `/v1/*` request (04.0 AC3), no other `fetch`/XHR, no `loginWithRedirect` call and no navigation. (04.0 AC3's existing test is updated only for the new one-liner.)
7. **`PublicEntry` still decides when it shows, unchanged.** `PublicEntry.tsx`, `BootstrapGate.tsx`, `login.ts`, `Callback.tsx` and `router.tsx` are not modified by this spec (a diff check in the PR), and the existing 04.0 tests for the four outcomes (live session to `/app`; hint cookie to `ResumingSession` with the redirect; no cookie to `Landing`; `?signin` and an already-attempted history entry to `Landing`) pass unchanged.
8. **Loading and error paths preserved.** (a) While the Auth0 SDK is `isLoading`, the route shows the full-screen "Starting…" spinner and not `Landing` (the existing 04.0 "Bootstrap gate" test). (b) After a failed login, `AuthError`'s "Try again" goes to `/?signin`, which renders `Landing`, and its Log in button works there: one new end-to-end router test, from `/callback?error=access_denied` through "Try again" to a `loginWithRedirect` call. The landing screen itself has no loading or error state of its own (it never had one).
9. **Already signed in.** With `isAuthenticated`, `/` redirects to `/app` and `Landing` is not rendered (the existing 04.0 test), including with `?signin` present.
10. **Stable test hooks.** `data-testid="landing"` stays on the `main` and `data-testid="landing-login"` on the button (`router.test`, `AppShell.test` and `workoutRouting.test` find the screen by the first; nothing in `e2e/` or `scripts/smoke.mjs` names landing text or test ids, and they are not edited, so the Spec 06.3 smoke's `NAMES.logIn` lookup keeps working).

### 6.1 Markup

```tsx
<main className={styles.landing} data-testid="landing">
  <div className={styles.column}>
    <div className={styles.top}>
      <h1 className={styles.name}>
        <span>Strength</span> <span>in Numbers</span>
      </h1>
    </div>
    <div className={styles.foot}>
      <p className={styles.line}>
        <span>Log your lifts</span> <span>See your progress.</span>

```

The space between the spans matters: the spans are blocks, so the space is invisible, but it keeps the text content and the heading's accessible name "Strength in Numbers" rather than "Strengthin Numbers" (AC1). `Button`'s default `type="button"` and `variant="primary"` apply. The screen does not use `ui/Screen` (a `section` with its own padding and a 40 rem measure, built for in-app pages inside `AppShell`); the landing renders outside `AppShell` and needs its own full-viewport column. (D8.)

### 6.2 Stylesheet shape (the design values are tokens; this is the structure, not final numbers)

- `.column`: `width: 100%`, `max-width: var(--landing-column-max)`, `flex: 1`, flex column, `text-align: center`.
- `.top`: `flex: 1`, flex, `align-items: center`, `justify-content: center`, `padding-block: var(--space-8)` (the name never touches the hairline).
- `.name`: `font-size: var(--font-size-brand)`, `font-weight: 700`, `font-stretch: var(--font-stretch-brand)`, `letter-spacing: var(--letter-spacing-brand)`, `line-height: 0.92`; `.name span { display: block }`.
- `.foot`: flex column, `gap: var(--space-6)`.
- `.line`: `font-size: var(--font-size-lg)`, `color: var(--color-muted)`, `border-top: 1px solid var(--color-line)`, `padding-top: var(--space-4)`; `.line span { display: block }`.
- `.login`: `min-height: calc(var(--tap-target-min) + var(--space-3))`, `font-size: var(--font-size-lg)`.
- `@media (min-width: 48rem)`: `.landing { justify-content: center }`, `.column { max-height: var(--landing-column-max-height) }` (the column still grows with `flex: 1`, so the cap is what centers it).


(The name's `0.92` line-height stays unitless, as `--line-height` is. Layout tokens of this kind already exist: `--stepper-min-width`, `--field-min-width`.) Dark values are untouched. The `clamp()` gives about 3.3rem at 320 px, 3.7rem at 390 px and the 5.5rem cap on desktop; "in Numbers" at 75% width fits the 288 px column at 320 (checked in the mockup).

### 6.3 Focus and keyboard

No `autoFocus`, no `tabIndex`, no focus management effect. The button is the first and only tab stop; the global focus ring applies. A screen reader reads the landmark, the heading ("Strength in Numbers"), the sentence, then the button. Without a period after "Log your lifts", some screen readers run the two lines together without a pause; O2.

### 6.4 Reduced motion

Nothing moves, so there is nothing to reduce (AC20).

### 6.5 What is deliberately not done

No busy/disabled state after a tap (D9); no `Cache-Control`/preload additions (the font is already preloaded in `index.html`); no `<meta name="description">` or Open Graph tags (they are product-page and sharing concerns, deferred with the GA site); no autofocus; no login-hint prefill; no "remember me" copy.

### 6.6 Harness checks (AC26)

In `capture.mjs`, after the landing loads, evaluate in the page: below 48rem, the button's `getBoundingClientRect()` against `window.innerHeight` (the box's top at least 85% of the viewport height, and `innerHeight - bottom` equal to the computed `padding-bottom` of `main`); at every width, the name's vertical center within `--space-4` of the midpoint between the column's top and the sentence's top border, the line-box count of each `span` in the `h1` and the `p` (exactly 1), and `scrollWidth <= clientWidth`. Violations go to `_report.json` under `landing`. A new 320 x 568 mobile context (landing only; the rest of the harness keeps 390 and 1280), a `page.keyboard.press("Tab")` capture for the focus state, and an override-theme capture reuse the existing anonymous-context code.

## 12. Decisions & open questions

### Decisions

- ✅ **D1 (owner, 2026-10-17) — Design only, the same functionality.** The page keeps one control, a Log in button that starts the existing Auth0 flow. *Rejected for now:* a request-access button or waitlist (BL-19), and any sign-up-policy change.
- ✅ **D2 (owner, 2026-10-15) — A calm front door, not a product page.** Name in Instrument Sans (no mark), one line, a big Log in button in the thumb zone, on the Stone background, nothing else. A product page waits for the production launch (Spec 14).
- ✅ **D3 (owner, 2026-10-17; supersedes the 2026-10-15 line) — The sentence is two lines, "Log your lifts" / "See your progress."** Replaces "Log your lifts. See the numbers move." and v0.1's "Log your lifts, follow your plan, see your progress." Punctuation of the first line is O2.
- ✅ **D4 (owner, 2026-10-15) — The button says "Log in".** Unchanged; it is also the accessible name the e2e login helper finds.
- ✅ **D5 (owner, 2026-10-15) — Whether strangers can sign up is an Auth0 setting to check separately, not a design decision.** See "Owner-side checks".
- ✅ **D6 (mine, revised in v0.2) — Two arrangements of one column, at the existing 48rem breakpoint.** Below 48rem the column fills the viewport height, so the button is bottom-anchored in the thumb zone and the name centers in the space above the hairline. At 48rem and up the column is capped at `--landing-column-max-height` and centered, so a desktop button sits under the sentence. *Correction:* v0.1 said "the repo has no width breakpoints today"; `AppShell.module.css` already has `@media (min-width: 48rem)`, and this reuses that literal. *Rejected:* one layout at every width (the v0.1 design: at 1280 x 800 the button sat about 260 px below the sentence, the "stranded" case v0.1 said to revisit); a `(pointer: coarse)` query (a second axis to test, where width already separates the cases).
- ✅ **D7 (mine, revised in v0.2) — Brand and landing tokens, base block only:** `--font-size-brand` (a `clamp()`, 3.25–5.5rem), `--font-stretch-brand` (75%), `--letter-spacing-brand` (-0.02em), `--landing-column-max` (30rem), `--landing-column-max-height` (40rem). *Rationale:* `tokens.css` is the only place design values are written, the name needs a size above `--font-size-xl`, and nothing else should reuse these, so they get role-named tokens instead of a general scale. The condensed 75% width is the font's own width axis (the figure tokens use 90%), so it adds no font file. Non-color tokens are not duplicated into the dark blocks (17.0). *Correction:* v0.1's 2.5rem slug did not fit "strength-in-" on one line as claimed, and `text-wrap: balance` broke it as "strength-" / "in-numbers" at 320, 390 and 1280; v0.2's line breaks are authored in the markup (AC14).
- ✅ **D8 (mine) — Keep a plain `main` with its test ids; do not use `ui/Screen`.** *Rationale:* `Screen` is the in-app scaffold (a `section` with the standard gutter and 40 rem measure, inside the `AppShell` scroller); the landing is outside the shell and needs a full-viewport column. The `landing` and `landing-login` test ids are used by several router and shell tests, so removing them would churn tests for no gain.
- ✅ **D9 (mine) — No busy/disabled state after the tap.** *Rationale:* the owner asked for the same functionality, and `loginWithRedirect` leaves the page within moments. `Button` does support `busy`, which would also stop a double tap (a second `loginWithRedirect` overwrites the first PKCE state in storage, so a very fast double tap could, in theory, fail the callback's state check and show `AuthError`; this was never reported). *Revisit* only if that is ever seen; it would be a one-line change plus a test. Not an open question because behavior is out of scope.
- ✅ **D10 (owner, 2026-10-17; reverses v0.1's D10) — The name is "Strength in Numbers", in the `h1` and `<title>`.** PRODUCT.md's Brand Commitments already write it that way; the lowercase hyphenated `strength-in-numbers` is the repo name, and in the largest type on the page it read as one (critique P1). The `h1` is two authored lines, "Strength" / "in Numbers". Other places that print the slug are O3.
- ✅ **D11 (owner, 2026-10-17; reverses v0.1's left alignment) — Centered text.** The name, the sentence and the button label are centered in the column. The left-aligned in-app screens are unaffected: the landing is a title card, not an app screen.
- ✅ **D12 (mine) — Muted, not ink, for the sentence.** *Rationale:* it makes the name the single strongest element and keeps the page to two weights of gray plus one teal action; `--color-muted` on `--color-bg` passes 4.5:1 in both themes (5.2:1 / 6.8:1).
- ✅ **D13 (owner, 2026-10-17) — One hairline above the sentence.** A 1px `--color-line` rule the full column width, chosen over the same design without it. It separates the title card from the action group. It is the decorative hairline, never `--color-border` (Two Borders Rule).

### Open questions

- **O1 — Restyle `ResumingSession` and `AuthError` in this PR, or leave them unstyled? (Owner.)** Both are the same kind of unstyled 04.0 placeholder (default `h1`/button/link) and are the screens next to this page in the two flows that matter: the returning lifter (hint cookie) sees `ResumingSession`, not `Landing`, on nearly every open; a canceled or failed login shows `AuthError`. After this PR the front door will look finished and its neighbors will not. *Recommendation (v0.2, after the critique):* include `ResumingSession` in 17.3, because it is the screen a returning lifter actually sees, as a flash of browser-default type before Universal Login; leave `AuthError` to the design-refresh "Final pass" list or a 17.3.1 that reuses Landing's column. (v0.1 recommended leaving both out.) They would share `Landing.module.css`'s column and the same `Button`, so the follow-up is small. If the owner says include them, it adds two files, about six tests and screenshots, still one session.

- **O2 — A period after "Log your lifts"? (Owner.)** As given, the first line has no period and the second does. *Recommendation:* "Log your lifts." / "See your progress.": the lines then match, and screen readers pause between them (§6.3). Either is a one-string change.
- **O3 — Rename the slug elsewhere? (Owner.)** The in-app header (`AppShell.tsx`'s `APP_NAME`), the `Misconfigured` screen and the boot error message still print `strength-in-numbers`. After this spec the landing and the browser tab say "Strength in Numbers" and the header inside the app does not. *Recommendation:* change `APP_NAME` and the `Misconfigured` copy in this PR (two strings and their tests); keep export filenames and the boot console message as the slug.
- **O4 — Prevent the double-tap login? (Owner; reopens D9.)** Two very fast taps start two logins, and the second can make the first fail on the "Couldn't sign you in" screen. Passing `busy` to the `Button` after the first tap greys it out and prevents that. *Recommendation:* do it; the behavior stays "one tap, one login". One line plus a test.
- **O5 — Fewer stylesheet-scan criteria? (Owner.)** Several criteria (AC16, AC17, AC19, AC20) are enforced by tests that scan `Landing.module.css` for banned properties. They pin today's design, so a later visual tweak means editing tests too. *Recommendation:* keep the token, color-role and safe-area scans (they guard system rules), and verify the rest by the harness captures and review.
