## 1. Purpose, scope & non-goals

Carol's gym programs sections by the clock: "5 rounds, one every 5:00", "AMRAP 12", "Time cap 15:00". Today she keeps the gym's clock, writes the times down elsewhere, and the app has nowhere to put them: a section is a name and a note. This spec adds the **data and the API**: a section (in a routine and in a workout) can have one of three **timer formats**, **Set Timer**, **AMRAP** and **Time Cap**, with the format's plan numbers; a workout's timed section stores its **result** (round times, rounds + reps, a finish time, a capped flag) as numbers; History gets a one-line score per timed section; and the Hevy export, the "changed since sent" fingerprint and the Hevy import learn the new data. Spec 10.7 is the UI.

> **First-principles note: why every write names its target ("set round 3's time", never "add a round").** The web app queues round times and results offline, like sets (Spec 06.2): saved on the phone, sent later, **possibly sent twice** (a reply is lost, the app retries). A write that means "append" turns a replay into a second round. A write that means "round 3 is 3:41" can be applied twice, or late, with the same outcome. HTTP calls this *idempotent*: doing it again changes nothing. So round times are addressed by round number (`PUT …/round-times/3`), and the result is a whole-value `PUT`. A set gets the same protection from `clientGeneratedId`; here the natural key (section, round) does the job and no client id is needed.

> **First-principles note: two kinds of "round time".** The clock the lifter reads is different per format. In a **Set Timer** ("every 5:00") the clock restarts each round, so a round's number is *how long that round took* (3:41). In an **AMRAP** or a **Time Cap** the clock runs once from zero, so a round's number is *the clock's reading when the round ended* (4:10, 8:35, 12:50). The second kind only goes up and cannot pass the limit or cap; the first cannot pass the round length. Both are stored as plain seconds in the same column; the format says which kind they are, and the validators differ (§6.3).

### In scope

- Migration `0018_timed_sections`: plan columns on `routine_section` and `workout_section`; result columns on `workout_section`; a child table `workout_section_round` (one row per recorded round); CHECKs.
- `@sin/core`: `dto/section-timer.ts` (schemas, limits), `timer.ts` (pure: `formatClock`, `describeTimer`, `sectionScore`, `scoreText`, `roundTimeIssues`, `resultIssues`, `timerFitsRecorded`), DTO changes on `RoutineSection`, `WorkoutSection`, `WorkoutSummary`, the create/update section schemas, the routine section input; the Hevy changes in `hevy/`.
- Routes: the routine `POST`/`PUT` bodies carry `timer`; `POST /v1/workouts/{id}/sections` and `PATCH /v1/workout-sections/{id}` carry `timer`; four new routes, `PUT`/`DELETE /v1/workout-sections/{id}/round-times/{round}` and `PUT`/`DELETE /v1/workout-sections/{id}/result`.
- Reads: routine reads, workout detail / active, the History list row, the account export.
- The start copy carries the plan onto the workout's section.
- Hevy: `buildHevyWorkout`, `hevyFingerprintSource`, the import of a placeholder's duration.

### Non-goals

- **UI** (Spec 10.7): screens, the "Log result" control, the offline outbox op itself, the routine-from-text reader's rules for turning gym-app text into a timer, any grouping logic that makes a timed section's exercises a superset in the editor. **No client reads or writes the new surface until 10.7** (DESIGN §6 rollout convention).
- A live clock that runs the rounds (design §4). Round times are numbers so a clock can feed them later; nothing is built for it.
- Records, progress charts or "compared with last time" for section scores. The PR engine reads `set_entry` only and stays untouched.
- Formats beyond the three; a score typed as free text (anti-goal); a timer that is required (anti-goal).
- Changing how an untimed section looks, behaves, validates, or hashes (AC8, AC29).
- Offline *section* writes: name, note and timer changes stay online-only (Spec 10.6 D3). Only round times and the result are replay-safe by design; whether the web queues them is 10.7's choice.
- A new advisory-lock key, a new rate-limit group, a body-limit change, a scheduler.
- Importing a format from Hevy (design §6): the import only adds a "Time m:ss" line.

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("09.5 AC7 — …")`). Infra / pipeline criteria are verified by CI or review (§10). "Finished" means the preflight read `ended_at IS NOT NULL`. Seconds are whole numbers throughout.

### Phase A: the data

**Shapes and pure code**

1. **Contract.** `RoutineSection` gains `timer: SectionTimer | null` as its **last** key. `WorkoutSection` gains, after `addedInWorkout`, in this order, `timer: SectionTimer | null`, `result: SectionResult | null`, `roundTimes: { round: number; seconds: number }[]`. All are **required** in `@sin/core` (no `.default`, `.optional()`, `.catch`; Spec 10.1 D4); `roundTimes` is never null. `WorkoutSchema` (hence `POST /v1/workouts`, the finish response, every `WorkoutSummary` base key), `WorkoutExercise`, `RoutineItem` are unchanged: key-set pins. `CreateWorkoutSectionSchema` and `UpdateWorkoutSectionSchema` gain `timer` (`SectionTimer | null`, optional); `UpdateWorkoutSectionSchema` also gains `discardResult` (`true`, optional); both stay strict. `/openapi.json` is regenerated (CI drift step green).
2. **Timer schema.** `SectionTimerSchema` is a discriminated union on `format`: `{ format: "set_timer", roundSeconds: 1–3600, rounds: 1–100 }`, `{ format: "amrap", capSeconds: 1–10800 }`, `{ format: "time_cap", capSeconds: 1–10800 | null }`; each variant is strict (a key of another variant is `422` on that key, e.g. `timer.rounds` on an AMRAP), every number is a whole number, `time_cap.capSeconds` is required-nullable on the response and optional-or-null on a request (absent = `null`, "For Time" with no cap). A missing `format`, an unknown format, `0`, a fraction, a string number and a value over its limit are each `422` on `timer.<field>`; all issues of a body are collected; messages are static (§7).
3. **Pure helpers** in `@sin/core` `timer.ts` (no I/O; `core:purity` green), unit-tested exhaustively and the **only** implementations (a source scan finds no second copy in `apps/`): `formatClock(seconds)` (`m:ss`; `h:mm:ss` from 3600; `0:05`), `describeTimer(timer)` (`Set Timer 5 × 5:00`, `AMRAP 12:00`, `Time Cap 15:00`, `For Time` for a time cap with no cap), `sectionScore(section)` (§6.5), `scoreText(score)` (§6.5), `roundTimeIssues(timer, existing, round, seconds)`, `resultIssues(timer, result)` and `timerFitsRecorded(timer, roundTimes, result)` (the rule tables of §6.3 / §6.4 / §6.6), each returning `TimerIssue[]` = `{ path, code, message }[]` (empty = valid / the plan still contains what is recorded). `code` is one of the fixed list `TIMER_ISSUE_CODES` (§6.9, exported as a `const` tuple) and `message` is the static text `TIMER_ISSUE_MESSAGES[code]`; a test asserts every code has a message and is produced by at least one rule row. Codes are in-process only: the `422` body keeps its existing `{ path, message }` shape (no `code` key). Server and screen use these, so they cannot disagree, and a screen keys its own wording on `code`, never on message text.

**Migration**

4. **Migration `0018`.** Additive and expand-only; applies cleanly over `0001–0017` with existing rows untouched (every existing section reads `timer: null`, `result: null`, `roundTimes: []`). The database itself rejects (raw SQL) on `routine_section` and `workout_section`: a `timer_format` outside the three, a format with a missing or foreign plan column (`rounds` on an AMRAP, a cap on a Set Timer, a `time_cap` cap of `0`), any plan number outside its range, plan columns with no format; on `workout_section`: result columns on a section whose format cannot hold them, an AMRAP result missing `rounds` or `reps`, a Time Cap result with both a finish time and `capped`, `capped` without a cap, a finish time above the cap, a capped result with neither `rounds` nor `reps`, any result number out of range; on `workout_section_round`: a `round_no` outside 1–100, `seconds` outside 1–10800, a duplicate `(section, round_no)`. Deleting a `workout_section` or its `workout` cascades its round rows.
5. **No-drift check moves.** `prisma migrate diff` (migrated database → `schema.prisma`) reports no difference beyond the two generated `set_entry` columns, asserted in `0018`'s integration test (`timed-sections-migration`); `hevy-claim-fingerprint-migration.integration.test.ts` keeps its `0017` checks but no longer carries the whole-schema diff (CLAUDE.md "Advisory-lock keys").

**Routine side**

6. **Routine writes.** `POST` / `PUT /v1/routines` accept `sections.<j>.timer` (a `SectionTimer` or `null`/absent for untimed). It is stored on the section, echoed exactly (the round trip is byte-stable except ids, Spec 09 AC13), replaced by a `PUT` with the rest of the document, and removed by a `PUT` that omits it. A `422` carries `sections.<j>.timer.<field>`. The legal maximum document of Spec 09.2 AC12 with eight timers is accepted under the existing 128 KiB `bodyLimit`.
7. **Routine reads.** Every routine read (list, get-one, `POST` / `PUT` responses) returns each section's `timer` from the **same single statement** as the header and items (Spec 09.2 AC2). The strong `ETag` changes when a timer changes and not otherwise; the first conditional `GET` after the deploy answers `200` (the bytes gained `timer`), not `304`.
8. **Untimed behavior is unchanged.** For a document with no timers everything in Spec 09 / 09.1 / 09.2 behaves byte-for-byte as before apart from `timer: null` on sections: the existing suites pass unmodified apart from additive assertions, and a recorded set of 10.3-editor bodies (no `timer`) replays with the same status codes and stored rows.

**Start copy and workout reads**

9. **The start copies the plan.** `POST /v1/workouts { routineId }` copies each section's timer plan onto its `workout_section` (same `INSERT … SELECT`, same `FOR SHARE`, Spec 09.2 §6.4); `result` is empty and `roundTimes` is `[]`. A replay never re-reads the routine; after the start, editing or deleting the routine changes nothing in the workout's timers, and a workout timer write never reaches a routine (Spec 09.2 AC15, 09.4 AC22 extended).
10. **Workout reads carry the data.** `GET /v1/workouts/{id}` and `GET /v1/workouts/active` return `timer`, `result` and `roundTimes` (ordered by `round`) on every section, from the same single statement as the section list (`workoutSectionsJson`), so a read can never show sections of one moment and round times of another. A manual workout, a copied untimed section and every section that existed before `0018` read `null` / `null` / `[]`. `result` is `null` whenever all four result columns are empty (`{ rounds: null, reps: null, finishSeconds: null, capped: false }` is never returned).
11. **Account export and purge.** The export carries `timer`, `result` and `roundTimes` through the shared `workoutSectionsJson` + `toWorkoutSectionRecord` + `toWorkoutSectionDto` and the routine side through `ROUTINE_WITH_ITEMS`, with no export-specific statement; Spec 11's parity AC (export deep-equals the read routes) passes with a timed routine section and a timed workout section holding round times and a result in the fixture; the export still issues **≤ 8** statements; the purge discovery test finds `workout_section_round`, its fixture has victim rows in it, and no allowlist entry is needed (the foreign key cascades). `formatVersion` stays `1`.

### Phase B: the workout writes

**Section routes**

12. **Create with a timer.** `POST /v1/workouts/{id}/sections` accepts `timer`; the `201` section carries it, with `result: null` and `roundTimes: []`. Without `timer` it is exactly Spec 09.4 AC3.
13. **Change the timer.** `PATCH /v1/workout-sections/{id}` with `timer` (a `SectionTimer`, or `null` to remove) behaves by this table, in one transaction under the section row lock, and changes `updated_at` only when something changed:
    - equal to the stored timer: `200`, nothing written;
    - **nothing recorded** (no round time, no result): the timer is replaced, whatever the change;
    - **something recorded and the change keeps it** (same format and `timerFitsRecorded` returns no issue): the timer is replaced and the recorded data is kept; `discardResult` is ignored;
    - **something recorded and the change would not keep it** (a different format, `null`, or the same format with numbers that no longer contain what is recorded, such as fewer rounds than recorded or a cap below a reading): `409 section-result-exists` and nothing changes, **unless** the body carries `discardResult: true`, in which case the timer is replaced and the round rows and result columns are cleared in the same transaction.
    Both "would not keep it" cases therefore share one confirm-then-discard flow. `discardResult` without `timer` is `422` on `discardResult`. A body without `timer` leaves the timer and the recorded data untouched (name / note edits never clear anything).
14. **Round time, set.** `PUT /v1/workout-sections/{id}/round-times/{round}` with `{ seconds }` (strict) sets that round's number and answers `200` with the whole `WorkoutSection`. Path `round` is a whole number 1–100 (else `422` on `round`); `seconds` is a whole number ≥ 1. By format (rule tables in §6.3): **Set Timer:** `round ≤ rounds` and `seconds ≤ roundSeconds`; **AMRAP / Time Cap:** `seconds ≤ capSeconds` when there is a cap (else ≤ 10 800) and strictly later than the nearest lower round already recorded and strictly earlier than the nearest higher one. A violation is `422` on `seconds` (or `round`) with a static message. A section with no timer is `409 section-timer-mismatch`. Rounds may be recorded in any order and with gaps.
15. **Round time, clear.** `DELETE …/round-times/{round}` answers `204` whether or not that round was recorded (idempotent) and never fails a validity rule; a missing / foreign section is `404`; a section with no timer is `204` too (nothing to clear).
16. **Result, set.** `PUT /v1/workout-sections/{id}/result` with `{ rounds?, reps?, finishSeconds?, capped? }` (strict; absent = `null` / `false`) replaces the whole result and answers `200` with the `WorkoutSection`. By format (§6.4): **AMRAP:** `rounds` (0–999) and `reps` (0–9999) both required, `finishSeconds` and `capped` forbidden. **Time Cap:** either `finishSeconds` (1 up to the cap when there is one; 10 800 otherwise) alone, with `rounds`, `reps` and `capped` empty, or `capped: true` with a cap on the timer, `finishSeconds` empty and at least one of `rounds` / `reps`; `capped: true` on a time cap with no cap is `422` on `capped`. **Set Timer** and an untimed section: `409 section-timer-mismatch` (their score is derived from the round times). A body that breaks a field rule is `422` on the offending path, all issues collected.
17. **Result, clear.** `DELETE …/result` answers `204`, idempotent, `404` for a missing / foreign section; it clears the four result columns and leaves the round times.
18. **Replay safety.** Applying any request of AC14–AC17 twice in a row gives the same stored state and the same response as applying it once; the second application writes **nothing** (`updated_at` of the section and the round row unchanged, no `workout_edited` line, `changed: false` in the section line). A recorded sequence of valid operations over one section (sets and clears of several rounds and the result, with the same sequence replayed twice and with the *distinct-round* operations permuted) ends in the same state as the sequence applied once in order. (A reordered pair that targets the same round is last-write-wins, as for sets; the outbox keeps its own order, §11.)
19. **Authorization.** For all five new / changed section routes, a missing, malformed, foreign (another user's) workout or section is `404 not-found`, never `403`; two users, same ids.
20. **Finished workouts.** All of AC12–AC17 work on a finished workout: no `409 workout-finished`, no `409 workout-would-be-empty`. They recompute **no** records: the finished-mode statement log shows the per-user PR lock first (`lockUserRecords`) and no `personal_record` statement; `workout_edited` carries `records_recomputed: false` and the new `edit` kinds `section_timer_changed` (AC12–AC13) or `section_result_changed` (AC14–AC17). The workout's `ended_at`, `started_at`, `local_date`, sets, History order (and every History row key except `timedSections`, whose score is meant to change) and `GET /v1/personal-records` are byte-identical before and after.
21. **Live workouts and finish races.** On a live workout the same routes run exactly their own statements (no PR lock). A finish that commits between the preflight and the row lock restarts the write once in finished mode (`assertStillLive`, Spec 07.4 §6.1); a test races each write against a finish and asserts a legal outcome and no `40P01`.
22. **Concurrency.** Racing (a) two round-time writes on one section (the strictly-increasing rule holds afterwards, whichever wins), (b) a round-time write against a timer change, (c) a round-time write against the section's removal, (d) a result write against a timer change, (e) a round-time write against a set write on the section's exercises, (f) any of them against a finish or a discard, never raises `40P01`, never stores a state `assertSectionsConsistent` rejects, and never returns `500`.
23. **Cascades.** Removing a section (Spec 09.4 AC7) and deleting a workout delete the round rows with them; removing a section's *exercises* touches neither the timer nor the result.
24. **No server-side superset coupling.** Giving a section a timer, removing it, and moving or adding exercises into a timed section change nothing in any exercise's `superset_group` beyond what Spec 09.4 AC13 / AC16 already do (a test pins the group of every exercise before and after). Whether a timed section's exercises are kept in one superset is the client's job (§12 D7).

**History**

25. **History row score.** Each item of `GET /v1/workouts` gains `timedSections: { id, position, name, timer, score }[]` as its **last** key: the workout's sections that have a timer, in position order (`[]` when none; never an untimed section), with `score` = `sectionScore(section)` computed by the `@sin/core` function from the same rows (`SectionScore | null`). It is built in the existing page statement of the History list (one more scalar subquery; the list stays two statements, page plus volume, with no new round trip). `recordCount`, `totalVolume` and every other key are unchanged; the key-set pin of a History row is updated to this one addition; `WorkoutSchema`, the finish response and the detail are unchanged by it. The History latency benchmark (`bench:history`, Spec 07.1 AC20) stays within its bound with a fixture where every row has two timed sections of 20 round times.

### Phase C: Hevy

26. **A timed section is sent as the workout placeholder.** `buildHevyWorkout` sends every section with a `timer` as the `workout_placeholder` marker, whatever its name and whatever the section rules say (a timed "Warm-up" is a workout placeholder; a timed "Accessory" is too, its note no longer going on the first exercise). The marker is `{ exercise_template_id: <workout placeholder>, superset_id: null, notes, sets }` placed where the section's first exercise run starts (the existing rule, including non-contiguous runs). `notes` is the section name, a newline, the **timer line** (AC28), and, when the section has a note, a newline and the note. `sets` is one set `{ type: "normal", duration_seconds: D }` when `D` is known and `[]` otherwise, with `D` from the table of §6.7. An untimed section's marker or notes are byte-identical to today's (golden fixtures from the current implementation).
27. **No placeholder pair.** When the account has no workout-placeholder pair, a timed section's name, timer line and note go on its first exercise's notes (`name`, newline, line, newline, note, a blank line, the exercise notes), the `section_no_placeholder` notice is counted once per section as today, and no duration is sent for it.
28. **The timer line.** One pure function builds it from `describeTimer` and `scoreText` (§6.7): segments joined by ` · `: the timer description; the recorded round times in round order (`3:41, 3:38, 3:30`; omitted when none); the score text (omitted when none). Example: `Set Timer 5 × 5:00 · 3:41, 3:38, 3:30, 3:25, 3:28 · total 17:42`. A timer with nothing recorded is its description alone.
29. **The fingerprint.** `hevyFingerprintSource` includes, for a section **with a timer only**, the timer plan, the result and the round times after the existing `[name, notes, position]` entries; a section without a timer contributes exactly what it does today. Hence: (a) for a workout with no timed section the source string is **identical** to today's (a golden string per fixture, computed from the pre-change function), so no already-sent workout changes state; (b) the version tag stays `v1`; (c) changing any plan number, round time, result field or the capped flag of a timed section changes the source (a test mutates each in turn); (d) a stored fingerprint of a workout sent before `0018` still compares equal to a recomputed one for that unchanged workout, so it reads `sent`, not `changed`.
30. **Import.** `translateHevyWorkout`, for a placeholder (either role) whose sets carry `duration_seconds`, adds the line `Time m:ss` (`formatClock` of the **sum** of the placeholder's positive durations) as the **first line** of the section's note (then a newline and the rest of the note, if any); the cuts of Spec 19.0 AC10 apply to the whole note, so the line is never the part that is cut. A placeholder with no duration imports exactly as today, the notice list is unchanged (`placeholder_sets_ignored` still counts the placeholder's sets), and no `timer` is ever created by the import.

### Cross-cutting

31. **Route wiring.** The new and changed routes declare `config: { published: true, problems: […], writeGroup }`: the round-time and result routes `writeGroup: "sets"` (they are the high-rate writes the outbox replays), the section create / patch `"workouts"` as today. `RATE_LIMITS` is unchanged. Real CORS preflights are added for `PUT` and `DELETE` on `/v1/workout-sections/{id}/round-times/{round}` and `/v1/workout-sections/{id}/result` (an `inject` test never exercises the preflight, CLAUDE.md); `CORS_METHODS` already lists both. The two new `409` slugs, `section-timer-mismatch` and `section-result-exists`, render as RFC 9457 on the root and the `/v1` scope and are added to the problem-matrix test.
32. **Static messages.** Every `message:` in the new schemas and helpers is fixed text or a module constant, including the discriminator's (`static-issue-messages.test.ts` probes the exported schemas and scans `src/`); a `422` body never contains a submitted value.
33. **Logging hygiene.** New lines `workout_section_timer_set { workout_id, section_id, user_id, format, cleared }`, `workout_section_round_set { …, round, changed }`, `workout_section_round_cleared { …, round, removed }`, `workout_section_result_set { …, changed }`, `workout_section_result_cleared { …, removed }` and the field additions of §9 carry ids, enum values, counts and booleans only: no section name or note, no seconds, no reps in any captured line (distinctive values sent, none found). `telemetry/allowlist.ts`, `views.ts` and `METRIC_NAMES` are unchanged (a test pins the allowlist).
34. **Consistency helper.** `assertSectionsConsistent(db)` (Spec 09.2 AC29, extended by 09.4 AC23) also checks, on every workout section: a round row exists only for a timed section; Set Timer rows have `round_no ≤ rounds` and `seconds ≤ round_s`; AMRAP / Time Cap rows are strictly increasing in `round_no` and `≤ cap`; the result columns fit the format. It runs after each integration test of this spec.
35. **Docs and release order.** DESIGN.md, `docs/specs/README.md`, CLAUDE.md (`apps/api`, `packages/core`), the amended specs and the runbook carry the edits of §11; the release order (migration `0018` before the code; API before Spec 10.7) is stated in each PR description and a runbook "0018" note.

### What Spec 10.7 will need from this spec (so nothing is rediscovered there)

- **Outbox op.** One new op kind keyed `(workoutId, sectionId, round)` for round times and `(workoutId, sectionId)` for the result, carrying a *final value* (set or clear), coalesced last-write-wins per key, sent FIFO with the other ops (Spec 06.2). The replay guarantee of AC18 is what makes "send again" safe.
- **Rules in the browser.** The same `roundTimeIssues` / `resultIssues` / `timerFitsRecorded`, `describeTimer`, `sectionScore`, `scoreText`, `formatClock`, so the field errors match the server's.

- **Issue codes.** The helpers return `code` (§6.9); the screen keys its wording on it.

Notes:

- **Why columns for the plan and result, and a child table for round times.** The plan and the result are one fixed handful of numbers per section, so they are columns the CHECKs can police row by row. Round times are a variable-length list that is written *one entry at a time and replayed*. A child table makes "set round 3" an `INSERT … ON CONFLICT (workout_section_id, round_no) DO UPDATE` and "clear round 3" a `DELETE`: the primary key is the idempotency key, gaps are natural (a skipped round), and nothing rewrites a whole list. An array column (`integer[]`) would need a read-modify-write of the list per entry (racy without the row lock, and ugly with gaps) and could not carry a per-entry CHECK. A JSON blob would give up the CHECKs and the "numbers, not text" requirement (design §4).
- **Why the cross-table rules are the handler's job.** "Strictly increasing", "≤ the cap" and "≤ the round length" compare a round row with its section's plan, which a CHECK cannot see (no cross-table CHECK in PostgreSQL). The handler enforces them under the section row lock (§6.2); `assertSectionsConsistent` is the test-side guard (AC34). The same-row rules (result vs. cap, plan shape) are CHECKs.
- **Limits.** Round length ≤ 1 h, rounds ≤ 100, cap ≤ 3 h, readings ≤ 3 h, AMRAP rounds ≤ 999, reps ≤ 9 999. They are generous for a gym session and keep every number in `SMALLINT` / `INTEGER`. A change is a forward migration (a CHECK widening is additive) plus the `@sin/core` constants.
- **Lock profile.** Constant-less nullable `ADD COLUMN`s and one `NOT NULL DEFAULT false` (metadata-only on PostgreSQL 11+), two CHECK additions over small tables (validated by a scan holding a lock for milliseconds), one `CREATE TABLE`. No rewrite.
- **Purge.** `workout_section_round` cascades from `workout_section` ← `workout` ← `user`; no purge-ordering step.
- **Start copy.** The Spec 09.2 `INSERT … SELECT` names the four `timer_*` columns; the result columns and `result_capped` take their defaults (nothing recorded).

## 6. Behavior & logic

### 6.1 Envelope and lock order

Every write resolves ownership with the cheap unlocked preflight of Spec 09.4 §6.1 (`… JOIN workout w ON … WHERE w.user_id = $acting`, returning `w.ended_at`) and runs in `withWriteMode`.

- **Section create / `PATCH`:** exactly 09.4's envelope (`lockWorkoutStructure`: deferred constraint, the per-workout advisory lock, workout `FOR SHARE`, `assertStillLive`), then the section row `FOR UPDATE`.
- **Round-time and result writes** change no position or membership, so they **skip the structure advisory lock** (D19): `[finished: PR lock] → workout row FOR SHARE (assertStillLive) → section row FOR UPDATE → round rows`. The section row lock serializes round writes, result writes and timer changes on one section, which is what the cross-row rules need. This is deadlock-free against 09.4's order: a section remove takes structure lock → workout `FOR SHARE` → section `FOR UPDATE`, the same relative order; a section *move* locks an exercise row, then the section row `FOR SHARE`, and a round write never requests an exercise row; set writes lock exercise rows and workout `FOR SHARE` only; a finish waits on `FOR SHARE` holders and takes nothing a section write waits for. A section removed while a write waits on its row lock ends as `404` when the lock is granted and the row is gone.
- A vanished workout or section under the lock is `404`.

### 6.2 Round-time write

`PUT …/round-times/{round}`: under the section row lock, read the section's timer and its round rows (`SELECT round_no, seconds … ORDER BY round_no`, at most 100). No timer → `section-timer-mismatch`. Run `roundTimeIssues(timer, existing, round, seconds)` (§6.3); any issue → `422`. If a row for `round` exists with the same `seconds`: return the section, **write nothing**. Else `INSERT … ON CONFLICT (workout_section_id, round_no) DO UPDATE SET seconds = EXCLUDED.seconds, updated_at = now()`. The response is the whole `WorkoutSection` read inside the same transaction (`workoutSectionsJson` filtered to the section, same row builder as the reads). `DELETE` is `DELETE FROM workout_section_round WHERE … AND round_no = $r` and reports whether a row went (for the log).

### 6.3 Round-time rules (`roundTimeIssues`)

| Format | `round` | `seconds` | Paths |
|---|---|---|---|
| Set Timer | `≤ rounds` ("beyond the planned rounds") | `≤ roundSeconds` ("longer than the round") | `round`, `seconds` |
| AMRAP, Time Cap | any 1–100 | `≤ capSeconds` when there is a cap; **strictly later** than the nearest *lower* recorded round ("not later than the previous round"); **strictly earlier** than the nearest *higher* one ("not earlier than the next round") | `seconds` |

The rule compares with the neighbors in `existing` *excluding* the round being written, so re-saving a round with its own value, or changing it within its neighbors, passes. Because each write is validated against the current neighbors, a round can arrive before its predecessors (offline replay in any order) and still be accepted when it fits what is there; the later predecessors are then checked against it. The Set Timer sum is the score; fewer rounds than planned is legal (the lifter stopped early).

### 6.4 Result write (`resultIssues`)

`PUT …/result` runs `resultIssues(timer, body)` after the field schema: **AMRAP** needs `rounds` and `reps` (`422` on the missing one: "required") and refuses `finishSeconds` / `capped`; **Time Cap** either `finishSeconds` alone (≤ cap when there is one) or `capped: true` with a cap (`422` on `capped`: "needs a cap"), no `finishSeconds`, and at least one of `rounds` / `reps` ("give rounds or reps"); a body that is all empty is `422` on `rounds` ("nothing to record" — clearing is `DELETE`). A Set Timer or untimed section is `section-timer-mismatch` before any of this. The write is one `UPDATE workout_section SET result_… WHERE id AND (result columns IS DISTINCT FROM the new ones)`; zero rows updated with the section present is a no-op replay. Readings already recorded are **not** compared with the finish time or the capped result (D10).

### 6.5 The score (`sectionScore`) and its text

- Set Timer: `total_time` over the recorded round times (`seconds` = their sum, `rounds` = how many), `null` when none are recorded.
- AMRAP: `rounds_reps` from `result`, `null` without a result. (Round times are extra detail and never change the score.)
- Time Cap: `finish_time` from `result.finishSeconds`; `capped` from a capped result (`rounds` / `reps` as recorded, either may be `null`); `null` without a result.

`scoreText`: `total 17:42` · `5 rounds + 7 reps` (singular `1 round`, `1 rep`) · `finish 14:20` · `Capped · 4 rounds + 7 reps` (`Capped · 7 reps` when `rounds` is `null`; `Capped · 4 rounds` when `reps` is `null`). History shows `describeTimer(timer)` + ` · ` + `scoreText(score)` ("Set Timer 5 × 5:00 · total 17:42"); the Hevy line (§6.7) uses the same functions.

### 6.6 Timer change over recorded data

`PATCH` with `timer` locks the section row, reads the recorded round times and result, and decides per AC13. For a same-format change `timerFitsRecorded(newTimer, roundTimes, result)` returns no issue when: Set Timer: every recorded round is `≤ rounds` and every time `≤ roundSeconds`, and there is no result (a result cannot exist); AMRAP / Time Cap: every reading is `≤ capSeconds` (when present), a finish time is `≤ capSeconds`, a capped result still has a cap, and the result's shape belongs to the new format (a same-format change keeps the shape). A same-format change that fits keeps the data and ignores `discardResult`; otherwise (different format, `null`, or issues returned) the request is `409 section-result-exists` unless `discardResult: true`, which runs `DELETE FROM workout_section_round WHERE workout_section_id = $s` and clears the result columns in the same transaction as the `UPDATE` of the timer columns (one statement order that never violates the CHECKs: clear the result, then set the timer).

### 6.7 Hevy (Phase C)

**Duration `D` of the marker's single set** (seconds; `null` = no set sent):

| Timer | `D` |
|---|---|
| Set Timer | the total of the recorded round times; `null` when none |
| AMRAP | `capSeconds`, the AMRAP's total time (Carol, design §2) |
| Time Cap, finished | the finish time |
| Time Cap, capped | `capSeconds` (O1) |
| Time Cap, no result | `null` |

**The timer line:** `describeTimer` · the recorded round times (`formatClock` each, in round order, comma separated; for an AMRAP / Time Cap these are the clock's readings) · `scoreText`. A gap in the recorded rounds is not marked (the list shows what was entered). The line is built once, in `hevy/` next to `buildHevyWorkout`, from the DTO.

**`buildHevyWorkout`:** in the section walk, `treatment = section.timer ? "workout_placeholder" : sectionTreatment(name, rules)`. The marker's `notes` for a timed section is `name\nline` plus `\nnote` when the section has one (`nameAndNote` generalized); `sets` is `[{ type: "normal", duration_seconds: D }]` or `[]`. The rest of the walk (run starts, markerless fallback, `markerlessIds`) is unchanged, so a timed section whose workout has no placeholder pair falls back like any section (AC27). **An empty timed section (no exercises) emits nothing**, like every empty section (D16).

**Fingerprint:** the section entry stays `[name, notes, position]` for an untimed section and becomes `[name, notes, position, [format, roundSeconds, rounds, capSeconds], result ? [rounds, reps, finishSeconds, capped] : null, [[round, seconds], …]]` for a timed one (absent plan numbers `null`, round times sorted by round). The version tag stays `v1`. Nothing in the untimed branch may change the order, the arity or `JSON.stringify`'s output (AC29 is a golden test); the workout-level, exercise and set parts are untouched.

**Import:** `SectionWalk.placeholder(role, rawNotes, durationSeconds)` receives the sum of the placeholder's sets' positive `durationSeconds` (`0` / `null` = none) and `placeholderSection` passes `Time ${formatClock(d)}` to `sectionFromPlaceholder` as a separate lead line that becomes the first line of the section's note **after** the section name has been taken from the placeholder's notes (a workout placeholder's first notes line is the section name, so prepending to the raw notes would name the section "Time 17:42"); the cut code (`SECTION_NOTES_MAX`) trims the tail, never the line. Positive durations are summed and rounded to whole seconds; a sum that rounds to 0 adds no line. Only the first run's marker of a non-contiguous timed section carries the duration set on export (later runs' markers have `sets: []`). (Corrected while planning Phase C, 2026-11-01.) A Hevy workout round-tripped from SIN therefore lands with the exported timer line in the note and a `Time` line above it: accepted, the import is a one-time tool and guessing a format back is out (design §6).

### 6.8 Edge cases

- **Untimed section**: all `PUT`s on it are `409 section-timer-mismatch`; all `DELETE`s `204`.
- **A timed section with no exercises** is legal everywhere; it never blocks a finish; it can hold a result (the Hevy export does not send it, D16).
- **A copied section keeps its plan when renamed**; the plan is data, not name; clearing it is `PATCH { timer: null }`.
- **Time Cap whose cap is later added or removed** is a same-format change: it keeps the data iff `timerFitsRecorded` returns no issue (removing a cap from a capped result does not fit: `409 section-result-exists`, or discard with `discardResult: true`).
- **Set Timer rounds reduced below recorded rounds** does not fit: `409 section-result-exists`, or discard with `discardResult: true` (clears all recorded round times and the result of that section).
- **Clock:** `updated_at` uses the database `now()`.
- **Records:** none of this reads or writes `set_entry` or `personal_record`; the finish integrity rule, records, progress and volume are indifferent (as Spec 09.2 AC19).

### 6.9 Issue codes (`TIMER_ISSUE_CODES`)

## 7. Security & privacy

- **Authorization is inherited.** Every statement resolves the section through its workout's `user_id = $acting`; a foreign id is `404`. The round number and the section id are the only identifiers a client supplies, and the only ids written are the section's own; no body field names another row.
- **Mass assignment.** All request schemas are strict; ids, `position`, `addedInWorkout`, `roundTimes` and `score` are never accepted on a section body; the result and round times have their own routes.
- **Input as numbers.** Every new field is a bounded whole number or an enum; there is no new free text. Validation messages are static (#57): the discriminator and cross-field refinements use constants (`static-issue-messages.test.ts` probes them), so a `422` never echoes a value.
- **Logging.** Ids, enum values, booleans and counts only (AC33); no seconds, reps, names or notes. The `err` serializer already masks request-validation errors.
- **Abuse bounds.** ≤ 100 round rows per section, ≤ 8 sections per workout, so ≤ 800 rows per workout; the `sets` write group (120/min) and the in-flight cap bound a loop; the History subquery reads at most 8 sections per row.
- **PII.** Workout durations and scores are health-adjacent training data, already the nature of the app; they are in the export and removed by the purge (AC11). No new third party: Hevy receives the score only through the owner-only export that already exists, with the private flag set.

### Resolved: owner decisions (design §2, Carol 2026-11-01), restated

- ✅ **D1 — Three formats and only these; timers optional (owner).** Set Timer (round length and rounds are the plan, a working time per round, the score is the total), AMRAP (a time limit; the score is rounds + reps as two numbers; round times optional), Time Cap (a cap; the score is the finish time, or how far she got if capped; intermediate round times optional). - ✅ **D2 — Exercises keep logging their own sets; the section result never replaces them (owner).** Records, volume and progress read `set_entry` only. **Rationale:** the anti-goal in the design: the section score must not compete with the sets.
- ✅ **D3 — Round times are numbers; AMRAP / Time Cap readings are the gym clock when the round ends, Set Timer times are per-round durations (owner).** So they can be compared and summed, and a later live clock can feed them. **Rejected:** free text.
- ✅ **D4 — The same writes work offline (owner), so they must be replay-safe.** The API half is AC14–AC18; the outbox half is Spec 10.7.
- ✅ **D5 — Routines carry the format; the start copies it; the reader fills it in (owner).** The reader's rules are 10.7's / 10.4's (non-goal).
- ✅ **D6 — Hevy: a timed section is the "Workout" placeholder with a duration; Set Timer → total working time, Time Cap → finish time, AMRAP → its time limit (owner).** Calls the design's §6 made and Carol accepted: the placeholder is used whatever the section is named; a missing placeholder pair uses the existing fallback; import adds a "Time" line and never rebuilds a format; a format change clears the result after a confirm; capped Time Cap = rounds + reps with a flag; Set Timer may have fewer rounds than planned; "For Time" is a Time Cap with no cap.

### Resolved: this spec's calls (mine)

- ✅ **D7 (mine) — The superset coupling lives in the UI, not the API.** The server stores workout-side supersets as sent (Spec 09.2 §6.5, 09.4 D7) and a routine's as the editor sends them (the PUT round trip is byte-stable, 09.2 AC4); a timer on a section is a different fact from "these exercises are grouped". **Rationale:** if the server grouped a timed section's exercises it would (a) change the stored document in a routine `PUT` the client did not send, breaking the echo contract; (b) fight 09.4's rule that a section move drops the exercise from its superset; (c) need its own answer to "what if the section has two groups, or a group of one", all of which the regroup rules (`planSessionChange`, `settle`, extended by 10.7's `groupRange`) answer on the client, and a timed section may legitimately hold more than one superset (design §2), so only a client that sees the section's current groups can decide whether to fill grouping in; (d) not help the offline path at all. The cost: a second client could leave a timed section ungrouped. The data stays valid either way (the superset is display and Hevy `superset_id`, the score does not depend on it), so no integrity is at stake. Spec 10.7 fills grouping in only where the section has none (on setting a timer, and on add / move into a timed section, §3). AC24 pins that the API does not.
- ✅ **D8 (mine) — `timer` is one nested discriminated object in the DTO, flat columns in the database.** `{ format, roundSeconds, rounds }` / `{ format, capSeconds }` / `{ format, capSeconds | null }`. **Rationale:** one key says "timed or not", a variant cannot carry another variant's number (strict schemas make it a `422`), a `PATCH` replaces the whole plan atomically, and the CHECK in SQL mirrors the union exactly. **Rejected:** four sibling nullable keys (every consumer re-checks which combination is legal) and a `kind` string plus a free `plan` JSON (no CHECKs).
- ✅ **D9 (mine) — Round times are a child table `workout_section_round`, keyed `(section, round_no)`; the result is four columns on the section.** See §4 notes. **Rejected:** `integer[]` (read-modify-write, gaps, no per-entry CHECK), a JSON column.
- ✅ **D10 (mine) — Readings are validated against the plan and each other, not against the finish time or the AMRAP result.** Strictly increasing and within the limit or cap is Carol's rule ("they only go up and stay within the limit or cap"). Coupling readings to the finish time or to `rounds` adds an order-dependence between two independent offline writes (which would have to arrive in a legal order) for a typo the screen can warn about. **Rejected:** coupling them; accepting any numbers (the stated rule would be unenforceable and Set Timer totals could exceed the round length).
- ✅ **D11 (mine) — Absolute-keyed `PUT` / `DELETE` routes, not a field on `PATCH /workout-sections/{id}`.** The `PATCH` stays the online-only edit of name, note and timer; the high-rate, replayable writes get their own routes, their own `sets` write group (they replay beside sets) and their own outbox op. `DELETE` is idempotent (`204` whether or not it existed) so a replayed clear never fails; `PUT` returns the whole section so the client can reconcile. **Rejected:** `POST …/rounds` (append, not replay-safe), a whole-array `PUT` of all round times (a replay of an old array would overwrite a newer entry, and two queued edits would not coalesce per round).
- ✅ **D12 (mine) — Two `409`s and `422`s by cause.** `422` is a value that breaks a rule given the stored timer (the same family as a set that breaks its exercise's modality, Spec 05.1). `409 section-timer-mismatch` is "this section has no timer that takes this write" (a stale screen after another device changed the format; the outbox drops it). `409 section-result-exists` is "this would clear recorded data". **Rationale:** the outbox and the screens act on the difference (retry-never vs refetch vs ask).
- ✅ **D13 (mine; extended by Carol's F2 answer, 2026-11-01) — A timer change that would not keep the recorded data needs `discardResult: true`.** That is a different format, removal, **and a same-format change whose numbers no longer contain the data** (fewer rounds than recorded, a cap below a reading), so the lifter meets one confirm-then-discard flow, not a dead end. Carol's rule is "changing the format clears the result after a confirm". The confirm is the UI's, but a stale second device could otherwise erase a score typed on the first with no confirm at all. The flag makes the server enforce that a confirm happened (Anti-goal: losing a score). **Rejected:** server clears silently; always refuse a change (a lifter must be able to fix a wrong format).
- ✅ **D14 (mine) — Limits:** round length ≤ 3 600 s, rounds ≤ 100, cap ≤ 10 800 s, readings ≤ 10 800 s, AMRAP rounds ≤ 999, reps ≤ 9 999. Generous for a gym session, small for the types. A product limit, changeable with a forward migration and a constant.
- ✅ **D15 (mine) — The score is derived, never stored, and `sectionScore` / `scoreText` in `@sin/core` are the only implementation.** The DTO carries the raw numbers; History rows also carry `score` (computed with the same function on the server so the list needs no round times on the wire); the Hevy line, the summary and History all print through `scoreText`. **Rejected:** a stored `total_seconds` (a second source of truth that every round write must keep in step).
- ✅ **D16 (mine) — History rows carry every timed section (≤ 8), each with `score`; an empty timed section is not sent to Hevy.** How many the row shows ("first plus N more") is the UI's. An empty section emits nothing in the Hevy export today, and a timed one has no run of exercises to anchor its marker to; the score stays in SIN and in the fingerprint. **Rejected:** inventing a placement rule for a marker with no exercises, for a case (an AMRAP with no exercises) that is not what Carol logs.
- ✅ **D17 (mine) — Hevy duration for each format** (§6.7), with the capped Time Cap rule at O1; the notes line shape of the design's example is kept, round times are listed bare in round order with no gap marker.
- ✅ **D18 (mine) — The fingerprint keeps `v1` and the untimed section entry byte-for-byte.** A version bump would make every stored fingerprint read `sent` (spec 19.0 AC26), hiding real changes in every sent workout; adding an element to every section entry would change every hash and mark every sent workout with a section as "changed since sent". Appending data **only for timed sections** changes the string for exactly the workouts that gained a timer, which is the correct "changed" signal.
- ✅ **D19 (mine) — Round and result writes skip the structure advisory lock.** They change no position or section membership; the section row `FOR UPDATE` serializes everything that reads a section's round rows. The lock order is stated in §6.1. **Rejected:** the structure lock for every write (it would serialize unrelated exercise edits behind each queued round time on a replay burst).
- ✅ **D20 (mine) — Placeholder duration on import:** the sum of the placeholder's positive set durations, as the first line of the section note, for both placeholder roles. A warm-up placeholder with a duration is something Carol logs by hand today; dropping its time would lose data silently. No notice is added (`placeholder_sets_ignored` still counts the sets; the duration is kept as text). First line, so a note over the 2 000-character limit loses its tail, never the time.
- ✅ **D21 (mine) — `edit` kinds `section_timer_changed` and `section_result_changed`** extend the finished-edit log (Spec 07.4 §9, 09.4); no records change, `records_recomputed: false`.
- ✅ **D22 (mine) — Three PRs.** A (data and routines) is the only one with a release step; B (writes and History) is the largest; C (Hevy) is pure and independent of B.
