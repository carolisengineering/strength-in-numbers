## 1. Purpose, scope & non-goals

Ship the **PR engine**: the `personal_record` table, the pure `@sin/core` math
that decides what a record is, the write path that keeps the table correct when
a workout is finished or deleted, a rebuild job, and the two reads a client needs
to show a PR (the finish response's `newRecords`, and `GET /v1/personal-records`).

**Roadmap split (D1).** The old row "07 History, progress & PR engine (API)" is
three specs: **07.0 PR engine** (this one), **07.1 history list API**
(`GET /v1/workouts?cursor=`), **07.2 progress series API**
(`GET /v1/progress/exercises/{id}`). 07.1 and 07.2 read `set_entry` directly and
do not depend on `personal_record`; they are split off because each is a
session on its own and 07.0 is the only one that touches the finish transaction.

### In scope

- Table `personal_record`, migration `0008_create_personal_record`, the Prisma
  model.
- `packages/core/src/records.ts` — `estimate1rm`, `computeRecords`, the exact
  integer helpers — plus `RECORD_TYPE_VALUES` / `RECORD_UNIT_VALUES` in
  `enums.ts` and `dto/personal-record.ts`.
- The recompute on **finish** (inside 05.0's finish transaction) and on **delete
  of a finished workout** (inside 05.0's delete transaction), and a
  **`records:rebuild`** release-step script.
- `PATCH /v1/workouts/{id}` returns `newRecords`; new
  `GET /v1/personal-records?exerciseId=&workoutId=`.
- The hand-reconciliation fixture (10 sessions) that seeds M2's exit criterion.

### Non-goals

- **History list** (07.1) and **progress series** (07.2).
- **`body_metric` / total-load PRs.** `weighted_bodyweight` records use the added
  load only (D2); a body-weight-inclusive total waits for a body-metric table.
- **`duration` / `distance_duration` PRs** — no record type for them in v1.
- **`rep_pr_at_weight`** (DESIGN §4.5, already deferred).
- **UI** — the finish-screen PR summary and the records list are Spec 08.
- **A nightly rollup table** (`exercise_daily_stat`, DESIGN §4.6).
- **Rate-limit changes.** `PATCH`/`DELETE /v1/workouts/{id}` stay in 05.2's
  `workouts` group; the new `GET` gets L1 only (05.2 D5).
- **Caching.** The new `GET` is the default `no-store`, no `ETag`.
- **Editing a finished workout's sets.** Still post-v1 (DESIGN §4.5); when it
  ships it calls the same recompute (§6.3).

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number
(`describe("AC7 — …")`), following 05.0 §10 / 05.1 §10.

1. **Migration creates `personal_record` cleanly.** `0008_create_personal_record`
   applies on a fresh database and on top of `0001`–`0007`; creates the table with
   exactly the columns, types and nullability of §4; the four `ON DELETE CASCADE`
   FKs; the `record_type`, `unit`, type↔unit and `value > 0` `CHECK`s; the
   unique index and the two secondary indexes. `prisma validate` passes with the
   `PersonalRecord` model and the four back-references; no drift between the
   migrated database and `schema.prisma` (05.0 AC1's technique).
2. **The `CHECK` vocabularies are drift-guarded against `@sin/core`.** A raw
   insert of an out-of-vocabulary `record_type` / `unit`, or of a mismatched
   pair (`max_reps` with `kg`), is rejected; every legal pair is accepted. A unit
   test asserts the `.sql` **contains** the clauses rendered from
   `RECORD_TYPE_VALUES`, `RECORD_UNIT_VALUES` and `RECORD_UNIT_BY_TYPE`
   (string containment — 03.1 AC2 / 05.1 AC2's technique).
3. **`estimate1rm` is Epley, exact, bounded.** `estimate1rm(w, reps) =
   w × (30 + reps) / 30` over integer thousandths, rounded half-up to 0.001 kg;
   `null` for `reps < 1` or `reps > 12` and for non-integer `reps`. Boundary
   cases 0 / 1 / 12 / 13, and a rounding table including a `.5`-thousandth
   exact-tie and an lb-derived weight (e.g. 135 lb stored as its
   `weight_kg`).
4. **Weights are parsed, never floated.** `parseWeightKgMilli("61.235")` returns
   `61235`; `"60"`, `"60.5"`, `"0.001"`, `"9999.999"` parse exactly; anything not
   matching `^\d+(\.\d{1,3})?$` throws. `milliToDecimalString` is its exact
   inverse. No comparison in `records.ts` uses a `number` that is not an integer.
5. **`computeRecords` eligibility is per modality, by the set's own snapshot.**
   `weight_reps` and `weighted_bodyweight` sets yield `heaviest_weight`
   (reps ≥ 1), `best_est_1rm` (1 ≤ reps ≤ 12) and `best_set_volume`;
   `bodyweight_reps` yields only `max_reps`; `duration` and `distance_duration`
   yield nothing. A set with `weight ≤ 0`, `reps` null/0 (where the type needs
   reps ≥ 1), or a null measure the type needs is ineligible for that type, never
   an error. A lineage whose modality changed over time simply drops the old
   sets that do not qualify under their own `modality_snapshot`.
6. **Ties keep the earliest.** Equalling a record is not a new PR: with equal
   best values the earliest set in chronology holds the record, across workouts
   and within one workout (lowest `set_number`).
7. **`previous_value` is the best of strictly-earlier workouts.** For each
   record, `previousValue` is the best eligible value for that type over
   workouts strictly before the record's workout in chronology, `null` when
   there is none; sets in the record's own workout never count. Always
   `< value` when non-null.
8. **Chronology is `started_at`, not `ended_at`.** Input order is
   `(workout started_at, workout id, workout_exercise position, set_number)`;
   `computeRecords` makes no use of any `ended_at`. A backdated session takes its
   real place in history: a record earlier by `started_at` displaces a later
   workout's record of the same value (ties) and takes `previous_value` slots
   correctly.
9. **Rebuild ≡ live (property test).** For seeded-random histories (many
   workouts, repeated values, backdated starts, mixed modalities, a set of
   generator seeds fixed in the test): (a) `computeRecords(history)` equals an
   independently written brute-force reference; (b) for every prefix `k`,
   `computeRecords(history[0..k])` equals the result of incrementally applying
   workout `k` to the state after `k-1` (what a live finish sequence produces);
   (c) the output is invariant under the order workouts *arrived* in, since only
   chronology matters.
10. **The qualifying-set query is exact.** Integration: only `set_type =
    'working'` sets in workouts with `ended_at IS NOT NULL`, of the acting
    user, in the lineage's roots, are loaded; `warmup` / `drop` / `failure` and
    in-progress workouts' sets never count; `is_complete = false` working sets
    **do** count (D5); sets whose measures are null (finished during 05.1's
    documented rollback window) are tolerated, not errors.
11. **Fork lineage merges.** The lineage root of a set's exercise is
    `COALESCE(exercise.forked_from_exercise_id, exercise.id)`. Sets logged on a
    global exercise, on a fork of it, and on a **second** fork of it by the same
    user all contribute to one record per type. A from-scratch custom exercise is
    its own root. Each DTO's `exerciseId` is the root; `sourceExerciseId` and
    `exerciseName` are the source set's own exercise id and name snapshot.
12. **Finish writes the records and returns them.** `PATCH /v1/workouts/{id}`
    with `endedAt` returns `200` with `newRecords` = the rows whose `workoutId` is
    this workout (≤ 4 per touched root), each with the §5 shape; the same rows
    are in `personal_record`. The very first finish of an exercise yields its
    eligible types with `previousValue: null`.
13. **A non-finish `PATCH` returns `newRecords: []`**, writes nothing to
    `personal_record`, and takes no PR lock. A finish whose exercises have no
    eligible sets (e.g. only `duration`) returns `[]` and leaves any existing rows
    for those roots intact (they are recomputed to the same values).
14. **A repeat finish is `409 workout-finished` and the records are
    recoverable.** The second finish `PATCH` answers `409 workout-finished`
    (unchanged, 05.0), and `GET /v1/personal-records?workoutId=<id>` returns the
    same records the first response carried, as long as the workout still holds
    them (D18).
15. **A backdated finish can take a record from a later workout.** Finish W2
    (later `started_at`) with a record, then finish W1 (earlier `started_at`,
    finished afterwards) with an equal-or-better value: after W1's finish the
    record's `workoutId` is W1 (ties) or the better value, W2's row for that type
    is gone or re-pointed with the right `previousValue`, and `newRecords` of W1's
    response lists it.
16. **Deleting a finished workout recomputes.** `DELETE /v1/workouts/{id}` of the
    workout that holds a record: the rows it sourced are removed by cascade and
    the root is recomputed in the same transaction — the next-best set is
    promoted (with a correct `previousValue`), or no row remains when no
    qualifying set is left. Deleting an **in-progress** workout takes no PR lock,
    runs no recompute and leaves `personal_record` untouched.
17. **A recompute failure rolls the finish back.** With a fault injected into the
    recompute, the finish answers `500`, `ended_at` is still `NULL`, no
    `personal_record` row changed, and a retry of the same `PATCH` (fault removed)
    succeeds. The same holds for delete: the workout still exists.
18. **Concurrent writers equal the serial result, without deadlock.** For one
    user: (a) finish of W1 concurrent with delete of finished W0; (b) finish of W1
    concurrent with delete of W1 itself; (c) two finishes of different workouts
    — each outcome is one of the serial orders' results, nothing `500`s, no
    deadlock (`40P01`) surfaces, and `personal_record` equals a full rebuild
    afterwards.
19. **`GET /v1/personal-records` filters and resolves lineage.** With no
    parameters: all the caller's rows. `exerciseId` filters to that exercise's
    lineage root — a fork's id, the origin's id and a second fork's id all return
    the same rows. `workoutId` returns the rows that workout currently holds. Both
    together intersect. Response `{ records: PersonalRecord[] }`, ordered
    `achievedAt` desc then `workoutId`, `exerciseId`, `recordType`; un-paginated.
20. **No existence oracle, no cross-user read.** Another user's `exerciseId` or
    `workoutId`, an absent id, and an exercise the caller cannot see (another
    user's custom exercise or fork) all return `200 { records: [] }` — never
    `404`/`403`, identical bodies. User A's rows are never returned to user B. A
    *malformed* id is `422 validation-error` (querystring schema), a format error
    that reveals nothing.
21. **Contract and caching.** Both routes return `401` with no/invalid token and
    appear in `GET /openapi.json` (`config.published: true`, `problems: []`); the
    `PATCH` operation's `200` is the extended schema; `GET` carries
    `Cache-Control: no-store` and no `ETag`; the CI OpenAPI drift check is green.
    The `PATCH` addition is additive — existing `Workout` fields are unchanged.
22. **`records:rebuild` reproduces live state.** `pnpm --filter @sin/api run
    records:rebuild` over a database built by live finishes leaves
    `personal_record` byte-for-byte equal (excluding `id`/`created_at`); over a
    database with finished workouts and an empty table it produces the same rows a
    live history would have; stale rows (an exercise whose last qualifying set is
    gone) are deleted; `--user <id>` touches only that user; a second run is a
    no-op. It takes the same per-user lock as the live path.
23. **An account purge reaches `personal_record` with no ordering step.**
    `DELETE FROM "user"` succeeds with no FK error and removes the user's rows;
    other users' rows are untouched.
24. **Logging.** `workout_finished` carries `record_count` (rows whose
    `workout_id` is this workout); no record value, set id or exercise name is
    logged by this spec; a non-finish `PATCH` emits no new line.
25. **`@sin/core` additions land cleanly.** `RECORD_TYPE_VALUES`,
    `RECORD_UNIT_VALUES`, `RECORD_UNIT_BY_TYPE`, `estimate1rm`,
    `computeRecords`, `parseWeightKgMilli`, `milliToDecimalString`, the
    `RecordSet` / `ComputedRecord` types, `PersonalRecordSchema`,
    `UpdatedWorkoutSchema` (+ inferred types) are exported **by name** from the
    barrel and added to `check-exports.mjs`'s `EXPECTED`; `pnpm run core:purity`
    stays green; `PersonalRecordSchema` parses a valid payload and rejects a
    missing field and an unknown record type.
26. **Hand reconciliation.** A fixture of 10 sessions across ≥ 4 exercises (all
    three weighted types, `max_reps`, a fork, an lb entry, a backdated session, a
    tie, a warm-up that would otherwise win) with hand-computed expected records
    (stored beside the fixture, with the arithmetic in comments) passes through
    both the live finish path and `records:rebuild` and matches exactly.
27. **Finish-latency measurement is recorded.** A benchmark script runs the finish
    path against the fixture scaled to ~2 years of history for one user, and the
    measured p50/p99 are written into §12 at implementation time against DESIGN
    §1.3's 400 ms. A measurement, not a CI gate (D19).
28. **Docs stay consistent.** Every edit in §11's "DESIGN.md / doc edits" is
    applied, the README roadmap row 07 is replaced by 07.0 / 07.1 / 07.2, and
    `docs/runbooks/first-deploy.md` gains the rebuild step.

## 4. Data model

Owned by this spec: **`personal_record`**. Migration
**`0008_create_personal_record`** — additive, expand-only, hand-authored SQL (the
same carve-out as 03.1 §4 / 05.0 §4 / 05.1 §4: the literal-list `CHECK`s are
drift-guarded against `@sin/core` constants and are not expressible in the
Prisma DSL). Applied on top of `0007`.

```
Table: personal_record
  id                    uuid         PK, app-generated UUIDv7
  user_id               uuid         NOT NULL FK → "user"(id)       ON DELETE CASCADE
  exercise_id           uuid         NOT NULL FK → exercise(id)     ON DELETE CASCADE
                                     -- the LINEAGE ROOT, not necessarily the exercise logged (§6.2)
  record_type           text         NOT NULL CHECK IN (<@sin/core RECORD_TYPE_VALUES>)
                                     -- 'heaviest_weight','best_est_1rm','best_set_volume','max_reps'
  value                 numeric(12,3) NOT NULL CHECK (value > 0)
  unit                  text         NOT NULL CHECK IN (<RECORD_UNIT_VALUES>)   -- 'kg','kg_reps','reps'
  previous_value        numeric(12,3) NULL      -- best of this type from strictly-earlier workouts
  source_set_entry_id   uuid         NOT NULL FK → set_entry(id)    ON DELETE CASCADE
  workout_id            uuid         NOT NULL FK → workout(id)      ON DELETE CASCADE
  achieved_at           timestamptz  NOT NULL   -- = workout.started_at
  local_date            date         NOT NULL   -- = workout.local_date
  created_at            timestamptz  NOT NULL DEFAULT now()

  CONSTRAINT personal_record_type_unit_check CHECK (
    (record_type IN ('heaviest_weight','best_est_1rm') AND unit = 'kg')
    OR (record_type = 'best_set_volume' AND unit = 'kg_reps')
    OR (record_type = 'max_reps' AND unit = 'reps'))

Indexes:
  personal_record_user_exercise_type_key  UNIQUE (user_id, exercise_id, record_type)
  personal_record_workout_idx             (workout_id)             -- ?workoutId= lookup; workout-delete cascade
  personal_record_source_set_idx          (source_set_entry_id)    -- set_entry cascade
```

- **`value` is `numeric(12,3)`, not 10,3 (D4).** `best_set_volume` is `reps ×
  weight_kg`, and 05.1's column bounds (D11: reps ≤ 32 767, weight ≤ 9 999.999)
  allow a product of ≈ 3.3 × 10⁸. `numeric(10,3)` holds 7 integer digits and would
  overflow into a permanently-500ing finish for that user. `(12,3)` holds 9
  integer digits; `previous_value` matches.
- **No `updated_at`, and the row `id` is not stable.** Rows are replaced wholesale
  on recompute (§6.3); `created_at` therefore means "when this recompute wrote
  the row", **not** when the PR was set — `achieved_at` is that (D16). The DTO
  exposes no record id for the same reason.
- **`exercise_id` is a lineage root and an FK to `exercise`.** A root is always
  a real `exercise` row (a global row, or a user's from-scratch custom row), so
  the FK holds; `ON DELETE CASCADE` mirrors `workout_exercise.exercise_id`
  (05.0 D37) so an account purge needs no ordering step (AC23). No index on
  `exercise_id` alone: the unique index's `user_id`-leading prefix serves every
  read, and `exercise` is only ever hard-deleted by a purge.
- **The type↔unit `CHECK` is the one cross-column rule** — cheap integrity for a
  derived table, and it makes a unit-mixing bug in the recompute fail loudly
  (D17). It is a second drift-guarded clause, rendered from `RECORD_UNIT_BY_TYPE`.
- **Prisma model**, client-shape only (`@@map("personal_record")`, per-field
  `@map`s, `@db.Uuid`, `@db.Decimal(12, 3)`, `@db.Timestamptz(6)`, `@db.Date`):
  `PersonalRecord` with relations to `User`, `Exercise`, `SetEntry`, `Workout`
  (all `onDelete: Cascade`). **Each of the four parents gains a
  `personalRecords PersonalRecord[]` back-reference** — Prisma-client-only, the
  same trap 05.0 §4 / 05.1 §4 recorded (`prisma validate` fails without them).
- **No index on `set_entry` or `workout_exercise` is added (D17).** 05.1 §12
  left "all sets for exercise X across a user's workouts" to this spec. The
  recompute query joins `workout` through `workout_user_started_idx (user_id,
  started_at DESC)` and `workout_exercise` through `workout_exercise_exercise_idx`
  (05.0 §4) — adequate for one user's history (low thousands of sets). AC27's
  benchmark is the check; if it fails, the additive fix is an index, not a
  redesign (§12 O1).
- **Backfill: none in the migration.** Rows for workouts finished before this
  release come from `records:rebuild` (§6.5, §11).

## 5. API surface

Both routes under `/v1`, authenticated, through the 03.0 route-schema convention,
published (OpenAPI opt-in per issue #10). The ambient `401`s are listed once.

```
PATCH /v1/workouts/{id}                          (existing; response changes)
  200  UpdatedWorkout        — Workout + newRecords: PersonalRecord[]
                               ([] for any PATCH that is not a finish)
  (errors unchanged: 404 not-found, 409 workout-finished,
   409 incomplete-working-sets, 422, 401)

GET /v1/personal-records?exerciseId=&workoutId=  auth required
  200  { records: PersonalRecord[] }
  422  validation-error      — a malformed exerciseId / workoutId
  401  unauthenticated / invalid-token
  config: { published: true, problems: [] }       — no writeGroup (a GET)
```

- **`exerciseId`** (optional) — resolved to its lineage root (§6.2), so a fork's
  id returns the same rows as the origin's. Resolved only through exercises the
  caller can see (a global row, or one they own); anything else matches nothing.
- **`workoutId`** (optional) — the records that workout currently holds.
- Both optional; both together intersect; neither ⇒ all the caller's records.
- **Unknown, foreign and unresolvable ids ⇒ `200 { records: [] }`**, never `404`
  — there is no existence oracle (§7, AC20).
- **Un-paginated, a documented exception to DESIGN §6's cursor rule** (like
  `GET /v1/exercises`): rows are bounded at ≤ 4 per lineage root, so the whole
  list is ≤ 4 × (exercises the user has ever logged) — low hundreds at the
  extreme — and no cursor exists to be wrong.
- **Caching:** the default `/v1` policy — `no-store`, no `ETag`, no
  `config.httpCache` (the result changes with every finish and delete, and a
  validator would buy nothing).
- **Ordering:** `achieved_at DESC, workout_id, exercise_id, record_type` —
  deterministic.
- **No rate-limit change** (§1).

### `@sin/core` additions

```ts
// packages/core/src/enums.ts — additions (frozen, like MODALITY_VALUES)
export const RECORD_TYPE_VALUES = Object.freeze(
  ["heaviest_weight", "best_est_1rm", "best_set_volume", "max_reps"] as const);
export type RecordType = (typeof RECORD_TYPE_VALUES)[number];
export const RECORD_UNIT_VALUES = Object.freeze(["kg", "kg_reps", "reps"] as const);
export type RecordUnit = (typeof RECORD_UNIT_VALUES)[number];
export const RECORD_UNIT_BY_TYPE: Readonly<Record<RecordType, RecordUnit>> = Object.freeze({
  heaviest_weight: "kg", best_est_1rm: "kg", best_set_volume: "kg_reps", max_reps: "reps",
});

// packages/core/src/dto/personal-record.ts — new module. Imports only enums + ids
// (acyclic, 05.1 D12): dto/workout.ts imports this, never the reverse.
export const PersonalRecordSchema = z.object({
  exerciseId: ExerciseIdSchema,          // the lineage root
  sourceExerciseId: ExerciseIdSchema,    // the source set's actual exercise (label as the user sees it now)
  exerciseName: z.string(),              // the source workout_exercise's name snapshot
  recordType: z.enum(RECORD_TYPE_VALUES),
  value: z.number().positive(),          // JSON number, like set weight/weightKg (dto/set-entry.ts)
  unit: z.enum(RECORD_UNIT_VALUES),
  previousValue: z.number().positive().nullable(),
  sourceSetId: SetEntryIdSchema,
  workoutId: WorkoutIdSchema,
  achievedAt: z.iso.datetime({ offset: true }),
  localDate: z.iso.date(),
});
export type PersonalRecord = z.infer<typeof PersonalRecordSchema>;

// packages/core/src/dto/workout.ts — addition
export const UpdatedWorkoutSchema = WorkoutSchema.extend({
  newRecords: z.array(PersonalRecordSchema),
});
export type UpdatedWorkout = z.infer<typeof UpdatedWorkoutSchema>;

// packages/core/src/records.ts — new module (pure; the purity check applies)
export interface RecordSet {            // one qualifying set, caller-sorted (§6.1)
  setId: string;
  workoutId: string;
  modality: string;                      // the set's workout_exercise.modality_snapshot
  weightKgMilli: number | null;          // integer thousandths of a kg
  reps: number | null;
}
export interface ComputedRecord {
  recordType: RecordType;
  valueMilli: number;                    // value × 1000, an integer, for EVERY type
  unit: RecordUnit;
  setId: string;
  workoutId: string;
  previousValueMilli: number | null;
}
export function parseWeightKgMilli(decimalString: string): number;
export function milliToDecimalString(milli: number): string;       // 61235 → "61.235"
export function estimate1rm(weightKgMilli: number, reps: number): number | null; // → milli
export function computeRecords(sets: readonly RecordSet[]): ComputedRecord[];    // ≤ 1 per type
```

Points that are choices, not accidents:

- **`valueMilli` is uniform across types** (`max_reps` is `reps × 1000`, volume is
  `reps × weightKgMilli`), so one formatter and one `numeric(12,3)` column serve
  all four, and no code path divides.
- **`PersonalRecordSchema` has no record id** (§4) and no `createdAt`.
- **`value` / `previousValue` are `z.number()`** (D14 below in §12): exactly
  representable — at most 9 integer + 3 fractional digits, far inside a double's
  15–16 — matching how 05.1 serializes `weight` / `weightKg`. Comparison never
  happens on them; it happens on the integers in core and in `numeric` in
  Postgres.
- **`UpdatedWorkoutSchema` is a new name, not a mutation of `WorkoutSchema`.**
  `WorkoutSchema` is the shape of `POST`, `GET /workouts/{id}` (via
  `WorkoutDetail`) and `GET /workouts/active`; only `PATCH` grows `newRecords`.

## 6. Behavior & logic

### 6.1 The math (`packages/core/src/records.ts`)

**Exact arithmetic.** `set_entry.weight_kg` is `numeric(7,3)` and is the canonical
comparison value (DESIGN §4.8). The repository selects it as **text**
(`weight_kg::text`, *not* the `::float8` that `SET_ENTRY_COLUMNS` uses for the
set DTO) and `parseWeightKgMilli` turns `"61.235"` into the integer `61235`. All
comparison and arithmetic then happen on integers. Magnitudes: weight ≤
9 999 999 milli; × (30 + 12) ≈ 4.2 × 10⁸; reps × weight ≤ 32 767 × 9 999 999 ≈
3.3 × 10¹¹ — all far inside `Number.MAX_SAFE_INTEGER` (≈ 9 × 10¹⁵), so no `BigInt`
is needed.

**Epley, rounded half-up.** `estimate1rm(w, reps)` = `floor((w × (30 + reps) + 15)
/ 30)` for integer `1 ≤ reps ≤ 12`, else `null`. (`x / 30` rounded half-up to the
integer milli is `floor((x + 15) / 30)`.) The `1 ≤ reps ≤ 12` window is
DESIGN §4.5's.

**Eligibility** — a set contributes to a type only if it qualifies under **its
own** `modality`:

| Modality | `heaviest_weight` | `best_est_1rm` | `best_set_volume` | `max_reps` |
|---|---|---|---|---|
| `weight_reps` | `w` where `reps ≥ 1` | `estimate1rm(w, reps)` | `reps × w` | — |
| `weighted_bodyweight` (added load only, D2) | same | same | same | — |
| `bodyweight_reps` | — | — | — | `reps` where `reps ≥ 1` |
| `duration`, `distance_duration` | — | — | — | — |

with the additional rule (D5) that a weight-based type needs `w > 0` and `reps`
non-null, and a value of 0 is never a record (`best_set_volume` of a `reps: 0`
failure set is 0 ⇒ ineligible). Null measures make a set ineligible for the type,
never an error: 05.1 §11 warns that sets finished during a rollback window may
lack required measures.

**`computeRecords(sets)`** — input: one lineage root's qualifying sets, pre-sorted
by `(workout started_at, workout id, workout_exercise position, set_number)`
(D13: the `position` tiebreak is needed because a workout can hold the same
lineage twice — a fork and its origin, or one exercise added twice — and
`set_number` restarts per `workout_exercise`). Sets of one workout are therefore
**contiguous**; `computeRecords` throws if a `workoutId` reappears after another
began (a caller bug, not a data state). Algorithm, per type: walk the workouts in
order; within a workout take the best eligible value, earliest set winning
(strict `>`); if it is strictly greater than the running best so far, it becomes
the record holder with `previousValueMilli = running best before this workout`
(or `null`); then fold the workout's best into the running best. The result is the
final holder — O(n), one pass. Output: ≤ 1 `ComputedRecord` per type, in
`RECORD_TYPE_VALUES` order.

**Ties.** Equalling the running best is not a new record (strict `>`), so the
earliest set holds, and `previousValue < value` always holds when non-null.

**Chronology is `started_at`** (the workout's), then workout id, then position,
then `set_number` — never `ended_at`. A session logged a day late carries its real
`started_at` (05.0 allows up to 7 days back, DESIGN §6) and lands in its true
place; finishing it later can therefore take a record from a workout that
finished earlier (§6.4).

### 6.2 Lineage root

`root(exercise) = COALESCE(exercise.forked_from_exercise_id, exercise.id)`, in SQL
against the **current** `exercise` row. Forking never chains (03.2 §6: `/fork`
refuses non-global targets), so one hop is the whole lineage; a user may fork the
same global row more than once, and the origin plus all of that user's forks share
one root. Consequences, stated so nobody expects more:

- It merges **fork ↔ origin ↔ other fork** — the realistic split: a user forks
  "Bench Press" to rename or retag it and keeps training.
- It does **not** merge a catalog row that the seed *retired* with its replacement
  key (the seed is append-only: a changed name/modality is a new row — 03.1 §6.3).
  Those are different roots; §12 O2.
- A from-scratch custom exercise is its own root.
- The `exercise_id` column holds the root; the source set's own exercise and its
  name snapshot ride in the DTO (`sourceExerciseId`, `exerciseName`) so a UI can
  label the record "as the user currently sees it" while linking to the lineage.

### 6.3 The write path — one recompute for finish, delete and rebuild (D8)

All three call one function, **`recomputeRecordsForRoots(tx, userId, roots)`**
(`apps/api/src/repositories/personal-record.prisma.ts`, taking a transaction
client — the same shape as 05.1's `assertWorkingSetsComplete(client, …)`), which,
for each root:

1. Loads the root's qualifying sets in **one** raw-SQL statement:

   ```sql
   SELECT root.id AS root_id, se.id AS set_id, se.set_number, se.reps,
          se.weight_kg::text AS weight_kg, we.modality_snapshot,
          we.exercise_id AS source_exercise_id, we.exercise_name_snapshot,
          w.id AS workout_id, w.started_at, w.local_date
   FROM "set_entry" se
   JOIN "workout_exercise" we ON we.id = se.workout_exercise_id
   JOIN "workout" w           ON w.id = we.workout_id
                             AND w.user_id = $user AND w.ended_at IS NOT NULL
   JOIN "exercise" e          ON e.id = we.exercise_id
   CROSS JOIN LATERAL (SELECT COALESCE(e.forked_from_exercise_id, e.id) AS id) root
   WHERE se.set_type = 'working' AND root.id = ANY($roots::uuid[])
   ORDER BY root.id, w.started_at, w.id, we.position, se.set_number
   ```

   (`is_complete` is deliberately not in the `WHERE` — D5.)
2. Groups rows by root and runs `computeRecords` on each group.
3. **Replaces** the root's rows: `DELETE FROM personal_record WHERE user_id = $user
   AND exercise_id = ANY($roots)` then one `INSERT` per computed record (a new
   UUIDv7 id, `achieved_at` / `local_date` from the source workout, `value` /
   `previous_value` via `milliToDecimalString`). A root with no qualifying sets
   gets no rows — which is how a delete that removes the last qualifying set
   retracts a PR. Delete-then-insert (not upsert) means no stale row can survive
   a type dropping out, and the unique index cannot trip inside one transaction.

It returns the rows it wrote, so callers can derive `newRecords` with no second
read.

**Why a per-lineage full recompute and not something incremental (D8).**
Considered:

- **A — recompute the touched lineages from their full qualifying history, via one
  function** (chosen). One code path is finish, delete *and* rebuild, so "rebuild
  equals live" is true by construction rather than by test discipline, and the
  property test (AC9) checks the pure core, not two implementations. Cost: one
  query + O(n) per touched root per finish — measured in AC27.
- **B — incremental at finish** (compare this workout's sets against the stored
  record, update on a win). Cheapest per finish, but delete needs a second,
  different algorithm (the next-best set is not stored), a backdated finish needs
  a third, and rebuild a fourth — the exact drift R4 warns about.
- **C — SQL-side aggregation** (window functions / `DISTINCT ON` in Postgres).
  Fast, but puts Epley's rounding and the tie rule in SQL, a second
  implementation of the math that `@sin/core` already owns and that web/mobile
  clients cannot reuse or unit-test.

**The finish path** (`updateWorkout`, `workout.prisma.ts`), when
`nextEndedAt !== null`, in this order inside the existing transaction:

1. `SELECT … FROM workout … FOR UPDATE` (05.0, unchanged — first statement).
2. 05.0's `ended_at` / bounds checks, then 05.1's `assertWorkingSetsComplete`
   (unchanged; a rejected finish never reaches PR work).
3. `UPDATE "workout" SET … ended_at = …` (unchanged).
4. **New:** `SELECT pg_advisory_xact_lock(hashtext(${"pr:" + userId}))` as its own
   statement; then the touched roots —
   `SELECT DISTINCT COALESCE(e.forked_from_exercise_id, e.id) FROM workout_exercise
   we JOIN exercise e ON e.id = we.exercise_id WHERE we.workout_id = $id`; then
   `recomputeRecordsForRoots`. Because it runs **after** the `UPDATE`, in the same
   transaction, the loader's `w.ended_at IS NOT NULL` sees this workout as finished
   (a transaction reads its own writes) — no "include this workout" special case.
5. `newRecords` = returned rows whose `workout_id` is this workout; the existing
   `exerciseCount` read; return `{ workout, exerciseCount, newRecords }`.

The code comment at the current seam ("Spec 07's PR recompute goes after this one,
still before the UPDATE") is corrected to "after the UPDATE" when this lands
(D9 explains why that is the better order).

**The delete path** (`deleteWorkout`): today it reads the workout without a row
lock and issues the `DELETE`. It becomes: (1) `SELECT id, user_id, ended_at FROM
workout … FOR UPDATE` (lock moved to a row lock — D9); (2) if `ended_at IS NULL`,
the existing delete and nothing else (an in-progress workout sourced no row);
(3) if finished: take the PR advisory lock, capture the touched roots (same
query as above), `DELETE` (cascade removes the rows it sourced), then
`recomputeRecordsForRoots` on the captured roots.

**Locking and deadlock-freedom (D9).** The per-user advisory lock
`pg_advisory_xact_lock(hashtext('pr:' || user_id))` serializes every PR writer for
one user (finish, delete, rebuild) — recomputes of different lineages could in
principle run in parallel, but one lock is simpler and a single user's finishes
are not concurrent in practice. The `pr:` prefix keeps its key domain distinct
from 05.0's `hashtext(workout_id)` and 05.1's `hashtext(workout_exercise_id)`
(05.1 §12 left that namespacing open; this spec namespaces only its own key — a
collision costs a spurious wait, never correctness). **Lock order is workout row
(`FOR UPDATE`) → PR advisory lock**, everywhere. The delete's new row lock is what
makes that true: without it, "finish W1" (holds W1's row, wants the advisory lock)
could deadlock with "delete W1" (holds the advisory lock, wants W1's row for its
`DELETE`) — AC18(b). Set creates take only `FOR SHARE` on the workout and their
own advisory lock, never the PR lock, so no new cycle. **Correctness rests on
READ COMMITTED** (the default; Prisma's interactive transaction does not change
it): the loader statement runs *after* the lock is acquired, so it sees every
recompute committed before it; a test asserts the isolation level so a future
change to `SERIALIZABLE` (which would break this reasoning) fails loudly.

**Failure (D10).** The recompute runs inside the finish/delete transaction; any
error rolls the whole thing back and the client sees `500`. The finish is retried
by the 06.2 queue. Rejected: *finish, then recompute best-effort afterwards* — a
workout with stale PRs and no signal to retry is the R4 failure mode; a visible
`500` the client can retry is better than silent wrongness.

### 6.4 Backdated and displaced records

Because chronology is `started_at`, a finish can change records of *other*
workouts: finishing a backdated W1 can take a tie from later W2 (earliest wins),
or lower a later record's `previous_value`. That is intended — it is exactly what
a full recompute of the lineage gives. Consequently a stored row's `workout_id`
and `previous_value` are facts about *the current history*, not immutable events,
and `GET ?workoutId=` returns what a workout holds now (D18).

### 6.5 Rebuild (`records:rebuild`)

`pnpm --filter @sin/api run records:rebuild [--user <id>]`, mirroring the catalog
seed's structure (D11): entry `apps/api/scripts/rebuild-records.ts`, logic in
`apps/api/src/records/` so it compiles into `dist/` and runs in the Docker image
(`node apps/api/dist/records/cli.js`); reads `DATABASE_URL` (the direct Neon host,
runbook B4); not a Prisma hook; exit `1` on failure.

Per user — one transaction each, with an explicit `timeout: 60_000` like the seed
(Prisma's interactive-transaction default is 5 s): take the PR advisory lock;
roots = every root appearing in the user's finished workouts **union** every root
that currently has a `personal_record` row (so stale rows are removed); call
`recomputeRecordsForRoots`. Users are enumerated as those with a finished workout
or any `personal_record` row; `--user` restricts to one id (an unknown id is a
no-op with a log line). Batching per user keeps each lock short and bounds
memory. Idempotent: a re-run with unchanged data rewrites identical rows. Safe
against live traffic because it takes the same lock as the live path. It logs one
`records_rebuilt` line per user (`user_id`, `root_count`, `record_count`) and a
final summary — no values.

**It is a manual release step after `migrate deploy`**, like the catalog seed
(runbook; §11). Staging already has finished workouts (06.x dogfooding); they get
rows only once rebuild runs — *or* when a later finish/delete touches their
exercise, since the recompute is always from full history (§11).

### 6.6 Business logging

`workout_finished` (existing, `routes/workouts.ts`) gains `record_count` =
`newRecords.length`. Nothing else is emitted; record values, set ids and exercise
names are never logged (05.0 §9's "ids, counts and durations only").

### 6.7 The two reads

`GET /v1/personal-records` is a plain read through a small
`PersonalRecordRepository.list(actingUserId, { exerciseId?, workoutId? })`, always
`WHERE user_id = $actingUserId`. `exerciseId`: resolve through `SELECT
COALESCE(forked_from_exercise_id, id) FROM exercise WHERE id = $1 AND
(owner_user_id IS NULL OR owner_user_id = $actingUserId)`; no row ⇒ empty result
(no query against `personal_record`). `workoutId`: an equality on `workout_id`,
which `user_id` already scopes. `exerciseName` and `sourceExerciseId` are **not**
stored on the row (§4), so the read joins `set_entry` (via `source_set_entry_id`)
and `workout_exercise` to take `we.exercise_id` and `we.exercise_name_snapshot`
from the source set. `recomputeRecordsForRoots` returns the same two values from
its loader rows, so the finish response and the `GET` agree.

## 7. Security & privacy

- **Authorization boundary.** Every read and write filters by the acting user's
  id; `personal_record` carries `user_id` directly (unlike `set_entry`), so there
  is no join chain to get wrong. A cross-user probe is an empty list, never `403`
  or `404` (AC20) — the same "no existence oracle" posture as 03.1 / 05.0.
- **Exercise visibility on `exerciseId`.** The lineage resolution only sees
  exercises the caller may see (global, or owned). Resolving another user's fork id
  would otherwise answer "this id is a fork of root R" — a small leak of someone
  else's catalog structure for free; it is closed by returning empty.
- **PII.** Records are training data (DESIGN §8.2 — sensitive) and are
  user-owned rows covered by the existing purge (cascade, AC23) and, in Spec 11,
  export. `exerciseName` is the user's own snapshot string, returned to them only;
  it is never logged.
- **Abuse surface.** No new write endpoint; the existing finish/delete are
  already per-user write-limited and in-flight capped (05.2). A recompute is
  bounded by one user's own history. Hostile-but-valid data (reps 32 767 ×
  weight 9 999.999) fits `numeric(12,3)` (D4) and cannot make a finish 500.
- **Integrity.** The table is a cache: a corrupted or missing row is repaired by
  `records:rebuild`, never by a user-facing write.

## 11. Deployment & rollback

`0008_create_personal_record` is additive and expand-only; it creates a new table
and adds FKs whose referenced tables are taken at `SHARE ROW EXCLUSIVE` for an
instant (harmless — no release-step migration runs concurrently).

**Release ordering** (extends 05.1 §11):

1. `prisma migrate deploy` (Neon **direct** host) applies `0008` **before** the
   code goes live. Unlike 05.1's routes, this is not optional ordering: the new
   finish code `INSERT`s into `personal_record`, so code live ahead of the table
   would answer every finish with `500`.
2. New code goes live: finishes start writing rows and returning `newRecords`;
   deletes start recomputing; `GET /v1/personal-records` serves.
3. **Run `records:rebuild`** against the same `DATABASE_URL` (a manual release
   step like `seed:catalog`, docs/runbooks/first-deploy.md gets a new step after
   B5). Staging already has finished workouts that get records only once it runs.
   Until then the table is empty for exercises nobody has touched — and **self-heals
   per lineage**: the first finish or delete that touches an exercise recomputes it
   from full history, so even a skipped rebuild only leaves untouched exercises
   un-recorded, never wrong.
4. `/openapi.json` reflects the routes and the `PATCH` shape; CI drift check catches
   a mismatch before merge.

**No feature flag** — "off" is the absence of a UI consumer until Spec 08, and the
additive `newRecords` field breaks no existing client (the web finish flow ignores
unknown fields).

**Rollback:** revert the code commit. `personal_record` stays, inert; production
undo is a forward migration, never a down script (the down — `DROP TABLE
"personal_record"` — is dev/test only, as in 05.0/05.1). **Caveat:** workouts
finished or deleted during the rollback window do **not** update the table, so its
rows go stale; **after re-deploying (or deploying a fix), run `records:rebuild`**
— it is the repair for exactly this, and is idempotent.

## 12. Decisions & open questions

- ✅ **D1 — the roadmap row 07 is split into 07.0 / 07.1 / 07.2 (owner decision,
  2026-10-06).** 07.0 PR engine (this), 07.1 history list, 07.2 progress series.
  **Rationale:** the three are independent reads/writes over `set_entry`, each a
  session on its own (README: "small enough to finish in one work session"), and
  only 07.0 touches the finish transaction. 07.1 / 07.2 depend on 05.1 (not on
  07.0), except 07.2 reuses `estimate1rm` from 07.0's core module.
- ✅ **D2 — four record types and a per-modality table (owner decision).**
  `heaviest_weight`, `best_est_1rm`, `best_set_volume`, `max_reps`; `weight_reps`
  and `weighted_bodyweight` get the first three (added load only for the latter,
  because no `body_metric` table exists to add body weight to), `bodyweight_reps`
  gets `max_reps`, `duration` / `distance_duration` get none in v1. **Rationale:**
  a distinct `max_reps` type replaces DESIGN §4.5's old "value = reps, unit =
  'reps'" overload, which made one column mean two things and defeated a
  type↔unit `CHECK`.
- ✅ **D3 — exact integer arithmetic, Epley half-up.** Weights are integer
  thousandths parsed from `weight_kg`'s text; `estimate1rm` rounds half-up to
  0.001 kg; no `BigInt` needed (§6.1). **Rationale:** R4 — a float `>` on
  `61.234999…` vs `61.235` is the kind of silent PR error users notice.
- ✅ **D4 — `value` / `previous_value` are `numeric(12,3)`, not the brief's
  `(10,3)`.** **Rationale:** `reps × weight_kg` at 05.1's own column bounds is
  ≈ 3.3 × 10⁸; `(10,3)` caps at 9 999 999.999 and a hostile-but-valid set would
  make that user's finish `500` forever. **Consequence:** the brief's column type
  is amended; core `valueMilli` still fits comfortably in a safe integer.
- ✅ **D5 — what qualifies.** `set_type = 'working'` in **finished** workouts
  only; `is_complete` ignored; and a weight-based type additionally needs
  `weight_kg > 0` and non-null `reps` (the rep-needing types `reps ≥ 1`); a value
  of 0 is never a record. **Rationale:** finish integrity (05.1) already
  guarantees required measures, and many users never tick the box — a PR system
  that depended on it would silently skip real sets. The `> 0` thresholds are an
  addition to the brief: without them a `weight: 0` set would be a "heaviest
  weight" of 0 and a `reps: 0` failure set a volume of 0.
- ✅ **D6 — chronology is `started_at`; ties go to the earliest set.** Not
  `ended_at`. **Rationale:** a backdated session takes its real place in history
  (and can displace a later workout's record, §6.4); equalling a record is not
  beating it, so the earliest keeps it.
- ✅ **D7 — lineage root is `COALESCE(forked_from_exercise_id, id)`**, with the
  source exercise id and name snapshot in the DTO. **Rationale:** forking never
  chains (03.2) so one hop suffices, and a user may fork a global row more than
  once — origin and all forks share one root, so forking to rename does not split
  a user's PR history. **Correction to the brief's wording:** this does *not*
  protect against the catalog seed replacing a global row (retire + new key = a
  new `exercise.id`, and 03.1's seed forbids editing a live row's name) — that is
  O2. Editing a global row's non-identifying fields never changed its id anyway.
- ✅ **D8 — approach A: recompute the touched lineages from full history through
  one function** (finish, delete, rebuild share it). Rejected: incremental-at-
  finish (needs distinct algorithms for delete, backdated finish and rebuild —
  four implementations of one rule); SQL-side aggregation (puts Epley and the tie
  rule in SQL, a second implementation of math `@sin/core` owns and the clients
  reuse). **Rationale:** "rebuild ≡ live" by construction, which is the property
  R4 and M2's exit criterion care about. **Cost:** O(history of the touched
  lineages) per finish — AC27 measures it.
- ✅ **D9 — lock order: workout row `FOR UPDATE` → per-user PR advisory lock; the
  recompute runs *after* the `UPDATE`; delete gains a row lock.** The advisory key
  is `hashtext('pr:' || user_id)`, a namespaced domain. **Rationale (found while
  drafting):** the brief's finish ordering is sound, but `deleteWorkout` today
  takes no workout row lock, so "finish W1" (row, then advisory) and "delete W1"
  (advisory, then row via `DELETE`) form a deadlock cycle; locking the workout row
  first in delete removes it, with one extra statement already implied by
  reading the row. Running the recompute after the `UPDATE` lets the loader's
  `ended_at IS NOT NULL` see the workout as finished by reading its own write; the
  current code comment says "before the UPDATE" and is corrected. **Rejected:**
  one global lock (cross-user stalls); locking inside `recomputeRecordsForRoots`
  only (hides the order from the callers that must also hold the row lock).
- ✅ **D10 — a recompute failure fails the finish/delete.** `500`, rolled back,
  retried by the 06.2 queue. **Rationale:** correctness over a finish with stale
  PRs and nothing to prompt a retry. **Rejected:** best-effort recompute after
  commit.
- ✅ **D11 — rebuild mirrors the catalog seed.** `records:rebuild [--user <id>]`,
  per-user transaction, explicit timeout, same lock, manual release step after
  `migrate deploy`, logic in `src/records/` (compiled into `dist/`) with a thin
  entry in `scripts/`. **Rationale:** one operational pattern for "derived data
  the release must (re)build"; the seed's `prisma.seed`-hook avoidance applies for
  the same reason (a dev `migrate reset` must not run it silently).
- ✅ **D12 — API shape.** `newRecords` is an additive field on the existing
  `PATCH` (`UpdatedWorkoutSchema`, new name — `WorkoutSchema` is shared); the new
  `GET` is un-paginated (≤ 4 rows per lineage; a documented exception to DESIGN
  §6, like the catalog), `no-store`, no ETag, `published`, no `writeGroup`;
  foreign / unknown ids are empty lists (no oracle); a *malformed* id is `422` —
  the querystring-schema path every other `/v1` route takes, and a format error
  reveals nothing (the brief did not specify malformed ids; path-param `404`
  doesn't apply to a query string).
- ✅ **D13 — sort key gains `workout_exercise.position`.** `(started_at, workout
  id, position, set_number)`, not the brief's `(started_at, workout id,
  set_number)`: `set_number` restarts per `workout_exercise`, and one workout can
  hold the same lineage twice (a fork and its origin, or one exercise added
  twice). Without the tiebreak, "earliest set wins" would be undefined within such
  a workout.
- ✅ **D14 — `value` serializes as a JSON number.** Matching `weight` / `weightKg`
  in `dto/set-entry.ts`. At most 12 significant digits, exact in a double; all
  comparison happens on integers (core) or `numeric` (Postgres).
- ✅ **D15 — a record's row is a cache entry, replaced wholesale.** Delete +
  insert per recompute; `created_at` means "written by the recompute", not "PR
  set" (`achieved_at` is that); the DTO exposes no record id. **Rationale:** no
  stale-row cases, no unique-index races in one transaction. **Rejected:** upsert
  plus a delete-stale step (two code paths for one outcome).
- ✅ **D16 — `previous_value` is the best of strictly-earlier workouts.** Not
  "the previous record holder's value", not "earlier sets": sets of the same
  workout never count, so a workout's own best-of-session is not its own "previous".
  Always `< value` when non-null.
- ✅ **D17 — indexes and constraints.** Unique `(user_id, exercise_id,
  record_type)` plus `(workout_id)` (the `?workoutId=` lookup *and* the
  workout-delete cascade) and `(source_set_entry_id)` (the `set_entry` cascade); a
  compound type↔unit `CHECK` and `value > 0`; no new `set_entry` /
  `workout_exercise` index — this answers 05.1 §12's open read-path question with
  "use `workout_user_started_idx` and `workout_exercise_exercise_idx`, measure,
  add an index additively if AC27 says so". The `CHECK`s are beyond the brief; they
  cost nothing and turn a unit-mixing recompute bug into a loud failure.
- ✅ **D18 — `?workoutId=` returns what the workout holds now.** After a lost
  finish response, the finish screen recovers its records, with the caveat that a
  later backdated finish may have displaced one (§6.4). **Rationale:** storing a
  per-finish snapshot to replay would be a second, immutable table to keep
  consistent for a UI case that is rare and degrades gracefully.
- ✅ **D19 — latency is measured, not gated.** AC27's benchmark records p50/p99
  against DESIGN §1.3's 400 ms; CI timing assertions on a shared runner are
  flaky. If the number is bad, the levers in order: an additive index (D17),
  recompute only the roots whose sets changed *and* skip when none, then SQL-side
  pre-aggregation (D8's rejected option C, behind the same function).
- ✅ **D20 — mixed-modality lineages compare across modalities.** If a lineage's
  modality changed (e.g. `weight_reps` → `weighted_bodyweight`), `heaviest_weight`
  compares a barbell load with an added load. **Rationale:** the set's own
  snapshot decides *eligibility* (so old non-qualifying sets drop out — the
  brief), but renaming the meaning of "weight" mid-history is rare and the
  alternative (a record per modality) is a bigger model for a corner case. Noted,
  not solved.
- ✅ **D21 — the property test uses a seeded PRNG, not `fast-check`.** **Rationale:**
  "no new dependencies" for a solo project, and a fixed seed list makes
  failures reproducible; a hand-rolled generator is ~30 lines. Revisit if shrinking
  would have saved real time.
- ✅ **D22 — module layout.** Pure math in `@sin/core` (`records.ts`); the recompute
  in `apps/api/src/repositories/personal-record.prisma.ts` behind a
  `PersonalRecordRepository` interface (reads) plus the transaction-client
  `recomputeRecordsForRoots` function (writes), following the 05.0/05.1
  interface + `*.prisma.ts` split; `updateWorkout` / `deleteWorkout` call the
  function directly (as they call `assertWorkingSetsComplete`). `UpdateWorkoutResult`
  gains `newRecords`; `buildApp` / `V1RouteDeps` gain `personalRecordRepository`.

- **Open O1 — finish-route p99 on a ~2-year history.** To be measured at
  implementation (AC27) and written here: p50 `__ ms`, p99 `__ ms` vs 400 ms.
  Nothing is decided on it until then.
- **Open O2 — catalog retire-and-replace does not merge PR history.** When the
  seed retires a global row and adds a replacement key, a user's records on the old
  row and on the new one are separate lineages. Fixing it needs a catalog-level
  "supersedes" link (a 03.x concern) or a user-facing "merge exercises" action.
  Not in 07.0; owner to say whether it matters before the catalog grows.
- **Open O3 — `rep_pr_at_weight` and duration/distance PRs** remain deferred
  (DESIGN §4.5); `max_reps` on weighted modalities (most reps at *any* weight) is
  also unspecified — v1 gives it to `bodyweight_reps` only.
