## 1. Purpose, scope & non-goals

Ship the **write side** of the exercise catalog that Spec 03.1 deferred:
`POST /v1/exercises` (custom create), `PATCH /v1/exercises/{id}` (edit an
**owned** row only — never a global row), `POST /v1/exercises/{id}/fork`
(copy-on-write fork of a global row, with an optional body of edits applied on
top), and `DELETE /v1/exercises/{id}` (soft-delete an owned row). Adds the
additive `forked_from_exercise_id` column, resolving 03.1's open D9. Adds a
hard per-user active-custom-exercise cap and the new `@sin/core` write DTOs.

### In scope

- `POST /v1/exercises`, `PATCH /v1/exercises/{id}`,
  `POST /v1/exercises/{id}/fork`, `DELETE /v1/exercises/{id}`.
- Migration `0003_exercise_fork_provenance` — additive
  `forked_from_exercise_id` column + FK.
- The hard per-user active-custom-exercise cap (500), enforced atomically.
- `CreateExerciseSchema`, `UpdateExerciseSchema`, and the `forkedFromExerciseId`
  addition to `ExerciseSchema` in `@sin/core`.

### Non-goals

- **The `GET /v1/exercises` M2M/`skipProvisioning` 401 gap is out of scope.**
  It's a 03.1 bug (verified live on staging 2026-09-15), not a 03.2 feature —
  every 03.2 write endpoint inherently requires a fully provisioned identity
  anyway (an `email` claim is needed to create the `user` row at all). Tracked
  as a separate backlog item against 03.1; not fixed here.
- No "undelete" endpoint for a soft-deleted custom exercise.
- No un-retiring a global row (curation tool territory).
- No promotion of a custom exercise into the global catalog (moderation cost
  — DESIGN §4.2).
- No `GET /v1/exercises/{id}` (deferred again — §12 D16).
- Modality→required-measure validation, rate limiting/write-frequency abuse,
  and the exercise-picker UI (including the client-side "hide the
  forked-from origin" rule this spec's DTO enables) are Spec 05/06.

## 2. Acceptance criteria

1. Migration `0003_exercise_fork_provenance` additively adds
   `forked_from_exercise_id uuid NULL REFERENCES exercise(id) ON DELETE
   RESTRICT`; no backfill.
2. `POST /v1/exercises` creates an owned custom exercise: `201`,
   `catalogKey: null`, `ownerUserId` = caller, `forkedFromExerciseId: null`,
   `isActive: true`, `secondaryMuscleIds` in submitted order. `.strict()`
   body; bad `name`/`modality` → `422`; unknown `primaryMuscleId`/
   `equipmentId`/any `secondaryMuscleIds` entry → `422` naming all bad fields
   together, not just the first.
3. The per-user active-custom-exercise cap (500) is enforced atomically and
   is a **single budget shared by create and fork** (both insert a row) — a
   concurrency integration test at the boundary, mixing `POST /v1/exercises`
   and `POST .../fork` requests, proves no user ever exceeds it, and the
   request that would exceed it gets `409`, never silently admitted.
4. `PATCH /v1/exercises/{id}` on the caller's own custom row updates in
   place: `200`, same `id`, `updatedAt` bumped. A partial body that is valid
   on its own but produces an invalid **merged** result (e.g. submits
   `secondaryMuscleIds` restating the base row's untouched `primaryMuscleId`)
   → `422 validation-error` naming the conflicting field — the cross-field
   check re-runs against the merge, not just the raw body (§6).
5. `PATCH /v1/exercises/{id}` on a **global** row is rejected —
   `409 exercise-immutable-use-fork`, telling the client to use the fork
   endpoint instead. Never silently forks. `PATCH` on the caller's **own**
   row that has already been soft-deleted (`isActive=false`) is likewise
   rejected — `409 exercise-retired` — never revives a deleted row via edit
   (consistent with the §1 non-goal "no undelete endpoint").
6. `POST /v1/exercises/{id}/fork` on a global, active row: `201`,
   `Location: /v1/exercises/{newId}`, new row has `catalogKey: null`,
   `ownerUserId` = caller, `forkedFromExerciseId` = origin id, unedited
   fields copied from origin, any fields in the optional request body
   override them. The origin row is byte-for-byte unchanged (its own
   `updatedAt` doesn't move). An overlay body that is individually valid but
   conflicts with the origin's *unedited* fields once merged (same
   restated-`primaryMuscleId` case as AC4) → `422 validation-error`, same
   merge-then-validate rule as `PATCH` (§6).
7. `POST .../fork` on the caller's *own* row, or on a retired row (global
   `isActive=false`), is rejected `409` — never forks an already-owned or
   dead row.
8. Ownership/visibility boundary is 404, not 403, for "not visible":
   `PATCH`/`POST .../fork`/`DELETE` on an absent id or another user's custom
   row → `404`, indistinguishable from each other (reuse `findVisibleById`).
9. `DELETE /v1/exercises/{id}` soft-deletes the caller's own custom row
   (`is_active=false`), `204`, idempotent (repeat call also `204`s), rejected
   for a global row with `403` (row is visible — no enumeration risk in
   saying so).
10. `forkedFromExerciseId` ships on the `Exercise` DTO (`null` unless a
    fork), is included in the ETag hash, and in the OpenAPI schema.
    `GET /v1/exercises` does **not** server-side-suppress a forked origin —
    both origin and fork remain in the full pull and any delta (resolves D9).
11. All new endpoints require auth (`401` with no/invalid token), appear in
    `GET /openapi.json`, CI drift check stays green.
12. `@sin/core` purity/typecheck: new DTOs compile with no React/DOM/Node
    imports; missing required `POST` field fails `.parse()`; unknown key on
    any `.strict()` schema fails.
13. Docs consistent: `specs/README.md` 03.2 row updated to reflect this
    spec's status; DESIGN §4.2 gains the `forked_from_exercise_id` column +
    resolved-D9 note (at implementation time); DESIGN §4.9 wording
    double-checked against these `DELETE` semantics.

## 4. Data model

One migration, **`0003_exercise_fork_provenance`**, additive, hand-authored
SQL (matching `0002`'s convention of hand-authored SQL for constraints
Prisma's DSL can't express):

```sql
ALTER TABLE "exercise" ADD COLUMN "forked_from_exercise_id" UUID NULL;
ALTER TABLE "exercise" ADD CONSTRAINT "exercise_forked_from_exercise_id_fkey"
  FOREIGN KEY ("forked_from_exercise_id") REFERENCES "exercise"("id")
  ON DELETE RESTRICT ON UPDATE CASCADE;
```

`RESTRICT` matches the existing `primary_muscle_id`/`equipment_id`
convention. The self-referential FK always points at a global row in
practice, enforced at the application layer (forking never chains — §6),
not by a `CHECK` (which can't reference another row). No new index — nothing
queries *by* this column yet; add one only when a query plan needs it, same
posture 03.1 used for `is_active`. No backfill — nullable, defaults `NULL`
for every existing row.

```

  201  Exercise                                    Location: /v1/exercises/{id}
  422  validation-error

  422  validation-error
  401  unauthenticated / invalid-token

  201  Exercise (new id)                           Location: /v1/exercises/{newId}

  409  exercise-already-owned        — target is already the caller's own row
  409  exercise-retired              — target isActive=false
  409  exercise-limit-reached

  401  unauthenticated / invalid-token

DELETE /v1/exercises/{id}                         auth required
  204  (no body) — idempotent
  403  exercise-immutable — target is a global row
  404  not-found
  401  unauthenticated / invalid-token
```

**DTOs** (`packages/core/src/dto/exercise.ts` additions), `camelCase`, same
pattern as 03.1's `ExerciseSchema`:

```ts
// @sin/core — dto/exercise.ts additions

// ExerciseSchema (03.1) gains one field:
export const ExerciseSchema = z.object({
  // ...existing fields (03.1 §5)...
  forkedFromExerciseId: ExerciseIdSchema.nullable(),
});

export const CreateExerciseSchema = z
  .object({
    name: CatalogName,
    modality: z.enum(MODALITY_VALUES),
    primaryMuscleId: z.string().nullable().default(null),
    secondaryMuscleIds: z.array(z.string()).max(4).default([]),
    equipmentId: z.string().nullable().default(null),
  })
  .strict()
  .superRefine((val, ctx) => {
    const seen = new Set<string>();
    for (const id of val.secondaryMuscleIds) {
      if (seen.has(id)) {
        ctx.addIssue({ code: "custom", path: ["secondaryMuscleIds"], message: "duplicate muscle id" });
      }
      seen.add(id);
    }
    if (val.primaryMuscleId !== null && val.secondaryMuscleIds.includes(val.primaryMuscleId)) {
      ctx.addIssue({ code: "custom", path: ["secondaryMuscleIds"], message: "must not restate primaryMuscleId" });
    }
  });
export type CreateExercise = z.infer<typeof CreateExerciseSchema>;

// Same fields, all optional — used by both PATCH and the /fork overlay body.
export const UpdateExerciseSchema = z
  .object({
    name: CatalogName,
    modality: z.enum(MODALITY_VALUES),
    primaryMuscleId: z.string().nullable(),
    secondaryMuscleIds: z.array(z.string()).max(4),
    equipmentId: z.string().nullable(),
  })
  .partial()
  .strict();
export type UpdateExercise = z.infer<typeof UpdateExerciseSchema>;

export const MAX_CUSTOM_EXERCISES_PER_USER = 500;
```

Since a partial `UpdateExerciseSchema` body can't see the base row's current
values, the muscle-id cross-field check (no duplicates, no restating
`primaryMuscleId` in `secondaryMuscleIds`) is re-run server-side against the
**merged** result (base row overlaid by the partial body), not against the
raw body — for both `PATCH` and the `/fork` overlay (§6).

## 6. Behavior & logic

- **`PATCH`** only ever updates a row where `origin.ownerUserId ===
  actingUserId`; any other visible target (global, `ownerUserId === null`)
  is rejected with `ExerciseImmutableUseForkError` — the client is expected
  to call `/fork` instead. A target that *is* owned by the caller but
  already soft-deleted (`isActive=false`) is rejected with
  `ExerciseRetiredError` — editing never revives a deleted row (§1 non-goal
  "no undelete endpoint", AC5). `PATCH` never branches into forking itself; this
  was a deliberate revision from an earlier draft that had `PATCH` branch
  into a 201-with-new-id fork response, rejected because a `PATCH` returning
  a different resource than the one addressed breaks the client's ability to
  treat the response as "the updated version of what I asked for."
  **Atomicity note**: the ownership/global/retired checks above are read
  logic ahead of the write, not baked into the write's own `WHERE` clause —
  unlike the cap insert (below), which is fully atomic by construction. The
  actual `UPDATE` must be `UPDATE exercise SET ... WHERE id = $1 AND
  owner_user_id = $2 AND is_active = true`, checking rows-affected
  afterward (zero ⇒ re-run the visibility/state checks to pick the right
  404/409), so a same-user race between a `PATCH` and a concurrent `DELETE`
  on the same row can never silently apply an edit to a row that just
  became retired. This is same-user-only (no tenant boundary at risk) but
  needs a concurrency test alongside AC5's other cases.
- **`POST /fork`** only operates on a global row (`ownerUserId === null`)
  that is active; forking the caller's own row is rejected `409
  exercise-already-owned` (already owned — just `PATCH` it); forking a
  retired row is rejected `409 exercise-retired`. On success: copy the
  origin's fields, apply the optional request body's overlay fields on top,
  re-run the muscle-id cross-field check on the *merged* result, insert as a
  new row with `ownerUserId = caller`, `catalogKey = null`,
  `forkedFromExerciseId = origin.id`. Forking never chains — the FK always
  points at the original global row, never at another fork, because `/fork`
  refuses non-global targets outright.
- **`DELETE`** soft-deletes owned rows only (`is_active=false`, idempotent);
  `403 exercise-immutable` on a global target. Matches DESIGN §4.9's
  existing deletion-matrix row exactly (soft-delete for history readability)
  — this spec just ships the endpoint that triggers it. `workout_exercise`
  already snapshots `exercise_name_snapshot`/`modality_snapshot` at log time
  (DESIGN §4.4), so soft-delete/fork never corrupts past session display
  regardless of what happens to the `exercise` row afterward.
- **Reference validation** (create + fork overlay): batch-check all of
  `primaryMuscleId` + `secondaryMuscleIds` (deduped) + `equipmentId` against
  `muscle_group`/`equipment` in one query each (mirrors the seed's "validate
  everything, then write" convention from 03.1 §6.3). Collect *all* bad
  references into one `422 validation-error`, rather than relying on the
  DB's FK errors (which only cover two of three fields and report one
  violation at a time — `secondary_muscle_ids` has no DB FK at all per 03.1
  §4, so this pre-check is its only integrity guard). Real FKs on
  `primary_muscle_id`/`equipment_id` remain as defense-in-depth.
- **The per-user cap (500 active rows)** is enforced atomically by
  `insertWithCap` (`exercise.prisma.ts`), serialized per-user via
  `pg_advisory_xact_lock(hashtext(actingUserId))`. **This requires two
  *separate* statements inside one `prisma.$transaction` — lock acquisition
  first (`tx.$executeRaw`), then a second statement (`tx.$queryRaw`) that
  does the CTE'd count+insert — not one CTE'd statement that folds the lock
  into the count's `WITH` clause.** An earlier draft of this spec (and an
  earlier implementation, since corrected — whole-branch-review finding C1,
  2026-09-17) used the single-statement form:

  ```sql
  -- Superseded — do not reintroduce (see D23). Looks safe, is not.
  WITH _lock AS (
    SELECT pg_advisory_xact_lock(hashtext($1))
  ),
  _cap AS (
    SELECT count(*) AS active_count
    FROM exercise, _lock
    WHERE owner_user_id = $1 AND is_active = true
  )
  INSERT INTO exercise (...) SELECT ... FROM _cap WHERE _cap.active_count < $9
  RETURNING *;
  ```

  reasoning that joining `_lock` into `_cap` forces a real data dependency,
  so Postgres's CTE inlining (PG12+) can't evaluate `_cap` independently of
  the lock. That reasoning addresses the wrong layer: the problem isn't
  planner inlining, it's when the statement's MVCC snapshot is taken. Under
  READ COMMITTED, **a statement's snapshot is fixed at that statement's
  start, before the executor runs** — blocking mid-statement on
  `pg_advisory_xact_lock` never refreshes the snapshot the rest of that same
  statement sees, no matter how the CTEs are wired together. Concretely: two
  concurrent callers can each open a snapshot showing 499 active rows before
  either touches the lock; one acquires it and commits, landing at 500; the
  second, unblocked immediately after, is still reading the *same pre-commit
  snapshot it started with* — sees 499, passes the `< 500` gate, and inserts
  a 501st row. No amount of restructuring the CTEs inside a single statement
  can fix this, because the snapshot is already stale before the lock is
  even requested.

  **What actually ships** is two sequential statements in one transaction:

  ```sql
  -- Statement 1 (tx.$executeRaw): acquire the lock, nothing else.
  SELECT pg_advisory_xact_lock(hashtext($1));

  -- Statement 2 (tx.$queryRaw): only runs, and only opens its own
  -- snapshot, after statement 1 has returned.
  WITH _cap AS (
    SELECT count(*) AS active_count
    FROM exercise
    WHERE owner_user_id = $1 AND is_active = true
  )
  INSERT INTO exercise (id, owner_user_id, catalog_key, name, modality,
                        primary_muscle_id, secondary_muscle_ids, equipment_id,
                        is_active, forked_from_exercise_id, created_at, updated_at)
  SELECT $2, $1, NULL, $3, $4, $5, $6, $7, true, $8, now(), now()
  FROM _cap
  WHERE _cap.active_count < $9
  RETURNING *;
  ```

  Because statement 2 doesn't begin — and therefore doesn't fix its
  snapshot — until statement 1 has returned, a caller only ever reaches
  statement 2 after the lock is confirmed held *and* any prior holder's
  transaction has committed or rolled back. Its count is then guaranteed
  current as of that commit, closing the race above. **Both statements must
  stay inside the same `prisma.$transaction`** (not two separate
  transactions) so the lock is held across both and released atomically with
  the insert.
  **Parameterization**: both statements are Prisma tagged-template calls
  (`$executeRaw`/`$queryRaw`) — every interpolation is a driver-bound
  parameter, never `$executeRawUnsafe`/`$queryRawUnsafe`/string-concatenated
  SQL — matching `exercise.prisma.ts`'s existing documented convention for
  this table. This is worth stating explicitly here, not just inheriting the
  convention by reference, because `name` (up to 120 chars of verbatim user
  text) flows through this exact statement on this table's first-ever
  user-write path.
  `hashtext(actingUserId)`'s 32-bit output space has a real but
  not attacker-targetable collision surface: `ownerUserId` is never exposed
  for another user (only `null` or the caller's own id), so an attacker
  cannot choose a UUID to deliberately collide with a specific victim's lock
  key.

  Zero rows returned from statement 2 ⇒ cap hit ⇒ throw
  `CustomExerciseLimitError`. Counts only `is_active=true` rows, since the
  cap exists to bound `GET /v1/exercises`'s unpaginated pull (03.1 §6.1's
  bounded-set assumption), not to limit lifetime creates — a user who
  deletes old customs to make room isn't penalized. This is covered by a
  dedicated concurrency integration test at the cap boundary (§10, AC3), not
  just unit coverage — a weak (2-caller) race can pass against the broken
  single-statement form purely from scheduling luck, so the test fires 10
  genuinely concurrent callers to reliably contend on the same snapshot
  window (see D23).

  **`POST /fork` shares this exact `insertWithCap` function**, not a second,
  ad hoc insert — same two-statement lock/count/insert sequence, with
  `$3..$8` bound to the origin's (overlay-merged) fields and `$8` (
  `forked_from_exercise_id`) bound to the origin's `id` instead of `NULL`.
  This matters because the cap is a single shared budget across create *and*
  fork — a fork-specific insert that skipped the lock/count sequence would
  let a user slip past 500 active rows via `/fork` even with `POST
  /exercises` correctly capped. The concurrency test at the 499/500 boundary
  (§10, AC3) must therefore fire a **mix** of `POST /exercises` and `POST
  .../fork` requests, not creates alone, to exercise this shared budget.
- **D9, resolved:** ship `forked_from_exercise_id` for provenance (also
  useful for a plausible future "revert to global" action), but do **not**
  filter the origin out of `GET /v1/exercises` server-side. Rationale: the
  global origin's `updated_at` cannot change per-fork (it's shared across
  every caller — bumping it per-fork would corrupt the shared ETag for every
  other user), so a server-side suppression filter would only take effect on
  a *fresh* full pull (new device, reinstall), silently diverging from an
  already-synced client's cached view — a correctness gap worse than the
  cosmetic duplicate it would fix. Suppression instead becomes a
  **client-side** rule for Spec 06: hide any global row whose `id` matches
  some visible row's `forkedFromExerciseId`, computed entirely from the
  client's own already-fetched cache, at zero additional network cost and no
  delta-consistency risk.
- **Cursor derivation (03.1's flagged "revisit" item): no change needed.**
  The `MAX(updated_at)`-derived `serverTime` cursor's correctness was always
  MVCC-visibility-based (a row's app-stamped `updated_at` can never be seen
  by a reader before the writing transaction commits) — not
  single-writer-based. This holds identically whether the writer is the seed
  script or one of many concurrent user requests, since the existing
  per-caller visibility filter (`owner_user_id IS NULL OR owner_user_id =
  actingUserId`) already scopes the cursor's window to what that caller can
  see; one user's write never perturbs another user's cursor.
- Two browser tabs racing a `PATCH` on the same owned row: last-write-wins,
  no optimistic lock — matches the existing `set_entry` convention (DESIGN
  §4.4) of deferring full conflict resolution while there's one web client.
  The `updatedAt` on the response is what a client can use to detect it lost
  such a race.

## 7. Security & privacy

- This is the first user-controlled write into a table every previous row
  was curator-authored for — the storage contract is unchanged
  (`CatalogName` bounds length/control-chars, stored verbatim,
  output-encoded at render time by Spec 06), but it raises the stakes on
  that boundary holding, since a stored-XSS-shaped payload can now originate
  from any user, not just a reviewed data file.
- 404-not-403 on "not visible" everywhere (absent id or another user's row
  — no enumeration signal distinguishes the two, reusing
  `findVisibleById`'s existing convention). `DELETE`/`PATCH` against a
  *visible* global row is 403/409 with the real reason instead, since the
  row's existence isn't a secret (everyone sees it via `GET /v1/exercises`).
- The cap is a resource bound (protects the unpaginated `GET /v1/exercises`
  invariant), not a rate limit (doesn't throttle create/delete *frequency*)
  — intentionally non-duplicative with Spec 05's general write-quota
  system, which addresses a different failure mode.
- `forked_from_exercise_id` provenance is not sensitive — it only ever
  points at a public global row.
- Structured logs for create/fork/edit/delete record
  `exercise_id`/`owner_user_id`/`forked_from_exercise_id` only — never the
  raw `name` value (arbitrary user text has no business being duplicated
  into logs).
- No new PII.

## 12. Decisions & open questions

### Resolved

- ✅ **D9** (carried from 03.1, resolved here) — ship
  `forked_from_exercise_id` for provenance; suppression of the forked origin
  from the catalog view is a **client-side** rendering rule (Spec 06), not a
  server-side visibility filter, because the shared/immutable-per-caller
  nature of the global row's `updated_at` makes a query-level filter break
  the `updated_since` delta contract for already-synced clients (§6).
- ✅ **D14** — forking is a dedicated `POST /v1/exercises/{id}/fork`
  endpoint, not a branch inside `PATCH`. `PATCH` stays conventional (200,
  same id, owned rows only, rejects global targets); `/fork` takes an
  optional edit-overlay body and returns 201 + `Location`, the same shape a
  plain `POST` create would. This was revised from an initial draft where
  `PATCH` branched into a fork response — rejected as insufficiently
  RESTful (a `PATCH` shouldn't return a resource other than the one
  addressed).
- ✅ **D15** — hard cap of 500 active custom exercises per user, shipped as
  a code constant (not env var), enforced via an advisory-lock-guarded
  atomic insert (§6) rather than a plain pre-check (racy under concurrency)
  or a DB `CHECK`/trigger (can't express a cross-row count in a `CHECK`;
  triggers are foreign to this codebase's "app stamps its own timestamps"
  convention). **Amended by D23** (2026-09-17) — "atomic insert" here means
  the two-statement lock-then-count-and-insert sequence D23 records, not the
  single CTE'd statement §6 originally showed; D15's headline (advisory-lock
  cap, code constant, no CHECK/trigger) is unaffected.
- ✅ **D16** — no `GET /v1/exercises/{id}` in 03.2, deferred again. Nothing
  in this spec's flows needs it: the client already holds the full row
  locally (03.1's full-catalog cache) for an edit form, and the
  `PATCH`/`fork`/`DELETE` responses return current row state directly. Ship
  it only when a real consumer (e.g. a deep-link screen) exists.
- ✅ **D17** — cursor derivation needs no change for concurrent user writes;
  the correctness argument was always MVCC-visibility-based, not
  single-writer-based (§6).

- ✅ **D18** (resolved on this review pass) — **`secondaryMuscleIds` length
  cap stays 4.** No existing convention anchors this number (DESIGN §4.2
  and 03.1 leave the curated-data array uncapped; 4 is new with this spec),
  but it is a plain Zod `.max()` on an internal DTO, not a migration-locked
  value — raising it later costs a one-line schema change, not a data
  migration. 4 comfortably covers real compound movements (e.g. squat:
  quads/glutes/hamstrings + core) without meaningfully constraining a
  curator or a custom-exercise author. Kept out of `MAX_CUSTOM_EXERCISES_PER_USER`'s
  treatment (not exported as a named constant) since, unlike the cap, no
  other spec needs to reference it.
  **Amended by D22** (2026-09-17) — the merged-result length check this
  decision's rationale assumed would never fire against curated data in fact
  did, once the check was extended to cover `/fork`'s copy-on-write. D22
  scopes the cap to caller-submitted arrays only, restoring this decision's
  "curated data stays uncapped" premise; the headline ("cap stays 4") is
  unchanged, only its scope is corrected.

- ✅ **D19** (resolved on this review pass) — **status code family for
  "operation attempted against the wrong kind of row" keeps the existing
  403/409 split, on this explicit rule:** `403` is a permanent, no-recourse
  prohibition — nobody, ever, can perform that operation on that kind of row
  (`DELETE` on a global row: a global row can never be deleted, full stop).
  `409` is a conflict with the target's *current state* that has an
  actionable resolution the client can retry differently (`PATCH` on a
  global row → call `/fork` instead; fork an already-owned or retired row →
  the client picked the wrong target/moment). `422` was considered and
  rejected for all four names — it reads as "the request body is malformed,"
  which none of these are; the body is fine, the target row's state is what
  conflicts, and RFC 9110's `409 Conflict` ("request conflicts with the
  current state of the target resource") is the better fit whenever there's
  a next step. Applying the rule: `PATCH` global → `409
  exercise-immutable-use-fork`; `PATCH` on the caller's own already-retired
  row → `409 exercise-retired`; fork on own/retired row → `409
  exercise-already-owned`/`exercise-retired`; `DELETE` global → `403
  exercise-immutable` (unchanged from §5 — this decision documents the rule
  those codes already followed, so no API-surface change was needed).

- ✅ **D20** (design-level security review, 2026-09-15, accepted by the
  user) — **the cap's connection-pool blast radius is an accepted risk for
  the deploy window, not mitigated in 03.2.** The advisory lock
  (`pg_advisory_xact_lock`, held for the full write transaction, serialized
  per-user) is contended on connections drawn from the app's shared pool
  (`connection_limit=8`). A burst of concurrent `POST
  /exercises`/`POST .../fork` from one account can occupy several of those
  8 connections simultaneously, which — because the pool is process-wide —
  can back up other users' unrelated requests, not just the offending
  account's own. Decision: accept this until Spec 05's general rate
  limiter ships, rather than adding an interim app-level concurrency cap
  now. Rationale: triggering it requires scripted abuse from a single
  account against a pre-launch app; an interim guard would add scope to
  03.2 for a risk Spec 05 is already the designated owner of closing
  properly.
- ✅ **D21** (design-level security review, 2026-09-15, accepted by the
  user) — **unbounded `exercise` table growth via create→delete cycling is
  an accepted risk for the deploy window, not mitigated in 03.2.** The
  500-item cap only bounds `is_active=true` rows; soft-deleted rows are
  never purged (DESIGN §4.9, by design, for history/snapshot integrity), so
  with no write-frequency throttle until Spec 05, a scripted account can
  grow the table and its backups without bound. Decision: accept rather
  than pull a minimal write-rate quota forward into 03.2. Rationale: same
  as D20 — the growth is slow, cheap to clean up later with a one-off
  purge job if it ever matters in practice, and Spec 05 is the deliberate
  home for write-frequency limits.

- ✅ **D22** (post-implementation correction, code review, 2026-09-17) —
  **the `secondaryMuscleIds` 4-cap applies only to arrays the caller
  submits, never to an array inherited unedited from a base row or a `/fork`
  origin.** Amends D18's scope (D18's "cap stays 4" headline is unchanged).
  Found: a same-day fix that added a length check to the merge-then-validate
  step (`muscleIdCrossFieldIssues`, shared by `PATCH` and `/fork` via
  `assertMergedFieldsValid`) closed one latent bug (a fork of an over-cap
  curated row producing a custom row a later `PATCH` would silently keep
  over-cap forever) by introducing a worse one: the seed's
  `ExerciseInput.secondaryMuscleIds` is deliberately uncapped (D18), so the
  first curated exercise shipped with 5+ secondaries becomes **permanently
  unforkable** — `POST .../fork` with an *empty* overlay body returns `422`
  naming a field the caller never touched.
  **Why the caller-submitted side gives, not curated data:** re-reading D18's
  own rationale — "comfortably covers real compound movements... without
  meaningfully constraining a curator or a custom-exercise author" — the cap
  was never meant to bind curators; it exists to keep a *human-typed* list
  sane in a form/JSON file. Nothing downstream depends on
  `secondaryMuscleIds.length ≤ 4` holding for any particular row (no DB
  `CHECK` — Spec 03.1 §4 notes arrays can't be FK'd — no `ETag`/serialization
  logic, no other spec). A fork that truncated or rejected a faithfully-copied
  field would itself be the bug: `/fork` is specified (AC6, §6) to copy the
  origin byte-for-byte before any overlay applies. So a custom row ending up
  with 5+ secondaries via fork is not a defect to prevent — it is correct
  copy-on-write behavior — and the cap still does its one job (bounding what
  a human types) because it re-applies the instant a caller's own patch/overlay
  actually includes `secondaryMuscleIds`, even to resubmit unchanged values.
  **Options considered and rejected:** (A) cap curated data too (`.max(4)` on
  the seed's `ExerciseInput`) — rejected, since it constrains curators for a
  constraint D18 itself says was never meant to bind them, and permanently
  forecloses a legitimate 5-prime-mover curated exercise for no compensating
  benefit. A CI/lint-enforced cap on the catalog JSON (instead of the runtime
  seed schema) — rejected for the same underlying reason; moving the
  enforcement point doesn't answer whether curators *should* be bound by a
  picker-form UX constraint, and duplicates a number that is load-bearing
  nowhere else.
  **Implementation:** `muscleIdCrossFieldIssues` (`@sin/core`) gains an
  options bag (`{ checkLength?: boolean }`, default `true`, so
  `CreateExerciseSchema`'s call site is unaffected — a `POST` body always
  fully specifies the field). `assertMergedFieldsValid`
  (`apps/api/src/repositories/exercise-writes.ts`) takes the caller's
  patch/overlay alongside the merged result and passes
  `checkLength: "secondaryMuscleIds" in patch` — the same `"key" in patch`
  idiom `mergeWritableFields` already uses to distinguish "present in this
  request" from "absent, keep the base value." `updateExercise` and
  `forkExercise` (`apps/api/src/repositories/exercise.prisma.ts`) pass their
  `patch`/`overlay` through to the now-two-argument
  `assertMergedFieldsValid`. Duplicate-id and restated-`primaryMuscleId`
  checks are unaffected — they are data-integrity rules, not UX bounds, and
  keep running against the full merged result unconditionally on both
  `PATCH` and `/fork`. No change to the seed (`apps/api/src/seed/catalog.ts`)
  — `ExerciseInput.secondaryMuscleIds` stays uncapped, per D18 as amended.

- ✅ **D23** (post-implementation correction, whole-branch review finding C1,
  2026-09-17) — **the per-user 500-row cap's lock acquisition and its
  count+insert must be two separate statements inside one
  `prisma.$transaction`, not one CTE'd statement.** Supersedes §6's original
  single-statement sample (`WITH _lock AS (SELECT pg_advisory_xact_lock(...)),
  _cap AS (SELECT count(*) ... FROM exercise, _lock ...)`) and amends D15's
  "atomic insert" characterization to mean this two-statement sequence.
  **Found:** the single-statement form's prose argued that joining `_lock`
  into `_cap`'s `FROM` clause creates a real data dependency, defeating
  Postgres's CTE inlining (PG12+) and thereby forcing the count to wait on
  the lock. That reasoning targets the wrong layer. Under READ COMMITTED, a
  statement's MVCC snapshot is fixed at that statement's *start*, before the
  executor runs — blocking mid-statement on `pg_advisory_xact_lock` does not
  refresh the snapshot the rest of that same statement sees, regardless of
  how its CTEs are wired together. Two concurrent callers can each fix a
  snapshot showing 499 active rows before either requests the lock; one
  acquires it and commits at 500; the second, unblocked immediately after,
  still reads its own stale pre-commit snapshot — sees 499, passes the `<
  500` gate, and inserts a 501st row, breaching the cap. The bug was latent
  in the original implementation and, before this fix, could pass against a
  weak (2-caller) concurrency test purely from scheduling luck, which is how
  it survived per-task review.
  **Fix:** split the lock into its own statement
  (`tx.$executeRaw` running `SELECT pg_advisory_xact_lock(hashtext(actingUserId))`)
  ahead of a second statement (`tx.$queryRaw` running the CTE'd count+insert),
  both inside one `prisma.$transaction`. Because the second statement doesn't
  begin — and so doesn't fix its snapshot — until the first has returned, it
  only ever runs after the lock is confirmed held and any prior holder's
  transaction has committed or rolled back, so its count is always current
  as of that commit. Shipped in `insertWithCap`
  (`apps/api/src/repositories/exercise.prisma.ts`), shared verbatim by
  `createExercise` and `forkExercise` per D15/§6.
  **Verification:** the previous 2-caller concurrency tests were hardened
  into two 10-caller tests that reliably contend on the same snapshot window
  — `exercise-repository.integration.test.ts`: "C1 — never exceeds the cap
  under genuine concurrency" (10 concurrent `createExercise` calls at the
  495/500 boundary, expects exactly 5 fulfilled/5 rejected, final count 500)
  and "shares the create cap: a mixed create+fork burst at the 499/500
  boundary never exceeds it" (10 calls split between `createExercise` and
  `forkExercise` at the 499/500 boundary, expects exactly 1 fulfilled/9
  rejected). Both fail against the single-statement form and pass against
  the two-statement form.
  **Why not weigh the single-statement form as a real option:** it isn't a
  tradeoff to weigh — it is incorrect under READ COMMITTED regardless of how
  the CTEs are joined, so there was no second option once the snapshot-timing
  mechanism was understood; this entry exists so a future reader doesn't
  "simplify" the shipped code back into the single-statement form on the
  belief that it's equivalent.
