## 1. Purpose, scope & non-goals

### Purpose

Today a finished workout is read-only: every set and exercise write answers `409 workout-finished`, and the start time can never change after creation. So one wrong tap stays wrong forever, a forgotten workout cannot be logged on its real day, and an app opened late leaves a wrong clock. This spec makes the **server** able to (a) accept every live-logging write on a finished workout while keeping personal records, History and Progress exactly right, and (b) change a workout's start time and duration, live or finished.

**Success** (brief §1): after any edit, History, the workout summary, Progress and personal records read as if the workout had been logged correctly in the first place, and an edited or back-dated workout is indistinguishable from any other (brief §4.4 — no marker column, no flag in any DTO).

### In scope

- **Phase A.** The existing set and workout-exercise write routes, and the title/notes part of `PATCH /v1/workouts/{id}`, accept a **finished** workout. Each such write is one transaction that takes the per-user PR lock first, writes, and recomputes the affected lineages with the existing `recomputeRecordsForRoots`. A finished-mode write that would leave the workout with **no sets** is refused (`409 workout-would-be-empty`). A finished-mode set has its `completed_at` kept inside the workout's span. `@sin/core` gains the pure "does this set change affect records" predicate.
- **Phase B.** `PATCH /v1/workouts/{id}` gains `startedAt`, `tzOffsetMinutes` (only with `startedAt`) and `durationSeconds`, for live **and** finished workouts. A live workout stores a "took" (`workout.planned_duration_s`, migration `0012`) that the client turns into the finish `endedAt`. On a finished workout `startedAt` / `durationSeconds` rewrite the start and the end, re-derive `local_date`, shift set `completed_at` by the start delta, and recompute records.
- New error `409 workout-would-be-empty`; `workout-finished` narrows to "this workout is already finished" (re-finish).
- The flow rules the UI spec needs: which route does what, the error→behavior table, offline vs online, cache invalidation (§3, §5).

### Non-goals

- **UI** — the edit screen, banner, Change Time sheet, Done, "Delete this whole workout instead?" dialog, where Edit workout sits (a later UI spec; §3 lists what it can rely on).
- **New routes or HTTP methods.** None (D1). So no `CORS_METHODS`, `writeGroup` or OpenAPI-gate additions beyond the problem lists.
- **Editing a workout's planned sets, sections or routine notes** (09 / 09.1 / 09.2 snapshots) — they stay immutable start-time snapshots with no write route (D14).
- **Un-finishing** a workout (reopening it as live). `endedAt` on a finished workout stays rejected (D17).
- **An "edited" / "logged later" marker, an audit trail, an undo, a Save/Cancel draft** (brief §3, §4.2).
- **Rejecting overlapping workouts** (brief §5; D10).
- **Offline queueing of finished-workout edits** (D12).
- **Bulk edits, multi-device conflict resolution beyond today's last-write-wins per row.**

### Fit for one work session

Phase A is a repository refactor of eight write paths onto one "write mode" helper plus the recompute call; Phase B is one migration, one PATCH extension and a pure retime function. Each is one PR and one sitting; together they are a long session. If time runs out, the cut is the phase boundary, not a spec split: Phase A ships and is useful alone (fix a wrong set), Phase B is independent of A's UI.

## 2. Acceptance criteria

Every behavioral criterion has ≥1 test whose `describe` is tagged **`"07.4 ACn — …"`**; infra criteria are verified by CI. §10 maps each to a method. "Finished mode" means the target workout has `ended_at` set; "live mode" means it does not.

### Phase A — editing a finished workout's contents

1. **Set writes open on a finished workout.** `POST /v1/workout-exercises/{id}/sets`, `PATCH /v1/sets/{id}` and `DELETE /v1/sets/{id}` succeed (`201`/`200`/`204`) when the parent workout is finished. None of the three can return `409 workout-finished` any more. A measure validation failure is still `422`.
2. **Exercise writes open on a finished workout.** `POST /v1/workouts/{id}/exercises`, `PATCH /v1/workout-exercises/{id}` (`position`, `notes`, `supersetGroup`) and `DELETE /v1/workout-exercises/{id}` succeed on a finished workout; positions stay the dense `0 … n-1` sequence (05.0 AC11); none returns `workout-finished`.
3. **`PATCH /v1/workouts/{id}` on a finished workout.** `title` / `notes` edits are `200`; `PATCH {}` and `{ endedAt: null }` are `200` no-ops returning the row unchanged; **`endedAt` non-null is still `409 workout-finished`** (the "already finished" recovery path, Q16, depends on it). On a live workout all behavior is unchanged. Schema validation still precedes state (`{ title: "" }` is `422` on a finished workout).
4. **Finished-mode lock order.** In finished mode the first data-touching statement of every write transaction (set create/patch/delete, exercise add/patch/delete, workout PATCH, including title/notes-only) is `lockUserRecords`; it precedes every workout, `workout_exercise` and `set_entry` row lock and every per-parent advisory lock. A live-mode write, and an idempotent set replay that finds its stored row, take no PR lock.
5. **The mode is decided without a lock and re-checked under the lock; a flip restarts the request.** If a write was preflighted as live and the workout is found finished under its row lock (a finish committed in between), the repository abandons that transaction and re-runs the whole request once in finished mode. The request then succeeds with records recomputed; it never answers `409 workout-finished` and never commits a finished-workout write without taking the PR lock first.
6. **Records follow set edits exactly.** After a finished-mode set create, patch (`weight`, `weightUnit`, `reps`, `setType`) or delete, the lineage's `personal_record` rows equal what `records:rebuild` would produce from scratch: a heavier new set takes the record; lowering or deleting the record set promotes the next best set (same workout or an earlier/later one) and restates every `previous_value`; a tie is still won by the earliest set. The recompute runs in the edit's transaction; a recompute failure rolls the edit back (`500`).
7. **Records follow exercise edits.** Removing a finished workout's exercise recomputes its lineage root; reordering exercises recomputes exactly the roots that occur more than once in that workout (the tie-break reads `workout_exercise.position`) and no other; adding an exercise, `notes` and `supersetGroup` edits recompute nothing.
8. **Edits that cannot affect records recompute nothing.** A finished-mode set write whose set is not `working` before and after, or that changes none of `setType`, `reps`, `weightKg` (for example only `rpe`, `distance`, `durationS`, `isComplete`), issues no `DELETE FROM personal_record` and no loader query. The predicate is the pure `@sin/core` function `setChangeAffectsRecords` (unit-tested exhaustively).
9. **Finished-mode integrity.** In finished mode a `working` set must satisfy the finish rule (`isWorkingSetComplete` for its modality): a create or patch whose resulting working set lacks a required measure is `422 validation-error` naming the missing fields, nothing written. Warm-up / drop / failure sets stay exempt. Live mode is unchanged (half-filled rows allowed).
10. **The server refuses to empty a finished workout.** In finished mode, a `DELETE /v1/sets/{id}` that would take the workout's total `set_entry` count (any set type) from ≥1 to 0, or a `DELETE /v1/workout-exercises/{id}` whose cascade would, is `409 workout-would-be-empty` (problem+json, no extension member), nothing changed, no recompute. Deleting any set while others remain, or an exercise that has no sets while other exercises do, succeeds. A live workout may delete its last set. `DELETE /v1/workouts/{id}` is unchanged and is the only way to remove the last set.
11. **The guard is race-free.** Two concurrent deletes of the last two sets of a finished workout produce exactly one `204` and one `409 workout-would-be-empty`; one set remains.
12. **`DELETE /v1/workouts/{id}` is unchanged** (`204` live or finished, `404` on repeat, lock order and recompute per 07.0), so the UI's "Delete this whole workout instead?" confirm needs no new route.
13. **`completed_at` stays inside the span in finished mode.** A set created complete in a finished workout gets `completed_at = LEAST(GREATEST(now(), started_at), ended_at)`, not `now()`; a `PATCH` that flips `isComplete` false→true stamps the same value (`COALESCE(completed_at, …)`); an already-complete set keeps its value; `isComplete: false` clears it. A set created incomplete has `NULL`.
14. **Create idempotency is unchanged.** A replayed `clientGeneratedId` on a finished workout answers `200` with the stored set (no second row, no PR lock, no recompute), including when the workout was finished after the first attempt; a first-time keyed create on a finished workout is `201`.
15. **Concurrency matrix.** Real-concurrency integration (`Promise.all` of independent `inject`s, 07.0 AC18 style): finished-mode edit vs finish of another workout, vs delete of another workout, vs delete of the same workout, vs another edit of the same workout, vs a live-mode set write on the user's live workout. Each result is one of the serial outcomes; no `500`, no `40P01`; the final `personal_record` table equals a full recompute; the transaction isolation level is still `READ COMMITTED`.
16. **Authorization is unchanged.** Another user's workout, exercise or set is `404` (never `403`) on every changed route in finished mode, and a malformed id is `404`.
17. **Live logging is unchanged and not slower.** A live-mode set create/patch/delete and exercise write issue the same statements as before Phase A (no PR lock, `completed_at = now()`), apart from the one preflight read that already existed.

### Phase B — Change Time

18. **Migration `0012`.** `0012_workout_planned_duration` applies on a fresh database and on the existing chain, adds `workout.planned_duration_s INTEGER NULL` and the two named CHECKs of §4, changes no existing row, and `prisma validate` plus the whole-schema `prisma migrate diff` show no drift. The `86400` literal is drift-guarded against the `@sin/core` constant.
19. **DTOs.** `UpdateWorkoutSchema` accepts `startedAt`, `tzOffsetMinutes` and `durationSeconds` and stays a `strictObject`; `tzOffsetMinutes` without `startedAt`, and a non-null `endedAt` together with `durationSeconds`, are `422`; `localDate` is still an unknown key (`422`). `WorkoutSchema` gains required-nullable `plannedDurationSeconds`; `WorkoutSummary`, `WorkoutDetail`, the finish response and the export carry it through the shared mappers.
20. **Change Time on a live workout.** `PATCH { startedAt }` moves the start; the stored `local_date` / `tz_offset_minutes` are re-derived from it (D8); no PR lock, no set is touched. `PATCH { durationSeconds: n }` stores the plan, `{ durationSeconds: null }` clears it, `0 ≤ n ≤ 86400` else `422`. The resulting end (`startedAt + durationSeconds`) may not be more than 5 minutes in the future (`422` naming `durationSeconds`, or `startedAt` when the move caused it).
21. **Finish with a plan.** A live workout with `plannedDurationSeconds = n` finished by `PATCH { endedAt: startedAt + n }` is accepted under the existing finish rules; the finish clears `planned_duration_s` (the response carries `plannedDurationSeconds: null`; the CHECK forbids a plan on a finished row); the stored duration equals `n` seconds exactly. `endedAt` and `durationSeconds` in one body is `422`. `workout_finished.duration_seconds` equals the stored duration.
22. **Change Time on a finished workout.** `{ startedAt }` alone moves the workout: `ended_at = new started_at + old duration`. `{ durationSeconds }` alone sets `ended_at = started_at + n`. Both together set both. `durationSeconds: null` is `422`. The new end may not be more than 5 minutes in the future. `ended_at ≥ started_at` always (zero duration is allowed).
23. **The start bound.** A **changed** `startedAt` must be ≤ now + 5 minutes and ≥ `WORKOUT_START_EDIT_FLOOR` (`2000-01-01T00:00:00Z`, a fixed date, not a rolling window) else `422` naming `startedAt`; a `startedAt` equal to the stored value is accepted without a bound check (so echoing an old start back is harmless). `POST /v1/workouts` keeps its 7-day past bound.
24. **Calendar fields follow the start.** When `startedAt` changes, `local_date` and `tz_offset_minutes` are rewritten in the same `UPDATE` from `tzOffsetMinutes` when sent, else `offsetMinutesForZone(startedAt, user.timezone)`; they never change otherwise (05.0 AC6 amended). A start at 23:30 local (UTC−5, 04:30Z next day) lands on the local day, and a DST-transition day uses the offset in force at that instant.
25. **Set times move with a finished workout.** When a finished workout's start changes by Δ, every non-null `set_entry.completed_at` of the workout shifts by Δ (gaps preserved, `NULL` stays `NULL`); after any finished-mode time change, and at every finish, every non-null `completed_at` lies within `[started_at, ended_at]` (out-of-span values are clamped). A live workout's Change Time never shifts or clamps sets.
26. **Records follow a re-time.** After a finished workout's `startedAt` changes, all its lineage roots are recomputed in the same transaction: `achieved_at` and `local_date` of rows it holds are the new ones, a workout moved earlier can take a record from a later one (and the later one loses it, `previous_value` restated), and the table equals `records:rebuild`. A duration-only change recomputes nothing (records do not depend on `ended_at`) but still takes the PR lock first (AC4).
27. **History, Progress and the cursor follow.** After a re-time the workout appears at its new place in `GET /v1/workouts` (order `started_at DESC, id DESC`), with the new `localDate`; its progress-series point has the new `localDate` / `startedAt`. A cursor issued before the edit still decodes and pages without `422`/`500`; pages remain strictly ordered, and a page sequence started after the edit contains the workout exactly once.
28. **Overlap allowed; one-active rule untouched.** Change Time to a span overlapping another workout (live or finished) succeeds. Editing or re-timing a finished workout while another workout is live succeeds, and neither affects the `workout_user_active_key` index. A live workout can be re-timed while finished workouts exist.
29. **PATCH is idempotent.** Repeating an identical Change Time request returns `200` and leaves the data as after the first (the shift is computed from the stored start, so Δ is 0 the second time).
30. **Export.** `GET /v1/account/export` includes `plannedDurationSeconds` on each workout (hand-written workout statement updated) and the edited sets/times as stored; the existing export and purge tests pass; no new table, so the purge discovery test needs no change.

### Cross-cutting

31. **Contract.** No new route or method; `CORS_METHODS` unchanged; every changed write route keeps its `writeGroup`; the published problem lists are updated (`workout-would-be-empty` on both `DELETE`s; `workout-finished` removed from the set and exercise routes, kept on `PATCH /v1/workouts/{id}`); the OpenAPI drift check is green and `/v1` responses keep `no-store`.
32. **Observability.** `workout_edited`, `workout_retimed` and `workout_edit_refused` are emitted as §9 specifies; `workout_finished` gains `had_planned_duration`; no line, and no `422` detail, contains a `title`, `notes` or measure value.
33. **Performance.** A finished-mode set write (set edit + lineage recompute) on the 07.0 AC27 fixture scaled to ~2 years stays within the DESIGN §1.3 400 ms p99 (`bench:finish` gains an edit scenario; dev tool, result recorded in §12).
34. **Docs.** Every edit in §11 "Doc edits" is applied. *(Review.)*

ALTER TABLE "workout" ADD COLUMN "planned_duration_s" INTEGER;
ALTER TABLE "workout" ADD CONSTRAINT "workout_planned_duration_range"
  CHECK ("planned_duration_s" IS NULL OR ("planned_duration_s" >= 0 AND "planned_duration_s" <= 86400));
-- Only a live workout carries a plan; finishing clears it in the same UPDATE (§6.5).

## 5. API surface

All under `/v1`, existing auth, `404`-not-`403`, `problem+json`. No new path or method.

### 5.1 `PATCH /v1/workouts/{id}` (extended)

Body (`strictObject`, all optional):

| Key | Type | Live workout | Finished workout |
|---|---|---|---|
| `title`, `notes` | string \| null | as today | as today (was `409`) |
| `endedAt` | ISO \| null | non-null = finish; `null` = no-op | non-null = `409 workout-finished`; `null` = no-op |
| `startedAt` | ISO datetime | move the start (AC20, 23) | move the workout: end follows, duration kept unless `durationSeconds` is also sent (AC22) |
| `tzOffsetMinutes` | int −720…840 | only with `startedAt`, else `422` | same |
| `durationSeconds` | int 0…86 400 \| null | store the plan; `null` clears | set `ended_at = started_at + n`; `null` = `422` |

Cross-key rules: non-null `endedAt` with `durationSeconds` → `422` (they are alternatives). A body with `startedAt` **and** a non-null `endedAt` on a live workout is allowed (move then finish; the end is validated against the new start).

Response `200`: `UpdatedWorkout` = `Workout` (+ `plannedDurationSeconds`) + `newRecords` (`[]` except on a finish). Errors: `404`, `409 workout-finished` (re-finish only), `409 incomplete-working-sets` (finish only, unchanged), `422 validation-error` with `errors[].path` ∈ `startedAt | endedAt | durationSeconds | tzOffsetMinutes` and **static messages** (CLAUDE.md #57): "must not be more than 5 minutes in the future", "must not be before 2000-01-01", "would end in the future", "must not be before startedAt", "requires startedAt", "cannot be combined with endedAt", "not allowed on a finished workout".

## 6. Behavior & logic

### 6.1 Write modes (Phase A)

`finished ⇔ ended_at IS NOT NULL`, and a workout never becomes live again (no un-finish; D17), so the mode is monotonic: live → finished at most once. Every affected repository method (`createSet`, `updateSet`, `deleteSet`, `addWorkoutExercise`, `updateWorkoutExercise`, `deleteWorkoutExercise`, `updateWorkout`) already starts with a plain, unlocked ownership read that returns `ended_at` (05.0 §6.6 phase 1, 05.1 §6.2). That value is the **preflight mode**. A shared helper (`withWriteMode`) then:

1. **Finished mode:** open the transaction; first statement `lockUserRecords`; then the method's existing statements (per-parent advisory lock → `workout … FOR SHARE` → child row locks), **without** the `ended_at !== null → WorkoutFinishedError` throw; then the operation-specific tail of §6.2.
2. **Live mode:** exactly today's statements. If the in-transaction re-check (the existing `FOR SHARE` read of `ended_at`) finds the workout finished, throw an internal `WriteModeChanged` signal; the helper rolls back (releasing everything) and re-runs the request **once** in finished mode. A second flip is impossible (monotonic), and a vanished row is `404`.

Why preflight + restart rather than "always take the PR lock": the live set write is the hot path (anti-goal: don't slow live logging); the lock costs nothing uncontended but would put every live write into the PR lock graph that 07.0 AC18 had to debug. The restart occurs only when a finish lands inside a write's few-millisecond window.

**Lock order is unchanged in spirit and now explicit:** PR lock → per-parent advisory lock (`hashtext(workout_exercise_id)` for sets, `hashtext(workout_id)` for exercise structure) → workout row → child rows. In finished mode every write of a user is serialized by the PR lock, so the inner locks are uncontended among finished-mode transactions and need no change. The 07.0 statement "set creates and other non-PR writers never take the PR lock" is amended to "live-mode writes never take it".

### 6.2 Per-operation tail (finished mode)

| Operation | After the write, in the same transaction | Recompute roots (AC6–8) |
|---|---|---|
| Set create | integrity (AC9) before the insert; `completed_at` per AC13 | the exercise's root, iff `setChangeAffectsRecords(none, new)` |
| Set patch | merge, integrity, `completed_at` | the root, iff `setChangeAffectsRecords(old, new)` |
| Set delete | last-set guard (§6.3) before the `DELETE` | the root, iff the deleted set was `working` |
| Exercise add | none | none |
| Exercise patch | none | if `position` changed: the roots occurring more than once in this workout; else none |
| Exercise delete | last-set guard before the `DELETE`; the cascade removes its sets and `workout_planned_set` rows | its root, iff it had a `working` set |
| Workout PATCH (title/notes) | none | none |
| Workout PATCH (Change Time) | §6.5 | all roots of the workout iff `startedAt` changed |

`setChangeAffectsRecords(before, after)` (pure, `@sin/core`): false when neither side is `setType = 'working'`; otherwise true when the set is created or deleted, or any of `setType`, `reps`, `weightKg` (milli-units) differs. Records ignore `is_complete`, `rpe`, `distance`, `durationS` (07.0 D5), so those edits are inert. Roots come from `rootsForWorkout` (whole workout) or a one-exercise variant (`COALESCE(forked_from_exercise_id, id)` of the `workout_exercise`'s exercise). The recompute is `recomputeRecordsForRoots`, unmodified; PR math stays in `records.ts`.

### 6.3 The last-set guard

Inside the finished-mode transaction, after the row lock and before the `DELETE`: `n = count(set_entry)` over the workout (any set type, one statement) and `removed` = 1 for a set, or the exercise's own set count. If `n ≥ 1 && n − removed = 0` → `WorkoutWouldBeEmptyError` (rolls back, no recompute, logs `workout_edit_refused`). "Any set type" matches Finish's enabling rule (17.1: Finish counts every set); a workout of only warm-ups stays valid. The rule fires only on these two deletes — the only edits that can reduce the count — and only from ≥1 to 0, so a legacy finished workout that already has zero sets (an API-only finish) is neither blocked from other edits nor made worse. Because every finished-mode write of the user holds the PR lock, two devices cannot both pass the check (AC11); no new advisory key is introduced.

### 6.4 Change Time: the pure retime function

`resolveRetime(current: { startedAt, endedAt | null, plannedDurationS | null }, patch: { startedAt?, durationSeconds?, endedAt? }, now) → { startedAt, endedAt | null, plannedDurationS | null, startChanged, endChanged }` or a field error. Rules, in order:

1. `startedAt` given and **different** from `current.startedAt` → bound check: `≤ now + 5 min` and `≥ 2000-01-01T00:00:00Z` (AC23). Equal → ignored.
2. Live: `plannedDurationS' = patch.durationSeconds` if the key is present (null clears), else the stored value. If a plan exists after the patch: `startedAt' + plan ≤ now + 5 min`, else `422` (`durationSeconds`, or `startedAt` when only the start moved).
3. Finished: `duration = patch.durationSeconds ?? (current.endedAt − current.startedAt)`; `endedAt' = startedAt' + duration`; `endedAt' ≤ now + 5 min`. `durationSeconds: null` → `422`.
4. A non-null `endedAt` (live finish): existing rules (`≥ startedAt'`, `≤ now + 5 min`); the plan is cleared.

`resolveRetime` is DB-free and unit-tested with an injected clock (the 05.0 `workout-writes.ts` pattern); the repository applies its output.

### 6.5 Change Time: the transaction

```
PATCH (startedAt / durationSeconds)
  preflight read -> mode
  finished: BEGIN; lockUserRecords            -- AC4 (every finished-mode write)
  live:     BEGIN                             -- no PR lock (a flip -> restart, §6.1)
  SELECT ... FROM workout WHERE id AND user_id FOR UPDATE   -- row lock, first data statement in live mode
  resolveRetime(...)                         -- 422s roll back
  tz   = patch.tzOffsetMinutes ?? offsetMinutesForZone(startedAt', user.timezone)   -- only if startedAt changed
  UPDATE workout SET started_at, ended_at, local_date = localDateFor(startedAt', tz),
         tz_offset_minutes = tz, planned_duration_s, title, notes, updated_at = now()
  finished & start changed:  UPDATE set_entry SET completed_at = completed_at + (started_at' - started_at_old)   -- AC25
  finished & (start or end changed) | finish:  clamp completed_at into [started_at', ended_at']
  finished & start changed:  recomputeRecordsForRoots(rootsForWorkout(id))                                      -- AC26
  COMMIT
```

A finish (live → finished) keeps today's order (`lockUserRecords` first when `endedAt` is non-null, row lock, integrity check, `UPDATE` — which now also sets `planned_duration_s = NULL` — then the clamp, then the recompute). The clamp is an `UPDATE … WHERE completed_at < started_at OR completed_at > ended_at`, which matches no rows for a normal workout.

**`tz` and `local_date`.** `local_date` is derived exactly when `startedAt` changes, in the same `UPDATE`, from the client's offset when sent (the UI spec should send the device offset *at the new instant*, so a DST difference between today and the workout day is honored) else the profile zone at that instant — the same rule as `POST` (05.0 §6.3). `tzOffsetMinutes` is never accepted without `startedAt`.

**Why Δ is computed from stored values.** The shift uses `new started_at − old started_at` read under the row lock, so a replayed identical request has Δ = 0 (AC29), and two devices sending different starts end consistently with the last one.

### 6.6 `completed_at` rules (decision summary, brief §5)

| Case | Rule |
|---|---|
| Live set write | unchanged: `now()` on the false→true transition |
| Live Change Time | sets untouched (they were logged at their real time; only the start was wrong) |
| Finish | clamp any out-of-span `completed_at` into `[started_at, ended_at]` (covers a forgotten workout whose sets were logged "today" against a start/took of yesterday, and a start moved later than an early set) |
| Finished set create / false→true | `LEAST(GREATEST(now(), started_at), ended_at)` |
| Finished start change | shift by Δ, then clamp |
| Finished duration-only change | no shift; clamp (a shrinking duration collapses later sets onto the new end; lengthening does not restore them — accepted) |

`created_at` / `updated_at` of sets are real write times and are never rewritten. Nothing reads `completed_at` for ordering (sets order by `set_number`).

### 6.7 Records, History, Progress

- **Chronology** is `started_at` (07.0), so a re-time is a records event; a duration-only change is not.
- **History** (07.1) orders by `(started_at, id)`; the cursor is a position, not a row reference, so it stays valid when a row moves: a workout moved across the boundary of an in-flight paging session can be skipped or shown twice **in that session** (the same property as a concurrent finish or delete, Q14); the client restarts the list after an edit. 07.1 D12's "finished workouts are immutable, so the only race is a delete" is amended to "a delete or an edit"; the two statements may disagree on one row for one fetch (counts vs volume), healed by the next fetch.
- **Progress** (07.2) reads `local_date` / `started_at` of the workout at request time; nothing is stored there.
- **`newRecords`** stays a finish-only field; finished-mode edits return no records.

### 6.8 Concurrency and idempotency (summary)

- **Two devices, one finished workout:** serialized by the PR lock; per-row last-write-wins as in DESIGN §4.4; `updatedAt` on the returned row lets a client notice. A stale device deleting an already-deleted set gets `404`, a stale `PATCH` of a deleted set gets `404`.
- **Edit while another workout is live:** nothing in finished mode touches `workout_user_active_key`; the live workout's writes take no PR lock and so never wait on an edit's recompute.
- **Retries:** set create is keyed (`clientGeneratedId`, replay → `200`, AC14); `PATCH`es are idempotent (AC29); `DELETE` repeats are `404` (the client treats `404` on delete as done).
- **Edit vs delete of the same workout:** both take the PR lock first; the loser sees `404`.

### 6.9 Snapshots (09 / 09.1 / 09.2)

No route writes `workout_planned_set`, `workout_section`, `routine_notes_snapshot` or `section_id`; edits never touch them. Deleting an exercise cascades its `workout_planned_set` rows (the plan existed only for that card); a section left without exercises stays (empty sections are legal, 09.2). An exercise added to a finished workout is loose with no plan, appended at the end or at the requested position; reorders ignore section boundaries and consumers already tolerate that (09.2). `routineName` is unchanged.

## 7. Security & privacy

- **Authorization boundary unchanged:** ownership resolved through the join to `workout.user_id`, `404` not `403`, malformed id `404` (AC16). Finished-mode code paths receive `actingUserId` like every other.
- **What is newly writable:** the user's own historical rows only. No cross-user path is added.
- **Abuse / cost:** each finished-mode set write runs a lineage recompute under a per-user lock. It is bounded by the existing `sets` (120/min) and `workouts` (60/min) groups and the in-flight cap of 4; a user who inflates their own history slows only their own writes (the lock is per user), and AC33 bounds the single-request cost at 07.0's budget. No new limit is added; if the benchmark fails, tighten the `sets` group for finished mode before shipping.
- **Input bounds:** start bound (≤ now + 5 min, ≥ 2000-01-01 UTC) stops absurd dates; `durationSeconds` ≤ 86 400 and the DB CHECKs stop absurd spans; `tzOffsetMinutes` keeps its range.
- **Data integrity as a security property:** the finished-mode integrity rule (AC9) keeps a half-filled set from entering the PR engine; the empty-workout guard prevents a state the UI cannot display sensibly.
- **PII / logging:** no new PII; no `title`, `notes` or measure in any log or `422` detail (static messages, CLAUDE.md #57).

## 11. Deployment & rollback

**Phase A** ships as an ordinary merge to `main`: no migration, no env change, no release step. **Phase B** ships migration `0012` as a **manual release step before the code goes live** (`DATABASE_URL=… pnpm run db:migrate:deploy`, runbook B4), because the new reads select the column (the `0009`–`0011` pattern); then the merge. After either phase: `records:rebuild` is **not** required (the cache is maintained in-transaction); as a spot check, `records:rebuild --user <id>` for a staging account after a few edits must be a no-op.

**Rollout order (DESIGN §6):** `plannedDurationSeconds` is a new response field, so Phase B ships to the API one release before any client that reads it, and rolling the API back past it rolls the client back. Phase A adds no response field; the UI may follow it once deployed and verified.

**Rollback:** Phase A — revert; set/exercise writes on finished workouts answer `409` again; data already edited stays consistent (records were recomputed in each transaction). Phase B — revert the code; the column stays (expand-only); old code ignores it, and a live workout's stored plan is simply never used. Never roll a migration back in production.

## 12. Decisions & open questions

- ✅ **D1 — Reuse the existing write routes on finished workouts; add no edit routes.** *Rationale:* the brief wants "the same screen as logging"; the web already has the set/exercise mutations, the DTOs and their error handling, and a parallel `/edit/...` family would duplicate validation, OpenAPI and the client. The only real difference between live and finished is the transaction's lock/recompute envelope, which belongs in one repository helper (`withWriteMode`), not in the route surface. A mode-specific behavior is visible in exactly two places (error tables in §5.2). *Rejected:* dedicated `/workouts/{id}/edits` routes (duplication; a second contract to keep in sync); a bulk "replace the whole finished workout" `PUT` (conflicts with "each change saves as you make it", brief §4.2, and loses per-row last-write-wins). *Cost:* a queued live op from a second device now lands on a finished workout instead of `409`; accepted and arguably better (no lost set), and flagged for the UI spec (§3).
- ✅ **D2 — Uniform finished-mode envelope: PR lock first on every finished-mode write; mode preflighted without a lock and re-checked under the row lock, restart once on a flip.** *Rationale:* 07.0's AC18 deadlock rule is "PR lock before any workout row lock", and whether a workout is finished is only known after reading it; since finished is monotonic, an unlocked preflight is safe and the rare flip is a bounded restart. Taking the lock on *all* finished-mode writes (even title/notes) makes the rule testable as one statement-order assertion and removes any reasoning about `FOR UPDATE` versus the recompute's FK `KEY SHARE` locks. *Rejected:* taking the PR lock on every write including live (puts the hot path into the PR graph); taking it only when a recompute will run (per-operation reasoning, easy to get wrong).
- ✅ **D3 — Recompute per edit kind, decided by a pure `@sin/core` predicate and the §6.2 table, inside the edit's transaction.** *Rationale:* records depend on exactly `(set_type = working, reps, weight_kg, lineage root, started_at, workout id, exercise position, set_number)`; recomputing only when one of those can change avoids the O(history) cost on rpe/notes/superset edits while the recompute itself stays the single shared function (Q13), so "rebuild equals live" holds by construction (AC6 proves it). Reorder recomputes only duplicated roots because position is the only tie-break input it changes. A start change recomputes all roots because `achieved_at`, `local_date`, chronology and every `previous_value` depend on it; a duration change does not (records never read `ended_at`).
- ✅ **D4 — The empty-workout guard is `409 workout-would-be-empty`, counts every set type, fires only on the two deletes, and is serialized by the PR lock.** *Rationale:* it is a state conflict (the same request succeeds if another set exists), so `409` like `workout-finished`, with a distinct slug so the client can offer "Delete this whole workout instead?" without parsing text; no ids in the body. Any set type matches Finish's enabling rule. Reusing the PR lock avoids a new advisory-lock key (CLAUDE.md: never reuse a key across caps). *Rejected:* `422` (it is not a field error); `403`; auto-deleting the workout on the last delete (a destructive side effect the lifter did not confirm).
- ✅ **D5 — Change Time rides on `PATCH /v1/workouts/{id}`** with `startedAt`, `tzOffsetMinutes` and `durationSeconds`, validated on the merged result by one pure `resolveRetime`. *Rationale:* the brief's lifter enters start + duration, so the API takes start + duration, not an end (an end would force the client to compute and would let it send an end before the start); one function serves live and finished; `PATCH` is already CORS-listed and rate-grouped. `endedAt` stays the finish verb. *Rejected:* a `POST /workouts/{id}/retime` verb route (a new route for a field edit); letting `endedAt` be edited on a finished workout (the brief's UI never asks for it, and it would make "finish" and "edit end" the same field with two meanings).
- ✅ **D6 — "Took" on a live workout is stored server-side (`planned_duration_s`), and the client sends the resulting `endedAt` at Finish.** *Rationale:* stored, it survives a reload, a closed tab and a second device, needs no new `localStorage` key (and so no `USER_DATA_KEY_PREFIXES` / logout handling), and is visible to the export; the finish request keeps its one meaning ("here is the end"), so the existing validation, the `409` recovery path and Spec 17.2's finish dialog (which shows the duration before the lifter confirms) all keep working. *Rejected:* client-only state (lost on reload/another device — the "wrong duration" anti-goal); the server substituting `start + took` for the client's `endedAt` (a request that is silently overridden is a worse contract, and needs a second finish form to be explicit). *Known edge:* a stale second device that finishes with its own "now" ignores the plan; its dialog shows that duration first, so it is visible, not silent.
- ✅ **D7 — A *changed* start has a fixed floor, 2000-01-01 UTC, and no rolling past window; `POST` keeps 7 days.** *Rationale (owner, 2026-10-18):* the 7-day bound on `POST` guards a stale device clock for a live start. A Change Time start is typed by the lifter, and a rolling window (366 days was drafted) would only guard a mistyped year while blocking real fixes to workouts more than a year old and, later, imported history (#87). A mistyped date is visible at once on the summary and in History and is fixed with Change Time again. The fixed floor still rejects nonsense (a zeroed or broken clock value) that would stretch Progress's "All" range and invite overflow reasoning. The bound applies only when the value *changes*, so echoing a stored start never trips it. *Rejected:* keeping 7 (blocks fixing anything older than a week); a 366-day window (O1, declined by the owner); no bound at all (accepts garbage dates). The floor is one constant.
- ✅ **D8 — `local_date` and `tz_offset_minutes` are re-derived exactly when `startedAt` changes, in the same `UPDATE`, from the client offset when sent, else the profile zone at that instant.** *Rationale:* 05.0's "derived once, never re-derived" protected against drift on reads and unrelated edits; a start change is the one event where the calendar day is supposed to move. The same offset-source rule as `POST` keeps the day equal to what the lifter typed, and a client offset computed for the *workout's* instant handles DST between today and then.
- ✅ **D9 — Set `completed_at`: shift on a finished start change, clamp into `[started_at, ended_at]`, live Change Time never shifts, finished creates use `LEAST(GREATEST(now(), started), ended)`, Finish normalizes.** *Rationale:* brief §5 settles "move with the workout" for a finished re-time. The live case differs: when an app was opened late, the sets were logged at their real time and only the start was wrong, so shifting them would be false; the Finish clamp then guarantees the §4.4 invariant (no set completes outside its workout) for the forgotten-workout flow, where the lifter logs from memory *today* against a start/took of *yesterday* and the sets must not read as completed after the end. A clamp rather than synthesized spacing: we cannot know the real gaps for logged-from-memory sets; identical timestamps are harmless because nothing orders by `completed_at`. *Rejected:* shifting on a live move; leaving sets at `now()` (violates §4.4 in the export).
- ✅ **D10 — Overlapping workouts are allowed** (brief §5). Nothing in Change Time reads other workouts; the one-active index only concerns `ended_at IS NULL`, which finished edits never change.
- ✅ **D11 — Concurrency:** finished-mode writes of one user serialize on the PR lock; across devices last-write-wins per row (DESIGN §4.4); set create replay stays keyed and answers before any lock; `PATCH` is idempotent by construction (Δ from stored values); `DELETE` repeat is `404`. Editing a finished workout while another is live is unrestricted.
- ✅ **D12 — Finished-workout edits and Change Time are online-only, not outboxed.** *Rationale vs "never lose an edit silently":* the outbox exists to protect a set tapped mid-workout with bad gym signal. A finished edit is deliberate, usually made on any connection, and its outcome depends on the server in ways a queue would hide: the empty-workout guard can refuse a queued delete after the screen already showed it gone, a record may change as a result, and a Change Time can fail its bound checks. A failed online write is *visibly* failed (the row shows the error and does not change), so nothing looks saved that is not; a deferred rejection is exactly the silent loss the brief forbids. Routines took the same route (Spec 10.0). The API makes this safe: every request is retryable (D11), so the UI may auto-retry a timeout. *Rejected:* reusing the outbox for finished edits (needs a finished-detail projection, a deferred-409 path for the guard, and stale records meanwhile).
- ✅ **D13 — Finished mode enforces the finish integrity rule as `422` on the set write.** A working set without its required measures would enter the PR engine as a null-measure row; Finish refuses that with `409 incomplete-working-sets`, but on a single set write the problem is a field problem, so `422` with field paths and a static message. Live half-filled rows stay allowed.
- ✅ **D14 — Plans, sections and routine notes are not editable** (no route exists; D-by-omission from 09 / 09.1 / 09.2); an exercise delete cascades its plan rows; an added exercise is loose.
- ✅ **D15 — Analytics are three log events plus one field** (§9), following the 05.0 ids-and-enums convention, one `edit` enum rather than an event per route, and an `edit_refused` event so the product can see the guard's hit rate.
- ✅ **D16 — Numbering: 07.4, not 05.3.** *Rationale:* the suggested 05.3 would sit before 06.0 in the README's dependency-ordered table while depending on 07.0 (PR engine) and 07.1 (history order), which come later; 07.x already holds the derived-data family this spec must keep correct (records, history, progress), and the README's dependency order and numeric order then agree. The 05.0 / 05.1 amendments are called out in §11 instead. Easy to rename if the owner prefers the lifecycle family.
- ✅ **D17 — `endedAt` on a finished workout stays `409 workout-finished`; `PATCH {}` and `{ endedAt: null }` become `200` no-ops.** The Finish "recovery path" (Q16) reads that `409` to learn its own first finish landed; there is no un-finish.
