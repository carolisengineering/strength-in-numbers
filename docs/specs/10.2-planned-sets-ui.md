## 1. Purpose, scope & non-goals

The routine editor learns a **weight** and a per-set plan; a workout started from a routine shows **where the lifter is** ("Set 3 of 4") and **arrives with the next set filled in**, so logging a planned set is one tap. Everything the screens need is already on the wire after Spec 09.1; **this spec changes no API, no migration and no server behavior.**

**This spec reverses both halves of Spec 10.1 decision D3** ("no set prefill from targets, no '2 of 4 sets' count") — see D1 for how and why that is safe.

> **First-principles note — "draft, not a server row".** The set-entry form on an exercise card is *local UI state* (a `useReducer` draft of strings, Spec 06.1 D13). Nothing exists on the server until the lifter taps "Log set". That is why prefilling is safe: Spec 10.1 worried that a prefilled set might be mistaken for a logged one (and what it would mean for the "every working set must be complete" finish rule). A prefilled draft is neither — it cannot be counted in volume, cannot become a record, cannot block Finish — until a tap turns it into a real set.

> **First-principles note — "pure reducer".** The editor's draft lives in a plain function `reduce(state, action) → state` with no React in it (Spec 10.0 D7); components only dispatch actions and render state. That is what lets this spec add "Plan each set" rows, reorder and collapse as table-driven unit tests rather than UI tests, and keeps the client-only `key`s that identify rows out of anything the server sees.

### In scope

- **Editor (routines):** a Weight field and kg / lb toggle in the item sheet's quick line; "Plan each set" (one editable row per set: type, reps, weight; add, remove, move up / down); "Back to the quick line" when lossless; the weight in the row summary line.
- **Session (workouts):** the entry-row draft is prefilled from the next planned set; the label "Set k of N" (plus the type when not working) and "Extra set"; the active card's target line gains the weight.
- Draft / validation / fakes changes in `routineDraft.ts`, `validateDraft.ts`, `targetFormat.ts`, `exerciseLookup.ts`, `setDraft.ts`, `EntryRow.tsx`, `supersetRows.ts`, and the web test fakes.
- A manual phone check.

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|
| Planned duration / distance for timed and distance exercises | FI-11 (their rows are "N sets" with a type only) |
| Per-set RPE (the prefill leaves RPE blank); automatic progression | Not planned |
| Editing the plan from inside a session (the snapshot is read-only) | Not planned (09.1) |
| Matching logged sets to planned rows by type or value | Rejected (D2) |
| A planned-versus-logged comparison on the finished-workout screen or History | D8 |
| Drag-and-drop reordering of rows | Move up / Move down, as 10.0 D3 |
| Persisting entry-row drafts across reloads (including a prefill) | Spec 06.5 |
| Offline editing of routines | Online-only, as 10.0 D5 |
| Any API / migration / release step | None |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.2 ACn — …"`** (the 08.x / 10.x convention). Levels are in §10. **Phase A** (AC1–AC9): pure editor layer. **Phase B** (AC10–AC19): editor screens. **Phase C** (AC20–AC31): session. **Phase D** (AC32–AC37): cross-cutting, verification, docs.

### Phase A — pure code: formatting, draft, validation

1. **Weight parsing.** `parseWeight(text)` (`targetFormat.ts`): blank → `null`; a decimal with `.` or `,` and up to **3** decimals, `0 … SET_WEIGHT_MAX` (from `@sin/core`, not a literal) → the number; negative, more than 3 decimals, non-numeric, or above the maximum → a static message (never echoing the input). Its accept / reject set equals `PlannedSetInputSchema.shape.weight`'s for every tested value (a parity table). `formatWeight(62.5) → "62.5"`, `formatWeight(100) → "100"`.
2. **Weight summary.** `plannedWeightText(rows)` (`targetFormat.ts`, pure) considers only rows with a non-null `weight`: none → `""`; all with the same weight **and** unit → `"@ 100 kg"`; all in one unit with different weights → `"@ 60–100 kg"` (lowest–highest, en dash); rows in more than one unit → `""` (never a converted or mixed figure). Rows without a weight (a bodyweight or weightless warm-up row) are ignored, and warm-up rows count.
3. **`targetLine` with a plan.** `targetLine(t, sets?)` takes an optional second argument. With no second argument or an empty / weightless plan the output is **byte-identical to today** (the 10.0 / 10.1 `targetFormat` and card tests pass unmodified). With a plan the weight text follows the sets × reps part and precedes RPE and rest: `"4 × 6–8 @ 100 kg · RPE 8.5 · 2:00"`, `"3 sets @ 60–100 kg"`, `"8–10 reps @ 20 kg"`; weight text alone when there is neither a set count nor reps.
4. **Draft model and load.** A `DraftItem` gains `weight: number | null`, `weightUnit: "kg" | "lb" | null` and `plan: readonly DraftSet[] | null` (`DraftSet = { key, setType, repsLow, repsHigh, weight, weightUnit }`; row keys are client-only). `load` from a server `Routine` (D5): an item with ≥1 row for which `isUniformWorking(sets)` holds → **quick mode** (`plan: null`; `targetSets` = row count; reps and weight from the first row); any other item with rows (a ramp, a warm-up, mixed reps or units) → **plan mode** (`plan` = its rows); an item with no rows → quick mode with the item's own `targetSets` (null) and rep columns. Loading never marks the draft dirty (except the existing superset `adjusted` case).
5. **Plan actions (reducer).** `setPlanned` (additive, beside the unchanged `setTargets`) with the table-driven behaviors: **enter plan mode** from the quick line — `targetSets` rows copying the quick reps / weight / unit as `working` (blank sets → one row; D11); **add row** (appended; copies the last row's reps, weight and unit, type `working`; a no-op at 20 rows); **remove row** (a no-op at one row); **move row up / down** (a no-op at the edges); **set row field**; **set unit** — relabels *every* row (and the quick weight) to the chosen unit without converting values (D3); **collapse to the quick line** — only when `isUniformWorking(rows)`, else a no-op that leaves the state identical by reference; rows → `targetSets`, reps and weight of the first row. After every plan action the item's `targetSets` / `targetRepsLow` / `targetRepsHigh` equal `deriveTargets(rows)` (the reducer is the one place that keeps them in step, so `targetLine(item)` equals what the server will store). An action that changes nothing leaves the state identical by reference and `dirty` unchanged (10.0 AC1); the superset invariant of `settle` is unaffected by any plan action (a property test over random plan actions mixed with link / move actions).
6. **The request body.** `toRoutineInput(draft, { modalityOf })` emits **exactly one form per item** (Spec 09.1 AC7), and never `null` quick-line keys next to `sets`:
   - plan mode → `sets` = the rows;
   - quick mode with a set count → `sets` = `expandQuickLine(...)` rows plus the quick weight and unit on each when present;
   - quick mode without a set count → the legacy `targetRepsLow` / `targetRepsHigh` keys only (no `sets`, no `targetSets`; the O1 default), and a weight present without a set count is a validation error (AC7);
   - a `weightUnit` only ever travels with a `weight`; positions and row `key`s are never sent;
   - fields the exercise's modality cannot carry are **omitted** (D6): no `weight` / `weightUnit` for `bodyweight_reps`; rows of only `{ setType }` — no reps, no weight — for `duration` and `distance_duration`. An unknown modality (the catalog has not synced) omits nothing.
7. **Validation.** `validateDraft` runs `RoutineWriteSchema.safeParse(toRoutineInput(...))` plus `plannedSetViolations(modality, rows)` from `@sin/core` (the same function the API uses), and maps issues to the sheet: quick-mode paths (`items.i.sets.j.weight` / `weightUnit`) → the item's **Weight** field, (`…repsLow` / `repsHigh`) → **Reps**, (`items.i.sets`) → **Sets**; plan-mode paths → a **row** issue `{ itemKey, rowKey, field }`. Client-owned message: a weight with no set count → "Enter the number of sets to plan a weight". All messages come from a static table in the app's wording (never Zod's text) and never echo input. `ITEM_FIELDS` / `issueForPath` learn the new fields; the 10.0 `validateDraft` tests pass unmodified.
8. **Server errors map to the same places.** `routineErrors.ts` maps a `422` whose `errors[].path` is `items.<i>.sets.<j>.<field>` (or `items.<i>.sets`) to the same issue targets as AC7, using the saved draft's item and row keys; a `422` that names nothing on screen falls back to the existing form-level message. `409 exercise-retired` and `routine-name-taken` are unchanged.
9. **Exercise modality.** `exerciseLookup`'s `ExerciseInfo` gains `modality: Modality | null` (`null` when the catalog does not hold the exercise); existing fields and tests are unchanged.

### Phase B — routine editor screens

10. **Quick line gains Weight.** The item sheet shows **Weight** (a text input, `inputMode="decimal"`) and a **kg / lb** segmented toggle beside Sets and Reps, for `weight_reps` and `weighted_bodyweight` exercises. The toggle defaults to the profile's `unitPreference` (`useSession`) when the item has no stored unit and shows the stored unit otherwise. "4 × 6–8 @ 100 kg" typed in the quick line is what `toRoutineInput` expands into four identical working rows (AC6). Every 10.0 sheet behavior (sheet-local strings, **Done** parses everything, **Close** discards, invalid fields keep the sheet open with a message beside the field) is unchanged (10.0 AC28). Done on an untouched sheet — quick or plan mode — does not arm the leave guard (10.0 AC1).
11. **Fields gated by exercise.** For `bodyweight_reps` the Weight field and toggle are not shown; for `duration` and `distance_duration` neither Weight nor Reps is shown (Sets, RPE, Rest, Notes remain) and the plan rows show only the type. Which exercise an item is comes from the lookup (AC9); with an unknown modality all fields show.
12. **"Plan each set".** In quick mode the sheet always offers a **Plan each set** button. Activating it enters plan mode (AC5): the quick Sets / Reps / Weight inputs are replaced by a list of rows; **RPE, Rest, Notes** (item-level, Spec 09.1 D3) stay.
13. **Plan rows.** Each row is a labeled group "Set k": a **Type** select (Warm-up, Working, Drop, Failure — the 05.1 labels), **Reps** (one input, `8` or `8-10`, parsed by the existing `parseReps`), **Weight** (when the exercise allows), and Move up / Move down / Remove buttons. **Add set** appends a row (AC5) and is disabled with "Up to 20 sets" at 20; Remove is disabled on the only row; Move up / down are disabled (not hidden) at the edges. A single **kg / lb** toggle sits above the rows (AC5 / D3): with rows in different units neither segment is selected and a line says "Mixed units — pick one to use for all sets"; each row's weight is shown with its own unit as read-only text until then. Each button carries the tap-target class.
14. **Back to the quick line.** Plan mode shows **Back to the quick line** only when `isUniformWorking(rows)`; otherwise it is absent and a line says "Sets differ, so they can't be shown as one line". Taking it never changes what would be saved (the rows it produces expand back to the same rows). It is the only way out of plan mode besides Close.
15. **Row summary.** The editor row and the preview row show `targetLine(item, rows)` with the weight (a ramp reads "3 × 6–10 @ 60–100 kg"); the row's accessible name (`itemAccessibleName`) includes it. Items in quick mode with a weight show the same as plan mode with identical rows.
16. **Validation in the sheet.** **Done** in plan mode parses every row (`parseReps`, `parseWeight`); invalid rows show their message beside the field and keep the sheet open; nothing reaches the draft until all rows parse (10.0 D4). In quick mode a weight with a blank Sets field shows "Enter the number of sets to plan a weight". Client messages and server `422` messages (AC8) appear in the same places.
17. **Save round trip.** Saving a loaded routine after an edit elsewhere (Save is disabled when not dirty, 10.0) sends, for every untouched item, a body that the (fake) server stores as the same rows: a quick-mode item with a weight → N identical rows; a ramp → its rows; a rowless reps-only item → the legacy reps keys. A no-op sheet **Done** on any item changes nothing (a regression test over one routine containing every shape).
18. **Time-based and bodyweight data are cleaned, not lost silently.** Opening an item whose exercise cannot carry stored reps / weight (legacy data: reps on a plank) in the sheet shows only the fields the modality allows; on any Save those stored values are omitted from the body (AC6, D6), whether or not the sheet was opened. Opening the sheet starts the hidden fields blank, so **Done** on such an item is a real change (the item becomes dirty) and the clean-up is part of a deliberate save; no message is shown (the values were not displayed).
19. **Routine start is unchanged.** Starting a workout from the preview or Start screen sends exactly the same request as today (`useBeginWorkout`); the editor never writes a workout.

### Phase C — workout session screens

20. **The next planned set.** `nextPlanned(plannedSets, loggedCount)` (`features/workouts/plannedSets.ts`, pure): with `plannedSets.length = N > 0` and `loggedCount < N` → the row at index `loggedCount` ("set `loggedCount + 1` of N"); with `loggedCount ≥ N` → **extra**; with `N = 0` → **none**. `loggedCount` is the number of sets in the list the card renders — **all types, including queued and failed rows from the outbox projection** (06.2), so the index advances the instant a log is queued. Deleting a logged set steps the index back; the index never reads `setNumber`, which is append-only and not dense (DESIGN §4.4).
21. **The label.** `setLabel(...)` and the entry row: `"Set 3 of 4"` for a working planned set; `"Set 1 of 5 · Warm-up"` (the 05.1 label) when the row's type is not `working`; `"Extra set"` after the plan; and exactly today's `"Set {n + 1}"` when there is no plan. The label is a text node in the entry row's existing slot (no new landmark); the form's accessible name and the "Set N logged" announcement are unchanged.
22. **Seeding the draft.** `seedDraft({ plannedSets, sets, defaults, attemptKey })` (`setDraft.ts`, pure) is the one place a draft is built from the list. For a **planned** next set: start from today's copy-forward of the last logged set (or blank when none), then overlay the row — `setType` from the row, `reps` = `repsLow` (when not null), `weight` and the weight **unit** from the row (when `weight` is not null), RPE blank — so a field the plan leaves unspecified keeps today's copy-forward value (D4). For **extra** and **none**: exactly today's `draftFromSet` result (`setType: "working"`, RPE blank). Weight text uses `formatWeight`; nothing is "0" for a null.
23. **One-tap logging.** On a routine-started exercise with a plan whose next row has the measures its modality requires, the draft is valid on arrival: the **Log set** button is enabled and a single tap sends `POST …/sets` with the row's values, `isComplete: true`, the draft's `attemptKey` as `clientGeneratedId`, and the row's `setType`. A planned warm-up logs as `warmup` (it stays out of personal records and volume, which read `set_entry` only). A row that leaves a required measure blank (e.g. weight not planned) leaves the button disabled until the lifter types it, as an empty draft does today; the field is not marked invalid until touched (06.1 §5.4).
24. **After a log.** When a log succeeds and the lifter has not typed since the tap, the next draft is built by `seedDraft` for the new count: the next planned row, or — after the last planned row — "Extra set" with today's copy-forward of the set just logged. If the lifter *has* typed since the tap, their values are kept and only the attempt key is re-minted (the existing `editedSinceTap` behavior, unchanged) — the **label** still advances.
25. **Count changes not caused by this row's own log.** When the number of sets on the card changes by any other route (a delete from the edit sheet, a refetch after another device logged), an **untouched** draft (nothing typed since it was seeded) is re-seeded for the new count; a draft the lifter has edited keeps their values, and only the label follows the count. A refetch that does not change the count never changes the draft. (This replaces the brief's phrase "the existing `editedSinceTap` rule": that ref only guards the response of a log, and today no refetch rewrites the draft; the reconcile rule above is new.)
26. **An untouched prefill is not a set.** The prefill is created on mount / re-seed without any request, is **not** stored (no `localStorage` / `sessionStorage` key, no outbox op), is never counted by `findIncompleteWorkingSets` or the Finish rule, does not block Finish, and is not sent by anything except the lifter's Log tap. Navigating away and back re-seeds it from the list.
27. **No plan, no change.** A manually added exercise, a workout started before Spec 09.1 and a routine item without rows render **exactly today's entry row** (label `"Set {n + 1}"`, copy-forward draft) — a test compares the markup to the pre-change structure.
28. **Supersets and repeats.** Each card seeds from its own exercise's `plannedSets` and its own logged count, independent of its neighbors in a superset bracket; a routine that lists one exercise twice yields two cards with their own plans; Move up / Move down and regroup (10.1) never change a card's plan or progress.
29. **Card target line.** The active card's target line passes the exercise's `plannedSets` to `targetLine` (AC3): `"4 × 6–8 @ 100 kg · RPE 8"`; nothing extra for mixed units or no weights. Edge cases are the AC2 table.
30. **The finished workout shows the weight too (D8, owner ruling 2026-10-11).** `FinishedWorkoutScreen` at both routes (the summary after Finish and the History detail) renders the same target line as the active card, weight included (`supersetRows` has no option for it — both screens get the weight). The History **list** row is unchanged (it shows no target line). Neither screen shows a planned-versus-logged comparison. 10.1's finished-screen tests change only in their expected target-line text for items with planned weights; items without planned weights render exactly as before.
31. **Strict schemas stay strict.** The web adds no `.default([])` / `.catch` for `sets` or `plannedSets`; `workoutFake` and `routineFake` (the msw handlers) **always** emit them, the routine fake applying the same `expandQuickLine` / `deriveTargets` the API uses and the workout fake copying rows on start by position — so the editor and session tests exercise the same expansion rules as production.

### Phase D — cross-cutting and verification

32. **Boundaries and purity.** New pure code imports only `@sin/core` and sibling leaf modules; `workouts/ → routines/` imports stay exactly the three leaf modules of 10.1 AC28 (`targetFormat.ts`, `LinkToggle.tsx`, `SupersetBracket.tsx`) — `plannedWeightText` / `targetLine` live in `targetFormat.ts`, so no new cross-import appears (the 10.1 source scan passes unchanged). `core:purity` is untouched (this spec adds nothing to core).
33. **Observability and hygiene.** No new `track()` event or property (`set_logged`, `workout_started { fromRoutine }` are unchanged; no weight, rep count, type or label is sent); `reportError` unchanged; no planned value in any log or analytics argument (a spy test over the new paths).
34. **Accessibility and tokens (component level).** In `a11y.test.tsx` (`describe("10.2 AC34 — …")`): plan rows are a real list of labeled groups; every control has a visible label and a name that includes its set number ("Set 2 type", "Set 2 weight"); disabled controls are `disabled` with the reason in text (not tooltip-only); the unit toggle is a radio group / pressed-state buttons with a group label; the entry-row label is plain text. Every touched `*.module.css` uses `var(--…)` only and `assert:css-tokens` passes; a source scan of the files this spec adds finds no `style=`, `<style`, `dangerouslySetInnerHTML`. Pixel sizes, focus and the 320 px layout need a browser (AC36).
35. **No other behavior change; no backend change.** The existing `@sin/web` suites pass with edits limited to fixtures that gain `sets` / `plannedSets` and to the signature change of `toRoutineInput`; the Playwright smoke is unchanged; `git diff main --stat` shows **no** path under `apps/api/`, `packages/core/` (Spec 09.1 already added the helpers), `render.yaml`, `Dockerfile` or `.github/workflows/`.
36. **Manual phone check (owner, recorded in the PR description).** On a phone against staging (Spec 09.1 deployed): build a routine with a ramp and a warm-up and one quick-line item with a weight ("4 × 6–8 @ 100 kg"); reopen both and confirm the ramp stays a ramp and the uniform item collapses to the quick line; start it; confirm "Set 1 of N · Warm-up" arrives filled, **one tap logs it** and the next row arrives; log past the plan and see "Extra set" with the last set copied; delete a set and see the index step back; try it on a superset pair and on an exercise added by hand; **airplane mode** mid-plan (queued sets advance the count); check **320 px and 390 px** — the 20-row sheet scrolls, nothing overflows sideways, every control is reachable one-handed and ≥ 44 px; VoiceOver reads a row ("Set 2 weight"); finish and confirm History and the summary look as before.
37. **Docs stay consistent.** DESIGN.md, `docs/specs/README.md`, `docs/feature-ideas.md` and the Spec 10.1 amendment note carry the edits listed in §11; each of AC1–AC35 has ≥1 committed test tagged with its number; AC36 is verified by the PR description, AC37 by review.

### 5.4 Flow summary

- Editor: type the quick line → Done; or "Plan each set" → edit rows → Done → Save (whole `PUT`, one form per item).
- Session: arrive → draft filled with the next planned set → one tap logs it → the next row arrives; after the last row "Extra set"; deleting a set steps back; typing in the draft always wins over a re-seed.
- Finish → summary / History as today.

### 5.5 Error handling

Unchanged matrix (10.0 §5.6, 06.1 §5). New: a `422` on a plan row's field shows beside that row (AC8). No new failure mode exists on the session side — a prefilled draft that fails to log fails like any draft (06.1 §6.5, the attempt key is kept for the retry).

## 6. Behavior & logic

### 6.1 The editor draft (AC4–AC6)

| Server item (`sets`, columns) | Draft after `load` |
|---|---|
| ≥1 row, `isUniformWorking` | quick mode: `targetSets` = count, reps / weight / unit from row 0, `plan: null` |
| ≥1 row, otherwise | plan mode: `plan` = rows (keys minted), `targetSets` / reps = `deriveTargets(rows)` |
| no rows | quick mode: the item's own `targetSets` (null), reps columns, no weight |

Mode is a property of the item (`plan !== null`). `setTargets` keeps editing the five targets + notes; **`setPlanned`** carries `{ mode: "quick", weight, weightUnit }` or `{ mode: "rows", rows }` and every plan edit (add / remove / move / field / unit / collapse / enter) described in AC5. `settle` (superset normalization) is untouched and runs after every changing action as before. The unit-toggle semantics (D3): the toggle sets `weightUnit` on the quick weight and on every row; with mixed units loaded it shows neither segment selected.

### 6.2 Request building and validation (AC6–AC8)

`toRoutineInput` is the only place that decides the form. It needs the item's modality, so it takes `{ modalityOf: (exerciseId) => Modality | null }` (the editor passes the lookup; the tests pass a map). The parity guarantee is structural: the same `RoutineWriteSchema` and `plannedSetViolations` the API runs, so the sheet cannot accept a value the API would reject (10.0 AC9's promise, extended). The server stays the authority: an unknown modality is permissive on the client and a `422` from the API is mapped back to the row (AC8).

### 6.3 Weight text (AC1–AC3)

`plannedWeightText` ignores rows with no weight, requires one unit across the rest, formats with `formatWeight` (no trailing zeros, no thousands separator) and an en dash for a range. `targetLine(t, sets?)` inserts it as `" @ …"` after the sets × reps part (or in its place when only reps / only sets exist) and before RPE and rest. Called with one argument it is unchanged — which is how the finished screens and History keep 10.1's output (D8).

### 6.4 The session draft (AC20–AC25)

```
count   = exercise.sets.length                       // the rendered, outbox-projected list
planned = exercise.plannedSets
label   = setLabel(nextPlanned(planned, count), count)
draft   = seedDraft({ plannedSets: planned, sets: exercise.sets, defaults, attemptKey })
```

`seedDraft` = today's `draftFromSet(sets.at(-1) ?? null, …)` **then**, if `nextPlanned` is a planned row, the overlay of AC22. `createDraftReducer`'s `logged` / `reset` paths call it, so the mount, post-log and re-seed paths cannot differ. `EntryRow` keeps `seededFor` (the count it last seeded for) and an `edited` flag (set by any field change, cleared when a seed replaces the draft): when `exercise.sets.length !== seededFor` and the change was not this row's own post-log seeding, an unedited draft is re-seeded and an edited one is left alone (AC25). The `editedSinceTap` / `lastLoggedAt` double-tap logic is untouched. How the wiring is arranged (reducer action vs. render-time comparison) is an implementation choice under the AC24 / AC25 / 06.1 / 06.2 tests; re-seeding with the same inputs is idempotent apart from re-minting the attempt key, which is safe because an in-flight request already carries its own key.

*Implemented wiring:* `EntryRow` reconciles at render time — `seededFor` (the count the draft was last built for) and `untouched` (no edit since the last seed or log) are state; when `seededFor !== count` the draft re-seeds only if untouched, and the row's own log sets `seededFor` ahead of the prop so it never re-seeds itself.

### 6.5 Edge cases

- **Plan longer than the lifter wants** — they stop; the unlogged rows are just not used (nothing is stored). **Shorter** — "Extra set" with copy-forward, exactly today.
- **Failed queued set** — it stays in the list (06.2) and counts until discarded; discarding steps the index back and re-seeds an untouched draft (AC25).
- **A workout started from a routine whose plan is `[]` for an exercise** (a rowless item) — "no plan": today's behavior for that card while sibling cards have plans.
- **Time-based exercise** — "Set 2 of 3" with the type prefilled; duration inputs blank (copy-forward still fills minutes / seconds from the last logged set, as today).
- **Mixed units in a plan** — the draft takes the row's own unit; the card's target line shows no weight (AC2).
- **Bodyweight exercise** — the row has reps (and no weight); `seedDraft` never writes a weight the modality does not show.
- **Profile unit differs from a planned unit** — the plan wins for the prefilled set (the unit is part of the plan, DESIGN §4.8); later copy-forward follows the set just logged, as today.

### 6.6 Hand-offs

Spec 06.5 (persisted entry-row drafts) must treat a stored draft equal to what `seedDraft(...)` would now produce as *untouched* and not persist it (or must re-seed it on restore). Otherwise a prefill saved before a set was deleted or logged elsewhere would survive a reload and shadow the current plan position (AC25). Recorded here so 06.5 inherits the constraint.

## 7. Security & privacy

- **Authorization is the server's** (Spec 09.1 §7): the client adds no authority; every id goes to the API in the path as before.
- **User text** — routine and exercise names, notes — is rendered as React text and never reaches `track` / `reportError` (AC33). Planned weights and reps are training data: they appear only in the DOM and in the routine `PUT` / set `POST` bodies, never in analytics, logs or URLs.
- **Nothing new is stored in the browser** (AC26, §4). Logout clearing is unaffected.
- **Abuse:** bounded by the server (20 rows, `routines` write group); the sheet's own caps (AC13) mirror them for usability, not security.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-11, from the brief)

- ✅ **D1 — Prefill and "Set k of N" reverse both halves of Spec 10.1 D3 (brief decisions 1 and 4).** 10.1 D3 said "no set prefill from targets, no '2 of 4 sets' count", on the grounds that "prefill and progress counts are separate product decisions with their own edge cases (what does a prefilled set mean for the incomplete-set rule?)". This spec is that separate decision. **How it is reversed:** (a) *prefill* — the entry row's draft is seeded from the next planned set (AC22–AC24); (b) *count* — the entry row's label becomes "Set k of N" / "Extra set" (AC21); the edge cases 10.1 feared are answered by "the draft is not a server row": it is never stored, never counted by the finish rule, never a set until the lifter taps Log (AC26). 10.1's other content (target line on the card, notes, bracket, regroup) is untouched; it gets an amendment note pointing here. **Rationale:** in the gym the lifter wants the screen to say what to lift and when to stop; the owner chose "prefill, not display-only" and "progress on the draft row". **Rejected:** display-only planned values (a second tap-and-type per set); a combined planned-vs-logged list (a second UI for a problem the label solves).
- ✅ **D2 — The next planned set is chosen by position: the index is the number of sets currently on the card (all types, queued and failed included); no matching by type or value (brief).** Delete a logged set and the index steps back. **Rationale:** predictable and testable; matching would need rules for a lifter who logs a drop set where a working set was planned. The count is `exercise.sets.length`, never `setNumber` (append-only, so not dense after a delete). **Consequence:** a lifter who logs an extra warm-up consumes a planned row; the label shows it and the prefill can be overtyped.
- ✅ **D3 — One unit toggle per item; it relabels every row without converting; the profile preference is only the default (brief: "defaults to the profile").** With mixed units loaded (possible only from other clients, since the editor never creates them) neither segment is selected until the lifter picks one. **Rationale:** per-row unit controls on a 320 px phone are clutter for a case nobody creates, but silently relabeling mixed data would corrupt weights, hence the explicit mixed state. A plan's unit is data (DESIGN §4.8) and wins over the profile in the session. **Rejected:** per-row toggles; converting values on toggle (a lossy conversion of numbers the lifter typed).
- ✅ **D4 — A planned field left null falls back to today's copy-forward (found by reading the code; an extension of the brief's "holds that planned set's values").** **Rationale:** Spec 09.1's backfill and legacy expansion produce rows with reps and no weight; without the fallback, a routine from before this feature would regress — today the weight carries forward from the first logged set, but "Set 2 of 4" would blank it. The overlay changes nothing when a row is fully specified, and `setType` always comes from the row. **Rejected:** blanking unspecified fields (a regression for every existing routine).
- ✅ **D5 — Quick line first; plan mode is explicit; "back to the quick line" only when lossless (brief decision 3 and §4).** Load picks quick mode for uniform working rows and plan mode otherwise. **Rationale:** most items stay a ten-second entry, and nothing is ever silently lost: a ramp never collapses, and a quick-mode item saves as identical rows that load back as quick mode.
- ✅ **D6 — Fields a modality cannot carry are hidden in the sheet and omitted from the request (resolved with Spec 09.1 D5).** `bodyweight_reps` has no weight; `duration` and `distance_duration` plan only a type. **Rationale:** the API rejects them in the row form but tolerates them in the legacy form (so old clients keep working); the new editor therefore cleans what it re-saves instead of preserving meaningless values. The cost — a one-time silent drop of stored reps on a timed exercise the first time that item is saved from the new editor — is accepted: the values were never displayed in the new sheet, never used by the session and never meaningful for the modality (AC18 makes the save knowing, not accidental).
- ✅ **D7 — Re-seeding rule: an untouched draft follows the count, an edited one never changes (replaces the brief's "existing `editedSinceTap` rule" — corrected by reading `EntryRow`).** `editedSinceTap` only governs the response of a log; the draft is built once on mount and rebuilt only by `logged` / `rekey`, so a refetch cannot overwrite it today. The new need is the *delete* case (the index steps back) and another device logging, which require a reconcile rule; AC25 states it, §6.4 sketches the wiring. **Rationale:** typing always wins; an untouched draft is derived data and may be recomputed freely.
- ✅ **D8 — The weight appears on the target line everywhere it is shown: the active card, the finished screen (both routes, including the History detail) and the editor / preview rows (owner ruling 2026-10-11, replacing the draft's reading of "unchanged").** One `targetLine` / `supersetRows` path with no per-screen option. **Rationale:** the owner wants to see what was programmed when looking back at a workout; one rendering path means the two screens can never disagree. **Not included:** a planned-versus-logged comparison.
- ✅ **D9 — Validation reuses the core schema and `plannedSetViolations`; the server stays the authority (brief).** The sheet cannot accept a value the API would reject, except where the client lacks information (an unsynced catalog gives an unknown modality, treated permissively); a resulting `422` is mapped to the row (AC8). **Rationale:** one rule table (09.1 AC23) rather than a second copy in the web app.
- ✅ **D10 — No analytics change.** **Rationale:** the funnel question this feature raises ("do lifters follow plans?") needs Spec 13's stack; adding a property now would have no consumer. Nothing blocks adding `fromPlan` later.
- ✅ **D11 — "Plan each set" with a blank Sets field creates one row; the last row cannot be removed; there are never zero rows in plan mode.** **Rationale:** a plan with no rows is the quick line with nothing in it — "Back to the quick line" (always available for one row) is the way out, so a zero-row plan mode would be a state with no meaning.
- ✅ **D12 — Rows are reordered with Move up / Move down buttons, not drag-and-drop** (the 10.0 D3 / 06.1 D16 convention). **Rationale:** consistent with the rest of the app, accessible by default, no gesture library on a phone in a gym.

### Resolved by reading the code (corrections and qualifications to the brief)

- **`editedSinceTap` does not guard refetches** (D7); the brief's wording was imprecise. The behavior it wanted is delivered by AC25.
- **The editor does not know the profile unit or the exercise's modality today**: `ExerciseInfo` has `name` and `state` only (AC9 adds `modality`), and the routine screens do not read `useSession` (AC10 adds it for the default unit).
- **`toRoutineInput` sends all five quick-line keys, `null` when blank**, so the new emitter must drop the null keys when it sends `sets` (Spec 09.1 AC7 is key-presence based); its signature gains the `modalityOf` option (AC6).
- **`RoutineItemInputSchema.shape.targetSets` etc. are read by `targetFormat.ts`** (Spec 09.1 D13 keeps the schema a single object so that keeps working).
- **`supersetRows` is shared by the active and finished screens**, which is why the weight appears on both without an option (D8).
- **A rollback of this spec flattens plans** when routines are re-saved from the old editor (§11) — a consequence of the legacy form being accepted forever (Spec 09.1 D11).
