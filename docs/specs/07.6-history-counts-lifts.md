## 1. Purpose, scope & non-goals

**Purpose.** A History row says "6 PRs" next to a summary that says "New records on 3 lifts" (Spec 17.6 AC3). Both are true to their own rule and they disagree. Today `recordCount` is the number of `personal_record` rows the workout holds now, other than `best_set_volume` (Spec 07.3). That counts a first-ever number (Spec 17.6 D1: not brass, not counted) and it counts one lift twice when one heavy set beats both the weight and the estimate. This spec changes the count to: **the number of lifts that hold at least one beaten, non-volume record in that workout.**

> **First-principles note — "lift", "beaten" and "held now".** A *lift* is an exercise lineage root (`personal_record.exercise_id`; a fork and its origin are one lift, Spec 07.0 §6.2). A record is *beaten* when it replaced an earlier best: `previous_value` is not null (Spec 07.0 D16 makes that value the best over strictly earlier workouts, always below `value`). The first number ever logged has `previous_value = NULL` and beat nothing. *Held now* (D18) means the count reads the rows in the table today, so it changes when a later or backdated workout takes a record or when a past workout is edited or deleted. This spec changes none of that.

**In scope.**
- **Phase A (PR 1, API):** the `record_count` subquery in `listFinishedWorkouts`; the `recordCount` doc comment; the tests; the audit row.
- **Phase B (PR 2, web):** the History badge's wording and accessible name, and the web test helpers' count.

**Non-goals.**
- A new field or a rename (D5, O2).
- Any change to what records exist, how they are computed, stored or rebuilt (Spec 07.0, `@sin/core` `records.ts`).
- The finish response, `GET /v1/personal-records`, Progress and the summary (Spec 17.6).
- Any rounding on the server (AC5, D4).
- The account export (`recordCount` is not in it).

### Findings checked

| Finding | Verdict |
|---|---|
| `recordCount` counts every non-volume row, first records included, and one lift twice. | **Right.** The subquery in `workout-history.prisma.ts` is `SELECT count(*)::int FROM "personal_record" pr WHERE pr.workout_id = w.id AND pr.record_type <> ${HISTORY_COUNT_EXCLUDES}`. Nothing tests `previous_value` or groups by lift. |
| History says "6 PRs" beside "3 lifts". | **Right**, for a workout with three lifts that each beat weight and estimate; or three beaten lifts plus first records. |
| A rounded-zero est. 1RM gain could make the server's count disagree with the ledger. | **No, as long as 17.6 AC6 stands.** The web drops that row only while the lift has another beaten row, and "the lift still counts" when it is the only one. So a lift is counted by the ledger exactly when it has a beaten non-volume row, rounded or not. The server needs no rounding and no PR math (§6.3). The parity test (AC7) fails first if 17.6 ever changes that. |
| 17.2 AC32 (equal numbers) is gone. | **It holds again, in a new form.** 17.6 retired it because the summary counted lifts and History counted rows. Now both count lifts, so History's N equals the summary heading's N (AC7). |
| The change needs a schema change or a new field. | **No.** The field keeps its name and type; only its meaning narrows, as in 07.3 (§11). |

## 2. Acceptance criteria

Terms as in the first-principles note. "Non-volume" means `record_type <> 'best_set_volume'`, the `HISTORY_COUNT_EXCLUDES` constant (07.3). "Held" means the rows with `workout_id` = that workout today.

### Phase A — the count (API)

1. **Lifts, not rows.** `recordCount` for a finished workout is the number of distinct `exercise_id` values among the non-volume rows it holds whose `previous_value` is not null. It is `0` when there are none.
2. **A lift counts once.** A lift whose heaviest weight and est. 1RM are both beaten counts 1. A workout that logged a fork and its origin (one root) counts that lift once. Three lifts that each beat two records give `3`, not `6`.
3. **First records are not counted.** A workout whose only rows have `previous_value` null counts `0`. A lift with a beaten row and a first row counts 1 (its beaten row). A first-only lift beside a beaten lift adds nothing. This reverses Spec 07.3 D4 and Spec 17.2 D13 for the History count (owner, Spec 17.6 D1).
4. **Set volume is still excluded.** A workout whose only beaten row is `best_set_volume` counts `0` (07.3 AC2); a workout whose beaten volume sits beside a beaten weight counts the lift once.
5. **"Beaten" is the stored fact, with no rounding.** A row counts when `previous_value IS NOT NULL`, however small the difference. In particular a lift whose only beaten row is an est. 1RM that rounds to a zero gain on screen still counts 1, which is what Spec 17.6 AC6 shows. No `@sin/core` function is called, and no arithmetic or rounding on record values is added to the SQL.
6. **Held now, edited and deleted workouts.** After each of the following, `recordCount` equals the rule applied to what `GET /v1/personal-records?workoutId=` returns for that workout: a backdated finish that takes the record; deleting the earlier workout (a beaten row becomes a first row, so the count falls); a finished-mode set edit that raises a set above the old best (the count rises); lowering the holder so the next-best set takes the record; a re-time that moves the workout before or after another; a workout finished before Spec 07.0 with no rows (`0` until `records:rebuild`). The 07.1 AC14 scenario is updated to the new numbers.
7. **It equals the ledger.** For every fixture workout in a shared set, `recordCount` equals `liftsWithBeatenRecords(records)` computed over the same workout's `GET ?workoutId=` rows, and Spec 17.6's `buildRecordLedger` heading count equals the same function over the same rows. The fixtures include: weight and estimate beaten on one lift; a lone rounded-zero est. 1RM lift; a first-only lift; a mixed lift; volume only; a fork and its origin; seven lifts. `liftsWithBeatenRecords` is a pure, DTO-level function in `@sin/core` (D6); it does arithmetic on nothing.
8. **No shape change.** `WorkoutSummarySchema` parses the same fields; the DTO tests and both public-surface inventory tests pass unchanged. Only the `recordCount` doc comment changes.
9. **Paging is untouched.** Keyset order, cursors and the other columns of the statement are unchanged; the 07.1 suite passes with only the numbers in AC14 updated.
10. **Latency.** `bench:history` is re-run (its fixture is extended so that most workouts hold records with a non-null `previous_value`): first-page and deep-page p99 stay under DESIGN §1.3's 400 ms, and p50 stays within 10% of the figure 21.1 §12 records for the same bench through `sin_app`. No index is added.
11. **After Spec 21.1.** The subquery names the user (`pr.user_id = w.user_id`) as well as the workout, so the statement is `user-filtered` on its own; the audit row is regenerated with `audit:queries --write` and stays `user-filtered`. With RLS on and the request on `sin_app`, another user's records never change A's count (a case in the cross-user suite or the policy suite). The statement count of a History page does not change (still one statement for the page, 21.1 AC19's figure of 12 through the handle).
12. **A reps record counts like any other (Spec 07.5, when it has shipped).** A beaten `max_reps_at_weight` row counts its lift once; a first-time row at a new weight counts nothing; a lift that beat both a reps record and a weight record counts 1. Whichever of 07.5 and 07.6 ships second adds the test. (Guard its setup as well as the test body: `describe.skipIf` still runs `beforeAll`.)
13. **Docs consistent.** The cross-doc updates in §12 are made.
14. **Every behavioral AC has a tagged test.** AC1–AC9, AC11 and AC12 have ≥1 test named `07.6 ACn — …`.

### Phase B — the copy (web)

15. **The badge names lifts.** For `recordCount > 0` the row shows the trophy and the owner's chosen wording (D7: "PR on 3 lifts" / "PR on 1 lift", shortened to "3 lifts" / "1 lift" if it wraps at 320 px), in brass as today. With `recordCount === 0` there is no badge and the row is unchanged (08.0 AC12). The wording fits one line at 390 px and, if it does not at 320 px, the short form "3 lifts" is used and the long form moves to the accessible name.
16. **The accessible name matches the summary.** The visually hidden text reads "Records on 3 lifts" ("Records on 1 lift"), the same count the summary's heading names (Spec 17.6 AC3, AC15). The visible text stays `aria-hidden` as in 17.2 AC31.
17. **Test data follows the rule.** `workoutFake`'s `recordCount` and the screenshot harness's History data use `liftsWithBeatenRecords`, not a row count; the harness shows a row where the old and new numbers differ (6 rows, 3 lifts).
18. **Phone check (owner).** On the iPhone, with a workout that beat weight and estimate on one lift: History says "PR on 1 lift", and the summary says "New record" or "New records on 1 lift". The two agree.
19. **Every behavioral AC has a tagged test.** AC15–AC17 have ≥1 test named `07.6 ACn — …`.

## 6. Behavior & logic

### 6.1 The exact change

In `listFinishedWorkouts` the last select column is today

```sql
(SELECT count(*)::int FROM "personal_record" pr
  WHERE pr.workout_id = w.id AND pr.record_type <> ${HISTORY_COUNT_EXCLUDES}) AS record_count
```

and becomes

```sql
(SELECT count(DISTINCT pr.exercise_id)::int FROM "personal_record" pr
  WHERE pr.workout_id = w.id AND pr.user_id = w.user_id
    AND pr.record_type <> ${HISTORY_COUNT_EXCLUDES}
    AND pr.previous_value IS NOT NULL) AS record_count
```

The constant stays bound as a parameter. `pr.exercise_id` is already the lineage root. `pr.user_id = w.user_id` is new and costs one comparison on rows already fetched; it makes the subquery filter by user in its own text (the audit's rule) rather than only through `w`.

### 6.2 Why SQL and not a recount

Same reasoning as Spec 07.3 §6.2: the count reads the rebuildable cache. The History list does not fetch records per row (that would be an N+1), and the web never re-derives the figure. Recomputing through `records.ts` on read would break `CLAUDE.md`'s rule that PR math lives only in `@sin/core`.

### 6.3 The edge cases, decided

- **`previous_value` is null.** Not beaten, not counted (AC3). A rebuild or an edit that turns a beaten row into a first row (the earlier workout was deleted, or re-timed after this one) lowers the count; the row and the count move together because both read the table.
- **A rounded-zero est. 1RM gain.** On screen, 17.2 D16 / 17.6 AC6 drop such a row while the lift has another beaten row, and keep the lift counted when it is the only one ("the lift still counts"). So the ledger's lift count is "lifts with a beaten non-volume row" with no exception. The server's rule is the same sentence. They cannot disagree without a change to 17.6 AC6. If that ever changes (a lone zero-gain estimate stops counting), the count would need either the rounding in SQL, which is PR display math that must not leave the web, or a stored flag; the parity test (AC7) fails first and that change would need its own decision.
- **Edited workouts.** An edited past workout holds whatever the recompute left (Spec 07.4). The count is the rule applied to those rows. Nothing marks a workout as edited (07.4 brief §4.4).
- **Fork and origin.** Same root, one lift.
- **Old workouts.** A workout finished before `records:rebuild` first ran has no rows and counts `0`, as today.
- **Retired exercises.** The query joins no exercise table; unchanged.

### 6.4 Wording (proposal for Phase B)

"N PRs" over a count of lifts can mislead: a lifter who beat weight and estimate on one lift sees "1 PR" and a panel with two rows, or reads "3 PRs" and counts six rows. Options:

| Option | Visible text | Note |
|---|---|---|
| **(a) Keep** | "3 PRs" | No web work. Reads as a count of records; wrong against the panel. |
| **(b) Name the unit (chosen)** | "PR on 3 lifts" / "PR on 1 lift" | Same noun as the summary's "New records on 3 lifts". Longest. |
| **(c) Short** | "3 lifts" next to the trophy | Fits anywhere; the trophy carries "PR". Less self-explanatory. |

**Recommendation: (b),** with (c) as the fallback at 320 px if the harness shows the row wrapping. The owner decides (O1).

## 11. Deployment & rollback

**Phase A** ships as an ordinary merge to `main` (auto-deploys staging), after Spec 21.1 has finished. No migration, no `seed:catalog`, no `records:rebuild`, no env change. **Rollout with no schema change:** the field keeps its name and type, so DESIGN §6's new-field rule is not triggered. An old web build under the new API shows "N PRs" where N is now a count of lifts, which still reads correctly ("3 PRs" for three lifts that set records); a build with Spec 17.6's ledger and the old badge shows two numbers that now agree. Nothing parses a different shape.

**Phase B** (the copy) merges after Phase A is deployed, so the new words always sit on the new number.

**Order with Spec 07.5:** 07.6 first, so that History's number never counts the per-weight rows (each of which would otherwise add one to Spec 07.3's row count). Either order is safe for data.

**Rollback:** revert the commit. Nothing is persisted, nothing to repair.

**Doc edits** (made with the implementation): `@sin/core` `dto/workout.ts` `recordCount` comment becomes "the number of lifts (lineage roots) that hold at least one beaten, non-volume record in this workout now (Spec 07.6): the count the finish summary's heading names. A first-ever record beat nothing and is not counted."
