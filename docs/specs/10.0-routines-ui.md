## 1. Purpose, scope & non-goals

Let a lifter keep a small library of routines and start a session from one. Routines live **inside the Workouts tab** (the nav stays four tabs): the Start screen lists them, a tap opens a **preview** (name, notes, items with target lines and the superset bracket) with **Start this routine / Edit / Delete**, and a routed **editor** builds or edits one — name, notes, an ordered list of exercises with targets, and supersets via a "Superset with next" toggle between neighbours. No API change, no migration, no new env var, no new browser-storage key, no new dependency.

> **First-principles note — the draft reducer.** The editor holds a *draft*: a plain object (`{ name, notes, items[], dirty }`) that only exists in memory while the screen is open. A **reducer** is a pure function `(state, action) → newState`; React's `useReducer` calls it for every user action ("move item 3 up"). Keeping it a separate, React-free file means the tricky part — superset groups must stay contiguous, 2 to 8 long — is a table of `before → action → after` unit tests with no DOM. The screen is then dumb: it dispatches actions and draws the state. Nothing is saved until the lifter presses **Save**, which sends the *whole* routine in one `PUT` (Spec 09 D2) — that is why no autosave and no per-edit request exist.
>
> **Why supersets are per item but edited per boundary.** The server stores a number on each item (`supersetGroup`); two items are "in the same superset" when they share a non-null number. The UI never shows numbers. It shows a toggle *between* item *i* and item *i+1* ("linked to next"), which is derivable from the numbers (neighbours share one) and which makes it impossible to build a non-adjacent group. After each action the reducer renumbers 1, 2, 3 … using Spec 09's own `normalizeSupersetGroups`, so the draft already equals what the server will store.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"10.0 ACn — …"`** (the 08.0 / 08.1 convention). Levels are in §10. **Phase A** (AC1–AC13): pure logic, client, queries, errors. **Phase B** (AC14–AC35): routes and screens. **Phase C** (AC36–AC40): cross-cutting and verification. **Docs** (AC41–AC42).

### Phase A — draft, validation, formatting, client, queries

1. **Draft basics.** `routineDraft` (`features/routines/routineDraft.ts`, pure, no React) exposes `initialDraft()`, `reduce(state, action)` and the actions `rename`, `setNotes`, `add`, `remove`, `moveUp`, `moveDown`, `setTargets`, `toggleLink`, `load`. `initialDraft()` is `{ name: "", notes: "", items: [], dirty: false }`; every action except `load` sets `dirty: true` (an action that changes nothing — moving the first item up — leaves the state **identical by reference** and `dirty` unchanged). Each item has a client-only `key` (unique within the draft, stable across moves, edits and group changes; never sent to the server). `add(exercise)` appends an ungrouped item with every target `null`; the same exercise may be added twice; at 30 items `add` is a no-op. `remove` drops the item. `setTargets` replaces one item's target fields and notes, nothing else.
2. **Linking and unlinking.** "Linked to next" for items *i*, *i+1* is derived (both carry the same non-null `supersetGroup`). `toggleLink(i)` on an unlinked boundary merges the two neighbours' runs (an ungrouped neighbour joins the other's group; two groups become one); on a linked boundary it splits the run at that boundary, and a side left with a single item becomes ungrouped. If a merge would make a run of more than **8** items (`SUPERSET_GROUP_MEMBERS_MAX`), `toggleLink` is a no-op and `canLink(state, i)` returns `{ ok: false, reason: "A superset can have up to 8 exercises" }`; `toggleLink` on the last item or an out-of-range index is a no-op.
3. **Moves keep groups contiguous.** A grouped item that moves *within* its run swaps with its neighbour and the group is unchanged. A grouped item at the run's edge moving *outward* leaves the group (the run dissolves if one member remains) and takes the neighbour's slot. An **ungrouped** item moving into a run jumps over the *whole* run (it never lands inside). `moveUp` on item 0 and `moveDown` on the last item are no-ops. Table-driven, including runs at the start and end of the list and two adjacent runs.
4. **Removal and normalisation.** Removing a member of a two-item run ungroups the survivor; removing from a larger run shrinks it. **After every action** the draft's `supersetGroup` values equal `normalizeSupersetGroups(…)` of themselves (1, 2, 3 … by first appearance, `null` untouched) and every non-null group is a contiguous run of 2 to 8 items — asserted by a property-style test that applies a long pseudo-random (seeded) action sequence and checks the invariant after each step.
5. **Loading a routine.** `load(routine)` builds the draft from a `Routine` (`items` in `position` order, fresh `key`s, server item ids discarded, `targetRpe` kept as the decimal), `dirty: false`, `adjusted: false`. If the routine carries a non-contiguous group (possible only via the raw API; Spec 09 AC12 allows it), `load` splits each group into contiguous runs (a run of one becomes ungrouped), renumbers, sets `adjusted: true` and `dirty: true`; the editor shows "Supersets were adjusted so grouped exercises sit together" until the next action or dismissal.
6. **The payload.** `toRoutineInput(draft)` returns `{ name, notes?, items[] }` for `RoutineWriteSchema` (Spec 09 §5): `name` trimmed; `notes` omitted when blank after trim; per item `exerciseId`, the targets (`null` for blank — blank means "no target", **never `0`**), `targetRpe` as the decimal (the server owns the tenths conversion, Spec 09 AC10; the client never calls `rpeToTenths`), `supersetGroup`, `notes` (omitted when blank); **no `position`** and no `id`/`key` (Spec 09 AC11 — a stray key is a `422`). Array order is position. For any draft that `validateDraft` accepts, `RoutineWriteSchema.safeParse(toRoutineInput(draft))` succeeds, and the parsed groups equal the draft's.
7. **Validation.** `validateDraft(draft, { exerciseState })` (`validateDraft.ts`, pure) runs `RoutineWriteSchema.safeParse` on the would-be payload and maps each issue path (`items.3.targetRepsLow`) to `{ itemKey, field }` (`name`, `notes`, `items` for the list as a whole, or an item field in {`exerciseId`, `targetSets`, `targetRepsLow`, `targetRepsHigh`, `targetRpe`, `restSeconds`, `supersetGroup`, `notes`}); messages come from a field-keyed table in the app's wording (never Zod's text). Plus, in this order: name required after trim and ≤ 80 (`ROUTINE_NAME_MAX`); `items.length ≥ 1` → "Add at least one exercise"; any item whose exercise is retired (`exerciseState(item.exerciseId) === "retired"`) → that item's `exerciseId` error "No longer available — remove or replace". The result is `{ ok, errors }`; `ok` is `true` iff there are no errors. A group-size issue from Zod (impossible given AC4) is surfaced as a generic form error **and** passed to `reportError` as a bug.
8. **Duplicate-name warning.** `nameTaken(name, routines, selfId?)` is true when another routine in the list cache has the same name **trimmed and case-insensitively** (`"push a"` vs `"Push A"`); the routine being edited (`selfId`) never conflicts with itself. It is a *warning*, not a validation error: it shows the message "You already have a routine with this name" on the name field, does **not** disable Save (the cache can be stale; the server's `409 routine-name-taken` is authoritative and shows the same message, AC31).
9. **Target parsing and formatting.** `targetFormat.ts` (pure): `parseRest("1:30") → 90`, `"0:00" → 0` (a real "no rest", distinct from blank → `null`), `"15:00" → 900`, rejects `"15:01"`, `"1:75"`, `"1:5"`, `"abc"`, `"-1:00"`; `formatRest(90) → "1:30"`, `formatRest(0) → "0:00"`. `parseReps("8")` → `{ low: 8, high: 8 }`, `parseReps("8-10")` (also en dash) → `{ 8, 10 }`, rejects `"10-8"`, `"0"`, `"101"`, `"8-"`; blank → both `null`. Sets accept integers 1–20, RPE is one of the fixed choices 6, 6.5, … 10 (a `<select>`, no free text), notes ≤ 500 (`ROUTINE_ITEM_NOTES_MAX`). All bounds come from the `@sin/core` constants / schema, not literals. `targetLine(item)` renders only what is set, joined by ` · `: sets and reps → `3 × 8–10` (equal bounds → `3 × 8`), sets only → `3 sets`, reps only → `8–10 reps`, RPE → `RPE 8` / `RPE 8.5`, rest → `2:00`; nothing set → `""`. `routineSummary(routine)` → `6 exercises · 2 supersets` (singular `1 exercise`, `1 superset`; the superset part omitted when there are none; supersets counted as distinct non-null groups).
10. **The client builds the right requests.** `createRoutineClient(api)` (`routineClient.ts`, React-free, shaped like `workoutClient.ts`) implements `list()` → `GET /v1/routines` parsed with `RoutineListResponseSchema` and returned as `Routine[]`; `get(id)` → `GET /v1/routines/{id}`; `create(body)` → `POST /v1/routines`; `replace(id, body)` → `PUT /v1/routines/{id}`; `remove(id)` → `DELETE /v1/routines/{id}`; responses parsed with `RoutineSchema`; every id is path-encoded (`encodeURIComponent`; an id `a/b?c#d` cannot change the path). The client has no ETag code (the API's `private, no-cache` + `ETag` lets the browser's HTTP cache revalidate, Spec 09 AC4).
11. **The error classifier.** `classifyRoutineError(error)` (`routineErrors.ts`, pure, never throws) maps an error to one of `name-taken` (409 `routine-name-taken`), `limit` (409 `routine-limit`), `retired` (409 `exercise-retired`, with the offending item **indexes** parsed from `errors[].path` of the form `items.<i>.exerciseId`; for a start, the single `routineId` path), `validation` (422, `fieldErrors` as `{ path, message }`), `not-found` (404), `rate-limited` (429), `network` (`isNetworkError`), `unauthenticated` (401), `server` (≥ 500), `unknown` — keyed on `ApiError.status` and `ApiError.type` (the slug), never on title or detail text, and carrying `requestId`. `reportRoutineUnexpected(op, error)` calls `reportError(error, { source: "routines", op })` for `unknown` **and** for `validation` (the client should have caught it), and for nothing else; `op` is one of a static set (`"load-routines"`, `"load-routine"`, `"save-routine"`, `"delete-routine"`).
12. **Query keys and cache writes.** `ROUTINE_KEYS = { all: ["routines"], list: ["routines","list"], detail: (id) => ["routines","detail", id] }`. `useRoutines()` is `useQuery` on `list` with `retry: false`, `networkMode: "always"` (offline fails as a `network` error instead of pausing, as 08.1 D11), `refetchOnWindowFocus: false`, no own `staleTime` (inherits the app default). `useRoutine(id)` returns the routine from the list cache when present (a `select` by id) and otherwise reads `detail(id)` (`networkMode: "always"`, `retry: false`) — the deep-link path. The mutation hooks (`useCreateRoutine`, `useReplaceRoutine`, `useDeleteRoutine`) use `networkMode: "always"` and write in **hook-level** `onSuccess` (06.1's rule — correct even if the component unmounted): create and replace write the returned `Routine` into `detail(id)` and into the list (inserted or replaced, **re-sorted by lowercase name then id**, the server's order); delete removes the routine from both. A list that is not cached is not created by a write (the next `useRoutines` fetches it).
13. **Starting from a routine uses the same idempotent start.** The start logic of `StartWorkout` (key minted on first tap and held in a ref, reused by every retry, discarded on success; a synchronous in-flight guard; `409 workout-in-progress-exists` → adopt) is extracted into a hook `useBeginWorkout({ routineId?, … })` in `features/workouts/`, used by both `StartWorkout` and the preview. With `routineId` the body is `{ clientGeneratedId, startedAt, routineId }` (`CreateWorkout` already carries `routineId`, so `useStartWorkout` is unchanged); without it the body is byte-for-byte today's. `workout_started` is tracked as `{ resumed, fromRoutine }` — `fromRoutine` a boolean, **no routine id**, present on both existing call sites (`false` for an empty start). The extraction is behaviour-preserving: `StartWorkout.test.tsx`, `observability.test.tsx` and the `WorkoutsScreen` tests pass unmodified except for the button label (AC14) and the `workout_started` payload assertions.

### Phase B — routes and screens

14. **Routes and navigation.** `router.tsx` gains, under `ProtectedRoute > ProtectedLayout`: `workouts/routines/new` → editor (create), `workouts/routines/:id` → preview, `workouts/routines/:id/edit` → editor (edit), and the bare `workouts/routines` → `<Navigate to="/app/workouts" replace />` (the Start screen is the routines list). `/app/workouts` and `/app/workouts/:id` (finished workout) are unchanged. At every `/app/workouts/routines/…` path the Workouts nav link has `aria-current="page"` and no other does (`navItemFor`'s prefix match, no change to `navItems.ts`). A router test over `createMemoryRouter(routes)` pins all four paths, including that the bare `/app/workouts/routines` lands on `/app/workouts` and never on `FinishedWorkoutScreen` (§6.1). The Start screen's primary button is relabelled **"Start empty workout"** (the `<h1>` "Start a workout" is unchanged).
15. **The Routines section.** Below the Start button the Start screen shows a "Routines" heading (`<h2>`) and, from `useRoutines()`, a `<ul>` in the list's order (server order, lowercase name). Each `<li>` is **one link** (≥ 44 px) to `/app/workouts/routines/<id>` (id path-encoded) with line 1 the name and line 2 `routineSummary`. Below the list a **New routine** link to `/app/workouts/routines/new`. The section renders only on the no-active-workout Start screen — an active workout shows the session exactly as today.
16. **Routines section states.** Pending: a small `role="status"` line "Loading routines…" (not the full-viewport `Spinner`); **Start empty workout is usable throughout**. `[]`: one line "Routines are reusable workouts — build one, then start it in a tap." plus **New routine**. Failure with no data: an `InlineNotice` (`tone="error"`) "Couldn't load routines" + "Retry" (`refetch()`) + the request id when present — offline included (reads use `networkMode: "always"`). A failed background refresh with rows cached keeps the rows and shows "Couldn't refresh your routines" + Retry. `reportRoutineUnexpected("load-routines", …)` runs, reporting only `unknown`.
17. **The 50-routine limit.** With 50 routines in the list, **New routine** renders as a disabled control (not a link) with the text "You've reached 50 routines — delete one to add another" (the constant is `ROUTINES_PER_USER_MAX`, not a literal). A server `409 routine-limit` on create shows the same text in the editor (AC32) and leaves the draft intact.
18. **Preview content.** `/app/workouts/routines/:id` renders one `<h1>` with the routine's name; its notes when present; then the items in order. Each item shows the exercise name (from the catalog store, AC30), `targetLine`, and the item's notes when present; items in the same superset sit inside one bracket (a vertical line, decorative — `aria-hidden`) and each row's accessible name includes group membership (`"Bench press, superset 1, 3 × 8–10"`; group numbers are the routine's dense 1, 2, 3 …). Actions: **Start this routine** (primary), **Edit** (→ `…/edit`), **Delete**, and a "Back to Workouts" link (≥ 44 px) → `/app/workouts`.
19. **Preview loading states.** The routine comes from the list cache when present, else `detail(id)` (AC12). Pending detail: `role="status"` "Loading routine…". `404` (also a malformed id, which the API answers `404 not-found`, Spec 09 AC3): "That routine no longer exists" with a link "Back to Workouts" — not an error notice, not reported. Any other failure: `InlineNotice` error "Couldn't load this routine" + Retry + request id; `reportRoutineUnexpected("load-routine", …)`.
20. **Start success.** "Start this routine" calls the AC13 hook with `routineId`. While in flight the button is busy and a second tap issues no second request (the ref guard). On success the app navigates to `/app/workouts` with `replace` (so Back does not return to the preview) and the session screen appears (the active-workout query is invalidated by `useStartWorkout`, as for an empty start). A retry after a failed attempt reuses the same `clientGeneratedId`; a **new** preview mount mints a new key. After a successful start the new workout contains the routine's exercises in order with the superset groups (asserted on the *request* and, in the phone check, on the data — AC40; Spec 09 AC16 owns the server copy).
21. **An active workout blocks Start on the preview.** When `useActiveWorkout()` has data (a deep-linked preview while a session is running) the preview shows, in place of the Start button, the text "Finish your current workout first" and a link "Go to your workout" → `/app/workouts`; **Edit** and **Delete** stay available. While the active query is pending or failed the Start button is shown (the server's `409` is the backstop, AC22).
22. **Start failures.** Handled on the preview, the draft/routine untouched, each with the request id where shown: (a) `409 workout-in-progress-exists` (a race): adopt it as `StartWorkout` does (invalidate the active query, `workout_started { resumed: true, fromRoutine: true }`), navigate to `/app/workouts` (replace) carrying the one-time notice "You already had a workout in progress — resumed it. The routine wasn't applied." (AC23); (b) `409 exercise-retired`: stay, show "One of this routine's exercises is no longer available. Edit the routine to replace it." with an **Edit** action; (c) `404`: navigate to `/app/workouts` (replace) with the notice "That routine no longer exists" and invalidate `ROUTINE_KEYS.list` (and remove `detail(id)`); (d) `422` (bad device clock): the same clock message `StartWorkout` shows; (e) network / `429` / other: "Couldn't start your workout — try again." with **Try again** (same key). `reportUnexpected("start-workout", …)` runs as today.
23. **One-time notices across navigation.** `WorkoutsScreen` initialises its notice from router location state `{ notice: "routine-gone" | "routine-not-applied" }` (mapped to the two strings above; an unknown value is ignored), so the Start screen (or the resumed session) shows it once, dismissibly, through the existing `InlineNotice` path. No other `WorkoutsScreen` behaviour changes; its existing notice tests pass unmodified.
24. **Delete.** **Delete** opens a `ConfirmDialog`: title "Delete {name}?", body "Past workouts keep their history.", confirm "Delete" (danger variant), cancel "Cancel". Confirm calls `remove(id)` (busy while pending); on success the routine is removed from both caches (AC12) and the app navigates to `/app/workouts` (replace). A `404` on delete is treated as success (an already-applied delete, as `useDeleteWorkout`'s `ignoreNotFound`). Failures keep the dialog's page and show an `InlineNotice`: offline → "You're offline — try again when connected", `429` → "Too many changes in a short time — wait a minute and try again", other → "Couldn't delete this routine — try again." + request id. Cancel changes nothing.
25. **Editor shell and loading.** `…/routines/new` shows an empty draft with the `<h1>` "New routine"; `…/routines/:id/edit` loads the routine exactly as the preview does (AC12, AC19) and shows the `<h1>` "Edit routine"; a `404` shows the AC19 message. The draft is created once from the first loaded routine and is **not** reset by a later cache update (a background refetch cannot clobber edits); navigating from one routine's editor to another mounts a fresh draft (the route element is keyed by id). A header row holds **Cancel** and **Save**; below it a name field (`Field`, label "Name"), a notes field ("Notes", optional), the item list, and **Add exercise**. Nothing is written to `localStorage`/`sessionStorage`; no server request is made until Save.
26. **Adding exercises.** **Add exercise** opens the 06.0 `ExercisePicker` (`open` / `onPick` / `onClose`, inside the existing `CatalogProvider`); a pick dispatches `add`, the editor then closes the picker (the picker never closes itself), and the new row is appended at the end, ungrouped, with empty targets; the lifter can pick the same exercise again. At 30 items **Add exercise** is disabled and says "A routine can have up to 30 exercises" (`ROUTINE_ITEMS_MAX`).
27. **Item rows.** Each item is a row: a main control (≥ 44 px) showing the exercise name and `targetLine` (e.g. "Bench press · 3 × 8–10 · RPE 8 · 2:00"; just the name when no targets) that opens the item sheet (AC28), and an **Options** disclosure (`aria-expanded`, as 06.1's `ExerciseCard`) revealing **Move up**, **Move down** and **Remove**. Move up is disabled on the first row, Move down on the last. After a move, focus is on the moved row's main control; after a remove, on the next row's main control, or on **Add exercise** when none is left. The row's accessible name carries group membership (AC33).
28. **The item sheet.** The row's main control opens a `Sheet` titled with the exercise name, holding sheet-local fields: Sets, Reps (one input: `8` or `8-10`), RPE (select: "No target", 6 … 10 in halves), Rest (`m:ss`), Notes. Every field may be blank (blank = no target). **Done** parses all fields (AC9); invalid fields show their message beside the field (`Field`'s `error`) and keep the sheet open; valid → `setTargets`, close. **Close** (the sheet's own button / Escape) discards the sheet's edits. Reopening shows the stored values (`formatRest`, the reps in `8` / `8-10` form).
29. **The superset link control.** Between every pair of adjacent rows is a toggle button with `aria-pressed` (true when linked) and an accessible name like "Superset Bench press with Barbell row" (≥ 44 px). Pressing it dispatches `toggleLink(i)`; when `canLink` is false the button is `aria-disabled`/disabled and the reason "A superset can have up to 8 exercises" is shown beside it and referenced by `aria-describedby`. A linked run is drawn with a continuous vertical bracket; the bracket carries no semantics (`aria-hidden`) and no colour-only meaning. There is no control after the last row.
30. **Retired and unknown exercises.** An item's exercise is looked up in the catalog store's **raw rows** (`useCatalog().state.rows`, which still holds retired rows; `visible` deliberately excludes them, so it is not used for lookup). A row whose exercise has `isActive === false` shows its name and the text "No longer available — remove or replace" (preview and editor) and blocks Save (AC7). An exercise not in the store at all (catalog not yet loaded, or never synced) is shown as "Exercise" and is **not** treated as retired; the name appears when the store loads. The same marker appears on the preview, which does not offer a replace action — Edit is the path.
31. **Save gating and messages.** **Save** is disabled while `validateDraft` is not `ok` or while a save is in flight, and the reason is shown next to the offending thing — name error under the name field, "Add at least one exercise" above **Add exercise**, per-item errors on the row (and the item sheet), each referenced by `aria-describedby` and announced (`role="alert"` only for errors that appear after an attempted action, not on first render). A blank, untouched new routine shows no errors until the lifter has interacted or pressed Save. The duplicate-name warning (AC8) appears beside the name as the lifter types.
32. **Save success and navigation.** Create: `POST /v1/routines` with `toRoutineInput(draft)`; on success the response is written to the caches (AC12) and the app navigates (replace) to the new routine's **preview**. Edit: `PUT /v1/routines/{id}` with the whole document; on success caches updated and navigate (replace) to that routine's preview. A second tap while pending sends no second request. The request body is exactly `toRoutineInput(draft)` — a test compares it to the draft, including a repeated exercise, a superset, blank and set targets, and RPE `8.5` as the decimal.

## 6. Behavior & logic

### 6.1 Route ranking (verified)

React Router 7 scores a route by its segments: static segments outrank dynamic ones, and **a path only matches a URL with the same number of segments** (no prefix matching for a non-splat route). Checked against the real `matchRoutes` (react-router 7.18.3) with the current route config plus the three new routes:

| URL | Today | With 10.0 |
|---|---|---|
| `/app/workouts/routines/new` | `/app/*` NotFound | editor (create) |
| `/app/workouts/routines/abc` | `/app/*` NotFound | preview |
| `/app/workouts/routines/abc/edit` | `/app/*` NotFound | editor (edit) |
| `/app/workouts/abc` | `workouts/:id` | `workouts/:id` (unchanged) |
| `/app/workouts/routines` (no further segment) | `workouts/:id` with id `routines` | **unchanged** — still the finished-workout screen with id `routines` |

So the brief's premise ("static `routines/…` outranks `workouts/:id`") is true but not what makes it safe: the new paths have **three or more** segments after `/app`, so they never compete with the two-segment `workouts/:id`. The one real collision is the bare `/app/workouts/routines`, which would otherwise fall through to `FinishedWorkoutScreen` with id `routines`; a static `workouts/routines` route (static outranks dynamic at equal segment count) redirects it to `/app/workouts`. AC14's router test pins all of this.

### 6.2 The draft reducer

State: `{ name: string; notes: string; items: DraftItem[]; dirty: boolean; adjusted: boolean }`, where `DraftItem = { key, exerciseId, targetSets, targetRepsLow, targetRepsHigh, targetRpe, restSeconds, notes, supersetGroup, retired? }` (numbers or `null`; `retired` is the server-reported flag of AC33). The **invariant** after every action: every non-null group is a contiguous run of 2 to 8 items, numbered 1, 2, 3 … by first appearance. Implementation shape — a private `settle(items)` that (1) breaks any run of one into ungrouped, (2) splits any non-contiguous group into contiguous runs, (3) calls `normalizeSupersetGroups` — applied at the end of every reducer branch, so a rule can never be forgotten by a single action.

- **toggleLink(i)** computes the would-be run length by walking left and right from the boundary; > 8 → no-op. Link: give both sides one group (the left side's number if it has one, else the right's, else a fresh number), then `settle`. Unlink: give the right side a fresh number from the split point, then `settle` (a one-item side becomes ungrouped).
- **moveUp/moveDown** operate on *blocks*: a block is a whole run or a single ungrouped item. If the moving item is ungrouped and the neighbour in that direction belongs to a run, the item jumps the whole run (it swaps with the run as a block). If the moving item is grouped and its neighbour in that direction is in the same run, plain swap. If grouped and at the run's edge moving outward, the item swaps with the neighbour and then `settle` removes it from the run (the run dissolves when one member remains). The tests are a table `(items, action) → items` over these cases.
- **load** applies `settle` and compares: if `settle` changed any group, `adjusted: true, dirty: true`.

### 6.3 Validation

`validateDraft` builds the payload with `toRoutineInput`, runs `RoutineWriteSchema.safeParse`, and walks `error.issues`: `path[0] === "items" && typeof path[1] === "number"` → `{ itemKey: draft.items[path[1]].key, field: path[2] }`; a root-level `items` issue is the list error. Messages are looked up by `(field, code)` (e.g. `targetRepsLow` + custom "must be at most targetRepsHigh" → "Low can't be more than high"). Client-owned checks (retired, "Add at least one exercise") run first so the lifter sees the actionable message rather than Zod's generic one. The sheet's own parse (AC9) catches malformed text before it can reach the draft, so a draft normally only fails on name, empty list and retired items.

### 6.4 Data flow and cache

`useRoutines()` feeds the Start screen, the preview/editor lookup (via a `select` by id) and the duplicate-name check. Preview and editor never fetch `detail(id)` when the list holds the routine. If the list is cached but lacks the id (created on another device), the detail query runs (a miss is a real `404` or a real routine). A save writes the response into `detail(id)` and the list; the preview then reads the new routine from the list at once. A delete removes both entries and the `useRoutine` for that id must not refetch (the navigation away happens in the same tick). **Why `networkMode: "always"` on reads and writes:** TanStack's default *pauses* a query or mutation while the browser reports offline, which would leave a spinner or a disabled Save with no message; `"always"` runs it, so the request fails and the classified `network` error shows the offline message (08.1 D11, 06.2 D5). The set outbox is *not* extended to routines (D5).

### 6.5 Start from the preview

`useBeginWorkout({ routineId })` owns the key ref, the in-flight ref and the error state previously inline in `StartWorkout`; it returns `{ begin, busy, error, requestId, kind }`. `StartWorkout` becomes a thin consumer; the preview supplies `routineId` and maps the returned `kind` to AC22's behaviours. Navigation happens in the preview (it knows the route), the hook only reports the outcome. A mounted preview is one key; a fresh mount (leaving and returning) mints a new key, which is correct: the earlier attempt either created the workout (then the active query / `409` adopt path covers it) or did not.

### 6.6 The leave guard

`useBlocker(() => draft.dirty && !leaving.current)` with a `ConfirmDialog` driven by the blocker's `state === "blocked"` (`proceed()` / `reset()`). `leaving` is set synchronously just before the post-save `navigate`. `useBlocker` requires a data router, which the app already uses (`createBrowserRouter`; tests use `createMemoryRouter`). It does not cover a reload or tab close, so a `beforeunload` listener (`event.preventDefault()`) is added while `draft.dirty` and removed when clean, after a successful save, or on unmount.

## 7. Security & privacy

- **Authorization is the server's** (Spec 09 AC28): a tampered `:id` can only name a routine the caller owns, otherwise `404`; the client adds no authority.
- **Path injection.** Every id goes into a request path through `encodeURIComponent` (AC10) and into links the same way.
- **User text.** Routine names, notes and exercise names are user data: rendered as React text (escaped), never as markup, never in `reportError`/`track` (AC38), and kept out of URLs.
- **No persistence of routines in the browser** (AC35): nothing to clear at logout; the query cache dies with the redirect. No inline styles (AC37); CSP unchanged.
- **Abuse.** The 30-per-minute `routines` write group and the 50 / 30 / 8 limits are the server's; the client surfaces `429` as a fixed message (it does not auto-retry a write) and disables Save while one is in flight.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-10)

- ✅ **D1 — Split 10 into 10.0 and 10.1; the rest timer stays M4.** 10.0 is routine management plus start; 10.1 is everything that shows routine-derived data *inside a session*. **Rationale:** each is one work session, and 10.0 delivers a usable loop (build → start) on its own. DESIGN's M3 row had listed the per-group rest timer, which belongs to the M4 rest timer; corrected in DESIGN §9, §2 item 8 and Q5. Rejected: one large Spec 10; moving the rest timer into M3.
- ✅ **D2 — Routines live inside the Workouts tab; tapping one opens a preview, never a one-tap start.** The nav stays four tabs. **Rationale:** routines are a way to *start a workout*, so they belong beside Start; a fifth tab or a replaced tab changes the shell's information architecture for a list of ≤ 50 rows. A preview costs one tap but prevents an accidental session start (one active workout at a time) and gives Edit/Delete a home. Rejected: a Routines tab; one-tap start from the list; a long-press menu (undiscoverable one-handed).
- ✅ **D3 — Supersets are edited with a "Superset with next" toggle between neighbours; groups are always contiguous; reorder is Move up / Move down (06.1 D16), no drag-and-drop.** **Rationale:** a boundary toggle makes a non-adjacent or one-member group *unrepresentable* in the UI, so the bracket (a vertical line) is always truthful, and it works one-handed with 44 px targets. The server permits non-adjacent members (Spec 09 AC12) but nothing in the product needs them. Rejected: multi-select + "Group" (modal state, awkward on a phone); a group-number picker per item (exposes the storage representation, invites gaps); drag-and-drop (a new dependency or a hand-written pointer/keyboard-accessible implementation, for a list that is rarely reordered).
- ✅ **D4 — Targets are edited in a sheet; rows show a compact summary line.** **Rationale:** six fields × up to 30 items inline would be a wall of inputs; the line "Bench press · 3 × 8–10 · RPE 8 · 2:00" is enough to review a routine, and the sheet gives each field full-width tap targets. Every field may be blank (blank = no target, never `0`).
- ✅ **D5 — Explicit Save, "Discard changes?" on leave, in-memory draft, writes online-only.** No autosave, no `localStorage` draft, no outbox. **Rationale:** a routine write is a whole-document `PUT` that regenerates item ids and is last-write-wins (Spec 09 D2/D8); autosaving partial edits would send half-built routines and burn the 30/min `routines` write group. A persisted draft needs a `sin:` storage key, logout clearing and a reconcile story for a routine edited elsewhere — a lot for an activity done at a desk or between sets, not mid-set. The cost is a lost draft if the user confirms the browser's reload / close prompt (AC34). Rejected: autosave; draft persistence; the 06.2 outbox for routines.
- ✅ **D6 — "Save as routine" from a past workout is out of 10.0**, recorded as a follow-up. **Rationale:** it is a second entry into the editor needing a workout→draft mapping and a decision about what to carry (targets from actual sets?); the brief keeps 10.0 to one session.
- ✅ **D7 — A `features/routines/` module mirroring `features/workouts/`, a pure reducer for the draft, no new dependencies.** **Rationale:** the reducer isolates the one hard part (AC2–AC4) from React; a form library or a state library would add a dependency for state this small. Rejected: component state with ad-hoc handlers (superset rules scattered across handlers); a form library.
- ✅ **D8 — The group invariant is enforced by one `settle` pass after every action, and move semantics are block-based** (§6.2). **Rationale:** a single normalising step cannot be bypassed by a forgotten rule in one action, and "an ungrouped item jumps a whole run" is the only move behaviour that never places a stranger inside a group. Rejected: letting an item be dragged into a group's middle (then offering "leave group"); per-action invariant code.
- ✅ **D9 — Validate with `RoutineWriteSchema` plus a field-keyed message table; the duplicate-name check is a non-blocking warning.** **Rationale:** the client cannot drift from the server's rules if it runs the same schema; Zod's own text is not the app's voice. The list cache can be stale (another device), so only the server's `409` may block. Rejected: a hand-written client validator duplicating the rules; blocking Save on the cached-name check.
- ✅ **D10 — Routines are read from one list cache (with a detail fallback for deep links); mutations write the returned `Routine`; no refetch on window focus; no client ETag code.** **Rationale:** ≤ 50 small documents in one request is the API's design (Spec 09 AC2); the browser HTTP cache already revalidates by `ETag`, so app-level conditional-request code would duplicate it.
- ✅ **D11 — Reads and mutations use `networkMode: "always"`.** **Rationale:** offline must produce an immediate message with the draft intact, not a paused request (06.2 D5, 08.1 D11).
- ✅ **D12 — A separate `classifyRoutineError` / `reportRoutineUnexpected`.** **Rationale (reality):** `classifyWorkoutError` maps any unrecognised 409 — including `routine-name-taken` / `routine-limit` — and `429` to `unknown`, and `reportUnexpected` would therefore *report* an expected conflict. Extending the workout classifier would widen a union other screens switch over; the routine screens need their own kinds (name field vs notice). The start path keeps the workout classifier, whose kinds already cover it.
- ✅ **D13 — Start logic is extracted to `useBeginWorkout`, not copied.** **Rationale:** the idempotency-key discipline (key in a ref, reused by retries, in-flight ref guard, adopt on `409`) is subtle and must stay identical; the preview and the empty start differ only in `routineId` and in what a failure means. The key is per mounted surface.
- ✅ **D14 — `workout_started` gains a boolean `fromRoutine`; no routine id, no new event.** **Rationale:** the funnel question "do routines get used" needs only the boolean; ids/names in analytics are avoided (DESIGN §8.1); richer routine analytics wait for Spec 13.
- ✅ **D15 — A retired exercise is detected client-side from the catalog's raw rows and blocks Save; the server `409 exercise-retired` is the backstop.** **Rationale:** the lifter should be told *before* a round trip, and the catalog store retains retired rows (it only hides them from the picker). Retired is data, not a crash: the item stays named so it can be removed.
- ✅ **D16 — One-time cross-screen notices travel in router location state**, not a global store. **Rationale:** `WorkoutsScreen`'s notice is local state; router state is the smallest channel from the preview to it and cannot go stale in the query cache. Cost: it survives a reload of that history entry (O8).
- ✅ **D17 — The leave guard uses React Router's `useBlocker`.** **Rationale:** it covers Cancel, nav links and the Back button uniformly in a data router, which the app already is. A `beforeunload` listener covers reload and tab close, which `useBlocker` cannot see; its dialog is the browser's own.
- ✅ **D18 — Rest is entered as `m:ss` and stored as seconds; RPE is chosen from fixed values; reps are one input (`8` or `8-10`).** **Rationale:** matches how lifters write targets; a select for RPE makes an off-step value (Spec 09 AC10) unrepresentable; `0:00` is a real value distinct from blank.

### Resolved by reading the code (corrections to the design brief)

- **There is no `RoutineInputSchema`.** The write schema is `RoutineWriteSchema` (items: `RoutineItemInputSchema`) in `packages/core/src/dto/routine.ts`; the spec uses those names.
- **`ApiError.errors[]` entries are `{ path, message }`, not `pointer`** (`apps/web/src/api/problem.ts`; the API's paths are `items.<i>.exerciseId`, Spec 09 §5). The brief's "`errors[].pointer`" is read as `path`.
- **The static-over-dynamic route ranking is not what keeps these routes safe** — segment count is (§6.1); the one real collision, the bare `/app/workouts/routines`, gets a redirect route (AC14).
- **The Start button is labelled "Start workout" today** (the `<h1>` is "Start a workout", pinned by ~20 tests). The brief's "Start empty workout" is adopted as the new button label (two test lines change); the heading is untouched.
- **`useStartWorkout` already accepts `routineId`** (`CreateWorkout` carries it), so "gains optional `routineId`" needs no hook change; the work is that the key/guard/adopt logic lives *inside* `StartWorkout`'s component body and must be extracted (D13).
- **`classifyWorkoutError` / `reportUnexpected` do not know the routine slugs or `429`** (D12).
- **`ExercisePicker` is `open` / `onPick(exercise)` / `onClose` and never closes itself**; it must be rendered inside `CatalogProvider` (it is, via `ProtectedLayout`). `useCatalog().visible` excludes retired rows and fork origins; item lookup uses `state.rows` (AC30).
- **`Sheet` is a full-height modal `<dialog>`, not a bottom sheet**, and **`Screen` has only a title and children** (no header slot): the "bottom item sheet" is the shared `Sheet`, and the editor builds its own Cancel/Save row inside the screen (O4, O5).
- **06.1's Move up / Move down live behind an Options disclosure** on the exercise card; the editor reuses that pattern (AC27).
- **08.1 sets `networkMode: "always"` per query** (an option on each `useQuery`), mutations per hook — confirmed; no global default is changed.
- **`track` props admit booleans**, but `observability.test.tsx` pins `workout_started` to `{ resumed }` and `StartWorkout.test.tsx` asserts the exact payload; both are edited (AC13, AC38).
- **`WorkoutsScreen`'s notice is local `useState`** (D16); the repo has no existing `useBlocker` use (D17).
