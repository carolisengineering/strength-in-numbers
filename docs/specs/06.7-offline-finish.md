## 1. Purpose, scope & non-goals

The owner's worst case at the gym is "finishing a workout and losing all the in-progress data", and up to 100 people at her gym will use the app where signal is poor. Since Spec 06.2, a set logged with no signal is safe: it sits in a persisted outbox and survives a reload. But **Finish itself needs signal**. It is locked while any set is unsent, and with no signal it fails with "You're offline — try again when you have signal", leaving the workout open (06.2 §1 non-goals, "not planned for v1"). This spec reverses that: **Finish works with no signal and sorts itself out later.**

Goals: (1) tapping Finish with no signal, or with signal that dies during the request, always succeeds from the lifter's point of view; (2) the workout reaches the server later, complete, in order, once, with the real end time; (3) the lifter always knows the true state, on the phone only or in the cloud; (4) an automated browser test proves it.

> **First-principles note (what "saved on this phone" means, and what it cannot mean).** A web page can store text in the browser's `localStorage`. The app already keeps its list of unsent writes (the *outbox*, Spec 06.2) there. A finished-but-unsent workout is one more entry in that list: "when you can, tell the server this workout ended at 6:42 pm". That entry survives closing the tab and restarting the phone. What it cannot do is *send itself*: a web page runs code only while it is open. There is no *service worker* (a script the browser can run in the background) and no background sync in this app, and iPhone browsers do not let an ordinary web app send while closed. So "saved on this phone" is true, and "it will send" is true **only while the app is open with signal**. The copy says so plainly (§6.10). Losing the phone, or clearing the browser's data, before it sends loses the workout; the owner has accepted that.

> **First-principles note (why the finish is a queue entry and not a flag).** The server rejects a finish if the workout still has an incomplete working set, and it applies sets in the order they arrive. If the finish were sent beside the queued sets instead of after them, it could land first and the sets would arrive on a finished workout. Making it one more queued operation that sends last, for its own workout, gives ordering, retry, backoff and persistence from machinery that already exists and is tested.

### In scope

- A `finish` outbox op: its shape, persistence, ordering, send, outcome table, and the timeouts every outbox send now has (§4, §6.1–§6.5).
- Per-account outbox storage, and what a forced sign-out keeps versus a deliberate one (§4, §6.8).
- `QueuedWorkoutClient.finishOrQueue`, the landing effects (caches, drafts, tracking, the Hevy event), the summary's waiting state, the Workouts screen's waiting card, the one-time "saved" line, "reopen to fix", the start / edit / discard locks, the logout-guard wording (§5, §6.3–§6.10).
- The Playwright offline run (§6.12).

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|

| Sending while the app is closed (service worker, background sync, installable PWA) | Post-v1 (DESIGN §2 non-goals). Sending happens only while the app is open |
| Opening the app with no signal | **Not possible and not attempted** (owner, 2026-11-08, keeping 06.2 D11): sign-in is memory-only (DESIGN Q12), so a reload or reopen needs the network before any screen renders. No service worker and no stored workout snapshot are added. If the lifter swipes the app away in a dead spot they get a browser error until they have signal; the data stays safe in storage and sends after the next sign-in |
| Phone notifications | Not planned |
| Working out personal records on the phone (provisional records) | Not planned. `@sin/core` has the math, but the server stays the one source |
| Editing, starting another workout, or discarding while a finish is waiting | Locked on purpose (§5.3) until the finish lands or is refused |
| A message at the moment of a forced sign-out | The Auth0 redirect leaves nowhere to show one; open item O2 |
| Expiry of a held (kept-after-forced-sign-out) outbox file | Open item O3 |

### Anti-goals (failures even if it technically works)

- Any path that quietly discards a finished workout or its sets.
- The app implying the workout is safe in the cloud when it is only on the phone — including the Hevy auto-push, `workout_finished` tracking and draft cleanup firing early.
- A retry that creates a duplicate set or a second finish, or stamps the time of sending instead of the time of tapping.
- Copy that says "saved on this phone" when the write to storage failed.

### Fit for one work session

It is not; it is four PRs (§11): **A** the outbox half (React-free), **B1** the client, landing effects and caches (no visible change), **B2** the screens, **C** the browser test. A ships alone and is safe (nothing creates a finish op yet; the per-account storage, the send timeout and the forced-sign-out rule go live). B1 ships alone and is inert (no screen calls `finishOrQueue`). B2 is the one that changes what the lifter sees. C needs B2 deployed to staging.

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"06.7 ACn — …"`** (the 06.4 D6 convention). Level in brackets; §10 maps each. **Phase A** (AC1–AC12): the outbox. **Phase B1** (AC13–AC20): client and landing. **Phase B2** (AC21–AC35): the screens. **Phase C** (AC36–AC39): the browser test. **Docs and gates** (AC40–AC41).

### Phase A — the outbox half

1. **A `finish` op exists and persists.** `OutboxOpSchema` gains `{ ...CommonShape, kind: "finish", body: { endedAt: string; keepRoutine?: true }, meta: FinishMeta }` (no `workoutExerciseId`; §4). A file holding it round-trips through `parseOutboxFile`; the file stays `v: 1`. A file written by the previous release (set, note, round, result ops only) loads unchanged. `isSetOp` is false for it, so no counter that counts sets counts it. [unit]
2. **At most one finish per workout, and it sends last.** `enqueueFinish` on a workout that already has a finish op (queued, sending) returns without adding one; on a *failed* finish op it replaces it with a fresh op (the reopen-and-finish-again path, AC29). The drainer sends a finish op only when no other op of its workout is left in the queue. If an earlier op of its workout is `failed`, the finish op becomes `failed` too with the same `failure` and `blockedBy: <opId>` (as a create's follow-ups do, 06.2 AC4). `enqueue*` of a set, note, round or result op on a workout that has a non-failed finish op is refused (a defensive no-op, reported once with a static tag). [unit]
3. **The finish outcome table.** `classify` gains the `finish` row: 2xx → done (landed). `409 workout-finished` → *reconcile* (below). Network failure, 5xx, 408, 429 → retry with 06.2's backoff. `422` whose `errors` contain `{ path: "endedAt", message: RETIME_MESSAGES.future }` → retry (a phone clock more than 5 minutes ahead passes once real time catches up). `409 incomplete-working-sets` → fail. `404` → fail (the workout is gone). Any other 4xx, including any other `422`, → fail. *Reconcile:* read the workout (`getById`, with the send timeout); `endedAt === null` → fail; `endedAt` equal (to the millisecond) to the op's → done, outcome `ours` (the first reply was lost); otherwise → done, outcome `elsewhere` (finished on another device); a network error on the read → retry; `404` → fail. [unit]
4. **A replay sends the same finish.** The op's `endedAt` is fixed at enqueue and never recomputed. A `sending` finish op found on load becomes `queued, attempted: true` (06.2 §6.1) and sends the same body; the server's `409` then reconciles as `ours`. Nothing merges into an attempted finish. [unit]
5. **Every outbox send has a deadline and an abort signal.** Each `send` passes an `AbortSignal` to the REST client and also races a timer of `SEND_TIMEOUT_MS` (20 000): a hung request or a hung token fetch ends as an `ApiError.network` (retryable), releases `draining`, and the next attempt follows the backoff. The REST `WorkoutClient` write methods accept an optional `{ signal }` and forward it to `api.request`. **Retry now** works after a hung send (it no longer waits behind `draining`). [unit]
6. **A `404` on a note, round or result op is not "done" while a finish waits.** When the workout has a finish op in the queue (any status), `classify` treats the `404` of a `note`, `round` or `result` op as `fail`, so the lifter sees it. With no finish op the 06.2 / 10.7 rule is unchanged (`done`). A `404` on a set `delete` stays `done`. [unit]
7. **`settle` cannot lose a workout that has a finish op.** `settle(activeId)` keeps every op, in every status, of any workout that has a finish op, and the id-map entries they need; it removes failed ops of other workouts only as before (Spec 18.0 AC25 amended). `dropWorkout` is the only way those ops leave besides landing and the Discard in AC30. [unit]
8. **Outbox storage is per account.** The file lives at `sin:workout:outbox:<userId>`. On load the store reads that key; if absent it reads the legacy `sin:workout:outbox` and, if its `userId` matches, adopts it (writes the per-user key, then removes the legacy key; a failed write leaves the legacy key). A legacy file of another user is left alone. A user signing in on the same phone loads only their own key and never writes another's. The cross-tab watch (`conflict`) is on the per-user key. [unit]
9. **A forced sign-out keeps unsent workout data; a deliberate one clears it.** `clearUserData(storage, { keep })` takes an optional predicate. `logoutAndClear(logout, storage, mode?)`: the **forced** mode (`useApi`'s `onAuthLost`) keeps every key starting `sin:workout:outbox:`, and the legacy `sin:workout:outbox` too (Phase A final review, 2026-11-16: a session lost before the outbox adopted that file must not lose its sets); the **deliberate** mode (`useSession().logout`, reached by "Sign out anyway") passes the signed-in `userId` and clears that user's outbox file and everything else, but keeps *other* users' outbox files; with no `userId` (the other callers) it clears every outbox file, as today. In both, drafts, the rest timer, catalog, recents and the Hevy key are cleared as today, and `blockUserDataWrites()` still runs first. After the forced sign-out the same user signing in finds the ops and sends them; a different user never sees them (06.2 AC8). [unit]
10. **The outbox knows whether "saved on this phone" is true.** `OutboxState` gains `durable: boolean`: `false` once a storage write threw or `conflict` is true, `true` otherwise (and `true` for an outbox that has never had to write). [unit]
11. **The logout guard counts a waiting workout, as a workout.** `count()` no longer derives sets by subtraction: `Unsaved` gains `workouts?: number` (present only above zero), a `finish` op in any status counts there and in no other bucket, and `unsavedMessage` words it ("1 finished workout hasn't sent. If you sign out now it'll be lost."), joined with the other parts as 10.7 AC39 does. [unit]
12. **Finish ops never count as set failures.** A failed `finish` op fires `workout_finish_failed { status }` (once) and never `set_sync_failed`; the `set_sync_failed` count and `set_sync_delayed` ignore it. [unit]

### Phase B1 — the client, landing and caches

13. **`finishOrQueue` always resolves, and says which.** `WorkoutClient.finishOrQueue(id, body, meta)` (REST client: wraps `finish`, resolves `{ status: "landed" }`; queued client: enqueues the op, then waits at most `FINISH_WAIT_MS` (8 000) for it to settle) resolves `{ status: "landed" }` or `{ status: "queued", reason: "offline" | "slow", durable: boolean }`. With `navigator.onLine === false` it resolves `queued/offline` at once, without waiting. It never rejects for a network, timeout or server reason (those are the op's, AC3); it rejects only for a programming error. A finish enqueued behind unsent sets waits for them within the same budget. [unit]
14. **Landing effects run in one place, once.** When a finish op leaves the queue by success (`landed`, `ours`, `elsewhere`) the provider's `onFinishSynced` runs, before any waiter resolves: it writes `["workouts","detail",id]` from the response (or the re-read, for `ours` / `elsewhere`), calls `applyFinishedCaches(queryClient, id, newRecords | null)`, sets `["workouts","active"]` to `null` if it holds this workout, clears this workout's drafts and rest timer (`clearWorkout`), tracks `workout_finished`, and calls `emitWorkoutFinished` — for `landed` and `ours` only, never `elsewhere` (§12 D9). `useFinishWorkout` has no `onSuccess` effects of its own after this change. The same workout emits at most once per page load (a module-level set in `finishEvents.ts`), so a `409` replay cannot double-emit. [unit + component]
15. **Nothing treats a waiting workout as in the cloud.** When `finishOrQueue` resolves `queued`: no `emitWorkoutFinished`, no `workout_finished`, no draft clear, no `applyFinishedCaches`, no record or History invalidation, and `["records",{workoutId}]` is untouched. The rest timer is cleared (the workout is over, §12 D6). `workout_finish_queued { reason }` is tracked. The detail cache is seeded with the projected finished copy so the summary can open (AC16). [component]
16. **The summary reads a projected copy while a finish waits.** `getById(id)` on the queued client: if a non-failed finish op exists for `id`, it returns the cached detail (or, with none cached, the server's copy) with the outbox projection applied and `endedAt` set to the op's — and makes **no request** when a copy is cached. Otherwise it is the REST read. `["workouts","active"]` never holds a workout with `endedAt` set from an unsent finish. [unit]
17. **A local check runs at tap time.** Before enqueueing, `ActiveSession` runs `findIncompleteWorkingSets` on the projected workout; any hit shows the existing "N working sets are missing data" banner and flags the rows, with no request and no op (offline included). The server's `409 incomplete-working-sets` still fails the op if it races (AC3). [component]
18. **Starting is blocked while a finish waits.** `useBeginWorkout` (both Start buttons: the Start screen's and a routine preview's) refuses while the outbox holds a finish op in any status, with no request, and exposes `START_BLOCKED_MESSAGE`. [unit]
19. **A refused finish returns the workout to `ActiveSession`.** A `failed` finish op is not applied by any projection; the active workout renders the in-progress screen again (it is still live on the server); AC29 specifies the screen. The op stays in the outbox with its `failure` until the lifter taps Finish again (it is replaced, AC2) or the workout lands, is dropped (AC30) or discarded. [unit + component]
20. **A workout gone from the server can be dropped, once.** `discardUnsentWorkout(workoutId)` removes the workout's ops and id-map entries (`dropWorkout`), its drafts and rest timer, its detail cache, and tracks `workout_discarded { phase: "unsent" }`. It is reachable only from the gone card (AC30). [unit]

### Phase B2 — the screens

21. **Finish is unlocked by unsent writes, and locked by refused ones.** Finish no longer waits for queued sets, notes or timer entries (06.2 AC16 amended). It is disabled while any op of the workout is `failed` (a set, note, round or result the server refused); the 06.4 in-flight guard, the zero-set rule and the structure lock still apply. A failed *finish* op does not lock it. One rule covers every way to finish (amended 2026-11-14, after Specs 17.1 and 17.4): the bar's Finish mode, the Workout menu's End workout early / Finish workout, and the Finish button of a workout with no plan. **The reason is said in two places.** The session's status line (17.4 AC10), while any op has failed, shows only `finishLocked(n)` — "{n} things couldn't be saved — fix them first" (n counts failed ops; singular "1 thing couldn't be saved — fix it first") — in place of 17.4's "… not saved yet" list (owner, 2026-11-14: the failure is what to act on, and the line stays within two lines at 320 px beside Undo); with only queued writes the line keeps the "not saved yet" text. The Workout menu's disabled End / Finish item gives `finishLocked(n)` as its reason, or "Log a set first". [component + harness]
22. **The Finish dialogs say what will happen.** With the browser offline, both dialogs show "No signal. Finish saves this workout on your phone, and it sends when you're back online with the app open." With unsent writes (online) they show "{n} sets haven't sent yet. They send first." The dialogs' other content (17.2) is unchanged. [component]
23. **Tapping Finish with no signal opens the summary with the saved-on-phone message.** The summary shows the stats, exercises and sets as for a finished workout, and a polite `role="status"` message that is, exactly, the §6.10 text `SAVED_OFFLINE` for `reason: "offline"`, `SAVED_SLOW` for `"slow"`, and `NOT_DURABLE` when `durable` is false (re-evaluated live from `OutboxState.durable`). The Finish dialog's choices travel with the op: the end time chosen at the tap, `keepRoutine` only when true, and (in `meta`) ended early and the unlogged planned set count (§6.2). [component]
24. **The summary has a waiting state.** While a finish waits: no personal-records block (the 17.6 record ledger and its first-time lines), no **Workout menu** (since Spec 17.6 B it holds both Edit workout and Delete workout; the line "You can edit this workout after it sends." sits where it was), no **Send to Hevy** section, and `/app/{workouts,history}/:id/edit` redirects to the summary. [component]
25. **Landing while the summary is open updates it in place.** The message is replaced by "Sent to the cloud." and the record ledger appears in place (Spec 17.6), the Workout menu and the Hevy section return, with no navigation and no flicker; for `ours` the records are fetched by workout id (08.0 AC7); for `elsewhere` the message is `SAVED_ELSEWHERE`. [component]
26. **The Workouts screen shows the waiting workout from storage.** With a finish op in any non-failed status, `/app/workouts` renders the waiting card **before** `GET /v1/workouts/active` answers and without waiting for it: "1 workout waiting to send", the started time and the exercise and set counts (from `meta`), **View workout** (to the summary) and **Retry now**; the status text is offline "No signal. It sends when the app is open and you have signal." or online "Sending…" (a polite region that announces a change of state, not each retry), plus "Keep this page open." when `durable` is false. No Start, no routines Start (AC18), no discard. Reopening with signal holds the card until the send finishes. [component]
27. **The one-time "saved" line.** When a finish lands while the summary of that workout is not open, the provider appends `{ workoutId, lifts, how }` to `sin:workout:landed` (§4), where `lifts` is the summary's own count: the lifts its heading counts in `buildRecordLedger` (Spec 17.6), which since minor 476 (Spec 17.6 AC6, owner 2026-11-14) are the lifts with a row that rose, not every lift the panel draws, or `null` for `ours` and `elsewhere`. The Workouts screen shows, above the Start screen, one link (a `TextLink`): "Your workout saved: new records on 2 lifts" (one lift: "Your workout saved: a new record"; `lifts: null` or 0 → "Your workout saved."), which opens that summary (owner, 2026-11-14: count lifts, as the summary does). The entry is removed when the link is tapped or dismissed, when the screen it was shown on unmounts, and when that workout's summary is opened by any route. A landing while the summary is open writes no entry. [component]
28. **Finished elsewhere is said, not hidden.** The `elsewhere` outcome shows `SAVED_ELSEWHERE` on the open summary, and on the landed line "Your workout saved." (the other device's end time and routine choice stand). [component]
29. **Reopen to fix.** When a finish op fails and the server still has the workout live (the cached active workout has its id), `ActiveSession` shows an error banner with the reason (§6.10 `REFUSED_*`: blocked by N failed sets, missing data with the rows flagged, the clock message, or "the server refused it" with the request id), the failed rows with their own Discard / Edit (06.2 AC14), and a Finish that works again once nothing else has failed. Tapping Finish again replaces the failed op (AC2) and goes through AC13. Nothing the server accepted is touched. [component]
30. **The gone card.** When a finish op has failed and the workout is *not* the server's active one (a `404`, or active answers `null` or another id), the Workouts screen shows "This workout couldn't be saved" with the reason "It was deleted on another device." and **Discard from this phone** behind a `ConfirmDialog`; confirming calls `discardUnsentWorkout` (AC20). Nothing else offers to throw a finished workout away. [component]
31. **The logout-guard dialog counts and words a waiting workout.** Profile's Sign out with a finish op waiting opens the warning ("1 finished workout hasn't sent. If you sign out now it'll be lost."), going through the same sync-then-warn machine as 06.5 (AC13–AC18 unchanged). [component]
32. **A forced sign-out is invisible to the data.** With a finish op waiting, `onAuthLost` leaves `sin:workout:outbox:<userId>` in storage (AC9); after signing in as the same user the waiting card shows and the finish sends; as another user, it does not. [component]
33. **Copy is static and in one file.** Every string in §6.10 lives in `workouts/messages.ts` (or `outbox/finishMessages.ts` re-exported from it); the only dynamic values are integers; no set value, exercise name, id or time is interpolated; the American spelling and plain-word rules hold. [unit scan]
34. **Accessibility.** The saved / sent message and the waiting status are polite live regions that persist across the change of state (one announcement per change); **Retry now**, **View workout**, the landed link and **Discard from this phone** meet 06.1 AC33's tap-target and contrast rules; focus after the tap lands on the summary's heading. Real focus behavior is checked on a phone (§10). [component + manual]
35. **Hygiene.** No new non-test module names `localStorage` / `sessionStorage`; the only new storage keys are `sin:workout:outbox:<userId>` and `sin:workout:landed`, both under `sin:workout:`; no workout id, time or count reaches `track`, `reportError` or the console except as AC12 / §9 list; the logout scan (no other file builds `logoutParams`) passes unmodified. [unit scan]

### Phase C — the browser test

36. **No signal, start to finish.** In a real browser against staging, with `context.setOffline(true)`: log three sets, tap Finish, see the saved-on-phone message; go back online; the workout lands with every set exactly once, in the order logged, with the end time the lifter tapped (not the time of sending), and the record cards appear. [e2e]
37. **Close and reopen with the API held back.** After an offline finish, reconnect, reload, and hold the workout and set endpoints with `page.route` (letting `GET /v1/me` through): the Workouts screen shows "1 workout waiting to send" and the outbox file holds the finish op; releasing the held requests lands everything and shows the one-time "saved" line. [e2e]
38. **The connection drops during the finish request.** Two runs: (a) the request is aborted before it reaches the server; (b) the server processes it and the reply is lost (`route.fetch()`, then offline, then abort). Both end saved exactly once, with the original end time; (b) is reconciled by the `409` as `ours`. [e2e]
39. **It cleans up after itself and runs where the smoke runs.** Every test starts from "no live workout" and deletes the finished workout it made (best effort in `afterEach`, by id); the file is `*.smoke.spec.ts` so the existing `pnpm --filter @sin/web run e2e` step and `e2e` CI job (staging, `E2E_AUTH0_*` secrets) run it; no CSP violation or console error across any test (06.3 AC2's guard). [e2e + CI]

## 4. Data model

No server-side tables or migrations. Browser-storage keys, all under the existing prefix `sin:workout:`:

| Key | Value | Written | Removed |
|---|---|---|---|
| `sin:workout:outbox:<userId>` (**new**, replaces the single key) | `{ v: 1, userId, ops, idMap }` — the same file shape as 06.2 §4 | after every op change | when empty; a deliberate sign-out of that user (or any sign-out that passes no user, AC9); a parse failure. **Kept** by a forced sign-out |
| `sin:workout:outbox` (legacy) | the previous release's file | never written again | adopted into the per-user key on first load (AC8); a deliberate sign-out |
| `sin:workout:landed` (**new**) | `{ v: 1, userId, items: [{ workoutId, lifts: number \| null, how: "landed" \| "ours" \| "elsewhere" }] }`, newest first, at most 5 | when a finish lands off-screen (AC27) | when shown and left, tapped, dismissed, or the workout's summary opens; every sign-out; a user mismatch or parse failure on load |

`FinishOp` (a member of `OutboxOpSchema`):

```ts
{ ...CommonShape, kind: "finish",
  body: { endedAt: string; keepRoutine?: true },          // exactly the PATCH body (10.5 AC13)
  meta: { startedAt: string; exerciseCount: number; setCount: number;
          endedEarly: boolean; unloggedPlannedSets: number; hadPlannedDuration: boolean } }
```

`CommonShape` already carries `id, workoutId, userId, status, attempted, attempts, nextAttemptAt, enqueuedAt, failure?`; the finish op adds `failure.blockedBy?` as a plain optional string for the cascade (AC2). `meta` is scalars only: what the summary card, the tracking call and the Hevy event need after a reload, with no names or values.

**Parse compatibility.** The file schema stays `v: 1` and gains one union member. (1) A file from the previous release has no `finish` op and parses unchanged. (2) A release that does not know `finish` but has Spec 10.7 AC66's tolerant reader skips the op and counts it (reporting once); it would then drop it on its next write — which is why the finish rides in a **new per-account key**: an older bundle after a rollback never reads, and so never rewrites, the new files (§11 rollback). (3) The legacy key is read once by the new release for adoption (AC8).

**Size.** A finish op is a few hundred bytes. The landed file is under 1 KB.

## 5. Screens & flows

*(UI spec — replaces "API surface". **No API change.**)*

### 5.1 Finish with no signal

1. The lifter taps **Finish workout**; the dialog says "No signal. Finish saves this workout on your phone, and it sends when you're back online with the app open." They tap **Finish**.
2. The dialog closes and the summary opens at once: the stats, the exercises and sets, no record cards, and the message `SAVED_OFFLINE` (§6.10).
3. They lock the phone. Later they open the app with signal; it signs in, loads, sends the unsent sets and then the finish. The workout's screen (or, on the Workouts tab, the card) changes: **Sent to the cloud.** and the record cards, or, if they are on the Workouts tab, the line "Your workout saved: 2 new records".

### 5.2 Finish with weak signal

The dialog's button stays busy for up to eight seconds while the sets and the finish try to send. If the finish lands in that time, the summary opens with records exactly as today. If not, the summary opens with `SAVED_SLOW`, and the op keeps trying; when it lands, the message becomes "Sent to the cloud." and the records appear.

### 5.3 While it waits

| Action | Behavior |
|---|---|
| Look at it | Yes: the summary (§5.1), and on Workouts the card "1 workout waiting to send" with **View workout** and **Retry now**. |
| Edit it | No, until it lands: "You can edit this workout after it sends." The edit route redirects to the summary. |
| Start a new workout | No, until it lands: "Your last workout hasn't sent yet. You can start a new one after it does." (Starting needs signal anyway, and with signal the queue sends first; this protects the server's one-active-workout rule.) |
| Send it to Hevy | No, until it lands (it is not in the cloud). |
| Sign out | Warned first (06.5): "1 finished workout hasn't sent. If you sign out now it'll be lost." |
| Throw it away | No — except after the server has refused it and no longer has it (§5.4). |
| Be force-signed-out | The workout and any unsent sets are kept for that account and send when that person signs back in. |

### 5.4 When the server says no

- **Refused, workout still live ("reopen to fix").** The in-progress screen is back with a banner: "Your workout is still open — it couldn't be finished. 2 sets couldn't be saved. Fix or discard them, then tap Finish again." (or the missing-data text with the rows flagged, or the clock text, or "The server refused it. Check your workout, then tap Finish again." with a request id). The good sets are untouched. Finish again replaces the failed attempt.
- **Gone from the server.** The Workouts screen shows "This workout couldn't be saved. It was deleted on another device." with **Discard from this phone** (confirm dialog). This is the only place a finished workout can be thrown away from the phone.
- **Finished on another device.** Treated as saved: "Your workout is saved. It had already been finished on another device, so this phone's end time wasn't used." Queued sets already landed on it (Spec 07.4); only this phone's end time and keep-routine choice are not used.

### 5.5 Reopening the app

With signal: sign-in, then the Workouts screen shows the waiting card from storage immediately (before the active read answers), then the send runs. Without signal: today's sign-in failure (non-goals); the data waits in storage.

## 6. Behavior & logic

### 6.1 The life of a finish

```
 Finish tap ──local check (AC17)──▶ banner, no op
     │
     ▼
 enqueueFinish ──persist──▶ queued ──(all earlier ops of the workout gone)──▶ sending
     ▲                         ▲                                                │
     │ tap Finish again        └──── retry (network, 5xx, 408, 429, 422-future) ◄┤
     │ (replaces)                                                               │
   failed ◄── 409 incomplete / other 4xx / 404 / earlier op failed ◄────────────┤
                                                                                 ▼
                               2xx = landed; 409 + same endedAt = ours; 409 + different = elsewhere
                                          └──▶ onFinishSynced: caches, drafts, tracking, Hevy event
```

`status` is the 06.2 set (`queued | sending | failed`); there is no new status. "Waiting" means `queued | sending`; "refused" means `failed`.

### 6.2 Representation: the op, the projection, the readers

- **The op.** Enqueued by `enqueueFinish({ workoutId, body, meta })`. `endedAt` is `finishEndedAt(...)` read **once at the tap** (so a wait of minutes cannot move it) and `keepRoutine: true` is added only when the one-off's box was checked (10.5 AC13). `meta` is filled from the dialog's own numbers (17.2's `finishStats`): `exerciseCount`, `setCount`, `endedEarly`, `unloggedPlannedSets`, `hadPlannedDuration`, `startedAt`. These travel with the op, so a reload cannot lose the choices.
- **Order.** The queue is first in, first out, so a finish enqueued after a workout's other ops sits behind them. The drainer additionally refuses to send a finish while any other op of its workout is in the queue (AC2), because the live-workout shortcut (06.2 AC4 amended) may pick the live workout's oldest op out of order. A failed earlier op fails the finish with it: otherwise the finish would succeed without a set the lifter believes is part of the workout, which is a silent discard.
- **Projection.** `project()` is unchanged for the active workout: `["workouts","active"]` is the live workout plus the outbox's set, note and timer overlays and **never** an unsent finish. A new pure `withQueuedFinish(workout, ops)` applies a non-failed finish op's `endedAt` (the builder lists every other field a finished `WorkoutDetail` has that a live one lacks, such as a derived duration, and tests it). Only `QueuedWorkoutClient.getById` calls it (AC16). The Workouts screen does not read the active workout to decide it is waiting; it reads the ops (AC26), so it works with the API held back.
- **`FinishedWorkoutScreen`.** It stays one screen. `Summary` gains a `waiting` input from `useWaitingFinish(id)`. 06.4 D1 is unchanged and still correct: the screen removes the active entry on mount when `finished`; with a waiting finish that is harmless because nothing reads that entry to decide waiting. The screen registers itself in `summaryViewing` while mounted, which is how the provider knows not to write a landed-line entry (AC27).

### 6.3 The tap, in order (`confirmFinish`)

1. `finishLock` as today; clear the banner.
2. Local check (AC17). On a hit: flag rows, banner, stop.
3. Compute `endedAt` once; build `body` and `meta`.
4. `useFinishWorkout.mutateAsync` → `client.finishOrQueue`:
   queued client: `enqueueFinish` (persist; `durable` is read after the write) → clear the rest timer → if offline, resolve `queued/offline` → else `whenFinishSettles(opId, FINISH_WAIT_MS)`: `"landed"` → resolve `landed` (effects have already run, AC14), `"pending"` → resolve `queued/slow`.
5. On `queued`: seed the detail cache with the projected finished copy (AC15); track `workout_finish_queued { reason }`.
6. `afterFinished()` navigates to the summary (as today), which shows the message from the resolved value, kept in router state (`{ saved: "offline" | "slow" }`) so a reload of the summary shows the persistent `waiting` message from storage instead (the message text is derived from the waiting state plus `durable`; the router state only picks offline versus slow wording).

`finishOrQueue` carrying the rest of today's `confirmFinish` error handling is gone: a network, timeout or server failure is the *op's* (AC3), so `confirmFinish`'s `catch` shrinks to programming errors. `confirmAlreadyFinished` is replaced by the op's reconcile (AC3); its idea (compare the re-read with what we sent) is reused.

### 6.4 Sending, timeouts and outcomes

`send(op)` gains the deadline (AC5): an `AbortController` per attempt; `setTimeout(SEND_TIMEOUT_MS)` aborts it and rejects a race with `ApiError.network`; the REST client forwards `{ signal }` to `api.request` (which already passes it to `fetch`, `api/client.ts`). An aborted `fetch` already maps to `ApiError.network`; the race covers a hung `getToken`. `FINISH_WAIT_MS` (8 s) is shorter than `SEND_TIMEOUT_MS` (20 s) on purpose: when the lifter's wait ends, the request is **not** cancelled; it keeps going and a late success shows up through the landing effects. A request whose outcome is unknown after an abort is replayed safely (the `409` reconcile, or the create's idempotency key).

### 6.5 Phone clock

A phone clock more than five minutes ahead makes `endedAt` fail the server's `endedAt ≤ now + 5 min` rule with a `422` whose field error is `{ path: "endedAt", message: RETIME_MESSAGES.future }`. Matching the static message (the API never returns a value in it, #57) lets `classify` retry it; it passes once real time catches up. Any other `422` is a refusal. (The start of a workout is bounded the same way, so this is rare.)

### 6.6 Landing effects (`onFinishSynced`)

In this order, so a waiter that resolves right after sees a consistent cache: (1) the detail cache from the response or re-read; (2) `applyFinishedCaches` (records seeded from `newRecords`, or removed so the summary fetches by workout id: 08.0 AC6 / AC7); (3) `["workouts","active"]` → `null` if it holds this workout (not `removeQueries`: 06.4 D1's warning is about the *mounted* observer, and a `null` is what the Workouts screen needs to show Start); (4) drafts and rest `clearWorkout`; (5) `track("workout_finished", { exerciseCount, setCount, durationMin, endedEarly, unloggedPlannedSets, hadPlannedDuration, queued, waitedMs? , viaReplay? })` from `meta` (`queued` is true when the lifter saw the saved message; `waitedMs` only then; `viaReplay: true` for `ours`; `elsewhere` tracks `workout_finish_elsewhere` instead); (6) if the summary is not viewing, `landedStore.add`; (7) `emitWorkoutFinished` for `landed` and `ours`, once per workout per page load. Nothing in (1)–(7) runs at the tap.

### 6.7 Reopen to fix

A refused finish does not change anything the server has. The state is derived, not stored: *the workout is in progress iff the server's active workout is it and no non-failed finish op exists.* A failed finish op leaves the active cache as the live workout (AC19), so the existing `WorkoutsScreen → ActiveSession` path renders it. `ActiveSession` reads `useWaitingFinish(workout.id).failed` and shows the banner (AC29). The failed finish op is the banner's memory; it is cleared by the next Finish tap (replace), by landing, or by the lifter dismissing the banner (removes only that op). Because `settle` keeps it (AC7), a `getActive` refetch cannot erase the explanation.

Why Finish is locked by *any* failed op of the workout (AC21), not only sets: a refused note, round or result is also data the lifter believes is saved; finishing past it would leave it behind with no row to point at once the workout is "finished".

### 6.8 Sign-out: forced, deliberate, another person

- **Forced** (`useApi` → `onAuthLost`, i.e. a lost session or a double `401`): `logoutAndClear(logout, storage, "forced")` → `blockUserDataWrites()`, `clearUserData(storage, { keep: isOutboxFile })`, Auth0 logout. The kept files are valid because ops are bound to `Me.id` (06.2 D12); the writes are blocked afterwards, but the last persisted file is always a state from which replay is safe (a create replays by key, a finish by `409`, a note or timer entry is a keyed replace).
- **Deliberate** (the guard's "Sign out anyway", and a sign-out with nothing unsaved): `useSession().logout` passes the signed-in `userId`; that user's file and the legacy key go, other users' files stay.
- **Other callers** (`AuthError`, the account-deleted screens): no `userId`; every outbox file is cleared as before.
- **Another person on the same phone** signs in: their store loads only their key (AC8). The first person's unsent workout stays stored (accepted by the owner for a shared phone) and sends when they sign back in.

### 6.9 The one-time "saved" line

The lifter may be anywhere when a finish lands. If the summary for that workout is open (`summaryViewing`), the in-place message handles it (AC25) and nothing is stored. Otherwise the provider calls `landedStore.add` and the Workouts screen shows the first entry whose `userId` matches. "Remembers it was shown" is the entry's removal (AC27): on tap, on dismiss, when the screen it was shown on unmounts, and when that workout's summary opens. A storage failure here is reported once (`{ source: "workout-storage" }`) and the line is simply not shown; the workout is in the cloud either way.

### 6.12 The browser test (Phase C)

**File.** `apps/web/e2e/offline-finish.smoke.spec.ts`, matched by the existing project's `testMatch: /\.smoke\.spec\.ts/`, using the `mobile-chromium` project and the saved login (`storageState`), so `auth.setup.ts` and `playwright.config.ts` are unchanged. It follows the smoke's conventions: `installGuards` (CSP and console errors, 06.3 AC2), `warmApi`, `NAMES` / `EXERCISES`, `openDialog`, `logBar`, `makeCurrent`. Because Playwright runs files alphabetically with one worker, it runs before `session.smoke.spec.ts`; each test leaves the user with no live workout and no leftover finished workout, so order does not matter.

**Helpers added to `helpers.ts`.** `discardLeftoverWorkout(page)` (the smoke's "clean slate" step extracted; the smoke calls it), `startWithSets(page, sets)` (start, add the first exercise, log N sets), `holdApi(page, { allow })` (a `page.route("**/v1/**")` that parks every request whose path is not allowed, returning `{ release(), count() }`), `dropFinishReply(page, context, mode)`, `outboxOps(page)` (counts ops across every `sin:workout:outbox:*` key; `pendingOutboxOps` is rewritten on top of it, since the key is per account now), `deleteFinished(page, id)`.

**Making the record assertion deterministic.** The test user's history is unknown, so each set is logged heavier than any real one (500 in the profile's unit): a first-record or heaviest-weight card is then certain. The record cards are asserted, never their values.

**Holding the API back.** `page.route` intercepts the browser's requests before they leave; a parked request is simply not continued. Auth0 is on another origin (`/oauth/token`, `/authorize`) and unaffected. The hold lets `GET /v1/me` (and the exercise catalog reads) through, because the app does not render any protected screen until `/v1/me` answers (04.0); everything under `/v1/workouts`, `/v1/workout-exercises`, `/v1/sets` and `/v1/personal-records` is parked. The held send times out after 20 s and is retried; the test releases well before that (4–6 s).

**Cutting the network mid-finish.** `context.setOffline(true)` takes the whole browser context offline and fires the page's `offline` event, as airplane mode would. For mid-finish: `page.route("**/v1/workouts/*", handler)` matching the `PATCH` whose body has `endedAt`. Variant (a): `await context.setOffline(true); await route.abort("failed")` — the server never saw it. Variant (b): `const reply = await route.fetch()` (the server processes the finish), record `reply.json().endedAt`, then `setOffline(true)` and `route.abort("failed")` — the reply is lost. Both reconnect after a wait longer than the backoff's first step and assert the result.

**Asserting the real end time.** The test records `before = Date.now()` and `after = Date.now()` around the Finish click, listens to the wire (`page.on("request")`) for the finish `PATCH`, and asserts `before ≤ Date.parse(body.endedAt) ≤ after + 1 s` **and** that the request was sent at least 5 s after `after` (so a send-time stamp would fail). It also reads the response's `endedAt` and asserts equality (for variant (b), from the `route.fetch()` reply).

**Asserting exactly once, in order.** After landing, the test reloads (fresh read from the server), opens `/app/history/<id>` and asserts the card's list items equal the logged sets in order (distinct reps 5, 6, 7), and that History has exactly one row for the id.

**Cleanup on staging.** `afterEach` (best effort, wrapped so it never masks the failure): go to `/app/history/<id>` (the id is read from the summary URL the moment it opens, offline included), Workout menu → Delete → confirm; if the test died earlier, the next test's `discardLeftoverWorkout` removes a live leftover; an orphaned *finished* workout (a failure between landing and cleanup) is deleted by hand from History, and the runbook says so.

**Same CI job.** Yes: the existing `e2e` job runs `pnpm --filter @sin/web run e2e`, which runs every `*.smoke.spec.ts`; the job already has the staging URLs, the `E2E_AUTH0_*` secrets (scoped to that step), the concurrency group that serializes runs on the one test user, and the failure-only artifact. A second job would repeat the login and the install for no isolation gain. Expected added time: three to five minutes (staging cold starts included). Retries stay at 1; every test is self-cleaning so a retry starts clean.

## 7. Security & privacy

- **New data at rest.** `localStorage` now also holds an unsent finish: a timestamp, a boolean, the workout id and a few counts (no names, no set values beyond those already in the outbox). The same class as 06.2 §7; under `sin:workout:`.
- **Kept after a forced sign-out — the one real change.** 06.0 AC20 ("a forced logout leaves no user data on the device") is relaxed for **outbox files only**, by the owner's decision, so a lost session cannot destroy a workout. Cost, accepted by the owner: on a shared phone, one person's unsent sets and finish stay stored after they are signed out. Mitigations: files are per account and bound to `Me.id` (a different user never loads or sends them, AC8); they hold no catalog, no profile and no Hevy key; a deliberate sign-out by that person clears them; the catalog, recents, drafts, rest timer and Hevy key are cleared on every sign-out as before.
- **No cross-user replay.** Ops carry `userId`; the per-account key adds a second wall.
- **No new ingress.** Stored values are zod-parsed on load; the server revalidates every body. The `endedAt` is client-chosen but bounded server-side (`startedAt ≤ endedAt ≤ now + 5 min`), and an attacker who controls the browser could already set it.
- **Observability hygiene.** Events carry reasons, statuses and integers only (§9).
- **The Hevy event.** Nothing reaches Hevy for a workout that is not in the cloud (AC14, AC15).

### Resolved in this draft (builder's questions from the brief) — each is **(this draft)**

- ✅ **D1 — A waiting finish is a new `finish` outbox op, in the same file.** **(this draft)** **Rationale:** ordering, retry, backoff and persistence are the outbox's job and are already tested; a side flag would need a second ordering rule. **Alternatives rejected:** a separate "pending finishes" store (two queues, two sort orders, two guards); sending the finish beside the sets (can land first). **Consequence:** every consumer of "unsaved" must exclude or count it deliberately (AC1, AC11, AC12).
- ✅ **D2 — The op is `{ kind: "finish", body: the PATCH body, meta }`, `meta` scalars only.** **(this draft)** **Rationale:** `body` is exactly what 10.5 AC13 and 18.0 pin, so nothing about the wire changes; `meta` lets a reload keep the Finish dialog's choices (ended early, unlogged planned sets, the card's counts). **Consequence:** the schema gains one union member; `v` stays 1.
- ✅ **D3 — The storage key becomes per account: `sin:workout:outbox:<userId>`, with legacy adoption.** **(this draft)** **Rationale:** the single key held one user's file and a second user's first write overwrote it, which would destroy the data the owner wants kept after a forced sign-out; the new key also makes an older bundle ignore finish ops after a rollback. **Alternative rejected:** one multi-user file (an older reader would fail to parse it and drop it). **Consequence:** the e2e helper and the conflict watch read the new key (A).
- ✅ **D4 — The unsent finish is projected only into the summary (`getById`), never into `["workouts","active"]`; "waiting" is read from the ops.** **(this draft)** **Rationale:** the active entry drives `WorkoutsScreen` → `ActiveSession` and 06.4 D1's cache dance; putting `endedAt` there would make a refused finish a state to un-project. Reading the ops also lets the Workouts card render with the API held back. **Alternative rejected:** project into `active` (the screen would need a third branch inside the query's data).
- ✅ **D5 — "Reopen to fix" is derived, not stored:** a failed finish op is ignored by every projection, so the live workout simply renders `ActiveSession`, with the failed op as the banner's memory; `settle` keeps it. **(this draft)** **Rationale:** the least state; nothing to flip back.
- ✅ **D6 — The rest timer is cleared at the tap; drafts are cleared at landing.** **(this draft)** **Rationale:** the timer is meaningless once the workout is over; drafts are the lifter's typing and a refused finish reopens the workout, so they must survive until the cloud has it.
- ✅ **D7 — `FINISH_WAIT_MS = 8000` and `SEND_TIMEOUT_MS = 20000`.** **(this draft)** **Rationale:** eight seconds is the longest a lifter will watch a busy button at the end of a workout and matches the sign-out wait (06.5 `SYNC_WAIT_MS`); twenty seconds lets a slow but working request finish after the wait ends (the request is not cancelled at eight). Both are first guesses to tune after the phone week. **Consequence:** a finish that takes 9 s shows "saved on this phone" and turns into "Sent to the cloud." a moment later; the wording is true both ways.
- ✅ **D8 — The Finish dialog's choices:** `endedAt` fixed once at the tap, `keepRoutine: true` only when checked, the rest in `meta`. **(this draft)**
- ✅ **D9 — The Hevy event fires for `landed` and `ours`, not `elsewhere`; at most once per workout per page load.** **(this draft)** **Rationale:** a workout finished on another device is that device's to send; `createOnly` and the link claim make a duplicate harmless, but not emitting is simpler and cheaper.
- ✅ **D10 — Landing effects live in the provider's `onFinishSynced`, once, before waiters resolve; `useFinishWorkout` has none.** **(this draft)** **Rationale:** the wait and the op can both complete; one owner of the effects makes a double emit impossible by construction.
- ✅ **D11 — Per-account kept files; the forced path keeps all outbox files, the deliberate path clears the signed-in user's and keeps others'; callers with no user clear all.** **(this draft)** **Rationale:** "Only 'Sign out anyway' clears" is about the person in front of the phone; clearing someone else's unsent workout from a second person's sign-out would be the loss the owner fears. - ✅ **D12 — The "saved" line is stored in `sin:workout:landed` and removed when shown-and-left, tapped, dismissed or its summary is opened; none is written if the summary is open.** **(this draft)** **Rationale:** one key under the existing prefix; no state machine; the failure mode (a missed line) costs nothing because the workout is in the cloud.
- ✅ **D13 — Finish is locked by any failed op of the workout, not only sets;** a `404` on a note / round / result op is a failure (not "done") while a finish waits. **(this draft)** **Rationale:** the brief's rule ("locked while a set has been refused") protects against leaving data behind; the same logic holds for the other op kinds, and trap 2 (silent 404 drops) is only closed if they fail. **Consequence:** an exercise removed on another device with a note pending now shows one "couldn't be saved" row; the lifter discards it.
