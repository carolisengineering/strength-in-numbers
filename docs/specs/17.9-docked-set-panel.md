# Spec 17.9 — Docked set panel: the current set stays above the nav, the list scrolls above it (web)

**Status:** v0.1 draft (2026-11-08). Not implemented. **This is a draft that needs a mockup and an owner decision before any implementation.** The agreed plan is to mock it up and decide after Specs 17.4, 17.7 and 17.8 have shipped and been used on the phone. The first open question (§12 Q1) is whether it is still worth building at all.

**Source:** the whole-app Impeccable critique of 2026-11-08 (23/40), step 5 of its agreed fix order. The owner likes the large numbers and buttons and wants them kept.

**Kind:** UI (web only). **No API, `@sin/core`, migration, CSP or env change; nothing is deferred to the API.** Three phases, each its own PR, after a Phase 0 that writes no code: **0** a mockup and the owner's decision; **A** the docked panel for logging; **B** correcting a logged set in the same panel.

**Depends on:** 17.4, 17.7 and 17.8 shipped (the 56 px Log button and status line, the Warm-up and More row, centered labeled steppers, the panel label with rest). Spec 17.1 (the "now" screen, `logAction`), 06.5 (drafts), 10.1 / 10.3 (supersets, sections), 10.7 (timed sections), 18.0 (the edit screen, which keeps its sheets), `ui/visualViewport.ts` (#204, #206, #207).

**Design refs:** `apps/web/PRODUCT.md` (principle 1: the next set comes first), `apps/web/DESIGN.md`, `apps/web/CLAUDE.md` (Workout screen "now", iPhone keyboard frame).

## 1. Purpose, scope & non-goals

**Purpose.** Today the current-set panel is the last thing inside the current exercise's card, so after a log the lifter scrolls to find it (17.4 AC14–AC16 scroll it back into view) and the exercise name, the target and the rest readout scroll away with the card. A fixed panel above the nav would make the controls always in the same place, so a set is "same spot, thumb, tap". Correcting a logged set would use the same panel, instead of a sheet that opens a different form.

**The idea.**

```
┌ header ──────────────────────────┐
│ scrolling list                   │  cards show name, target, logged rows
│  ...                             │
├ docked panel ────────────────────┤  fixed, above the nav
│ Overhead Press        Rest 1:42  │  label: exercise, set, target, rest
│ Set 2 of 4 · target 6–8          │
│ [−5]     47.5 lb         [+5]    │  weight row
│ [−1]       6             [+1]    │  reps row
│ [Warm-up]  [More]                │
│ 1 set not saved yet              │  status line (17.4)
│ [        Log 47.5 × 6          ] │  56 px
├ nav ─────────────────────────────┤
```

**In scope**
1. The panel and the session bar leave the scrolling card and sit in a slot between the scroller and the nav.
2. A compact form for short viewports and an inline fallback below that.
3. The keyboard-up frame, focus visibility (WCAG 2.4.11) and zoom.
4. Tapping a logged row loads that set into the panel to edit, with Save, Cancel and Delete (under More).

**Non-goals**
- The edit screen for finished workouts (18.0) keeps its sheets and `EditSetForm`.
- Undo and protecting Delete set (17.5): this spec only places Delete.
- Timed-section result entry (10.7): the Log result sheet is unchanged.
- Any new data, request or event.
- Wide-screen layouts beyond keeping the dock in the 40rem column.

## 2. Acceptance criteria

These describe the behavior if the owner decides to build it (Q1). They are numbered by phase so a phase can move without renumbering.

### Phase 0 — mockup and decision (no code)

1. **A mockup exists.** A static mockup (outside `src/`) shows the docked panel at 390 × 844, 320 × 568, and 390 × 844 with the keyboard up, in light and dark, for: weight × reps, a duration exercise, a carry, calories, rest running and at "Ready", editing a logged set, the compact form and the fallback. It states where Weight and Reps captions and the unit go in a row (§5.2).
2. **The decision is recorded.** The owner's answer to Q1, made against the criteria in §12, is written into §12 as ✅ or ❌ with a date. Phases A and B are not started without a ✅.

### Phase A — the docked panel

3. **A slot, not an overlay.** In docked mode `AppShell` has a slot between `<main>` and the nav. The current exercise's `EntryRow` and the session bar (status line and Log) render into it. The scroller's bottom edge equals the slot's top edge, so nothing in the list sits under the dock (harness, at 390 × 844, with the status line shown, with More open and with a rest running).
4. **Focus is never obscured (WCAG 2.4.11).** Focusing each focusable element in the list leaves it fully inside the scroller's rectangle, above the dock (harness). No `scroll-padding` for the dock is needed, because the scroller ends at the dock; 17.4's `--session-bar-clearance` remains for the fallback.
5. **Rows, in order.** Label (exercise, set, target, rest), the measure rows for the modality (17.8's steppers or fields), Warm-up and More, the status line, Log. 17.4's reserved status line and 56 px button keep their behavior: the button's top is at the same y with no message and with one (harness).
6. **Height budget.** At 390 × 844 the weight × reps dock is at most the §5.1 figure and the list keeps at least `--dock-list-min` (10rem). The mockup may revise the figure; the harness asserts the revised one.
7. **Compact form.** Below a viewport height of 41.5rem and down to 36rem, the dock uses a compact layout (§5.1): one label line, 56 px rows, no caption lines. The steppers keep their 44 px minimum targets.
8. **Inline fallback.** Below 36rem tall (and in landscape on a phone), nothing is docked: the panel is back in the card and the bar is the sticky bar, exactly as 17.4, 17.7 and 17.8 left them, with `--session-bar-clearance` and the scroll to the panel after a log. The mode comes from `matchMedia` on the same two literals as the CSS; one component (`EntryRow`) serves both mount points.
9. **Mode change keeps the draft.** Crossing a threshold (rotation, a resized window) remounts the panel. The draft survives through 06.5's draft persistence if edited, and re-seeds if not; focus may be lost once.
10. **The seam.** The dock mounts `EntryRow` for the current exercise, keyed by exercise id; it still publishes its action to the `logAction` store; `ExerciseCard` renders `EntryRow` only in the inline fallback. `seedDraft` stays called only from `setDraft.ts` and `EntryRow.tsx`.
11. **One button element.** The bar's button is the same `LogBarButton` across Log, Finish and Add modes (17.1 AC29, AC39). The portal target of the bar is the slot in docked mode, so a transition from Log to Finish after the last planned set keeps focus on it. In Finish mode the panel stays with its secondary "Log extra set" (17.1 AC27); with no exercise, only the bar shows.
12. **Superset alternation.** After a log in a superset, current moves to the partner (17.1 AC15): the dock's label and fields change, the card list expands the partner, focus stays on Log, and the 600 ms double-tap window holds across the swap.
13. **Other modalities.** Duration, distance, carry and calories panels fit with no more height than weight × reps (they have one or two measure rows), and 17.8's steppers and centered fields render unchanged.
14. **Timed sections.** A timed section's "Log result" sheet opens above the dock and returns focus to its opener; the "N timer entries not saved yet" message joins the status line (17.4 AC11).
15. **Keyboard up.** With `data-keyboard="open"` the nav is hidden as today and the dock is the bottom of the visible frame (`--app-top`, `--app-height`). Its `max-height` is the frame's height minus the header; if it is taller it scrolls inside itself, and the focused field is scrolled into view inside the dock. An empty status line takes no space (17.4 AC12).
16. **Rest.** `RestLine` stays the 3 px sticky line at the top of the scroller. The rest figure and "Ready" (17.8) are in the dock's label; the label row's height does not change when a rest starts or ends.
17. **No scroll after a log.** In docked mode a log scrolls nothing (17.4 AC14–AC16 apply only to the fallback). After an advance, the new current card is revealed in the list as 17.1 AC11 does.
18. **`.bar` rules.** The session bar in the slot keeps the `ActionBar` rules that matter (`.bar > button { flex: 1 }`, the hint's full-width basis); the panel is not inside `.bar`. No other screen's bar changes.
19. **Zoom.** At a 640 × 360 CSS-pixel viewport (a 1280 × 720 window at 200%) and 320 × 256 (400%), the fallback applies, nothing is clipped or hidden, and there is no two-dimensional scroll (WCAG 1.4.4, 1.4.10).
20. **Regression guards.** Draft persistence, offline queueing and "Not saved yet" on rows (17.1 AC34), one primary `Button`, the Set rows' tags, and every 17.4, 17.7 and 17.8 behavior (in the fallback or the dock) are unchanged. Existing tests change only where this spec amends a criterion.

### Phase B — editing a logged set in the panel

21. **Load.** In docked mode, tapping a logged row on the current card loads that set into the panel: the label reads "Editing set 2 · Overhead Press", the fields are prefilled by `draftForEdit`, the row shows a selected state (`aria-pressed` and a visible fill, never color alone), the bar's button reads "Save 47.5 × 8" (`aria-label` "Save 47.5 × 8, set 2 of Overhead Press"), a Cancel button sits with Warm-up and More, and Delete set is inside More.
22. **Save.** Sends only what changed (`diffForPatch`); nothing changed sends no request and returns. Success returns to the new-set panel. Failure shows the message in the dock and stays in edit mode with the typed values (as the sheet does).
23. **Cancel keeps the next set.** A value typed into the new-set draft before tapping a row is still there after Cancel or Save. The draft is flushed to storage before the new-set panel unmounts (06.5) and restored as an edited draft.
24. **One edit at a time.** Tapping another logged row while the edit has unsaved changes does not discard them (§12 Q3, recommendation); with none, it switches rows.
25. **Delete.** Delete set is under More while editing, and uses 17.5's inline confirm ("Delete set 2? … Keep set"), shown inside the dock in place of the Save row; this spec only moves it. Until 17.5 ships it is today's `useDeleteSet` behavior.
26. **Row kinds.** "Needs data" rows, a failed row's Edit button (422) and a not-yet-saved row load into the dock like any other, through the same `useUpdateSet` the sheet uses.
27. **No rest or log side effects.** Saving an edit neither starts nor clears the rest timer and sends no `set_logged`; the update emits what the sheet's did.
28. **The double-tap window.** A second tap within 600 ms of Save that would land on a different panel is the same tap (`LogBarButton`'s owner check), so a double-tap on Save never logs a set.
29. **Fallback and edit screen.** In the inline fallback, tapping a row opens `SetEditSheet` as today. The edit screen for finished workouts is unchanged.

### Docs and verification

30. **Docs consistent.** The cross-doc updates in §12 are made.
31. **Every behavioral AC has a tagged test.** AC3–AC20 (except harness-only AC3, AC4, AC6, AC7, AC15, AC16, AC19) and AC21–AC29 have at least one test named `17.9 ACn — …`, enforced by an `acTags.17-9.test.ts` scan.
32. **Visual review.** `pnpm --filter @sin/web run screens` captures the dock in the forms of AC1, light and dark, at 390 × 844, 320 × 568, 1280 px and the keyboard-up fake (`01k`).
33. **Phone check (owner).** On the iPhone, a full workout with a superset, a duration exercise and a correction: the dock never covers a control, the keyboard case works, rotating does not lose a draft, correcting a set feels like logging one.

## 5. Screens & flows

### 5.1 The numbers

Measured from the 2026-11-08 capture of main at 390 × 844 (`01-workout-active.layout.json`): the scroller is 709 px tall, so the header is about 68 px and the nav about 67 px (844 − 709 − 68). The nav height at 320 px and the iPhone's home-indicator inset are **not** measured (the capture is Chromium, with no inset); the harness must measure them. Today one measure block (caption 21 + gap 4 + input 60 + unit 21) is 106 px, and two blocks sit 118 px apart.

| Dock form | Rows | Height | List at 390 × 844 (709 − dock) | List at 320 × 568 (433 − dock) |
|---|---|---|---|---|
| Today's blocks, docked as they are | pad 12 + label 45 + gap 12 + blocks 106 + 12 + 106 + gap 12 + Warm-up/More 44 + gap 12 + status 44 + gap 4 + Log 56 + pad 12 | 477 | 232 | none (negative) |
| Captions and unit folded into 60 px rows | pad 12 + label 45 + 8 + 60 + 8 + 60 + 8 + 44 + 8 + status 44 + 4 + Log 56 + pad 12 | **369** | **340** | none (87) |
| Compact | pad 8 + label 24 + 6 + 56 + 6 + 56 + 6 + 44 + 6 + Log 56 + pad 8 (status empty) | 276 | not used | 157 (109 when the status line shows) |

What follows from them:
- Docking today's blocks as they are leaves 232 px at 390 × 844, about one card. So the dock only works if each row drops its separate caption and unit lines (§5.2). The design review's rough figure for the panel was 356 px; this table gets 346 px with a 21 px status line, and 369 px with the 44 px one.
- 340 px of list is the current card with three logged rows (about 256 px: header 76, three rows at 52, padding 24) and one collapsed neighbor.
- At 320 × 568 the full dock leaves 87 px, which is not a list. The compact form leaves 157 px (132 px when the status line shows), 3 px short of `--dock-list-min` (160). So a 568 px tall screen falls just under the compact threshold and lands in the inline fallback unless the mockup trims the compact form by a few pixels; the mockup and the harness decide.
- Thresholds follow from the list minimum: full needs about 369 + 160 + 135 = 664 px, so `min-height: 41.5rem`; compact needs 276 + 160 + 135 = 571 px, so `min-height: 36rem`. These two literals are in the media query and in `useDockMode` (a CSS custom property cannot be used in a media query); a test pins that they are equal.
- The status line is 44 px (`--session-status-height`, owner, 2026-11-08; Spec 17.4 D5), and these figures use it.
- Keyboard up: the frame is 844 − K tall and the nav is hidden, so the list is 776 − K − 369. K, the keyboard's cover, is not observed on a real phone here; for K = 300 the list is 107 px, and the dock never exceeds frame − header (AC15).

### 5.2 Rows without caption lines (to settle in the mockup)

The 369 px figure needs Weight and Reps captions, and the unit, to share the 60 px row. Candidates for the mockup: the caption as a small label above the figure inside the row's box with the unit beside the number; or the unit drawn inside the field's right edge, with the visible caption kept (the label is required by WCAG 3.3.2 and 2.5.3, so it cannot be hidden). This is a design question and not decided here.

## 6. Behavior & logic

### 6.1 The mode

`useDockMode()` reads two `matchMedia` queries and returns `"full"`, `"compact"` or `"inline"`. `ActiveSession` chooses the portal target from it. `data-keyboard` does not change the mode: iOS keeps the layout viewport's height when its keyboard opens (`ui/visualViewport.ts`), so the media queries do not fire; the frame variables drive the keyboard case (AC15).

### 6.2 Why a slot, not `position: sticky`

A sticky bar inside the scroller overlays the list, so every focus reveal needs a `scroll-padding` that equals the bar's height, and the panel's height changes (status line, More, a rest label that wraps, keyboard). A slot makes the scroller end at the dock by layout, so focus and `scrollIntoView` cannot land under it, and WCAG 2.4.11 holds without a measured number.

### 6.3 `EntryRow` outside the card

`EntryRow` needs `exercise`, `unitPreference`, `onGone`, `onLogged` and `logExtra`, all of which `ActiveSession` already holds for the current exercise. The `logAction` store is the seam: the panel publishes `{ label, ariaLabel, disabled, busy, run }` and `LogBarButton` reads it, wherever each is mounted. A dock-edit publisher adds the Save action in Phase B; `LogBarButton` gains no logic but a `save` label (the owner check already covers the double-tap).

### 6.4 Edit mode

An `editingSetId` in `ActiveSession`'s state (or a small store) swaps the dock's content: `EntryRow` unmounts (its edited draft is already stored by 06.5) and a `DockEditForm` mounts with `draftForEdit(set, defaults)` and `useUpdateSet` / `useDeleteSet`. On Save or Cancel it unmounts and `EntryRow` mounts, restoring the stored draft as a touched one. Because the logged rows exist only on the current card, an edit is always of the current exercise.

## 12. Decisions & open questions

**Settled (owner, 2026-11-08, accepted recommendation): each recommendation below was taken.**

1. ✅ **Is it still worth building after 17.4, 17.7 and 17.8? Not yet (owner, 2026-11-08): decide after one week of real workouts with those three shipped.** Those specs fix the biggest costs (a carried next set, a 56 px Log button that stays put, the panel scrolled into view, centered labeled steppers, no dropdowns), and this one is the largest change, with a permanent second layout (the inline fallback) to keep. The phone check can answer it:

   | Question | Build A if | Build B if |
   |---|---|---|
   | In a workout of 15+ sets, how many times did you scroll to reach the panel or lose the exercise's name? (a tally) | more than 1 in 5 sets | |
   | How many logged sets did you correct, and did the sheet feel like a different tool? | | 2 or more per workout, and "unfamiliar" |
   | Median `set_logged.msToLog`, before and after (if telemetry is on) | informational: it should not rise | |
   | What is your phone's viewport height in CSS pixels, and does the mockup leave 4+ rows of list? | the mockup leaves at least `--dock-list-min` on it | |

   If the first answer is "rarely" and corrections are under two per workout, the answer is ❌. If only the first is yes, build Phase A alone.
2. ✅ **Where do the captions and units go in a row?** (§5.2) Needed for the 369 px figure. *Recommendation:* caption small above the figure, inside the row, the unit beside the number; decide on the mockup.
3. ✅ **Tapping another row while an edit has unsaved changes.** *Recommendation: keep the current edit and do nothing* (Save and Cancel are adjacent), so a half-made correction is never silently lost. The alternative, switching and discarding, is faster and loses a change.
4. ✅ **Should small phones fall back?** *Recommendation: yes, the inline fallback below 36rem tall* (§5.1). It costs a second layout forever; the alternative is a docked panel with only the Log button and a "Set" expander on short screens, which is a third layout.

**Decisions proposed here (for the mockup)**
- ✅ **D1 — A slot, not an overlay** (§6.2). (owner, 2026-11-08, accepted recommendation).
- ✅ **D2 — The inline fallback stays.** A height below the compact threshold, landscape phones and 200% zoom cannot hold a dock without hiding the list; the fallback is the layout 17.4, 17.7 and 17.8 already ship, so it is already tested.
- ✅ **D3 — Phase B follows Phase A and may not ship.** Editing in the dock is the larger part of the change and its value (same muscle memory) is separable.
