## 1. Purpose, scope & non-goals

### 1.1 Purpose

Bring Carol's Hevy history, the routines she picks and her custom exercises into SIN, once, safely. She presses **Import from Hevy**; the app reads everything from Hevy, asks only about what it cannot decide (routines to copy, exercises it cannot pair), shows a summary of exactly what will happen and what will be skipped or dropped, and then does it, in batches, showing progress. If the tab closes or the signal drops, running it again finishes the job and never duplicates.

**Success:** on staging, with her real key, the summary says "1,013 workouts: 960 will be imported, 41 already in SIN (matched), 8 skipped"; every skipped workout and every dropped set is listed by date and title with a reason; after the run, History, the records and the charts show the full history; running the import a second time reports "0 to import, 1,013 already in SIN"; and the Hevy key never reached SIN.

### 1.2 In scope

**Phase A (PR 1)**
- The Hevy screen's **Import from Hevy** card, the screen `/app/profile/hevy/import`, its pure session model (§5, §6.1).
- Preflight: key, mapping, markers, time zone and unit lines (§6.2).
- Reading Hevy: templates, folders, routines, workouts, with progress and reconciliation against Hevy's own count (§6.3).
- The routine checklist by folder with the cap room (§5.3, §6.4).
- The names step through `PairingCards` and `savePairings` (§6.5).
- The summary from a server dry run (§5.5, §6.6).

**Phase B (PR 2)**
- The run: batches, pacing, stop, pause, resume (§6.7); the finish step (§6.8); the routines step (§6.9); caches (§6.10).
- The done screen and the report download (§5.7, §6.11).
- The leave guard, the stale-records banner, harness, phone check.

### 1.3 Non-goals (and where they live)

| Not here | Lives in / why |
|---|---|
| Fetching new Hevy workouts after this import | Design "later" (Hevy's events feed) |
| Hevy's CSV export as a source | Design "later" |
| Writing to Hevy | 20.2 |
| Importing routine folders as anything | Design non-goal; folders only group the checklist |
| Per-workout choices ("import this, not that") | Design: all workouts; skips are rule-driven and reported |
| Un-importing from the UI | An operator statement in the runbook (19.1 §11); the import is one-time |
| Background import with the app closed | Needs a server-held key (design future option 1) |
| Keeping the screen awake | D7 |

### Fit for one work session

Phase A is a reducer, three reads, two existing components and one dry-run loop. Phase B is a batch runner with failure handling plus two small steps. Two PRs at the phase boundary.

## 2. Acceptance criteria

Every behavioral criterion has at least one test tagged **`"20.1 ACn — …"`**; `acTags.20-1.test.ts` checks the tags for unit-tested ones. §10 maps each to a method. "The run" is the real import; "the summary" is the dry-run result screen.

### Phase A: read, choose, pair, summarize

1. **Entry.** The Hevy screen shows an **Import from Hevy** card (to `/app/profile/hevy/import`) only with status `200`; without a stored key the card says "Add your Hevy key first" and the route renders 20.0's key card (`HevyKeyCard`) instead of the flow. The route is inside the protected layout and `NotFound` when the status is not `200` (20.0 AC1).
2. **Preflight.** The first screen states, before anything is read: that the import reads all your Hevy workouts and can take several minutes; that the tab must stay open and online; that dates use **this device's time zone** (`Intl` zone name shown) and, if it differs from the Profile zone, says so with a link to Profile; that weights are stored in the Profile unit (`kg` or `lb`); and that running it again is safe. A **Start** button begins reading. If `GET /v1/hevy/status` reports `recordsStale: true`, a banner above offers **Finish the last step** (calls `POST /v1/hevy/import/finish`, §6.8) first; it is one component (`StaleRecordsBanner`) shared with the Hevy screen (AC22).
3. **Reading Hevy.** In order: `GET /v1/workouts/count` (20.0 AC8's `workoutCount`; the client gains no other method), exercise templates (`pageSize=100`), routine folders, routines, workouts (`pageSize=10`, page 1…n), each through `listAll` on the shared pacer, each with a visible stage line and "page x of y". **Cancel** aborts at once and keeps nothing; a second **Start** reads from empty, and late replies of the cancelled read are ignored (a read generation counter on every I/O action). Everything read is held in memory only: no `localStorage` key, no `USER_DATA_KEY_PREFIXES` change, no cache entry with an infinite `gcTime`.
4. **Reconciliation.** When reading ends, the number of distinct workout ids read is compared with `workout_count`; a difference shows "Hevy reported {n} workouts but sent {m}. Workouts added or removed while reading can cause this; run the import again later to catch up." and the flow continues with what was read. Duplicate ids across pages are counted once.
5. **Read failures.** A page that still fails after the client's retries stops the read at "Couldn't finish reading Hevy" with the stage, **Try again** (restarts that stage) and **Cancel**; a `bad_key` ends at the key prompt; an `unexpected_reply` says "Hevy's reply wasn't understood" and stops (nothing partial is carried forward); offline pauses with the network sentence and a **Try again**.
6. **The request mapping.** `toImportWorkout(hevyWorkout, { zone })` (pure, `importRequest.ts`) builds the 19.1 request object: ids and times as sent; exercises ordered by Hevy `index`, sets by `index`; snake_case to camelCase; `tzOffsetMinutes = offsetMinutesForZone(start_time, zone)` **at that workout's own instant** (so a workout in July and one in January in a DST zone get different offsets); a set `type` outside `HEVY_SET_TYPE_VALUES` drops the whole workout into the summary as "unreadable" (never sent); every request body passes `HevyImportBatchSchema`. `chunkBatches` makes batches of at most 25 workouts and at most about 400 KiB of JSON, never splitting a workout (a single workout over the byte bound goes alone; the server's 512 KiB limit is the backstop). Every list sent is ordered newest `start_time` first, ties by `id` ascending (`sortNewestFirst`, the one place).
7. **Routines step.** With folders and routines read, a checklist **grouped by Hevy folder** (folder order by `index`; routines whose `folder_id` is `null` are grouped under "No folder") shows each routine with its exercise count. Nothing is ticked by default. A line shows "You have {used} of 50 routines; room for {room} more." from the existing routines list (`ROUTINES_PER_USER_MAX`), and ticking is disabled for further routines once the room is used (the checkboxes explain why). A routine whose name (after trimming to 80 characters, case-insensitive) already exists in SIN is shown "Already in your routines" and cannot be ticked; a second Hevy routine with the same name as one already ticked is unavailable with "Same name as one you chose" (it would only end as "already there" and use a room slot). A routine whose `folder_id` names a folder that was not read is listed under "No folder", never dropped. **Tick all in this folder** ticks up to the room, in Hevy's order. A live count "{n} routines chosen" is a polite status line. Skipping the step (none ticked) is normal.
8. **Section markers.** If the fetched workouts or ticked routines contain Hevy exercises titled `Warmup` or `workout` (case-insensitive, trimmed; "Warmup Sets" is not a marker), counting ticked routines, and the mapping has no marker pair for them, the flow stops before the names step with "Your Hevy workouts use Warmup and workout exercises as section markers. Choose them so they aren't imported as exercises." and 20.0's `PlaceholderSheet` (AC30 there); **Skip** continues and those templates then appear as ordinary names (the user's call).
9. **Names step.** The Hevy templates referenced by the fetched workouts and the ticked routines that have **no pair** (role `exercise`, `skip` or a marker) in the mapping, or whose paired SIN exercise is retired, become `PairingNeed`s with usage counts ("41 workouts, 1 routine"), sorted by usage descending, and are shown in `PairingCards` (20.0 AC26-AC27). With none, the step is skipped. A template a workout uses that is **absent from Hevy's template list** (for example a deleted custom exercise) is also a need, handled by AC32. A header line says how many new exercises the choices would create and the room under the 500-exercise cap ("This would create 37 exercises; you can add 462 more"); **Continue** is disabled while any card is invalid or the creates exceed the room. "You can add {room} more" uses `customExerciseRoom` = the 500-exercise cap minus the visible custom exercises.
10. **Saving the names.** **Continue** calls `savePairings` (20.0 AC28): exercises are created one at a time (progress "Creating exercises… 12 of 37"), then the pairs are saved, then the mapping and catalog queries are refreshed; a failure shows the 20.0 sentences and returns to the cards with the decisions intact; leaving the screen mid-way stops further creates (the 10.4 abort rule), and what was created stays and is reused on the next try.
11. **The summary request.** With the mapping saved, the app sends **dry-run** batches (`dryRun: true`), newest workout first (Spec 19.1 O1), sequentially, with a progress line ("Checking your workouts… 400 of 1,013"). Each response is validated with `HevyImportResultSchema`; a count mismatch (results vs sent) or a schema failure is an internal error (`ImportReplyError`) shown as "The server's reply wasn't understood." with **Back**; a `429` waits `Retry-After` (default 5 s) and re-sends the same batch. No request in this step writes a workout (the server guarantees it; the test asserts the client sent `dryRun: true` on every one).
12. **The summary screen.** Shows, from the aggregated results:
    - **Workouts:** total read; **to import** (`create`); **already in SIN** (`already_imported` + `already_matched`); **sent from SIN** (`sent_from_sin`); **duplicates of a SIN workout** (`duplicate`); **deleted in SIN earlier** (`deleted_in_sin`); **can't be imported** (`no_usable_sets` + `time_invalid` + `rejected` + the unreadable ones of AC6); **waiting for a pairing** (`unpaired`).
    - **Sets:** how many will be kept and how many dropped, with the drop reasons and counts (the static labels for `set_missing_measure`, `set_forbidden_measure`, `set_out_of_range`, `exercise_skipped`, `exercise_no_sets`).
    - **Routines:** how many ticked; new exercises created in the names step.
    - **Lists:** every duplicate, every can't-be-imported workout and every workout with dropped sets, each as `{local date} · {title or "Untitled"} · {reason}` (a blank or whitespace-only title is "Untitled"; any title renders as text, never markup), grouped by reason, each group collapsed with its count and expandable (first 50, **Show 50 more**), so nothing is dropped silently and 1,000 rows are never rendered at once.
    The sum of the outcome counts equals the number read (a test asserts it). **No workout is written on this screen.**
13. **Unpaired remains.** If `unpaired` results remain after the names step (a pair was removed or a SIN exercise retired in between), the summary lists the templates and **Back to names** returns to the cards; **Import** is disabled while any workout is `unpaired`. In Phase A the Import button is rendered disabled with "Importing comes in the next update. Nothing has been written." (`IMPORT_NOT_YET`); Phase B deletes that constant and wires the button.
14. **Confirm.** The primary button reads "Import {n} workouts" (and "and {k} routines" when any are chosen). **Back** returns to any earlier step without losing the read (the data is in the session). Zero to import and zero routines (including an account with no Hevy workouts) shows "Nothing new to import" and a **Done** button that leads back to the Hevy screen. With none to create the button never counts "0 workouts": "Link {d} workouts" when any match a SIN workout (and "and import {k} routines"), "Import {k} routines" when only routines are chosen, and "Import workouts" (disabled) when only unpaired workouts remain (minor 239, D21).
15. **No storage, no leak.** The session lives in a reducer (`importSession.ts`, pure) and component state only. A source scan fails if any module in `features/hevy/import/` names `localStorage`, `sessionStorage` or the `StorageAdapter`, or builds a URL containing the key; the Hevy data (workouts, routines, templates) is never put in router state and is dropped when the screen unmounts.

### Phase B: the run, finish, routines, resume, report

16. **The run.** **Import** sends real batches (`dryRun: false`), newest first, one at a time, for the workouts whose dry-run outcome was `create` or `duplicate` only (a `duplicate` is sent so the server writes its link; every other outcome is already settled and is not re-sent). Progress shows "Importing… 325 of 1,013 · {k} skipped" and the date of the batch in flight, in a polite status updated per batch (not per workout). The client sends nothing to Hevy during the run.
17. **Results are accumulated.** Each batch's results update the counts and the lists; a `create` whose real result is `already_imported` (another tab won) is counted as such. The final counts are shown on the done screen and equal the sum of the batch results.
18. **Pace.** Batches are sent back to back with a 250 ms gap (the server is the bottleneck; the `hevy` group allows 60 a minute and a 1,013-workout run is ~41 batches). A `429` honors `Retry-After` and retries the same batch; the run never drops below one in-flight request.
19. **Failures during the run.** A network error or `5xx` retries the same batch automatically up to 3 times (2 s, 4 s, 8 s); after that the run **pauses** with "Paused: couldn't reach the server. Everything imported so far is saved." and **Resume** (re-sends the failed batch; safe because the import is idempotent; a `429` wait does not count toward the three retries) and **Stop**; a `422` stops with a static message and the batch's first error path (never a title); a `404` (the gate changed) stops with "The Hevy import isn't available on this account"; `401` follows the existing session-expiry path. Coming back online (the `online` event) offers Resume, never auto-resumes after a **Stop**.
20. **Stop and leave.** **Stop** finishes the batch in flight, then ends the run in the "Stopped" state with the counts so far and **Resume** / **Finish up** (§6.8). Navigating away or closing the tab while running opens a `ConfirmDialog` ("Stop the import? What's imported so far stays, and you can run it again.") through the router blocker and a `beforeunload` handler that is installed only while running; confirm stops after the batch in flight. Cancel keeps running. Stop tapped during a retry or `429` wait ends the run at once without sending the waiting batch (a Resume re-sends it); **Import**, **Resume** and **Finish up** pressed twice start one runner (a ref guard, not React state).
21. **Resume after a close.** After a reload, a closed tab or a Stop, **Import from Hevy** starts a fresh read (§6.3). The dry run then reports the earlier results as `already_imported` (the links), the summary's "to import" shrinks to what is left, and the run sends only that. A test with a fake API that persists links across two runs asserts the second summary's `already_imported` equals the first run's `create` count and that no workout is sent twice with `dryRun: false` once it is imported.
22. **Finish.** After the last batch (or **Finish up** after a stop) the app calls `POST /v1/hevy/import/finish` once and shows "Updating your records…"; success shows "Records updated."; a failure shows "Your workouts are in, but updating your records didn't finish." with **Try again**, and the Hevy screen shows the stale-records banner (from `GET /v1/hevy/status`) until a finish succeeds. A run in which no workout was created does not call finish unless the status says stale. A finish answering `recomputed: false` (another tab finished first) still shows "Records updated." and clears the banner; it is not an error. The stale-records banner is also shown on the Hevy screen itself while `recordsStale` is true.
23. **Routines.** After finish, each ticked routine is translated with `translateHevyRoutine` (pairs from the saved mapping; the user's unit) and created with the existing routine create (`POST /v1/routines`, **not** `oneOff`; one at a time, no more than 20 a minute), progress "Creating routines… 3 of 12". Outcomes: created; `409 routine-name-taken` is "already there" (counted as skipped, not an error); `409 routine-limit` stops the step with "Your routine limit was reached; {k} routines weren't created" and lists them; a translation `unpaired` (cannot happen after the names step, defended) or a `422` lists the routine with a static reason; the translator's notices (items cut, sets cut, time targets not kept…) are listed per routine. A translation that returns `no_items` (only placeholders and skips) is listed as "nothing to import" and skipped, not an error. A routine step failure never affects the workouts already imported.
24. **Caches.** After the run (and after a successful finish) the app resets `["history","list"]` and invalidates `["progress"]`, `["records"]`, `["exercises","usage"]` (if present), `["routines"]`, `["hevy","status"]` and `["hevy","mapping"]` (as §6.10 lists), using one `applyImportedCaches` helper beside `applyEditedCaches`; History, Progress and Records show the imported data without a reload. The catalog is refreshed once (`refresh(true)`) after exercise creation (AC10).
25. **The done screen.** Shows final counts (workouts imported, matched, skipped by reason, sets dropped; routines created / already there / not created; exercises created), a note "The records were updated" (or the failure state), links **View History** and **Back to Hevy**, and **Download report**.
26. **The report.** A CSV (UTF-8, header `kind,date,title,outcome,detail`) with one row per workout that was not simply `create` (duplicates, skips, drops: `detail` = the reason codes and counts) and one per routine outcome, built locally by a pure function and saved with `saveBlob` as `hevy-import-report.csv`. It contains titles (stays on the device) and never the key; every field is RFC 4180-quoted when it holds a comma, quote, CR or LF, and a field starting with `=`, `+`, `-` or `@` gets a `'` prefix so a spreadsheet never runs it; a test asserts the key is absent from every row. The same lists are on screen (AC12); the report is for keeping.
27. **Scale.** The reducer and lists handle 1,500 workouts: a test runs a fake Hevy and a fake API through a full 1,500-workout import in the test environment without more than 25 workouts per request, without rendering more than 50 list rows per group, and with the progress status updating once per batch.
28. **Pre-write safety.** The run cannot start if the status query is no longer `200`, the key was removed, the mapping query failed, or the summary is stale (the mapping changed after the dry run: any `PUT`/`PATCH` of the mapping through 20.0's mutations marks the summary stale and requires a new dry run).
29. **Screens, tokens, accessibility.** `assert:css-tokens` passes; the screens harness (fake Hevy and fake API) captures, light and dark at 390 and 1280 px: preflight, reading, routines checklist, names cards, summary (with every list group), running, paused, stopped, done with a routines failure; the 'frontDoor'-style layout report fails the run on a layout violation; the screens have landmarks and ordered headings, polite live regions that are empty at first paint, focus moves to the new step's heading on each step change, controls ≥ 44 px, no color-only state. There is no axe dependency (Carol, 2026-10-26): the repo's structural a11y tests (roles, names, landmarks, heading order, live regions empty at first paint) stand in for it on each state.
30. **Import boundaries.** A scan test fails if `features/hevy/import/` is imported by anything outside `features/hevy/` and `app/router.tsx`, if any module outside `hevyImportClient.ts` names `/v1/hevy/import`, or if `features/workouts/` or `features/routines/` imports from `features/hevy/import/` (the routine create is called through the existing routine client and hooks).
31. **Manual rehearsal (after each phase on staging).** With her real key against **staging**: read, choose three routines, pair (including a Calories and a Skip), read the summary and compare its totals with Hevy's own workout count and the number she expects to be duplicates; run; check History order, a PR in Progress, a calories exercise's chart, a farmer carry; run it again and see "0 to import". Recorded in `gym-checklist-2026-10.md`. The production run is a separate, deliberate step (the runbook).

32. **Templates Hevy no longer lists (resolved by Carol, 2026-10-26).** A workout exercise whose `exercise_template_id` is absent from Hevy's template list (`missingTemplates`) still gets a `PairingNeed`: the card is built from the workouts' own exercise `title`, with the Hevy type inferred from the measures its sets carry (weight and reps `weight_reps`, reps only `reps_only`, duration `duration`, and so on; none at all `reps_only`) and a "No longer in Hevy" label. It is matchable to a SIN exercise, can be created as New, or skipped, exactly like any other card (20.0 AC26-AC27), and is saved to the mapping as a pair carrying that id, title and inferred type. A used-but-unlisted template therefore never blocks **Import** for good. A test covers a deleted custom exercise: card shown, matched, saved, and its workout then `create` in the dry run.

## 4. Data model

None server-side, and **nothing persisted client-side**: no storage key, no draft, no checkpoint. The session (what was read from Hevy, the ticks, the pairing cards, the summary, the run's progress) is in memory. Resume is "run it again": the server's `hevy_link` rows are the memory of what is done (D2). The only server state this screen causes is the mapping (20.0), created exercises, `workout` rows with their links, routines and, until finish, `hevy_account.records_stale`.

## 6. Behavior & logic

### 6.1 The session model

`importSession.ts` is a pure reducer: `{ step, read, routinePicks, needs, summary, run }`; actions are the user's choices and the I/O results, so every transition is unit-tested without React. The I/O (Hevy reads, API batches) is in plain async functions with an `AbortSignal`; a hook `useImportSession` wires them to the reducer and owns the abort controller (aborted on unmount).

### 6.2 Preflight

Reads `useMe()` (zone, unit), `useHevyStatus()` and the stored key. The device zone is `Intl.DateTimeFormat().resolvedOptions().timeZone`. The preflight is text, not a form: there is nothing to choose before reading.

### 6.3 Reading

`GET /v1/workouts/count` first (its reply is only used for reconciliation); then templates, folders, routines and workouts via `listAll` with the stage names above. Workouts are held as parsed `HevyWorkout`s keyed by id (a `Map`, so duplicates across shifting pages collapse). **Resume reads everything again** (D2): Hevy pages shift when workouts are added, so a stored page cursor could skip one; at 600 ms per request the whole read of ~110 requests is about a minute and a half, and the server's links make the writes skip what is done.

### 6.4 Routines

Folders sorted by Hevy `index`; a routine's group is its `folder_id` (`null` is "No folder"). The room is `ROUTINES_PER_USER_MAX − routines.length` from the existing routines list (one-offs count: the cap counts rows). Name collision uses the same trimmed, 80-character, case-insensitive comparison as the server's unique index on `(user_id, lower(name))`.

### 6.5 Names

`needs = templatesUsedBy(workouts ∪ tickedRoutines) − pairedTemplates`. A template titled `Warmup` or `workout` without a marker pair is handled by AC8 first. Usage counts come from the same walk. Skipping (`skip` pair) is the user's explicit choice and is reported in the summary as `exercise_skipped` drops, not hidden.

### 6.6 The summary

`aggregateResults` is a pure fold over `HevyImportResult[]` into counts, a drop table and `summaryLists` (grouped, sorted by date descending then title). Titles come from the fetched Hevy workouts (the server does not echo them). The dry run reflects the **saved** mapping, which is why the names step saves before the summary (D3).

The dry run is exact per batch, not across batches: two Hevy workouts in different batches that both match one SIN workout each answer `duplicate`, and in the real run the second one is created. So the summary may undercount creates by one per such pair (rare: two Hevy workouts with the same title within an hour on one day). The run's own results are what the report shows.

### 6.7 The run

```
for batch in chunkBatches(sendable, 25 / 400 KiB):
    post { dryRun: false, workouts }  -> results
    accumulate
    wait 250 ms
until done | stopped | failed
```

`sendable` = the workouts whose dry-run outcome was `create` or `duplicate`. Stop is checked between batches. A batch is re-sent whole on retry; the server answers `already_imported` for what already landed (19.1 AC19), so the counts stay right.

### 6.8 Finish

One `POST /v1/hevy/import/finish` after the run's batches, or from the stale banner, or from **Finish up**. It is the only call that recomputes records; the Records, Progress and History badges are correct only after it succeeds, which is why a failure is loud and persistent (the banner).

The client sends it with no body and no `Content-Type`, as `RoutineClient.keep` does (a JSON content type with an empty body is Fastify's `400`, 19.1 §5.2). It never overlaps a finish with batches: the finish waits for the batch in flight, and no batch starts while a finish is in flight (a finish over 30 s holds the row a concurrent batch's write needs, and can time that batch out to a `500`; the retry is safe, but the run should not cause it).

### 6.9 Routines

Order: after finish, so a routine-cap or name problem cannot delay the records. Each routine: `translateHevyRoutine(routine, { pairs, modalityOf, unit })`, `RoutineWriteSchema.parse` as a last check, `POST /v1/routines`. The exercise ids come from the saved pairs. The existing routine hooks' `networkMode: "always"` and no-outbox rules apply (10.0).

### 6.10 Caches

`applyImportedCaches(queryClient)`: `resetQueries(["history","list"])`, `invalidateQueries` for `["progress"]`, `["records"]`, `["exercises","usage"]`, `["routines"]`, `["hevy","status"]`, `["hevy","mapping"]`.

### 6.11 Copy

Reason labels, step text and failure sentences live in `features/hevy/import/messages.ts` (static, American English): every code from 19.1 has exactly one label; a test fails if a code lacks one. Hevy's own text and any workout title are never put in a failure sentence; titles appear only in the lists and the report, as text.

## 7. Security & privacy

- **The key** is used only by the Hevy client (20.0 AC7). The import's API calls (`/v1/hevy/import/*`) carry the bearer token and workout data, never the key.
- **Untrusted data.** Everything from Hevy is schema-parsed (20.0 AC8), rendered as text, size-bounded by the 19.1 request schema, and sanitized again by the server (19.1 §7).
- **Titles** live in memory and in the report file the user chooses to save; they are not logged, not sent anywhere but the import request, not stored.
- **Scope of damage.** The import creates records in the signed-in account only; the largest harm (a wrong pairing) is bounded by the summary and the runbook's undo (19.1 §11); the owner-only gate bounds who can trigger it.
- **No new origin;** the CSP change was 20.0's.

## 8. Config & secrets

None. No env var, flag or secret. The batch size (25), body size (~400 KiB), pacing constants (250 ms, 20 routines a minute) are constants beside the screen.

## 12. Decisions & open questions

- **D1 ✅ One screen with steps, under the Hevy screen (mine).** Rationale: a one-time, linear flow whose later steps depend on earlier ones; the `nav` of steps and a reducer keep it testable; separate routes per step would make a reload land in the middle of state that is only in memory.
- **D2 ✅ Resume is "run it again", with no stored checkpoint (mine; the design asked for resumable and no duplicates).** Rationale: the server's links are the authoritative record of what is done and survive a closed tab, a reload and another device; a client checkpoint would be a second, wrong-able copy (Hevy's pages shift when workouts are added). Cost: a re-read of Hevy (about 1.5 minutes) and a dry run before a resumed run; both show progress.
- **D3 ✅ The names step saves pairings (and creates exercises) before the summary, not after Confirm (mine; Carol: "pairs made here save to the same mapping").** Rationale: the summary must be computed against the real mapping (the server dry run cannot see unsaved decisions), and an unpaired workout cannot be counted truthfully otherwise. The cost is that exercises exist before the lifter has confirmed the import; they are visible in the Exercises tab and the cap room is shown first. Rejected: a server dry run that accepts a draft mapping (a second code path for the same rules).
- **D4 ✅ Workouts first, then finish, then routines (mine; see 19.1 §6.6).**
- **D5 ✅ Newest first (mine; Spec 19.1 O1's default).** If Carol answers oldest first, `chunkBatches`' input order flips; nothing else changes.
- **D6 ✅ Nothing is ticked by default in the routine checklist, and a name collision is not ticked for you (Carol: "she picks"; mine for the rest).** Rationale: copying every routine is an explicit non-goal; the cap is 50.
- **D7 ✅ No Screen Wake Lock for the import (mine).** Rationale: the workout screen's lock is a per-device preference tied to logging (#108) and importing it would couple features; the import is resumable by design, expected to be run on a laptop or a phone left on the screen for a couple of minutes, and says so on the first screen.
- **D8 ✅ The report is a local CSV built from the session (mine).** Rationale: the design wants every drop and skip listed; on screen is for reading, a file is for keeping and for diffing against Hevy. Built on the device because titles stay on the device.
- **D9 ✅ Unreadable Hevy workouts (an unknown set type) are summarized as "can't be imported" and never sent (mine).** Rationale: the server's schema is strict about set types; sending would fail the whole batch.
- **D10 ✅ Dates use the device's zone, with the Profile zone shown beside it if different (Carol: device time zone at import; mine: the notice).** Rationale: Hevy stores no zone; the design chose the device. A mismatch with Profile is worth one line because Change Time defaults to Profile.

- **D11 ✅ Routines are created with `useCreateRoutine`, not an editor-free 10.4 path (mine, from the build plan).** Rationale: 10.4 saves through `RoutineEditor`; the existing hook (`networkMode: "always"`, no outbox, never `oneOff`) is the smallest correct path. Only `useImportSession` imports it.
- **D12 ✅ A routine step's `routine-limit` stops the step; later routines are listed as not created (mine).** Rationale: the cap cannot clear mid-run, so trying the rest wastes requests.
- **D13 ✅ The leave guard, run guard and generation counter are client-side only (mine).** Rationale: they only prevent double sends and stale replies; the server's idempotency stays the backstop.
- **D14 ✅ Owner decision (Carol, 2026-10-26): no axe dependency.** The repo's structural a11y tests stand in for it (AC29; 20.0 AC32).
- **D15 ✅ Owner decision (Carol, 2026-10-26): a template missing from Hevy's list gets a pairing card built from the workouts' exercise title, matchable or skippable like any other (AC32).**
- **D16 ✅ Owner decision (Carol, 2026-10-29): the routines boundary.** 20.0 AC31 / D14 forbade any `features/hevy/` import from `features/routines/`; the one exception is `features/hevy/import/useImportSession.ts`, which may import `routines/queries` (the list, Phase A) and `routines/useRoutineMutations` (the create, Phase B, D11). The 20.0 scan pins that file and those two modules.
- **D17 ✅ Owner decision (Carol, 2026-10-29): a Hevy workout the request schema can't carry is unreadable.** D9 extended: a workout whose request fails `HevyImportWorkoutSchema` (a title over 200, more than 200 exercises or sets, a time without an offset, …) is never sent and is counted under "can't be imported", because one such workout would fail its whole batch.
- **D18 ✅ Owner decision (Carol, 2026-10-29): workouts a Stop left unsent.** After **Stop** then **Finish up**, a workout the dry run marked `create` or `duplicate` that the run never sent is listed on the done screen ("{n} not imported (stopped)") and in the report (outcome `not_imported_stopped`), so nothing is dropped silently (AC12). Running the import again sends it.
- **D19 ✅ Owner decision (Carol, 2026-10-29): other `4xx` answers during the run.** Beyond the `422`, `404`, `401` and `429` of AC19, any other `4xx` (a `413` for one workout over the body limit, a `400`, a `403`) stops the run as `invalid` with an empty path; a `403 account-deleted` also invalidates `["me"]`, so the layout takes over (CLAUDE.md "Account lifecycle UI").
- **D20 ✅ The leave guard covers the finish and the routines too (mine, from the build).** AC20 names "running"; the guard is also on while the finish and the routine creates run, because they write too. After a `422` stop only **Finish up** is offered, and after a `404` or `401` neither: re-sending a batch the server refused, or one past a closed gate, can't succeed.
- **D21 ✅ Owner decision (Carol, 2026-10-31): the confirm words when no workout is created (minor 239; O1 of the minors batch, the proposed default accepted as is).** A run whose sendable workouts are all matches sends them only to write their links, so the button says **Link 3 workouts** (and "and import 2 routines"); routines alone read **Import 2 routines**; only-unpaired reads **Import workouts**, disabled, under the unpaired card that says why. With any workout to create the words are AC14's, unchanged. The summary's count line says "1 already matches a workout in SIN (it'll be linked, not copied)" for one (minor 248).

No owner question is open in this spec.
