## 1. Purpose, scope & non-goals

### 1.1 Purpose

Carol keeps Hevy as a second, private copy of the workouts she logs in SIN. On a finished workout she taps **Send to Hevy**; it appears in Hevy the way she would call the same workout. If she later edits the workout in SIN, the screen says **Changed since sent to Hevy** and offers **Update in Hevy**. If she turns on **auto-push**, each workout is sent when she finishes it, while the app is open. Hevy has no delete in its API, so deleting in SIN leaves the Hevy copy and says so.

**Success:** she finishes a workout, taps Send once (or doesn't, with auto-push on), sees "Sent to Hevy", opens Hevy and finds one private workout with her title, times, exercises, sets, supersets and section markers; edits a set in SIN, sees "Changed since sent to Hevy", taps Update and finds Hevy corrected; and no tap, retry, slow network or second device ever produced a second Hevy copy.

### 1.2 In scope

**Phase A (PR 1)**
- `HevyWorkoutSection` on the finished-workout screen (the post-finish summary and `/app/history/:id`): states, buttons, notices (§5.1, §6.1).
- The send and update sequences with the claim protocol, failure classes and the lost-response check (§6.2-§6.4).
- Pairing for export: unmapped exercises, picking a Hevy exercise, creating one in Hevy, leaving one out (§5.2, §6.5).
- The delete note on both Delete dialogs (§6.7).

**Phase B (PR 2)**
- The **auto-push** switch (Hevy screen), the finish event, the background send and its summary line (§5.3, §6.6).

### 1.3 Non-goals (and where they live)

| Not here | Lives in / why |
|---|---|
| Deleting or removing anything in Hevy | The API has none (design); the dialog only says so |
| Sending a live workout | Only finished workouts have a link or a stable body |
| Exporting routines | Not requested (design: routines are import-only) |
| Sending with the app closed | Needs a server-held key (design future option 1) |
| An offline queue or retry-later for sends | Online-only, like routines and edits (D8) |
| Bulk "send all my old workouts" | Not requested; each is a tap, or auto-push going forward |
| Editing a Hevy exercise after creating it | Hevy cannot; the create step confirms before it happens |
| Resolving a Hevy copy that was edited in Hevy | `PUT` overwrites it (design: Hevy is only a copy) |

### Fit for one work session

Phase A is one component with a small state machine, one sheet and a sequence of calls with careful failure handling. Phase B is a switch, a bus and one hook. Two PRs at the phase boundary.

## 2. Acceptance criteria

Every behavioral criterion has at least one test tagged **`"20.2 ACn — …"`**; `acTags.20-2.test.ts` checks the tags for unit-tested ones. §10 maps each to a method. A "send" is a create (`POST` to Hevy); an "update" is a `PUT`. "Begin / complete / release" are the 19.0 link routes.

### Phase A: Send, Update, pairing, delete note

1. **Where it shows.** `HevyWorkoutSection` renders on the finished-workout screen (both the summary after Finish and `/app/history/:id`, one component) only when `GET /v1/hevy/status` is `200`. It does not render on the live session, the edit screen, or for any other user. `features/workouts/` imports exactly `HevyWorkoutSection` and `HevyDeleteNote` from `features/hevy/send/index.ts`, nothing else from `features/hevy/` (a scan test), and `features/hevy/` imports from `features/workouts/` only `import type` of the workout types, the finish-event bus (`finishEvents`) and the workouts' `queries` module (the workout detail query hook, `useWorkoutClient` and `WORKOUT_KEYS`, which the send and auto-push need to read a fresh detail).
2. **States.** `useHevyLink(workoutId)` (`["hevy","link",id]`, `staleTime: 0`, `refetchOnMount: "always"`, `retry: false`) drives the section: **none** → text "Not in Hevy yet." and a secondary **Send to Hevy** button; **sending** (a claim on another device, or this device's request in flight) → "Sending to Hevy…" and the button disabled; **sent** → "Sent to Hevy" with the date the link was last synced, no button; **changed** → "Changed since sent to Hevy" and a secondary **Update in Hevy** button. A link with `origin: "imported"` reads "From Hevy" in place of "Sent to Hevy" (and "Matched with a Hevy workout" for `matched`); both are `sent`/`changed` in behavior, so an edit offers **Update in Hevy** (design: linked imported and matched workouts behave like sent ones). A `404` or a network error on the link read renders nothing (never an error row for an owner-only line).
3. **No key.** With status `200` but no stored key, the section says "Add your Hevy key in Profile to send workouts." with a link to `/app/profile/hevy`, and no button; a `changed` / `sent` state is still shown (it is server data), with **Update in Hevy** replaced by the same link.
4. **The send sequence.** Tapping **Send to Hevy** runs, in this order and nothing else: (a) read the workout detail (already cached), the mapping and the catalog; (b) `buildHevyWorkout`; if exercises are unmapped, AC13 first; (c) `POST /v1/workouts/{id}/hevy-link` (begin) → `mode: "create"`; (d) Hevy `POST /v1/workouts` with the built body; (e) parse the reply (`{ workout: [Workout] }`, id from the single element); (f) `PUT /v1/workouts/{id}/hevy-link { hevyWorkoutId, fingerprint }` with the fingerprint begin returned; (g) refresh the link query. A test with a recording fake Hevy and fake API asserts exactly that call order, that the Hevy body deep-equals `buildHevyWorkout`'s output (so `is_private: true`, times, sections, supersets are the pure function's), and that the SIN API never receives the key.
5. **One tap, one copy.** The run lives in a module-level in-flight map and the mutation, not in the component, so leaving the screen mid-send still reaches `complete` and invalidates the link query. The button is disabled from the tap until the whole sequence ends; the sequence is a TanStack mutation with key `["hevy","send",workoutId]` and `networkMode: "always"`, `retry: false`, and a second component or the auto-push hook that starts the same key while one runs attaches to it instead of starting another. A double click (two events in one tick), a re-render, and two mounted sections produce one begin and one Hevy `POST`.
6. **Another send in progress.** `409 hevy-send-in-progress` on begin shows "Another send is in progress. Try again in a minute." with the button re-enabled, and makes no Hevy call.
7. **The lost-response check.** When begin answers `staleClaim: true` (an earlier send was interrupted), the app first looks for the copy: `findHevyCopy` reads Hevy's `GET /v1/workouts` newest first (`pageSize=10`, at most 5 pages) for a **candidate**: a workout with the **same `start_time` instant** (parsed, so `Z` and `+00:00`, with or without milliseconds, match; one second apart does not) **and the same number of exercises with at least one set** as the built body (D28). One candidate is the copy, whatever its title; several are settled by **the title of the built body** (which may be the routine name or `Workout`, not `detail.title`), and if that doesn't pick exactly one the check is inconclusive. Found → skip the `POST` and complete with that id ("Found it in Hevy; linked."). Not found and a page with a workout older than this one's start was reached (conclusive) → send normally. Not found and 5 pages scanned without reaching an older workout (inconclusive) → "Not sure whether an earlier send reached Hevy." with **Check again** and **Send anyway**, and no `POST` until the user taps **Send anyway**.
8. **A definite Hevy failure releases the claim.** A Hevy `400` (`rejected`), `403` limit, `401`/`403` `bad_key` on the `POST`: `DELETE …/hevy-link` (release), then the static sentence for the kind (`rejected`: "Hevy didn't accept this workout."; `limit`: "Your Hevy account has reached a limit."; `bad_key`: "Hevy didn't accept your key. Check it in Profile." with a link); Hevy's own text is never shown; the button returns.
9. **An ambiguous failure keeps it.** A network error, a timeout, a `5xx` or an unreadable reply on the `POST`: the claim is **not** released; the section says "Not sure whether Hevy received it. Check before sending again." with **Check Hevy** (runs `findHevyCopy`; found → complete; conclusive not found → release and re-enable **Send to Hevy**; inconclusive → the AC7 choices). There is no automatic retry of a Hevy write anywhere (20.0 AC11).
10. **Recording the id can fail after Hevy accepted.** If Hevy returned an id and `complete` fails (network, `5xx`), `complete` is retried up to 3 times (1 s, 2 s, 4 s); then the section shows "Sent to Hevy, but this app couldn't record it. Tap Try again; it won't send again." with **Try again** that only repeats `complete` (the id and fingerprint are held in the mutation's state, never storage); a reload loses them, and the next **Send to Hevy** then takes the AC7 path (stale claim, `findHevyCopy`) and finds the copy instead of creating a second. A `409 hevy-id-in-use` or `hevy-link-conflict` on complete shows the static "This Hevy workout is already linked to another workout here." and keeps the claim for the user to resolve (rare; no automatic action).
11. **Update.** **Update in Hevy** (state `changed`) runs: begin (`mode: "update"`, the stored `hevyWorkoutId`), Hevy `PUT /v1/workouts/{id}` with the whole rebuilt body (`buildHevyWorkout`, same as a send), parse the reply (a bare `Workout`), `complete` with the id and the new fingerprint; the section returns to "Sent to Hevy". Nothing is sent to Hevy until the tap (design); the `changed` state alone never calls Hevy. An ambiguous `PUT` failure shows "Not sure whether Hevy updated it." with **Try again** (a `PUT` is safe to repeat); definite failures release as in AC8.
12. **A copy deleted in Hevy.** A Hevy `404` on the update `PUT` shows "That workout isn't in Hevy any more." with **Send as a new Hevy workout**: release, then begin with `{ relink: true }` (19.0 AC27) and the send sequence of AC4 from (d).
13. **Unmapped exercises on export.** When `buildHevyWorkout` returns `unmapped`, a `Sheet` "Match exercises for Hevy" lists one card per unmapped SIN exercise (name, type label, "used in this workout"). Each card offers **Pick a Hevy exercise** (a searchable list of Hevy's templates, loaded with `useHevyTemplates` and filtered to those `hevyPairingProblem` accepts for the exercise's type, with `calories_as_reps` assumed for a Calories exercise; each shows Hevy's title and its type label from 20.0's `HEVY_TYPE_LABELS`, not a second map), **Create in Hevy** (AC14), or **Leave out of this workout**. **Continue** is enabled when every card has a choice. Picks and creates are saved to the mapping with `PATCH { upsert }` (an exercise's first pairing becomes its `exportAs`, 19.0 AC24) before the send continues; **Leave out** is for this send only, saves nothing, and adds the notice "{name} was left out" to the sent notices (D2). A card whose exercise already has a pairing never appears.
14. **Create in Hevy.** **Create in Hevy** opens a confirmation step on the card with: the title (prefilled from the SIN name, with ` (calories)` appended for a Calories exercise), the Hevy type (prefilled by `hevyTypeForModality`, changeable among the types `hevyPairingProblem` accepts for the exercise), the primary muscle, other muscles and equipment (prefilled through 19.0's `SIN_MUSCLE_TO_HEVY` and `SIN_EQUIPMENT_TO_HEVY`, which also give the body, validated by 19.0's create-template schema; `other` when unknown), and the sentence "Hevy can't edit or delete an exercise after it's created. Check the details." Nothing is created until **Create in Hevy** is confirmed. The request (`createTemplate`, body built by a pure `hevyExerciseCreateBody` from the card values) is made once, never retried; the reply's id (string or number, normalized to a string) becomes the pair (`hevyType` as chosen, `measureRule: "calories_as_reps"` for a Calories exercise, else `null`). `403` limit shows "Your Hevy account has reached its custom exercise limit." and returns the card to its choices; other failures are the static sentences of AC8 and the card keeps its state.
15. **Notices after a send.** The notices from `buildHevyWorkout` (19.0 AC11: `{ code, count }`, with `names` on `section_no_placeholder`; counts and names are data the UI phrases) are shown once, under the section, as short sentences from a static map ("2 sets weren't sent because they were incomplete.", "RPE below 6 was left out of 1 set.", "Section 'Warm-up' had no marker exercise, so its note went on the first exercise.", "{name} was left out."; and, plan copy: `rpe_rounded` "RPE was rounded to Hevy's steps on {n} sets.", `distance_rounded` "Distances were rounded to whole meters.", `title_fallback` no sentence); they disappear on the next navigation (not stored).
16. **Online only.** If the mapping or the workout detail cannot be read when Send is tapped, the outcome is the network sentence with no begin and no claim. With no network the buttons are not disabled; tapping runs the sequence and fails at the first request with the network sentence ("Couldn't reach Hevy. Check your connection and try again."), having changed nothing (a failed begin leaves no claim). No offline queue, no outbox, no draft.
17. **Edits flip the state.** After a finished-workout edit (Spec 18.0 Done, Change Time, section and exercise edits) or a delete-and-readd, reopening the summary or History detail shows `changed` for a linked workout when the server says so (the link query refetches on mount); a test with the fake API that recomputes the fingerprint asserts `sent` → `changed` after a set edit and `changed` → `sent` after an update.
18. **Delete note.** Both Delete dialogs (the finished-workout screen's "Delete workout" and the edit screen's "Delete this whole workout instead?") show, when the link query has a `hevyWorkoutId`, the paragraph "This workout is also in Hevy. Deleting it here doesn't remove it from Hevy; delete it there yourself." through `HevyDeleteNote`, which fetches the link when the dialog opens and renders nothing for a non-owner, a `none` link or a failed read. The dialog's buttons, focus (Cancel first) and behavior are otherwise unchanged. After a delete the link row remains as a tombstone (19.0 AC31); the app does nothing with it.
19. **Static, safe copy.** Every sentence is from `features/hevy/send/messages.ts` (American English, no Hevy text, no workout title, no exercise name except where a card names its own exercise); a test fails if a `HevyError` kind, a begin/complete problem slug or a notice code has no sentence.
20. **The key stays put.** The 20.0 AC7 scan and spy tests are extended to the send flow: no SIN request contains the key; `reportError` is called with `source: "hevy-send"` and `op` ∈ `begin`, `hevy-post`, `hevy-put`, `complete`, `release`, `create-template`, `find-copy` for non-network, non-4xx failures, with static messages.
21. **Screens, tokens, accessibility.** `assert:css-tokens` passes; the harness (fake Hevy, fake API) captures, light and dark at 390 and 1280 px, the section in each of none / sending / sent / changed / imported / no-key, the pairing sheet (with a create confirmation), the "not sure" states, and both Delete dialogs with the note; no new design value; no brass (records only); controls ≥ 44 px; status text in a polite live region that is empty at first paint; focus moves to the sheet heading on open and back to the button on close. There is no axe dependency (Carol, 2026-10-26): the repo's structural a11y tests stand in for it on each state.
22. **Manual live check (after Phase A on staging, against the real Hevy account).** Send one real workout containing a superset, a section with notes, a Warm-up section and a Calories exercise; open it in Hevy and confirm title, times, exercises, sets, supersets, markers, notes and that it is private; edit a set in SIN, Update, confirm; delete the Hevy copy in Hevy and use **Send as a new Hevy workout**. The result answers Spec 19.0 O1-O2 (private flag; empty-sets placeholder). Recorded in `gym-checklist-2026-10.md`.

### Phase B: auto-push

23. **The switch.** The Hevy screen shows **Send each workout to Hevy when I finish it** (a labeled switch, off by default) only with status `200` and a stored key; it explains "Works while the app is open. If something can't be sent, the workout's screen has a Send to Hevy button." and is stored as `"on"` under `sin:pref:hevy-auto-push` through the `StorageAdapter` by `ui/hevyAutoPush.ts` (the `keepAwake.ts` pattern: only `"on"` is stored, anything else reads off). The key is **not** a user-data prefix, so Sign out keeps the preference; with no key (after sign-out) auto-push does nothing (AC25).
24. **The finish event.** `features/workouts/finishEvents.ts` exports `onWorkoutFinished(listener)` and `emitWorkoutFinished({ workoutId })`; `useFinishWorkout`'s `onSuccess` emits it once per successful finish, after its existing cache work, and `ActiveSession.confirmAlreadyFinished` (the `409 workout-finished` recovery, which seeds the caches itself and does not run `onSuccess`) emits it too, so a finish whose response was lost still triggers auto-push once; a duplicate emission is harmless because AC28's three layers make the send once. `features/workouts/` imports nothing from `features/hevy/` for this (the bus is the seam; a scan test pins the direction).
25. **Auto-push runs when, and only when,** the app receives the event and: status is `200` (a cached `200` is enough), the setting is on, a key is stored, the browser reports online, and `buildHevyWorkout` over the **fresh** finished detail (fetched with `staleTime: 0`, `endedAt` set) and the mapping (fetched if not cached, never read as "unmapped" because it was not loaded) returns `ok` (every exercise mapped). It first reads the link and goes on only when the state is `none` (so it is create-only without ever claiming a linked workout), then runs the AC4 sequence silently as a send, through the same mutation key as the button (a per-call runner, `useSendRunner`, over the same in-flight map). Leaving the summary mid-send does not stop it. If any condition fails it does nothing and says nothing at the time; if the workout has unmapped exercises, the finished screen shows the line "{n} exercises need matching before this can go to Hevy." ("1 exercise needs matching…" for one) above **Send to Hevy** (which opens the AC13 sheet) whenever auto-push is on and the workout is unsent and unmatched, not only after a skipped auto-push (no stored "skipped" flag; D8). Offline at the event: nothing at all happens (no begin, so no claim shows "Sending to Hevy…" for two minutes). After a sign-out the preference stays but there is no key, so nothing is sent and the switch is hidden.
26. **Never blocks or surprises.** The finish flow, navigation and the post-finish summary do not wait for auto-push. While it runs, the section shows "Sending to Hevy…"; on success "Sent to Hevy"; on failure the section shows the matching AC8/AC9 message and the button (the claim protocol makes a later manual send safe). Auto-push never creates a Hevy exercise and never opens a sheet.
27. **No background.** Auto-push has no timer, no service worker and no retry loop: a workout finished while the app was closed, offline, or whose send failed is sent only by the button. The switch's help text says so (AC23). A test asserts no `setTimeout`/`setInterval` is used by the hook beyond the sequence's own backoff.
28. **Exactly once.** Finishing the same workout twice (a replayed finish response, two tabs) emits at most one send: the mutation key, the begin claim and `hevy_link_hevy_id_key` are the three layers; a test with two listeners and a duplicate event produces one Hevy `POST`.
29. **Auto-push stays inside the boundary.** It uses the same `HevyClient`, mapping and link hooks as the button (no second code path for the sequence); a scan test fails if the sequence is implemented twice.
30. **Screens and phone check.** The harness captures the switch (off, on, no key); on Carol's iPhone: turn auto-push on, finish a workout, see "Sent to Hevy" appear on the summary without a tap; finish one with an unmatched exercise and see the matching line; turn it off and finish one. Recorded in the gym checklist.

## 6. Behavior & logic

### 6.1 The state machine

`state = f(linkRead, mutationState)`: the server link state (`none` / `sending` / `sent` / `changed`) is the base; the local `["hevy","send",id]` mutation overlays `sending` and the AC9/AC10 "not sure" and "couldn't record" states, which exist only while the mutation object lives. After any terminal outcome the link query is refetched, so the screen shows server truth.

### 6.2 The sequence

```
build -> (unmapped? sheet) -> begin --409--> message
                                |
                       staleClaim? -> findHevyCopy -> found: complete | inconclusive: ask | notfound: continue
                                |
                          Hevy POST/PUT --definite fail--> release + message
                                |        --ambiguous--> keep claim, "not sure"
                          complete (3 tries) -> refetch link
```

Everything between begin and complete is one async function (`runSend`) over injected dependencies (client, API, clock) so every branch is unit-tested without React; `useSendToHevy` wraps it in the mutation.

### 6.3 `findHevyCopy`

Scans `GET /v1/workouts?page=n&pageSize=10` for `n = 1…5` through the shared pacer, newest first by Hevy's own ordering (the builder confirms the order during the live check, AC22, and the conclusive rule depends on it: if Hevy orders by creation instead of start time the scan is bounded by the 5 pages and the "inconclusive" path is what Carol sees; recorded in the PR). A match needs `start_time` equal as instants (parsed, so `Z` versus `+00:00` does not matter) and equal title. It returns `found(id) | notFound | inconclusive`. It never writes.

### 6.4 Why the claim protocol, in one paragraph

Hevy has no idempotency key, so SIN supplies the only guard it can: the **claim** (server-side, one at a time per workout), the **disabled button** (one tap), the **shared mutation** (one tab or hook), the **unique Hevy-id link** (one copy per Hevy workout), and the **lost-response check** (look in Hevy before creating again). The only unguarded gap is a `POST` that Hevy processed whose reply was lost on a device that is then closed before the AC7 check can run, and that case is resolved by the same check on the next tap rather than hidden.

### 6.5 Building the Hevy exercise create body

`hevyExerciseCreateBody({ title, hevyType, primaryMuscle, otherMuscles, equipment })`: `exercise_type` the chosen Hevy type; `equipment_category` from 19.0's `SIN_EQUIPMENT_TO_HEVY` (`other` if unknown); `muscle_group` the primary through `SIN_MUSCLE_TO_HEVY` (for example `core` → `abdominals`, `quads` → `quadriceps`, `back` → `upper_back`; `other` when unset); `other_muscles` the translated secondaries without the primary and without duplicates. Validated against `CustomExerciseType` / `MuscleGroup` / `EquipmentCategory` enums from the Hevy schema before sending.

### 6.6 Auto-push hook

`useHevyAutoPush()` is mounted once in `ProtectedLayout`'s provider tree (inside the query client and session). It subscribes to `onWorkoutFinished`; on an event it re-reads the setting, key and status, fetches the workout detail (fresh), builds, and calls `runSend` through the same mutation key. It holds no state beyond the subscription.

### 6.7 Delete note

`HevyDeleteNote({ workoutId })` is rendered inside each dialog's body; its link query is enabled only while the dialog is open. The note is informational: the dialog's confirm still calls the existing delete mutation, and deleting does not touch Hevy.

---

## 7. Security & privacy

- **The key** is used only by the Hevy client; the begin, complete and release calls carry the bearer token and ids/fingerprints, never the key (AC4, AC20).
- **What leaves the device to Hevy:** the workout body (title, notes, times, exercises, sets, notes) the user chose to send, marked private; and, for Create in Hevy, an exercise's title, type, muscles and equipment. Nothing else; no SIN ids.
- **What the server learns:** that a workout was sent, and Hevy's id for it (19.0). No Hevy content comes back to SIN beyond the id.
- **Hevy replies are untrusted:** schema-parsed, id used only as an opaque string; their text is never rendered (AC8, AC19).
- **Auto-push** is opt-in per device, off by default, sends only finished, fully mapped workouts, creates only, and never creates Hevy exercises.
- **Visibility:** owner-only (the gate); a non-owner's browser makes only the status request.

## 8. Config & secrets

None. No env var, flag or secret. The scan limits (5 pages of 10), the complete-retry waits (1/2/4 s) and the key `sin:pref:hevy-auto-push` are constants beside the code.

## 12. Decisions & open questions

- **D1 ✅ The section sits under the stats on the finished-workout screen and is one component for the summary and History detail (mine).** Rationale: the screen already serves both (08.0); the action belongs to the finished workout, not to the Workout menu, which holds edits and delete, and a separate line makes the state (Sent / Changed) visible without opening anything.
- **D2 ✅ "Leave out of this workout" is for one send and saves nothing (mine).** Rationale: the design's "Unmapped exercise on export: the app asks to map it, or to create a Hevy custom exercise". Leaving one out is the escape hatch for an exercise Carol does not want in Hevy; making it permanent would be a `skip` pair, which means "ignore on import" in the mapping and would silently change imports too. The notice records it.
- **D3 ✅ The claim protocol is the double-copy defence, and a lost response is resolved by looking in Hevy (mine; the design requires no second copy).** See §6.4. Rejected: a client-side "sending" flag in storage (lost on a reload, not shared across devices); trusting the button alone.
- **D4 ✅ Export pairing is its own sheet, not `PairingCards` (mine).** Rationale: import pairing answers "which SIN exercise is this Hevy one" from a template list; export answers "which Hevy exercise is this SIN one" and offers creating one in Hevy, which is irreversible and needs a confirmation step. Different data, different defaults; sharing the component would bend both. The pure `hevyPairingProblem` is the shared rule.
- **D5 ✅ Create-in-Hevy appends ` (calories)` and pairs with `calories_as_reps` for a Calories exercise (Carol's convention; mine to default it).** Rationale: Hevy has no calories field and her existing convention stores calories in reps on a "(calories)"-named exercise; creating one that follows it keeps imports and exports symmetric (19.0 D10).
- **D6 ✅ Auto-push creates only, never updates, never creates Hevy exercises, and never opens UI (mine; Carol: "works while the app is open").** Rationale: an unattended action must not make irreversible Hevy changes (exercises) or overwrite (updates); the manual button covers everything else, and the claim protocol makes a manual send after a failed auto-push safe.
- **D7 ✅ Auto-push is triggered by an event bus in `workouts/`, not by `workouts/` calling Hevy code (mine).** Rationale: keeps the dependency pointing one way (`hevy/` knows `workouts/`, never the reverse) and keeps the logging path free of an owner-only feature; the finish mutation emits an event that has no listener for anyone else.
- **D8 ✅ Sends are online-only with no queue (mine; follows the project's rule for deliberate actions).** Rationale: a queued Hevy write would have to survive logout, key removal and mapping changes, and would be a write that retries by itself, which the double-copy rule forbids.
- **D9 ✅ The auto-push preference is a device setting under `sin:pref:` (mine).** Rationale: it describes this device's behavior, like keep-awake and theme; it is inert without the key, which logout removes, so no cross-account leak.
- **D10 ✅ Imported and matched workouts offer Update like sent ones (design, Carol-accepted).** The overwrite of the Hevy original is accepted by the design.

- **D11 ✅ Notices carry counts, and section names as data (mine; with 19.0 D28).** Rationale: the sentences need them; 19.0 returns data and the UI owns the words. `rpe_rounded`, `distance_rounded` and `title_fallback` get plan copy (AC15).
- **D12 ✅ Muscles and equipment come from 19.0's tables, not a hand-written list in §6.5 (mine).** Rationale: one source of truth; a test asserts the §6.5 examples (`core` to `abdominals`, `quads` to `quadriceps`) come out the same.
- **D13 ✅ The section sits under the 18.0 Edit row, not directly under the stats (mine).** Rationale: 18.0 AC1 already put **Edit workout** there; the Hevy section follows it and stays above the records block and the exercise list.
- **D14 ✅ The workouts module boundary is `queries` + `finishEvents` + `import type` (mine).** Rationale: the send and auto-push need `useWorkoutClient` and `WORKOUT_KEYS`, which live in `queries`; widening the scan to exactly these keeps the dependency one-way in spirit.
- **D15 ✅ A conclusive "not found" after a check releases the claim from the client (mine).** Rationale: it is a `DELETE` the user did not tap, but it only clears a claim and re-enables Send; the alternative strands a "sending" row for two minutes.
- **D16 ✅ Owner decision (Carol, 2026-10-26): no axe dependency.** Structural a11y tests stand in (AC21).
- **D17 ✅ Owner decision (Carol, 2026-10-30): the claimed fingerprint keeps today's contract (the Phase A plan's Q1).** Complete sends back the begin's fingerprint and the server stores it (19.0 minor 144); a `409 hevy-no-claim` on complete reads as refused and the link is read again. Minors 139 and 144 stay held (19.0 D22); Phase A needs no API change.
- **D18 ✅ Owner decision (Carol, 2026-10-30): two Hevy answers AC8 / AC9 don't name are definite (Q2).** A Hevy `429` on the create or update, and a `404` on a create, release the claim and show the static sentence (`429`: 20.0's "Hevy asked us to slow down…"). Hevy answered and wrote nothing.
- **D19 ✅ Owner decision (Carol, 2026-10-30): a SIN `429` during a send (Q3).** On begin or release it is the generic failure (a refused begin made no claim); on complete it is retried like a `5xx` (three times, 1-2-4 s), then "couldn't record it". 19.1 D22 (an unrecorded claim and a later import) is unchanged (Q4).
- **D20 ✅ Owner decision (Carol, 2026-10-30): create-only sends, built in Phase A (Q5).** A send may be marked `createOnly`; when begin answers `mode: "update"` (another device sent it meanwhile) it releases the claim and writes nothing (`skipped: already_sent`). Phase B's auto-push passes it, so it never updates a copy (D6).
- **D21 ✅ The follow-ups after an ambiguous failure don't begin again (mine, from the build).** The claim from the first begin is still fresh (two minutes), so a second begin would be refused as "in progress". Check Hevy, Check again, Send anyway and Try again on an update carry the begin's fingerprint (and Hevy id) from the outcome, held in mutation state only.
- **D22 ✅ The auto-push switch's checked box is a selection, so its style sheet is on `ui/roles.test.ts`'s teal allow-list (mine).** `features/hevy/AutoPushSetting.module.css` joins `SIGNAL_ALLOWED`, as Keep screen on (#108) did: `accent-color: var(--color-selected)` on a checked box is the same role.
- **D23 ✅ AC29's scan: Hevy's workout writes are looked for in `features/hevy/` only (mine, from the build).** `updateWorkout(` is also the SIN workout client's method in `features/workouts/`, so a whole-`src/` scan for the name would flag it. Only `features/hevy/` can hold a `HevyClient`; there, only `send/runSend.ts` calls the writes and `client/hevyClient.ts` declares them. `/hevy-link` is still scanned across all of `src/` (only `runSend.ts` and the `GET` in `useHevyLink.ts`).
- **D24 ✅ Auto-push sends with `createOnly` (mine; settles the Phase B plan's open question 1 through D20).** If a send lands between auto-push's link read (`none`) and its begin, begin answers `update` and the run releases and writes nothing, so auto-push never updates a copy (D6). Its checks' fresh mapping is handed to the run for that run only (`SendReads`, minor 263), so an auto-push reads it once; the workout is still read twice, the run's read right before its begin, so an edit made just after the finish reaches Hevy (AC4).
- **D25 ✅ A claim lost after Hevy took the write keeps the copy's id (mine, minor 257).** When `complete` answers `hevy-no-claim` after the Hevy write, the outcome keeps the Hevy id and the section offers Try again (`reclaim`): a new begin, then that copy is updated (`PUT`), or created if it was deleted in Hevy meanwhile, so the lifter never makes a second copy by sending again. If the new begin answers `update` (another device linked it), its own copy is updated. A reclaim that fails, or meets an unmatched exercise, is offered again, never a plain Send (which would post a second copy).
- **D26 ✅ A follow-up keeps its claim and stays offered (mine, minor 258).** A Check Hevy, Send anyway or Try again on an update whose reads fail, or that meets an unmatched exercise, keeps the claim and offers the same follow-up again (the needs-matching sentence when the sheet was closed), for as long as the claim holds; once it has gone stale the link no longer reads "sending" and Send begins on a stale claim, which looks in Hevy first (AC7). The minor proposed releasing before the sheet; a released claim would let the next Send (after Cancel or a reload) begin without a stale claim and skip AC7's look in Hevy, so the claim is kept instead.
- **D27 ✅ A link read as "sending" is read again (mine, minor 260).** Another device's claim was made before this screen read it, so the link is read again one claim window plus a second later (`SENDING_RECHECK_MS`), and on focus, while it reads "sending"; nothing is polled otherwise. The needs-matching line and the Hevy screen's switch follow another tab's change to the preference (minor 264, through `watchExternalWrites`).
- **D28 ✅ Owner decision (Carol, 2026-11-01): the lost-response check matches by start time and exercise count, the title only as a tiebreaker (minor 262).** A rename between an interrupted send and the check no longer hides the copy (which led to a duplicate). (Mine:) the count is of exercises with at least one set, on both sides: section markers and exercises whose sets were all dropped are sent with `sets: []` (19.0 AC12, O2), and whether Hevy keeps or lists those is unconfirmed, so counting them could hide every sectioned workout's copy. Several candidates that the title doesn't settle are inconclusive (the AC7 choices). Cost: exercises added or removed between the interrupted send and the check hide the copy.
