## 1. Purpose, scope & non-goals

### 1.1 Purpose

Everything Hevy needs a key, and a mapping from Hevy's exercises to SIN's. This spec gives Carol a **Hevy** screen under Profile where she pastes her key (kept on this device only, verified against Hevy), loads the mapping she keeps in a file (checked before anything is saved), reviews and edits what is paired, and downloads the mapping back as the same file. It also builds the **pairing component** (the Check-names step, for Hevy exercises) that the import and the send reuse.

**Success:** on staging she pastes a key, sees "Hevy key ending 3f9a, verified for jane_doe" and her Hevy username; loads her CSV and reads "212 will be paired, 3 left out", with each left-out line saying why; confirms; downloads the file and gets back what she loaded; and nothing she did put the key in a request to SIN, a log line or an error report. Everyone else sees no trace of any of it.

### 1.2 In scope

**Phase A (PR 1): the key and the Hevy client**
- The Profile entry (hidden unless `GET /v1/hevy/status` is `200`) and the `/app/profile/hevy` screen shell (§5.1).
- The key store (`sin:hevy:` prefix, remember or memory-only), the key card (paste, verify, last four, Replace, Remove) (§5.2, §6.2).
- The browser Hevy client: `api-key` header, schema-parsed replies, pacing, errors, no retry of a write (§6.3).
- The CSP change in both files and the parity check (§6.1).

**Phase B (PR 2): mapping and pairing**
- Load a mapping file: parse, resolve, preview, confirm (§5.3, §6.4). Download it (§6.5).
- The pairings screen: review, change which Hevy exercise a SIN exercise is sent as, remove a pairing (§5.4).
- The shared pairing component and its save (§5.5, §6.6).
- Harness, tests, phone check.

### 1.3 Non-goals (and where they live)

| Not here | Lives in / why |
|---|---|
| Fetching or writing workouts, routines | 20.1 (import), 20.2 (send) |
| Any server-held key | Future option (design); the key never leaves the device |
| Importing Hevy routine folders as anything | Design non-goal |
| Editing a Hevy exercise | Hevy's API has no edit; a created Hevy exercise is final (20.2 confirms before creating one) |
| Section rules editing on screen | The two named rules and the default come from the file or the defaults (D6); a screen for them is a later change |
| Showing Hevy controls to anyone but the owner | The gate (19.0); a `404` status hides everything |

### Fit for one work session

Phase A is a store, a client with a pacer, one card and one CSP edit. Phase B is a file flow, a list screen and a component derived from an existing one. Two PRs at the phase boundary.

## 2. Acceptance criteria

Every behavioral criterion has at least one test tagged **`"20.0 ACn — …"`**; `acTags.20-0.test.ts` checks the tags for unit-tested ones. §10 maps each to a method. "The key" is the Hevy API key; "the mapping" is Spec 19.0's.

### Phase A: the key, the client, the CSP

1. **Hidden by default.** `useHevyStatus()` calls `GET /v1/hevy/status` (key `["hevy","status"]`, `retry: false`, `staleTime` 5 minutes). `404`, a network error or a pending query render **no** Hevy row, text or route entry; only `200` shows the Profile row **Hevy** (to `/app/profile/hevy`). A direct visit to `/app/profile/hevy` when the status is not `200` renders the app's `NotFound`. The e2e smoke asserts the test user sees no "Hevy" text on Profile. Existing web tests run with MSW `onUnhandledRequest: "error"`, so the default handler set gains one `GET */v1/hevy/status` -> `404` (with a comment saying why) so every existing Profile test keeps passing.
2. **The key store.** `features/hevy/keyStore.ts` is React-free and goes through the `StorageAdapter` only. A remembered key is stored under `sin:hevy:key:<userId>` as `{ v: 1, key }`, checked by a Zod schema on read (a bad value reads as no key and is removed). `USER_DATA_KEY_PREFIXES` gains `"sin:hevy:"`, so `clearUserData` removes it on logout; the four hygiene tests that pin the prefix list (`sections.hygiene`, `drafts.hygiene`, `routines/hygiene`, `routines/import/hygiene`) take the new list, keeping their intent ("no prefix beyond Hevy's"), and `clearUserData.test` adds `sin:hevy:key:user-a` to its cleared set; the Spec 04.0 AC7 source scan and `workoutPrefix`-style tests still pass (no module but `storage.ts` names `localStorage`).
3. **Don't remember.** Saving with **Don't remember** keeps the key in a module-level memory store for this page load only: nothing is written to storage, a reload or logout forgets it, and an earlier remembered key for the user is removed. A remembered save clears the memory copy.
4. **Key shape.** A pasted key is trimmed and must be a UUID (Hevy documents `format: uuid`); anything else shows "That doesn't look like a Hevy key." and makes no request. The field is a plain text input (not `type="password"`, so no password-manager prompt), shown unmasked while typing, with `autocomplete="off"`, `autocapitalize="off"` and `spellcheck="false"` (D3); after saving only the **last four characters** show.
5. **Verification.** **Save** calls Hevy `GET /v1/user/info` with the pasted key before storing. Success with `is_pro: true`: the key is stored and the card reads "Hevy key ending ••••{last4}" and "Signed in to Hevy as {username}". `401` or `403`: "Hevy didn't accept that key. Check that it's a current key from a Hevy Pro account." and nothing is stored. `is_pro: false`: "This key is from a Hevy account without Pro, so Hevy's API won't work. Nothing was saved." Network failure: "Couldn't reach Hevy. Check your connection and try again." A reply that fails the schema: "Hevy's reply wasn't understood." A `404` ("User not found") shows the bad-key sentence. (No key is stored in any failure.) After a reload only the key is stored, so the card reads the username with `useHevyUser()` (`["hevy","user"]`, `staleTime` 5 min, `gcTime` 10 min, `retry: false`, removed on every key save or remove); if that call fails the card shows the last four plus that failure's sentence. Sentences for kinds the spec does not fix (`rate_limited`, `rejected`, `not_found`, `server`, `aborted`) are plan copy in `messages.ts` and may be changed in review.
6. **Replace and Remove.** **Replace** shows the paste field again (the old key stays until a new one verifies). **Remove** opens a `ConfirmDialog` ("Remove the Hevy key from this device?") whose confirm deletes the stored and memory copies; mappings, links and everything on the server are untouched. Both are announced in a polite status line.
7. **Never leaves the device.** The key is sent in exactly one place, the `api-key` header of a request to `https://api.hevyapp.com`. A source scan (comments stripped) fails if the literal `api-key` or `api.hevyapp.com` appears in any non-test module other than `hevyClient.ts`; a test spies on the SIN API client and asserts no request URL, header, body or query contains the key through the whole key flow; `reportError` (the app's only error-reporting seam) and the router's error boundary receive error objects whose `message`, `name` and `stack` do not contain the key (a test throws from inside each failure path with a recognizable key and greps every captured call).
8. **The Hevy client.** `features/hevy/client/hevyClient.ts` is React-free, built from `{ fetch, getKey, sleep, now }`, and exposes `userInfo`, `workoutCount` (`GET /v1/workouts/count`, parsed with 19.0's `HevyWorkoutCountSchema`; 20.1 AC3 needs it), `listTemplates`, `listWorkouts(page)`, `listRoutines(page)`, `listFolders(page)`, `createWorkout`, `updateWorkout`, `createTemplate` (body and reply per 19.0's create-template schemas). Every reply is parsed with the 19.0 Zod schema (`HevyUserInfoSchema` parses Hevy's `{ data: … }` wrapper, …); a failure throws `HevyError { kind: "unexpected_reply" }`. Requests carry `api-key`, `Accept: application/json` and, for bodies, `Content-Type: application/json`; no cookies (`credentials: "omit"`), `referrerPolicy: "no-referrer"`.
9. **Errors are typed and static.** `HevyError.kind` is one of `bad_key` (401/403 except the case below), `limit` (a 403 whose `error` equals `exceeds-custom-exercise-limit`; Hevy documents no routine-limit text and this client creates no Hevy routines, so any other 403 is `bad_key`), `rate_limited` (429), `rejected` (400, with Hevy's message **never** shown), `not_found` (404), `server` (5xx), `network`, `unexpected_reply`, `aborted`. A static `HEVY_COPY[kind]` maps each to the sentence the UI shows; Hevy's own error text is never rendered or logged (it may echo user input).
10. **Pacing.** `createPacer` enforces at least **600 ms** between any two requests from one client, **no request in the first 60 seconds of an hour** (UTC `:00:00` to `:00:59`: the call waits until `:01:00`), and honors `Retry-After` (seconds or an HTTP date) on `429`. Pure and unit-tested with an injected clock and `sleep`: a request at 12:59:59.700 is delayed to 13:01:00; two requests at the same instant are 600 ms apart; `Retry-After: 7` delays the next request by at least 7 s.
11. **Retries.** `GET`s retry up to 3 times on `429`, `5xx` and network failures with 1 s, 2 s, 4 s waits (and `Retry-After` when longer); `POST` and `PUT` are **never** retried by the client (a retry could create a second Hevy copy); an `AbortSignal` ends any wait at once with `aborted`.
12. **Pagination helpers.** `listAll(fetchPage, { onPage })` walks `page` 1…`page_count` (workouts, routines, folders at `pageSize=10`; templates at `pageSize=100`), reports progress `{ page, pageCount }` after each page, stops on abort, and treats a missing or zero `page_count` as one page. A page that fails after its retries ends the walk with that error and the pages already read.
13. **The CSP.** `render.yaml`'s si-web-staging block and `apps/web/firebase.json` send a `connect-src` of `'self'`, the API origin, the Auth0 origin **and `https://api.hevyapp.com`**, with every other directive unchanged. `assert-render-yaml.mjs` asserts the Hevy origin is allowed and no other new origin is; `firebase-parity.mjs` expects exactly `'self'` + the production API origin + the Auth0 origin + the Hevy origin (it must no longer find "the" Auth0 token with a bare `.find`: the Auth0 token is the first `https://` token that is neither the staging API nor the Hevy origin; it exports `HEVY_ORIGIN`); `assert-render-yaml.mjs` requires `connect-src` to be exactly that set (`'self'`, API, Auth0, Hevy); the web smoke gains `checkHevyOrigin(csp)`, which fails unless `connect-src` contains the Hevy origin; its tests, and `assert-firebase-json` in the CI `web` job, pass; a test fails if `connect-src` contains `*`, `https:` or any Hevy origin other than `https://api.hevyapp.com`.
14. **The screen shell.** `/app/profile/hevy` is a `Screen` titled "Hevy" with a `BackLink` "Back to Profile", the key card, and (Phase B) the mapping card. Loading, offline (the key card works from storage; verification needs the network) and error states are covered; every control is ≥ 44 px.
15. **Offline copy.** With no network, **Save** shows the network sentence of AC5; nothing else on the screen requires the network except Phase B's file flow (§6.4).
16. **Harness and tokens.** `assert:css-tokens` passes; no new design value; the screenshot harness captures the screen in light and dark at 390 and 1280 px (key absent, key present, verification failed) with the fake Hevy client, serving Hevy's `/v1/...` paths from a separate route for `api.hevyapp.com` (the SIN fake-API route is narrowed to the fake API's origin plus `/v1/`, because Hevy's paths also start with `/v1/`); `roles.test.ts` unchanged (no brass, teal only for the primary button).

### Phase B: mapping file, pairings, pairing component

17. **Mapping card.** Shows "N exercises paired" (from `GET /v1/hevy/mapping`, `pairs.filter(role === "exercise").length`), **Load a file**, **Download file**, **Review pairings**; with no key the file flow's resolving step says "Add your Hevy key first" and **Load a file** is disabled until one exists (Hevy's template list is needed to resolve titles, D4).
18. **Choosing a file.** An `<input type="file" accept=".csv,text/csv">` (visually a button, reachable by keyboard) reads the file with `file.text()`; over 1 MiB or 5,000 lines is refused before parsing ("That file is too big to be a mapping."); a parse error (`bad_header` and the other 19.0 AC14 codes) shows the code's static sentence (plan copy, one per code) and the line number and offers no confirm.
19. **Resolving.** For each line the app resolves the Hevy side (template id, else the title matched **exactly** against the fetched Hevy templates; two templates with one title is "ambiguous") and the SIN side (`sin_id` must be a visible active catalog row, else `sin_name` matched by `normalizeExerciseName` equality; two visible rows with one normalized name is "ambiguous"; the file never guesses, so `matchExerciseName`'s custom-first tie-break is not used here). Templates come from `listAll` over `GET /v1/exercise_templates` (progress "Reading Hevy's exercise list… page 3 of 7"), held in memory only for the session (TanStack cache, `gcTime` 10 minutes, no storage). A line with an id and a title that disagree resolves by the id and is listed as a notice.
20. **Checking.** Each resolved exercise line is checked with `hevyPairingProblem(hevyType, modality, rule)`. A `reps_only` Hevy exercise whose title contains "(calories)" paired with a Calories exercise and no rule is flagged "needs the calories rule" with a one-tap **Count calories as reps** that sets `calories_as_reps` on that line in the preview (never applied silently, D5); an assisted-weight exercise paired with Bodyweight reps and no rule likewise offers **Ignore the assist weight**. The offer is decided by `fixableRule(hevyType, modality)` (the one `MeasureRule` that makes `hevyPairingProblem` null when the no-rule call is a problem, else `null`), because 19.0 §6.2 returns `type_mismatch`, not `rule_required`, for an assisted exercise with no rule. Any other problem is listed as "{Hevy title} can't be paired with {SIN name}: the types don't match" with the two type labels.
21. **The preview.** After resolving, a screen lists: **Will be paired** (count, collapsed list), **Left out** (each line: its file line number, the two names as written, and one reason: not found in Hevy, not found in SIN, ambiguous, type mismatch, retired exercise), **Section rules and placeholders** (what the file sets, and a note when a placeholder exercise was not found), and **Will be removed** ("N pairings in the app that are not in this file", listed by name, collapsed). Nothing is saved yet. **Cancel** leaves everything unchanged.
22. **Confirm.** The primary button reads "Load {n} pairings" (and "leave out {m} lines" in its description when m > 0) and is disabled while a calories or assist fix is unresolved. It sends **one** `PUT /v1/hevy/mapping` with the resolved pairs (`exportAs` as the file says; blank means the first for that exercise, normalized by `normalizeExportAs` before sending) and the section rules; success invalidates `["hevy","mapping"]` and `["hevy","status"]` and shows "Loaded {n} pairings." A `422` shows a static "The server didn't accept this mapping" notice with the first error's path only (never a title) and leaves the preview open; offline shows the network sentence; a `429` shows the retry-after sentence.
23. **Download.** **Download file** fetches `GET /v1/hevy/mapping`, builds the CSV with `formatMappingCsv` (writing the **effective** section rules: the two defaults when the user has none), and saves `hevy-mapping.csv` through `saveBlob` as a locally created Blob (UTF-8, `text/csv`). Download then Load of the same file yields "0 removed, 0 left out" and an identical mapping (a test round-trips through the fake API).
24. **Pairings screen.** `/app/profile/hevy/pairings` lists the paired SIN exercises (A-Z, searchable with `searchByName`), each with its Hevy pairings underneath (Hevy title, Hevy type label, rule badge "calories as reps" / "ignores assist weight") and **Sent as** marking the export-as pairing. An exercise that was soft-deleted (`exerciseActive: false`) is listed under "Exercises you deleted" with only **Remove**; skipped Hevy exercises and the two placeholders are listed under their own headings. The list renders at once from the mapping query and is not virtualized (≤ 2,000 pairs; a test renders 600).
25. **Pairing actions.** On an exercise with more than one pairing, **Send as this** on a non-export pairing issues `PATCH { upsert: [{ …pair, exportAs: true }] }`; **Remove pairing** (a `ConfirmDialog` naming the Hevy exercise; the last pairing of an exercise says the exercise "won't be sent to Hevy until you pair it again") issues `PATCH { remove: [id] }`. Both are pessimistic, online-only (`networkMode: "always"`, `retry: false`), disabled while in flight, and refresh the mapping query from the response; an error shows a static notice and changes nothing on screen.
26. **The pairing component.** `features/hevy/pairing/` exports `PairingCards`, a controlled list of one card per unpaired Hevy template (`PairingNeed = { template, context, missing? }`; with `missing`, the card also shows "No longer in Hevy", for Spec 20.1 AC32), built on the 10.4 pattern: card state is a pure model `pairingCards.ts` (`initialPairingCards`, `chooseMatch`, `chooseNew`, `chooseSkip`, `chooseExisting`, `problemFor`, `validity`), each card offers **exact** or **similar** match (by `matchExerciseName` over the visible catalog, pre-selected), **Choose another** (`ExercisePicker` with `allowCreate={false}`), **New** (the `ExerciseFields` inputs prefilled from `exerciseFromHevyTemplate`, with the suggested rule shown as a checkbox the user must tick or untick) and **Skip** (the Hevy exercise is paired as `skip`; its sets are dropped in the import and reported). Defaults: a match when one exists, else New. A trailing parenthetical ("(Barbell)") counts: when `matchExerciseName(title)` finds nothing, the match is retried with `title.replace(/\s*\([^()]*\)\s*$/, "")` and any hit is `similar`. No screen in this spec hosts `PairingCards` (its consumers are 20.1's import and the New card in 20.2's own sheet, 20.2 D4), so it is covered by component and unit tests with a test-only host. Each card shows the Hevy title, type label and, when given, where it was used ("3 workouts, 1 routine").
27. **Pairing validity.** A card is valid iff its chosen SIN exercise (or New's modality) passes `hevyPairingProblem` with the card's rule, a New card's fields pass `CreateExerciseSchema` and its name is non-blank, and the card is not a duplicate of another card's New name (the 10.4 AC27 name check, now in the neutral `features/catalog/newExerciseName.ts`: `newNameProblem`, `duplicateNewNameKeys`; 10.4's `cards.ts` imports it back and its tests are unchanged). An invalid card shows its one reason in text and blocks **Continue**; the component reports `{ valid, decisions }` to its parent and never writes anything itself.
28. **Saving pairings.** `savePairings(decisions, deps)` (React-free, after `prepareImportBody`'s shape) creates the New exercises **one at a time, in order, online-only** through `createCustom`, paced at **no more than 15 per minute** (the API's `exercises` group allows 20; D7) and honoring `429`'s `Retry-After`; before a retry it refreshes the catalog and reuses an exercise already created under that name and a recorded `created` map entry; a `409 exercise-limit-reached` stops with the 500-cap sentence and saves **no** pair; once all exist it issues `PATCH /v1/hevy/mapping { upsert }` (batches of ≤ 200), then invalidates `["hevy","mapping"]`. A pair is only written after its exercise exists; a failure leaves a re-runnable state (nothing is half-paired: exercises created stay, the retry reuses them).
29. **New exercises are not leftovers.** Every New card whose `Continue` was not pressed creates nothing (the creates happen only in `savePairings`); leaving the screen discards the card state (in memory only; no storage key; `USER_DATA_KEY_PREFIXES` gains nothing beyond AC2).
30. **Placeholders.** (`PlaceholderSheet`.) If the mapping has no `warmup_placeholder` or `workout_placeholder` pair, the mapping card says "Section markers aren't set up. Sections will go into the first exercise's notes." with **Choose them** opening a sheet that fetches Hevy's templates, lets her pick the Hevy exercise for each of Warmup and workout (a searchable list, with her existing "Warmup" / "workout" titles pre-selected if found exactly), and saves them with `PATCH { upsert }` (`role` `warmup_placeholder` / `workout_placeholder`, `hevyType` from the template). Optional; the screen works without them.
31. **Import boundaries.** A scan test fails if `features/hevy/` imports from `features/routines/import/` other than its pure models (`cards.ts` helpers it reuses are re-exported from a neutral module in this spec, D8), if any module outside `features/hevy/` calls `api.hevyapp.com`, or if `features/catalog/` imports from `features/hevy/`. Stricter than first drafted: no `features/hevy/` file imports from `features/routines/` at all (the shared name checks moved to `features/catalog/`, D8).
32. **Accessibility.** The Hevy screen, the preview and the pairing cards have landmarks and headings in order; every status/notice is a polite live region that is empty at first paint; focus moves to the preview heading after resolving and to the status line after a save; no color-only state. There is no axe dependency in the repo (Carol, 2026-10-26): the structural a11y tests (roles, names, landmarks, headings, live regions, via Testing Library, as the existing screens' do) stand in for it on each screen state.
33. **Phone check (manual, after each phase on staging).** On Carol's iPhone, one-handed: paste the key (Don't remember, then remembered), see the last four, Replace and Remove; load her CSV and read the preview; confirm; download and compare to the original; open Pairings, change a Sent-as and remove one. (Pairing a template through a New card has no entry point in this spec; that step moves to 20.1's phone check.) Recorded in `gym-checklist-2026-10.md`. A live check against real Hevy (no stored key) confirms the browser can call `api.hevyapp.com` under the CSP (CORS `*`, header `api-key` allowed).

## 4. Data model

None server-side. Client:

- **One `localStorage` key:** `sin:hevy:key:<userId>` = `{ v: 1, key }` when the key is remembered (AC2). Covered by `USER_DATA_KEY_PREFIXES`, so logout removes it.
- **No other storage.** Templates, the resolved file, the preview and the pairing cards are in memory (TanStack cache with finite `gcTime`, component state). The mapping is read from the server on each visit (`private, no-cache` + `ETag`).
- **Router state:** none.

### 5.2 Loading a file (a sheet, then a screen)

## 6. Behavior & logic

### 6.1 CSP

The one new origin is `https://api.hevyapp.com`. In `render.yaml` the `connect-src` value becomes `'self' https://si-api-ft2f.onrender.com https://dev-gncuqvfir0wv0t4l.us.auth0.com https://api.hevyapp.com`; `apps/web/firebase.json` the same with the production API origin; `firebase-parity.mjs`'s expected `connect-src` set gains the Hevy token; `assert-render-yaml.mjs` adds it to its allowed list and keeps the "no relaxation" checks (`*`, `unsafe-*`, `blob:`, `data:` in `connect-src`). Hevy replies `Access-Control-Allow-Origin: *` and allows the `api-key` header, so a plain `fetch` works; the first live check (AC33) confirms it, and if Hevy ever blocks the origin the symptom is the same as a missing CORS method: the screen reports "Couldn't reach Hevy", which is what the user sees offline too (the 2026-10-11 PUT bug's lesson: the client cannot tell the difference, so AC33's live check is the guard).

### 6.2 The key

`useHevyKey()` reads `keyStore.get(userId)` (memory first, then storage). `save(raw, { remember })`: trim → UUID check → `HevyClient.userInfo()` with a **candidate** client (the key is passed in, not read from the store) → on success `keyStore.set` → invalidate nothing on the server. The field is cleared after a save. The key is never put in router state, a query key, a React Query cache entry, a log or `reportError`'s context. The last four characters are derived on render from the stored key (not stored separately).

### 6.3 The client and the pacer

One `HevyClient` instance per signed-in session (`useHevyClient`), sharing one `createPacer` so concurrent callers (the template read and a send) are serialized through the same gap. Writes are never retried by the client (AC11); 20.2 owns what to do after an ambiguous write. Each method returns the parsed value; none returns Hevy's raw error text.

### 6.4 The file flow

Pure steps first, then I/O: `parseMappingCsv(text)` (errors stop here) → `resolveLines(lines, { templates, catalog })` (pure; returns `{ pairs, leftOut, notices, needsRule }`) → the preview → `PUT`. Resolution order per line: `kind` `exercise` / `skip` need a Hevy ref; `exercise` also a SIN ref; `placeholder` needs a Hevy ref and `rule` `warmup` or `workout`; `section` needs `sin_name` and a treatment. `export_as` blank or `no` for every pairing of an exercise normalizes to "first in file order"; `yes` on two lines of one exercise keeps the first and lists a notice. Loading **replaces** the mapping (D2): the preview's "Will be removed" says exactly what that deletes.

### 6.5 Download

The CSV is `formatMappingCsv(mappingToCsvLines(mapping, sinNameOf))` (19.0 AC14, D24) and lists, in order: exercise pairs (by Hevy title), skips, placeholders, then section rules (effective, so a user with none gets `Warm-up → warmup_placeholder` and `Accessory → notes_on_first` written out and can edit them in the file). `export_as` is written `yes`/`no` for every exercise pair, so the file is explicit.

### 6.6 Pairing decisions

`initialPairingCards(needs, visible)`: for each Hevy template, `matchExerciseName(title, visible)` (with the 10.4 normalization: case, diacritics, a trailing parenthetical like "(Barbell)" is kept for the exact test and dropped for the similar test); `defaultMeasureRule(title, type)` seeds the rule checkbox; New's `ExerciseFields` values come from `exerciseFromHevyTemplate`. `problemFor(card)` is `hevyPairingProblem(template.type, chosenModality, card.rule)`. A card marked **Skip** needs no SIN exercise. The decisions the component reports are `{ template, action: "pair" | "create" | "skip", exerciseId?, create?: CreateExercise, rule }`.

## 7. Security & privacy

- **The key.** Stored on the device only, behind the `StorageAdapter`, cleared on logout (AC2); never sent to SIN; never in a log, error report, URL, query key or router state (AC7). It is readable by script on this origin: the strict CSP (`script-src 'self'`, no inline, no `eval`) is the control, the same one that protects the Auth0 session. The risk is the owner's to accept (design option 2); a stolen key can read and write her Hevy data and nothing in SIN.
- **The only new network destination** is `https://api.hevyapp.com`, in `connect-src` only (AC13).
- **Untrusted replies.** Every Hevy reply is schema-parsed (AC8); Hevy strings are rendered as text (React-escaped), never as markup, and never used in a route, a storage key or a selector. Hevy error text is not shown (AC9).
- **The file** is read locally with `file.text()`; nothing is uploaded; the server receives the resolved ids only.
- **Visibility.** A non-owner has no Hevy UI and the routes 404 (19.0). The status query is the only Hevy-related request a non-owner's browser makes.
- **Privacy.** Hevy exercise titles and ids are user data stored on the server (exported and purged with the account, 19.0). No analytics, no telemetry attribute.

## 12. Decisions & open questions

- **D1 ✅ The Hevy screen lives under Profile at `/app/profile/hevy`, not in the tab bar (mine).** Rationale: owner-only, rarely used after setup; a fifth tab or a Workouts-tab section would show it to everyone or crowd the logging path. Profile already holds Account data and device settings.
- **D2 ✅ Loading a file replaces the mapping, and the preview says what it removes (mine).** Rationale: the design says the file and the app must never drift and the download is the backup; "the file is the mapping" is the only rule that keeps that true. The preview's "Will be removed" list and the Cancel make it safe; on-screen pairings made since the last download are the only thing at risk, and that is exactly what the list names.
- **D3 ✅ The pasted key is shown unmasked while typing, with browser helpers off (mine).** Rationale: it is a 36-character UUID pasted once; masking hides typos, and a `type="password"` field makes browsers offer to save it in the password manager, which is a copy outside this app's control. After saving only the last four characters show.
- **D4 ✅ The file's Hevy titles are resolved in the browser against Hevy's live template list (mine; follows 19.0 D4).** Rationale: ids are stable but unreadable; Carol will write titles. Resolution needs the key, so **Load a file** needs a key first. Exact title match only (no fuzzy matching of file input): a typo is "not found in Hevy", listed, not guessed.
- **D5 ✅ The calories and assist rules are proposed, never applied silently (mine; Carol's convention is the proposal).** Rationale: the anti-goal is calories read as reps. The suggestion fires on "(calories)" in the title (Carol's naming convention *(Carol)*) and on assisted types; the user sees a ticked box and a sentence, and **Continue** confirms. A pairing that needs a rule and lacks one cannot be saved (the server refuses it too, 19.0 AC23).
- **D6 ✅ Section rules come from the file or the defaults; no on-screen editor in this spec (mine).** Rationale: there are three treatments and two named rules; the design puts them in the file. The placeholder pairs are the part that needs a screen (AC30) because they reference Hevy exercises.
- **D7 ✅ Creating exercises is paced at 15 per minute (mine).** Rationale: the `exercises` write group allows 20 per minute (05.2); a run of 100+ New cards would otherwise hit `429` repeatedly. Staying under it is cheaper than backing off; 429 handling remains as the safety net.
- **D8 ✅ The pairing component copies the 10.4 pattern and shares only pure helpers (mine).** Rationale: 10.4's `NameCard` is tied to the routine-import session (its handoff, `usedIn` section names); the Hevy card has different content (a Hevy type, a rule, Skip). A neutral module re-exports `matchExerciseName` use and the name-duplicate check so neither feature imports the other's screens.
- **D9 ✅ No telemetry or analytics (mine).** One user; the logs on both sides are enough.

- **D10 ✅ `sin:hevy:` joins `USER_DATA_KEY_PREFIXES` and updates the four hygiene tests (mine, from the build plan).** Rationale: the tests pin the list on purpose; they change in the same PR with their intent intact.
- **D11 ✅ Default MSW `GET /v1/hevy/status` -> 404 (mine).** Rationale: `onUnhandledRequest: "error"` would fail every existing Profile test on the new request; the handler's comment says so.
- **D12 ✅ `fixableRule` decides the offered fix (mine).** Rationale: 19.0 §6.2 returns `type_mismatch` for an assisted exercise with no rule, yet AC20 wants "Ignore the assist weight" offered; one function covers calories and assisted.
- **D13 ✅ Hevy replies come from 19.0's schemas, including the `data` wrapper, the count and the create-template schemas (mine).** Rationale: no web substitute (19.0 D26).
- **D14 ✅ Strict import boundary: `features/hevy/` imports nothing from `features/routines/` (mine).** Rationale: the name checks moved to `features/catalog/newExerciseName.ts`; the 10.4 tests are unchanged. `MAPPING_OFFLINE`, `MAPPING_RATE_LIMITED` and `EXERCISE_LIMIT_REACHED` are copied into Hevy's `messages.ts`, not imported.
- **D15 ✅ No axe: structural a11y tests (Carol, 2026-10-26).** Rationale: the repo has no axe dependency and adds none.
- **D16 ✅ Plan copy for type labels (`HEVY_TYPE_LABELS`), CSV error sentences, left-out reasons and status lines (mine).** Rationale: the spec fixes none; Carol may change them in review.
- **D17 ✅ The harness and the CSP check scripts change with the CSP (mine).** Rationale: Hevy's `/v1/` paths would be swallowed by the fake-API route, and `firebase-parity` cannot find "the" Auth0 token once a third origin exists.
- **D18 ✅ The user-info schema keeps what AC5 reads (mine, from the Phase A build).** 19.0's `HevyUserInfoSchema` parsed `data.{ id, name, url }` and stripped `username` and `is_pro`, which Hevy sends (19.0's own OpenAPI-copied fixture has both). It now keeps `username` (optional) and requires `is_pro` (a boolean), so a reply without `is_pro` is `unexpected_reply` ("Hevy's reply wasn't understood."). The fix is in `@sin/core`, as the plan asks for a schema gap, never a web substitute. The card shows `username`, else `name`.
