## 1. Purpose, scope & non-goals

Make the finished-workout data M2's APIs already serve visible on a phone: a **History** tab that lists finished workouts newest-first and opens any of them, and a **Personal records** block on the workout summary that shows which records that workout holds, how much each beat the previous best, and in the lifter's own unit. No API change, no migration, no new env var, no new browser-storage key.

> **First-principles note — why the finish response matters here.** The records a finish creates arrive *once*, in the `PATCH` response (`newRecords`). The web client currently parses that response with `WorkoutSchema`; Zod's default object parsing **strips unknown keys**, so `newRecords` is silently dropped before any component sees it. The summary could still get the same data from `GET /v1/personal-records?workoutId=` (07.0 AC14), but that costs a spinner on the one screen the lifter looks at right after Finish. So the client parses the response with `UpdatedWorkoutSchema` and writes `newRecords` into the cache under the key the summary reads; the GET is only the fallback (opening a workout from History, or after a lost finish response).

### In scope

- `/app/history` — `HistoryScreen`: keyset-paged list with a "Load more" button; empty, loading and error states.
- `/app/history/:id` — the existing `FinishedWorkoutScreen`, with a `section: "workouts" | "history"` prop that sets only the back link and the post-delete redirect.
- The "Personal records" block on that summary (both routes).
- The client plumbing: `historyClient`, `recordsClient`, `features/units/format.ts`, the cache effects of finish and delete, and the web `finish` fix (`UpdatedWorkoutSchema`).
- One extra Playwright smoke step; a manual phone check.

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|
| Progress tab, charts, chart library, per-exercise records list | Spec 08.1 (`/app/progress` stays `ComingSoon`) |
| History filters / search / date range (07.1 D2, O4) | Unscheduled |
| Infinite scroll, virtualised lists | Not planned — "Load more" is a deliberate choice (§12 D3) |
| A "New PR!" animation, confetti, a PR toast outside the summary | Not planned |
| Notes on history rows | Settled here (D5); 07.1 O2 closed |
| Any API change — including dropping `notes` from `WorkoutSummary` | Optional later API follow-up (D5) |
| Editing a finished workout | Deferred (DESIGN §2) |
| Persisting history or records to `localStorage` / the outbox | Not planned (D10) |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"08.0 ACn — …"`** (the prefix keeps `grep` honest next to 06.x's `ACn` blocks in shared files; 06.4 D6's precedent). Levels are in §10. **Phase A** (AC1–AC9): pure logic, clients, cache effects. **Phase B** (AC10–AC22): screens. **Phase C** (AC23–AC27): cross-cutting and verification. **Docs** (AC28–AC29).

### Phase A — logic, clients, cache

1. **Weight and volume are formatted in the lifter's unit.** `formatWeightKg(kg, pref)` and `formatVolumeKg(kg, pref)` (`features/units/format.ts`, pure, React-free). `pref = "kg"`: the value as stored, at most 3 decimals (`weight_kg` is `numeric(7,3)`), `en` grouping — `102.5 kg`, `6,420 kg`, `101.25 kg`. `pref = "lb"`: `kg / 0.45359237`, rounded to at most 1 decimal, `en` grouping — `100 kg → 220.5 lb`, `6,420 kg → 14,153.7 lb`. A trailing `.0` is never printed. `formatRecordValue(record, pref)` maps `unit: "kg"` → weight, `"kg_reps"` → volume, `"reps"` → `"12 reps"` (`"1 rep"`), with no conversion for reps; its `switch` over `RecordUnit` ends in a `never` check, so a new unit value is a compile error.
2. **Round trip.** A set entered as 225 lb is stored as 102.058 kg (the generated `weight_kg`); `formatWeightKg(102.058, "lb")` is `225 lb`. The same holds for 135, 315 and 45 lb entered values, and `formatVolumeKg` of a kg·reps sum built from them. A test iterates `RECORD_UNIT_VALUES` and asserts `formatRecordValue` handles every member without throwing.
3. **The history client builds the right request.** `listWorkouts({ cursor? })` issues `GET /v1/workouts?limit=20` and, with a cursor, `&cursor=<value>` where the cursor is percent-encoded (a value containing `+ / = & # ?` round-trips to the same string server-side); the body is parsed with `WorkoutHistoryResponseSchema`. The cursor is passed through verbatim — never decoded, parsed or constructed in `apps/web` (a source scan finds no `atob` / base64 handling or `v1.` literal under `features/history/`).
4. **The records client builds the right request.** `listRecords({ workoutId?, exerciseId? })` issues `GET /v1/personal-records` with exactly the filters given, each percent-encoded (an id `a/b?c#d` cannot change the path or add a parameter); the body is parsed with `PersonalRecordsResponseSchema` and the function returns `records`.
5. **The web `finish` keeps `newRecords`.** `WorkoutClient.finish` parses with `UpdatedWorkoutSchema` and returns `UpdatedWorkout` (06.1's `Workout` return type widens). A response with two records comes back with both. `["workouts","detail",id]` is seeded from the *workout fields only*: the cached object has no `newRecords` key.
6. **Finish success updates three caches, at hook level.** In `useFinishWorkout`'s `onSuccess` (so it runs even if the lifter navigated away — 06.1 AC12): (a) `["records",{workoutId}]` is set to `newRecords`, so the summary renders its block with **no** `GET /v1/personal-records`; (b) every `["history"]` query is invalidated; (c) every *other* `["records"]` query is invalidated (a finish can take a record from an older workout, 07.0 AC15) — and the entry written in (a) is **not** invalidated by (c) (it is fresh and correct; a predicate excludes it). The existing `workout_finished` event and detail seeding are unchanged.
7. **The "already finished" recovery gets the same effects.** Finish is never queued in the outbox (§6.2 — the outbox carries set writes only), so the only second route to "finished" is `ActiveSession.confirmAlreadyFinished` (the `409 workout-finished` ⇒ success path, a lost first response). It calls the same shared helper with no `newRecords`: the workout's `["records",{workoutId}]` entry is **removed** (so the summary fetches `GET /v1/personal-records?workoutId=`, which returns what the lost response carried — 07.0 AC14), and `["history"]` and the other `["records"]` queries are invalidated. After that path the summary shows the block.
8. **Deleting a finished workout updates the caches.** In `useDeleteWorkout`'s `onSuccess`, only when `phase === "finished"`: the workout's `["records",{workoutId}]` entry is removed; `["history"]` and `["records"]` are invalidated (the delete recomputes — another workout may regain a record). An `"active"` discard touches neither (an in-progress workout has no records and is not in the list). The existing detail removal and `["workouts","active"]` invalidation are unchanged, and a repeated delete answering `404` (treated as success, 06.1) applies the same effects.
9. **History paging.** `useHistoryList()` is an infinite query keyed `["history","list"]`; `getNextPageParam` returns the last page's `next` (`null` ends the list and `hasNextPage` is false); `initialPageParam` is `undefined` (page 1 sends no cursor). The screen's rows are the pages flattened **and de-duplicated by `id`** (first occurrence wins), so a row that shifts across a page boundary between two requests is shown once.

### Phase B — screens

10. **Routes and navigation.** `/app/history` renders `HistoryScreen`; the History nav item has no `comingSoon` flag and no badge; `/app/progress` still renders `ComingSoon`. `/app/history/:id` renders `FinishedWorkoutScreen` with `section="history"`; `/app/workouts/:id` with `section="workouts"`. At `/app/history/:id` the History nav link has `aria-current="page"` and the Workouts link does not (and conversely at `/app/workouts/:id`); the shell header title reads "History". An id whose workout is not finished still redirects to `/app/workouts` (06.1's rule, unchanged); an unknown id renders `NotFound` (unchanged).
11. **A history row.** Each row is one link to `/app/history/<id>` (the id path-encoded). Line 1: the date from `localDate`, formatted by the same pinned `en-GB` / `timeZone: "UTC"` formatter the summary uses (`Tue 6 Oct`). Line 2: `exerciseNames` joined with `", "`, followed by ` +N` when `exerciseCount > exerciseNames.length` (N = the difference). Line 3: `"{workingSetCount} sets"` (`"1 set"`), then ` · {volume}` formatted by `formatVolumeKg(totalVolume, pref)` — the volume part is **omitted entirely** (including the separator) when `totalVolume` is `null`. A row never renders `notes` or `title`, even when the fixture supplies them. The whole row is the tap target (≥ 44 px tall).
12. **The record badge.** A row with `recordCount > 0` shows a trophy badge (U+1F3C6) on line 1 whose accessible name is `"{n} personal records"` (`"1 personal record"` for 1), via `role="img"` + `aria-label` on the badge; the glyph itself is not announced separately. `recordCount === 0` renders no badge and nothing in its place.
13. **Load more, and the end.** Below the last row a "Load more" button is shown while the last loaded page's `next !== null`. Tapping it requests the next page with that cursor, appends the rows in order, is `disabled` and labelled "Loading…" while the request runs (no layout jump), and focus is never moved by the append. When `next === null` no button renders and nothing replaces it. There is no scroll listener (a source scan finds no `IntersectionObserver` / `scroll` handler in `features/history/`).
14. **Empty and loading states.** While page 1 is pending: the existing `Spinner` (label "Loading your history…"). `{ items: [], next: null }`: the text "No finished workouts yet" and a link to `/app/workouts`; no "Load more".
15. **First page fails.** An error with no data renders a full `InlineNotice` (`tone="error"`) "Couldn't load your history" with a "Try again" action (calls `refetch()`) and the request id when the error carries one. No rows, no Load more. A `network`, `server`, `unauthenticated` or `unknown` failure all take this path; `reportUnexpected` runs and reports only `unknown` (existing rule).
16. **A later page, or a background refresh, fails.** With rows already shown, a failed "Load more" keeps every row and replaces the button with a small `InlineNotice` "Couldn't load more" whose "Try again" calls `fetchNextPage()` again with the same cursor. A failed background refetch (after an invalidation) keeps the cached rows and shows "Couldn't refresh your history" with "Try again" → `refetch()`. In neither case does the screen blank or lose scroll position.
17. **A stale cursor resets the list.** A `422` whose field error path is `cursor` (a cursor format older than the deployed API) silently resets `["history","list"]` to page 1 — no error notice; the lifter sees the Spinner or the first page again — and calls `reportError(error, { source: "history", op: "stale-cursor" })` exactly once per occurrence. A `422` with any other path, or a non-`422`, is **not** treated this way (it takes AC15 / AC16). The reset is guarded so a persistently failing first page cannot loop (one reset per mount of the screen; the second occurrence shows the AC15 notice).
18. **The Personal records block.** On the summary, above the exercise sections, a section headed "Personal records" lists one line per record, ordered by `exerciseName` (locale-compare) then the `RECORD_TYPE_VALUES` order. Format: `"{exerciseName} — {label} {value}"` plus ` (was {previousValue})` when `previousValue !== null`, or ` (first record)` when null — e.g. `Bench Press — Heaviest weight 102.5 kg (was 100 kg)`. Labels: `heaviest_weight` → "Heaviest weight", `best_est_1rm` → "Best est. 1RM", `best_set_volume` → "Best set volume", `max_reps` → "Most reps"; the label `switch` is exhaustive over `RecordType` (a `never` check). Values and `previousValue` use `formatRecordValue` in the lifter's unit (a `max_reps` line reads `Pull-up — Most reps 12 reps (was 10 reps)`). The name is the record's `exerciseName` snapshot, never looked up in the catalog. The list is a real list (`<ul>`) in a `<section aria-labelledby>`.
19. **The block's states; the summary never waits on it.** No records (`[]`) → the whole section, heading included, is absent. While the records query is pending → nothing is rendered in its place (no spinner, no reserved space) and the exercise sections render at once. On failure → the section appears with an `InlineNotice` "Couldn't load records" and a "Try again" that refetches; the workout, its sets, the Delete control and the back link are unaffected and fully usable. A failed records request never changes the summary's own loading or error handling.
20. **The `section` prop.** With `section="workouts"` the back link reads "Back to Workouts" → `/app/workouts` and a successful delete navigates to `/app/workouts` (06.1, unchanged). With `section="history"` the link reads "Back to History" → `/app/history` and a successful delete navigates to `/app/history`. Nothing else differs between the two routes (same heading "Workout summary", same cache keys, same 06.4 active-entry cleanup guarded by id).
21. **Finish lands on a summary with its PRs and no extra fetch.** Through the real flow (`ActiveSession` → Finish → `/app/workouts/:id`) with a fake client returning `newRecords`: the block shows the records on first paint, and the request log contains no `GET /v1/personal-records`. After navigating to History, the finished workout's row appears (the invalidated list refetches) with the badge matching `recordCount`.
22. **Units follow the profile, with a safe fallback.** History volumes and the records block read `unitPreference` from `useMe()`. While `useMe()` has no data (loading) they format as `kg` — the same fallback as `ActiveSession` — and re-render in `lb` when the preference arrives or is changed on Profile (no stale text).

| Failure | Where | UI | Reported |
|---|---|---|---|
| any failure, page 1, no data | History | full notice + Try again (AC15) | `unknown` only |
| any failure, next page | History | small notice, rows kept, Try again → `fetchNextPage` (AC16) | `unknown` only |
| any failure, background refetch | History | small notice, rows kept, Try again → `refetch` (AC16) | `unknown` only |

| any failure | records block | block-local notice + Try again (AC19) | `unknown` only |
| `404` on the workout | summary | existing `NotFound` (unchanged) | no |
| offline | either | the same notices (`network` kind); no special handling, History is not part of the outbox (D11) | no |

## 6. Behavior & logic

### 6.1 Cache design

**Keys.**

```ts
HISTORY_KEYS = { all: ["history"], list: ["history", "list"] } as const;
RECORDS_KEYS = {
  all: ["records"],
  forWorkout: (workoutId: string) => ["records", { workoutId }],
  forExercise: (exerciseId: string) => ["records", { exerciseId }],   // 08.1
};
```

TanStack matches `invalidateQueries({ queryKey })` by **prefix** and hashes object keys stably, so `["records"]` covers every records query — 08.1's included — and `["history"]` covers the list.

**Freshness.** Neither query sets its own `staleTime`: both inherit the app-wide default (30 s, `AppRoot.tsx`), with `retry: false`. The reason is the seed: `setQueryData` stamps the entry as just-updated, so a 30 s window means the summary's `useQuery` mounts without refetching what finish just wrote (AC6, AC21); a `staleTime` of 0 would refetch it at once, defeating the point. Freshness against writes is by explicit invalidation (below), not by timing. A workout finished on *another device* shows up in History within 30 s of returning to the tab, or on the next mount after that — accepted.

**Finish success** — one helper, `applyFinishedCaches(queryClient, workoutId, newRecords | null)`:

1. If `newRecords` is given: `setQueryData(RECORDS_KEYS.forWorkout(id), newRecords)`; else `removeQueries(RECORDS_KEYS.forWorkout(id))`.
2. `invalidateQueries({ queryKey: HISTORY_KEYS.all })`.
3. `invalidateQueries({ queryKey: RECORDS_KEYS.all, predicate: q => !sameKey(q.queryKey, RECORDS_KEYS.forWorkout(id)) })` — every *other* records query; the predicate matters because a bare prefix invalidation would mark step 1's fresh entry stale and the summary would refetch it.

An invalidated query that no component observes is only *marked* stale; it refetches when next mounted, showing cached data meanwhile (stale-while-revalidate). So History after a finish shows its old rows for a moment, then the new row appears. For an *infinite* query a refetch re-walks every loaded page in order, using each refreshed page's own `next` — never a cached cursor — so the walk cannot reuse a cursor that the earlier pages invalidated. The cost is up to N sequential requests for N loaded pages, each measured at ~35 ms server-side (07.1 O1); accepted (D10).

**Delete success** — `applyDeletedCaches(queryClient, workoutId)`: `removeQueries(RECORDS_KEYS.forWorkout(id))`, then the same two invalidations. The row of the deleted workout can be visible for the sub-second until the History refetch lands after the redirect; tapping it in that window yields the existing `NotFound`. Accepted — pruning the cached pages by hand would add a second code path for a window that closes itself.

**Where they run.** `useFinishWorkout.onSuccess` and `useDeleteWorkout.onSuccess` (hook level, 06.1 AC12: they run even if the component unmounted), and `confirmAlreadyFinished`. The mutation hook's detail seeding spreads the response into the cached detail; it now destructures first — `const { newRecords, ...workout } = updated` — so `newRecords` never lands in `["workouts","detail",id]` (AC5).

### 6.2 What the outbox does and does not replay (verified in the tree)

The design brief asked whether an outbox-replayed finish reaches `useFinishWorkout`'s `onSuccess`. **There is no replayed finish.** `outbox/ops.ts` defines three op kinds — set `create`, `update`, `delete` — and `WorkoutClientProvider` wires only those (`onSynced` → `applySynced`, which writes set rows). `createQueuedWorkoutClient` spreads `...rest`, so `finish` is the REST client's own method, and Finish is *blocked* while any set write is queued (06.2 AC16) and runs with `networkMode: "always"` so it fails at once offline. The "replay" that exists is different: `ActiveSession.confirmAlreadyFinished` — after a `409 workout-finished` it fetches the workout, sees `endedAt`, seeds `["workouts","detail",id]` and tracks `workout_finished { viaReplay: true }`, **without ever passing through `useFinishWorkout.onSuccess`**. So today that path would skip the history invalidation and the records entry. Hence the shared helper (§6.1) and AC7; on this path `newRecords` is gone with the lost response, which is exactly the case the `?workoutId=` GET exists for (07.0 AC14). One more consequence for AC21's framing: the *normal* finish gets its records for free, the *recovered* finish costs one small GET — both end on the same screen.

### 6.3 History paging

`useHistoryList()`:

```ts
useInfiniteQuery({
  queryKey: HISTORY_KEYS.list,
  initialPageParam: undefined as string | undefined,
  queryFn: ({ pageParam }) => client.listWorkouts({ cursor: pageParam }),
  getNextPageParam: (last) => last.next ?? undefined,   // null/undefined ends the list
});
```

The cursor is a position, opaque by contract (07.1 §6.2 rule 3); the client stores it only as a function argument. Rows are flattened with a `Map` keyed on `id` (insertion order = first occurrence). De-duplication is a guard, not a feature: keyset paging already prevents the duplicates that offset paging produces, but an invalidation refetch of N pages can straddle a concurrent finish (a workout "finishing into" the boundary), and a duplicated React `key` is a console error and a rendering bug.

**Stale cursor (AC17).** `HistoryScreen` runs an effect on `query.error`: if it is an `ApiError` with status 422 and a `fieldErrors` entry whose `path` is `"cursor"` and the mount's reset flag is unset, it sets the flag, calls `queryClient.resetQueries({ queryKey: HISTORY_KEYS.list })` and `reportError`. `resetQueries` returns the query to its initial state (no data, no error) and refetches page 1 for the mounted observer — so the lifter sees the Spinner and then the first page, never an error. The once-per-mount flag bounds a pathological server that keeps answering 422 for page 1.

### 6.4 Units

`formatWeightKg(kg, pref)`: `pref === "kg"` → `NUMBER.format(kg) + " kg"` with the *same* pinned `Intl.NumberFormat("en", { maximumFractionDigits: 3 })` as `workouts/format.ts` (so 3 decimals, `en` grouping — `weight_kg` and `personal_record.value` are `numeric(…,3)`, so kg is shown exactly as stored); `pref === "lb"` → `LB.format(kg / 0.45359237) + " lb"` with `maximumFractionDigits: 1`. `0.45359237` is the exact definition of the pound (DESIGN §4.8). `formatVolumeKg` is the same function with the unit word attached (volume is kg·reps; the repetition count is dimensionless, so converting the kg factor converts the sum). Intl rounds half-away-from-zero at the last digit, which is the behaviour a lifter checking a number by hand expects; a value that rounds to a whole number prints without `.0` because `Intl` drops trailing fraction zeros under `maximumFractionDigits` alone.

Why 1 decimal for lb but 3 for kg: converting kg→lb is irrational, so extra digits are noise (and 225 lb round-trips through a 3-decimal kg store to 224.99999… which rounds to `225`); kg is shown as entered and stored, and rounding 101.25 kg to `101.3` would break a hand reconciliation. Set rows in the summary keep showing each set in the unit it was *entered* in (`formatSet`, unchanged) — a lifter who logs in lb with an lb profile sees lb everywhere; one who logs a kg set under an lb profile sees that set in kg and its record in lb, by design (the record is a derived, canonical number).

### 6.5 The records block

`PersonalRecordsBlock` reads `useWorkoutRecords(workoutId)` (`useQuery`, key `RECORDS_KEYS.forWorkout`, `queryFn: () => client.listRecords({ workoutId })`). It sorts a copy (`exerciseName.localeCompare`, then `RECORD_TYPE_VALUES.indexOf`) so that the order is the same whether the data came from the finish response or the GET (their server orderings are independently specified, 07.0 §5). It renders nothing while pending, nothing for `[]`, the notice on error. It is a sibling of the exercise sections inside `Summary`, so a failure there cannot unmount them (AC19). `DeleteWorkoutControl` remains its own component (06.1's reason: the delete removes the detail query; nothing here changes that).

## 7. Security & privacy

- **Authorization is the server's.** History and records are scoped by the authenticated user in 07.1 / 07.0; a tampered cursor or id can only name the caller's own rows (07.1 §7). The client adds no authority: it never decodes the cursor.
- **Path/query injection.** Every id and cursor placed in a URL is encoded (`encodeURIComponent` for path segments, `URLSearchParams` for query values) — the 06.4 AC5 rule extended to the two new clients (AC3, AC4).
- **Cross-user residue.** Nothing persists across page loads, and logout is a full redirect, so the in-memory cache cannot leak history to the next user of a shared browser. (If a later spec adds an in-SPA logout without a reload, it must `queryClient.clear()`; recorded in §12 O3.)
- **PII in logs.** The cursor encodes a timestamp and a workout id; it appears in the *API's* request line (07.1 AC19). In the browser it appears only in the request URL; the client's `routeTemplate` strips query strings from observability tags, and no `reportError` / `track` payload here carries it (AC25). Names and values (exercise names, weights) are user data and stay out of tags.
- **CSP.** No new origin, inline style or script; the trophy badge is a text glyph, not an image or a font download.

## 12. Decisions & open questions

### Resolved (drafting-time; owner-approved 2026-10-08 unless noted)

- ✅ **D1 — Split Spec 08 into 08.0 (History + PR display) and 08.1 (Progress charts).** **Rationale:** one work session each; 08.0 is all data the APIs already serve and needs no new dependency, while 08.1 carries a chart-library decision that should not block the history screen; the two halves also map onto M2's "reconciled by hand for 10 sessions" exit criterion (records and history here, charts there). Q16.
- ✅ **D2 — The summary is reused under `/app/history/:id` with a `section` prop, rather than navigating History rows to `/app/workouts/:id`.** The prop controls only the back link and the post-delete redirect. **Rationale:** `navItemFor` highlights the nav tab by pathname prefix, so opening a workout from History at `/app/workouts/:id` would highlight Workouts and mislead; a second route is one line, and no state is duplicated (same query keys, same component). **Rejected:** a `?from=history` query parameter (survives a reload as a hidden mode and does not move the highlight) and router `state` (lost on reload and deep links).
- ✅ **D3 — "Load more" button, not infinite scroll.** **Rationale:** one-handed gym use favours an explicit control the lifter can see and tap; there is no scroll listener to test, no observer lifecycle, and no accidental request storm on a slow Render free-plan cold start; a 20-row page is already several screens on a phone. **Cost:** one tap per page; revisit if real use shows long scrolling.
- ✅ **D4 — Row content is date, names (+N), working sets · volume, record badge.** **Rationale:** these are exactly the fields 07.1 computes per row (D3/D16 there), enough to recognise a session at a glance without opening it; volume uses the profile's unit (D8).
- ✅ **D5 — History rows do not show notes (settles 07.1 O2).** **Rationale:** a ≤ 4,000-character free-text field would break the three-line row's scan-ability and its fixed height; notes remain on the workout itself. The API keeps sending `notes` on every row (the `WorkoutSummary` shape is 07.1's, stable); dropping it from the list response is an **optional additive follow-up** (a slimmer row type), recorded here and not scheduled — the saving is small (most notes are empty) and a stable shape is worth more.
- ✅ **D6 — Records are cached under `["records",{ workoutId }]` and seeded from the finish response; `GET /v1/personal-records?workoutId=` is the fallback.** **Rationale:** the data the lifter most wants to see arrives for free in the response the client already waits for, so the summary renders it with no spinner and no second request; the GET covers opening an old workout from History and the lost-response recovery. One query key serves both, so the screen has one code path.
- ✅ **D7 — Finish and delete effects live in one shared helper pair, called from the mutation hooks and from `confirmAlreadyFinished`.** **Rationale:** §6.2 — there is no outbox-replayed finish, but there *is* a second "finished" path that bypasses the hook; three call sites of two small functions is cheaper and safer than letting the replay path drift. **Rejected:** moving all finish handling into the screen (loses the hook-level guarantee that a response landing after the lifter left still updates the cache, 06.1 AC12).
- ✅ **D8 — Units are formatted on the client in pure functions; lb at 1 decimal, kg at stored precision.** **Rationale:** the API serves canonical kg (DESIGN §4.8) and the profile preference is a presentation concern; pure functions are testable exhaustively (R4: silent wrongness hurts most here). kg is not rounded to 1 decimal, which the brief suggested, because 101.25 kg is a real load and `101.3` would break hand reconciliation; lb is rounded because the conversion is irrational. Shared with 08.1's chart axes.
- ✅ **D9 — Freshness by explicit invalidation on top of the app-wide default `staleTime` (30 s).** **Rationale:** §6.1 — the seeded records entry must not be refetched at once, which a `staleTime` of 0 would do. Every write that changes history or records (finish, delete, the recovery path) invalidates; a write on another device is picked up within 30 s of returning to the tab.
- ✅ **D10 — History and records are not persisted.** In-memory query cache only. **Rationale:** both are server-derived, cheap to refetch, and could be wrong if replayed from disk after a delete elsewhere; persisting would add a user-data storage key to clear on logout and a stale-data failure mode for no gain at this scale. An invalidated infinite query re-walks its loaded pages — accepted at ~35 ms a page (07.1 O1); the deep-list case (many pages) is rare in a gym session.
- ✅ **D11 — History is offline-naive.** A failed request shows the ordinary notice; there is no outbox, no cached-offline view. **Rationale:** reading history is not the time-critical gym path (06.2 protects *logging*); a spinner-then-notice on a dead connection is honest and cheap.
- ✅ **D12 — The Playwright smoke asserts the History row but not PR content.** **Rationale:** whether a given run produces a record depends on the test account's prior finished workouts (a tie goes to the earlier workout, 07.0), so an assertion would be flaky the moment a stray finished workout exists. PR display is covered by component tests with fixed fixtures and by the manual check (AC27). DESIGN §8.3's "see PR" step therefore stays unasserted; reword at implementation if a dedicated clean test account makes it safe.
- ✅ **D13 — Stale cursors reset silently, and are reported.** **Rationale:** a `422` on `cursor` can only mean the cursor format outlived a deploy (the client never constructs one), so the lifter did nothing wrong and cannot fix it by retrying; starting from page 1 is the only useful recovery, and the report tells us when deploys break open tabs. The once-per-mount guard stops a server fault from becoming a request loop.
- ✅ **D14 — The "Personal records" block shows records the workout holds *now*.** (§5.3.) **Rationale:** it is the definition `newRecords` and `recordCount` already use (07.0 D18), so the row badge, the finish summary and a later visit agree; a record that a later workout beat disappears from the earlier workout's block, which is the truth of "personal record".

### Resolved by reading the code (corrections to the design brief)
