# Spec 05.1 — Set Logging (API)

**Status:** Draft v0.3 — architect review pass applied (2026-09-21): fixed the
unit-accompanies-value merge/schema-layer mismatch, the finish-transaction
lock-ordering gap in §6.5, and the DESIGN §6 edit-list omission; 05.0 §6.5 has
since been amended to state the lock-first discipline generally (D8), closing
that follow-up question. One open item remains: which mechanism
(`SELECT … FOR UPDATE` vs. reordering the `UPDATE`) implements the lock.
**Last updated:** 2026-09-21
**Design refs:** DESIGN.md §4.4 (`set_entry` — nullable measures, per-modality
validation "not by DB `CHECK`s", finish-integrity rule), §4.8 (unit handling —
`weight_kg` / `distance_m` generated columns, canonical constants), §4.9
(deletion matrix — `set_entry` hard-deletes, transient during an in-progress
session), §6 (representative endpoints, `/v1` conventions). Spec 05.0 (session
lifecycle) — this spec fills its "Extension seam 1" and builds on its
conventions throughout: branded ids, `z.strictObject` request bodies,
allowlist response schemas, `assertOwned`-style ownership resolution, the
`workout-finished` immutability signal, and the per-parent advisory-lock
pattern for an append/insert path.

---

## 1. Purpose, scope & non-goals

Ship **set logging**: the `set_entry` table, the endpoints to create, edit and
delete a set within a `workout_exercise`, the per-modality validation that
decides which measures a set needs (`packages/core`), and the finish-time
integrity rule that 05.0 deliberately left unenforced (its "Extension seam
1" — DESIGN §4.4's "enforced at finish").

### In scope

- The `set_entry` table, migration `0006_create_set_entry`.
- `POST /v1/workout-exercises/{id}/sets`, `PATCH /v1/sets/{id}`,
  `DELETE /v1/sets/{id}`.
- Per-modality required/forbidden measure validation, as pure functions plus
  Zod schemas in a new `packages/core/src/dto/set-entry.ts`.
- The finish-integrity rule, added to `workoutRepository`'s finish transition
  (05.0 §6.5's named seam): every `working` set must satisfy its modality's
  required measures, or the finish is rejected.
- Extending `WorkoutDetail`'s per-exercise shape with a `sets` array, ordered
  by `set_number` ascending (05.0's `WorkoutDetailSchema` docstring already
  names this as 05.1's job).
- The `@sin/core` additions those need: `SetEntryId`, the set DTOs, and the
  validation functions.

### Non-goals

- **Personal records and any history/progress read.** `personal_record`, the
  e1RM/volume math, and every progress query are **Spec 07**. This spec writes
  `set_entry` rows; it computes nothing from them.
- **Rate limiting and per-user write quotas** are **Spec 05.2**. This spec
  ships no write throttle, same as 05.0.
- **Reordering sets.** `set_number` is an append-only ordinal assigned once at
  creation (§4, §6) — there is no reorder endpoint and no renumbering on
  delete, unlike `workout_exercise.position` in 05.0.
- **Editing a set after the workout is finished**, beyond what 05.0's
  `workout-finished` signal already blocks on every write. There is no "unlock
  a finished workout to fix a typo'd set" flow in v1 (DESIGN §4.5: finished
  workouts are immutable).
- **The logging UI** — the active-set input controls, rest timer, per-modality
  form fields — is **Spec 06**.

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number
(`describe("AC7 — …")`), mostly integration (Testcontainers) plus `@sin/core`
and route-level unit tests, following 05.0 §10's method exactly.

1. **Migration creates `set_entry` cleanly.** `0006_create_set_entry` applies
   on a fresh database and on top of the full existing chain (through 05.0's
   `0005`); creates `set_entry` with exactly the columns, types and
   nullability of §4; the FK `set_entry.workout_exercise_id →
   workout_exercise(id) ON DELETE CASCADE`; the `set_type` `CHECK`; and the
   named indexes. `prisma validate` passes with the `SetEntry` model and
   `WorkoutExercise.sets` back-reference, and there is no drift between the
   migrated database and `schema.prisma` (05.0 AC1's technique).
2. **`set_type`'s `CHECK` is drift-guarded against `@sin/core`.** A raw insert
   of a value outside `SET_TYPE_VALUES` is rejected; each member is accepted.
   A unit test asserts the migration `.sql` **contains** the clause rendered
   from the frozen constant (string containment, 03.1 AC2 / 05.0 AC2's
   technique) — `SET_TYPE_VALUES` already exists in `enums.ts` (added ahead of
   need), so this spec adds no new enum, only the guarded `CHECK`.
3. **Create appends the next `set_number`, scoped per `workout_exercise`.**
   `POST /v1/workout-exercises/{id}/sets` returns `201` with
   `Location: /v1/sets/{id}` and `setNumber = max(set_number) + 1` for that
   `workout_exercise_id` (`1` when there are none yet — `set_number` is
   1-based, matching how a lifter counts sets). Two different
   `workout_exercise` rows number independently starting at 1. `setNumber` is
   never a client-settable input (unknown key ⇒ `422` on both create and
   patch).
4. **Ownership resolves through the exercise→workout chain, 404 not 403.**
   A `set_entry` row carries no `user_id`; its ownership is its parent
   `workout_exercise`'s workout's. Another user's set, an absent id, and a
   malformed id are all `404 not-found` — indistinguishable, never `403` — on
   all three routes (create's `{id}` is the *workout_exercise* id; patch/delete's
   is the *set*'s own id). A malformed id is `404` via the branded
   `isSetEntryId` guard in the repository, before any query (05.0 AC15's
   pattern).
5. **`workout-finished` guards all three writes.** `POST
   /v1/workout-exercises/{id}/sets`, `PATCH /v1/sets/{id}` and `DELETE
   /v1/sets/{id}` each return `409 workout-finished` when the set's (or the
   target workout_exercise's) workout has `ended_at` set — the same slug 05.0
   defined, reused rather than redefined. There is no exemption for `DELETE`
   here (unlike 05.0 AC9's whole-workout `DELETE`, which *is* exempt): once a
   workout is finished, its sets are frozen along with everything else; the
   only escape hatch remains deleting the whole workout.
6. **Per-modality required measures gate `isComplete: true`.** Setting
   `isComplete: true` — on create or via a later `PATCH` — while a measure
   §6's table marks *required* for that set's `modality_snapshot` is null (and
   stays null after merging the request onto the existing row, for `PATCH`) is
   `422 validation-error` naming the missing field(s). The same create/patch
   with `isComplete` omitted or `false` succeeds with those fields still null
   — a half-filled in-progress set is always a legal write.
7. **Forbidden measures are rejected regardless of `isComplete`.** Populating
   a measure §6's table marks *forbidden* for the set's modality (e.g.
   `distanceM` on a `weight_reps` set) is `422 validation-error`, whether or
   not `isComplete` is set — this is a shape error, not a completeness one.
   `rpe` is accepted, null or non-null, on every modality.
8. **`PATCH` re-validates the merged row, not just the delta.** A `PATCH`
   supplying only `{ isComplete: true }` against a set that already has its
   required measures stored from an earlier write succeeds; the same `PATCH`
   against a set still missing one is `422`, exactly as if that measure had
   been omitted from a single combined request (the merge-then-validate
   pattern `exercise.ts`'s `UpdateExerciseSchema` merge path already uses).
9. **Delete is hard, allowed only in progress, and leaves a gap.** `DELETE
   /v1/sets/{id}` returns `204`, hard-deletes the row, and does not renumber
   any other set in that `workout_exercise` — `set_number` is a permanent
   ordinal, so deleting set 2 of 3 leaves sets 1 and 3, never renumbers 3 down
   to 2. A repeat `DELETE` of the same id is `404`. `DELETE` against a
   finished workout is `409 workout-finished` (AC5) — this route has no
   finished-workout exemption.
10. **Concurrent creates against one `workout_exercise` never collide or
    500.** **Six** concurrent `POST …/sets` against the same
    `workout_exercise` all return `201` with six distinct `setNumber`s
    (`1..6`), none `500`, none `409`: the create transaction takes
    `pg_advisory_xact_lock(hashtext(workoutExerciseId))` before reading
    `max(set_number)`, exactly as 05.0 §6.8 serializes its own per-workout
    add path, and the unique index (§4) is the backstop, not the primary
    mechanism. Six for the same reason 05.0 AC12 picked six: the pooled
    connection limit (`connection_limit=8`), not this criterion, is what a
    larger fan-out would actually be testing.
11. **The advisory lock re-checks `ended_at` inside the transaction.** The
    create transaction re-reads the parent workout's `ended_at` under `FOR
    SHARE` after taking the lock (05.0 §6.7's pattern) — a workout finished
    concurrently with an in-flight create either lets the create commit first
    or answers `409 workout-finished` and writes nothing, never a set row
    whose `created_at` postdates its workout's `ended_at`.
12. **Sets ride along in `WorkoutDetail`, ordered.** `GET /v1/workouts/active`
    and `GET /v1/workouts/{id}` return each exercise's `sets`, ordered by
    `set_number` ascending, via the extended `WorkoutExerciseDetailSchema`
    (§4). Deleting a set removes it from that array on the next read; nothing
    else in the array shifts.
13. **The finish-integrity rule blocks the finish, once, for the whole
    workout.** `PATCH /v1/workouts/{id}` with `endedAt` set is
    `409 incomplete-working-sets` when **any** `working` set across **any**
    of the workout's exercises is missing a measure required by its
    `modality_snapshot` (§6's table) — checked inside the same finish
    transaction 05.0 opened, per its "single entry point" contract (05.0 §6.5,
    Extension seam 1). The problem+json body carries no set or exercise id
    (no extension member) — same "no id leak" convention as
    `workout-in-progress-exists` (05.0 AC4). Fixing or deleting the offending
    set(s) and retrying the same `PATCH` then succeeds.
14. **`warmup` / `drop` / `failure` sets are exempt from the finish check.**
    A workout finishes successfully with a `warmup`, `drop` or `failure` set
    that has **no** measures populated and `isComplete: true` — DESIGN §4.4
    scopes the integrity rule to `working` sets only, and this spec does not
    widen it. The same three types are still subject to AC6/AC7's per-write
    validation when they *do* carry values (a `drop` set with a weight and
    reps validates exactly as a `working` one would).
15. **An account purge reaches `set_entry` with no ordering step.** Deleting a
    `user` row removes their `workout` rows, which cascade through
    `workout_exercise` to `set_entry` (`user → workout → workout_exercise →
    set_entry`) in one `DELETE`, with no FK violation — `set_entry` adds no
    new purge-ordering obligation beyond what 05.0 §4 already discharged,
    since it hangs off `workout_exercise`, not off `exercise` or `user`
    directly.
16. **The `set_created` log line is emitted without free text.** `POST
    …/sets` logs `set_created` with the set's id, its `workout_exercise_id`,
    `setType` and `modalitySnapshot` — no measure values (a weight or rep
    count is not free text, but is still excluded on the same "log shape,
    not content" principle 05.0 §9 used for counts). `PATCH` and `DELETE` emit
    no line beyond the request log — only creation and the (05.0-owned)
    finish/delete-workout transitions are business events.
17. **The `@sin/core` additions land cleanly.** `SetEntryId` ships the full
    `brandId()` quartet; `dto/set-entry.ts`'s schemas parse a valid payload
    and reject a missing required field, an unknown key, and every
    §6-table violation (required-missing, forbidden-present) across all five
    modalities; the pure `requiredMeasuresFor` / `forbiddenMeasuresFor`
    functions are exhaustively tested against §6's table (one case per
    modality per direction). Every new export is added **by name** to
    `check-exports.mjs`'s `EXPECTED` array; `pnpm run core:purity` stays green.
18. **All three routes are authenticated and in the published contract.**
    Each returns `401` with no token and with an invalid token, each appears
    in `GET /openapi.json` with camelCase schemas, and the extended
    `WorkoutExerciseDetailSchema` (with `sets`) replaces the plain
    `WorkoutExerciseSchema` in the two `GET` routes' emitted response shape.
    The CI OpenAPI drift check stays green.
19. **Docs stay consistent.** Every edit listed in §11's `DESIGN.md` edits
    subsection is applied. `docs/specs/README.md`'s 05.1 row moves from "Not
    started" to "Draft".
20. **Unit-accompanies-value is enforced against the merged row, not just the
    request body.** A `PATCH` supplying `{ weight: 52.5 }` alone against a set
    that already has `weightUnit` stored succeeds (the merged row is
    complete); the same `PATCH` against a set with **no** stored `weightUnit`
    is `422` naming `weightUnit`. On **create**, `weight` present without
    `weightUnit` (and vice versa; same for `distance`/`distanceUnit`) is
    always `422`, since there is no stored row to merge against. This rule
    fires before the modality-aware checks (§6.1) in every case.
21. **The finish-integrity check cannot be fooled by a set that commits mid-
    finish.** Fire a `PATCH /v1/workouts/{id}` finish and a `POST
    …/workout-exercises/{id}/sets` that would leave an incomplete `working`
    set concurrently against one in-progress workout with otherwise-complete
    data; the only two outcomes are (a) the set's create commits first and the
    finish then sees it and answers `409 incomplete-working-sets`, or (b) the
    finish's exclusive lock is acquired first, the create then blocks and
    ultimately answers `409 workout-finished` having written nothing, and the
    finish succeeds against the workout as it stood before the create began —
    never a `200` finish that overlooked a `working` set which in fact
    committed before the finish transaction committed (§6.5).

**Consumers must note:**

- **`WorkoutExerciseSchema` is not replaced on the wire; `WorkoutDetailSchema`
  is repointed.** 05.0 shipped `WorkoutExerciseSchema` (no `sets`) as the type
  for `PATCH`/`DELETE /v1/workout-exercises/{id}` responses, which stay as-is
  — those endpoints return one workout-exercise row, not its sets. This spec
  adds a new `WorkoutExerciseDetailSchema = WorkoutExerciseSchema.extend({
  sets: z.array(SetEntrySchema) })` and changes `WorkoutDetailSchema.exercises`
  to use it. This is additive to 05.0's shipped contract, not a breaking
  rename — a client reading `WorkoutDetail.exercises[].sets` today has never
  worked, so no consumer regresses.
- **07's finish-transaction extension runs after this spec's check.** 05.0
  named one seam; this spec and 07 both extend it, in order: 05.1's
  integrity check first (it can reject the finish outright), then 07's PR
  recompute (which only runs once the finish is going to succeed). `workoutRepository`'s
  finish method documents this ordering inline.

## 4. Data model

Owned by this spec: **`set_entry`**. Migration **`0006_create_set_entry`** —
additive, expand-only, applied on top of 05.0's `0005`. Hand-authored SQL, the
same carve-out 03.1 §4 and 05.0 §4 use: the `CHECK (set_type IN (…))` literal
list is not expressible in the Prisma schema DSL as a drift-guarded constant,
so the `.sql` file is the source of truth and the Prisma model exists for the
client only.

```
Table: set_entry
  id                     uuid        PK, app-generated UUIDv7
  workout_exercise_id    uuid        NOT NULL FK → workout_exercise(id) ON DELETE CASCADE
  set_number             smallint    NOT NULL        -- 1-based, append-only, never renumbered (§6)
  set_type               text        NOT NULL DEFAULT 'working'
                                     CHECK (set_type IN (<@sin/core SET_TYPE_VALUES>))
  reps                   smallint    NULL
  weight                 numeric(7,3) NULL           -- exactly as entered
  weight_unit            text        NULL CHECK (weight_unit IN (<WEIGHT_UNIT_VALUES>) OR weight_unit IS NULL)
  weight_kg              numeric(7,3) GENERATED ALWAYS AS (
                                       CASE WHEN weight IS NULL THEN NULL
                                            WHEN weight_unit = 'kg' THEN weight
                                            ELSE weight * 0.45359237 END
                                     ) STORED
  distance               numeric(9,3) NULL
  distance_unit          text        NULL CHECK (distance_unit IN (<DISTANCE_UNIT_VALUES>) OR distance_unit IS NULL)
  distance_m             numeric(9,3) GENERATED ALWAYS AS (
                                       CASE WHEN distance IS NULL THEN NULL
                                            WHEN distance_unit = 'm' THEN distance
                                            WHEN distance_unit = 'km' THEN distance * 1000
                                            ELSE distance * 1609.344 END
                                     ) STORED
  duration_s             integer     NULL
  rpe                    numeric(3,1) NULL
  is_complete            boolean     NOT NULL DEFAULT false
  completed_at           timestamptz NULL
  created_at/updated_at  timestamptz NOT NULL DEFAULT now()

Indexes:
  set_entry_workout_exercise_number_key UNIQUE (workout_exercise_id, set_number)
```

- **`weight_kg` / `distance_m` reuse 03.1/DESIGN §4.8's exact conversion
  constants** (`0.45359237`, `1000`, `1609.344`). These must be identical to
  whatever `packages/core`'s unit-conversion helpers use (Spec 02) — DESIGN
  §4.8 calls out that drift here "silently corrupts PRs and charts" (R4). A
  migration unit test asserts the generated-column expressions render these
  literal constants, the same string-containment technique used for the
  `CHECK` lists.
- **`set_entry_workout_exercise_number_key` is a plain (non-deferrable) unique
  constraint**, not `DEFERRABLE` like 05.0's `workout_exercise_position_key`.
  Nothing here ever needs two rows to briefly share a `set_number` — there is
  no reorder, no renumbering-on-delete — so an ordinary unique index both
  documents the invariant and is the collision backstop behind the advisory
  lock (§6). No separate `(workout_exercise_id)` index is created: every query
  this spec issues filters by `workout_exercise_id` alone or by that column
  plus an equality/range on `set_number`, both served by the composite unique
  index's leading column.
- **No `CHECK` ties a measure to its modality.** DESIGN §4.4 is explicit that
  per-modality validation lives in `packages/core`, not the database — a
  `set_entry` row's `modality_snapshot` lives one join away, on its parent
  `workout_exercise`, and a `CHECK` cannot see another table's column. The
  database only enforces shape (numeric precision, the two unit vocabularies,
  the `set_type` vocabulary); §6's required/forbidden rules are enforced in
  the API layer, at both write time and finish time.
- **`weight_unit` / `distance_unit`'s `CHECK`s allow `NULL`.** A set with no
  weight has no unit either; the `CHECK` must not reject the common "duration
  modality, no weight at all" row. (`weight IS NULL` does not itself imply
  `weight_unit IS NULL`, so the two are validated together at the API layer,
  not by a cross-column `CHECK` — Postgres can express that constraint, but a
  second drift-guarded literal-list `CHECK` per column is simpler to test than
  one compound one, and matches the one-`CHECK`-per-concern style 05.0 and
  03.1 already use.)
- **The `WorkoutExercise` model gains a `sets SetEntry[]` back-reference** —
  Prisma-client-only, same trap 05.0 §4 recorded for `User.workouts` /
  `Exercise.workoutExercises`.
- **`@@map("set_entry")` / per-field `@map`s**, plus every type Prisma's
  `migrate diff` compares (`@db.Uuid`, `@db.SmallInt` for `set_number` /
  `reps`, `@db.Numeric(7,3)` for `weight` / `weight_kg`, `@db.Numeric(9,3)`
  for `distance` / `distance_m`, `@db.Numeric(3,1)` for `rpe`,
  `@db.Timestamptz(6)`), matching 05.0 AC1's no-drift requirement. The two
  `GENERATED ALWAYS AS … STORED` columns are declared in Prisma as ordinary
  nullable columns with no `@default` — Prisma has no generated-column DSL, so
  (03.1's `change_xid`-adjacent precedent aside) these are read-only from the
  client's perspective by convention, never written by the app, and the
  migration's `NNNN_create_set_entry` file is the only place their expressions
  live.

## 5. API surface

All three routes are under `/v1`, require authentication, and go through the
Spec 03.0 route-schema convention. The two ambient failures
(`401 unauthenticated` / `401 invalid-token`) are listed once per route, as
05.0 §5 does.

```
POST /v1/workout-exercises/{id}/sets              auth required
  201  SetEntry                                    Location: /v1/sets/{id}
  404  not-found              — {id} absent, or its workout is owned by a
                                 different user
  409  workout-finished       — the parent workout has endedAt set
  422  validation-error       — malformed body, a forbidden measure for the
                                 modality, or isComplete=true with a required
                                 measure missing (§6)
  401  unauthenticated / invalid-token

PATCH /v1/sets/{id}                               auth required
  200  SetEntry               — { setType?, reps?, weight?, weightUnit?,
                                 distance?, distanceUnit?, durationS?, rpe?,
                                 isComplete? }
  404  not-found              — absent, or its workout is owned by a
                                 different user
  409  workout-finished       — the parent workout has endedAt set
  422  validation-error       — same rules as create, checked against the
                                 merged row (§6)
  401  unauthenticated / invalid-token

DELETE /v1/sets/{id}                              auth required
  204  (no body) — hard delete; no renumbering of sibling sets
  404  not-found              — absent, or its workout is owned by a
                                 different user
  409  workout-finished       — the parent workout has endedAt set
                                 (no exemption — contrast 05.0 AC9's whole-
                                 workout DELETE)
  401  unauthenticated / invalid-token
```

**No `GET /v1/sets/{id}`.** A set is read through `GET /v1/workouts/{id}` or
`GET /v1/workouts/active`, in `exercises[].sets` (§4), the same choice 05.0
made for `workout_exercise` itself.

**Path ids.** `{id}` on create is a `WorkoutExerciseId`; on patch/delete it is
a `SetEntryId`. Both are declared `z.object({ id: z.string() })` and turned
into `NotFoundError` by the branded guard before any query — a malformed id is
`404`, never `422`, matching 05.0 §5's convention for every id-taking route.

### `@sin/core` DTOs

```ts
// packages/core/src/ids.ts — addition
const setEntryId = brandId("SetEntryId");
export const SetEntryIdSchema = setEntryId.schema;
export type SetEntryId = z.infer<typeof SetEntryIdSchema>;
export const parseSetEntryId = setEntryId.parse;
export const isSetEntryId = setEntryId.is;

// packages/core/src/dto/set-entry.ts — new module
import { z } from "zod";
import { SET_TYPE_VALUES, WEIGHT_UNIT_VALUES, DISTANCE_UNIT_VALUES, type Modality } from "../enums.js";
import { SetEntryIdSchema, WorkoutExerciseIdSchema } from "../ids.js";
import { WorkoutExerciseSchema } from "./workout.js";

export type MeasureName = "reps" | "weight" | "distance" | "durationS";

/** §6's table, as data. Order matters only for stable error-field ordering. */
const MEASURE_RULES: Record<Modality, { required: MeasureName[]; forbidden: MeasureName[] }> = {
  weight_reps:          { required: ["weight", "reps"], forbidden: ["durationS", "distance"] },
  bodyweight_reps:      { required: ["reps"],            forbidden: ["weight", "durationS", "distance"] },
  weighted_bodyweight:  { required: ["reps", "weight"],  forbidden: ["durationS", "distance"] },
  duration:             { required: ["durationS"],       forbidden: ["weight", "reps", "distance"] },
  distance_duration:    { required: ["distance", "durationS"], forbidden: ["weight", "reps"] },
};

export const requiredMeasuresFor = (m: Modality): readonly MeasureName[] => MEASURE_RULES[m].required;
export const forbiddenMeasuresFor = (m: Modality): readonly MeasureName[] => MEASURE_RULES[m].forbidden;

// RPE bounds: DESIGN glossary, "1-10"; numeric(3,1) column allows one decimal.
const Rpe = z.number().min(1).max(10).multipleOf(0.1);

/** One logged set. Responses are z.object — a field allowlist (03.0 §6.5). */
export const SetEntrySchema = z.object({
  id: SetEntryIdSchema,
  workoutExerciseId: WorkoutExerciseIdSchema,
```

Points on the listing that are choices, not accidents:

- **`UpdateSetSchema` is the same shape as `CreateSetSchema`**, not a
  `.partial()` of `SetEntrySchema` — a `PATCH` never touches `setNumber`,
  `id`, `workoutExerciseId`, `completedAt`, `weightKg`/`distanceM` (generated,
  never client-writable), or `createdAt`/`updatedAt`; naming the allowed
  fields explicitly, once, keeps create and update from silently drifting
  apart the way a `.partial()` of the full response schema would invite.
- **`weightUnit` defaults are not applied by the schema.** A `weight` with no
  `weightUnit` is a shape error caught by §6.1's "unit accompanies value"
  rule. That rule is **handler-level, not a schema-level `superRefine`** — see
  §6.1 for why: on `PATCH` it must run against the *merged* row (existing
  `weightUnit` overlaid by whatever the request supplies), the same
  merge-then-validate point the modality checks use, not against the raw
  request body alone. A schema-level `superRefine` on `CreateSetSchema` /
  `UpdateSetSchema` would see only the body and would wrongly reject a
  legitimate `PATCH { weight: 52.5 }` that leaves an already-stored
  `weightUnit` untouched. This is stated fully in §6.1, not repeated here.
- **`completedAt` is server-stamped, never client-supplied.** Setting
  `isComplete: true` (via create or patch) stamps `completed_at = now()` in
  the same write; setting it back to `false` (allowed pre-finish, since
  nothing here is immutable until the workout finishes) clears it to `NULL`.
  Neither field is a `CreateSetSchema`/`UpdateSetSchema` key.

## 6. Behavior & logic

### 6.1 Per-modality measure rules

The table below is `dto/set-entry.ts`'s `MEASURE_RULES`, restated for
review — this is the concrete content DESIGN §4.4 deferred to this spec.

| Modality | Required | Forbidden | `rpe` |
|---|---|---|---|
| `weight_reps` | `weight`, `reps` | `durationS`, `distance` | optional |
| `bodyweight_reps` | `reps` | `weight`, `durationS`, `distance` | optional |
| `weighted_bodyweight` | `reps`, `weight` (added load) | `durationS`, `distance` | optional |
| `duration` | `durationS` | `weight`, `reps`, `distance` | optional |
| `distance_duration` | `distance`, `durationS` | `weight`, `reps` | optional |

A measure not listed as required or forbidden for a modality (there are none
in this table — every modality's five measures are one or the other, `rpe`
aside) would simply be optional; the table is exhaustive over the five
non-`rpe` measures for each modality by construction.

**Unit-accompanies-value is a cross-field rule, checked at the same point as
the modality checks below — handler-level, not a schema-level `superRefine`.**
`weight` non-null requires `weightUnit` non-null and vice versa (same for
`distance`/`distanceUnit`), independent of modality. This **cannot** be a
`superRefine` on `CreateSetSchema` / `UpdateSetSchema`: that schema is shared
by create and patch (§5), and a `PATCH` body is validated against the schema
*before* the handler ever sees the stored row. A schema-level check sees only
the fields present in that one request, so a legitimate `PATCH { weight: 52.5
}` — updating the weight of a set that already has `weightUnit: "kg"` stored,
without resending it — would be wrongly rejected as "weight with no unit."
This rule therefore runs in the handler, against the **merged** row on patch
(point 3 below) exactly like the modality checks, and against the raw body on
create (point 2 below, where there is no stored row to merge). It still fires
before the modality-aware required/forbidden checks — a `weight` with no unit
anywhere in the merged shape is malformed regardless of what modality it
belongs to — but "before" now means "the first handler check", not "in the
schema."

**The modality-aware checks are handler-level, not schema-level**, for the
same reason 05.0 §5 gives for its clock-skew and `endedAt` rules: a Zod schema
sees only the request body, not the target row's `modality_snapshot` (create:
the parent `workout_exercise`'s; patch: the set's own, read with the row). The
handler:

1. Resolves `modality` (via the parent `workout_exercise.modality_snapshot`;
   05.0 already snapshots it, so no extra join to `exercise` is needed).
2. For **create**: validates the request body's `weight`/`weightUnit` and
   `distance`/`distanceUnit` pairing (above), then its populated measures
   against `forbiddenMeasuresFor(modality)` — any present ⇒ `422`. If
   `isComplete: true`, additionally validates every `requiredMeasuresFor(modality)`
   entry is present in the body ⇒ else `422`.
3. For **patch**: computes the *merged* row (existing values overlaid by the
   request's provided keys — omitted keys keep their stored value, `null`
   clears it, exactly as 05.0's `UpdateWorkoutSchema` distinguishes omission
   from `null`), then runs the same unit-pairing and modality checks against
   the merged shape. This is the same "merge, then re-run the pure check"
   idiom `exercise.ts`'s `MuscleFieldIssue` comment documents for
   `UpdateExerciseSchema`.
4. A single `422` response lists every violated field via `fieldErrors`, not
   just the first — matching `ValidationError`'s existing `FieldError[]`
   shape.

### 6.2 Create

`POST /v1/workout-exercises/{id}/sets`:

1. Resolve the workout_exercise via the repository with `actingUserId`;
   absent or another user's ⇒ `404`. Parent workout finished ⇒ `409
   workout-finished`. Cheap early exit, as 05.0 §6.6 step 1.
2. Run §6.1's checks against the request body and the resolved
   `modality_snapshot`.
3. Open the append transaction (§6.3): take the per-`workout_exercise`
   advisory lock, re-check the workout's `ended_at` under `FOR SHARE`, read
   `max(set_number)` for this `workout_exercise_id`, insert at `max + 1` (or
   `1`), applying `completed_at = now()` when `isComplete: true` is set.
   Return `201` with `Location: /v1/sets/{id}`.

### 6.3 The per-`workout_exercise` advisory lock

Mirrors 05.0 §6.7/§6.8's shape, scaled down for an append-only sequence with
no renumbering:

- The transaction's first data-touching statement is
  `SELECT pg_advisory_xact_lock(hashtext($workoutExerciseId))`.
- `max(set_number)` is read as a separate, later statement — never folded into
  the same CTE as the lock, for the same snapshot-trap reason 05.0 §6.8 gives
  (03.2 D23).
- Because nothing here ever needs two rows to briefly share a `set_number`,
  there is **no deferred constraint** — `set_entry_workout_exercise_number_key`
  stays a plain, immediately-checked unique index, and the lock exists purely
  to prevent two concurrent creates from both computing the same `max + 1`
  before either commits.
- `hashtext` is applied to a `workout_exercise_id`, a different id domain from
  05.0's `workout_id` locks — the two schemes can theoretically collide on the
  same 32-bit hash bucket, which only ever costs a spurious wait, never a
  correctness bug (advisory locks are cooperative, and the two code paths lock
  different rows).

### 6.4 Patch and delete

`PATCH /v1/sets/{id}`: resolve the set through its `workout_exercise` →
`workout` chain with `actingUserId`; absent/another-user's ⇒ `404`; parent
workout finished ⇒ `409 workout-finished`; else run §6.1's merge-then-validate
check and update. No advisory lock is needed — a patch never changes
`set_number` or inserts a row, so there is nothing to serialize against.

`DELETE /v1/sets/{id}`: same resolution and `workout-finished` guard, then a
plain hard delete. No lock, no renumbering (§4).

### 6.5 The finish-integrity check (05.0's Extension seam 1)

Inside `workoutRepository`'s existing finish transaction (05.0 §6.5), after
its own `ended_at < startedAt` etc. checks and before commit:

```
SELECT we.modality_snapshot, se.reps, se.weight, se.distance, se.duration_s
FROM workout_exercise we
JOIN set_entry se ON se.workout_exercise_id = we.id
WHERE we.workout_id = $workoutId AND se.set_type = 'working'
```

For every row returned, run `requiredMeasuresFor(modality_snapshot)` against
the non-null measures present; any row missing one ⇒ the whole finish is
rejected with `IncompleteWorkingSetsError` (`409 incomplete-working-sets`) and
the transaction rolls back — no partial finish, `ended_at` stays `NULL`.
`warmup` / `drop` / `failure` sets are excluded from the query's `WHERE`
entirely (AC14): they are never inspected at finish time, regardless of what
they contain.

This check runs **before** 07's future PR-recompute extension in the same
transaction (§3, "Consumers must note") — a finish that is going to be
rejected for incomplete data should never reach PR computation.

**This check's correctness depends on ordering it *after* the finish
transaction takes its exclusive lock on the `workout` row, not before.**
05.0 §6.5/§6.7 establish that the finish transaction's row-level exclusive
lock on `workout` (the lock implicit in its `UPDATE workout SET ended_at =
…`, or an explicit `SELECT … FOR UPDATE` taken earlier in the same
transaction) is what a concurrent create's `FOR SHARE` re-check (§6.3) waits
on. That mechanism guarantees the *set of rows a create writes* is fully
decided (committed or rolled back) by the time the finish transaction holds
the exclusive lock — but only for statements that run **after** the lock is
acquired. If this spec's integrity `SELECT` above were issued before that
exclusive lock is taken (e.g. run immediately as the first statement of the
finish transaction, ahead of any lock-acquiring read), a concurrent create
could still be mid-flight, holding the `FOR SHARE` lock and about to insert
an incomplete `working` set: this `SELECT` would miss that not-yet-committed
row, the check would pass on stale data, the finish's later `UPDATE` would
then block until the create commits, and would still succeed once the lock
is released — finishing a workout with an incomplete set that was never
actually checked. The fix is procedural, not structural: **the finish
transaction's first data-touching statement must be one that takes the
exclusive lock on the target `workout` row** (`SELECT … FOR UPDATE`, or the
`UPDATE` itself moved to the front and left uncommitted until every check
passes), and every check that reads across tables — 05.0's own
`ended_at`/`startedAt` checks, this spec's integrity check, and 07's future PR
recompute — must run **after** that lock is held, so each sees a fully
settled snapshot with no in-flight concurrent write on this workout's
subtree. This is the same "lock first, as its own statement, ahead of the
read it protects" discipline 05.0 §6.7/§6.8 already applies to the position
transaction (03.2 D23); 05.0 did not need to state it for its own finish
transaction because nothing 05.0 checks there can be invalidated by a
concurrent write mid-transaction (whether an exercise gets added before or
after the exclusive lock does not change 05.0's finish decision) — 05.1 is
the first spec whose finish-time check *can* be invalidated that way, so this
spec is where the requirement must be made explicit. (AC21 covers it.)

### 6.6 Business logging

`set_created` is emitted on the fresh `201` create, carrying the new set's id,
its `workout_exercise_id`, `setType` and `modality_snapshot` — no measure
values, following 05.0 §9's "ids, counts and durations only, never free text"
rule, extended here to also exclude numeric measures on the conservative side
(they are not free text, but excluding them costs nothing and keeps the rule
simple: this line never carries anything a lifter typed). `PATCH` and `DELETE`
emit no line beyond the request log, matching how 05.0 treats non-transition
`PATCH`es on `workout`.

## 7. Security & privacy

- **Authorization boundary is unchanged from 05.0**: every route resolves
  ownership through a join chain rooted at `workout.user_id`, and a
  cross-user probe gets `404`, never `403` (§5, AC4). No new PII: `set_entry`
  holds only numbers and enum values, no free text.
- **No new abuse surface beyond volume.** A set write is cheap (one row, no
  cascading fan-out); 05.2 covers the write-quota gap this spec, like 05.0,
  deliberately leaves open. A malicious client can create unbounded sets on
  one `workout_exercise` today — the same gap 05.0 recorded for
  `workout_exercise` itself, closed for both by 05.2.
- **Numeric bounds are shape validation, not a security control per se**, but
  worth restating: `reps`/`durationS` reject negative values at the schema
  layer, `weight`/`distance` reject negative values, and the database's
  `smallint`/`numeric(7,3)`/`numeric(9,3)` column types are the backstop
  against an out-of-range value ever reaching a generated-column computation
  that could overflow or misbehave.

## 12. Decisions & open questions

- ✅ **D1 — server-issued `SetEntryId`, not `PUT`-by-`setNumber`.** DESIGN's
  original representative sketch (§6) addressed a set by
  `(workout_exercise_id, set_number)` via `PUT`. This spec instead gives every
  set a branded id and uses `POST` create + `PATCH`/`DELETE` by id, matching
  05.0's convention for `workout_exercise` itself. **Rationale:** consistency
  with the rest of the API (one identity scheme, not two), and it decouples a
  set's identity from its display ordinal — useful the moment `set_number`
  needs to mean "the order it was logged in" rather than "a key the client
  picked." **Consequence:** DESIGN §6's representative-endpoints sketch (and
  its "Idempotency" bullet's `PUT`-by-`(workout_exercise_id, set_number)`
  clause) is stale here; it was illustrative, not binding (05.0 already
  diverged from it for workouts/exercises) — §11 lists the DESIGN.md edit that
  reconciles it, the same treatment 05.0 gave its own divergences.
- ✅ **D2 — `set_number` is a gap-tolerant, append-only ordinal, not a dense
  `0…n-1` sequence.** Unlike `workout_exercise.position`, deleting a set never
  renumbers its siblings. **Rationale:** sets are logged live, sequentially,
  during a workout; reordering or backfilling a gap is not a real workflow the
  way exercise reordering is, and the dense-sequence machinery (advisory lock
  + deferrable constraint + shift-on-delete) is real complexity 05.0 needed
  and this spec does not. **Consequence:** `set_number` is 1-based (not
  0-based like `position`) since it is meant to read as "set 1, set 2…" to a
  human, and a deleted set's number is never reused.
- ✅ **D3 — full per-modality validation at finish, not DESIGN's literal "at
  least one measure."** DESIGN §4.4's current wording is looser than what
  this spec ships; §11 records the DESIGN edit. **Rationale:** "at least one
  measure" would accept a `weight_reps` working set with `reps` alone and no
  weight, which is not a usable strength-training record — the whole point of
  per-modality validation (which this spec already owns) is undermined if the
  finish-time backstop uses a different, weaker rule than every individual
  write already enforces.
- ✅ **D4 — the finish-integrity failure is a hard `409`, not a soft
  finish-anyway.** **Rationale:** matches DESIGN's "enforced at finish"
  wording literally, keeps `personal_record` (07) from ever needing to reason
  about a "finished but incomplete" workout, and gives the client one clear
  recovery path (fix or delete the set, retry the same `PATCH`) rather than a
  silent partial state.
- ✅ **D5 — non-`working` sets are fully exempt from the finish check, at any
  completeness.** **Rationale:** DESIGN §4.4 scopes the rule to `working`
  sets explicitly ("warmup/drop/failure excluded" — echoing §4.5's PR-record
  scoping), and a `failure` set with zero reps logged ("I couldn't do the
  set at all") is a legitimate, meaningful record, not incomplete data.
- ✅ **D6 — no deferrable constraint, no reorder machinery for sets.** A
  direct consequence of D2; recorded separately because it is the reason
  §6.3's advisory lock is simpler than 05.0's, and a future spec reading this
  one should not expect to find a `SET CONSTRAINTS … DEFERRED` here.
- ✅ **D7 — unit-accompanies-value is a handler-level, merge-aware check, not
  a schema-level `superRefine`.** The initial draft put this rule in
  `CreateSetSchema`/`UpdateSetSchema` directly; fixed in this review pass
  (§5, §6.1, new AC20). **Rationale:** `UpdateSetSchema` is `CreateSetSchema`
  reused verbatim (§5) and is validated against the raw `PATCH` body before
  the handler runs, so a schema-level check cannot see the set's stored
  `weightUnit` — it would reject a legitimate `PATCH { weight: 52.5 }` that
  leaves an already-stored unit untouched, exactly the shape of update AC8
  already expects to work for the modality-required fields. Matching the
  modality checks' existing merge-then-validate point (§6.1 point 3) fixes it
  for both rules with one mechanism instead of two.
- **Open — where the finish transaction's row lock is acquired, precisely.**
  §6.5 states the *requirement* (the exclusive lock on `workout` must be held
  before this spec's integrity check, 05.0's own `ended_at`/`startedAt`
  checks, and 07's future PR recompute all run), but the *mechanism* — an
  explicit `SELECT … FOR UPDATE` as the transaction's first statement, versus
  reordering the existing `UPDATE workout SET ended_at = …` to the front and
  deferring `ended_at`'s actual assignment until every check passes — is an
  implementation choice 05.0 did not have to make (nothing it checks there
  needs a fresh mid-transaction read) and this review does not resolve. Left
  for whichever spec's implementation PR lands first between 05.0 and 05.1;
  whoever writes `workoutRepository`'s finish method needs to pick one and the
  other spec should not re-derive it independently.
- ✅ **D8 — 05.0 §6.5 amended to state the lock-first discipline generally,
  closing the open question above.** The finish transaction is 05.0's own
  transaction (its "single entry point"); 05.1 only extends it, so the
  requirement now lives where the transaction is defined — the same shape of
  fix `workoutRepository`'s reorder path already uses by stating its ordering
  directly in §6.7/§6.8 rather than leaving it to whichever spec extends the
  position transaction next. 05.0 §6.5 now states "every check inside the
  transaction that reads across tables must run after \[the exclusive] lock is
  held" as a standing rule, not specific to 05.1, so Spec 07's future PR
  recompute inherits it without re-deriving it. 05.0's own §6.5 text also now
  corrects the "at least one measure populated" wording in its Extension seam
  1 paragraph to match this spec's actual D3 rule, closing a second, smaller
  drift between the two files that this review had only fixed on the 05.1
  side.
- **Open — the `hashtext(workoutExerciseId)` / 05.0's `hashtext(workoutId)`
  advisory-lock-key collision.** §6.3 notes the two lock domains can share a
  hash bucket by coincidence, costing a spurious wait, never a correctness
  bug. Left open, same as an accepted, bounded risk — not worth a namespacing
  scheme (e.g. hashing a tagged string) unless it is ever observed to matter
  in practice.
- **Open — `set_entry`'s eventual read path for Spec 07.** This spec does not
  add an index shaped for "all sets for exercise X across all of a user's
  workouts" (07's PR-recompute and progress-chart access pattern) beyond the
  unique index on `(workout_exercise_id, set_number)`, which does not help a
  query keyed by `exercise_id`/`user_id`. Left to 07, which owns that access
  pattern and can add the index it needs additively, with 05.0 §4's
  `workout_exercise_exercise_idx` as the join path already in place.
