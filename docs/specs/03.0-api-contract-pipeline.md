## 1. Purpose, scope & non-goals

Stand up the **contract pipeline** every later API spec relies on, and prove it
against the one resource that already exists (`/v1/me`). No new domain resource,
no migration.

The pipeline: DTOs are authored **once** as Zod schemas in `@sin/core`;
`fastify-type-provider-zod` wires those schemas into Fastify route validation and
handler typing; `@fastify/swagger` emits an **OpenAPI 3.1** document from the same
schemas; a CI job re-emits the document and fails on an un-regenerated diff.

> **First-principles note (JS-ecosystem, for a backend dev newer to it):**
> A wire contract has two faces — a *runtime validator* (reject a malformed
> payload) and a *static type* (the handler knows the shape). Kept separate they
> drift. A Zod schema (`z.object({...})`) is both at once: it validates, and
> `z.infer<typeof schema>` reads the TypeScript type off it. We write each DTO
> once as Zod in `@sin/core`; the route imports it, so its validation and its
> handler types share one definition. `fastify-type-provider-zod` also lets
> `@fastify/swagger` render those schemas into an **OpenAPI document** — the
> language-neutral description of every route, which we publish as the API's
> external contract. CI re-emits it and fails on an undocumented change, so the
> published contract can never silently diverge from the code.

### In scope

- **Dependencies wired** — `@fastify/swagger` + `fastify-type-provider-zod`,
  registered in `buildApp` so both the root scope and the `/v1` child scope
  inherit the validator/serializer compilers.
- **Error-mapper extension** — `normalizeError` (Spec 01) folds the
  type-provider's `RequestValidationError` into the existing RFC 9457
  `422 validation-error` + `errors[]` contract, and `ResponseValidationError`
  into `500 internal` (logged, never leaked). Without this, Zod validation
  failures fall through to `500`. Message hygiene is pinned in §6.2 / §7.
- **Response schema = field allowlist** — the default
  `fastify-type-provider-zod` serializer parses the handler's return through the
  `response` schema; with plain `z.object` schemas (no `.passthrough()`) unknown
  keys are dropped, so a handler that returns an extra field (an internal column,
  `auth_sub`, a soft-delete timestamp) cannot leak it onto the wire (§6.5, §7).
- **`/v1/me` migrated onto the pipeline** — `GET` response validated by
  `@sin/core` `MeSchema`; `PATCH` body by `UpdateMeSchema`, response by
  `MeSchema`. The hand-written `patchBodySchema` object literal and the
  `isValidTimeZone` helper in `apps/api/src/routes/me.ts` are both deleted — the
  `timezone` IANA check moves into `UpdateMeSchema` as a `.refine()` (§12 P6, a
  small additive change to Spec 02's `@sin/core` schema). Behaviour is unchanged
  (see AC3).
- **OpenAPI 3.1 emit** — served at `GET /openapi.json`, **unauthenticated**
  (§7), covering **only the public `/v1` surface** with `camelCase` schemas
  derived from the Zod DTOs. `/v1/_authcheck` (Spec 01 smoke-only) and the health
  routes are excluded (`hide: true`); no `servers:` block naming an internal
  host; the document is rendered **once at boot** and served as a constant, never
  `app.swagger()` per request.
- **Committed artifact + drift check** — `openapi.json` is checked into the repo
  (P3); a CI step re-emits it and `git diff --exit-code`s it; a `pnpm` script
  regenerates it locally.
- **DESIGN edits** — §6 reframed (below); §7 CI row updated; Spec 02 §12's open
  question about whether `MeSchema` should be generated is closed (it is not —
  it is the authoring format).

### Non-goals

- **Any catalog / exercise work** — Spec 03.1.
- **`openapi-typescript` / client codegen** — not happening under P2; consumer
  types come from `z.infer` on the `@sin/core` schemas.
- **`@fastify/swagger-ui`** — emit only, no interactive docs page in v1.
- **Response-schema validation for routes other than `/v1/me`** — each later
  spec adds `response` schemas for its own routes; this spec only sets the
  pattern and the error handling for them.
- **New auth, rate-limit, or CORS rules** — inherits Spec 01 unchanged apart
  from the one carve-out for `GET /openapi.json` (§5, §7): unauthenticated,
  optionally CORS-`*` for that path only.

## 2. Acceptance criteria

Behavioural criteria (AC2, AC3, AC4, AC7) get ≥1 test naming their number. AC1,
AC5, AC6 are pipeline/doc criteria verified by CI and review (§10).

1. **Type-provider wired.** A route can declare `schema: { body, querystring,
   response }` with Zod schemas and receive a fully-typed handler; the
   `fastify-type-provider-zod` validator + serializer compilers are set in
   `buildApp` and both the root and `/v1` scopes use them. Verified by review +
   the `/v1/me` migration compiling without casts.
2. **Zod validation errors keep the RFC 9457 contract, without leaking.** A
   `RequestValidationError` from the type provider is mapped by `normalizeError`
   to `422 application/problem+json` with `type` = `.../validation-error`,
   `errors: [{ path, message }]` populated from the Zod issues — identical shape
   to Spec 01's AJV path. `errors[].message` is the Zod **issue** message (a
   constraint description), never an echo of the submitted value; `path` names
   the field, not the schema internals. A `ResponseValidationError` maps to
   `500 internal` with a generic `detail` — the failing path/schema appears
   **only** in the server log (`error` level), never on the wire. Both root and
   `/v1` scope route through the same `normalizeError`, so CLAUDE.md's "error
   contract on both scopes" holds with this one change. Tested via
   `fastify.inject` on a probe route and on `/v1/me`, asserting a submitted
   secret-shaped string does not appear in the `422` body.
3. **`/v1/me` migrated, behaviour preserved.** `patchBodySchema` and
   `isValidTimeZone` are deleted; `GET`/`PATCH /v1/me` validate against
   `@sin/core` `MeSchema` / `UpdateMeSchema` (the latter now carrying the
   `timezone` `.refine()` — P6). The entire Spec 01 `/v1/me` test suite passes
   unchanged: unknown body key → `422` (Zod `.strict()`), bad `unitPreference` →
   `422`, empty `timezone` → `422` (`min(1)`), invalid IANA zone → `422`
   (`.refine`), happy `GET`/`PATCH` bodies byte-identical. `plugins/auth` +
   `repositories/user` line coverage stays ≥ 90% (CLAUDE.md gate).
4. **OpenAPI 3.1 document served, scoped to the public surface.** `GET
   /openapi.json` → `200 application/json`, **no auth required**, containing
   `/v1/me` (GET + PATCH) with `camelCase` component schemas matching the Zod
   DTOs, and **not** `/v1/_authcheck`, `/healthz`, `/readyz`, or a `servers:`
   entry naming an internal host (tests assert their absence). The response body
   is a boot-time constant — a spy asserts `app.swagger` is called ≤ 1× across N
   injected requests. Preferred: the document validates against the OpenAPI 3.1
   meta-schema (S3 dev dep). Fallback if clean 3.1 output isn't reachable this
   session (§12 P-note): assert it parses as JSON, `openapi` starts `"3.1"`,
   `paths["/v1/me"]` is present with `camelCase` schemas, and the exclusions
   above hold — strict meta-schema validation becomes a follow-up.
5. **Drift check.** `openapi.json` is committed at the repo root. A CI step runs
   the emit script and `git diff --exit-code openapi.json`; changing a route
   schema without regenerating fails CI. A documented command
   (`pnpm --filter @sin/api run openapi:emit`) regenerates it.
6. **Docs reframed.** DESIGN §6 no longer says client types are *generated from*
   the OpenAPI document or that Spec 02 hand-authors a pattern "the generator
   must match"; it states Zod DTOs in `@sin/core` are the authoring format and
   OpenAPI 3.1 is emitted from them, published at `/openapi.json` (public `/v1`
   surface only), and drift-checked in CI. DESIGN §7's CI row matches.
   `specs/README.md` has a 03.0 row. Spec 02 §12's `MeSchema`-generation
   question is marked closed.
7. **Response schema is a field allowlist.** With the serializer compiler
   configured to strip unknown keys, a probe route whose handler returns an
   object containing an extra field not in its `response` schema (e.g.
   `authSub`, `deletedAt`) produces a wire response with that field **absent**.
   A regression test covers `GET /v1/me` returning exactly the `MeSchema`
   fields and nothing else.

## 5. API surface

### `GET /openapi.json` — the contract document

No auth (§7). `200 application/json` — the OpenAPI 3.1 document for the **public
`/v1` surface**: the app-facing `/v1/*` routes (all of which still require auth to
*call*), minus `/v1/_authcheck` and the health routes. "Public" describes the
*document*, not the routes it lists. Emitted from the registered Zod route
schemas. An explicit carve-out from Spec 01 §5.5 / §7 ("the API serves only JSON
to authenticated clients"): the document is non-sensitive schema and external
discoverability is a stated goal (DESIGN §3.4 — "the API is the contract").
Hardening:

- **Route exclusions.** `/v1/_authcheck` (Spec 01 — smoke-only, not for app use)
  and `/healthz` / `/readyz` are marked `hide: true` and never appear in the
  document.
- **No infra disclosure.** `@fastify/swagger` is configured with **no**
  `servers:` block (or only the public base URL) — never an internal Render
  hostname — and no request/response `examples` drawn from real data.
- **Constant body.** The document is rendered **once** after `app.ready()` at
  boot and cached as a string; the route returns that string. `app.swagger()` is
  never called per request, so this unauthenticated route is not a CPU vector.
- **CORS.** Not touched in 03.0 — `/openapi.json` stays same-origin (Spec 01's
  `WEB_ORIGIN` allowlist is unchanged). If an external browser consumer ever
  needs it, widening is a one-line per-path origin rule
  (`Access-Control-Allow-Origin: *` for `GET /openapi.json` only — safe, no
  credentials, no secrets) and **not** a change to `WEB_ORIGIN`.
- **Caching.** `Cache-Control: public, max-age=300` — it is deploy-static.

The two probe routes used to test AC2 / AC7 (a route with a Zod `body` that
echoes nothing, a route whose handler returns an over-wide object) are **test
fixtures**, registered only under test, never shipped.

### `GET` / `PATCH /v1/me` — unchanged contract, now schema-driven

Request/response shapes exactly as Spec 01 §5. The only observable change is the
*origin* of a rejection: `PATCH` unknown-key and bad-enum errors now come from
Zod (`UpdateMeSchema` is `.strict()`), still surfaced as `422 validation-error`
+ `errors[]` (AC2, AC3).

## 6. Behavior & logic

### 6.1 Type-provider registration

In `buildApp`, before routes: `app.setValidatorCompiler(validatorCompiler)` and
`app.setSerializerCompiler(serializerCompiler)` from `fastify-type-provider-zod`
(the default serializer — it parses each response through its schema; §6.5), and
register `@fastify/swagger` with `transform: jsonSchemaTransform` (also from
`fastify-type-provider-zod`). Done on the root instance so the `/v1` child scope
inherits all of it. Routes opt in by typing the instance with
`.withTypeProvider<ZodTypeProvider>()` (or a shared typed alias).

### 6.2 Error mapping

`normalizeError` (Spec 01) gains two branches, ordered before the generic
fallthrough. **Pin the detection API to the installed `fastify-type-provider-zod`
version** (§3): current versions expose the request guard
`hasZodFastifySchemaValidationErrors(err)` and the response class
`ResponseValidationError` — there is **no** `RequestValidationError` class.

- **Request** — `hasZodFastifySchemaValidationErrors(err)` → construct the
  existing Spec 01 `ValidationError` with `errors` mapped from the Zod issues:
  - `path` = the issue's field path joined with `.` — **bare field name, no
    `body` / `querystring` section prefix** (matches Spec 01's `/v1/me` `422`
    bodies and 03.1 AC6, which assert `path: "updated_since"`).
  - `message` = built from `issue.code` + the constraint only (e.g.
    `"must be one of: kg, lb"`, `"required"`, `"must be ≤ 80 characters"`) via a
    small `issue → message` mapper. **Zod's default messages for
    `invalid_enum_value` / `invalid_type` embed the received value** — the mapper
    discards `issue.received` / `issue.input` / any value so nothing the caller
    submitted is reflected back. Applied to request *and* response issue mapping.
  - Status `422`, `type` `.../validation-error`.
- **Response** — `err instanceof ResponseValidationError` → the existing Spec 01
  `500` / `internal` mapping (however Spec 01 names it), generic `detail` — the
  failing field path and schema go **only** to
  `request.log.error({ issues }, "response schema violation")`, never into the
  response. A handler returning a shape that violates its own declared `response`
  schema is a bug, not a client error.

So `errors[].message` is a fixed constraint phrase and `path` is a bare field
name; a test submits a token-shaped string to a failing enum/length field and
asserts the string is absent from the `422` body.

Because every route — root and `/v1` — funnels through this one `normalizeError`,
the CLAUDE.md rule "error contract registered on BOTH the root scope and the
`/v1` child scope" is satisfied by this single edit; a test asserts a Zod
`422` on a root-scope probe route and on a `/v1` route.

### 6.3 OpenAPI emit + serving

**Emit** — `apps/api/scripts/emit-openapi.ts`: `buildApp()`, `await
app.ready()`, `const doc = app.swagger()`, write `JSON.stringify(doc, null, 2) +
"\n"` to `<repo root>/openapi.json`. Key order is deterministic (swagger output
is stable given stable route registration order; the script does not re-sort).
`pnpm --filter @sin/api run openapi:emit` runs it; CI runs the same and
`git diff --exit-code`s the file.

**Serve** — `app.swagger()` is only valid after `ready()`, so an `onReady` hook
computes it **once** and `JSON.stringify`s it into a module-scoped constant. The
`GET /openapi.json` route (registered outside the `/v1` scope, so no auth plugin)
returns that constant with `Content-Type: application/json` +
`Cache-Control: public, max-age=300`. The swagger registration sets `hide: true`
on `/v1/_authcheck` and the health routes and omits `servers:` / real-data
`examples` (§5, §7). AC4 spies on `app.swagger` and asserts it is called at most
once across N injected requests.

### 6.4 `/v1/me` migration specifics

`GET /v1/me`: `schema.response[200] = MeSchema`. The handler already returns that
shape; `isNewUser` is optional in `MeSchema` so the create-path response still
validates.

`PATCH /v1/me`: `schema.body = UpdateMeSchema`, `schema.response[200] = MeSchema`.
The `timezone` IANA check (Spec 01 does it handler-side with
`Intl.DateTimeFormat`) **moves into `@sin/core` `UpdateMeSchema` as a
`.refine()`** (§12 P6) — the schema is the contract, so the constraint belongs
in it, and `Intl` is ECMA-402 so it passes the `@sin/core` purity check.
`apps/api/src/routes/me.ts` drops its `isValidTimeZone` helper; the empty-string
(`min(1)`) and invalid-zone (`.refine`) cases both surface as `422` through the
Zod error path (AC3). Small additive change to Spec 02's shipped
`UpdateMeSchema`, carried here (§11).

### 6.5 Response schema = field allowlist

`fastify-type-provider-zod`'s serializer compiler already `.parse()`s the
handler's return value through the `response` schema and reserialises the result
— so with a plain `z.object` (never `.passthrough()`) unknown keys are dropped
**by default**. This spec's rule is therefore: adopt the default serializer, and
every `response` schema is a plain `z.object`. That makes each `response` schema a
positive field allowlist — a handler bug (or a future ORM change that widens a
row object) cannot leak `auth_sub`, `email_verified`, `deleted_at`, or any other
unlisted column onto the wire. `MeSchema` as the `GET /v1/me` response schema is
the first instance; AC7 is the regression guard.

## 7. Security & privacy

- **`GET /openapi.json` is unauthenticated** — a deliberate carve-out from Spec
  01 §7 (the document is route + schema metadata, no user data; publishing the
  contract is a stated goal, DESIGN §3.4). Guard rails, all in §5 / §6.3 and
  enforced by AC4:
  - **only the public `/v1` surface** — `/v1/_authcheck` and the health routes
    are `hide: true`, so the doc is not a map of internal/probe endpoints;
  - **no `servers:` block** with an internal host; no real-data `examples`; no
    security-scheme client secrets;
  - **served as a boot-time constant** — no per-request `app.swagger()`, so the
    anonymous route cannot be used as a CPU amplifier;
  - CORS widened for this path only if external browser consumers need it, never
    by touching the Spec 01 `WEB_ORIGIN` allowlist.
- **Response schema = field allowlist** (§6.5). The serializer strips unknown
  keys, so a handler or ORM change cannot leak an unlisted column (`auth_sub`,
  `email_verified`, `deleted_at`, …). This is a *positive* security control the
  pipeline gives every later route for free; AC7 guards it.
- **Error responses do not leak.** `errors[].message` is the Zod constraint
  message, never the submitted value; a `ResponseValidationError` → `500` puts
  the failing path/schema in the log only, never in `detail`. The `422` body
  shape is unchanged from Spec 01. (§6.2, AC2.)
- No change to any authenticated route's authz. The `/v1/me` swap is
  behaviour-preserving (AC3).

## 12. Decisions & open questions

### Resolved

- ✅ **P1 — the contract pipeline is its own spec, landing before the catalog.**
  Extracted from Spec 03.1 on the `architect` review (2026-09-03): it has zero
  catalog dependency, it is the "risky new infrastructure worth isolating" that
  Spec 03.1 D1's own rationale invoked (D1 split reads from writes but left the
  pipeline bundled with reads), and proving it against the existing `/v1/me`
  de-risks every later API spec. Keeps both 03.0 and 03.1 to one work session.

- ✅ **P2 — Zod is the authoring format; OpenAPI 3.1 is emitted from it.**
  (Spec 03.1 D7, unchanged.) `fastify-type-provider-zod` + `@fastify/swagger`;
  no `openapi-typescript`; consumer types via `z.infer`. Chosen over authoring
  the OpenAPI document directly because one Zod object is validator + type at
  once, it extends Spec 02's DTO pattern, and it lets the SPA re-validate
  responses with the server's exact rules. A spec-first OpenAPI workflow buys
  nothing for a solo, TypeScript-only API.

- ✅ **P3 — `openapi.json` is committed to the repo.** Drift check =
  re-emit + `git diff --exit-code`. Contract changes show up in PR review (the
  developer reviews their own PRs via `/code-review` + `change-auditor`), and the
  check is trivial. (Resolves Spec 03.1 D7's open sub-point / review S3.)

- ✅ **P4 — `GET /openapi.json`, unauthenticated, narrowly scoped.** Explicit
  carve-out from Spec 01 §7; non-sensitive schema, external discoverability
  intended (DESIGN §3.4). Hardening from the design-level security review
  (2026-09-03) — the testable parts are enforced by AC4:
  - the document covers **only the public `/v1` surface** — `/v1/_authcheck` and
    the health routes are `hide: true`;
  - **no `servers:` block** naming an internal host; no real-data `examples`; no
    security-scheme client secrets;
  - the body is **rendered once at boot** and served as a constant — no
    per-request `app.swagger()`, so the anonymous route is not a CPU amplifier;
  - CORS **not changed** in 03.0 (`/openapi.json` is same-origin); a future
    per-path `*` widening for it alone is safe and does not touch `WEB_ORIGIN`.

- ✅ **P5 — every `response` schema is a plain-`z.object` field allowlist**
  (design-level security review). `fastify-type-provider-zod`'s default
  serializer already parses the handler's return through the schema and
  reserialises it, so a `z.object` (never `.passthrough()`) drops unknown keys —
  a handler or ORM change cannot leak an unlisted column (`auth_sub`,
  `deleted_at`, …). No special config; AC7 is the regression guard; every later
  spec inherits the control for free.

- ✅ **P6 — the `/v1/me` `timezone` IANA check moves into `@sin/core`
  `UpdateMeSchema` as a `.refine()`.** The schema is the contract, so the
  constraint lives in it (not a handler-side check duplicated per route); `Intl`
  is ECMA-402 and passes the `@sin/core` purity check. `routes/me.ts` drops its
  `isValidTimeZone` helper; empty-string and invalid-zone both surface as `422`
  via the Zod path (§6.4, AC3). Small additive change to Spec 02's shipped
  `UpdateMeSchema`, carried in this PR (§11).
