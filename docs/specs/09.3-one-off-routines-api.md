## 1. Purpose, scope & non-goals

Spec 10.4 lets the owner paste the text of today's gym class and get a routine. Most of those routines are used once. Left alone a daily import fills the routines list with dead entries and reaches the 50-routine cap (Spec 09 D6) in about seven weeks. This spec adds the **server half of the fix**: a routine can be created as a **one-off**; it carries an expiry; it **removes itself, in the same transaction, when a workout started from it is finished**; it can be turned into an ordinary routine with **Keep** (a small write, or a flag on the finish); and an unfinished one-off is removed lazily after **14 days**. The workout is never touched: History reads from the workout's own snapshots (`routine_name_snapshot`, `workout_section`, `workout_exercise`), and `workout.routine_id` is already `ON DELETE SET NULL`.

> **First-principles note — "lazy expiry".** Nothing runs on a clock: there is no scheduler in this system (Spec 11 deferred its cron too). So "removed after 14 days" cannot mean "at day 14"; it means "no later than the next time the owner looks at their routines". Every list read (and every create) first deletes that user's expired one-offs, then answers. The owner can never see an expired one-off; the table can hold one only until its owner next asks.

> **First-principles note — "lock order".** A database lock is taken on a row so two transactions cannot change it at once. If transaction A holds row 1 and waits for row 2 while B holds row 2 and waits for row 1, the database kills one of them (a deadlock, SQLSTATE `40P01`) and the user sees a 500. The only cure is that every code path takes its locks in the same order. §6.2 states that order for this spec; the finish path is the one that needed care.

### In scope

- Migration `0013_routine_one_off`: `routine.one_off_until timestamptz NULL` and one CHECK.
- `@sin/core`: `ROUTINE_ONE_OFF_DAYS = 14`; `RoutineCreateSchema` (`POST` only, accepts `oneOff: true`); `Routine.oneOffUntil`; `WorkoutDetail.routineIsOneOff`; `UpdateWorkoutSchema.keepRoutine`.
- Routes: `POST /v1/routines` (`oneOff`), `POST /v1/routines/{id}/keep` (new), `PATCH /v1/workouts/{id}` (`keepRoutine`), the routine list order, the lazy expiry sweep on `GET /v1/routines` and `POST /v1/routines`.
- The finish transaction's one-off handling and its lock order (§6.2).
- Workout detail read: the flag that tells the client the workout came from a one-off.
- Export (through the shared mappers plus one hand-written `SELECT` edit), logging.

### Non-goals

- **UI** (Spec 10.5). **No client reads the new fields until 10.5** (DESIGN §6 rollout convention).
- Raising `ROUTINES_PER_USER_MAX` (stays 50; one-offs count toward it).
- Making a hand-built routine a one-off from the product, or turning a kept routine back into one. The API has no "make one-off" route and `PUT` cannot set the mark. (`POST` accepts `oneOff: true` from any client; "only text imports are one-offs" is a UI rule, §12 D13.)
- Changing History, the workout, its sections or the finish response in any way. Backfilling anything: routines imported before this ships stay ordinary.
- A scheduler, a cron, an undo for the removal, a configurable TTL, extending the expiry on edit or on start.
- Any change to the duplicate-name rule (`routine_user_name_key`): a one-off that removed itself frees its name.

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("09.3 AC7 — …")`). Infra / pipeline criteria are verified by CI or review (§10).

**Shapes and reads**

1. **Contract.** `Routine` (response) gains `oneOffUntil: string | null` (ISO datetime with offset), the **last** key; `WorkoutDetail` gains `routineIsOneOff: boolean`, on the **detail only** (`WorkoutSchema`, hence `POST /v1/workouts`, the finish response, `WorkoutSummary` and every History row, is unchanged: a test pins the key set of a list row and of the finish response). Both are **required** in `@sin/core` (no `.default`, no `.optional()`, no `.catch`; Spec 10.1 D4). `UpdateWorkoutSchema` gains `keepRoutine`; a new `RoutineCreateSchema` is the `POST` body. `/openapi.json` is regenerated (CI drift step green) and publishes the Keep route with its `404` problem; the routes' `401` behavior is unchanged.
2. **Every routine read carries the expiry.** List, get-one and the `POST` / `PUT` responses return `oneOffUntil` (the stored instant, or `null` for an ordinary routine), from the same single statement as the header and items (Spec 09 AC14 / 09.2 AC2 extend). The strong `ETag` hashes the new bytes: Keep changes the validator; an unchanged routine keeps it; the first conditional `GET` after the deploy answers `200` (the bytes gained a key), not `304`.
3. **List order.** `GET /v1/routines` returns one-offs first, newest created first, then ordinary routines by `lower(name)`, `id` (today's order). Ties among one-offs fall back to `lower(name)`, `id`. Get-one is unaffected. The order is stated in §5 so Spec 10.5's client mirror cannot drift (its parity test is 10.5 AC1).
4. **The workout flag.** `GET /v1/workouts/{id}` and `GET /v1/workouts/active` return `routineIsOneOff: true` iff the workout's `routine_id` references an existing routine whose `one_off_until IS NOT NULL` **now**. It is `false` for a manual workout, a workout from an ordinary routine, a workout whose routine was deleted (`routine_id` is `NULL`), and a workout whose routine was kept. A workout whose one-off is past its expiry but still held by this live workout reads `true`. The add-exercise and patch-exercise responses carry no such field.

**Create and write rules**

5. **Create as a one-off.** `POST /v1/routines` with `oneOff: true` stores `one_off_until = now() + 14 × 24 hours` (database clock, `make_interval(hours => 336)`, not calendar days) and returns it in `oneOffUntil`; without `oneOff` the column is `NULL`. `oneOff: false`, `null`, a string or any other value is `422` on `oneOff`. A client can never send the expiry: `oneOffUntil` in a body is `422` (strict schemas). `PUT /v1/routines/{id}` with a `oneOff` key is `422` on `oneOff` (the shared `RoutineWriteSchema` stays strict and does not gain it).
6. **A `PUT` never changes the mark.** Replacing a one-off keeps `one_off_until` byte-identical (the expiry is **not** extended by an edit, D3); replacing an ordinary routine keeps `NULL`. The `PUT` body carries no key for it, and the response shows the unchanged value.
7. **Cap and names.** One-offs count toward `ROUTINES_PER_USER_MAX` (the 51st create is `409 routine-limit` whatever the mix). An **expired one-off never blocks a create**: `POST` first sweeps (AC21), and its cap count then excludes any one-off past its expiry (the only survivors are held by a live workout, ≤ 1, so at most 51 rows exist). A swept one-off frees its name: creating a routine with an expired one-off's name succeeds (`201`, not `409 routine-name-taken`).

**Keep**

8. **Keep.** `POST /v1/routines/{id}/keep` (no body) on the caller's one-off sets `one_off_until = NULL` and `updated_at = now()` and answers `204`. A following read shows `oneOffUntil: null`; the routine is thereafter never swept and never removed by a finish (AC13). Name, notes, items, sections, planned sets and id are untouched.
9. **Keep is idempotent and total.** A repeat answers `204` and changes nothing (no `updated_at` bump, same `ETag`). Keeping an ordinary routine answers `204`, a no-op. Keeping a one-off that is past its expiry but not yet swept succeeds and rescues it. A missing, foreign (another user's) or malformed id is `404 not-found`, never `403`. Keeping a routine that a finish just removed is `404`.
10. **Route wiring.** The Keep route declares `config: { published: true, problems: [NotFoundError], writeGroup: "routines" }`; app assembly fails without `writeGroup` (Spec 05.2), it shares the `routines` budget (30/min) and `RATE_LIMITS` is unchanged. `CORS_METHODS` is unchanged (`POST` is already listed) and the assembly guard passes; a real preflight test for `POST /v1/routines/{id}/keep` is added (an `inject` test never exercises the preflight, CLAUDE.md). A request with **no body and no `Content-Type`** succeeds (the web sends exactly that).

**Finish**

11. **`keepRoutine` on the finish.** `PATCH /v1/workouts/{id}` accepts `keepRoutine` (boolean). It requires a finish: with `endedAt` absent or `null` it is `422` on `keepRoutine` (static message `requires endedAt`), including `false`. `false` equals absent. No other `PATCH` rule changes (Change Time, `durationSeconds`, strict keys).
12. **Finish removes the one-off.** Finishing (`endedAt` non-null) a live workout whose routine is a one-off, with `keepRoutine` absent or `false`, deletes that routine in the same transaction as the finish: the `routine` row, its items, sections and planned-set rows are gone (cascade), the finish response is byte-for-byte what it is today, and the finished workout still reads `routineName`, `sections`, `routineNotes`, every exercise with its targets and planned sets exactly as before the finish; its `routine_id` is `NULL`.
13. **Finish with Keep.** The same finish with `keepRoutine: true` clears the mark instead (`one_off_until = NULL`, `updated_at = now()`); the routine, items, sections and sets are untouched and the routine is ordinary from then on.
14. **Everything else is unaffected.** A finish of a manual workout, of a workout from an ordinary routine, or of a workout whose routine is already gone (deleted by hand, or kept on another device) succeeds as today; `keepRoutine` is ignored; no routine is deleted or altered. The routine delete statement and the keep statement both carry `one_off_until IS NOT NULL` in their `WHERE`, so a bug upstream still cannot remove an ordinary routine (a test hands the finish path an ordinary routine id and asserts nothing is deleted). Taking the routine lock is also skipped for an ordinary routine: a test holds `FOR UPDATE` on an ordinary routine in another transaction and the finish does not wait.
15. **Atomic with the finish.** `409 incomplete-working-sets`, any `422` from the time rules, a failing record recompute or an injected failure after the routine delete roll back **both**: the workout stays live, the routine stays one-off, with its rows intact. Removal happens only after the finish `UPDATE` and the record recompute have succeeded.
16. **Re-finish does nothing to routines.** `PATCH` with a non-null `endedAt` on an already-finished workout is, as today, `409 workout-finished` (the code has no idempotent success for it, §12); the routine is untouched whatever `keepRoutine` says, and **no routine lock is taken** on that path (the lock statement filters `ended_at IS NULL`). A `keepRoutine: true` re-finish does not rescue a routine the first finish removed or alter one it kept.
17. **Only a finish touches the routine.** Start (`POST /v1/workouts`), live title/notes `PATCH`, Change Time, `DELETE /v1/workouts/{id}` (discard) of a live workout, set and exercise writes, and finished-workout edits (Spec 07.4) never delete, keep or lock a one-off. After a discard the routine is still a one-off with its original expiry and can be started again.
18. **History and records are indifferent.** After a finish that removed its one-off: `GET /v1/workouts/{id}`, the History list row (`routineName`), the summary's `newRecords` and `GET /v1/personal-records` are identical to the same finish of the same workout started from an ordinary routine (`records:rebuild` produces the same rows). The 07.0 suites pass unmodified.

**Expiry**

19. **What the sweep removes.** The sweep deletes the acting user's routines with `one_off_until IS NOT NULL AND one_off_until <= now()` **and no live workout** (`workout.routine_id = routine.id AND ended_at IS NULL`). It never touches an unexpired one-off, an ordinary routine of any age, or another user's routine. Items, sections and planned sets go with the routine (no orphans: `assertSectionsConsistent` and the derived-column checks stay green).
20. **A held one-off survives.** An expired one-off with a live workout started from it is not removed, by the sweep or by anything else, until that workout is finished (which removes or keeps it, AC12 / AC13) or discarded (the next sweep then removes it).
21. **Where the sweep runs.** On `GET /v1/routines` before the list is read, and on `POST /v1/routines` before the cap count, inside the create's transaction after the cap's advisory lock. It does **not** run on get-one, `PUT`, `DELETE`, Keep, start, finish or the account export (get-one of an expired, unswept id may still answer `200`; the web reads the list first). When no one-off is expired the sweep issues **one** read statement and writes nothing (no transaction opened).
22. **The ETag moves when the sweep removes rows.** A list read that sweeps returns the post-sweep document; a conditional `GET` whose `If-None-Match` was the pre-sweep `ETag` answers `200` with the new one, never `304`. A sweep that removes nothing leaves the `ETag` and the `304` path as they were.
23. **The sweep is safe against concurrent routine work.** It selects its candidates `FOR UPDATE SKIP LOCKED` and re-checks "no live workout" in a **second statement** after the locks are held. Repeated racing runs of the sweep against (a) a start from the same expired one-off, (b) a finish of its workout, (c) a `PUT`, (d) a Keep, (e) another sweep never raise `40P01`, and always end in one of the legal outcomes of §6.3: never a live workout whose `routine_id` was nulled by the sweep, never a half-deleted routine.

**Concurrency and lock order**

24. **One lock order, enforced by a test.** The finish path takes, in this order: the per-user PR advisory lock (`lockUserRecords`), the one-off routine row `FOR UPDATE`, the workout row `FOR UPDATE`, then the existing statements. A statement-log capture asserts the order on a finish of a one-off workout and asserts the routine lock statement is absent for an ordinary routine, a manual workout and a re-finish.
25. **Pairwise races.** Repeated `Promise.all` runs of the finish of a one-off's workout against each of: a routine `PUT`, a routine `DELETE`, Keep, another finish of the same workout, a discard of the same workout, a sweep, and a start from the same routine (which must lose to the one-active rule) raise no `40P01` and end in a legal state: the workout finished exactly once or deleted; the routine removed, kept or gone, per §6.3; no half-removed routine; no live workout with a routine row that was removed beneath it.

**Migration, cross-cutting**

26. **Migration `0013`.** Additive only; applies cleanly over `0001–0012` with existing data untouched; adds `one_off_until` and `routine_one_off_until_check` (`one_off_until IS NULL OR one_off_until > created_at`); the database rejects (raw SQL) a one-off whose expiry is not after `created_at`. No backfill: every pre-`0013` routine reads `oneOffUntil: null` and no existing value changes (including routines imported by Spec 10.4 before 10.5 ships).
27. **No-drift check moves.** `prisma migrate diff` (migrated database → `schema.prisma`) reports no difference beyond the two generated `set_entry` columns, asserted in `0013`'s integration test (`routine-one-off-migration`); `workout-planned-duration-migration.integration.test.ts` keeps its `0012` checks but no longer carries the whole-schema diff (CLAUDE.md). *amended 2026-10-23, Spec 09.4: the check moved on to `workout-sections-migration` with `0014`.*
28. **Export and purge.** The account export (Spec 11) carries `oneOffUntil` on routines through `routes/mappers.ts` and `routineIsOneOff` on workouts through one added expression in its hand-written workout `SELECT`; Spec 11's parity AC (export deep-equals the read routes) passes with a one-off and a workout from it in the fixture, and the export still issues **≤ 8** statements. No table or foreign key is added, so the purge discovery test needs no change.
29. **Logging hygiene.** `routine_created` gains `one_off` (boolean); new `routine_kept { routine_id, user_id, changed }` and `routine_one_offs_expired { user_id, routine_count }` (only when ≥ 1 removed); `workout_finished` gains `one_off_removed` and `one_off_kept` (booleans). Ids, counts and booleans only: no routine name, note or section text in any captured line (Spec 09 AC30 / 09.2 AC28 extend).
30. **Bounded read.** The maximum fixture of 09.2 AC30 (50 routines, full items, 8 sections each, a mix of one-offs and ordinary) is still returned by `GET /v1/routines` in **one** list statement plus the sweep's single read, under the same loose time bound.
31. **Docs and release order.** DESIGN.md, `docs/specs/README.md`, CLAUDE.md and the runbook carry the edits of §11; the release order of §11 (migration `0013` before the code; API before Spec 10.5) is stated in the PR description and a runbook "0013" note.

## 4. Data model

Migration `apps/api/prisma/migrations/0013_routine_one_off/migration.sql`, hand-authored like `0009`–`0012`; `schema.prisma` gains `Routine.oneOffUntil DateTime? @map("one_off_until") @db.Timestamptz(6)` (Prisma does not model the CHECK; the no-drift check, AC27, is the guard). Additive / expand-only: no column dropped, renamed or retyped; no backfill; no new table.

```sql
-- Spec 09.3 §4 — 0013_routine_one_off. Additive, expand-only.
-- Down (dev/test teardown only; production undo is `git revert` + a forward migration):
--   ALTER TABLE "routine" DROP CONSTRAINT "routine_one_off_until_check", DROP COLUMN "one_off_until";

ALTER TABLE "routine"
    ADD COLUMN "one_off_until" TIMESTAMPTZ(6),
    ADD CONSTRAINT "routine_one_off_until_check"
        CHECK ("one_off_until" IS NULL OR "one_off_until" > "created_at");
```

Notes:

- **One column carries both the mark and the expiry** (NULL = ordinary; the brief's call, accepted). Keep sets it to `NULL`; nothing ever sets it after create, so "newest first" is `created_at DESC` for one-offs and the expiry is always `created_at + 14 days` for rows this code wrote.
- **No new index.** A user has ≤ 50 routines (≤ 51 incl. a held one) and `routine_user_name_key (user_id, lower(name))` already leads with `user_id`, so the sweep's `user_id = $1` scan is at most 51 rows. The "live workout from this routine" probe uses the existing partial index `workout_routine_idx (routine_id) WHERE routine_id IS NOT NULL`.
- **The CHECK** validates against existing rows (all `NULL`) and costs a table scan under a lock on a small table; the lock window is milliseconds. It is the DB-level floor under the handler: an expiry can never precede creation.
- **Cascade facts this spec relies on (no change):** deleting a `routine` cascades `routine_item` (→ `routine_item_set`) and `routine_section`, and sets `workout.routine_id` to `NULL` (`workout_routine_id_fkey ... ON DELETE SET NULL`); `workout.routine_name_snapshot`, `routine_notes_snapshot`, `workout_section`, `workout_exercise`, `workout_planned_set` are the workout's own.

## 6. Behavior & logic

### 6.1 The sweep

`sweepExpiredOneOffs(userId)` in `routine.prisma.ts`, shared by `list` and `create` (it is not a public route and not a repository-contract method callers see; the repository reports how many it removed so the route can log it):

1. **Probe** (no transaction): `SELECT 1 FROM routine WHERE user_id = $u AND one_off_until IS NOT NULL AND one_off_until <= now() LIMIT 1`. None → done (AC21's single read).
2. Otherwise open a short transaction and **lock the candidates**: `SELECT id FROM routine WHERE user_id = $u AND one_off_until IS NOT NULL AND one_off_until <= now() ORDER BY id FOR UPDATE SKIP LOCKED`. A routine someone else is using right now (a `PUT`, a Keep, a finish, a start's `FOR SHARE`) is skipped, not waited for: it survives this sweep and the next one retries.
3. **Then, as a second statement** (so it sees every workout committed before the locks were granted): `DELETE FROM routine r WHERE r.id = ANY($ids) AND r.one_off_until IS NOT NULL AND r.one_off_until <= now() AND NOT EXISTS (SELECT 1 FROM workout w WHERE w.routine_id = r.id AND w.ended_at IS NULL) RETURNING r.id`. The count feeds `routine_one_offs_expired`.

*Why two statements.* A single `DELETE … WHERE NOT EXISTS (live workout)` evaluates the `NOT EXISTS` against the statement's snapshot. If a start commits between the snapshot and the moment the `DELETE` obtains its row lock, Postgres re-checks the row's own columns but not the subquery, and would delete a routine a live workout was just started from (nulling that workout's `routine_id`). Locking first and testing in a later statement closes the gap: any start that held the routine's `FOR SHARE` is either committed (its workout is visible → the routine is kept) or the sweep's `SKIP LOCKED` skipped the row.

In `create`, the sweep runs inside the transaction after `pg_advisory_xact_lock(hashtext('routine:' || user_id))` and before the cap count, so a swept one-off frees both its slot and its name for this very insert. The cap count is `count(*) WHERE user_id = $u AND (one_off_until IS NULL OR one_off_until > now())` (AC7).

### 6.2 The finish transaction and the lock order

Today's live finish (`updateWorkout`, `mode === "live"`, `patch.endedAt != null`): `lockUserRecords` → `SELECT … FROM workout … FOR UPDATE` → retime checks → `assertWorkingSetsComplete` → `UPDATE workout` → count → `clampSetTimes` → `recomputeRecordsForRoots`. This spec inserts one statement before the workout lock and one after the recompute:

```
1. lockUserRecords(tx, userId)                                  -- existing: per-user PR advisory lock
2. NEW  SELECT r.id FROM routine r
        WHERE r.id = (SELECT w.routine_id FROM workout w
                      WHERE w.id = $workout AND w.user_id = $u AND w.ended_at IS NULL)
          AND r.user_id = $u AND r.one_off_until IS NOT NULL
        FOR UPDATE                                              -- the one-off's row, or no row (and no lock)
3. SELECT … FROM workout WHERE id … FOR UPDATE                  -- existing
   … existing statements … UPDATE workout (finish) … recomputeRecordsForRoots …
4. NEW  if step 2 returned a row:
          keepRoutine === true → UPDATE routine SET one_off_until = NULL, updated_at = now()
                                  WHERE id = $r AND user_id = $u AND one_off_until IS NOT NULL
          else                 → DELETE FROM routine WHERE id = $r AND user_id = $u AND one_off_until IS NOT NULL
```

*Why the routine lock comes before the workout lock (the code contradicts a naive "lock the workout, then the routine").* The existing `DELETE /v1/routines/{id}` runs `DELETE FROM routine`, and the foreign key's `SET NULL` then updates the referencing `workout` rows: it holds **routine → workout**. A finish that locked **workout → routine** would deadlock with it (the routine delete holds X and needs the live workout's row; the finish holds that row and needs X). The brief's rule "skip a one-off with a live workout" cannot prevent this, because that rule governs the *sweep*, not the hand `DELETE` route. So the whole system uses one order: **PR lock → routine row → workout row(s) → child rows**.

Checking each actor against that order:

| Actor | Locks, in order | Cycle with finish? |
|---|---|---|
| Finish (above) | PR → routine `FOR UPDATE` (one-offs only) → workout `FOR UPDATE` → … | — |
| Routine `PUT` | routine `FOR UPDATE` only | No: holds one lock, requests none. |
| Routine `DELETE` | routine row → `SET NULL` on referencing workouts | Same order as finish; whoever gets the routine first wins, the other waits or gets `404`. Never waits for a PR lock. |
| Keep | routine row (`UPDATE`) | One lock only. |
| Start | its own **new** workout row (invisible to others until commit) → routine `FOR SHARE` → its own workout `UPDATE` | The only way into a start's uncommitted row is another start's unique-index wait; the holder waits only on a routine lock whose holder waits on nothing the start holds. Start and finish of the same routine cannot overlap (the one-active rule makes the start fail at its insert, before any routine lock). |
| Sweep | routine rows `SKIP LOCKED` (never waits) → cascade, `SET NULL` on *finished* workouts only (a held one is excluded) | Never waits on a routine, so it cannot be a link in a cycle; finished-workout rows are only locked by PR-lock holders, and the finish holds the PR lock. |
| Discard (`deleteWorkout`) | PR lock → workout row | Queues behind the finish on the PR lock; takes no routine lock. |
| Live non-finish `PATCH`, set writes | workout row only | Hold one lock, request none. |

**Step 2 locks only a one-off.** An ordinary routine matches no row, takes no lock, and a finish of a workout from it is as it is today (AC14). A `Keep` that commits while the finish waits at step 2 makes the row fail the predicate after the wait (READ COMMITTED re-checks the locked row), so the finish proceeds without a routine and removes nothing: the owner's Keep wins. **`ended_at IS NULL` in the subselect** is what makes a re-finish take no routine lock (AC16); the workout's own `FOR UPDATE` then finds it finished and throws `409 workout-finished` as today.

**Step 4** runs only when the finish is certain to commit, so every earlier failure (`409 incomplete`, `422`, a recompute error) leaves the routine alone (AC15). The `DELETE` cascades to the routine's children and sets `workout.routine_id` to `NULL` on this workout (its row lock is ours) and on any finished workout still referencing the routine (whose rows are only ever locked by PR-lock holders — we hold it).

**Result and log.** `UpdateWorkoutResult` gains `oneOff: "removed" | "kept" | "none"`; the route logs `one_off_removed` / `one_off_kept` on `workout_finished` (§9). A `keepRoutine: true` finish of a workout with no one-off is `"none"`.

### 6.3 Legal outcomes of the races (AC23, AC25)

| Race | Outcomes |
|---|---|
| Finish vs routine `PUT` | `PUT` first: the finish then deletes the updated routine. Finish first: `PUT` gets `404`. |
| Finish vs routine `DELETE` | Either order: the routine is gone; the workout is finished; the loser of a delete-vs-finish sees `404` on the delete. |
| Finish (no keep) vs Keep | Keep first: routine stays, ordinary, finish succeeded. Finish first: routine gone, Keep `404`. |
| Finish (keep) vs Keep | Routine kept either way; `one_off_kept` true only if the finish was the one that cleared it. |
| Sweep vs start of the same expired one-off | Start holds `FOR SHARE` first: the sweep skips the row; the workout is live and holds the routine. Sweep first: the start's `FOR SHARE` finds no row → `404`, the start rolls back, no workout row remains. Never a live workout with a nulled `routine_id`. |
| Sweep vs finish | The finish holds the row (skip) or the workout is no longer live and the one-off is already removed/kept by the finish. |
| Two sweeps | The second skips what the first locked; its probe or delete finds nothing. |

### 6.4 Reads

- **Routine:** `ROUTINE_WITH_ITEMS` selects `r.one_off_until`; `RoutineDbRow` / `RoutineRecord` gain `oneOffUntil: Date | null`; `toRoutineDto` emits `oneOffUntil: r.oneOffUntil?.toISOString() ?? null` last. `list` takes the order of §5.
- **Workout detail:** `loadSectionSnapshot` (the detail's one extra statement, 09.2) gains `EXISTS (SELECT 1 FROM routine r WHERE r.id = w.routine_id AND r.one_off_until IS NOT NULL) AS routine_is_one_off`; no other `workout` `SELECT` changes; `WorkoutDetailRecord` and `toWorkoutDetailDto` carry it. The export's workout `SELECT` gains the same expression (§3).
- **Keep:** `UPDATE routine SET one_off_until = NULL, updated_at = now() WHERE id = $1::uuid AND user_id = $2::uuid AND one_off_until IS NOT NULL RETURNING id`; with no row returned, `SELECT 1 FROM routine WHERE id AND user_id` decides `204` (exists: no-op) or `404`. A malformed id is `404` before any query (`isRoutineId`).

### 6.5 Edge cases

- **Edit does not extend the expiry** and does not clear the mark (D3); neither does start.
- **Expired and held, then finished:** the finish step 2 locks it (it is still a one-off), the finish removes or keeps it as asked.
- **Expired and held, then discarded:** the next list read or create sweeps it.
- **The same name twice:** importing the same text again before the first import is used or expires is `409 routine-name-taken`, as today (10.4's client check shows it first).
- **Clock:** `now()` is the database clock in every comparison; client clocks never decide expiry.
- **A one-off with a finished workout still referencing it** (not produced by this code, possible only by data repair): the sweep would delete it and null that reference; harmless.

## 7. Security & privacy

- **Authorization is inherited.** Every new statement is `user_id = $acting`: Keep, the sweep, the finish's routine lock and delete, the flag. A foreign id is `404`, never `403`. User B cannot keep, sweep or learn the expiry of A's routine (the integration fixture has two users).
- **Mass assignment.** The client chooses only "one-off or not" (`oneOff: true`) at create. The expiry, the mark afterwards and `updated_at` are server-written; `oneOffUntil` in any body is an unknown key → `422`; `PUT` rejects `oneOff`.
- **No unintended deletion.** Only rows with a non-null mark are ever removed automatically; the three deleting statements (finish, sweep, and the hand `DELETE` route which is unchanged) are scoped as above, and the two automatic ones repeat the `IS NOT NULL` predicate (AC14). A routine the owner built or kept cannot be removed by this feature, which is the brief's anti-goal.
- **Abuse bounds.** One-offs are routines: the cap (50), the `routines` write group (30/min) and the in-flight cap bound creation; the sweep is bounded by ≤ 51 rows per user and runs a write at most once per expiry batch. A user cannot create a one-off that outlives 14 days unfinished.
- **GET with a side effect.** The list read deletes expired rows. The effect is idempotent, scoped to the caller's own data, takes only `SKIP LOCKED` locks, and the cache policy (`private, no-cache` + `ETag`) is unaffected because the `ETag` is computed after the sweep.
- **PII.** Names and notes are never logged (§9); a removed one-off's text is gone from the database (its copy lives only in the workout snapshots, which belong to the owner and are in the export).

## 12. Decisions & open questions

Owner decisions are labeled **(owner)**; calls that are the designer's or builder's and may be refined are labeled **(mine)**.

### Resolved (owner-approved 2026-10-19, from the brief)

- ✅ **D1 — A one-off removes itself when a workout started from it is finished (owner).** Finish and End workout early both go through the finish `PATCH`, so both remove it; discard and start never do. **Rationale:** the common case is a class done once; the workout is already in History through its snapshots, so the routine is dead weight. **Rejected:** removal on start (the owner may restart after a discard), a "used" counter, soft delete (an undeletable zombie row for nothing).
- ✅ **D2 — Server-side removal inside the finish transaction (owner).** **Rationale:** the same on any device, no client step that can be skipped, atomic with the finish (a failed finish leaves the routine). **Rejected:** a client-issued `DELETE` after the finish (a lost request leaves the one-off; a second device never does it).
- ✅ **D3 — 14 days from creation, unfinished one-offs removed lazily (owner accepted the proposal).** An edit and a start do not extend it. **Rationale:** the expiry is a promise shown as a date ("on Fri 16 Oct"); moving it on edit would make that date untrustworthy. The cost of a wrong expiry is pasting the text again.
- ✅ **D4 — Keep clears the mark forever (owner).** Two entry points (preview button, Finish checkbox) over two server paths (Keep route, `keepRoutine`). **Rationale:** "once kept, behaves like any other routine, forever". The Finish checkbox needs a server path inside the finish transaction (the routine would otherwise be deleted first); the preview needs a write that is not a whole-document `PUT`.
- ✅ **D5 — One column, `one_off_until` (owner accepted the brief's call).** Mark and expiry together; `NULL` = ordinary. **Rejected:** a boolean plus `created_at` arithmetic (two things to keep in step; the expiry date the UI shows would be computed in two places).
- ✅ **Placement, copy, caps (owner).** One-offs first, newest first, then the usual order; one-offs count toward 50; `PUT` never carries the mark; routines imported before 10.5 stay ordinary (no backfill).

### Resolved — builder calls the brief left open or qualified (mine)

- ✅ **D6 (mine) — Keep returns `204`, as the brief's call, with no body.** A `200` + routine would let the client reuse its `PUT` cache path; rejected to stay with the brief. Spec 10.5 patches its caches locally and revalidates.
- ✅ **D7 (mine) — Sweep on `GET /v1/routines` and `POST /v1/routines` only.** The brief offered "on read, on write or both". The list is the only read the web makes before showing routines; create is the only write whose result an expired row can change (cap and name). `PUT`/`DELETE`/start/get-one do not sweep: extra `SKIP LOCKED` traffic on every write for no visible gain, and a rename colliding with an unswept expired name resolves itself on the next list read (a `409 routine-name-taken`, then success).
- ✅ **D8 (mine) — The cap count excludes expired rows; the sweep still runs first.** The brief allows either as long as an expired one-off never blocks a create. The sweep alone is not enough: an expired one-off held by a live workout survives it, so the count also ignores expired rows (≤ 1 row, at most 51 exist). Name collisions are solved by the sweep, which is why it runs first.
- ✅ **D9 (mine) — Two-statement sweep with `SKIP LOCKED` (§6.1).** The brief's "skip a one-off with a live workout" is necessary but a single `DELETE … NOT EXISTS` has a snapshot gap against a concurrent start (§6.1). Locking first and testing second closes it, and `SKIP LOCKED` means a sweep never waits, so it cannot be part of a deadlock.
- ✅ **D10 (mine) — The routine lock sits before the workout lock in the finish (§6.2).** This is the one place the brief's reasoning is incomplete: it removes the sweep-vs-finish cycle by skipping live one-offs, but the hand `DELETE /v1/routines/{id}` takes routine → workout (through `SET NULL`) and would deadlock a workout → routine finish. A single statement with a subselect (so no extra round trip and no unlocked pre-read for the app to act on) takes the routine lock first, only for one-offs.
- ✅ **D11 (mine) — The workout flag is `routineIsOneOff: boolean` on `WorkoutDetail`, computed from the live routine row.** The Finish dialog needs "does finishing this remove a routine?", not the routine's id or expiry. It is true while the routine exists and carries the mark; it self-corrects if the routine is kept or deleted elsewhere (the dialog would be stale for one render at worst, and the server decides at finish regardless). **Rejected:** `routineId` on `WorkoutSchema` (widens every workout response and History row for one screen; the 09.2 D14 precedent), a stored `from_one_off` column on `workout` (goes stale, needs a write at start and at Keep).
- ✅ **D12 (mine) — `RoutineCreateSchema` is a separate schema, not a widened `RoutineWriteSchema`.** The write body is a strict object with a `superRefine`; making `oneOff` part of it would let `PUT` accept the key, contradicting "a `PUT` never changes it". The strict object and the refinement are split so both schemas share them.
- ✅ **D13 (mine) — The API does not know "from text".** `oneOff: true` is accepted from any authenticated client; the UI's "from text" meta line is correct only because Spec 10.4's Save is the only caller. If a second creator ever exists, the row needs a source column and Spec 10.5's copy needs a field.
