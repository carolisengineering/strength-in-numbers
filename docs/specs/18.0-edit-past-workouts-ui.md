## 1. Purpose, scope & non-goals

### 1.1 Purpose

Make History and Progress match what the lifter actually did (brief §1). Spec 07.4 taught the server to accept every live-logging write on a finished workout and to move a workout's start and duration; this spec is the screen that uses it:

1. **Fix a finished workout.** From the workout summary (opened from History, or right after Finish) **Edit workout** opens the edit screen: the logging screen's exercise cards and set rows in edit mode. The lifter changes or deletes a set, adds a set, adds or removes an exercise, reorders (Move), links and splits supersets, edits an exercise's note, changes the workout's time (**Change Time**), and edits its **title and notes** (a Details sheet). Each change saves as it is made. **Done** returns to the summary, where records are already updated.
2. **Log a forgotten workout through the normal Start.** Start empty or from a routine, tap **Change Time** on the workout screen and set the day, the start and how long it took, log from memory, tap **Finish**: the workout ends at start + took, not at "now", and lands in History on its real day.
3. **Fix the clock on a live workout** with the same **Change Time**.

The title and notes, when set, are shown on the summary (and the title on the History row), so editing them has a visible result. An edited or back-dated workout looks exactly like any other (brief §4.4): there is no marker anywhere.

> **First-principles note — "pessimistic" versus "optimistic" writes.** The live screen is *optimistic* for sets: a logged set is shown at once as "Not saved yet" while a persisted queue (the outbox, Spec 06.2) delivers it later, because the gym has bad signal and the lifter must not wait. An edit to a *finished* workout is the opposite on purpose (07.4 D12): the screen changes only when the server's answer arrives. Nothing is shown that the server has not accepted, so "a failed save that looks saved" (brief §7) cannot happen by construction. The price is that an edit needs a connection; the benefit is that the server can refuse an edit for reasons the client cannot predict (it would leave the workout empty, a time is out of bounds) and the lifter sees that refusal where it happened.

> **First-principles note — query keys, "invalidate" and "reset".** TanStack Query keeps server data in a cache addressed by *query keys* (arrays such as `["workouts","detail","<id>"]`). A key that is a prefix of another matches it, so one call can cover a family. **Invalidating** a family marks its entries stale; entries someone is currently displaying (active) refetch at once, the others just refetch the next time a screen mounts them. **Resetting** throws the entry's data away so the next mount starts from page 1. While the edit screen is open, History, Progress and the records lists are not displayed, so invalidating them costs no requests; they refresh when the lifter next opens them. That is why the edit screen can invalidate after every write (§6.2).

> **First-principles note — a date and a time of day are not a moment.** `<input type="date">` and `<input type="time">` give strings such as `"2026-10-16"` and `"18:00"` with no time zone. The server stores a *moment* (`startedAt`, in UTC) plus the offset that was in force there (`tzOffsetMinutes`, minutes east of UTC). Turning the strings into a moment needs a zone; this app uses the **device's** zone, the same as the live screen's "Started 18:05", and sends the offset at the *new* instant, so a day on the other side of a daylight-saving change is still the day the lifter typed (07.4 §6.5).

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"18.0 ACn — …"`**, enforced by a scan test in the style of `acTags.17-3.test.ts` (AC47). "Edit mode" means the edit screen; "live" means `ActiveSession`. Levels are in §10.

### Phase A — the edit screen

**Getting there**

1. **The entry point.** The workout summary (`FinishedWorkoutScreen`, both `section`s) shows a `secondary` **Edit workout** button directly under the stats row, above the records block. It navigates to `/app/workouts/:id/edit` (section `workouts`) or `/app/history/:id/edit` (section `history`). It is present on the summary shown right after Finish (same component). While the workout is loading or failed to load the button is absent. Tapping it makes no request of its own.
2. **Routes.** Both edit routes are protected children of the shell. `/app/workouts/routines/new`, `…/routines/:id` and `…/routines/:id/edit` still resolve to the routine screens (a router regression test). An id whose workout is **live** (`endedAt` null) redirects (`replace`) to `/app/workouts`; an unknown id renders `NotFound`; a load failure renders the summary's "Couldn't load this workout." with **Try again**. The screen starts from the server's truth: it refetches the detail on mount even when the summary just cached it, and on window focus (§6.1).

**The frame**

3. **Banner, header, Done.** The screen's `h1` is "Edit workout". Under it: a banner reading `Editing {Tue 14 Oct} workout` (the date is `formatLocalDate(localDate)`, the same text History shows), then the header line `Started {Tue 14 Oct, 18:05} · Took {52 min}` (device-zone start, `formatMinutes(workoutMinutes(startedAt, endedAt))`). The bottom `ActionBar` holds one `Button` **Done**, the screen's **only** `primary` button. The banner is not a live region and uses a neutral surface tint (no teal, no brass).
4. **What edit mode does not have.** The edit screen renders none of: the Workout menu, **Discard workout**, **End workout early**, **Finish workout**, `SessionClock`, `RestLine` / `RestReadout`, `LogBarButton`, the entry row (current-set panel), `SyncStatus`, "Not saved yet" tags, `RoutineNotePanel`, collapsed exercise cards. Every exercise renders as an expanded card; no "current exercise" is chosen.
5. **The cards are the logging screen's.** The edit screen renders exercises through `supersetRows` → `sectionSegments`: section headings with their notes, superset brackets (runs ≥ 2), target lines, warm-up marks, `SetText`. For one fixture workout, each card's set rows show the same text as the summary's (a parity test). A workout's non-contiguous section structure (07.4 §6.9) renders without error.

**Editing sets**

6. **Edit a set.** Tapping a set row opens the existing `SetEditSheet` prefilled from the stored set. **Save** sends `PATCH /v1/sets/{id}` with only the changed keys (`diffForPatch`); nothing changed → no request, the sheet closes. On `200` the row in the cached detail (`["workouts","detail",id]`) is replaced by the response and the sheet closes.
7. **Delete a set.** **Delete set** in the sheet sends `DELETE /v1/sets/{id}`; on `204` **or `404`** (a repeat is done) the row leaves the cached detail and the sheet closes. The "last set" case is AC18–AC19.
8. **Add a set.** Each card has an **Add set** button (below its set rows). It opens the `SetEditSheet` in *add mode*: title `New set · {exercise}`, fields prefilled by copy-forward from the exercise's last set (`seedDraft` with no plan: no "Set 3 of 4" and no "Extra set" in edit mode), no **Delete set**, submit labeled **Add set**. Submit sends `POST /v1/workout-exercises/{id}/sets` with `isComplete: true` and a `clientGeneratedId` minted when the sheet opens and **kept across failures** (re-minted only on the next opening). `201` / `200` (replay) upserts the row; the sheet closes. A tap on submit while the request is in flight sends no second request.

**Editing exercises**

9. **Add an exercise.** **Add exercise** (end of the list; also the only control of an empty workout) opens `ExercisePicker`; picking sends `POST /v1/workouts/{id}/exercises`. On `201` the detail is refetched and the new card appears expanded at the end, loose (no section, no plan) with its heading scrolled into view. While the add is in flight a placeholder "Adding {name}…" shows and every structure control waits (the live `structureLock`).
10. **Remove an exercise.** Options → **Remove exercise**: an exercise with no sets is removed at once; with sets, `ConfirmDialog` "Remove {name}?" / "{N sets} will be deleted." / **Remove**. `DELETE /v1/workout-exercises/{id}` → on `204` or `404` the detail is refetched (positions shift). The "last exercise with sets" case is AC18–AC19.
11. **Move and link.** **Move up / Move down** and the link toggles behave as on the live screen: planned by `planSessionChange` from the card's segment slots (`positionOffset`), sent as the minimal ordered `PATCH /v1/workout-exercises/{id}` list one after another, with the same refusals (`canLinkRule`, section edges with their reasons) and the same `NO_FREE_GROUP_MESSAGE`; after the last PATCH, or the first failure, the detail is refetched once. They are online-only (as 10.1 D6) and the cards redraw once, from that refetch.
12. **Exercise notes.** **Add note / Edit note** opens `NoteSheet`. In edit mode **Save waits for the server**: the sheet shows a busy submit, sends `PATCH /v1/workout-exercises/{id}` with exactly `{ notes }`, closes on `200` (the exercise's `notes` / `updatedAt` are written into the detail), and on failure **stays open with the typed text** and an inline error (AC15–AC16). An unchanged note closes without a request. Unlike live, nothing is optimistic and nothing is queued.

**Leaving**

13. **Done.** **Done** navigates (`replace`) to the summary of the same section (`/app/{section}/:id`) and sends no request. It is disabled with the hint "Saving…" while any edit write is in flight. The browser / Android back gesture also leaves with no prompt (there is nothing unsaved: AC14). A half-typed Add set sheet is not an edit and is dropped silently.

**Writes: pessimistic, visible, retry-safe**

14. **Nothing is shown that the server has not accepted.** In edit mode the cached detail is written **only** from a successful response or a refetch, for every write kind (set create / patch / delete, exercise add / remove / move / regroup / note, details, Change Time). A failed write leaves the cache, the rows and the order exactly as before and shows its failure where the lifter acted (AC15–AC16). There are no pending / "Not saved yet" states in edit mode.
15. **Offline.** A network failure on any edit write shows "You're offline — try again when you have signal" in the control's own place (the sheet's form error; the screen banner for structure writes), keeps the typed values, and re-enables the control. The screen itself opens from the cached workout while offline; a failed refresh shows "Couldn't refresh your workout — showing the last copy we have." with the cached data intact (the offline-open case).
16. **The error table.** Every row of §5.4 is the behavior: for each route, `404` / `409 workout-would-be-empty` / `422` / network / other-or-5xx resolves to the copy and cache effect in the table. Unknown `409` slugs and `workout-finished` (unreachable in normal operation, kept for an API rollback) take the generic "try again" row. Messages never echo a response body; `requestId` is shown where the live screen shows it.
17. **Retry rules.** **Add set** retried after a failure re-sends the **same** `clientGeneratedId` (a lost response cannot add the set twice, 07.4 AC14). Set `PATCH`, set `DELETE`, exercise `DELETE` and the note `PATCH` are idempotent: **Try again** / **Save** re-sends them. **Add exercise** has no idempotency key: after an ambiguous failure the detail is refetched and the lifter is asked to check before adding again (no Try again, as live). There is no automatic retry in edit mode.

**The last set**

18. **`409 workout-would-be-empty` opens the dialog.** On `DELETE /v1/sets/{id}` or `DELETE /v1/workout-exercises/{id}` the `409` opens a `ConfirmDialog` (danger): title "Delete this whole workout instead?", body "A workout can't be left with no sets. Deleting it also removes it from History and Progress, and any records it holds.", confirm **Delete workout**, cancel **Keep it** (focus starts on Cancel, Spec 12). **There is no client pre-check**: the request is always sent and the server decides (D6). **Cancel** closes the dialog; the set / exercise is unchanged in the cache and on screen (the delete sheet closes too).
19. **Confirm deletes the workout.** **Delete workout** calls `DELETE /v1/workouts/{id}` through `useDeleteWorkout` (`phase: "finished"`, so `applyDeletedCaches` runs and the drafts / rest stores are cleared), then navigates (`replace`) to the section's home (`/app/history` or `/app/workouts`). A `404` counts as done. A failure shows "Couldn't delete the workout — try again" with **Try again** on the edit screen (the dialog closes), same as the summary's delete.
20. **The workout vanished.** If a write answers a workout-level `404`, or a refetch of the detail does, the screen is replaced in place by the notice "That workout no longer exists." with a link back to the section's home; no write is attempted afterwards. A `404` on a *set* or *exercise* with the workout still present shows "That set no longer exists" / "That exercise was removed from the workout", refetches the detail, and closes the sheet.

**Isolation from the live session**

21. **Edit mode never touches live-session machinery.** Edit writes use the plain REST client (`EditWorkoutClientContext`), never the queued one, **even while a live workout is cached with queued ops**; they never enqueue, never write `["workouts","active"]`, never read or write `sin:workout:outbox`, `sin:workout:drafts` or `sin:workout:rest`, never publish to the `logAction` store, and never use `SET_MUTATION_KEY` (so a pending edit does not disable a live Finish). A test opens an edit session while a live workout has a queued op, a stored draft and a running rest timer, edits, and asserts all three are untouched. A source scan (AC46) pins the same for the edit modules.

**Caches**

22. **Cache refresh after every successful finished-mode write.** `applyEditedCaches(queryClient, workoutId)` runs in the hook-level `onSuccess` of every edit write (set create / patch / delete, exercise add / remove / move / regroup / note, details, Change Time on a finished workout — not on a live one): it **resets** `["history","list"]` (the list restarts at page 1; a re-time moves rows), **invalidates** `["progress"]` and `["records"]` (all families: `["records","all"]`, `["records",{workoutId}]`, `["records",{exerciseId}]`), and the workout's own `["workouts","detail",id]` is written from the response (set writes, note, Change Time) or invalidated (structure writes, which shift siblings' positions). The key shapes are asserted exactly. It sits beside `applyFinishedCaches` / `applyDeletedCaches` in `features/records/cache.ts`. A write whose response is cancelled by unmount still runs it (hook-level callbacks, as `useWorkoutMutations`).
23. **No request burst; the summary is fresh.** While the edit screen is open, no request is made to `GET /v1/workouts` (list), `/v1/progress/…` or `/v1/personal-records` however many edits are made (inactive queries are only marked stale). After **Done**, the summary shows the edited sets, header stats and record cards, with exactly one `GET /v1/personal-records?workoutId=` (the fake serves records recomputed from the edited sets); History opened next shows page 1 re-read, with the edited counts.

**The outbox (Spec 06.2 amended, §6.4)**

24. **A late op that lands on a finished workout refreshes its caches.** When the outbox delivers an op (set create / update / delete, or a note) for a workout that is **not the cached active workout** — the workout was finished on another device, 07.4 D1 / O3, "applied, not `409`" — `WorkoutClientProvider`'s `onSynced` / `onNoteSynced` calls `applyEditedCaches` and invalidates `["workouts","detail",workoutId]`. For an op of the active workout nothing changes.
25. **The gone path no longer drops unsent ops.** `queuedWorkoutClient.getActive` calls the new `outbox.settle(activeId)` instead of `retainOnly`: queued and sending ops of a workout other than the active one **stay and drain** (the server applies them to a finished workout, or `404`s them for a deleted one); only **failed** ops of other workouts, and id-map entries no remaining op needs, are removed. `outbox.dropWorkout(id)` removes every op of one workout and is called by `useDeleteWorkout` on success (an own discard / delete). 06.2 AC17's "the gone path removes every op" is replaced by this rule.
26. **The `workout-finished` branch and the `422` race.** The outbox's `409 workout-finished` handling (fail the op and every later op of the workout, `classify.ts` `fail`) and `resolveFailure`'s `workout-finished → gone` mappings are **unchanged** and now fire only if the API is rolled back past 07.4; their existing tests are retagged to say so. A half-filled working set that loses a race to a Finish and is refused with `422` is an ordinary `4xx`: the op becomes `failed` (no retry), the row shows "Couldn't save" with **Edit** (status 422) and **Discard** while its workout is the active one; the **Edit** sheet's `PATCH` is a normal write that the server now accepts in finished mode or answers with field errors. If its workout is no longer the active one, the failed op is reported (`reportUnexpected`, `set_sync_failed`) and removed by the next `settle` (accepted residual risk, D9).

**Telemetry, offline open, identity**

27. **Telemetry (A).** Each successful edit write emits one scalar event `workout_edit { edit }` with `edit ∈ set_added | set_changed | set_deleted | exercise_added | exercise_removed | exercise_moved | exercise_regrouped | exercise_noted | details_changed` (the same enum as the server's `workout_edited`); opening the screen emits `workout_edit_opened { section }`; the dialog emits `workout_edit_refused { reason: "would_be_empty", choice: "deleted" | "kept" }` when answered. Edit mode emits **none** of the live events (`set_logged`, `set_edited`, `set_deleted`, `exercise_added`, `exercise_removed`, `exercise_moved`); no event carries a name, a note, a weight or a title.
28. **Looks like any other workout.** After any edit the summary, the History row and Progress render with no marker: `FinishedWorkoutScreen`, `HistoryRow` and the Progress components read no `updatedAt`, and no string such as "edited" or "logged later" exists in them (a source scan); the only visible difference on the summary is the **Edit workout** button, which every finished workout has.

**Workout title and notes (added with the owner's answer to O1; numbered 50–58 so AC1–AC49 keep their numbers)**

50. **The summary shows them.** `FinishedWorkoutScreen` (both sections) renders, when set: the **title** as a paragraph above the date line (the largest text of the header block; not a heading, so the `h1` "Workout summary" and the exercise `h2`s keep their order), and the **notes** in a `section` named "Workout notes" after the "From routine" and routine-notes lines and before the stats row, with a small muted label "Notes" above the text. When `title` is `null` no title element exists; when `notes` is `null` no notes section and no label exist. There is **no placeholder** on the summary (a workout without them looks like any other).
51. **Plain text, line breaks kept, XSS-safe.** Title and notes are rendered only as React text children: no `dangerouslySetInnerHTML`, no markdown, no link detection. Notes use `white-space: pre-wrap` so their line breaks show, and `overflow-wrap: anywhere` so a long unbroken string wraps (no horizontal scroll at 320 px); the title wraps the same way. A test renders `<img src=x onerror=…>`, `<script>…</script>` and `**bold**` as literal text with no element created. A source scan (AC46) finds no `dangerouslySetInnerHTML` in the files that render them.
52. **The edit screen's Details panel.** Under the header line and above the first card, a `section` headed "Details" (`h2`) shows the title (or the muted "No title") and the notes in full, pre-wrapped (or the muted "No notes"), and a `secondary` button **Edit details**. The panel is on the edit screen only; its text is rendered like AC51.
53. **The Details sheet and its validation.** **Edit details** opens a `Sheet` titled "Details" with **Title** (single-line input, hint `{n} / 120`), **Notes** (textarea, hint `{n} / 4000`) and **Save details**, prefilled from the cached detail. Validation uses `@sin/core`: the typed text is checked with `UpdateWorkoutSchema` (`WORKOUT_TITLE_MAX` 120, `WORKOUT_NOTES_MAX` 4000, no control characters; notes may contain line breaks and tabs, a title may not contain line breaks), after trimming leading and trailing whitespace; errors use the pinned copy of §5.7, shown under the field, and no request is sent while one is showing. The counts use string length (the server's measure), not code points.
54. **Saving, clearing and only-changed.** A field is sent only if its text differs from its initial text; none changed → no request, the sheet closes. A changed field that is empty after trimming is sent as `null` (clears the value); the client never sends `""`. The request is `PATCH /v1/workouts/{id}` with exactly the changed keys, through `WorkoutClient.updateWorkout` (online-only, `networkMode: "always"`, no outbox). On `200` the response's `title`, `notes` and `updatedAt` are merged into the cached detail, the sheet closes, "Details saved" is announced, and `applyEditedCaches` runs. Failures follow §5.4's Details row: the sheet stays open with the typed text; a network failure shows the offline copy; a `404` takes the workout-vanished path (AC20); a `422` shows the field copy chosen by re-checking the typed text (the server's static message is never displayed); anything else shows "Couldn't save the details — try again". **Save details** again is the retry (the `PATCH` is idempotent); a second tap while in flight sends no second request.
55. **Round trip.** Against the web fake: set a title and notes with line breaks on a finished workout, **Done** → the summary shows both (line breaks intact); edit again and clear the title (empty) → the summary shows no title element, the request body was `{ "title": null }`, and the notes were not sent.
56. **History shows the title.** `HistoryRow`'s first line shows `{date} · {title}` when `title` is set, **in place of** the routine name (`{date} · {routineName}` is unchanged when there is no title); the existing truncation keeps the badge's box (10.1 AC25) and nothing overflows at 320 px. History **never shows notes**. The web reads the title from `WorkoutSummary.title`, which the list already serves, and the list is reset after a details edit (AC22) so the new title appears.
57. **Accessible.** The Details sheet and panel meet AC44 (labels via `Field`, errors tied to their controls, the Sheet's usual focus, "Details saved" in the screen's one polite status line, axe-clean in light and dark); the summary with a title and long notes is axe-clean and has no horizontal scroll at 320 px.
58. **The live screen is unchanged.** `ActiveSession` renders and edits no title or notes (D18); a source scan finds no read of the workout's `title` / `notes` fields in it, and the Start screen is unchanged.


### Phase B — Change Time

**Client and sheet**

29. **The client method.** `WorkoutClient.updateWorkout(id, body)` (added in Phase A for `{ title, notes }`, AC54) also accepts Change Time's keys: `PATCH /v1/workouts/{id}` with exactly the keys given (`startedAt`, `tzOffsetMinutes`, `durationSeconds`), parsed with `UpdatedWorkoutSchema`. It is on the REST client; the queued client inherits it (**never** queued: Change Time is online-only). `finish` is unchanged.
30. **The sheet.** `ChangeTimeSheet` (a `Sheet`, title "Change Time") has: **Day** (`<input type="date">`, `min` = 2000-01-01 from `WORKOUT_START_EDIT_FLOOR`, `max` = today's device-local date), **Started at** (`<input type="time">`), **Took** as two numeric inputs **Hours** (0–24) and **Minutes** (0–59), and a submit **Save time**. Initial values: day and time are the workout's `startedAt` in the device zone; Took is `plannedDurationSeconds` (live, rounded to minutes) or `workoutMinutes(startedAt, endedAt)` (finished), empty when a live workout has no plan. A live workout shows the hint "Leave empty and Finish ends the workout when you tap it." under Took; a finished workout's Took is required.
31. **Only what changed is sent.** The body contains `startedAt` + `tzOffsetMinutes` only if Day or Started at differs from its initial value, and `durationSeconds` only if Took differs. Nothing differs → no request, the sheet closes. Changing only Took never sends a start (so `local_date` and the offset are untouched, 07.4 AC24); changing only the day or time never sends a duration (the server keeps the old one, 07.4 AC22). A finished workout's seconds survive a start-only change on the server; the *form* shows whole minutes.
32. **Instants and offsets.** `startedAt` is built from the Day and Started at strings in the **device zone** (`new Date(y, m - 1, d, h, min)`), sent as ISO UTC; `tzOffsetMinutes` is the device offset **at that instant** (`startWorkoutFields(date)`), not today's. A table test covers a negative offset, a late-evening time whose UTC day differs, a daylight-saving-change day, and a nonexistent local time (spring-forward gap: JS normalizes forward and the sheet sends what JS built). Seconds of the start reset to `:00` when the start is rewritten.
33. **Pre-validation with the shared rules, pinned copy.** Before sending, the sheet runs `resolveRetime` from `@sin/core` on the stored workout and the edited values with the current time, and maps the result's `message` (a `RETIME_MESSAGES` constant) to the pinned copy of §5.6, shown under the field named by `path` (`startedAt` → Started at, `durationSeconds` → Took). The **same mapping** renders a server `422` whose `errors[].path` is `startedAt`, `durationSeconds` or `endedAt`. An unknown message shows "Check the time and try again." Hours / Minutes that are not whole numbers in range show their own pinned messages; blank Day / Started at show "Pick a day." / "Pick a time.". No request is sent while a field has a client error.

**The live screen**

34. **A Change Time control on the live header (layout A, mockups approved 2026-10-18, D22).** The header has two rows. Row 1: the ticking `SessionClock`, or the static `Took {1 h}` in its place when a plan exists (AC35), then **Workout menu**. Row 2: `Started {18:05}` (today), or `Started {Fri 16 Oct, 18:00}` when the start's device-local day is not today, then a `secondary` **Change Time** button. "Took" is never repeated on row 2. The button is not inside the Workout menu (D8). It opens the sheet in live mode.
35. **Live save.** On `200` the response (without `newRecords`) is merged into `["workouts","active"]` (`startedAt`, `endedAt` null, `localDate`, `tzOffsetMinutes`, `plannedDurationSeconds`, `updatedAt`); nothing else changes: no set, draft, rest timer or outbox op is touched, and History / Progress / records are **not** invalidated (a live workout has no row there). The header reflects the new start at once. **When a plan exists the ticking `SessionClock` is replaced by the static "Took {1 h}"; without a plan it keeps ticking from the (possibly moved) start** (O2).
36. **Clearing "Took".** Emptying both Took fields on a live workout that has a plan sends `durationSeconds: null` (the plan is cleared); emptying them when there was no plan sends nothing for the duration.
37. **Finish with a plan.** `confirmFinish` sends `endedAt = finishEndedAt(startedAt, plannedDurationSeconds, now)`: when a plan exists, `startedAt + plan` as ISO; otherwise today's `finishTimestamp(startedAt, now)`. `finishEndedAt` is pure (in `timestamps.ts`). Both Finish dialogs' duration comes from the same function (so the dialog shows the plan, not elapsed time), `workout_finished` gains `hadPlannedDuration`, and every other part of the Finish contract (`finishLock`, waits, failure rows, `409` recovery) is unchanged (Spec 17.1 §6.7 amended for this one line, §11).
38. **The dialogs say where it ends.** When a plan exists, `FinishDialogBody` shows `Ends {Fri 16 Oct, 19:00}, as set in Change Time.` after the stats and before the planned-sets flag; without a plan nothing is added. (Amends Spec 17.2 AC1 / AC2's order only in that case, §11.)
39. **The forgotten-workout flow, end to end.** Against the web fake: Start empty → Change Time (day two days back, 18:00, took 1 h) → log two sets → Finish → the request carries `endedAt` = that start + 1 h; the summary's header reads "1 h"; History's first page shows the workout under the **backdated** date, in the right place in the order; the finish response carries `plannedDurationSeconds: null`. (A second test does the same from a routine, with planned sets prefilled.)

**The edit screen**

40. **Change Time on a finished workout.** The edit header shows a `secondary` **Change Time** button after the Took text (Phase A's header had none). Took is required. On `200` the response's `startedAt`, `endedAt`, `localDate`, `tzOffsetMinutes`, `updatedAt` are merged into the cached detail, the banner shows the new day ("Editing Fri 16 Oct workout"), and `applyEditedCaches` runs (History restarts: a re-time moves rows; Progress and records follow).

**Failures and concurrency**

41. **Failure behavior.** A network failure keeps the sheet open with the typed values and the offline copy; `404` takes the workout-vanished path (AC20); a `422` shows the mapped copy under the named field; any other failure shows "Couldn't change the time — try again". **Save time** again is the retry (the `PATCH` is idempotent, 07.4 AC29). Nothing changes in the cache on failure.
42. **One request at a time.** **Save time** is busy while the request is in flight and a second tap sends no second request. The sheet is modal, so no other control (Finish included) can be used meanwhile; `useChangeTime` still exposes `isPending` so `ActiveSession` includes it in `structureBusy` (belt and braces for keyboard paths).
43. **Telemetry (B).** A successful Change Time emits `workout_retimed { where: "live" | "edit", changed: "start" | "duration" | "both", daysBack }` (`daysBack` = whole days between now and the new start, ≥ 0; absent when the start did not change). The Finish event gains `hadPlannedDuration`.

## 6. Behavior & logic

### 6.1 The edit screen is a sibling of `ActiveSession`, not a mode of it

`EditWorkoutScreen` composes the logging screen's *leaf* components in edit mode (D3):

- reused as is: `supersetRows`, `sectionSegments`, `SessionSection`, `SupersetBracket`, `LinkToggle`, `ExercisePicker`, `NoteSheet`, `ConfirmDialog`, `Sheet`, `ActionBar`, `resolveFailure`, `useRegroup` (with a `refresh` option so it refetches `detail(id)` instead of `active`), `planSessionChange` / `canLinkRule`;
- reused with an `edit` switch: `ExerciseCard` (`mode="edit"`: no `EntryRow`, no sync tags, an **Add set** button, a note save that waits), `SetEditSheet` (add mode; its write hooks come from the edit family);
- new: the screen, its write hooks, `LastSetDialog`, `applyEditedCaches`.

`ActiveSession.tsx` gets **no** edit branch (AC46); its only Phase B changes are the header control, the finish end time and the clock (AC34–AC38). `EntryRow` and the logAction / rest / draft stack are never mounted in edit mode.

The screen reads its workout through `useEditableWorkout(id)`: key `["workouts","detail",id]` (the summary's key), `refetchOnMount: "always"`, `refetchOnWindowFocus: true`, `retry: false`. It reads the unit preference with `useMe` (as the summary does).

**Which client.** `WorkoutClientProvider` already builds the plain REST client (`createWorkoutClient(api)`) to hand to the outbox; it additionally provides it as `EditWorkoutClientContext`. Edit hooks use only that. (The queued client would also fall through to REST for a workout that is not the cached active one, but that is an accident of its `cached()` check; relying on it would couple edit mode to live state.)

### 6.2 Writes, caches and ordering

**Edit mutations** (`useEditMutations.ts`): one family with the same call shapes as the live hooks, so `SetEditSheet` / `ExerciseCard` pick the family from a `useScreenMode()` context value (`live` by default, `edit` provided by `EditWorkoutScreen`) in exactly one seam:

| Hook | Call | Success (hook-level `onSuccess`) |
|---|---|---|
| `useEditCreateSet` / `useEditUpdateSet` | `createSet` / `updateSet` on the REST client | write the row into `detail(id)` (`withSetUpserted`); `track("workout_edit", …)`; `applyEditedCaches` |
| `useEditDeleteSet` | `deleteSet`, `404` → done | `withSetRemoved`; track; `applyEditedCaches` |
| `useEditAddExercise` / `useEditRemoveExercise` | `addExercise` / `removeExercise` | invalidate `detail(id)` (siblings shift), return its promise so `isPending` spans the refetch; track; `applyEditedCaches` |
| `useEditSetNote` | `PATCH { notes }` | `withExerciseNotes`; track; `applyEditedCaches` |
| `useEditDetails` | `updateWorkout(id, { title?, notes? })` | merge `title`, `notes`, `updatedAt` into `detail(id)`; track `details_changed`; `applyEditedCaches` |
| regroup | `useRegroup({ refresh })` | one refetch of `detail(id)`; `exercise_moved` / `exercise_regrouped` tracked once per plan; `applyEditedCaches` |

Every set mutation is keyed `EDIT_MUTATION_KEY = ["workouts","edit"]` (not `SET_MUTATION_KEY`), and **Done** is disabled while `useIsMutating({ mutationKey: EDIT_MUTATION_KEY }) > 0`. As in the live hooks, `onMutate` of a set write cancels an in-flight read of `detail(id)` and `onSettled` re-reads once if one was interrupted, so a stale response cannot land on top of a write and erase it (06.1 §6.2).

**Hook-level callbacks** (not call-site): TanStack skips call-level callbacks when the component unmounted before the response; hook-level ones still run, so a lifter who taps Done while a request is in flight still gets correct caches.

**`applyEditedCaches(queryClient, workoutId)`**:

```ts
queryClient.resetQueries({ queryKey: HISTORY_KEYS.list });            // ["history","list"]: restart at page 1
queryClient.invalidateQueries({ queryKey: PROGRESS_KEYS.all });        // ["progress"], every series
queryClient.invalidateQueries({ queryKey: RECORDS_KEYS.all });         // ["records"], incl. the workout's own
```

Unlike `applyFinishedCaches` there is no seeded entry to protect, so the records invalidation is a bare prefix and includes `["records",{workoutId}]` (the summary re-reads it on mount). History is **reset**, not invalidated (07.4 §6.7: a moved row can make a paging session skip or repeat a row; the client restarts the list after an edit); the History screen is not mounted, so the reset costs nothing until the lifter opens it. The detail itself is not in this helper: set / note / time writes put the response in, structure writes invalidate.

Why the whole `["progress"]` family and not "the touched lineages": the 08.1 helpers already invalidate the family (AC8 there), a series refetch is one small request on a screen that is mounted later, and a lineage-precise list would need the exercise-to-root mapping on the client for no visible gain.

### 6.3 The last set (AC18–AC19)

```
user taps Delete set / Remove exercise (confirmed)
  -> send the DELETE (always; no pre-check)
  -> 204 / 404  : normal success
  -> 409 workout-would-be-empty:
       close the sheet / confirm; open LastSetDialog  (cache unchanged, nothing recomputed server-side)
       Keep it        : close; track workout_edit_refused { choice: "kept" }
       Delete workout : useDeleteWorkout({ phase: "finished" }) -> navigate home; track { choice: "deleted" }
```

Identified by `error.type === "workout-would-be-empty"` (the slug, never the text), classified in `errors.ts` as a new `WorkoutErrorKind`. **No client pre-check** (D6): the cached detail can be stale (a second device may have added or removed a set), and offering to delete a whole workout on stale data is the one destructive mistake this screen could make; the server's answer is the authority and the cost is one round trip in a rare case. The dialog's body is static and states the consequence.

### 6.4 The outbox, amended (Spec 06.2)

The outbox (Spec 06.2) is the persisted list of unsent *live* set and note writes. Spec 07.4 changed what the server does with one of them that arrives late. Decisions, with the code they touch:

1. **A queued op that lands on a workout finished on another device is now applied** (07.4 D1, O3: no lost set). Nothing in `outbox.ts`'s `send` / `succeed` changes. What was missing is the *refresh*: the op changed a finished workout and the server recomputed its records, but the client's `onSynced` only patches `["workouts","active"]`. `WorkoutClientProvider.onSynced` / `onNoteSynced` therefore compare the op's `workoutId` with the cached active workout and, if it is not the active one, call `applyEditedCaches` and invalidate `detail(workoutId)` (AC24).
2. **The gone path stops discarding unsent ops (AC25).** `queuedWorkoutClient.getActive` called `outbox.retainOnly(server?.id ?? null)`: a `404` from `/active` (the workout was finished or deleted elsewhere) dropped every op of any other workout. Before 07.4 those ops were doomed (`409`); now an op for a *finished* workout would be applied, and dropping it before it was sent is silent data loss. `retainOnly` is replaced by `settle(activeId)`: keep queued and sending ops of other workouts and let the server say what happened to each (applied for a finished workout; `404` for a deleted one — `classify` fails it, no retry); remove **failed** ops of other workouts (nothing renders or retries them) and any id-map entry no remaining op needs. Own deletes are explicit: `useDeleteWorkout.onSuccess` calls `outbox.dropWorkout(id)` (an op for a workout the lifter just deleted must not be sent).
3. **The `workout-finished` halt branch is unchanged and now rollback-only (AC26).** The outbox never sends a finish (Finish is a REST call), so `409 workout-finished` can no longer come from any op. The branch in `fail()` and `resolveFailure`'s `workout-finished → gone` rows stay as the behavior under an API rollback past 07.4 Phase A; the new comment says so and their tests are retagged. Deleting them would make a rollback lose sets silently.
4. **The new `422` is an ordinary `4xx`.** Live logging always sends complete sets (`parseDraft` is the gate, and a create carries `isComplete: true`), so the finished-mode integrity `422` (07.4 AC9) is reachable only for a set that was half-filled by another client, edited, and refused after a Finish. `classify` already treats a `422` as permanent: the op becomes `failed`, its row shows "Couldn't save" with **Edit** (status 422) and **Discard**. Nothing new in the outbox.
5. **A stale live screen keeps working, on a finished workout.** A second device's screen that still shows the workout as live can now log a set into it (it succeeds). The existing window-focus refetch of `/active` (`refetchOnWindowFocus: true`) ends that screen on the next focus; nothing more is added. This is the cost accepted in 07.4 D1.

**Residual risk (D9):** a failed op of a no-longer-active workout is reported and removed by `settle` without being shown. It needs two devices, a Finish race and a request the client had already validated. The lifter can re-add the set through Edit workout. If the telemetry shows it, a surface is a follow-up.

### 6.5 Change Time

**`changeTime.ts` (pure):**
- `initialValues(workout, now)` → `{ day, time, hours, minutes }` (device zone; Took from the plan or the stored duration).
- `buildPatch(workout, form)` → `{ startedAt?, tzOffsetMinutes?, durationSeconds? }` containing only changed groups (AC31); `startedAt` from `new Date(y, m - 1, d, h, min)`, `tzOffsetMinutes` from `startWorkoutFields(date)`.
- `validate(workout, patch, now)` → calls `resolveRetime({ startedAt, endedAt, plannedDurationS }, patch, now)` and maps the result with `copyFor(result)` (the §5.6 table). The same `copyFor` renders a server `422`.
- `daysBack(now, startedAt)`.

**`useChangeTime(workout, where)`:** `mutationFn` = `client.updateWorkout(id, patch)` on the REST client; `networkMode: "always"` (fails at once offline, as every non-set write); hook-level `onSuccess`: strip `newRecords`, merge the `Workout` into `active` (live) or `detail(id)` (edit) and, **for a finished workout only**, `applyEditedCaches`.

**Merging.** `{ ...cachedDetail, ...workout }` (the finish hook's pattern): the response is a `Workout` (no `exercises`), so `exercises`, `sections` and `routineNotes` are kept. The live merge also leaves `["history","list"]` alone: a live workout has no row there.

**The live clock.** A plan makes "elapsed since start" meaningless (a Friday workout logged on Sunday would read `40:12:07`), so with a plan the header shows the static "Took {1 h}"; without one it ticks from the stored start, which may have moved (`SessionClock` already derives from `startedAt`).

### 6.6 Finish with a plan (AC37–AC38)

```ts
// timestamps.ts
export function finishEndedAt(startedAt: string, plannedDurationSeconds: number | null, now: Date): string {
  return plannedDurationSeconds === null
    ? finishTimestamp(startedAt, now)
    : new Date(Date.parse(startedAt) + plannedDurationSeconds * 1000).toISOString();
}
```

`confirmFinish` (the one finish path) and `dialogStats` call it; nothing else in the Finish contract changes. The server accepted `start + plan` as a valid end when the plan was set (end ≤ now + 5 min) and time only moves forward, so the request stays valid; if the lifter changes the start *after* setting a plan, the server revalidates the pair (07.4 AC20) and the sheet pre-validates it (AC33). The finish clears the plan server-side.

`confirmAlreadyFinished` (the `409` recovery) is unchanged: if a second device finished first with its own "now", the summary shows that device's duration (07.4 D6 "known edge").

### 6.7 Edge cases

- **Edit while a live workout exists.** Allowed (07.4 AC28). The live workout's outbox drains in the background; nothing here touches it (AC21). Opening an edit route unmounts `ActiveSession` (drafts persist as on any navigation).
- **Edit from History while the History list is paged.** The reset (AC22) means coming back shows page 1.
- **A workout with zero sets** (a legacy API-only finish): editable; the dialog guard never fires because the delete rule is "≥ 1 → 0" (07.4 §6.3). Add exercise works; the empty-state hint is "Add your first exercise".
- **Travelers.** The edit header and sheet show the start in the **device's** zone; the banner and History show `localDate`, the zone the workout was recorded in. They can differ for a workout logged in another zone; changing only Took never rewrites either.
- **Spring-forward gap** (AC32): the sheet sends what JS built; the summary then shows the server's `localDate`.
- **Overlap** is allowed (07.4 D10); no message.
- **Two tabs.** The edit screen has no persisted state; the outbox's two-tab guard is unaffected.

### 6.9 Title and notes (AC50–AC58)

`details.ts` is pure: `normalize(text)` trims the ends (internal line breaks and spaces are kept) and maps empty to `null`; `validate(field, text)` runs `UpdateWorkoutSchema.safeParse({ [field]: normalized })` and maps the first issue to the §5.7 copy by *kind* (length, control characters, other), never by displaying the issue message; `buildPatch(workout, form)` returns only the fields whose text differs from the initial text, each normalized (empty → `null`). `DetailsSheet` keeps its own state and commits once on **Save details**, like `NoteSheet`. Rendering is shared by the summary and the edit panel through one small component so the pre-wrap, wrap and plain-text rules live in one place. The History row reads `WorkoutSummary.title` (already served; no API change). The live screen is untouched (D18).

## 7. Security & privacy

- **No new authorization path.** Every call is an existing `/v1` route with the user's token; another user's workout, set or exercise is `404` (07.4 AC16), which the edit screen renders as `NotFound` / the AC20 view. The route param is passed through `encodeURIComponent` by the REST client like every id.
- **Destructive action.** The only destructive control, "Delete this whole workout instead?", is shown on the server's say-so (no stale client pre-check, D6), defaults focus to Cancel, and states the consequence.
- **Input bounds** are the server's (07.4 §7); the client's pre-validation is a courtesy and is never trusted (a server `422` is rendered with the same copy).
- **Privacy.** No new data leaves the device. Telemetry is scalars only (§9); no note text, name, weight, title or workout notes are logged or tracked. User text (workout title and notes, exercise notes, exercise names) is rendered only as React text children: no HTML, markdown or link parsing (AC51), so stored content cannot inject markup; `pre-wrap` is CSS only. No new `localStorage` key, so logout needs no change (AC46).
- **No cross-user residue.** Edit mode keeps no per-user persisted data; the TanStack cache is cleared by `logoutAndClear` as today.

## 12. Decisions & open questions

### Decisions

- ✅ **D1 — Numbering: 18.0, not 08.2 or 17.4.** *Rationale:* the README table is in dependency order and each spec's number should not precede what it depends on. 08.2 would sit before 09–10 and 17.x, but this spec needs 10.1 / 10.3 (the cards, regroup, the note sheet), 17.1 (the live header and Finish contract) and 17.2 (the Finish dialogs, summary stats). 17.x is the closed design-refresh family (17.0–17.3, milestone line "Design refresh"). The milestone line already lists "Post-M4 improvements (issues #89 / #90) = 07.4 (API; its UI spec is not yet numbered)", so the UI spec joins that line as the first member of a new 18.x family. Mirrors 07.4 D16's reasoning (numeric order = dependency order). *Rejected:* 08.2 (order), 17.4 (wrong family), 07.5 (API family). Easy to rename if the owner prefers History's family.
- ✅ **D2 — Two phases, A then B (Change Time second).** *Rationale:* A is the larger and the more valuable alone (fix a wrong set); B is a self-contained sheet plus two small edits to the live screen and shares nothing with A except the edit header's link. Each fits a session; the A1 / A2 cut (§11) is the pressure valve. *Rejected:* B first (smaller, but the brief's main use is fixing past workouts); one PR (the diff would mix the outbox amendments with the finish contract change).
- ✅ **D3 — The edit screen is a sibling of `ActiveSession`, composing leaf components, not a mode of it.** *Rationale:* `ActiveSession` is ~800 lines of live-only machinery (current exercise, rest timer, the log bar, outbox state, drafts, Finish, Discard, announcements). An `editing` prop would put a branch beside each, and each branch is a place for a live behavior to leak into a finished workout (a draft overwriting the live workout's drafts, a rest timer starting) or for edit code to slow live logging (brief §7). The leaf pieces the owner means by "the same screen as logging" — cards, set rows, sheets, Move, link, notes, the picker — are reused as they are, so the screen *looks* like logging. *Rejected:* `ActiveSession mode="edit"`; a copy-paste fork of the file (drift). *Cost:* a small amount of duplicated orchestration (`structureLock`, failure handling, ~100 lines); extracting a shared hook is a follow-up once both stabilize. *Covered by:* AC21, AC46.
- ✅ **D4 — Outbox: keep unsent ops of other workouts and let the server decide; drop only failed ones; own deletes drop explicitly (`settle`, `dropWorkout`); the `workout-finished` branch stays as rollback-only code (mine).** *Rationale:* 07.4 O3 (owner) chose that a queued op landing after a Finish elsewhere is *applied* rather than lost. The client contradicted it: `getActive` → `retainOnly(null)` discarded those ops on the `/active` `404` before they were sent, so the new server behavior would never be reached on exactly the path it was built for. `settle` honors the decision with the fewest moving parts (no extra request to ask whether a workout was finished or deleted: each op's own answer says so). The `409` branch is dead in normal operation but it is what protects a lifter's sets if the API is rolled back, so it stays with a comment and retagged tests. *Rejected:* checking `GET /v1/workouts/{id}` before dropping (an extra request in a query function, undecidable offline); deleting the branch; building a surface for failed ops of non-active workouts (D9).
- ✅ **D5 — Edit writes are pessimistic, on an explicit REST client, with their own mutation key and no optimistic state.** *Rationale:* 07.4 D12. The explicit `EditWorkoutClientContext` makes the separation from the queued client a rule (AC21) instead of an accident of the queued client's `cached()` check. A separate key keeps a pending edit from disabling a live Finish. *Rejected:* routing edits through the queued client; optimistic edits with rollback (a visible flip-back is worse than a short wait on a deliberate edit).
- ✅ **D6 — No client pre-check for the last-set dialog; always ask the server.** *Rationale:* 07.4 §3 allows a pre-check from the cached detail (total sets = 1). The cache can be stale, and a false positive offers to delete a workout the lifter thinks has one set but has two. The server answer is authoritative and costs one round trip in a rare case; offline it fails with the offline text, which is also correct. *Rejected:* pre-check (saves a round trip, risks the one destructive mistake on this screen).
- ✅ **D7 — Add set is a sheet (the existing `SetEditSheet` in add mode), not the inline entry row (owner-confirmed, O3).** *Rationale:* edit mode has no current exercise and no bottom Log bar (brief §5), so the inline `EntryRow` would have to appear on every expanded card at once, six forms on a six-exercise workout. A sheet reuses the exact fields and failure handling of the edit sheet, keeps the failure next to the control, closes only on success (pessimistic by construction), and needs no `logAction` / draft / rest machinery. The sets are still added with the same fields the lifter knows.
- ✅ **D8 — The live Change Time control sits on the header's started line, outside the Workout menu (mine).** *Rationale:* the owner's mockup puts it inline, and the forgotten-workout flow starts with it; the 17.1 D13 rule ("rare actions in the menu") is for actions away from the thumb that the lifter rarely needs, while this one is the first tap of a deliberate flow. It is one `secondary` button on a line that already exists, so live logging gains no row and no new primary action.
- ✅ **D9 — A failed op of a no-longer-active workout is reported and removed, not shown (mine).** *Rationale:* reaching it needs two devices, a Finish race and a client-validated request that the server then refuses. A surface (a notice on the Start screen with a Discard) is more UI than the risk earns, `set_sync_failed` telemetry will show if it happens, and the lifter's remedy (Edit workout → Add set) exists. *Accepted residual risk.*
- ✅ **D10 — Change Time works in the device's zone; only changed groups are sent (mine).** *Rationale:* the live screen already shows the device-zone start; a form in two zones would confuse. ### Resolved by reading the code

- **No workout title / notes UI existed anywhere** (so O1 needed a decision, now made). **The queued client already falls through to REST** for a workout that is not the cached active one, which is why live code "works" on a finished workout today; D5 makes it a rule. **The drafts store holds one workout** (`{ v:1, userId, workoutId, byExercise }`), so an edit session using it would overwrite the live workout's drafts; edit mode uses no draft persistence (AC21). **`retainOnly(null)` on the `/active` `404`** dropped every unsent op (§6.4 item 2, D4). **`formatStartedTime` uses the device zone**, which fixes D10. **TanStack infinite queries refetch all loaded pages in order**; that is why History is *reset*, not invalidated, after a re-time.
- **Route collision.** `workouts/:id/edit` could in principle match `workouts/routines/edit`; routine ids are UUIDs and `routines/edit` is not a route today, so there is no live collision; AC2 pins that the routine routes still resolve.
