## 1. Purpose, scope & non-goals

Close the small defects, test gaps and doc drift Spec 06.1's final review left behind, in one session, before Spec 06.2 builds on them. Nothing here adds a feature: every item is a robustness fix (ACs 1, 4, 5, 7), a polish fix (2, 3, 6, 8, 11), a missing test (9, 10, 12–15) or a doc correction (16–19). No API change, no migration, no new env var, no new storage key.

> **First-principles note (why the "parent re-render" item, AC1, is real).** A TanStack query's cached entry is held by the cache, but each component using it holds an *observer* pointing at that entry. `removeQueries` deletes the entry; the observer keeps its pointer until its component next renders, and then it looks the key up again, finds nothing, builds a fresh entry in the `pending` state and starts a fetch. So "remove the cache entry, then navigate" is only safe if the component that watches the entry does not render between the two statements. React Router wraps navigation in a transition, so navigation is *not* synchronous; anything that re-renders the parent in that gap (a focus event, any state change) shows a spinner and unmounts the session. The fix is to stop depending on the gap.

### Phase A — session screen

1. **Finish success does not depend on the parent's render timing.** After `PATCH` finish succeeds and before navigation completes, a re-render of `WorkoutsScreen` neither shows the `<Spinner>` nor the Start screen, and issues no `GET /v1/workouts/active` (the session stays on screen until the route changes). Once `FinishedWorkoutScreen` has mounted for workout `id`, the `["workouts","active"]` entry no longer holds a workout with that `id`, so revisiting `/app/workouts` shows the Start screen without flashing the finished workout. If the cached active workout has a *different* id (06.1 AC30's history-detail reuse, Spec 08), `FinishedWorkoutScreen` leaves it alone. The same holds on the `409 workout-finished` ⇒ success path (06.1 AC28).
2. **The start time never prints hour 24.** `formatStartedTime(iso, { timeZone? })` (new, `format.ts`) uses `Intl.DateTimeFormat("en", { hour: "2-digit", minute: "2-digit", hourCycle: "h23" })`: `00:05` for 00:05, `12:05`, `23:59`; never `24:05`. `ActiveSession` uses it; no module under `src/features/workouts/` mentions `hour12`.
3. **Scroll-into-view uses a ref, not the document.** When Finish is blocked by `409 incomplete-working-sets` (06.1 AC27), `scrollIntoView` is called on the first flagged row in display order (exercise `position`, then `setNumber`) — exactly once per diagnosis, on that element only — via a React ref. No non-test module under `src/features/workouts/` calls `document.querySelector` / `querySelectorAll` / `getElementById`.
4. **Enter in an invalid, untouched entry row shows what is wrong.** With an untouched empty `weight_reps` row, pressing Enter in the Weight input sends no request, reveals the "Enter a number"-style message for every invalid visible field (the same static messages touched fields already get; `role="alert"` via `Field`), and leaves the draft, attempt key and `touched` semantics for later edits unchanged. Enter in a *valid* row still logs exactly one set (06.1 AC23 unchanged); the Log button stays `disabled` while the draft is invalid (06.1 AC23 unchanged).
5. **Every id interpolated into a request path is encoded.** For all nine id-bearing `WorkoutClient` operations (`getById`, `finish`, `deleteWorkout`, `addExercise`, `moveExercise`, `removeExercise`, `createSet`, `updateSet`, `deleteSet`), an id such as `a/b?c#d` yields the path segment `a%2Fb%3Fc%23d`; a lower-case GUID is unchanged (so 06.1 AC1's table still passes verbatim).
6. **No branch handles an action its operation cannot produce.** `SetEditSheet`'s failure handler has no `ok` branch, and `ActiveSession.handleFailure` has no `ok` case: `remove-exercise` / `delete-set` already convert `404` to success inside the mutation (`ignoreNotFound`), so those callers never see it. 06.1 AC20 / AC25's "404 counts as success" tests still pass unchanged.
7. **An add-exercise `404` costs one `GET /v1/workouts/active`, not two.** Both outcomes (workout gone → Start screen with the gone notice; exercise unavailable → "That exercise isn't available" + `catalog.refresh(true)`) issue exactly one `GET /active`.
8. **The carried-over one-line notices can be dismissed.** The "resumed" notice (`RESUMED_NOTICE`), the "out of date, reloaded" notice (`STALE_NOTICE`) and the gone notice render a "Dismiss" button (`InlineNotice` gains optional `onDismiss`). Tapping it hides the notice and it stays hidden after a banner appears and clears (today `banner ?? notice` brings it back), after a refetch, and after a re-render; a *new* notice later (a second gone event) shows again. The state-derived `REFRESH_FAILED_NOTICE` has no Dismiss (it clears when a refetch succeeds). Errors and warnings with a retry action keep their "Try again" only.
9. **A diagnosis interrupted by the next set write is corrected by retrying Finish.** With a `409 incomplete-working-sets` whose `GET /active` is held in flight, a set logged meanwhile (which cancels that read) leaves the screen showing its pre-refetch copy and a banner computed from it; once the 06.1 I1 re-read lands the set list is the server's; tapping Finish again and getting the `409` again re-diagnoses from fresh data and marks the server's incomplete set(s). No flagged row is ever one the current cache holds as complete. (Test only — no mechanism change, §12 D3.)
10. **A set write answering `404` while the workout still exists.** *Update set:* the sheet closes, exactly one `GET /active` runs, the set list is the server's, the notice reads "Your workout was out of date, so it has been reloaded." (never "already finished or removed"), and `workout_conflict { kind: "gone" }` is tracked once. *Delete set:* the sheet closes, the row is removed from the cache, no notice, no `GET /active`, and `set_deleted` is tracked (06.1 AC25's "404 counts as success", now asserted against a workout that is still active).
11. **No stale review-note references.** The comment on `SET_MUTATION_KEY` in `useWorkoutMutations.ts` states the behavior it supports ("Finish stays disabled while any set write is in flight") instead of "(Review Focus #4)"; no non-test source under `apps/web/src/` contains the text `Review Focus`.

## 6. Behavior & logic

### 6.1 Finish success without the render-timing assumption (AC1)

Today `useFinishWorkout.onSuccess` calls `removeQueries(active)` and `setQueryData(detail(id))`; the `navigate` runs later at the call site. Between them the parent's observer points at a deleted entry (see the §1 note).

Chosen mechanism (§12 D1): the hook-level `onSuccess` **only seeds** `["workouts","detail",id]` (and tracks `workout_finished`); `confirmAlreadyFinished` does the same. `FinishedWorkoutScreen` runs, in an effect keyed on `id`, `if (queryClient.getQueryData(active)?.id === id) queryClient.removeQueries({ queryKey: active })`. At that point the Workouts screen has unmounted (different route element), so no observer can resurrect the entry. The id guard keeps Spec 08's history-detail reuse from clearing an unrelated active workout. If the lifter left the Workouts tab before the response arrived, the stale active entry survives until they return; `refetchOnMount: "always"` (06.1 §6.2) replaces it, and the finished workout is shown for one round trip at worst, then the next write or refetch resolves it through the existing `409 workout-finished` path. Accepted.

Test technique: mock `useNavigate` to a no-op so navigation never happens, finish through the UI, `rerender` the tree, and assert no spinner and an unchanged `GET /active` count (this fails against today's code); then render `FinishedWorkoutScreen` with a seeded active entry (same id → removed; other id → kept).

### 6.2 Smaller mechanisms

- **AC2.** Extract `formatStartedTime` into `format.ts`; the optional `timeZone` exists so the test is machine-independent (`timeZone: "UTC"`). Node's ICU prints `24:05` for `hour12:false` at 00:05; `hourCycle: "h23"` does not.
- **AC3.** `ActiveSession` holds `firstFlaggedRef`; `ExerciseCard` accepts `firstFlaggedId` and an `onFirstFlaggedRef` callback ref it attaches to the matching row button. The effect keyed on `flaggedIds` calls `firstFlaggedRef.current?.scrollIntoView?.({ block: "center" })` (the `?.` guard stays for jsdom). "First" = first in render order, which is `position` order then set order, so the ref is assigned by the first card containing a flagged id. `hygiene.test.ts` gains the `document.` scan.
- **AC4.** An HTML form whose default submit button is `disabled` does not fire `submit` on Enter — so today's `log()` early-return is never reached; the browser swallows the key. Chosen mechanism (§12 D2): `EntryRow`'s `<form>` gets an `onKeyDown` that, for Enter on an `<input>` (not a select or button) while `!parsed.ok`, calls `preventDefault()` and adds every field in `parsed.errors` to `touched`, so `clientErrors` renders. The Log button stays `disabled` (AC23 of 06.1 unchanged). Not in scope: the edit sheet (it already shows every error, untouched or not — 06.1 §5.5 / `SetEditSheet`).
- **AC5.** A one-line `seg = encodeURIComponent` in `workoutClient.ts`, applied to every interpolated id. GUIDs pass through unchanged; `getById`'s id comes from `useParams`, i.e. from the URL bar, which is why that one mattered most. (BL-10: a malformed percent-encoded URL is the *server's* problem and stays there.)
- **AC6.** Delete the dead branches; do not delete `{ type: "ok" }` from `FailureAction` — `sessionErrors.test.ts` pins the matrix row "404 ⇒ treated as success", which is still the documented behavior (06.1 §5.8) even though the hook now applies it.
- **AC7.** In `handleFailure`'s `unavailable` case the refetch has already happened; calling `onGone` re-invalidated. `gone(reason, { refetched })` forwards the flag; `WorkoutsScreen.markGone(workoutId, refetched)` skips `invalidateQueries` when true (it still records `goneId`, so the notice is derived from the data the first refetch produced).
- **AC8.** `WorkoutsScreen` owns `notice` and `goneId`; a dismiss handler clears both and is passed to `StartWorkout` and `ActiveSession`. `ActiveSession`'s `shown = banner ?? notice` is unchanged: once the state is cleared there is nothing to come back. `InlineNotice` renders Dismiss only when `onDismiss` is given (a `Button variant="secondary"`, tap-target class like every control, 06.1 AC33).
- **AC10–AC11.** Tests and a comment only; no mechanism change.

### 6.3 Interrupted diagnosis (AC9) — why no mechanism

`diagnoseIncomplete` awaits `invalidateQueries`, then reads the cache. A set write started meanwhile calls `cancelQueries` (06.1 AC11), which cancels that read; TanStack swallows the cancellation, the `await` resolves, and the cache still holds the pre-refetch copy plus the new set. The I1 fix then re-reads after the set write. So the flags come from a copy that is *stale but never wrong about what is on screen*: `flagged` is already intersected with the live cache (06.1 `ActiveSession`'s `useMemo`), so a flag can disappear but cannot sit on a complete row. The harm is a missed flag, or the fallback "Some sets are incomplete — reload and check your sets", and only when another client wrote an incomplete working set in the same few hundred milliseconds (this UI only creates complete sets, 06.1 §5.6). Retrying Finish re-runs the diagnosis. That is enough; AC9 pins it (§12 D3).

## 12. Decisions & open questions

### Resolved (drafting-time; reversible at review)

- ✅ **D1 — Finish: seed the detail in the hook; remove the active entry from the destination screen.** (AC1.) **Rationale:** the defect is a dependency on the parent not re-rendering between two statements; moving the removal to a place where no observer exists removes the dependency instead of narrowing the window. **Alternatives rejected:** *navigate first, then `removeQueries`* — navigation is a transition, so the observer can still render in the gap; *`setQueryData(active, null)`* — safe against the spinner/fetch, but flashes the Start screen for a frame before the summary and still needs a guard for unmount-before-response. **Consequence:** `FinishedWorkoutScreen` knows about the active cache key (guarded by id); 06.2's queue seeds the detail the same way.
- ✅ **D2 — Enter in an invalid row is handled by a key handler, not by un-disabling the button.** (AC4.) **Rationale:** the browser blocks implicit submission when the default button is disabled, so a `submit` handler can never run; keeping the button disabled preserves 06.1 AC23 and its tests, and `aria-disabled` would change the semantics for assistive tech and the existing "disabled until valid" criterion. **Consequence:** one `onKeyDown` in `EntryRow`; the edit sheet is unchanged (it already shows all errors).
- ✅ **D3 — An interrupted `diagnoseIncomplete` needs a test, not a mechanism.** (AC9, §6.3.) **Rationale:** flags are intersected with the live cache, so the failure mode is a missed flag or the fallback message, requires another client's write in a sub-second window, and is corrected by the lifter's next tap on Finish. A re-diagnose-after-set-write mechanism would couple the finish flow to the set-write hooks for a case the server's retry already covers. **Revisit if** 06.2's partial-set logging makes incomplete sets common.
- ✅ **D4 — AC5 covers all nine id-bearing operations, not only `getById`.** The review item named `getById`, but every operation interpolates an id raw; only `getById`'s id comes from the URL bar. **Rationale:** "consistent" means all of them; the change is one helper and GUID paths are byte-identical, so nothing else moves.
