## 1. Purpose, scope & non-goals

Ship the client-side exercise catalog: a React-free store that syncs
`GET /v1/exercises` into `localStorage`, a picker sheet built on top of it, and
a create-custom form. This is the first real consumer of Spec 03.3's sync-token
contract — the picker is what DESIGN §5.2's "client pulls the whole
caller-visible set once and reconciles incrementally" design was written for.

> **First-principles note (why a store, not just a `useQuery`):** TanStack
> Query (already in the app for `useMe`) caches a *server response* keyed by
> a query key, for as long as the app is open. The exercise catalog needs more
> than that: it must survive a page reload without re-pulling hundreds of rows
> every time, it must merge an incremental delta into what's already stored
> (a `useQuery` cache entry is replaced wholesale, not merged), and it must be
> erasable on logout. That's *application* state with its own update rules,
> not a cached request — so it gets a dedicated store (`catalogStore.ts`) that
> owns a `localStorage` mirror, with a thin `useCatalog()` hook wrapping it
> for React (via `useSyncExternalStore`, the hook React ships specifically for
> "some non-React object is the source of truth, re-render me when it changes").
> Contrast with `useMe`: `GET /v1/me` is small, per-user, and has no local
> merge logic — a plain `useQuery` is the right tool there and stays that way.

### In scope

- **`src/api/client.ts` extension** — `ApiRequestOptions` gains an optional
  `cache` (a `RequestCache` value) that is passed to the underlying `fetch`.
  That is the only client change: catalog sync uses the existing throwing
  `request()` and branches on the thrown `ApiError`'s status.
- **`src/storage/`** — `StorageAdapter` + a `localStorage` implementation + an
  in-memory one, and `clearUserData()` (removes every user-scoped key).
- **`src/auth/logout.ts`** — `logoutAndClear()`, the single logout path every
  caller uses, so user data is cleared however the session ends.
- **`src/ui/Sheet.tsx`** — a modal sheet primitive on the native `<dialog>`.
- **`src/features/catalog/`** — `catalogSync.ts` (pure), `visibility.ts`
  (pure), `catalogStore.ts` (the React-free store), `CatalogProvider.tsx`,
  `useCatalog.ts`, `referenceData.ts`, `ExercisePicker.tsx`,
  `CreateExerciseForm.tsx`.
- **The picker UI**: search, recents, an A–Z list, muscle/equipment filters, a
  "create custom" affordance, and the loading/empty/error states for all of
  the above.
- **Create-custom only.** `POST /v1/exercises` (Spec 03.2) with the modality
  choice up front and everything else folded under "More details".
- **Forked-origin hiding** (DESIGN §4.2, Spec 03.2 D9) — the client-side rule
  that suppresses a global row from the picker when a visible custom row's
  `forkedFromExerciseId` points at it. This is the one piece of "my custom
  exercises" management this spec touches.
- **Observability**: `exercise_picked`, `custom_exercise_created`,
  `catalog_reset` events via the existing `track()`/`reportError()` seams.

### Non-goals

- **Mounting anything.** No route, no nav-item flip, no "Add exercise" button,
  and `<CatalogProvider>` is not placed in the component tree — `Workouts`
  stays `comingSoon` in `navItems.ts`. Spec 06.1 mounts the provider and
  `<ExercisePicker>` and owns the M1 happy-path Playwright smoke (moved there
  from where DESIGN §8.3 originally placed it, since there is nothing to
  drive end-to-end until a workout screen exists). The one user-reachable
  change in this spec is that logout now also clears user-scoped
  `localStorage` keys (of which none exist until 06.1).
- **`ETag` / `If-None-Match` on the exercise sync.** Dropped in v0.2 (§12):
  the sync token already makes an unchanged catalog a tiny response, the
  server's `ETag` is namespaced by the `since` value so it almost never
  matches once the token advances, and reading or sending those headers
  cross-origin would need an API CORS change.
- **Edit, fork, and delete of a custom exercise** — a future "my exercises"
  management screen. This spec's create form is one-way: name it, save it,
  it's picked. `PATCH`/`POST .../fork`/`DELETE /v1/exercises/{id}` (Spec 03.2)
  are not called anywhere in this spec.
- **The workout session screen, set rows, add/reorder/remove-exercise UI,
  finish, delete-workout** — Spec 06.1.
- **Offline write queue, unsynced-state UI, retry/backoff, the localStorage
  mirror of an *in-progress workout*** — Spec 06.2. (This spec's own
  `localStorage` mirror is of the *catalog*, a read-mostly reference dataset;
  06.2's is of a live, in-progress write — different data, different risk,
  deliberately kept separate.) 06.1's writes go through one small seam
  (§3, §6) specifically so 06.2 can insert a queue there without reworking
  06.1.
- **List virtualization.** The list renders every visible row (a few hundred
  curated rows plus at most 500 custom ones). Revisit only if a real device
  shows scroll or open-time jank (§12).

## 2. Acceptance criteria

Behavioral criteria (AC1–AC29) each get ≥1 Vitest/RTL test naming their number
(`describe("AC7 — …")`). AC30–AC31 are CI criteria — see §10. AC32 is the
coverage-of-criteria check. AC1–AC23 are **phase A** (data layer); AC24–AC29
are **phase B** (UI) — see §6.1.

### Phase A — data layer

1. **The API client accepts a `cache` option.** `ApiRequestOptions` gains
   `cache?: RequestCache`. When set, the value reaches the underlying `fetch`
   on the first attempt **and** on the 401-refresh retry; when omitted, `fetch`
   is called exactly as before. `get`/`post`/`patch`/`delete` keep their
   signatures and behavior. `src/api`'s ≥90% line-coverage gate still passes.
2. **`mergeCatalogRows` merges a delta by `id`.** Given stored rows and
   incoming rows, the result contains every stored row not present in the
   incoming set, overlaid by every incoming row; any incoming row with
   `isActive: false` is removed from the result entirely (not kept as a
   tombstone — the client only needs to know a row is gone). Neither input
   array is mutated.
3. **`classifySyncFailure` maps a thrown value to an outcome.** An `ApiError`
   with status `410` → `{ kind: "reset", reason: "410" }`; status `422` →
   `{ kind: "reset", reason: "422" }`; anything else (a network `ApiError`,
   `5xx`, `401`, any other status, a non-`ApiError` value) →
   `{ kind: "transient" }`. It never throws.
4. **`visibleRows` hides retired rows.** Any row with `isActive: false` is
   excluded.
5. **`visibleRows` hides forked origins.** Given a global row `G` and an
   active custom row `C` with `C.forkedFromExerciseId === G.id`, `G` is
   excluded and `C` remains. A global row with no active fork pointing at it
   remains. A *retired* fork does not hide its origin.
6. **`sortByName` sorts A–Z, accent- and case-insensitive.** Order follows
   `new Intl.Collator("en", { sensitivity: "base" })` (`"É"` sorts adjacent to
   `"E"`; `"a"` and `"A"` interleave by name, not by case). The locale is
   pinned so the order does not depend on the device or CI machine.
7. **`searchByName` is a substring match on folded names.** Both the query and
   each `name` are folded with
   `s.normalize("NFD").replace(/\p{M}/gu, "").toLowerCase()` and the query is
   trimmed; a row matches when its folded name contains the folded query
   (`"cafe"` matches a row named `"Café Curl"` — a fabricated example name).
   An empty or whitespace-only query returns every row.
8. **`filterByAttributes` filters by muscle and equipment.** A muscle filter
   matches a row whose `primaryMuscleId` **or** any `secondaryMuscleIds` entry
   equals the value; an equipment filter matches `equipmentId` exactly. Both
   may be active at once (AND); each is independently clearable (`null`).
9. **Storage keys are versioned and per-user.** The catalog persists under
   `sin:catalog:v1:<userId>`; recents persist under `sin:recents:v1:<userId>`.
   Two stores built for different `userId`s over the same `StorageAdapter`
   never read each other's data.
10. **Stored data is schema-validated on load; anything invalid is
    discarded.** On construction the catalog value is checked against the
    versioned envelope (`{ version: 1, rows, syncToken }`) with the core
    `ExerciseSchema` for every row. A wrong `version`, a row that fails
    `ExerciseSchema`, or unparsable JSON removes the key, starts the store
    empty with `syncToken: null` (so the next refresh is a full pull), and
    tracks `catalog_reset { reason: "corrupt" }` once. A *missing* key is the
    normal first-run case: start empty, no event. An invalid recents value is
    discarded to an empty list with no event. No exception escapes.
11. **A `StorageAdapter` failure degrades to in-memory operation, once.** If
    `get`/`set`/`remove`/`keys` throws (private-browsing quota, disabled
    storage), the store keeps working from in-memory state for the rest of
    that session, calls `reportError()` **exactly once** for that store
    instance (tagged `{ source: "catalog-storage" }`), and never throws to a
    caller.
12. **Cold start reads storage before touching the network.** After
    construction, `getState()` reflects the validated stored rows, sync token
    and recents with **no** network call; a network call happens only when
    `refresh()` is invoked.
13. **Constructing a store sweeps every other user-data key.** Construction
    removes every `sin:catalog:*` / `sin:recents:*` key other than this
    store's own two keys — another user's data left behind by a logout path
    that could not run, or an orphaned older-version key.
14. **`refresh()` is a no-op when the store was refreshed recently.** Calling
    `refresh()` within `CATALOG_REFRESH_STALE_MS` (§8) of the last
    *successful* refresh issues no request; calling it after the window
    elapses, or after a failed refresh, does. `lastRefreshAt` is in-memory
    only, so the first `refresh()` after a page load always issues a request.
15. **A sync request carries the token and bypasses the HTTP cache.** A
    refresh calls `GET /v1/exercises?since=<syncToken>` (URL-encoded; the
    query is omitted when `syncToken` is `null`) with `cache: "no-store"`
    unconditionally and no conditional request headers. The browser's HTTP
    cache is therefore never a participant in catalog sync, so the
    revalidate-into-a-stale-body loop Spec 03.3 §3 warns about **cannot occur
    by construction**.
16. **Concurrent refreshes share one request; a forced one queues one
    follow-up.** Two `refresh()` calls issued before the first resolves
    produce exactly one request and settle together. `refresh(true)` skips
    AC14's staleness rule; issued while a request is in flight, it schedules
    **exactly one** follow-up request that starts after the in-flight one
    settles (any number of forced calls in that window coalesce into the one
    follow-up), and its promise settles when the follow-up does. The promise
    `refresh()` returns never rejects — failures land in `status`.
17. **A delta merges; a full pull replaces.** A `200` to a request that sent
    `since` is merged into the stored rows (AC2). A `200` to a request with no
    `since` **replaces** the stored rows with its active rows. In both cases
    `syncToken` becomes the response's value verbatim, `status` becomes
    `"idle"`, `lastRefreshAt` is set, and the state is persisted.
18. **A `410`/`422` reset does exactly one full pull and keeps the old rows
    until it lands.** On a `reset` outcome (AC3) the store tracks
    `catalog_reset { reason }` once and issues exactly one request with no
    `since`. The previously stored rows stay in `getState()` until that pull
    succeeds, then are replaced (AC17). If the pull fails, the rows are kept,
    `syncToken` is set to `null` and persisted (so the next refresh is a plain
    full pull, not another reset), `status` becomes `"error"`, and no further
    request is made for that `refresh()` call — a server that keeps failing
    cannot loop the client. Recents are untouched by a reset.
19. **A transient failure keeps the cached state.** On a `transient` outcome
    (AC3 — network failure, `5xx`, a `401` that survived the client's
    refresh-and-retry, any other status) `rows`, `recentIds` and `syncToken`
    are unchanged, `status` becomes `"error"`, and `reportError()` is **not**
    called (an outage is expected, not exceptional). A `200` whose body fails
    `ExercisesResponse` validation is handled the same way, except that
    `reportError()` **is** called (tagged `{ source: "catalog-sync-schema" }`).
    This spec adds no auth handling: `onAuthLost()` has already fired inside
    the client (Spec 04.0 §6.4).
20. **Every logout path clears user data first.** `clearUserData(storage)`
    removes every key starting with `sin:catalog:` or `sin:recents:` — not
    just the current user's — leaves every other key untouched, and never
    throws (a failing storage is swallowed). `logoutAndClear(auth0Logout)`
    calls it and then calls Auth0's `logout` with
    `returnTo: window.location.origin`; Auth0's `logout` is still called when
    clearing fails. All three logout sites — `useSession().logout`, the API
    client's `onAuthLost` (`useApi`), and `<AccountDeleted>` — go through
    `logoutAndClear`.
21. **Recents are capped at 10, most-recent-first, and filtered live.**
    `recordPick(id)` prepends the id to `recentIds`, dedupes (an
    already-present id moves to the front), truncates to `MAX_RECENTS`, and
    persists. `pickRecents(visible, recentIds)` returns the matching rows in
    `recentIds` order, drawn only from the *visible* set, so a since-retired
    or forked-origin id drops out of the derived list without a cleanup step.
22. **`useCatalog()` reflects the store, including picks.** `getState()`
    returns the same object reference until something changes, and a new one
    after every change to rows, recents, sync token or status — so a component
    using `useCatalog()` re-renders after `recordPick` as well as after a
    refresh. Mounting the hook calls `refresh()` (staleness-gated, AC14).
    `<CatalogProvider userId>` creates one store per `userId` and reuses it
    across re-renders; `useCatalog()` outside a provider throws an error that
    names the provider.
23. **Creating a custom exercise inserts locally and re-syncs.** A successful
    `POST /v1/exercises` (response parsed with `ExerciseSchema`) inserts the
    returned row into the store immediately, records it as a pick, tracks
    `custom_exercise_created`, persists, and calls `refresh(true)` without
    awaiting it. A failed `POST` rejects with the client's `ApiError` and
    changes no state.

### Phase B — UI

24. **`<Sheet>` is a modal dialog.** `<Sheet open title onClose>` renders a
    native `<dialog>` opened with `showModal()` while `open` is true and
    closed otherwise; it is labelled by its title (`aria-labelledby`); the
    close button (accessible name "Close") and the dialog's `cancel` event
    (Escape, Android back) both call `onClose` and do not close the dialog on
    their own — the parent owns `open`.
25. **Picker layout.** Recents render above the A–Z list and are hidden
    entirely while a search or a filter is active. The search input is not
    focused on open. Each row shows the name, a second line (modality label,
    plus the equipment name when known), a "Custom" tag when `ownerUserId` is
    non-null, and carries the `--tap-target-min`-driven class. The muscle and
    equipment filters list the reference data in `displayOrder`, each with an
    "All …" option that clears it; if reference data fails to load, the
    filters are not rendered and the list still works. A create row is always
    the last item: `Can't find it? Create "<search text>"`, or "Create a
    custom exercise" when the search is empty.
26. **Picker states.** No rows and a refresh in flight → `<Spinner/>`. No rows
    and `status: "error"` → "Couldn't load exercises" + a Retry button that
    calls `refresh(true)`. Rows present and `status: "error"` → the list
    renders with no error text. Search/filter matching zero rows → "No
    exercises match" plus the create row.
27. **Picking.** Tapping a row calls `recordPick(exercise.id)`, tracks
    `exercise_picked { source, msSinceOpen }`, then calls `onPick` with the
    full `Exercise`. `source` is `"recent"` for a recents row, `"search"` for
    a list row while a search or filter is active, otherwise `"list"`. The
    picker does not close itself.
28. **Create form layout.** Opening it from the create row swaps the sheet's
    content to the form (title "Create exercise") with `name` prefilled from
    the search text. It offers the five modality options up front as a radio
    group, with primary muscle, secondary muscles and equipment under a
    collapsed "More details". Save is disabled until the trimmed name is
    non-empty and a modality is chosen. Cancel returns to the list with the
    search text intact.
29. **Create outcomes.** `201` → the new exercise is picked exactly as in
    AC27 (`onPick` fires with it; it is in recents) and the sheet returns to
    the list view. `409 exercise-limit-reached` → a plain form-level message,
    no field marked. `422` → per-field messages under the matching input, the
    Spec 04.1 AC7 pattern (`errors[].path` → field; an unmatched path → a
    form-level message). Any other failure → a form-level "Couldn't save.
    Try again." In every failure case the form stays open with its input
    intact and Save re-enabled.

### Infra

30. **`assert:css-tokens` stays green.** Every new `*.module.css` file
    references design values only via `var(--…)` (Spec 04.1 AC1's check).
31. **Coverage gate.** `vitest.config.ts` adds `≥90%` line thresholds for
    `src/features/catalog/**` and `src/storage/**`, alongside the existing
    `src/api/**` / `src/auth/**` gates.
32. Each of AC1–AC29 has ≥1 committed test tagged with its number; AC30–AC31

**Consumers must note:**

- **06.1's catalog writes go through `useCatalog().createCustom` /
  `recordPick`, not a direct `api.post` call**, so 06.2 can insert a write
  queue inside those two functions without 06.1 changing its call sites.
- `CatalogState` is `{ rows: Exercise[], recentIds: string[], syncToken:
  string | null, status: "idle" | "loading" | "error", lastRefreshAt: number |
  null }`. `rows` is the raw stored set (it can include forked origins) —
  render from `useCatalog().visible`, not from `state.rows`. Adding a field
  is additive; removing or renaming one is breaking.
- The picker never calls `PATCH`/`fork`/`DELETE` (§1 non-goals) — a future
  "my exercises" spec adding those must not assume this store already
  handles optimistic edit/delete; it doesn't.
- Anything new that writes user-scoped data to `localStorage` must use a
  `sin:<name>:` prefix and add it to `USER_DATA_KEY_PREFIXES`.

## 4. Data model

No server-side tables or migrations — this is client-only persisted state.

### `localStorage` schema

```ts
// Key: `sin:catalog:v1:<userId>`
interface StoredCatalogEnvelope {
  version: 1;
  rows: Exercise[];       // validated against @sin/core ExerciseSchema per row (AC10)
  syncToken: string | null;
}

// Key: `sin:recents:v1:<userId>`
interface StoredRecentsEnvelope {
  version: 1;
  ids: string[];          // ExerciseId, most-recent-first, length <= 10
}
```

- **Versioned key, not a versioned-envelope migration.** Bumping the schema
  bumps `v1` → `v2` in the key name; there is no in-place migration. An old
  key is removed by AC13's sweep the next time a store is constructed (it's
  a cache, rebuilt from the network).
- **No tokens, no workout data, ever written here.** Only exercise rows, ids
  and the sync token. Auth tokens stay in memory only (Spec 04.0 §7, Q12) —
  this storage layer is a distinct, lower-stakes surface and must never be
  reused for anything credential-bearing.
- **In-memory-only fallback** (AC11): the public `CatalogState` does not
  distinguish "backed by storage" from "in-memory this session" — a consumer
  doesn't need to know.

## 5. Screens & flows

*(UI spec — replaces "API surface". The API surface consumed is Spec 03.3 §5
(`GET /v1/exercises`) and Spec 03.2 §5 (`POST /v1/exercises`), both unchanged
by this spec.)*

### `<Sheet open title onClose>`

> **First-principles note (why the native `<dialog>`):** a modal has to trap
> keyboard focus inside itself, make the page behind it inert, close on
> Escape, and return focus to whatever opened it. The browser's `<dialog>`
> element does all of that when opened with `showModal()`, with no library.
> The catch is that jsdom (the fake DOM the unit tests run in) does not
> implement `showModal()`/`close()`, so `src/test/setup.ts` gains a small
> shim that toggles the `open` attribute; the real focus/Escape behavior is
> exercised by 06.1's Playwright smoke.

A full-height sheet with the title and a close button in the header. The
close button comes first in DOM order, so `showModal()`'s automatic focus
lands on it rather than on the search field (AC25). The parent owns `open`;
the `cancel` event is `preventDefault()`ed and forwarded to `onClose` (AC24).

### `<ExercisePicker open onPick onClose />`

Actions placed in the thumb zone (DESIGN §1.2).

```
┌─────────────────────────────────┐
│  Add exercise                [x]│  ← Sheet header
├─────────────────────────────────┤
│  [ Search exercises...        ] │  ← not autofocused
│  [ All muscles ▾ ] [ All equipment ▾ ]
├─────────────────────────────────┤
│  Recent                         │  ← hidden while searching/filtering
│   • Barbell Back Squat          │
│   • Romanian Deadlift           │
├─────────────────────────────────┤
│  All exercises                  │
│   • Arnold Press          Custom│
│   • Barbell Back Squat          │
│   • Bench Press                 │
│   …                              │
│   Can't find it? Create "curl"  │  ← always present, prefilled from search
└─────────────────────────────────┘
```

- **Search field**: filters the A–Z list per `searchByName` (AC7). **Not
  auto-focused** on open — a phone keyboard popping up before the user has
  looked at recents is the wrong default (recents-first is the point).
- **Filters**: two native `<select>` elements styled as chips — muscle and
  equipment — populated from `useMuscleGroups()` / `useEquipment()` in
  `displayOrder`, each with an "All …" first option that clears it. A native
  select gives a phone its own full-screen option picker for free and keeps
  "at most one value per category" true by construction.
- **Recent**: up to 10 rows from `useCatalog().recents`, hidden entirely
  (not just emptied) whenever the search field is non-empty or a filter is
  set.
- **All exercises**: `useCatalog().visible` (already `visibleRows` +
  `sortByName`), then `searchByName` + `filterByAttributes`. Each row: name,
  a second line with the modality label and equipment name (e.g. "Weight ×
  reps · Barbell"; the equipment part is omitted when the row has none or
  reference data is unavailable), a "Custom" tag when `ownerUserId` is set,
  and a ≥44px tap target (`--tap-target-min`).
- **Create row**: always the last item (AC25). Tapping it swaps the sheet to
  `<CreateExerciseForm>` with `name` prefilled from the search text.
- **States** (AC26), decided from `state.rows.length` and `state.status`:
  - no rows, `loading` → `<Spinner/>`;
  - no rows, `error` → "Couldn't load exercises" + Retry (`refresh(true)`);
  - rows present → the list, whatever `status` is (a failed background
    refresh is silent);
  - search/filter matches nothing → "No exercises match" + the create row.
- **`onPick(exercise)`** — called with the full `Exercise` object after
  `recordPick` and the `exercise_picked` event (AC27). The picker does not
  close itself: 06.1 may want to do something with the selection (append it
  to the session) before dismissing via `open`.

### 6.2 API client

`ApiRequestOptions` gains `readonly cache?: RequestCache`; `fetchOnce` adds it
to the `fetch` init only when defined. Nothing else in the client changes —
in particular there is no non-throwing variant: the store calls
`api.request(path, { cache: "no-store" })` and classifies what it throws.

### 6.3 `catalogSync.ts`

```ts
export function mergeCatalogRows(stored: readonly Exercise[], incoming: readonly Exercise[]): Exercise[] {
  const byId = new Map(stored.map((r) => [r.id, r]));
  for (const row of incoming) {
    if (row.isActive) byId.set(row.id, row);
    else byId.delete(row.id);
  }
  return [...byId.values()];
}

export type SyncFailure =
  | { kind: "reset"; reason: "410" | "422" }
  | { kind: "transient" };

export function classifySyncFailure(error: unknown): SyncFailure { /* AC3 */ }
```

A full pull's "replace" is `mergeCatalogRows([], incoming)` — the same
function, starting from nothing.

### 6.4 `visibility.ts`

```ts
export function visibleRows(rows: readonly Exercise[]): Exercise[];   // active, minus forked origins
export function sortByName(rows: readonly Exercise[]): Exercise[];    // Intl.Collator("en", { sensitivity: "base" })
export function searchByName(rows: readonly Exercise[], query: string): Exercise[];
export function filterByAttributes(rows: readonly Exercise[], f: { muscleId: string | null; equipmentId: string | null }): Exercise[];
export function pickRecents(visible: readonly Exercise[], recentIds: readonly string[]): Exercise[];
```

`visibleRows` is the single choke point for both hiding rules, and it must
see the **whole** row set: "is this row someone's fork origin" depends on
every other row's `forkedFromExerciseId`. That is why recents are derived
with `pickRecents(visible, recentIds)` — a lookup into the already-visible
set that preserves `recentIds` order — and never by running `visibleRows` or
`sortByName` over the recents subset (which would re-sort them A–Z and miss
forks that aren't themselves recent). The origin ids are collected into a
`Set` once per call, so the pass is linear.

### 6.5 `catalogStore.ts`

```ts
export interface CatalogStore {
  getState(): CatalogState;
  subscribe(listener: () => void): () => void;
  refresh(force?: boolean): Promise<void>;   // never rejects
  createCustom(input: CreateExercise): Promise<Exercise>;   // rejects with ApiError
  recordPick(id: string): void;
}

export function createCatalogStore(deps: {
  api: Pick<ApiClient, "request" | "post">;
  storage: StorageAdapter;
  userId: string;
  now?: () => number;   // defaults to Date.now; tests inject a clock
}): CatalogStore;
```

- **State is immutable.** Every change builds a new `CatalogState` object and
  then notifies; `getState()` returns the current object. This is what
  `useSyncExternalStore` needs: it compares snapshots by reference, so
  mutating in place — or returning a fresh object on every call — would
  respectively never re-render or re-render forever (AC22).
- **Construction** (no network): sweep other user-data keys (AC13), read and
  validate both envelopes (AC10), set the initial state with `status:
  "idle"`, `lastRefreshAt: null`.
- **`refresh(force?)`**:
  1. If a request is in flight: a non-forced call returns the in-flight
     promise; a forced call sets a `followUp` flag and returns a promise that
     settles after the follow-up run (AC16).
  2. If not forced and `now() - lastRefreshAt < CATALOG_REFRESH_STALE_MS`,
     return a resolved promise (AC14).
  3. Set `status: "loading"`, request `/v1/exercises` (+ `?since=` when a
     token is stored) with `cache: "no-store"` (AC15), and validate the body
     with `ExercisesResponse.safeParse`.
  4. `200` + valid → merge or replace by whether `since` was sent (AC17).
     Thrown → `classifySyncFailure`: `transient` → AC19; `reset` → track the
     event, issue the one full pull, apply or fail per AC18. Invalid body →
     AC19 with `reportError`.
  5. When the run settles, if `followUp` is set, clear it and run once more.
- **`createCustom(input)`**: `api.post("/v1/exercises", input, ExerciseSchema)`;
  on success insert the row (`mergeCatalogRows(rows, [row])`), `recordPick`,
  track, persist, `void refresh(true)` (AC23). If a full pull that started
  *before* the `POST` committed lands afterwards, its replace can drop the new
  row for a moment; the forced follow-up (AC16) is a delta from that pull's
  token, which includes the new row, so it returns within one round trip.
- **`recordPick(id)`**: AC21's dedupe/cap rule, persist recents, notify.
- **Persistence**: every write goes through a wrapper that catches a throwing
  adapter, calls `reportError()` once per store instance, and carries on
  in memory (AC11).

### 6.6 `CatalogProvider.tsx` / `useCatalog.ts`

```tsx
export function CatalogProvider({ userId, storage, children }: {
  userId: string;
  storage?: StorageAdapter;   // defaults to localStorageAdapter()
  children: ReactNode;
}) { /* useApi() + useMemo(() => createCatalogStore(...), [api, storage, userId]) */ }

export function useCatalog() {
  const store = useCatalogStore();   // throws outside <CatalogProvider>
  const state = useSyncExternalStore(store.subscribe, store.getState);
  useEffect(() => { void store.refresh(); }, [store]);
  const visible = useMemo(() => sortByName(visibleRows(state.rows)), [state.rows]);
  const recents = useMemo(() => pickRecents(visible, state.recentIds), [visible, state.recentIds]);
  return { state, visible, recents, refresh: store.refresh, createCustom: store.createCustom, recordPick: store.recordPick };
}
```

Calling `useCatalog()` from several components is cheap: `refresh()` dedupes
(AC14, AC16). 06.0 ships the provider but does not mount it (§1); tests wrap
components in it with a `memoryStorageAdapter()`.

### 6.7 Logout

```ts
// src/auth/logout.ts
export function logoutAndClear(auth0Logout: Auth0Logout, storage = localStorageAdapter()): void {
  clearUserData(storage);   // never throws
  void auth0Logout({ logoutParams: { returnTo: window.location.origin } });
}
```

Clearing runs **before** the Auth0 redirect because the redirect unloads the
page. `clearUserData` is a standalone function, not a store method, because
two of the three logout sites have no store: `onAuthLost` fires inside the
API client and `<AccountDeleted>` renders outside the protected layout.
`localStorageAdapter()` itself must not throw when `window.localStorage` is
inaccessible (some privacy modes throw on property access) — it defers the
access to each call, where AC11 / `clearUserData` already catch.

### 6.8 Reference data (muscle groups / equipment)

`referenceData.ts` exposes `useMuscleGroups()` / `useEquipment()` as plain
`useQuery` calls — `api.get("/v1/muscle-groups", MuscleGroupsResponse)` then
`.muscleGroups`, and the `equipment` equivalent — with
`staleTime: Infinity` (the tables change only on a deploy, so once per page
load is enough). These calls leave the browser's HTTP cache alone: it
revalidates with the endpoint's `ETag` on its own, and there is no local
merge state for a reused body to corrupt.

## 7. Security & privacy

- **No credential data in storage.** The stored envelopes hold only exercise
  rows, ids, and the opaque sync token — never an access or refresh token
  (those stay in-memory only, Spec 04.0 §7). `catalogStore.ts`'s only network
  calls are `GET` and `POST /v1/exercises`.
- **Logout must clear the catalog** (AC20) because custom exercise names are
  **user-authored free text** persisted on a possibly shared device; leaving
  them behind is a privacy leak of "what this person trains," however minor.
  That is why clearing is wired into all three logout paths rather than only
  the button, why it removes every user's keys rather than the current
  one's, and why store construction sweeps again (AC13) for the cases no
  logout code can cover (a closed tab, a crashed page).
- **Stored data is validated, not trusted, on load** (AC10) — a corrupted or
  hand-edited `localStorage` value can't crash the app or feed a malformed
  row into rendering.
- **Output encoding.** Exercise `name` (server-stored verbatim, per Spec 03.1
  §7 / Spec 03.2 §7) is rendered through React's normal auto-escaping — no
  `dangerouslySetInnerHTML` anywhere in this spec's components.
- **No new personal data class.** Exercise names are the user's own authored
  data, already bounded by `CatalogName` (1–120 chars, no control
  characters).
- **Observability hygiene.** `track()`/`reportError()` calls never include an
  exercise `name` or id (§9) — DESIGN §8.1, Spec 04.1 §9.

## 9. Observability

Via the existing `track()`/`reportError()` no-op seams (Spec 04.1 §9; Spec 13
swaps in real backends):

- **`exercise_picked { source: "recent" | "list" | "search", msSinceOpen: number }`**
  — fired by `<ExercisePicker>` before the caller's `onPick`. `msSinceOpen`
  (sheet open → pick) is a client-observable proxy for DESIGN §1.3's "<5s to
  log one set" metric, since the picker is the first step of that loop.
- **`custom_exercise_created`** — fired on a successful `createCustom`, no
  properties (Spec 04.1's `profile_saved` precedent).
- **`catalog_reset { reason: "410" | "422" | "corrupt" }`** — fired once per
  reset (AC10, AC18), from `catalogStore`. `"410"` bounds how often clients
  fall behind the sync horizon; `"422"` should be ~never (it implies a
  malformed stored token) and is worth investigating if it appears.
- **`reportError`**: once per store instance for a storage failure
  (`{ source: "catalog-storage" }`, AC11) and for a sync body that fails
  validation (`{ source: "catalog-sync-schema" }`, AC19). No stored value or
  row content is included.
- **No exercise names, ids, or other row content in any event.**

## 12. Decisions & open questions

### Resolved

- ✅ **v0.2 review changes (owner-approved 2026-10-01).**
  - **No `ETag`/`If-None-Match` on the exercise sync, and no `requestRaw`.**
    The API's CORS policy allows only `Authorization`, `Content-Type` and
    `X-Request-Id` as request headers and exposes only `X-Request-Id`, so a
    cross-origin client can neither read `ETag` nor send `If-None-Match`
    without an API change. And the change would buy almost nothing: the
    server namespaces the `ETag` by the `since` value, the client advances
    `since` after every sync, so a `304` is only possible when no write
    happened anywhere in the database — and all it would save is an empty
    `{ exercises: [], syncToken }` body. With `304` gone there is no
    non-error status the store must branch on, so v0.1's `requestRaw()`
    (a non-throwing client entry point) is dropped too: the store uses the
    existing `request()` plus a `cache` option and classifies the thrown
    `ApiError`.
  - **`cache: "no-store"` on every catalog sync**, not only the post-`410`
    pull DESIGN §5.2 names. The store owns the sync state and persists it;
    the browser's HTTP cache on top would be a second cache with its own
    staleness questions. See the DESIGN §5.2 cross-doc update below.
  - **Logout clearing is a standalone `clearUserData()` behind one
    `logoutAndClear()` helper** used by all three logout sites, with a sweep
    at store construction as a backstop (v0.1 hooked only
    `useSession().logout` and put `clearAll()` on a store instance that two
    of the sites don't have).
  - **Recents live in the store snapshot (`recentIds`) and are derived with
    `pickRecents`** (v0.1's sketch re-sorted them A–Z, checked forked-origin
    hiding against the recents subset only, and would not have re-rendered
    on a pick).
  - **A reset keeps the old rows until the full pull succeeds**, and a full
    pull replaces rather than merges.
  - **A forced refresh during an in-flight request queues one follow-up**
    instead of being deduplicated onto a request that predates the write.
  - **`<Sheet>` (native `<dialog>`) and `<CatalogProvider>` are specified**;
    v0.1 assumed both without defining them.
  - **Two build phases on one branch** (§6.1); v0.1's single AC24 is split
    into AC24–AC29.
- ✅ **The 06 split — 06.0 / 06.1 / 06.2.** Spec 06 (DESIGN §9, `docs/specs/
  README.md`) is split into this catalog-client-and-picker spec (06.0),
  the session screen (06.1: start/resume, add/reorder/remove exercises,
  per-modality set rows, finish including `409 incomplete-working-sets`,
  delete workout, and the M1 Playwright smoke), and connectivity resilience
  (06.2: write queue, unsynced-state UI, retry/backoff keyed on a set
  `clientGeneratedId`, a `localStorage` mirror of the in-progress workout,
  blocking Finish while writes are pending). Rationale: 06.0 has no
  dependency on Spec 05.x at all (it only touches the catalog); 06.2 is a
  meaningfully different problem (write reliability) from either 06.0
  (read-mostly reference data) or 06.1 (the core logging UI). **Note for
  06.2:** Spec 05.1 first merged *without* the set `clientGeneratedId`; it
  was added as a follow-up (Spec 05.1 D15, migration `0007`), so 06.2's
  dependency is met.
- ✅ **Scope: picker + create-custom only; edit/fork/delete deferred.** A
  "my exercises" management screen is real scope Spec 03.2 already built the
  API for, but bundling it here would roughly double this spec's UI surface
  for a feature that isn't on the critical path to logging a first workout.
  Forked-origin hiding **is** in scope, because forks can already exist via
  the API today and an un-hidden fork-plus-origin pair would be a visibly
  broken picker from day one.
- ✅ **Catalog persistence: `localStorage`, per-user, behind a
  `StorageAdapter`.** An injected interface keeps `catalogStore.ts` testable
  without a real DOM and gives Spec 06.2 the same seam for its own mirror.
- ✅ **Picker defaults: recents above A–Z, search not auto-focused.** Recents
  address the actual return-user workflow DESIGN §1.3's <5s metric targets —
  most sets logged are for an exercise the user has done recently.
- ✅ **What ships in 06.0: components, provider and store, not mounted.**
  `Workouts` stays `comingSoon`; Spec 06.1 flips it. No feature flag needed.
- ✅ **Create form: modality up front, everything else under "More
  details."** The one field that changes what a later set-logging row looks
  like is the one thing asked immediately.
- ✅ **Architecture: a React-free store with a thin `useSyncExternalStore`
  hook (approach 1 of 3 considered).**
  - **Rejected: TanStack Query + its persister plugin.** The persister
    persists the *entire* query cache indiscriminately (including `["me"]`),
    so clearing just the catalog on logout would need a second persister
    configuration or manual filtering of one shared blob. The merge-by-id
    logic also has no natural home in a `queryFn`/`select` pair, which is
    designed around "replace the cached value with the new response."
  - **Rejected: a single React hook holding all the state.** Untestable
    without mounting a component for every scenario, and not reusable
    outside React — DESIGN §3.4 principle 4 wants data logic separable from
    the view layer.
  - **Chosen:** a plain object with `subscribe`/`getState`, the shape
    `useSyncExternalStore` was designed for. `CatalogProvider.tsx` and
    `useCatalog.ts` are the only files in the data layer that import React.

### Open

- **No list virtualization** (§1). Accepted for M1; the trigger to revisit
  is visible jank on a real phone with a large custom catalog, measured in
  06.1's manual gym testing.
- **Exact export names** are a naming detail left to implementation — the
  *shapes* in §3/§6 are the contract; a rename before 06.1 lands is not
  breaking.
