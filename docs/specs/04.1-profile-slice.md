## 1. Purpose, scope & non-goals

Turn the Spec 04.0 skeleton into something a person can use: a **CSS-Modules +
design-token styling foundation**, a small set of UI primitives, the thumb-zone
`AppShell` with bottom navigation, a `useSession()` convenience hook, a React
**error boundary**, and **one real vertical slice** — a **Profile** screen that
reads and `PATCH`es `/v1/me`. The slice exercises the API client, the RFC 9457
error contract, a TanStack Query mutation + cache update, and the form pattern end
to end, so later feature specs (06, 08, 10, 12) inherit a proven pattern.

> **First-principles note (styling, for a backend dev newer to the browser
> side):** the browser's CSS cascade + **custom properties** (`--name: value` on a
> selector, read as `var(--name)`) already *are* a theming engine. We put the
> whole design vocabulary — colour, spacing scale, type scale, radius, a minimum
> tap-target size — in one `tokens.css` on `:root`, and every component reads only
> `var(--…)`. **CSS Modules** means a file `Button.module.css` whose class names
> Vite rewrites to be unique, so styles are locally scoped with no naming
> convention to maintain and no runtime cost. This "styles are data, referenced by
> name" model is the same one React Native's `StyleSheet` uses, so the mental
> model ports if a native app is ever built (DESIGN §3.4). No CSS framework — see
> §12 Q11.

### In scope

- **`src/ui/tokens.css`** — CSS custom properties on `:root` (colour, `--space-*`,
  type scale, `--radius-*`, `--tap-target-min`), plus a `prefers-color-scheme`
  block. **`src/ui/reset.css`** — a minimal, boring CSS reset.
- **UI primitives** — `Button`, `Field` (label + input/select + error slot),
  `Screen` (page scaffold), `Spinner`, each `Component.tsx` + `Component.module.css`
  reading only tokens. `Spinner` is **moved** from `src/screens/` (where 04.0
  shipped it unstyled) to `src/ui/`, not duplicated — see §6.1.
- **Inline SVG icons** — `src/ui/icons.tsx`, one small component per nav item.
  No icon package (§12 Q25).
- **`<AppShell>`** — the styled protected frame that `ProtectedLayout` (shipped
  in 04.0) renders around its `<Outlet/>` once `GET /v1/me` resolves: a `<header>`
  (section title + a profile affordance), a scrollable `<main>` with the route
  `<Outlet/>`, and a bottom-anchored `<nav>` driven by a declarative nav-item
  registry. Nav items: Workouts / History / Progress / Profile; the future-section
  items render "coming soon" stubs. 04.0's `AuthedPlaceholder` is deleted.
- **`useSession()`** — `{ user: Me, isAuthenticated, login(), logout() }`, wrapping
  `useAuth0` + `useMe` + the shared 04.0 `login()` helper.
- **Observability seams** — `src/observability/reportError.ts` + `track.ts`,
  no-op functions Spec 13 later swaps for Sentry / PostHog. Spec 04.0 §6 planned
  them but **did not ship them**; this spec owns them (§3, §9).
- **`<RootErrorBoundary>`** — a React error boundary for the routed subtree,
  registered as the root route's `errorElement` (§6.4 explains why an outer
  wrapper alone would not work); a recoverable fallback ("Reload"), calls the
  `reportError()` seam.
- **`NotFound` screen** — "Page not found" + a link to `/app`, mounted as the
  `/app/*` catch-all inside the shell and the top-level `*` route. Spec 04.0
  deferred it here (its router comments say so); the current `*` → `/app`
  redirect goes away.
- **Profile slice** — route `/app/profile`; `useMe()` for load; a form for
  `displayName` / `unitPreference` / `timezone` (a `<select>` from
  `Intl.supportedValuesOf("timeZone")`, §12 Q23); `PATCH /v1/me` via a TanStack
  Query mutation; `422` → per-field inline errors; `200` → `queryClient.setQueryData`
  so the shell header reflects the new `displayName` with no reload.
- **Cross-doc edits** — none outstanding: DESIGN §3.2 / §9 and the
  `specs/README.md` 04.1 row were applied with the 04.0 PR. The `useMe.ts` code
  comment that says PATCH "invalidates this key" is corrected in this spec's PR
  (§6.5).

### Non-goals

- **Everything in Spec 04.0** — the package, config, Auth0 flow, API client,
  router, bootstrap gate, CI, deploy, CSP.
- **Any feature screen** — Spec 06 (logging + picker), 08 (history / progress),
  10 (routines), 12 (account export/delete UI). Nav items for those render
  "coming soon" stubs here.
- **A component library / Storybook / visual-regression tooling** — four
  primitives, styled by hand, is the v1 surface. Revisit if the primitive set
  grows past ~a dozen.
- **Theming / user-selectable themes** — only `prefers-color-scheme`. A theme
  switcher is post-v1.
- **Client-side `Intl` timezone validation** — the server validates the IANA name
  and returns `422`; the client does not re-implement it. (Populating the
  timezone `<select>` from `Intl.supportedValuesOf` is presentation, not
  validation — the server stays the authority; §12 Q23.)
- **A tablet / desktop side-rail nav** — bottom nav at every width in v1; wide
  screens only cap `<main>` width (§12 Q24).
- **An icon package** — inline SVG only (§12 Q25).
- **`localStorage` persistence of the query cache** — R1 / M4.

## 2. Acceptance criteria

Behavioural criteria (AC2–AC9) each get ≥1 Vitest/RTL test naming their number
(`describe("AC4 — …")`). AC1 is a review + lint/grep criterion — see §10. AC10 is
the coverage-of-criteria check.

1. **Styling foundation.** A single `src/ui/tokens.css` defines the colour /
   `--space-*` / type-scale / `--radius-*` / `--tap-target-min` custom properties
   on `:root`; every `*.module.css` in `apps/web` references design values only as
   `var(--…)` (no hard-coded hex / px for colour, spacing, or radius — lint/grep);
   `apps/web/package.json` `dependencies` contains no CSS framework (no `tailwindcss`,
   `bootstrap`, `@mui/*`, `styled-components`, `@emotion/*`, etc.).
2. **Thumb-zone shell.** `<AppShell>` renders a single bottom-anchored `<nav>`
   whose stylesheet rule text sets `min-height` / `min-width` on each interactive
   nav target to `var(--tap-target-min)` and sets `padding-bottom` to a value
   containing `env(safe-area-inset-bottom)`. `--tap-target-min` resolves to `44px`
   in `tokens.css`. (Real computed geometry + 320px no-horizontal-overflow is
   verified in the M1 e2e — §10.)
3. **Shell mounts only when authed + bootstrapped.** `ProtectedLayout` renders
   `<AppShell>` only on its `200 /v1/me` branch, so the shell never appears while
   the `me` query is pending or errored; an unauthenticated visit to
   `/app/profile` never mounts `<AppShell>` (redirect handled by Spec 04.0
   `ProtectedRoute`, re-asserted here). The `<header>` shows the current
   `displayName` (or `email` fallback). An unknown path under `/app/*` renders
   `<NotFound>` inside the shell; an unknown top-level path renders `<NotFound>`
   without it.
4. **`useSession()` surface.** `useSession()` returns `{ user, isAuthenticated,
   login, logout }`; `user` is the `MeSchema`-typed body from the `["me"]` query;
   `login()` delegates to the shared 04.0 `login()` helper with the current
   `pathname + search` as `returnTo` (so `audience`, `redirect_uri` and the
   `offline_access` scope stay defined in exactly one place); `logout()` calls
   Auth0 `logout` with `returnTo: window.location.origin`.
5. **Profile loads current values.** `/app/profile` renders the `displayName`,
   `unitPreference` (`<select>` populated from `UNIT_PREFERENCE_VALUES` with the
   current value selected), and `timezone` (`<select>` populated from
   `Intl.supportedValuesOf("timeZone")` with the current value selected; falls
   back to a text input when that API is unavailable) from `GET /v1/me`; while
   the query is pending it shows `<Spinner/>`, not an empty form.
6. **Profile saves.** Submitting the form issues `PATCH /v1/me` with only the
   changed fields (JSON body validated against `UpdateMeSchema` shape); a `200`
   calls `queryClient.setQueryData(["me"], body)` and the `<AppShell>` header
   reflects the new `displayName` **without a reload or refetch**. `displayName`
   cleared to empty submits `null`.
7. **Profile validation errors.** A `422` `validation-error` response maps each
   `errors[].path` (the API emits bare field names — `displayName`, dotted for
   nesting, `(body)` for a body-level failure) to an inline message under the
   matching `<Field>`; a path that matches no field (incl. `(body)`) renders as
   the form-level message; the submitted value is **not** echoed back into the
   message; fields without an error entry are left untouched; a non-validation
   error (`5xx` / network) shows a single form-level message carrying the
   `requestId`.
8. **Error boundary.** A render error thrown inside any route element is caught
   by `<RootErrorBoundary>` — registered as the root route's `errorElement`, not
   only as a wrapper around `<RouterProvider>` — which shows a recoverable
   fallback with a "Reload" action (not a blank page, not React Router's default
   error page) and calls the `reportError()` seam once with the error.
9. **Primitives behave.** `<Field>` associates its `<label>` with the control
   (`htmlFor` / `id`) and renders `errors` text with `role="alert"` /
   `aria-describedby`; `<Button>` reflects `disabled` and a `busy` state
   (`aria-busy`, not clickable while busy); `<Screen>` renders a titled region
   (`<h1>` / labelled landmark).
10. Each behavioural criterion (2–9) has ≥1 committed test tagged with its
    number; 1 is verified by review + lint/grep per §10.

## 5. Screens & flows

*(UI spec. API surface consumed: Spec 01 §5 — `GET /v1/me` (via 04.0 `useMe`),
`PATCH /v1/me`, and the RFC 9457 error bodies.)*

### Routes added

| Path | Auth | Screen | Notes |
|---|---|---|---|
| `/app` | protected | `<AppShell>` → `AppIndex` | `AppIndex` = a short "welcome" body until Spec 06 adds the real default. |
| `/app/profile` | protected | `<AppShell>` → `ProfileScreen` | The vertical slice. |
| `/app/workouts`, `/app/history`, `/app/progress` | protected | `<AppShell>` → `ComingSoon` | Real screens in 06 / 08 / 10. |
| `/app/*` (unknown) | protected | `<AppShell>` → `NotFound` | Replaces 04.0's placeholder catch-all. |
| `*` (unknown, top level) | public | `NotFound` | Replaces 04.0's `<Navigate to="/app">` redirect. Link target is `/app` (`ProtectedRoute` bounces an unauthenticated user to `/`). |

The shipped 04.0 router is `BootstrapGate > ProtectedRoute > ProtectedLayout >
{index, *}`. `ProtectedLayout` already runs the `me`-query gate (spinner /
`AccountDeleted` / `RetryScreen`); its `200` branch returns a bare `<Outlet/>`.
This spec changes that one branch to `<AppShell><Outlet/></AppShell>` and
replaces the two `AuthedPlaceholder` children with the routes above.
`AuthedPlaceholder.tsx` is deleted (its "signed in as" + "Log out" behaviour
moves into the shell header / Profile screen).

### Shell & one-handed layout

- `<AppShell>`: `<header>` (section title + a profile/menu affordance showing
  `displayName`), a scrollable `<main>` holding the `<Outlet/>`, and a `<nav>`
  fixed to the bottom edge. Bottom nav because the reachable zone on a phone held
  one-handed is the lower third of the screen (DESIGN §1.2).
- Nav registry: `NAV_ITEMS: { to, label, icon, comingSoon? }[]` — Workouts /
  History / Progress / Profile. `icon` is a React component from
  `src/ui/icons.tsx` (inline SVG, `aria-hidden`, `currentColor` fill, sized by
  `var(--space-6)`); the `label` text is always rendered beneath it, so icons are
  decorative and the nav is usable with none. Each target is
  `min-height`/`min-width` `var(--tap-target-min)`, spaced by `var(--space-*)`.
  `padding-bottom` on the `<nav>` includes `env(safe-area-inset-bottom)` so it
  clears the iOS home indicator.
- Breakpoints: mobile-first. Base styles target a 320–430px column. The nav
  stays bottom-anchored at **every** width (Q24); a single
  `@media (min-width: 48rem)` tier only caps `<main>` at a readable measure
  (`max-width: 40rem`, centred) so desktop review is comfortable without a
  second layout to build and test. A side-rail nav is a later spec. All layout
  in `rem` / `%` / `clamp()` — no fixed px widths that could overflow at 320px.

### Profile screen (the slice)

- Load: `useMe()` (from 04.0). Pending → `<Spinner/>`.
- Fields:
  - `displayName` — text, ≤ 80 chars, clearable → submits `null`.
  - `unitPreference` — `<select>` from `UNIT_PREFERENCE_VALUES`.
  - `timezone` — `<select>` whose options are `Intl.supportedValuesOf("timeZone")`
    (≈ 400 IANA names; every current browser ships it), current value selected.
    If the stored value is not in the list (older browser, alias name) it is
    appended as an extra option so the form never silently changes it. Where
    `Intl.supportedValuesOf` is undefined the field degrades to a text input.
    The server remains the validator and returns `422` on a bad name (Q23).
- Submit → `useMutation(() => api.patch("/v1/me", body, MeSchema))` where `body`
  is only the changed fields:
  - `200` → `queryClient.setQueryData(ME_QUERY_KEY, body)`; a success
    affordance; the `<AppShell>` header re-renders from the updated query. The
    `PATCH` response carries no `isNewUser`, so the cache entry drops it — every
    consumer already treats absent and `false` alike.
  - `ApiError.isValidation()` → distribute `errors[]` to `<Field>`s by `path`.
  - other `ApiError` → one form-level message showing `err.requestId`.
- The header's profile affordance and the Profile nav item both route to
  `/app/profile`; the header one exists so the current user's name is visible
  from any section, the nav one so Profile is reachable from the thumb zone.

### Terminal / empty states

- Reuses Spec 04.0's `AuthError` / `AccountDeleted` / `RetryScreen` /
  `ResumingSession` / `Landing` — this spec only restyles them against the
  tokens (no behavioural change).
- Adds `NotFound` (04.0 deferred it): `<Screen title="Page not found">` with a
  single link to `/app`.

### 6.3 `useSession()`

```ts
import { login } from "./login";                  // 04.0 shared helper

export function useSession() {
  const { isAuthenticated, loginWithRedirect, logout } = useAuth0();
  const { data: user } = useMe();                 // 04.0
  const loc = useLocation();
  return {
    user,
    isAuthenticated,
    login: () => login(loginWithRedirect, loc.pathname + loc.search),
    logout: () => logout({ logoutParams: { returnTo: window.location.origin } }),
  };
}
```

`login()` **must** go through the shipped `src/auth/login.ts` helper rather than
calling `loginWithRedirect` directly: the helper is the one place that sets
`audience`, the `/callback` `redirect_uri`, and the `offline_access` scope. A
direct call with only `appState` would silently issue a token without the API
audience — the request would then fail `401` on every `/v1` call.

### 6.4 Error boundary

> **First-principles note (why a plain wrapper is not enough):** a React error
> boundary catches errors thrown by components *below* it — unless something
> closer catches first. React Router's data routers (`createBrowserRouter`, which
> 04.0 uses) install their **own** boundary on every route: a render error inside
> a route element is caught by the nearest route's `errorElement`, or by the
> router's built-in default error page. So a class boundary wrapped around
> `<RouterProvider>` would never see a route render error — the user would get
> React Router's unstyled "Unexpected Application Error!" page and `reportError`
> would never fire. The fix is to hand the router *our* fallback for that slot.

Two pieces, one file (`app/RootErrorBoundary.tsx`):

- **`RootErrorBoundary`** — the route-level fallback. A function component
  rendered as the root route's `errorElement`; it reads the error with
  `useRouteError()`, calls `reportError(error, { boundary: "root" })` from a
  `useEffect` keyed on the error object (so a re-render does not spam the
  seam), and renders a `<Screen title="Something broke">` with a "Reload"
  `<Button>` (`() => window.location.reload()`). Registered on the **root**
  route (the `BootstrapGate` element) so it covers every route below it,
  including the public ones.
- **`AppErrorBoundary`** — a small class component (`getDerivedStateFromError`
  + `componentDidCatch`, the only way to make a class-free codebase catch
  errors outside the router) wrapped around `<RouterProvider>` in `AppRoot`,
  for errors thrown by the providers themselves. Same fallback, same
  `reportError` call, guarded by a `reported` flag.

Neither catches async errors in event handlers or queries — those surface as
`ApiError` and are handled in-screen. AC8's test renders a throwing route
element through `createMemoryRouter(routes, …)` and asserts the *route-level*
fallback appears, not the router's default page.

### 6.5 Profile mutation & cache

- `useUpdateMe()` (`features/me/useUpdateMe.ts`) wraps `useMutation`; its
  `mutationFn` returns the parsed `Me` (04.0 client `schema.parse`).
- On success: `queryClient.setQueryData(ME_QUERY_KEY, body)` — a direct cache
  write, **never** `invalidateQueries`, so the header updates synchronously with
  no second `GET /v1/me` (AC6). `useMe` already sets `staleTime: Infinity`, so
  the written value is served as-is to every consumer. The `useMe.ts` comment
  claiming PATCH invalidates the key is wrong and is corrected in this PR.
- On `ApiError`: `err.isValidation()` → build a `Record<fieldName, message>` from
  `err.errors`. The API's `path` is a **bare field name** (`displayName`), dotted
  for nested keys (`a.b`) and `(body)` for a body-level issue such as an
  unrecognised key (see `apps/api/src/errors/problem.ts` `zodFieldPath`). Key the
  record on the path as sent; a path with no matching `<Field>` — including
  `(body)` — falls through to the form-level message. Anything else → form-level
  message with `err.requestId`.
- The form tracks which fields are dirty; the `PATCH` body includes only dirty
  fields. An empty `displayName` input serialises as `null` (explicit clear), not
  omitted.

### 6.6 Coming-soon stubs

`ComingSoon` renders a `<Screen title={section}>` with one line ("Coming with the
next release"). The nav item stays visible (`comingSoon: true` dims it and shows a
small marker) so the shell's information architecture is stable as later specs
fill sections in.

## 7. Security & privacy

- **PII in the shell.** `displayName` / `email` are rendered (the user's own
  data). They must never be put into `X-Request-Id`, `track()` event names/props,
  or `reportError()` metadata (DESIGN §8.1). `<RootErrorBoundary>` passes only the
  `Error` object and a static `{ boundary }` tag to `reportError()`.
- **Validation-error hygiene.** The `422` handler renders `errors[].message` as
  the API sent it (already value-free per Spec 01 / 03.0) and **never** echoes the
  user's submitted value into the error text (AC7) — avoids reflecting attacker
  input if `displayName` ever contained markup.
- **No new network origins.** Profile talks to `PATCH /v1/me` on the same API base
  URL already in the CSP `connect-src` (Spec 04.0 §7). No CSP change.
- **No secrets, no tokens** touched here — auth is entirely Spec 04.0's client.
- **Output encoding.** All user data is rendered through React (auto-escaped);

## 12. Decisions & open questions

### Resolved

- ✅ **Q11 — Styling: CSS Modules + CSS custom-property tokens, no framework.**
  From first principles the cascade + custom properties already are a theming
  system: `tokens.css` on `:root` is the design system, `*.module.css` gives
  locally-scoped styles with zero runtime and no naming convention to maintain,
  and the "styles are data" model ports to React Native's `StyleSheet`. Rejected:
  **Tailwind** — strong productivity + market signal, but a second styling
  language layered on CSS, and the developer is explicitly newer to frontend
  (CLAUDE.md); the DESIGN ethos (Fastify over Nest, SPA over Next, "smallest
  concept surface for learning") points the same way. Also rejected: **CSS-in-JS**
  (runtime cost on mid-range gym phones, React 19 friction) and **zero-runtime
  CSS-in-TS** (vanilla-extract / Panda — more tooling than a solo v1 needs).
  Revisit Tailwind only if styling velocity becomes a measured bottleneck.

- ✅ **Q16 — One vertical slice only (Profile).** The frame plus `GET`/`PATCH
  /v1/me` proves the client, the error contract, a TanStack Query mutation +
  cache write, and the form pattern end to end without bleeding into Spec 06's
  scope. Other nav sections render "coming soon" stubs so the information
  architecture is stable for later specs.

- ✅ **Q22 — `AppShell` + bottom-nav live in 04.1, not 04.0.** The thumb-zone
  criterion (tap-target sizing, safe-area inset) is only verifiable against the
  token system, which this spec introduces — so the styled shell and its nav
  registry belong here. Spec 04.0's protected area renders a minimal placeholder
  until this spec swaps in `<AppShell>` as the layout route's `element`. Both
  specs are M0, so Spec 06's dependency on "the shell" is satisfied within the
  same milestone.

- ✅ **Q23 — Timezone is a `<select>` fed by `Intl.supportedValuesOf("timeZone")`,
  not a free-text input.** (v0.2, design review 2026-09-10.) Typing
  `America/Los_Angeles` on a phone keyboard, with a round-trip `422` as the only
  feedback, is exactly the gym UX DESIGN §1.2 forbids. Every current browser
  exposes the ICU zone list through `Intl.supportedValuesOf` and the device's
  own zone through `Intl.DateTimeFormat().resolvedOptions().timeZone`, so a
  select with the right default costs nothing. This is presentation, not
  validation: the server keeps validating the name (the "no client-side IANA
  validation" non-goal stands), a stored value missing from the list is kept as
  an extra option, and the field degrades to text where the API is absent.
  Rejected: a searchable combobox (a primitive this spec does not otherwise
  need — revisit if the picker in Spec 06 wants one anyway).

- ✅ **Q24 — Bottom nav at every width; no tablet side-rail in this spec.**
  (v0.2.) v0.1 moved the nav to the side above `48rem`. That is a second layout
  to build, style, and test with no acceptance criterion covering it, in a spec
  whose goal is the phone. Wide screens now only cap `<main>` at a readable
  measure. A side rail is additive later (a media-query block in
  `AppShell.module.css`, no component change), so nothing is foreclosed.

- ✅ **Q25 — Nav icons are inline SVG components, no icon package.** (v0.2.)
  v0.1 declared an `icon` field but never said where icons came from. An icon
  library is a dependency the AC1 "no CSS framework" check would not catch, adds
  bundle weight, and is a second thing to learn. Four hand-written `<svg>`
  components in `src/ui/icons.tsx` (`aria-hidden`, `currentColor`, sized by a
  token) cover this spec; labels are always rendered so icons stay decorative.
  Revisit with a tree-shakeable set (e.g. `lucide-react`) only if the count
  grows past what is comfortable to hand-write.
