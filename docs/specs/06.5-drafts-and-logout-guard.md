## 1. Purpose, scope & non-goals

Close the last two ways a lifter loses typing or logged sets without being told, after 06.2 made logged sets durable:

1. **Drafts.** Values typed into the entry row but not yet logged live only in React state. A phone that evicts the tab during a rest period (R1) loses them, and the lifter returns to a blank row. This spec persists an *edited* draft and restores it.
2. **Logout guard.** Today Sign out discards the outbox silently (06.2 §11 "Known gaps"). This spec makes the Profile Sign out button first try to sync, then warn, then allow.

> **First-principles note (what "persisted draft" means here).** A *draft* is the entry row's text fields: strings such as `"12."` that may not even parse yet (06.1 D13). It is not a set and never reaches the server or the outbox. Persisting it is a plain write of those strings to `localStorage`, read back when the same card mounts again. The only design questions are *when to write* (not on every keystroke; it would thrash storage), *when to trust what is read back* (only for the same user and workout), and *when to throw it away* (the instant it is stale).
>
> **First-principles note (why the guard is a state machine).** "Sign out, but first try to save" takes time: a request may be in flight, the network may be down, the lifter may change their mind, and the outbox keeps changing underneath. A small pure state machine (`idle → syncing → warning`) with an injected clock lets every one of those races be table-tested without a DOM, and keeps the React part to rendering its state.

### In scope

- `draftStore` (React-free) and `useDraftPersistence` (the hook `EntryRow` calls), under `apps/web/src/features/workouts/drafts/` (§6.1–§6.4).
- Restore, re-seed interplay and clearing rules (§6.3–§6.4).
- `logoutGuard` (React-free), `useLogoutGuard` and the dialog, wired to Profile's Sign out button only (§6.5–§6.8).
- **Rename:** `ProfileScreen`'s control, today labeled "Log out", is relabeled **Sign out** (owner decision, 2026-10-15) to match the dialog's "Sign out anyway" and Spec 12's wording. `ProfileScreen.tsx` therefore changes (label, the guard composition) and `ProfileScreen.test.tsx`'s "Log out" queries become "Sign out".
- Copy in `messages.ts` (§6.9).

### Non-goals (with where they live)

| Not here | Lives in |
|---|---|
| Two tabs co-operating (Web Locks, cross-tab draft or outbox sync) | **Spec 06.6**. Until then 06.2 §6.8 stops the second tab, and two tabs on one workout can overwrite each other's draft (D12) |
| Playwright run with `context.setOffline()` | **Spec 06.6** (depends on 06.3's harness, whose live run is still blocked on the Auth0 test user) |
| Guarding the forced paths: the `useApi` lost-session logout, the `AccountDeleted` / `AuthError` screens, Spec 12's Sign out | Unchanged and unguarded by design (D4): none can ask a question, and a lost session clears the outbox on purpose (06.2 D6) |
| A `beforeunload` prompt on tab close or reload | Rejected (D8): mobile browsers ignore it, and a closed tab keeps its outbox |
| Counting drafts as "unsaved" at logout | Rejected (D5): an unlogged draft is not a set the lifter believes is saved |
| Persisting drafts for the edit sheet, routine editor or any other form | Not planned. The entry row is the only value the gym loop loses |
| Draft expiry, a "Restored" cue | Open, defaults in §12 |
| Persisting the workout itself, or opening the app offline | 06.2 D11 (tokens are memory-only, DESIGN Q12) |

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"06.5 ACn — …"`** (the 06.4 D6 / 12 convention). Levels are in §10. **Phase A** (AC1–AC11): drafts. **Phase B** (AC12–AC24): the logout guard. **Docs and gates** (AC25–AC27).

### Phase A — persisted drafts

1. **A draft round-trips through storage.** `draftStore.set(workoutExerciseId, fields)` followed by a debounce flush writes one value under `sin:workout:drafts`, shaped `{ v: 1, userId, workoutId, byExercise: { [workoutExerciseId]: { weight, reps, distance, minutes, seconds, rpe, weightUnit, distanceUnit, setType } } }`. The fields are exactly those nine; **`attemptKey` is never written**. `get(workoutExerciseId)` on a fresh store over the same storage returns the same nine fields.
2. **Restore is for the same user and workout, and shape-checked.** On load the value is zod-parsed. A value that fails to parse, has `v !== 1`, has a different `userId`, or a different `workoutId` than the store was built for is dropped (the key removed) and `get` returns `undefined`. Only a *parse* failure is reported (once, `{ source: "workout-drafts" }`); a user or workout mismatch is silent (it is the normal stale case). Never thrown.
3. **Writes are debounced and flushed on leave.** Calls to `set` within 300 ms of each other produce one `storage.set`, carrying the latest fields. `flush()` writes a pending value at once and cancels the timer. The hook calls `flush()` on `visibilitychange` when `document.visibilityState === "hidden"` and on `pagehide`, and on unmount.
4. **A storage failure is reported once and never thrown.** If `storage.set` throws, the store keeps working in memory, reports `{ source: "workout-drafts" }` once per store (06.0 AC11's pattern), and never throws to a caller. A `storage.get` that throws is treated as "no value", reported once.
5. **Nothing is written after logout's write block.** After `logoutAndClear` (`blockUserDataWrites()`), a pending debounce firing, a `flush()`, and a later `set` leave no `sin:workout:drafts` key behind (`clearUserData` removed it; the adapter's block ignores the writes). The store adds no second mechanism for this.
6. **Only an edited draft is persisted.** `EntryRow` calls `set` only once `untouched` is false (the lifter has typed or changed a unit or type). An untouched row writes nothing, and is re-seeded from the plan / last logged set as today (10.2 AC22 / AC25 unchanged). Reaching the same values by hand is still an edit.
7. **A remounted card restores an edited draft.** With an edited draft in storage for this user, workout and exercise, a new `EntryRow` for that exercise shows the stored values in the nine fields, with a **fresh** `attemptKey` (`crypto.randomUUID()`), and starts with `untouched = false`.
8. **A restored draft is never overwritten by a re-seed.** After a restore, a change of the card's logged count by any route but this row's own log (a delete from the edit sheet, another device) does not rebuild the draft (10.2 AC25's rule, applied because the draft starts touched).
9. **Logging clears the stored draft, typing after the tap keeps it.** When this row's own log resets the draft (the `logged` branch), that exercise's entry is removed (the key is removed when `byExercise` becomes empty). When the lifter typed after tapping Log (the `rekey` branch, 06.1 §6.5), the draft is kept and the newer values are persisted.
10. **A workout ending drops its drafts.** Finishing (`useFinishWorkout` success), discarding (`useDeleteWorkout` success) and the gone path (06.1 AC29) each call `draftStore.clearWorkout(workoutId)`. An entry for an exercise that is no longer in the workout is ignored on restore and removed on the next write.
11. **Drafts survive an ordinary reload but not a user change.** A reload keeps the key (signing in is not logging out, 06.2 §6.6). Logout and lost session remove it through the `sin:workout:` prefix (06.0 AC20); a different user signing in on the same browser finds it dropped by AC2.

### Phase B — the logout guard

12. **Nothing unsaved: log out at once.** With no op in the outbox, `requestLogout()` calls the supplied `logout` immediately, in the same tick, with no dialog. Edited drafts do not change this (AC21).
13. **Unsaved and online: sync first.** With ≥1 op in `queued` or `sending`, `navigator.onLine` true and `conflict` false, the guard enters **syncing**: it calls `outbox.retryNow()` once and opens the dialog "Saving your sets…" with a spinner and **Cancel**. If the outbox empties within `SYNC_WAIT_MS` (8000), the guard calls `logout` with no further prompt.
14. **Still unsaved after the wait: warn.** If ops remain when `SYNC_WAIT_MS` elapses (measured by the injected clock), the guard enters **warning**: "N sets haven't saved. If you sign out now they'll be lost." with **Stay** (default focus) and **Sign out anyway**. Sign out anyway calls `logout`; Stay returns to idle.
15. **Cases that skip the wait.** Offline from the start (`navigator.onLine` false), a second-tab `conflict`, or only `failed` ops (nothing `retryNow()` can send) go straight to **warning** without calling `retryNow()` and without the spinner.
16. **Failed ops count.** An op in `failed` (a permanent 4xx such as a 422 or a `409 workout-finished`) is unsaved. A failed-only outbox warns (AC15) rather than logging out silently.
17. **Cancel and Stay leave the outbox running.** Cancel during syncing, and Stay in warning, return to idle, close the dialog, leave the outbox untouched, and never later call `logout`, even if the outbox empties afterwards. The guard is reusable: a second request starts from idle.
18. **Races.** (a) Further `requestLogout()` calls (taps) while syncing or warning are ignored. (b) If the outbox empties while the warning is up, the guard proceeds with `logout` without asking again. (c) On every transition toward `logout` the guard re-reads the outbox: if an op appeared or failed since the tap, it takes the warning path rather than logging out. (d) After `logout` is called the guard is finished; nothing it scheduled fires.
19. **The guard changes no other logout path.** `logoutAndClear` keeps its signature and behavior; the `useApi` lost-session path and the `AccountDeleted` / `AuthError` screens still log out unguarded and a lost session still clears the outbox (06.2 D6, AC9). A source scan shows `useLogoutGuard` is imported by `ProfileScreen` only.
20. **The dialog is accessible.** It is a `ConfirmDialog`; in warning, **Stay** has initial focus (the dialog's `data-confirm-cancel` button) and **Sign out anyway** uses the danger variant; in syncing the spinner is accompanied by the text, the dialog title is the live status, and **Sign out anyway** is disabled so a tap cannot skip the wait. Moving syncing → warning in place re-focuses **Stay** (`focusKey`). Escape and the Android back gesture act as Cancel / Stay.
21. **Drafts are discarded silently.** An edited draft in storage never triggers the dialog, never adds to N, and is removed by `logoutAndClear` as today.
22. **Copy is static.** `messages.ts` is the only source of dialog text; N is the only dynamic value, an integer; no set value, exercise name or id is interpolated (§7).
23. **The Profile button is "Sign out" and runs the guard.** The control's accessible name is "Sign out" (no "Log out" text remains on the screen). Tapping Sign out on Profile with unsaved ops opens the dialog instead of logging out; with none, it logs out as today. `useSession().logout` is unchanged.
24. **Counting.** N is the number of ops in `queued` / `sending` / `failed` for the signed-in user (06.2 AC8 keeps other users' ops out of the outbox). Set ops and note ops (Spec 10.3) are both unsaved, and `messages.ts` words the two (§6.9).

### Docs and gates

25. **Hygiene scans.** (a) The only storage key the new files name is `sin:workout:drafts`, under a prefix in `USER_DATA_KEY_PREFIXES`; no new prefix is added. (b) No new non-test file names `localStorage` / `sessionStorage` (comments included; the 04.0 AC7 scan passes unmodified). (c) No draft value or guard-count-bearing object is passed to `track`, `reportError` or `console`; the only error context is the static tag. (d) The logout scan (no other file builds `logoutParams`) passes unmodified.
26. **Coverage and docs.** `src/features/workouts/drafts/**` and `logoutGuard.ts` get a ≥ 90 % line gate in `vitest.config.ts`; the existing gates still pass. DESIGN §5.3, R1, §9's milestone line, the README rows and Spec 06.2's pointers carry the edits in §11. CLAUDE.md gains the line in §11.
27. **Each of AC1–AC25 has ≥1 committed test tagged with its number** (`"06.5 ACn — …"`), enforced by a scan test in the style of Spec 12's `acTags.12.test.ts`.

## 4. Data model

No server-side tables, migrations or API. One new browser-storage key under the existing `sin:workout:` prefix (already in `USER_DATA_KEY_PREFIXES`, so logout and `onAuthLost` clear it with no code change):

| Key | Value | Written | Removed |
|---|---|---|---|
| `sin:workout:drafts` | `{ v: 1, userId, workoutId, byExercise: { [workoutExerciseId]: DraftFields } }` | debounced ~300 ms after an edit; flushed on `visibilitychange` → hidden, `pagehide`, unmount | when `byExercise` is empty; finish / discard / gone; logout; lost session; a parse failure or user / workout mismatch on load |

`DraftFields` = `{ weight, reps, distance, minutes, seconds: string; rpe: string; weightUnit: WeightUnit; distanceUnit: DistanceUnit; setType: SetType }`. `attemptKey` is excluded because it is the create's idempotency key (06.1 §6.5): re-using a stored one across a tab restart could make a new tap replay an old create. It is re-minted on restore.

The value holds one workout only: writing a draft for a different `workoutId` replaces it (a lifter has one active workout, 05.0). Size is a few hundred bytes per edited exercise. `v` lets a later spec migrate the shape.

1. The lifter types weight 62.5 and reps 8 for the third set, locks the phone, and the browser evicts the tab.

1. Profile → **Sign out**. A dialog titled "Saving your sets…" with a spinner and **Cancel** appears. The outbox retries once at once.

3. Otherwise the dialog changes in place to "3 sets haven't saved. If you sign out now they'll be lost." with **Stay** (focused) and **Sign out anyway** (danger). Stay returns to Profile; the outbox keeps retrying.

Profile → **Sign out** with signal off: the warning appears immediately, without the spinner step.

## 6. Behavior & logic

### 6.1 `draftStore`

React-free, built per `(userId, workoutId)`. `load()` parses once at construction (AC2). `set(id, fields)` updates an in-memory map and (re)arms a 300 ms timer from the injected clock (a `setTimeout` wrapper, as the outbox's clock); the timer's write is `storage.set(KEY, JSON.stringify({ v: 1, userId, workoutId, byExercise }))`. `clearExercise(id)` deletes the entry and writes (or removes the key when empty) immediately, not debounced, because a stale draft restoring after a log would be a visible bug. `clearWorkout(workoutId)` removes the key if it holds that workout. `flush()` and `dispose()` as in AC3. Failure handling is one `try/catch` around each storage call (AC4). Nothing in this module reads `window` or `document`; the hook owns the event listeners.

### 6.2 `useDraftPersistence`

Called by `EntryRow` with the current draft and `untouched`. It (a) reads `restored` once at mount via `useDraftStore()?.get(exercise.id)`; (b) when `untouched` is false, calls `set` with the nine fields (never `attemptKey`) in an effect keyed on those fields; (c) registers the `visibilitychange` (hidden) and `pagehide` listeners and the unmount cleanup that call `flush()`; (d) exposes `clear()` for AC9. With no `DraftStoreContext` (a test that mounts `EntryRow` bare) it is a no-op.

### 6.3 Restore and the 10.2 re-seed rule

`EntryRow`'s `useReducer` initializer takes `restored` when present: `{ ...restored, attemptKey: crypto.randomUUID() }`, and the `useState` for `untouched` starts `false` in that case. Because 10.2's re-seed (`if (seededFor !== count && untouched) dispatch seed`) only fires for an untouched draft, a restored draft is protected by construction (AC8) with no change to that rule. One subtlety, resolved: a restored draft for a card whose logged count has since changed (another device logged a set) still shows the lifter's typed values; they can see the set list above and edit. This matches the live behavior of a typed-in draft.

### 6.4 When a draft is cleared

| Event | Action |
|---|---|
| This row's own log, draft reset (`logged` branch) | `clearExercise(id)` |
| Log tap, lifter typed since (`rekey` branch) | keep; the next effect persists the newer values |
| Edit sheet, delete set, other devices | nothing (the draft is independent of the list) |
| Remove exercise (06.1) | nothing at once; an orphan entry is ignored on restore and pruned on the next write (AC10) |
| Finish / discard / gone | `clearWorkout(workoutId)` |
| Logout / lost session | `clearUserData` via the prefix; the write block stops stragglers (AC5) |

A `clearExercise` after the log never races a pending debounce: it cancels the timer and drops that id from the in-memory map first.

### 6.5 `logoutGuard` — the state machine

```
idle ──request()──▶ unsaved = count(ops)
  unsaved = 0                         ──▶ proceed()                         (AC12)
  unsaved > 0, can sync               ──▶ syncing: retryNow(); wait ≤ SYNC_WAIT_MS   (AC13)
  unsaved > 0, offline|conflict|only failed ──▶ warning                      (AC15, AC16)
syncing ──outbox empty──▶ proceed()
        ──wait elapsed──▶ warning                                            (AC14)
        ──cancel()──────▶ idle                                               (AC17)
warning ──"Sign out anyway"──▶ proceed()
        ──outbox empty──────▶ proceed()                                      (AC18b)
        ──cancel()/Stay─────▶ idle
```

"Can sync" = `online && !conflict && ops.some(status is queued or sending)`. The guard subscribes to the outbox while not idle, and unsubscribes and clears its timer on every exit. Every move toward `proceed()` re-reads the outbox once more (AC18c): if ops are present it goes to warning instead. The wait uses the injected `clock` (`now()`, `setTimeout`), so a test advances fake time rather than sleeping. `proceed` is the supplied `logout` and is called at most once per guard lifetime.

`retryNow()` leaves `failed` ops alone (06.2), which is why a failed-only outbox skips the wait: there is nothing to wait for.

### 6.6 The seam: why Profile composes, and `useSession` does not change

The outbox lives in `features/workouts` and is reachable only through `OutboxContext`, which `WorkoutClientProvider` mounts under `ProtectedLayout`. `src/auth/` sits below `features/` in the dependency direction (the layer that knows nothing about screens). If `useSession` exposed `requestLogout()`, it would have to read the outbox, so `auth/` would import `features/workouts` — a cycle in spirit (`features/workouts` already imports `auth` through `useApi`) and a new coupling for every screen that calls `useSession`. A context injected into `auth/` to avoid the import would work but adds an indirection with one consumer.

**Chosen seam (owner-approved):** `useLogoutGuard(proceed)` lives in `features/workouts/`, reads `useOutbox()`, and `ProfileScreen` composes it with the unchanged session function:

```tsx
const { logout } = useSession();
const guard = useLogoutGuard(logout);        // features/workouts
<Button onClick={guard.request}>Sign out</Button>
{guard.dialog}
```

`ProfileScreen` (`features/me`) importing a hook from `features/workouts` is a feature-to-feature import. It is acceptable here because the CLAUDE.md "only `routines/` may be imported by `workouts/`" rule runs the other way and `me` has no such restriction; the import is added to the boundary scan's allow-list for `ProfileScreen` only (AC19). `useSession` deliberately gets no `requestLogout()` (D6).

### 6.7 The dialog

One `ConfirmDialog` instance whose props follow the phase, so syncing → warning happens in place without a close/open flicker: syncing — `title="Saving your sets…"`, body a `Spinner` with visible text, `cancelLabel="Cancel"`, `confirmDisabled`; warning — the count message, `cancelLabel="Stay"`, `confirmLabel="Sign out anyway"`, `variant="danger"`, `focusKey` changing on the phase so focus returns to Stay (Spec 12's props; see Depends). The title text is a polite live region's content so the syncing → warning change is announced once (06.2 AC15's pattern).

### 6.8 What stays outside

`logoutAndClear` is called by the supplied `logout` exactly as before: write block first, then `clearUserData`, then the Auth0 redirect. The guard never touches storage. A forced logout during syncing (the lost-session path fires meanwhile) simply navigates away; the guard's timer dies with the page.

### 6.9 `messages.ts`

Static strings: the syncing title and "Cancel"; the warning title ("Sign out with unsaved sets?"); body for sets only, notes only, and both (singular/plural variants as a small table keyed by `(n === 1)`), e.g. "1 set hasn't saved. If you sign out now it'll be lost." / "3 sets haven't saved. If you sign out now they'll be lost."; "Stay"; "Sign out anyway". The formatter takes two integers and nothing else.

## 7. Security & privacy

- **New data at rest.** `localStorage` now also holds typed, unlogged measure strings (weights, reps; no names, no ids beyond GUIDs). The same class as the outbox (06.2 §7) and the catalog cache; cleared on logout and lost session via the prefix; every write respects the logout write block (AC5).
- **No cross-user restore.** The `userId` in the value (`Me.id`) is checked on load (AC2); a different user on the same browser never sees it, even if a clear were missed.
- **No new ingress.** The stored value is zod-parsed; a tampered key cannot inject a shape. Restored strings pass through the same `parseDraft` validation as typed ones before any request.
- **Observability hygiene.** No draft value and no op content reaches `track`, `reportError` or the console (AC25). The only context is the static `{ source: "workout-drafts" }` tag. The guard emits nothing.
- **The guard is not a security control.** It protects the lifter's data from an accidental tap, not the device from a person with the page open.

No new events (§12 O4). `reportError` with `{ source: "workout-drafts" }`: storage write failure, read failure or a parse failure, once per store, no values. This gives the owner the only signal worth having before the phone week: whether storage writes fail on a real phone.

| Criterion | Level | Verified by |

## 12. Decisions & open questions

### Resolved (owner, 2026-10-15 brainstorm, unless noted)

- ✅ **D1 — Split: 06.5 = drafts + logout guard; 06.6 = multi-tab (Web Locks) + Playwright offline run.** **Rationale:** the four items 06.2 deferred do not fit one session, and the two kept here are the ones a lifter feels directly; multi-tab and offline e2e both want a real-phone/browser harness (06.3's live run is still blocked on the Auth0 test user).
- ✅ **D2 — Persist only an edited draft; an untouched row re-seeds.** **Rationale:** an untouched row is a pure function of the plan and last set (10.2); persisting it would freeze stale seeds and fight the re-seed rule. **Consequence:** nothing is stored for a lifter who has not typed.
- ✅ **D3 — One key, `sin:workout:drafts`, one workout, no `attemptKey`.** **Rationale:** under the existing prefix, logout and lost session already clear it; a lifter has one active workout; a stored `attemptKey` could make a new tap replay an old create (06.1 §6.5). **Alternative rejected:** one key per exercise (more keys to clear, no benefit).
- ✅ **D4 — The guard covers Profile's Sign out only.** **Rationale:** the forced paths cannot ask a question, and a lost session clears the outbox deliberately (06.2 D6).
- ✅ **D5 — Edited drafts do not count as unsaved.** **Rationale:** they are not sets the lifter believes are saved; the warning is for data the lifter thinks is safe. **Consequence:** logout discards a draft without warning.
- ✅ **D6 — The seam is the Profile screen composing `useLogoutGuard` (features/workouts) with the unchanged `useSession().logout`.** **Owner-approved (2026-10-15).** **Rationale:** §6.6. An earlier idea, `useSession().requestLogout()`, was dropped on purpose: it needs the outbox inside `auth/`. **Alternatives rejected:** `requestLogout` on `useSession` with a context injected into `auth/` (indirection for one consumer); moving the outbox context into `auth/` (wrong layer).
- ✅ **D7 — Sync, then warn, then allow (06.2 D9).** `SYNC_WAIT_MS = 8000` as a guess for a flaky gym connection. A failed-only, offline or conflicted outbox skips the wait because nothing can be sent.
- ✅ **D8 — No `beforeunload` prompt.** **Rationale:** mobile browsers ignore it, and the outbox survives a closed tab or reload.
- ✅ **D9 — Debounce 300 ms, flush on hidden/pagehide.** **Rationale:** fewer writes than per-keystroke, and `visibilitychange` → hidden is the last reliable event on mobile before eviction (`pagehide` as the second net).
- ✅ **D10 — A restored draft starts touched.** **Rationale:** it protects the lifter's typing from the 10.2 re-seed with no change to that rule.
- ✅ **D11 — Failed ops count as unsaved.** **Rationale:** a `failed` op is a set the screen showed and the server never got; silently dropping it is exactly the loss this spec exists to prevent.
- ✅ **D12 — Two tabs may overwrite each other's draft until 06.6.** **Rationale:** 06.2 §6.8 already stops the second tab's outbox, and a draft is cheap to retype; 06.6 will decide ownership.

### Open (defaults apply until the owner decides after the phone week)

- **O1 — A "Restored" cue** on a restored entry row. Default: none (the values simply appear).
- **O2 — Draft expiry.** Default: none; a draft dies with its workout (AC10). A lifter returning to a day-old workout sees yesterday's typing.
- **O3 — `SYNC_WAIT_MS` (8000).** Tunable after the phone week, in either direction.
- **O4 — Telemetry for the guard** (outcome and a count, nothing else). Default: none; add only if the owner wants to know how often the warning is hit.
- **O5 — Wording "sets" for the count.** The count is outbox ops (an edit or delete of an already-synced set is one op). The owner's copy says "sets"; "changes" would be exact. Default: "sets" for set ops, with notes worded separately (§6.9).
