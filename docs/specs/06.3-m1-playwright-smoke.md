## 1. Purpose, scope & non-goals

Run **one happy-path browser session** against the deployed staging web and API, with a real Auth0 Universal Login, after every merge to `main`: sign in, start a workout, log a set on each of the five modalities, survive a hard reload, reorder / edit / remove, finish, read the summary, delete. It also discharges the browser-only obligations earlier specs explicitly handed to "the M1 smoke" because jsdom cannot show them: the real redirect round-trip and cold-load resume, CSP enforcement, real layout (320 px, tap targets), and the real `<dialog>` focus behavior the 06.0 unit tests only shim.

> **First-principles note (what Playwright is, and why Vitest is not enough).** Vitest runs our code in **jsdom**, a pretend browser written in JavaScript: there is no layout engine (so no real widths, no overflow, no tap-target sizes), no real `<dialog>` focus trapping or Escape handling (hence the `showModal` shim), no CSP enforcement, and no real Auth0 redirect. **Playwright** drives a real browser over the network like a user: it opens pages, finds elements by role and accessible name (`getByRole('button', { name: 'Log set' })` — the names a screen reader uses, so the tests also police accessibility), taps, and waits for results with auto-waiting that avoids most sleeps. A *browser context* is an isolated profile (its own cookies and storage); `storageState` saves a context's cookies so later contexts start already logged in. The cost is speed, a real network, and flakiness — so Playwright here is **one happy-path smoke**, not a second test suite; behavior is tested in the Vitest layer (06.1).

### In scope

- `@playwright/test` as a devDependency of `@sin/web`; `apps/web/playwright.config.ts`, `apps/web/e2e/` (`auth.setup.ts`, `session.smoke.spec.ts`, `helpers.ts`), a `pnpm --filter @sin/web run e2e` script.
- The real Auth0 Universal Login once per run, with the saved auth state reused.
- The happy-path session (§5) and the browser-only checks (§2 AC2–AC4).
- A `main`-only, post-deploy, serialized CI job; a build-commit meta tag so the job knows the deployed web build is the pushed SHA.
- A runbook section for the one-time external setup (Auth0 test user, repo variables / secrets).

### Non-goals

- **Behavior coverage.** Error branches, validation, the `409 incomplete-working-sets` recovery (unreachable through the real UI — 06.1 §5.6), conflict handling: all Vitest/RTL in 06.1. The smoke does not mock the API.
- **Silent refresh-token rotation** (04.0 §10 item 3): a documented **manual check**, not automated (§12 D2).
- **Per-PR runs** against a local stack, a fake IdP, or a test-only auth bypass (rejected, §12 D1).
- **WebKit / Firefox projects** (§12 D3); real-device soft-keyboard and safe-area checks (manual, recorded in 06.1's PR).
- **"See PR"** (DESIGN §8.3's original last step): not assertable until Specs 07/08.
- Any change to the app beyond the build-commit meta tag (§6.3).

## 2. Acceptance criteria

1. **The M1 happy path runs in a real browser.** Mobile Chromium (Pixel 7 emulation), real Auth0 Universal Login on the staging tenant, the deployed staging web and API: land on `/app/workouts`; discard any leftover in-progress workout through the UI; Start; add one real catalog exercise per modality — Barbell bench press (`weight_reps`), Pull-up (`bodyweight_reps`), Weighted dip (`weighted_bodyweight`), Plank (`duration`), Treadmill run (`distance_duration`) — via the real picker (search, pick); log one set on each; hard-reload and confirm all five exercises and all five sets are restored from `GET /v1/workouts/active`; move one exercise up and confirm the order survives a reload; edit one set's value; remove one exercise; Finish through the confirm dialog; see the summary with the remaining sets; Delete the workout from the summary; land on the Start screen.
2. **Zero CSP violations and zero console errors** throughout the run (a `securitypolicyviolation` listener and console capture, asserted empty) — in particular the self-hosted Auth0 worker loads under `worker-src 'self'` and no inline style is blocked (Spec 04.0 §10 item 4; 06.1 §6.8).
3. **Real layout.** At a 320 px viewport the Start screen and the session screen have `scrollWidth <= clientWidth` (no horizontal overflow) and every visible interactive element is ≥ 44 × 44 CSS px by `getBoundingClientRect` — the 320 px / tap-target checks Spec 04.1 §10 handed to the smoke, extended to the workout screens.
4. **Real dialog, redirect and resume behavior.** Opening the picker puts focus on its Close button (not the search field); Escape closes it and focus returns to "Add exercise"; the confirm dialog traps focus and Escape cancels it (06.0 §5 / §10 handoff). A hard reload of `/app/workouts` shows "Resuming your session…" and returns to the same path with no credential re-entry — the Auth0 session cookie is still valid (Spec 04.0 §10 items 1 and 2: a real Universal Login landing on an authed screen rendered from `GET /v1/me`, and the cold-load path via the `is.authenticated` hint and `returnTo`).
5. **The job is safe to run on `main`.** It runs only on pushes to `main`, after the API smoke and the web post-deploy smoke; two runs never overlap (one test user); it waits until the deployed web build's `sin-commit` meta equals the pushed SHA and warms the Render free-plan API before the first test; it uploads traces and screenshots on failure only and never the saved auth state; a leftover workout from a failed prior run is cleaned up by the next run through the UI.
6. **The suite is runnable locally.** `pnpm --filter @sin/web run e2e` runs the same specs against `E2E_BASE_URL` / credentials from the environment; the runbook documents it.
7. **The manual checks are written down.** The runbook lists the checks this smoke deliberately does not automate: silent refresh-token rotation without a redirect (04.0 §10 item 3), soft keyboard vs the sticky bar on iPhone Safari and Android Chrome, `env(safe-area-inset-bottom)` with a home indicator (04.1 carry-over).
8. **The build-commit tag is correct and inert.** `index.html` carries `<meta name="sin-commit" content="…">` set from `RENDER_GIT_COMMIT` at build time (`"dev"` when unset); a unit test of the Vite config transform asserts both; the web `assert:build-output` check stays green and the CSP is unchanged.
9. **Docs stay consistent.** DESIGN §8.3 and §9, the README rows, and Spec 06.1 §12 D21–D24 agree with this spec.

## 4. Data model

None server-side. The smoke runs as one dedicated Auth0 user and so owns throwaway rows in the staging database: it deletes its workout at the end of every run, and the next run discards a leftover active workout first. Client-side: `e2e/.auth/state.json` (Playwright `storageState`, gitignored) holds the live Auth0 session cookie and the hint cookie.

## 5. Screens & flows

*(e2e spec — replaces "API surface". It drives the screens of Spec 06.1 §5.)*

```
setup project   (once per run)
  open /app → redirected to Auth0 Universal Login → fill E2E_AUTH0_USERNAME / PASSWORD
  → wait for /app/workouts → save storageState → e2e/.auth/state.json

mobile-chromium project  (Pixel 7, uses the saved state)
  beforeAll: warm the API (GET /readyz, retry up to ~120 s)
  1  goto /app/workouts           → cold load: "Resuming your session…" → back on the path   (AC4)
  2  if "Discard workout" is visible: discard through the confirm dialog
  3  Start workout
  4  for each of the five exercises: Add exercise → (focus on Close; search; pick) → card appears
       → fill the modality's fields → Log set → row appears
  5  page.reload() → five cards, five sets                                                   (AC1)
  6  Move up on one card → reload → order kept
  7  edit a set (sheet) → Save → value shown; remove one exercise (confirm)
  8  Finish → confirm → summary lists the remaining sets
  9  Delete workout → confirm → Start screen
  throughout: CSP / console capture empty (AC2); at 320 px: overflow + target size checks on
  the Start screen and the session screen (AC3)
```

Locators are role/name based; no CSS selectors, no `data-testid` dependence beyond what 06.1 already ships. Traces and screenshots on failure only; Chromium only.

## 6. Behavior & logic

### 6.1 Auth strategy

The real Universal Login is driven once per run (`setup` project) and its `storageState` reused by the test project. Each test's cold load therefore exercises the real session-resume path through Auth0's still-valid session cookie without re-entering credentials (AC4). Tokens remain memory-only in the page (Q12): the smoke never reads or injects a token.

### 6.2 Run hygiene

- **Warm-up.** Render's free plan sleeps; `beforeAll` polls the API's `/readyz` (≤ ~120 s) so the first UI action is not a cold start.
- **Idempotent re-runs.** One active workout per user (05.0): the first step discards a leftover through the UI (which also exercises Discard), and the run ends by deleting its own workout (which exercises delete-after-finish).
- **Serialization.** `concurrency: { group: e2e-staging, cancel-in-progress: false }` in the workflow: two pushes to `main` in quick succession must not race on the one test user.

### 6.3 Knowing the deployed web build is this SHA

The API smoke waits on `/healthz` for the deploy; a static site has no such endpoint, so the smoke could otherwise test the previous build (a false green or a flake). `vite.config.ts` stamps `<meta name="sin-commit" content="${RENDER_GIT_COMMIT ?? "dev"}">` into `index.html` (Render sets `RENDER_GIT_COMMIT` at build time — **unverified** against Render's current build environment; the implementation confirms it and picks another stamp if absent). The job polls `E2E_BASE_URL/` until the meta equals `GITHUB_SHA` (bounded, then fails). The tag carries a public commit hash only; the CSP is unaffected.

### 6.4 CI job

A new `e2e` job in `ci.yml`: `needs: [smoke]`, `if: github.ref == 'refs/heads/main'`, actions pinned to commit SHAs (CLAUDE.md), `pnpm install --frozen-lockfile`, Playwright browser install (cached), `pnpm --filter @sin/web run e2e`, and `actions/upload-artifact` on failure for `apps/web/test-results/` and the HTML report only — **not** `e2e/.auth/`.

## 7. Security & privacy

- **`e2e/.auth/state.json` is secret-equivalent** (a live Auth0 session cookie): gitignored, never uploaded as an artifact, regenerated every run.
- **Traces include request headers** — `Authorization: Bearer …` — so a failure artifact contains a staging access token. Mitigations: failure-only traces, short artifact retention, staging only, tokens expire; accepted for a dedicated test user on a dev tenant.
- **Credentials** only in GitHub Actions secrets; never logged, never in the repo. The test user is non-personal and owns only throwaway data.
- **The job never runs on pull requests** (no secret exposure to PR code) and never against production.
- The `sin-commit` meta is a public commit hash; nothing sensitive is stamped.

## 9. Observability

Playwright's HTML report, failure traces and screenshots, uploaded on failure. The job's red/green status on `main` is the signal; no app-side telemetry is added. A flaky-run pattern (cold starts, Auth0 rate limits) is recorded in the runbook rather than hidden by retries; the config allows at most one retry in CI, and a pass-on-retry is reported as flaky.

## 11. Deployment & rollback

- **Ships as:** a dev dependency, the `e2e/` folder, one workflow job, the meta-tag build change (web bundle; no API change, no migration). Merge to `main` → Render deploys the web bundle → the job runs.
- **Rollout order:** land after 06.1 is deployed and the web post-deploy smoke (the `TODO(Track B)`) is live. The first runs on `main` may fail on setup problems (Auth0 URLs, test user); the job is **not** a required check at first, so a red run never blocks a merge; promote it only once it has been stable across several merges.
- **Rollback:** delete or disable the job (or revert the PR). The meta tag is inert and can stay. Nothing to unwind server-side; the test user and its (deleted-each-run) data are harmless.

## 12. Decisions & open questions

### Resolved

- ✅ **D1 — Runs post-deploy against staging, with a real Auth0 test user (owner decision, 2026-10-01; was 06.1 O9).** Alternatives: **(B)** per-PR against a local stack (Postgres + API + `vite preview`) with the real tenant for login only — needs the SPA client's callback/logout/web-origin lists extended to the preview origin and gives no CSP signal (`vite preview` does not serve the Render headers); **(C)** a fake IdP — rejected: `auth0-spa-js` requires an HTTPS domain, so a faithful fake needs TLS and a re-implemented OIDC surface; a **test-only auth bypass** in the bundle is also rejected — it weakens the smoke and ships test code. **Rationale:** (A) is the only option that tests the real redirect, the real CSP, real hosting and the real cold-load path, and it mirrors the existing post-deploy API smoke. **Cost:** regressions are caught after merge, not before (Vitest/RTL is the pre-merge net); needs a test user, secrets, the SHA wait and serialization. Option (B) is a possible later follow-up.
- ✅ **D2 — Silent refresh-token rotation (Spec 04.0 §10 item 3) is a documented manual check (owner decision, 2026-10-01; was O10).** Automating it needs either a very short staging access-token lifetime or page-clock manipulation: both flaky and tenant-config-dependent. Items 1, 2 and 4 and Spec 04.1's layout items are automated (AC2–AC4).
- ✅ **D3 — Chromium with Pixel 7 emulation only (owner decision, 2026-10-01; was O11).** WebKit (the iOS Safari engine) is the real-world target and `<dialog>` / viewport behavior differs, but a second project doubles CI time and flake surface for a solo project; add WebKit once the Chromium smoke is stable. Real-iPhone behavior stays a manual check (AC7).
- ✅ **D4 — The smoke is split out of Spec 06.1 (owner decision, 2026-10-01; was O12).** Different kind of work, external prerequisites that can stall independently of the screen.
- ✅ **D5 — The smoke logs one set per modality.** The seeded catalog has all five modalities (10 rows), so one session covers every per-modality row against the real API.
- ✅ **D6 — The job is not a required check at first** (§11); a flaky e2e must not block merges while the external setup settles.

### Open

- **Which stamp identifies the web build, if `RENDER_GIT_COMMIT` is not available in a static-site build environment** (§6.3) — unverified; resolved at implementation by checking Render's build environment.
- **Whether the staging web site and the Auth0 SPA client are fully configured** (§1 prerequisites) — unverified; the owner confirms or the Track B checklist is completed first.
- **Test-user email constraints** from Spec 01's claim handling — unverified.
