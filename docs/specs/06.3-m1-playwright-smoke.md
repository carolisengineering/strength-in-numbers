## 1. Purpose, scope & non-goals

Run **one happy-path browser session** against the deployed staging web and API, with a real Auth0 Universal Login, after every merge to `main`: sign in, start a workout, log a set on each of the five modalities, survive a hard reload, reorder / edit / remove, finish, read the summary, delete. It also discharges the browser-only obligations earlier specs explicitly handed to "the M1 smoke" because jsdom cannot show them: the real redirect round-trip and cold-load resume, CSP enforcement, real layout (320 px, tap targets), and the real `<dialog>` focus behavior the 06.0 unit tests only shim.

> **First-principles note (what Playwright is, and why Vitest is not enough).** Vitest runs our code in **jsdom**, a pretend browser written in JavaScript: there is no layout engine (so no real widths, no overflow, no tap-target sizes), no real `<dialog>` focus trapping or Escape handling (hence the `showModal` shim), no CSP enforcement, and no real Auth0 redirect. **Playwright** drives a real browser over the network like a user: it opens pages, finds elements by role and accessible name (`getByRole('button', { name: 'Log set' })` — the names a screen reader uses, so the tests also police accessibility), taps, and waits for results with auto-waiting that avoids most sleeps. A *browser context* is an isolated profile (its own cookies and storage); `storageState` saves a context's cookies so later contexts start already logged in. The cost is speed, a real network, and flakiness — so Playwright here is **one happy-path smoke**, not a second test suite; behavior is tested in the Vitest layer (06.1).

## 2. Acceptance criteria

1. **The M1 happy path runs in a real browser.** Mobile Chromium (Pixel 7 emulation), real Auth0 Universal Login on the staging tenant, the deployed staging web and API: land on `/app/workouts`; discard any leftover in-progress workout through the UI; Start; add one real catalog exercise per modality — Barbell bench press (`weight_reps`), Pull-up (`bodyweight_reps`), Weighted dip (`weighted_bodyweight`), Plank (`duration`), Treadmill run (`distance_duration`) — via the real picker (search, pick); log one set on each, **waiting after every Log set until that set has synced** (§6.5); then, with the outbox empty, hard-reload and confirm all five exercises and all five sets are restored from `GET /v1/workouts/active` (nothing is pending, so Spec 06.2's persisted outbox contributes nothing and the screen can only be showing server data); move one exercise up (Options → Move up) and confirm the order survives a reload; edit one set's value and wait for it to sync; remove one exercise (Options → Remove exercise → confirm); Finish through the confirm dialog (Finish is enabled, i.e. not blocked by 06.2's "N sets not saved yet" gate); see the summary with the remaining sets; Delete the workout from the summary; land on the Start screen.
2. **Zero CSP violations and zero console errors** throughout the run (a `securitypolicyviolation` listener and console capture, asserted empty) — in particular the self-hosted Auth0 worker loads under `worker-src 'self'` and no inline style is blocked (Spec 04.0 §10 item 4; 06.1 §6.8). One console message is exempt, by exact match: Chromium's "Failed to load resource … status of 404" for `GET /v1/workouts/active`, which is how the API says "no workout in progress" (05.0) and which the client turns into the Start screen. Every other failed request still fails AC2 (final review C2, 2026-10-04).
3. **Real layout.** At a 320 px viewport the Start screen and the session screen have `scrollWidth <= clientWidth` (no horizontal overflow) and every visible interactive element is ≥ 44 × 44 CSS px by `getBoundingClientRect` — the 320 px / tap-target checks Spec 04.1 §10 handed to the smoke, extended to the workout screens.
4. **Real dialog, redirect and resume behavior.** Opening the picker puts focus on its Close button (not the search field); Escape closes it and focus returns to "Add exercise"; the confirm dialog traps focus and Escape cancels it (06.0 §5 / §10 handoff). A hard reload of `/app/workouts` (tokens are memory-only, so the page signs in again) issues a navigation to the Auth0 `/authorize` endpoint, shows no credential form, and returns to the same path — the Auth0 session cookie is still valid (Spec 04.0 §10 items 1 and 2: a real Universal Login landing on an authed screen rendered from `GET /v1/me`, and the cold-load path via the `is.authenticated` hint and `returnTo`). "Resuming your session…" is **not** asserted: `PublicEntry` fires `loginWithRedirect` the moment it renders, so the text is on screen for a frame or two and a Playwright assertion on it would be a coin flip; the unit tests own it (04.0 AC4).
5. **The job is safe to run on `main`.** It runs only on pushes to `main`, after the API smoke and the web post-deploy smoke; two runs never overlap (one test user); it waits until the deployed web build's `sin-commit` meta equals the pushed SHA and warms the Render free-plan API before the first test; it uploads failure screenshots and error context only — no traces, no HTML report, never the saved auth state (§7); a leftover workout from a failed prior run is cleaned up by the next run through the UI. The wait uses `RENDER_GIT_COMMIT` (§6.3); a `"dev"` stamp, or a stamp that never matches, fails the job after the bound rather than passing.
6. **The suite is runnable locally.** `pnpm --filter @sin/web run e2e` runs the same specs against `E2E_BASE_URL` / credentials from the environment; the runbook documents it.
7. **The manual checks are written down.** The runbook lists the checks this smoke deliberately does not automate: silent refresh-token rotation without a redirect (04.0 §10 item 3), soft keyboard vs the sticky bar on iPhone Safari and Android Chrome, `env(safe-area-inset-bottom)` with a home indicator (04.1 carry-over).
8. **The build-commit tag is correct and inert.** `index.html` carries `<meta name="sin-commit" content="…">` set from `RENDER_GIT_COMMIT` at build time (`"dev"` when unset; Render sets it at build time and runtime for static sites too); a unit test of the Vite config transform asserts both; the web `assert:build-output` check stays green and the CSP is unchanged.
9. **Docs stay consistent.** DESIGN §8.3 and §9, the README rows, and Spec 06.1 §12 D21–D24 agree with this spec.

## 4. Data model

None server-side. The smoke runs as one dedicated Auth0 user and so owns throwaway rows in the staging database: it deletes its workout at the end of every run, and the next run discards a leftover active workout first. Client-side: `e2e/.auth/state.json` (Playwright `storageState`, gitignored) holds the live Auth0 session cookie and the hint cookie, plus whatever the app origin's `localStorage` held when it was saved (taken right after login, before any set is logged, so it carries no outbox).

## 6. Behavior & logic

### 6.1 Auth strategy

The real Universal Login is driven once per run (`setup` project) and its `storageState` reused by the test project. Each test's cold load therefore exercises the real session-resume path through Auth0's still-valid session cookie without re-entering credentials (AC4). Tokens remain memory-only in the page (Q12): the smoke never reads or injects a token.

### 6.2 Run hygiene

- **Warm-up.** Render's free plan sleeps; the `setup` project polls the API's `/readyz` (≤ ~120 s) **before it logs in**, because the login itself lands on a screen that calls `GET /v1/me` (final review I3), and the smoke's `beforeAll` polls again.
- **Idempotent re-runs.** One active workout per user (05.0): the first step discards a leftover through the UI (which also exercises Discard), and the run ends by deleting its own workout (which exercises delete-after-finish).
- **Serialization.** `concurrency: { group: e2e-staging, cancel-in-progress: false }` in the workflow: two pushes to `main` in quick succession must not race on the one test user.

### 6.3 Knowing the deployed web build is this SHA

The API smoke waits on `/healthz` for the deploy; a static site has no such endpoint, so the smoke could otherwise test the previous build (a false green or a flake). `vite.config.ts` stamps `<meta name="sin-commit" content="${RENDER_GIT_COMMIT ?? "dev"}">` into `index.html` (Render documents `RENDER_GIT_COMMIT` as available at build time and at runtime for every service type, static sites included — render.com/docs/environment-variables, checked 2026-10-04; the first deploy of the implementation PR confirms it in practice). The job polls `E2E_BASE_URL/` until the meta equals `GITHUB_SHA` (bounded, then fails). If the variable were ever absent the stamp is `"dev"`, which never equals a SHA, so the wait times out **loudly** instead of testing a stale build. The tag carries a public commit hash only; the CSP is unaffected. **Superseded runs** (final review I4): if a later push to `main` is deployed before this run's wait, the site serves a commit this SHA is an ancestor of; the script checks that with `git merge-base --is-ancestor` (the job checks out full history), prints a `::notice::`, sets `superseded=true`, and the job skips the tests — that later push's own run tests the build. A stamp that is older, unrelated, `"dev"` or missing still fails after the bound.

### 6.4 CI job

A new `e2e` job in `ci.yml`: `needs: [smoke]`, `if: github.ref == 'refs/heads/main'`, actions pinned to commit SHAs (CLAUDE.md), a first step that skips the rest with a `::notice::` when either credential secret is empty (D10), the credential secrets in the `env` of only that step and the test step (not the job, so install scripts and apt never see them — final review I5), `actions/checkout` with `fetch-depth: 0`, the SHA wait (§6.3) before the install, `pnpm install --frozen-lockfile`, Playwright browser install (cached), `pnpm --filter @sin/web run e2e`, and `actions/upload-artifact` on failure for `apps/web/test-results/` only (screenshots, error context) — **not** `e2e/.auth/`, no traces, no HTML report (§7).

### 6.5 Waiting for a set to sync (Spec 06.2)

Since 06.2, **Log set** resolves immediately: the row appears marked "Not saved yet", the write sits in a persisted outbox (`localStorage` key `sin:workout:outbox`) and a drainer sends it. A reload at that moment would restore the row from the *outbox*, not from `GET /v1/workouts/active`, and AC1 would pass without testing the server. So after every Log set (and after the set edit in step 7) the smoke waits for the synced state before doing anything else:

1. wait for the new row to exist (the card's list item count rises, or the entry row's "Set N" label advances) — this must come first, because "no unsaved text" is also true in the instant before the row renders;
2. `await expect(page.getByText(/not saved yet/i)).toHaveCount(0)` — one locator covering both the row tag and the bar hint; both are 06.2's text (not colour) markers and are present exactly while the outbox holds an op for the workout (06.2 AC14, AC16);
3. `expect(Finish).toBeEnabled()` before the first reload (it is the gate, so it also proves no structure write is in flight).

Before reload step 5 the smoke also reads `sin:workout:outbox` via `page.evaluate` and asserts its `ops` array is empty (`pendingOutboxOps` = 0). The key itself is **not** removed after a full sync: the store keeps an id-map entry per synced set of the current workout (`retainOnly`), and only drops the key when ops *and* id map are both empty (final review C1, 2026-10-04). `e2e/` is outside `apps/web/src`, so 04.0's AC7 source scan for `localStorage` does not apply; keep the read confined to one helper. A set that lands `failed` ("Couldn't save", status line "N sets couldn't be saved") is a smoke failure, not something to work around. The wait uses the generous staging timeout (a free-plan API can be slow), and there is no "Retry now" click: if the drainer does not deliver, that is the signal.

Finish's gate is thereby satisfied by construction, not by sleeping: the smoke taps Finish only after the waits above, and Playwright auto-waits for the button to be enabled.

## 7. Security & privacy

- **`e2e/.auth/state.json` is secret-equivalent** (a live Auth0 session cookie): gitignored, never uploaded as an artifact, regenerated every run.
- **Traces include request headers** — `Authorization: Bearer …` — so a failure artifact contains a staging access token. A trace also records the `Cookie` header of the `/authorize` navigation (the Auth0 session cookie, secret-equivalent like `e2e/.auth`) and, for the login step, the typed password. So: **CI records no traces** (`trace: "off"` when `CI` is set) and the `setup` project never traces, even locally; the uploaded failure artifact is `test-results/` only (screenshots and error context), kept 3 days. **No HTML report**: it stores every step title, and a `fill` step's title is the typed value, so the report would carry the test user's password; the repo is public, so artifacts are downloadable by any GitHub user (security review, 2026-10-04 — reproduced locally: a fake password was in the report's embedded data, and absent from `test-results/` after the fix). The `list` reporter prints no step parameters. Screenshots and the report's error context can show the test user's email (Universal Login clears the password field on failure), which is non-personal. Locally, smoke traces are kept on failure for debugging and never leave the machine (final review I2, 2026-10-04).
- **Credentials** only in GitHub Actions secrets; never logged, never in the repo. The test user is non-personal and owns only throwaway data.
- **The job never runs on pull requests** (no secret exposure to PR code) and never against production.
- The `sin-commit` meta is a public commit hash; nothing sensitive is stamped.
- **Browser storage of the logged-in staging user.** 06.2 persists unsynced set writes in `localStorage` under `sin:workout:` (cleared by `clearUserData`, as are `sin:catalog:` and `sin:recents:`). A passing run's end state leaves nothing that matters there: every set is synced before each reload and before Finish (§6.5), the outbox key is removed when the outbox empties, finishing or deleting clears the workout's ops (06.2 AC17), and the browser context is discarded after the run (only the harmless catalog cache and recents were ever in it). A *failed* run can leave a pending op in a context that is also thrown away, so it cannot leak into the next run; the saved `storageState` is regenerated each run and holds no outbox.

## 9. Observability

Failure screenshots and error context, uploaded on failure (no traces and no HTML report in CI, §7). The job's red/green status on `main` is the signal; no app-side telemetry is added. A flaky-run pattern (cold starts, Auth0 rate limits) is recorded in the runbook rather than hidden by retries; the config allows at most one retry in CI, and a pass-on-retry is reported as flaky.

## 11. Deployment & rollback

- **Ships as:** a dev dependency, the `e2e/` folder, one workflow job, the meta-tag build change (web bundle; no API change, no migration). Merge to `main` → Render deploys the web bundle → the job runs.
- **Rollout order:** 06.1, 06.2 and 06.4 are already on staging and the web smoke passes against it, so this PR can land before the owner actions in §12 (test user, two secrets) are done: until then the `e2e` job skips with a notice (D10). The PR itself turns the `TODO(Track B)` web smoke step on. The first runs on `main` may fail on setup problems (Auth0 URLs, test user); the job is **not** a required check at first, so a red run never blocks a merge; promote it only once it has been stable across several merges.
- **Rollback:** delete or disable the job (or revert the PR). The meta tag is inert and can stay. Nothing to unwind server-side; the test user and its (deleted-each-run) data are harmless.

## 12. Decisions & open questions

### Resolved

- ✅ **D1 — Runs post-deploy against staging, with a real Auth0 test user (owner decision, 2026-10-01; was 06.1 O9).** Alternatives: **(B)** per-PR against a local stack (Postgres + API + `vite preview`) with the real tenant for login only — needs the SPA client's callback/logout/web-origin lists extended to the preview origin and gives no CSP signal (`vite preview` does not serve the Render headers); **(C)** a fake IdP — rejected: `auth0-spa-js` requires an HTTPS domain, so a faithful fake needs TLS and a re-implemented OIDC surface; a **test-only auth bypass** in the bundle is also rejected — it weakens the smoke and ships test code. **Rationale:** (A) is the only option that tests the real redirect, the real CSP, real hosting and the real cold-load path, and it mirrors the existing post-deploy API smoke. **Cost:** regressions are caught after merge, not before (Vitest/RTL is the pre-merge net); needs a test user, secrets, the SHA wait and serialization. Option (B) is a possible later follow-up.
- ✅ **D2 — Silent refresh-token rotation (Spec 04.0 §10 item 3) is a documented manual check (owner decision, 2026-10-01; was O10).** Automating it needs either a very short staging access-token lifetime or page-clock manipulation: both flaky and tenant-config-dependent. Items 1, 2 and 4 and Spec 04.1's layout items are automated (AC2–AC4).
- ✅ **D3 — Chromium with Pixel 7 emulation only (owner decision, 2026-10-01; was O11).** WebKit (the iOS Safari engine) is the real-world target and `<dialog>` / viewport behavior differs, but a second project doubles CI time and flake surface for a solo project; add WebKit once the Chromium smoke is stable. Real-iPhone behavior stays a manual check (AC7).
- ✅ **D4 — The smoke is split out of Spec 06.1 (owner decision, 2026-10-01; was O12).** Different kind of work, external prerequisites that can stall independently of the screen.
- ✅ **D5 — The smoke logs one set per modality.** The seeded catalog has all five modalities (10 rows), so one session covers every per-modality row against the real API.
- ✅ **D6 — The job is not a required check at first** (§11); a flaky e2e must not block merges while the external setup settles.

- ✅ **D7 — Wait for synced state, not a sleep, before every reload and before Finish (2026-10-04; consequence of Spec 06.2).** The signal is the absence of `/not saved yet/i` plus an enabled Finish (§6.5). Alternatives: polling `GET /v1/workouts/active` from the test with the page's token (rejected — the smoke never reads a token, §6.1); a fixed delay (rejected — flaky and slow); reading only the outbox key (kept as a supplementary assertion, not the primary signal, since it is storage rather than user-visible behavior).
- ✅ **D8 — `RENDER_GIT_COMMIT` is the build stamp (2026-10-04).** Render documents it for build time and runtime on all service types, static sites included; fallback `"dev"` fails the SHA wait loudly after its bound. No second stamp mechanism is built.
- ✅ **D9 — "Resuming your session…" is not asserted in the browser (owner decision, 2026-10-04).** It is transient by design; AC4 asserts the observable behavior (the Auth0 `/authorize` round-trip with no credential form, back on the same path).
- ✅ **D10 — The `e2e` job skips with a notice while its credentials are absent (owner decision, 2026-10-04).** Its first step checks `E2E_AUTH0_USERNAME` / `E2E_AUTH0_PASSWORD`; if either is empty it writes a `::notice::` and every later step is skipped, so `main` stays green until the owner actions below are done. Alternatives: fail until set up (rejected — a permanently red job on `main` trains you to ignore it); hold the PR until set up (rejected — couples merging to dashboard work). Once the secrets exist the job runs with no code change. The web origin is not part of the check: `STAGING_WEB_BASE_URL` falls back to the known staging origin in both the web smoke step and this job (2026-10-04, implementation ruling), so a missing variable cannot turn `main` red either.
