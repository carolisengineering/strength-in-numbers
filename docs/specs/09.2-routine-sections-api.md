## 1. Purpose, scope & non-goals

A lifter wants to put a note where it applies — "warm-up: 5 minutes of rowing, then band pull-aparts" belongs to a *group* of exercises, not to one of them and not to the whole routine — read it while training, and see it again afterwards in History. Today a routine has one note (`routine.notes`, never copied to a workout) and each item has one (`routine_item.notes`, copied onto `workout_exercise.notes` by Spec 09 D22). This spec adds the **data and the API**: a routine owns up to eight named **sections** (each with a note) that its items can belong to; starting a workout from the routine **snapshots** the sections, each exercise's section and the routine's own note onto the workout; both are returned on the existing read routes. Spec 10.3 is the UI (the editor's section headers and "Move to section", the session's headings and the per-exercise "Note" action, the History view).

> **First-principles note — "snapshot".** A workout must read the same forever, even after the routine it came from is edited or deleted (Spec 09 D1, the same reason `exercise_name_snapshot` exists). So starting a workout *copies* what the session needs — here the section names and notes, which exercise sits in which section, and the routine's note — into rows and columns that belong to the workout. Nothing on the workout side points back at a routine section, so nothing a later routine edit does can reach it.

> **First-principles note — "whole-document replace with unstable ids".** A routine is edited by sending the *entire* document (`PUT`), and the server deletes and re-creates its items (Spec 09 D2). Row ids are therefore not stable across edits and cannot be used inside the request to say "this item belongs to that section" — the sections do not have ids yet when the body is written. So the body is self-contained: each section carries a **request-local key** (any short label unique within that body), items name their section by that key, and the server maps keys to the new row ids while it inserts. The keys exist only inside one request; they are never stored or returned.

### In scope

- Migration `0011_create_routine_sections`: tables `routine_section` and `workout_section`; columns `routine_item.section_id`, `workout_exercise.section_id`, `workout.routine_notes_snapshot`.
- `@sin/core`: `dto/routine-section.ts` (schemas, limits), pure `sections.ts` (`sectionOrderViolations`, `sectionSpanViolations`, `groupBySection`), branded ids.
- Routine routes: `RoutineWriteSchema` accepts `sections` and per-item `sectionKey`; `Routine` gains `sections`, `RoutineItem` gains `sectionId`; the section rules of §6.1.
- `POST /v1/workouts { routineId }` copies the sections, sets each exercise's `section_id` and snapshots the routine's note (§6.4).
- Workout reads: `WorkoutDetail` gains `sections` and `routineNotes`; `WorkoutExercise` gains `sectionId`.
- Pinning tests for `PATCH /v1/workout-exercises/{id}` `notes` (which already exists, §12) so Spec 10.3 can rely on it.

### Non-goals

- **UI** (Spec 10.3). **No client reads the new fields until 10.3** (DESIGN §6 rollout convention).
- **Editing sections or section membership inside a running workout.** `workout_section` is a snapshot written only by the start copy; `section_id` on an exercise has no write route (D9).
- **Moving a section between routines, section templates, per-section timers**, drag-and-drop (brief).
- **Backfilling sections or routine notes for older workouts.** They read `sections: []`, `routineNotes: null`, `sectionId: null`.
- **Copying the routine's note into `workout.notes`.** The workout's own note is the lifter's; the routine's note travels in its own snapshot column (D5).
- **Changing the History list, the Progress sessions list or `WorkoutSummary`.** FI-7's other question ("exercise history for that day" in the Progress sessions list) is deliberately not covered; the Progress list stays unchanged unless the owner asks (brief).
- **A schema-level limit on notes beyond the existing ones, an advisory lock, a new error slug, a new route** (D8, §5).

## 2. Acceptance criteria

Every behavioral criterion gets ≥1 test naming its number (`describe("AC7 — …")`, the Spec 09 convention). Infra / pipeline criteria are verified by CI or review (§10).

**Shapes and reads**

1. **Contract.** `Routine` (response) gains `sections: RoutineSection[]` and `RoutineItem` gains `sectionId: RoutineSectionId | null`; `WorkoutDetail` gains `sections: WorkoutSection[]` and `routineNotes: string | null`; `WorkoutExercise` gains `sectionId: WorkoutSectionId | null`. All are **required** in `@sin/core` (arrays never null, ids required-nullable; no `.default`, no `.optional()` — Spec 10.1 D4). `RoutineSection` and `WorkoutSection` are each exactly `{ id, position, name, notes }` (`notes` nullable). `WorkoutSchema` (hence `POST /v1/workouts`, the finish `PATCH`, `WorkoutSummary` and every History list row) is **unchanged**: a test pins the key set of a list row. The routine routes and the workout read routes stay published in `/openapi.json` with the new schemas; `401` behavior is unchanged.
2. **Ordered, atomic routine reads.** Every routine read (list, get-one, the `POST` / `PUT` responses) returns `sections` ordered by position from the **same single statement** that reads the header and items (§6.3), extending Spec 09 AC14 / 09.1 AC2: a concurrent `PUT` can never produce a read with the old sections and new items, or the reverse. The strong `ETag` hashes the new bytes: a change of one section's note changes the validator; an unchanged routine keeps it; the first conditional `GET` after the deploy answers `200` (the bytes gained `sections` / `sectionId`), not `304`.
3. **Workout read shapes.** `GET /v1/workouts/{id}` and `GET /v1/workouts/active` return `sections` ordered by position and `routineNotes`; every `WorkoutExercise` they return (and the `201` of `POST /v1/workouts/{id}/exercises`, and the `200` of `PATCH /v1/workout-exercises/{id}`) carries `sectionId`: the copied section's id for a routine-started exercise in a section, `null` for a loose one, for a manually added one and for every workout started before `0011`. A manual workout reads `sections: []`, `routineNotes: null`.

**Routine writes**

4. **Document form.** `POST` / `PUT /v1/routines` accept `sections` (0–8 entries `{ key, name, notes? }`) and, per item, `sectionKey` (a declared key, or `null` / absent for a loose item). Position of a section is its array index (never sent). The response echoes exactly what was stored (the round trip is byte-stable except item and section ids, Spec 09 AC13). A body with no `sections` key stores zero sections — it is the whole document (D6); a body that omits `sections` yet carries an item `sectionKey` is `422` on that item (AC6).
5. **Section field matrix.** Strict, paths `sections.<j>.<field>`: `key` a string matching `^[A-Za-z0-9_-]{1,32}$`, unique within the body (a duplicate → `422` on the later `sections.<j>.key`); `name` trimmed, 1–40 characters, no control characters, **duplicates allowed**; `notes` `null` / absent or 1–2 000 characters, multi-line allowed, no control characters other than TAB / LF / CR (the `noControlCharsExceptWhitespace` rule of item and routine notes); more than **8** sections → `422` on `sections`; `sections: null` → `422`; an unknown key on a section → `422`. All issues of a body are collected into one `422` (Spec 09 §6.2 step 2).
6. **Item references.** An item's `sectionKey` must equal a declared `sections[*].key`, else `422` on `items.<i>.sectionKey`. `null` and an absent key both mean loose; a `sectionKey` that is not a string matching AC5's key pattern is `422` on the same path.
7. **Order invariant.** Items are listed **loose first, then section by section in the declared order, each section as one contiguous run** (a section with no items, and an unused declared section, are fine). Any item that breaks this — a loose item after a sectioned one, an item of an earlier section after a later one, a section split in two runs — is `422` on that item's `items.<i>.sectionKey` ("list loose exercises first, then each section in order"). The server never reorders on the client's behalf (D7).
8. **Supersets stay inside a section.** All items that carry the same `supersetGroup` label must carry the same `sectionKey` (loose counts as one "section"); every later member that differs from the group's first member is `422` on its `items.<i>.supersetGroup` ("a superset can't span sections"). Spec 09's other group rules — 2–8 members, dense renumbering by first appearance across the whole document — apply unchanged. A document that satisfies AC7 and AC8 is stored with `routine_item.superset_group` exactly as Spec 09 would store it.
9. **Whole replace replaces sections.** A `PUT` replaces the item list **and the section list** in one transaction (sections and items are deleted and re-inserted with fresh ids; no section from the previous document survives); a `PUT` that fails (`422`, `409`) leaves the routine, its sections and its items exactly as they were (Spec 09 AC13 extended). Deleting a routine deletes its sections (cascade). A body with `sections: []` removes every section.
10. **Optional everywhere.** A routine with no sections, with sections and no loose items, with some items loose and some sectioned, with an **empty** section, or with several sections sharing a name, is stored and read back exactly as sent. The Spec 09 floor (≥ 1 item, D18) is unchanged.
11. **Spec 09 / 09.1 rules are unchanged.** For a section-free document everything in Spec 09 / 09.1 behaves byte-for-byte as before apart from `sections: []` and `sectionId: null` in responses: a recorded set of request bodies produced by the Spec 10.2 editor (no `sections`, no `sectionKey`) replays with the same status codes and the same stored targets and planned sets. Name rules, limits (50 / 30 / 8), RPE, planned sets, `exercise-retired`, last-write-wins, delete and the authorization boundary (Spec 09 AC5–AC15, AC28; 09.1 AC3–AC10) pass **unmodified** apart from additive `sections` / `sectionId` assertions.
12. **Body size.** The legal maximum document of Spec 09.1 AC11 plus 8 sections with 40-character names and 2 000-character notes (≈ 17 KB more, ≈ 91 KB in all) is accepted under the existing 128 KiB route `bodyLimit`; the global 64 KiB limit and every other route are untouched.

**Start from a routine and workout reads**

13. **Start copies the sections.** `POST /v1/workouts { routineId }` copies the routine's sections to `workout_section` (`position`, `name`, `notes` verbatim, fresh ids) in the same transaction, under the same `FOR SHARE` on the routine, and sets `workout_exercise.section_id` of each copied exercise to the workout section created from its item's section (matched on section position); a loose item gets `NULL`. **Empty sections are copied too** (a section note such as "5 minutes of rowing" is an instruction with no exercise). A routine with no sections copies none and the response is exactly today's.
14. **The routine's note is snapshotted.** The same transaction sets `workout.routine_notes_snapshot` to the routine's `notes` verbatim (`NULL` → `NULL`). `workout.notes` is not touched (it stays whatever the start request sent). A manually started workout has `routine_notes_snapshot IS NULL`. Only the detail read selects the column (AC3).
15. **The workout stays self-contained.** After a start, editing, replacing or deleting the routine changes nothing in the workout's `sections`, `routineNotes` or any exercise's `sectionId` (Spec 09 AC21 / 09.1 AC13 extended). Deleting a workout deletes its `workout_section` rows (cascade). There is no route that writes `workout_section`, `routine_notes_snapshot` or `section_id`.
16. **Replay and atomicity.** An idempotent replay of the start returns the stored workout and **never re-reads the routine or copies again** (Spec 09 AC18 / AC33; tested after the routine was replaced with different sections and deleted); a failed start (`404`, `409 exercise-retired`, `409 workout-in-progress-exists`) leaves no `workout`, no `workout_section` row and no `routine_notes_snapshot`.
17. **Running-workout writes never touch sections.** `POST /v1/workouts/{id}/exercises` creates a **loose** exercise (`sectionId: null`) whatever the workout's sections; `PATCH /v1/workout-exercises/{id}` with `position` and / or `supersetGroup` (Spec 05.0 / 09 AC23) never changes `section_id`; `UpdateWorkoutExerciseSchema` stays strict, so a `sectionId` key is `422`. Removing an exercise leaves its section (possibly now empty) in place.
18. **Exercise notes via `PATCH` are pinned.** `PATCH /v1/workout-exercises/{id}` already accepts `notes` (§12): `{ notes: "x" }` sets it, `{ notes: null }` clears it, an absent key leaves it, a `position`-only or `supersetGroup`-only body never alters it (Spec 10.1 AC11's guarantee, server side), `""` and more than 4 000 characters are `422` on `notes`, and a finished workout answers `409 workout-finished`. These are tests of existing behavior, added so Spec 10.3 can rely on it.
19. **Logging and records are indifferent.** A section-started workout creates no `set_entry`; the finish integrity rule (Spec 05.1) and the PR engine (Spec 07.0, including `records:rebuild`) read `set_entry` only and produce identical results with and without sections.

**Migration**

20. **Migration `0011`.** Additive only; applies cleanly over `0001–0010` with existing data untouched. The database itself rejects (raw SQL insert / update) on each section table: a `position` outside 0–7, a duplicate `(parent, position)`, a `name` that is empty, longer than 40 characters or not trimmed, a `notes` that is empty or longer than 2 000 characters; on `workout`, a `routine_notes_snapshot` that is empty or longer than 2 000 characters. Deleting a `routine_section` sets its items' `section_id` to `NULL` (never deletes them); deleting a `routine` / `workout` cascades its sections; both `section_id` columns are indexed (§4).
21. **No backfill.** On a database holding routines and workouts written before `0011`: no section row is created, `routine_item.section_id` / `workout_exercise.section_id` / `workout.routine_notes_snapshot` are `NULL` everywhere, no existing column value changes, and every pre-`0011` routine and workout reads with `sections: []` and `sectionId: null` (and `routineNotes: null`).
22. **No-drift check moves.** `prisma migrate diff` (migrated database → `schema.prisma`) reports no difference beyond the two generated `set_entry` columns, asserted in `0011`'s integration test (`routine-sections-migration`); `planned-sets-migration.integration.test.ts` keeps its `0010` constraint checks but no longer carries the whole-schema diff (CLAUDE.md: it lives in the newest migration's test).
    > **Amended by Spec 09.3 (2026-10-22):** the whole-schema no-drift check moved on to `routine-one-off-migration` (`0013`).
23. **Account purge.** `DELETE FROM "user"` cascades both new tables in one statement; the purge fixtures contain at least one row in each (so Spec 11 AC23's "every discovered table had victim rows" guard stays green), and the discovery test needs no allowlist entry (the new foreign keys are `CASCADE` or `SET NULL`).

**Cross-cutting**

24. **Export.** The account export (Spec 11) carries `sections` and `sectionId` on routines and `sections`, `routineNotes` and `sectionId` on workouts, composed through the shared `routes/mappers.ts` DTO builders; Spec 11's parity AC (export deep-equals the read routes) passes with section rows in the fixture, and the export still issues **≤ 8** statements (the workout sections are aggregated into the existing workout statement, §3).
25. **Pure helpers.** `@sin/core` `sections.ts` (no I/O, no imports beyond core siblings; `core:purity` green) exports `sectionOrderViolations`, `sectionSpanViolations` and `groupBySection` with the behavior of §5; the API uses the first two for AC7 / AC8 and Spec 10.3 reuses all three, so server and editor cannot disagree.
26. **Strict schemas stay strict.** Core tests pin that a `Routine` without `sections`, a `RoutineItem` without `sectionId`, a `WorkoutDetail` without `sections` / `routineNotes` and a `WorkoutExercise` without `sectionId` fail `safeParse`; no `.default(…)` / `.catch` anywhere in `@sin/core` or `apps/web` for these fields (a source scan).
27. **Error contract, OpenAPI, rate limits.** No new error slug and no new route; the new `422` paths use the existing `validation-error`; `/openapi.json` is regenerated (CI drift check green) and the `contract-pipeline` / problem-matrix tests need no row change; routine writes stay in the `routines` write group; `RATE_LIMITS` is unchanged.
28. **Logging hygiene.** `routine_created` / `routine_updated` and `workout_started_from_routine` gain `section_count` — a count only; no section name, section note, routine note or exercise note appears in any captured line (Spec 09 AC30 / 09.1 AC26 extend).
29. **Concurrency.** Two racing `PUT`s of one routine, and a `PUT` racing a start, always leave / return one complete document: a started workout carries either the old sections with the old item→section mapping or the new ones, never a mix, and `assertSectionsConsistent(db)` (every item's section belongs to its own routine; every exercise's section to its own workout; every section position dense from 0) holds after each test. No advisory lock is added (D8).
30. **Worst-case read is bounded.** Spec 09.1 AC27's maximum fixture extended with 8 sections on each of 50 routines is returned by `GET /v1/routines` in **one** database statement and under a loose time bound (CI tripwire, set at implementation from a local run, ×5).
    > **Amended by Spec 09.3 (2026-10-22):** the list now also runs the expiry sweep probe, so the statement count this criterion bounds includes it.
31. **Docs and release order.** DESIGN.md §4.3 / §4.4 / §4.9 / §6 / §9 / Q21 and the README rows match this spec (§11 list); the release order of §11 (migration `0011` before the code; API before Spec 10.3) is stated in the PR description and the runbook note.

## 4. Data model

Migration `apps/api/prisma/migrations/0011_create_routine_sections/migration.sql`, hand-authored like `0009` / `0010` (CHECKs and unique indexes carry the contract; `schema.prisma` gains `RoutineSection` and `WorkoutSection` models, the two `sectionId` fields and `Workout.routineNotesSnapshot`, and the CI `prisma migrate diff` check is the guard — AC22). Additive / expand-only: no existing column is dropped, renamed or retyped; there is no backfill.

```sql
-- Spec 09.2 §4 — 0011_create_routine_sections. Additive, expand-only.
-- Down (dev/test teardown only; production undo is `git revert` + a forward migration):
--   ALTER TABLE "workout_exercise" DROP COLUMN "section_id";
--   ALTER TABLE "routine_item" DROP COLUMN "section_id";
--   ALTER TABLE "workout" DROP COLUMN "routine_notes_snapshot";
--   DROP TABLE "workout_section", "routine_section";

CREATE TABLE "routine_section" (
    "id"         UUID           NOT NULL,
    "routine_id" UUID           NOT NULL,
    "position"   SMALLINT       NOT NULL,
    "name"       TEXT           NOT NULL,
    "notes"      TEXT,
    "created_at" TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    "updated_at" TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    CONSTRAINT "routine_section_pkey" PRIMARY KEY ("id"),
    CONSTRAINT "routine_section_routine_fkey" FOREIGN KEY ("routine_id") REFERENCES "routine"("id") ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT "routine_section_position_check" CHECK ("position" BETWEEN 0 AND 7),
    CONSTRAINT "routine_section_name_check" CHECK (char_length("name") BETWEEN 1 AND 40 AND "name" = btrim("name")),
    CONSTRAINT "routine_section_notes_check" CHECK ("notes" IS NULL OR char_length("notes") BETWEEN 1 AND 2000)
);
-- Not deferrable: PUT deletes a routine's sections before re-inserting (§6.2).
-- Also the FK lookup index, and with the position CHECK it caps a routine at 8 sections.
CREATE UNIQUE INDEX "routine_section_routine_position_key" ON "routine_section" ("routine_id", "position");

CREATE TABLE "workout_section" (
    "id"         UUID           NOT NULL,
    "workout_id" UUID           NOT NULL,
    "position"   SMALLINT       NOT NULL,
    "name"       TEXT           NOT NULL,
    "notes"      TEXT,
    "created_at" TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    "updated_at" TIMESTAMPTZ(6) NOT NULL DEFAULT now(),
    CONSTRAINT "workout_section_pkey" PRIMARY KEY ("id"),
    CONSTRAINT "workout_section_workout_fkey" FOREIGN KEY ("workout_id") REFERENCES "workout"("id") ON DELETE CASCADE ON UPDATE CASCADE,
    -- the same three CHECKs, named workout_section_{position,name,notes}_check
);
CREATE UNIQUE INDEX "workout_section_workout_position_key" ON "workout_section" ("workout_id", "position");

ALTER TABLE "routine_item"
    ADD COLUMN "section_id" UUID,
    ADD CONSTRAINT "routine_item_section_fkey" FOREIGN KEY ("section_id") REFERENCES "routine_section"("id") ON DELETE SET NULL ON UPDATE CASCADE;
CREATE INDEX "routine_item_section_idx" ON "routine_item" ("section_id") WHERE "section_id" IS NOT NULL;

ALTER TABLE "workout_exercise"
    ADD COLUMN "section_id" UUID,
    ADD CONSTRAINT "workout_exercise_section_fkey" FOREIGN KEY ("section_id") REFERENCES "workout_section"("id") ON DELETE SET NULL ON UPDATE CASCADE;
CREATE INDEX "workout_exercise_section_idx" ON "workout_exercise" ("section_id") WHERE "section_id" IS NOT NULL;

ALTER TABLE "workout"
    ADD COLUMN "routine_notes_snapshot" TEXT,
    ADD CONSTRAINT "workout_routine_notes_snapshot_check"
        CHECK ("routine_notes_snapshot" IS NULL OR char_length("routine_notes_snapshot") BETWEEN 1 AND 2000);
```

Notes:

- **`ON DELETE SET NULL`, and the partial indexes.** Deleting a section must never delete the exercises in it (the editor's "delete section keeps its exercises", Spec 10.3), so the item-side foreign key is `SET NULL`; the workout-side one is `SET NULL` for symmetry. Postgres implements `SET NULL` by scanning the referencing table for the deleted section's id; without an index every section delete — including the cascade when a whole workout or routine is deleted — would sequentially scan `workout_exercise` / `routine_item`. The partial indexes (only non-null values) make that lookup cheap and cost nothing for the common loose item (D11).
- **Single-column foreign keys.** Nothing in the schema forces an item's section to belong to the item's own routine; the single write path does (as it does for the derived columns of 09.1 §4). A composite `(routine_id, section_id)` foreign key would, but Prisma's schema language cannot express the `SET NULL (column)` form it would need and the no-drift check would flag it (D11). `assertSectionsConsistent` (AC29) is the test-side guard.
- **Limits.** Name 1–40 trimmed (`btrim`), duplicates allowed (no unique index on the name); section `notes` 1–2 000, the same bounds as `routine.notes` (D3); the routine snapshot is 1–2 000, the same bounds as `routine.notes` (the copy is verbatim). `position` 0–7 plus the unique index is the DB-level cap of 8 sections per routine, the 09.1 D4 defense-in-depth.
- **`workout_section.name` / `notes` are the routine's, copied verbatim**, so the same CHECKs hold for the copy by construction.
- **`created_at` / `updated_at`** because DESIGN §4.0 says every table carries them; informational (rows are replaced or snapshotted, never updated in place).
- **ids:** the application inserts `routine_section` rows with `uuidv7()` ids; the start copy inserts `workout_section` rows in SQL with `gen_random_uuid()` (Postgres 16 has no `uuidv7()`; 09.1 D6).
- **The `0011` lock profile:** two `CREATE TABLE`s, three nullable `ADD COLUMN`s (metadata-only) and two foreign-key additions whose validation scans `routine_item` / `workout_exercise` once while holding a lock that blocks writes to them; both tables are small (a beta's worth of rows), so the window is milliseconds. No row is rewritten.
- **Hard purge:** both tables cascade from their parents (`routine` ← `user`; `workout` ← `user`); the `SET NULL` edges are on the allowed list of Spec 11's discovery test by their rule — no purge-ordering step (AC23).

## 6. Behavior & logic

### 6.1 Validation order (POST / PUT; extends Spec 09 §6.2 / 09.1 §6.1)

1. Zod: shape, ranges, strict keys, `sections.length ≤ 8`, section field rules (AC5), item `sectionKey` pattern.
2. Zod `superRefine`: duplicate keys; each item's `sectionKey` resolved to an index into `sections` (an undeclared key, or any key when `sections` is absent, is an issue on `items.<i>.sectionKey` and that item's ref counts as unresolved so it raises no second issue); then `sectionOrderViolations` and `sectionSpanViolations` over the resolved refs; then the existing item rules (09 / 09.1). All issues collected.
3. Repository transaction: unchanged from 09.1 (exercise visibility → retired → modality).

Shape errors still never take a lock or run a query: every section rule is a function of the body alone.

### 6.2 Create and replace

As Spec 09 §6.3 / 09.1 §6.3, with sections inserted between the routine row and the items:

- **Create:** advisory lock, cap count, `INSERT routine`, `assertItemExercisesUsable`, then **one bulk `INSERT INTO "routine_section"`** for all sections (≤ 8 rows, ids from `uuidv7()` in the application, kept in a `key → id` map), then `insertItems` with each item's `section_id` taken from the map, then the planned-set insert.
- **Replace:** `SELECT … FOR UPDATE` on the routine row (the lock order of Spec 09: row lock only), exercise checks, `UPDATE routine`, `DELETE FROM routine_item`, **`DELETE FROM routine_section`**, then the same inserts as create. Items go first so the `SET NULL` action has nothing to do; the delete-then-insert order is what lets `routine_section_routine_position_key` stay non-deferrable. `created_at` and the lock rules are unchanged.

### 6.3 Reads

- **Routine:** `ROUTINE_WITH_ITEMS` gains `'section_id', ri.section_id` in each item's `json_build_object` and a second scalar column `COALESCE((SELECT json_agg(json_build_object('id', s.id, 'position', s.position, 'name', s.name, 'notes', s.notes) ORDER BY s.position) FROM "routine_section" s WHERE s.routine_id = r.id), '[]'::json) AS sections`. It stays **one statement**, so the Spec 09 AC14 / ETag guarantee (no torn document) extends to sections (AC2). `RoutineDbRow` / `ItemDbRow` / `toRoutine` / `toRoutineItemDto` gain the fields; `toRoutineDto` keeps schema key order (the ETag hashes the bytes).
- **Workout:** `loadExercises` selects `section_id`; `toDetail` issues one more statement for the workout's `sections` (`ORDER BY position`) and reads `routine_notes_snapshot` — only the detail path selects the column; the many other `workout` `SELECT`s (history list, finish, start) are untouched. The add route's `RETURNING` and the patch route's `RETURNING` list `section_id` (the column exists, so add returns `null` with no special case). `toExerciseRecord` / `WorkoutExerciseDbRow` and `WorkoutDetailRecord` gain the fields, which is how the shared mapper carries them to Spec 11.
- The routine `ETag` changes for every routine at deploy (the bytes gained `sections` and `sectionId`); clients revalidate once with a `200` (AC2).

### 6.4 Start from a routine (extends Spec 09 §6.5 step 4 and 09.1 §6.4)

Steps 1–3 are unchanged, except that the `FOR SHARE` `SELECT` of the routine also returns `notes`. Immediately after the workout insert, still inside the transaction and under that `FOR SHARE`, **before** the item read:

```sql
INSERT INTO "workout_section" (id, workout_id, position, name, notes, created_at, updated_at)
SELECT gen_random_uuid(), $workout, rs.position, rs.name, rs.notes, now(), now()
FROM "routine_section" rs
WHERE rs.routine_id = $routine
```

The item read gains `ws.id AS section_id` through `LEFT JOIN "routine_section" rs ON rs.id = ri.section_id LEFT JOIN "workout_section" ws ON ws.workout_id = $workout AND ws.position = rs.position`, and the `workout_exercise` `INSERT` writes it. The join on **section position** is exact: the copy above gave each `workout_section` its routine section's `position` verbatim (unique within each parent), so each exercise lands in precisely the section created from its item's section. The final `UPDATE "workout" SET routine_id, routine_name_snapshot` also sets `routine_notes_snapshot = $routineNotes`. The statement returns the inserted section count, which feeds the log line (§9). The replay path (Spec 09 step 1, no row inserted) returns before any of this — it never reads the routine or copies twice (AC16). A failure anywhere rolls the whole transaction back.

### 6.5 Workout-side structure is stored as sent (D4, D9)

The server does **not** enforce "loose first, contiguous runs" or "a superset stays inside a section" on a workout. Exercises added during the workout are loose and appended at the end — after the last section — and a lifter may reorder exercises (`PATCH position`) or link them (`PATCH supersetGroup`, Spec 09 D10: no adjacency or density rule on a workout). So a workout's list can legitimately hold a loose tail after sectioned runs, and, from a client that does not respect the rule, a section split into two runs or a group spanning two sections. Every consumer must **tolerate** such lists (Spec 10.3 renders maximal runs and breaks superset runs at section boundaries); the invariant is a promise of the routine editor and the routine write API, not a workout-side constraint.

### 6.6 Edge cases

- A routine with sections but whose items are all loose is legal (all sections empty); the start copies the empty sections and the session shows their headings and notes.
- Two sections may share a name; the order of positions is the only identity.
- An item whose exercise is retired later keeps its `section_id`; the start still fails `409 exercise-retired` (Spec 09 AC17), so no section is copied for a retired start.
- A `PUT` of an unchanged document still re-creates sections and items (new ids; the `ETag` changes by the ids only, Spec 09 §6.8).
- A legacy-form body — from the Spec 10.2 editor, which sends no `sections` — **removes the routine's sections** and clears every item's section: the body is a whole replacement (D6). That is the contract, not a bug; it matters for a Spec 10.3 rollback (10.3 §11). While no client creates sections (until 10.3 merges) there is nothing to lose.
- Old code after a rollback of this spec: its routine `PUT` deletes the items but leaves `routine_section` rows in place, now empty; the new code later reads them as empty sections (harmless; §11).
- The routine's `notes` and a section's `notes` may be long multi-line text; the workout's `workout.notes` and every exercise note are unaffected by the start.

## 7. Security & privacy

- **Authorization is inherited, with no new surface.** There is no route addressed by a section id; sections are reached only through a routine or workout the caller owns (every Spec 09 query is `user_id = $acting`; the start copy joins from the user-scoped routine under `FOR SHARE`). User B cannot read, write or copy A's sections (Spec 09 AC28 extends: the fixture includes sections). A foreign section id cannot be named at all — items refer to sections by request-local key, and the only ids the server writes into `section_id` are ones it just inserted for the same routine or workout.
- **Mass-assignment.** `RoutineSectionInputSchema` is strict; ids, positions, timestamps and `sectionId` are never accepted (AC5, AC17).
- **Abuse bounds.** ≤ 8 sections per routine (schema and DB), ≤ 2 040 characters per section, so ≤ 50 × 8 × ≈ 2 KB ≈ 0.8 MB per user at the absolute maximum on top of 09.1's plan rows, inside the bounded unpaged list (AC30 is the tripwire; real routines hold a few short notes). Bodies stay at 128 KiB; the `routines` write group (30 / min) and the in-flight cap bound the write rate.
- **PII / sensitivity.** Names and notes are free text a lifter may use for health information ("left shoulder — keep it light"). They are never logged (§9), are included in the account export and removed by the purge (AC23, AC24), and are rendered as text, never as markup, by every client (Spec 10.3 AC36).
- **Cache.** Routine reads stay `private, no-cache` + `ETag`; workout reads stay `no-store`; error bodies carry no section values.
- **No new secret, no new egress, no new dependency.**

## 11. Deployment & rollback

`0011` is additive and expand-only: two new tables, three nullable columns and two foreign keys; a sub-second lock on `routine_item` / `workout_exercise` while the foreign keys validate (§4).

**Release order (hard dependency; extends Spec 09 §11 / 09.1 §11):**

1. **Migrate first.** `DATABASE_URL='<neon direct url>' pnpm run db:migrate:deploy` applies `0011` **before** the code goes live (manual step, never on boot). Old code ignores the new tables and columns, so the migration safely precedes it. Verify with `db:migrate:status` on Neon (the 2026-10-04 incident: do not assume).
2. **Then merge 09.2** → Render auto-deploys the API. The same commit also redeploys the static web site, whose `@sin/core` schemas now require `sections` / `sectionId` / `routineNotes`; for the minutes in which the new bundle is live against the not-yet-deployed API the routine and workout screens would fail to parse. This is accepted on staging (single tester, no data effect, self-healing), exactly as 09.1 §11 step 2 — the convention's "API one release ahead" is honored at the level of verified deploys, and it is why the web gains no *use* of the fields in this release.
3. **Verify** on staging: `GET /v1/routines` shows `sections: []` and `sectionId: null` on every routine; `GET /v1/workouts/active` (or any `GET /v1/workouts/{id}`) shows `sections` and `routineNotes`; run the **consistency queries** (items whose section belongs to a different routine; exercises whose section belongs to a different workout — both expected 0) and record them in `docs/runbooks/first-deploy.md` as a short "0011" note. There is no backfill and no rollout-window hazard: old code never writes the new columns, and no client creates sections until Spec 10.3.
4. **Spec 10.3 may merge only after step 3** (API one release ahead).

**Rollback:** revert the code commit. The tables and columns stay, inert. Old code reads new-code routines correctly (it ignores sections); an old-code routine `PUT` deletes the items — clearing `section_id` — but leaves the section rows, which the new code would later read as empty sections. Workout snapshots keep their `workout_section` rows and `section_id`s; old code ignores them. Production undo is a forward migration, never a down script. After a revert, 10.3 (if merged) must be reverted too (DESIGN §6). Rolling 09.2 back **while sections exist** leaves routines whose sections silently vanish from the old editor and are flattened on its next save (D6) — say so in the PR description.

**No feature flag** — "off" is the absence of a UI consumer until Spec 10.3.

## 12. Decisions & open questions

### Resolved (owner-approved 2026-10-13, from the brief)

- ✅ **D1 — Section rows and a nullable `section_id` on items (brief decision 6, "approach 1").** `routine_section`, `workout_section`, `routine_item.section_id`, `workout_exercise.section_id`. **Rationale:** sections are queryable, constrained by the database (length, position, cap) and flow through the shared read DTOs to the export. **Rejected:** heading pseudo-rows in the item list (every consumer — start copy, supersets, counts, History, export — would filter by row kind); a JSON column on `routine` (not queryable, no CHECKs, and it contradicts Spec 09 D1's rejection of a JSON snapshot and the rule that DTOs flow to the export).
- ✅ **D2 — Optional everywhere (brief decision 1).** A routine may have no sections, use only some, or have empty ones; an item may be loose; loose items sit before the first section. **Rationale:** sections must never be a tax on the ten-second routine; the invariant "loose first" is what makes "no section" a place on the screen rather than a hole.
- ✅ **D3 — Names are free text, 1–40 characters, duplicates allowed; the five starters are UI copy only; ≤ 8 sections; section notes take the routine-note limit, 2 000 (brief decision 2 and open item 1; owner ruling 2026-10-13).** The code has two existing note limits — `ROUTINE_NOTES_MAX` 2 000 for the routine and `ROUTINE_ITEM_NOTES_MAX` 500 for an item, with `WORKOUT_NOTES_MAX` 4 000 for a workout or workout-exercise note. The owner chose 2 000, the routine's, so a section can hold a short coaching paragraph; the routine snapshot is 2 000 too. The cost is layout: a long note pushes the first exercise down a phone screen (Spec 10.1 O3 is the precedent), which Spec 10.3's phone check watches (it may add a clamp). Raising later is a forward migration; lowering is not. **Rationale for free text:** no vocabulary table to migrate or localize; starters are a convenience the UI offers, and storing plain text means a future starter list changes no data. **Rejected:** a unique name per routine (two "Accessory" blocks are legitimate and the position is already the identity).
- ✅ **D4 — A superset lives inside one section (brief decision 3).** Enforced by the server on routine writes (AC8); on a workout, stored as sent (Spec 09 D10 has no adjacency rule there) and tolerated by every consumer (§6.5). **Rationale:** a bracket drawn across a section heading is a contradiction on screen; rejecting it at the routine write keeps the data clean where one client controls the shape, while the workout side keeps the "half-applied state is acceptable" property that Spec 10.1's regroup planner relies on.
- ✅ **D5 — The routine's note is snapshotted in its own column and shown in both the session and History; section names and notes are snapshotted onto the workout (brief decisions 4 and 5).** `workout.routine_notes_snapshot` and `workout_section`; the routine's note is **not** copied into `workout.notes`. **Rationale:** `workout.notes` is the lifter's own free text and a later spec may give it a UI; mixing the routine's text into it would make "what did I write" and "what did the routine say" indistinguishable and un-copyable twice. Session edits to an exercise note stay in that workout (the existing `PATCH` writes only `workout_exercise.notes`) — nothing writes back to the routine, because no route does.
- ✅ **D6 — A routine write is the whole document; sections travel with request-local keys (brief, "API").** `sections: [{ key, name, notes? }]`, items `sectionKey`. A body with no `sections` key has no sections — it flattens the routine's sections exactly as a legacy-form body flattened plans (09.1 D11). **Rationale:** whole-replace with unstable ids (Spec 09 D2) cannot reference rows that do not exist yet; "preserve existing sections when the key is absent" would need item→section identity the replace cannot keep, and a partial-merge rule is exactly what whole-replace exists to avoid. The cost — an old editor re-saving a sectioned routine flattens it — is accepted and documented for a 10.3 rollback. **Rejected:** a `sectionIndex` integer on items (simpler, but couples items to array order, so a reordered or hand-edited body silently re-points items; the keys cost one duplicate check); heading rows (D1).
- ✅ **D7 — Order is validated, never repaired (brief).** A body that is not loose-first / contiguous / in declared order is `422`. **Rationale:** silently reordering would change what the lifter sees without telling the client; the editor's `settle` already produces canonical order, so a violation is a client bug worth surfacing, and the same helper (`sectionOrderViolations`) serves both sides.

### Resolved by reading the code (corrections and qualifications to the brief)

- ✅ **D8 — No new advisory-lock key (brief: "own advisory-lock key, never reuse one").** The advisory lock in this codebase guards *count-then-insert* caps across separate requests (`routine:` + user id for 50 routines, `hashtext(user_id)` for custom exercises). The 8-section cap is a property of one request body: a `PUT` already holds the routine row `FOR UPDATE` and replaces all sections at once, a `POST` creates a brand-new routine nobody else can write, and the DB `position` CHECK + unique index is the backstop (the 09.1 D4 defense-in-depth). There is no interleaving that can exceed 8, so a lock would add contention for nothing. AC29 tests the real concurrency (PUT vs PUT, PUT vs start) instead, and CLAUDE.md records "no new key".
- ✅ **D9 — `section_id` on a workout exercise has no write route; exercises added to a running workout are loose (brief).** The workout-side structure is a snapshot; moving a running workout's exercise between sections would need a new `PATCH` key, a snapshot-editing rule and a UI, none of which the brief asks for. **Consequence (Spec 10.3):** the session must keep Move up / Move down inside a section and render a loose tail honestly; the server permits any `position` order (§6.5).
- ✅ **D10 — `PATCH /v1/workout-exercises/{id}` already accepts `notes`; no API change (the brief says the route "gains `notes`" — it does not need to).** `UpdateWorkoutExerciseSchema` has `notes: WorkoutNotes.nullable().optional()` (1–4 000 characters, no control characters except TAB / LF / CR), the repository applies it by key presence (`"notes" in patch`), `null` clears, and a position-only or group-only body never reads it. What is missing is purely client-side: the web `WorkoutExercisePatch` deliberately has no `notes` key (Spec 10.1 AC11). So this spec adds **tests** that pin the existing behavior (AC18), not a field. The same `422` / `409 workout-finished` / `writeGroup: workouts` rules apply, and the 4 000-character ceiling is higher than the 500 a routine item carries, which is why Spec 10.3 caps the *editor* (not the API) at 500 (10.3 D6).
- ✅ **D11 — Foreign keys are single-column `ON DELETE SET NULL` with partial indexes (brief: "ON DELETE SET NULL" on the routine side, silent on the workout side).** See §4. A composite same-parent foreign key was considered and rejected: Prisma cannot express `SET NULL (column)` and the whole-schema no-drift check (AC22) would fail.
- ✅ **D12 — Section rules live in a new `@sin/core` `sections.ts`; `supersets.ts` is unchanged (brief: "`supersets.ts` gains the section check").** `supersets.ts` operates on `SessionSlot { id, group }`; a section check needs a third field and the module is the pinned contract of Spec 10.1 (AC4's "tolerant inputs"). A sibling module over plain index arrays gives the API and the editor the same functions without widening that contract; the editor's `settle` still sits on top and the property test of Spec 10.3 AC6 checks it against the core helpers.
- ✅ **D13 — The export's workout side needs hand edits (brief: "gains sections for free").** Routines: free. Workouts: three edits to `account-export.prisma.ts` (§3), with the sections folded into the workout statement so AC8 of Spec 11 (≤ 8 statements) is not at risk.
- ✅ **D14 — `sections` and `routineNotes` ride on `WorkoutDetail` only.** **Rationale:** the brief says History list rows stay unchanged, and `WorkoutSchema` is shared by the start, finish and list routes; adding fields there would widen each of them for a screen that reads only the detail. Same pattern as 07.0 D12 (`newRecords` on a new name rather than on the shared schema).
- ✅ **D15 — Response-field rollout (DESIGN §6).** API one release before the UI; required fields; the same-commit web redeploy caveat is the one 09.1 already accepted (§11 step 2).
