## 1. Purpose, scope & non-goals

Replace the app's generic dark-blue look with the **Stone** identity: a calm, light-first, warm-neutral system where color only ever means something. The app keeps every screen, control and word it has today; this spec changes how they are painted and typeset.

> **First-principles note — what a "token" buys us.** Every color in the app is a CSS custom property (a variable) declared once in `src/ui/tokens.css`; component stylesheets only say `var(--color-text)`. Re-theming is therefore a change to one file, plus the places where a component picked the *wrong role* for a color (e.g. "accent" used for links, tabs, charts and buttons alike). Most of this spec's work is the second part: deciding what each color *means* and re-pointing components accordingly.

> **First-principles note — light/dark.** Browsers expose the OS setting as the media query `prefers-color-scheme`. CSS in `:root` is the default; a `@media (prefers-color-scheme: dark)` block overrides it. The `color-scheme` property additionally tells the browser to draw its own widgets (scrollbars, native select popups, autofill) in the matching theme. A user override has to beat the OS setting, and a media query cannot be overridden from outside, so the override is an attribute on `<html>` (`data-theme="light|dark"`) that the CSS selects on; a tiny bit of JavaScript sets it from a stored preference. With the attribute absent ("System") the media query rules alone.

> **First-principles note — tabular figures.** Many fonts draw `1` narrower than `0`, so a column of weights ("135", "225", "115") does not line up and a ticking duration jitters. OpenType has a feature, `tnum`, that swaps in equal-width digits; CSS turns it on with `font-variant-numeric: tabular-nums`. Instrument Sans has `tnum` (verified 2026-10-15: all ten digits at one width) but its *default* digits are proportional, so we must switch it on.

### In scope

- **Theme mechanism.** Light is the base `:root`; dark applies through two selectors carrying identical values: `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` (System, or an explicit Dark) and `:root[data-theme="dark"]` (flipping today's dark-default / light-override).
- **Light / Dark / System switch on Profile** — a per-device preference, default System, stored through the `StorageAdapter`, applied to `<html>` before React mounts (§5.4, §6.1).
- **The screenshot harness as a committed dev tool** (`apps/web/scripts/screens/`, `pnpm --filter @sin/web run screens`; §6.10).
- **Palette and semantic tokens** (§5.1), contrast-verified for WCAG 2.2 AA in both themes, with the old `--color-accent` / `--color-on-accent` **removed**.

- **Type:** Instrument Sans, self-hosted woff2 under the SPA's own origin, `font-display: swap`, a real fallback stack, tabular figures on by default (§6.4, §6.5).
- **Surfaces:** cards and list rows lose their outline and separate by tint; hairlines stay only where they carry meaning (§6.6).

- **An automated contrast + role test** (AC3–AC6), and the build-output checks that keep fonts CSP-clean (AC11).
- **Design documentation location** (`apps/web/DESIGN.md` + `design.json`) and the pointer/Q22 in `docs/DESIGN.md` (§6.9).

## 6. Behavior & logic

### 6.1 Theme mechanism

`tokens.css`: base `:root { color-scheme: light dark; …light values… }`, then:

```css
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { color-scheme: dark; …dark values… }
}
:root[data-theme="dark"] { color-scheme: dark; …the identical dark values… }
:root[data-theme="light"] { color-scheme: light; }
```

*System* = no attribute: the media query decides. *Light* forces the base values even on a dark OS (the `:not([data-theme="light"])` guard keeps the media block out). *Dark* forces the dark values even on a light OS (the attribute block). The dark values are written twice because CSS cannot share a declaration list between a media block and a selector; AC20 makes drift a test failure. (Rejected: `color-mix`/`light-dark()` — would need non-hex tokens and defeat the exact-contrast test; JS-set inline custom properties — a second place for design values.) Non-color tokens stay in the base block only. Color values are opaque hex only, so the contrast test computes exact ratios.

**Applying the stored value.** `src/ui/theme.ts` (React-free): `THEME_KEY = "sin:pref:theme"`; `applyStoredTheme(storage = localStorageAdapter())` reads the key, and sets `document.documentElement.dataset.theme` only for exactly `"light"` or `"dark"` (anything else, or a read that throws, means System and leaves the attribute off); `setThemePreference(pref, storage)` writes/removes the key (`"system"` removes it) and applies. Wrapped in try/catch — a failed write still applies for this page view.

**No inline script (CSP).** The usual "set the theme in an inline `<script>` in `<head>`" trick is forbidden by `script-src 'self'`. Instead `applyStoredTheme()` is the **first statement of `bootstrap()`** (the single boot seam, Spec 04.0), before the config check and before `createRoot`. **Flash risk:** the module script runs after the stylesheet is applied, so on a device with an explicit override that differs from the OS, the empty `#root` can paint for a frame or two in the OS theme's ground color before the attribute flips; no UI is rendered in the wrong theme because React has not mounted. It is minimized by (a) running first, ahead of the config parse and React, (b) `type="module"` scripts being deferred but small and hash-cached, (c) the page being blank anyway until auth completes. Users on System (the default) see none. Accepted; a build-time external `theme-init.js` (`<script src>`, CSP-clean, render-blocking) is the escape hatch if the phone check shows a flash (§12 D14).

**`theme-color` metas follow the page.** `index.html` has one tag per OS scheme, each holding that theme's ground (AC5 pins both to `tokens.css`). A forced theme copies its own tag's value into both, so whichever tag the browser matches agrees with the page; System restores the originals. `ui/theme.ts` writes no color of its own, only values read from the tags. (v0.3 had accepted an OS-only limitation; the `/code-review` pass found the reliable route above, 2026-10-16.)

### 6.2 Color roles — the rules

- **Signal (teal) is the interactive/brand color:** the primary action, where you are (active nav), what you can follow (links), what is chosen (selection), the data series (chart) and the superset bracket. Teal does **not** mean "record", "warning" or "failed"; it never fills decoration that is none of those roles. It is the only chromatic color on most screens, which is the point: if it is teal you can act on or read it. Rule of thumb for the primary fill: one `Button` `primary` per screen where possible.
- **Brass means "a record", and nothing else.** It appears nowhere that is not a personal record; it is never used for selection, links or charts.
- **Warm-up sets are muted and marked W** — never a color of their own.
- **Danger means destructive or failed.** Delete, discard, a write that did not save, a validation error. Not "important".
- **Warning** (needs data, offline-adjacent cautions) is a distinct burnt orange so it is never mistaken for brass or danger; the words ("Needs data") carry the meaning, color only supports it.
- **State is never by color alone** (PRODUCT.md): selected = fill *and* `aria-pressed`/checked; active nav = weight *and* `aria-current`; warm-up = "W" *and* name.

### 6.3 Reclassifying `--color-accent` (D2)

`--color-accent` is removed, not aliased. An alias would leave every one of its 21 uses teal by default — the "one accent painted on everything" the direction refuses. Each use picks a role:

| Use (file) | Becomes | Why |
|---|---|---|
| `Button .primary` | `--color-signal` / `--color-on-signal` | the primary action |
| `.emptyLink` (History, Routines empty states) | `--color-signal` text | it is literally "do this next" |
| Inline/back links (`reset.css a`, `.back` ×2, Progress links, `ExercisePicker .createRow`) | `--color-signal`, underlined | a link is interactive; underline keeps it from being color-only |
| Selected chip/segment (`ChoiceGroup`, `UnitToggle`, `ExercisePicker .tag`, `RoutinesSection` outlined link, checked `CreateExerciseForm .choice`, `ExerciseProgress .session[aria-pressed]`) | `--color-selected` fill + `--color-on-selected` text (or outline), aliases of signal / on-signal | a chosen option is an interactive state; the alias reads as a role and can diverge later |
| Active nav item (`AppShell .navTarget[aria-current]`) | `--color-signal`, weight 700 (inactive: muted) | current location; bold is the non-color cue (D4) |
| Superset bracket (`SupersetBracket .bracket`) | `--color-signal` | grouping you can act on (link/split); ≥ 3:1 against the card (D4) |
| Spinner top arc (`Spinner`, `useLogoutGuard`) | `--color-text` | "working" |
| Chart line and dots (`LineChart`) | `--color-signal` stroke and fill (≥ 3:1 on the chart panel, `--color-surface`) | the data series is this app's one chart color; brass stays reserved for records (a PR marker on the chart is 17.2's call) |

The signal allow-list (AC6) is the file list in AC6: every stylesheet in the table above, plus `reset.css` and `tokens.css`. Anything else needs a spec amendment. The Spinner is the one former accent use that goes to ink (`--color-text`): it means "working", not an interaction.

### 6.4 Fonts under the CSP

**What the CSP needs, exactly.** The SPA's CSP (`render.yaml`, header on `/*`, mirrored in Spec 04.0 §6.6 and DESIGN §8.2) already says `default-src 'self'; … style-src 'self'; … font-src 'self'`. A font is fetched from the SPA's own origin — `https://<spa-host>/assets/<name>-<hash>.woff2` — which `font-src 'self'` allows, and the existing `/assets/*` rule gives it `Cache-Control: public, max-age=31536000, immutable`. **No CSP change, no `render.yaml` change.** What would *break* it:

- Any Google Fonts `<link>` or `@import` (a third-party origin; also leaks the visitor's IP to Google).
- **A `data:` URI font.** Vite inlines any asset under `build.assetsInlineLimit` (4 KiB) as a `data:` URL, and `font-src 'self'` does not list `data:`. The variable woff2 is far over 4 KiB, but a small subset could cross it silently, so `vite.config.ts` sets `assetsInlineLimit` to a function returning `false` for `.woff2` (AC11 checks the build).
- A cross-origin font host (a CDN) — would need `font-src` and CORS; not needed.

**Files.** `src/ui/fonts/InstrumentSans-roman-latin.woff2` (+ `OFL.txt` and a three-line `README.md` giving source, version and subset). One file: the variable font carries both axes. No italic (the UI uses none). Subset: Basic Latin, Latin-1 (includes `× ·`), and U+2013/2014, U+2018–201D, U+2026, U+2212. Glyph coverage was checked against the upstream variable TTF on 2026-10-16: it has `× · – — ’ … − ↑ ↓ °` but **no `±` (U+00B1) and no `✓` (U+2713)**. `±` appears only in code comments. `✓` is in the visible "Superset ✓" label (`routines/LinkToggle.tsx`): it becomes a drawn `CheckIcon` from `ui/icons.tsx` beside the word "Superset", since a Unicode glyph standing in for an icon would fall back to the system font and break Q25's one-icon-system rule. The accessible name (`aria-label`, `aria-pressed`) is unchanged. Characters outside the subset (rare accented custom-exercise names) fall back per glyph to the system font — acceptable, and `unicode-range` is not needed with one file.

**`src/ui/fonts.css`** (imported by `bootstrap.tsx` between `tokens.css` and `reset.css`, so it is covered by `assert-css-tokens`, which forbids hex and `px` and allows this file):

```css
@font-face {
  font-family: "Instrument Sans";
  src: url("./fonts/InstrumentSans-roman-latin.woff2") format("woff2");
  font-weight: 400 700;
  font-stretch: 75% 100%;
  font-style: normal;
  font-display: swap;
}
```

`--font-family: "Instrument Sans", system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif;`.

**`font-display: swap`** shows text immediately in the fallback and swaps when the file arrives (no invisible text). Because the app is JavaScript-rendered, the browser would only discover the font after React has painted, so `index.html` carries a preload: `<link rel="preload" href="/src/ui/fonts/InstrumentSans-roman-latin.woff2" as="font" type="font/woff2" crossorigin>`. Two details that matter: Vite rewrites that `href` to the hashed `/assets/…` path at build time (AC11 asserts it did), and `crossorigin` is required even for same-origin fonts — fonts are always fetched in "anonymous CORS" mode, and a preload without the attribute is fetched twice. Metric-matched fallback faces (`size-adjust`) are not added: the shell paints after JS, so layout shift from the swap is negligible.

### 6.5 Tabular figures (D8)

One rule on `body` in `reset.css`: `font-variant-numeric: tabular-nums;` — inherited by everything, so weights, reps, set numbers, PR values, chart tick labels, durations, dates and the History meta line all align, with no per-component class to forget. The six existing component-level declarations become redundant and are deleted. Rejected: a `.num` utility class (every new number is a place to forget it, and a miss is a subtle misalignment no test notices). Cost: digits in running prose (notes, dates) are slightly wider; acceptable in a data app. SVG `<text>` (chart ticks) inherits it too. 17.1 may narrow the *width axis* (`font-stretch`) for large figures through its own token; this spec only guarantees the axis is declared.

### 6.6 Surfaces — fewer boxes

- **Panels** (`ExerciseCard .card`, `PersonalRecordsBlock .block`, `RoutineNotePanel`, `InlineNotice .notice` body, `HistoryScreen .row`, `ProgressScreen` list rows, `ExerciseProgressScreen .session`, `RoutinesSection` cards, `ConfirmDialog` bodies): drop `border`; background `--color-surface` (dialogs `--color-surface-raised`; the full-height `Sheet` keeps the `--color-bg` ground, as built) on the `--color-bg` ground. Existing padding and radii stay (Stage 1 layout).
- **Rows inside a panel:** separated by the existing `--space-*` gaps; no per-row borders. A `--color-line` hairline remains only between a card header and its sets *if* the screenshots show the grouping is unclear.
- **Controls** (inputs, selects, secondary and disabled buttons, checkboxes' labels): keep a 1 px `--color-border` outline — this is the 1.4.11 "boundary of a UI component" that must hit 3:1.
- **Sweep rule (mechanical):** `border…var(--color-border)` on a non-control → delete the declaration; on a control → keep. 43 uses across 32 files; each is one of those two.
- Elevation/shadows are not introduced.

### 6.7 The contrast test

`src/ui/tokens.contrast.test.ts` (Vitest, runs in jsdom but only reads files): reads `tokens.css`, strips comments, extracts the base `:root` block and the dark `@media` block with the same regex approach `assert-css-tokens` uses, builds `light = base`, `dark = { …base, …darkOverrides }` from the `@media` block (and asserts both dark blocks override *every* color key and are identical — AC2, AC20), resolves `var()` aliases (`--color-warmup`), then asserts a pair table `[fg, bg, min, label]` for both themes:

| Pairs | Min |
|---|---|
| text, muted, warmup on bg / surface / surface-raised; muted on signal-soft | 4.5 |
| on-signal on signal (primary button and selected chip); signal text on bg / surface / surface-raised / signal-soft (links, nav label on the nav's surface, CTA text); on-selected on selected (alias) | 4.5 |
| pr on bg / surface / pr-soft | 4.5 (light on `pr-soft` passes by 0.04 — see D11) |
| danger, success, warning on bg / surface / surface-raised | 4.5 |
| border on bg / surface / surface-raised; focus on bg / surface / surface-raised; signal as non-text on bg / surface (superset bracket, chart stroke and dots on the chart panel `--color-surface`) | 3.0 |
| exemption list: `line`, panel-vs-ground (AC4) | — |

The WCAG relative-luminance function is about 8 lines and lives in the test file (no dependency). The test prints the table on failure. The same helper is used by the `theme-color` assertion (AC5) in a sibling test.

## 7. Security & privacy

- **CSP is unchanged and stays strict** (§6.4): no new origin, no `unsafe-inline`, no `data:` fonts. AC11 keeps it that way.
- **Self-hosting the font is also the privacy choice:** a Google Fonts request would send each lifter's IP and referrer to a third party. No third-party request is added.
- **Licensing:** Instrument Sans is SIL OFL 1.1, which permits bundling and redistribution with the license text; `OFL.txt` ships beside the file.
- **No inline styles or scripts added** (`index.html` gains only `<meta>` and `<link>`).
- Authorization and PII are untouched. One new local key, `sin:pref:theme` (`light`|`dark`), holds no personal data; it is read defensively (any other value is ignored) and reaches the DOM only as a fixed-enum attribute, never as markup or CSS text.
- The harness's fake auth module is the one security-relevant artifact: it would bypass login if it shipped. AC19 makes its absence from the production bundle a checked property.
- Accessibility is treated as a requirement, not polish: WCAG 2.2 AA in both themes is test-enforced (AC3).

## 11. Deployment & rollback

**Ships** as one PR (one revert unit), merged to `main`, auto-deployed to staging by Render. No release step, no migration, no API change, no env var, no ordering constraint. Hashed asset names mean no stale-cache problem: new `index.html` references new CSS/font hashes.

**Rollback:** revert the PR (stored `sin:pref:theme` values are then ignored harmlessly; leftover keys need no cleanup). It is CSS and one static asset, so there is no data to repair. What makes it less trivial than "revert `tokens.css`":

1. **`--color-accent` is deleted, not aliased (D2):** restoring only `tokens.css` would leave ~16 stylesheets pointing at tokens that no longer exist (blank colors). Revert the whole PR, never a single file.
2. **Revert order:** if 17.1/17.2/17.3 have merged, they depend on these tokens and the font; revert them first or together.
3. The two markup hooks (trophy SVG, `data-set-type`/W mark) and the `index.html` meta/preload revert with the same PR; no data depends on them.
4. The harness is dev-only and reverts with the rest; nothing deployed depends on it.
5. After a revert the Spec 06.3 smoke confirms the app is up; a preload of a font that no longer exists would 404 harmlessly, but the revert removes the link too.

## 12. Decisions & open questions

### Decisions (✅ — to be recorded as Q22 in DESIGN.md)

- ✅ **D1 — Light-first, theme follows the OS by default.** Light is the base `:root`; dark is a deliberate `prefers-color-scheme: dark` override. *Rationale:* the owner trains in a boutique gym with natural light, and designed light first (2026-10-15); the default path is a media query needing no JavaScript, and `color-scheme` also themes native widgets; the owner-requested override is layered on top (D14). *Rejected:* keeping dark-default (contradicts the owner's decision).
- ✅ **D2 — `--color-accent` is replaced everywhere, no alias.** *Rationale:* the old token mixed roles (action, link, tab, selection, chart) under one name; the work is deciding each use's role (§6.3), and a removed token makes a missed one fail loudly (AC1, AC13). Several roles end up on teal, but as named tokens (`--color-signal`, `--color-selected`, `--color-focus`) that can diverge later. *Cost:* the revert is whole-PR (§11).
- ✅ **D3 — Two border tokens.** `--color-border` keeps its name but is now the 3:1 *control* boundary; `--color-line` is the new decorative hairline. *Rationale:* the mockup's quiet line (`#e3ded5`, 1.2:1) fails WCAG 1.4.11 for input boundaries, yet quiet hairlines are the look; one token cannot be both. Keeping the old name means controls need no edit.
- ✅ **D4 — Teal is the interactive/brand color; it carries the active nav item (teal + bold), links, the chart series, selection and the superset bracket (owner, 2026-10-16, from the mockups).** The architect's first proposal kept signal exclusively for "do this next" and gave nav/selection/links to ink and the bracket to muted; the owner chose teal for coherence — the mockups read as one calm system with brass as the only other color. *Consequences:* signal no longer means only "next", so its allow-list is wide (AC6) and the discipline moves to the other roles: brass stays records-only, warning and danger stay distinct hues, and state is never by color alone (bold + `aria-current`, checked radios, underlined links). `--color-selected` / `--color-on-selected` are kept as aliases of signal / on-signal (a role token reads clearer, and selection can diverge later without a sweep). Contrast of every teal pair is in the AC3 table.
- ✅ **D5 — Danger covers destructive *and* failed (owner confirmed, 2026-10-16).** Failed and invalid states ("Couldn't save", field errors, error notices) use the brick red together with delete/discard; warnings are a separate hue (D6).
- ✅ **D6 — Warning is burnt orange (`#9c4a0c` / `#e39a5b`), not ochre.** Ochre sits within a few degrees of brass; a warning that looks like a record would break "brass means records". The words carry the meaning anyway. Owner confirmed 2026-10-16.
- ✅ **D7 — One latin-subset roman variable woff2, committed in-repo.** Reproducible builds with no network at build time, one request, no italic. Fontsource-as-dependency was rejected (an extra package and a CSS file with its own `@font-face` we would then have to override).
- ✅ **D8 — Tabular figures globally on `body`.** See §6.5; rejected a `.num` class.
- ✅ **D9 — Preload the one font.** The app renders after JS, so without it the swap would be visible on every cold load.
- ✅ **D10 — Visual doc at `apps/web/DESIGN.md` + `design.json`, with a pointer in `docs/DESIGN.md`.** `docs/DESIGN.md` is not overwritten (owner rule).
- ✅ **D11 — The mockup hex values pass AA as given; they are the starting values and the test is authoritative.** Thinnest margin: light brass on `pr-soft` 4.54:1 — if the screenshots want more, darken `--color-pr` slightly (it is only used for large/bold text and the trophy there).
- ✅ **D12 — `theme-color` meta tags carry the ground color per theme,** asserted against `tokens.css` (AC5) because HTML is outside the css-tokens tripwire.
- ✅ **D13 — The History trophy becomes an SVG icon** so brass can color it (an emoji cannot be recolored) — the only icon added; 17.2 reuses it.

- ✅ **D14 — A Light / Dark / System switch on Profile (owner, 2026-10-16), applied by `data-theme` on `<html>`.** *Rationale:* an override must outrank the OS media query, which only an attribute selector can do; System (no attribute) keeps the zero-JS default path. *Rejected:* a build-time inline script (CSP forbids it), storing the choice on the server (needs an API and migration for a cosmetic setting; per-device is also the right semantics — a shared tablet and a phone may want different themes). The boot-time flash is accepted and minimized as in §6.1; an external render-blocking `theme-init.js` is the fallback.
- ✅ **D15 — `sin:pref:theme` is deliberately NOT in `USER_DATA_KEY_PREFIXES`.** `USER_DATA_KEY_PREFIXES` exists so logout removes *a user's data* from a shared device (catalog cache, recents, outbox, drafts — Spec 06.0 AC20, 06.5). A theme is not the user's data: it identifies no one, belongs to the device/browser, and clearing it on logout would make the app flip theme at every sign-out — a visible bug for the next sign-in. The `sin:pref:` namespace is the explicit home for such device preferences; `clearUserData`'s doc comment says so and the test in AC24 pins it. `blockUserDataWrites()` (which silences user-data writes during logout) correctly does not affect it. The write still goes through the `StorageAdapter`, so the 04.0 AC7 scan keeps passing; `ui/theme.ts` must not name the browser storage objects even in comments. (If the owner later wants the preference per account, it becomes a `/v1/me` field — a separate spec.)
- ✅ **D16 — The screenshot harness is committed as a dev tool** (owner, 2026-10-16): `apps/web/scripts/screens/`, run on demand, not in CI, with the fake auth reachable only through the scratch Vite config's alias (§6.10, AC19). *Rationale:* it is the verification method for every UI spec in the refresh (AC15 here, 17.1–17.3 after), and rebuilding it each time costs more than maintaining it.
- ✅ **D17 — The theme switch stays in this spec, one PR (owner, 2026-10-16).** The architect had flagged the combined scope (tokens/fonts/sweep + harness + switch) as over one session and offered a split into 17.0a; the owner chose a single PR. The order of work (§6.8) keeps it reviewable: harness first, tokens and sweep, then the switch last, so if the session runs out the switch is the clean cut point.
