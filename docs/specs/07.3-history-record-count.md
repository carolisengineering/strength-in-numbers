# Spec 07.3 — History record count excludes set volume (API)

**Status:** Implemented (this PR, 2026-10-17). Owner decided the approach on 2026-10-17 (Spec 17.2 D11, option A).
**Kind:** API (one query predicate and one doc comment). **No migration, no response-shape change, no release step.**
**Depends on:** Spec 07.1 (the History list and `recordCount`, D15), Spec 07.0 (`personal_record`, record types, D18 "held now").
**Gates:** Spec 17.2 Phase B (the History badge number and the summary's "N new" must agree). It ships one release before that PR (DESIGN §6 response-field rollout convention).
**Design refs:** DESIGN.md §4.5 (record types; `best_set_volume`), §6 (API-first rollout), Spec 07.1 AC14 / D15 / §6.1, Spec 17.2 §3.2 and D11, CLAUDE.md "Personal records" and "Paginated lists".

---

## 1. Purpose, scope & non-goals

### Purpose

`WorkoutSummary.recordCount` (the History row's number) is `count(*)` of every `personal_record` row the workout holds, which includes `best_set_volume`. Spec 17.2 hides set-volume records on the finish summary (owner decision, 2026-10-15; they stay in Progress). Left alone, a History row could say "3 PRs" over a summary listing 2, or show a trophy over a summary with no records section. The number a lifter sees in the list must mean what the summary lists. This spec changes what `recordCount` counts: **the records the workout holds now, other than `best_set_volume`.**

### In scope

- The `record_count` subquery in `listFinishedWorkouts` (`apps/api/src/repositories/workout-history.prisma.ts`) gains `AND pr.record_type <> 'best_set_volume'`.
- The doc comment on `recordCount` in `packages/core/src/dto/workout.ts` (and the 07.1 amendment notes).
- Updating the one existing test that asserts the old count (07.1 AC14, integration) and adding the new ones (§10).

### Non-goals

- **A new field** (`highlightRecordCount`) or any DTO shape change. The field name now slightly understates ("records shown"); the doc comment records it (D2).
- **Any change to what records exist**, how they are computed, stored or rebuilt (Spec 07.0, `@sin/core` `records.ts`). `best_set_volume` rows are still written, still rebuilt by `records:rebuild`, still returned by `GET /v1/personal-records`, still in `newRecords` on the finish response and still in Progress. Only this one count changes.
- **The finish response and `GET /v1/personal-records`.** They keep returning set-volume records; the web filters them for display (Spec 17.2). Filtering there would change Progress.
- **UI** (Spec 17.2 Phase B).
- **The export** (Spec 11): `recordCount` is not part of it (it composes workout detail DTOs, not History summaries; grep of `routes/mappers.ts` and the export finds no use).

## 2. Acceptance criteria

Behavioral criteria each have ≥1 test whose `describe` is tagged **`"07.3 ACn — …"`**. Levels are in §10.

1. **Set volume is not counted.** `recordCount` for a workout is the number of `personal_record` rows with `workout_id` = that workout and `record_type <> 'best_set_volume'`. A `weight_reps` workout that holds heaviest weight, est. 1RM and set volume (the case Spec 07.1 AC14 builds) has `recordCount: 2`, not 3.
2. **Volume-only workout.** A workout that holds only a `best_set_volume` record has `recordCount: 0` (the History row shows no badge). The `personal_record` row still exists (the test asserts the row count is 1).
3. **Other types still count.** A workout holding a `max_reps` record (a `bodyweight_reps` exercise) counts it; a workout holding all four types for different exercises counts three.
4. **Still "held now".** The count still drops when a later or backdated finish takes the record (07.1 AC14's scenario, with the updated numbers: `2` then `0`). The change adds a type filter only; the "held now" rule (07.0 D18) is unchanged.
5. **Nothing else changes.** The finish response's `newRecords`, `GET /v1/personal-records` and the Progress data still include `best_set_volume` rows; a test finishing the AC1 workout asserts `newRecords` has 3 entries while the History row says 2.
6. **No shape change.** `WorkoutSummarySchema` parses the same fields; the existing core DTO test and both public-surface inventory tests pass unchanged. The OpenAPI document differs only if the `recordCount` description is published (it is a doc-comment change; if the generated description changes the inventory snapshot is updated, nothing else).
7. **Page behavior preserved.** Keyset paging, ordering and cursors are untouched (a regression run of the 07.1 integration suite passes with only the AC14 numbers updated). The page-latency benchmark (`bench:history`) is re-run once and the first-page p99 stays within the 07.1 AC20 budget (no new index; the predicate is a filter on rows already fetched through `personal_record_workout_idx`).
8. **Docs.** The 07.1 spec (AC14 and D15) carries an "amended by 07.3" note, `WorkoutSummary.recordCount`'s comment says what it excludes and why, and DESIGN.md §4.5 gets the one-sentence note listed in §11. *(Review.)*

## 4. Data model

None. No table, column, index or migration. The type filter uses the existing `personal_record_workout_idx` for the `workout_id` lookup and filters the handful of matching rows (at most four types times the exercises a workout holds).

## 6. Behavior & logic

### 6.1 The exact change

In `workout-history.prisma.ts` the page query's last select column is today

```sql
(SELECT count(*)::int FROM "personal_record" pr WHERE pr.workout_id = w.id) AS record_count
```

and becomes

```sql
(SELECT count(*)::int FROM "personal_record" pr
  WHERE pr.workout_id = w.id AND pr.record_type <> ${HISTORY_COUNT_EXCLUDES}) AS record_count
```

where `HISTORY_COUNT_EXCLUDES` is a named constant in that file typed `RecordType` (`"best_set_volume"`) and bound as a parameter, in the same style as `WORKOUT_SUMMARY_NAMES_MAX` (07.1 D16). Everything else in the query, the cursor and the volume query is untouched. This is not PR math: which rows are records is still decided only by `@sin/core` `records.ts`; this query merely chooses which stored rows to count for a display figure.

### 6.2 Why a filter and not a recount in core

The count is a read of the rebuildable cache, like 07.1 D15's. Adding a type predicate keeps it one indexed lookup per row; a recount through `records.ts` would re-run PR math on read, which CLAUDE.md forbids ("PR math lives only in `@sin/core` `records.ts`"; the cache is the read path).

### 6.3 Edge behavior

- A workout that holds no records, or only set-volume records: `0`.
- A rebuild (`records:rebuild`) rewrites rows; the count follows the rows, so the figure is identical before and after a rebuild.
- Retired or forked exercises: unchanged (the query counts by `workout_id`, with no join to exercises).

## 12. Decisions & open questions

- ✅ **D1 — Narrow `recordCount` rather than add a field. Owner decided 2026-10-17 (via Spec 17.2 D11).** *Rationale:* the only consumer is the History badge, which must agree with the summary; one number with one meaning is simpler than two near-identical fields that every future consumer must choose between. *Rejected:* a new `highlightRecordCount` (cleaner name, permanent duplication); no change (a trophy over an empty summary).
- ✅ **D2 (mine) — Keep the name `recordCount`.** *Rationale:* renaming a published response field is an interface change, and the repo's rule is to ask before renaming; the doc comment carries the precise meaning.
- ✅ **D3 (mine) — Exclude by type in the SQL, with a named constant, rather than count in application code or add a stored column.** *Rationale:* it stays one indexed lookup (07.1 D15's shape), reads the rebuildable cache, and keeps record eligibility in `records.ts`.
- ✅ **D4 (mine) — First-ever records still count.** Spec 17.2 D13 (owner decided) keeps `previousValue: null` records in the badge and "N new"; this spec only removes the set-volume type.
- **Open:** none.
- **AC7 benchmark (2026-10-17, `bench:history`, 200 sessions x 6 exercises x 4 sets, limit 50):** first page p50 33.3 ms, p99 34.5 ms; deep page p50 32.8 ms, p99 34.5 ms. Well inside DESIGN §1.3's 400 ms p99.
