## 1. Purpose, scope & non-goals

### 1.1 Purpose

After Spec 05.3 the server can hold, validate, record and chart three more kinds of exercise, and the web compiles against them, but no screen offers them: the create form is pinned to the legacy five and every other web site that switches on a modality has a plain fallback arm. This spec makes the three types usable in the app **wherever the existing five are**:

| Type (`modality`) | Name shown | Logs | Example |
|---|---|---|---|
| `calories` | Calories | calories only | Echo Bike |
| `weight_distance` | Weight + distance | the total weight carried, and how far | farmer carry |
| `weight_duration` | Weight + duration | the total weight held, and for how long | weighted sandbag hold |

**Success:** Carol creates "Echo Bike" as Calories, starts a workout, logs 20 cal with one tap on the bar, finishes, sees "Most calories 20 cal" on the summary and the chart on Progress, edits a set the next day, and puts a farmer carry in a routine with a target weight; none of it needed a workaround, and nothing about the five existing types looks or behaves differently.

### 1.2 In scope

**Phase A (PR 1): create, log, edit, routines**
- Create / pick: the create form offers all eight types (removes 05.3's temporary `CREATABLE_MODALITIES` filter), final labels, a one-line hint under the type choices (§6.1).
- Live logging: the entry panel and its draft (`setDraft.ts`, `SetFields.tsx`, `EntryRow.tsx`), a calories stepper (`stepper.ts`), the bar label (`logAction.ts`), set text (`format.ts`), collapsed summaries (`summaryLine.ts`), the persisted draft (`drafts/`), the outbox projection (verified; 05.3 Phase A already added `calories: null`), Finish integrity (`incomplete.ts`, volume absent), the incomplete-set copy (unchanged, verified).
- Editing past workouts: the shared set sheets (`SetEditSheet.tsx`, `edit/EditSetForm.tsx`) through `SetFields`, `diffForPatch`, server field errors.
- Routines: the item sheet and plan rows for the three types (target weight for both weighted types; nothing for calories), `validateDraft`, target lines.
- History and the summary: set text, volume omitted when null (verified).
- The screens harness: fixture exercises, sets and an active workout of the new types (live and edit screens).

**Phase B (PR 2): records, Progress, importer**
- Records: `records/labels.ts`, `units/format.ts` (cal, m, s), `RecordsSection`, `recordCards.ts` (`LEAD_ORDER`), the finish `RecordCardList`.
- Progress: `progress/metrics.ts` (three metrics, the unit-conversion fix), `progress/exercises.ts` (list headline), `ExerciseProgressScreen.tsx` (integer ticks).
- The importer: `routines/import/cards.ts` and `handoff.ts` pass `name.calories` into `guessModality`.
- The screens harness: records and series for the new types.

**Both:** a source-scan test pinning the final shape, tag test `acTags.18-1.test.ts`, docs (CLAUDE.md paragraph, README row, 05.3 amendment note), a manual phone check.

## 2. Acceptance criteria

Every behavioral criterion has at least one test whose `describe` is tagged **`"18.1 ACn — …"`**; `acTags.18-1.test.ts` (AC38) checks the tags. §10 maps each to a method. "New types" means `calories`, `weight_distance`, `weight_duration`; "legacy types" means the five that exist today.

### Phase A: create, log, edit, routines

**Create and pick**

1. **The create form offers all eight types.** `ExerciseFields` iterates `MODALITY_VALUES` (order: the five legacy, then Calories, Weight + distance, Weight + duration); `CREATABLE_MODALITIES` and 05.3's AC21 pin are removed and replaced by a test that the radio values equal `MODALITY_VALUES`. `CreateExerciseForm`, the picker's inline create and the import's New card (`NameCard`) all use it, so all three offer the same eight. Creating each new type sends that `modality` in `POST /v1/exercises` and, in the picker, the row's meta line reads e.g. "Calories · Rowing machine".
2. **Labels.** `MODALITY_LABELS` is exactly: Weight × reps, Bodyweight × reps, Weighted bodyweight, Duration, Distance + duration, **Calories, Weight + distance, Weight + duration**. The exercise card's modality line (`ExerciseCard`) shows the same text.
3. **A hint under the choices.** Once a type is selected a one-line hint (`MODALITY_HINTS`, §6.1) appears under the choices and is the fieldset's `aria-describedby`; before a choice nothing is shown. All eight types have a hint. (Cuttable, D4.)

**Entry panel and draft**

4. **Which fields each type shows.** `visibleMeasures(modality)` returns, for all eight modalities, exactly `requiredMeasuresFor(modality)` in the order weight, distance, reps, durationS, calories (`DISPLAY_ORDER`). For the five legacy modalities the order is unchanged (no legacy modality has both weight and distance).
5. **Calories panel.** A `calories` card's entry panel shows one stepper group "Calories · cal" with a labeled text input (`inputMode="numeric"`), and no weight, reps, distance or duration input. "Set options" holds the Set type select only.
6. **Calories stepper.** `stepCalories` / `caloriesAtLimit` in `stepper.ts`: one tap changes the number by 5 (`CALORIES_STEP`), a blank or unparsable text steps from 0, − stops at 0 and + at `SET_CALORIES_MAX` (the button is disabled at its limit, not hidden), the button names are "Decrease calories by 5" / "Increase calories by 5", and a tap dispatches the ordinary `edit` action (17.1 AC21), so it is an edit like a keystroke.
7. **Weight + distance panel.** Weight stepper (steps by the draft's weight unit: 5 lb / 2.5 kg, 17.1) and a Distance figure input whose label includes the draft's unit ("Distance (m)"); no reps input. "Set options" holds Set type, Weight unit and Distance unit (m, km, mi, ft: `DISTANCE_UNIT_VALUES`, AC40).
8. **Weight + duration panel.** Weight stepper, then Minutes and Seconds figure inputs exactly as `duration` has them; no reps input. "Set options" holds Set type and Weight unit.
9. **Distance unit default.** A new draft for `weight_distance` starts with distance unit `m` whatever the profile's unit, and the lifter can switch it to feet (or km, mi) for that set; a draft copied forward from a logged set keeps that set's unit (a carry logged in feet makes the next draft feet); `distance_duration` still defaults to `km` / `mi` from the profile (`unitDefaultsFor` takes the modality). The same default applies to the edit screen's Add set.
10. **`parseDraft` per type.** `calories` is parsed as a whole number `0 … SET_CALORIES_MAX` with the existing static messages (Required, Enter a whole number, Can't be negative, Too large); the body for each new type holds exactly its required measures (`calories` only; `weight` + `weightUnit` + `distance` + `distanceUnit`; `weight` + `weightUnit` + `durationS`) and, generated over modality × measure from `forbiddenMeasuresFor`, **never** a forbidden one. RPE handling is unchanged (read when valid, otherwise dropped, never an error).
11. **The draft carries calories.** `SetDraft` gains `calories: string`; `DraftField` gains `"calories"`; `draftFromSet` / `draftForEdit` / `seedDraft` / the reducer carry it (a null stored value becomes `""`, never `"0"`); a copy-forward after a calories set pre-fills its calories; `EntryRow`'s `TEXT_FIELDS` includes it so an untouched field shows no error; RPE stays blank on an entry draft.
12. **Planned prefill (10.2).** For the two weighted types the next planned row's weight and unit are prefilled into the draft (a planned row never has reps for them); for `calories` a planned row prefills only the set type; progress through the plan stays positional (`exercise.sets.length`), an edited draft is never overwritten by a re-seed.
13. **Server field errors.** A `422` naming `calories` shows under the Calories input (`INPUT_FOR_MEASURE`); any other unmatched path is the form-level message, as today.
14. **Persisted drafts.** The `sin:workout:drafts` schema gains `calories` as `z.string().default("")`, so a drafts file written by the previous bundle still loads (it is not dropped as unreadable); an edited calories draft is stored and restored, `useDraftPersistence` lists `calories` among its effect inputs, and `draftStore` copies the ten fields by name (`attemptKey` still never stored).

**Logging, display, Finish**

15. **The bar label.** `logLabel` returns "Log 20 cal" (calories), "Log 24 · 40 m" (weight + distance: the weight carries its unit only when it differs from the profile's, the distance always carries its unit) and "Log 20 · 1:30" (weight + duration), and "Log set" while the draft does not parse; it stays the screen's one primary `Button` with the 600 ms double-tap window (17.1). The legacy labels are unchanged.
16. **Logging.** Tapping the bar on a calories card creates a set with `calories` and no other measure; offline, the outbox projection (`outbox/project.ts`) shows the queued set with its `calories` as "20 cal" and the usual "Not saved yet"; a replay with the same `clientGeneratedId` does not create a second set (06.2). The same holds for a weight + distance and a weight + duration set (weight, distance and duration shown, canonical `weightKg` / `distanceM` recomputed by the projection).
17. **Set text.** `formatSetParts` / `formatSet` render "20 cal"; "24 kg · 40 m"; "20 kg · 1:30" (m:ss, the existing `formatDuration`), with `–` for a null measure and the existing " (Warm-up)" suffix; the card rows, the summary, History detail and the edit screen all use it. Legacy text is unchanged.
18. **Collapsed rows.** `collapsedSummary` for a planned weighted-type exercise reads "… · next 24" (the planned weight, with its unit only when it differs from the profile's, as `weight_reps` does) and falls back to "set N" when the row has no weight; a `calories` exercise reads "set N"; the counts and the done check follow 17.1 AC10 unchanged.
19. **Finish integrity.** `findIncompleteWorkingSets` flags a working set of each new type that lacks a required measure (using `requiredMeasuresFor`, which includes `calories`); the banner copy is unchanged ("N working sets are missing data. Fix or delete them, then finish again."). `finishStats` volume stays `null` and the "volume" item is absent for a workout of new types only; a History row for such a workout shows no volume segment; a mixed workout shows the legacy sets' volume only.

**Editing past workouts**

20. **The set sheets.** `SetEditSheet` (live) and `EditSetForm` (edit screen) render, through `SetFields` (variant `sheet`), for `calories` a Calories text field; for `weight_distance` Weight + unit select and Distance + unit select; for `weight_duration` Weight + unit select and Minutes / Seconds. Edit prefill (`draftForEdit`) shows the stored values; **Add set** on the edit screen seeds from the last set with the AC9 unit default.
21. **Patching.** `diffForPatch` includes `calories` when changed and omits it when equal; for a new type it never sends a measure the type forbids and never sends RPE; saving an unchanged sheet sends nothing. Finished-mode refusals (`422` naming a missing field, `409 workout-would-be-empty`) reach the user through the existing 18.0 copy and the AC13 field mapping.

**Routines**

22. **Item sheet.** For a `calories` item the sheet shows Sets, Rest and Notes only (no Reps, no Weight, no unit toggle); for a weighted-type item it shows Sets, Weight (with the unit toggle), Rest and Notes, no Reps; plan mode (`PlanRowList`) shows Type only for calories, and Type + Weight for the weighted types. These follow from `forbiddenMeasuresFor` and need no new branch; a test pins them for all three.
23. **Request bodies and validation.** `toRoutineInput` for each new type sends no `repsLow` / `repsHigh` / `targetReps*` keys and, for calories, no weight; a weighted-type item with a weight and a set count sends `sets` rows with `weight` + `weightUnit`; `plannedViolationIssues` reports nothing for such bodies (the client never produces what 09.1 refuses). A weighted-type weight without a set count is still blocked by the existing message.
24. **Target lines.** `targetLine` reads "3 sets @ 24 kg · 2:00" for a planned weighted-type item and "3 sets" for a calories item; the routine editor row, the preview and a started workout's card use it; a routine item whose exercise is missing still reads "Removed exercise".

**Harness**

25. **Fixtures.** `apps/web/scripts/screens/data.mjs` gains three exercises (Echo Bike, Farmer Carry, Weighted Sandbag Hold), a `calories` field in its set builder and POST handler, an active workout with a current card of each new type (and one planned weighted item), and a finished workout containing them; the strict-schema check passes and `pnpm --filter @sin/web run screens` captures the create form (eight types and a hint), the live screen for each new type, and the edit-screen sheet, light and dark, 390 and 1280 px, with no layout violation (every enabled control ≥ 44 px).

**Feet (owner answer O1; appended as AC40 to keep existing numbers)**

40. **Feet in the set controls and text.** The two distance-unit selects (`SetFields` sheet and entry variants) list exactly `DISTANCE_UNIT_VALUES` (`m, km, mi, ft`) from `@sin/core`, with no local copy; a weight + distance draft switched to `ft` shows the Distance label "Distance (ft)", and `parseDraft` sends `distanceUnit: "ft"`; `logLabel` reads "Log 24 · 40 ft", `formatSet` "24 kg · 40 ft" (and "40 ft · 1:30" for `distance_duration`); the outbox projection shows a queued feet set with `distanceM` = distance × 0.3048 (through `toCanonicalMeters`); a drafts file holding `distanceUnit: "ft"` loads and round-trips; the edit sheet prefills and patches the unit (`diffForPatch` sends `distanceUnit` when it changes). Feet are available on `distance_duration` too (05.3 D18), whose profile default stays km / mi. Records and charts of a feet carry show meters (AC27, AC32).

### Phase B: records, Progress, importer

26. **Record labels.** `recordLabel` / `shortRecordLabel` return "Most calories", "Longest distance", "Longest hold" for `max_calories`, `max_distance`, `max_duration` (the same text for both, D10), replacing 05.3's compile arms; both switches keep their `never` default.
27. **Record values.** `formatRecordValue` renders `cal` as "20 cal"; `m` as meters with a thousands separator and up to three decimals ("40 m", "1,200 m", "12.5 m"), **the same for kg and lb accounts and for a record set in feet** (a 40 ft carry is the canonical 12.192 m and reads "12.192 m"); `s` through the new pure `formatSeconds` ("45 s", "1 min 30 s", "2 min", "1 h 2 min 5 s"). `formatRecordByType` is unchanged. A gain is shown as "+5 cal", "+10 m", "+15 s", never "+0".
28. **Records list.** `recordLine` / `RecordsSection` read "Echo Bike — Most calories 120 cal (was 110 cal)", "(first record)" when there is no previous value; `sortRecords` places the new types after the legacy four in `RECORD_TYPE_VALUES` order.
29. **Finish record cards.** `LEAD_ORDER` stays derived from `RECORD_TYPE_VALUES` without `best_set_volume`, so it ends heaviest, est. 1RM, most reps, calories, distance, duration; a test pins the resulting order. A calories card leads "Most calories"; a weight + distance card leads "Heaviest weight" with a "Longest distance" chip, or leads "Longest distance" when only that was broken; a weight + duration card likewise with "Longest hold". The card's set text is the lead set via `formatSet`; `recordsNewCount` counts them; the card uses the existing brass record styling and no other color (17.0 `roles.test.ts` allow-lists unchanged).
30. **Progress list.** `HEADLINE` in `progress/exercises.ts` is est. 1RM, heaviest weight, most reps, then calories, distance, duration; an exercise with only a calories record reads "Most calories 120 cal · Tue 6 Oct".
31. **Chart metrics.** `Metric` gains `calories`, `distance`, `duration` (fields `maxCalories`, `maxDistance`, `maxDuration`; units `cal`, `m`, `s`); `METRIC_ORDER` is est1rm, topSet, volume, reps, calories, distance, duration; chip labels "Calories", "Distance", "Time"; `availableMetrics` lists only those with a non-null point (so a calories exercise offers only Calories, a carry offers Top set and Distance, a hold offers Top set and Time); `defaultMetric` prefers est1rm, topSet, reps, calories, distance, duration.
32. **Units on the chart.** `pointsFor` converts to lb only for `kg` and `kg_reps` metrics (today it converts everything but reps, which would turn calories, meters and seconds into pounds); `captionFor` reads "Calories", "Distance (m)", "Time (seconds)" for the new metrics and is unchanged for the old; the readout, the sessions list and `chartSummary` use `formatPointValue`; reps, calories and time use integer y-axis ticks (`LineChart integer`), distance does not.
33. **Series equals record.** For a fixture lineage of each new type the chart's best point equals the Records list value for the matching record (`topSetWeight` ↔ heaviest weight, `maxCalories`, `maxDistance`, `maxDuration`), in kg and lb.
34. **The importer's hint.** `initialCards` passes `{ calories: name.calories }` to `guessModality`, and `buildHandoff` (`handoff.ts`) passes the same hint in both of its fallbacks (it looks the flag up by name key). A pasted `Max Cal Echo Bike with remaining time` gives a New card "Echo Bike" with **Calories** pre-selected; `20 Cal Row` gives New "Row" with Calories; a name that matches an existing exercise keeps that exercise (the guess only seeds New); saving creates the exercise with the card's type; the imported item carries no reps and keeps the "20 Cal" note. Both Hiraya fixtures still read as their example tests say, and their cards differ from today's only by Echo Bike's pre-selected type.
35. **Harness, records and series.** `data.mjs`'s `computeRecords` and `progressFor` cover the three types (records for each, a series with the new fields), so the harness captures the Records list, a finish summary with a calories card and a carry card, and the Progress chart for each new type.

## 4. Data model

None. No migration, no table, no column, no persisted-format change except one: the **local** drafts file `sin:workout:drafts` gains an optional `calories` string (AC14). It is read with a default, so both directions of a bundle rollback are safe (an old bundle's schema ignores the extra key because Zod objects strip unknown keys). The outbox file is untouched; its op bodies are validated by `CreateSetSchema` / `UpdateSetSchema` from `@sin/core`, which accept `calories` after 05.3 Phase A.

## 6. Behavior & logic

### 6.1 Labels and hints (`catalog/labels.ts`)

`MODALITY_LABELS` is unchanged from 05.3's entries (D3). `MODALITY_HINTS: Record<Modality, string>`, plain and with an example each (mine, D4):

| Type | Hint |
|---|---|
| Weight × reps | Weight and reps, like a squat. |
| Bodyweight × reps | Reps only, like a pull-up. |

### 6.4 Steppers (`stepper.ts`)

```

stepCalories(text, direction): String(clamp(toWhole(text) ± 5, 0, SET_CALORIES_MAX))

```

`toWhole` is the existing helper (blank or unparsable is 0). A value that is not a multiple of 5 steps by 5 from where it is (22 → 27); it does not snap. Why 5 (D7): bike and ski sessions are logged in tens of calories, so a step of 1 is a tap marathon, and a step of 10 skips the 15s and 25s she writes in plans; typing stays available for anything else.

- **D8 ✅ "·" separates the pair in set text and the bar label ("24 kg · 40 m"), not "×".** Rationale: weight × reps is a product (volume), a carry is not; "·" is what `distance_duration` already uses. **(mine)**

- **D10 ✅ Record names: "Most calories", "Longest distance", "Longest hold"; chip names equal the long names.** Rationale: they match "Most reps" and 05.3's compile arms; chips already carry full short names such as "Most reps". "Longest hold" for `max_duration` is right for the only type that has it today; the deferred records for `duration` can reuse it ("plank hold") or a later spec can split the wording. **(mine)**
