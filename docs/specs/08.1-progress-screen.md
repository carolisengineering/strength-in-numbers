## 1. Purpose, scope & non-goals

Make the progress numbers visible: a **Progress** tab that lists the exercises the lifter holds records for, and a **per-exercise screen** with a line chart of one metric over time (estimated 1RM, top set, volume, reps), a range switch, a tappable readout that links back to the session, and that exercise's personal records. No API change, no migration, no new env var, no new browser-storage key, and **no chart library** — the chart is a small hand-written SVG component (D1, Q17).

> **First-principles note — what an SVG chart is, and why no library.** SVG is markup for shapes. A `<svg viewBox="0 0 360 220">` declares its own coordinate system, 360 units wide and 220 tall, and the browser scales that box to whatever width CSS gives it (`width: 100%`; the height follows from the box's aspect ratio). A line chart is then arithmetic: map each session's date to an x coordinate and its value to a y coordinate, emit one `<polyline points="x,y x,y …">` and one `<circle>` per point, plus a few `<line>` / `<text>` elements for the axes. React renders those elements like any others. A chart library does the same arithmetic but also brings an opinionated component tree, its own styling system (usually inline `style` attributes or injected `<style>` tags — both blocked by this app's `style-src 'self'`, or at best an exception to the "design values live in `tokens.css`" rule), a resize observer, and tens of kilobytes. This chart has one series, ≤ ~400 points, four y ticks and no animation; the whole job is ~150 lines of pure geometry plus ~100 lines of JSX, and the geometry is pure functions that can be tested exhaustively (R4: a wrong plotted number is a visible wrong number).
>
> **Why `null` matters.** The API returns every metric on every point, and any of them may be `null` at a point ("no eligible set that session" — a warm-up-heavy day, a 13+-rep set for e1RM, Spec 07.2 §3). `null` is not `0`. The client **skips** a point for a metric whose value is `null`; it never plots zero. That is the whole of 07.2 O2's client-side resolution (D3).

## 2. Acceptance criteria

Behavioral criteria each get ≥1 test whose `describe` is tagged **`"08.1 ACn — …"`** (08.0 / 06.4 D6's prefix convention). Levels are in §10. **Phase A** (AC1–AC9): pure logic, client, queries, cache effects. **Phase B** (AC10–AC24): screens. **Phase C** (AC25–AC29): cross-cutting and verification. **Docs** (AC30–AC31).

### Phase A — logic, client, queries

1. **Range start dates, with month-end clamping.** `rangeStart(today, range)` (`features/progress/range.ts`, pure, integer arithmetic on the `YYYY-MM-DD` string — no `Date`, so no timezone or DST input): `"3m"` → `today` minus 3 calendar months, `"1y"` → minus 12 months, `"all"` → `undefined`. When the target month is shorter than the source day the day **clamps to the target month's last day**: `2026-05-31` → `2026-02-28`; `2028-05-31` → `2028-02-29`; `2028-02-29` minus 12 months → `2027-02-28`; `2026-01-31` minus 3 months → `2025-10-31` (year borrow); `2026-03-31` → `2025-12-31`. The result is the *inclusive* lower bound (07.2 AC10). `rangeLabel(range)` gives the wording used in the summary and the empty state (`"3 months"`, `"1 year"`, `"all time"`).
2. **Metrics are data-derived and null-safe.** `METRICS` (`metrics.ts`) lists the four metrics in display order — `est1rm` ("Est. 1RM", field `bestE1rm`, record unit `kg`), `topSet` ("Top set", `topSetWeight`, `kg`), `volume` ("Volume", `totalVolume`, `kg_reps`), `reps` ("Reps", `maxReps`, `reps`). `pointsFor(series, metric, pref)` returns the chart points for one metric: it **skips** points whose field is `null` (never plots `0`), keeps API order (oldest → newest), and gives each point `{ id: workoutId, localDate, canonical, y }` where `canonical` is the served number (kg / kg·reps / reps) and `y` is the number to **scale** — for weight and volume metrics under `pref = "lb"`, `y = kgToLb(canonical)` (`@sin/core`; the one copy of the pound's definition), converted **before** ticks are chosen so ticks fall on round lb values. `availableMetrics(series)` lists metrics with ≥ 1 non-null point, in `METRICS` order. `defaultMetric(available)` is `est1rm` if present, else `topSet`, else `reps`; `volume` is never the default; `undefined` when `available` is empty. `resolveMetric(chosen, available)` returns `chosen` if it is in `available`, else `defaultMetric(available)`.
3. **`niceTicks(min, max, count, { integer? })`** (`scale.ts`, pure) returns ascending tick values on a 1-2-5 × 10ⁿ step, at most `count + 1` ticks, with `ticks[0] ≤ min` and `ticks[last] ≥ max` (the y domain is the first-to-last tick). A flat series (`min === max`) is padded first (±10 % of `|v|`, or ±1 for `v = 0`) so a single value gets a real axis; a single value therefore yields ≥ 2 ticks. With `integer: true` (the reps metric) the step is never below 1 and every tick is an integer. Cases: flat (`100,100`), single (`1,1`), wide (`0.5 … 480 000`, volume in lb), narrow (`101.2 … 101.8`), reps (`8 … 12`), and an lb series (`231.5 … 270.1`) — no tick is `NaN`/`Infinity`, none is a float artefact (`0.30000000000000004` prints as `0.3`: ticks are rounded to the step's decimal places).
4. **Chart geometry.** `layoutChart(points, viewBox)` (`scale.ts`, pure) maps points into the fixed viewBox **360 × 220** with a plot area inside fixed margins. **x is real time**: `(days since the first point's `localDate`) / (days between first and last)` — so a 3-week gap is a visible gap; two sessions on one date share an x; all points on one date, or a single point, are centred. y is linear on the tick domain, larger values higher (SVG's y grows downward — a test pins a larger value having a *smaller* y). `hitAreas(layout)` gives each point one rect, and the rects tile the whole viewBox: each x column runs between the midpoints to its neighbouring columns (the outer columns reach the edges), and same-date points split their column at the y midpoints, higher value on top — so hit targets never overlap, a tap selects the point whose area it lands in, and a dense stretch never shrinks a sparse point's target. *(Final review I2, 2026-10-08: replaces v0.1's `hitRadius` — 28 units, else half the nearest x-gap with a floor of 8 — whose floor made neighbouring circles overlap on any 1Y/All chart of weekly sessions, so a tap on a dot often selected the next session, and one same-date pair shrank every target.)* `xLabels(points)` returns 3–4 evenly thinned labels at **first-of-month** dates inside the span (`Oct`), falling back to the first and last point's day-month (`6 Oct`, `21 Oct`) when the span holds fewer than two month starts, and to the single date for one point; labels carry a two-digit year (`Oct 26`) **iff the span crosses a calendar-year boundary** (D9).
5. **The progress client builds the right request.** `getSeries(exerciseId, { from? })` issues `GET /v1/progress/exercises/{id}` with the id **path-encoded** (`encodeURIComponent`; an id `a/b?c#d` cannot change the path or add a parameter) and `?from=YYYY-MM-DD` built with `URLSearchParams` only when `from` is given; it never sends `to`; the body is parsed with `ProgressSeriesSchema`. `getSeries` has no knowledge of ranges or clocks.
6. **Records grouping and keys.** `groupByExercise(records)` (`exercises.ts`, pure) groups by `exerciseId` (the lineage root) and returns one entry per exercise: `exerciseId`, `name` = the **newest** record's `exerciseName` snapshot (newest by `Date.parse(achievedAt)`), `newest` (that record), and `headline` — the record to show: `best_est_1rm` if the exercise has one, else `heaviest_weight`, else `max_reps`; `best_set_volume` is **never** the headline; `null` when the exercise has none of the three. Entries are ordered newest record first (`achievedAt` descending), ties by `name.localeCompare`, then `exerciseId`. `RECORDS_KEYS.list` is `["records","all"]`; `useAllRecords()` is `useQuery` on it calling `listRecords({})` with no filter; `useExerciseRecords(id)` is `useQuery` on the existing `RECORDS_KEYS.forExercise(id)` calling `listRecords({ exerciseId: id })`. Both keys sit under the `["records"]` prefix, so 08.0's finish/delete invalidation already covers them.
7. **The series query.** `useSeries(exerciseId, range)` (`queries.ts`) is `useQuery` keyed `["progress", exerciseId, range]` (`PROGRESS_KEYS.series(id, range)`; `PROGRESS_KEYS.all = ["progress"]`) with `placeholderData: keepPreviousData`, `retry: false` and `networkMode: "always"` (offline fails as a `network` error instead of pausing — D11; final review I1); no own `staleTime` (inherits the 30 s default, as 08.0 D9). The `from` value is computed **inside `queryFn`**, at fetch time, as `rangeStart(today(), range)` where `today()` is the clock read from `ProgressClockContext` (default: the device's local calendar date, `YYYY-MM-DD`, from `getFullYear/getMonth/getDate`); the date is **not** part of the key. Each range is its own cache entry: switching 3M → 1Y → 3M issues two requests, not three, within the stale window. While a new range's first load is pending, `data` is the previous range's series with `isPlaceholderData: true`.
8. **Finish and delete invalidate progress.** `applyFinishedCaches` and `applyDeletedCaches` each also call `invalidateQueries({ queryKey: PROGRESS_KEYS.all })` (so a finish, a delete, the "already finished" recovery path — all call sites of 08.0 D7's helper pair — refresh every cached series on next view). 08.0's AC6 / AC7 / AC8 tests are extended, not duplicated; nothing else about those helpers changes, and 08.0's tests that do not mention progress pass unmodified.
9. **The chart's accessible summary.** `chartSummary({ metric, range, points, pref })` (`metrics.ts`, pure) returns `"{Metric}, {range label}: {first} to {last}, best {max}"` — e.g. `Est. 1RM, 3 months: 105 kg to 122.5 kg, best 122.5 kg` — with values through `formatRecordValue(canonical, unit, pref)` (so it matches the readout and the records block to the character), `first`/`last` being the oldest and newest plotted points and `best` the maximum; for one point `"{Metric}, {range label}: 1 session, {value}"`. Under `lb` the same string reads `231.5 lb to 270.1 lb, best 270.1 lb` (conversion through the shared formatter, not a second implementation).

### Phase B — screens

10. **Routes and navigation.** `/app/progress` renders `ProgressScreen`; `/app/progress/:exerciseId` renders `ExerciseProgressScreen`; both under the existing `ProtectedRoute > ProtectedLayout > AppShell`. The Progress `NAV_ITEMS` entry has no `comingSoon` flag, and **no** nav item has one; the nav shows no "coming soon" badge. At `/app/progress/<id>` the Progress link has `aria-current="page"` and no other nav link does (via `navItemFor`'s prefix match); the shell header title reads "Progress". The `/app/progress` route no longer renders `ComingSoon`. The tests that pinned Progress as coming soon (`workoutRouting.test.tsx`'s nav-item test; `HistoryScreen.test.tsx`'s "…`/app/progress` is still coming soon" case) are updated in the same PR.
11. **A Progress list row.** `ProgressScreen` calls `useAllRecords()` once (no filter) and renders one `<li>` per `groupByExercise` entry, **each a single link** to `/app/progress/<exerciseId>` (id path-encoded; ≥ 44 px tall). Line 1: the name. Line 2: the headline in the lifter's unit — `Best est. 1RM 122.5 kg`, `Heaviest weight 60 kg` (label from `recordLabel`, value from `formatRecordValue`) or `Most reps 15 reps` — followed by ` · ` and the **newest record's `localDate`** through `formatLocalDate`; with no headline type the line is the date alone. Rows are in `groupByExercise` order. The list is a `<ul>` with an accessible name; the screen has the single `<h1>` "Progress".
12. **List states.** Pending: the full-screen `Spinner` (label "Loading your progress…"). `records: []`: the text "No records yet — finish a workout to see your progress" and a link "Go to Workouts" to `/app/workouts`; no list. Failure with no data: a full `InlineNotice` (`tone="error"`) "Couldn't load your progress" with "Try again" (`refetch()`) and the request id when the error carries one; a failed background refresh with rows cached keeps the rows and shows "Couldn't refresh your progress" + "Try again". `network`, `server`, `unauthenticated` and `unknown` failures all take these paths; `reportUnexpected("load-progress-list", …)` runs and reports only `unknown`.
13. **The exercise screen's frame.** `ExerciseProgressScreen` reads `exerciseId` from the route and renders the single `<h1>`: the exercise name — the newest record's `exerciseName` from `useExerciseRecords(id)` — or the fallback **"Exercise progress"** while that query is pending, failed or empty. Below it, in order: the metric control (AC14), the range chips (AC15), the chart area (AC16–AC17, AC20–AC21), the sessions list (AC18), the per-exercise records (AC19), and a link "Back to Progress" → `/app/progress` (≥ 44 px). Defaults on mount: metric = `resolveMetric(undefined, …)` (est. 1RM when it has data), range = `3m`. The records query never delays the title's fallback or the chart.
14. **The metric control.** A `role="group"` named "Metric" with one button per `availableMetrics(series)` entry for the **current range's** series — a metric with no non-null point in this range is not offered — each with `aria-pressed` and ≥ 44 px tall. The pressed button is `resolveMetric(chosen, available)`: the lifter's choice is kept in component state across range changes while the screen is mounted, and when the chosen metric has no data in the new range the effective metric falls back to `defaultMetric` *without discarding the choice* (returning to a range where it has data restores it). The control is absent when nothing is offered (AC20).
15. **The range chips.** A `role="group"` named "Range" with three `aria-pressed` buttons "3M" (default), "1Y", "All". Selecting one requests `from` = `rangeStart(today(), range)` (AC1) — the fake's request log shows `from=<expected>` for 3M and 1Y and **no `from`** for All, with the injected clock. Each range is its own cache entry (AC7). While a new range's first load is pending, the previous range's chart stays rendered (no empty flash), the chart area carries `aria-busy="true"` and a small `role="status"` line "Loading {range label}…" is added beside it; when the data lands, `aria-busy` clears. The chips stay enabled during loading (a rapid second tap supersedes the first; the screen shows only the latest range's data).
16. **The chart.** `LineChart` (`features/progress/LineChart.tsx`; generic over points, no fetching, no data hooks) renders one `<svg viewBox="0 0 360 220" width="100%">` with no `ResizeObserver` and no JS measuring, `role="img"` and `aria-label` = `chartSummary(…)` (AC9). Inside: one `<polyline>` through the points in order when there are ≥ 2 (none for one point — a lone dot), one visible `<circle>` per point, 3–4 horizontal ticks with labels from `niceTicks` (values only, no unit — the unit is in the caption and the readout), the x labels from `xLabels` (AC4), and one transparent **hit rect** per point from `hitAreas(layout)` with an `onClick` that calls `onSelect(point.id)`. The selected point's visible dot is larger and carries `data-selected="true"` and a class (size, not colour alone, marks it). No SVG child is focusable (no `tabIndex`, no `<a>`); the keyboard and screen-reader path is AC18. A caption above the chart names the metric and unit (`Est. 1RM (kg)`, `Volume (lb × reps)`, `Reps`). The component reads colours, stroke widths and font sizes from CSS-module classes on tokens only (AC26).
17. **Selection and the readout.** The default selection is the **newest** plotted point. Tapping a point's hit area selects it. A readout above the chart (`aria-live="polite"`, `aria-atomic="true"`) shows `"{date} · {value}"` — date through the year-bearing formatter (`Tue 6 Oct 2026`, D9), value through `formatRecordValue` — and next to it (outside the live region) a link **"Open workout"** → `/app/history/<workoutId>` (id path-encoded; ≥ 44 px). The selection is a workout id: it survives a metric switch when that workout has a value for the new metric, and otherwise falls back to the newest point; on a range change it likewise falls back when the workout is outside the new range.
18. **The sessions list.** Below the chart, a `<ul>` (named "Sessions") of every plotted point, **newest first**, one `<li>` per point containing a `<button>` whose text is `"{date} · {value}"` (same formatters as the readout) with `aria-pressed` for the selected point and ≥ 44 px height. Activating a row selects the same point as tapping its dot — the readout and the chart's selected dot follow. This is the keyboard / screen-reader / small-target path (D5). Rows reflect the current metric and range, so a metric a session has no value for does not list it.
19. **The exercise's personal records.** `useExerciseRecords(id)` feeds a `RecordsSection` (the shared presentational part extracted from 08.0's block, AC-guarded by 08.0's own unchanged tests): heading "Personal records", a `<ul>` ordered by `sortRecords`, each line `recordLine(record, pref)` (`Bench Press — Best est. 1RM 122.5 kg (was 120 kg)`), all four types shown (including `best_set_volume`). `[]` → the whole section, heading included, is absent; pending → nothing in its place. The section is a sibling of the chart area, so neither can unmount the other.
20. **Empty and thin ranges.** A series with `points: []` shows "No sessions in the last 3 months" (wording per range: "…in the last year", "No sessions yet" for All) in place of the metric control, chart and sessions list; the range chips stay usable. A series whose points all have `null` for every metric (07.2 D7 — e.g. a duration exercise reached by URL) shows "Nothing to chart for this exercise yet" instead of a chart, with no metric control. **One** plotted point renders a dot, no polyline, a readout, and one sessions row. These states are not errors and are not reported.
21. **Series failure.** *No data yet* (first load fails): the chart area shows an `InlineNotice` (`tone="error"`) "Couldn't load this chart" with "Try again" (`refetch()`) and the request id when present; the range chips and "Back to Progress" stay usable and the records section is unaffected. *A new range fails while another range was already shown*: TanStack drops `placeholderData` on error, so the screen keeps the last successfully displayed `{ range, series }` and keeps **that** chart visible, with its own summary/caption wording, plus an `InlineNotice` "Couldn't load {range label}" + "Try again" — the chart never silently shows data for a range other than the one it is labelled with. A failed background refetch with cached data keeps the data and shows "Couldn't refresh this chart". `reportUnexpected("load-progress-series", …)` runs and reports only `unknown`.
22. **Records failure on the exercise screen.** A records failure shows the shared block-local notice "Couldn't load records" with "Try again" and **keeps cached records visible beside it** (08.0's post-review behavior, inherited from `RecordsSection`); the chart, controls, sessions list and Back link are unaffected. `reportUnexpected("load-records", …)` (the existing op).
23. **Unknown and malformed ids.** A series `404` (a well-formed id the caller cannot see) or `422` (malformed id) renders the existing `NotFound` screen — when there is no previously displayed series to keep (a `404` on a *later* range of an already-shown exercise takes AC21's path). The records query cannot supply this signal: `GET /v1/personal-records?exerciseId=` resolves any *visible* id to its lineage root and answers `200 []` for an unknown or foreign one (07.0 §5), so only the series decides. No `reportError` for either.
24. **Units follow the profile, with a safe fallback.** The list headline, the tick scale, tick labels, the caption, the readout, the sessions rows, the chart summary and the records lines all read `unitPreference` from `useMe()`; while it has no data they format as `kg`, and re-render in `lb` when the preference arrives or changes (no stale text). Under `lb` the plotted `y` values and ticks are in lb (AC2), and a session's displayed value equals `formatRecordValue(canonical, unit, "lb")` — the same string History and the records block show for the same number.

### Phase C — cross-cutting and verification

25. **Accessibility and one-handed layout (component level).** Following 08.0 AC23's pattern in `a11y.test.tsx`: the list screen and the exercise screen each have exactly one `<h1>`; the chart `<svg>` has `role="img"` and a non-empty accessible name; the metric and range groups are named groups of `aria-pressed` buttons with accessible names; every button and link carries the tap-target class; the readout is `aria-live="polite"`; the sessions list and the records list are real lists; error notices are `role="alert"`, empty and `aria-busy` states are not alerts; no SVG descendant is focusable. Tap-target pixel sizes and the 320 px hit-area sizes (§6.3) are verified in a browser (AC28 / AC29), since jsdom has no layout.
26. **Tokens only; no inline styles.** Every new `*.module.css` references design values via `var(--…)` (unitless SVG values — `stroke-width: 2`, `opacity: 0.6` — are not `px` and pass `assert-css-tokens`; the script flags only `px` ≠ 0/1, hex and colour functions); `pnpm --filter @sin/web run assert:css-tokens` passes; `tokens.css` is edited only if a genuinely new token is needed (then in the same PR). A source scan over `features/progress/` (non-test files) finds **no** `style=`, no `<style`, and no `fill=` / `stroke=` attribute (all paint is CSS classes), and no `ResizeObserver`, `getBoundingClientRect` or `window.innerWidth`. The CSP is unchanged.
27. **Observability and hygiene.** No new `track()` event. `reportError` is called only through `reportUnexpected` with `{ source: "workouts", op }` where `op` ∈ {`"load-progress-list"`, `"load-progress-series"`, `"load-records"`} — static tags only, never an exercise id, name, value or date (a spy test over every failure path, 06.1 AC35's pattern). No new `localStorage` / `sessionStorage` reference (04.0 AC7's scan stays green); `USER_DATA_KEY_PREFIXES` is unchanged; no `persister`.
28. **Playwright smoke gains a Progress step** (Spec 06.3's single test; skipped like the rest until the Auth0 test-user secrets exist). After the Finish step and before the History step: open **Progress** from the nav; the bench-press row (located by role `link` whose name contains "Barbell bench press") is visible; open it; the chart `<svg>` with `role="img"` whose name matches `/^Est\. 1RM, 3 months:/` is visible and the metric group is visible. **No value is asserted** (08.0 D12's reasoning: whether this run sets a record depends on the account's prior workouts — but the *row* exists whenever any finished workout in the account trained the lineage, and the run's own workout is finished at that point). The `workoutId` capture moves up into the Finish step so the later History/delete steps are unaffected. The smoke's zero-console-error / zero-CSP-violation guard (06.3 AC2) stays green, which is also the real-browser check that the SVG carries no blocked inline style.
29. **Manual phone check (recorded in the PR description).** On a phone: the chart for a real exercise shows points whose readouts match hand-computed values for **ten** sessions (top set, e1RM = `w × (1 + reps/30)`, session volume, max reps) in the profile's unit, including a kg↔lb profile switch; the 3M / 1Y / All chips behave; **dot taps land on the intended point** at 320 px and 360 px; the sessions list is operable with VoiceOver (each row announces date and value; the readout is announced on selection); the 320 px nav and chart do not overflow. The ten hand-reconciled sessions, shared with 08.0's AC27, are M2's exit criterion (DESIGN §9) — this spec owns the chart half.

## 6. Behavior & logic

### 6.1 Data flow and cache

**Keys.**

```ts
PROGRESS_KEYS = { all: ["progress"], series: (id, range) => ["progress", id, range] } as const;
RECORDS_KEYS  = { all: ["records"], list: ["records", "all"],
                  forWorkout: (id) => ["records", { workoutId: id }],
                  forExercise: (id) => ["records", { exerciseId: id }] };   // list is new; the rest are 08.0's
```

TanStack matches `invalidateQueries({ queryKey })` by prefix, so `["progress"]` covers every series and `["records"]` — already invalidated by 08.0's helpers — covers both new records queries. The only new write path is one line in each helper (AC8). Because `invalidateOthers` in 08.0's `cache.ts` already spares only the finished workout's own records entry, `["records","all"]` and `["records",{ exerciseId }]` are invalidated by every finish and delete, which is right: a finish can create or move a record for any lineage.

**Freshness.** Neither query sets its own `staleTime`; both inherit the app default (30 s) with `retry: false`, as 08.0 D9. Freshness against writes is by explicit invalidation; against another device by the 30 s window. An invalidated series that no component observes is only marked stale and refetches when the screen next mounts, showing cached data meanwhile.

**The range → `from` mapping runs at fetch time.** `useSeries`'s `queryFn` reads `today()` when it runs, so a tab left open across midnight computes the new window on its next fetch; the date is deliberately **not** in the key (a key containing "today" would make every midnight a cache miss for no reason, and the 30 s freshness bound makes the staleness irrelevant). `ProgressClockContext` exists purely as a test seam (a default context value of the device's local date; a test provides `() => "2026-10-08"`), the same shape as the client contexts.

**Device date vs `local_date`.** `workout.local_date` is derived once at write time in the *profile's* time zone (05.0); `today()` is the *device's* calendar date. When they differ (a lifter travelling), the 3-month window's edge can move by a day. That is harmless for a rolling "last 3 months" view, and using the profile time zone would need a tz library for no visible gain. Recorded (D7).

**Previous data while loading (`keepPreviousData`).** On a range change the query key changes; without help the observer's `data` would be `undefined` until the new request resolves and the chart would flash empty. `placeholderData: keepPreviousData` makes `data` the previous key's data (flagged `isPlaceholderData`) for that interval. TanStack drops the placeholder when the query **errors** (placeholder data exists only while `status === "pending"`), so the failed-new-range case (AC21) needs the explicit `lastShown` ref: the screen writes `{ range, series }` into it in an effect whenever it renders real (non-placeholder) data, and falls back to it on error. The ref holds the data the lifter was last looking at, labelled with its own range, so the screen can never present one range's points under another range's name.

### 6.2 Metrics and plotted points

`pointsFor(series, metric, pref)` is a `flatMap` over `series.points`: `const canonical = point[METRICS[metric].field]; if (canonical === null) return []`. `y = isWeightLike(metric) && pref === "lb" ? kgToLb(canonical) : canonical`. The displayed *string* never derives from `y`: it comes from `formatRecordValue(canonical, unit, pref)` — one rounding rule across History, the records block and the chart (08.0 AC1, D8). `y` exists only to position things.

The **series max equals the PR** guarantee (07.2 AC14) holds for the **All** range of the est. 1RM, top-set and reps metrics: the chart's highest point equals the records block's `best_est_1rm` / `heaviest_weight` / `max_reps` value for the same exercise. A 3M or 1Y chart's best is the best *within the window* and need not match the PR. **Volume** is a session sum and is never expected to match `best_set_volume` (07.2 D12) — which is why volume is never the default metric: it is the one chart whose peak a lifter could compare, wrongly, with the "Best set volume" line.

### 6.3 Geometry (`scale.ts`)

- **ViewBox 360 × 220.** Margins: left 48 (y labels up to `1,234.5`-style at 14 units ≈ 40 wide), right 16, top 12, bottom 28 (x labels). Plot area 296 × 180.
- **Ticks.** `niceTicks(yMin, yMax, 4)`: pad a flat series, pick `step = niceStep((max - min) / count)` from {1, 2, 5} × 10ⁿ, `ticks = floor(min/step)…ceil(max/step)` multiplied back and rounded to the step's decimals. The y domain is `[ticks[0], ticks[last]]`; y px = `top + plotH × (1 − (y − t0)/(tN − t0))`.
- **x.** `dayNumber(localDate)` = days since 1970-01-01 from `Date.UTC(y, m−1, d) / 86 400 000` (UTC arithmetic on the date string, no local-zone input). `x = left + plotW × (day − day0)/(dayN − day0)`; the denominator is zero for one point or one date, in which case x is the plot centre.
- **Hit targets.** WCAG 2.5.5 / this app's `--tap-target-min` is 44 CSS px. The SVG scales with its container (scale 0.8 for the 288 px chart at a 320 px viewport). Each point's hit rect is its share of a tiling of the viewBox (AC4): full height for a lone point in its column, as wide as the midpoints to its neighbours — so a sparse point's target is far larger than 44 px, and a dense series degrades to narrower but never-overlapping strips (the sessions list is the guaranteed 44 px path). Hit rects stay inside the viewBox, are drawn last (on top) with `fill: transparent` (CSS) and `pointer-events: all`. *(Final review I2: replaced v0.1's radius-with-floor-8 circles, which overlapped.)*
- **Lines.** `polyline` and gridlines use CSS `vector-effect: non-scaling-stroke` with unitless widths so stroke weight is the same CSS-pixel thickness at any container width; label `font-size` is a token (`--font-size-sm`), which in SVG is read in *user units* and scales with the viewBox (≈ 11 px at 320 px) — acceptable for secondary labels, since the exact numbers are in the readout and the list (AC29 checks legibility on the phone).

### 6.4 The exercise screen's state machine

```
const [range, setRange]       = useState<Range>("3m");
const [chosen, setChosen]     = useState<Metric | null>(null);      // the lifter's explicit choice
const [selectedId, setSelect] = useState<string | null>(null);      // null ⇒ newest
const series  = useSeries(id, range);
const shown   = series.data ?? lastShown.current?.series;           // AC15 / AC21
const available = availableMetrics(shown);
const metric    = resolveMetric(chosen, available);
const points    = pointsFor(shown, metric, pref);
const selected  = points.find(p => p.id === selectedId) ?? points.at(-1);
```

`selectedId` and `chosen` are *preferences* that are re-validated against the current data on every render (AC14, AC17) rather than reset by effects — no effect-driven state-sync, nothing to forget to clear. The route element is keyed by `exerciseId` (`<ExerciseProgressScreen key={id} />` via a small wrapper) so navigating between two exercises starts from defaults and never carries one exercise's range, metric or `lastShown` into another. `lastShown` is written in a `useEffect` on `series.data` when `!series.isPlaceholderData`.

### 6.5 The Progress list

`groupByExercise` (AC6) is pure. The list shows **only** exercises with at least one record: an exercise trained but with no record (duration, or a `bodyweight_reps` set of 0 reps) does not appear (D6) — its chart is reachable only by URL, hence AC20's all-null state. The records come from one unfiltered request that 08.0 already shaped for this (07.0: ≤ 4 rows per lineage root, un-paginated, "low hundreds at the extreme").

### 6.6 Dates

- **List line 2** keeps 08.0's `formatLocalDate` (`Tue 6 Oct`).
- **Readout and sessions rows** use `formatLocalDateWithYear` (`features/progress/dates.ts`): the same pinned `en-GB` / `timeZone: "UTC"` options plus `year: "numeric"` (`Tue 6 Oct 2026`), because on the **All** range two sessions can share a day-and-month a year apart and these are the places a lifter distinguishes one session from another.
- **X-axis labels** (AC4) show the year only when the plotted span crosses a calendar-year boundary.
- History rows are untouched (08.0 O5 stays as it was); the new formatter is the obvious building block if the owner decides to act on it.

## 7. Security & privacy

- **Authorization is the server's.** Series and records are scoped to the authenticated user (07.2 §7, 07.0 §7); a tampered `:exerciseId` can only name an exercise the caller can see, otherwise `404` — and the client adds no authority.
- **Path/query injection.** The route param goes into the request path through `encodeURIComponent` and `from` through `URLSearchParams` (AC5); the same for the records filter (08.0 AC4) and for every link built from a server id (`/app/progress/<id>`, `/app/history/<id>`). A hostile id such as `../x` or `a?b` cannot escape its path segment.
- **No inline style, no injected markup.** The SVG is built from React elements with CSS-module classes; no `dangerouslySetInnerHTML`, no `style` prop or attribute, no `<style>` (AC26). `style-src 'self'` forbids inline style *attributes* and `<style>` elements; React `style={{…}}` props are applied through the CSSOM and are allowed by that policy, but the design forbids them anyway — design values live only in `tokens.css`, so a chart that needed a computed pixel in `style` would be a design violation first and a CSP question never.
- **Exercise names and values are user data.** They appear in the DOM (including the `aria-label`) and nowhere in logs: `reportError` tags are static (AC27). Names come from the record's snapshot, escaped by React like any text.
- **Cross-user residue.** As 08.0 §7: nothing persists; logout is a full redirect; an in-SPA account switch would have to `queryClient.clear()` (08.0 O3).
- **CSP.** No new origin, script or style source; no image or font download.

## 12. Decisions & open questions

### Resolved (drafting-time; owner-approved 2026-10-08)

- ✅ **D1 — Hand-written SVG chart; no chart library.** **Rationale:** one series, ≤ ~400 points, four y ticks, no animation — the job is geometry, which is cheaper to write and to test as pure functions than to adapt a library to this app's constraints (`style-src 'self'`, "design values only in `tokens.css`", an `assert:css-tokens` tripwire, a mobile-first bundle). A library would add tens of kB, its own styling path and a resize observer, and would make the plotted numbers pass through code we did not write — R4 wants the opposite. Rejected: Recharts / visx / uPlot / Chart.js (each either injects inline styles, ships a styling system, or draws to `<canvas>` — which has no accessible structure and no CSS tokens). Cost: no zoom, pan or animation, and a later richer chart (e.g. multi-series) may justify revisiting. Q17.
- ✅ **D2 — The chart is generic and dumb; the screen owns data and state.** `LineChart` takes points, a formatter, the selected id, `onSelect` and a summary string, and never fetches; geometry lives in `scale.ts`, metric knowledge in `metrics.ts`. **Rationale:** the pure pieces carry the risk and are tested without a DOM; the component is thin enough to test by counting elements. A later chart reuses them.
- ✅ **D3 — 07.2 O2 resolved client-side: skip `null` per metric; the API keeps all-null points.** **Rationale:** a point is "a session that trained the lineage" (07.2 D7); whether it has a countable value is per metric (a session with only a 15-rep set has no e1RM but has a top set). Dropping all-null points in the API would not solve the per-metric case anyway, and the client already needs the null-skip. An all-null series (a duration exercise) therefore renders as "Nothing to chart for this exercise yet" (AC20). No API change; Spec 07.2's behavior and tests stand. Q17.
- ✅ **D4 — A new `ProgressClientProvider`, not an extension of `HistoryRecordsClientProvider`.** **Rationale:** the providers are ~10-line adapters from `useApi()` to a client; adding a third client to the history/records one would rename or overload a component whose name and tests are 08.0's, for no gain. Tests inject through each context independently. Cost: one more provider line in `ProtectedLayout`.
- ✅ **D5 — Point selection by tapping a dot, plus a sessions list as the accessible path.** The SVG is `role="img"` with a summary; dots are not focusable. **Rationale:** a chart of 100 focusable dots is a keyboard trap and a screen-reader wall; a labelled summary + a plain list of buttons gives the same information and the same selection action to everyone. Hit areas are the touch-friendly path: rects tiling the viewBox (§6.3), wide for sparse points and narrowing — never overlapping — when points are dense, where the list takes over.
- ✅ **D6 — The Progress list is built from `GET /v1/personal-records` (no filter), grouped by lineage root.** **Rationale:** it is one small request that already carries each exercise's name snapshot, a headline number and a recency date; a catalog-driven list would need a "which exercises has the user trained" API that does not exist and would list exercises with nothing to chart. **Consequence:** an exercise with sessions but no records (duration; zero-rep) is not listed — reachable only by URL (AC20 covers its chart), acceptable because it has nothing chartable in v1. `best_set_volume` is never the headline because it is a single-set number a lifter would compare with the chart's *session-sum* volume (07.2 D12).
- ✅ **D7 — `from` is computed at fetch time from the device's local date; clamped month arithmetic on the date string.** **Rationale:** a rolling window needs "today"; computing it in `queryFn` keeps a long-open tab honest without putting a date in the key; string arithmetic avoids `Date`'s zone and DST inputs and makes 31 May − 3 months a pure, pinned `28 Feb`. The device-vs-profile time-zone edge (§6.1) is accepted. Rejected: `to` (the API default of "everything up to now" is what we want; a `to` would only add a second thing to get wrong) and a server-computed window.
- ✅ **D8 — Each range is its own cache entry; `keepPreviousData` for the loading gap, a `lastShown` ref for the error gap.** **Rationale:** §6.1 — placeholder data does not survive an error, and the alternative of one cache entry refetched with a changing `from` loses the "back to 3M is instant" behavior and the clean per-range failure semantics. The ref guarantees a chart is never labelled with a range it does not show.
- ✅ **D9 — Dates: year in the readout and sessions rows; year on x labels only across a year boundary; list line 2 and History rows unchanged.** **Rationale:** the readout/list are where a lifter tells sessions apart (a year-old "Tue 6 Oct" would mislead on All); x labels are space-constrained and a year only matters when the axis crosses it. This answers 08.0 O5 for the places this spec owns and leaves History rows as the owner's call (O2).
- ✅ **D10 — Screen state is not persisted across navigation.** Leaving for "Open workout" and pressing Back returns to defaults (3M, est. 1RM, newest selected). **Rationale:** persisting range/metric would add a `sin:progress:` storage key (and logout clearing) or lifting state into the router; the loss is one tap, and the cached series makes the return instant. Revisit if the phone check says it's annoying (O5).
- ✅ **D11 — Progress is offline-naive.** A failed request shows the ordinary notice (as 08.0 D11); reading a chart is not the time-critical gym path. *(Final review I1, 2026-10-08: TanStack's default `networkMode: "online"` **pauses** a query offline rather than failing it, which left the previous range's chart under the new range's chip with no notice; `useSeries` sets `networkMode: "always"` so offline is the `network` failure this decision assumes. Code review #1, same day: the Progress list's and the exercise screen's records queries (`useAllRecords`, `useExerciseRecords`) do the same, so opening Progress after losing signal shows the notice instead of an endless spinner. Other reads, 08.0's History included, keep the app-wide default; a cold start offline still stops at the `/v1/me` bootstrap, which is pre-existing.)*
- ✅ **D12 — The `comingSoon` mechanism and `ComingSoon` screen stay.** No nav item uses them after this spec, but the `NavItem.comingSoon?` field is part of 04.1's published registry contract and 04.1's tests exercise it; deleting it is a separate cleanup, not a requirement of this feature. **Rationale:** smallest coherent change; the Routines/Account tabs (Specs 10 / 12) may reuse it. The router stops rendering `ComingSoon`, so it is unreferenced production code until then — noted for the next dead-code sweep (O6).
- ✅ **D13 — `RecordsSection` extracted from 08.0's block rather than duplicated.** **Rationale:** the exercise screen needs exactly 08.0's states (absent when empty, block-local notice, cached records kept on a failed refresh); a copy would diverge. The extraction is guarded by 08.0's own tests passing unmodified.

### Resolved by reading the code (corrections to the design brief)

- **`Spinner` is a full-viewport component** (`min-height: 100dvh`), so the exercise screen's in-place loading uses a small `role="status"` line instead (§5.3); the list screen, like History, may use `Spinner` as the whole screen.
- **`placeholderData` is dropped on error** (TanStack: placeholder exists only while `pending`), so "a failed new range keeps the previous range visible" needs the `lastShown` ref (D8) in addition to `keepPreviousData`.
- **`GET /v1/personal-records?exerciseId=` accepts any visible id and returns `200 []` for an unknown one** (07.0 §5; resolved to the lineage root), so the exercise screen's `NotFound` can come only from the series' `404` / `422` (AC23), never from the records query.
- **`PersonalRecordsBlock` owns its query** (`useWorkoutRecords`), so "reuse the block" is realised by extracting the presentational `RecordsSection` (D13) rather than importing the block as-is.
- **The CSS tripwire's `px` rule is `px` only** (non-0/1 flagged; hex and colour functions flagged): unitless `stroke-width: 2` and `opacity` pass; `rem`/`em` pass. SVG geometry numbers live in TS (coordinates, radii), not CSS, and are layout arithmetic rather than design values; colours, stroke weights and label sizes are CSS-only (AC26).
- **`style-src 'self'`** blocks inline style attributes and `<style>`; React's `style` prop is CSSOM and would be allowed, but the design forbids inline styles regardless (§7, AC26).
- **`workoutFake`'s records handler filters `exerciseId` by equality** — fine for tests that use lineage-root ids; the fake does not model fork resolution (covered server-side by 07.0).
- **`comingSoon` still has a registry field and a screen** (D12); the 04.1 AppShell test derives its expectation from `NAV_ITEMS`, so it passes unchanged.
