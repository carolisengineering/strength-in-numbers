# apps/web (`@sin/web`)

Web-side conventions, moved here from the root `CLAUDE.md` (which still holds the repo-wide rules). The routine-from-text reader and import rules are in `packages/core/CLAUDE.md`; the API side of each spec is in `apps/api/CLAUDE.md`.

## Conventions & gotchas

- **Web logout + user data** (Spec 06.0): `logoutAndClear()` (`apps/web/src/auth/logout.ts`) is the only place that calls Auth0 `logout` — a unit test fails if another source file builds `logoutParams`. Anything that persists per-user data in `localStorage` uses a `sin:<name>:` key prefix listed in `USER_DATA_KEY_PREFIXES` (`apps/web/src/storage/clearUserData.ts`) so logout clears it, and goes through the `StorageAdapter` in `apps/web/src/storage/storage.ts` — the Spec 04.0 AC7 source scan fails if any other non-test module names `localStorage` / `sessionStorage` (comments included). The delete confirmation's Sign out calls `logoutAndClear` via `useAuth0`, never `useSession` (that would restart a `useMe` fetch).
- **jsdom has no `<dialog>` `showModal()`/`close()`** — `apps/web/src/test/setup.ts` shims them (attribute toggle only). Real focus/Escape behavior needs a browser test.
- **Sheet action row** (Spec 17.10): `Sheet` draws one row under its scrolling body, as a sibling (never sticky): the danger slot, its own dismiss button (`dismissLabel`, default "Cancel"; it calls `onDismiss ?? onClose`, is `aria-disabled` and does nothing while `dismissible` is false (it keeps focus), and Close and Escape always call `onClose`), then the primary slot, with a `status` line and a `notice` (a save failure, kept in view) above them. A sheet fills it by rendering `SheetActions` (`primary`, `danger`, `status`, `notice`) wherever its state lives; it portals into the slots (`ui/sheetSlots.ts`) and throws outside a `Sheet`. The sheet's `<form>` keeps an id from `useId`, and the row's primary is `type="submit" form={id}`, so it is still the form's default button (Enter works in a browser; user-event can't see a button outside the form, so the harness checks Enter). Every sheet has the row and no sheet draws its own Cancel (a scan in `Sheet.actions.test.tsx` checks the Cancel copy constants are only `dismissLabel`s; Match for Hevy's in-card Cancels act on a card and are the listed exception). The picker's create view passes `onDismiss` (back to the list, search kept), and the load sheet's does mid-read (stop the reads, back to Choose a file). Tests reach the row and body by `data-sheet-actions` / `data-sheet-body` through `src/test/sheetHelpers.ts` (`sheetRow()`, `sheetBody()`); a test that finds two Cancels scopes to the dialog. The harness's `sheetRows` report fails the run on an open sheet with no row, a row off the frame's bottom, a body control under it, a short or clipped button, a failed Enter / focus check, or the picker's last row under its Cancel row. `ClockField` takes `hint={null}` and `describedBy` so a group says the clock hint once (`ResultSheet`'s `result-clock-hint`).
- **Routines UI** (Spec 10.0): routines live under the Workouts tab (`/app/workouts/routines/…`; the bare path redirects). The editor's draft is the pure, private `routineDraft` reducer — one `settle` pass keeps every superset a contiguous run of 2–8, and its `key`s never reach the server. Routine reads and writes are online-only with `networkMode: "always"` (no outbox, no stored draft); the start reuses `useBeginWorkout`, which keeps its key after success so a late tap replays it. Catalog sync drops retired exercises, so a routine item whose exercise is absent after a sync renders as "Removed exercise". `workout_started` carries `fromRoutine`. The item sheet has a quick line and a plan mode (Spec 10.2). Sections live in the draft (`DraftSection`, `sectionKey` on items); `settle` also keeps items in canonical section order and splits supersets at section boundaries (Spec 10.3).
- **Routines session side** (Spec 10.1): superset link / split / block-move rules live in `@sin/core` `supersets.ts` (the 10.0 editor delegates to them; `settle` stays on top). The session regroups with `planSessionChange` → a minimal ordered `PATCH /v1/workout-exercises/{id}` list (group patches first, position last; untouched groups keep their numbers; new runs take the smallest free 1–99), sent one at a time by `useRegroup` (online-only, no outbox, no Try again except a single-position move). Display: a bracket only on contiguous runs ≥ 2; "superset N" is the on-screen ordinal (`runOrdinals`), never the stored `supersetGroup`; both session screens go through `supersetRows`. `updateWorkoutExercise` has no `notes` parameter (Spec 09 D22). `workouts/` may import only `targetFormat`, `LinkToggle`, `SupersetBracket` (plus the existing `RoutinesSection`) from `routines/`. Response fields follow DESIGN §6's rollout convention (API one release first; no `.default(null)`).
- **Account lifecycle UI** (Spec 12): downloads go through `ApiClient.requestBlob` (token, 401 refresh, `ApiError`, `Retry-After`, filename from `Content-Disposition`) and `saveBlob` — never a bare `fetch` or an `<a href>` to the API; the export Blob is never parsed or stored. `useExportAccount` is called once in the Profile form and shared with the delete dialog. The delete result lives in the TanStack **mutation** cache (`["account","delete"]`, `gcTime: Infinity`) and `ProtectedLayout` renders `AccountDeletedConfirmation` instead of the app when it is set — so no provider can call `/v1` again; never `queryClient.clear()` there (it empties the mutation cache and reverts the gate). A `403 account-deleted` from any account call means 'done': invalidate `["me"]` and let the layout render `AccountDeleted` (the export awaits that refetch and stays quiet only if `meTookOver` — `me` itself 403s or 401s — else it shows its generic failure, BL-17); a `401` shows no notice (`onAuthLost` has started the logout). The grace days in copy come from `ACCOUNT_PURGE_GRACE_DAYS`; copy says 'at least', 'erase', never 'purge'. `ConfirmDialog` focuses Cancel explicitly; with `dismissible={false}` it ignores Escape and reopens itself on a native close (a second Escape), which the exercise Delete dialog sets while busy (Spec 12's delete keeps Escape working mid-request, AC18).
- **Planned sets UI** (Spec 10.2): the entry row is a draft, so the next planned set is *prefilled* into it, never stored — progress is positional (`exercise.sets.length` of the outbox-projected list picks `plannedSets[n]`; never `setNumber`, which is not dense), a planned field left null keeps today's copy-forward, the lifter's own weight and in-range reps stay where the plan holds still but never across a change of set type (Spec 17.4), and an edited draft is never overwritten by a re-seed (`seedDraft` in `setDraft.ts` is the one place a draft is built from the list; `EntryRow` re-seeds only an untouched draft when the count changes by any route but its own log). The routine editor's item is in quick mode (`plan: null`) or plan mode; the item sheet keeps its own state and commits once on Done (`setPlanned` + `setTargets`), the structural row operations are the pure functions in `planRows.ts`, and `toRoutineInput(draft, { modalityOf })` is the only place that picks the request form — exactly one of `sets` or the legacy quick-line keys, never `null`s beside `sets`, omitting fields the exercise's modality cannot carry. `targetLine(t, sets?)` shows the weight only when given the plan, and `supersetRows` passes each exercise's `plannedSets` on every screen (no per-screen option). The plan rows component is `PlanRowList.tsx` (a file named `PlanRows.tsx` would collide with `planRows.ts` on case-insensitive disks). Rolling 10.2 back and re-saving routines from the old editor flattens plans.
- **Routine sections UI** (Spec 10.3): `routineDraft` holds `sections` and a `sectionKey` per item; `settle` is the one place that keeps items loose-first / section-ordered and splits supersets at section boundaries, and `toRoutineInput` is the only place request keys (`s1…`) are minted — a section-free draft sends today's body. The session groups through `supersetRows` (runs break at section boundaries) then `sectionSegments`; a workout's section structure is seeded by the start copy, then the workout's own (Spec 09.4), and may hold a loose tail, so never compare `sectionId`s by hand. Session Move/link act on the card's segment (`planSessionChange` is fed the segment's slots; `useRegroup.run`'s `positionOffset` makes its position patches absolute). An exercise note is a `note` outbox op (`WorkoutClient.setExerciseNote`, coalescing, Finish waits for it); `WorkoutExercisePatch`/`useRegroup` still never carry `notes`.
- **Workout screen "now"** (Spec 17.1): one exercise is current (`chooseCurrent` / `advanceAfterLog` in `currentExercise.ts` are pure; `useCurrentExercise` holds only the lifter's choice, and `advanceFrom` never moves a lifter who already tapped elsewhere); collapsed rows come from `collapsedSummary`; the bottom `ActionBar` button (`LogBarButton`) is fed by the `logAction` store (published by the current `EntryRow`, which calls `onLogged` last and withdraws on unmount) and is the screen's one primary `Button`, one element across Log / Finish / Add modes, with the 600 ms double-tap window spanning a panel swap. Steppers (`stepper.ts`) step by the draft's weight unit (5 lb / 2.5 kg) in integer milli-units and dispatch the ordinary `edit` action, so they are edits like keystrokes. The component is `NumberStepper.tsx` (a `Stepper.tsx` would collide with `stepper.ts` on case-insensitive disks). **Entry panel** (Spec 17.8 Phase A): a stepper's label sits above one grid row (`data-stepper-row`, the harness's hook) of − input +, so the buttons are centered by structure; the buttons are `--stepper-size` (56 px) and show their step as text from `stepText` ("−5", U+2212, never a hyphen), with names from `stepName` ("−5 lb, decrease weight for X"); `NumberStepper` takes `decreaseText` / `increaseText`, and the result sheet's steppers use `RESULT_COPY.stepDown` / `stepUp`. The panel's label leads with the exercise's name (`aria-hidden`; the form's `aria-label` names it), then the set line, `setLabel` in its own span plus ` · target …` from `setTarget(row, modality)` (`plannedSets.ts`; only the measures the type can show). The rest readout is a figure with a "Rest" caption (`data-state` running / ready; "Ready" is a filled teal ground) inside an always-mounted `data-rest-slot`, so a rest never moves the steppers. End workout early and Finish share `confirmFinish`. Session tests reach controls through `src/test/sessionHelpers.ts` (`makeCurrent`, `logButton`, `optionsButton`, `finishButton`, `discardWorkout`). RPE is hidden, never stripped: the draft, `parseDraft`, DTOs and the export keep it, and a sheet that cannot show a value must not null it (`ItemSheet`, `SetEditSheet`). The rest timer (Phase C) is timestamp-based (`remainingSeconds(timer, now)` in `restTimer.ts`; `restAfterLog` decides start/clear and runs in `onLogged` before the advance guard), stored under `sin:workout:rest` by `restStore.ts` (zod-checked; 5 s future tolerance; the 900 s bound comes from `RoutineItemInputSchema`), ticked only by `useNow` in `SessionClock`, `RestReadout` and `RestLine`, cleared on finish, discard and gone beside the drafts, and has no sound, vibration or notification. The header's "Started …" label reads today from `useToday` (one re-render at local midnight and on becoming visible), which is not `useNow`; `useNow` keeps its three callers. The line's fill is a native `<progress>` (no inline style, CSP). **Logging fixes** (Spec 17.4): the workout bar has its own class and `data-session-bar` (`--bar-action-height`, `--session-bar-clearance`; every other `ActionBar` keeps 44 px), and its messages are one always-present `session-status` line above the button, joined with " · ", not `ActionBarHint`s, so a message never moves the button. After a log, `onLogged` asks for the current panel to be revealed, unless the lifter typed since the tap or moved elsewhere; the reveal waits until the screen holds the set count the log left, because the new row renders after `onLogged` runs, and then brings back whatever in the list has focus (never the bar's own button: scrolling to a sticky element drags the list). `EntryRow` re-seeds an untouched draft when the count or the last set's values change (`seedKeyOf`), so correcting a logged set can't leave its old value one tap from being logged again. The harness's logging-loop step logs four sets with `state.trackLogged` and fails the run on a covered control or a moved button; it clicks by coordinates, because `locator.click()` scrolls a sticky bar's list, and turns off `overflow-anchor`, because Chromium's scroll anchoring hides the drift. **Undo and Delete set** (Spec 17.5): Undo is a real delete through `useDeleteSet` (`viaUndo: true`), never a delayed send, so the outbox's cancel-or-delete rules apply offline and a crash can't lose a set. `useUndoLastLog` holds the offer in React state only; `undoOffer.ts` is the pure part (`offeredRow`, `undoPhase`, the copy, `statusLineText`). An offer shows once its row is listed and ends if the row leaves or its values change (`setValuesKey`), because the row renders after `onLogged` runs and swaps its client key for the server id when it syncs. The line says "undone" only when no op for the set is left in the queue. A restore reaches `EntryRow` as a one-shot `restore` prop and applies through the `restore` draft action (`draftForEdit`, a new attempt key, so a re-log isn't replayed as the undone set): after any re-seed, only once the row has left the list, and only if the draft is untouched. It stays a prefill, is never stored, and `seedDraft` doesn't change. The bar is `.statusRow` (the `<p data-session-status>` and Undo) then Log, so read Log as `:scope > button`; `.undo`'s margins keep its box at 44 px and 8 px from Log without moving the bar. A failed delete or create re-reads `/active` to bring its row back (a rejected create fails the delete queued behind it without naming it). A live region says nothing when its words don't change, so Undo clears the screen's region at the tap and a restore clears the panel's. Delete set asks first in both sheets (`useDeleteConfirm`; since Spec 17.10 the confirm is drawn in the sheet's row by `SetSheetActions`: Keep set where Delete set was, the confirm's Delete set where Save was, the question as the status line; tests tap through `deleteSetIn`), and has no undo. **Card declutter** (Spec 17.7 Phase B): the panel's Set options is a `WarmupToggle` ("Warm-up for X", `aria-pressed` exactly when the draft's type is warm-up, a tap is an ordinary `edit`; it doesn't stick past a log) and More ("More set options for X"; the block scrolls into view with `block: "nearest"`; it is open for one set, keyed by the draft's `attemptKey`, so a log closes it and the next panel fits above the bar at 320 × 568); `setLabel(plannedSets, count, draft.setType)` names the draft's type, not the plan's. On the live screen the superset toggles are only in the current card's Options (`ExerciseCard`'s `linkAbove` / `linkBelow`, built in `ActiveSession.renderRow`; `LinkToggle`'s `direction` gives "Superset with previous / next", named "Superset with next: {neighbor}" so the name starts with the text; without `direction` it is still "Superset {above} with {below}"; tests find a joint's toggle from either side with `linkToggle` / `linkToggleQuery`), and the joint keeps only the bracket. Add / Edit note is in Options on both screens; the header's note row renders only while the note is pending or failed (it keeps `failedRowRef`), and both carry `data-note-action`, which `markupOf` strips. The live card has no type line. Tests open Options through `showOptions(user, name?)` (`showLinks` for the toggles) and More through `openSetOptions`; the harness's `card and more` step (`cardDeclutter`) checks the header against `CARD_HEADER_BASE_390` and More's block against the bar.
- **Edit past workouts** (Spec 18.0): the edit screen is a sibling of `ActiveSession`, never a mode of it. Edit workout is the summary's Workout menu item above Delete workout (Spec 17.6 AC22); tests reach it through `openEditFromSummary` (`src/test/sessionHelpers.ts`). Edit writes are pessimistic and online-only on the plain REST client (`EditWorkoutClientContext`), keyed `["workouts","edit"]`, and the cached detail changes only from a response; every success runs `applyEditedCaches` (reset `["history","list"]`, invalidate `["progress"]` and `["records"]`). `409 workout-would-be-empty` opens "Delete this whole workout instead?" (no client pre-check). `EditKind` (the `workout_edit` enum) also carries Spec 10.6's `section_added`, `section_changed`, `section_removed`, `exercise_sectioned`. Edit mode never touches the outbox, drafts or rest store. The outbox's gone path calls `settle` (keeps unsent ops, drops failed ones of other workouts); while the oldest op belongs to another workout and is backing off, `drain` lets the live workout's oldest op go first (`OutboxDeps.activeWorkoutId`; each workout's own ops stay in order, nothing is failed for it); `409 workout-finished` handling is rollback-only. Change Time sends only changed groups (`startedAt` + the device offset at that instant, `durationSeconds`), is pre-validated with `resolveRetime`, and a live "took" makes Finish send `finishEndedAt(...)`; with a plan the live header shows "Took …" instead of the ticking clock. `changeTime.ts` is the one place the patch is built (device-zone `new Date(y, m-1, d, h, min)`, offset at that instant, only changed groups, Took checked only when changed) and `resolveRetime` / server `422`s map to `EDIT_COPY` by message; `useChangeTime` takes its client and cache key from the caller (so `changeTime/` never names `WORKOUT_KEYS.active`), and decides by the response's `endedAt` whether to run `applyEditedCaches`; the live header is two rows (clock or "Took …" + Workout menu; Started + Change Time via `WorkoutMenu`'s `below`); `workout_finished` carries `hadPlannedDuration`. Tests that build or format local times pin the zone with `pinTimeZone` / `inTimeZone` (`src/test/timeZone.ts`).
- **Finish & PR moments, Phase A** (Spec 17.2): both Finish dialogs and the summary header take duration, exercises, sets and volume from `finishStats.ts` (working sets only; volume is `sumVolumeMilli` from `@sin/core`; `workoutMinutes` is shared). The shared dialog body is `FinishDialogBody`; the stats list component is `FinishStatsList.tsx` (a `FinishStats.tsx` would collide with `finishStats.ts` on case-insensitive disks). The dialogs read "now" once when they open (`useMemo` keyed on the open flag). `finishLock` is not touched (Spec 18.0 Phase B changed only `confirmFinish`'s end time, `finishEndedAt`, and added `hadPlannedDuration` to `useFinishWorkout`; Spec 10.5 adds `keepRoutine` to `useFinishWorkout`'s variables and an optional `oneOff` prop to `FinishDialogBody`); Finish enabling and `workout_finished.setCount` still count every set. No animation or live region on the celebration. **Phase B, replaced by the record ledger (Spec 17.6 Phase A):** `PersonalRecordsBlock` (with a `section` prop) sits right after the date and renders `buildRecordLedger` (`recordLedger.ts`, pure: set volume filtered out, one lift per lineage root, a row per beaten record in `RECORD_TYPE_VALUES` order, a zero-gain est. 1-rep max dropped beside another row, one shared "from your …" line when every row came from one set, the heading counting lifts: "New records on 3 lifts" / "New record", "Records from this workout…" in History) through `RecordLedgerPanel.tsx` (a `RecordLedger.tsx` would collide with `recordLedger.ts` on case-insensitive disks) and `FirstTimeLines.tsx` (a first-ever number is a quiet line, not brass, not counted); long lists collapse after 4 to 3 (`collapsedCount`). `formatRecordPair` (`units/format.ts`) is the only record arithmetic in the web (old → new, gain, the spoken sentence); "Est. 1-rep max" is the one name for the estimate (`recordLabel`, `METRICS.est1rm.label`). Progress keeps `RecordsSection`. An est. 1RM is rounded for display only (`roundedE1rm`: 1 lb / 0.5 kg, integer step counts, gains from rounded values) wherever it shows (`formatRecordByType`, the chart readout); no PR math leaves `@sin/core`. History shows `recordCount` exactly as served (Spec 07.3 excludes set volume) as a trophy plus "N PRs"; the web never re-derives it.
- **Workout sections UI** (Spec 10.6): `features/workouts/sections/` is the one set of section controls (`useSectionActions` takes each screen's lock, banner, status line, refetch, gone path and offline text; `SectionDialogs` draws the sheet and the remove confirm from it; only `useSectionMutations` names the live client or `WORKOUT_KEYS.active`). The four writes are online-only (`networkMode: "always"`, `retry: false`, no outbox) and count in `structureBusy`; live success invalidates only `["workouts","active"]`. The client never sends a position — `setExerciseSection` sends exactly `{ sectionId }` and the server places and de-supersets it (`WorkoutExercisePatch` has no `sectionId`, `useRegroup` never writes it). `NewExercisesLine` is the only caller of `@sin/core` `sectionForNewExercise` and nothing else reads `addedInWorkout`. A section move remounts its card, so both screens reveal it through `useRevealMoved` (an effect on `segments`, armed only if the cache already shows the move, #157) with focus on its heading, never through `select` / `advanceFrom`. Edit appears only where a caller passes `onEdit` (never on the summary); the list end (the line, Add section, and Add exercise once there are exercises) is always drawn. All copy is `sectionCopy.ts`; failures go through `resolveSectionFailure` (a create is never retried blind: refetch first). The edit screen (Phase B) uses the same controls through `edit/useEditSectionMutations.ts`: the REST client, `EDIT_MUTATION_KEY` (so Done waits), create / update written into `["workouts","detail",id]` from the response, remove / move re-read the detail, `editSucceeded` on every success (`workout_edit` with `section_added` / `section_changed` / `section_removed` / `exercise_sectioned`), and the same `useRevealMoved`; no edit module imports `sections/useSectionMutations`. A write that patches a cached workout from its response goes through `readGuard.ts` (`guardReads` in `onMutate`, `rereadIfStale` in `onSettled`), and a structure re-read uses `rereadUntilLanded` (#154, #158).
- **Timed sections UI** (Spec 10.7): `features/sectionTimer/` is the neutral home of the clock field, `TimerFields` (file `TimerFieldGroup.tsx`; a `TimerFields.tsx` would collide with `timerFields.ts` on case-insensitive disks) and `TimerLine`. `routines/` and `workouts/` both import it, and it imports neither (a scan pins it). Every clock and score string is `@sin/core` `timer.ts` (through `TimerLine`), except the field's own digit display (`digitsToText`). The clock field holds digits only and fills from the right (`341` is 3:41); typing, Backspace and paste all go through `nextDigits`. All copy is `timerCopy.ts`, with bounds from `@sin/core`. The routine draft carries `timer`, and `toRoutineInput` emits it only when set (a For Time cap with no `capSeconds` key), so an untimed body is unchanged. A timed section's grouping only fills in (`timedGroupRange`: fill when nothing is grouped, join only to exactly one superset or one lone exercise, never rewrite two supersets), and only on the triggers of §6.4 (becoming timed or changing format; adding or moving into a timed section). It never happens in `settle`, on load, or on a plain edit. Timer equality is `@sin/core` `timersEqual`.
- **One-off routines UI** (Spec 10.5): `routines/oneOff.ts` (`isOneOff`, `oneOffDay(iso, { timeZone? })` in the device zone, `en-GB`, `timeZone` only for tests, `oneOffMeta`, `oneOffNote`) is the one place that decides 'is one-off', the expiry day and the list/preview wording; the copy lives in `routines/messages.ts` (list, preview) and `workouts/messages.ts` (`KEEP_IN_ROUTINES`, `oneOffFinishLine`). `sortRoutines` (`useRoutineMutations.ts`) mirrors the server's order (one-offs first, newest `createdAt` first, then lowercase name, then id) — change it together with Spec 09.3's SQL order. `oneOff: true` is added only in `routineClient.create(body, { oneOff })` (`useCreateRoutine` variables are `{ body, oneOff? }`); the import's create gets it through `RoutineEditor`'s `initial.oneOff` (`EditorStart.oneOff`), set only by `ImportEditRoute` — not inside `saveImport.ts`, which never calls the create; `toRoutineInput` never emits it and no `PUT` carries it, and a source scan (`routines/oneOff.scan.test.ts`) pins where `oneOff` and `keepRoutine` may appear. Keep is `RoutineClient.keep(id)` (body-less `POST`, no `Content-Type`) through `useKeepRoutine`, whose `onSuccess` patches list and detail with `oneOffUntil: null`, re-sorts, then invalidates `ROUTINE_KEYS.all` and `WORKOUT_KEYS.active` (so a live workout from that routine stops showing the Finish line); a `404` is not success (the preview says the routine no longer exists and the list is invalidated). The Finish dialogs take an optional `oneOff` prop on `FinishDialogBody` (`FinishOneOff { name, keep, onKeepChange }`) built in `ActiveSession` for both the Finish dialog and `EndEarlyDialog`; one `keepOneOff` state is reset to unchecked by `openFinish` / `openEndEarly` (all four openers use them), `confirmFinish` sends `keepRoutine: workout.routineIsOneOff && keepOneOff`, and `useFinishWorkout` puts `keepRoutine: true` on the wire only when true (`WorkoutClient.finish` body `{ endedAt; keepRoutine?: true }`), so `workouts/` imports nothing new from `routines/`. `applyFinishedCaches` (`records/cache.ts`) invalidates `ROUTINE_KEYS.all` on every finish, including the `409` recovery, because the flag cannot gate it; `applyDeletedCaches` is unchanged. The Keep confirmation is announced through a polite live region that holds only the confirmation, is empty from first paint and stays mounted across the Keep (no status role, so nothing is nested); a Retry notice stays up while its retry is in flight.
- **New exercise types UI** (Spec 18.1): `catalog/labels.ts` `MODALITY_LABELS` / `MODALITY_HINTS` are the one place for type text; the create form (`ExerciseFields`) offers all eight `MODALITY_VALUES`, with the chosen type's hint as the fieldset's `aria-describedby`. `DISPLAY_ORDER` is weight, distance, reps, durationS, calories. `unitDefaultsFor(pref, modality)` starts a carry (`weight_distance`) in meters whatever the profile says (`distance_duration` keeps km / mi); callers pass the modality (`EntryRow`, `SetEditSheet`, `EditSetForm`). The draft carries `calories` (a whole number, `SET_CALORIES_MAX`; stored drafts default it to `""` so an older file still loads); the calories stepper steps by 5 (`CALORIES_STEP`, no snapping). **Steppers for every measure** (Spec 17.8 Phase B): a duration steps its total by `DURATION_STEP_S` (5 s) and rewrites both fields (`stepDuration`), a distance by `DISTANCE_STEP` (m / ft 10, km / mi 0.1) in milli-units, bounded like `parseDraft` (the entered value and its meters, `distanceLimitMilli`); `NumberStepper.tsx` exports `StepperFrame` (the − / + row around any center, so a duration is the frame around Minutes and Seconds, wrapping at `--duration-field-min-width`), and `SetFields`' `StepperMeasures` is the one measures switch for the panel and the sheet (`nameCarryUnit` for the panel's carry label, `below` for the sheet's unit strips, drawn inside the Field in the unit line's place, #203). Both layouts take `exerciseName`; `TextField` selects on focus. `logLabel` groups weight and distance with `formatCount`. A logged row ends with a muted `PencilIcon` (`.setIcon`, `aria-hidden`). Distance units come only from `DISTANCE_UNIT_VALUES`; a carry's entry label names its unit ("Distance (ft)"). The new types' text separates measures with "·", never "×" ("24 kg · 40 m", "Log 20 · 1:30"); calories are grouped like other counts (`formatCount`, "1,200 cal"). **Phase B:** a record distance is meters for every account, even a carry typed in feet (`formatRecordValue` `m`: up to 3 decimals, so a gain never shows float noise); record and chart seconds read in words through `formatSeconds` ("1 min 30 s").
