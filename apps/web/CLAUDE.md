# apps/web (`@sin/web`)

Web-side conventions, moved here from the root `CLAUDE.md` (which still holds the repo-wide rules). The routine-from-text reader and import rules are in `packages/core/CLAUDE.md`; the API side of each spec is in `apps/api/CLAUDE.md`.

## Conventions & gotchas

- **Web logout + user data** (Spec 06.0): `logoutAndClear()` (`apps/web/src/auth/logout.ts`) is the only place that calls Auth0 `logout` — a unit test fails if another source file builds `logoutParams`. Anything that persists per-user data in `localStorage` uses a `sin:<name>:` key prefix listed in `USER_DATA_KEY_PREFIXES` (`apps/web/src/storage/clearUserData.ts`) so logout clears it, and goes through the `StorageAdapter` in `apps/web/src/storage/storage.ts` — the Spec 04.0 AC7 source scan fails if any other non-test module names `localStorage` / `sessionStorage` (comments included). The delete confirmation's Sign out calls `logoutAndClear` via `useAuth0`, never `useSession` (that would restart a `useMe` fetch).
- **jsdom has no `<dialog>` `showModal()`/`close()`** — `apps/web/src/test/setup.ts` shims them (attribute toggle only). Real focus/Escape behavior needs a browser test.
- **Routines UI** (Spec 10.0): routines live under the Workouts tab (`/app/workouts/routines/…`; the bare path redirects). The editor's draft is the pure, private `routineDraft` reducer — one `settle` pass keeps every superset a contiguous run of 2–8, and its `key`s never reach the server. Routine reads and writes are online-only with `networkMode: "always"` (no outbox, no stored draft); the start reuses `useBeginWorkout`, which keeps its key after success so a late tap replays it. Catalog sync drops retired exercises, so a routine item whose exercise is absent after a sync renders as "Removed exercise". `workout_started` carries `fromRoutine`. The item sheet has a quick line and a plan mode (Spec 10.2). Sections live in the draft (`DraftSection`, `sectionKey` on items); `settle` also keeps items in canonical section order and splits supersets at section boundaries (Spec 10.3).
- **Routines session side** (Spec 10.1): superset link / split / block-move rules live in `@sin/core` `supersets.ts` (the 10.0 editor delegates to them; `settle` stays on top). The session regroups with `planSessionChange` → a minimal ordered `PATCH /v1/workout-exercises/{id}` list (group patches first, position last; untouched groups keep their numbers; new runs take the smallest free 1–99), sent one at a time by `useRegroup` (online-only, no outbox, no Try again except a single-position move). Display: a bracket only on contiguous runs ≥ 2; "superset N" is the on-screen ordinal (`runOrdinals`), never the stored `supersetGroup`; both session screens go through `supersetRows`. `updateWorkoutExercise` has no `notes` parameter (Spec 09 D22). `workouts/` may import only `targetFormat`, `LinkToggle`, `SupersetBracket` (plus the existing `RoutinesSection`) from `routines/`. Response fields follow DESIGN §6's rollout convention (API one release first; no `.default(null)`).
- **Account lifecycle UI** (Spec 12): downloads go through `ApiClient.requestBlob` (token, 401 refresh, `ApiError`, `Retry-After`, filename from `Content-Disposition`) and `saveBlob` — never a bare `fetch` or an `<a href>` to the API; the export Blob is never parsed or stored. `useExportAccount` is called once in the Profile form and shared with the delete dialog. The delete result lives in the TanStack **mutation** cache (`["account","delete"]`, `gcTime: Infinity`) and `ProtectedLayout` renders `AccountDeletedConfirmation` instead of the app when it is set — so no provider can call `/v1` again; never `queryClient.clear()` there (it empties the mutation cache and reverts the gate). A `403 account-deleted` from any account call means 'done': invalidate `["me"]` and let the layout render `AccountDeleted` (the export awaits that refetch and stays quiet only if `meTookOver` — `me` itself 403s or 401s — else it shows its generic failure, BL-17); a `401` shows no notice (`onAuthLost` has started the logout). The grace days in copy come from `ACCOUNT_PURGE_GRACE_DAYS`; copy says 'at least', 'erase', never 'purge'. `ConfirmDialog` focuses Cancel explicitly; with `dismissible={false}` it ignores Escape and reopens itself on a native close (a second Escape), which the exercise Delete dialog sets while busy (Spec 12's delete keeps Escape working mid-request, AC18).
- **Planned sets UI** (Spec 10.2): the entry row is a draft, so the next planned set is *prefilled* into it, never stored — progress is positional (`exercise.sets.length` of the outbox-projected list picks `plannedSets[n]`; never `setNumber`, which is not dense), a planned field left null keeps today's copy-forward, and an edited draft is never overwritten by a re-seed (`seedDraft` in `setDraft.ts` is the one place a draft is built from the list; `EntryRow` re-seeds only an untouched draft when the count changes by any route but its own log). The routine editor's item is in quick mode (`plan: null`) or plan mode; the item sheet keeps its own state and commits once on Done (`setPlanned` + `setTargets`), the structural row operations are the pure functions in `planRows.ts`, and `toRoutineInput(draft, { modalityOf })` is the only place that picks the request form — exactly one of `sets` or the legacy quick-line keys, never `null`s beside `sets`, omitting fields the exercise's modality cannot carry. `targetLine(t, sets?)` shows the weight only when given the plan, and `supersetRows` passes each exercise's `plannedSets` on every screen (no per-screen option). The plan rows component is `PlanRowList.tsx` (a file named `PlanRows.tsx` would collide with `planRows.ts` on case-insensitive disks). Rolling 10.2 back and re-saving routines from the old editor flattens plans.
- **Routine sections UI** (Spec 10.3): `routineDraft` holds `sections` and a `sectionKey` per item; `settle` is the one place that keeps items loose-first / section-ordered and splits supersets at section boundaries, and `toRoutineInput` is the only place request keys (`s1…`) are minted — a section-free draft sends today's body. The session groups through `supersetRows` (runs break at section boundaries) then `sectionSegments`; a workout's section structure is seeded by the start copy, then the workout's own (Spec 09.4), and may hold a loose tail, so never compare `sectionId`s by hand. Session Move/link act on the card's segment (`planSessionChange` is fed the segment's slots; `useRegroup.run`'s `positionOffset` makes its position patches absolute). An exercise note is a `note` outbox op (`WorkoutClient.setExerciseNote`, coalescing, Finish waits for it); `WorkoutExercisePatch`/`useRegroup` still never carry `notes`.
- **Workout screen "now"** (Spec 17.1): one exercise is current (`chooseCurrent` / `advanceAfterLog` in `currentExercise.ts` are pure; `useCurrentExercise` holds only the lifter's choice, and `advanceFrom` never moves a lifter who already tapped elsewhere); collapsed rows come from `collapsedSummary`; the bottom `ActionBar` button (`LogBarButton`) is fed by the `logAction` store (published by the current `EntryRow`, which calls `onLogged` last and withdraws on unmount) and is the screen's one primary `Button`, one element across Log / Finish / Add modes, with the 600 ms double-tap window spanning a panel swap. Steppers (`stepper.ts`) step by the draft's weight unit (5 lb / 2.5 kg) in integer milli-units and dispatch the ordinary `edit` action, so they are edits like keystrokes. The component is `NumberStepper.tsx` (a `Stepper.tsx` would collide with `stepper.ts` on case-insensitive disks). End workout early and Finish share `confirmFinish`. Session tests reach controls through `src/test/sessionHelpers.ts` (`makeCurrent`, `logButton`, `optionsButton`, `finishButton`, `discardWorkout`). RPE is hidden, never stripped: the draft, `parseDraft`, DTOs and the export keep it, and a sheet that cannot show a value must not null it (`ItemSheet`, `SetEditSheet`). The rest timer (Phase C) is timestamp-based (`remainingSeconds(timer, now)` in `restTimer.ts`; `restAfterLog` decides start/clear and runs in `onLogged` before the advance guard), stored under `sin:workout:rest` by `restStore.ts` (zod-checked; 5 s future tolerance; the 900 s bound comes from `RoutineItemInputSchema`), ticked only by `useNow` in `SessionClock`, `RestReadout` and `RestLine`, cleared on finish, discard and gone beside the drafts, and has no sound, vibration or notification. The header's "Started …" label reads today from `useToday` (one re-render at local midnight and on becoming visible), which is not `useNow`; `useNow` keeps its three callers. The line's fill is a native `<progress>` (no inline style, CSP).
- **Edit past workouts** (Spec 18.0): the edit screen is a sibling of `ActiveSession`, never a mode of it. Edit writes are pessimistic and online-only on the plain REST client (`EditWorkoutClientContext`), keyed `["workouts","edit"]`, and the cached detail changes only from a response; every success runs `applyEditedCaches` (reset `["history","list"]`, invalidate `["progress"]` and `["records"]`). `409 workout-would-be-empty` opens "Delete this whole workout instead?" (no client pre-check). `EditKind` (the `workout_edit` enum) also carries Spec 10.6's `section_added`, `section_changed`, `section_removed`, `exercise_sectioned`. Edit mode never touches the outbox, drafts or rest store. The outbox's gone path calls `settle` (keeps unsent ops, drops failed ones of other workouts); while the oldest op belongs to another workout and is backing off, `drain` lets the live workout's oldest op go first (`OutboxDeps.activeWorkoutId`; each workout's own ops stay in order, nothing is failed for it); `409 workout-finished` handling is rollback-only. Change Time sends only changed groups (`startedAt` + the device offset at that instant, `durationSeconds`), is pre-validated with `resolveRetime`, and a live "took" makes Finish send `finishEndedAt(...)`; with a plan the live header shows "Took …" instead of the ticking clock. `changeTime.ts` is the one place the patch is built (device-zone `new Date(y, m-1, d, h, min)`, offset at that instant, only changed groups, Took checked only when changed) and `resolveRetime` / server `422`s map to `EDIT_COPY` by message; `useChangeTime` takes its client and cache key from the caller (so `changeTime/` never names `WORKOUT_KEYS.active`), and decides by the response's `endedAt` whether to run `applyEditedCaches`; the live header is two rows (clock or "Took …" + Workout menu; Started + Change Time via `WorkoutMenu`'s `below`); `workout_finished` carries `hadPlannedDuration`. Tests that build or format local times pin the zone with `pinTimeZone` / `inTimeZone` (`src/test/timeZone.ts`).
- **Finish & PR moments, Phase A** (Spec 17.2): both Finish dialogs and the summary header take duration, exercises, sets and volume from `finishStats.ts` (working sets only; volume is `sumVolumeMilli` from `@sin/core`; `workoutMinutes` is shared). The shared dialog body is `FinishDialogBody`; the stats list component is `FinishStatsList.tsx` (a `FinishStats.tsx` would collide with `finishStats.ts` on case-insensitive disks). The dialogs read "now" once when they open (`useMemo` keyed on the open flag). `finishLock` is not touched (Spec 18.0 Phase B changed only `confirmFinish`'s end time, `finishEndedAt`, and added `hadPlannedDuration` to `useFinishWorkout`; Spec 10.5 adds `keepRoutine` to `useFinishWorkout`'s variables and an optional `oneOff` prop to `FinishDialogBody`); Finish enabling and `workout_finished.setCount` still count every set. No animation or live region on the celebration. **Phase B:** the summary renders `RecordCards` from `recordCards.ts` (`buildRecordCards`: set-volume records filtered out, one card per lineage root, lead = heaviest weight, else est. 1RM, else max reps, a zero-gain e1RM demoted to a chip; `recordsNewCount` is the "N new" figure); the component file is `RecordCardList.tsx` (a `RecordCards.tsx` would collide with `recordCards.ts` on case-insensitive disks), and Progress keeps `RecordsSection`. An est. 1RM is rounded for display only (`roundedE1rm`: 1 lb / 0.5 kg, integer step counts, gains from rounded values) wherever it shows (`formatRecordByType`, the chart readout); no PR math leaves `@sin/core`. History shows `recordCount` exactly as served (Spec 07.3 excludes set volume) as a trophy plus "N PRs"; the web never re-derives it.
- **Workout sections UI** (Spec 10.6): `features/workouts/sections/` is the one set of section controls (`useSectionActions` takes each screen's lock, banner, status line, refetch, gone path and offline text; `SectionDialogs` draws the sheet and the remove confirm from it; only `useSectionMutations` names the live client or `WORKOUT_KEYS.active`). The four writes are online-only (`networkMode: "always"`, `retry: false`, no outbox) and count in `structureBusy`; live success invalidates only `["workouts","active"]`. The client never sends a position — `setExerciseSection` sends exactly `{ sectionId }` and the server places and de-supersets it (`WorkoutExercisePatch` has no `sectionId`, `useRegroup` never writes it). `NewExercisesLine` is the only caller of `@sin/core` `sectionForNewExercise` and nothing else reads `addedInWorkout`. A section move remounts its card, so both screens reveal it through `useRevealMoved` (an effect on `segments`, armed only if the cache already shows the move, #157) with focus on its heading, never through `select` / `advanceFrom`. Edit appears only where a caller passes `onEdit` (never on the summary); the list end (the line, Add section, and Add exercise once there are exercises) is always drawn. All copy is `sectionCopy.ts`; failures go through `resolveSectionFailure` (a create is never retried blind: refetch first). The edit screen (Phase B) uses the same controls through `edit/useEditSectionMutations.ts`: the REST client, `EDIT_MUTATION_KEY` (so Done waits), create / update written into `["workouts","detail",id]` from the response, remove / move re-read the detail, `editSucceeded` on every success (`workout_edit` with `section_added` / `section_changed` / `section_removed` / `exercise_sectioned`), and the same `useRevealMoved`; no edit module imports `sections/useSectionMutations`. A write that patches a cached workout from its response goes through `readGuard.ts` (`guardReads` in `onMutate`, `rereadIfStale` in `onSettled`), and a structure re-read uses `rereadUntilLanded` (#154, #158).
- **One-off routines UI** (Spec 10.5): `routines/oneOff.ts` (`isOneOff`, `oneOffDay(iso, { timeZone? })` in the device zone, `en-GB`, `timeZone` only for tests, `oneOffMeta`, `oneOffNote`) is the one place that decides 'is one-off', the expiry day and the list/preview wording; the copy lives in `routines/messages.ts` (list, preview) and `workouts/messages.ts` (`KEEP_IN_ROUTINES`, `oneOffFinishLine`). `sortRoutines` (`useRoutineMutations.ts`) mirrors the server's order (one-offs first, newest `createdAt` first, then lowercase name, then id) — change it together with Spec 09.3's SQL order. `oneOff: true` is added only in `routineClient.create(body, { oneOff })` (`useCreateRoutine` variables are `{ body, oneOff? }`); the import's create gets it through `RoutineEditor`'s `initial.oneOff` (`EditorStart.oneOff`), set only by `ImportEditRoute` — not inside `saveImport.ts`, which never calls the create; `toRoutineInput` never emits it and no `PUT` carries it, and a source scan (`routines/oneOff.scan.test.ts`) pins where `oneOff` and `keepRoutine` may appear. Keep is `RoutineClient.keep(id)` (body-less `POST`, no `Content-Type`) through `useKeepRoutine`, whose `onSuccess` patches list and detail with `oneOffUntil: null`, re-sorts, then invalidates `ROUTINE_KEYS.all` and `WORKOUT_KEYS.active` (so a live workout from that routine stops showing the Finish line); a `404` is not success (the preview says the routine no longer exists and the list is invalidated). The Finish dialogs take an optional `oneOff` prop on `FinishDialogBody` (`FinishOneOff { name, keep, onKeepChange }`) built in `ActiveSession` for both the Finish dialog and `EndEarlyDialog`; one `keepOneOff` state is reset to unchecked by `openFinish` / `openEndEarly` (all four openers use them), `confirmFinish` sends `keepRoutine: workout.routineIsOneOff && keepOneOff`, and `useFinishWorkout` puts `keepRoutine: true` on the wire only when true (`WorkoutClient.finish` body `{ endedAt; keepRoutine?: true }`), so `workouts/` imports nothing new from `routines/`. `applyFinishedCaches` (`records/cache.ts`) invalidates `ROUTINE_KEYS.all` on every finish, including the `409` recovery, because the flag cannot gate it; `applyDeletedCaches` is unchanged. The Keep confirmation is announced through a polite live region that holds only the confirmation, is empty from first paint and stays mounted across the Keep (no status role, so nothing is nested); a Retry notice stays up while its retry is in flight.
- **New exercise types UI** (Spec 18.1): `catalog/labels.ts` `MODALITY_LABELS` / `MODALITY_HINTS` are the one place for type text; the create form (`ExerciseFields`) offers all eight `MODALITY_VALUES`, with the chosen type's hint as the fieldset's `aria-describedby`. `DISPLAY_ORDER` is weight, distance, reps, durationS, calories. `unitDefaultsFor(pref, modality)` starts a carry (`weight_distance`) in meters whatever the profile says (`distance_duration` keeps km / mi); callers pass the modality (`EntryRow`, `SetEditSheet`, `EditSetForm`). The draft carries `calories` (a whole number, `SET_CALORIES_MAX`; stored drafts default it to `""` so an older file still loads); the calories stepper steps by 5 (`CALORIES_STEP`, no snapping). Distance units come only from `DISTANCE_UNIT_VALUES`; a carry's entry label names its unit ("Distance (ft)"). The new types' text separates measures with "·", never "×" ("24 kg · 40 m", "Log 20 · 1:30"); calories are grouped like other counts (`formatCount`, "1,200 cal"). **Phase B:** a record distance is meters for every account, even a carry typed in feet (`formatRecordValue` `m`: up to 3 decimals, so a gain never shows float noise); record and chart seconds read in words through `formatSeconds` ("1 min 30 s"). Progress charts add Calories, Distance and Time (`METRICS`); `pointsFor` converts to lb only for `kg` / `kg_reps` metrics, and `INTEGER_METRICS` (reps, calories, duration) get whole-number ticks. The importer passes the reader's `name.calories` into `guessModality` (`cards.ts`, both `handoff.ts` fallbacks), so "Max Cal Echo Bike" starts as Calories; a matched existing exercise keeps its own type.
- **Exercises tab** (Spec 18.2): the Progress tab is **Exercises**: `/app/exercises` (All exercises, the layout's index), `/app/exercises/records` (Records, today's Progress list; the static segment outranks `:id`), `/app/exercises/:id` (the exercise page, a sibling of the layout, keyed by id); `/app/progress` and `/app/progress/:exerciseId` are permanent `replace` redirects, and only `features/exercises/paths.ts` writes these paths (a scan allows `/app/progress` only in `router.tsx` comments). The usage query is `["exercises","usage"]` (`staleTime: 0`, `retry: false`, `networkMode: "always"`, memory only), and "logged" is `usage.has(lineageRootId(row))`. The list model is `buildExerciseRows` (logged by last-logged date desc, then A–Z with `nameCollator`, then id); search only narrows it (`searchByName`), and the list waits for usage so the order never jumps. The page resolves through `resolveExercise`: a store row is found at once (even before the first sync), a fork origin goes to its newest active fork by `replace`, and an unknown id is `deleted` only after a sync (its history still shows) and draws only once its series and records have answered, so a made-up id goes straight to Not found; a series `404` / `422` with no data is still `NotFound`. A never-logged page sends no series or records request (`useSeries` / `useExerciseRecords` take `enabled`). The Progress body is `ExerciseProgressBody` (`features/progress/`), and `features/progress/` never imports `features/exercises/`. File names keep components and pure modules apart on case-insensitive disks (`ExerciseScreen.tsx` / `resolveExercise.ts`, `ExerciseDetails.tsx` / `detailRows.ts`, `AllExercises.tsx` / `exerciseRows.ts`, `EditExerciseSheet.tsx` / `exerciseInput.ts`). **Phase B:** Edit, Make your own copy and Delete are online-only TanStack mutations (`useExerciseMutations.ts`: `networkMode: "always"`, `retry: false`, no outbox) over the catalog store's `updateCustom` / `forkExercise` / `deleteCustom` (the only module that calls `PATCH` / `DELETE` / `…/fork` on `/v1/exercises`, a scan pins it); every success runs `applyExerciseCaches` (`["records"]`, `["progress"]`; a delete drops its routines read). Errors key on status and slug through `classifyExerciseError`, never the server's text (a `422`'s field messages are the static `@sin/core` text, #57; the import's create uses the same classifier). The Edit sheet sends only changed fields (`toUpdateExerciseInput`; `{}` keeps Save disabled), its type radios are `canChangeModality` (all but the current one disabled while usage is unknown), and a `409 exercise-type-locked` resets only the type and re-reads usage. Make your own copy is a bodiless fork that navigates after `mutateAsync` (the fork's store merge redirects the built-in's page first) with `{ notice: "copied" }`, read from the location and cleared by a replace. The Delete dialog reads `GET /v1/exercises/{id}/routines` fresh on every opening (`gcTime: 0`) and keeps Delete disabled until it answers; the page keeps drawing the row it is deleting until it navigates (`replace`, `{ notice: "deleted", name }`), so the deleted variant never flashes. Telemetry is `custom_exercise_updated { typeChanged }`, `custom_exercise_forked`, `custom_exercise_deleted { routineCount }`, success only.
- **Hevy integration (UI)** (Spec 20.0): `features/hevy/`. The Hevy API key lives on the device only, in `keyStore.ts` (`sin:hevy:key:<userId>` = `{ v: 1, key }`; `sin:hevy:` is in `USER_DATA_KEY_PREFIXES`, so logout clears it; "Use for this visit only", or storage that refuses the write, keeps it in memory). `client/hevyClient.ts` is the only code that sends it, in the `api-key` header to `https://api.hevyapp.com` (a source scan pins both literals there); every reply is parsed with 19.0's `@sin/core` schemas (`HevyUserInfoSchema` keeps `username` and `is_pro`, which the key check reads), a `HevyError`'s `message` is static and has no `cause`, and only `GET`s are retried (429 / 5xx / network, 1-2-4 s, `Retry-After` honored) — a write never is. One shared pacer (`sharedClient.ts`) spaces every Hevy request 600 ms apart and skips the first minute of each UTC hour; tests make it and the retry waits instant through `setInstantPacing` (`src/test/hevyHarness.tsx`). The screen is gated by `GET /v1/hevy/status` (`HevyRoute`: spinner, then NotFound for anyone but the owner); Profile's row appears only on a `200`, and `src/test/msw/handlers.ts` answers that status `404` by default. `connect-src` names the Hevy origin in both `render.yaml` and `apps/web/firebase.json`, and both check scripts and the web smoke insist on exactly that set. The screens harness serves Hevy from its own route; its SIN route matches only the app's origin (Hevy's paths also start with `/v1/`). **Phase B (mapping and pairings):** a mapping file goes `parseMappingCsv` (which also returns each line's `lineNumbers`) → Hevy's template list (with the key) → `mapping/resolveLines.ts` (pure; never guesses: an ambiguous title or name is left out with its line) → the preview (paired, left out, rules to confirm, what the replace removes) → one `PUT` that replaces the whole mapping; Download refetches and writes 19.0's file with the effective section rules, so a round trip changes nothing. Every mapping write is pessimistic and online-only, and the cache changes only from the response. The Pairings screen (`/app/profile/hevy/pairings`) is single-pair `PATCH`es. The new-exercise name checks live in the neutral `catalog/newExerciseName.ts` (Spec 10.4's import uses them too), and nothing in `features/hevy/` imports `features/routines/` (a scan pins it) except `import/useImportSession.ts`, which may use `routines/queries` and `routines/useRoutineMutations` (Spec 20.1, owner ruling 2026-10-29). `pairing/` is 20.1's and 20.2's: `PairingCards` (file `PairingCardList.tsx`; `PairingCards.tsx` would collide with `pairingCards.ts` on case-insensitive disks) is controlled and never writes; `savePairings` is the only writer — creates one at a time, 4 s apart, a retry refreshing first and reusing what an earlier attempt made, then `PATCH` batches of 200 with `exportAs: false`. A skip stays until removed (O1). The section-marker sheet is mounted only while open, because it reads Hevy's template list. **Minors 166–193:** `HEVY_KEYS.status(userId)` / `user(userId)` are per user (`statusAll` / `userAll` for invalidation); the key store caches the parsed key and hears other tabs' `storage` events; `hevyTemplatesQuery(client)` (`mapping/useHevyTemplates.ts`) is the one template read (the hook and the load sheet's `fetchQuery`); its progress goes to `mapping/templatesProgress.ts` (`useTemplatesProgress`), which every reader watches, so one that joins a running read shows its page (minor 197); the key card re-checks the quiet minute at its boundary (`msUntilQuietChange`) in an always-mounted polite region, and a refused stored key stays named under its ending (minors 199, 203); `mappingErrorMessage(err, generic?)` is the one mapping-error sentence (a 429 says how long, through `ui/waitText.ts`); `useSavePairingsDeps()` is `savePairings`' deps (its patch writes the mapping cache; a refresh that leaves the catalog in error rejects); the mapping CSV escapes a formula-like text cell with one leading `'`, and the parse drops a leading `'` only before `=`, `+`, `-`, `@` or `'` (minor 196), so `'90s Press` loads as written. **Import (Spec 20.1):** the import session is in memory (resume = run it again; the server's links are the memory), batches are the server's idempotent unit, and finish is the only records step (`applyImportedCaches` after the run and after a successful finish); a finish goes with no body and no `Content-Type`, and `importLane.ts` keeps it from overlapping a batch (a real batch's request is never aborted; the run's waits go through `importWait.ts`, which `setInstantPacing` makes instant). The run reads its own results from a ref, never the reducer's copy, which lags a render behind the last batch. Every runner goes through `runSafely` (a throw is reported and lands on Stopped or Done, never a busy step), and once the run starts the route keeps the flow even if another tab removes the key. `ui/useLeaveGuard.ts` is the one leave guard (the import run and `RoutineEditor`). **Send to Hevy (Spec 20.2 Phase A):** `send/runSend.ts` is the one sequence — read and build (`buildHevyWorkout`), begin (the claim), the Hevy write, complete — with release only on a definite failure (a Hevy `400`, limit, refused key, `429`, or a `404` on a create; owner answer Q2) and no write ever retried by itself; only complete (a SIN call) retries, 1-2-4 s. After an ambiguous failure the claim is still fresh, so Check Hevy, Send anyway and Try again carry the begin's fingerprint (and Hevy id) instead of beginning again; such a follow-up whose reads fail, or that meets an unmatched exercise, keeps the claim and stays offered (D26). A `hevy-no-claim` after the Hevy write keeps the copy's id and offers `reclaim` (a new begin, then a `PUT` to that copy; D25). A link reading `sending` is re-read after `SENDING_RECHECK_MS` and on focus.
