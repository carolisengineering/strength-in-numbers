# apps/api (`@sin/api`)

API-side conventions, moved here from the root `CLAUDE.md` (which still holds the repo-wide rules). The web side of each spec is in `apps/web/CLAUDE.md`.

## Conventions & gotchas

- **Telemetry** (Spec 13.0): off unless `OTEL_*_EXPORTER` is set. Boot entry is `dist/main.js` (it starts telemetry before importing `server.js` — don't import Fastify from `telemetry/`). A new span attribute or metric attribute is exported only if added to `telemetry/allowlist.ts` / `telemetry/views.ts` with a test; never ids, paths, IPs, user agents or user input. Metric names in `METRIC_NAMES` are queried by `ops/grafana/` — rename both together. Business counters sit beside their log line (`workout_started`, `workout_finished`, `set_created`). Telemetry tests import the app dynamically *after* `startTestTelemetry()`.
- **Error contract** (RFC 9457 problem+json) must be registered on BOTH the root scope and the `/v1` child scope.
- **Finished-workout edits** (Spec 07.4 Phase A): set / workout-exercise writes and title/notes work on a finished workout. Every repository write runs inside `withWriteMode` (`apps/api/src/repositories/write-mode.ts`): the mode comes from the existing unlocked preflight; finished mode takes `lockUserRecords` FIRST, then the usual locks, then recomputes only the lineages the edit can affect (`@sin/core` `setChangeAffectsRecords`; a reorder only the moved card's root, and only if that lineage appears twice in the workout); a live write runs today's statements, and a finish landing mid-write restarts it once in finished mode (`assertStillLive`). `409 workout-finished` means only a re-finish; `409 workout-would-be-empty` guards the two deletes (any set type counts); a finished-mode working set must be complete (`422`); a finished-mode `completed_at` is `LEAST(GREATEST(now(), started_at), ended_at)` (NULL bounds in live mode). Write results carry `finishedEdit` for the `workout_edited` / `workout_edit_refused` log lines (Spec 09.4 adds the `edit` kinds `section_added`, `section_changed`, `section_removed`, `exercise_sectioned`). **Change Time (Phase B):** `PATCH /v1/workouts/{id}` takes `startedAt`, `tzOffsetMinutes` (only with `startedAt`) and `durationSeconds`; every time rule is `@sin/core` `resolveRetime` (the API wraps it as `retimeOrThrow`), and a `startedAt` equal to the stored one is no change. `local_date` / `tz_offset_minutes` are re-derived only when `startedAt` changes (`calendarFor`). A live workout's "took" is `planned_duration_s` (live-only CHECK; the finish clears it, and the client sends `endedAt = startedAt + plan`); a live Change Time never touches sets. A finished re-time shifts set times by Δ from the stored start (`shiftSetTimes`), any finished time change and every finish clamp them into `[started_at, ended_at]` (`clampSetTimes`), and only a start change recomputes records. Neither rewrites a set's `updated_at`. Migration `0012` is a manual release step before the code goes live.
- **OpenAPI publication is opt-in** (#10): a public `/v1` route needs `config: { published: true, problems: [...] }` to appear in `/openapi.json`; anything else is hidden by default. `schema: { hide: true }` is now only the infra routes' opt-out from the response-schema check. Never set `config.swaggerTransform` (app assembly fails — it bypasses the gate).
- **CORS methods**: `CORS_METHODS` (`apps/api/src/plugins/cors-methods.ts`) is the only list of cross-origin methods; app assembly fails if a route uses one that isn't in it (`HEAD` excepted). A missing method makes the browser refuse the request, which the SPA can only report as "offline" — the 2026-10-11 routine-edit `PUT` bug. `app.inject` tests skip the preflight, so they never catch this on their own.
- **`/v1` caching** (#17/#18): `Cache-Control` is set only by the `/v1` cache policy (`apps/api/src/plugins/cache-policy.ts`) — `no-store` by default and on every error; a `GET` that serves an `ETag` declares `config: { httpCache: "revalidate" }` → `private, no-cache`. Never hand-set `Cache-Control` in a `/v1` handler, and no `Vary: Authorization` (`private` is the cross-user protection).
- **Catalog seed** (`apps/api/prisma/seed.ts` → `src/seed/`) is a manual release step after `migrate deploy`, NOT Prisma's `prisma.seed` hook. Append-only: never edit a live row's `name`/`modality` in `prisma/catalog/exercises.json` — retire the key and add a new one.
- **`DATABASE_URL`**: `resolveDatabaseUrl` backfills `sslmode=require` + `sslaccept=strict` (server-cert + hostname verification) + `connection_limit=8` at runtime, and boot rejects libpq's `sslmode=verify-full` (Prisma silently downgrades it to `prefer`). The stored secret must carry `sslaccept=strict` itself because `prisma migrate deploy` reads the raw URL. For Neon, use the **direct** host (not `-pooler`) for `prisma migrate deploy`.
- **Fastify v5** wants `loggerInstance` (not `logger`) for a prebuilt pino; `buildApp` branches on the arg type.
- **Personal records** (Spec 07.0): `personal_record` is a rebuildable cache keyed on the exercise's lineage root (`COALESCE(forked_from_exercise_id, id)`). Every write goes through `recomputeRecordsForRoots` (finish, delete, `records:rebuild`), and every PR writer takes `lockUserRecords` (per-user advisory lock) as its FIRST statement, before any workout row lock — the recompute's INSERTs take FK `KEY SHARE` locks on other workouts' rows, so row-lock-first deadlocks (AC18). PR math lives only in `@sin/core` `records.ts` on integer milli-units; Spec 07.2's e1RM chart must reuse `estimate1rm`. Seven record types since Spec 05.3 (below).
- **Paginated lists** (Spec 07.1 §6.2): keyset, never offset; an opaque `v1.` cursor encoding the sort tuple with a unique tiebreaker; timestamps travel as Postgres-formatted UTC text with microseconds (`to_char(… AT TIME ZONE 'UTC', …US"Z"')`), never through a JS `Date`; a malformed cursor is a 422 on `cursor` before any query; `next: null` ends the list. Copy `apps/api/src/repositories/workout-cursor.ts`.
- **Rate limits** (Spec 05.2): every `/v1` write route declares `config: { writeGroup }` (app assembly fails without it); limits live only in `RATE_LIMITS` (`apps/api/src/plugins/rate-limit.ts`); a test that exceeds them passes `rateLimits: GENEROUS_LIMITS` / `limitsWith(...)` to `buildTestApp`. `config.skipRateLimit` is for the liveness/readiness probes only; `/openapi.json` is limited (L1 + its `ipBudget: "docs"` budget, AC17). The client address is `clientAddress()` — `CF-Connecting-IP` only when the socket is private/loopback (Render's own infrastructure), else the socket itself; Fastify has no `trustProxy` and `X-Forwarded-For` is never read. Never trust Cloudflare's IP ranges as proxies — WARP/Worker end users egress from them and could forge either header. Every request logs `client_ip`; re-run runbook D4.d after any hosting change. On Cloud Run, `CLIENT_IP_SOURCE=cloud-run` selects the Spec 15 rule (the right-most `X-Forwarded-For` entry, `CLOUD_RUN_XFF_HOPS` from the right, behind a non-public socket; `CF-Connecting-IP` never read); `render` (the default) is the Cloudflare rule — re-run D4.d (or Part F11 on Cloud Run) after any hosting change.
- **Routines** (Spec 09): routine writes are whole-document `PUT`s with unstable item ids; `supersetGroup` on a routine is normalised dense via `@sin/core` `normalizeSupersetGroups`, on a workout it is stored as sent (any 1–99, a group of one allowed). `targetRpe` converts to tenths in exactly one place (`rpeToTenths` / `tenthsToRpe`). Start-from-routine is `POST /v1/workouts { routineId }`: the copy runs inside the start transaction after the one-active insert, under `FOR SHARE` on the routine row, and snapshots the five targets, `supersetGroup` and the item's `notes` (D22); a replay never re-reads the routine. Migration `0009` is a manual release step before the code goes live (the new workout reads select `routine_name_snapshot`).
- **Planned sets** (Spec 09.1): `routine_item_set` rows are the source of truth; `routine_item.target_sets/target_reps_*` are derived by the server on every write (`resolveItemPlan` → `@sin/core` `deriveTargets`) — never assign them by hand. A routine item takes `sets` OR the legacy quick fields, never both (key presence, `null`s included); legacy input expands into identical working rows (`expandQuickLine`), and a rep range with no set count stays rowless (O1). `workout_planned_set` is an immutable snapshot written only by the start copy (`INSERT … SELECT` joined on `position`, under the routine's `FOR SHARE`); a replay never re-reads the routine. Migration `0010` is a manual release step before the code goes live; if an old-code routine `PUT` ran in the window, re-run the guarded backfill (runbook). Routine write routes have a 128 KiB `bodyLimit`; SQL-side inserts use `gen_random_uuid()` (Postgres 16 has no `uuidv7()`).
- **Account lifecycle** (Spec 11): `DELETE /v1/account` only sets `deleted_at` (every `/v1` call then 403s via `resolveUser`); data is removed only by `account:purge --confirm` after ≥ `ACCOUNT_PURGE_GRACE_DAYS` (`@sin/core`), which takes `lockUserRecords` first and keeps the grace check inside the `DELETE`. A new user-owned table must cascade from `user` — the purge test discovers tables from `pg_constraint` and fails otherwise. The export composes the read DTOs through `routes/mappers.ts`; when a read DTO gains a field the export gains it for free, so never hand-map in the export. `GET /v1/account/export` has its own per-user budget (`config.userBudget: "export"`, `RATE_LIMITS.exportPerUser`).
- **Routine sections** (Spec 09.2): `routine_section` rows are written only by a routine `PUT`/`POST` (the body is the whole document: `sections` with request-local `key`s, items reference them by `sectionKey`; no `sections` key means none; keys are never stored); the server rejects an item list that is not loose-first with each section one contiguous run, and a superset spanning sections (`@sin/core` `sections.ts`, shared with the editor). `workout.routine_notes_snapshot` is an immutable snapshot written only by the start copy (`INSERT … SELECT` under the routine's `FOR SHARE`, exercises matched to sections on section `position`); `workout_section` is seeded by that copy and is then the workout's own: `POST /v1/workouts/{id}/sections`, `PATCH`/`DELETE /v1/workout-sections/{id}` (live or finished, `withWriteMode`), `sectionId` on `PATCH /v1/workout-exercises/{id}`; a replay never re-reads the routine. The workout side is stored as sent (an added exercise is loose and lands at the requested position or the end, and reorders ignore section boundaries) — consumers must tolerate non-contiguous lists. Migration `0011` is a manual release step before the code goes live. The export's workout statements are hand-written: add new workout columns there too.
- **Workout sections** (Spec 09.4): `workout_section.added_in_workout` is the origin (copied = false); a plain `POST …/exercises` (no `position`) joins the last section iff it is added (`@sin/core` `sectionForNewExercise`), placed by `insertIndexForSection` (after the section's own run, before a loose tail); `PATCH sectionId` is the only way to change an exercise's section — the server places it (never combined with `position`), drops it from its superset, and records recompute only through the existing reorder rule; a section remove loosens its exercises and renumbers the rest one row at a time (the position index is not deferrable). Migration `0014` is a manual release step before the code. Every structure write (section and exercise add / move / remove) takes `lockWorkoutStructure` (`workout-section.prisma.ts`) in its transaction; the two adds run the shared `workoutPreflight` on the root client first; a section move positions from the ranks it read, with no extra `count(*)`.
- **One-off routines** (Spec 09.3): `routine.one_off_until` is both the mark and the expiry (NULL = ordinary); only `POST /v1/routines` can set it (`oneOff: true`; `PUT` rejects the key), only Keep or a finish with `keepRoutine: true` clears it, nothing extends it. `GET /v1/routines` serves one-offs first, newest created first, then by `lower(name)`, `id`. A finish of a workout from a one-off deletes the routine inside the finish transaction **after** the recompute; the lock order is PR lock → one-off routine row → workout row (the routine `DELETE` route holds routine → workout through the FK's `SET NULL`, so workout → routine would deadlock); a re-finish is `409` and takes no routine lock. Expiry is lazy: `GET /v1/routines` and `POST /v1/routines` sweep (`FOR UPDATE SKIP LOCKED`, then a second statement re-checks 'no live workout'); never sweep from `PUT`/`DELETE`/start/finish. The sweep and the finish's routine statements all live in `apps/api/src/repositories/routine-one-off.prisma.ts` (one module holds every guarded statement). `RoutineRepository.list` / `create` return the committed sweep's count (`{ routines, swept }` / `{ routine, swept }`), which the route logs as `routine_one_offs_expired`; a create that throws returns nothing, its sweep rolled back. The detail's and export's one-off mark is `routineIsOneOffSql("w" | '"workout"')`. The API fakes compose: each `FakeWorkoutRepository` adds a live-routine provider to the `FakeRoutineRepository`; the web fake sweeps only with `sweepExpired: true` (10.5's tests model a device clock ahead of the server's). Keep is `POST /v1/routines/{id}/keep` (`204`, no body, never checks the cap). The finish result carries `oneOff: "removed" | "kept" | "none"`, logged as `one_off_removed` / `one_off_kept` on `workout_finished`. The client side is Spec 10.5 (`apps/web/CLAUDE.md`). Migration `0013` is a manual release step before the code.
- **Advisory-lock keys**: 03.2's custom-exercise cap locks `hashtext(user_id)`, Spec 09's routine cap locks `hashtext('routine:' || user_id)`, the PR engine uses `lockUserRecords`. Never reuse a key across caps. The whole-schema `prisma migrate diff` no-drift check lives in the newest migration's integration test (`hevy-migration` for `0016`); move it when adding `0017`. Routine sections (09.2) add no lock key: the 8-section cap is a schema/DB limit on a whole-document write that already holds the routine row lock. One-off routines (09.3) add no lock key. Workout sections (09.4) add no lock key (the per-workout structure lock serializes them). Exercise management (03.4) adds no lock key: the type rule is a `NOT EXISTS` on the guarded `UPDATE`. The Hevy integration (19.0) adds no lock key: mapping writes lock the `user` row, a link begin locks the `workout` row.
- **New exercise types** (Spec 05.3): `@sin/core` `MEASURE_RULES` (`dto/set-entry.ts`) is the one rule table for the eight modalities; every validator, the finish check and the routine plan rules derive from it. `calories` is a whole-number `set_entry.calories SMALLINT` (`SET_CALORIES_MAX`, no unit, plumbed through the same statements as `duration_s`); every legacy modality forbids it. `personal_record.value` / `previous_value` are `NUMERIC(14,3)`. The `0002` / `0005` / `0006` / `0008` drift guards are frozen to their legacy lists; the live lists are guarded against `0015` (`new-modalities-migration-drift-guard.test.ts`, each `IN (...)` on one line). `ft` is a fourth distance unit (`FT_TO_M = 0.3048`); `0015` rebuilt the generated `distance_m` with every unit named and no catch-all, so a future unit widens the CHECK and the expression together (the `0015` guard fails otherwise). The web side is Spec 18.1 (`apps/web/CLAUDE.md`). Migration `0015` is a manual release step before the code (runbook). **Phase B:** records follow §6.2 of the spec: `heaviest_weight` is gated by `HEAVIEST_LOAD` (so it also fills for the two weighted types), e1RM and set volume stay on `LOAD_MODALITIES` (rep-load only), and `max_calories` / `max_distance` / `max_duration` each read one measure of one modality. `toRecordSet` (`personal-record.prisma.ts`) is the one loader-row mapping for the recompute and the progress series. `setChangeAffectsRecords` is modality-aware through `RECORD_MEASURES_BY_MODALITY`, so a legacy `distance_duration` / `duration` edit still recomputes nothing. The reader marks a name `calories` (`ReadName.calories`) from `Max Cal …` or a leading `20 Cal Row`; `guessModality(name, hint?)` takes it. Run `records:rebuild` after deploying Phase B.
- **Exercise management** (Spec 03.4): `@sin/core` `modality-change.ts` is the type-change rule (`modalitiesCompatible`: same required and forbidden measures, so `weight_reps` ↔ `weighted_bodyweight` is the only cross-type pair; `compatibleModalities`, `canChangeModality`, `lineageRootId`). Once the exercise's lineage (the root plus the caller's forks of it, retired included) has any of the caller's `set_entry` rows, `PATCH` and the `/fork` overlay refuse an incompatible type with `409 exercise-type-locked`. The probe is one SQL fragment, `lineageHasSetsSql` (`exercise.prisma.ts`), user-scoped through `workout.user_id`; on `PATCH` it is a `NOT EXISTS` on the same guarded `UPDATE` (a zero-row result rechecks: retired, locked, or once more), on fork a read before the capped insert. A same-type or compatible change never reads sets. `updateExercise` returns `{ exercise, modalityChanged }`; the refusal logs `custom_exercise_type_change_refused` (enum values only). A type change touches only the `exercise` row: no recompute, no lock. A delete that lands during the type-change retry answers `409 exercise-retired`, and a set logged during it `409 exercise-type-locked` (the miss rechecks the lineage again, minor 224); only a still-active second miss with no sets is `InternalError`. **Phase B reads:** `GET /v1/exercises/{id}/routines` (the delete warning) is exact-id (never the lineage), owner-scoped, `no-store`, answers for a retired own exercise, and never sweeps one-offs; `GET /v1/exercises/usage` returns the latest `local_date` per **lineage root** (`rootId` is the built-in for a fork; the client maps rows with `lineageRootId`), counts any set (warm-ups, incomplete, live) like the type lock, and revalidates with an `ETag`. A delete still changes only the exercise row (pinned in `exercise-delete-pins.integration.test.ts`).
- **Hevy integration** (Spec 19.0): owner-only. `HEVY_ENABLED_USER_IDS` (config, a frozen `Set`; unset = nobody) gates every Hevy route through an `onRequest` hook in its own child of the `/v1` scope (`routes/hevy.ts`): after auth (a deleted account still gets `403`), before the write-group `preParsing` and body parsing, so anyone else gets the unknown-route `404`, never a `413`/`400`/`422`/`429`. No Hevy route is published; writes use `writeGroup: "hevy"` (60/min). The pure core is `@sin/core` `hevy/` (vocabulary, Hevy API schemas, pairing, set translation, sections, `buildHevyWorkout`, `hevyFingerprintSource`, the mapping CSV); `readHevyType` reads Hevy's real type names (`bodyweight_weighted` / `bodyweight_assisted`) as the vocabulary's, and an unsupported type is `null`, which only a skip pair may store (`hevy_type` is NULL only there). Tables (`0016`, a manual release step before the code): `hevy_exercise_pair` and `hevy_section_rule` (written only by `PUT` / `PATCH /v1/hevy/mapping`, under the user row lock; a patch settles each exercise's one `exportAs` by clearing before setting, since the partial unique index is checked row by row), `hevy_link` (begin / complete / release on `/v1/workouts/{id}/hevy-link`; `deleteWorkout` deletes a claim-only row and leaves a linked one as a tombstone with `workout_id = NULL`), `hevy_account` (`records_stale`, written by 19.1). The "changed since sent" fingerprint is server-only: `v1:` + SHA-256 of `hevyFingerprintSource` over `toWorkoutDetailDto` (`apps/api/src/hevy/fingerprint.ts`), read in the begin transaction through `readWorkoutDetail`. The Hevy key never reaches the server (no route takes it; bodies are strict). The account export carries a `hevy` block through the shared mappers (`toHevyPairDto`, `toHevySectionRuleDto`, `toHevyExportLinkDto`). Logs carry `user_id` and counts only. **Import translation (Spec 19.1 Phase A):** pure `@sin/core` — `translateHevyWorkout` (one function serves the dry run and the write; precedence `time_invalid` → `unpaired` → `no_usable_sets`; every drop and notice is a `{ code, count }` over the fixed lists in `dto/hevy-import.ts`), `isDuplicateWorkout`, `translateHevyRoutine` (always a `RoutineWriteSchema`-valid `sets`-form body or `unpaired` / `no_items`; supersets never span a section), `exerciseFromHevyTemplate`. No `Intl` there: cuts go through `cutCodePoints`; the section walk and pair checks are the internal `hevy/importShared.ts`. **Import endpoints (Phase B):** `POST /v1/hevy/import/workouts` (≤ 25 per batch, `dryRun`, `HEVY_IMPORT_BODY_LIMIT` 512 KiB) and `POST /v1/hevy/import/finish` sit inside 19.0's gated scope (`registerHevyImportRoutes`); every statement is `hevy-import.prisma.ts`. Per workout, in order: link lookup → `translateHevyWorkout` → duplicate candidates → (dry run stops) → one transaction (workout, sections, exercises, sets, the `imported` link with the stored workout's fingerprint, `hevy_account.records_stale = true`). A dry run answers what the real run would (an in-request `decided` map and `claimed` set, and the same pure `importableProblem` re-check); that re-check before the write, the usable-exercise check (`FOR SHARE` on the exercise rows, so a retire either lands first or waits) and Postgres `23503` / `23514` / `22003` answer `rejected`. A raw query's SQLSTATE is read only through `rawSqlState` (`pg-errors.ts`). `hevy_import_batch` is logged from a `finally` with the totals so far and `partial: true` when the batch threw. The importer never recomputes records or takes `lockUserRecords`: the flag and `finish` do (`lockUserRecords` FIRST, then the `hevy_account` row), and `rebuildUserRecords` (`records/rebuild.ts`) is the per-user rebuild `records:rebuild` shares. Runbook: `docs/runbooks/hevy-import.md`.
